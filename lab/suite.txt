# suite.txt lists every lab check with the class that decides how it may be scheduled.
# tools/labhost reads it for `labhost run all`.
#
# Format, one job per line:  <class> <default> <scenario> [args...]
#
#   class    parallel         may run beside any number of other parallel jobs, each in its own
#                             sandbox. Nothing it touches is shared outside its own namespaces
#                             and its own workdir.
#            exclusive-heavy  runs alone in the Lab Host VM: the value it asserts on, or the value
#                             a person reads from it, is a measurement of memory or of achieved
#                             rate, and a neighbour is one confounder too many.
#            exclusive-timing runs alone in the Lab Host VM: it asserts on what does or does not
#                             happen inside a wall-clock window, without first waiting for the
#                             state that window observes to have converged, so a neighbour's or a
#                             prior step's leftover activity can bleed into the window (see
#                             docs/testing.md's rule against wall-clock-only wait windows, which a
#                             check restructured to converge first can usually leave). No check
#                             needs this class today; the class exists so that a check whose
#                             negative claim genuinely cannot be made to wait for convergence
#                             first has a home.
#            exclusive-global runs alone in the Lab Host VM: it changes a value a network namespace
#                             does not isolate, such as net.netfilter.nf_conntrack_max,
#                             net.core.rmem_max or the conntrack hash size. lifecycle.sh's
#                             check 12 is the one check in this class today.
#   default  yes              part of `labhost run all`
#            no               run it by naming it (it needs something the Lab Host cannot always
#                             provide, e.g. release binaries fetched from the network, or it is a
#                             long check that docs/testing.md runs at a phase or a release
#                             candidate instead)
#
# The set of jobs with default=yes covers exactly what the per-test suite covers: both modes of
# e2e, ipv6, rates, lifecycle and usage, plus split-merge, import-export and connlimit in the one
# mode each of them has, and exhaustion's checks in the modes they apply to. lifecycle is listed
# per check, so a check can have its own class.
#
# The check 5 family floods thousands of connections and datagrams. 5, 5b and 5e read RSS under that
# load and run alone. 5c and 5d assert on an admission decision instead, and 20 repetitions of each
# in a pool of eight sandboxes, overlapping each other, passed with identical held counts, so they
# run in the pool. 5f and 5g also assert on admission decisions, with exact held counts, but have not
# been repeated in the pool, so they run alone.
#
# Order: `labhost run all` hands the parallel jobs to its pool in the order of this file, and runs
# the exclusive jobs one at a time, in the order of this file, once the pool is empty. The parallel
# jobs are therefore listed longest first, so that the jobs that take minutes start at once and
# the short ones fill the pool around them; listed in any other order, one of the long jobs can
# start last, and the pool then waits for it alone. A new parallel job goes where its running time
# puts it. Where the exclusive jobs are listed does not change when they run; they come last.
#
# agentkernel.sh runs the kernel-mode agent's checks (design section 7b) against the given server
# mode, taking the checks to run as a space-separated list of its own. Its default list of checks
# takes over 10 minutes end to end, past labhost's default per-job timeout, so it is split here
# into groups instead of the one-job-per-check granularity lifecycle.sh uses: each job starts its
# own server and agent before its first check, and a group pays for that once. Within a group the
# checks run in the given order. teardown removes the agent's WireGuard interface, table and
# records that the group's earlier checks depend on, so it must be a group's last check; 22 leaves
# rules that resolve then removes, so a group must not run both (this file avoids that by keeping
# them in different groups). resolve is a job of its own: it waits on the agent's 30-second check
# again and again, which makes it one of the longest checks, and a group that runs other checks
# after it becomes the longest job of the suite, the one the pool ends up waiting for. 24, 17, 18
# and 19 are a group without it, and so run right after the setup, before resolve, as they do in
# the script's own default list. reconnect and stale only apply with a kernel-mode server and print
# SKIP with a userspace-mode one; they are still registered for both modes, the same as this file
# already does for lifecycle.sh's mode-specific checks. Every group runs well inside labhost's
# per-job timeout. See docs/testing.md for L16.
#
# agentdoctor.sh runs `wgft agent doctor` against a kernel-mode agent (design section 10.2c), with
# the server in the given mode, one job per mode, the same granularity as e2e.sh and ipv6.sh.
#
# lifecycle.sh's check 9c asserts that nothing is applied during a 35 s window with nothing
# changed. It used to wait only for forwarding to come back after the preceding flush/delete, not
# for their own "applied"/drift log lines to actually land, so a neighbour's load could delay one
# of those lines into the window and read as an unexplained apply (17 of 20 in a pool of 8, 18 of
# 20 in the whole suite, always alone 20 of 20). Restructured to wait for both prior repairs' own
# log lines before taking the window's baseline (docs/testing.md); measured again at 20 of 20
# alone, 20 of 20 in a pool of 8 beside the rest of this file's parallel jobs, so it now runs in
# the pool.
#
# connlimit.sh opens 160 to 320 concurrent flows, but what it asserts on is a kernel-side
# per-source cap: three rounds beside 0, 4 and 8 sandboxes gave byte-identical counts and the
# same 12 PASS lines, so it belongs in the pool.
#
# lifecycle.sh check 12 sets net.core.rmem_max and net.core.wmem_max, which are one value for the
# whole VM, and writes /etc/sysctl.d/90-wgft.conf, so it runs alone and restores both at its end.
#
# exhaustion.sh drives the userspace dataplane's retained resources with external input (see its
# header). postclose, acceptq, ackflood and wgstall assert on, or print for a person to read, a live
# heap, an RSS, a round-trip time or an achieved connection rate under a flood, so they run alone.
# postclose is the longest job of the file, a little over three minutes: its load runs until the
# second eviction log line, a minute after the table fills, and its drain is a 60 s TIME_WAIT. It
# runs by default in userspace mode only; the kernel-mode run exercises the same table on the
# agent's listening side and is run by name at a phase or a release candidate (docs/testing.md
# L19), to keep the suite's wall time down. mss asserts only on a handshake
# being dropped and on transfers completing, and touches only its own namespaces, so it runs in the
# pool. acceptq and ackflood need a kernel-mode server in front of the agent and wgstall a userspace
# one; they are listed for that mode only, rather than registered for both modes to print SKIP.
#
# usage.sh puts the ordinary kinds of traffic through a rule (HTTP, keystrokes, game-like UDP, bulk)
# and asserts only that they arrive whole; the round-trip times and rates it prints are not
# assertions, so it runs in the pool.
#
# version-skew.sh needs the v0.3.0, v1.1.3 and immediately-previous release binaries (v1.4.0 is
# OLD_VERSION's default as of this revision; see the script's own header comment). A lab VM on a
# host without outbound IPv4 cannot fetch them (GitHub has no IPv6), so they have to be staged
# into the VM first, and the check is opt-in for that reason, exactly as it is in the per-VM suite
# today.
