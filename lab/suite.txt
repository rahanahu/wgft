# suite.txt lists every lab check with the class that decides how it may be scheduled.
# tools/labhost reads it for `labhost run all`.
#
# Format, one job per line:  <class> <default> <scenario> [args...]
#
#   class    parallel         may run beside any number of other parallel jobs, each in its own
#                             sandbox. Nothing it touches is shared outside its own namespaces
#                             and its own workdir.
#            exclusive-heavy  runs alone in the Lab Host VM: the value it asserts on, or the value
#                             a person reads from it, is a measurement of memory or of achieved
#                             rate, and a neighbour is one confounder too many.
#            exclusive-timing runs alone in the Lab Host VM: it asserts on what does or does not
#                             happen inside a wall-clock window, without first waiting for the
#                             state that window observes to have converged, so a neighbour's or a
#                             prior step's leftover activity can bleed into the window (see
#                             docs/testing.md's rule against wall-clock-only wait windows, which a
#                             check restructured to converge first can usually leave). No check
#                             needs this class today; the class exists so that a check whose
#                             negative claim genuinely cannot be made to wait for convergence
#                             first has a home.
#            exclusive-global runs alone in the Lab Host VM: it changes a value a network namespace
#                             does not isolate, such as net.netfilter.nf_conntrack_max or the
#                             conntrack hash size. No check needs this class today; the class
#                             exists so that a check that starts changing such a value has a home.
#   default  yes              part of `labhost run all`
#            no               run it by naming it (it needs something the Lab Host cannot always
#                             provide, e.g. release binaries fetched from the network)
#
# The set of jobs with default=yes covers exactly what the per-test suite covers: both modes of
# e2e, ipv6, rates and lifecycle, plus split-merge, import-export and connlimit in the one mode
# each of them has. lifecycle is listed per check, so a check can have its own class.
#
# The check 5 family floods thousands of connections and datagrams. 5, 5b and 5e read RSS under that
# load and run alone. 5c and 5d assert on an admission decision instead, and 20 repetitions of each
# in a pool of eight sandboxes, overlapping each other, passed with identical held counts, so they
# run in the pool.

# check 9c asserts that nothing is applied during a 35 s window with nothing changed. It used to
# wait only for forwarding to come back after the preceding flush/delete, not for their own
# "applied"/drift log lines to actually land, so a neighbour's load could delay one of those
# lines into the window and read as an unexplained apply (17 of 20 in a pool of 8, 18 of 20 in
# the whole suite, always alone 20 of 20). Restructured to wait for both prior repairs' own log
# lines before taking the window's baseline (docs/testing.md); measured again at 20 of 20 alone,
# 20 of 20 in a pool of 8 beside the rest of this file's parallel jobs, so it now runs in the pool.
parallel         yes  lifecycle.sh kernel 9

# connlimit.sh opens 160 to 320 concurrent flows, but what it asserts on is a kernel-side
# per-source cap: three rounds beside 0, 4 and 8 sandboxes gave byte-identical counts and the
# same 12 PASS lines, so it belongs in the pool.
parallel         yes  connlimit.sh

# version-skew.sh needs the v0.3.0 and v0.4.0 release binaries. A lab VM on a host without
# outbound IPv4 cannot fetch them (GitHub has no IPv6), so they have to be staged into the VM
# first, and the check is opt-in for that reason, exactly as it is in the per-VM suite today.
parallel         no   version-skew.sh
