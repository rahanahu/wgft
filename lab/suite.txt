# suite.txt lists every lab check with the class that decides how it may be scheduled.
# tools/labhost reads it for `labhost run all`.
#
# Format, one job per line:  <class> <default> <scenario> [args...]
#
#   class    parallel         may run beside any number of other parallel jobs, each in its own
#                             sandbox. Nothing it touches is shared outside its own namespaces
#                             and its own workdir.
#            exclusive-heavy  runs alone in the Lab Host VM: the value it asserts on, or the value
#                             a person reads from it, is a measurement of memory or of achieved
#                             rate, and a neighbour is one confounder too many.
#            exclusive-timing runs alone in the Lab Host VM: it asserts on what does or does not
#                             happen inside a wall-clock window, without first waiting for the
#                             state that window observes to have converged, so a neighbour's or a
#                             prior step's leftover activity can bleed into the window (see
#                             docs/testing.md's rule against wall-clock-only wait windows, which a
#                             check restructured to converge first can usually leave). No check
#                             needs this class today; the class exists so that a check whose
#                             negative claim genuinely cannot be made to wait for convergence
#                             first has a home.
#            exclusive-global runs alone in the Lab Host VM: it changes a value a network namespace
#                             does not isolate, such as net.netfilter.nf_conntrack_max or the
#                             conntrack hash size. No check needs this class today; the class
#                             exists so that a check that starts changing such a value has a home.
#   default  yes              part of `labhost run all`
#            no               run it by naming it (it needs something the Lab Host cannot always
#                             provide, e.g. release binaries fetched from the network)
#
# The set of jobs with default=yes covers exactly what the per-test suite covers: both modes of
# e2e, ipv6, rates and lifecycle, plus split-merge, import-export and connlimit in the one mode
# each of them has. lifecycle is listed per check, so a check can have its own class.
#
# The check 5 family floods thousands of connections and datagrams. 5, 5b and 5e read RSS under that
# load and run alone. 5c and 5d assert on an admission decision instead, and 20 repetitions of each
# in a pool of eight sandboxes, overlapping each other, passed with identical held counts, so they
# run in the pool.

# agentkernel.sh runs the kernel-mode agent's checks (design section 7b) against the given server
# mode, taking the checks to run as a space-separated list of its own. Its default list of checks
# takes over 10 minutes end to end, past labhost's default per-job timeout, so it is split here
# into five groups instead of the one-job-per-check granularity lifecycle.sh above uses; several of
# these checks share tens of seconds of setup, so grouping them costs less than splitting further.
# Within a group the checks run in the given order. teardown removes the agent's WireGuard
# interface, table and records that the group's earlier checks depend on, so it must be a group's
# last check; 22 leaves rules that resolve then removes, so a group must not run both (this file
# avoids that by keeping them in different groups). reconnect and stale only apply with a
# kernel-mode server and print SKIP with a userspace-mode one; they are still registered for both
# modes, the same as this file already does for lifecycle.sh's mode-specific checks. Five such
# groups, one sandbox each, ran inside the full default suite's pool of 8 (`labhost run -parallel
# 8 all`) with 0 FAIL for every group in both server modes; the slowest group (resolve, in either
# mode) took under 5 minutes, comfortably inside labhost's per-job timeout. See docs/testing.md
# for L16 and for how this suite's total wall-clock time changed once these groups joined the pool.
parallel         yes  agentkernel.sh kernel drift 22 25 16 teardown
parallel         yes  agentkernel.sh kernel route session
parallel         yes  agentkernel.sh kernel resolve 24 17 18 19
parallel         yes  agentkernel.sh kernel notify pin reconnect
parallel         yes  agentkernel.sh kernel stale
parallel         yes  agentkernel.sh userspace drift 22 25 16 teardown
parallel         yes  agentkernel.sh userspace route session
parallel         yes  agentkernel.sh userspace resolve 24 17 18 19
parallel         yes  agentkernel.sh userspace notify pin reconnect
parallel         yes  agentkernel.sh userspace stale

# agentdoctor.sh runs `wgft agent doctor` against a kernel-mode agent (design section 10.2c), with
# the server in the given mode. One run takes about a minute, well inside labhost's per-job
# timeout, so each mode is its own single job, the same granularity as e2e.sh and ipv6.sh above.
parallel         yes  agentdoctor.sh kernel
parallel         yes  agentdoctor.sh userspace

exclusive-heavy  yes  rates.sh kernel
exclusive-heavy  yes  rates.sh userspace
# connlimit.sh opens 160 to 320 concurrent flows, but what it asserts on is a kernel-side
# per-source cap: three rounds beside 0, 4 and 8 sandboxes gave byte-identical counts and the
# same 12 PASS lines, so it belongs in the pool.
parallel         yes  connlimit.sh

# version-skew.sh needs the v0.3.0 and v0.6.0 release binaries (v0.6.0 is OLD_AGENT_VERSION as of
# this revision; see the script's own header comment). A lab VM on a host without outbound IPv4
# cannot fetch them (GitHub has no IPv6), so they have to be staged into the VM first, and the
# check is opt-in for that reason, exactly as it is in the per-VM suite today.
parallel         no   version-skew.sh
