## 10. 操作インタフェース

### 10.1 Web UI

- ダッシュボードは 1 カラムで、上からサーバー情報、警告、エージェント一覧、ルール一覧、適用中のファイアウォール設定の順に並べる。ルール一覧の上には、ルールが残っている未登録のエージェントごとに帯を出す(後述の「未登録のエージェントの帯」)。警告は 1 件以上あるときだけ帯状のバナーで出し、0 件のときは何も表示せず場所を取らない(ヘッダの全体ヘルスの見出しに件数が出るので十分)。ヘッダの全体ヘルスの隣には、警告が 1 件以上あるときだけ件数を出し、押すとバナーへ飛ぶ。ヘッダの全体ヘルス、エージェント一覧、ルール一覧、警告バナーは 5 秒ごとに部分更新するので、警告バナーの受け皿の要素は 0 件でも DOM に残し、0 件から増えたときに次の更新で描き直す。ルール一覧の畳んだグループの開閉は、部分更新をまたいで保つ。ファイアウォール設定はルール一覧の下に全幅で置き、既定では折りたたむ
- ヘッダの全体ヘルスの要約(2026-09-24、所有者の決定):オンラインのエージェントの数を、有効なエージェントの数に対して示す。無効なエージェントは分母に含めず、1 台以上あるときだけ「無効 N」を添える。無効は宣言どおりの状態なので、オンラインの割合を下げて故障に見せないためである。無効なエージェントのルールは診断の印が SKIPPED になるので、エラーの数に含まれない
- ダッシュボード以外の共通の枠のページは、上部の移動を左寄せのパンくずで行い、右上にダッシュボードへ戻るボタンを置かない。言語の切り替えはダッシュボードにだけ置き、他のページはダッシュボードで選んだ言語にクッキーで従う。POST の結果のページ(発行した接続文字列、読み込みの確認)で切り替えると、読み直しで結果が消えるためである。パンくずは「ダッシュボード」から今いるページまでを並べ、今いるページの項目だけはリンクにしない。並べる階層は実際に開けるページに限る。ルールの一覧のページは無いので、ルールの詳細ページは「ダッシュボード / ルール」、接続テストは「ダッシュボード / ルール / 接続テスト」、読み込みの確認は「ダッシュボード / ルールの読み込み / 読み込みの確認」、診断の画面は「ダッシュボード / 診断」と「ダッシュボード / 診断 / ルール」になる。ルールは「TCP 8080 → office」のように、プロトコル、受信ポート、持ち主のエージェントで呼ぶ。エージェントの詳細ページは「ダッシュボード / エージェント」になり、エージェントは「エージェント home」のように名前で呼ぶ
- ダッシュボード上部に vpsd と VPS 環境の情報を出す:バージョン、稼働時間、wg インタフェース/アドレス/待ち受けポート、エージェントの接続先エンドポイント、エージェント API ポート、MTU、カーネル版、nftables 版、`ip_forward` の今の値と wgft が起動時に設定したか、conntrack の UDP タイムアウト。`ip_forward` は今の値を先に示す(2026-09-25)。起動時の記録だけを示すと、稼働中に外から 0 にされた server でも「wgft が設定」と出て、転送が止まっていることが見えないためである。カーネルモードの server で 0 なら危険の色で示し、戻すコマンドを添える。今の値を返さない旧い版の server では、今までどおり記録だけを示す。これは構成・環境の確認用で、ヘッダの全体ヘルス(動的な健康)とは別

- エージェント一覧:名前、割り当てアドレス、最終ハートビート、処理済み世代、最終ハンドシェイク、wg ピアのエンドポイント IP、stream の接続元 IP、警告。名前の下に wg 公開鍵の先頭だけを小さく添え、`agent pubkey` の出力と見比べられるよう全体は title 属性(ホバー表示)に持たせる。両 IP の食い違いが続くと 5.2 節の警告になる。警告の隣に「警告を消す」操作を置く。行にはエージェントの無効化と有効化の操作を置き、削除は置かない。削除は次項の詳細ページと、警告のバナー(5.2 節)に置く。行の操作は、有効なエージェントには「無効化」、無効なエージェントには「有効化」とし、ルールの行の操作と同じ語を使う(2026-09-24、所有者の決定)。どちらも転送を止めて設定を残すという同じ意味だからである。無効化は確認のダイアログを出し、このエージェントのルールがすべて転送を止めて通信中のセッションも切れることと、登録、鍵、ルールの設定が残り有効化で戻ることを示す。有効化は確認しない。エージェントの名前は詳細ページへのリンクにする。無効なエージェントの行は、状態を故障の色でない「無効」で示し、要対応の行にしない(2026-09-24、所有者の決定)。トンネルの状態、最終ハンドシェイク、最終ハートビートは参考の値として控えめな色で示し、接続していなくても警告や故障の色にしない。反映待ちの印も出さない。VPS は無効なエージェントのルールを転送しないので、世代の遅れは転送に関わらないためである。窃取の警告を持つ無効なエージェントの行は、要対応の行にする。無効の間も恒久トークンは使えるためである。接続していないエージェントのトンネルの状態は、5.2 節のとおり最後の報告であることが分かる色で示し、ok には見せない。IP の食い違いの比較も接続していない間は出さない。接続している間の比較は、一致、食い違い、確認済みの食い違いの 3 つを出し分ける。比較は 5.2 節の監視と同じ正規化と組の識別で行う。今の組が確認済みの組(5.2 節)なら、IP が食い違っている事実だけを示し、警告の色にせず、要対応の行にもしない。確認済みの組が捨てられれば、表示は一致か食い違いに戻る。確認済みの組を読めないときは、確認済みでない食い違いとして警告の色で示し、読めなかったことをログに出す
- エージェントの詳細ページ(`/ui/agents/{name}`)。一覧の行のエージェント名から開く(2026-09-24、所有者の決定)。無効化と有効化の操作を置き、末尾の「危険な操作」の区画にエージェントの削除を置く。削除は、エージェントの名前を入力させて確認する。無効化と区別し、元に戻せない操作を誤って選ばせないためである。削除の確認には、ルールも削除する選択を置く(5.1 節)。ページには、一覧の行と同じ状態のほか、割り当てアドレス、公開鍵の全体、stream の接続元 IP と WireGuard のエンドポイント、最終ハートビートと最終ハンドシェイク、処理済み世代、登録の時刻、無効にした時刻、そのエージェントを持ち主とするルールの一覧を出す。ルールの一覧の各行は、ルールの詳細ページへのリンクにする。削除の区画は「危険な操作」の見出しと、枠を故障の色の線で描くボタンを持つ。入力された名前は server が照合し、一致しなければ何も削除せず、同じページに誤りを示す。ブラウザの JavaScript は名前が一致するまで削除のボタンを押せなくするが、これは補助であり、守りは server の照合である。警告のバナーの削除は、確認のダイアログで確かめ、エージェントの名前をフォームに添えて送るので、同じ照合を通る。server はエージェントの行を消してから dataplane へ公開し、公開の失敗を誤りとして返す。そのため削除が誤りを返したときは、エージェントを読み直す。行が既に無ければ、削除は済んだが転送への反映はまだで、server が 30 秒ごとに試し直すことを示す。行が残っていれば、削除できなかったことを示す。ルールも削除する選択は、そのエージェントを持ち主とするルールが有効無効を問わず 1 本以上あるときだけ出し、本数を添える。選んだ削除のフォームは、ページを描いた時点のルール集合のハッシュを送る。server は、エージェントを削除する前に今の集合と比べ、違えば何も削除しない。ルールの削除のバッチにも同じハッシュを `ExpectedDigest` として渡す。ルールの削除だけが失敗した場合と、エージェントの削除は済んだが反映がまだの場合は、エージェントは削除したことと、ルールは残っていて転送せず、未登録のエージェントの帯から削除し直せることを示す。無効化、有効化、削除の POST は、他の Web UI の POST と同じく、Host の検査と他オリジン発の変更の拒否を通る(11 節)
- 未登録のエージェントの帯(2026-09-24、所有者の決定):ルールが残っている未登録のエージェントごとに 1 本出す。帯は、エージェントの名前、削除済みであること、そのエージェントを参照するルールの本数(例:「home は削除済みです。このエージェントを参照するルール: 10 本」)と、その本数のルールをまとめて削除するボタンを持つ。削除はルールのバッチ 1 回で行い、確認のダイアログを出す。同じ名前で登録し直すつもりなら、帯を残したまま待てばよい(5.1 節)。帯はルール一覧の区画の中の表の上に置き、ルール一覧と一緒に 5 秒ごとに描き直す。帯は故障ではないので、警告の色にしない。帯の本数は、そのエージェントを参照するルールを有効無効を問わずに数え、一括削除もそのすべてを消す。一括削除のフォームは、帯が示した本数と、帯を描いた時点のルール集合のハッシュ(`proto.RulesDigest`)を送る。server は、そのエージェントが登録されていれば何も削除しない。帯を描いた後に同じ名前で登録し直した場合に、動いているエージェントのルールを消さないためである。今の本数が送られた本数と違う場合と、ルール集合が送られたハッシュと違う場合も、何も削除しない。確かめたより多いルールや、確かめた後に変わったルールを消さないためである。ハッシュの照合は、読み込みの適用と同じくバッチの `ExpectedDigest`(5.4 節)で、バッチのトランザクションの内側で行う。登録の確認からバッチまでのごく短い間に同じ名前で登録し直した場合は見分けない。登録はルール集合を変えないのでハッシュでは捉えられず、そこで消えるのは利用者が削除を確かめたルールそのものなので、受け入れる
- 接続文字列の発行
- ルール一覧と追加、編集、削除、有効無効の切り替え。各ルールにエージェント側の適用状態と、接続元制限で拒否した累積数を表示する。適用状態は無効なルールなら常に disabled とし、有効なルールは持ち主のエージェントの直近のハートビート(5.2 節)から次の優先順位で判定する:エージェントが無効なら「エージェント無効」、未登録なら「エージェント未登録」(どちらも灰色で示し、他の適用状態の頭の ● の代わりに横棒を添え、エラーの数に含めない。5.1 節)、未接続なら agent offline、エージェントの処理済み世代が最新より古い(そのルールをまだ報告していない場合を含む)なら pending、それ以外はエージェントが報告したそのルールの状態に従い ok なら applied、error なら error とする。error の理由の文は一覧には出さず、ルールの詳細ページと診断の画面で読む。適用状態の右には診断の印を置く(後述の「ルール一覧の診断の印」)。一覧は `group` ごとの見出しで畳めるように区切り(見出しにグループ名と件数、折りたたみ可)、`group` の空いたルールは「その他」に入れる。畳んだグループでも見出しに error のルール数を出す。ヘッダの全体ヘルスの要約にも error のルール数を含める。この 2 つの error のルール数は、適用状態ではなく、診断の印が FAILED のルールの数である。各ルールには `note` を薄字の副題として常に添える。追加フォームで「説明」(`note`)と「グループ」(`group`。既存グループの候補を出しつつ自由入力)を設定できる。追加フォームの「無効のまま追加」は CLI の `rule add --disabled` にあたる
- ルール一覧の診断の印(2026-09-24、所有者の決定):状態の列の中で、適用状態の右に印を 1 つ置く。新しい列は作らない。印は、ルールの総合判定(10.2a 節)を 10.2d 節の経路の図と同じ関数で写したものである。画面が自ら決めるのは、UNKNOWN の印に添える節点と、持ち主のエージェントが未登録のルールの扱いの 2 つだけである(10.2d 節)。OK は緑の円と ✓、FAILED は赤の八角形と ✕ に止まった節点の名前、UNKNOWN は黄のひし形と ? に最初の UNKNOWN の節点の名前、SKIPPED は灰色の横棒の円とする。無効なルールと、無効なエージェントのルールは SKIPPED になる。図形は診断の画面の節点と同じものを使う。記号は読み上げの対象から外し、「診断: FAILED at WireGuard」のような文を読み上げに渡す。状態の語と節点の名前は英語のままにする(10.2d 節)。印は、診断の画面のそのルールのページへのリンクである。持ち主のエージェントが未登録のルール、つまり `agent.connection` の reason が `agent_not_registered` のルールは、`server doctor` では FAILED だが(5.1 節)、印を灰色の「エージェント未登録」とし、エラーの数に含めない。ヘッダの全体ヘルスとグループの見出しの error のルール数は、印が FAILED のルールを数える。赤い ✕ の行が「エラー 0 件」の見出しの下に並ばないようにするためである。適用状態と印は出どころが違い、食い違うことがある。例えば、適用済みのルールでもハンドシェイクが古ければ印は ✕ WireGuard になる。どちらも書き換えずに並べる。エージェント一覧には印を置かない。ダッシュボードとその部分更新は、ルールとエージェントを診断と同じ 1 回の読み取り(10.2d 節)から組み立てる。適用状態と印と件数は同じ時点の証拠から作られ、印のための読み取りは増えない。疎通の確認は呼ばない
- ルールの詳細ページ(`/ui/rules/{id}`)。一覧の各ルールの「詳細」から開く。ルールの要約に一覧と同じ適用状態(理由を含む)を出し、有効無効の切り替えの下に、設定、アクセス制御、ルール操作の 3 つの区画をこの順に置く。設定の区画は group、note、レート制限を 1 つのフォームにまとめ、末尾の 1 つの保存ボタンで保存する。アクセス制御の区画の拒否リストと許可リストは、追加と「外す」のたびにその場で保存する。ルール操作の区画の分割と統合は、ボタンを押した時点で実行する。保存は管理用 API のバッチ 1 回(`upsert`、分割は 2 件の `upsert`、統合は `upsert` と `delete`)で行う。group、note、接続元制限、レートの変更では ID も世代も変わらない(5.3 節)。保存の後は同じ詳細ページを表示する(分割の後は縮んだ元のルールの、統合の後はこのルールの、どちらも ID が変わらない詳細ページ)
  - 設定のグループと説明:group と note は転送に関わらないので、既存ルールに対して ID そのままで後付け・変更できる
  - 設定のレート制限:`per_source_rate`(1 つの接続元からの新しい接続)、`new_flow_rate`(ルール全体の新しい接続)、`packet_rate`(パケット。通信中のデータも含めて数える)の 3 つに、回数、単位(`second` から `week`)、「制限しない」を置く。`per_source_rate` と `new_flow_rate` が数えるのは新しい接続(TCP は 1 本のコネクション、UDP は初めて見た送信元アドレスとポートの組)であり、開いている接続は数えない。`packet_rate` は通信中のデータも含めて数えるため誤読されやすく、区画を折りたたんで値が入っているときだけ開く。値が入っている欄には読み上げの一文(例:「1 つの接続元から 1 分に 10 本まで」)を添える。「制限しない」は値を外す。TCP のルールでは `packet_rate` を保存しても効かないこと(7a.9 節)を、TCP のルールに限りその欄に添える。入力欄自体は無効にせず、他の欄を保存しても保存済みの `packet_rate` は消さない。区画の見出しには、このルールの累積 drop 数を一覧と同じ値で添える
  - 設定の保存:フォームは描いた時点の保存値を hidden で持ち、保存はそれと比べて利用者が変えた欄だけを今のルールに当てはめる。比べる単位はルールの欄(group、note、`per_source_rate`、`new_flow_rate`、`packet_rate`)で、レートは回数と単位を 1 つの値として扱う。回数と単位を別々に当てはめると、どちらの側も選んでいないレートができうるためである。レート欄は保存値で埋めて描くので、説明だけを変えた保存がレート欄の入力で拒まれることは無い。入力に誤りがあれば何も保存せず、その欄に誤りを示し、すべての欄の入力を残して描き直す。利用者が変えた欄が、ページを描いた後に別の経路(CLI や別のタブ)でも別の値に変わっていれば、上書きせず何も保存しない。その欄に今の値を示し、利用者の入力を残し、hidden の保存値を今の値に改めて描き直す。確かめてから保存し直すと利用者の値が入る。利用者が変えていない欄は、別の経路で変わっていても今の値のまま残る。確定の呼び出しには読み取った時点のルール集合のハッシュを `ExpectedDigest`(5.4 節)として渡し、読み取りから確定までの間の割り込みも拒む。拒まれたときは入力を残して描き直し、保存し直すとその時点の値と改めて比べる
  - アクセス制御の拒否リスト(`source_deny`):各 CIDR の行に「外す」を置く。追加は複数行の入力で受け、1 行に 1 つの CIDR かアドレスを書く。前後の空白と空行は無視し、単独のアドレスには `/32` を補い、既にある CIDR は重ねて加えない。解釈は CLI の `rule deny add` と同じである。IPv4 の CIDR として読めない行が 1 つでもあれば何も保存せず、その行の番号と内容を示し、入力を残したまま同じページを表示し直す
  - アクセス制御の許可リスト(`source_allow`):拒否リストと同じ形である。空のリストへの最初の追加は他の接続元を全部落とし、最後の 1 件を外すと全接続元に開くので、どちらも確認のダイアログを出す
  - ルール操作の分割:`listen_port` が範囲のルールにだけ出す。分割する位置は範囲の 2 番目から末尾までのポートから選ぶ。結果の 2 つのルール(受信範囲と実効宛先)は、送信前に JS がその場で計算して示す。組み立てと検査は CLI の `rule split` と共有する(5.4 節)
  - ルール操作の統合:同じプロトコルの他のルールから、`listen_port` が直前・直後で隣接するものを探し、5.4 節の統合の条件をすべて満たすものだけを候補として、それぞれに「このルールと統合」ボタンを出す。候補が 1 つも無く、隣接するルールがあるときは、直前を優先してその 1 件の理由(例:拒否リストが違う)を示す。組み立てと検査は CLI の `rule merge` と共有し、この画面のルールが `id1` にあたる(削除されるのは相手)
- TCP ルールの疎通確認。`vpsd` から `10.200.0.x:listen_port`(エージェントのリスナー)に接続し、エージェントの中継を通して `target` に届くかを見る。`target` は LAN アドレスで `vpsd` からは経路がないため、直接は試さない。UDP は送信だけでは失敗が分からないので持たず、エージェントの適用状態で代える。持ち主のエージェントが無効か未登録のルールには、ルール一覧の接続テストのボタンを出さない。server がそのルールの疎通確認を拒むためである(5.1 節)
- ルール一覧の見出しにある書き出しと読み込み(`GET /ui/rules/export`、`/ui/rules/import`)。書き出しは現在の全ルールを、CLI の `rule import` が読む配列と同じ形の JSON でダウンロードさせる。読み込みはアップロードした内容をまだ適用せず、現在のルールと ID で突き合わせた差分の確認ページを表示する。差分の計算(追加・変更・削除・変わらないの判定と、変更したルールのフィールドごとの説明)は `proto.DiffRules` が持ち、削除対象の抽出は `proto.DeletedIDs` が持つ。CLI の `rule import` もこの 2 つを使い、独自の突き合わせを持たない。拒否/許可リストの変更は件数でなく、増えた CIDR と減った CIDR(例:`+198.51.100.0/24 -203.0.113.0/24`)で示す。件数だけでは、同じ件数のまま内容が入れ替わる変更(1 件を別の CIDR に差し替えるなど)が変わらないと見えてしまうためである。確認ページは、削除の行に通信中のセッションが切れる旨の注記を添え、適用が拒まれる理由を一覧にして適用ボタンを出さない。一覧にする理由は、`Daemon.Batch` が保存の前に行う判定のうち、管理用 API から観測できる範囲と同じものである。内訳は、未登録のエージェントを指すルール、`Rule.Validate` に落ちるルール(今のルールから変わっていない行は除く。5.4 節)、ID の重複、予約ポート(WireGuard、管理用 API、エージェント用 API)との重なり、`listen_port` の重なりである。後の 3 つは `proto.ValidateUpsert` が読み込み後の集合全体に対して判定する。予約ポートの集合は、`Daemon.reserved` を組むのと同じ規則で `admin.ServerInfo` から組む。この読み取りに失敗した場合は、予約ポートを空として続行せず、確認そのものを止める。空として続行すると、`Batch` が拒む読み込みを受理されると示すことになるためである。他テーブルの DNAT との衝突と bind 中のポートの検査(`internal/vpsd/apply.go` の `checkRule`)は、root と `nft` を必要とし、確認を描く層からは呼べないので確かめない。これは CLI の `--dry-run` と同じ確かめない範囲である。適用は、アップロードした内容(ID を確定させた後の JSON)と、確認ページを描いた時点の世代、およびその時点のルール集合全体のハッシュ(`proto.RulesDigest`)を hidden で持たせて送る。`group`、`note`、接続元制限、レートだけの変更は世代を上げない(5.3 節)ため、世代の一致だけでは別経路(CLI など)からの変更を見逃すので、ハッシュも一致させる。適用の直前に今の世代とハッシュを取り直し、どちらかが確認ページを描いた時点と違えば何も変えず、アップロードし直すよう求める。この事前の取り直しと、実際にバッチを確定させる呼び出しとの間にもわずかな競合可能期間が残るため、確定の呼び出し自身にも同じハッシュを `ExpectedDigest`(5.4 節)として渡し、バッチ側のトランザクションの内側で読み取りと確定を割り込みなく結びつける。事前の取り直しをすり抜けた食い違いは、この照合の誤り(`ErrBatchConflict`)を同じ「アップロードし直す」画面に写して防ぐ。削除を含む適用には `data-confirm` を付ける

### 10.2 CLI

CLI は管理用 API を叩く薄い層で、Web UI と同じことができる。

```
wgft agent join-string --name home
wgft agent rotate-key
wgft rule add --agent home --udp 2456-2457 --to 192.168.1.20:2456 --group game --note "週末サーバ"
wgft rule add --agent home --tcp 443 --to 192.168.1.30:443 --proxy --proxy-protocol
wgft rule set r_01J --group friends --note "公開サバ"
wgft rule deny add r_01J 203.0.113.0/24
wgft rule ls
wgft server nft
```

`rule ls` は `group` ごとにまとめて表示し、各ルールの `note` も出す。`rule add` の `--group` と `--note` は省略できる。`rule set` は既存ルールの `group` と `note` だけを ID そのままで変える(転送に影響せず世代も上げない)。`--group ""` で外す。

ルールの ID の表示と受け取りの境界を次のとおり定める(2026-09-25、所有者の決定)。表の ID の列、`status` の行の要約、診断の一覧の行のように、ルールを見分けるために示す ID は、先頭 12 文字に省略記号 `…` を付けた短い形でよい。そのまま打つコマンドとして示す場所には、完全な ID を使う。診断の次の一手(人向けの出力の `Check:` の行と `--json` の `next`、Web UI の同じ所見)と、`server doctor` の終了の 1 行が名指すルールがこれに当たる。短い形をコマンドに埋めると、打った運用者が見つからないという誤りに当たるためである。ルールの ID を受け取るコマンドは、完全な ID のほかに、前方一致が 1 つだけの ID の先頭を受け取り、末尾の省略記号 `…` か `...` を落としてから照合する。表の短い形をそのまま貼っても通すためである。ただし、`rule import` と管理用 API は 5.3 節の範囲の任意の文字列を ID として受けるので、省略記号で終わる ID もありうる。そこで、照合を次の順に行う。まず生の入力と完全に一致する ID を探し、あればそれを指す。無ければ、末尾の省略記号を落とした残りで始まる ID を探す。1 つだけならそれを指し、2 つ以上なら候補の完全な ID を挙げて拒む。省略記号の付いた入力では、残りと完全に一致する ID があっても、それを先に指さない(2026-10-03、所有者の決定)。表の短い形の省略記号は、その先に文字が続くことを示す。残りと完全に一致する ID を先に指すと、表の行とは別のルールを指しうる。例えば ID が `aaaaaaaaaaaa` と `aaaaaaaaaaaab` の 2 本あると、表は後者を `aaaaaaaaaaaa…` と示す。この形を貼った入力は、前者を指さずに 2 本の候補を挙げて拒む。省略記号の無い入力は、生の入力の完全一致が先に立つ。`web` と `webserver` の 2 本があると、`web` は `web` を指し、`web…` は 2 本の候補を挙げて拒む。省略記号を落とした残りが空になる入力、つまり空の文字列と省略記号だけの入力は、ルールが 1 本しか無い配置でもそのルールを指さずに拒む。前方一致に求める長さは、省略記号の有無で変えない(2026-10-03、所有者の決定)。12 文字は表示で省略する長さであり、ルールの ID の最小の長さでも、受け取る先頭の最小の長さでもない。省略記号の無い短い先頭を受けながら、同じ先頭に省略記号を付けた入力だけを拒むと、利用者から見て一貫しないためである。このため、`r_...` のようなプレースホルダを貼った入力は、`r_` で始まるルールが 1 本だけの配置ではそのルールを指す。省略記号の無い `r_` も同じルールを指す。ID はほぼ任意の文字列なので、URL のパスに埋めるときは、`url.PathEscape` でパスの 1 つの区切りとして escape する。Web UI のリンクとフォームの送信先、保存の後の戻り先、CLI が管理用 API に出すリクエストのどれも同じである(2026-09-30)。未登録のエージェントの帯の削除のボタンの送信先には、ルールの `agent` を埋めるので、同じく escape する。書き込むルールの `agent` は登録済みのエージェントの名前でなければならず、その名前は 5.1 節の文字種に従う。このため、帯の名前に `/` や `..` が入るのは、この文字種の検査ができる前に保存されたエージェントの名前だけであり、帯の送信先の escape はその名前に備える多重の守りである。escape しないと、`/`、`..`、`?` を含む ID の行のボタンが、ブラウザの解決によって別のルールやエージェントの経路へ送信する。ID と `agent` は、`.` と `..` を受けない(2026-09-30、所有者の決定)。ブラウザは WHATWG URL 標準に従い、`%2E` と `%2E%2E` も区切りの `.` と `..` として扱う。このため escape しても、そのルールやエージェントの Web UI のボタンが別の経路へ送信する。`agent` については、登録済みのエージェントの名前であることの検査がこの 2 つを既に拒んでいるので、`.` と `..` を拒むのは多重の守りである。区切りとして拒むのはこの 2 つだけで、`...` や `.a` のような文字列は受ける。拒むのはルール単体の検査(`proto.Rule.Validate`)なので、CLI、管理用 API、Web UI、取り込みのどれにも効く。この検査の前に保存された `.` や `..` のルールは、触らない限り読み込みと転送を続け、他のルールの変更も妨げない。そのルール自身の変更は拒み、削除はできる。ルールのバッチの検査が、変えていない行には検査を掛け直さないためである(`proto.ValidateUpsert`)。`pathSegment` は `.` と `..` を今も `%2E` の形にする。CLI が、拒むようにする前に保存された `.` や `..` のルールを管理用 API で指すためである。

CLI が管理用 API に出す HTTP リクエストには固定のタイムアウト(30 秒)がある。サーバが応答しない場合は待ち続けず、そのアドレスと待った時間を添えたエラーで止まる。管理用 API の応答はどれも束縛されている(バッチの本文の上限、ルール一覧、TCP の疎通確認は server 側の dial の期限が既定 5 秒)ので、この時間はどの正当な呼び出しにも十分な余裕がある。
`server nft` は適用中の `wgft` テーブルをそのまま表示し、手で確認したいときに使う。

### 10.3 運用の流れ

初回セットアップ(VPS):

1. `/etc/wgft/server.env` に `WGFT_MODE=kernel` と `WGFT_WG_ENDPOINT` を書き、`wgft server check` で検査してから、systemd で `wgft server run` を起動する。root もカーネル WireGuard も使えない VPS では、代わりに `WGFT_MODE=userspace` を焼き込んだコンテナイメージを `WGFT_WG_ENDPOINT` とデータのボリュームだけ与えて起動する(6.3 節)。入れ方でモードが決まり、systemd ならカーネル、Docker ならユーザー空間である。初回起動で SQLite、自己署名証明書、wg0 のサーバ鍵を作り、モードとアドレス帯を記録する(9 節)。対話は無く、初回に決めるのはモードだけである
2. VPS のファイアウォールで WireGuard とエージェント用 API のポートを開ける。これは手作業で、`vpsd` は行わない
3. 起動ログに 6.1 節の警告(forward の `policy drop` など)が出ていれば、提示された行を 1 回だけ足す

同梱の systemd の unit は `vpsd` を root では動かさない。`DynamicUser=yes` で systemd がサービスの寿命だけ非特権の利用者を割り当て、`AmbientCapabilities` で `CAP_NET_ADMIN` と `CAP_NET_BIND_SERVICE` の 2 つだけを渡す。前者はカーネルの WireGuard、nftables、conntrack の netlink と `net.ipv4.ip_forward` の書き込みに、後者はプロキシモードの 1024 未満の待ち受けに使う。ネットワーク系の sysctl は `CAP_NET_ADMIN` があれば root でなくても書けるので、6.1 節の「`vpsd` 自身が 1 にする」はそのまま成り立つ。`ProtectKernelTunables` は `/proc/sys` を読み取り専用にして書き込みを妨げるので付けない。root のままで `/proc/sys` を書き込み可にすると、侵害されたときに root 所有のほかの sysctl まで書き換えられるので、非 root にする意味はここにある。ファイルシステムは `ProtectSystem=strict` で読み取り専用にし、書けるのはデータの置き場と実行時ディレクトリだけにする。システムコールは `@system-service` から `@privileged` と `@resources` を除いたものに絞る。データの置き場の実体は `/var/lib/private/wgft` になり、`/var/lib/wgft` はそこへのシンボリックリンクになる。root で動く旧い unit が作ったディレクトリは、最初の起動で systemd が移して所有者を付け替えるので、unit を差し替えて再起動するだけで更新でき、サーバ鍵も登録済みのエージェントも引き継がれる。root からは従来どおり読めるので、CLI と `teardown` の使い方は変わらない。設定ファイルの権限は 11a 節による。`systemd-analyze security` の値は 8.6 から 2.0 になった(systemd 252)。

メモリが尽きたときの扱いは次のとおり。7 節の同時フロー数の上限は、`vpsd` が保持するフローの数を抑えるが、プロセスのメモリの量を抑える上限ではない。OOM キラーに殺された場合は、unit の `Restart=on-failure` が 2 秒後に起動し直す(compose は `restart: unless-stopped`)。ルール、サーバ鍵、エージェントの登録は SQLite にあるので失われない。カーネルモードでは、`vpsd` が落ちている間も、プロキシモード(6.2 節)以外のルールの転送は続く。ホスト全体のメモリが尽きた場合にカーネルが選ぶプロセスは `vpsd` とは限らないので、unit には `MemoryMax=` の例をコメントで添える。値はホストの大きさで変わるので既定では有効にせず、起動時に出るソフト上限より上に置くよう書く。ソフト上限はメモリの上限ではないので、この置き方だけで OOM を避けられるとは限らない。ユーザー空間モードで最悪の場合に要るメモリの量は、7 節の「プロセス全体のメモリの上界」の段落にホストの要件として書く。

管理 UI と CLI への入り方(11 節)。どの経路でもパスワードの入力は無い:

- VPS 上の CLI:`sudo wgft rule add ...` のように root で叩く。ソケットを開けるのは root と `vpsd` 自身だけなので、sudo がそのまま認証になる
- Tailscale を使う場合(推奨):`--admin-tailscale` を付けて起動し、tailnet 内の端末から `http://<VPS の tailnet 名>:8686/` を開く
- Tailscale が無い、または tailnet が落ちたとき:SSH でソケットを手元に引く。`~/.ssh/config` の該当ホストに `LocalForward 8686 /run/wgft/admin.sock` を書いておけば、`ssh vps` を張るだけで `http://localhost:8686/` が開く

エージェントの追加(自宅):

1. `wgft agent join-string --name home` で接続文字列を 1 本発行する
2. 自宅の LXC か Docker で、接続文字列を `WGFT_JOIN` に入れてエージェントを起動する。名前は接続文字列に紐付いているので入力しない。接続文字列には `#` が入るのでクォートする。状態ファイルの置き場所をボリュームにしておく
3. エージェント一覧に名前が現れ、最終ハンドシェイクが埋まれば完了。接続文字列はこの時点で使い切りになる

ルールの追加と監視:

1. `wgft rule add` で追加する。VPS の nftables に即反映され、エージェントに全体状態が配信され、ルール一覧に `ok` が出る
2. `error` なら理由(`target` に繋がらない、など)が一覧に出る
3. 拒否カウンタや新規フロー数はルール一覧で見る。荒らしには `wgft rule deny add` で対処し、通信中のフローも含めて即座に切れる

普段の運用で人が触るのは、ルールの追加と拒否リストの追加だけである。
エージェントは再起動しても状態ファイルから復旧し、VPS が再起動しても `vpsd` が同じ鍵で wg0 を作り直すので、どちらも手作業は要らない。

撤去(アンインストール):

`vpsd` は停止しても wg0 と `table inet wgft` を残す(再起動で転送を途切れさせないため)。
やめるときは、`vpsd` が自分で作ったものだけを消す撤去操作を CLI の 1 コマンドとして持つ。
これは**停止した `vpsd` の後片付け**として行う。`vpsd` が稼働中なら何も消さずに拒否し、
先に停止するよう案内する(動いたまま消すと、次のルール変更や systemd の再起動で
作り直される)。稼働の判定は、`vpsd` が起動時に状態ファイルへ取る flock(エージェントの
状態ファイルと同じ形)で行う。

撤去の間の排他(2026-10-03、所有者の決定):何かを変える撤去は、ロックファイルが無ければ作ってロックを取り、サーバのデータベースを開く前から終わるまで持つ。取れなければ稼働中として拒否する。判定の後に起動した `vpsd` が、撤去の途中で wg0 とテーブルを作り直すことと、`--purge` が消すデータベースを使うことを防ぐためである。`vpsd` もデータベースを開く前にこのロックを取る(9 節)ので、ロックを持つ撤去の間に起動した `vpsd` はデータベースにも wg0 にもテーブルにも触れずに終了コード 1 で終わる。同梱の unit が再起動を繰り返しても、撤去が終わるまでは同じ所で終わり、撤去が終わった後の再起動で起動する。ロックファイルが無い場合も作って取るのは、取らずに進むと、撤去が不在を読んだ後に起動した `vpsd` がロックファイルを作って資源を作り、撤去がその資源を消しうるためである。ロックの状態を読めなければ、何も消さずに止まる。ロックファイルが symlink か FIFO である場合と、権限で開けない場合がこれに当たる。以前は警告を出して撤去を続けていた。稼働中の `vpsd` の資源を消す危険を、撤去が進めないことより重く見る。

撤去が作ったロックファイルは、持ち主とグループを、サーバのデータベースの置き場のディレクトリの持ち主とグループに合わせる。同梱の unit は `vpsd` を `DynamicUser=yes` で動かす。root の撤去が作った 0600 のロックファイルが root の持ち物のまま残ると、`vpsd` は次の起動でそれを開けず、終了コード 1 の再起動を繰り返す。持ち主の正しい置き場の中にある root の持ち物のファイルを systemd が直さないことは、systemd 252 のラボで確かめた。付け替えはロックを取った記述子に対して行い、既にあったロックファイルの持ち主は変えない。作ってから付け替えるまでの短い間に撤去が強制終了された場合だけは、root の持ち物のロックファイルが残りうる。この場合、`vpsd` の起動の誤りはロックファイルを開けないことを示すので、運用者はロックファイルを消して起動し直す。置き場のディレクトリそのものが無ければ、何かを変える撤去は、`vpsd` の起動と同じく 0700 で作ってからロックファイルを作ってロックを取り、その旨を出力に示す。取らずに進むと、撤去の途中に起動した `vpsd` が、systemd の作った置き場でロックを取って資源を作り、撤去がその資源とデータベースを消すためである。撤去が作ったディレクトリとその中のロックファイルは root の持ち物のまま残す。合わせる先の持ち主が無いためである。同梱の unit では、systemd が次の起動で root の持ち物の `/var/lib/wgft` を `/var/lib/private/wgft` へ移し、中のファイルごと持ち主を付け替えるので、`vpsd` は起動する。これはラボで確かめた。`vpsd` を非 root の利用者で手で動かす配置で、`vpsd` が一度も置き場を作っていないうちに root が撤去を実行した場合は、運用者が置き場の持ち主を直す必要がありうる。この場合は未確認である。`--dry-run` と `--yes` の無い `--purge` は、置き場もロックファイルも作らない。置き場のパスが行き先の無い symlink である場合、例えば `/var/lib/private/wgft` だけが消されて `/var/lib/wgft` が残っている場合は、置き場を作れないので、撤去は何も消さずに終了コード 1 で止まる。この扱いは単体試験で確かめたもので、同梱の unit の上では未確認である。撤去が途中で強制終了されると、ロックはカーネルが放し、ロックファイルは置き場の持ち主の持ち物のまま残る。`vpsd` はそのまま起動でき、撤去もそのまま実行し直せる。

撤去はサーバのデータベースを読むだけなので、読み取り専用で開き、スキーマの移行も権限の締め直しもしない。`--purge` で消すデータベースと、`--purge` の無い撤去が残すデータベースのどちらも、移行する理由が無い。残すデータベースは、次に起動した `vpsd` が移行する。以前は書き込みの形で開いていたので、`--dry-run` でも古い版のスキーマを上げ、その版の `vpsd` が開けないデータベースにした。

`--dry-run` は何も作らず、何も書かない。ロックファイルを作らない `Inspect`(10.2c 節)で同じ判定をし、稼働中なら拒否し、ロックの状態を読めなければ止まる。ロックは取らない。取ると、試しの間に起動した `vpsd` が終了コード 1 で終わるためである。`--yes` の無い `--purge` も、消すものを示して確認を求めるだけなので、同じ扱いにする。

消す順序と対象(`vpsd` が作ったものだけ。既に無いものはエラーにせず飛ばす):

1. `table inet wgft` を削除する。他テーブルには触れない。
2. ルール 0 件で 6.1 節の conntrack 収束を走らせ、wgft 由来の DNAT 済みエントリを消す(テーブルを消してもエントリは残るため)。順序はテーブル削除・conntrack 収束・wg0 削除。
3. wg0 を削除する。消すのは秘密鍵が状態ファイルのサーバ鍵と一致するインタフェースだけで、状態ファイルに鍵が無い(空)場合は相手の鍵が空でも所有とみなさず、`--adopt-existing` を要求する。`--adopt-existing` でも、同名でも WireGuard 以外のリンク(veth や bridge)は消さない。
4. `--purge` のときだけ、状態ファイルを消す。SQLite は WAL なので `.sqlite` と `-wal`・`-shm` の 3 つ。最後にロックファイルを消し、その後でロックを放す。放した後に起動した `vpsd` は新しいロックファイルとデータベースを作り、撤去の後の新しい起動と同じ結果になる。

wg インタフェース名は、`vpsd` が起動のたびに撤去用の手掛かりとしてサーバのデータベースへ記録する(`--wg-interface` を変えても撤去が追従できるようにするため。teardown コマンド自身には名前を渡す手段が無い)。この記録が無い、または読めない場合、撤去は既定名 `wgft0` を仮定するとその旨を出力に示す(10.5 節)。黙って仮定すると、`--adopt-existing`(鍵の一致を見ずに削除する)と組み合わさったときに、実際とは別名の無関係な WireGuard インタフェースを消しかねないためである。この場合の対処は、実際のインタフェース名を確かめてから手で消すか、記録が失敗する原因(サーバのデータベースへの書き込み)を直してから `vpsd` を再起動し、記録し直させることである。

可逆性:`--purge` を付けない撤去は元に戻せる。`vpsd` を起動し直せば同じ鍵と証明書で
wg0 とテーブルが戻り、エージェントは再接続だけで復旧する(9 節)。鍵が消えて
再登録が要るのは `--purge` のときだけである。

自動では戻さないもの(「手で戻す一覧」を出すだけ。追加を自動でやらない原則の裏返し)。
一覧は一般論ではなく、状態ファイルと実状態から具体値を出す:

- VPS のファイアウォールで開けたポート。SQLite から出す(`wg-port` の UDP、エージェント用 API の TCP、全ルールの `listen_port`)。
- 他テーブルに足した wg0 参照行(6.1 節の提示で `DOCKER-USER` などに足した `oifname "wg0" accept` の類)。実状態から所在を列挙する(`check` の検査の逆向き)。
- `ip_forward`。6.1 節の 2 段の記録と、撤去が読んだ今の値から、次のどれかを出す(2026-10-03、所有者の決定)。他の転送が使っている可能性があるので自動では戻さない。
  - 確定の記録がある:`vpsd` が 0 から 1 にした日時と、他に転送を使っていなければ戻す手順を示す。予定の記録の有無は問わない
  - 確定の記録が無く、予定の記録がある:`vpsd` が 0 を読んで 1 を書き始めた日時と、結果を記録していないので `vpsd` が変えたかもしれないことを示す。今の値を添え、確かめて判断するよう案内し、`vpsd` が変えていて他に転送を使っていなければ戻す手順を示す。書いた直後に止まった場合と、書けなかった場合などを撤去は区別できないので、変えたとも変えていないとも言い切らない
  - どちらの記録も無い:`vpsd` は変えておらず、何もしなくてよいと示し、今の値を添える。以前は今の値を読まずに「already 1」と示していた
  - 記録を読めない:どれとも言わず、読めなかった理由と今の値を示し、確かめて判断するよう案内する。以前は読めない記録を「変えていない」として示していた

  今の値を読めなければ、値の代わりに読めなかった理由を示す。今の値は読むだけで、書けるかの probe もしない。`--dry-run` も同じ行を出す。記録した `vpsd` と撤去が同じ network namespace で動くことを前提にする。
- systemd の unit・env、バイナリ、`/var/lib/wgft` ディレクトリは `vpsd` が置いたものではないので一覧に出す。

全体の順序:先に自宅エージェントを止めるか VPS 側で `agent revoke` し(稼働中の `vpsd`
にしか効かない)、その後 `vpsd` を停止して撤去する。撤去後にエージェントが残っても、
接続不能を 5.1 節の一時障害とみなしてバックオフ再接続を続けるだけで害はないが、止まらない。

ユーザー空間モードの自宅エージェントは wireguard-go と netstack なのでカーネルに何も残さず、
プロセスを止めて `agent.json`(と隣の `.lock`・`.sock`)を消せば消える。VPS 側では、
エージェントの削除が恒久トークンを使えなくし、ピア・conntrack・割り当てアドレスを回収する。

カーネルモードのエージェント(7b 節)は、停止しても wgft0 と `table inet wgft_agent` を残す。
これを消すのが `wgft agent teardown` であり、`server teardown` と同じく停止したエージェントの
後片付けとして行う(2026-09-24、所有者の決定)。稼働中のエージェントの 30 秒ごとの収束や
外からの変更への収束は消した資源を作り直しうるので、エージェントが稼働中なら撤去は何も消さずに
拒否し、先に停止するよう案内する。この拒否は普通の誤りであり、終了コードは 1 である。稼働の判定は、
`rotate-key` と同じくロックファイルを作らない `Inspect`(10.2c 節)で行う。判定の後に起動した
エージェントが撤去の途中で資源を作り直さないように、ロックファイルがあって誰も持っていなければ、
撤去は flock を取って終わるまで持つ。取れなければ稼働中として拒否する。ロックファイルが無ければ、
`rotate-key` と同じ理由で flock を取らずに進める(9 節)。ロックの状態を読めなければ、何も消さずに止まる。

撤去が読む設定は、`agent run` と同じ `WGFT_DATA_DIR` と `WGFT_WG_INTERFACE` であり、`agent.env` と
フラグの別名(`--data-dir`、`--wg-interface`、`--config`)から受け取る。消す順序と対象は次のとおりである
(2026-09-24)。既に無いものは誤りにせず飛ばすので、途中で止まった撤去はそのまま実行し直せる。

1. WireGuard インタフェースのうち、秘密鍵が状態ファイルの鍵か 1 つ前の鍵(7b.4 節)と一致するものを、
   名前によらず消す。設定の名前のもの、作業用の名前 `wgftnew<CRC32>`(7b.4 節)のもの、`WGFT_WG_INTERFACE`
   を変える前の名前で残ったものがこれに当たる。テーブルを先に消すと、wgft0 が残っている間に
   filter_pre と input の守りが無くなるので、インタフェースを最初に消す
2. conntrack のエントリのうち、wgft0 から入って wgft が DNAT したものを消す。状態ファイルの公開の記録と、
   収束が済んでいない公開の列(7b.4 節)を前の公開とし、空の公開を今の公開として、7b.4 節の収束を走らせる。
   撤去はこれらの記録を消すので、後でカーネルモードで起動し直したときの収束は、撤去の前のフローを
   見分けられない。ここで消さなければ、宣言から消えた宛先へ DNAT したエントリが conntrack の期限まで残る。
   エージェントのトンネルアドレスは `last_state` から取る。停止中の `rotate-key` の後のように `last_state`
   が無ければ、消す前のインタフェースのアドレスを使う。前の公開の記録が無いか、どちらからもアドレスが
   分からなければ、wgft のフローを見分けられないので何も消さず、その旨を示す。
   conntrack の読み出しか削除に失敗した場合は、警告を出して続ける
3. `table inet wgft_agent` を消す。他のテーブルには触れない
4. 状態ファイル `agent.json` のカーネルモードの記録を消して保存する。消すのは、モード、1 つ前の鍵、
   `ip_forward` の記録、公開の記録、収束が済んでいない公開の列である。撤去の後にユーザー空間モードで
   起動し直せるように、登録の情報、今の鍵、`last_state` は残す。1 か 3 が失敗した場合は記録を消さずに
   誤りを返すので、関門は残った資源を見落とさない。保存は元のファイルの持ち主を保つ(9 節)

起動時のエージェントは、別の名前で今の鍵か 1 つ前の鍵を持つインタフェースを警告するだけで消さない
(7b.4 節)。撤去はこれを消す(2026-09-24)。所有の根拠は鍵であり、名前が変わっても所有は変わらない。
常駐のプロセスは運用者が `WGFT_WG_INTERFACE` を変えた意図を推し量らずに警告にとどめ、撤去は運用者が
明示して実行する後片付けとして消す。消す前の名前は `--dry-run` で確かめられる。

設定の名前か作業用の名前を持つリンクのうち、鍵が一致しない WireGuard インタフェース、鍵を持たない
WireGuard インタフェース、WireGuard 以外のリンクには触れない。撤去はその名前と理由を出力に示し、
状態ファイルを失って鍵が一致しなくなった場合に `ip link del <名前>` で消す手順を示す(7b.4 節)。
ユーザー空間モードのエージェントはカーネルのインタフェースを使わず、残ったリンクは切り替えを
妨げないので、この場合も撤去は成功として終える。

端の場合の扱いは次のとおりである(2026-09-24)。

- 何も残っていないホスト:何も変えずに成功として終える
- 記録だけが残ったホスト:ホストを再起動した後は wgft0 もテーブルも無く、状態ファイルの記録だけが
  11a 節の切り替えの関門を止める。撤去は記録を消して成功として終える
- 状態ファイルが無いデータディレクトリ:何も消さず、見つけた `table inet wgft_agent` と WireGuard
  インタフェースを示して、普通の誤りとして終了コード 1 で止まる(2026-09-24、所有者の決定)。インタフェース
  のうち、`WGFT_WG_INTERFACE` の名前と作業用の名前のものには wgft の設定の名前である印を付け、個人の VPN
  など他の WireGuard のリンクと見分けられるようにする。稼働の判定は
  指したデータディレクトリのロックファイルしか見ないので、`--data-dir` がエージェントの実際のデータ
  ディレクトリを指していないと、稼働中のエージェントを停止したものと取り違える。そのまま消すと、稼働中の
  エージェントのテーブルが消え、次の見直しまで転送が止まる。ラボで再現した。文面は、指したディレクトリ
  に認証情報が無いことと、`--data-dir` か `WGFT_DATA_DIR` で実際のデータディレクトリを指すことを示し、
  認証情報を本当に失った場合は、エージェントを止めて持ち主を確かめたうえで `nft delete table inet
  wgft_agent` と `ip link del <名前>` で手で消す道を示す。11b 節の非対称の規則は、
  systemd の再起動を止める終了コード 3 を避けるための規則であり、一発実行のコマンドには当たらない。
  この場合も、稼働中のエージェントへの拒否や `server teardown` の誤りと同じく、何も消さずに止まった
  普通の誤りとして終了コード 1 にする
- 未知のモードの記録:記録が `kernel` でも `userspace` でもなければ、何も消さずに種別 `conflict` の拒否で
  止まる。その記録は新しい版が書いた可能性があり、この版はその版が残した資源を判定できない。記録を
  消すと、その版の撤去が手掛かりを失う。文面は、記録を書いた版の撤去を使う道と、状態ファイルを控えから
  戻す道を示す
- 権限の不足:インタフェースとテーブルの読み書きには `CAP_NET_ADMIN` が要る。足りなければ種別
  `prerequisite` の拒否で止まる。`--dry-run` も同じ読み出しを行うので、同じく止まる

フラグは 11a 節の 1 回限りの操作の規則に従い、設定の別名のほかに `--dry-run` だけを持つ。`--dry-run` は、
消すもの、触らないもの、手で戻す一覧を示し、何も変えない。稼働中のエージェントに対しては、`--dry-run`
も拒否する。確認の `--yes` は持たない。`server teardown` が確認を求めるのは元に戻せない `--purge` だけで
ある。エージェントの撤去は登録の情報と鍵を残し、`WGFT_MODE=kernel` で起動し直せば wgft0 とテーブルが
戻るので、確認を求めない。消える `ip_forward` の記録の中身は、撤去の出力が示す。

自動では戻さないものは、状態ファイルの記録から具体値を出した「手で戻す一覧」として示す。

- `ip_forward`:他の用途で転送を使っているかもしれないので、自動では戻さない。状態ファイルの記録から
  「エージェントが 0→1 にした(日時)」か「0 から変えた記録が無い」かを示し、前者だけ戻し方を示す
- `WGFT_MODE`:`agent.env` の `WGFT_MODE=kernel` を外すか `userspace` にしてから起動する。残したまま
  起動すると、エージェントはカーネルモードで資源を作り直す
- `CAP_NET_ADMIN`:カーネルモードのためにエージェントの unit へ重ねた権限は、ユーザー空間モードでは要らない

出力は、消すもの、触らないもの、実行の結果、手で戻す一覧を 1 行ずつ示す。人が読む表示であり、
7a.11 節の保証の外である。Windows と macOS では、`server` の一群と同じく種別 `prerequisite` の
拒否として終了コード 3 で止まる(11b 節)。

### 10.4 ログ

`vpsd` とエージェントは、ログを標準エラー出力に 1 行ずつ書き、ファイルには書かない。同梱の unit では journald が受け取るので、運用者は `journalctl -u wgft` と `journalctl -u wgft-agent` で読む。Docker では `docker logs` で読む。ログファイルとその回転は wgft が持たない。

ログは、デバッグ用の設定なしで次の 5 つに答えられるだけの行を出す。

1. 起動に成功したか、どの版とモードで動いているか
2. どのエージェントが接続し、切断したか
3. どのルールの変更が適用されたか
4. どの世代がどのエージェントに届いたか
5. 転送が止まったとき、失敗が WireGuard、ルールの適用、待ち受け、中継先のどこで起きたか

行の種類は次のとおりである。

- 起動の行:`vpsd` は最初のルールとデータプレーンの適用が済み、管理用 API とエージェント用 API の待ち受けをすべて開けた時点で、版、モード、インタフェース名、世代、ルールとエージェントの件数を 1 行に出す。待ち受けを開けずに終わる場合は、この行を出さない。エージェントは起動時に版、名前、データの置き場所を出す
- ルールの変更の行:バッチ操作(5.4 節)が成功するたびに、操作の出所、追加、変更、削除したルールの ID、結果の世代を 1 行に出す。出所は CLI のサブコマンド名か Web UI の操作名(追加、編集、削除、分割、統合、読み込み)で、バッチの要求の `op` で渡す。`op` は記録にだけ使い、挙動を変えない。`op` の無い要求は `api` と記録する。ID は種別ごとに 20 件までを出し、残りは件数で示す
- エージェントの出来事の行:登録、再登録、削除、鍵の再生成、stream の接続と切断、世代の配信と適用、窃取検知の警告(`ip-mismatch` は、警告の行を新しく作った回と、食い違いが連続 8 回に達した回に出す。同じ組の食い違いが続く間の更新では出さない)、`ip-mismatch` の確認済みの組の記録と破棄(5.2 節)を、エージェントの名前か世代とともに出す
- 失敗の行:WireGuard、nftables、ユーザー空間の転送、待ち受け、中継先のどれで起きたかと、元のエラーを含める。ルールの変更を SQLite に確定した後でデータプレーンへの適用に失敗した場合は、変更の行に続けて失敗の行を出す
- 状態の行:エージェントは 30 秒ごとにトンネルとルールの状態を組み立てるが、前回と同じ内容なら出さない

パケットごと、成功したフローごとの行は出さない。フローの上限での拒否と中継先への接続の失敗は、待ち受けごとに 1 分に 1 回までにする。どちらも接続のたびに起きうる失敗で、中継先が落ちている間や不正な接続が続く間に journal を埋めるためである。エージェントの stream の再接続の待ちの行も、前の行と同じ文面なら 1 分に 1 行までにし、文面が変われば、つまり待ちの長さか理由が変われば、すぐに出す。間引いた数は次に出す行に添える。`vpsd` のプロセスが止まっていてトンネルが新しい間は、待ちが 10 秒に留まり、同じ行が続くためである(5.2 節)。

エージェント用 API の TLS のハンドシェイクの誤り(net/http が書く行のうち "TLS handshake error" を含む行)も同じ考え方で間引く(2026-10-01)。この待ち受けは認証の前に TCP で届くので、相手は TLS のハンドシェイクを送らずに閉じるだけで行を出させられる。行を、証明書を理由に拒んだもの(`bad certificate`。10.2c 節の運用の案内を添える)とその他の 2 つに分け、理由ごとに 1 分に 1 回まで間引く。証明書を理由に拒んだ行を分けて持つのは、他の理由(ハンドシェイクを送らない接続など)が続いても、運用に要る案内の行が埋もれないようにするためである。理由の文面そのものを鍵にした間引きは行わない。相手が送った値(ALPN の一覧など)をそのまま埋め込む理由文があり、鍵の数を相手が増やせてしまうためである。間引いた数は次に出す行に添える。間引きの対象はこの行だけであり、同じ ErrorLog が書くほかの行(ハンドラの panic、Accept の誤りなど)はそのまま出す。

登録トークン、恒久トークン、秘密鍵、`Authorization` ヘッダ、接続文字列の全体はログに出さない。公開鍵と、証明書の指紋の先頭は出してよい。CI の検査(`scripts/check-log-tokens.sh`)は、トークンと接続文字列に触れるログの行を、人が確かめた行の一覧と照合する。

### 10.5 読み取り失敗の見せ方

サーバのデータベースやカーネルの wg 状態の読み取りが失敗したとき、失敗を「0 件」や「0」のような正常な結果に変えて見せてはならない。宛先ごとの見せ方は次のとおりである。

- サーバのログ:原因を記録する。同じ原因を要求のたびに際限なく記録しない(上の「パケットごと、成功したフローごとの行は出さない」と同じ考え方)。ただし 15 秒・30 秒間隔のような一定周期の監視ループ(5.2 節の窃取検知など)は周期そのものが頻度の上限になるので、失敗するたびに 1 行出してよい
- 管理用 API:読み取りが失敗した応答は 5xx とし、本文にどの読み取りが失敗したかを含める。世代 0 や空の一覧のような、捏造した値を 200 で返してはならない
- CLI:管理用 API の 5xx は Client がそのままエラーとして返し、コマンドは 0 以外の終了コードで止まる(10.2 節)。CLI 自身の側では別扱いを持たない
- Web UI:ページや区画が依拠する読み取りが失敗したら、そのページ・区画はエラーの状態を出す。空の一覧や「0」のような、通常時と見分けの付かない値では描かない

セキュリティに関わる読み取りは、フェイルオープンかフェイルクローズかを次のとおり分ける。

- 窃取検知(5.2 節)の 15 秒ごとの監視は、wg のピア状態かエージェント一覧の読み取りに失敗すると、その回の判定を飛ばす(フェイルオープン)。判定を続ける他の手段が無いためで、原因はログに残す。この間は新たな不一致を検知できない
- ダッシュボードとルール詳細ページに出す適用状態(ok/pending/error/agent offline)、拒否数、拒否・許可リストは、運用者が「今は問題が無い」と判断する材料である。これらの元になる読み取りが失敗したら、正常に見える値を出さず、そのページ・区画をエラーの状態にする(フェイルクローズ)
- ルール読み込みの確認ページが使う世代とハッシュ(10.1 節)は、読み取りに失敗した値をそのまま確認ページへ埋め込むと、後の一致判定を意図せず通してしまう(捏造した値どうしが偶然一致する)。世代の読み取りが失敗したら確認ページ自体を 500 で止め、確認や適用を進めない(フェイルクローズ)

一覧が 1 行の付随情報を欠いたまま続けてよいのは、その情報が他の計算に使われない、その行だけの補足であり、欠けたことをログに残すときに限る(admin_backend.go の `Agents()` が 1 エージェントの警告を読めなかった場合)。エージェントのアドレスのように他の行や他の計算(wg のピア構成、アドレスの重複割り当ての判定)に使われる値では、読み取れない・解釈できない行があれば読み取り全体を失敗として返す。半端な値で計算を続けるより、読み取りを丸ごと止める方が安全である。

`Agents()` の wg ピア状態(wgctrl の読み取り)は例外として、失敗してもエージェント一覧そのものは返す(フェイルオープン。原因はログに残す)。エンドポイント IP・最終ハンドシェイクの列が空欄になり、IP の食い違いの比較も出なくなるが、これは表示用の読み取りであり、窃取検知の正本は 5.2 節の 15 秒ごとの監視である。一覧全体を止めるほどの重みは無いと判断した。
