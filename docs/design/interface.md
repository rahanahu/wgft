## 操作インタフェース

Web UI と CLI は同じ管理用 API でルールとエージェントを操作します。
CLI の出力は英語で、Web UI は日本語と英語を切り替えます。


<a id="101-web-ui"></a>
### Web UI

- ダッシュボードは 1 カラムで、上からサーバー情報、警告、エージェント一覧、ルール一覧、適用中のファイアウォール設定の順に並べる。
  ルール一覧の上には、ルールが残っている未登録のエージェントごとに帯を出す(後述の「未登録のエージェントの帯」)。
  警告は 1 件以上あるときだけ帯状のバナーで出し、0 件のときは何も表示せず場所を取らない(ヘッダの全体ヘルスの見出しに件数が出るので十分)。
  ヘッダの全体ヘルスの隣には、警告が 1 件以上あるときだけ件数を出し、押すとバナーへ飛ぶ。
  ヘッダの全体ヘルス、エージェント一覧、ルール一覧、警告バナーは 5 秒ごとに部分更新するので、警告バナーの受け皿の要素は 0 件でも DOM に残し、0 件から増えたときに次の更新で描き直す。
  ルール一覧の畳んだグループの開閉は、部分更新をまたいで保つ。
  ファイアウォール設定はルール一覧の下に全幅で置き、既定では折りたたむ
- ヘッダの全体ヘルスの要約(2026-09-24、所有者の決定):オンラインのエージェントの数を、有効なエージェントの数に対して示します。
  無効なエージェントは分母に含めず、1 台以上あるときだけ「無効 N」を添える。
  無効は宣言どおりの状態なので、オンラインの割合を下げて故障に見せないためです。
  無効なエージェントのルールは診断の印が SKIPPED になるので、エラーの数に含まれない
- ダッシュボード以外の共通の枠のページは、上部の移動を左寄せのパンくずで行い、右上にダッシュボードへ戻るボタンを置かない。
  言語の切り替えはダッシュボードにだけ置き、他のページはダッシュボードで選んだ言語にクッキーで従います。
  POST の結果のページ(発行した接続文字列、読み込みの確認)で切り替えると、読み直しで結果が消えるためです。
  パンくずは「ダッシュボード」から今いるページまでを並べ、今いるページの項目だけはリンクにしません。
  並べる階層は実際に開けるページに限る。
  ルールの一覧のページは無いので、ルールの詳細ページは「ダッシュボード / ルール」、接続テストは「ダッシュボード / ルール / 接続テスト」、読み込みの確認は「ダッシュボード / ルールの読み込み / 読み込みの確認」、診断の画面は「ダッシュボード / 診断」と「ダッシュボード / 診断 / ルール」になります。
  ルールは「TCP 8080 → office」のように、プロトコル、受信ポート、持ち主のエージェントで呼ぶ。
  エージェントの詳細ページは「ダッシュボード / エージェント」になり、エージェントは「エージェント home」のように名前で呼ぶ
- ダッシュボード上部に vpsd と VPS 環境の情報を出す:バージョン、稼働時間、wg インタフェース/アドレス/待ち受けポート、エージェントの接続先エンドポイント、エージェント API ポート、MTU、カーネル版、nftables 版、`ip_forward` の今の値と wgft が起動時に設定したか、conntrack の UDP タイムアウト。
  `ip_forward` は今の値を先に示す(2026-09-25)。
  起動時の記録だけを示すと、稼働中に外から 0 にされた server でも「wgft が設定」と出て、転送が止まっていることが見えないためです。
  カーネルモードの server で 0 なら危険の色で示し、戻すコマンドを添える。
  今の値を返さない旧い版の server では、今までどおり記録だけを示します。
  これは構成・環境の確認用で、ヘッダの全体ヘルス(動的な健康)とは別

- エージェント一覧:名前、割り当てアドレス、最終ハートビート、処理済み世代、最終ハンドシェイク、wg ピアのエンドポイント IP、stream の接続元 IP、警告。
  名前の下に wg 公開鍵の先頭だけを小さく添え、`agent pubkey` の出力と見比べられるよう全体は title 属性(ホバー表示)に持たせる。
  両 IP の食い違いが続くと [5.2 節](control/connection.md#52-全体状態の配信とハートビート)の警告になります。
  警告の隣に「警告を消す」操作を置く。
  行にはエージェントの無効化と有効化の操作を置き、削除は置かない。
  削除は次項の詳細ページと、警告のバナー([5.2 節](control/connection.md#52-全体状態の配信とハートビート))に置く。
  行の操作は、有効なエージェントには「無効化」、無効なエージェントには「有効化」とし、ルールの行の操作と同じ語を使う(2026-09-24、所有者の決定)。
  どちらも転送を止めて設定を残すという同じ意味だからです。
  無効化は確認のダイアログを出し、このエージェントのルールがすべて転送を止めて通信中のセッションも切れることと、登録、鍵、ルールの設定が残り有効化で戻ることを示します。
  有効化は確認しません。
  エージェントの名前は詳細ページへのリンクにします。
  無効なエージェントの行は、状態を故障の色でない「無効」で示し、要対応の行にしない(2026-09-24、所有者の決定)。
  トンネルの状態、最終ハンドシェイク、最終ハートビートは参考の値として控えめな色で示し、接続していなくても警告や故障の色にしません。
  反映待ちの印も出さない。
  VPS は無効なエージェントのルールを転送しないので、世代の遅れは転送に関わらないためです。
  窃取の警告を持つ無効なエージェントの行は、要対応の行にします。
  無効の間も恒久トークンは使えるためです。
  接続していないエージェントのトンネルの状態は、[5.2 節](control/connection.md#52-全体状態の配信とハートビート)のとおり最後の報告であることが分かる色で示し、ok には見せない。
  IP の食い違いの比較も接続していない間は出さない。
  接続している間の比較は、一致、食い違い、確認済みの食い違いの 3 つを出し分ける。
  比較は [5.2 節](control/connection.md#52-全体状態の配信とハートビート)の監視と同じ正規化と組の識別で行います。
  今の組が確認済みの組([5.2 節](control/connection.md#52-全体状態の配信とハートビート))なら、IP が食い違っている事実だけを示し、警告の色にせず、要対応の行にもしません。
  確認済みの組が捨てられれば、表示は一致か食い違いに戻る。
  確認済みの組を読めないときは、確認済みでない食い違いとして警告の色で示し、読めなかったことをログに出す
- エージェントの詳細ページ(`/ui/agents/{name}`)。
  一覧の行のエージェント名から開く(2026-09-24、所有者の決定)。
  無効化と有効化の操作を置き、末尾の「危険な操作」の区画にエージェントの削除を置く。
  削除は、エージェントの名前を入力させて確認します。
  無効化と区別し、元に戻せない操作を誤って選ばせないためです。
  削除の確認には、ルールも削除する選択を置く([5.1 節](control/registration.md#51-登録))。
  ページには、一覧の行と同じ状態のほか、割り当てアドレス、公開鍵の全体、stream の接続元 IP と WireGuard のエンドポイント、最終ハートビートと最終ハンドシェイク、処理済み世代、登録の時刻、無効にした時刻、そのエージェントを持ち主とするルールの一覧を出す。
  ルールの一覧の各行は、ルールの詳細ページへのリンクにします。
  削除の区画は「危険な操作」の見出しと、枠を故障の色の線で描くボタンを持ちます。
  入力された名前は server が照合し、一致しなければ何も削除せず、同じページに誤りを示します。
  ブラウザの JavaScript は名前が一致するまで削除のボタンを押せなくするが、これは補助であり、守りは server の照合です。
  警告のバナーの削除は、確認のダイアログで確かめ、エージェントの名前をフォームに添えて送るので、同じ照合を通る。
  server はエージェントの行を消してから dataplane へ公開し、公開の失敗を誤りとして返します。
  そのため削除が誤りを返したときは、エージェントを読み直す。
  行が既に無ければ、削除は済んだが転送への反映はまだで、server が 30 秒ごとに試し直すことを示します。
  行が残っていれば、削除できなかったことを示します。
  ルールも削除する選択は、そのエージェントを持ち主とするルールが有効無効を問わず 1 本以上あるときだけ出し、本数を添える。
  選んだ削除のフォームは、ページを描いた時点のルール集合のハッシュを送る。
  server は、エージェントを削除する前に今の集合と比べ、違えば何も削除しません。
  ルールの削除のバッチにも同じハッシュを `ExpectedDigest` として渡す。
  ルールの削除だけが失敗した場合と、エージェントの削除は済んだが反映がまだの場合は、エージェントは削除したことと、ルールは残っていて転送せず、未登録のエージェントの帯から削除し直せることを示します。
  無効化、有効化、削除の POST は、他の Web UI の POST と同じく、Host の検査と他オリジン発の変更の拒否を通る([11 節](security/admin-transport.md#11-セキュリティ))
- 未登録のエージェントの帯(2026-09-24、所有者の決定):ルールが残っている未登録のエージェントごとに 1 本出す。
  帯は、エージェントの名前、削除済みであること、そのエージェントを参照するルールの本数(例:「home は削除済みです。
  このエージェントを参照するルール: 10 本」)と、その本数のルールをまとめて削除するボタンを持ちます。
  削除はルールのバッチ 1 回で行い、確認のダイアログを出す。
  同じ名前で登録し直すつもりなら、帯を残したまま待てばよい([5.1 節](control/registration.md#51-登録))。
  帯はルール一覧の区画の中の表の上に置き、ルール一覧と一緒に 5 秒ごとに描き直す。
  帯は故障ではないので、警告の色にしません。
  帯の本数は、そのエージェントを参照するルールを有効無効を問わずに数え、一括削除もそのすべてを消す。
  一括削除のフォームは、帯が示した本数と、帯を描いた時点のルール集合のハッシュ(`proto.RulesDigest`)を送る。
  server は、そのエージェントが登録されていれば何も削除しません。
  帯を描いた後に同じ名前で登録し直した場合に、動いているエージェントのルールを消さないためです。
  今の本数が送られた本数と違う場合と、ルール集合が送られたハッシュと違う場合も、何も削除しません。
  確かめたより多いルールや、確かめた後に変わったルールを消さないためです。
  ハッシュの照合は、読み込みの適用と同じくバッチの `ExpectedDigest`([5.4 節](control/batches.md#54-ルールのバッチ操作))で、バッチのトランザクションの内側で行います。
  登録の確認からバッチまでのごく短い間に同じ名前で登録し直した場合は見分けない。
  登録はルール集合を変えないのでハッシュでは捉えられず、そこで消えるのは利用者が削除を確かめたルールそのものなので、受け入れる
- 接続文字列の発行
- ルール一覧と追加、編集、削除、有効無効の切り替え。
  各ルールにエージェント側の適用状態と、接続元制限で拒否した累積数を表示します。
  適用状態は無効なルールなら常に disabled とし、有効なルールは持ち主のエージェントの直近のハートビート([5.2 節](control/connection.md#52-全体状態の配信とハートビート))から次の優先順位で判定する:エージェントが無効なら「エージェント無効」、未登録なら「エージェント未登録」(どちらも灰色で示し、他の適用状態の頭の ● の代わりに横棒を添え、エラーの数に含めません。
  [5.1 節](control/registration.md#51-登録))、未接続なら agent offline、エージェントの処理済み世代が最新より古い(そのルールをまだ報告していない場合を含む)なら pending、それ以外はエージェントが報告したそのルールの状態に従い ok なら applied、error なら error とします。
  error の理由の文は一覧には出さず、ルールの詳細ページと診断の画面で読みます。
  適用状態の右には診断の印を置く(後述の「ルール一覧の診断の印」)。
  一覧は `group` ごとの見出しで畳めるように区切り(見出しにグループ名と件数、折りたたみ可)、`group` の空いたルールは「その他」に入れる。
  畳んだグループでも見出しに error のルール数を出す。
  ヘッダの全体ヘルスの要約にも error のルール数を含めます。
  この 2 つの error のルール数は、適用状態ではなく、診断の印が FAILED のルールの数です。
  各ルールには `note` を薄字の副題として常に添える。
  追加フォームで「説明」(`note`)と「グループ」(`group`。
  既存グループの候補を出しつつ自由入力)を設定できます。
  追加フォームの「無効のまま追加」は CLI の `rule add --disabled` にあたる
- ルール一覧の診断の印(2026-09-24、所有者の決定):状態の列の中で、適用状態の右に印を 1 つ置く。
  新しい列は作りません。
  印は、ルールの総合判定([10.2a 節](diagnosis/server-observations.md#102a-転送の診断-server-doctor))を [10.2d 節](web-doctor.md#102d-web-ui-の診断の画面)の経路の図と同じ関数で写したものです。
  画面が自ら決めるのは、UNKNOWN の印に添える節点と、持ち主のエージェントが未登録のルールの扱いの 2 つだけである([10.2d 節](web-doctor.md#102d-web-ui-の診断の画面))。
  OK は緑の円と ✓、FAILED は赤の八角形と ✕ に止まった節点の名前、UNKNOWN は黄のひし形と ? に最初の UNKNOWN の節点の名前、SKIPPED は灰色の横棒の円とします。
  無効なルールと、無効なエージェントのルールは SKIPPED になります。
  図形は診断の画面の節点と同じものを使います。
  記号は読み上げの対象から外し、「診断: FAILED at WireGuard」のような文を読み上げに渡す。
  状態の語と節点の名前は英語のままにする([10.2d 節](web-doctor.md#102d-web-ui-の診断の画面))。
  印は、診断の画面のそのルールのページへのリンクです。
  持ち主のエージェントが未登録のルール、つまり `agent.connection` の reason が `agent_not_registered` のルールは、`server doctor` では FAILED だが([5.1 節](control/registration.md#51-登録))、印を灰色の「エージェント未登録」とし、エラーの数に含めません。
  ヘッダの全体ヘルスとグループの見出しの error のルール数は、印が FAILED のルールを数えます。
  赤い ✕ の行が「エラー 0 件」の見出しの下に並ばないようにするためです。
  適用状態と印は出どころが違い、食い違うことがあります。
  例えば、適用済みのルールでもハンドシェイクが古ければ印は ✕ WireGuard になります。
  どちらも書き換えずに並べる。
  エージェント一覧には印を置かない。
  ダッシュボードとその部分更新は、ルールとエージェントを診断と同じ 1 回の読み取り([10.2d 節](web-doctor.md#102d-web-ui-の診断の画面))から組み立てる。
  適用状態と印と件数は同じ時点の証拠から作られ、印のための読み取りは増えません。
  疎通の確認は呼びません
- ルールの詳細ページ(`/ui/rules/{id}`)。
  一覧の各ルールの「詳細」から開きます。
  ルールの要約に一覧と同じ適用状態(理由を含む)を出し、有効無効の切り替えの下に、設定、アクセス制御、ルール操作の 3 つの区画をこの順に置く。
  設定の区画は group、note、レート制限を 1 つのフォームにまとめ、末尾の 1 つの保存ボタンで保存します。
  アクセス制御の区画の拒否リストと許可リストは、追加と「外す」のたびにその場で保存します。
  ルール操作の区画の分割と統合は、ボタンを押した時点で実行します。
  保存は管理用 API のバッチ 1 回(`upsert`、分割は 2 件の `upsert`、統合は `upsert` と `delete`)で行います。
  group、note、接続元制限、レートの変更では ID も世代も変わらない([5.3 節](control/rules.md#53-ルールのスキーマ))。
  保存の後は同じ詳細ページを表示する(分割の後は縮んだ元のルールの、統合の後はこのルールの、どちらも ID が変わらない詳細ページ)
  - 設定のグループと説明:group と note は転送に関わらないので、既存ルールに対して ID そのままで後付け・変更できます
  - 設定のレート制限:`per_source_rate`(1 つの接続元からの新しい接続)、`new_flow_rate`(ルール全体の新しい接続)、`packet_rate`(パケット。
    通信中のデータも含めて数える)の 3 つに、回数、単位(`second` から `week`)、「制限しない」を置く。
    `per_source_rate` と `new_flow_rate` が数えるのは新しい接続(TCP は 1 本のコネクション、UDP は初めて見た送信元アドレスとポートの組)であり、開いている接続は数えません。
    `packet_rate` は通信中のデータも含めて数えるため誤読されやすく、区画を折りたたんで値が入っているときだけ開きます。
    値が入っている欄には読み上げの一文(例:「1 つの接続元から 1 分に 10 本まで」)を添える。
    「制限しない」は値を外す。
    TCP のルールでは `packet_rate` を保存しても効かないこと([7a.9 節](policy.md#7a9-admission-policy-のコンパイラ))を、TCP のルールに限りその欄に添える。
    入力欄自体は無効にせず、他の欄を保存しても保存済みの `packet_rate` は消さない。
    区画の見出しには、このルールの累積 drop 数を一覧と同じ値で添える
  - 設定の保存:フォームは描いた時点の保存値を hidden で持ち、保存はそれと比べて利用者が変えた欄だけを今のルールに当てはめる。
    比べる単位はルールの欄(group、note、`per_source_rate`、`new_flow_rate`、`packet_rate`)で、レートは回数と単位を 1 つの値として扱う。
    回数と単位を別々に当てはめると、どちらの側も選んでいないレートができうるためです。
    レート欄は保存値で埋めて描くので、説明だけを変えた保存がレート欄の入力で拒まれることはありません。
    入力に誤りがあれば何も保存せず、その欄に誤りを示し、すべての欄の入力を残して描き直す。
    利用者が変えた欄が、ページを描いた後に別の経路(CLI や別のタブ)でも別の値に変わっていれば、上書きせず何も保存しません。
    その欄に今の値を示し、利用者の入力を残し、hidden の保存値を今の値に改めて描き直す。
    確かめてから保存し直すと利用者の値が入ります。
    利用者が変えていない欄は、別の経路で変わっていても今の値のまま残る。
    確定の呼び出しには読み取った時点のルール集合のハッシュを `ExpectedDigest`([5.4 節](control/batches.md#54-ルールのバッチ操作))として渡し、読み取りから確定までの間の割り込みも拒みます。
    拒まれたときは入力を残して描き直し、保存し直すとその時点の値と改めて比べる
  - アクセス制御の拒否リスト(`source_deny`):各 CIDR の行に「外す」を置く。
    追加は複数行の入力で受け、1 行に 1 つの CIDR かアドレスを書きます。
    前後の空白と空行は無視し、単独のアドレスには `/32` を補い、既にある CIDR は重ねて加えない。
    解釈は CLI の `rule deny add` と同じです。
    IPv4 の CIDR として読めない行が 1 つでもあれば何も保存せず、その行の番号と内容を示し、入力を残したまま同じページを表示し直す
  - アクセス制御の許可リスト(`source_allow`):拒否リストと同じ形です。
    空のリストへの最初の追加は他の接続元を全部落とし、最後の 1 件を外すと全接続元に開くので、どちらも確認のダイアログを出す
  - ルール操作の分割:`listen_port` が範囲のルールにだけ出す。
    分割する位置は範囲の 2 番目から末尾までのポートから選ぶ。
    結果の 2 つのルール(受信範囲と実効宛先)は、送信前に JS がその場で計算して示します。
    組み立てと検査は CLI の `rule split` と共有する([5.4 節](control/batches.md#54-ルールのバッチ操作))
  - ルール操作の統合:同じプロトコルの他のルールから、`listen_port` が直前・直後で隣接するものを探し、[5.4 節](control/batches.md#54-ルールのバッチ操作)の統合の条件をすべて満たすものだけを候補として、それぞれに「このルールと統合」ボタンを出す。
    候補が 1 つも無く、隣接するルールがあるときは、直前を優先してその 1 件の理由(例:拒否リストが違う)を示します。
    組み立てと検査は CLI の `rule merge` と共有し、この画面のルールが `id1` にあたる(削除されるのは相手)
- TCP ルールの疎通確認。
  `vpsd` から `10.200.0.x:listen_port`(エージェントのリスナー)に接続し、エージェントの中継を通して `target` に届くかを見る。
  `target` は LAN アドレスで `vpsd` からは経路がないため、直接は試しません。
  UDP は送信だけでは失敗が分からないので持たず、エージェントの適用状態で代える。
  持ち主のエージェントが無効か未登録のルールには、ルール一覧の接続テストのボタンを出さない。
  server がそのルールの疎通確認を拒むためである([5.1 節](control/registration.md#51-登録))
- ルール一覧の見出しにある書き出しと読み込み(`GET /ui/rules/export`、`/ui/rules/import`)。
  書き出しは現在の全ルールを、CLI の `rule import` が読む配列と同じ形の JSON でダウンロードさせる。
  読み込みはアップロードした内容をまだ適用せず、現在のルールと ID で突き合わせた差分の確認ページを表示します。
  差分の計算(追加・変更・削除・変わらないの判定と、変更したルールのフィールドごとの説明)は `proto.DiffRules` が持ち、削除対象の抽出は `proto.DeletedIDs` が持ちます。
  CLI の `rule import` もこの 2 つを使い、独自の突き合わせを持ちません。
  拒否/許可リストの変更は件数でなく、増えた CIDR と減った CIDR(例:`+198.51.100.0/24 -203.0.113.0/24`)で示します。
  件数だけでは、同じ件数のまま内容が入れ替わる変更(1 件を別の CIDR に差し替えるなど)が変わらないと見えてしまうためです。
  確認ページは、削除の行に通信中のセッションが切れる旨の注記を添え、適用が拒まれる理由を一覧にして適用ボタンを出さない。
  一覧にする理由は、`Daemon.Batch` が保存の前に行う判定のうち、管理用 API から観測できる範囲と同じものです。
  内訳は、未登録のエージェントを指すルール、`Rule.Validate` に落ちるルール(今のルールから変わっていない行は除く。
  [5.4 節](control/batches.md#54-ルールのバッチ操作))、ID の重複、予約ポート(WireGuard、管理用 API、エージェント用 API)との重なり、`listen_port` の重なりです。
  後の 3 つは `proto.ValidateUpsert` が読み込み後の集合全体に対して判定します。
  予約ポートの集合は、`Daemon.reserved` を組むのと同じ規則で `admin.ServerInfo` から組む。
  この読み取りに失敗した場合は、予約ポートを空として続行せず、確認そのものを止めます。
  空として続行すると、`Batch` が拒む読み込みを受理されると示すことになるためです。
  他テーブルの DNAT との衝突と bind 中のポートの検査(`internal/vpsd/apply.go` の `checkRule`)は、root と `nft` を必要とし、確認を描く層からは呼べないので確かめない。
  これは CLI の `--dry-run` と同じ確かめない範囲です。
  適用は、アップロードした内容(ID を確定させた後の JSON)と、確認ページを描いた時点の世代、およびその時点のルール集合全体のハッシュ(`proto.RulesDigest`)を hidden で持たせて送る。
  `group`、`note`、接続元制限、レートだけの変更は世代を上げない([5.3 節](control/rules.md#53-ルールのスキーマ))ため、世代の一致だけでは別経路(CLI など)からの変更を見逃すので、ハッシュも一致させる。
  適用の直前に今の世代とハッシュを取り直し、どちらかが確認ページを描いた時点と違えば何も変えず、アップロードし直すよう求めます。
  この事前の取り直しと、実際にバッチを確定させる呼び出しとの間にもわずかな競合可能期間が残るため、確定の呼び出し自身にも同じハッシュを `ExpectedDigest`([5.4 節](control/batches.md#54-ルールのバッチ操作))として渡し、バッチ側のトランザクションの内側で読み取りと確定を割り込みなく結びつける。
  事前の取り直しをすり抜けた食い違いは、この照合の誤り(`ErrBatchConflict`)を同じ「アップロードし直す」画面に写して防ぐ。
  削除を含む適用には `data-confirm` を付ける

<a id="102-cli"></a>
### CLI

CLI は管理用 API を叩く薄い層で、Web UI と同じことができます。

```
wgft agent join-string --name home
wgft agent rotate-key
wgft rule add --agent home --udp 2456-2457 --to 192.168.1.20:2456 --group game --note "週末サーバ"
wgft rule add --agent home --tcp 443 --to 192.168.1.30:443 --proxy --proxy-protocol
wgft rule set r_01J --group friends --note "公開サバ"
wgft rule deny add r_01J 203.0.113.0/24
wgft rule ls
wgft server nft
```

`rule ls` は `group` ごとにまとめて表示し、各ルールの `note` も出す。
`rule add` の `--group` と `--note` は省略できます。
`rule set` は既存ルールの `group` と `note` だけを ID そのままで変える(転送に影響せず世代も上げない)。
`--group ""` で外す。

ルールの ID の表示と受け取りの境界を次のとおり定める(2026-09-25、所有者の決定)。
表の ID の列、`status` の行の要約、診断の一覧の行のように、ルールを見分けるために示す ID は、先頭 12 文字に省略記号 `…` を付けた短い形でよい。
そのまま打つコマンドとして示す場所には、完全な ID を使います。
診断の次の一手(人向けの出力の `Check:` の行と `--json` の `next`、Web UI の同じ所見)と、`server doctor` の終了の 1 行が名指すルールがこれに当たる。
短い形をコマンドに埋めると、打った運用者が見つからないという誤りに当たるためです。
ルールの ID を受け取るコマンドは、完全な ID のほかに、前方一致が 1 つだけの ID の先頭を受け取り、末尾の省略記号 `…` か `...` を落としてから照合します。
表の短い形をそのまま貼っても通すためです。
ただし、`rule import` と管理用 API は [5.3 節](control/rules.md#53-ルールのスキーマ)の範囲の任意の文字列を ID として受けるので、省略記号で終わる ID もありうる。
そこで、照合を次の順に行います。
まず生の入力と完全に一致する ID を探し、あればそれを指す。
無ければ、末尾の省略記号を落とした残りで始まる ID を探す。
1 つだけならそれを指し、2 つ以上なら候補の完全な ID を挙げて拒みます。
省略記号の付いた入力では、残りと完全に一致する ID があっても、それを先に指さない(2026-10-03、所有者の決定)。
表の短い形の省略記号は、その先に文字が続くことを示します。
残りと完全に一致する ID を先に指すと、表の行とは別のルールを指し得ます。
例えば ID が `aaaaaaaaaaaa` と `aaaaaaaaaaaab` の 2 本あると、表は後者を `aaaaaaaaaaaa…` と示します。
この形を貼った入力は、前者を指さずに 2 本の候補を挙げて拒みます。
省略記号の無い入力は、生の入力の完全一致が先に立つ。
`web` と `webserver` の 2 本があると、`web` は `web` を指し、`web…` は 2 本の候補を挙げて拒みます。
省略記号を落とした残りが空になる入力、つまり空の文字列と省略記号だけの入力は、ルールが 1 本しか無い配置でもそのルールを指さずに拒みます。
前方一致に求める長さは、省略記号の有無で変えない(2026-10-03、所有者の決定)。
12 文字は表示で省略する長さであり、ルールの ID の最小の長さでも、受け取る先頭の最小の長さでもない。
省略記号の無い短い先頭を受けながら、同じ先頭に省略記号を付けた入力だけを拒むと、利用者から見て一貫しないためです。
このため、`r_...` のようなプレースホルダを貼った入力は、`r_` で始まるルールが 1 本だけの配置ではそのルールを指す。
省略記号の無い `r_` も同じルールを指す。
ID はほぼ任意の文字列なので、URL のパスに埋めるときは、`url.PathEscape` でパスの 1 つの区切りとして escape します。
Web UI のリンクとフォームの送信先、保存の後の戻り先、CLI が管理用 API に出すリクエストのどれも同じである(2026-09-30)。
未登録のエージェントの帯の削除のボタンの送信先には、ルールの `agent` を埋めるので、同じく escape します。
書き込むルールの `agent` は登録済みのエージェントの名前でなければならず、その名前は [5.1 節](control/registration.md#51-登録)の文字種に従います。
このため、帯の名前に `/` や `..` が入るのは、この文字種の検査ができる前に保存されたエージェントの名前だけであり、帯の送信先の escape はその名前に備える多重の守りです。
escape しないと、`/`、`..`、`?` を含む ID の行のボタンが、ブラウザの解決によって別のルールやエージェントの経路へ送信します。
ID と `agent` は、`.` と `..` を受けない(2026-09-30、所有者の決定)。
ブラウザは WHATWG URL 標準に従い、`%2E` と `%2E%2E` も区切りの `.` と `..` として扱う。
このため escape しても、そのルールやエージェントの Web UI のボタンが別の経路へ送信します。
`agent` については、登録済みのエージェントの名前であることの検査がこの 2 つを既に拒んでいるので、`.` と `..` を拒むのは多重の守りです。
区切りとして拒むのはこの 2 つだけで、`...` や `.a` のような文字列は受ける。
拒むのはルール単体の検査(`proto.Rule.Validate`)なので、CLI、管理用 API、Web UI、取り込みのどれにも効く。
この検査の前に保存された `.` や `..` のルールは、触らない限り読み込みと転送を続け、他のルールの変更も妨げない。
そのルール自身の変更は拒み、削除はできます。
ルールのバッチの検査が、変えていない行には検査を掛け直さないためである(`proto.ValidateUpsert`)。
`pathSegment` は `.` と `..` を今も `%2E` の形にします。
CLI が、拒むようにする前に保存された `.` や `..` のルールを管理用 API で指すためです。

CLI が管理用 API に出す HTTP リクエストには固定のタイムアウト(30 秒)があります。
サーバが応答しない場合は待ち続けず、そのアドレスと待った時間を添えたエラーで止まります。
管理用 API の応答はどれも束縛されている(バッチの本文の上限、ルール一覧、TCP の疎通確認は server 側の dial の期限が既定 5 秒)ので、この時間はどの正当な呼び出しにも十分な余裕があります。
`server nft` は適用中の `wgft` テーブルをそのまま表示し、手で確認したいときに使います。
