## 7. データプレーン(自宅側)

エージェントは、ユーザー空間モードとカーネルモードの 2 つのモードを持つ。既定はユーザー空間モードであり、`WGFT_MODE=kernel` を明示した Linux のエージェントだけがカーネルモードで動く(11a 節)。モードはエージェント全体で 1 つであり、ルール単位で混ぜない。以下の箇条と収束の規則はユーザー空間モードのものであり、カーネルモードは 7b 節に定める。

- 動作条件:エージェントのプロセスは特権も `NET_ADMIN` も要らず、Docker のコンテナ 1 つでも動く。ただし、ホストが次の項のソケットのバッファの条件を満たすことを要する。コンテナで動かす場合、条件を満たすのはコンテナのホストの設定である(後述の「コンテナでのバッファの条件」の項)
- ソケットのバッファの条件:ユーザー空間モードは、WireGuard の UDP ソケットが、wireguard-go の要求する受信と送信のバッファを実際に得ることを動作条件とする。推奨ではなく条件である。後述の「netstack の出力」の構造は、この条件を満たす環境での評価に基づいて採用しており(改訂の記録 2026-09-27)、満たさない環境での過負荷の見え方は未確認であるためである。条件は `vpsd` のユーザー空間モード(6.3 節)にも同じく当てはまる
- Linux でのバッファの条件:wireguard-go は、UDP ソケットを開くときに受信と送信のバッファをそれぞれ 7 MiB 要求する。カーネルはこの要求を `net.core.rmem_max` と `net.core.wmem_max` の値で切り詰める。wireguard-go は続けて `SO_RCVBUFFORCE` と `SO_SNDBUFFORCE` でも同じ値を要求し、どちらの誤りも無視する。この要求は、初期の user namespace で `CAP_NET_ADMIN` を持つプロセスでは上限を超えて通り、持たないプロセスでは失敗してバッファは上限の値に留まる。コンテナや LXC ベースの VPS の中で与えた `CAP_NET_ADMIN` は、そのコンテナの user namespace の中に限られるので、この要求を通さない(6.1 節)。wireguard-go はそのことを報告しない。Linux はソケットのバッファの大きさを要求の 2 倍に設定し、`getsockopt` もその 2 倍の値を返す。この大きさはソケットに溜められる量の上限であり、ソケットは開いた時点でその量のメモリを使うのではない。ラボでは、14680064 を得たソケットが、何も溜めていない間は `ss -m` で 0 バイトを使っていた。溜まったときに使うのはカーネルのメモリであり、ソフト上限の式の外の項である(後述の「プロセス全体のメモリの上界」の段落)。Linux での条件は、実際の WireGuard のソケットの実効の受信と送信のバッファが、どちらも 14680064 バイト以上であることとする(2026-09-27、所有者の決定)。7 MiB の要求が通ったソケットの実効の値がこれに当たる。判定に sysctl の値を使わないのは、初期の user namespace で `CAP_NET_ADMIN` を持つプロセスが sysctl の値より大きいバッファを得られるためである。その権限を持たないプロセスがこの値を得るには、`net.core.rmem_max` と `net.core.wmem_max` がどちらも 7340032 以上である必要がある。エージェントは capability を持たずに動くので、エージェントのホストではこの sysctl の値が得られるバッファを決める。wgft はこの sysctl を書き換えない。書き換えはホスト全体の設定の変更であり、wgft が管理する範囲の外にあるためである
- バッファを測る時点:エージェントとユーザー空間モードの `vpsd` は、トンネルを立てるたびに自分の WireGuard のソケットを測る(2026-09-27、所有者の決定)。ソケットのバッファは開いたときに決まり、後から sysctl を変えても変わらない。一方で、エージェントは同じプロセスの中で、起動、`rotate-key`、トンネルの作り直し、wg 設定の変更のたびに新しいソケットを開く。起動のときだけ測ると、後から開いたソケットの値を見落とす。`rotate-key` で開き直したソケットが、その時点の sysctl の値で新しいバッファを得ることは、ラボで確かめた。作り直しと wg 設定の変更の経路は、トンネルを立てる同じ関数を通ることをコードで確かめたが、その経路で開き直すことはラボで観測していない
- バッファの測り方:トンネルを立てたプロセスは、自分のファイル記述子のうち、wireguard-go の `IpcGet` が返す listen port に bind した UDP ソケットを探し、`getsockopt` で `SO_RCVBUF` と `SO_SNDBUF` を読む。IPv4 と IPv6 のソケットのうち小さい方の値を使う。wireguard-go の UDP バインドは置き換えず、ソケットの値も変えない。この読み取りは権限を要らない。付属の systemd の unit と同じ設定の砂箱の中と、付属の compose ファイルのコンテナの中でも読めることを確かめた。測る手段を持つのは Linux だけである
- 条件に届かないときの知らせ方:エージェントと `vpsd` は、測った値が条件に届かない場合と測れなかった場合に、英語の警告の行をログに出す。行は丸括弧を使わず、測った値、条件の値、2 つの sysctl に書く値を含む。警告は 1 分に 1 回までに絞り、トンネルを続けて作り直しても行が並ばないようにする。wire protocol には載せず、`wgft status` を degraded にもしない。起動は拒まない。拒むと、既定の値が条件に届かないディストリビューションで、更新しただけの配置が止まるためである。エージェントの測った値は、`agent doctor` の `tunnel.socket_buffers` が示す(10.2c 節)
- `server check` が示す材料:`server check` は、`vpsd` のソケットを測れない。これから起動する `vpsd` の権限も知らない。付属の systemd の unit は `CAP_NET_ADMIN` を与えるが、その権限で上限を超えられるのは VM や専用のホストの上だけである。LXC ベースの VPS やコンテナの中では超えられず、独自の配置では権限を与えないこともある。そのため `server check` は判定をせず、人が判断する材料として 3 つの値を示す。今の `net.core.rmem_max` と `net.core.wmem_max`、`CAP_NET_ADMIN` を持たないプロセスが得る値、条件の値である。2 つ目の値は、`SO_RCVBUF` と `SO_SNDBUF` だけで 7 MiB を要求する試しのソケットで得る。FORCE を使わないので、root で実行しても権限を持たないプロセスの値になる。wireguard-go と同じ手順の試しのソケットは使わない。`server check` は root で実行することが多く、root ではその手順の FORCE が通って、必ず条件を満たして見えるためである。付属の unit を理由に示す材料を省くこともしない。決め手は、稼働中の `vpsd` が自分のソケットを測った値とその警告の行である。管理用 API、`server doctor` の JSON、Web UI には何も加えない。終了コードは他の所見と同じく 0 のままである(7a.11 節)
- コンテナでのバッファの条件:コンテナの中のプロセスは、この 2 つの sysctl を変えられない。値はホスト全体で 1 つであり、初期の network namespace の側でだけ変えられる(6.1 節)。コンテナで動かすエージェントと `vpsd` では、コンテナのホストがこの sysctl を設定し、条件を満たしたかどうかは、コンテナの中の実際の WireGuard のソケットの実効の値、たとえば `agent doctor` で確かめる(2026-09-27、所有者の決定)。付属の compose ファイルは、uid 65532 と `cap_drop: [ALL]` の非特権のまま保つ。`CAP_NET_ADMIN` をコンテナに加えることと root で動かすことは、この条件の解決策にしない。確かめた範囲は次のとおりである。ラボの Debian 12 の VM(カーネル 6.1)では、Docker 20.10 で付属の `agent.compose.yaml` を動かした。イメージは、配布物と同じ最終段でラボのバイナリから作った。エージェントは、ホストの既定の値のまま `agent doctor` でこの条件の未達を示し、ホストで両方の sysctl を 7340032 にしてコンテナを再起動すると条件を満たした。同じ作り方のイメージで付属の `server.compose.yaml` を動かした `vpsd` も、既定の値では警告を出し、ホストの値を上げて再起動すると出さなかった。同じ VM で、Docker の `--sysctl` による設定は失敗した。実装の前には、wireguard-go と同じ手順で UDP ソケットを開いて値を読む使い捨てのプログラムで、次を確かめた。同じ Debian 12 の VM の rootful の podman 4.3 でも、ホストの値を上げるとコンテナの中のソケットが条件を満たした。Fedora 44 のホスト(カーネル 7.2)の Docker 29 では、`--sysctl` と特権のコンテナの中からの書き込みがどちらも拒まれ、付属の compose ファイルと同じ権限のコンテナはホストの値の 2 倍を得た。user namespace を分けた `unshare` と rootless の podman では、`CAP_NET_ADMIN` を持たせても FORCE が拒まれた。非特権の Incus のコンテナ(Incus の既定のままで、security の設定も nesting も無い)では、付属の `agent.service` で capability を持たずに動くエージェントが、既定の値では条件の未達を示し、コンテナのホストで両方の sysctl を 7340032 にしてエージェントを再起動すると条件を満たした(改訂の記録 2026-09-27)。Proxmox VE のコンテナ、nesting を有効にしたコンテナ、rootless のコンテナ、非特権の LXC や Incus のコンテナの中のユーザー空間モードの `vpsd` は対象から外さないが、条件を満たせるかどうかは未確認である
- Linux 以外でのバッファの条件:Windows と macOS の wireguard-go も 7 MiB を要求するが、FORCE を使わない。得られる値を決める仕組み、その値での過負荷の見え方、2 倍の値を報告するかどうかは未確認である。この 2 つの OS には、Linux の仕組み(sysctl、FORCE、capability、要求の 2 倍の報告)を当てはめない。wgft はこの 2 つの OS でソケットを測らず、試しのソケットによる予測も条件の判定に使わない。`agent doctor` の `tunnel.socket_buffers` は NOT TESTED を示す
- wireguard-go と gVisor の netstack でユーザー空間にトンネルを持つ
- IPv4 の断片の入口:TUN の `Write` は、受け取った IPv4 の断片をすべて wgft の再組み立ての表(`internal/nettun`)に渡し、完成した datagram だけを netstack に渡す。断片を gVisor の再組み立てには渡さない。固定版の gVisor の再組み立ては、断片化された datagram ごとに期限の処理のタイマーを取り消さずに残し、そのタイマーは期限の 30 秒まで生きるので、保持する量が上限ではなく断片の届く速さで決まるためである(改訂の記録 2026-09-27)
- 再組み立ての表:Device ごとに 1 つで、未完成の datagram 128 件、保持する断片 512 個、保持 byte 4 MiB を上限とし、未完成の datagram の期限は 30 秒である。保持 byte は、表の固定の管理領域、保持する断片の複製、完成した datagram の複製 1 つ分を数える。数えた byte は Go のヒープの実際の費用ではない。値は設定項目にしない。表は 1 秒ごとに期限を過ぎた項目を消す。`vpsd` のユーザー空間モードでは、表を全エージェントのピアで共有する
- 表が満杯のときの扱い:新しい断片に、項目、断片の枠、保持 byte、完成した datagram の複製の余地のどれかが足りないときは、その断片と同じ datagram 以外で最も古い未完成の項目を 1 件ずつ消して空きを作る。消せる項目が無いとき、つまり 1 つの datagram だけで上限に届くときは、その断片を捨てる。新しい断片を拒む方式は採らない。その方式では、損失で断片の欠けた少数の datagram が表を期限の 30 秒占め、その間は全ルールの断片化された UDP が完成しなくなるためである。1 つの datagram の断片が続けて届けば、表が満杯でも完成する。同じ datagram の断片の間に表を 1 周させる数の断片が挟まると、その datagram は完成しない
- 断片の検査:ヘッダーの checksum、長さ、flag、option の形を検査し、重なる断片と矛盾する断片はその datagram ごと捨てる。後続の断片は copy bit の立った option だけを持てる。完成した datagram のヘッダーには最初の断片のヘッダーを使い、どれかの断片が CE なら ECN を CE にする
- 断片に対する ICMP:期限を過ぎた項目は、最初の断片を持ち、宛先がこの Device のアドレスであるときだけ、gVisor の `OnReassemblyTimeout` に渡して Time Exceeded を送る。追い出した項目には送らない。期限を過ぎて消去を待つ間(最大 1 秒)に追い出された項目にも送らない。option の不正な断片には、wgft が組み立てた Parameter Problem を返す。送らない条件、引用の長さ、送る速さの制限は、同じ入力を与えたときの固定版の gVisor の結果を試験の期待値にしている。既知の差は 3 つある。1 つ目として、後続の断片が copy bit の無い option を持つと、wgft はその断片を捨て、option の型の byte を指す Parameter Problem を返す。pointer の値は IPv4 ヘッダーの先頭からの offset で、この場合は 20 である。固定版の gVisor は、正しい Timestamp か Record Route の option を持つ後続の断片を受け入れて組み立てた(試験で同じ入力を与えて確かめた)。2 つ目として、Timestamp の flags が不正な後続の断片には、固定版の gVisor は flags の byte を指す pointer 23 を返し、wgft は 1 つ目と同じ pointer 20 を返す。3 つ目として、最初の断片が copy bit の無い option を、長さは正しく中身が不正な形で持つとき、固定版の gVisor はその断片に直ちに Parameter Problem を返して捨てる。wgft は option の中身を検査せずにその断片を保持する。datagram が完成すると、gVisor が組み立てた datagram を検査し、それを引用して同じ pointer の Parameter Problem を返す。完成しなければ、期限の Time Exceeded になる。どちらの場合も datagram は届かない。wgft はこの 3 つの差を試験で固定し、gVisor の option の検査の手順を写さない。断片を ICMP を送らずに黙って捨てる方式にはしない
- TUN の `Write` の誤り:`Write` はバッチの中の 1 件を処理できなくても残りを処理し、受け取った件数と最初の誤りを返す。断片を捨てたことと、後述の UDP の受信の会計が datagram を捨てたことは、誤りとして返さない。wireguard-go は `Write` の誤りをバッチごとに回数を絞らずログへ出すので、断片や UDP の入力でログが埋まらないようにするためである。誤りを返すのは、閉じた後の `Write` と IPv4 でない packet だけである
- IPv4 の Total Length:TUN の `Write` は、IPv4 のヘッダーの Total Length より後ろの byte を切り捨ててから扱う。固定版の wireguard-go は `Write` に渡す前に同じ切り捨てを行うが、wgft はその挙動に頼らない。gVisor は Total Length より後ろの byte を読まず、後述の UDP の受信の会計は gVisor に渡す長さで予約するので、2 つの長さを wgft の側で一致させるためである
- ICMP の誤りの入口:TUN の `Write` は、完成した IPv4 の datagram のうち ICMP の誤り(Destination Unreachable、Source Quench、Redirect、Time Exceeded、Parameter Problem)を、外側の送信元が引用された datagram の宛先と一致するときだけ netstack に渡す。断片で届いた誤りは再組み立ての後に確かめる。引用の宛先を読めない短い誤りも捨てる。`vpsd` のユーザー空間モードでは全エージェントのピアが 1 つの Device を共有し、wireguard-go が確かめるのは、外側の送信元が送ってきたピアの AllowedIPs(そのエージェントのトンネルのアドレス 1 つ)に入ることだけである。固定版の gVisor は、外側の送信元と引用の宛先の一致も、引用された TCP のシーケンス番号も確かめない。この確認が無ければ、あるエージェントは、`vpsd` と別のエージェントの間のフローを引用した Port Unreachable でそのフローの UDP のセッションを閉じさせ、Fragmentation Needed でそのフローの TCP の segment を縮められる。トンネルの中に途中のルータは無いので、正当な誤りを出すのは引用された datagram の宛先、すなわち相手のエージェントのトンネルのアドレスである。カーネルモードのエージェントが転送した先の自宅の LAN で生まれた誤りは、エージェントのホストの conntrack が、引用の宛先と外側の送信元の両方をエージェントのトンネルのアドレスに書き換えてから wgft0 へ送るので、この確認を通る。ラボで、LAN のホストが返した Port Unreachable がこの形で wgft0 に出ることと、`vpsd` の中継がその誤りを受けてセッションを閉じることを確かめた。エージェントのホスト自身が転送の途中で出す Fragmentation Needed が同じ形になるかは未確認である。
- Fragmentation Needed の MTU の下限:TUN の `Write` は、next-hop MTU が 552 より小さい Fragmentation Needed を、送信元によらず捨てる。固定版の gVisor は下限を持たず、68 を受けると、その TCP の接続の segment の payload を 1 byte まで縮める。552 は Linux の既定の `min_pmtu`(`net.ipv4.route.min_pmtu`)で、カーネルモードの `vpsd` のホストが PMTU を下げる下限と同じ値である。IPv4 の最小の再組み立ての大きさの 576 は採らない。Linux が受け入れる 552 から 575 の値まで捨てる理由が無いためである。値は設定項目にしない。LAN の MTU が 552 以上であれば、この下限は誤りを捨てないので、PMTU の発見は今までどおり働く。宛先のホスト自身のインタフェースの MTU が 552 より小さい場合は、そのホストが SYN-ACK で示す MSS が `vpsd` の segment を抑えるので、この誤りに頼らない。552 より小さいのが途中の区間だけの場合は、`vpsd` の側の PMTU を下げられないので、大きな segment は届かない(7b.7 節の、LAN の側の小さい MTU の区間と同じ場合である)。Linux は `min_pmtu` より小さい MTU を受けると、誤りを捨てずに PMTU を 552 に固定し、以後は DF を立てずに送るので、途中のルータの断片化で届く。wgft は誤りを捨てるので、この点で Linux と異なる
- 捨てた ICMP の誤り:ICMP を返さず、ログにも出さない。gVisor が自分で捨てる誤りと同じ扱いである。Device は IPv4 だけを扱い、IPv6 の packet は `Write` の誤りになるので、ICMPv6 の誤りに当たる確認は持たない。エージェントの Device にも同じ確認が効く。エージェントに packet を送れるピアは `vpsd` だけで、`vpsd` の netstack が出す誤りの送信元は `vpsd` のトンネルのアドレスなので、エージェントの側で正当な誤りを捨てることは無い
- UDP の受信の会計:TUN の `Write` は、この Device のアドレス宛ての完成した IPv4 の UDP の datagram を、UDP の受信の会計(`internal/nettun`)に通してから netstack に渡す。会計は、Device の全ての UDP の endpoint の受信のキューに溜まる datagram を数える。UDP Length が IPv4 の残りより短い場合も配送し、読み取り時に照合する長さには UDP Length を使う。予算には IPv4 の残り全体を算入し、後続の byte を含む packet の保持を覆う。UDP Length が UDP ヘッダーより短い場合や IPv4 の残りを超える場合は配送しない。更新後の gVisor は受信キューに `PacketBuffer.MemSize()` を算入する
- UDP の受信の予算:Device ごとに 1 つで、4 MiB と 4096 件を上限とする。byte は、IPv4 ヘッダーの後ろにある UDP ヘッダーを除いた全 byte に 1 件あたり 64 byte を足して数える。UDP Length が示す利用者データより後ろに byte があれば、その分も算入する。読み取り時に照合する `ReadResult.Total` は UDP Length から UDP ヘッダーの長さを引いた値であり、予算の byte とは異なる。数えた byte は Go のヒープの実際の費用ではない(次の項)。値は設定項目にしない。datagram は endpoint に渡す前に予約し、読み手が読んだときと endpoint を閉じたときに返す。予約できない datagram は捨て、ICMP を返さない。gVisor の endpoint の受信のキューが満杯のときと同じ扱いである。4 MiB は、ラボの通常の負荷で 1 MiB が応答の一部を拒んだことを受けて、資源の上界として十分に小さく、実際の費用を説明できる値として採った(改訂の記録 2026-09-27)。最適値として探した値ではなく、この量までの burst を失わない保証でもない。`vpsd` とエージェントは同じ値を使う。両者の Device は役割が違うが、別の値を置く根拠となる実測が無いためである(2026-09-27、所有者の決定)
- 予算と実際の費用の関係:固定版の gVisor では、受信のキューに入った datagram 1 件が使う Go のヒープは、約 0.7 KiB の固定の部分(gVisor の packet の管理の構造など)に、IPv4 と UDP のヘッダーを含む packet 全体を 2 の冪に切り上げた大きさを足した量である(試験で測った)。IPv4 の option の無い packet 全体は payload に 28 byte を足した大きさで、会計が数える byte(payload に 64 byte を足した値)より小さい。したがって切り上げた大きさは数えた byte の 2 倍未満であり、受信のキューが使う生きているヒープは、Device ごとに「使用中の数えた byte の 2 倍 + 使用中の件数 × 約 0.7 KiB」を目安とする。予算いっぱいでは約 11 MiB になる。この換算は固定版の gVisor の作りから導いた見積もりであり、gVisor を更新すると変わりうる
- endpoint 1 つの上限:endpoint 1 つが持てる量は、byte と件数のどちらでも Device の予算の 1/4 まで(1048576 byte、1024 件)とする。目的は、読み手が止まった 1 つの endpoint による Device 全体の飢餓の封じ込めである。4 つ程度の止まった endpoint が同時に予算を使えば、Device 全体の予算は依然として尽きうる。更新後の gVisor は packet 全体と `PacketBuffer` の構造を受信キューに算入する。会計は endpoint を開くとき、gVisor の受信キューの上限を会計の byte 上限に最大 IPv4・UDP ヘッダーと `PacketBuffer` の構造の費用を件数上限分加えた値にする。会計の byte と件数の上限が先に効くようにするためである。ルールごとの予約や完全な公平性は提供しない。これ以上の分離は、必要性が実測された場合に検討する。上限を置く理由は、通常の故障で 1 つのルールの読みが止まるためである。エージェントの UDP の待ち受けは、新しいセッションの宛先の名前解決を読み取りと同じ goroutine で待つので、名前解決が応答しないだけで読みが止まる。上限の無い形では、このときに同じエージェントの別のルールの UDP が大きく失われた(改訂の記録 2026-09-27)
- 予算による拒否の知らせ方:会計は、endpoint 1 つの上限による拒否と Device の予算による拒否を別々に数え、拒否があれば、2 つの数と 2 つの上限を英語の 1 行のログに出す。行は Device ごとに 1 分に 1 回までに絞る。`wgft status`、Web UI、wire protocol、admin API には載せない。gVisor 自身の endpoint の受信のキューの上限は前項のとおり会計の byte と件数の上限が先に効く値に設定する。上限まで受理する条件では、受信のキューの溢れで gVisor が datagram を先に捨てないことを試験で確かめた。仮に gVisor が捨てた場合は、会計はその予約をすぐに返し、その datagram はこの 2 つの数にもログの行にも入らない
- 受理の判定とロックの範囲:会計は、予約した datagram を gVisor に渡した後、宛先の endpoint の公開の統計(`PacketsReceived` と受信の誤りの数)の差で、その 1 件を endpoint が受け取ったかを判定する。受け取らなかった datagram(checksum の誤り、接続済みの endpoint への別の送信元、受信のキューの溢れなど)の予約はすぐに返す。この差を 1 件に帰属させるため、同じ endpoint への配送、読み取り、閉鎖は endpoint ごとのロックで直列にする。Device 全体の帳簿のロックは加減と表の参照の間だけ持ち、gVisor への配送の間は持たない。TCP、ICMP、断片、この Device 宛てでない packet は、どちらのロックも取らない。例外は、どの endpoint も登録していないポート宛ての UDP である。この datagram は帳簿のロックを持ったまま 1 回だけ gVisor に渡し、gVisor が Port Unreachable を返す。同じポートを同時に開く endpoint が、予約の無い datagram を受け取らないためである。ロックの順は endpoint のロックから帳簿のロックの 1 方向だけである
- UDP の endpoint の作り方:Device の UDP の endpoint は、`DialUDP` と `ListenUDP` が登録表を通して作り、作ると同時に会計に登録する。Device は gVisor の stack を外に出さない。登録表の外で作った UDP の endpoint は予約の無い datagram を受け取り、会計の不変条件を壊すためである。netstack の中でこの Device のアドレスに宛てた UDP の送信も、TUN の入口と同じ予約、配送、判定を通す
- UDP の接続:`DialUDP` と `ListenUDP` は、gVisor の `gonet.UDPConn` の代わりに wgft の接続を返す。読み取りと自分宛ての送信を会計に通すためである。期限、短い読み取り、誤りの形は `gonet.UDPConn` と同じにした(試験で同じ手順を与えて比べた)。違いは、`Close` の後の読み取りと、`Close` で解かれた読み取りの待ちが `net.ErrClosed` を返すことである。`gonet.UDPConn` はこの場合に `io.EOF` を返した
- UDP の送信時の断片化:管理下の UDP endpoint は PMTU discovery を無効にする。更新後の gVisor の既定値は DF を立て、MTU を超えたローカル送信を断片化しても各断片の DF と ID 0 を残す。この断片は受信側の検査で拒否される。PMTU discovery を無効にすると、断片の DF が下がり、同じ非ゼロ ID を持つため、再組み立てを通る。TCP と ICMP の設定は変えない
- 会計の不整合:会計は、予約の無い datagram を読み取った場合、読み取った datagram の長さが予約と一致しない場合、1 回の配送で 2 件以上を受け取ったと読める場合、統計が逆に動いた場合を、不変条件の違反として扱う。違反を検出すると、その Device の UDP を止める。以後、この Device 宛ての UDP を捨て、自分宛ての UDP の送信、`DialUDP`、`ListenUDP` は誤りを返す。TCP は止めない。止まった状態は Device を閉じるまで続き、プロセスを再起動すれば戻る。検出したときは、違反の内容と再起動の案内を含む英語の行をログに 1 回だけ出す。最初に検出した違反を保ち、後の違反で内容を置き換えない。エージェントでは `agent doctor` の `tunnel.udp_accounting` が FAILED を示す(10.2c 節)。ユーザー空間モードの `vpsd` では、ログの行だけで知らせる(2026-09-27、所有者の決定)。`server doctor` の JSON、管理用 API、Web UI、wire protocol は変えない。観測の面が違うのは、エージェントには同じホストの中の制御ソケットと `agent doctor` という面があり、`vpsd` で同じことをするには公開している管理用 API と JSON の契約を増やす必要があるためである。稀な内部の不変条件の違反のために今その契約を増やす必要は無い。`vpsd` で診断のコマンドからの機械的な検出が要る実例が出たら、別に判断する。この停止は資源の逼迫のときの動作ではなく、依存の更新や wgft 自身の不具合による不変条件の違反を安全側で検出するものである。違反の後に会計だけを外して UDP を続ける形は、会計が作る保持の上限を失うので採らない(2026-09-27、所有者の決定)。外部の入力だけでは違反を起こせないことを、断片、長さの誤り、option、checksum の誤り、broadcast と multicast の宛先を混ぜた packet の列を与える試験で確かめた。あらゆる入力について示したものではない
- keepalive の ping の endpoint:エージェントが keepalive ごとにトンネル内へ送る ping は、ping ごとに ICMP の endpoint を 1 つ作り、`vpsd` のトンネルアドレスへ接続して echo を 1 つ送り、応答を読むか期限が来たら閉じる。endpoint は bind しない。固定版の gVisor の ICMP の endpoint は、bind で登録した identifier を、続く接続でも閉鎖でも解放しない。bind と接続を続けて行うと ping ごとに endpoint と identifier が 1 つずつ残り、identifier の範囲を使い切った後は ping が毎回失敗する。bind しない endpoint は接続のときに identifier を 1 つだけ登録し、閉鎖でそれを解放する。送信元のアドレスは接続の経路が選ぶ。Device はアドレスを 1 つしか持たないので、選ばれるのはエージェントのトンネルアドレスである。`DialPing` は接続の後に endpoint の送信元のアドレスを確かめ、渡されたアドレスと違えば endpoint を閉じて誤りを返す
- netstack の出力:netstack が送り出すパケットは、gVisor の `channel.Endpoint` が持つ深さ 1024 の FIFO のキュー 1 つに入る。wireguard-go の読み取り(TUN の `Read`)は、このキューから 1 回に 1 件ずつ取り出す(pull)。gVisor と wireguard-go の間のキューはこの 1 つだけである。キューが満杯のときは新しく送り出すパケットを捨て、送り出す側の netstack は待たない。捨てたパケットは、TCP では再送で補われ、UDP のデータグラム、ICMP の応答、TCP の RST では失われる。満杯による損失を ICMP の誤りや TCP の RST に変えて相手に知らせることはしない。`Close` は読み取りを先に取り消し、待っている `Read` を `os.ErrClosed` で返す
- 出力のキューの隔離:プロトコルごとのキュー、ルールごとのキュー、公平化のための順序の入れ替えは持たない。このため過負荷のときは、負荷と無関係な通信(別のルールの通信や、送る量の少ないフロー)にも少量のパケットの欠落が起こることがある。欠落は負荷が終われば止まる。ユーザー空間モードは、カーネルモードと同等の QoS と DoS の隔離を保証しない。7a.10 節のルール 1 本の上限とルールごとの最低分はフローの数に効き、このキューの中のパケットには効かない
- netstack の TCP の短い障害の後の回復:エージェントの netstack の TCP も、送る向きでは経路の短い障害の後の回復がカーネルの TCP より遅い。ユーザー空間モードはこれを既知の制限とする(6.3 節の性質の違いの項)
- 1 回の読み取りの件数:`Read` は 1 回に 1 件だけを返し(`BatchSize` は 1)、複数の件をまとめて返さない。wireguard-go の送信のキューは、パケットではなく 1 回の `Read` の結果を入れる入れ物を数える。k 件ずつ返すと、後述の滞留のメモリの上限が k 倍になるためである
- WireGuard の受信の 1 回の件数:wireguard-go に渡す UDP のバインドは、1 回の受信で 1 件だけを渡す包み(`internal/dataplane/userspace/wgbind`)である(`BatchSize` は 1)。wireguard-go の受信のキューは、送信のキューと同じく、パケットではなく 1 回の受信の結果を入れる入れ物を数え、1 件ごとに `MaxMessageSize` のバッファを持つ。Linux の標準のバインドは 1 回に 128 件まで読むので、そのままでは後述の受信の向きの滞留の上限が 128 倍になる。包みは標準のバインドを内側に持ち、内側の 1 回の件数と同じ数のバッファで内側を読み、wireguard-go の呼び出しごとに 1 件ずつ写して渡す。読み取りの syscall の数は変わらず、内側の 1 回の読み取り(`recvmmsg`、GRO)と sticky socket の送信元の固定はそのまま使う。内側のバインドの 1 回の件数が既に 1 の Windows と macOS では包まない。内側の誤りは同じ値のまま返す。wireguard-go は `net.Error` への直接の型の判定で一時的な誤りかどうかを見るので、包んだ誤りは非一時的なものでも一時的と読まれるためである。閉じた後の受信は、手持ちの datagram を捨てて `net.ErrClosed` を返す。送信は内側にそのまま渡す。包みは wireguard-go の Linux の経路の監視を止める。監視は、バインドの型が標準のバインドそのものであるときだけ始まり、経路の変化のたびに、ピアの宛先への経路の出口のインタフェースが sticky の送信元のものと違えば次の送信で送信元を消す。監視が経路の変化の直後に直せるのは、古い送信元アドレスがホストに残ったまま出口のインタフェースが変わる場面だけである。アドレスごと消える場面では、監視があってもタイマーで回復する(コードを読んだ判断で、未確認)。`vpsd` のようにピアが複数あるときは、監視のピアの走査が送信元を記録していないピアで止まる作りのため、監視は元から確実ではない。送信元を消す経路は wireguard-go のタイマーにも残っている。データを送って応答が無いときと、ハンドシェイクの再送のたびである。エージェントは keepalive ごとにトンネル内へ ping を送るので、Linux のエージェントで古い送信元アドレスが残ったまま出口だけ変わる場合の回復は、通信があれば最大 15 秒程度、無ければ ping の間隔を含めて最大 40 秒程度になりうる。これは既知の trade-off であり、送信の失敗時の送り直しや送信元の解除は持たない。据え置きのエージェントと VPS が主な用途で、送信側まで変えると 1 回の件数の変更の評価と原因の分離が難しくなるためである(2026-09-27、所有者の決定)。実機や通常の利用でこの回復の時間が問題として確認されたら、送信側の補いを別に検討する。`vpsd` はピアの endpoint を設定に持たず、相手から認証されたパケットが届くたびに endpoint を sticky の送信元ごと置き換える。したがって `vpsd` では、経路の監視を失う影響は事実上無い
- wireguard-go の UDP バインドは、Windows では `conn.NewDefaultBind()` ではなく `conn.NewStdNetBind()` を明示して使う。既定の `NewDefaultBind()` は Windows では Registered I/O を使う `WinRingBind` を返すが、`WinRingBind` は `SIO_UDP_CONNRESET` を無効にしない。このため、到達できない宛先へ送った UDP に対して Windows 自身のスタックが生成する ICMP port unreachable では、Windows の非同期受信が WSAECONNRESET として報告し、`device.RoutineReceiveIncoming` がこれを回復不能な誤りと判定して受信ループを止め、そのトンネルは以後受信できなくなる(改訂の記録 2026-09-21)。`conn.NewStdNetBind()` は Go の `net` パッケージ経由でソケットを開き、同じ状況でも受信を続ける。この選択は Windows でのバッチサイズを変えない。依存するこの版の `golang.zx2c4.com/wireguard` では、`WinRingBind.BatchSize()` も `StdNetBind.BatchSize()` も Windows で 1 を返し、差が無いためである。残る差は、自前のリングバッファと Go の netpoller 経由の UDP ソケットとの間の、パケットごとの syscall や I/O 完了通知のオーバーヘッドであり、その大きさは未測定である。受信が止まらないことを優先する。前述の「WireGuard の受信の 1 回の件数」の包みは、内側の 1 回の件数が 1 なので Windows では使われない。この WSAECONNRESET は Windows 自身のスタックが答える ICMP で再現できる一方、実サーバーの到達不能な UDP ポートへインターネット越しに送る計測では現れなかった(改訂の記録 2026-09-21)。ICMP がその経路のどこで失われているかと、他の経路でなら届きうるかは未確認である
- トンネルの作り直し:エージェントは、WireGuard のハンドシェイクが 300 秒新しくならない状態が続いたら、`device.Device` と netstack ごとトンネルを作り直す。回復は 2 段である。第 1 段は 4 節の軽い回復で、ハンドシェイクが keepalive の 5 倍(既定で 125 秒)の間成立しなければ、エンドポイントの名前を引き直し、トンネル内へ ping を 1 つ送る。第 2 段が作り直しであり、第 1 段を繰り返しても戻らない故障に備える。対象の故障は、wireguard-go の受信の goroutine が終わったまま戻らない状態である。`device.RoutineReceiveIncoming` は `net.ErrClosed` 以外の非一時的な誤りを受けると戻り、起こし直す経路が無い。この状態のトンネルは送信を続けるが二度と受信しないので、ハンドシェイクは永久に成立せず、第 1 段のどちらの操作でも戻らない。エージェントは受信の停止そのものを観測できないため、判定にはハンドシェイクの成立だけを使う。転送量をハートビートに載せる必要は無い(5.2 節)。この点検が 30 秒ごとに読む最終ハンドシェイクの値は、stream の再接続の待ちを打ち切る判定にも使う(5.2 節)
- 作り直しを決める位置:判定と作り直しはエージェントの本体(`internal/agent`)が行う。作り直しにはリスナーの開き直しと最後に受け取った全体状態が要り、トンネルの package はどちらも持たないためである。手順は、wg 設定が変わったときの張り直しと同じものを使う
- 作り直しの閾値:300 秒とする。WireGuard の時定数から決めた値である。エージェントは送信の側なので、鍵を作ってから 120 秒(`RekeyAfterTime`)を過ぎた最初の送信で新しいハンドシェイクを始め、keepalive が 25 秒ごとに送信を起こすので、健全なトンネルの最終ハンドシェイクは 145 秒以内に必ず新しい値になる。180 秒(`RejectAfterTime`)を過ぎた鍵は送信にも使えないので、300 秒の時点のトンネルは既に 120 秒以上まったく通信していない。ハンドシェイクの再送の打ち切り(`RekeyAttemptTime`、90 秒)も済んでいる。閾値を keepalive の倍数にしないのは、この 3 つの時定数が keepalive の値によらず一定だからである
- 経過時間の測り方:エージェントは、`IpcGet` が返す最終ハンドシェイクの値そのものと、その値を最初に観測した時刻を覚え、観測してからの経過時間で判定する。最終ハンドシェイクは壁時計の秒であり、NTP の補正や手動の変更で飛ぶ。値と現在時刻の差で測ると、155 秒以上前への飛びが健全なトンネルを 300 秒古く見せ、中継中のフローを 1 度無駄に切ってしまう。観測してからの経過時間は Go の単調な時計で測るので、壁時計がどちらへ飛んでも作り直しは起きず、抑えられもしない。健全なトンネルの値は 145 秒以内に必ず新しくなるので、観測の時刻もその周期で進む。値が新しくなり、かつゼロでなければ、作り直しの間隔も初期値に戻す。判定の起点には、値を観測した時刻とトンネルを立てた時刻の遅い方を使う。作り直した直後の device はハンドシェイクがゼロで、前の値もゼロだったときは値が変わらず、観測の時刻が更新されないためである。ハンドシェイクが一度も成立していないトンネルの起点はトンネルを立てた時刻になり、起動の直後に受信が止まる場合も作り直しの対象に入る
- サスペンドの扱い:`time.Now` が持つ単調な読みの出どころは GOOS ごとに違う。Go 1.27.1 の runtime では、Linux が `CLOCK_MONOTONIC`(`runtime/sys_linux_amd64.s`)、macOS が `mach_absolute_time`(`runtime/sys_darwin_amd64.s`)、Windows が `KUSER_SHARED_DATA` の `InterruptTime`(`runtime/time_windows.h`、`runtime/sys_windows_amd64.s`)である。Linux の `CLOCK_MONOTONIC` と macOS の `mach_absolute_time` はサスペンド中に進まないので、復帰した後のエージェントは、第 1 段の回復に 300 秒の起きている時間を与えてから作り直す。Windows の `InterruptTime` は unbiased ではない方であり、スリープとハイバネートの時間を含むので、300 秒を超えるスリープからの復帰では最初の判定で 1 回作り直す。どちらの場合も、300 秒を超える中断の後のセッションは `RejectAfterTime` を過ぎて既に使えず、作り直しで切れるのは死んだフローだけである。Go の runtime がどの時計を読むかはこの版の原典で確かめた。macOS の `mach_absolute_time` がサスペンド中に進まないことは、実機の Mac で時計そのものを測って確かめた(改訂の記録 2026-09-21、issue #124)。Windows の `InterruptTime` がスリープの時間を含むことは、Windows 11 の実機でエージェントの挙動から確かめた。約 11 分 32 秒のスリープから復帰したエージェントは、新しいハンドシェイクの無い期間をスリープを含めて 11 分 36 秒と数え、復帰の直後にトンネルを 1 回作り直した。時計そのものを測るプログラムは使っていない(改訂の記録 2026-09-27、issue #280)。ハイバネートの時間を含むことは OS の文書に拠るもので、実機では未確認である。Linux の `CLOCK_MONOTONIC` がサスペンド中に進むかどうかは OS の文書に拠るものであり、実機では未確認である
- 作り直しの間隔:サーバが停止しているだけの場合も、エージェントから見た症状は受信の停止と同じであり、区別できない。そこで作り直しの間隔をバックオフで広げる。1 回目は 300 秒で、以後は 600 秒、900 秒と倍にし、900 秒を上限とする。ゼロでない新しいハンドシェイクを観測したら間隔を 300 秒に戻す。サーバが長く停止した後に戻った場合、トンネルが健全なら作り直しを待たずにハンドシェイクで復旧し、受信が死んでいる場合は最長 900 秒で作り直す
- 作成に失敗したときの再試行:トンネルを立てる手順は古いトンネルを閉じてから新しいものを作るので、作成そのものが失敗するとトンネルが 1 つも無い状態で残る。エージェントは、その状態を予定の時刻に試し直す。1 回目は次の 30 秒の判定で試し、続けて失敗するほど 300 秒、600 秒、900 秒と間隔を広げ、900 秒を上限とする。トンネルが無い間は転送が全部止まっているので、1 回目だけは間隔を置かない。対象は、ハンドシェイクが新しくならないことによる作り直しの作成が失敗した場合と、全体状態の適用の中で作成が失敗した場合の 2 つである。`rotate-key` と停止で閉じたトンネルも、最初の全体状態を受け取る前のトンネルの無い状態も対象にしない。
- 試し直さない失敗:wg 設定そのものが誤っている全体状態は対象にしない。サーバの公開鍵やアドレスが解釈できない場合、同じ全体状態では何度作っても同じ結果になるためである。エージェントはトンネルを立てないまま次の全体状態を待ち、ハートビートでは試し直しを待っていない理由を送る。
- 試し直しが使う全体状態:エージェントは、作成に失敗したときの全体状態をメモリの上に控え、試し直しはその全体状態から立てる。認証情報ファイルの `last_state` は適用を終えた全体状態しか指さず、新しい全体状態の適用が作成で失敗した場合は 1 つ前の全体状態を指したままである。そちらから立てると、サーバが想定していない wg 設定とルールのトンネルになる。控えは保存せず、再起動の後は保存済みの `last_state` で立て、stream が今の全体状態を配り直す。試し直しが成功したら、その全体状態の適用を最後まで進め、処理済み世代と `last_state` もその時点で進める。適用が終わるまで世代を進めないので、ハートビートの世代は実際に適用した内容と食い違わない。
- `rotate-key` との関係:`rotate-key` は古いトンネルを閉じてから新しい鍵で全体状態を適用し直す。閉じた時点で試し直しの控えは消えるので、閉じてから適用し直すまでの競合可能期間に watchdog がトンネルを立てることはない。その適用の作成が失敗した場合は、失敗そのものが控えを付け直すので、試し直しは新しい鍵で立てる。
- 作り直しの費用:鍵、アドレス、`AllowedIPs`、エンドポイントは同じ値で立て直すので、VPS 側のピアの設定は変えなくてよい。認証情報ファイルも書き換えない。リスナーは閉じて開き直すので、中継中の TCP 接続と UDP のセッションは切れる。切れるのは、閾値の時点で既に 120 秒以上パケットの通っていないフローだけである。制御プレーンは wg を通らない(5 節)ので、作り直しの間も stream の接続と全体状態の受信は続く。古いトンネルは新しいものを作る前に閉じる。ただし、閉じたトンネルは、それを使っていた処理がすべて戻るまで参照が残り、GC されない。このため古い世代と新しい世代は、古い世代の処理が終わるまで重なりうる。閉じたトンネルが残す量は、後述の「プロセス全体のメモリの上界」の段落で扱う
- 作り直しの見せ方:1 回の作り直しにつき、理由と次の間隔を含む英語のログを 1 行出す。作成に失敗したときは、理由と、次に試すまでの時間か試し直さない旨を 1 行出し、試し直すときにも 1 行出す。判定は 30 秒ごとに行うが、ログは作り直しと作成のときだけ出す。ハートビートのトンネルの状態は、作り直した直後はハンドシェイク待ちなので、既存の `error` と `handshake not established` になる。作成に失敗してトンネルが無い間は `error` を送り、理由で 4 つの場合を区別する。試し直しを待っている場合、試し直さない失敗で終わった場合、全体状態をまだ受け取っていない場合、`rotate-key` や停止で閉じた直後の場合である。試し直しを待っている理由の文言は作り直しと適用で共通にする。運用者から見てどちらも「作成に失敗して試し直す」であり、区別する意味が無いためである。理由は人が読む文言であり、新しい状態も新しい項目も加えない(7a.6 節)
- ルールの各ポートごとにリスナーを netstack 上に開き、LAN 内の `target` へ自分で接続して中継する
- エージェントから見た送信元は VPS の masquerade により常に `10.200.0.1` で、フローは送信元ポートで区別される。したがって全ルール共通の UDP 同時フロー上限は約 64k になる
- UDP は `(送信元 IP, 送信元ポート)` の組ごとにセッションを持ち、無通信が全体状態の `udp_timeout_stream` 続いたら閉じる。VPS の conntrack は assured になる前のフローを `udp_timeout`(既定 30 秒)で消すので、数パケットで終わるフローではエージェント側に死んだセッションが最長 90 秒残る。害は小さいので、この非対称は許容する。セッション数の上限は後述の「同時フロー数の上限」に従い、超えた新規パケットは捨てる。宛先からの応答を待つ間、セッションは読み取りバッファを持たない。データグラムの到着だけを先に待ち、届いてから共有プールの 65535 バイトのバッファを借りて全体を読み、公開側へ送り終えたら返す。したがって応答の大きさによらずデータグラムは欠けない。共有プールが同時に貸すバッファの数はプロセス全体で 64 個までであり、その意味は後述の「応答のバッファの枠」の項に書く。到着を待つ手段は、カーネルのソケット(エージェントの宛先側)では、Unix は 1 バイトの `MSG_PEEK`、Windows はゼロバイトの `WSARecv`(`MSG_PEEK` 付き)をオーバーラップ I/O で発行し完了通知で待つ(Go ランタイムの `RawRead` が行う。スレッドは塞がない)。netstack の接続(`vpsd` のエージェント側)ではエンドポイントの待ち行列(`waiter.Queue`)である。wireguard-go の `tun/netstack`(`netstack.Net`)は stack を公開しないため、エージェントと `vpsd` はどちらも netstack と TUN の接続部分を写して自前で持つ共通の内部パッケージ(`internal/nettun`)を使う。stack への直接アクセスは、`vpsd` はこの `waiter.Queue` のため、エージェントは後述の TCP の拒否のために、それぞれ要る。この 3 つ以外の GOOS のエージェントでは到着だけを待つ手段を使わず、セッションごとに 65535 バイトを持ち続ける。2026-09-18 までは Windows を含む全セッションが 65535 バイトを保持し、上限いっぱいの 4096 セッションがルール 1 本で約 292 MiB になっていた(改訂の記録 2026-09-18 の実測)。macOS のエージェントは、宛先へのカーネルのソケットを開くたびに送信バッファ(`SO_SNDBUF`)を 65535 バイトに上げる。macOS の UDP の送信バッファの既定は `net.inet.udp.maxdgram` の 9216 バイトで、これを超えるデータグラムの書き込みは `EMSGSIZE` で失敗するためである。BSD 系のカーネルは UDP の送信バッファにデータを溜めず、この値は 1 個のデータグラムの最大長として効くだけなので、上げてもセッションごとのメモリは増えない。Linux の既定(約 208 KiB)は 65535 バイトより大きいので変えない。netstack の接続も変えない。宛先への書き込みが失敗したらセッションを閉じ、そのことをリスナーごとに 1 分に 1 回までログに出す
- 応答のバッファの枠:宛先からの応答を読むバッファは、プロセス全体で同時に 64 個(4 MiB)までしか貸さない。`vpsd` もエージェントもプロセスで 1 つの枠の集まりを持ち、エージェントがトンネルを作り直しても数は変わらない。上限がかかるのは同時に貸し出しているバッファの数であり、借りている分の保持はこの数 × 65535 バイトを上限に持ち、セッション数、ルールの本数、OS によらない。返されて誰も借りていないバッファは共有プールが一時的に持ち、GC が回収する。以前はセッションごとの goroutine が上限なしに借りられたので、この保持の上限はセッション数に比例していた(改訂の記録 2026-09-27)。枠が無いセッションは、枠が空くか、そのセッションか待ち受けが閉じるまで待つ。待つ間、応答のデータグラムは宛先側の接続の受信のキュー(`vpsd` では前述の UDP の受信の予算の中の endpoint のキュー、エージェントではカーネルのソケットの受信バッファ)に留まるので、この待ちでデータグラムは失われない。待ちの間に届く新しい応答は、それぞれのキューの既存の上限が捨てる。枠を持つ間の仕事は、バッファへの読み取り 1 回と公開側への送信の試み 1 回だけである。`vpsd` は後述の「公開側への応答の送信」のとおり公開側で待たないので、`vpsd` では 1 つの待ち受けの詰まりが枠を持ち続けることは無い。エージェントの公開側の送信が待つ条件は同じ項の末尾に書く。待つセッションはフローの予算(後述の「同時フロー数の上限」)を持ったまま待つが、枠の保持がこの短い区間に限られるので、待ちもその範囲に収まる。待ちを取り消すのは、待ち受けを閉じたとき(ルールの削除と無効化、`vpsd` とエージェントの停止)と、セッションを閉じたとき(無通信、接続元制限の変更による sweep)である。ルールごとや待ち受けごとに枠を分けない。分けると上限が待ち受けの数に比例するためである。64 は設定項目にしない。この値は、通常の負荷で正常な通信が枠を待つ時間が利用者に意味を持たないことをラボで確かめて採った値であり、この数までなら安全という保証の数ではない。枠の待ちは回数と時間を内部で数えるだけで、ログ、`wgft status`、Web UI、wire protocol、管理用 API には出さない。セッションの終了で取り消された待ちは回数だけを数え、時間の合計と最長には入れない。無通信で閉じたセッションの長い待ちが最長の観測値にならないためである。到着だけを待つ手段を持たない GOOS(unix でも Windows でもない)のエージェントは、セッションごとに持ち続けるバッファを枠の外で使うので、この上限はその GOOS には当てはまらない
- 公開側への応答の送信:`vpsd` のユーザー空間モードは、公開側のホストのカーネルの UDP ソケットへ応答を 1 回だけ送ろうとする。ソケットの送信バッファが満杯(`EAGAIN`)なら、そのデータグラムを捨てて枠を直ちに返し、セッションは続ける。書けるようになるまで待たない。カーネルモードでは転送される応答はソケットの送信バッファを持たず、経路が詰まればカーネルが qdisc で捨てるので、ユーザー空間モードも捨てるという同じ意味にする。ただし捨てる場所の深さは違う。カーネルモードが捨てるのは qdisc の待ち行列(既定の `pfifo_fast` で 1000 件)であり、ユーザー空間モードが捨てるのは待ち受けごとのソケットの送信バッファ(Linux の既定 `net.core.wmem_default` で約 208 KiB。1300 バイトの datagram なら skb の管理の領域を含めて 90 件ほど、65535 バイトの datagram なら 2 個ほど)である。以前の形では、送信の待ちの間に宛先側の endpoint のキュー(UDP の受信の予算)も burst を吸収していたので、待たない送信だけでは 1 つの待ち受けが吸収できる burst が小さくなる。混雑していない経路でも、1 回の入力に対する応答の burst が送信バッファを超えれば、超えた分を捨てる。このため公開側のソケットには固定の送信バッファを要求する(後述の「公開側のソケットの送信バッファ」)。ラボでは、混雑していない経路の代わりに公開側を 100 Mbit に絞り、1 回の入力に対する応答の burst の大きさを段階的に変えて以前の形と比べた。送信バッファに収まる burst では差が無く、送信バッファを超える burst では、この形は以前の形より多くを捨てた。以前の形も同じ大きさの burst の一部を別の場所で失っており、その場所は未確認である(改訂の記録 2026-09-27)。待つ形では、詰まった 1 つの待ち受けのセッションが枠を持ち続け、無関係なルールのセッションが枠を借りられず、プロセス全体の UDP の応答が止まる。混雑している公開側で応答を待ち続けることに、接続する利用者にとっての価値は無く、混雑が去れば次のデータグラムから戻る方が UDP として自然である(2026-09-27、所有者の決定)。待たないので、そのセッションは宛先側の接続を読み続け、公開側の詰まりが前述の UDP の受信の予算を占めることも無い。`EINTR` はやり直す。それ以外の送信の誤りは、今までどおりセッションを閉じる。満杯で捨てた応答は累計で数え、英語の 1 行のログに 1 分に 1 回まで出す。捨てた応答も宛先からは読めているので、待ち受けの最後の応答の時刻(10.2a 節)には記す。`wgft status`、Web UI、wire protocol、管理用 API には載せない。エージェントの公開側は netstack の待ち受けであり、この 1 回だけの送信は使わない。その送信は、endpoint の送信バッファ(gVisor の既定 212 KiB)が使われている間は書けるようになるまで待つ。使われたままになるのは、後述の「netstack の出力」のキューにパケットが留まっている間、つまりトンネルの送信(wireguard-go の TUN の読み取り)が止まっているときである。そのときは全ルールの応答が同じく止まるので、この待ちが枠によるルール間の新しい飢餓を作ることは無い。待ちは、トンネルの送信が進むか、待ち受けを閉じると解ける。セッションを閉じても、この送信の待ちは解けない
- 公開側のソケットの送信バッファ:`vpsd` のユーザー空間モードは、公開側の UDP ソケットを開くたびに、固定の送信バッファ(`SO_SNDBUF` に 2 MiB)を要求する。設定項目にしない。応答の送信は待たないので、1 回の入力に対する正常な応答の burst を吸収するのはこのバッファだけであり、Linux の既定(`net.core.wmem_default` で約 208 KiB)では、混雑していない経路でも 1 回の入力に対する大きい応答の burst を捨てた(改訂の記録 2026-09-27)。このバッファは Go のヒープの予算ではなく、公開側の UDP ソケットごとのカーネルの資源である。プロセス全体では、おおむね「該当する公開側のソケットの数 × ソケットごとの上限」がカーネル側の保持点になる。ソケットごとの上限は kernel から読んだ実効の値で、Linux では要求の 2 倍の 4 MiB である。実際にメモリを使うのは送信が滞留している間だけで、ソケットを開いた時点でその量を使うのではない。Linux は `setsockopt` に渡した値の 2 倍をソケットに割り当て、`getsockopt` もその 2 倍の値を返す。要求は `net.core.wmem_max` で切り詰められ、切り詰められた場合は burst の許容がその分だけ下がる。`vpsd` は開いたソケットの実効の値を `getsockopt` で読み返し、要求の 2 倍に届かなければ、WireGuard のソケットのバッファの警告と同じ形の英語の 1 行を、プロセスで 1 分に 1 回まで出す。行は実効の値、要求の値、書き換える sysctl を含む。`vpsd` はこの sysctl を書き換えない。ユーザー空間モードの `vpsd` の動作条件(前述の「ソケットのバッファの条件」)は `net.core.wmem_max` を 7340032 以上とするので、条件を満たすホストではこの要求は切り詰められない。WireGuard のソケットは `CAP_NET_ADMIN` の FORCE で上限を超えられるが、この公開側のソケットの要求は FORCE を使わないので、上限が小さいホストでは WireGuard の警告が出ずにこの警告だけが出ることがある。このバッファはルール間の隔離ではなく、待たない送信を保ったまま正常な burst を吸収するためのものである。「setsockopt に渡した値」と「kernel から読んだ実効の値」は、この文書でも試験でも区別する
- エージェントの LAN 側のソケットの受信バッファ:ユーザー空間モードのエージェントは、UDP のセッションごとに LAN の宛先へのカーネルの UDP ソケットを 1 つ開き、その受信バッファ(`SO_RCVBUF`)を設定しない。受信バッファの大きさは OS の既定の値で、Linux では `net.core.rmem_default` である。宛先からの応答は、セッションが読むまでこのバッファに溜まる。溜まったときに使うのはカーネルのメモリであり、Go のヒープにもソフト上限の式にも入らない。この段の上界は、セッション数と 1 つのソケットの受信バッファの大きさの積である。Linux ではさらに、`net.ipv4.udp_mem` がホスト全体の UDP のソケットのメモリの上限として効く。この上限はホストの全ての UDP のソケットに共通なので、ここに溜まる量が大きいと、同じホストの WireGuard のソケットの受信も巻き込みうる。1 つのセッションに届く応答の burst がセッションの読み取りに追いつかず受信バッファを超えると、超えた分はそのセッションで捨てられうる。カーネルモードのエージェントにはこの段が無い。カーネルが応答をそのまま転送し、ユーザー空間のソケットを通さないためである。受信バッファは大きくしない。大きくすると、セッション数との積でカーネルのメモリの上界が大きくなり、ホスト全体の UDP のメモリを圧迫しうる一方で、得られる利点は大きな burst をさらに守れることだけだからである。通常の利用で明確な退行が確認された場合に限り、大きくする比較を改めて行う(2026-09-27、所有者の決定)。macOS と Windows での既定の値と数え方は未確認である
- TCP は接続ごとに `target` へ接続し、ハーフクローズを保って中継する(6.2 節と同じ)。接続数の上限は後述の「同時フロー数の上限」に従い、超えた接続は accept の直後に閉じる。この拒否は RST を送って即座に終える(`internal/nettun.TCPConn.Abort`。実ソケットでは `SetLinger(0)`)。netstack 上で通常の `Close` を使うと、graceful shutdown を経て gVisor の既定の TIME_WAIT(60 秒、`tcp.DefaultTCPTimeWaitTimeout`)にエンドポイントが残り、同時フロー数の上限を超える接続のフラッドでは、上限が抑えるはずの保持分を超えてメモリが増え続ける(GitHub issue #25)。中継の側から成立済みの接続を切るときも、netstack の側の接続は同じ `Abort` の RST で切る。切るのは、ポートが宣言から消えたとき、実効宛先が変わって閉じ直すとき(後述の収束の規則)と、エージェントの終了で中継を閉じるときである。中継中のクライアントに何が届くかは、VPS のモードと切る理由で変わる。ユーザー空間モードの VPS では、クライアントとエージェントの間に `vpsd` 自身の中継(`internal/netpipe`)が挟まる。エージェント側の読み取りが RST で失敗すると、`vpsd` はクライアント側の接続を通常の `Close` で閉じる(6.2 節)ので、クライアントは切る理由によらず通常 FIN を見る。これは `internal/netpipe` の実装を読んで確かめたもので、ラボでは確かめていない。カーネルモードの VPS では、パケットがそのまま届くので理由ごとに違う。実効宛先の変更で切るときは、クライアントに RST が即座に届くことを実際の VPS で確かめた。ポートが宣言から消えたとき、つまりルールを無効化または削除したときは、VPS 側が該当の DNAT と conntrack を公開の時点ですでに取り除いているため、この RST は切った直後はクライアントに届かない(6.1 節)。その後の届き方は、無効化や削除がそのまま続くか、直後に元へ戻るかで変わる。無効化や削除がそのまま続く場合、host の input firewall が既定で drop する実際の VPS では、次に送るパケットもおそらく同じく drop され、RST も届かないと考えられるが、これはコードから導かれるだけで、未確認である。無効化した直後に有効化する場合と、削除した直後に同じポートへ追加し直す場合は、クライアントは次に送るまで何も気付かず、次に送ると RST を受け取ることを、実際の VPS で確かめた。この RST はおそらく開き直した待ち受けから送られたものだが、これは推測であり未確認である。この届き方は、ルールの無効化と削除が公開してからエージェントへ配ることを前提にする。5.1 節のエージェントの無効化はエージェントへ配ってから公開するため、この前提が成り立たず、クライアントへの届き方は別に未確認である。エージェントの再起動で切るときも、クライアントは次に送るまで何も気付かず、次に送ると RST を受け取ることを実際の VPS で確かめた。エージェントが止まったままの場合は試しておらず、届き方は未確認である。待ち受けを閉じるときに accept の途中で、まだ中継に登録していなかった接続も、登録せずに同じく切る。この接続は閉じ直しの bind に間に合わないことがあり、その場合の待ち受けは次の 30 秒ごとの再試行(5.2 節)で開く。通常の `Close` で切ると、エージェントのエンドポイントが TIME_WAIT に 60 秒残り、相手が閉じなければ FIN_WAIT_2 にさらに長く残る。その間は同じポートで待ち受けを開けず(`port is in use`)、閉じ直したルールと、無効にした直後に有効に戻したルールは、保持が終わった後の再試行まで転送できない。クライアントに届くのが FIN でなく RST になる、または届かないことがあるのは前述のとおりだが、切ることが決まっているセッションなので、この届き方の違いは許容する。カーネルモードの conntrack の収束(6.1 節)も、フローを FIN で閉じずに断つ。宛先側の接続は実ソケットで待ち受けのポートを塞がないので、通常の `Close` のままにする。VPS の中継が切ったセッションは、エージェントには RST として届く(6.2 節)。公開側のクライアントが RST で切ったセッションも、VPS の中継からはエージェントに RST として届く(6.2 節)。エージェントの中継は、公開側の接続の読み取りの失敗を受けて宛先への接続を通常の `Close` で閉じ、枠を返す。セッションが自然に終わる経路(クライアントか宛先のハーフクローズ、EOF)は、グレースフルクローズで終える。この経路でエージェントが先に閉じた接続は、終わった時点で中継の管理から外れるので RST で切れず、TIME_WAIT の間ポートを保持する。宛先が先に閉じる HTTP のようなセッションがこれに当たる。すぐに解放されるのは中継が切るセッションだけで、このような接続が残っている間にルールを閉じ直すと、待ち受けは保持が終わった後の再試行まで開かない。無通信のタイムアウトは持たない。カーネルモードの conntrack が established の TCP を 5 日間保つのと同じく、長く黙る正規の接続(SSH など)を切らないためである
- netstack の TCP のバッファ:netstack の TCP の接続は、送信と受信のバッファの大きさに上限を持つ(2026-09-30、所有者の決定)。全接続に小さな最低分(以下 floor。送信 256 KiB、受信 256 KiB)を保証し、大きなバッファ(以下 boost。送信と受信のどちらも 4 MiB)は、プロセスあたり同時に 16 本の接続までの枠で貸す。`vpsd` もエージェントもプロセスで 1 つの枠の集まりを持ち、トンネルを作り直しても数は変わらない。`vpsd` のユーザー空間モードでは、全エージェントへの接続が同じ 16 本を分け合う。`vpsd` とエージェントの枠は別々であり、1 本の接続の両端の予約を調停しない。片側だけが枠を得た接続の速さは、得ていない側の floor で決まる。値はどれも設定項目にしない。4 MiB は gVisor の既定の自動調整の上限と同じ値であり、ラボでは単独の転送が以前より遅くならなかった(改訂の記録 2026-09-30)。以前はバッファを gVisor の自動調整に任せていた。送信のバッファの上限は受け入れた byte だけを数え、書き込み 1 回ごとに gVisor が持つ管理の構造を数えないので、読まない相手へ 1 byte の書き込みを繰り返すと、接続 1 本の保持が byte の上限を大きく超えて増えた
- 書き込みの数の上限:接続が送信のキューに持つ書き込みの数を、送信のバッファ 1 KiB あたり 1 回に抑える。floor では 256 回、boost では 4096 回である。byte の上限だけでは前項の保持を抑えられないためである。wgft の接続は gVisor に書く前に、送信のキューに残る byte が、直前の 255 回(boost では 4095 回)に受け入れた長さの和より少ないことを確かめる。確かめ方は、送信のバッファをその和に設定し、書き込める状態かを見て、設定した値を読み返すことである。送信のキューは送った byte の列の末尾なので、この条件が成り立てば、それより前の書き込みはすべて相手が確認しており、キューに残る書き込みは今回の 1 回を含めて上限以内になる。成り立たなければ、書き込める状態になるまで待つ。そのため wgft の接続は `gonet.TCPConn` の書き込みを使わず、書き込みの期限と、`Close` による待ちの解除を自分で持つ。長さの履歴は、boost を持たない間は直前の 255 回分を持ち、boost を得たときに 4095 回分に広げ、boost を返すと 255 回分に戻す。広げた直後の、覚えていない古い長さは 0 として数える。和を小さく見積もるので、条件は成り立ちにくくなる側にだけずれ、上限は崩れない
- boost を求める条件:読み取りと書き込みのどちらかの向きで、250 ms の区間に 64 KiB 以上を実際に読めたか gVisor が受け入れた接続は、枠を 1 つ求める。区間は入出力が成功したときに時計を読んで区切り、タイマーは使わない。枠は 1 本の接続の両方の向きに 1 つである。空きの枠が無く、後述の返せる枠も回収できる枠も無いときは、待たず、切らず、floor のまま続け、次の区間で条件を満たしたときに求め直す。boost を得た接続は、受信のバッファをその場で 4 MiB にし、送信のバッファを次の書き込みで 4 MiB にする
- 握手と floor の設定:Device は、TCP の endpoint を 1 つも作る前に、gVisor の stack に送信の範囲(既定と上限が 256 KiB)と受信の範囲(既定 256 KiB、上限 4 MiB)を設定する。設定に失敗したら stack を閉じ、Device を作らない。受信の上限を 4 MiB にするのは、gVisor が握手のときの受信の窓の scale を受信の上限から決めるためである。握手を終えた接続には、`Accept` と `DialTCP` が呼び出し側へ返す前に、floor を固定の値として設定して読み返す。固定すると gVisor の自動調整が止まる。握手の前に固定すると、窓の scale が floor から決まり、後で boost を得ても広い窓を広告できない。gVisor は受信のバッファを接続の読み取りのときにだけ自動で広げるので、最初の読み取りの前に固定すれば、枠の外で広がることはない。SYN cookie で成立した接続も gVisor の `Accept` から同じ経路を通ることは、ソースで確かめた。この経路を通る SYN cookie の接続は試験していない。`DialTCP` は `gonet` の dial を使わず、endpoint を自分で持って接続し、取り消しと失敗のどの出口でも endpoint を 1 回だけ閉じる。floor を設定できなかった接続は、`Accept` では RST で閉じて次の接続を待ち、`DialTCP` では RST で閉じて誤りを返す
- 枠を返す時機:接続の最後の `Close` か `Abort` が戻り、その接続の読み取りと書き込みが実行中でなく、endpoint が CLOSED か ERROR、または TIME_WAIT で受信のキューが空のとき、その枠は返せる。返すのは、空きの無い枠の集まりへの取得の要求が枠を調べるときである。枠を返すためのタイマーと goroutine は持たない。TIME_WAIT を返せる状態に含めるのは、固定版の gVisor が、自分の FIN が確認されたときにだけ TIME_WAIT に入り、相手の FIN を受けたときに順序外の受信のキューを捨て、読み取りを閉じた後に届いたデータでは接続を中断するためである(ソースで確かめた)。TIME_WAIT の接続が送った byte は、すべて確認済みである。受信のキューが空という条件は、固定版の gVisor では `Close` が受信のキューを捨てるので常に成り立つ。gVisor の更新でこの性質が変わっても、返した枠の後に受信のデータを残さないために置いている。FIN_WAIT_2 は返せる状態に含めない。`Close` の前に届いた順序外の受信のデータが残りうるためである。FIN_WAIT_2 の接続は、gVisor の期限(既定で 60 秒)の後に CLOSED になってから返せる
- 需要の無い保有者からの回収:取得の要求は、空きの枠も返せる枠も無いときだけ、1 秒の間どちらの向きにも前述の条件を満たしていない保有者を探し、1 本を floor に戻して枠を受け取る。戻す手順は次のとおりで、どれかが成り立たなければ、その保有者のバッファを boost の大きさに戻して枠を持たせたまま、次の保有者を見る。書き込みが実行中の保有者は戻さない。書き込みは待つ間も書き込みの排他を持つので、この排他を待たずに取れなければ見送る。受信は、バッファを先に floor に縮め、その後で endpoint が受信の segment に使っているメモリが floor 以下であることを求める。このメモリは、読まれていない受信のキューの segment、順序外の segment、処理を待つ segment を含む。gVisor は、データのある segment を、このメモリが受信のバッファ以下のときだけ受け入れる。順序外のデータが floor を超えたまま縮めると、穴を埋める再送も受け入れられず、正常な相手でも接続が止まる(単体テストで再現した)。floor 以下で縮めた後に新しく順序外に積めるのは、gVisor の規則(順序外の byte と segment の長さの和が受信のバッファの 3/4 未満)の分だけである。このため、処理を待つ segment が処理されれば、このメモリは floor 以下に戻り、穴を埋める segment は大きさによらず受け入れられる。gVisor はこのメモリを公開しないので、wgft は endpoint の非公開のフィールドを読む。読むだけで書かない。フィールドの名前と型は起動時に確かめ、go.mod の固定の版と合わなければ回収をしない。合わないことは 1 回だけログに出す。gVisor の更新でフィールドが変われば単体テストが落ちる。gVisor の内部に依存する代わりに、公開の TCP probe で全 segment の状態を写す方法と、回収をやめる方法があるが、前者は全 TCP の費用が大きく、後者は通常の利用の性能の退行を戻すので採らなかった(2026-09-30、所有者の決定)。送信は、キューに残る byte が floor と直前の 255 回の書き込みの長さの和の小さい方より少ないことを、書き込みと同じ方法で確かめる。成り立てば、floor の byte と書き込みの数の上限がその時点から成り立つ。送信の向きを閉じた(`CloseWrite`)保有者は戻さない。固定版の gVisor は、送信を閉じた endpoint を、キューにデータが残っていても書き込める状態と答えるので、送信の確かめが何も示さないためである。中継は片方向の EOF を `CloseWrite` で伝えるので、相手が読むのを止めた転送の後に起こる。このような保有者は、返せる状態になるまで枠を持つ。floor に戻った接続は、需要が戻ると枠を求め直す。1 秒は、転送を終えて開いたままの接続が boost を持ち続けて後続の転送を floor に留めないための値であり、最適値として探した値ではない
- TCP のバッファの上界:boost の分は、プロセスあたり 16 本 × (送信 4 MiB + 受信 4 MiB) の 128 MiB を名目の上限とし、floor を超える増分は 120 MiB である。floor の分は接続 1 本あたり送信 256 KiB と受信 256 KiB で、書き込みの数は 256 回、長さの履歴は 1 KiB である。boost を得た接続は書き込みを 4096 回まで持ち、長さの履歴は 16 KiB になる。byte の値はバッファが数える量であり、Go のヒープの上限ではない。書き込み 1 回ごとに gVisor が持つ管理の構造と、受信の segment の管理の費用は、書き込みの数と segment の数に応じて byte の外にかかる。TCP のバッファの仕組みは接続の数を抑えない。プロセス全体の TCP のバッファの量は、接続の数に floor を掛けた量と boost の分の和で抑えられる。接続の数には、同時フロー数の上限が数える中継の接続のほかに、accept の待ち行列の接続と、閉じた後に TIME_WAIT などで残る接続と、送り残しを持って閉じた接続が入る。accept の待ち行列と TIME_WAIT の数の上限は、後述の「プロセス全体のメモリの上界」の段落に書く。送り残しを持って閉じた接続の数を抑える仕組みは無い(後述の「送り残しを持って閉じた netstack の接続」)
- TCP のバッファで保証しないこと:floor と boost は資源の上限であり、最低の速さも遅れの上限も保証しない。17 本目以降の同時の転送は、需要のある 16 本が枠を持つ間 floor のまま進む。相手が読まない保有者は、送信のキューが floor の確かめを通らないので回収されず、枠を持ち続ける。接続を閉じても、送ったデータが確認されるまでは返らない。1 秒を超えて間の空く転送は、その間に枠を回収されうるので、再開のたびに floor から始まることがある。回収した接続の受信のメモリは、回収の時点で floor 以下であることを確かめてある。その後は、処理を待つ segment が一時的に floor を超えさせることはあるが、処理が済めば floor 以下に戻る。穴を埋めない相手は、順序外のデータを floor 以下の量で持たせ続けられる。順序外が floor を超えている保有者は回収しないので、その保有者は枠を持ち続ける。枠は、返すまで閉じた接続を参照する。取得の要求が来なければ最大 16 本の閉じた接続が残り、トンネルを作り直した後なら古い Device の stack も GC されずに残る。取得の要求は、枠の写しを調べる間も写しに載る接続を参照し、この参照は要求が戻ると消える。Windows と macOS のエージェントでの速さは確かめていない
- 中継のカーネルの TCP ソケットの受信のバッファ:ユーザー空間モードの中継は、カーネルの TCP ソケットを 2 か所で持つ。`vpsd` が公開側で accept する接続(`Transparent` の TCP のルールとプロキシモードのルールの中継)と、エージェントが LAN の宛先へ dial する接続である。中継の反対側が進まなくなると、このソケットには読まれないデータが溜まり、Linux は受信のバッファを自動調整の上限(`net.ipv4.tcp_rmem` の最大値。既定で 6 MiB)まで広げる。カーネルの TCP のメモリの上限(`net.ipv4.tcp_mem`)はホスト全体で 1 つであり、network namespace ごとには分かれない。使用量がこの上限に達すると、カーネルは受信のキューが空の接続にしか新しい segment を受け入れないので、同じホストの無関係な TCP(別のルール、SSH、エージェント用 API)まで、再送の時間ごとに 1 segment ずつしか進まなくなる。エージェントを LXC のようなコンテナで動かすと、カーネルを共有する他のコンテナの TCP も同じく遅くなる。ラボでは、読まない相手を両端に置いた中継を同時フロー数の上限の近くまで保持させると上限に達し、別のルールの小さな転送が数秒かかった(改訂の記録 2026-10-01)。このため中継は、この 2 か所のソケットの受信のバッファを、組にした netstack の接続の boost の枠(前述)に合わせて固定する(2026-10-01、所有者の決定)。固定したソケットでは Linux の自動調整が止まる。値はどれも設定項目にしない。この固定が抑えるのは、中継が持つカーネルのソケットが受信の側に溜める量だけである。ホスト全体の TCP のメモリを使い切ることによる巻き添えは、この固定だけでは防げない。ラボでは、1 つのカーネルを共有する `vpsd` とエージェントの受信の予算(後述の「プロセス全体のメモリの上界」の段落)の和が `tcp_mem` に収まる条件では、遅れが無くなった。`tcp_mem` を既定のままにした条件では、この固定の後も上限に達し、別のルールの小さな転送が数秒かかった
- 枠に合わせた固定:中継は、組のうちカーネルの TCP ソケットの側の受信のバッファを中継を始める前に固定し、組にした netstack の接続が boost の枠を持つかどうかに合わせて固定し直す。カーネルの側は、`vpsd` では公開側で accept した接続、エージェントでは LAN の宛先へ dial した接続である。netstack の側は、`vpsd` ではエージェントへ dial した接続、エージェントでは `vpsd` から accept した接続である。枠を持たない間は `SO_RCVBUF` で 128 KiB(実効の値 256 KiB)を、枠を持つ間は 4 MiB(実効の値 8 MiB)を要求する。固定し直すのは、netstack の接続が枠を得たときと、需要の無い保有者として floor に戻るときである。floor に戻るときの条件は次の項に書く。枠を得て返すのは netstack の接続だけなので、この固定は枠の数を増やさず、大きいバッファを持つカーネルのソケットはプロセスあたり 16 本までである。遠い利用者からの転送と LAN の宛先からの転送は、枠を得るまでは floor の窓で進み、枠を得た後は以前と同じ程度の窓を使える(ラボで確かめた)。宛先への試し接続は中継をしないので固定しない。UDP のソケットは変えない(前述の「エージェントの LAN 側のソケットの受信バッファ」)
- floor に戻す前の確かめ:`SO_RCVBUF` を下げても、カーネルのソケットがすでに持つ受信のデータは解放されない。受信のメモリが下げた値を超えていても、Linux は次の segment を受け入れるかを決めるときまで減らさない。減らすときに捨てるのは順序外のキューだけで、受信のキューの順序内のデータはまとめ直す(`tcp_collapse`)だけで捨てない(6.1 と 2026-10 の開発版のソースで確かめた)。穴を残して順序外のデータを送り、その後は何も送らない相手では、データは中継に読まれないまま残り、netstack の接続は需要の無い保有者に見える。そこで中継は、netstack の接続が floor に戻る前に、カーネルのソケットの受信のメモリが floor の実効の値(256 KiB)以下であることを求める。受信のメモリは `SO_MEMINFO` の `SK_MEMINFO_RMEM_ALLOC`(`sk_rmem_alloc`)で読む。この値は受信のキューと順序外のキューの segment の truesize の和であり、Linux が segment を受け入れるかを決めるときに受信のバッファの実効の値と比べる量である(同じソースで確かめた)。今読めるデータの量(`SIOCINQ`)は順序外のキューを含まないので使わない。中継は受信のメモリを先に読み、floor を超えていればバッファに触らない。超えていなければ受信のバッファを floor に下げてからもう一度読み、受信のバッファと受信のメモリがどちらも floor 以下のときだけ戻す。超えるか読めなければ、カーネルのソケットを boost に戻し、netstack の接続は boost のまま枠を持ち続ける。この扱いは、gVisor の側の受信のメモリが floor を超える保有者を戻さない規則(前述の「需要の無い保有者からの回収」)と同じ形である。この保有者は、別の接続が枠を求めるたびに改めて試される。穴が埋まって中継がデータを読むと受信のメモリが減り、戻せるようになる(`vpsd` の公開側についてラボで確かめた)。穴を残したまま黙る相手は、その間は枠を持ち続けるが、boost の大きさで持つソケットは枠の数を超えない。確かめの読み書きは、netstack の接続の排他の中で行う。下げた後の Linux は、segment を受け入れる前に受信のメモリを受信のバッファと比べ、超えていれば減らし、減らせなければその segment を捨てる。比べるのは加える前なので、受け入れた後に 1 skb 分を超えうる。6.1 は、受信のキューが空のときの順序内の segment を比べずに受け入れるので、超過はおよそ 2 skb 分になりうる。GRO でまとめた skb は 64 KiB 程度になりうる。このため floor に戻したソケットの受信のメモリは、floor に数 skb を加えた量に収まる。この量はソースから読み取ったもので、測定では未確認である。この確かめにより、floor を超える受信のメモリを持つカーネルのソケットも、この超過を除いてプロセスあたり 16 本までになる。`SO_MEMINFO` は Linux 4.12 で加わった
- エージェントの LAN 側の値:エージェントの LAN 側を固定の 256 KiB にして枠に合わせない形は採らなかった(2026-10-01、所有者の決定)。固定の窓は、宛先からクライアントへの向きの速さを、窓の大きさを LAN の往復の時間で割った値までに抑える。ラボでは、LAN に往復の時間を加えると、この向きの転送が以前より大きく遅くなった。所有者はこれを通常の利用での退行と判断した。宛先がエージェントと同じカーネルで動く場合(同じホストの別のコンテナなど)、宛先が送れずに待つデータは宛先の送信のバッファに残り、同じ `tcp_mem` に数えられる。この量は宛先の設定で決まり、wgft は抑えない
- 要求の通り方:要求は `SO_RCVBUFFORCE` で行い、権限が無ければ `SO_RCVBUF` に落ちる。`SO_RCVBUF` は `net.core.rmem_max` で切り詰められるためである。ユーザー空間モードの動作条件(前述の「ソケットのバッファの条件」)を満たすホストでは、`rmem_max` が 7340032 以上か、初期の user namespace の `CAP_NET_ADMIN` で FORCE が通るので、4 MiB の要求はどちらかで通る。条件を満たさないホストでは、boost の値が `rmem_max` の 2 倍に切り詰められ、遠い利用者からの転送と LAN の宛先からの転送が以前より遅くなりうる
- 窓の scale と窓の上限:カーネルの側の接続の握手は Linux の既定のまま行う。窓の scale は握手のときに `tcp_rmem` の最大値と `rmem_max` の大きい方から決まり、既定の値では 4 MiB の窓を広告できる。握手の前に受信のバッファを固定すると、scale が固定した値から決まり、後で boost の枠を得ても広い窓を広告できない。一方、握手の後に受信のバッファを固定すると、窓の上限(Linux の `window_clamp`)が自動調整で広がらなくなる。Linux 6.1 は握手の時点の受信のバッファから決めた窓の上限を持ち続け、7.2 は受信のバッファを固定するたびに窓の上限をそのバッファに合わせて置き直す(ラボの 6.1 と開発のホストの 7.2 で確かめた)。そこで中継は、受信のバッファを固定するたびに `TCP_WINDOW_CLAMP` で窓の上限を 4 MiB に置く。窓はこの上限と受信のバッファから決まる窓の小さい方になり、枠を持たない間は受信のバッファが、枠を持つ間は 4 MiB の上限が窓を決める。窓の上限だけで窓を抑える形は採らない。受信のバッファの自動調整が窓の上限を上書きし、上限が保たれないためである
- 固定する受信のバッファの上界:`vpsd` の公開側の受信のバッファは、プロセスあたり K × 256 KiB + 16 × 8 MiB を上限とする。既定の K の 2048 では 640 MiB である。この上界が数えるのは、動いている中継のソケットの受信の側だけである。ソケットが溜める受信のメモリにこの上界が効くのは、前述の floor に戻す前の確かめと、次の項の accept の直後の確かめによる。ソケットごとに数 skb の超過がありうる(前述)。accept が返す前のソケットはこの上界に入らない(次の項)。エージェントの LAN 側は、エージェントの K × 256 KiB + 16 × 8 MiB を上限とする。エージェントの boost の枠はエージェントのプロセスの 16 本である。どちらも名目の上限であり、実際に使うのはデータが溜まっている間だけである
- accept の直後の固定:`vpsd` の公開側では、中継は accept した接続の受信のバッファを、接続元の確かめ、Admission Policy、同時フロー数の上限、エージェントへの dial より前に floor に固定する。`Transparent` の TCP のルールの中継とプロキシモードのルールの中継で、accept の扱いは同じである。固定していないソケットでは、受信のメモリが受信のバッファを超えたときに、Linux が受信のバッファを `net.ipv4.tcp_rmem` の最大値まで広げうる。ホスト全体の TCP のメモリが `tcp_mem` の最初の値より少ない間に、受信のバッファを広げる経路(`tcp_clamp_window`)が働くためである(6.1 のソースで確かめた)。穴の後に小さい順序外の segment を続ける相手は、この広がりを起こしうる。dial の後の最初の固定は、枠を持たない接続を受信のメモリを確かめずに floor に下げるので、固定が dial の後だけなら、dial を待つ間に溜めたデータが K と 16 本の外に残る。中継は固定の直後に `SO_MEMINFO` で受信のメモリと受信のバッファを読む。どちらかが floor の実効の値を超えるか、固定か読み取りに失敗すれば、その接続を Admission Policy にも同時フロー数にも数えずに `SetLinger(0)` の RST で切り、頻度を絞ったログを 1 行出す。固定しても、ソケットがすでに持つデータは解放されないためである(前述の「floor に戻す前の確かめ」)。通った接続は floor に固定されたまま Admission と dial を待ち、dial の後は前述の枠に合わせた固定に移る。待ち受けのソケットには固定を置かないので、窓の scale は前述の「窓の scale と窓の上限」と同じく握手のときの Linux の既定から決まる。netstack の接続、カーネルモードのプロキシモードの中継、Linux 以外では何もしない。この固定が守るのは、accept が返した後のソケットだけである。握手を終えて accept の待ち行列にあり、まだ accept が返していないソケットは固定されておらず、同じ広がりで溜めうる。この待ち行列のソケットが溜める量は、この固定では抑えない。この固定は、ホスト全体の TCP のメモリを守るものでもない。固定したソケットを 6.1 の受信のバッファを広げる経路が広げず、受信のメモリが floor に数 skb を加えた量に留まることは、6.1 のソースと、wgft を通さないソケットの測定で、その測定の条件の下で確かめた。その測定では、穴の後に小さい順序外の segment を続ける相手に対して、固定しないソケットは受信のバッファを広げて溜め、固定したソケットは floor の近くに留まった。wgft の中の順序(accept、固定、受信のメモリの確かめ、Admission、dial)と、確かめが通さない接続を RST で切って Admission にも dial にも進めないことは、両方の accept のループを通る単体テストで確かめた。同じ相手を wgft の公開側に向けた測定は未確認である
- 固定しないもの:送信のバッファは固定せず、Linux の自動調整のままにする。これは送信の側を安全と判断したのではなく、上界を持たない保持を残したまま先送りする判断である(2026-10-01、所有者の決定。13 節)。残る保持とその危険は次のとおりである。
  - 送信のキュー:最初から読まない相手を置いたラボの再現では、中継の送信の側に溜まる量は受信の側より小さかった。一方、読むのを速く続けた後に止める相手では、送信のバッファが自動調整の上限(`net.ipv4.tcp_wmem` の最大値。既定で 4 MiB)まで広がり、`vpsd` の公開側のソケットとエージェントの LAN 側のソケットは、どちらもその上限の近くまで溜めた(ラボで確かめた)。送信のバッファを boost の枠に合わせて固定するだけでは上界にならない。中継の書き込みが終わった後もデータは送信のキューに残り、その間に netstack の接続の枠は回収されうるためである
  - 閉じた後のソケット:中継が閉じたカーネルのソケットは、送り残したデータを持ったまま、プロセスから離れてカーネルに残る。この残ったソケットは同時フロー数の上限 K にも boost の 16 本にも数えられない。ラボでは、送り残しを持つ 20 本が合わせて 54 MiB を 200 秒以上持ち続けた。閉じたソケットは、穴の後ろの順序外の受信のデータも持ったまま残りうる。Linux 6.1 は閉じるときに受信のキューだけを捨て、読まれていない順序内のデータが無ければ FIN を送ってソケットを孤児にする。順序外のキューを捨てるのは、ソケットを壊すとき、`tcp_disconnect`、相手の FIN を処理したときだけである(ソースで確かめた)。このため、boost の枠を得て穴を残し、黙った相手の接続を中継が閉じると(宛先の RST、ルールの変更による切断、`vpsd` の再起動など)、閉じたときの受信のバッファまでの順序外のデータが、相手が黙る限り FIN の再送が尽きるまで(既定でおよそ 100 秒以上)残る。この間、netstack の接続の枠は返るので、この保持も K と 16 本の外にある。wgft を通さないソケットでは、閉じた後も順序外のデータが残り、FIN の再送が尽きた後に消えることをラボで確かめた。wgft の中継を通した再現と、boost の大きさに近い量での再現は未確認である。送り残しと同じく、v1.3.0 の後の設計に含める
  - 残る危険:相手が読むのを止める操作を繰り返すと、どちらの保持もホスト全体の `tcp_mem` を使い、前述の巻き添えを起こしうる。1 本の保持が長く続くことはラボで確かめた。繰り返したときにホスト全体へ及ぶ影響は未確認である。v1.3.0 の後に送信の側と閉じた後のソケットの扱いを設計し直す
- Linux 以外の OS とカーネルモード:Linux 以外では固定しない。Windows と macOS のエージェントは OS の自動調整のままであり、固定したときの速さと、ホスト全体の TCP のメモリの上限の働き方を確かめていないためである。カーネルモードの `vpsd` のプロキシモードの中継は、両側がカーネルのソケットであり、固定の対象にしない。カーネルモードのエージェントは中継を持たないので、LAN 側の固定の対象が無い
- TCP の待ち受けの accept と UDP の待ち受けの読み取りが、待ち受けを閉じた場合以外の理由で失敗したときは、6.3 節の `vpsd` の中継と同じ部品なので同じく試し直し、ルールの状態は変えない。エージェントの待ち受けは netstack の上にあり、gVisor の TCP の `Accept` が誤りを返すのはエンドポイントが待ち受けの状態でないときだけである。中継自身が待ち受けを閉じた場合は試し直さずに終える。それ以外にエージェントで TCP の試し直しに至る経路は見つかっていない。エージェントの UDP の待ち受けは接続していない netstack のエンドポイントで、読み取りが誤りを返すのは、読みの期限(中継は設けない)、受信が閉じたこと(`Close`、`Shutdown`、stack の `Close`)、ICMP などで立つ直前の誤りだけである。直前の誤りは、接続したエンドポイントでしか立たない。このため UDP も、中継自身が待ち受けを閉じた場合を除いてこの試し直しに至らない(gVisor v0.0.0-20250503011706-39ed1f5ac29c のソースで確かめた。改訂の記録 2026-09-24)
- TCP の待ち受けを開いたときは、`target` へ 1 回だけ試し接続し、すぐ閉じる(`internal/dataplane/userspace/relay` の `checkTarget`)。繋がらない宛先を、フローが来る前にルールの `error` として報告するためである。宛先からは中身の無い接続 1 本に見える。UDP は送信だけでは到達を確かめられないので行わない
- `vpsd` からの PROXY protocol ヘッダは中身を見ずに素通しする
- 宛先の許可一覧:エージェントは、接続してよい宛先の一覧を `WGFT_AGENT_ALLOW_TARGETS` で受け取る(11a 節)。一覧があるとき、中継は一覧に入らない宛先へ接続しない。判定は、TCP の接続 1 本ごとと UDP のセッション 1 つごとに、実際に接続するアドレスと実効宛先のポートに対して行う。`target` がホスト名のときの名前解決の結果も判定の対象なので、DNS の変更で一覧の外へ向かうことはない。一覧があるとき、中継はホスト名の `target` を自分で解決し、一覧が通すアドレスだけへ接続する。判定したアドレスそのものへ接続するので、判定と接続の間に名前を引き直すことはない。通したアドレスの試し方は、一覧が無いときに使う Go の接続(`net.Dialer`)に合わせる。TCP では、解決の結果の先頭のアドレスと同じ族のアドレスを先に試す。300 ミリ秒のうちに繋がらなければ、もう一方の族のアドレスも並行して試し始め、先に繋がった接続を使う。同じ族の中では解決の結果の順に 1 つずつ試し、接続の期限の 10 秒の残りを、まだ試していないアドレスの数で分ける。1 つのアドレスの持ち分は 2 秒を下回らない。UDP は族を分けずに順に試す。Go の接続と違い、接続の期限は名前の解決の後から数え、名前の解決には別に 5 秒の期限を持つ。通したアドレスへの接続がすべて失敗した場合は、解決の結果の順で最後に試したアドレスの誤りを返す。一覧が通すアドレスが 1 つも無い場合は、最初に拒んだアドレスの理由を返す。この試し方の前は、通したアドレスを解決の結果の順に 1 つずつ、それぞれ 10 秒の期限で試していた。黙って捨てる IPv6 のアドレスが先に並ぶ名前では、接続に 10 秒かかり、5.2 節の 2 秒の接続確認がそのルールを `error` にしえた(改訂の記録 2026-10-03)。`target` が IP リテラルのルールは適用のときにも判定し、一覧の外にあればそのポートの待ち受けを開かず、5.2 節のルールの `error` として理由を報告する。収束の単位はポートなので、判定もポートごとに行う。ポートの範囲を持つルールで、範囲の一部のポートの実効宛先だけが一覧の外にある場合は、そのポートの待ち受けだけを開かず、範囲の他のポートは転送を続け、ルール全体は `error` として報告される。`target` がホスト名のルールの待ち受けは開き、接続のときに拒む。拒んだ TCP の接続は RST で終え、UDP のデータグラムは捨て、リスナーごとに 1 分に 1 回までログに出す。10.1 節の疎通確認は、エージェントの中継を通って宛先へ接続する経路なので、同じ一覧に従う。一覧が無いときは制限しない。狭める経路は、VPS を奪った攻撃者が `target` を書き換えてエージェントを自宅の LAN への踏み台にする経路である(11 節)
- ブロードキャストとマルチキャストの宛先:エージェントは、ブロードキャストとマルチキャストのアドレスへ転送しない(2026-10-03、所有者の決定)。拒むのは、全域のブロードキャストのアドレス `255.255.255.255`、IPv4 のマルチキャストのアドレス(`224.0.0.0/4`)、IPv6 のマルチキャストのアドレス(`ff00::/8`)と、エージェントのホストの帯のブロードキャストのアドレスである。ユーザー空間モードの中継は IPv6 のアドレスを書いた宛先の待ち受けを開かないので、IPv6 のマルチキャストのアドレスはホスト名の解決の結果にだけ現れる。帯のブロードキャストのアドレスは、ホストのインタフェースの IPv4 のアドレスとプレフィクス長から求める。プレフィクス長が 30 以下の帯の末尾のアドレスがこれに当たる。`/31` と `/32` の帯には帯のブロードキャストのアドレスが無いので、`/31` の両端のアドレスは拒まない。末尾が `.255` のアドレスでも、ホストのどの帯の末尾でもなければ拒まない。たとえば `/23` の帯の中ほどにある `.255` のアドレスはホストのアドレスとして扱う。インタフェースの一覧は、読んでから 5 秒の間は読み直さずに使う。一覧を読めなかった場合は、帯のブロードキャストのアドレスかどうかを判定できないので、その判定だけを行わずに転送し、読めなかったことと再び読めたことをログに 1 行ずつ出す。全域のブロードキャストとマルチキャストの判定は一覧に依らないので、この場合も拒む。判定の単位と報告は宛先の許可一覧と同じである。`target` が IP リテラルのルールは適用のときに判定し、該当すればそのポートの待ち受けを開かず、5.2 節のルールの `error` として理由を報告する。`target` がホスト名のルールは、TCP の接続 1 本ごとと UDP のセッション 1 つごとに名前解決の結果のアドレスで判定し、該当するアドレスへは接続しない。解決の結果にほかのアドレスがあれば、そちらへ接続する。どのアドレスへも接続しなかった場合の扱いは、許可一覧で拒んだ場合と同じである。この判定は許可一覧の有無に依らない。許可一覧があるときは、中継が自分で解決したアドレスを判定する。許可一覧が無いときは、中継はこの判定の導入の前と同じく宛先を名前のまま Go の接続に渡し、Go の接続が解決した各アドレスを、ソケットを作ってから接続する前に判定する(`net.Dialer` の `Control`)。名前の解決、TCP で IPv6 と IPv4 のアドレスを少しずらして並べて試すこと、接続の期限をアドレスの間で分けることは、ユニキャストの宛先では導入の前と変わらない。理由の文言は 2 つのモードで同じであり(7b.2 節)、`server doctor` はこれを `target_not_unicast` に分類する(10.2a 節)。拒む理由は 2 つある。カーネルモードでは、帯と全域のブロードキャストへ向けた DNAT のパケットは LAN へ出ず、エージェントのホスト自身の待ち受けに届いた(ラボで確認)。公開したポートの外にあるホスト自身の待ち受けへの経路になる。IPv4 のマルチキャストへ向けた DNAT のパケットは、LAN のグループにもホスト自身のグループの待ち受けにも届かなかった(ラボで確認)。ユーザー空間モードでは、この変更の前は、全域のブロードキャスト、帯のブロードキャスト、IPv4 のマルチキャストのどの宛先へも UDP のデータグラムが送られ、LAN のホストに届いていた(ラボで確認)。VPS を奪った攻撃者は、1 つのルールで LAN のすべてのホストかマルチキャストのグループへ届けられる。Wake-on-LAN のマジックパケットをブロードキャストへ送る宛先は、どちらのモードでもサポートしない。ユーザー空間モードでは、この変更の前はそのようなパケットが LAN に届いていた可能性があり、この変更がそれを止める。マジックパケットとそれを受ける機器では確かめておらず、この変更の前に機器を起こしていたかは未確認である。Wake-on-LAN の機能が必要になれば、別に設計する。エージェントを Docker のブリッジのネットワークのコンテナで動かす場合(`deploy/agent.compose.yaml` の既定)、帯のブロードキャストの判定に使うインタフェースはコンテナ自身のネットワークのものである。LAN の帯のブロードキャストのアドレス(たとえば `192.168.50.255`)は、その帯のインタフェースをコンテナが持たないので、帯のブロードキャストとしては拒まない

収束の判定はポート単位で行う。
エージェントは全体状態から、各リスナーの宣言値 `(proto, port) → (実効宛先, 所属ルール ID)` を計算し、現在の状態と突き合わせる。
実効宛先は、ルールの `target` のポートに、そのポートの範囲内での位置を足したものである。
実効宛先の比較は文字列で行い、`target` がホスト名のときの名前解決はセッション確立時に行う。DNS の変更でリスナーは閉じ直されず、新規セッションだけが新しい IP へ向く。

- ポートが宣言に現れて現在にない:開く
- ポートが現在にあって宣言にない:閉じる。そのポートの UDP セッション表を破棄し、中継中の TCP 接続もすべて切る。netstack の側は RST で切る(前述の TCP の項)
- 実効宛先が違う:閉じてから開く。セッションは閉じるときと同じ切り方で切れる
- 所属ルール ID だけが違う:何もしない。セッションは残る

この規則から、ルールの操作ごとの挙動が次のように導かれる。

- `enabled = false`:そのルールの全ポートが宣言から消えるので閉じる。`true` に戻すと開くだけで、切れるセッションはない。無効にしたときに切ったセッションはポートを保持しないので、直後に `true` に戻しても待ち受けはすぐに開く
- `target` の変更:全ポートの実効宛先が変わるので閉じ直す
- 範囲の伸縮:差分のポートだけ開閉する。範囲をずらして同じポートの実効宛先が変わった場合は、そのポートだけ閉じ直す
- ルールの分割と統合(5.4 節のバッチで 1 世代として行う):ポートの実効宛先が変わらなければセッションは残り、所属ルール ID だけが移る

ルール 1 本の上限は、今までどおり、そのルールに所属するリスナーのセッション合計で判定する。分割で移ったリスナーの既存セッションも、上限の判定では移動先のルールの数に入る。
ルールごとの最低分(7a.10 節)は、そのルールの登録に数えるセッションの数で判定する。セッションは、受け付けたときのルールの登録で数える。
分割で所属ルール ID が変わったリスナーの既存セッションは、分割元のルールの登録が続くあいだ、最低分の判定では分割元で数え、移動先のルールでは数えない。リスナーがその後に受け付けるセッションは、移動先のルールの登録で数える。
ルールの登録が退役したとき(そのルールの新しいセッションを受け付けているリスナーが無くなったとき。統合と名前の変更で消えるルール、削除、無効化、fail-closed を含む)、その登録のセッションのうち、今も新しいセッションを受け付けているリスナーが運ぶものは、そのリスナーの今のルールの登録で数える。したがって統合で消えたルールの既存セッションは統合先のルールで数え、分割の後に分割元のルールを削除すると、分割先のリスナーが運ぶ既存セッションは分割先のルールで数える。
統合で合計が上限を超えた場合、既存セッションは追い出さず、期限切れで上限を下回るまで新規を捨てる。

同時フロー数の上限は次の 3 段で、どれかに達したら新規のフローだけを拒む。既存のフローは追い出さない。プロセス全体の上限と、接続元 IP ごとの上限(`vpsd` だけ)が設定項目である(11a 節)。ルールごとの上限は設定項目ではなく、プロセス全体の上限から導く内部の値である。1 つのルールへのフラッドが全体の枠を使い切り、他のルールまで止めることを防ぐ。新しいフローを受け付けているルールが 2 本以上あるとき、ルール 1 本の上限はプロセス全体の上限の半分(切り上げ)である。各ルールは隔離予約から導く最低分を持ち、後から加わるルールのための小さな予備を空けておく。1 本のルールが保持できるのは、ルール 1 本の上限を超えない範囲で、自分の最低分と、他のルールの最低分と予備を残した残りの、大きいほうまでである。ルールが 1 本なら、そのルールは予備を除くプロセス全体の上限を保持できる。全体を上げれば、ルール 1 本の上限と最低分も一緒に上がる。最低分と予備の式、ルールの数え方、拒否の理由は 7a.10 節に定める。

| 上限 | UDP のセッション | TCP の接続 | 数え方 |
|---|---|---|---|
| ルールごと | 受け付けているルールが 2 本以上ならプロセス全体の上限の半分(切り上げ。既定で 4096)。ただし他のルールの最低分と予備を残すので、2 本か 3 本の構成で保持できるのはそれより少ない(既定で 4094)。1 本ならプロセス全体の上限から予備の 4 を除いた値(既定で 8188) | 同じ規則による値(既定で 1024。2 本か 3 本の構成で保持できるのは 1022、1 本なら 2044) | 上限はそのルールのリスナーが運ぶフローの合計、最低分はそのルールの今の登録に数えるフローの数(7a.10 節) |
| プロセス全体 | `WGFT_MAX_UDP_FLOWS`(既定 8192) | `WGFT_MAX_TCP_FLOWS`(既定 2048) | 全ルールの合計。`vpsd` では 6.2 節の中継の接続も同じ数に含める |
| 接続元 IP ごと | `WGFT_MAX_UDP_FLOWS_PER_SOURCE`(既定 256) | `WGFT_MAX_TCP_FLOWS_PER_SOURCE`(既定 128) | 全ルールの合計。`vpsd` だけ。ユーザー空間モードは Go の評価器(7a.9 節)で数え、カーネルモードは 6.1 節の `ct count` で数える。どちらのモードも `new_flow_rate` より先に判定し、拒んだフローを `src_flow` の drop に数える。値を 0 にするとそのプロトコルの上限を無効にする。エージェントから見た接続元は常に `10.200.0.1` なので、エージェントでは数えない |

プロセス全体の上限があるので、ルールの本数を増やしても保持するフローの数の最大は増えない。ルールの本数そのものには上限を設けない。リスナー 1 つの固定費(UDP は受信用の 65535 バイトのバッファ 1 つ)はポートの数に比例する。`vpsd` ではポートの数を管理者が決めるので、インターネットの側の攻撃者からは増やせない。エージェントではポートの数を `vpsd` が配る全体状態が決め、エージェントはその数に上限を持たない(後述のエージェントの上界の段落)。上限に達して拒んだことは、リスナーごとに 1 分に 1 回までログに出す。

プロセス全体の上限は、保持するフローの数の最大を決める値であり、メモリのバイト数の上限ではない。フロー 1 本が使うメモリは、フローの種類と状態で変わる。ラボの実測(改訂の記録 2026-09-18)では、フローを開いてデータを流さずに保持した状態で、`vpsd` のユーザー空間モードの UDP のセッション 1 件が使うメモリは約 14 KiB、TCP の接続 1 本は約 30 から 55 KiB だった。この値はその条件での測定であり、フロー 1 本の費用の一般的な値ではない。TCP の接続が使うメモリは接続の状態で変わり、この測定値より大きくなることがある。

`vpsd` とエージェントは起動時に、フロー数の上限から計算したメモリのソフト上限をランタイムに設定する(`debug.SetMemoryLimit`)。値は `32 MiB + 12 KiB × UDP の全体上限 + 44 KiB × TCP の全体上限` で、既定の上限では 216 MiB になる。係数は前述の測定から決めた定数であり、VPS のメモリの量は見ない。運用者が環境変数 `GOMEMLIMIT` を設定していれば、その値を優先し、wgft は設定しない。有効な値は起動ログに出す。ソフト上限は GC の目標である。wgft は現在 GOGC を設定しない。Go のランタイムは GOGC の既定(100)では、生きているヒープの 2 倍になるまで回収を待つ。このため、フラッドのように割り当てが続く間は RSS が保持分の約 2 倍まで膨らむ(既定の上限で保持分 176 MiB が 320 MiB になった)。ソフト上限を設定すると、ランタイムが管理するメモリがその値に近づいたところで回収を早めるので、この膨張が抑えられる。一方、生きているヒープがソフト上限を超えると、ランタイムは回収を繰り返して CPU を使うが、メモリの使用はソフト上限を超えて増える(改訂の記録 2026-09-19 の Windows のエージェントの測定)。したがってソフト上限はメモリの上限でも保証でもなく、wgft はソフト上限をメモリの安全の前提にしない。

フローの数とは別に、netstack から wireguard-go へ向かう出力の経路も、滞留するパケットの数の上限を構造として持つ。gVisor のキューが持つのは、トンネルの MTU 以下のパケット 1024 件とその管理のためのメモリである。wireguard-go は、取り出したパケットを 1 件ごとに新しいバッファに置く。バッファの大きさは `MaxMessageSize` で、Linux と macOS では 64 KiB、Windows では約 2 KiB である。ピアごとの送信のキューと device 全体の暗号化のキューは、どちらも入れ物を 1024 個まで持ち、入れ物 1 個は 1 回の `Read` の結果である。`Read` が 1 件ずつ返すので、UDP の送信が進まなくなり、ピアの送信のキューが埋まったとき、そのピアに滞留するのは、キューの 1024 個に、送信の処理が持つ 1 個と、キューへ入れるのを待つ読み取りが持つ 1 個を加えた 1026 件である。Linux では、この 1026 件のバッファが約 64 MiB になる。ハンドシェイクを待つパケットの置き場(ピアごとに入れ物 128 個。満杯なら古いものから捨てる)が重なると、約 72 MiB になる。wireguard-go の TUN の読み取りが固定で持つバッファは、device 全体の 1 回の件数(バインドの 1 回の受信の件数と TUN の 1 回の読み取りの件数の大きい方)の分で、後述の包みによりどちらも 1 なので 1 件分である。wireguard-go のバッファの pool は Linux では上限を持たないので、この滞留の上限を決めるのは、キューの長さと 1 回の `Read` の件数である。エージェントのピアは `vpsd` の 1 つだけなので、エージェントの滞留の上限は 1 ピア分の値である。`vpsd` のユーザー空間モードはエージェントごとにピアを持つので、滞留の上限は 1 ピア分の値にピアの数を掛けたものになる。前述のメモリのソフト上限の式はフローの数だけから導き、この滞留を含まない。受信の向き(wireguard-go から netstack へ)のキューも同じ形の上限を持つ。wireguard-go は WireGuard のソケットから読んだパケットを、ピアごとの受信のキューと device 全体の復号のキューに入れる。どちらも入れ物を 1024 個まで持ち、入れ物 1 個は 1 回のソケットの読み取りの結果で、1 件ごとに `MaxMessageSize` のバッファを持つ。標準のバインドの 1 回の読み取りは Linux では最大 128 件、それ以外の OS では 1 件なので、そのままでは構造の上界が Linux でピアごとに 1024 × 128 × 64 KiB(約 8 GiB)になる。前述の「WireGuard の受信の 1 回の件数」の包みが 1 回に 1 件を渡すので、復号と TUN の `Write` が受信に追いつかず、ピアの受信のキューが埋まったとき、そのピアに滞留するのは、キューの 1024 個に、キューへ入れるのを待つ受信が持つ 1 個と、TUN へ書いている処理が持つ 1 個を加えた 1026 件である。Linux では受信の goroutine が IPv4 と IPv6 に 1 つずつあり、両方が同じピアのキューの空きを待つと、キューへ入れるのを待つ入れ物が 2 個になるので 1027 件になる。Linux では、このバッファが約 64 MiB になる。これは生きているヒープの上界であり、RSS は後述の数え方で GC の係数を掛けた値である。device 全体の復号のキューは同じ入れ物を指すだけで、バッファを増やさない。ハンドシェイクのパケットのキューは device 全体で 1024 件のバッファを持ち、満杯なら捨てる。ほかに、包みは Linux で受信の関数(IPv4 と IPv6 に 1 つずつ)ごとに 128 件分のバッファを固定で持つ。TUN の `Write` は受け取ったパケットを netstack に同期して渡し、netstack の受け手の読み取りを待たずに戻る。したがって受信のキューに溜まるのは主に、CPU が復号と TUN の `Write` に追いつかない間であり、その量はソケットの読み取りの速さと、復号と TUN の `Write` の速さの差で決まる。ただし受信の処理は、鍵の更新の直後に送信を待つパケットを送るときと、握手を送るときに送信の向きを待つので、送信が進まない間にも溜まりうる。ピアの受信のキューが満杯の間は、wireguard-go の受信の goroutine(受信の関数ごとに 1 つ)がそのキューの空きを待つ。その間、同じ address family の他のピアの読み取りも待ち、届いたパケットはカーネルの WireGuard のソケットのバッファに溜まり、超えた分をカーネルが捨てる。この定常の状態は 1 回の受信の件数によらず同じで、他のピアの進む速さも同じである。1 回の件数が 1 のときに変わるのは、待ちに入るまでにそのピアが保持できるパケットの数である。この数は、包みが無いときの数に対して 1 回の読み取りが返した件数分の 1 になり、最も小さくなるのは 128 件を返したときの 128 分の 1 である。短い burst では、包みが無ければ待たずに済む(その分のメモリを使う)ところで、包みは待ちに入る。持続する過負荷ではどちらも同じ定常の状態に入る。負荷が去ればキューは空き、読み取りは戻る。満杯のときに無関係なピアへどの程度波及するかは、ラボの VM では受信のキューを満杯にできなかったので未確認である(改訂の記録 2026-09-27)。

プロセス全体のメモリの上界(式に数えた保持点がすべて同時に最悪になっても、それらが使うメモリがそれを超えないと示せる値)は、ユーザー空間モードのホストの要件として示す(2026-09-30、所有者の決定)。既定の上限(`WGFT_MAX_TCP_FLOWS` が 2048、`WGFT_MAX_UDP_FLOWS` が 8192)で、エージェントが 1 つ、TCP の宛先が 1 つの `vpsd` の上界は約 5.0 GiB であり、この `vpsd` を動かすホストには約 5.9 GiB のメモリが要る。この値は、後述の式に数えた保持点(入力に応じてデータや状態を持つ場所)がすべて同時に最悪になった場合のものであり、普段の使用量の予想ではない。式に入れていない保持点が後述のとおりあり、その中には量の上限を定めていないものもあるので、プロセスのメモリがこの値を超えないことは示せていない。wgft はメモリの量を見て新しいフローを断る仕組みを持たないので、上界がホストのメモリを超える構成では、すべての保持点を埋める攻撃を受けると OOM になりうる。既定の上限は変えない。メモリの小さいホストでは、運用者が後述の表を見て上限を下げる。カーネルモードの `vpsd` のメモリの上界は、ここでは定めていない。カーネルモードでも、エージェント用 API の認証前の接続と、プロキシモードのルールの TCP の中継は `vpsd` のプロセスが持つ。

上界は、保持点ごとの生きているヒープの上界を合計し、それに (1 + GOGC/100) を掛けて数える(2026-09-27、所有者の決定)。goroutine のスタックとランタイムの領域は、この積とは別の項として足す。wgft は現在 GOGC を設定しないので、GOGC は Go の既定の 100 とし、生きているヒープの 2 倍を置く。wgft は GOGC を明示して設定する方針であり、その値は未定である。メモリのソフト上限は GC の目標なので、上界を下げる根拠にしない(前述)。カーネルのソケットのバッファはプロセスの外の項であり、ホストに要るメモリを求めるときに別に足す。

`vpsd` の生きているヒープの上界は、次の表の項の和である。記号の K は `WGFT_MAX_TCP_FLOWS`、U は `WGFT_MAX_UDP_FLOWS`、A はエージェントの数、D は TCP の宛先の数、R は `per_source_rate` を持つルールの数、L は UDP の待ち受けの数を表す。TCP の宛先はエージェントのアドレスとポートの組であり、範囲のルールはポートの数だけ宛先を持つ。出どころの列の「導出」はソースから読んだ件数と確保の大きさの積、「測定」はホストかラボで測った値、「推定」はソースの構造からの見積もりである。測定は、どれも 1 つの版の 1 回の測定である。

| 保持点 | 生きているヒープの上界 | 出どころ |
|---|---|---|
| 固定の費用(ランタイム、データベース、管理用 API、トンネル 1 つ) | 17 MiB | 測定 |
| wireguard-go のピアごとのキュー(送信と受信の両方向) | 136.3 MiB × A | 導出 |
| wireguard-go の device 全体のキュー(ハンドシェイクのキューを含む) | 65 MiB | 導出。CPU が 4 個のときの値で、CPU の数に比例して少し増える |
| IPv4 の再組み立てと、ピア 1 つの待機の分 | 4 MiB + 0.15 MiB × A | 導出と測定 |
| UDP の受信の会計 | 10.4 MiB | 測定。前述の換算が最も大きくなる datagram の大きさの場合 |
| netstack の出力のキュー | 64 MiB | 導出。測った場面では 7 MiB 以下だった |
| 応答のバッファと UDP の待ち受けの読み取り | 7 MiB + 0.46 MiB × L | 導出と推定 |
| UDP のセッション | 4.5 KiB × U | 測定 |
| TCP のフロー(floor、endpoint、中継のコピーのバッファ) | 648 KiB × K | 測定。導出の値は 586 KiB |
| TCP の boost | 120 MiB | 導出 |
| `vpsd` が dial した TCP の接続の TIME_WAIT | 487 MiB × D | 件数は導出、1 本の大きさは測定 |
| 送信元ごとの新規フローの表 | 14 MiB × R | 推定 |
| エージェント用 API の認証前の接続 | 177 KiB × 1024 | 測定。測った要求の形のうち最大のもの |
| エージェント用 API の認証済みの stream | 3.9 MiB × A | 件数は導出、1 本の大きさは測定。確立した 1 本と、確立の前か置き換えられて閉じる途中の 2 本の分 |
| API の制限の表、設定、試し接続 | 12 MiB | 推定 |

TCP のフロー 1 本の値には、バッファが数える byte と中継のコピーのバッファから導いた 586 KiB ではなく、ラボで届いた 648 KiB を使う。差は、前述の「TCP のバッファの上界」の項のとおり byte の外にかかる gVisor の管理の構造の分と推定しているが、内訳は未確認である。goroutine のスタックは 3.2 KiB × U + 24 KiB × K + 16 KiB × 1024 + 55 KiB × A + 2 MiB とする(TCP の項は推定、ほかは測定)。ランタイムの領域は、10 MiB に生きているヒープの 5% を足した値とする(測定から丸めた)。プロセスの上界は、生きているヒープの 2 倍にこの 2 つを足した値である。既定の上限で A、D、R、L がどれも 1 なら、生きているヒープの上界は約 2.4 GiB で、プロセスの上界は約 5.0 GiB になる。

エージェント用 API の認証前の接続は、プロセスあたり 1024 本(コードの定数で、設定項目ではない)までで、送信元の段ごとの上限もある(11 節)。同時接続数の上限 4096 本の残りは認証を通った stream で、エージェントごとに、確立した 1 本と、確立の前か置き換えられて閉じる途中の 2 本までである(11 節)。置き換えられて閉じる途中の stream は、それを置き換えた stream の確立の前の枠を、閉じ終わるまで占める(5.2 節)。確立した 1 本は、1 MiB の上限に近いハートビートを読んでいる途中で約 1.3 MiB を持ち、確立の前の 1 本は、64 KiB のヘッダと 4 KiB の上限に近い最初のメッセージで約 124 KiB を持つ。どちらもホストで TLS の接続を張って測った値で、同じプロセスのクライアントの側の分を含む。置き換えられて閉じる途中の 1 本は、ハートビートを読んでいる途中の確立した 1 本と同じ状態にあるので、同じ約 1.3 MiB と数える。表の 3.9 MiB × A は、3 本がどれも測った形のハートビートを読んでいる途中の場合の値である。ハートビートのルールの状態の項目の数にはコードの上限が無く、`vpsd` は 1 MiB の読み取りの上限の内側の項目を、文字列を切り詰めたうえですべて保存する。小さい項目を多数並べた形では、保存する量だけで測った値を大きく超えうる。その量はソースの構造から 1 エージェントあたり約 17 MiB と推定しており、測っていない。この形のハートビートを送れるのは、そのエージェントの恒久トークンの持ち主だけである。

`vpsd` が中継のためにエージェントの待ち受けへ dial した TCP の接続は、`vpsd` の側が先に閉じると、gVisor の TIME_WAIT(60 秒)の間、送信元のポートを宛先ごとに予約し続ける。予約できるポートは gVisor の一時ポートの範囲の 49,536 個なので、宛先 1 つあたりの TIME_WAIT は 49,536 本以下である。1 本は TIME_WAIT の間に約 10 KiB を持ち(測定)、宛先 1 つあたり約 0.5 GiB になる。この量まで積むには、1 つの宛先へ毎秒約 826 本の新しいフローを 60 秒続ける必要がある。ポートを使い切ると、その宛先への新しい接続だけが失敗し、他の宛先と既存の接続には及ばない。このときクライアントに何が届くかは未確認である。この量は受け入れ、上界の項として数える(2026-09-30、所有者の決定)。一時ポートの範囲を狭めて宛先あたりの量を減らす案は採らなかった。狭めると、通常の通信で `vpsd` の dial の失敗が約 3 倍に増えたためである。この失敗は、宛先が先に閉じた接続がエージェントの側に TIME_WAIT の 4 つ組を残し、同じ 4 つ組を使う新しい SYN を gVisor が捨てることで起きる。今の範囲でも、同じ失敗はより低い頻度で起きる。この失敗は既知の制限として残す。

送り残しを持って閉じた netstack の接続は、中継が終わった後も残る保持点であり、wgft はその数を抑える仕組みを持たない。中継は、両方向が閉じたときと片方向が誤りで終わったときに、netstack の接続を通常の `Close` で閉じる(6.2 節)。gVisor は送信の向きを閉じるとき(`CloseWrite` か `Close`)、送信のキューの残りの後ろに FIN を置き、相手の FIN を受けていなければ FIN_WAIT_1 に、受けていれば LAST_ACK に移る。FIN_WAIT_1 の間に相手の FIN が届くと CLOSING に移る。`Close` は、受信のキューが空なら RST を送らない。同時フロー数の枠は中継が終わった時点で返るので、この接続は K に数えない。中継の書き込みが netstack の接続の送信で待つ間は、反対向きが誤りで終わるか、接続が RST で切られない限り、中継は終わらず、その接続は K に数えたまま残る。反対向きが誤りで終わると、`Close` がこの待ちを解き、中継は終わる。boost の枠を持っていた接続は、送ったデータが確認されるまで枠を返さないので、16 本に数えたまま残る(前述の「TCP のバッファで保証しないこと」)。枠を持たない接続は 16 本にも数えない。中継の側から意図して切る経路(待ち受けを閉じるとき、接続元制限の変更で切るとき、プロキシモードの中継を切るときなど)は RST で切るので、この状態を作らない。同じ経路は `vpsd` とエージェントのどちらの netstack にもある。

この状態を終わらせる仕組みは無いと、コードから判断している。相手が受信の窓を 0 のまま zero window probe に ACK を返す限り、gVisor は送信を打ち切らない。FIN_WAIT_1、CLOSING、LAST_ACK を期限で終わらせるタイマーは gVisor に無く、FIN_WAIT_2 の 60 秒の期限はこれらの状態に効かない。wgft は netstack の接続に keepalive、user timeout、linger、再送の回数を設定しない。相手が読み始めれば、接続は残りのデータを送りきって TIME_WAIT に移る。1 本が持つ送り残しは、枠を持たない接続では送信の floor の 256 KiB を超えないとコードから判断している。

VM を使わない 1 プロセスの Go の試験では、この状態の接続が観察を終えた 118 秒の時点まで残り、1 本が持つ送り残しは最大 213 KiB だった。213 KiB はその試験の 1 本の値であり、全体の上限ではない。

この保持は、前述の上界の式にも表にも、後述の「上界の式に入れない」一覧にも入っていない。前述のプロセスの上界はこの保持を含まない。未確認:118 秒を超える保持、LAST_ACK に残る場合の再現、プロキシモードの中継での再現、トンネルの作り直しでこの接続が解放されるかどうか、gVisor の管理の構造を含めた 1 本あたりのメモリの量、接続の数の上限と多数の接続での合計の量。

エージェントの生きているヒープの上界も同じ形の和で、`vpsd` と次の点が違う。既定の上限で、`vpsd` とエージェントの K が同じで、エージェントの TCP の待ち受けが 1 つなら、エージェントのプロセスの上界は約 5.6 GiB である。

- 固定の費用:ランタイムとトンネル 1 つの分として 20 MiB とする(推定)
- wireguard-go のキュー:ピアは `vpsd` の 1 つだけなので、ピアごとのキューと device 全体のキューの 1 組を持つ
- UDP のセッション:1.2 KiB × U とする(測定)。LAN の宛先へのカーネルの UDP ソケットは別にあり、ホストの項である
- エージェント用 API と送信元ごとの新規フローの表:エージェントはどちらも持たない
- accept の待ち行列:256 KiB ×(`vpsd` の K + 96)とする(推定)。待ち行列の接続は `vpsd` の dial だけが作る。`vpsd` がエージェントへ dial するのは、中継(プロキシモードの中継を含む)と、運用者が管理用 API か Web UI から起こす疎通確認(10.1 節。1 回につき 1 本)である。中継の dial の数は `vpsd` の K で抑えられる。96 の内訳は記録に残っていない。2026-10-03 の改訂までは、`vpsd` は待ち受けを開くときにも試し接続を同時に 32 件まで行っていた(6.3 節)。1 件の待ちを打ち切った後も下の dial は 5 秒の期限まで残るので、96 はその分(32 の 3 倍)と推定しているが、確かめていない。今はこの 96 を疎通確認の分の余裕として残す。疎通確認の同時の数を抑える仕組みは、コードを読んだ範囲では見つからなかった。この項は、疎通確認を同時に 96 本を超えて起こさない運用も前提とする。この上界は `vpsd` が信頼された相手であることを前提とする。gVisor の構造だけで見ると、待ち行列は待ち受け 1 つあたり 8,191 本まで伸びうる
- TIME_WAIT:487 MiB × エージェントの TCP の待ち受けの数とする。受けた側でも 4 つ組の一意性から宛先あたりと同じ件数になるという推定による
- 試し接続、boost の枠が参照する古い stack、少数の古いトンネルの世代:合わせて 4.4 MiB とする(推定)。boost の枠が参照する古い stack は最大 16 個である
- goroutine のスタック:2.2 KiB × U + 24 KiB × K + 2 MiB とする(TCP の項は推定、ほかは測定)

エージェントの上界のうち、待ち受けの数に比例する項(TIME_WAIT と UDP の待ち受けの読み取り)と accept の待ち行列の項は、`vpsd` が信頼された相手であることを前提とする。accept の待ち行列の項は、運用者が疎通確認を同時に 96 本を超えて起こさないことも前提とする(前述の一覧の項)。エージェントの待ち受けは `vpsd` が配る全体状態のルールのポートごとに 1 つ開き、エージェントは待ち受けの数に上限を持たない。範囲のルールはポートの数だけ待ち受けを開くので、範囲が 1-65535 の UDP のルール 1 本で、待ち受けの受信用のバッファだけで約 4 GiB(65535 × 64 KiB)になる。この値はソースから導いたもので、測っていない。11 節は、VPS を奪った攻撃者が全体状態の値を自由に選べることを脅威に含める。その攻撃者に対するエージェントのメモリの上界は定めていない。

ホストに要るメモリは、プロセスの上界に、カーネルの固定の分と、OS と他のプロセスのための余白 256 MiB(推定)を足し、1 - 0.093 で割った値とする。カーネルの固定の分は、`vpsd` では WireGuard のソケットの 56 MiB と、公開側の UDP の待ち受け 1 つあたり約 4.2 MiB である。公開側の TCP とエージェント用 API のソケットのバッファは、名目では K と接続の数に比例して大きい。ホスト全体の TCP のバッファは、上限 `net.ipv4.tcp_mem` を超えて増えない。0.093 は、この上限の既定の値がメモリに占める割合である(ラボのホストの値からの推定。Linux の既定の値はメモリの量に比例する)。ホストに要るメモリは今までどおりこの割合で数える。この数え方が示すのは、TCP のバッファが上限まで使われてもメモリが足りることだけである。上限に達すると前述の巻き添えが起きるので、`tcp_mem` の上限は TCP を遅らせずに使える量ではない(次の段落)。エージェントのホストでは、LAN 側の UDP のソケットの受信のキュー(名目で U × `net.core.rmem_default`)をホスト全体の `net.ipv4.udp_mem` が抑え、LAN 側の TCP のバッファを `tcp_mem` が抑える。この分はホストの設定で決まるので、次の表ではエージェントのホストに要るメモリを示さない。

中継のカーネルの TCP ソケットの受信の予算は、前述の「中継のカーネルの TCP ソケットの受信のバッファ」の固定から決まる K × 256 KiB + 128 MiB である。`vpsd` では公開側のソケットの、エージェントでは LAN 側のソケットの予算であり、どちらもそのプロセスの K で決まる。この予算は、動いている中継のソケットが受信の側に溜める量の上限であり、ホストが安全であるための十分な条件ではない。送信の側、中継が閉じた後に残るソケット(前述の「固定しないもの」)、エージェント用 API、同じホストの他の TCP には、別にメモリが要る。予算は、ホストの実際の `net.ipv4.tcp_mem` と比べる。`tcp_mem` はページの数で表した 3 つの値で、順に、圧迫を始めない量、圧迫の閾値、上限である。byte に直すにはページの大きさ(`getconf PAGESIZE`、多くのホストで 4096)を掛ける。使用量が圧迫の閾値を超えると、カーネルは TCP のバッファの使い方を抑え始め、上限に達すると前述の巻き添えが起きる。このため予算は上限より小さいだけでなく、圧迫の閾値と比べて余裕があることを見る。Linux の既定の `tcp_mem` は、起動時にカーネルが数えた空きのページから決まる。上限はそのページの数の約 3/32、圧迫の閾値は 1/16 で、圧迫の閾値は上限の 2/3 である。空きのページはメモリの量より少ないので、既定の値はメモリの量にこの割合を掛けた値より小さい。次の表のホストに要るメモリと同じ大きさのホストで `tcp_mem` が既定の値なら、既定の K の予算 640 MiB は、上限(約 560 MiB)と圧迫の閾値(約 375 MiB)のどちらも超える。K が 1024 と 512 の行も、予算が圧迫の閾値を超える。圧迫の閾値を下回るのは K が 256 の行だけで、その差も小さい。実際の圧迫の閾値は空きのページから決まり、メモリの量から数えた値より小さいので、ホストによっては K が 256 の行も圧迫の閾値を超える。この比較は 1 つのプロセスの予算だけで数えたものである。1 つのカーネルを共有するプロセスの予算は合算する。`vpsd` とエージェントを同じホストで動かす場合や、LXC のようなコンテナで動かす場合がこれに当たる。予算が収まらないときは、まず K(`WGFT_MAX_TCP_FLOWS`)を下げる。`tcp_mem` を変えるかどうかは、ホストの管理者がメモリの量と他の用途を確かめて決めることであり、LXC の中から変えるものではない。上限を引き上げると、TCP が使える回収できないカーネルのメモリが増えるので、引き上げることは無条件の解決にならない。

設定と履歴に比例して増える小さい保持点(観測の履歴、拒否の数の記録、データベースのキャッシュと WAL、エージェントの制御ソケットの接続)は、式にも前述の一覧にも入れていない。どれも量は小さいと推定しているが、未確認である。

警告の行は、この小さい保持点に入れない。警告の行は (エージェント, 種類, detail) の組で重複を除く。`ip-flapping` の detail は往復した 2 つの IP を含み、`ip-mismatch` の detail は stream の接続元 IP と wg エンドポイント IP を含むので、どちらも IP の組が違えば別の行になる。行の数はエージェントごと、種類ごとに 64 行までで、記録するたびに、最後に検出した日時が古い行から消す(5.2 節。2026-10-02 の 2 つの改訂の前は、どちらの種類にも上限が無かった)。stream の接続元 IP を観測するのは認証を通った stream だけであり、wg の endpoint を動かせるのは WireGuard の鍵の持ち主だけである。このため、上限までの行を新しい IP の組で入れ替えられるのは、そのエージェントの恒久トークンの持ち主か WireGuard の鍵の持ち主である。管理用 API の agent の一覧は、エージェントごとに、そのエージェントの警告の行だけを読む。上限に達したときのデータベースの大きさと、一覧を返すときのメモリの量は測っていない。これらの行は、式にも前述の一覧にも入れていない。

ラボ(4 vCPU の VM)で、ユーザー空間モードの `vpsd` に、floor を満たした TCP のフロー、エージェント用 API の認証前の接続(当時の上限は 4096 本)、UDP のセッションを、それぞれ上限の近くまで同時に保持させた。生きているヒープの最大は 1.66 GiB だった。既定のソフト上限の下で、RSS の最大は 1.88 GiB、cgroup のメモリの最大は 2.68 GiB だった。cgroup の値は、cgroup に数えられたカーネルのソケットのバッファ約 0.2 GiB を含む。さらに約 0.6 GiB は、transparent huge pages を always にしたホストの設定によると推定している。madvise にした同じ負荷では 2.05 GiB だった。どの値も、測った生きているヒープにこの数え方を当てはめた値の内側だった。ソフト上限を外した同じ負荷の実行(`GOMEMLIMIT=off`)では、生きているヒープの最大は 1.87 GiB で、RSS は生きているヒープの約 2.2 倍まで増えた。RSS の最大は、その実行の生きているヒープの最大 1.87 GiB にこの数え方を当てはめた値の内側だったが、差は約 0.6% だった。既定のソフト上限は RSS を生きているヒープの近くに保ったが、保持している間、GC が 4 個の CPU の約 30% を使った。ソフト上限は保証ではないので(前述)、表はソフト上限の効果を見込まない。このラボでは、boost、wireguard-go のキュー、出力のキュー、再組み立ての表、送信元ごとの新規フローの表、管理用 API を埋めていない。すべての項を同時に埋めた場合の RSS、エージェントのプロセスの実測、係数のばらつき、この数え方の値が RSS の厳密な上界になるかどうかは未確認である。WireGuard のソケットのバッファが cgroup のメモリに数えられるかも未確認である。

接続元 IP ごとの上限は、少数の IP からフローを保持してルールの上限を埋め、正規の利用者を締め出す攻撃を防ぐ。送信元を偽装できる UDP では、この攻撃は防げない。カーネルモードの VPS にも、6.1 節の `ct count` による同じ設定値の上限がある。この上限はプロセス全体の上限と連動しない。プロセス全体の上限を上げても既定値(256、128)のまま変わらないので、メモリに余裕がある VPS でプロセス全体の上限を上げて同時フロー数を増やしたい運用者は、接続元 IP ごとの上限も明示して上げる必要がある。

ユーザー空間モードでは、サービスから見た接続元は常にエージェントのアドレスになる。カーネルモードの見え方は 7b.2 節に書く。
ユーザー空間モードを既定に置く理由は、自宅側に nftables と `ip_forward` の設定を要求せず、6.1 節と同じ他チェーンとの干渉問題を自宅側に持ち込まないためである。
性能面でも、想定する用途(ゲームサーバの UDP、数 Mbps)に対して netstack の処理能力は十分に余裕がある。
カーネルモードは、エージェントの停止中や更新の間も転送を続けたい Linux のホストのための選択肢であり、明示したときだけ使う(2026-09-24、所有者の決定)。カーネルが転送するので、中継のプロセスの処理能力にも依らない。干渉問題には、6.1 節と同じく他のテーブルとホストの設定を検査して提示し、自動では書き換えない方法で答える(7b 節)。
