### 未確認の点

挙動を確認した配置と、確認していない配置を区別します。
未確認事項は動作保証に含めません。


- LAN の側に wgft0 の MTU より小さい区間がある場合の MSS。
  `rt mtu` はその区間の MTU を反映しません
- ホスト自身の LAN のアドレスへの DNAT での TCP の MSS。
  ホストの TCP が wgft0 の経路の MTU から MSS を決めると見込んでいる
- wgft0 から入る向きの SYN でも `rt mtu` が wgft0 の MTU から決まる理由。
  結果はラボで観測したが、カーネルのソースでは確かめていません
- `deploy/agent.kernel.conf` を Debian 以外のディストリビューション、たとえば Ubuntu と Fedora の systemd で使った配置
- SELinux または AppArmor が有効なディストリビューション、nesting が無効か AppArmor のプロファイルが制限をかける Proxmox VE の非特権のコンテナ、Incus の非特権のコンテナ、WireGuard のモジュールを自動で読み込めないホスト
- `rotate-key` の途中で鍵がずれた場合の通しの動作。
  部品の段の所有の判定、つまり 1 つ前の鍵を持つインタフェースを自分のものとし、今の鍵へ書き換えることは、ラボで確かめた
- Tailscale そのものが加える規則での経路の警告。
  ラボでは、`vpsd` のトンネルアドレスを別の表へ送る規則を手で加えて確かめた
- keepalive ごとのデータグラムによる回復の時間を、ユーザー空間モードのエージェントの回復の時間と並べて測ること
- プロキシモードのルールと疎通確認が DNAT を通って届くこと
- Docker でのカーネルモード
- エージェントのホストで Docker が公開しているポートを宛先にした DNAT
- Docker そのものを動かしたホストでの conntrack の収束。
  ラボでは、Docker に見立てた DNAT の行を部品の段で確かめただけです。
  本物の wgft0 を通したフローの収束は、エージェントへの組み込みの後にラボで確かめた
- エージェントの停止中に狭めた許可一覧が、宛先がホスト名のルールの古いフローに効かないこと([7b.4 節](lifecycle.md#7b4-収束と停止)の conntrack の収束の判定)の、実際の運用での影響
- conntrack の表が大きいホストでの、エージェントの収束のメモリと時間。
  収束は IPv4 のエントリをすべて読んで持ちます
- リンクや nftables の変更が頻繁なホスト(コンテナを次々に作る Docker のホストなど)での、変更の通知の後の見直しの負荷。
  見直しは通知をまとめるたびにテーブルと wgft0 を読みます
