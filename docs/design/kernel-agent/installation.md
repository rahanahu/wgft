### カーネルに置くもの

kernel エージェントは WireGuard インタフェースと nftables の DNAT を作ります。
他のテーブルの規則とホストの設定は、検査して提示します。


エージェントは次の 2 つを自分の資源としてカーネルに置く。

- WireGuard インタフェース:既定名は `wgft0` で、`WGFT_WG_INTERFACE` で変えられる([11a 節](../security/configuration.md#11a-設定の渡し方))。
  ピアは VPS の 1 つだけで、AllowedIPs は `vpsd` のトンネルアドレスの /32 です。
  エンドポイントと keepalive([4 節](../network.md#4-ネットワーク))を持ち、決まった待ち受けポートは持ちません。
  鍵は認証情報ファイルの鍵を、アドレスと MTU は全体状態の値を使います
- nftables のテーブル:名前は `table inet wgft_agent` に固定します。
  同じホストに `vpsd` の `table inet wgft` があっても名前は衝突しません。
  [6.1 節](../vps/kernel.md#61-カーネルモード)と同じく、宣言が変わるたびにテーブル全体を 1 つの netlink のバッチで差し替える

テーブルの形は次のとおりです。
`192.168.1.20` と `192.168.1.22` は LAN の宛先の例です。
例は行のコメントを省いています。

```
table inet wgft_agent {
  chain filter_pre {
    type filter hook prerouting priority mangle; policy accept;
    iifname "wgft0" ct state established,related accept
    iifname "wgft0" tcp dport 25565 accept
    iifname "wgft0" udp dport 2456-2457 accept
    iifname "wgft0" drop
  }
  chain nat_pre {
    type nat hook prerouting priority dstnat - 1; policy accept;
    iifname "wgft0" tcp dport 25565 dnat ip to 192.168.1.22:25565
    # 範囲のずらしは無名の連結 map で表す(5.3 節の実効宛先)
    iifname "wgft0" udp dport 2456-2457 dnat ip to udp dport map { 2456 : 192.168.1.20 . 2456, 2457 : 192.168.1.20 . 2457 }
  }
  chain input {
    type filter hook input priority filter - 10; policy accept;
    iifname "wgft0" ct status dnat accept
    iifname "wgft0" ct state established,related accept
    iifname "wgft0" drop
  }
  chain forward {
    type filter hook forward priority filter - 10; policy accept;
    iifname "wgft0" tcp flags syn / syn,rst tcp option maxseg size set rt mtu
    oifname "wgft0" tcp flags syn / syn,rst tcp option maxseg size set rt mtu
    iifname "wgft0" oifname "wgft0" drop
    iifname "wgft0" ct status dnat accept
    oifname "wgft0" ct state established,related accept
    iifname "wgft0" drop
    oifname "wgft0" drop
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    iifname "wgft0" oifname != "wgft0" ct status dnat masquerade
  }
}
```

- DNAT:wgft0 から入るパケットを宛先ポートで照合し、実効宛先([7 節](../agent-dataplane.md#7-データプレーン自宅側))へ書き換える。
  範囲のルールのずらしは、無名の連結 map でポートごとの宛先アドレスとポートを引く。
  範囲のルールは、ずれが 0 でも map で書きます。
  DNAT の行はルールごとに 1 行で、(プロトコル、待ち受けポートの先頭、ルール ID)の順に並べ、コメント `wgft:<ルール ID>:dnat` で持ち主を示します。
  範囲のルールの行は宣言の範囲で照合し、map には許可一覧が通したポートだけを入れる([7b.2 節](targets.md#7b2-宛先の扱い))。
  一覧の外のポートのパケットは filter_pre で落ちる。
  map の要素は、1 通の netlink のメッセージに入れる数を区切って送る。
  google/nftables v0.3.0 は要素をすべて 1 つの属性に入れ、属性の長さは 16 ビットなので、約 1,800 ポートを超える範囲では長さがあふれる。
  ラボでは、8,001 ポートの範囲で先頭の 1,857 個だけが黙って入り、60,000 ポートの範囲ではバッチ全体が拒まれて他のルールの公開も止まった。
  区切って送れば、全幅の範囲(1 から 65535)まで欠けずに入ります
- 入口の守り(filter_pre):wgft0 から入る新しい接続のうち、公開した (プロトコル, ポート) の組だけを DNAT の前で通し、残りを落とす(2026-09-24、所有者の決定)。
  成立済みのフローと、その関連のパケットは通す。
  通す行はルールの公開したポートの範囲ごとに 1 行で、コメント `wgft:<ルール ID>:pass` で持ち主を示します。
  チェーンは conntrack の後、DNAT の前の優先度(`mangle`、-150)に置く。
  VPS の側から触れる面を入口で閉じるためです。
  この守りは他のテーブルの DNAT にも Docker の実装にも依らず、ct mark や ct label を使わないので他の用途のビットとも衝突しません。
  これが無いと、エージェントのホストで他のテーブルが全アドレスに公開したポート(Docker の `-p 8080:80` など)に、VPS から wgft0 のアドレスで届く。
  ラボで確かめた
- MASQUERADE:wgft0 から入って DNAT したフローのうち、wgft0 以外へ出るものだけに掛ける(2026-09-24、所有者の決定)。
  表を wgft0 の側だけで書くので、エージェントは LAN のインタフェース名を知る必要が無く、そのための設定項目も持ちません。
  LAN のセグメントを複数持つ家でも、出口は経路表が決める。
  LAN のインタフェースを環境から推測しない([11a 節](../security/configuration.md#11a-設定の渡し方))。
  `iifname "wgft0"` の条件が無いと、エージェントのホストで他のテーブルが DNAT したフロー(Docker が公開したポートなど)にも一致し、その宛先のサービスから見た送信元をエージェントのホストのアドレスに変えます。
  転送されるパケットの postrouting では、入力のインタフェースを照合できます。
  wgft の MASQUERADE が他のプログラムの DNAT のフローに触れる理由は無く、wgft 自身の経路はこの条件でも覆える
- forward:DNAT したフローとその返りだけを通し、wgft0 が絡む残りの転送を落とす。
  wgft0 が絡まない転送には触れない
- input:wgft0 から入る新規の接続のうち、DNAT していないものを落とす([11 節](../security/admin-transport.md#11-セキュリティ))。
  filter_pre の後ろの二重の守りです。
  エージェントのホスト自身の LAN のアドレスへの DNAT は forward ではなく input を通るので、input は `ct status dnat` のフローを通す([7b.2 節](targets.md#7b2-宛先の扱い))
- MSS:wgft0 を通る SYN の MSS を、入る向きと出る向きの両方で `rt mtu` にクランプします。
  カーネルモードは TCP を終端しないので、LAN のサーバと利用者は自分のインタフェースの MTU から MSS を合意し、wgft0 の MTU を超えるセグメントを送りうる。
  この場合、PMTUD の ICMP を落とすホストが経路に 1 台あるだけで、大きな TCP がその向きで止まります。
  片方の向きだけをクランプすると、もう片方の向きが止まります。
  固定の値ではなく `rt mtu` を使うのは、wgft0 の MTU の変更に追従させるためです
- DF の付いた大きな UDP の応答:カーネルモードは UDP も終端しないので、LAN の宛先が DF を付けて返す UDP のデータグラムは、大きさを変えずに wgft0 へ送られる。
  IP のパケットが wgft0 の MTU を超え、LAN の MTU に収まる応答は、エージェントのホストのカーネルが捨て、宛先へ ICMP fragmentation needed を返します。
  MTU が 1420 と 1500 なら、ペイロードが約 1393 から 1472 バイトの応答です。
  宛先がこの ICMP を受けて経路 MTU を学習すれば次の応答から通るが、その大きさの最初の応答は失われる。
  宛先のホストがこの ICMP を落とす場合は、その大きさの応答が失われ続けます。
  ユーザー空間モードのエージェントは UDP を終端して中継するので、この影響を受けない。
  以上をラボで確かめた。
  client から VPS への向きの同じ現象は [4 節](../network.md#4-ネットワーク)に書いた

テーブルは google/nftables の式で組み、`nft` コマンドを実行しません。
[6.1 節](../vps/kernel.md#61-カーネルモード)と同じく 1 つのバッチで送り、[7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)の指紋で外からの変更を見つけられるようにするためです。
指紋の関数は、server とエージェントで同じものをテーブル名を渡して使います。
google/nftables v0.3.0 は MSS の行の `rt` と `byteorder` の式を読み戻せず、誤りを出さずに読み飛ばす。
このため指紋はこの 2 つの式を見ません。
`nft replace rule` は行の handle を保つので、MSS の行をこの 2 つの式だけが違う行へ差し替えても指紋は変わりません。
固定の値への差し替えのように他の式が変わる差し替えは、指紋に表れる。
組み立ては `internal/dataplane/linuxkernel` の側に置くので、[7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)の import の境界は変わりません。

エージェントは起動のたびに `net.ipv4.ip_forward` を読み、1 でなければ 1 にします。
新しい network namespace の初期値は環境によって違い、コンテナの中の値はホストの値を写すことがあるので、初期値を当てにしません。
0 から 1 に変えたときは、その事実と日時を状態ファイル `agent.json` に記録し、撤去([10.3 節](../operations/setup.md#103-運用の流れ))で戻す候補として示します。
記録は値を書く前に保存します。
書いた後に保存すると、その間に落ちたとき、wgft が変えた値の記録が残らないためです。
記録を保存できなければ値を書かずに起動を終える。
値を書けなかったときは記録を元に戻します。
今の値を読めなかったときは、0 だったとは言えないので、1 を書いても記録しません。
いったん 1 にした値を自分では 0 に戻しません。
値を書く前に記録を保存する点は [6.1 節](../vps/kernel.md#61-カーネルモード)の `vpsd` と同じだが、違いが 2 つあります。
`vpsd` は書く前の予定の記録と書いた後の確定の記録の 2 段で、エージェントは書く前の 1 段だけです。
`vpsd` は予定の記録を保存できなくても警告して値を書くが、エージェントは記録を保存できなければ値を書かずに起動を終える。
書き込みに失敗した場合は、`vpsd` と同じく警告を出して起動を続けます。
値を読めず書けもしなかった場合は、1 でないとは言えないので、理由は値が分からないことと、読みの誤りと書きの誤りの両方を示し、「転送しない」ではなく「転送しないかもしれない」と述べる(2026-10-03)。
値が分かっていて 1 でない間は、宛先がホスト自身でないルールは転送されないので、それらのルールを `error` として報告します。
値が分からない間も、転送されないかもしれないので同じく `error` として報告します。
30 秒ごとの読み直しで値が 0 と分かれば、理由を値が 0 と述べる文に置き換える。
起動時に書けなかったことが分かっていれば、0 を読んで書けなかった場合と同じ理由にして、その事実を保つ。
この `error` は [7b.3 節](targets.md#7b3-ルールの状態と失敗の種類)の 2 つ目の種類と同じく報告だけに使い、DNAT は残します。
理由の文言は、どのホストの値かを名指す (2026-09-25)。
理由は `server doctor`、`status`、`agent ls`、Web UI で VPS の上で読まれるので、「このホスト」と書くと VPS の値に読めるためです。
`server doctor` はこの理由を `rule.target` の理由の符号 `agent_ip_forward_off` に分類する ([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))。
テーブル全体の失敗(3 つ目の種類)には当たらない。
`agent doctor` の `host.forwarding` はこの状態を FAILED とする([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))。
エージェントは値を 30 秒ごとに読み直し、1 になればルールの `error` を消す。
自宅のホストがルータとして振る舞える状態になることの影響は [11 節](../security/admin-transport.md#11-セキュリティ)に書きます。

`rp_filter` の strict は、受信したインタフェースが送信元への戻りの経路と異なるパケットを拒むため、複数の LAN セグメントを持つホストで転送を壊し得ます。
エージェントはこの値と、他のテーブルの forward の `policy drop` を検査して提示し、書き換えない([6.1 節](../vps/kernel.md#61-カーネルモード)と同じ方針)。

他の値の扱いは次のとおりです。

- 同時フロー数の上限:`WGFT_MAX_UDP_FLOWS` と `WGFT_MAX_TCP_FLOWS` はカーネルモードでは使いません。
  値が設定されていれば、使わない旨を起動時に 1 行出して起動を続けます。
  拒否にしないのは、モードを切り替えても同じ `agent.env` を使えるようにするためです。
  ルールごとの隔離も持たない([7a.10 節](../resource/admission.md#7a10-resource-guard-の再設計))
- UDP の期限:全体状態の `udp_timeout` と `udp_timeout_stream` は使いません。
  エージェントのホストの conntrack の期限が効く
- conntrack の表の上限:エージェントは変えず、読めれば提示するだけにする([7a.10 節](../resource/admission.md#7a10-resource-guard-の再設計)の kernel 側の保護)
- エンドポイントの引き直し:[4 節](../network.md#4-ネットワーク)と同じく、ハンドシェイクが keepalive の 5 倍の間成立しなければ、名前を引き直して wgctrl でピアに設定し直す。
  カーネルの WireGuard は名前を自分では引き直さないためです。
  名前の解決はエージェントのプロセスが行い、インタフェースの収束には解決の結果のアドレスを渡す。
  解決できていない間の収束は、カーネルが持つエンドポイントをそのまま残します。
  この間に初めてピアを置く場合は、エンドポイントの無いピアを置き、解決できた後の収束で加えます。
  名前を引くのは、起動時、この keepalive の 5 倍の契機、宣言のエンドポイントが変わったとき、まだ一度も解決できていない間の適用のたびです。
  5 倍の契機で引くのは、宣言のエンドポイントの名前です。
  宣言が新しい名前に変わってまだ解決できていない間も、旧い名前ではなく新しい名前を引く。
  5 倍の契機で引き直せたら、アドレスが変わらなくても wgft0 を収束させる。
  外から書き換えられたピアのエンドポイントは、ここで戻る。
  この収束に失敗したら、次の 30 秒ごとの見直しで引き直しと収束を試し直す。
  失敗した見直しも、残りの表の修復と経路の確かめは行います。
  稼働中に現れた重なりのように収束の失敗が続く間も、30 秒ごとの見直しが表の修復に届くためです。
  keepalive が 0 の設定では、5 倍の契機で引き直さない。
  5 倍の期間が 0 になり、見直しのたびに名前を引くことになるためです。
  エンドポイントが IP アドレスそのものの場合も、引く名前が無いので引き直さない。
  一度解決できた名前を引けなくなった場合は、直前に解決したアドレスを使い続けます。
  名前の解決が一時的に止まっただけで、それまで通じていたエンドポイントをピアから外すと、トンネルまで止めることになるためです。
  30 秒ごとの収束には直前に解決した結果を渡し、その都度引き直した結果もゼロ値も渡さない。
  その都度引き直すと、30 秒ごとに DNS へ問い合わせ、[4 節](../network.md#4-ネットワーク)の契機と違う時点でエンドポイントを動かすことになります。
  ゼロ値を渡すと、外から書き換えられたエンドポイントが戻りません。
  エンドポイントだけの食い違いは、テーブルの公開し直しを要する外からの変更として扱わない。
  インタフェースの収束だけで直り、またカーネルは認証済みのパケットが届いた送信元へエンドポイントを自分で移すので、外から変えられたとは限らないためです。
  [7 節](../agent-dataplane.md#7-データプレーン自宅側)のトンネルの作り直しはカーネルモードにはありません。
  作り直しが備える受信の goroutine の停止は、wireguard-go に固有の故障だからです
- セッションの回復:エージェントは keepalive ごとに、wgft0 を通して `vpsd` のトンネルアドレスへ小さな UDP のデータグラムを 1 つ送る。
  ユーザー空間モードのトンネルが keepalive ごとにトンネル内へ ping を送るのと同じ目的です。
  keepalive のパケットだけでは、`vpsd` の側がセッションを失ったとき(VPS の再起動や wg0 のピアの置き直し)に、エージェントは今のセッションを使い続け、新しいハンドシェイクを鍵の寿命まで始めない。
  エージェントがハンドシェイクを始めた側のセッションでは REKEY_AFTER_TIME の 120 秒の後、応じた側のセッションでは鍵が使えなくなる REJECT_AFTER_TIME の 180 秒までです。
  WireGuard は、データを送ってから 15 秒の間何も届かなければハンドシェイクをやり直すが、この契機を起こすのはデータのパケットだけで、keepalive は起こさない。
  データグラムを送れば、回復までの時間はユーザー空間モードと同じ桁になります。
  データグラムへの応答は要りません。
  セッションが生きていれば、データを受けた `vpsd` の側の WireGuard が keepalive を返し、それが契機を解く。
  ICMP の echo ではなく UDP を使うのは、生のソケットも追加の権限も要らないためです。
  データグラムは 1 バイトで、宛先は `vpsd` のトンネルアドレスの UDP のポート 9(discard)です。
  応答を求めないポートを選んだ。
  カーネルモードの `vpsd` は wg0 から入る新しい接続を input で数えずに落とし、ユーザー空間モードの `vpsd` の netstack はこのポートで待ち受けないので、どちらのモードでも `server doctor` とサーバのカウンタに表れない。
  keepalive が 0 の設定では送らない。
  送れない間は、理由が変わったときだけ 1 行出す。
  理由は下層の誤りの種類(errno)で比べる。
  書き込みの誤りの文言は、送るたびに違う送信元のポートを含むためです。
  ピアにエンドポイントが無い間、たとえば名前がまだ一度も解決できていない間は、送れない理由としてそのことを出す
- トンネルのアドレスの記録:エージェントは、登録で割り当てられたトンネルのアドレスを帯の長さまで状態ファイル `agent.json` に記録する([9 節](../state.md#9-状態の保存と再起動))。
  カーネルモードのエージェントは、全体状態の `wg.address` が記録と違えば、その全体状態を wgft0、アドレス、経路に触る前に拒み、ルールも適用しない(2026-09-25、所有者の決定)。
  VPS を奪った攻撃者が LAN の帯より細かい帯を配ると、wgft0 の接続経路が LAN の経路に勝つためです。
  LAN が `192.168.1.0/24` のときに `192.168.1.100/25` を配ると、ホストから LAN の半分へ届かなくなり、帯の先頭の次のアドレス `192.168.1.1` 宛ての通信は暗号化されて VPS へ届く。
  帯は server が自由に選べるので、引き込める宛先も自由に選べる。
  正規の運用では、登録の後にエージェントのアドレスは変わりません。
  server は `WGFT_WG_ADDRESS` の帯の変更を、`server teardown --purge` と登録のし直しなしには拒むためである([9 節](../state.md#9-状態の保存と再起動))。
  この記録が、server が配る帯に対する守りの境界です
  - 記録の時点:登録の応答はアドレスだけを返すので、登録の時点ではアドレスだけを記録し、帯の長さは最初に適用できた全体状態から記録します。
    記録の無い `agent.json`、つまりこの記録より前の版が書いたファイルも、最初に適用できた全体状態のアドレスを帯の長さまで記録します。
    起動時は `last_state` があれば stream より先に適用するので、その適用が成功すれば、更新したエージェントは更新の前に受け取った値を記録します。
    `last_state` が無い場合、たとえば停止中の `rotate-key` が消した後と、その適用が失敗した場合は、stream から最初に適用できた全体状態の値を記録します。
    適用に失敗した全体状態の値は記録しません。
    記録を置き換えるのは登録のし直しだけで、撤去([10.3 節](../operations/setup.md#103-運用の流れ))は記録を消さない。
    帯を移すときは、server の運用者が `server teardown --purge` を実行し、エージェントを新しい接続文字列で登録し直す
  - 拒んだとき:拒んだ全体状態の処理済み世代は進めません。
    トンネルが立っていれば、wgft0 とテーブルは直前に適用した全体状態のまま残り、30 秒ごとの見直しもその全体状態に対して続く。
    wgft0 とテーブルを消して転送を止めることはしません。
    奪われた VPS は VPS の側だけで転送を止められるので、止めても守れるものは増えず、見直しを止めると、テーブルが消えたときに守りの行が戻らなくなる([11 節](../security/admin-transport.md#11-セキュリティ))。
    server の側が新しい帯で動けば、トンネルの中の宛先と wgft0 の AllowedIPs が合わないので、通しの転送は止まります。
    ハートビートのトンネルの状態は `error` になり、理由は拒んだ世代、届いた値、記録を示します。
    ログの文面は、帯を移す正規の手順が登録のし直しであることを示します。
    トンネルがまだ無い間に届いた全体状態は、他の wg 設定の誤りと同じく作成の失敗として報告します。
    同じ検証は wg 設定の形も確かめるので、トンネルが立っている間に届いた全体状態の mtu、keepalive、server の公開鍵が不正な場合も、アドレスの場合と同じく wgft0 とテーブルを残したまま拒み、ハートビートに拒んだことを示します。
    拒んだことの表示を消すのは、拒んだ世代と同じか新しい世代の全体状態を受け入れたときだけです。
    公開に失敗していた古い世代の試し直しが通っても、表示は消えない。
    `agent doctor` の `tunnel.local` は、この場合に解決済みのエンドポイントが転送を続けられるとは述べず、server が拒んだ設定で動く間は転送が止まることと、登録のし直しを示します。
    server が配る wg 設定のうち、ホストに書く前に確かめる値の検証は、エージェントの中の 1 か所に集める
  - ユーザー空間モード:ユーザー空間モードのエージェントも同じ記録を持つが、記録と違うアドレスも使い、同じ値の間は警告を 1 行だけ出す。
    ユーザー空間モードのトンネルは netstack の中に閉じ、ホストのアドレスと経路に触れないので、この攻撃が成り立たないためです。
    公開済みのユーザー空間モードの挙動は変わりません。
    記録は書き換えないので、後でカーネルモードへ切り替えても照合の元が残る
- アドレス帯の重なり:エージェントは、wgft0 の帯がホストの他のインタフェースのアドレスの帯か main の経路と重なれば、wgft0 に何も書かずに終了コード 1 で止まります。
  重なりは両方向で見る(2026-09-25、所有者の決定)。
  wgft0 の帯が相手を含む場合は、相手の細かい経路が wgft0 の帯の一部を奪う。
  相手が wgft0 の帯を含む場合は、wgft0 の接続経路が相手の帯の一部を奪い、エージェントのホストからその部分のホストへ向かう通信がトンネルへ入ります。
  既定経路はどの帯も含むので対象にしません。
  `0.0.0.0/1` と `128.0.0.0/1` の 2 本の経路も対象にしません。
  OpenVPN の `redirect-gateway def1` のような VPN は、既定経路を消さずに上書きするためにこの 2 本を入れる。
  2 本は合わせて既定経路と同じ働きをし、どの帯も含むので、既定経路と同じ理由で除外します。
  対象にすると、この VPN を使うホストではどの帯でもカーネルモードが起動できません。
  長さ 0 か 1 のアドレスの帯も、`vpsd` のトンネルアドレスそのものでなければ同じ理由で除外します。
  この検査は多重の守りの 1 つで、守りの境界は上のアドレスの記録です。
  記録は server が帯を変えることを止め、この検査は利用者の設定の誤りで帯が LAN と重なった場合も止めます。
  重なりのうち、`vpsd` のトンネルアドレスそのもののアドレスと、そのアドレスを含み wgft0 の帯と同じかより細かい帯と経路は、`vpsd` への通信も wgft0 から奪う。
  前者はローカルに届き、後者は wgft0 の経路に勝つか並ぶためです。
  エラーの文面は、この場合に `vpsd` への応答がトンネルを通らないことを示します。
  帯の上半分を使うコンテナのブリッジのように、`vpsd` のトンネルアドレスを含まない重なりも拒みます。
  読むのは main の経路表だけです。
  main より先に引かれる規則の表、たとえば Tailscale がサブネットの経路を受け入れたときの表 52 が `vpsd` のトンネルアドレスを奪う場合は、この検査では見えません。
  このためエージェントは、wgft0 を収束させた後と、30 秒ごとの見直しと変更の通知の後の見直し([7b.4 節](lifecycle.md#7b4-収束と停止))で wgft0 が宣言どおりになった後に、規則を含む経路の引き当て(`RouteGet`)で `vpsd` のトンネルアドレスへの経路が wgft0 を通るかを確かめ、通らなければ警告を 1 行出す(2026-09-24、所有者の決定)。
  wgft0 が宣言と違う間は確かめない。
  wgft0 が消えたか down の間は、経路が既定経路へ出るのが当然で、原因の違う警告になるためです。
  警告は、引き当てが示す経路の出口と、`vpsd` への応答がトンネルを通らないおそれだけを述べ、原因を決めつけない。
  規則の表のほかに、稼働中に main の表に現れた重なりの経路も同じ警告になるためです。
  引き当ては、エージェントのホスト自身が送るパケットの経路を引く。
  送信元や入力のインタフェースで表を分ける規則、たとえば `from <LAN の帯> lookup X` は反映しません。
  DNAT した通信への LAN のホストからの応答は、エージェントのホストが転送するパケットなので、この種の規則が応答をトンネルの外へ送っても警告は出ない。
  起動は止めません。
  ポリシールーティングは稼働中にも変わり、起動の後に現れた規則を起動の拒否では扱えないためです。
  警告は食い違いが続く間 1 行だけ出し、経路が戻ったときにも 1 行出す。
  この所見を `agent doctor` に示すのは、カーネルモードの診断の段です。
  帯は server が決めるので、エラーの文面は重なった相手を示し、次の一手を 3 つ案内します。
  ホストの側でそのアドレスか経路を外すこと、server の運用者が `WGFT_WG_ADDRESS` で帯を移すこと、このエージェントをユーザー空間モード(`WGFT_MODE=userspace`)で動かすことです。
  帯を移すには、VPS での `server teardown --purge` と、すべてのエージェントの新しい接続文字列による登録のし直しが要る([9 節](../state.md#9-状態の保存と再起動))。
  ユーザー空間モードのトンネルはホストに経路を加えないので、重なりの影響を受けない。
  カーネルモードからユーザー空間モードへ切り替えるには、先に `agent teardown` が要る([11a 節](../security/configuration.md#11a-設定の渡し方))。
  同じ network namespace で `vpsd` を動かすと、その wg0 のアドレスがこの重なりに当たる。
  稼働中に重なりが現れた場合も、次の収束は何も書かずに失敗し、wgft0 はそのまま残る。
  次の収束は、wgft0 が宣言と食い違ったときか全体状態を適用するときであり、30 秒ごとの見直しは重なりのために経路とアドレスを読まない([7b.4 節](lifecycle.md#7b4-収束と停止))。
  このため、稼働中に現れた重なりは、その時点までこの検査では報告されない。
  ただし、引き当てが wgft0 以外を選ぶ重なりは、上の 30 秒ごとの経路の確かめが警告として報告します。
  起動の拒否(終了コード 3)にしないのは、相手のアドレスか帯が変われば次の起動で通るためである([11b 節](../security/startup.md#11b-起動の失敗の意味論))
