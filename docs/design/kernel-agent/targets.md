<a id="7b2-宛先の扱い"></a>
### 宛先の扱い

宛先の名前は全体状態の適用と定期的な見直しで解決します。
ルールを公開できない失敗と、公開後の TCP の接続確認の失敗を区別します。


DNAT は宛先の IP アドレスを要するので、宛先の扱いの形はユーザー空間モードと違う。
守る範囲は同じにする(2026-09-24、所有者の決定)。

- ホスト名の宛先:DNAT を組む前に解決し([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)の `Prepare`)、30 秒ごとに解決し直し、ポートごとの DNAT の宛先が変わったときだけテーブルを公開し直す。
  解決の結果の集合が変わっても、許可一覧を当てはめて選ぶアドレス(複数の A レコードの項)が同じなら公開し直さない。
  DNAT が同じでルールの理由の文言だけが変わった場合、たとえば解決の失敗の文面が変わった場合は、公開の記録とルールの状態を書き換え、テーブルは差し替えない。
  公開し直した後は新しいフローだけが新しい IP へ向き、成立済みのフローは切らない。
  ユーザー空間モードも宣言の宛先の文字列を比べ、解決の結果の変化ではリスナーを閉じ直さない([7 節](../agent-dataplane.md#7-データプレーン自宅側))ので、同じ意味になります。
  解決できないルールには DNAT を作りません。
  これは [7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)のルール単位で閉じる失敗であり、他のルールの公開は進めます。
  ユーザー空間モードは新しいセッションごとに解決するので、DNS の変更が効くまでの時間は、カーネルモードのほうが最長で 30 秒長い
- 解決に失敗した名前:一度解決できた名前の解決がその後に失敗した場合は、宣言の宛先の文字列が変わらない間、直前に解決できたアドレスを使い続け、次に解決できたときに置き換える(2026-09-24、所有者の決定)。
  DNS の一時的な失敗や、DNS がまだ使えない間の再起動で、動いていた DNAT を消さないためです。
  宛先の文字列は、ルール ID と組にして比べる。
  同じホスト名でもポートが変われば新しい宛先であり、一度も解決できていない宛先と同じく DNAT を作りません。
  直前のアドレスを使うときも、今の宛先の許可一覧、IPv4 だけの規則、ループバックと未指定のアドレスの拒否、ブロードキャストとマルチキャストの拒否を当てはめ直す。
  直前のアドレスは公開の記録([7b.4 節](lifecycle.md#7b4-収束と停止))にあるので、再起動の後も使える。
  解決に失敗したことと、直前の解決の結果で転送を続けていることは、ルールの `error` と理由(`name resolution of target host ... failed: ...; still forwarding to ... from the last successful resolution`)として、ハートビートと `agent doctor` に示します。
  理由に入る解決の誤りの文面からは、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)のとおり送信元とサーバのソケットの組を除く。
  同じルールに TCP の宛先の試し接続の誤りや `ip_forward` の誤り([7b.1 節](installation.md#7b1-カーネルに置くもの))があれば、その文言をこの理由の後ろに `; ` で続ける(2026-09-25)。
  直前のアドレスの宛先が応えないことを、server から見分けられるようにするためです。
  ホスト名は理由に 2 回入り、有効なホスト名は 253 バイトまで長くなる。
  hub の切り詰め([11 節](../security/admin-transport.md#11-セキュリティ))の外へ目印と試し接続の誤りが出ないように、解決の誤りの文面は、目印までと、目印の後ろに続く試し接続の誤りが切り詰めに収まる長さに短くします。
  `server doctor` は、この報告を転送の停止としては扱わない([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))。
  DNAT は残すので、この `error` は [7b.3 節](targets.md#7b3-ルールの状態と失敗の種類)の 2 つ目の種類と同じく報告に使います。
  ユーザー空間モードは新しいセッションごとに解決するので、名前を引けない間は新しいセッションを宛先へ繋げない。
  この点はモードの違いです
- IPv4 の宛先だけ:カーネルモードは IPv4 の宛先だけを扱う(2026-09-24、所有者の決定)。
  実装の制限ではなく、モードの機能の違いです。
  IPv6 のリテラルの宛先は、[7b.3 節](targets.md#7b3-ルールの状態と失敗の種類)の 1 つ目の種類の失敗としてそのルールだけを公開しません。
  ホスト名は A レコードだけで解決し、AAAA レコードだけを持つ名前も同じ種類の失敗とします。
  ユーザー空間モードの扱いは変わりません
- 複数の A レコード:ホスト名が複数の A レコードに解決されたときは、ポートごとの実効宛先で許可一覧が通すアドレスだけを残し、その中で最も小さいアドレスを使う(2026-09-24、所有者の決定)。
  どのアドレスも一覧が通さないポートだけを公開せず、すべてのポートがそうならルールを [7b.3 節](targets.md#7b3-ルールの状態と失敗の種類)の 1 つ目の種類の失敗とします。
  許可一覧が無ければ最も小さいアドレスを使います。
  一覧が通すアドレスが 1 つでもあればルールが働くという、ユーザー空間モードの意味を保つためです。
  最も小さいアドレスに決めるのは、DNS の応答の順が回るたびに DNAT の宛先が変わり、30 秒ごとにテーブルを公開し直すことを避けるためです。
  解決の結果に混ざるループバック、未指定、ブロードキャスト、マルチキャストのアドレスは使いません。
  モードの違いが 2 つ残る。
  ユーザー空間モードは、選んだアドレスに接続できなければ次のアドレスを試すが、カーネルモードは他のアドレスへ切り替えない。
  ユーザー空間モードは接続ごとに解決するので、接続が複数のアドレスに分かれうるが、カーネルモードは 1 つのアドレスへすべてのフローを向ける。
  切り替えと振り分けはカーネルの DNAT に新しい機能を足すことになるので、v1.2 では扱わない
- 宛先の許可一覧(`WGFT_AGENT_ALLOW_TARGETS`):DNAT を組むときに、ポートごとの実効宛先を判定します。
  ホスト名は解決の結果で判定します。
  一覧の外のポートには DNAT の行を作らず、範囲の他のポートは公開します。
  [7 節](../agent-dataplane.md#7-データプレーン自宅側)の IP リテラルの宛先の判定と同じ単位です。
  解決の結果が変わるたびに判定し直すので、DNS の変更で一覧の外へ向かうことはありません
- ループバックの宛先(`127.0.0.0/8`):カーネルモードでは拒み、DNAT を作りません。
  カーネルは DNAT でループバックへ向けたパケットを捨てます。
  wgft0 に `route_localnet` を立てれば届くが、DNAT を経ずにループバックを宛先とするパケットを捨てる守りの行が要り、書き換える sysctl も増えるので、この方法は採らない([13 節](../roadmap.md#制限と未実装の提案))。
  ルールの理由の文言は、カーネルモードがループバックの宛先を扱わないことを示します。
  同じホストのサービスには、ホスト自身の LAN のアドレスを宛先に書きます。
  未指定のアドレス(`0.0.0.0`)も同じく拒みます。
  ユーザー空間モードでは、`0.0.0.0` への接続はホスト自身に届くためです
- ブロードキャストとマルチキャストの宛先:[7 節](../agent-dataplane.md#7-データプレーン自宅側)と同じ判定で拒み、DNAT を作らない(2026-10-03、所有者の決定)。
  理由の文言はユーザー空間モードと同じです
- エージェントのホスト自身の LAN のアドレス:DNAT の後のパケットは forward ではなく input を通り、そのホストで待ち受けるサービスに届く。
  MASQUERADE を通らないので、サービスから見た送信元は VPS のトンネルアドレス(`10.200.0.1`)になります。
  LAN の別のホストのサービスから見た送信元は、エージェントのホストの LAN のアドレスです。
  送信元で接続を許可するサービスでは、この違いが設定に関わる。
  ホスト自身の input のファイアウォールがそのポートを塞いでいれば届かない。
  forward の MSS のクランプはこの経路に掛からない。
  UDP では、全アドレス(`0.0.0.0`)に bind したソケットから送信元のアドレスを選ばずに応答するサービスでは、応答が client に戻りません。
  入ったパケットは、宛先を wgft0 のアドレスからホストの LAN のアドレスへ DNAT されています。
  このソケットの応答では、カーネルが応答の宛先 `10.200.0.1` への経路から送信元を選ぶので、送信元は wgft0 のアドレスになります。
  この応答は conntrack が待つ応答の向きの組(送信元がホストの LAN のアドレス)と一致しないので、DNAT が戻されず、新しいフローとして wgft0 から出る。
  カーネルモードの server は、wg0 から届くこの応答を既存のフローに属さない新しいフローとして落とす。
  ユーザー空間モードの server も別の仕組みで落とすと見込むが、未確認です。
  ルールの `listen_port` を宛先のポートと同じにしても直らない。
  応答の組が既存のフローの組と衝突するので、conntrack が送信元のポートを付け替えるためです。
  ホストの LAN のアドレスで待ち受けるサービス、LAN の別のホストの宛先、TCP、ユーザー空間モードのエージェントでは起きない。
  受けたパケットの宛先のアドレス(`IP_PKTINFO`)から応答の送信元を選ぶサービスは影響を受けない見込みだが、未確認です。
  確かめたのは通常のソケットだけです。
  UDP の宛先は `server doctor` で NOT TESTED なので([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))、この制限は診断の判定に現れない。
  回避は、UDP のサービスをホストの LAN のアドレスで待ち受けさせるか、エージェントをユーザー空間モードで動かすことです。
  未確認とした点を除き、以上を試験用の実機で確かめた。
  直すことは後の版に残す([13 節](../roadmap.md#制限と未実装の提案))

<a id="7b3-ルールの状態と失敗の種類"></a>
### ルールの状態と失敗の種類

カーネルモードのルールの状態は、次の 3 つの種類の失敗で決まる(2026-09-24、所有者の決定)。

1. 公開できないルール:宛先が許可一覧の外にある場合、ホスト名を解決できない場合、ループバックの宛先である場合、ブロードキャストかマルチキャストの宛先である場合です。
   ルール単位の失敗であり、そのルールの DNAT を作らず、他のルールの公開は進めます。
   範囲のルールで一部のポートだけが許可一覧の外にある場合は、そのポートの DNAT だけを作りません。
   ルールは `error` と理由を報告します
2. TCP の宛先の接続確認の失敗:エージェントのプロセスは、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)と同じく適用のときと 30 秒ごとに TCP の宛先へ試し接続します。
   失敗したルールは `error` として報告するが、DNAT は残して転送を続けます。
   ユーザー空間モードでも接続確認の `error` は報告にだけ使い、中継を止めない([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))ので、同じ意味になります。
   試すのは、公開の記録の範囲、つまり宛先が連続するポートの並びごとに、その先頭のポートの 1 つだけである(2026-09-24、所有者の決定)。
   ユーザー空間モードはリスナーのポートごとに試すが、全幅の範囲のルールでは 30 秒ごとに約 60,000 回の接続になり、診断の副作用として大きすぎるためです。
   接続を受け付けず応答も返さない宛先では、期限の 2 秒と同時に試す数の 32 から、1 周期の 30 秒に試し終わらない。
   接続をすぐに拒む宛先でも、30 秒ごとに約 60,000 回の接続を LAN へ送る。
   期限の 2 秒と同時に試す数の 32 はユーザー空間モードと同じです
3. テーブル全体の公開の失敗:nftables のバッチが拒まれた場合などであり、backend 全体の失敗である([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))。
   エージェントは処理済み世代を進めず、新しい全体状態を `last_state` として確定せず、旧いテーブルを残したまま 30 秒ごとに試し直す。
   backend 全体の失敗では世代を進めないという [7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)の規則に合わせたものです。
   ルールごとの状態をこの失敗で `error` に書き換えない。
   ルール単位の失敗と混ぜると、運用者は宛先の問題とテーブルの問題を区別できないためです。
   server からは、`server doctor` の世代の遅れ([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor)の `agent.rules_received`)として見える。
   エージェントのホストの `agent doctor` は、公開の誤りを `dataplane.table` の所見として示すが、FAILED にはしません。
   旧いテーブルが残って転送を続けているので、このホストのエージェントが今は転送を担えない、とは言えないためである([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))。
   WireGuard インタフェースを変えられない場合も、この種類に入ります。
   試し直しは、公開できなかった全体状態を実行時の状態に控えて行います。
   控えはメモリの上だけに持ち、新しい全体状態が届けばそちらに置き換わる。
   同じ誤りが続く間はログを出さず、誤りが変わったときと公開できたときに 1 行ずつ出す

UDP のルールの `ok` は、そのルールの DNAT を公開したことを意味します。
UDP の宛先に届くかどうかは、ユーザー空間モードと同じく確かめない。
TCP のルールの `ok` は、DNAT を公開し、宛先への接続確認が成功したことを意味します。
範囲の TCP のルールでは、確かめたのは範囲ごとの先頭のポートだけであり、範囲の他のポートの宛先が待ち受けているかは確かめていません。
ユーザー空間モードの範囲の TCP のルールの `ok` は、すべてのポートの宛先への接続確認の成功を意味するので、この点はモードの違いです。
エージェントのホストの `agent doctor` では、1 つ目と 2 つ目の種類の失敗を持つルールを `dataplane.table` が FAILED として示す([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))。

理由は人が読む文言であり([7a.6 節](../architecture/wire-compatibility.md#7a6-維持する外部仕様と互換性))、全体状態とハートビートの形は変わりません。
`server doctor`([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))は、1 つ目の種類の理由を `rule.target` の理由の符号に分類します。
許可一覧の外は既存の `target_not_allowed`、解決の失敗は既存の `target_resolve_failed`、ループバックの宛先は新しい `target_loopback_unsupported` とする(2026-09-24、所有者の決定)。
ブロードキャストとマルチキャストの宛先は `target_not_unicast` とする(2026-10-03、所有者の決定)。
この符号は 2 つのモードに共通である([7 節](../agent-dataplane.md#7-データプレーン自宅側))。
1 つの符号にまとめないのは、運用者が次に取る手当てがそれぞれ違うためです。
分類は、エージェントの診断の実装と同じ段で加えます。
[7b.2 節](targets.md#7b2-宛先の扱い)の、直前の解決の結果で転送を続けているルールは、1 つ目の種類ではありません。
DNAT が残っているので、`server doctor` はこのルールを解決で止まったとは言わない。
扱いは [10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor)の `rule.target_resolve` の場合分けにある(2026-09-25)。
健全な UDP のルールの `rule.target` は、カーネルモードでも NOT TESTED の `udp_listener_only` になります。
符号の名前はリスナーを指すが、宛先を試していないという、符号が表す事実は変わりません。
