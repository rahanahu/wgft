### 登録

登録は、1 回限りの接続文字列から恒久トークンを取得する操作です。
無効化は登録を残して転送を止め、削除は恒久トークンを取り消します。


人が扱うのは接続文字列 1 本だけです。
登録は初回だけ行い、目的は恒久トークンを得ることに限る。

1. 管理者が Web UI か CLI で接続文字列を発行します。
   中身はエンドポイント、1 回限りの登録トークン、エージェント用 API の証明書の SHA-256 で、`wgft://host:port/token#sha256:...` の形をとる。
   トークンにはエージェント名を紐付ける
2. エージェントは接続文字列を環境変数 `WGFT_JOIN` か引数で受け取ります。
   名前は環境変数 `WGFT_NAME` か引数で任意に受け取ります。
   接続先の証明書がハッシュと一致しなければ中断します
3. エージェントは登録トークンを登録 API へ送る。
   名前を受け取っていれば名前も送り、名前がトークンに紐付いたものと違えば `vpsd` は拒否します。
   名前を送らなければ、トークンに紐付いた名前で登録します。
   名前はトークンに紐付いているので、自宅側で同じ名前をもう一度入力させる必要はありません
4. `vpsd` はエージェントを SQLite に作り、恒久トークン、割り当てアドレス、確定した名前を返します。
   この時点では wg ピアはまだない
5. エージェントは恒久トークンと名前を状態ファイル([9 節](../state.md#9-状態の保存と再起動))に保存し、stream に接続します。
   wg ピアの作成と設定の受け取りは stream で行う([5.2 節](connection.md#52-全体状態の配信とハートビート))

トークンの扱いは次のとおり。

- 登録トークンと恒久トークンは 128 ビット以上の乱数。
  SQLite にはハッシュだけを保存し、比較は定数時間で行います
- 登録と stream 接続の試行は送信元 IP ごとにレート制限します
- 登録トークンは 1 回限り、既定の有効期限は 1 時間
- 同じ名前に対して新しい登録トークンを発行すると、その名前に対する以前の未使用トークンはすべて無効化します。
  有効なトークンは常に最新の 1 本だけであり、複数の接続文字列が同じ名前で有効なままにはなりません
- エージェントを削除すると、その名前に対して発行済みの未使用トークンも合わせて無効化します。
  削除の前に発行され、まだ登録に使われていない古い接続文字列は、削除のあとは使えない

エージェントが削除され、恒久トークンが使えなくなった場合の復帰経路は次のとおり。
stream の認証が拒否(401)され、かつ `WGFT_JOIN` が与えられていれば、エージェントは初回登録をやり直す。
状態ファイルは初回登録が成功した時点で置き換え、失敗したら既存のファイルを残したまま止まります。
`WGFT_JOIN` は compose ファイルに残されたままになりやすく、管理者の誤操作や SQLite の復元で 401 が返ったとき、期限切れのトークンで登録に失敗して鍵まで失うことを防ぐためです。
状態ファイルには使用済みの登録トークンのハッシュを残し、`WGFT_JOIN` の値がそれと同じなら登録を試みずにエラーで止まります。
一時的な失敗(5xx、接続不能)は認証拒否と区別し、復帰経路に入らず再接続を続けます。
`WGFT_JOIN` がなければエラーを出して止まります。
削除したエージェントの名前は新しい接続文字列で再利用でき、割り当てアドレスは回収される。

サーバ証明書が変わったエージェントの復帰経路は次のとおり。
証明書が変わるのは `teardown --purge` のあとに `vpsd` を立て直したときで、エージェントの状態ファイルにあるピンと一致しなくなる。
エージェントはピンの不一致をほかの接続失敗と区別します。
`WGFT_JOIN` が与えられ、使用済みではなく、そのピンが状態ファイルのピンと違うときだけ、その接続文字列で初回登録をやり直す。
新しいピンを信頼する根拠は管理者が与えた接続文字列であり、登録トークンはそのピンに一致するサーバにしか送られないので、初回登録と同じ安全性になります。
状態ファイルの扱いは 401 の復帰経路と同じで、登録が成功した時点で置き換え、失敗したら既存のファイルを残します。
条件を満たす `WGFT_JOIN` がなければ、停止せずに再接続を続け、新しい接続文字列が要ることをログで案内します。
ピンの不一致は経路上の第三者が TLS を終端しているときにも起き、その場合は待てば元のサーバに戻るためです。

v1 は、稼働中の証明書の入れ替えを stream の中では行いません。
証明書の秘密鍵が漏れた場合の対処は、`wgft server teardown --purge` と全エージェントの再登録だけです。
再登録で配る新しい接続文字列が新しい証明書のピンを運ぶので、上記の復帰経路がそのまま使える。
入れ替えの手段を持たない判断の理由は、全体状態に「次の証明書ハッシュ」を載せる方式([13 節](../roadmap.md#制限と未実装の提案))が、ピンを追記する経路と、古いピンを捨てる時期の判断を新たに必要とし、v1 の想定する台数(自宅の数台)ではその費用に見合わないためです。
証明書の秘密鍵は、サーバ鍵とエージェントのトークンと同じくサーバのデータベースにあるので、守る範囲はデータベースの権限([9 節](../state.md#9-状態の保存と再起動))と同じになります。

接続文字列が漏れた場合、先に登録した側だけがエージェントになれ、本物は登録失敗で気付ける。
本物の起動後に漏れても、トークンは使用済みか期限切れなので使えない。
漏れた登録で得られるのは、エージェントが削除されるまで有効な恒久トークン 1 つです。
それで得られる wg0 上の 1 ピアは、ピア同士の通信も、wg0 から VPS 自身への新規接続も、wg0 から VPS の他のインタフェースへの転送も [6.1 節](../vps/kernel.md#61-カーネルモード)で遮断するため、到達できる先がありません。
第三者の接続は、[5.2 節](connection.md#52-全体状態の配信とハートビート)の IP の食い違いの警告と、[10.1 節](../interface.md#101-web-ui)の両 IP の表示で管理者に見える。

#### エージェントの無効化と有効化

エージェントの無効化は、登録を残したまま、そのエージェントのルールの転送を一時的に止める操作である(2026-09-24、所有者の決定)。
有効化は無効化を戻します。
操作は `wgft agent disable <name>` と `wgft agent enable <name>`、管理用 API の `POST /api/v1/agents/{name}/disable` と `POST /api/v1/agents/{name}/enable` である([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
この 2 つのコマンドは `--json` を持ちません。
無効かどうかは `agent ls --json` の `disabled` で読みます。

無効化が止めるものは次のとおり。

- VPS 側の転送:`vpsd` は、無効なエージェントのルールを dataplane に渡す宣言から外す。
  外れたルールは、ルール自身の無効化と同じ経路で止まります。
  DNAT と中継の待ち受けが消え、成立済みのフローも切れる([6.1 節](../vps/kernel.md#61-カーネルモード)、[6.2 節](../vps/proxy.md#62-プロキシモード)、[7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))。
  管理用 API の `rule_states` では、外れたルールの `apply_state` は `not_active` になり、`reason` はエージェントが無効であることを示します。
  ルール自身も無効なら、`reason` はルール自身の無効を示します。
  直す操作が `rule enable` と `agent enable` で違うためです
- エージェント側の転送:`vpsd` は、無効なエージェントに配る全体状態で、そのエージェントのルールをすべて `enabled:false` として載せる。
  エージェントは既存の `enabled` の扱いでリスナーとセッションを閉じます。
  無効化を知らない旧い版のエージェントも、同じ扱いで止まります。
  無効化の守りは、VPS 側の宣言からの除外と、この `enabled:false` の 2 つだけに頼る。
  全体状態には、エージェント自身の診断のために無効であることを示すフィールドを加算します。
  このフィールドは守りに使いません

無効化が変えないものは次のとおり。

- ルールの保存値:サーバのデータベースに保存したルールの `enabled` を書き換えない。
  `enabled:false` は配るときの写しだけにあります。
  有効化すると、各ルールは自分の `enabled` のとおりに戻る。
  例えばルール A と C が有効で B が無効のエージェントを無効化すると、3 本とも転送しなくなる。
  有効化すると A と C は転送を再開し、B は無効のまま残る
- 登録と接続:登録、恒久トークン、WireGuard の鍵とピア、トンネルのアドレスは残る。
  エージェントは無効の間も stream に接続でき、ハートビートとトンネルの状態も見える。
  ピアが残っていても、[6.1 節](../vps/kernel.md#61-カーネルモード)の forward は DNAT 済みでない wg0 行きのフローを落とすので、外からエージェントへ届く経路はありません
- 無効の間のルールの操作:ルールの追加、変更、削除と、ルールごとの有効と無効の切り替えは受け付けて保存します。
  保存したルールは有効化の時点から転送します

世代は、無効化と有効化のどちらでも 1 つ進めます。
配る内容、つまり `enabled` の写しと、上の無効を示すフィールドが変わるためである([3 節](../overview.md#3-用語)の世代の定義)。
状態が変わらない操作、つまり既に無効なエージェントの無効化と既に有効なエージェントの有効化は、世代を進めません。
世代はルール集合全体に 1 つなので([5.2 節](connection.md#52-全体状態の配信とハートビート))、進めた世代は接続中の全エージェントへ配る。
世代を進めるかどうかは、保存値ではなく配る写しで比べる。
無効なエージェントのルールの `enabled` だけを切り替える操作は、配る写しが `enabled:false` のまま変わらないので、世代を進めません。
無効なエージェントへのルールの追加、削除、`target` などの変更は、配る写しを変えるので世代を進めます。

データの持ち方:無効であることは、サーバのデータベースのエージェントの行の列 `disabled_at` の 1 つだけで持ちます。
NULL は有効を、値は無効にした時刻を表します。
既に無効なエージェントの無効化は、最初に無効にした時刻を書き換えない。
ルールの行には何も持ちません。
この列を加えるためにスキーマの版を 1 つ上げる。
版を上げない置き方(既存の表に値を置くなど)では、旧い版の server に戻したとき、旧い版が無効の印を読み飛ばし、無効のエージェントの転送を再開してしまう(fail-open)。
版を上げれば、旧い版の server はデータベースを新しすぎるとして起動を拒む([9 節](../state.md#9-状態の保存と再起動)、[11b 節](../security/startup.md#11b-起動の失敗の意味論))。
無効は、server の再起動、エージェントの再起動と再接続をまたいで保たれる。

操作の順序と失敗の扱い:

- 無効化の順序:サーバのデータベースへの保存を確定し、無効化だけを最後に公開に成功した全体状態へ重ねて配信を開始し、その後に dataplane へ公開します。
  実際の送信は非同期であり、dataplane の公開より先に完了する保証はありません。
  配信は公開の成否を待たず、止める向きの内容は公開より先に届いても安全側です。
  ルールのバッチ([5.4 節](batches.md#54-ルールのバッチ操作))は公開に失敗すると配らないので、無効化だけが配信の点で例外になります。
  保存は済んだがまだ公開していない他のエージェントの有効化やルール変更は、この配信に含めません
- 有効化の書き込みの時の検査:有効化は、そのエージェントの有効なルールに、ルールのバッチの upsert と同じ書き込みの時の検査(他のテーブルの DNAT との重なりと、VPS 上で bind 中のポート。
  [6.1 節](../vps/kernel.md#61-カーネルモード))を行います。
  無効の間に他のテーブルやプロセスがそのポートを取った場合に備えるためです。
  検査が拒んだ場合は何も保存せず、応答はその旨を伝える。
  有効化は、バッチの `force` に当たる上書きを持たない(2026-09-24、所有者の決定)。
  VPS 上でポートが bind されていれば、運用者がそのポートを空けてから有効化し直す。
  リクエストの本文を持たないという約束([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))とも揃う。
  上書きを後から加えることは、管理用 API と CLI の両方への加算になります
- 有効化の順序:保存を確定し、公開し、公開が成功したときだけ配る。
  公開に失敗した場合は配らず、30 秒ごとの再試行([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))が公開した時点で配る。
  公開に失敗している間、VPS とエージェントの両方が止まったままなので安全側です
- 保存は済んだが公開に失敗した場合:管理用 API は 422 を返し、「保存済みで、まだ公開していない」ことを伝える。
  有効化の検査が拒んで何も保存しなかった場合も 422 だが、応答の本文で 2 つを機械が区別できることを保証する([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
  CLI は 0 以外で終わる。
  無効化でこの場合に当たると、VPS には旧いテーブルが残り、転送を続けうる。
  接続中のエージェントが停止の全体状態を受け取れば、リスナーとセッションを閉じます。
  stream が切れている場合や配信が失敗した場合は、最後に受け取った全体状態のままリスナーを開いていることがあります。
  30 秒ごとの再試行が公開するか、エージェントが接続し直して停止の全体状態を受け取るまで、転送が続きうる
- 保存を確定できなかった場合:500 を返し、何も変えません
- 有効化の検査に要る読み取りに失敗した場合:他のテーブルの読み取りか、bind 中のポートの読み取りに失敗した場合です。
  検査の拒否ではないので 500 を返し、何も保存しません
- 公開できなかった世代の配信:公開に失敗した有効化の内容は、後の成功した全体適用で配る。
  30 秒ごとの再試行に限らず、変更の無いルールのバッチやエージェントの削除のように、別の理由で公開した経路も含む。
  `vpsd` は、配る全体状態の内容が変わったときに接続中の全エージェントへ配ることを、適用の 1 か所で行います。
  同じ世代でも内容が変われば配り直す
- 不明なエージェント名:404 を返します

疎通確認(`POST /api/v1/rules/{id}/check`。
[10.1 節](../interface.md#101-web-ui))は、無効なエージェントのルールを、無効なルールと同じく 422 で拒みます。

無効化は削除の前提ではありません。
削除は無効化を経ずに行え、無効なエージェントも削除できます。
削除でエージェントの行ごと `disabled_at` も消えるので、同じ名前で登録し直したエージェントは有効から始まる。

表示:Web UI は、エージェントの状態を「無効」と、そのエージェントのルールの状態を、頭に横棒を添えた「エージェント無効」と示し、どちらも故障の色にしません。
無効は宣言どおりの状態であり、故障ではありません。
`server doctor`、`status`、`agent doctor` での扱いは [10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor)、[10.2b 節](../status.md#102b-状態の要約wgft-status)、[10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor)に書きます。

#### エージェントの削除とルール

エージェントの削除(`wgft agent revoke <name>`、`DELETE /api/v1/agents/{name}`)は、サーバのデータベースからエージェントの行を消す。
恒久トークンは使えなくなり、ピアと割り当てアドレスは回収される([11 節](../security/admin-transport.md#11-セキュリティ))。
そのエージェントを持ち主とするルールは、削除の後も残る。
削除とルールの扱いは次のとおり(2026-09-24、所有者の決定)。

- Web UI の削除の確認:「このエージェントのルール N 本も削除する」の選択を置く。
  既定では選ばない。
  選んだ場合は、エージェントを削除した後に、既存のルールのバッチ([5.4 節](batches.md#54-ルールのバッチ操作))でそのルールを削除します。
  2 つの操作は 1 つのトランザクションではないので、ルールの削除だけが失敗すると、ルールは次項の形で残る
- CLI の削除:`agent revoke` に同じ選択を加えない。
  `agent revoke` の挙動は変えません
- 持ち主が削除されたルールの Web UI での扱い:故障ではなく、エージェントの登録を待つ状態として示します。
  削除の既定ではルールを残すので、同じ名前で登録し直せばそのまま使える。
  Web UI は、頭に横棒を添えた灰色の「エージェント未登録」と示し、エラーの数に含めません
- 持ち主が削除されたルールの CLI と管理用 API での扱い:`status` と `server doctor` は、次のメジャー版まで、これらのルールを今までどおりに扱う(2026-09-24、所有者の決定)。
  `status` は degraded に数え、`server doctor` は `rule.public_port` を FAILED `not_published` に、`agent.connection` を FAILED `agent_not_registered` にし、終了コードを 1 にします。
  機械向けの結果を変えると、それに頼る既存の自動化を壊すためである([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
  Web UI との違いは意図したものであり、互換性の保証から来る。
  人向けの表示である Web UI は [7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の保証の対象ではありません
- 持ち主が削除されたルールの一括削除:ダッシュボードのルール一覧の上に、ルールが残っている未登録のエージェントごとに帯を出す。
  帯は、そのエージェントが削除済みであることと、そのエージェントを参照するルールの本数を示し、それらをまとめて削除するボタンを持つ([10.1 節](../interface.md#101-web-ui))。
  問題の単位(削除したエージェント)と操作の単位を揃え、灰色の行の説明と解消を同じ画面で済ませるためです
