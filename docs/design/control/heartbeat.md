# ハートビートと到達性

ハートビートは処理済み世代、トンネル、ルールの状態を報告します。
server はエージェントから来た文字列を信頼の境界の外の入力として扱います。


ハートビート:

- エージェントは 30 秒ごとに送る。
  加えて、全体状態を適用するたびに(接続直後の最初の適用を含む)すぐに送る。
  WireGuard のハンドシェイクがまだ済んでいなければ、済むまで 1 秒ごとに、最長 10 秒まで送り直す。
  適用が続いたときは、まだ送っていない通知を 1 通にまとめる。
  中身は処理済み世代(最後に受け取って処理した世代。
  backend 全体の失敗を除き、部分失敗でも進めます。
  [7 節](../agent-dataplane.md#7-データプレーン自宅側)、[7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))、トンネルの状態(`ok` または `error` と理由、エンドポイントの解決結果)、ルールごとの状態(`ok` または `error` と理由)
- ルールの `error` は、リスナーの開放失敗(bind できない)か、TCP ルールで適用時の `target` への接続確認が失敗した場合を指す。
  UDP は到達確認ができないので開放失敗だけを見る。
  宛先の許可一覧([7 節](../agent-dataplane.md#7-データプレーン自宅側))が `target` を拒んだ場合も `error` になります。
  IP リテラルの `target` は適用のときに拒まれ、ホスト名の `target` は名前解決の後の接続のときに拒まれる。
  どちらの理由にも設定の名前を含めます。
  `error` のトンネル設定とルールは、エージェントが 30 秒ごとに再適用と確認を試み、状態が変わったら次のハートビートで報告します。
  ルールとトンネルの状態の理由に入る名前の解決の誤りの文面からは、問い合わせごとに変わる送信元とサーバのソケットの組(`read udp <送信元>-><サーバ>: `)を除く。
  DNS サーバは誤りの文面の `on <サーバ>` に残る。
  除かないと、同じ誤りが続く間も確認のたびに文面が変わり、状態の変化として扱われるためである([以前の検証 2026-09-24](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L266))。
  所属ルール ID が移ったリスナーの状態は、移った直後の再確認で新しいルール ID に付け替える。
  カーネルモードのエージェントはリスナーを持たないので、`error` の出どころを [7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード)で置き換える。
  `ok` と `error` がそのルールの転送について意味することは、モードで変わりません
- ハートビートのトンネルの状態と理由・解決したエンドポイント・ルールごとの状態と理由・ルール ID は、エージェントが選ぶ文字列であり、エージェントは信頼の境界の外にある([11 節](../security/admin-transport.md#11-セキュリティ))。
  `vpsd` はこれらの文字列を受け取ったまま保存せず、まず表示できない文字(`unicode.IsGraphic` が偽の文字。
  C0・C1 の制御文字、不正な UTF-8 のバイトを含む。
  日本語の文中の全角スペースのような Unicode の空白(Zs)は対象外である)を、その文字を Go の `strconv.Quote` と同じ書式(`\x1b` のような形)へ置き換え、続いてその結果を長さの上限で切り詰めてから保存します。
  この順序(置き換えてから切り詰める)は、保存する値の長さを上限の範囲に収めるためです。
  逆の順(切り詰めてから置き換える)では、上限まで残した生の文字がすべて表示できない文字だった場合、1 文字が数バイトへ膨らむ置き換えによって保存される長さが上限の数倍に達しうる(2026-09-26、レビューの指摘)。
  上限はトンネルとルールの理由が 512 バイト、ルール ID とトンネルのエンドポイントが 128 バイト、トンネルとルールの状態が 64 バイトで、いずれも実際にエージェントが送る値の長さに対して数倍の余裕を持つ値です。
  超えた分は rune の境目で切り、末尾に切ったことを示す印を添える。
  ルール ID の上限は、ルールの ID に許す長さ([5.3 節](rules.md#53-ルールのスキーマ))と同じ値です。
  ルールの検査が受ける ID は、この置き換えにも切り詰めにも掛からない。
  切り詰めと置き換えは、`agent ls`・`rule ls`・`status`・`server doctor` の人向けの出力だけでなく、保存する値そのもの、つまり管理用 API の `--json` が返す値にも及ぶ([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
  人向けの出力は、この受け口の処理とは別に、表示の直前でも同じ書式の置き換えをもう 1 段掛ける。
  エージェント自身の `agent doctor`・`rotate-key` が読む制御ソケットの応答は、この受け口を経由しないため、表示の直前の置き換えだけがこれを守る
- エージェントの側の理由の上限:エージェントは、ハートビートのトンネルとルールの理由を、送る前に次の順で変換します。
  まず不正な UTF-8 のバイトを、Go の `json.Marshal` と同じく 1 バイトずつ U+FFFD に置き換える。
  続けて受け口と同じ変換にかける。
  表示できない文字を同じ書式に置き換え、その結果を 512 バイトで切り詰める。
  切る位置は rune の境目で、末尾に切ったことを示す印を添える。
  印は 512 バイトの外に付く。
  理由はエージェントが作る文言で、宛先のホスト名や OS の誤りの文面を含むので、長さが決まらない。
  受け口の切り詰めはメッセージを読んだ後に掛かるので、接続を確立した後のメッセージの上限(1 MiB)は、エージェントが送ったままのメッセージに掛かる。
  上限を超えたメッセージは読めず、stream が切れる。
  理由を持つのは `error` のルールなので、上限が無いと、ルールが一斉に失敗した場面、つまり診断が最も要る場面で 1 通が上限を超えうる。
  最初の置き換えは、この変更より前に JSON の符号化がしていた置き換えと同じです。
  これを省いて受け口の変換を先にかけると、不正なバイトが 4 バイトの見える形(`\xfe` の形)になり、512 バイトの内に残る文言が前より短くなる。
  受け口の変換は、自分の結果にもう一度かけても、切り詰めの印より前の文言を変えません。
  したがって受け口の変換を持つ v1.2.0 以降の `vpsd` が保存する理由は、エージェントが切り詰めずに送った場合と、印より前の文言が同じです。
  違いは、エージェントが多バイト文字の途中を避けて 512 バイトより手前で切った場合に、受け口が保存する値の印の前に、エージェントの印の頭の 1 から 3 バイト(`.`)が残ることだけです。
  `server doctor` が分類に使う語([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))は印より前の文言から探すので、分類は変わりません。
  v1.2.0 より前の `vpsd` は理由を受け取ったまま保存するので、このエージェントと組むと、保存する理由は切り詰めて置き換えた後の値に変わる。
  その場合、分類に使う語が理由の 512 バイトより後ろにだけあれば、`server doctor` の理由の符号が変わりうる。
  この変化は理論上のもので、観測していません。
  エージェントのログの行には、切り詰める前の理由を書きます
- メッセージの符号化:エージェントは stream のメッセージを、HTML に埋め込むための書き換えをせずに JSON にします。
  この書き換えは Go の `json.Marshal` の既定で、`<`・`>`・`&` を `\u003c` の形の 6 バイトにします。
  どちらの形も同じ JSON の文字列を表すので、`vpsd` はどの版でも同じ値に読みます。
  書き換えを残すと、`&` を並べた理由が 1 文字あたり 6 バイトになり、1 つの理由が JSON で上限の 6 倍まで膨らむ。
  置き換えの後の理由には表示できない文字が無いので、JSON で 2 バイトになるのは `"` と `\` だけです。
  切り詰めの印は JSON で膨らまない ASCII なので、1 つの理由は、JSON で印と引用符を含めて 1039 バイトを超えません。
  ルール ID の長さは server が配る値で決まり、この上限の外にあります。
  ID が 128 バイトまでの表示できる文字なら、512 本のルールのすべてが最も膨らむ理由で `error` のハートビートも 1 MiB に収まる
- TCP ルールの `target` への接続確認は、適用のときだけでなく定期的にも行います。
  周期はハートビートと同じで、現在は 30 秒です。
  この値は今後変えることがあり、固定はしません。
  `error` のルールだけでなく `ok` のルールも確認の対象にします。
  `target` が落ちれば次の周期でそのルールが `error` になり、戻れば `error` は自動で消える。
  結果は後続のハートビートのルールごとの状態に入ります。
  確認は TCP の接続を開いてすぐに閉じる操作なので、`target` の側には、データを伴わない接続が周期ごとに 1 本届く。
  接続を記録するサーバでは、その記録が残る。
  宛先の許可一覧([7 節](../agent-dataplane.md#7-データプレーン自宅側))が拒む `target` には、この確認でも接続しません。
  UDP はこの方法で到達性を判定できないので、定期の確認を行いません
- 接続確認は中継の錠を持ちません。
  エージェントは確認の対象の待ち受けとその `target` を錠の中で写し取り、錠を放してから最大 32 件を同時に試み、結果を反映するときにもう一度錠を取ります。
  反映するのは、その待ち受けが今もあり、かつ `target` が試したときの値と同じ場合だけです。
  錠を放している競合可能期間に待ち受けが閉じた場合と `target` が変わった場合は、その結果を捨てます。
  この作りは適用のときの確認にも使います。
  適用は確認の結果を待ってから戻るので、ルールの最初の状態は適用の直後のハートビートに今までどおり載る
- 接続確認 1 件の期限は 2 秒です。
  この値は、中継が実際の通信のために `target` へ接続するときの期限とは別の値です。
  LAN の `target` の TCP のハンドシェイクは 1 ミリ秒の桁で済むので、2 秒には三桁の余裕があります。
  ハンドシェイクに 2 秒を超える `target` は、接続を受け付けていても `error` として報告される。
  `error` は報告にだけ使い、中継そのものを止めないので、誤って `error` になったルールも転送を続けます。
  期限を長く取ると、黙って捨てる `target` 1 つがその長さだけ確認を延ばす
- 到達性が変わった待ち受けは、変わったときだけログを 1 行出す。
  周期ごとには出さない。
  運用者が「LAN の `target` に届かない」と「エージェントが止まっている」を区別できるようにするためです
- `vpsd` は最終ハートビート、処理済み世代、トンネルとルールの状態、wg の最終ハンドシェイク時刻を記録し、UI に表示します
- 管理用 API は、ルールごとのこの状態(`state`・`reason`)を、報告したエージェント名・最終ハートビートの日時・そのエージェントが今も接続しているかとともに、`rule_id` をキーにした加算的なフィールドで `GET /api/v1/rules` にも載せる([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
  以前は `agent ls` の RULES 列と Web UI にしか出ておらず、`rule ls` だけを見る自動化はエージェント側の拒否理由(宛先の許可一覧による拒否、リスナーの開放失敗、接続確認の失敗)を追えなかった。
  この状態は、必ずそのルールの今の持ち主(`Rule.Agent`)のハートビートから引く。
  持ち主でない別のエージェントが、同じルール ID をたまたま古いハートビートに載せていても(ルールが持ち主を移った直後や、削除された後もそのエージェントが未接続のままだと起こりうる)、それを拾わない。
  今あるルールは、その持ち主がまだ一度もハートビートでこのルールを報告していなくても、必ずこのフィールドに 1 件の項目を持つ(2026-09-21、所有者の決定)。
  報告がまだ無いことと、この節点自体を実装していない Backend であることを JSON だけから見分けられるようにするためで、詳細は [7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)に定める
- stream が切れると `vpsd` は `Connected` を false にするが、最後に記録したトンネルとルールの状態、接続元 IP は消さずに残す(診断に使うため)。
  UI と CLI は `Connected` が false のエージェントについて、これらの値を今の状態として描いてはなりません。
  最後の報告であることが分かる形(古さを示す色、CLI の `last:` 接頭辞)で示し、いつの時点かは最終ハートビートの経過時間で表します。
  管理用 API の上記フィールドも、そのエージェントが接続中かを別途持たせることで同じ区別を伝える。
  stream の接続元 IP と wg エンドポイント IP の食い違いの比較(窃取の兆候。
  下記)も、両方が今のものでなければ意味を持たないので、`Connected` が false の間は出さない
- `vpsd` は 15 秒ごとに wg のピア状態(wgctrl の `Endpoint` と最終ハンドシェイク時刻)を読み、下の検知に使います。
  この読み取りかエージェント一覧の読み取りが失敗した回は判定を飛ばす([10.5 節](../operations/output.md#105-読み取り失敗の見せ方)のフェイルオープン)。
  原因はログに残します
