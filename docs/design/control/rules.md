### ルールのスキーマ

ルールは、VPS の公開ポートとエージェント経由の宛先を対応させる宣言です。
server は保存と配信の前に、ポート、宛先、ID、エージェントごとの本数を検査します。


```json
{
  "id": "r_01J...",
  "agent": "home",
  "group": "game",
  "note": "週末サーバ。フレンド用",
  "proto": "udp",
  "listen_port": "2456-2457",
  "target": "192.168.1.20:2456",
  "vps_mode": "kernel",
  "proxy_protocol": false,
  "source_allow": [],
  "source_deny": ["203.0.113.0/24"],
  "new_flow_rate": "100/second",
  "packet_rate": null,
  "per_source_rate": "10/second",
  "enabled": true
}
```

- `id`:ルールの ID。
  CLI と Web UI は `r_` と ULID の 28 バイトを作る。
  `rule import`、Web UI の読み込み、管理用 API のバッチでは、ID を書いて渡せる。
  ID は UTF-8 で 128 バイト以内とし、すべての文字が Go の `unicode.IsGraphic` が真の文字でなければなりません。
  長さは文字数ではなくバイトで数えます。
  日本語、記号、ASCII の空白と、全角スペースのような Unicode の空白(Zs)は受ける。
  空白を削ることも、全角と半角をそろえることもしません。
  制御文字(改行とタブを含む)、行と段落の区切り(U+2028、U+2029)、双方向の上書きやゼロ幅の文字、私用領域の文字は受けない。
  不正な UTF-8 も受けないが、管理用 API と読み込みは ID を JSON で受け取り、Go の `encoding/json` は不正な UTF-8 のバイトと対になっていないサロゲートの escape(`\ud800` など)を U+FFFD に置き換えてから渡す。
  このため、JSON の経路ではそのような ID は U+FFFD を含む ID として受ける。
  不正な UTF-8 の検査は、JSON を経ずに Go から検査を呼ぶ側のための多重の守りです。
  `.` と `..` も受けない([10.2 節](../interface.md#102-cli))。
  この長さと文字の範囲は、ハートビートの受け口([5.2 節](connection.md#52-全体状態の配信とハートビート))が置き換えも切り詰めもせずに保存する範囲と一致します。
  範囲の外の ID のルールは、エージェントの報告と ID が一致しないので、状態が永久に届かない。
  nftables のカウンタのコメント `wgft:<ID>:<種類>` も、この上限の下で 256 バイトの userdata に収まる。
  改行を含む ID がログの行を偽ることも防ぐ(2026-10-03、所有者の決定)。
  この検査の前に保存された行の扱いは [5.4 節](batches.md#54-ルールのバッチ操作)に定める
- `agent`:このルールの持ち主となるエージェントの名前。
  登録済みのエージェントでなければ `vpsd` は拒否します。
  転送の経路と、このルールを載せる全体状態の配り先の両方を決める
- `group`:任意。
  ルールを束ねる短いラベル 1 つ(例 `game`)。
  1 ルールに 1 つ。
  英数と `-_.`、32 文字以内。
  転送には影響しません。
  空のルールは UI で「その他」に入ります
- `note`:任意。
  このルールが何のためかを書く自由記述(120 文字以内)。
  転送には影響しません
- `proto`:`tcp` または `udp`
- `listen_port`:VPS で待ち受けるポート。
  `"2456-2457"` の範囲指定も許す。
  範囲のときは `target` のポートは先頭に対応し、以降は連番で写す。
  ルール間で重複できません
- `target`:自宅側の宛先。
  エージェントと同じホストなら `127.0.0.1:port` と書きます。
  `host:port` の全体を UTF-8 で 259 バイト以内とし、すべての文字が `unicode.IsGraphic` が真の文字でなければなりません。
  259 は DNS の名前の上限の 253 バイトに `:` と 5 桁のポートを足した値です。
  長さはバイトで数えるので、ポートの先頭に 0 を並べて長くした値も拒みます。
  文字の範囲はルールの ID と同じで、制御文字と不正な UTF-8 を受けない(2026-10-03、所有者の決定)。
  この検査の前に保存された行の扱いは [5.4 節](batches.md#54-ルールのバッチ操作)に定める
- `vps_mode`:`kernel`(nftables で転送)または `proxy`(`vpsd` 内の TCP 中継で転送)。
  `proxy` は TCP のみで単一ポート運用に限り、`listen_port` を範囲にはできない(カーネルモードとユーザー空間モードのどちらでも中継は [6.2 節](../vps/proxy.md#62-プロキシモード)の `proxyrelay` を使い、範囲を許すと先頭ポート以外が中継されないまま黙って失われるため)。
  ユーザー空間モード([6.3 節](../vps/userspace.md#63-ユーザー空間モード))では全ルールが `vpsd` 内の中継になるため区別に意味は無く、`proxy` は「PROXY protocol を付けられる TCP の中継」を選ぶ印としてだけ残る
- `proxy_protocol`:`vps_mode = proxy` のときだけ有効。
  PROXY protocol v2 ヘッダを付けて送る
- `source_deny`:列挙した CIDR を捨てます。
  最初に評価します
- `source_allow`:空でなければ、列挙した CIDR 以外を捨てます
- `new_flow_rate`:ルール全体の新規フロー数の上限
- `packet_rate`:ルール全体のパケット数の上限。
  UDP のデータグラムだけに効く。
  TCP のルールでも値は受け付けて保存するが、効かない([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)「TCP の packet_rate」)
- `per_source_rate`:接続元 IP ごとの新規フロー数の上限
- `enabled`:`false` でリスナーを閉じ、VPS 側のルールも外す。
  `true` に戻すと開き直す

エージェントに配るのは `id`、`proto`、`listen_port`、`target`、`enabled` だけです。
`agent` は全体状態に載せるフィールドではないが、どのエージェントの全体状態にその行を入れるかを決める。
持ち主を別のエージェントへ移す変更は、移す前のエージェントに配る内容からその行を取り除き、移した先のエージェントに配る内容にその行を加えるので、世代が上がる。
世代が上がるかどうかの判定は、行ごとの配る部分だけを並べて比べるのではなく、持ち主ごとにまとめた配る内容どうしを比べて行います。
`vps_mode`、`group`、`note` はエージェントに配らない。
`group` と `note` は管理用のメタデータで、転送にも全体状態にも影響しないため、変更しても世代は上がらずエージェントには配信されない。
プロキシモードのルールでも、エージェントは `vps_mode = kernel` のルールと同じく `listen_port` で受け、`vpsd` はそこへ接続して中継する([6.2 節](../vps/proxy.md#62-プロキシモード))。
受けるのは、ユーザー空間モードのエージェントではリスナー、カーネルモードのエージェントでは DNAT である([7 節](../agent-dataplane.md#7-データプレーン自宅側)、[7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))。
接続元制限の変更は全体状態の内容を変えないので、エージェントには配信されず、世代も上がらない。

1 つのエージェントが持てるルールは 512 本までである(2026-10-03、所有者の決定)。
数えるのは `agent` がそのエージェントの名前である行で、有効と無効を問わない。
無効なルールも `enabled:false` として全体状態に載るためです。
上限は設定項目にしません。
根拠は全体状態とハートビートの 1 通の上限([5.2 節](connection.md#52-全体状態の配信とハートビート))で、どちらもコードの定数です。
数の上限だけを設定で上げられると、エージェントが読めない全体状態を保存できるようになります。
ルールの ID、`target`、ハートビートの理由([5.2 節](connection.md#52-全体状態の配信とハートビート))の長さの上限の範囲で、符号化の後が最も長くなる値を選んでも、512 本の全体状態はエージェントが読む 4 MiB に収まり、この版のエージェントが送る 512 本のハートビートは `vpsd` が読む 1 MiB に収まる。
`target` の検査は全体の長さだけを見てホストの長さを別に制限しないので、最も長くなる `target` は、符号化で 6 バイトになる `&` をホストに詰め、1 桁のポートを付けた 259 バイトの値です。
単体試験が、`vpsd` とエージェントの実際の符号化でこの 2 つを確かめる。
この保証は、ルールの ID と `target` が上限の内側にあるルールについてのものです。
判定の仕方と、上限を超えて保存されたデータの扱いは [5.4 節](batches.md#54-ルールのバッチ操作)に定める。

`listen_port` に WireGuard、エージェント用 API、管理用 API(TCP で待ち受けている場合)のポートを指定した場合、`vpsd` は拒否します。
API のポートは待ち受けが実際に bind するポートで判定し、`host:port` のホストの部分は判定に使いません。
ポートをサービス名で書いた設定は、待ち受けと同じ規則で番号に直す([11a 節](../security/configuration.md#11a-設定の渡し方))。
`target` のポートに範囲の幅を足した実効宛先が 65535 を超える場合も拒否します。
VPS 上のプロセスが `0.0.0.0` か公開 IP で bind 中のポート(`/proc/net/tcp` と `/proc/net/udp` で確認する)も拒否します。
SSH のポートを指定して VPS から締め出される事故を防ぐためで、`--force` で上書きできます。
