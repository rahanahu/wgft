### ルールのバッチ操作

ルールのバッチ操作は、複数の変更を 1 トランザクションで保存します。
エージェントへ配る内容が変わる場合、結果の世代は最大 1 つ進みます。


管理用 API は、複数ルールの追加、変更、削除を 1 トランザクションで行うバッチ操作を持ちます。
バッチの結果で上がる世代は 1 つで、`listen_port` の重複検査はバッチ全体の適用後の状態に対して行います。
ルールの分割と統合はこのバッチで行い、CLI の `rule split` と `rule merge` はバッチの薄い層です。
分割を「縮める、足す」の 2 リクエストで行うと、中間の世代でポートが宣言から消えてセッションが切れるため、バッチが必要になります。
`vps_mode = proxy` のルールは単一ポート運用([5.3 節](rules.md#53-ルールのスキーマ))のため、分割は結果の両側が単一ポートになる場合だけ受け付ける(2 ポートの範囲を境界で割る場合に限る)。
3 ポート以上の `proxy` の範囲は、単一ポート運用にする前から保存されていた既存データとしてしか存在しえず、単発の分割では単一ポートまで割り切れないので、削除して単一ポートずつ作り直す。
統合(`rule merge <id1> <id2>`)は、エージェント、プロトコル、方式、`listen_port` の隣接、実効宛先の連続に加え、PROXY protocol、拒否/許可リスト、3 つのレート、`enabled` がすべて同じ組み合わせだけを受け付ける。
これらが違う 2 つを統合すると一方の値が黙って失われるため、条件に含めます。
`vps_mode = proxy` の組は、隣接していても統合すると必ず 2 ポート以上の範囲になるため、単一ポート運用の制約によりどちらの組み合わせでも統合できません。
統合したルールは `id1` の ID・`group`・`note`・接続元制限・レート・`enabled` を保ち、`listen_port` と実効宛先だけを `id2` の分まで広げる。
`id2` は削除します。
組み立てと検査は CLI と Web UI([10.1 節](../interface.md#101-web-ui))で共有します。

バッチ操作は、事前に読んだルール集合のハッシュ(`proto.RulesDigest`)を任意で受け取る(`ExpectedDigest`)。
指定すると、バッチはこのバッチ自身が変更しようとしている今のルール集合のハッシュと比べ、一致しなければ何も変えずに専用の誤り(`ErrBatchConflict`。
管理用 API では HTTP 409)を返します。
この照合は、ルール集合を読み取ってから変更を確定するまでを 1 トランザクションの内側で行うため、読み取りと、それを基にした変更の呼び出しとの間に他経路(別の CLI 呼び出しや別タブの Web UI)が割り込む競合を防ぐ。
ルール集合を読んでから確定までの間が開く操作(Web UI の読み込み確認・適用、CLI の `rule import`)がこれを使います。

バッチは変更後のルール集合全体を毎回検査するため、`Rule.Validate` に検査を後から追加すると、追加前から保存されていた、今回のバッチが触っていない既存ルールがその検査に落ち、以後の無関係なバッチまで失敗し得ます。
これを避けるため、`store.ApplyBatch` は `proto.ValidateUpsert` を使い、バッチの前後で ID・内容が変わらない行には `Rule.Validate` を掛け直さない。
ID の重複、予約ポート、`listen_port` の重なりの検査は変更の有無を問わず全体に対して行います。
これらは以前から全体を検査していたため、保存済みのデータは既に満たしています。
例外は、2026-10-02 の改訂で予約に加わったポート(ホスト名やサービス名で書いた API のポート)に重なる保存済みのルールで、扱いは [11a 節](../security/configuration.md#11a-設定の渡し方)に定める。
読み込みも同じ規則に従います。
CLI の `rule import` はこのバッチにそのまま送り、Web UI の読み込みの確認ページは、今のルールから変わっていない行を同じ判定(`proto.UnchangedIDs`)で除いてから `Rule.Validate` を掛ける。
確認ページだけが全体を検査すると、古い行を変えない読み込みが CLI では通るのに Web UI では適用ボタンが出ない、という経路の差が生まれるためです。
行が変わったかどうかの判定では、空の接続元リストの `nil` と空の配列を同じとみなす。

ルールの ID の長さと文字の検査([5.3 節](rules.md#53-ルールのスキーマ)、2026-10-03)の前に保存された、この検査に落ちる ID の行も、この規則で扱う。
その行は読み込みと転送を続け、無関係なバッチを妨げない。
書き出しをそのまま読み込み直す操作も通る。
同じ ID のままその行を変えるバッチは拒みます。
有効と無効の切り替え、接続元制限、レート、`group` と `note`、分割、その行の ID を残す統合がこれに当たる。
削除は通る。
その行を使い続けるには、同じ設定の行を正しい ID で作り直す。
`listen_port` の重なりはバッチの後の集合で判定するので、古い行を消して新しい ID の行を足す 1 回のバッチ(`rule import`)なら、ポートを空けずに置き換えられる。

`target` の長さと文字の検査([5.3 節](rules.md#53-ルールのスキーマ)、2026-10-03)の前に保存された、この検査に落ちる `target` の行も、この規則で扱う。
その行は読み込み、転送、配信を続け、無関係なバッチを妨げない。
書き出しをそのまま読み込み直す操作も通る。
その `target` のまま行を変えるバッチは拒みます。
有効と無効の切り替え、接続元制限、レート、`group` と `note`、分割、統合がこれに当たる。
削除と、`target` を正しい値に変える書き換え(`rule import`、管理用 API のバッチ)は通る。

エージェントあたりのルールの数の上限([5.3 節](rules.md#53-ルールのスキーマ))は、バッチの前後の集合を比べて判定します。
あるエージェントについて、バッチの後の本数が 512 を超え、かつバッチの前の本数より多いときに限り、バッチ全体を保存の前に拒みます。
上限まで足すバッチ(511 本から 512 本)は通り、超えるバッチ(512 本から 513 本)は拒みます。
持ち主を別のエージェントへ移す行は、移した先のエージェントの本数を同じ式で判定し、移す前のエージェントの本数を減らす。
判定は `proto.ValidateUpsert` が行うので、`store.ApplyBatch` を通るすべての保存に効く。
CLI の `rule add`・`split`・`merge`・`rm`・`set`・`enable`・`disable`・`deny`・`allow`・`rate`・`import`、Web UI の追加・編集・分割・統合・有効と無効の切り替え・削除・読み込み・未登録のエージェントの帯の一括削除、管理用 API のバッチです。
CLI の `--dry-run` と Web UI の読み込みの確認は、`admin.PreflightBatch` から同じ関数を呼ぶ。
拒否は管理用 API の既存の 422 で返し、文言はエージェントの名前、バッチの後の本数、上限を示します。
stream の接続と再接続、全体状態の組み立てと送信、エージェントの登録、無効化と有効化は本数を見ません。

上限の導入の前に保存された、512 本を超えるエージェントのルールは、読み込み、転送、配信を続けます。
`vpsd` は起動のたびに、上限を超えるエージェントごとに警告を 1 行ログに出す。
管理用 API と Web UI は開き、一覧を返します。
本数を増やさないバッチは通る。
削除、別のエージェントへの移し替え、統合、本数を変えない書き換え(有効と無効の切り替え、接続元制限、レート、`group`、`note`)、同じ本数での置き換えの読み込みがこれに当たる。
追加と分割、そのエージェントへの移し替えは、本数が上限まで減るまで拒みます。
512 本を超えるエージェントには、[5.3 節](rules.md#53-ルールのスキーマ)の保証は及ばない。
本数が増えると、多くのルールが長い理由で error を報告したときに、ハートビートが全体状態より先に読む側の上限を超えうる。
ハートビートが `vpsd` の読む 1 MiB を超えると、`vpsd` はその 1 通を読めずに stream を閉じる([5.2 節](connection.md#52-全体状態の配信とハートビート))。
ルールの ID と `target` の検査([5.3 節](rules.md#53-ルールのスキーマ))の前に保存された、上限より長い ID や `target` の行も、1 本あたりの大きさを [5.3 節](rules.md#53-ルールのスキーマ)の前提より大きくします。
そのような行を持つエージェントには、512 本以下でも [5.3 節](rules.md#53-ルールのスキーマ)の保証は及ばない。
