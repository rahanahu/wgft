# stream の生死と再接続

エージェントは WebSocket の ping と pong で応答の期限を確かめます。
ハートビートの送信成功だけでは接続の生存を判断しません。


接続の生死の判定:

- stream が生きているとは、その TCP が `ESTABLISHED` であることではなく、相手の応答が限られた時間の内に届くことです。
  半開きの TCP は `ESTABLISHED` のまま何分も残り、書き込みも成功し続けるので、ソケットの状態は判定の材料になりません
- ハートビートと ping は役割が違い、どちらも要る。
  ハートビートはエージェントの状態を `vpsd` に報告するもので、送信が成功したことは経路が通っていることを意味しません。
  ping と pong は、stream が双方向に通ることだけを測る
- エージェントは接続中の stream に 30 秒ごとに WebSocket の ping を送り、20 秒以内に pong が返らなければその接続を閉じて再接続します。
  経路が死んでから判定までに要する時間は最長 50 秒です
- 50 秒は、`vpsd` が何も届かない stream を閉じるまでの 90 秒に対して 40 秒の余裕を残します。
  エージェントの側が必ず先に気付いて繋ぎ直すので、運用者の画面が未接続を示す区間は、長くても繋ぎ直しに要する数秒になります。
  経路が戻っていなければ `vpsd` の側が 90 秒で閉じ、表示は従来どおり未接続になります
- 期限を間隔の 2 / 3 とするのは、同種の仕組みが採る比率に合わせるためです。
  Python の `websockets` は 20 秒の間隔に 20 秒の期限(1.0 倍)、MQTT は仕様が 1.5 倍、SSH の `ServerAliveInterval` と `ServerAliveCountMax` は 3 倍、NATS は 2 倍から 3 倍です。
  間隔の半分のような短い期限は、15 分の故障に対して数秒しか得をしないのに、混んだ回線や移動体の回線での 1 回の遅い往復を切断と見なす。
  30 秒と 20 秒は、どの実装も採っている範囲の内側にあります
- ping を判定に使う理由は、`vpsd` が待機中の stream へ定期的な送信を行わず、読みの期限を相手の送信に結び付けられないことです。
  ping は RFC 6455 が pong の返送を求める制御フレームなので、版と機能の交渉の対象にならず、旧い版の `vpsd` も応答します。
  JSON のメッセージの種類は増えません
- この判定が測るのは、経路が通っていることと、エージェント自身の読みの繰り返しが動いていることの両方です。
  `coder/websocket` は ping と pong の制御フレームを読みの繰り返しの中でしか処理せず、`Conn.Ping` 自身は接続から読まない(ライブラリの注釈が `Reader` と並行に呼ぶことを求めている)。
  エージェントが自分の都合で読みを止めれば pong は期限内に処理されない。
  転送の経路が生きているエージェントを未接続にしないためにこの性質が要るが、後から読む者が、エージェントの内部で止まった状態を回線の不調と取り違えないよう、ここに書いておく
- エージェントの ping は `vpsd` 側の 90 秒の期限を延ばさない。
  `vpsd` の期限が戻るのはデータのメッセージを読んだときだけなので、ハートビートが止まったエージェントが ping だけで接続を保ち続けることはありません
- OS の TCP の再送の打ち切りは判定に使いません。
  半開きの TCP への書き込みは送信バッファに入って成功するため、ハートビートの送信が失敗するのは OS が再送を諦めた後になります。
  打ち切りまでの時間は OS ごとに違い、実機の macOS では 1 分 31 秒、Linux の既定(`tcp_retries2` が 15)ではラボの実測で 15 分 53 秒だった。
  Linux の `tcp(7)` はこの既定を「およそ 13 分から 30 分」と書いており、実測はその範囲の内側にあります。
  OS ごとの差をそのまま wgft の回復時間にしないために、判定は wgft 自身が持ちます
- `TCP_USER_TIMEOUT` は判定に使いません。
  Linux にしかない設定であり、エージェントは Windows と macOS でも動くためです。
  TCP の keepalive も判定に使いません。
  送信したデータの応答を待っている区間では probe を送らないので、半開きの stream で頼りになる上限を与えない。
  ラボの実測でも、Go の既定の 15 秒の keepalive は上の 15 分 53 秒を縮めなかった
- Linux では、網の口を落とす操作もこの判定の対象になります。
  アドレスが残るので既存の接続への書き込みは成功し続け、stream は誤りを返さずに半開きになるためです
- 全体状態の適用の間は ping を送らず、ping を送ってから pong を待つ区間に適用が挟まった場合も判定しません。
  適用は TCP の宛先への試し接続を含み、宛先 1 つにつき最長 10 秒かかるので、pong の期限より長くなりうる。
  適用が戻らない場合の上限は、`vpsd` が何も届かない stream を閉じる 90 秒が与える
