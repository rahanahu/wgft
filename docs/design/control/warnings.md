# 接続元 IP の食い違いと往復

窃取の検知は、stream の接続元 IP と WireGuard のエンドポイント IP の食い違いと往復を観測します。
すべての窃取を検知する保証はありません。


窃取の検知:

- `vpsd` はエージェントごとに 2 つの IP を観測している。**
  stream の接続元 IP**(最終ハートビートが 45 秒以内の、生きている接続のもの)と、**wg ピアのエンドポイント IP**(最終ハンドシェイクが 3 分以内のもの)です。
  本物のエージェント 1 つだけが動いていれば、この 2 つは常に同じ IP になります
- 両方が観測でき、かつ食い違っている状態が 2 分間(15 秒間隔の監視で連続 8 回)続いたら、`ip-mismatch` の警告を 1 件残します。
  中身は両 IP と、最後に検出した日時
- 食い違いだけでは、第三者と本物の両方がフル稼働で置き換え合う場合を取りこぼす(ラボで実測)。
  WireGuard は認証済みパケットを受けるたびにエンドポイントを送信元へ更新するので、同じ鍵を 2 か所から使うとエンドポイントは keepalive のたびに両者の間を往復し、15 秒ごとの観測ではほぼ毎回ランダムになります。
  stream は supersede の後しばらく安定するため、食い違う確率は各観測で約 1/2 にとどまり、8 回連続は期待値で 1 時間ほどかかる。
  そこで第 2 の判定を置く
- **IP の往復**:`vpsd` はエージェントごと、チャネル(stream の接続元 IP、wg エンドポイント IP)ごとに、直近 10 分間に観測した IP の変化を記録します。
  stream は接続が認証されるたびに、wg は 15 秒ごとの観測で記録します。
  同じチャネルの IP が 10 分以内に A → B → A と、以前の値へ戻ったら `ip-flapping` の警告を 1 件残します。
  中身はチャネルと往復した 2 つの IP と、最後に検出した日時です。
  往復が示すのは、同じチャネルを 2 つのアドレスから交互に観測したという事実だけです。
  同じ鍵や同じ恒久トークンを 2 か所が使っている場合と、1 台のエージェントが 2 つの回線の間を移動して区間内に戻ってきた場合(ローミング)を、往復という現象自体からは見分けられない。
  回線の更新のような一方向の変化は往復になりません。
  運用者への対応は、そのエージェントがローミングすると分かっていれば警告を消し、分からなければエージェントを削除して登録し直すことです
- 2 つの判定の分担:フル稼働の置き換え合いと、本物が再接続や keepalive を続けている非対称の窃取は「往復」が数十秒から 1 分で捕まえる。
  本物が片方のチャネルで黙っている場合(stream を奪われて再接続できていない、など)は「食い違い」が 2 分で捕まえる
- どちらでも検知できない場合:本物のエージェントが完全に止まっていて第三者だけが動いているとき。
  往復も食い違いも起きず、正規の引っ越しと区別できません。
  これは IP を根拠にする限り検知できないので、受け入れる
- 自宅回線の IP 更新では警告しません。
  旧 IP の stream は TCP ごと死んでハートビートが止まり、45 秒で観測対象から外れる。
  新しい stream は新しい IP から来て、wg のエンドポイントも同じ IP に動くので一致します。
  2 分の猶予はこの入れ替わりの間の一時的な食い違いを吸収するためのものです
- どちらの警告も自動で消さない。
  置き換え合いの最中に出たり消えたりしないためです。
  同じ内容が再検出されたら、最後に検出した日時を更新するだけで、行は増やさない。
  回数は数えません。
  例外は次の 2 つの項の上限で、種類ごとに古い行だけを消す
- `ip-flapping` の警告の行の上限:サーバのデータベースは、エージェントごとに `ip-flapping` の行を 64 行まで持つ(2026-10-02、所有者の決定)。
  往復を記録するたびに、そのエージェントの `ip-flapping` の行のうち、いま記録した行と、ほかの行で最後に検出した日時が新しい 63 行を残し、それより古い行を消す。
  いま記録した行は必ず残るので、往復を検出したエージェントの警告が上限によって消えることはなく、前の項の「自動で消さない」は警告の単位では保たれる。
  上限に達しても検知は止まらず、管理者に見えるのは直近に検出した往復です。
  ただし時計が戻ると、未来の日時を持つ行は、時計がその日時に追いつくまで残る。
  その間に必ず見えるのは最新の往復 1 件だけです。
  64 行は 2 つのチャネルで共有し、8 つの回線の間を行き来するエージェントが作るすべての組(2 つのチャネルを合わせて 56 通り)を収める。
  1 つの回線を 1 つの IP と数え、デュアルスタックの回線や IPv6 の一時アドレスで増える IP は数えていません。
  上限を超えた行を持つ既存のデータベースは、そのエージェントの次の往復の記録で 64 行まで減る。
  `ip-mismatch` の行の上限は次の項にあり、この 64 行には数えません
- `ip-mismatch` の警告の行の上限:サーバのデータベースは、エージェントごとに `ip-mismatch` の行を 64 行まで持つ(2026-10-02、所有者の決定)。
  この 64 行は `ip-flapping` の 64 行とは別に数えます。
  食い違いを記録するたびに、そのエージェントの `ip-mismatch` の行のうち、いま記録した行と、ほかの行で最後に検出した日時が新しい 63 行を残し、それより古い行を消す。
  観測した組が確認済みの組で、警告を記録しなかった回は、行を消さない。
  いま記録した行が必ず残ること、上限に達しても検知が止まらないこと、時計が戻ったときに見える行は、`ip-flapping` の上限と同じです。
  上限で消すのは警告の行だけであり、確認済みの組を作ることも、変えることも、捨てることもない。
  上限で行が消えた組は確認済みにならないので、その組の食い違いを再び観測すれば、上限が無い場合と同じ判定で警告になります。
  管理者の「警告を消す」で確認済みの組になるのは、消す時点で行が残っている組だけです。
  連続回数の数え方と、確認済みの組との照合と破棄は、上限によって変わりません。
  64 行は、8 つの回線を持つエージェントで stream の接続元と wg エンドポイントが別の回線に出るすべての組(56 通り)を収める。
  1 つの回線を 1 つの IP と数える数え方は `ip-flapping` の上限と同じです。
  上限を超えた行を持つ既存のデータベースは、そのエージェントの次の食い違いの記録で 64 行まで減る
- 警告への対処はエージェントの削除しかないので、Web UI の警告のバナーでは、警告の隣に削除と「警告を消す」の操作を置く。
  エージェント一覧の行には削除を置かない([10.1 節](../interface.md#101-web-ui))。
  バナーの削除の確認は、削除が元に戻せないことと、一時的に止めるだけなら無効化を使うことを示します。
  「消す」は正当な事情(自分で 2 拠点から動かした、など)を管理者が確認したときに使います
- `ip-mismatch` の警告を消す操作は、警告の行を消すことに加えて、その警告が示す 2 つの IP の組を管理者が正当と確認した記録として、サーバのデータベースに残す(2026-09-24、所有者の決定)。
  以下、この記録を確認済みの組と呼ぶ。
  以前は行を消すだけだったので、同じ食い違いが続く限り、次の 15 秒の観測で同じ警告が戻っていました。
  確認済みの組は、エージェント、警告の種類、stream の接続元 IP、wg エンドポイント IP の 4 つで識別します。
  IP は正規化した値で比べ(IPv4 射影の IPv6 アドレスは IPv4 として扱う)、ポートと detail の文字列は識別に使いません
- 確認済みの組は、15 秒ごとの観測で次のように扱う
  - 同じ組の食い違いが続く間:警告を出し直さない
  - 2 つの IP が一致した観測:確認済みの組を捨てます
  - 別の組の食い違いの観測:確認済みの組を捨て、連続回数を数え直す。
    新しい組は、通常どおり 2 分(連続 8 回)続いてから警告になります。
    確認済みの組が無い間は、組が変わっても連続回数を数え直さない。
    IP を短い間隔で替える第三者が食い違いの警告を逃れないようにするためです
  - どちらかの IP を観測できない回:確認済みの組を捨てない。
    エージェントが切断している間と、server の再起動の直後で接続がまだ揃っていない間がこれに当たる
  - server の再起動:確認済みの組は残る
  - エージェントの削除:そのエージェントの確認済みの組を消す
  - 確認済みの組を読めない回:その回の判定を飛ばし、連続回数も進めません。
    読めないまま判定すると、管理者が確認した組の警告を出し直すためです
- 監視の回は、確認済みの組を読んでから警告を記録するまでの間に、管理者の「警告を消す」と入れ違うことがあります。
  警告の記録は、確認済みの組との照合と同じ SQL の文で行い、消したばかりの警告を戻しません
- 登録が無いエージェントの `ip-mismatch` の警告を消す操作は、行を消すだけで、確認済みの組を残さない。
  エージェントの削除の後に残った警告がこれに当たる。
  削除は確認済みの組を消すので、組を残すと、どのエージェントのものでもない組が残り続けます
- `ip-flapping` の警告を消す操作は、これまでどおり行を消すだけで、確認済みの組を残さない。
  往復を再び観測すれば警告は戻る
- 確認済みの組は、管理用 API、CLI、Web UI のどれにも一覧として出さない。
  記録したときと捨てたときに、エージェントの名前と 2 つの IP をログに 1 行ずつ出す([10.4 節](../operations/output.md#104-ログ))。
  確認済みの組を手で消す操作は持ちません。
  確認した組を窃取と疑い直したときの対処はエージェントの削除であり、削除は確認済みの組も消す
- 以前の版にあった置き換え回数の警告、二重接続の警告、交互置き換えでの受け付け停止、既知エンドポイント IP 集合と「受け入れる」操作は持ちません。
  「往復」は以前の交互検出と似ているが、stream の置き換えだけでなく wg エンドポイントも見ること、受け付けを止めず警告にとどめること、管理者に IP の登録を求めないことが違う。
  回線の IP 更新のたびに管理者の操作を要求する割に、守っている資産(wg0 上の 1 ピア。
  [5.1 節](registration.md#51-登録)のとおり到達できる先がない)に見合わないためです
