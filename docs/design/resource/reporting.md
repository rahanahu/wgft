#### 既定値と今の挙動との対応

拒否は budget、rule_cap、reserve、floor、spare の理由で数えます。
CLI と管理用 API は、Go が数える予算と拒否を報告します。


ルールごとの隔離は、次の 3 点だけから成る。
追加の設定項目は持ちません。

- ルールが 2 本以上なら、ルール 1 本の listener が運ぶフローの数は `C = ceil(T/2)` を超えません
- 受け付けている登録はそれぞれ最低分 `m = max(f, q)` を持ちます。
  `q` は予算から予備を除いた `T - f` から求めます
- 次に加わる 1 つの登録のために予備 `P = f = 4` を空けておき、残りは先着順に共有します

置き換える前のルールごとの上限は `max(floor(T/2), min(F, T))` で、`F` は設定項目にする前の固定値(UDP 4096、TCP 1024)です。
`F` は実際の資源の境界ではなく、以前の実装から引き継いだ定数なので、現在の `Pool` の式には使いません。
既定の予算はちょうど `T = 2F`(UDP 8192、TCP 2048)であり、`C` は以前の上限と同じ値(4096、1024)になります。
`T` が既定以上なら、`C` は以前の上限と同じか、`T` が奇数のときだけ 1 大きい。
ルールが 2 本以上の構成でルール 1 本の上限が下がるのは、`T` が既定より小さい場合だけです。
`T` が `F` 以下なら以前の上限 `T` が `ceil(T/2)` に、`F` と `2F` のあいだなら以前の上限 `F` が `ceil(T/2)` に下がり(UDP 6000 なら 4096 が 3000)、代わりにルール間の隔離を持ちます。

| 予算 `T` | 置き換える前のルールごとの上限 | `C` | `N = 1` の上限 | `N = 2` の `m` と 1 本の上限 | `N = 3` の `m` と 1 本の上限 |
|---|---|---|---|---|---|
| UDP 2048 | 2048 | 1024 | 2044 | 1022、1022 | 511、1022 |
| UDP 4096 | 4096 | 2048 | 4092 | 2046、2046 | 1023、2046 |
| UDP 6000 | 4096 | 3000 | 5996 | 2998、2998 | 1499、2998 |
| UDP 8192(既定) | 4096 | 4096 | 8188 | 4094、4094 | 2047、4094 |
| UDP 16384 | 8192 | 8192 | 16380 | 8190、8190 | 4095、8190 |
| TCP 1024 | 1024 | 512 | 1020 | 510、510 | 255、510 |
| TCP 2048(既定) | 1024 | 1024 | 2044 | 1022、1022 | 511、1022 |

表の「1 本の上限」は、他のルールがフローを持たないときの値です。
隔離予約 `q = floor(floor(T/2) / (N - 1))` の形(2026-09-20 から)との違いは次のとおりです。

- ルールが 1 本なら、保持できるのは `T - 4` である(`q` の形では `T`)
- ルールが 2 本以上なら、各ルールの最低分と 1 本の上限は `q` の形より高々 2 小さい。
  既定の TCP でルールが 2 本なら、1 本のルールが保持できるのは 1022 で、`C` の 1024 に届かない。
  このため、フラッドを受けたルールの拒否の理由は `rule_cap` ではなく `spare` になります
- 新しいルールは、予算が埋まっていても、加わる時点で予備の分の空きがあれば、すぐに下限の 4 本を通せる。
  `q` の形では、既存のフローが終わるまで 1 本も通せないことがあります
- 請求の合計が `T` を超えているあいだ、予約の部分の取得が `floor` で拒まれることがあります。
  `q` の形では、予約の内側のルールは `u < T` なら拒まれない。
  `budget` と `reserve` も、請求の合計が `T` を超えているあいだだけ起きる
- 統合、名前の変更、`Retiring` の UDP の listener の再開の後は、`q` の形と同じく、旧い接続をそれを運ぶ listener の今のルールで数えます。
  分割の後は、分割元の登録が続くあいだ、分割先の listener の既存のフローを最低分の判定では分割元で数える点が `q` の形と違う。
  ルール 1 本の上限と予約の部分の入口は listener が運ぶ数で見るので、分割先は `q` の形と同じく既存のフローで抑えられるが、前述の「保証しないこと」のとおり、分割元に残ったポートは `q` の形より少なくしか通せない場合があります
- ルールの追加と統合で受け付けを拒まず、既存のフローを追い出さないことは変わりません

置き換える前の固定値 `F` の挙動との違いは、ルールが 1 本なら以前のルールごとの上限ではなく `T - 4` まで保持できること、ルールが 3 本以上なら 2 本のルールがフラッドを受けても残りのルールが最低分まで新しいフローを通せること(以前は 2 本で `T` を使い切れるので、3 本目は 1 つも通せない)、`T` が既定より小さくルールが 2 本以上の構成ではルール 1 本の上限が下がり、代わりにルール間の隔離を持つこと(`T` が `F` 以下なら、以前はルール間の隔離を持たない)です。

最低分と予備には費用があります。
フローを持たないルールの最低分と予備も空きから除くので、他のルールが使っていなくても、1 本のルールが持てる数は前述の値で止まり、ルールが 1 本でも予算 `T` のすべては使えない。
フローを持たないルールの最低分を使わせるには、そのルールがフローを持ち始めたときに他のルールのフローを追い出す必要があり、[7a.5 節](../architecture/admission-resources.md#7a5-resource-guard)が禁じています。
ルールが 1 本(`N = 1`)の構成では、そのルールは予備の 4 を除いた `T - 4` まで保持できます。

#### 拒否の報告

Resource Guard の拒否は、Admission Policy の drop の種類(`deny`、`allow`、`per_source`、`src_flow`、`new_flow`、`packet`)に数えません。
SQLite に累積する drop カウンタにも、admin API の `drops` にも、[7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)の fixture にも含めません。
drop カウンタは利用者が設定した通信方針による拒否を表し、Resource Guard の拒否は wgft 自身の資源の都合による拒否なので、混ぜると利用者が方針の効き方を読み違えるためです。

UDP の受信の会計の拒否([7 節](../agent-dataplane.md#7-データプレーン自宅側))は、後述の `resource.Pool` の拒否の数にも含めません。
会計は Device ごとに拒否をメモリに数え、ログに 1 分に 1 回までの 1 行で出すだけです。

`resource.Pool` は、ルールごと、理由(`budget`、`rule_cap`、`reserve`、`floor`、`spare`)ごとの拒否の数をメモリに持ちます。
SQLite には保存しません。
資源の逼迫は今の状態を示す情報であり、再起動をまたいで累積しても意味を持たないためです。
累計の起点は、その `Pool` を作った時点です。
`vpsd` は起動時に 1 つ作って使い続けるので、起点はプロセスの起動と一致します。
エージェントは `Pool` をトンネルの中継の一部として作るので、トンネルを立て直すたびに起点が動く([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))。

ログは、今と同じく listener ごとに 1 分に 1 回までとし、文言で理由を分ける。
例は次のとおりです。

```
udp/2456: flow budget full: 8192 of 8192 in use in this process; dropping new flows
udp/2456: rule r1 holds 4096 flows and the rest of the budget is reserved for 1 other rule; dropping new flows
```

ルールが 2 本か 3 本の構成でフラッドを受けたルールは、他のルールの最低分と予備を残して `C` の手前で止まり、その拒否の理由は `spare` なので、2 行目ではなく `spare` の行になります。
`spare`、`floor`、`reserve` の文言は、空きの数、他の登録の満たされていない最低分と下限の合計と登録の数、予備の数から組み立て、空きをどのルールのために残しているかを示します。
他の登録の最低分が満たされていれば、その部分を文言に含めません。
文言が示すそのルールのフローの数は、その判定に使った数です。
`rule_cap` では listener が運ぶ数 `c_g`(改訂の前と同じ意味)を、`floor`、`spare`、`reserve` では `x_g` を示します。
英語の出力の約束(括弧の中で説明を続けない)に従います。
例は次のとおりです。

```
udp/2456: rule r1 holds 4094 flows, at or above its minimum of 2047, and the free part of the budget, 2051 of 8192, is held for the unfilled minimums of 1 other rule, 2047 flows, and 4 spare flows for a rule added later; dropping new flows
udp/2456: rule r1 holds 8188 flows and the free part of the budget, 4 of 8192, is kept spare for a rule added later; dropping new flows
udp/2456: rule r1 holds 300 flows, below its minimum of 4094, and the free part of the budget, 8 of 8192, is held for the first flows of 1 other rule and 4 spare flows for a rule added later; dropping new flows
```

admin API は、既存のフィールドを変えずに加算した次の 2 つを返します。
`GET /api/v1/rules` と `POST /api/v1/rules/batch` の応答に、プロトコルごとの `in_use` と `limit` を持つ `flow_budget` と、ルール ID から理由ごとの拒否の数への表 `resource_refusals` を加えます。
予算と拒否の数は、この項の CLI と管理用 API で報告します。
Web UI に予算と拒否の数の専用の表示は追加していません。
`rule ls --json` は応答をそのまま出力するので、同じキーが増える。
kernel モードの server が数えるのは `Relay` のルールの TCP だけであり、`Transparent` のフローは conntrack が持つので、これらのフィールドには現れない。
