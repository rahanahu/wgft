#### ホストで確かめることとラボで確かめること

ホストの単体テストは予算の計算と並行取得を検査し、ラボは実際の拒否と他ルールの転送を確かめます。


`resource.Pool` は OS に触れない純粋な Go の型なので、式の性質はホストの単体テスト(`go test ./internal/resource/...`)で確かめ、CI でも走らせる。
対象は次のとおりです。

- `N = 1` で `T - f` まで通すこと。
  `TotalMin` から `TotalMax` までのすべての `T` と、2 から数百までの `N` で、1 本のルールに受け付けを続けたときの最大が `min(C, max(m, T - P - (N - 1) × m))` になること(他のルールがフローを持たないとき)
- `TotalMin` から `TotalMax` までのすべての `T` で `C = ceil(T/2)` になり、既定以上の `T` で `C` が今のルールごとの上限を下回らないこと
- `TotalMin` から `TotalMax` までのすべての `T` で `f ≤ C` と `3f ≤ T` が成り立ち、`q ≥ f` となるすべての `N` で `N × m + P ≤ T` が成り立つこと
- 請求の合計が `T` 以下の時点で、どの登録も、他のルールのフラッドの最中も最低分まで通せること。
  空きが満たされていない下限の合計以上の時点で、下限に届かない登録が下限まで通せること。
  `N` が 1 から 2 に変わるときも含めて、加わる時点で `u + S_f + P ≤ T` なら新しい登録が下限まで通せること
- `floor` の拒否が請求の合計が `T` を超えているときだけ起きること。
  請求の合計が `T` を超えているあいだ、共有分の取得が拒まれること。
  `A` の更新と統合で既存のフローを追い出さないこと
- 分割で listener の所属ルールが変わっても、分割元の登録が続くあいだ、既存のフローが分割元で数えられ続けること。
  登録ごとに保った listener が運ぶ数が、listener のフロー数の和と毎手で一致すること。
  分割先の listener が `C` 以上を運ぶあいだ分割先が `rule_cap` で拒まれ、`m` 以上を運ぶあいだ予約の部分を使わないこと。
  条件 2 を下限の部分より後に置くとテストが落ちること。
  同じ ID の削除と再登録が別の登録になること。
  受け付けていない listener からの取得を拒み、拒否の数に入れないこと。
  手形の 2 度目の返却が何も変えないこと
- 帰属の規則:統合、名前の変更、`Retiring` の listener の再開、分割の後の分割元の削除、fail-closed、閉じ直しの後に、受け付けている listener が運ぶフローが退役した登録に残らないこと。
  受け付けていない listener が運ぶフローを移さないこと。
  生きている登録どうしで移さないこと。
  移しが `u` を変えず請求の合計を増やさないこと。
  これらを無作為の操作の列の毎手で確かめ、移しの発火を 1 つずつ外すとテストが落ちること
- `T - u ≥ S_f + P` が、いったん成り立った後、新しい登録のほかの操作で崩れないこと。
  `budget`、`reserve`、`floor` が請求の合計が `T` を超えているときだけ起きること
- 拒否の理由と数、並行した取得と返却(`-race`)
- `Pool` の受け付けと拒否が規則に一致すること、`proxyrelay` の拒否が RST になること(ループバックのソケットで確かめられます)
- `MemoryLimit` の値、設定層の検査、`nf_conntrack_max` の判定と提示の文言(`/proc` の読み取り先を差し替えるテストが今もある)

次のことはラボでだけ確かめる。

- 上限まで埋めたときの RSS:`lab/lifecycle.sh` の check 5 と 5b で、予算まで保持した状態にフラッドを重ね、server のユーザー空間モードと agent の RSS がソフト上限と余裕の和の内側にあることを確かめます。
  この確認はその負荷での退行を見つけるためのものであり、プロセスのメモリの上界を示すものではありません
- ルール間の隔離:check 5c と 5d で、2 本と 3 本のルールのうち 1 本にフラッドを掛けたまま、他のルールが最低分まで新しいフローを通せ、既存のフローが切れないことを確かめます。
- 既定より小さい予算の隔離:`WGFT_MAX_TCP_FLOWS=1024` の agent で、ルールが 2 本のとき 1 本が 510 本で止まり、他方が新しい接続を 510 本まで通せること。
  `WGFT_MAX_TCP_FLOWS=1500` でも、1 本が 748 本で止まること(check 5e)
- 拒否の理由:ユーザー空間モードの server で、`rule_cap`、`budget`、`floor`、`reserve` が実際の接続で起きること(check 5f)。
  `spare` は check 5c から 5e が確かめる
- 分割元に残ったポートと回避の手順:フラッドを受けたポートを分割で切り出すと、分割元に残ったポートが新しい接続を通せないこと、分割元のルールを 1 つのバッチで別の ID に置き換えると、そのポートが既存の接続を保ったまま最低分まで通せること(check 5g)
- 送信元ごとの上限との組み合わせ:`lab/connlimit.sh` は Admission Policy の試験なので結果は変わりません。
  agent のルールごとの上限は、最低分と予備の規則に従って検査します。
- 最低分と予備の隔離:check 5c から 5e は次の期待値で確かめます。
  1 本にフラッドを掛けたルールは、ルールが 2 本か 3 本の構成では `ceil((T - f)/2)`(`WGFT_MAX_TCP_FLOWS=1024` で 510、1500 で 748)で止まり、拒否の理由は `spare` になります。
  他のルールはそれぞれ最低分まで新しいフローを通せ、フラッドを受けたルールの既存のフローは切れない
- 最低分と予備の拒否の理由:定常の状態では `rule_cap`、`reserve`、`budget` が出なくなるので、請求の合計が `T` を超える場面を作って各理由を実経路で確かめる。
  `WGFT_MAX_TCP_FLOWS=1024` で、1 本のルールだけを 1020 本まで埋めてから 2 本目を加えると、1 本目は `rule_cap` で拒まれ、2 本目は下限の 4 本を通した後に `budget` で拒まれ、1 本目の接続を 10 本閉じると 2 本目は 6 本を通した後に `floor` で拒まれる。
  2 本のルールを 510 本ずつ埋めてから 3 本目を加えると、先の 2 本は `reserve` で、3 本目は 4 本を通した後に `budget` で拒まれる。
  どの場面でも既存の接続は切れない
- 登録の帰属の規則:3 本のルールのうち 1 本にフラッドを掛けて接続を保ち、それを別のルールへ統合した後と、2 ポートのルールの 1 ポートを分割してすぐ分割元を削除した後に、フラッドを続けたまま、無関係のルールが最低分の付近まで新しいフローを通せること。
  分割元を削除しない場合の、分割元に残ったポートの新しいフローの成否と拒否の理由も記録します
