### Resource Guard の再設計

Resource Guard は、Admission Policy が通したフローに、プロセス全体の予算、ルールの上限、登録ごとの最低分と予備を適用します。
既存のフローを公平化のために追い出すことはしません。


Resource Guard の型は `internal/resource` に置き、Admission Policy の型と分けます。
userspace の隔離は、共有プール、登録ごとの最低分、予備で判定します。
kernel の conntrack の表と set の大きさは観測して提示し、userspace の予算の式は適用しません。

#### 判定の位置と範囲

Resource Guard は、Admission Policy がフローを通した後にだけ判定する([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)の Phase 6 との境界)。
Go の側で判定する場所は、`relay.Manager` の UDP の新しいセッションと TCP の accept、`internal/vpsd/proxyrelay` の accept の 3 つです。
Admission Policy がフローを通した時点で、そのフローはレートのトークンと送信元ごとの同時フロー数の枠を使っています。
Resource Guard が拒んだときは、評価器が返した手形で送信元ごとの枠をその場で返し([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)の `AdmitFlow`)、レートのトークンは返さない。
kernel でも、conntrack の表が溢れて落ちるフローは prerouting の meter のトークンを既に使っているので、両モードで同じ扱いになります。

Resource Guard の対象は次の 4 つです。

- プロセス全体のフロー予算:`WGFT_MAX_UDP_FLOWS`/`WGFT_MAX_TCP_FLOWS`([7 節](../agent-dataplane.md#7-データプレーン自宅側))の値で、Go が保持するフローの合計を抑えます
- ルールごとの隔離:1 つのルールへのフラッドが予算を使い切り、他のルールの新しいフローまで止めることを防ぐ。
  後述の共有プール、ルール 1 本の上限、登録ごとの最低分と予備で実現します
- メモリのソフト上限:予算から導く値をランタイムに設定する(後述)。
  GC の目標であり、メモリの使用量の上限ではありません
- kernel の資源:conntrack の表と nftables の set の大きさを観測し、足りなければ提示する(後述)

#### 型の分割

Admission Policy と Resource Guard は、次の 2 つの型を持ちます。

| 型 | 置き場所 | 持つもの | 使う側 |
|---|---|---|---|
| `AdmissionLimits` | `internal/policy` | `UDPPerSource`、`TCPPerSource`、無効を表す `PerSourceOff`、既定値(256、128)、実効値を返す `UDPPerSourceCap`/`TCPPerSourceCap` | `policy.Build`、`planner.Input`、server の設定層 |
| `resource.Limits`([7a.5 節](../architecture/admission-resources.md#7a5-resource-guard)の `ResourceLimits`) | `internal/resource` | `UDPTotal`、`TCPTotal`、設定できる範囲(`TotalMin`、`TotalMax`)、既定値(8192、2048)、`MemoryLimit` | userspace backend、`proxyrelay`、agent、`cmd/wgft` のメモリの設定 |

`resource.Limits` は、[7a.5 節](../architecture/admission-resources.md#7a5-resource-guard)が `ResourceLimits` と呼んだ型です。
package の名前と型の名前が重ならないよう、型は `Limits` とします。
ゼロ値の項目を既定値で埋める規則(`WithDefaults`)は、両方の型が今の `flowcap.Limits` からそのまま引き継ぐ。
ゼロ値を「上限なし」にしないのは、設定層を通らずに組み立てた値で守りが黙って外れるためです。

`resource.Pool` は、プロセス全体の数とルールごとの数を 1 つの排他の中で判定します。
拒否のログを間引く `LogGate` は、宛先への dial の失敗にも使うため、`internal/lograte` に置きます。

`cmd/wgft` の設定層は、`WGFT_MAX_*_FLOWS` から `resource.Limits` を、`WGFT_MAX_*_FLOWS_PER_SOURCE` から `AdmissionLimits` を作る。
server は両方を、agent は `resource.Limits` だけを受け取ります。
設定項目の名前、範囲の検査、エラーの文言は変えません。

#### 共有プール、最低分と予備

`resource.Pool` は、プロトコルごとに 1 つずつ作る、プロセス全体のフロー予算です。
フローは listener(プロトコルとポート)で受け付け、2 通りに数えます。
最低分と請求の合計は、ルールの登録(後述)に数えます。
フローは受け付けたときの登録で数え、後述の[「退役した登録のフローの帰属」](admission.md#退役した登録のフローの帰属)の場合だけ別の登録へ移す。
分割で listener の所属ルールが変わっても、分割元の登録が続くあいだ、その listener の既存のフローは分割元で数え、移動先のルールでは数えない([7 節](../agent-dataplane.md#7-データプレーン自宅側)、2026-09-29 の所有者の決定)。
ルール 1 本の上限と予約の部分の入口は、登録の listener が今運んでいるフローの数も見る。
この数は改訂の前のルールのフロー数と同じ数え方である(2026-09-30 の所有者の決定)。
改訂の前は、ルールのフロー数をそのルールの listener のフロー数の合計とし、分割と統合で移った listener の既存のフローを移動先のルールで数え、予約 `q = floor(floor(T/2) / (N - 1))` で判定していた([以前の検証 2026-09-20](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L1361))。

プールの値は次の記号で定める。

- `T`:プロセス全体の予算(`resource.Limits` の `UDPTotal` または `TCPTotal`)
- `C`:ルールが 2 本以上あるときの、ルール 1 本の上限。
  どの `T` でも `ceil(T/2)` です
- `f`:登録ごとの下限。
  `T` によらない定数 4 であり、設定項目にしません
- `P`:次に加わる 1 つの登録のための予備。
  常に `f` です。
  帳簿の値として持たず、後述の条件 4 と条件 5 に常に含めます
- 登録:1 つの `Pool` の中で、あるルール ID が新しいフローを受け付けている listener を 1 つ以上持ち続けている期間であり、ルールの登録と呼ぶ。
  エージェントの登録([5.1 節](../control/registration.md#51-登録))とは別のものです。
  そのルールの受け付けている listener が 0 個から 1 個になった時点で始まり、0 個になった時点で退役します。
  退役した登録には、以後どの listener も加わらない。
  同じ ID のルールが再び受け付けを始めると、新しい登録になります。
  ルールの削除と無効化、ルール単位の fail-closed([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))、統合と名前の変更で消えるルールは登録を退役させる
- `A`:今受け付けている登録の集合。
  listener が新しいフローを受け付けるのは、bind が成功してから、`Retiring` になるか閉じるまでのあいだです。
  bind の途中の listener と bind に失敗した listener は受け付けていません。
  listener が受け付けを始めるのは bind が成功した時点であり、中継を始めるより前です。
  この 2 つの順序を逆にすると、bind が終わるまでのあいだ `N` が増えて他のルールの最低分が変わり(前者)、受け付けを始める前に受けたフローが拒まれる(後者)
- `N`:`A` の登録の数
- `q`:隔離予約。
  `N` が 2 以上なら `floor(floor((T - f)/2) / (N - 1))` で、`N` が 1 なら 0 です。
  改訂の前の式の `T` を、予備を除いた `T - f` に置き換えたものです
- `m`:登録ごとの最低分 `max(f, q)`。
  受け付けているすべての登録で同じ値であり、`N` が変わるたびに求め直す。
  最低分のうち最初の `f` を下限の部分、残りを予約の部分と呼ぶ
- `a_g`:登録 `g` に数える、まだ終わっていないフローの数。
  listener が `Retiring` になっても閉じても、そのフローが終わるまで数えます。
  後述の帰属の規則で移したフローは、移し先の登録で数えます
- `c_g`:登録 `g` の listener が運ぶ数。
  `g` に今属する受け付けている listener が運ぶ、まだ終わっていないフローの数で、そのフローをどの登録に数えるかは問わない。
  フローを運ぶ listener は、そのフローを受け付けた listener です。
  退役した登録は受け付けている listener を持たないので 0 です。
  受け付けているルールと登録は 1 対 1 なので、値は改訂の前のルールのフロー数(そのルールの受け付けている listener のフロー数の合計)と同じです
- `x_g`:`max(a_g, c_g)`。
  予約の部分の入口の判定にだけ使います
- `u`:プロセス全体のフロー数。
  退役した登録のフローも含めます
- `S`:満たされていない最低分の合計 `Σ max(0, m - a_g)`。
  和は `A` の登録 `g` を取ります
- `S_f`:満たされていない下限の合計 `Σ max(0, f - a_g)`。
  和は `A` の登録 `g` を取ります

受け付けている listener の新しいフローは、その listener が属する今の登録 `g` について、次の順に判定します。

1. `u < T` を満たさなければ `budget` で拒みます
2. `N ≥ 2` のとき、`c_g < C` を満たさなければ `rule_cap` で拒みます
3. `a_g < f`(下限の部分)なら通す
4. `x_g < m`(予約の部分)なら、`u + 1 + S_f + P ≤ T`(他の登録の満たされていない下限と予備を残しても、空きが 1 つ以上ある)のとき通し、満たさなければ `floor` で拒みます
5. それ以外は、`u + 1 + S + P ≤ T`(満たされていない最低分と予備を残しても、空きが 1 つ以上ある)のとき通す。
   満たさなければ拒み、理由は `u + 1 + S > T` なら `reserve`、そうでなければ `spare` です。
   `a_g < m` でも `x_g ≥ m` のため条件 4 に入らなかった登録では、`S` に自分の不足 `m - a_g` も入ります

空いた枠が回る順は、下限の部分、予備、予約の部分、共有分です。
下限の部分は予備の枠も使えるので、後から加わった登録は予備として空いていた枠で下限を得ます。

条件 2 は `c_g` で、条件 4 は `x_g` で判定し、下限の部分と `S`、`S_f`、請求の合計は `a_g` で数えます。
分割の直後、分割先は新しい登録として `a_g = 0` から数え始める。
`C` と予約の部分の入口を `a_g` で判定すると、分割先の listener が分割元の既存のフローを運んでいても分割先は最低分を新しく取れるので、フラッドを受けたポートを分割で切り出すたびに無関係のルールの取り分が減り、分割を重ねると無関係のルールが下限を下回り 0 本まで下がる(使い捨ての模型で確かめた)。
`c_g` で判定すると、分割先の listener が既に `C` 以上を運べば分割先を止め、`m` 以上を運べば予約の部分を使わせないので、分割先が新しく取る数は、改訂の前と同じく分割先の listener が既に運ぶフローで抑えられる。
予約の部分の入口の `x_g` は、改訂の前の「ルールのフロー数が予約以上なら予約の内側ではない」を登録の上で書いたものです。
下限の部分は `a_g` で判定するので、新しい登録の下限は listener が運ぶ数に左右されない。
ただし条件 2 が条件 3 より先なので、listener が `C` 以上を運ぶ登録は下限の分も取れません。
条件 2 を条件 3 と条件 4 より後に置くと、分割先が `a_g = 0` のまま最低分を取れて、分割先を止められない。

`rule_cap` は改訂の前と同じ定義です。
`c_g` は改訂の前のルールのフロー数と同じ数え方だからです。
`reserve` は、改訂の前と同じく、自分の取り分に届いていて、残りの空きが取り分の未使用分で埋まっていることを表します。
改訂の前の定義の `q` を `m` に、ルールのフロー数を `x_g` に置き換えたものです。
`floor` は、自分の最低分に届いていないルールの拒否で、空きを他の登録の満たされていない下限と予備に残すためのものです。
改訂の前の定義では予約の内側として `u < T` なら通していた場合に当たる。
`spare` は、`x_g` で見て自分の最低分に届いているルールの拒否で、他の登録の満たされていない最低分と予備を残すと空きが無いが、予備を除けば空きがある場合です。
他の登録の最低分が満たされていない場合を含み、ルールが 1 本のときにも起きる。
`floor` と `spare` はどちらも `reserve` と意味が違うので、`reserve` にまとめず、[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の開いた集合への値の加算とします。

受け付けていない listener(bind の前、`Retiring`、閉じた後)の新しいフローは、この判定の前に拒みます。
この拒否は予算による拒否ではないので、拒否の数に入れず、ログにも出さない。
中継は、拒んだ TCP の接続を他の拒否と同じく RST で終え([7a.5 節](../architecture/admission-resources.md#7a5-resource-guard))、UDP のデータグラムを捨てます。
この拒否は予算を持たない `Pool`(`T` が 0 以下。
試験だけで使う)でも行います。
listener を止める操作の途中、中継が停止の印を下ろしてから `Pool` の listener を止めるまでのあいだに取得したフローは、`Pool` から見ると受け付けている listener のフローなので、予算が埋まっていれば予算による拒否として数えます。
改訂の前と同じ振る舞いです。

#### 退役した登録のフローの帰属

ルールの登録が退役したとき、その登録のまだ終わっていないフローのうち、新しいフローを受け付けている listener が運ぶものは、その listener の今の登録へ移して数えます。
フローを運ぶ listener は、そのフローを受け付けた listener であり、所属ルールが変わっても変わりません。
listener が登録に加わったとき(`Retiring` の UDP の listener の再開と、受け付けている listener の所属ルールの付け替え)も、その listener が運ぶフローのうち退役した登録にあるものを、加わった登録へ移す。
移すのはこの 2 つの時点だけです。

- 受け付けていない listener(`Retiring`、閉じた後)が運ぶフローは移さず、退役した登録に残します。
  そのフローはどのルールの数にも入らず、`u` にだけ入ります。
  `Retiring` の listener が後で受け付けを再開すれば、そのときに移す
- 生きている登録どうしでは移さない。
  分割の後、分割元の登録が続くあいだは、分割先の listener が運ぶ既存のフローは分割元で数えます
- 移したフローは、移し先の登録が続くあいだは動かない。
  移し先が後で退役すれば、同じ規則でもう一度移る

この規則により、統合と名前の変更で消えたルールの既存のフロー、受け付けを再開した `Retiring` の UDP の listener の旧いセッション、分割の後に削除、無効化、fail-closed、閉じ直しをした分割元のフローのうち分割先の listener が運ぶものは、それを運ぶ listener の今のルールで数えます。
移しは `u` を変えず、移し先の不足を減らすだけなので、請求の合計を増やさない。
listener の所属は変わらないので `c_g` も変えません。
統合の後は、統合先の listener が運ぶ数が `C` を超えることがあり、そのあいだ統合先は `rule_cap` で新しいフローを拒まれる。
改訂の前の統合と同じ振る舞いです。

移しは、遷移の時点で `Pool` の操作の順に当てる。
どの時点でも受け付けている listener が運ぶフローをその listener の今の登録で数える、という規則にすると、分割でも生きている分割元から移すことになり、所属ルールの付け替えだけで請求の合計が増える。
そのため遷移の時点だけで移し、1 回の適用の中の操作の順に結果が依る場合を残す(後述の「保証しないこと」)。
適用の終わりに退役をまとめて処理する操作は持たない(2026-09-30、所有者の決定)。

#### 最低分と予備の性質

判定と帰属の規則は、1 つの `Pool` の中で次の性質を持ちます。

- `u ≤ T` は常に成り立つ
- `N ≥ 2` のあいだ、`c_g` が `C` 以上の登録は新しいフローを通せません。
  フローの受け付けで `c_g` が `C` を超えることはありません。
  `a_g` は `C` を超えることがあります
- `m ≤ floor((T - f)/2) < C` なので、`rule_cap` が最低分に届いていない登録を拒むのは、その登録の listener が運ぶフローのうち `C - a_g` 本以上が他の受け付けている登録に数えるフローのときだけです。
  他の登録のフローが listener に乗るのは、分割元が続く分割と、元の登録が続く付け替えで listener を受け取ったときだけです。
  新しいルールは最初は何も運ばないので `rule_cap` に拒まれない
- 予約の部分の入口が `a_g < m` の登録を閉じるのは、その登録の listener が、他の受け付けている登録に数えるフローを `m - a_g` 本以上運ぶときだけです
- 請求の合計 `u + S + P` が `T` を超える状態を許す。
  請求の合計を `T` より大きくするのは設定の変更だけで、フローの受け付けと終わりと帰属の移しはそれを増やさない。
  新しい登録のほかに、`N` が減って `m` が上がる退役と、`N` が 1 から 2 に増えて `m` が `f` から予算の約半分に上がる登録がこれに当たる
- 請求の合計が `T` 以下の時点では、`A` のどの登録も、その後に設定の変更が無く `c_g` が `C` 未満である限り、`a_g` が下限に届くまでと、その後 `x_g` が最低分 `m` に届くまで、新しいフローを通せる。
  `m` は改訂の前の `q` より高々 `f/2` 小さい。
  `q` が `f` 以上である限り `N × m + P ≤ T` が成り立つので、ルールの数が変わらないあいだに通したフローだけなら、請求の合計は `T` 以下に保たれる
- 請求の合計が `T` 以下なら `u ≤ T - P` なので、`budget`、`reserve`、`floor` は起きない。
  この 3 つは請求の合計が `T` を超えているあいだだけ起きる
- 空きが満たされていない下限と予備の合計以上(`T - u ≥ S_f + P`)という式は、フローの受け付けと終わり、退役、`N` の変化、帰属の移しでは崩れず、崩すのは新しい登録だけです。
  この式が成り立つあいだ、下限に届かないどの登録も、`c_g` が `C` 未満なら、他の登録の取得の順によらず下限まで新しいフローを通せる。
  加わる時点で `u + S_f + P ≤ T` なら、新しい登録も下限まで通せる。
  下限の保証はこの式が成り立つあいだに限る。
  予備は 1 つ分なので、続けて加わった 2 つ目以降の登録は予備が戻るまで保証されず、そのあいだは既存の登録で下限に届いていないものも含めて先着順になります
- 下限に届かない登録は、`c_g` が `C` 未満なら、`u = T` のときだけ拒まれる
- 請求の合計が `T` を超えているあいだは条件 5 を満たさないので、終わったフローの空きは、下限、予備の回復、予約の部分の順に回り、共有分には回らない。
  予約の部分どうしは先着順です。
  既存のフローは追い出さないので、この状態が続く時間に上限はありません
- ルールが 2 本以上あるとき、他のルールがフローを持たなければ、1 本のルールが保持できるのは `min(C, max(m, T - P - (N - 1) × m))` です。
  ルールが 2 本なら `ceil((T - f)/2)` で、`C` を下回る。
  このため、1 本のルールへのフラッドで `rule_cap` が拒否の理由になるのは、`T - P - (N - 1) × m ≥ C` となる構成です。
  `m` の切り捨てのため、この構成はルールの数に対して単調ではない(既定の TCP では 4 本から 7 本が最初の範囲である)。
  ほかに、ルールが加わって `m` が下がった直後と、統合や分割や付け替えで listener が `C` 以上を運ぶ登録でも `rule_cap` になります。
  ルールが 1 本なら、そのルールは `T - P` まで保持できます
- `q` が `f` を下回るほどルールが多い構成では `m = f` になります。
  `(N + 1) × f ≥ T` のときは条件 5 を満たせないので、どのルールも下限までしか保持できません。
  `f = 4` では、既定の TCP で受け付けているルールが 511 本以上のときに当たる。
  `(N + 1) × f > T` では予備の保証が成り立ちません。
  `(N + 1) × f ≤ T` でも、下限の保証は前述の `T - u ≥ S_f + P` が成り立つあいだに限る
- 受け付けている listener が運ぶフローが、退役した登録に残ることはありません

使い捨ての模型では、フラッドを受けたポートを分割で切り出すことを重ねる場面(フラッドが 1 ポートに集中する場合と、範囲に一様な場合)、分割と統合を数回往復する場面、統合、名前の変更、UDP の再開、分割の後の分割元の削除の場面で、無関係のルールが新しく通せる数は、改訂の前の形より少ない場合でも、その差は数本以内だった。
この値は模型の場面の値であり、証明ではありません。
分割元を削除した後に閉じた listener の旧い接続が残るあいだは除く。

この形は次のことを保証しません。

- 受け付けていない listener の旧い接続:閉じた listener と、再開しない `Retiring` の listener が運ぶ旧い接続は、切れるか終わるまで退役した登録に残り、どのルールの数にも入らずに `u` を占める。
  そのあいだに同じ ID のルールを登録し直したり、ルールの数が変わったりすると、無関係のルールが最低分を下回ることがあり、最悪で下限まで下がる。
  閉じた listener の接続はその場で切るので、影響は切り終えるまでのあいだと考えるが、未確認です。
  fail-closed の `Retiring` の listener の接続は、ルールが失敗しているあいだ残る
- 分割元が続くあいだの分割元と分割先:分割元の登録が続くあいだ、分割先の listener が運ぶ既存のフローは分割元の `a_g` に数えます。
  このため、分割元の `a_g` が `m` 以上なら、分割元に残ったポートの新しいフローは下限の部分も予約の部分も使えず、共有分だけになり、請求の合計が `T` に近いと 1 本も通せません。
  改訂の前の形では、分割元のフロー数を分割元に残った listener のフローで数えるので、予約の内側として通せる。
  判定の式から計算し、使い捨ての模型でも同じ値を確かめた例では、`T = 2048` で、ルール B の 1 ポートへのフラッドで B が 1022 本を持ち、そのポートを分割して D とすると、B に残ったポートは 1 本も通せない(改訂の前の形では 512 本まで通せる)。
  この状態は、分割先の listener が運ぶ既存のフローが終わるか、分割元の登録が退役して帰属の規則でそのフローが分割先へ移るまで続く。
  分割元に残ったポートの新しいフローをすぐに通すには、分割の後に分割元のルールを別の ID に置き換える。
  ルールの名前を変える専用のコマンドは無いので、分割元のルールの削除と、同じポート、同じ宛先で新しい ID を持つルールの追加を、1 つのバッチで適用します。
  `rule import` なら、`rule ls --json` の `rules` を書き出し、分割元の行の `id` を消して読み込む。
  分割元の登録が退役し、分割先の listener が運ぶ既存のフローは帰属の規則で分割先へ移り、新しい ID の登録は最低分を得ます。
  ポートと宛先が変わらないので listener は閉じずに所属ルールを付け替えるだけであり、分割元に残ったポートの既存の接続は切れない。
  この手順は、ユーザー空間モードの server とエージェントで、`rule import` の経路についてラボで確かめた(`lab/lifecycle.sh` の check 5g)。
  フラッドを受けたポートを分割で切り出し、分割元に別の利用者のポートが残る場合に当たる。
  無関係のルールの最低分はこの影響を受けない。
  分割先は新しい登録として最低分を全部請求し、分割先の listener が既存のフローを `m` 以上運べば予約の部分を使えず、その不足は請求に残って他のルールの最低分を超える取得を止めます
- 1 回の適用の中の順:1 回の適用(`vpsd` の 1 回の `Commit` か、エージェントの 1 回の `Apply`)の中で、分割元の最後の listener の閉鎖と、分割先の listener の別のルールへの付け替えが重なると、既存のフローをどちらのルールで数えるかは操作の順に依ります。
  悪い順では、無関係のルールが新しく通せる数が下がる。
  使い捨ての模型では、`T = 2048` で良い順の 511 に対して悪い順で 341 だった(改訂の前は 512)。
  `vpsd` の順は listener の表の順で決まらず、1 つのバッチにこの 2 つの変更を入れる経路は `rule import` で作れる。
  `proxyrelay` はいつも閉鎖を付け替えより先に行います。
  エージェントは操作をポートの順に行うので、同じルールの listener の開放が閉鎖より先になると、登録が退役せずフローを移さないことがあります。
  この場合の影響は関わるルールの中にとどまる
- 移し先と分割元の上限:帰属の移しの後、移し先の `a_g` と `c_g` は `C` を超えることがあり、最大で `T` までです。
  `c_g` が `C` を下回るまで、移し先は新しいフローを `rule_cap` で拒まれる。
  分割元は、分割先の listener が運ぶ既存のフローを `a_g` に数え続け、自分の listener が運ぶ数が `C` 未満なら共有分を取れるので、`a_g` が `C` を超えることがあります。
  この場合、後でルールが減って `m` が上がると、無関係のルールが通せる数が、`C` を登録の数で判定する形より数本から数十本少なくなりうると見積もるが、模型では再現していません。
  改訂の前の形も同じ振る舞いです
- listener が運ぶ数による行き詰まり:listener が `C` 以上を運ぶ登録は、自分に数えるフローが 1 本も無くても `rule_cap` で拒まれる。
  自分の他のポートの新しいフローも同じです。
  長く続く接続が残るあいだは拒まれ続けます。
  改訂の前と同じ振る舞いです
- フラッドを受けた分割先の新しいフロー:予約の部分の入口が閉じた分割先は、自分の不足を共有分の条件でしか取れません。
  共有分の条件は取る登録自身の不足を差し引かず、請求の合計が `T` 未満のときだけ通すので、分割の時点で請求の合計が `T` 以上なら、分割先は下限の分しか通せません。
  請求の合計に 1 つでも余りがあれば、分割先の取得は請求の合計を変えないので、分割先は不足を最低分まで取れます。
  このため、フラッドを受けた分割先が新しく通せる数は、分割の時点の請求の合計によって、改訂の前より少ないことも多いこともあります。
  使い捨ての模型で、分割の時点の請求の合計だけを変えてこの違いを確かめた。
  無関係のルールの最低分には影響しません
- 分割と統合の往復:分割のたびに分割先は新しい登録になり、下限の部分は `u < T` だけで通るので、フラッドを受けた分割先は下限の分を取ります。
  統合で分割先が退役すると、その分は帰属の規則で統合先へ移り、請求の合計が `T` を超える量が 1 往復ごとに `f` 増える。
  使い捨ての模型では、往復を百回を超えて重ねると統合の後の無関係のルールが最低分を下回り始め、その後は下がりが止まった。
  止まるのは、往復ごとに分割先の listener が運ぶ数が増えて `C` に届くと、条件 2 が下限の部分より先に分割先を拒むためであることを、同じ模型で確かめた
- 続けて加わる登録:フラッドを受ける新しいルールを 1 本ずつ加えていくと、無関係のルールは最低分を下回り、下限の分も失うことがあります。
  改訂の前の形にも同じ型の後退があります
- 請求の超過が続く時間:請求の合計が `T` を超える状態は既存のフローが終わるまで続く。
  長く続く接続で予算が埋まっていると、新しいルールは誰かが切断するまで下限も得られないことがあります
- ルールが 2 本の構成の共有分:`T - f` が偶数なら `2 × m + P = T` になるので、ルールが 2 本の構成では共有分が無く、どちらのルールも、他方が空いていても `m` を超えて保持できません
- 最低分は登録ごとで、listener ごとではありません。
  範囲のルールでは、最初に受け付けたポートが最低分を使います
- フローの数のほかの資源(byte、バッファ、RSS、TIME_WAIT、netstack の endpoint)は、この式では抑えない

閉じ直し([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「実効宛先が違う:閉じてから開く」)は、`Pool` の上では別の操作として扱わない。
閉じ直しのあいだもそのルールが別の listener で受け付けていれば登録は続き、そうでなければ旧い登録が退役して新しい登録が始まる。
エージェントの 1 ポートのルールの閉じ直しは後者、範囲のルールの閉じ直しと、listener を開き直さない server の中継と `proxyrelay` の宛先の変更は前者に当たる。
閉じた listener が運ぶフローは移さない。

`A`、登録、`m`、`S`、`S_f` と帰属の移しは、トランザクションの `Commit`([7a.2 節](../architecture/model.md#7a2-層と責務)の戻れない地点の後)で更新します。
更新はメモリの上の値の置き換えだけで失敗しないので、frontend の `Commit` の「失敗してはならない」という約束に合う。
既に数えているフローを切ることも追い出すこともしません。
`Commit` を持たないエージェントの `Apply` の経路([7 節](../agent-dataplane.md#7-データプレーン自宅側))では、listener ごとの bind の成功が同じ地点に当たる。

1 回の判定は、`a_g`、`u`、`S`、`S_f` を足し引きで保った値から、1 つの排他の中で一定の手間で行います。
`m` は `N` が変わるときだけ変わるので、`A` の登録の数に比例する `S` の作り直しは、登録の始まりと退役のときだけ行います。
帰属の移しの手間は、退役した登録の、listener と登録の組の数に比例します。
どれも `Commit` から呼ばれる操作であり、フローの取得と返却の経路には入りません。
`S_f` は `N` によらないので作り直さない。
フローの取得は、そのフローを受け付けた listener と登録の組を指す手形を返し、中継はフローの終わりにその手形を 1 度だけ返します。
2 度目の返却は何も変えません。
`Pool` の排他は末端の錠であり、`Pool` はその排他を持ったまま中継の関数を呼びません。

保証は 1 つの `Pool` の中に限る。
エージェントはトンネルを立て直すたびに `Pool` を作り直すので([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))、旧い `Pool` のフローが終わるまでのあいだ、プロセス全体の保持数は `T` を超えうる。
旧い世代の数に構造の上限は無いが、立て直しを起こすのは `vpsd` の全体状態、管理者の操作、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の作り直しの判定だけであり、旧い世代は、それを使っていた処理がすべて戻ると消える。
プロセス全体のメモリの上界での扱いは [7 節](../agent-dataplane.md#7-データプレーン自宅側)の「プロセス全体のメモリの上界」の段落に書く(2026-09-30、所有者の決定)。
