# 性能の模型 (N4)

この文書は、推奨の構成 S の性能の模型を、測った byte あたりの費用から組み立て、予想する詰まり、CPU の数ごとの動かし方、要件の折り合い、実行の仕組みの選択を定めます。
未採用の提案です([提案の索引](README.md))。
値の区別は[値の区別](README.md#値の区別)に従います。
10 Gbit/s に届くことは前提にせず、何が上限を決め、測定でどう見分けるかを示します。

## 模型に使う値

### 測定の条件

- 分けたラボ:agent を専用の N vCPU の VM に置き、相手は 8 vCPU の VM です。
  `lab/lab paired --split --placement apart` (暗号の worker のある build は `apart-mt`)、4 round × 2 回の中央値です([agent を専用の VM に置く](../../../../lab/README.md#agent-を専用の-vm-に置く---split))
- Inline:バッチの実装の後の main の Rust の agent で、データプレーンは 1 つのスレッドです
- A+:#808 から #810 を同じ Inline に載せた build で、4 CPU 以上で暗号の worker を 2 本持ちます
- 1 つの VM のラボ:5 つの network namespace を 1 つの 4 vCPU の VM に置いた、バッチの前の基準です([基準の値](../../v2/agent-throughput.md#基準の値))

## 役ごとの費用の模型

Inline のスレッドが詰まった時の byte あたりの時間を C とします。
C は、速さの逆数とスレッドの忙しさの積です。
受ける向きは約 1.0 ns/byte、送る向きは約 1.5 ns/byte です (推定、上の測定から導いた値)。

S が詰まった時の仕事を、役ごとの byte あたりの費用に分けます。

| 役 | 受ける向き | 送る向き | 区別 |
|---|---|---|---|
| shard 0 の読みと振り分け | 読み約 0.06、replay の確定と振り分け約 0.04 ns/byte | 無し | 推定 |
| 暗号 (手伝いに分けられる分) | 約 0.34 ns/byte | 約 0.29 ns/byte | 推定 (内訳の割合 × C) |
| 送り出しの system call とラボだけの受け手の処理 | 無し | 約 0.6 ns/byte。ラボだけの分を含みます | 推定 |
| 昇格した接続の持ち主 (核、0 埋め、中継、LAN の側の system call) | 約 0.55 ns/byte | 約 0.5 ns/byte | 推定 |
| スレッドを移る分 (cache line の移動、記述子) | 約 0.05 から 0.15 ns/byte | 約 0.05 から 0.1 ns/byte | 推定 |

速さの上限は、次の 4 つの最小です。

- 1 つの flow の上限:持ち主の 1 つのスレッドの費用の逆数です。
  受ける 1 stream で約 0.6 から 0.7 ns/byte なので 11 から 13 Gbit/s、送る 1 stream で約 0.55 から 0.6 ns/byte なので 13 から 15 Gbit/s です(推定)
- shard 0 の上限:読みと振り分けだけなら約 0.1 ns/byte で、上限になりません(推定)。
  shard 0 が昇格していない flow と UDP を持つ時は、その分が加わります
- CPU の総量:agent の VM の vCPU の数を、VM 全体の byte あたりの CPU で割った値です。
  Inline の VM 全体の値 (1.2 から 1.6 s/GB) にスレッドを移る分を加えると、4 vCPU で 18 から 25 Gbit/s です(推定)
- 外の上限:カーネルの外側の流れの処理、相手の VM、経路です([10 Gbit/s を決める上限](#10-gbits-を決める上限))

送る向きの推定は、ラボだけの受け手の処理を送り手の system call に数えるので、本物のホストでの値は未確認です。
A+ は暗号だけを worker に移して、送る 1 stream を 1.41 から 1.49 倍にしました (測定)。
S は、暗号に加えて送り出しの system call も手伝いの順序つきの送りに移せるので、A+ より上の値を見込みます(推定)。

## 予想する詰まり

- 受ける 1 stream:持ち主の核と中継です。
  4 vCPU 以上のラボでは、相手の VM が先に詰まる実行がありました (測定)
- 送る 1 stream:持ち主の LAN の側の読みと核です。
  送り出しを手伝いに移せない場合は、外側のソケットへの送り出しです
- 多くの stream:CPU の総量と、カーネルの外側の 1 つの流れの処理です
- 接続の入れ替わりが多い負荷:握手と終わりを持つ shard 0 です
- UDP の多い負荷:UDP を持つ shard 0 です

## CPU の数ごとの動かし方

N は、起動の時の利用できる CPU の数 (affinity と cgroup の割り当てを反映した値) から決まり、設定を持ちません。
対応の表は試作の測定で決め、表そのものは設計判断として固定します。

| 利用できる CPU | N の案 | 動き方 | 確かめること |
|---|---|---|---|
| 1 | 1 | Inline そのもの | Inline との同等 |
| 2 | 2 | 詰まるまで shard 0 だけが動き、詰まると重い flow を shard 1 に昇格させます | カーネルの仕事と CPU を取り合っても、N = 1 より悪くないこと。悪ければ N = 1 にします |
| 4 | 4 | 同上。暗号の手伝いが 3 本まで | N = 3 と比べ、カーネルの仕事に CPU を残す方が良いかを確かめます |
| 8 | 8 | 同上 | 8 を上限にするか。8 を超える CPU は試していません (未確認) |

S では、詰まっていない shard は眠っているので、N を CPU の数にしても中くらいの負荷の費用は増えません(推定)。
CPU の数より N が多いと、詰まった時に shard とカーネルが CPU を取り合うので、N は CPU の数を超えません(設計判断)。

## 要件の折り合い

### TCP の 1 stream

1 本の接続の状態機械は 1 つのスレッドでしか進められないので、1 stream の並列は暗号と送り出しと checksum の確かめを持ち主の外に出す形で得ます。
持ち主の残りの仕事 (核、0 埋め、中継、LAN の側の system call) が 1 stream の上限です。
0 埋めの 11.2% (測定) は持ち主に残るので、0 埋めを減らす変更は S と別に、1 stream の上限を引き上げます。

### TCP の多くの stream

重い flow を shard に昇格させるので、多くの stream は shard の数まで分かれます。
全 shard が詰まると、手伝いの空きが無いので、申し出の塊は申し出た shard が自分で行います。
このため全負荷の多くの stream では、スレッドを移るのは shard 0 から持ち主への 1 回だけになります(設計判断の帰結)。
この時の受信の復号は shard 0 に残りますが、shard 0 の読み、振り分け、復号の和は約 0.44 ns/byte で、約 18 Gbit/s まで上限になりません(推定)。

### UDP の低い遅れ

UDP は shard 0 の中で、Inline と同じ順と予算で処理します。
詰まっていない時は Inline と同じです。
詰まった時は、昇格で TCP の仕事が shard 0 から減るので、UDP の待ちは Inline より短くなると見込みます(推定)。
大きなバッチの UDP の datagram は、復号の塊 1 つ分 (8 から 16 µs) と前の塊の順を待ちます。
Inline はバッチ全体の復号 (64 packet で約 43 µs) を待つので、この待ちは Inline より短くなります(推定)。

### byte あたりの CPU

詰まっていない時は Inline と同じ経路なので、byte あたりの CPU は同じです。
詰まった時は、スレッドを移る分 (0.05 から 0.15 ns/byte、推定) と起床の費用が加わります。
受け入れの線は[受け入れの条件](verification.md#受け入れの条件)にあります。

### 公平

[flow の公平とワーカーの公平](#flow-の公平とワーカーの公平)にあります。

## 実行の仕組みの選択

### 輪の種類

| 輪 | 形 | 理由 |
|---|---|---|
| shard 0 から k の受け口 | SPSC | 書き手は shard 0 だけです |
| k から shard 0 の制御の知らせと返却 | k ごとの SPSC | shard 0 は k の数の輪を起床ごとに見ます。見る費用は index の load で、変わっていない line は cache に残ります |
| 申し出の板 | 固定の配列と塊ごとの状態の語 | 引き取りは CAS 1 回です。MPMC の queue は要りません |
| 送りの板 | 持ち主ごとの固定の配列 | 同上 |

MPSC の 1 つの輪は、書き手の CAS が末尾の 1 つの line に集まり、満ちた時に誰が待つかの規則が要るので採りません(設計判断)。
SPSC の輪の index は書き手と読み手で別の cache line に置き、書き手はバッチごとに 1 回だけ公開し、読み手は相手の index を手元に写して必要な時だけ読み直します。

### ワーカーの手元の空きの list

- 送信の枠:各 shard が手元の小分けの置き場を持ち、足りない時だけ全体から 1 組 (32 枠を仮の値にします) を取ります
- 平文の block:取るのは shard 0 だけで、持ち主が返却の輪で返すので、全体の錠は要りません
- chunk:今と同じく shard ごとの置き場で、chunk は shard をまたがずに取って返します

### 所有の移動と写しと cache line の費用

- 記述子 (32 byte 程度) だけを動かし、packet の中身は平文の block に置いたままにします
- 持ち主の核は今と同じく、受信のデータを自分の輪に写します。
  この写しが、別の core の cache にある平文を持ち主の手元に移す役も兼ねるので、写しを増やしません
- 中身を別の置き場に写して渡す形は、写しの費用 (0.093 から 0.097 ns/byte、測定) が cache の移動とほぼ同じで利点が無いので採りません(推定)
- 各 shard の核は自分の配列だけを書くので、shard の間で同じ cache line を書くのは、輪の index、申し出の板と送りの板の状態の語、平文の block の参照の数に限られます。
  これらは書き手ごとに cache line の境で分けます
- 昇格では、接続の構造体 (約 1.4 KiB) を 1 回写します。
  昇格は窓ごとに 1 本までなので、写しの費用は無視できる大きさです(推定)

### 動的なバッチの大きさ

- 読みの大きさ:今と同じく、前のバッチの時間から遅れの予算 (25 µs) に収まる枠の数を求め、空いている暗号文の枠の数で抑えます
- 申し出の判定:読みが要求した枠を満たしたか、遅れの予算の後にもデータが残った時で、かつバッチの byte が塊 2 つ分以上の時だけ申し出ます。
  1 つずつ読む OS (Windows と macOS) のバッチは塊 2 つ分に届かないので、申し出は起きません
  バッチを満たすために待つことはしません
- 塊の大きさ:塊の暗号の時間が 8 から 16 µs になる byte の数 (1,408 byte の packet で 12 から 24 個) を初めの値にします(推定)。
  申し出と引き取りと終わりの知らせの費用が塊の暗号の時間の 1 割を下回る大きさを、試作で測って決めます
- 送りの申し出:持ち主の核が 1 回の送りの相でバッチの枠を満たし、なお送るものが残った時だけ申し出ます

### 手伝いの規則

- 見る時機:各 shard は、起床ごとの loop の始めに申し出の板を見ます
- 空いている時:自分の受け口の queue と送りの仕事が空なら、申し出を引き取ります
- 積み残しが多い時:申し出た shard の引き取られていない塊が 2 バッチ分を超えたら、自分の仕事より先に 1 塊を引き取ります。
  shard 0 が復号を抱えて詰まり、昇格した接続への振り分けが遅れることを防ぐためです
- 選ぶ順:積み残しの最も多い shard の申し出から引き取ります
- 線の値:2 バッチ分は初めの値で、試作で決めます(設計判断)

### 起こし方

- 印と知らせ:各 shard は眠る前に眠りの印を立て、fence の後に queue を見直してから眠ります。
  書き手は公開と fence の後に印を見て、眠っている時だけ起こします
- 起こす相手:昇格した接続の packet と昇格の知らせは、持ち主を必ず起こします。
  申し出の塊は、積み残しが 2 回続いた時だけ眠っている手伝いを 1 本起こします。
  起床の費用 (7 から 80 µs、測定) より短い仕事のために起こさないためです
- 仕組み:Linux では eventfd を shard の poller に入れ、ほかの OS では実行環境の waker を使います

### busy polling と event 駆動

既定は event 駆動です。
待ちながら回る (spin) のは、shard 0 が、ほかの shard が引き取って処理中の先頭の塊を待つ時だけで、長さは塊の暗号の時間の上限までです。
眠っている shard を負荷の予測で回し続ける形は、中くらいの負荷の byte あたりの CPU と VM の出入りを増やすので採りません(設計判断)。

### CPU の固定、NUMA、SMT

- 固定:製品は shard を CPU に固定しません。
  コンテナと cgroup で利用できる CPU が変わり、固定の設定を持たない規則のためです
- 測定:ラボは置き方を固定して流し、固定しない実行も加えて製品の挙動を確かめます([測る値](verification.md#測る値))
- NUMA:1 つの node を前提にします。
  複数の node のホストでの挙動は未確認です
- SMT:N は論理の CPU の数で数えます。
  2 つの shard が同じ core の SMT の対に乗ると、暗号の速さが下がりえます。
  物理の core で数える方が良いかは測って決めます (未確認)

### 満ちた queue の扱い

- 受け口の queue:TCP の data の segment を捨てて数えます。
  最初は queue の上限での drop-tail にします
- CoDel:受け口の queue は wgft が順を決められる平文の queue なので、記述子に積んだ時刻を持たせ、取り出す時に CoDel (RFC 8289) を当てる形を後で比べます
- 捨てないもの:昇格の知らせと制御の知らせは捨てません([上限のある queue](memory.md#上限のある-queue))

## UDP を先にして TCP を飢えさせない規則

- shard 0 のバッチの中:UDP の datagram を同じバッチの TCP の segment より先に処理する今の規則を保ちます
- shard 0 の出力:4 つの組の byte の deficit round robin を保ちます。
  UDP の組は自分の quantum を超えて続けて送れないので、TCP の組は毎回の巡りで自分の分を得ます
- 遅れの予算:1 回の起床の仕事を 50 µs で区切る今の規則を、各 shard に当てます
- 昇格:shard 0 が詰まると重い TCP の flow を外へ出すので、UDP の待ちが減ります
- 外側のソケットの送り:UDP が動いている間、昇格した接続の shard は 1 回の送り出しの byte を小さな上限に抑えます([flow をまたぐ送り出しの順](ownership.md#flow-をまたぐ送り出しの順))
- 飢えの防止:TCP の flow は shard 0 にあっても deficit round robin で送り、昇格した flow は自分の shard で送るので、UDP の量によらず送る機会があります

## flow の公平とワーカーの公平

経路が詰まりの時 (家の回線など) は、どの shard も詰まっていないので、flow の間の配分は TCP の輻輳制御が決め、shard の分け方は公平に効きません(推定)。

shard の CPU が詰まりの時は、shard ごとの CPU が flow に分けられるので、次の場合に flow の公平が崩れます。

- shard ごとの flow の数の偏り:2 本を持つ shard と 1 本を持つ shard が並ぶと、2 本の側の flow は半分の CPU しか得ません。
  速さの比が 0.5、0.5、1 の 3 本の Jain の指数は 0.89 です(計算)
- shard 0 の flow:shard 0 に残る flow は、読み、振り分け、UDP と CPU を分けます
- 受け口の queue の捨て:満ちた持ち主の queue の flow だけが損失を受け、送り手の速さが下がります
- 手伝いの偏り:手伝いが 1 つの shard の申し出ばかり引き取ると、その shard の flow が速くなります

手当ては次のとおりです。

- 移し先:昇格は、flow の数と直近の byte で最も軽い shard を選びます
- 手伝いの順:手伝いは、積み残しの最も多い shard の申し出から引き取ります
- 昇格の続き:shard 0 が詰まっている間は昇格を続けるので、shard 0 に残る重い flow は減っていきます
- 採らない手当て:shard をまたぐ全体の deficit round robin は、packet ごとの同期が要るので採りません(設計判断)

受け入れの線は、経路が詰まりの時と CPU が詰まりの時で分けます([受け入れの条件](verification.md#受け入れの条件))。

## 10 Gbit/s を決める上限

10 Gbit/s に届くかは未確認です。
同じラボのカーネルモードの最大は 9,083 Mbit/s (8 vCPU、送る 4 stream、測定) なので、ラボの経路そのものが 10 Gbit/s の手前で上限になりえます。

| 上限 | 測定での見え方 |
|---|---|
| 1 つの flow の持ち主のスレッド | 持ち主のスレッドの実行の割合が 1.0 に近く、ほかの shard に空きがある |
| shard 0 | shard 0 の実行の割合が 1.0 に近く、昇格の後も下がらない |
| カーネルの外側の 1 つの流れの受信の処理 | agent の VM の 1 つの vCPU の受信の処理の時間が 1.0 に近い |
| 外側のソケットへの並んだ送り出し | 送り出しの system call 1 回の時間が N とともに伸びる (計測器つきの build) |
| CPU の総量 | agent の VM の忙しさが vCPU の数に近い |
| 相手の VM と経路 | ラボが相手の VM の詰まりを `peer_bound` として記録する。カーネルモードの腕も同じ速さで止まる |
| メモリの帯域 | 上のどれにも当たらずに、byte あたりの CPU が速さとともに伸びる |

外側の 1 つの流れの受信の処理が上限だと分かった時は、複数のセッションか複数の queue の link (F、G) を比べ直します([構成の比較](architecture.md#f-複数のセッションへの分割))。
