# 性能の模型 (N4)

この文書は、推奨の構成 U の性能の模型を、測った費用から組み立て、負荷ごとの振る舞い、予想する詰まり、CPU の数ごとの動かし方、実行の仕組みの選択、後の段を定めます。
未採用の提案です([提案の索引](README.md))。
値の区別は[値の区別](README.md#値の区別)に従います。
10 Gbit/s に届くことは前提にせず、何が上限を決め、測定でどう見分けるかを示します。

## 模型に使う値

### 測定の条件

- 分けたラボ:agent を専用の N vCPU の VM に置き、相手は 8 vCPU の VM です。
  `lab/lab paired --split --placement apart`、4 round × 2 回の中央値です([agent を専用の VM に置く](../../../../lab/README.md#agent-を専用の-vm-に置く---split))
- Inline:バッチの実装の後の main の Rust の agent で、データプレーンは 1 つのスレッドです
- 1 つの VM のラボ:5 つの network namespace を 1 つの 4 vCPU の VM に置いた、バッチの前の基準です([基準の値](../../v2/agent-throughput.md#基準の値))

## 役ごとの費用の模型

Inline のスレッドが詰まった時の byte あたりの時間を T と書きます。
受ける向き T_r は約 1.0 ns/byte、送る向き T_s は約 1.5 ns/byte です(推定、上の未公開の記録から導いた値)。

| 役 | 受ける向き | 送る向き |
|---|---|---|
| front の読み、復号、振り分け | 約 0.44 から 0.58 ns/byte | ACK の読みと復号だけ |
| front の counter の在庫の補充 (積み残しの間) | 無し | 約 0.02 から 0.04 ns/byte と、在庫が尽きた時の起床 |
| unit の実行 (核、0 埋め、中継、LAN の側の system call) | 約 0.55 から 0.65 ns/byte | 約 1.4 から 1.5 ns/byte。暗号化と送り出しを含みます |
| helper が unit を実行する時の cache の移動 | 約 0.05 から 0.15 ns/byte | 小さい |

区別はどれも推定です。

## 軽い負荷と中くらいの負荷

軽い負荷は Inline の最大の速さの 0.01 から 0.1 倍と対話の往復、中くらいの負荷は 0.25 から 0.5 倍です。

### U の振る舞い

軽い負荷と中くらいの負荷では front が詰まらず、積み残しに入りません(推定)。
front が全 unit をその場で実行し、Inline と違うのは次の点だけです。

| 違い | 費用 (推定) |
|---|---|
| unit の受け口の輪への書き込みと読み出し | packet あたり 20 から 50 ns |
| unit ごとの実行の始めと終わり | 起床と unit の組ごとに 50 から 100 ns |
| unit の epoll を読む system call | LAN の側の準備がある起床ごとに 0.3 から 0.5 µs |
| tokio を使わない executor と中継 | 未測定 |

1 packet の起床の Inline の仕事 (約 9.1 µs、推定) と比べると、CPU は 1.02 から 1.06 倍、遅れの増分は 1 µs 未満です(推定)。
最も大きな不確かさは executor と中継の作り直しの差で、P0 で本物の LAN の側のソケットを使って測ります([段階の試作](verification.md#段階の試作))。

### S の振る舞い (比べのため)

- 軽い負荷:受けた TCP のバッチごとに眠った持ち主を起こします。
  起床 1 回に 3 から 8 µs の CPU (受け渡し 1 回あたり約 4 µs の測定に近い値) を加えると、1 packet の起床で CPU は Inline の 1.3 から 1.9 倍です(推定)。
  受けた segment は持ち主の起床を待ち、直前まで動いていれば 2.0 から 2.4 µs、10 ms 眠った後は 7 から 80 µs が加わります
- 中くらいの負荷:0.5 倍の負荷で front の起床は毎秒 2 万から 4 万回あり、その都度持ち主を起こすと 0.06 から 0.32 CPU が加わります。
  Inline の約 0.5 CPU に対し、byte あたりの CPU は 1.12 から 1.64 倍です(推定)

## 積み残しの間

積み残しの間は、helper が unit を実行し、S と同じ受け渡しと起床を払います。
上限の見積もりは次のとおりです(推定)。

- 受ける 1 stream:front と helper の 2 段の pipeline です。
  遅い方の helper (0.6 から 0.8 ns/byte) が上限で、約 10 から 13 Gbit/s、Inline のスレッドの上限 (約 7.5 から 8 Gbit/s) の 1.3 から 1.7 倍です
- 受ける多くの stream:front (0.44 から 0.58 ns/byte) が直列の上限で、約 14 から 18 Gbit/s です
- 送る 1 stream:1 つのスレッドが Inline とほぼ同じ仕事をするので、Inline と同じ約 5.3 Gbit/s です
- 送る多くの stream:front の unit 0 と H 本の helper で、最大 H + 1 倍まで伸び、CPU の総量かカーネルか相手が先に上限になります。
  2 vCPU では unit 0 と unit 1 の 2 つのスレッドに分かれ、agent の VM の CPU の残り (Inline の送る 4 stream で約 1.0 CPU が空いています) の分だけ伸びると見込みます
- counter の在庫:front は ACK を受けて起き続けるので、在庫の補充は通常 front の起床に乗ります。
  front が眠っていた時だけ、64 datagram ごとに起床が最大 2 回加わります
- 大きな flow が helper に揃うまで:入る判定の約 0.6 ms と、起床ごとに 1 つの unit の受け渡しです

## 予想する詰まり

- 受ける 1 stream:unit の核と中継です。
  ラボでは相手の VM です
- 受ける多くの stream:front の読みと復号です
- 送る 1 stream:1 つのスレッドです
- 送る多くの stream:CPU の総量、外側のソケットへの並んだ送り出し、相手です
- 接続の入れ替わりが多い負荷と UDP の多い負荷:front です

## CPU の数ごとの動かし方

利用できる CPU の数 n_cpu は、affinity の CPU の数と、cgroup の割り当て (`cpu.max`) を整数の CPU に切り下げた値の小さい方で、1 以上です(設計判断)。
helper の数 H は n_cpu から決め、設定を持ちません。

| n_cpu | H | M = H + 1 | 振る舞い |
|---|---|---|---|
| 1 | 0 | unit を分けない | 今の核と同じ front |
| 2 | 1 | 2 | 積み残しの間は front (unit 0) と helper (unit 1) |
| 4 | 3 か 2 | 4 か 3 | 同上 |
| 8 | 7 か 6 | 8 か 7 | 同上 |

- H の選び方:H = n_cpu - 1 と n_cpu - 2 を、判定に使う組とは別の P2 の選びの実行で比べ、最大の負荷と CPU の取り合いの下の UDP の遅れと速さで決めます。
  n_cpu - 1 では、カーネルの受信と送信と LAN の側の TCP の処理と CPU を取り合います。
  分けたラボの Inline の受ける向きの 7.5 Gbit/s では、その分は約 0.2 CPU でした (測定、未公開の記録から導いた値)
- 上限:H は 7 までにします。
  8 を超える CPU は試していないためで、超える CPU は使いません (未確認)
- 優先度:helper のスレッドの優先度は変えません

## 要件の折り合い

### 送る 1 stream

基本の設計では、1 本の送る stream は 1 つのスレッドの仕事のままで、Inline と同じ速さです。
伸ばすには 1 本の flow の暗号化を別のスレッドで順序を保って手伝う形が要り、A+ と同じ種類の仕組みです。

- 暗号だけを移す上限:送る向きの CPU の 19.3% が暗号 (測定、未公開の記録) なので、暗号だけを移す形の上限は 1 / (1 - 0.193) で約 1.24 倍です(計算)
- A+ の測った値:送る向きで 1.41 から 1.63 倍、1 stream の組で 1.378 倍でした (#808 から #810)。
  暗号だけの上限を超えた理由は確かめていません。
  ラボで送り手の文脈に数えられる受け手の処理の分が効いた可能性があります(推定)
- A+ の測った費用:4 vCPU の固定の負荷の UDP の p50、CPU の取り合いの下の byte あたりの CPU 1.10 から 1.19 倍、8.4 MiB の常駐のメモリでした

### UDP の低い遅れ

受ける向きでは、積み残しの間に front が重い unit を helper に渡すので、UDP の待ちは Inline より短くなると見込みます(推定)。
送る向きでは、helper の送りの前に UDP を出す印と送りの上限で、UDP の前に並ぶ byte を Inline と同じ 1 バッチまでにします([UDP と helper の送り](ownership.md#udp-と-helper-の送り))。

### byte あたりの CPU

軽い負荷と中くらいの負荷は Inline に近く、積み残しの間は cache の移動 (0.05 から 0.15 ns/byte、推定) と起床の費用が加わります。

## 実行の仕組みの選択

- 輪:すべて SPSC です。
  MPSC の 1 つの輪は書き手の CAS が 1 つの cache line に集まるので採りません。
  輪と眠りの印の手順は、upstream の crate を変えずに使えるものがあればそれを使い、無ければ `unsafe` を 1 つの module に閉じた小さな実装にします
- 空きの list:送信の枠は executor ごと、平文の block は front が取り unit が返し、chunk と大きいバッファは unit の状態の置き場です
- 所有の移動と写し:記述子 (32 byte 程度) だけを動かします。
  front が unit を実行する時は平文は移らず、helper が実行する時は核が受信のデータを輪に写す時に平文が helper の cache に移ります
- バッチの大きさ:front の読みは今と同じく、前のバッチの時間から予算の半分 (25 µs) に収まる枠の数で決めます。
  起床の予算は 50 µs です。
  バッチを満たすために待つことはしません
- 起こし方:眠る前に眠りの印を立て、fence の後に輪を見直してから眠ります。
  書き手は公開の後に印を見て、眠っている時だけ起こします
- busy polling:使いません。
  #808 では手伝いを 50 µs 回すと byte あたりの CPU が 2.48 倍になりました (測定)
- 固定、NUMA、SMT:製品はスレッドを CPU に固定しません。
  ラボは置き方を固定した実行と固定しない実行の両方を流します。
  複数の NUMA の node と SMT の扱いは未確認です
- 満ちた queue:受け口の輪は記述子の上限と平文の置き場の上限で抑え、上限に達した unit の TCP の segment を捨て、front の読みは止めません([平文の置き場と unit の上限](memory.md#平文の置き場と-unit-の上限))

## flow の公平とワーカーの公平

経路が上限の時は、どの executor も詰まらないので、flow の間の配分は TCP の輻輳制御が決めます(推定)。
CPU が上限の時は、unit ごとの CPU が flow に分けられるので、次の場合に公平が崩れます。

- unit ごとの大きな flow の数の偏り:速さの比が 0.5、0.5、1 の 3 本の Jain の指数は 0.89 です(計算)
- 後で重くなる接続:作成の時に重さが分からず、同じ unit に入った 2 本は 1 つのスレッドを分けます
- 平文の置き場の上限での捨て:上限に達した unit の flow だけが損失を受けます

採らない手当ては、unit をまたぐ全体の deficit round robin (packet ごとの同期が要ります) と、動いている接続の移しです。

## 後の段

| 形 | 加える条件 | 要る仕組みと費用 |
|---|---|---|
| 受信の暗号の手伝い | front が受ける多くの stream の上限になると測った時 | 塊の番号の順の確定と、期限を過ぎた塊を front が復号し直す取り戻し。#808 では 25 µs の回に手伝いを入れても速さが変わらず、byte あたりの CPU が 27% 増えました (測定) |
| 1 本の flow の送りの手伝い | 所有者が A+ と同じ種類の費用を受け入れた時([所有者に決めてもらうこと](README.md#所有者に決めてもらうこと)) | 持ち主の順の暗号化と送り出しの板 |
| UDP のセッションを unit へ | 大きな量の UDP が front を詰まらせると測った時 | 接続した UDP の 4 つ組を表の鍵にし、セッションを作成の時に unit に置きます |

## 10 Gbit/s を決める上限

10 Gbit/s に届くかは未確認です。
同じラボのカーネルモードの最大が 9,083 Mbit/s (測定、未公開の記録) なので、ラボの経路そのものが 10 Gbit/s の手前で上限になりえます。

| 上限 | 測定での見え方 |
|---|---|
| 1 つの flow の unit を実行するスレッド | そのスレッドの実行の割合が 1.0 に近く、ほかに空きがある |
| front | front のスレッドの実行の割合が 1.0 に近い |
| 外側の UDP の流れ 1 本をカーネルが受信する処理 | agent の VM の 1 つの vCPU の受信の処理の時間が 1.0 に近い |
| 外側のソケットへの並んだ送り出し | `sendmmsg` 1 回の時間が helper の数とともに伸びる |
| CPU の総量 | agent の VM の忙しさが vCPU の数に近い |
| 相手の VM と経路 | ラボが `peer_bound` と記録する。カーネルモードの腕も同じ速さで止まる |

外側の UDP の流れ 1 本の受信が上限だと分かった時は、複数のセッションか複数の queue の link を比べ直します([構成の比較](architecture.md#f-複数のセッションへの分割))。
