# 性能の模型 (N4)

この文書は、推奨の構成 U の性能の模型を、測った費用から組み立て、負荷ごとの振る舞い、予想する詰まり、CPU の数ごとの動かし方、実行の仕組みの選択、後の段を定めます。
未採用の提案です([提案の索引](README.md))。
値の区別は[値の区別](README.md#値の区別)に従います。
10 Gbit/s に届くことは前提にせず、何が上限を決め、測定でどう見分けるかを示します。

## 模型に使う値

### 測定の条件

- 分けたラボ:agent を専用の N vCPU の VM に置き、相手は 8 vCPU の VM です。
  `lab/lab paired --split --placement apart`、4 round × 2 回の中央値です([agent を専用の VM に置く](../../../../lab/README.md#agent-を専用の-vm-に置く---split))
- Inline:バッチの実装の後の main の Rust の agent で、データプレーンは 1 つのスレッドです
- 1 つの VM のラボ:5 つの network namespace を 1 つの 4 vCPU の VM に置いた、バッチの前の基準です([基準の値](../../v2/agent-throughput.md#基準の値))

## 役ごとの費用の模型

Inline のスレッドが詰まった時の byte あたりの時間を T と書きます。
受ける向き T_r は約 1.0 ns/byte、送る向き T_s は約 1.5 ns/byte です(推定、上の未公開の記録から導いた値)。

| 役 | 受ける向き | 送る向き |
|---|---|---|
| front の読み | 約 0.06 ns/byte | ACK の読みだけ |
| front の復号 | 約 0.34 から 0.48 ns/byte | ACK の復号だけ |
| front の振り分けと記述子 | 約 0.04 ns/byte | 小さい |
| front の counter の貸し出し (積み残しの間) | 無し | packet あたり数十 ns で、約 0.02 から 0.04 ns/byte |
| unit の実行 (核、0 埋め、中継、LAN の側の system call) | 約 0.55 から 0.65 ns/byte | 約 1.4 から 1.5 ns/byte。暗号化と送り出しを含みます |
| helper が unit を実行する時の cache の移動 | 約 0.05 から 0.15 ns/byte | 小さい |

区別はどれも推定です。

## 軽い負荷と中くらいの負荷

この提案では、Inline の最大の速さの 0.01 から 0.1 倍と対話の往復を「軽い負荷」、0.25 から 0.5 倍を「中くらいの負荷」と呼びます。

### U の振る舞い

軽い負荷と中くらいの負荷では、front のスレッドの忙しさが Inline と同じく 0.5 以下で、積み残しに入りません(推定)。
front のスレッドが全 unit をその場で実行し、Inline と違うのは次の点だけです。

| 違い | 費用 (推定) |
|---|---|
| unit の受け口の輪への書き込みと読み出し | packet あたり 20 から 50 ns |
| unit ごとの実行の始めと終わり (期限の読み書き、輪の index) | 起床と unit の組ごとに 50 から 100 ns |
| unit ごとの核と表 | 同じ起床に複数の unit がある時、cache の当たりが少し下がります |
| 中継の状態機械と executor の poller | tokio の中継との差は未測定です |

packet あたりの Inline の CPU (受ける向き 2.4 µs、測定、バッチの前) と比べると、packet あたりの CPU は 1.05 倍以下、遅れの増分は 1 µs 未満です(推定)。
最も大きな不確かさは、中継を tokio の外の状態機械に作り直す差で、P0 で測ります。

### S の振る舞い (比べのため)

S では、持ち主のスレッドが unit を常に実行するので、受信の TCP のバッチごとに持ち主を起こします。

- 軽い負荷の CPU:受けた packet ごとに起床が 1 回あり、起床ごとに 3 から 8 µs の CPU を払うと、packet あたりの CPU は Inline の (2.4 + 3 から 8) / 2.4 で 2.3 から 4.3 倍です(推定)
- 軽い負荷の遅れ:受けた segment は持ち主の起床を待ちます。
  直前まで動いていれば 2.0 から 2.4 µs (測定、#809)、10 ms 眠った後は 7 から 80 µs (測定、未公開の記録) です。
  対話の往復では、要求ごとに長く眠った後の起床を払うので、p99 が最大で 80 µs 程度増えます(推定)
- 中くらいの負荷の CPU:0.5 倍の負荷で front の起床が毎秒 2 万から 4 万回あり、その都度持ち主を起こすと 0.06 から 0.3 CPU が加わり、byte あたりの CPU は 1.15 から 1.75 倍です(推定)。
  #808 の手伝いが同じ形の起床で 1.27 倍になったこと (測定) と同じ向きです
- 送る向きの counter:S は counter を常に貸すので、持ち主から front への求めの起床も加わります

### 対話の往復の遅れ

U の軽い負荷では、要求も応答も front のスレッドの 1 回の起床の中で処理するので、往復の遅れは Inline と同じ起床の数です。
U で往復に起床が加わるのは、積み残しの間に helper の unit に置かれた接続だけです。
対話の往復の遅れは P0 と P2 で測ります([測定の行列](verification.md#測定の行列))。

## 積み残しの間

積み残しの間は、helper が unit を実行し、S と同じ分担になります。
上限の見積もりは次のとおりです(推定)。

- 受ける 1 stream:front (0.44 から 0.58 ns/byte) と unit の helper (0.6 から 0.8 ns/byte) の 2 段の pipeline です。
  遅い方の helper が上限で、約 10 から 13 Gbit/s です。
  Inline のスレッドの上限 (約 7.5 から 8 Gbit/s) の 1.3 から 1.7 倍です
- 受ける多くの stream:front が直列の上限で、約 14 から 18 Gbit/s です。
  front が UDP と握手も持つ時は、その分だけ下がります
- 送る 1 stream:unit の helper の 1 つのスレッドが Inline とほぼ同じ仕事をするので、Inline と同じ約 5.3 Gbit/s です
- 送る多くの stream:helper の数 H の倍まで伸び、CPU の総量かカーネルか相手が先に上限になります
- CPU の総量:4 vCPU で、受ける向き 18 から 25 Gbit/s、送る向き 16 から 20 Gbit/s です
- 積み残しに入ってから大きな flow が helper に揃うまで:入る判定の 8 回の起床 (約 0.4 ms) と、起床ごとに 1 つの unit の受け渡しで、M = 7 なら 7 回の起床です

## 予想する詰まり

- 受ける 1 stream:unit の核と中継です。
  ラボでは相手の VM です
- 受ける多くの stream:front の読みと復号です
- 送る 1 stream:unit の 1 つのスレッドです
- 送る多くの stream:CPU の総量、外側のソケットへの並んだ送り出し、相手です
- 接続の入れ替わりが多い負荷:握手と行を持つ front と、作成の知らせです
- UDP の多い負荷:UDP を持つ front です

## CPU の数ごとの動かし方

利用できる CPU の数 n_cpu は、affinity の CPU の数と、cgroup の割り当て (`cpu.max`) を整数の CPU に切り下げた値の小さい方で、1 以上です(設計判断)。
割り当てより多いスレッドは割り当ての周期の間止められ、front の受信を止めるためです。
helper の数 H と unit の数 M は n_cpu から決め、設定を持ちません。

| n_cpu | H | M | 振る舞い |
|---|---|---|---|
| 1 | 0 | 0 | Inline そのもの |
| 2 | 1 | 1 | 積み残しが無い間は Inline に近く、積み残しの間は front と helper の 2 段です |
| 4 | 3 | 3 | 積み残しの間は 3 つの unit を 3 本の helper が実行します |
| 8 | 7 | 7 | 同上。8 を超える CPU は試していません (未確認) |

- H = n_cpu - 1:積み残しの間は front と H 本の helper が忙しく、カーネルの受信と送信と LAN の側の TCP の処理も CPU を使います。
  分けたラボの Inline では、agent の VM の CPU とデータの経路のスレッドの差 (カーネルなどの分) は、受ける向きの 7.5 Gbit/s で約 0.2 CPU でした (測定、未公開の記録から導いた値)。
  このため H = n_cpu - 1 では、最大の負荷で CPU を少し超えて取り合います(推定)
- 優先度:helper のスレッドの nice の値を上げます。
  Linux では、スレッドが自分の nice の値を上げるのに特権は要りません。
  CPU を取り合う時に、front とカーネルの処理が helper より先に CPU を得るためです(設計判断)
- 比べ:H = n_cpu - 2 を P2 で比べ、最大の負荷と CPU の取り合いの下の UDP の遅れと速さで決めます
- M = H:helper は前に実行した unit を受け取るので、cache が温まったままです。
  unit を helper より多くしても、CPU が増えないので並列は増えません
- Windows と macOS:n_cpu によらず Inline の経路です

## 要件の折り合い

### TCP の 1 stream

受ける 1 stream は、積み残しの間に front と helper の 2 段で伸びます。
送る 1 stream は、基本の設計では伸びません。
送る 1 stream を伸ばす後の段は、1 本の大きな flow の暗号化と送り出しを順序を保って手伝う形で、所有者が 2026-11-05 に止めた A+ の暗号の手伝いと同じ種類の仕組みです([後の段](#後の段))。

### TCP の多くの stream

接続は作成の時に unit に分かれ、積み残しの間は unit の数まで並列になります。

### UDP の低い遅れ

UDP は front の中で、Inline と同じ順と予算で処理します。
積み残しの間は front が TCP の処理を helper に渡すので、UDP の待ちは Inline より短くなると見込みます(推定)。

### byte あたりの CPU

軽い負荷と中くらいの負荷は Inline に近く、積み残しの間は cache の移動 (0.05 から 0.15 ns/byte、推定) と受け渡しの費用が加わります。

## 実行の仕組みの選択

### 輪の種類

すべて SPSC の輪です。
MPSC の 1 つの輪は書き手の CAS が 1 つの cache line に集まり、満ちた時の待ちの規則が要るので採りません(設計判断)。
輪と眠りの印の手順は、upstream の crate を変えずに使えるものがあればそれを使い、無ければ `unsafe` を 1 つの module に閉じた小さな実装にします。
どちらにするかは、loom などのメモリの順の模型の検査を当てられるかで、実装の時に決めます(未確認)。

| 輪 | 向き | 満ちた時 |
|---|---|---|
| 受け口の輪 | front から unit | unit の記述子の上限 (2,048) と block の上限で TCP の segment を捨てます |
| 制御の輪 | front から unit | 満ちません。容量 4 × N_c,u + 2 |
| 返却の輪 | unit から front | 満ちません。容量 2 × N_c,u |
| 戻しの輪 | unit から front | 容量 64。満ちたら SYN を捨てます |
| block の返却の輪 | unit から front | 満ちません |
| 受け渡しの輪 | executor ごと | 満ちません。容量 M |
| 貸し出しの輪 | front から helper | 求めた数までしか載せません |

輪の index は書き手と読み手で別の cache line に置き、書き手は起床ごとに 1 回だけ公開します。

### ワーカーの手元の空きの list

- 送信の枠:各 executor が自分の置き場を持ち、自分で返します
- 平文の block:取るのは front だけで、unit の持ち主が block の返却の輪で返します
- chunk と大きいバッファ:unit の状態に置き場を持ち、その unit の持ち主が取って返します

### 所有の移動と写しと cache line の費用

- 記述子 (32 byte 程度) だけを動かし、packet の中身は平文の block に置いたままにします
- front が unit をその場で実行する時は、平文は front の cache にあるので移りません
- helper が実行する時は、unit の核が受信のデータを自分の輪に写す時に、平文が helper の cache に移ります。
  中身を別に写して渡す形は、写しの費用 (0.093 から 0.097 ns/byte、測定) が cache の移動とほぼ同じなので採りません(推定)

### バッチの大きさ

front の読みの大きさは今と同じく、前のバッチの時間から遅れの予算 (25 µs) に収まる枠の数で決めます。
helper の送りのバッチも、今の送りの相の規則を使います。
バッチを満たすために待つことはしません。

### 起こし方

- 各 executor は眠る前に眠りの印を立て、fence の後に輪を見直してから眠ります。
  書き手は公開と fence の後に印を見て、眠っている時だけ起こします
- front は、helper が持ち主の unit に載せた時だけ、自分の起床の終わりに 1 回だけその helper を起こします。
  積み残しが無い間は helper に unit が無いので、helper を起こしません
- Linux では eventfd を executor の poller に入れます

### busy polling と event 駆動

event 駆動だけを使います。
眠る前に回り続ける形は、#808 で byte あたりの CPU が 2.48 倍になったので採りません (測定)。

### CPU の固定、NUMA、SMT

- 固定:製品はスレッドを CPU に固定しません。
  コンテナと cgroup で利用できる CPU が変わり、固定の設定を持たない規則のためです
- 測定:ラボは置き方を固定して流し、固定しない実行も加えます([測る値](verification.md#測る値))
- NUMA:1 つの node を前提にします。
  複数の node のホストは未確認です
- SMT:n_cpu は論理の CPU の数で数えます。
  物理の core で数える方が良いかは測って決めます (未確認)

### 満ちた queue の扱い

- unit の受け口の輪は、記述子の数と、unit が参照を持つ平文の block の数で抑えます([unit ごとの block の上限](memory.md#unit-ごとの-block-の上限))
- 上限に達した unit の TCP の segment を捨て、front の読みは止めません。
  捨てる segment は経路での損失と同じ扱いで、送り手が SACK と RACK で回復します
- 受け口の輪は wgft が順を決められる平文の queue なので、取り出す時に CoDel (RFC 8289) を当てる形を後で比べます

## UDP を先にして TCP を飢えさせない規則

- front のバッチの中:UDP の datagram を同じバッチの TCP の segment より先に処理する今の規則を保ちます
- front の出力:4 つの組の byte の deficit round robin を保ちます。
  UDP の組は自分の quantum を超えて続けて送れないので、TCP の組は毎回の巡りで自分の分を得ます
- 遅れの予算:1 回の起床の仕事を 50 µs で区切る今の規則を、各 executor に当てます
- 積み残しの間の送り:helper の送りは front の UDP の後ろに並びえます。
  基本の設計では送りの byte に上限を置かず、最大の送る負荷の UDP の遅れを測ってから、上限か executor ごとのソケットを比べます。
  executor ごとのソケットは送信元のポートを変えるので、server の endpoint の更新との関係を確かめる必要があります
- 飢えの防止:TCP は unit の持ち主が送るので、UDP の量によらず送る機会があります

## flow の公平とワーカーの公平

経路が上限の時 (家の回線など) は、どの executor も詰まらないので、flow の間の配分は TCP の輻輳制御が決め、unit の分け方は公平に効きません(推定)。

CPU が上限の時は、helper ごとの CPU が flow に分けられるので、次の場合に flow の公平が崩れます。

- unit ごとの大きな flow の数の偏り:2 本を持つ unit と 1 本を持つ unit が並ぶと、2 本の側の flow は半分の CPU しか得ません。
  速さの比が 0.5、0.5、1 の 3 本の Jain の指数は 0.89 です(計算)
- 静かな接続:直近の受信の packet で重みを付けるので、静かな長い接続は重みに入らず、大きな flow を偏らせません
- unit ごとの block の上限での捨て:上限に達した unit の flow だけが損失を受けます

採らない手当ては、unit をまたぐ全体の deficit round robin (packet ごとの同期が要ります) と、動いている接続の移しです。

## 後の段

次の形は基本の設計に含めず、試作で必要を測った時だけ加えます。

| 形 | 加える条件 | 要る仕組みと費用 |
|---|---|---|
| 受信の暗号の手伝い | 積み残しが続き、front が受ける多くの stream の上限になると測った時 | 塊の番号の順の確定と、期限を過ぎた塊を front が自分で復号し直す取り戻し。#808 では 25 µs の回に手伝いを入れても速さが変わらず、byte あたりの CPU が 27% 増えました (測定) |
| 1 本の flow の送りの手伝い | helper が窓の間 0.9 以上忙しく、その byte の 8 割以上が 1 本の flow で、ほかの helper に空きがある時 | 持ち主の順の暗号化と送り出しの板。A+ の暗号の手伝いと同じ種類の仕組みで、A+ の測った費用 (UDP の p50、CPU の取り合いの下の byte あたりの CPU、メモリ) を同じように持ちうるので、採るには所有者の判断が要ります |
| UDP のセッションを unit へ | 大きな量の UDP が front を詰まらせると測った時 | 接続した UDP の 4 つ組を表の鍵にし、セッションを作成の時に unit に置きます |

受信の暗号の手伝いの塊は、取り戻せる形にします。
確定 (`commit_decapsulate`) の前の復号は状態を変えないので、期限 (仮の値は 50 µs) を過ぎた塊を front が自分で復号し直しても正しさは崩れず、遅れた手伝いの結果は世代の違いで捨てます。
UDP の datagram は復号するまで見分けられないので、止まった塊を飛ばして UDP だけを先に渡す形は作れず、UDP の待ちは期限で抑えます。

## 10 Gbit/s を決める上限

10 Gbit/s に届くかは未確認です。
同じラボのカーネルモードの最大が 9,083 Mbit/s (測定、未公開の記録) なので、ラボの経路そのものが 10 Gbit/s の手前で上限になりえます。

| 上限 | 測定での見え方 |
|---|---|
| 1 つの flow の unit を実行する helper | helper のスレッドの実行の割合が 1.0 に近く、ほかの helper に空きがある |
| front | front のスレッドの実行の割合が 1.0 に近い |
| カーネルの外側の 1 つの流れの受信の処理 | agent の VM の 1 つの vCPU の受信の処理の時間が 1.0 に近い |
| 外側のソケットへの並んだ送り出し | `sendmmsg` 1 回の時間が helper の数とともに伸びる (計測器つきの build) |
| CPU の総量 | agent の VM の忙しさが vCPU の数に近い |
| 相手の VM と経路 | ラボが相手の VM の詰まりを `peer_bound` として記録する。カーネルモードの腕も同じ速さで止まる |
| メモリの帯域 | 上のどれにも当たらずに、byte あたりの CPU が速さとともに伸びる |

外側の 1 つの流れの受信の処理が上限だと分かった時は、複数のセッションか複数の queue の link を比べ直します([構成の比較](architecture.md#f-複数のセッションへの分割))。
