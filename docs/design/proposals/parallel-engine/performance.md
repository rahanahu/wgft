# 性能の模型 (N4)

この文書は、推奨の構成 S の性能の模型を、測った byte あたりの費用から組み立て、予想する詰まり、CPU の数ごとの動かし方、要件の折り合い、実行の仕組みの選択、後の段を定めます。
未採用の提案です([提案の索引](README.md))。
値の区別は[値の区別](README.md#値の区別)に従います。
10 Gbit/s に届くことは前提にせず、何が上限を決め、測定でどう見分けるかを示します。

## 模型に使う値

### 測定の条件

- 分けたラボ:agent を専用の N vCPU の VM に置き、相手は 8 vCPU の VM です。
  `lab/lab paired --split --placement apart`、4 round × 2 回の中央値です([agent を専用の VM に置く](../../../../lab/README.md#agent-を専用の-vm-に置く---split))
- Inline:バッチの実装の後の main の Rust の agent で、データプレーンは 1 つのスレッドです
- 1 つの VM のラボ:5 つの network namespace を 1 つの 4 vCPU の VM に置いた、バッチの前の基準です([基準の値](../../v2/agent-throughput.md#基準の値))

## 役ごとの費用の模型

Inline のスレッドが詰まった時の byte あたりの時間を T と書きます。
T は、速さの逆数とスレッドの忙しさの積で、受ける向き T_r は約 1.0 ns/byte、送る向き T_s は約 1.5 ns/byte です(推定、上の未公開の記録から導いた値)。

| 役 | 受ける向き | 送る向き |
|---|---|---|
| shard 0 の読み | 約 0.06 ns/byte | ACK の読みだけで小さい |
| shard 0 の復号 | 約 0.34 から 0.48 ns/byte (profile の割合と microbench の幅) | ACK の復号だけで小さい |
| shard 0 の振り分けと記述子 | 約 0.04 ns/byte | 小さい |
| shard 0 の counter の貸し出し | 無し | packet あたり数十 ns で、約 0.02 から 0.04 ns/byte |
| 持ち主 (核、0 埋め、中継、LAN の側の system call) | 約 0.55 から 0.65 ns/byte | 約 1.4 から 1.5 ns/byte。暗号化と送り出しを含みます |
| スレッドを移る分 (cache の移動) | 約 0.05 から 0.15 ns/byte | 小さい |

区別はどれも推定です。
ここから、次の上限を見積もります(推定)。

- 受ける 1 stream:shard 0 (0.44 から 0.58 ns/byte) と持ち主 (0.6 から 0.8 ns/byte) の 2 段の pipeline です。
  遅い方の持ち主が上限で、約 10 から 13 Gbit/s です。
  Inline のスレッドの上限 (約 7.5 から 8 Gbit/s) の 1.3 から 1.7 倍ですが、ラボでは相手の VM が先に詰まりえます
- 受ける多くの stream:shard 0 が直列の上限で、約 14 から 18 Gbit/s です。
  shard 0 が UDP と握手も持つ時は、その分だけ下がります
- 送る 1 stream:持ち主の 1 つのスレッドが Inline とほぼ同じ仕事をするので、Inline と同じ約 5.3 Gbit/s です
- 送る多くの stream:持ち主の数 N-1 の倍まで伸び、CPU の総量かカーネルか相手が先に上限になります
- CPU の総量:agent の VM の vCPU の数を、VM 全体の byte あたりの CPU (Inline の値にスレッドを移る分を加えた値) で割った値です。
  4 vCPU で、受ける向き 18 から 25 Gbit/s、送る向き 16 から 20 Gbit/s です

## 予想する詰まり

- 受ける 1 stream:持ち主の核と中継です。
  ラボでは相手の VM です
- 受ける多くの stream:shard 0 の読みと復号です
- 送る 1 stream:持ち主の 1 つのスレッドです
- 送る多くの stream:CPU の総量、外側のソケットへの並んだ送り出し、相手です
- 接続の入れ替わりが多い負荷:握手と TIME_WAIT を持つ shard 0 と、作成の知らせと中継の task の作成です
- UDP の多い負荷:UDP を持つ shard 0 です

## N が 2 以上の軽い負荷

N が 2 以上の時、shard 0 の UDP の経路と受信の復号は Inline と同じ呼び出しのままです。
Inline と違うのは、持ち主に置いた TCP の接続の扱いです。

| 違い | 費用の見積もり (推定) |
|---|---|
| 記述子の書き込みと block の参照の数 | packet あたり 10 ns 程度 |
| 持ち主への公開 | shard 0 の起床と持ち主の組ごとに 1 回の store |
| 持ち主を起こす system call | 持ち主が眠っている時、shard 0 の起床ごとに 1 回、約 0.4 から 0.6 µs (#809 の `unpark` の値) |
| 持ち主の起床と眠り | 起床ごとに数 µs の CPU。VM の出入りも加わります |
| 平文の cache の移動 | 約 0.05 から 0.15 ns/byte |
| 持ち主ごとの送り出し | 持ち主ごとに `sendmmsg` を呼ぶので、Inline より 1 回の呼び出しにまとまる datagram が減ります |
| 暗号化の分けた API | `begin_encapsulate` を shard 0、暗号化を持ち主で行います。#808 の分けた経路は 2 から 3.5% の増でした |

最も大きいのは起床の費用です。
0.5 倍の負荷 (約 2.6 Gbit/s) で shard 0 の起床が毎秒 2 万から 4 万回あり、その都度持ち主を起こすと、起床ごとに 3 から 8 µs の CPU で 0.06 から 0.3 CPU が加わります。
Inline のこの負荷の CPU は約 0.4 なので、byte あたりの CPU は 1.15 から 1.75 倍になりえます(推定)。
#808 の手伝いが同じ形の起床で 1.27 倍になったこと (測定) と同じ向きの見積もりです。

この費用は、受け入れの線を超える恐れが高い項目です。
試作の最初の段でこの値を測り、線を超えれば、代わりの形の昇格を比べ直します([代わりの形として残す昇格](architecture.md#代わりの形として残す昇格))。
線の値は所有者が決めます([所有者に決めてもらうこと](README.md#所有者に決めてもらうこと))。
待つことで起床を減らす形 (記述子が溜まるまで持ち主を起こさない形) は、TCP の遅れを加え、バッチを満たすために待たない規則に反するので採りません(設計判断)。

## CPU の数ごとの動かし方

N は、起動の時の利用できる CPU の数から決め、設定を持ちません。
利用できる CPU の数は、affinity の CPU の数と、cgroup の割り当て (`cpu.max`) を整数の CPU に切り下げた値の小さい方で、1 以上です(設計判断)。
割り当てより多いスレッドは、割り当ての周期の間止められ、shard 0 の受信を止めるためです。

| 利用できる CPU | N | TCP の接続の置き場 | 確かめること |
|---|---|---|---|
| 1 | 1 | shard 0 (Inline そのもの) | Inline との同等 |
| 2 | 2 か 1 | N = 2 なら shard 0 と shard 1 | N = 2 がどれかの組で 1.10 倍以上なら N = 2、そうでなければ N = 1 にします |
| 4 | 4 | shard 1 から 3 | N = 3 と比べ、カーネルの仕事に CPU を残す方が良いか |
| 8 | 8 | shard 1 から 7 | 8 を上限にするか。8 を超える CPU は試していません (未確認) |

## 要件の折り合い

### TCP の 1 stream

1 本の接続の状態機械は 1 つのスレッドでしか進められません。
受ける 1 stream は、読みと復号を shard 0 に、TCP と LAN の側の書き込みを持ち主に分ける 2 段で伸びます。
送る 1 stream は、基本の設計では伸びません。
送る 1 stream を伸ばすには、1 本の大きな flow の暗号化と送り出しを順序を保って手伝う後の段が要ります([後の段](#後の段))。
0 埋めの 11.2% (測定、未公開の記録) は持ち主に残るので、0 埋めを減らす変更は S と別に 1 stream の上限を引き上げます。

### TCP の多くの stream

接続を作成の時に持ち主の数に分けるので、多くの stream は持ち主の数まで分かれます。
大きな flow が揃うまでの時間は 0 です。

### UDP の低い遅れ

UDP は shard 0 の中で、Inline と同じ順と予算で処理します。
shard 0 が TCP の処理を持たない分 (N が 3 以上)、UDP の待ちは Inline より短くなると見込みます(推定)。
送る向きの UDP がカーネルの送信の待ち行列で TCP の後ろに並ぶ量は、[UDP を先にして TCP を飢えさせない規則](#udp-を先にして-tcp-を飢えさせない規則)で抑えます。

### byte あたりの CPU

最大の負荷では、スレッドを移る分 (0.05 から 0.15 ns/byte、推定) が加わります。
中くらいの負荷では、[N が 2 以上の軽い負荷](#n-が-2-以上の軽い負荷)の起床の費用が加わります。

## 実行の仕組みの選択

### 輪の種類

すべて SPSC の輪です。
MPSC の 1 つの輪は書き手の CAS が 1 つの cache line に集まり、満ちた時の待ちの規則が要るので採りません(設計判断)。

| 輪 | 向き | 満ちた時 |
|---|---|---|
| データの輪 | shard 0 から k | 持ち主ごとの block の上限で TCP の segment を捨てます。輪の記述子の数は上限の block の packet を入れられる大きさにします |
| 制御の輪 | shard 0 から k | 満ちません。容量は k の枠の数と定数です |
| 返却の輪 | k から shard 0 | 満ちません。容量は k の枠の数です |
| block の返却の輪 | k から shard 0 | 満ちません。容量は block の数以上です |
| 貸し出しの輪 | shard 0 から k | 在庫の上限で止めます |
| ライブラリの命令の輪 | 利用者から各 shard | 利用者に `WouldBlock` を返します |

輪の index は書き手と読み手で別の cache line に置き、書き手は起床ごとに 1 回だけ公開します。

### ワーカーの手元の空きの list

- 送信の枠:各 shard が自分の置き場を持ち、自分で返します
- 平文の block:取るのは shard 0 だけで、持ち主が block の返却の輪で返すので、全体の錠は要りません
- chunk と大きいバッファ:接続は shard を移らないので、取った shard が返します([chunk と大きいバッファの置き場](memory.md#chunk-と大きいバッファの置き場))

### 所有の移動と写しと cache line の費用

- 記述子 (32 byte 程度) だけを動かし、packet の中身は平文の block に置いたままにします
- 持ち主の核は今と同じく受信のデータを自分の輪に写し、この写しが平文を持ち主の手元に移す役を兼ねます
- 中身を写して渡す形は、写しの費用 (0.093 から 0.097 ns/byte、測定) が cache の移動とほぼ同じで利点が無いので採りません(推定)
- shard の間で同じ cache line を書くのは、輪の index と block の参照の数だけです。
  書き手ごとに cache line の境で分けます

### バッチの大きさ

shard 0 の読みの大きさは今と同じく、前のバッチの時間から遅れの予算 (25 µs) に収まる枠の数で決めます。
持ち主の送りのバッチも、今の送りの相の規則 (遅れの予算と枠の数) を持ち主ごとに使います。
バッチを満たすために待つことはしません。

### 起こし方

- 各 shard は眠る前に眠りの印を立て、fence の後に輪を見直してから眠ります。
  書き手は公開と fence の後に印を見て、眠っている時だけ起こします
- shard 0 は持ち主ごとに、自分の起床の終わりに 1 回だけ起こします
- Linux では eventfd を shard の poller に入れ、ほかの OS では実行環境の waker を使います

### busy polling と event 駆動

event 駆動だけを使います。
眠る前に回り続ける形は、中くらいの負荷の byte あたりの CPU と VM の出入りを増やすので採りません。
#808 では、手伝いを 50 µs 回すと byte あたりの CPU が 2.48 倍になりました (測定)。

### CPU の固定、NUMA、SMT

- 固定:製品は shard を CPU に固定しません。
  コンテナと cgroup で利用できる CPU が変わり、固定の設定を持たない規則のためです
- 測定:ラボは置き方を固定して流し、固定しない実行も加えます([測る値](verification.md#測る値))
- NUMA:1 つの node を前提にします。
  複数の node のホストは未確認です
- SMT:N は論理の CPU の数で数えます。
  物理の core で数える方が良いかは測って決めます (未確認)

### 満ちた queue の扱い

- 持ち主ごとのデータの輪は、持ち主が押さえる平文の block の数で抑えます([持ち主ごとの block の上限](memory.md#持ち主ごとの-block-の上限))。
  上限に達した持ち主の TCP の segment を捨て、shard 0 の読みは止めません
- 捨てる segment は経路での損失と同じ扱いで、送り手が SACK と RACK で回復します
- 持ち主ごとのデータの輪は wgft が順を決められる平文の queue なので、取り出す時に CoDel (RFC 8289) を当てる形を後で比べます

## UDP を先にして TCP を飢えさせない規則

- shard 0 のバッチの中:UDP の datagram を同じバッチの TCP の segment より先に処理する今の規則を保ちます
- shard 0 の出力:4 つの組の byte の deficit round robin を保ちます。
  UDP の組は自分の quantum を超えて続けて送れないので、TCP の組は毎回の巡りで自分の分を得ます
- 遅れの予算:1 回の起床の仕事を 50 µs で区切る今の規則を、各 shard に当てます
- 遅れに敏感な UDP:直近の窓 (仮の値は 1 秒) の byte の速さが閾値 (仮の値は 2 Mbit/s) より小さい UDP のセッションを、遅れに敏感な UDP とします。
  大きな量の UDP は数えません
- 送りの上限:遅れに敏感な UDP のセッションがある間、持ち主の 1 回の `sendmmsg` の byte を B / (N-1) に抑えます。
  B は Inline の 1 回の送りのバッチの最大の byte (64 枠 × MTU) です。
  UDP の datagram の前に並ぶ TCP の byte が、Inline と同じ量を超えないようにするためです(設計判断)。
  N = 8、MTU 1,420 で 1 回あたり約 13 KB で、GSO の 9 segment ほどです(計算)
- 上限の費用:1 回の呼び出しにまとまる datagram が減るので、送る向きの byte あたりの CPU が増えます。
  増え方は測定の項目です。
  shard ごとに別の外側のソケットを持つ形も、試作で比べる候補です
- 飢えの防止:TCP は持ち主の shard で送るので、UDP の量によらず送る機会があります

## flow の公平とワーカーの公平

経路が詰まりの時 (家の回線など) は、どの shard も詰まっていないので、flow の間の配分は TCP の輻輳制御が決め、shard の分け方は公平に効きません(推定)。

shard の CPU が詰まりの時は、shard ごとの CPU が flow に分けられるので、次の場合に flow の公平が崩れます。

- 持ち主ごとの flow の数の偏り:2 本を持つ shard と 1 本を持つ shard が並ぶと、2 本の側の flow は半分の CPU しか得ません。
  速さの比が 0.5、0.5、1 の 3 本の Jain の指数は 0.89 です(計算)
- 静かな接続の数え方:接続の数で選ぶので、静かな長い接続が多い shard に大きな flow が集まることがあります
- 持ち主ごとの block の上限での捨て:上限に達した持ち主の flow だけが損失を受けます

採らない手当ては、shard をまたぐ全体の deficit round robin (packet ごとの同期が要ります) と、動いている接続の移し (昇格の問題を持ち込みます) です。
受け入れの線は、経路が詰まりの時と CPU が詰まりの時で分けます([受け入れの条件](verification.md#受け入れの条件))。

## 後の段

次の形は基本の設計に含めず、試作で必要を測った時だけ加えます。

| 形 | 加える条件 | 要る仕組み |
|---|---|---|
| 受信の暗号の手伝い | 受信の積み残し (下の定義) が続き、shard 0 が受ける多くの stream の上限になると測った時 | 塊の番号の順の確定、期限を過ぎた塊の取り戻し |
| 1 本の flow の送りの手伝い | 持ち主が窓の間 0.9 以上忙しく、その byte の 8 割以上が 1 本の flow で、ほかの shard に空きがある時 | 持ち主の順の暗号化と送り出しの板 |
| UDP のセッションを持ち主へ | 大きな量の UDP が shard 0 を詰まらせると測った時 | 接続した UDP の 4 つ組を表の鍵にし、セッションを作成の時に置きます |
| 昇格 | N が 2 以上の中くらいの負荷の byte あたりの CPU が線を超えた時 | [代わりの形として残す昇格](architecture.md#代わりの形として残す昇格)の要るもの |

受信の積み残しは、shard 0 が遅れの予算を使い切った後にも外側のソケットにデータが残る起床が、窓 (仮の値は 100 ms) の中で続く状態です。
1 回のバッチでは判定しません。
#808 では、25 µs の予算の受信の回 (12 から 16 datagram) に手伝いを入れても速さが変わらず、byte あたりの CPU が 27% 増えました (測定)。
このため受信の暗号の手伝いは、積み残しが続く時だけ動かし、軽い負荷では動かしません。

受信の暗号の手伝いの塊は、取り戻せる形にします。

- 期限:手伝いが引き取った塊が、塊の暗号の時間の数倍 (仮の値は 50 µs) を過ぎても終わらなければ、shard 0 が同じ塊を自分で復号します
- 冪等:確定 (`commit_decapsulate`) の前の復号は状態を変えないので、同じ塊を 2 回復号しても正しさは崩れません。
  遅れて終わった手伝いの結果は、世代の違いで捨てます
- UDP:UDP の datagram は復号するまで見分けられないので、止まった塊を飛ばして UDP だけを先に渡す形は作れません。
  止まった塊の UDP の待ちは期限で抑えます

## 10 Gbit/s を決める上限

10 Gbit/s に届くかは未確認です。
同じラボのカーネルモードの最大が 9,083 Mbit/s (測定、未公開の記録) なので、ラボの経路そのものが 10 Gbit/s の手前で上限になりえます。

| 上限 | 測定での見え方 |
|---|---|
| 1 つの flow の持ち主のスレッド | 持ち主のスレッドの実行の割合が 1.0 に近く、ほかの shard に空きがある |
| shard 0 | shard 0 の実行の割合が 1.0 に近い |
| カーネルの外側の 1 つの流れの受信の処理 | agent の VM の 1 つの vCPU の受信の処理の時間が 1.0 に近い |
| 外側のソケットへの並んだ送り出し | `sendmmsg` 1 回の時間が N とともに伸びる (計測器つきの build) |
| CPU の総量 | agent の VM の忙しさが vCPU の数に近い |
| 相手の VM と経路 | ラボが相手の VM の詰まりを `peer_bound` として記録する。カーネルモードの腕も同じ速さで止まる |
| メモリの帯域 | 上のどれにも当たらずに、byte あたりの CPU が速さとともに伸びる |

外側の 1 つの流れの受信の処理が上限だと分かった時は、複数のセッションか複数の queue の link を比べ直します([構成の比較](architecture.md#f-複数のセッションへの分割))。
