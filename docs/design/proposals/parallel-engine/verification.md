# 検証の計画 (N6)

この文書は、推奨の構成 S の段階の試作、測定の計画、正しさの試験、数値の受け入れの条件を定めます。
未採用の提案です([提案の索引](README.md))。
受け入れの条件の数値は所有者に決めてもらう案で、LGTM の前は確定しません。

## 原則

- 1 コアの後退を隠さない:複数のコアの速さを示す表には、同じ表に N = 1 の行と byte あたりの CPU と UDP の遅れを必ず並べます
- UDP の遅れを TCP の速さと引き換えにしない:UDP の線を満たさない build は、速さが上がっても受け入れません
- S が Inline と違う所で測る:Inline と同じ経路になる負荷だけでなく、最大の負荷、shard 0 が詰まる前後、CPU の取り合い、接続の入れ替わりで測ります
- A+ を基準にしない:A+ (#808 から #810) は研究の比べの腕で、受け入れの基準は今の Inline です
- 段ごとに分けて測る:受信と送信の段を最初から分けて数える計測器を使います
- 使い捨ての試作はリポジトリに入れず、測定の詳細は PR に書きます

## 段階の試作

試作は、WireGuard の無い sans-IO から始め、暗号、本物の I/O、分けたラボの順に進めます。
各段の関門を満たしてから次の段に進みます。

### P0 WireGuard の無い sans-IO の engine

- 中身:ライブラリの直接の呼び出しの link と何もしない変換で engine を作り、合成の TCP と UDP の流れを流します。
  比べの相手は今の核のままの N = 1 です
- 作るもの:shard 0 の入口の判定、持ち主の選び方と渡す確立、TIME_WAIT の行の返却、輪、shard ごとのタイマーの輪と出力、全体の予算と credit
- 測るもの:N = 1 と今の核の byte あたりの CPU、持ち主に置いた接続の packet あたりの振り分けの費用、中くらいの負荷の起床の数と CPU、接続の作成の速さ
- 関門:N = 1 で今の核と出力が bit で一致すること。
  中くらいの負荷の byte あたりの CPU の見積もりが線の内か、線を超えるなら代わりの形の昇格と比べる材料が揃うこと

### P1 WireGuard の変換

- 中身:shard 0 の受信の 1 回の呼び出しと、counter の貸し出しを作ります
- 測るもの:貸し出しの費用、在庫の大きさと replay の窓への距離、暗号化し直しの回数、cache の miss
- 場所:ホストの道具 (`crates/wgft-agent-perf` と `scripts/agent-perf-stat.sh`) を shard の数を変えられる形に広げます。
  ラボの VM は PMU を仮想化しないので、cache の miss はホストで数えます([判定の手順](../../v2/agent-throughput.md#判定の手順)の道具の説明)
- 関門:N = 1 の経路が Inline と同じ費用で、貸し出しの shard 0 の費用が packet あたり 100 ns 以下であること

### P2 本物の I/O

- 中身:平らな UDP の link と WireGuard の UDP の link を、Incus の VM の network namespace の中の本物のソケットで動かします。
  ホストと Docker では測りません([テストの規範](../../../development/testing.md))
- 測るもの:外側のソケットへの並んだ送り出しの system call の時間、カーネルの受信の処理の vCPU ごとの時間、送りの上限の効果と費用、UDP の往復の遅れ
- 関門:UDP の往復の遅れが Inline の線の内であること

### P3 分けたラボ

- 中身:agent の build を S にして、分けたラボで Inline、A+、カーネルモードと比べます([測る値](#測る値))
- 関門:[受け入れの条件](#受け入れの条件)のすべてを満たすこと

後の段 ([後の段](performance.md#後の段)) の試作は、P3 で加える条件を満たした時だけ行います。
製品への実装は、P3 の結果と所有者の LGTM の後に始めます。

| 軸 | 値 |

| 向き | agent が送る向きと受ける向きの両方 |
| 負荷 | 何もしない時、Inline の最大の速さの 0.25 倍、0.5 倍、0.9 倍、1.0 倍、1.2 倍の固定の速さ、速さを制限しない最大の負荷 |
| UDP | 固定の間隔の UDP の ping を、どの負荷にも重ねます |

固定の速さの 1.0 倍と 1.2 倍は、Inline では詰まる負荷で、S では shard 0 の受信と持ち主の分担が効き始める所です。
ラボは、分けたラボの置き方を shard の数に合わせて広げる変更が要ります。
今の `--placement apart-mt` は暗号の worker 2 本の build 用です([agent を専用の VM に置く](../../../../lab/README.md#agent-を専用の-vm-に置く---split))。

|---|---|
| 速さ | 両方の向きの Mbit/s |

## 正しさの試験

### N = 1 の金の比べ

- N = 1 の engine の出力を、今の核の出力と bit で比べます。
  凍結した Go の記録との bit の一致の試験 ([Go の wgstack の記録との bit の一致](../../v2/wgstack-rs.md#go-の-wgstack-の記録との-bit-の一致)) をそのまま N = 1 に当てます
- TCP の適合の試験の台本 (Linux を参照にした台本) を N = 1 で流します

### 持ち主に渡す確立と TIME_WAIT の返却

- 適合の試験の台本を N = 4 で流し、N = 1 と同じ期待で通します
- 渡す時の競合の台本:SYN の再送、最後の ACK の再送、データを運ぶ最後の ACK、最後の ACK の直後のデータ、渡す前後の RST を、渡す点の前と後に置きます
- TIME_WAIT の返却の台本:返却の知らせの前後に FIN の再送と RST と新しい SYN を置きます。
  枠の中の TIME_WAIT への SYN を持ち主が捨てる違いは、期待した差として書きます
- 順の性質:試験の build で、shard 0 が datagram に読んだ順の番号を付け、持ち主が各 flow の番号が増えることを確かめます。
  送る向きは、各 flow の外側の送り出しの順が、持ち主の作った順と同じことを確かめます

### 決定的な交互の実行

- 試験の実行器は、すべての shard の 1 歩を 1 つのスレッドで種に従って交互に進め、輪、渡す確立、返却、貸し出しの任意の交互の順を作ります
- 確かめる不変条件:flow の中の順、各接続の持ち主が常に 1 つであること、shard 0 の表の項と持ち主の枠の一致、予算の和の不変条件、制御の輪と返却の輪の知らせを失わないこと、持ち主ごとの block の数が上限を超えないこと
- fuzz:今の `FuzzCore` に、shard の交互の順の種、渡す点の位置、返却の位置を操作として加えます。
  量は実行の回数で決めます

### メモリの順の模型

輪、眠りの印と起床の手順、最新の counter の公開を、loom などの模型の検査で、すべての交互の順について確かめます。
模型の検査の道具は試験だけの依存で、製品の build に入りません。

### 相互運用

server の相手 (カーネルの WireGuard、wireguard-go) を相手に、counter を shard の間で貸し出した時に、相手の窓 (8,128) の内で replay の拒否が起きないことを確かめます。

## メモリの試験

- 確保の数え:各 shard のスレッドで、定常の状態の packet あたりの確保が 0 であることを、今の `wgft-alloc-count` の試験の形で確かめます
- 上界と保持:敵対的な保持の試験 ([上界と敵対的な保持の試験](../../v2/wgstack-rs.md#上界と敵対的な保持の試験)) を N = 8 で流し、確保の最大が上界の式の値を超えないことを確かめます
- 遅い持ち主:1 つの持ち主を止めた時に、shard 0 の読みと UDP と別の持ち主の接続が続き、止めた持ち主の接続だけが捨てられることを確かめます
- 回復:入力を止めた後に、平文の block、送信の枠、credit が置き場に戻ることを確かめます
- 上界の表:今と同じく試験が上界の表を生成し、N = 1、2、4、8 の列を持たせます
- RSS:ラボで、RSS が上界と決めた余裕の和以下であることを N ごとに確かめます

## 受け入れの条件

数値は所有者に決めてもらう案です。
比は S / Inline で、ラボの組の推定と 95% の区間で判定します。
区間の扱いと流し直しの規則は、今の[判定の手順](../../v2/agent-throughput.md#判定の手順)に従います。

### N = 1 の同等

| 値 | 線 |
|---|---|
| 出力 | 今の核と bit で一致します |
| byte あたりの CPU (両方の向き、1 と 4 stream) | 推定が 1.02 以下で、`ci95_low` が 1.00 以下 |
| 速さ | 推定が 0.98 以上 |
| UDP の p50、p99、jitter | 推定が 1.10 以下で、`ci95_low` が 1.00 以下 |
| メモリの上界 | 増分 0 |

### UDP の遅れ (すべての N)

- 線:p99 と jitter の推定が 1.10 以下で、`ci95_low` が 1.00 以下です (今の非劣性の線)。
  p50 も同じ線にします
- 当てる負荷:何もしない時、0.25 倍、0.5 倍、0.9 倍、1.0 倍、1.2 倍の固定の速さ、速さを制限しない最大の負荷を、両方の向きで測ります
- CPU の取り合い:`--agent-load` で agent の VM の CPU の 1 つに負荷を置いた時も、同じ線を当てます
- 損失:Inline の損失に送った数の 0.1% を加えた数以下です

### 中くらいの負荷の byte あたりの CPU (N が 2 以上)

- 0.25 倍と 0.5 倍の固定の速さで、agent の VM の比の推定を線と比べます。
  VM の外の qemu の CPU も記録します
- 線の案は 1.10 です。
  模型の見積もりは 1.15 から 1.75 倍で、線を超える恐れが高い項目です([N が 2 以上の軽い負荷](performance.md#n-が-2-以上の軽い負荷))
- 線を超えた時は、代わりの形の昇格を比べ直します

### 最大の負荷の速さ (RTT 0)

| vCPU | 線 |
|---|---|
| 2 | すべての組で 1.00 以上。N = 2 を使うのは、どれかの組で 1.10 以上の時だけです |
| 4 | 送る 4 stream と 16 stream 1.50 以上、受ける 4 stream と 16 stream 1.30 以上、受ける 1 stream 1.25 以上、送る 1 stream 1.00 以上 |
| 8 | 送る 16 stream 1.70 以上、受ける 16 stream 1.30 以上、受ける 1 stream 1.25 以上、送る 1 stream 1.00 以上 |

- 受ける向きの線は、shard 0 の読みと復号の直列の上限を見込んだ値です([役ごとの費用の模型](performance.md#役ごとの費用の模型))
- 送る 1 stream は基本の設計では伸びないので、後退しないことだけを求めます
- 外の上限:組が agent の外で上限になる時 (ラボが `peer_bound` と記録した時か、カーネルモードの腕が同じ速さで止まる時) は、その上限の 0.95 倍以上で満たしたとします。
  この扱いをした組は、報告で分けて示します
- byte あたりの CPU:最大の負荷の agent の VM の比の推定が 1.15 以下です

### 接続の入れ替わり

- 1 秒あたりの接続の数の比の推定が 1.00 以上です
- 接続あたりの CPU の比の推定が 1.10 以下です

### 立ち上がり

- 16 本の stream を同時に始めて、定常の速さの 90% に届くまでの時間が Inline の 1.10 倍以内です

### CPU の取り合い

- `--agent-load` で agent の VM の CPU の 1 つに負荷を置いた時、速さの比が負荷の無い時の比の 0.9 倍以上で、UDP の線を満たします

### 長い RTT

- RTT 4 と 20 ms、ボトルネック 2,000 Mbit/s で、速さの比の推定が 0.98 以上、byte あたりの CPU の比は中くらいの負荷の線と同じです

### 公平

- 経路が詰まりの時:等しい 4 本と 16 本の flow の Jain の指数が 0.95 以上です
- CPU が詰まりの時 (最大の負荷):Jain の指数が 0.85 以上です。
  shard ごとの flow の数を記録します

### 損失と順

- 0.5 倍以下の固定の速さで、engine の中で捨てた数が 0 です
- 最大の負荷で、相手の再送の数と D-SACK の数の比の推定が 1.10 以下です
- CPU の取り合いの時も含めて、相手の replay の拒否が見える相手で 0 です

### TCP の遅れ

- 通信量の少ない stream の p99 が、qbench と分けたラボで Inline の 1.10 倍以内で、[wgstack の性能の段階](../../userspace/wgstack-performance.md#目標と制約)の目標を満たし続けます

### 敵対的な入力

- N = 8 で、敵対的な保持の試験の確保の最大が上界の式の値を超えず、入力が止まった後に戻ります
- N = 8 で、1 つの持ち主に向けた洪水が、shard 0 の UDP の線とほかの持ち主の接続の速さを崩しません

### メモリ

- N = 1:上界の増分が 0 です
- N = 8:上界の増分が実行環境の分を含めて 16 MiB 以内です
- すべての N:RSS が上界と決めた余裕の和以下で、shard のスレッドの packet あたりの確保が 0 です

## 報告の規則

- 結果の表は、N = 1 の行、byte あたりの CPU、UDP の p50 と p99 と jitter を、速さと同じ表に並べます
- 受け入れの条件の 1 つでも満たさない組があれば、ほかの組の速さの向上と分けずに示します
- 外の上限で判定した組は、そう判定したことを表に書きます
- A+ の値は研究の比べとして別の列に置き、受け入れの判定に使いません
- 測った条件 (build、置き方、round の数、除いた実行) を表ごとに書きます
