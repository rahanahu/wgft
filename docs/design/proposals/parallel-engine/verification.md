# 検証の計画 (N6)

この文書は、推奨の構成 S の段階の試作、測定の計画、正しさの試験、数値の受け入れの条件を定めます。
未採用の提案です([提案の索引](README.md))。
受け入れの条件の数値は所有者に決めてもらう案で、LGTM の前は確定しません。

## 原則

- 1 コアの後退を隠さない:複数のコアの速さを示す表には、同じ表に N = 1 の行と byte あたりの CPU と UDP の遅れを必ず並べます
- UDP の遅れを TCP の速さと引き換えにしない:UDP の線を満たさない build は、速さが上がっても受け入れません
- A+ を基準にしない:A+ (#808 から #810) は研究の比べの腕で、受け入れの基準は今の Inline です
- 段ごとに分けて測る:受信と送信の段を最初から分けて数える計測器を使います。
  A+ は段を分けずに数えたので、UDP の遅れの原因を受信と送信で切り分けられませんでした
- 使い捨ての試作はリポジトリに入れず、測定の詳細は PR に書きます

## 段階の試作

試作は、WireGuard の無い sans-IO から始め、暗号、本物の I/O、分けたラボの順に進めます。
各段の関門を満たしてから次の段に進みます。

### P0 WireGuard の無い sans-IO の engine

- 中身:ライブラリの直接の呼び出しの link と何もしない変換で、engine を 2 つ向かい合わせにつなぎ、合成の TCP と UDP の流れを流します。
  片方は今の核のままの N = 1 で、比べの相手にします
- 作るもの:shard 0 の入口の判定、昇格と返却、受け口の queue と制御の知らせの輪、shard ごとのタイマーの輪と出力、全体の予算と credit
- 測るもの:N = 1 と今の核の byte あたりの CPU、昇格した接続の packet あたりの振り分けと受け渡しの費用、昇格の手順の時間、shard ごとの CPU
- 関門:N = 1 で今の核と出力が bit で一致すること。
  振り分けの費用が packet あたり 50 ns 以下で、詰まった時に shard の数に応じて速さが伸びること

### P1 暗号の分担

- 中身:WireGuard の変換を sanstun の分けた API で作り、申し出の板と順序つきの完了と送りの板を加えます
- 測るもの:塊の大きさごとの損得の境、引き取りの費用、セッションの錠の待ち、小さな packet の経路の遅れ (申し出をしない時に Inline と同じか)、cache の miss
- 場所:ホストの道具 (`crates/wgft-agent-perf` と `scripts/agent-perf-stat.sh`) を shard の数を変えられる形に広げます。
  ラボの VM は PMU を仮想化しないので、cache の miss はホストで数えます([判定の手順](../../v2/agent-throughput.md#判定の手順)の道具の説明)
- 関門:申し出をしない経路が Inline と同じ費用であること。
  塊の大きさの損得の境が決まり、4 本の shard で暗号の速さが 3 倍以上になること

### P2 本物の I/O

- 中身:平らな UDP の link と WireGuard の UDP の link を、Incus の VM の network namespace の中の本物のソケットで動かします。
  ホストと Docker では測りません([テストの規範](../../../development/testing.md))
- 測るもの:外側のソケットへの並んだ送り出しの system call の時間、カーネルの受信の処理の vCPU ごとの時間、UDP の往復の遅れ、平文の置き場が尽きた回数
- 関門:UDP の往復の遅れが Inline の線の内であること。
  並んだ送り出しで system call の時間が伸びる大きさが分かること

### P3 分けたラボ

- 中身:agent の build を S にして、分けたラボで Inline、A+、カーネルモードと比べます([測る値](#測る値))
- 関門:[受け入れの条件](#受け入れの条件)のすべてを満たすこと

製品への実装は、P3 の結果と所有者の LGTM の後に始めます。

### 測定の行列

| 軸 | 値 |

| agent の VM の vCPU | 1、2、4、8 |
| TCP の stream の数 | 1、4、多く (16) |
| RTT | 0、4、20 ms。RTT のある経路はボトルネックの速さを置きます |
| 向き | agent が送る向きと受ける向きの両方 |
| 負荷 | 最大、固定 (Inline の最大の 0.25 倍と 0.5 倍)、何もしない時 |
| UDP | 固定の間隔の UDP の ping を、どの負荷にも重ねます |
| 置き方 | 固定 (shard の数に合わせた置き方) と固定しない形 |
| CPU の取り合い | agent の VM の CPU に別の負荷を置く形 (`--agent-load`) |
| 接続の入れ替わり | 短い接続を速く張って閉じる負荷 |

ラボは、分けたラボの置き方を shard の数に合わせて広げる変更が要ります。
今の `--placement apart-mt` は暗号の worker 2 本の build 用です([agent を専用の VM に置く](../../../../lab/README.md#agent-を専用の-vm-に置く---split))。

### 値

| 値 | 取り方 |
|---|---|
| 速さ | 両方の向きの Mbit/s |
| byte あたりの CPU | agent の VM、2 台の VM の和、VM の外の qemu の CPU。A+ は VM の外の qemu の CPU が 1.05 から 1.16 倍に増えたので、VM の出入りも見ます |
| UDP の遅れ | p50、p99、jitter、損失 |
| 公平 | 等しい flow の速さの Jain の指数と、shard ごとの flow の数 |
| スレッドの CPU | shard ごとの実行、CPU を待った時間、眠った時間の割合 |
| 待ち | shard 0 が先頭の塊を待った時間、手伝いの起床から始まりまで、終わりから気付くまで (受信と送信を分けます) |
| 同期の費用 | 塊あたりの CAS、セッションの錠の待ちの分布、起床の system call の数 |
| queue の深さ | 受け口の queue と申し出の板の深さの分布 |
| 損失と再送 | engine の中で捨てた数、相手の再送と D-SACK の数、相手の replay の拒否 (見える場合) |

| メモリ | 起動の時の上界と確保、起動の直後と転送中の最大の RSS |

段ごとの時間と queue の深さは、ラボの計測の feature を付けた build だけが数え、製品の build には入れません。

## 正しさの試験

### N = 1 の金の比べ

- N = 1 の engine の出力を、今の核の出力と bit で比べます。
  凍結した Go の記録との bit の一致の試験 ([Go の wgstack の記録との bit の一致](../../v2/wgstack-rs.md#go-の-wgstack-の記録との-bit-の一致)) をそのまま N = 1 に当てます
- TCP の適合の試験の台本 (Linux を参照にした台本) を N = 1 で流します

### TCP の状態機械と flow の中の順

- 強制の昇格:試験の build だけの口で、接続の任意の点 (確立の直後、損失の回復の途中、窓 0 の probe の途中、FIN の前後) で昇格を起こし、TCP の適合の試験の台本を同じ期待で流します
- 昇格の前後の比べ:同じ入力の列で、昇格を起こした実行と起こさない実行の、その接続が出す segment の列を比べます。
  タイマーの時機のずれだけを許す比べにします
- 順の性質:試験の build で、shard 0 が datagram に読んだ順の番号を付け、持ち主が各 flow の番号が増えることを確かめます。
  送る向きは、各 flow の segment の外側の送り出しの順が、持ち主の作った順と同じことを確かめます
- counter の窓:送りの板の暗号化し直しの規則が、線を超えた時に働くことを確かめます

### 決定的な交互の実行

- 試験の実行器は、すべての shard の 1 歩を 1 つのスレッドで種に従って交互に進め、queue、申し出の板、昇格、返却の任意の交互の順を作ります
- 確かめる不変条件:flow の中の順、各枠の持ち主が常に 1 つであること、予算の和の不変条件、制御の知らせと昇格の知らせを失わないこと、shard 0 の昇格した印と shard k の枠の一致
- fuzz:今の `FuzzCore` に、昇格、返却、shard の交互の順の種を操作として加えます。
  量は実行の回数で決めます

### メモリの順の模型

- 輪、申し出の板、送りの板、眠りの印と起床の手順を、loom などの模型の検査で、すべての交互の順について確かめます。
  模型の検査の道具は試験だけの依存で、製品の build に入りません

### 相互運用

- server の 3 つの相手 (カーネルの WireGuard、wireguard-go、sanstun を使う wgft) を相手に、shard の間で counter を交互に予約した時に replay の拒否が起きないことを確かめます。
  相手の窓の幅を確かめ、暗号化し直しの線を決めます

## メモリの試験

- 確保の数え:各 shard のスレッドで、定常の状態の packet あたりの確保が 0 であることを、今の `wgft-alloc-count` の試験の形で確かめます
- 上界と保持:敵対的な保持の試験 ([上界と敵対的な保持の試験](../../v2/wgstack-rs.md#上界と敵対的な保持の試験)) を、昇格した接続を含む形に広げ、確保の最大が上界の式の値を超えないことを確かめます
- 回復:入力を止めた後に、平文の block、送信の枠、credit が置き場に戻ることを確かめます
- 上界の表:今と同じく試験が上界の表を生成し、N = 1、2、4、8 の列を持たせます
- RSS:ラボで、RSS が上界と決めた余裕の和以下であることを、N ごとに確かめます

## 受け入れの条件

数値は所有者に決めてもらう案です。
比は S / Inline で、ラボの組の推定と 95% の区間で判定します。
区間の扱いと流し直しの規則は、今の[判定の手順](../../v2/agent-throughput.md#判定の手順)に従います。

### N = 1 の同等

| 値 | 線 |
|---|---|
| 出力 | 今の核と bit で一致します |
| byte あたりの CPU (両方の向き、1 と 4 stream) | 推定が 1.02 以下で、`ci95_low` が 1.00 以下 |
| 速さ | 推定が 0.98 以上 |
| UDP の p99 と jitter (何もしない時と負荷の時) | 推定が 1.10 以下で、`ci95_low` が 1.00 以下 (今の非劣性の線) |
| UDP の p50 | 同じ線 |
| メモリの上界 | 増分 0 |

### UDP の遅れ (すべての N)

- p99 と jitter:推定が 1.10 以下で、`ci95_low` が 1.00 以下です。
  何もしない時、0.25 倍と 0.5 倍の固定の負荷、送る向きの頭打ちにしない負荷の、両方の向きで満たします
- p50:同じ線です。
  A+ が送る向きの 0.25 倍の負荷で 2.3 から 2.9 倍に悪くした値なので、この線を加えます
- 損失:Inline の損失に送った数の 0.1% を加えた数以下です

### 中くらいの負荷の byte あたりの CPU (N が 2 以上)

- 0.25 倍と 0.5 倍の固定の負荷で、agent の VM の比の推定が 1.03 以下で、`ci95_low` が 1.00 以下です。
  詰まっていない時の S は Inline と同じ経路なので、ほぼ同等を求めます
- VM の外の qemu の CPU の比の推定が 1.05 以下です

### 最大の負荷の速さ (RTT 0)

| vCPU | 線 |
|---|---|
| 2 | すべての組で 1.00 以上。N = 2 を使うのは、どれかの組で 1.10 以上の時だけで、そうでなければ 2 CPU の N を 1 にします |
| 4 | 送る 1 stream 1.45 以上、送る 4 stream 1.60 以上、受ける 4 stream 1.45 以上、受ける 1 stream 1.00 以上 |
| 8 | 送る 1 stream 1.45 以上、送る 4 stream と受ける 4 stream と多くの stream 1.70 以上 |

- 外の上限:組が agent の外で上限になる時 (ラボが `peer_bound` と記録した時か、カーネルモードの腕が同じ速さで止まる時) は、その上限の 0.95 倍以上で満たしたとします
- byte あたりの CPU:最大の負荷の agent の VM の比の推定が 1.10 以下です。
  A+ の受ける 1 stream (1.14 から 1.17 倍) の悪化を受け入れません

### 長い RTT

- RTT 4 と 20 ms、ボトルネック 2,000 Mbit/s で、速さの比の推定が 0.98 以上、byte あたりの CPU の比の推定が 1.03 以下です

### 公平

- 経路が詰まりの時:等しい 4 本と 16 本の flow の Jain の指数が 0.95 以上です
- CPU が詰まりの時 (最大の負荷):Jain の指数が 0.90 以上です。
  shard ごとの flow の数を記録します

### 損失と順

- 固定の負荷で、engine の中で捨てた数が 0 です
- 最大の負荷で、相手の再送の数と D-SACK の数の比の推定が 1.10 以下です。
  順の乱れが相手の不要な再送を増やしていないことを、この値で見ます
- 相手の replay の拒否が、見える相手で 0 です

### TCP の遅れ

- 通信量の少ない stream の p99 が、qbench と分けたラボで Inline の 1.10 倍以内で、[wgstack の性能の段階](../../userspace/wgstack-performance.md#目標と制約)の目標を満たし続けます

### メモリ

- N = 1:上界の増分が 0 です
- N = 8:上界の増分が 12 MiB 以内です
- すべての N:RSS が上界と決めた余裕の和以下で、shard のスレッドの packet あたりの確保が 0 です

## 報告の規則

- 結果の表は、N = 1 の行、byte あたりの CPU、UDP の p50 と p99 と jitter を、速さと同じ表に並べます
- 受け入れの条件の 1 つでも満たさない組があれば、ほかの組の速さの向上と分けずに示します
- A+ の値は研究の比べとして別の列に置き、受け入れの判定に使いません
- 測った条件 (build、置き方、round の数、除いた実行) を表ごとに書きます
