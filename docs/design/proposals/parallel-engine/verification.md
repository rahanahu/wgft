# 検証の計画 (N6)

この文書は、推奨の構成 U の段階の試作、未決の項目、測定の計画、正しさの試験、数値の受け入れの条件を定めます。
未採用の提案です([提案の索引](README.md))。
受け入れの条件の数値は所有者に決めてもらう案で、LGTM の前は確定しません。

## 原則

- 1 コアの後退を隠さない:複数のコアの速さの表には、同じ表に利用できる CPU が 1 つの行と、byte あたりの CPU と UDP の遅れを並べます
- 軽い負荷を先に確かめる:軽い負荷と中くらいの負荷の後退を、P0 と P2 の関門で確かめます
- UDP の遅れを TCP の速さと引き換えにしない:UDP の線を満たさない build は、速さが上がっても受け入れません
- 確かめられないものを合格にしない:本物の I/O で比べられない組は「未検証」と報告し、合格に数えません
- 選びと判定を分ける:値の選び (helper の数、積み残しの値) は、判定に使う実行とは別の実行で決めます
- A+ (#808 から #810) は研究の比べの腕で、受け入れの基準は今の Inline です
- 使い捨ての試作はリポジトリに入れず、測定の詳細は PR に書きます

## 段階の試作

### P0 WireGuard の無い engine と本物の LAN の側のソケット

- 中身:何もしない変換と、ライブラリの直接の呼び出しの link で front と unit と helper を作ります。
  中継は tokio を使わない executor の上の状態機械で作り、LAN の側は本物のソケットを使います
- 測るもの:今の tokio の Inline と比べた、1 つの CPU の時と積み残しの無い時の packet あたりの CPU と往復の遅れ、積み残しの出入り、受け渡しの費用、unit と helper ごとのメモリ
- 関門:利用できる CPU が 1 つの時に、核の出力が今の核と bit で一致し、データプレーンの byte あたりの CPU と遅れが Inline と同じであること。
  積み残しの無い時の packet あたりの CPU が Inline の 1.05 倍以下であること。
  続く最大の負荷で積み残しの出入りが 1 秒に 1 回以下であること

### P1 WireGuard の変換

- 中身:front の受信と送信の 1 回の呼び出しと、helper の counter の在庫を作ります
- 測るもの:在庫の補充の費用と起床の数、捨てた在庫の数、cache の miss (ラボの VM は PMU を仮想化しないので、`crates/wgft-agent-perf` と `scripts/agent-perf-stat.sh` を広げてホストで数えます)
- 受ける向き:暗号の付いた合成の送り手で front と unit の 2 段を測ります。
  この値は診断で、受け入れの判定には使いません
- 関門:在庫の補充の front の費用が packet あたり 100 ns 以下であること

### P2 本物の I/O

- 中身:WireGuard の UDP の link を、Incus の VM の network namespace の中の本物のソケットで動かします([テストの規範](../../../development/testing.md))
- 選び:helper の数 H = n_cpu - 1 と n_cpu - 2 を、判定とは別の選びの実行で比べて決めます
- 関門:軽い負荷と中くらいの負荷の対話の往復と UDP の遅れが Inline の線の内であること。
  最大の負荷に CPU の取り合い (`--agent-load`) を重ねても UDP の線の内であること。
  続く最大の負荷で積み残しの出入りが 1 秒に 1 回以下であること

### P3 分けたラボ

- 中身:agent の build を U にして、分けたラボで Inline、A+、カーネルモードと比べます
- 関門:[受け入れの条件](#受け入れの条件)のすべてを満たすこと

### PW Windows と macOS

- 中身:全 OS で 1 つのデータプレーンにする場合、Windows 11 と macOS の実機で、front だけの executor を今の tokio のデータプレーンと比べます
- 関門:1 つの CPU の byte あたりの CPU と UDP の遅れが今の tokio のデータプレーンの線の内で、今の結合の試験と相互運用の試験が通ること。
  この関門を通るまで、Windows と macOS は今の tokio のデータプレーンのままにします

製品への実装は、P3 (と、1 つのデータプレーンにする場合は PW) の結果と所有者の LGTM の後に始めます。

## 未決の項目

骨格の設計で決めず、試作で決める項目です。
各項目は決める段と、決めるための試験を持ちます。

| 項目 | 今の候補 | 段 | 決める試験 |
|---|---|---|---|
| 積み残しの値 (8 回、10%、0.6 CPU、100 ms) と忙しさの割合 | [積み残し](ownership.md#積み残し)の規則。忙しさは仕事が待っていた時間で数えます | P0、P2 | 続く最大の負荷 (両方の向き、`--agent-load` の有無、大きな flow を試験の build で unit 0 に置いた形) で出入りが 1 秒に 1 回以下。5 ms 送って 50 から 150 ms 休む山の繰り返し |
| 渡す unit の選び | front の時間の 10% 以上を使う unit だけを渡します | P2 | UDP で front を詰まらせながら対話の TCP を流し、往復の遅れが 1.10 倍以内 |
| 受け渡しの順 | 古い実行者が unit の datagram を送り終えてから渡します | P0 | 外側のソケットが満ちて datagram が残る時に受け渡しを起こし、flow の中の送り出しの順を確かめる決定的な交互の実行 |
| 止まった helper からの取り戻し | helper が unit の 1 回の実行の始めと終わりに実行中の印を CAS で立てて下ろし、front は止まりを見つけた時に印が下りた unit を CAS 1 回で取り戻します。回収の印を立てたら実行者を起こし、上の線を超える credit も返させます | P0 | helper を止める試験と、nice 0 の CPU の負荷で helper を飢えさせる試験で、止まった unit の接続と回収が進むこと |
| 止まりの許容 | 約 1.7 ms ([平文の置き場と unit の上限](memory.md#平文の置き場と-unit-の上限)) | P2 | 最大の負荷で helper を 1、5、20 ms 止め、engine の中で捨てた数と相手の再送を、同じ止まりの Inline と比べます |
| 知らせの源と輪の容量 | 知らせの輪と返却の輪の容量を、枠ごとの知らせの数の上界から決めます。足りない源 (ルールの変更による accept した接続の終わり、DNS と dial の結果、古い handle の `abort` による行の削除、設定の更新) と、枠を使い直す時の重なりを数え直します | P0 | 枠の使い直し、ルールの変更、古い handle の abort を交互に起こす決定的な実行で、輪が満ちないこと |
| 行に移る時の窓 | front が表を替える前に unit に届いた FIN、RST、データは、戻しの輪で front に渡す形を候補にします | P0 | 返却の知らせの前後に FIN の再送、RST、FIN_WAIT_2 の行へのデータを置く台本で、今の核と同じ出力になること |
| counter の在庫の道 | 補充できない求めでのハンドシェイクの開始、送った数からの persistent keepalive の期限、endpoint の世代 ([counter の在庫](ownership.md#counter-の在庫)) | P1 | helper の unit だけがデータを持つ時のセッションの期限切れ、積み残しの後の keepalive と handshake の時機、積み残しの間の endpoint の変化 |
| データプレーンの作り直しの範囲 | 駆動 (`dataplane/driver.rs`)、`Handle::call` と `spawn_local`、`wgft-netstack`、配送を見る TCP の中継、UDP の中継、トンネルの ping、宛先の dial と名前の解決 (`targets`) | P0 | 本物の LAN の側のソケットでの CPU と遅れの比べ |
| アプリケーションの口と dial の道 | engine が接続ごとにアプリケーションを作る口、unit の epoll とタイマーの口、unit から front への dial の求めと完了の知らせ | P0 | dial の成功、拒否、期限、取り消しの台本 |
| 後で重くなる配置 | 直近の受信の packet の重み | P2、P3 | 静かな接続を多く張った後で、ランダムな一部に大きな転送を始める試行を繰り返し、速さの和と Jain の指数を下の 10% の値で判定します |
| unit の数えの読み出し | front が知らせで写しを求めます | P0 | 状態の読み出しが積み残しの間も返ること |

## 測る値

### 測定の行列

| 軸 | 値 |
|---|---|
| agent の VM の vCPU | 1、2、4、8 |
| TCP の stream の数 | 1、4、16 |
| RTT | 0、4、20 ms。RTT のある経路はボトルネックの速さを置きます |
| 向き | 送る向き (LAN から tunnel) と受ける向き (tunnel から LAN) |
| 負荷 | 何もしない時、Inline の最大の速さの 0.01、0.1、0.25、0.5、0.9、1.0、1.2 倍の固定の速さ、速さを制限しない最大の負荷 |
| 山 | 5 ms 送って 50 から 150 ms 休む繰り返し |
| 対話の往復 | 小さな要求と応答、積み残しの間の大きな応答 (ラボに加える道具) |
| UDP | 10、20、50 ms の間隔の UDP の ping を、どの負荷にも重ねます。受け渡しの間の値も分けて数えます |
| unit 0 の大きな flow | 試験の build で、大きな flow を unit 0 に置く形 |
| CPU の取り合い | `lab/lab paired --agent-load` |
| 接続の入れ替わり | 短い接続を速く張って閉じる負荷 |
| 立ち上がり | 16 本の stream を同時に始め、定常の速さに届くまでの時間 |
| 後で重くなる配置 | [未決の項目](#未決の項目)の試行 |
| 止まった helper | helper を 1、5、20 ms 止める形と、nice 0 の負荷で飢えさせる形 |

### 受ける向きの伸びの測り方

分けたラボでは、4 と 8 vCPU の受ける 1 stream で相手の VM が先に詰まります (測定、未公開の記録)。
受ける向きの判定は、分けたラボの相手の VM の vCPU を増やし、相手が `peer_bound` にならないことを確かめた本物の I/O の実行だけで行います。
ホストの合成の送り手の値は診断で、判定には使いません。
相手が詰まった組は未検証です。

### 値

速さ、byte あたりの CPU (agent の VM、2 台の VM の和、VM の外の qemu)、UDP の p50 と p99 と jitter と損失、対話の往復の p50 と p99、Jain の指数、executor ごとの CPU と起床の回数、積み残しの出入りと受け渡しの回数、受け口の輪の深さと捨てた数、捨てた counter の在庫、相手の再送の数、接続の速さと接続あたりの CPU、メモリの上界と確保と RSS を取ります。
段ごとの時間と輪の深さは、ラボの計測の feature を付けた build だけが数えます。

## 正しさの試験

- 1 つの CPU の金の比べ:engine の出力を今の核の出力と bit で比べ、凍結した Go の記録との bit の一致の試験 ([Go の wgstack の記録との bit の一致](../../v2/wgstack-rs.md#go-の-wgstack-の記録との-bit-の一致)) を当てます
- 2 つ以上の CPU の比べ:IP ID と乱数の種を試験の build だけの種で揃え、積み残しの無い形とある形で、1 つの CPU と同じ出力になることを確かめます
- 適合の試験:TCP の適合の台本を n_cpu = 4 で、積み残しの無い形とある形で流します
- 置く時と行に移る時の台本:SYN と最後の ACK の再送、データを運ぶ最後の ACK、置く前後の RST、行に移る前後の FIN と RST とデータ、枠の中の TIME_WAIT への SYN、RST を受けた後の同じ 4 つ組の SYN
- 順の性質:試験の build で front が datagram に付けた順の番号が、各 flow で増えることを unit の受け渡しの前後で確かめます
- 決定的な交互の実行と fuzz:front と helper の 1 歩を種に従って交互に進め、flow の中の順、各 unit の実行者が 1 つであること、表と枠の一致、予算の和、輪が満ちないことを確かめます。
  今の `FuzzCore` に交互の順と受け渡しの位置を加えます
- メモリの順の模型:輪、眠りの印と起床、受け渡しの枠を loom などで確かめます。
  道具は試験だけの依存です

## メモリの試験

- 各 executor のスレッドで、定常の状態の packet あたりの確保が 0 であることを、`wgft-alloc-count` の試験の形で確かめます
- 敵対的な保持の試験 ([上界と敵対的な保持の試験](../../v2/wgstack-rs.md#上界と敵対的な保持の試験)) を n_cpu = 8 で流し、確保の最大が上界の式の値を超えず、入力が止まった後に戻ることを確かめます
- 止まった helper で、front の読みと UDP とほかの unit が続き、止まった unit に新しい接続が置かれないことを確かめます
- 上界の表に n_cpu = 1、2、4、8 の列を持たせ、ラボで RSS が上界と決めた余裕の和以下であることを確かめます

## 受け入れの条件

数値は所有者に決めてもらう案です。
比は U / Inline で、ラボの組の推定と 95% の区間で判定します。
byte あたりの CPU は今の[判定の手順](../../v2/agent-throughput.md#判定の手順)と同じく `ci95_high` を線と比べ、遅れは推定と `ci95_low` の非劣性の線で判定します。

| 項目 | 線 |
|---|---|
| 1 つの CPU | 核の出力が bit で一致。byte あたりの CPU の `ci95_high` が 1.03 以下。速さの推定が 0.98 以上。UDP の p50、p99、jitter の推定が 1.10 以下で `ci95_low` が 1.00 以下。メモリの増分 0 |
| 軽い負荷と中くらいの負荷 (n_cpu が 2 以上) | 0.01 から 0.5 倍の固定の速さで、byte あたりの CPU の `ci95_high` が 1.05 以下。対話の往復の p50 と p99 の推定が 1.10 以下で `ci95_low` が 1.00 以下 |
| UDP の遅れ (すべての n_cpu) | p50、p99、jitter の推定が 1.10 以下で `ci95_low` が 1.00 以下。測定の行列のすべての負荷、山、受け渡しの間、CPU の取り合いで、両方の向き。損失は Inline の損失に送った数の 0.1% を加えた数以下 |
| 最大の負荷 2 vCPU | 送る 4 と 16 stream 1.25 以上、受ける 4 と 16 stream 1.10 以上、1 stream は両方の向きで 1.00 以上 |
| 最大の負荷 4 vCPU | 送る 4 と 16 stream 1.50 以上、受ける 4 と 16 stream 1.30 以上、受ける 1 stream 1.25 以上 (大きな flow を unit 0 に置いた形は 1.00 以上)、送る 1 stream 1.00 以上 |
| 最大の負荷 8 vCPU | 送る 16 stream 1.70 以上、受ける 16 stream 1.30 以上、受ける 1 stream 1.25 以上、送る 1 stream 1.00 以上 |
| 最大の負荷の CPU | byte あたりの CPU の `ci95_high` が 1.15 以下 |
| 積み残しの安定 | 続く最大の負荷で出入りが 1 秒に 1 回以下 |
| 詰まる前後 | 0.9、1.0、1.2 倍の固定の速さで速さの推定が 1.00 以上 |
| 接続の入れ替わり | 接続の速さの推定が 1.00 以上、接続あたりの CPU の推定が 1.10 以下 |
| 立ち上がり | 16 本の stream が定常の 90% に届く時間が Inline の 1.10 倍以内 |
| CPU の取り合い | 速さの比が負荷の無い時の比の 0.9 倍以上 |
| 止まった helper | 止まりの許容より短い止まりで engine の中で捨てた数が 0。長い止まりの相手の再送の数を同じ止まりの Inline と並べて報告します |
| 長い RTT | RTT 4 と 20 ms で速さの推定が 0.98 以上 |
| 公平 | 経路が上限の時 Jain の指数 0.95 以上。CPU が上限の時 0.85 以上。後で重くなる配置で下の 10% の値が 0.80 以上 |
| 損失と順 | 0.5 倍以下の固定の速さで engine の中で捨てた数が 0。最大の負荷で相手の再送と D-SACK の比が 1.10 以下。捨てた counter の在庫は送った datagram の 10 万に 1 以下 |
| TCP の遅れ | 通信量の少ない stream の p99 が Inline の 1.10 倍以内で、[wgstack の性能の段階](../../userspace/wgstack-performance.md#目標と制約)の目標を満たし続けます |
| 敵対的な入力 | n_cpu = 8 で確保の最大が上界の式の値以下。1 つの unit と 2 つの unit への同時の洪水が、UDP の線とほかの unit を崩しません |
| メモリ | 1 つの CPU で増分 0。n_cpu = 8 の線は P0 の後に決めます |

受ける向きの線は、相手が詰まらない本物の I/O の実行だけで判定します。

## 報告の規則

- 結果の表は、利用できる CPU が 1 つの行、byte あたりの CPU、UDP の p50 と p99 と jitter を、速さと同じ表に並べます
- 受け入れの条件の 1 つでも満たさない組と、未検証の組は、そう表に書きます
- A+ の値は研究の比べとして別の列に置きます
- 測った条件 (build、置き方、round の数、除いた実行) を表ごとに書きます
