# 検証の計画 (N6)

この文書は、推奨の構成 U の段階の試作、測定の計画、正しさの試験、数値の受け入れの条件を定めます。
未採用の提案です([提案の索引](README.md))。
受け入れの条件の数値は所有者に決めてもらう案で、LGTM の前は確定しません。

## 原則

- 1 コアの後退を隠さない:複数のコアの速さを示す表には、同じ表に利用できる CPU が 1 つの行と、byte あたりの CPU と UDP の遅れを必ず並べます
- 軽い負荷を先に確かめる:agent が多くの時間を過ごす軽い負荷と中くらいの負荷の後退を、P0 と P2 の関門で確かめます
- UDP の遅れを TCP の速さと引き換えにしない:UDP の線を満たさない build は、速さが上がっても受け入れません
- 確かめられないものを合格にしない:ラボの上限で比べられない組は「未検証」と報告し、合格に数えません
- A+ を基準にしない:A+ (#808 から #810) は研究の比べの腕で、受け入れの基準は今の Inline です
- 使い捨ての試作はリポジトリに入れず、測定の詳細は PR に書きます

## 段階の試作

試作は、WireGuard の無い sans-IO から始め、暗号、本物の I/O、分けたラボの順に進めます。
各段の関門を満たしてから次の段に進みます。

### P0 WireGuard の無い sans-IO の engine

- 中身:ライブラリの直接の呼び出しの link と何もしない変換で、front と unit と helper を作り、合成の TCP と UDP の流れを流します。
  比べの相手は今の核のままの Inline です
- 作るもの:front の核と unit の核の作り直し、unit への配置、輪と知らせ、unit の受け渡し、unit の中で動く状態機械の中継
- 測るもの:利用できる CPU が 1 つの時の今の核との差、積み残しが無い時の packet あたりの CPU と往復の遅れ、積み残しの出入りの時間と受け渡しの費用、unit と helper ごとのメモリ
- 受ける向きの伸び:合成の送り手を別のスレッドで動かし、front と unit の 2 段と多くの stream の速さを、ラボの相手の上限なしに測ります
- 関門:利用できる CPU が 1 つの時に今の核と出力が bit で一致すること。
  積み残しが無い時の packet あたりの CPU が Inline の 1.05 倍以下で、往復の遅れの増分が 1 µs 未満であること

### P1 WireGuard の変換

- 中身:front の受信と送信の 1 回の呼び出しと、積み残しの間の counter の貸し出しを作ります
- 測るもの:貸し出しの費用、求めから送りまでの時間、暗号化し直しの回数、cache の miss
- 受ける向きの伸び:ホストの道具 (`crates/wgft-agent-perf` と `scripts/agent-perf-stat.sh`) を、暗号の付いた合成の送り手から front と unit へ流す形に広げ、受ける向きの伸びを測ります。
  ラボの VM は PMU を仮想化しないので、cache の miss もホストで数えます([判定の手順](../../v2/agent-throughput.md#判定の手順)の道具の説明)
- 関門:利用できる CPU が 1 つの経路が Inline と同じ費用で、貸し出しの front の費用が packet あたり 100 ns 以下であること

### P2 本物の I/O

- 中身:平らな UDP の link と WireGuard の UDP の link を、Incus の VM の network namespace の中の本物のソケットで動かします。
  ホストと Docker では測りません([テストの規範](../../../development/testing.md))
- 測るもの:外側のソケットへの並んだ送り出しの時間、カーネルの受信の処理の vCPU ごとの時間、helper の数 H = n_cpu - 1 と n_cpu - 2 の比べ、UDP の往復の遅れ
- 関門:軽い負荷と中くらいの負荷の対話の往復の遅れと UDP の遅れが Inline の線の内であること。
  最大の負荷に CPU の取り合い (`--agent-load`) を重ねても UDP の線の内であること

### P3 分けたラボ

- 中身:agent の build を U にして、分けたラボで Inline、A+、カーネルモードと比べます([測る値](#測る値))
- 関門:[受け入れの条件](#受け入れの条件)のすべてを満たすこと

後の段 ([後の段](performance.md#後の段)) の試作は、P3 で加える条件を満たした時だけ行います。
製品への実装は、P3 の結果と所有者の LGTM の後に始めます。

| 立ち上がり | 16 本の stream を同時に始め、定常の速さに届くまでの時間 |
| 静かな接続 | 数百本の静かな長い接続を先に張ってから、大きな flow を始める形 |
| 止まった unit | 1 つの helper を止めたまま、新しい接続と UDP を流す形 |

ラボは、分けたラボの置き方を helper の数に合わせて広げる変更と、対話の往復の道具が要ります。
今の `--placement apart-mt` は暗号の worker 2 本の build 用です([agent を専用の VM に置く](../../../../lab/README.md#agent-を専用の-vm-に置く---split))。

### 受ける向きの伸びの測り方

分けたラボでは、4 と 8 vCPU の受ける 1 stream で相手の VM が先に詰まります (測定、未公開の記録)。
このため、ラボだけでは受ける向きの伸びを示すことも否定することもできません。
受ける向きの伸びは次の 2 つで測ります。

- ホストの道具:P0 と P1 の合成の送り手で、相手の上限なしに front と unit の 2 段を測ります
- 強い相手の VM:分けたラボの相手の VM の vCPU を増やし、相手が `peer_bound` にならないことを確かめてから測ります

相手が詰まった組は「未検証」とし、合格に数えません。

### 値

| 値 | 取り方 |
|---|---|
| 速さ | 両方の向きの Mbit/s |
| byte あたりの CPU | agent の VM、2 台の VM の和、VM の外の qemu の CPU |
| UDP の遅れ | p50、p99、jitter、損失 |
| 対話の往復の遅れ | p50、p99 |
| 公平 | 等しい flow の速さの Jain の指数と、unit ごとの大きな flow の数 |
| スレッドの CPU | executor ごとの実行、CPU を待った時間、眠った時間の割合、起床の回数 |
| 積み残し | 出入りの回数、受け渡しの回数と時間、無駄だった helper の起床 |
| 輪 | 受け口の輪の深さの分布、unit の上限で捨てた数、戻しの輪で捨てた SYN |
| counter | 暗号化し直しの回数、相手の再送の数 |
| 接続 | 1 秒あたりの接続の数と、接続あたりの CPU |
| cache の miss | ホストの道具で packet あたりの値 |
| メモリ | 起動の時の上界と確保、起動の直後と転送中の最大の RSS |

段ごとの時間と輪の深さは、ラボの計測の feature を付けた build だけが数え、製品の build には入れません。

## 正しさの試験

### 利用できる CPU が 1 つの時の金の比べ

- engine の出力を、今の核の出力と bit で比べます。
  凍結した Go の記録との bit の一致の試験 ([Go の wgstack の記録との bit の一致](../../v2/wgstack-rs.md#go-の-wgstack-の記録との-bit-の一致)) をそのまま当てます
- TCP の適合の試験の台本 (Linux を参照にした台本) を流します

### unit に置く確立と行の返却

- 適合の試験の台本を n_cpu = 4 で、積み残しの無い形とある形の両方で流し、同じ期待で通します
- 置く時の競合の台本:SYN の再送、最後の ACK の再送、データを運ぶ最後の ACK、最後の ACK の直後のデータ、置く前後の RST を、置く点の前と後に置きます
- 行の返却の台本:返却の知らせの前後に FIN の再送、RST、新しい SYN、FIN_WAIT_2 の行へのデータを置きます
- 枠の中の TIME_WAIT への SYN:使い直しの条件を満たす場合と満たさない場合で、今の核と同じ出力になることを確かめます
- RST を受けた後の同じ 4 つ組の SYN:アプリケーションが閉じる前でも、今と同じく待ち受けに届くことを確かめます
- 順の性質:試験の build で、front が datagram に読んだ順の番号を付け、unit が各 flow の番号が増えることを確かめます。
  unit の受け渡しの前後でも確かめます

### 決定的な交互の実行

- 試験の実行器は、front と helper の 1 歩を 1 つのスレッドで種に従って交互に進め、輪、配置、返却、受け渡し、貸し出しの任意の交互の順を作ります
- 確かめる不変条件:flow の中の順、各 unit を実行する executor が常に 1 つであること、front の表の項と unit の枠の一致、予算の和の不変条件、制御の輪と返却の輪が満ちないこと、unit ごとの block の数が上限を超えないこと
- fuzz:今の `FuzzCore` に、交互の順の種、置く点、返却の位置、受け渡しの位置を操作として加えます。
  量は実行の回数で決めます

### メモリの順の模型

輪、眠りの印と起床の手順、持ち主の語の受け渡しを、loom などの模型の検査ですべての交互の順について確かめます。
模型の検査の道具は試験だけの依存で、製品の build に入りません。

### WireGuard のタイマーと counter

- 積み残しの後に静かになったトンネルで、keepalive と handshake の開始が Inline と同じ時機に出ることを確かめます
- 貸し出しを使わずに捨てた場合の振る舞いを、試験の build で強制して確かめます
- server の相手 (カーネルの WireGuard、wireguard-go) を相手に、counter を executor の間で貸した時の暗号化し直しの回数と相手の再送を数えます

## メモリの試験

- 確保の数え:各 executor のスレッドで、定常の状態の packet あたりの確保が 0 であることを、今の `wgft-alloc-count` の試験の形で確かめます
- 上界と保持:敵対的な保持の試験 ([上界と敵対的な保持の試験](../../v2/wgstack-rs.md#上界と敵対的な保持の試験)) を n_cpu = 8 で流し、確保の最大が上界の式の値を超えないことを確かめます
- 止まった unit:1 つの helper を止めた時に、front の読みと UDP とほかの unit の接続が続き、止まった unit の接続だけが捨てられ、新しい接続が止まった unit に置かれないことを確かめます
- 回復:入力を止めた後に、平文の block、送信の枠、credit が置き場に戻ることを確かめます
- 上界の表:今と同じく試験が上界の表を生成し、n_cpu = 1、2、4、8 の列を持たせます
- RSS:ラボで、RSS が上界と決めた余裕の和以下であることを n_cpu ごとに確かめます

## 受け入れの条件

数値は所有者に決めてもらう案です。
比は U / Inline で、ラボの組の推定と 95% の区間で判定します。
区間の扱いと流し直しの規則は、今の[判定の手順](../../v2/agent-throughput.md#判定の手順)に従います。

### 利用できる CPU が 1 つの時の同等

| 値 | 線 |
|---|---|
| 出力 | 今の核と bit で一致します |
| byte あたりの CPU (両方の向き、1 と 4 stream) | 推定が 1.02 以下で、`ci95_low` が 1.00 以下 |
| 速さ | 推定が 0.98 以上 |
| UDP の p50、p99、jitter | 推定が 1.10 以下で、`ci95_low` が 1.00 以下 |
| メモリの上界 | 増分 0 |

### 軽い負荷と中くらいの負荷 (n_cpu が 2 以上)

- byte あたりの CPU:0.01 倍から 0.5 倍の固定の速さで、agent の VM の比の推定が 1.05 以下で、`ci95_low` が 1.00 以下です。
  VM の外の qemu の CPU も同じ線にします
- 対話の往復の遅れ:p50 と p99 の推定が 1.10 以下で、`ci95_low` が 1.00 以下です
- この線は、軽い負荷と中くらいの負荷の後退を受け入れない場合の線です([所有者に決めてもらうこと](README.md#所有者に決めてもらうこと))

### UDP の遅れ (すべての n_cpu)

- 線:p50、p99、jitter の推定が 1.10 以下で、`ci95_low` が 1.00 以下です (今の非劣性の線)
- 当てる負荷:測定の行列のすべての負荷を、両方の向きで測ります
- CPU の取り合い:`--agent-load` で agent の VM の CPU の 1 つに負荷を置いた時も、同じ線を当てます
- 損失:Inline の損失に送った数の 0.1% を加えた数以下です

### 最大の負荷の速さ (RTT 0)

| vCPU | 線 |
|---|---|
| 2 | すべての組で 1.00 以上 |
| 4 | 送る 4 stream と 16 stream 1.50 以上、受ける 4 stream と 16 stream 1.30 以上、受ける 1 stream 1.25 以上、送る 1 stream 1.00 以上 |
| 8 | 送る 16 stream 1.70 以上、受ける 16 stream 1.30 以上、受ける 1 stream 1.25 以上、送る 1 stream 1.00 以上 |

- 受ける向きの線は、ホストの道具か強い相手の VM で、相手が詰まらない形で判定します。
  相手が詰まった組は未検証で、合格に数えません
- 送る 1 stream は基本の設計では伸びないので、後退しないことだけを求めます
- byte あたりの CPU:最大の負荷の agent の VM の比の推定が 1.15 以下です

### 詰まる前後

- 0.9 倍、1.0 倍、1.2 倍の固定の速さで、速さの比の推定が 1.00 以上で、UDP の線を満たします
- 積み残しの出入りが 1 秒あたり 1 回を超えて繰り返さないことを確かめます

### 接続の入れ替わりと立ち上がり

- 1 秒あたりの接続の数の比の推定が 1.00 以上で、接続あたりの CPU の比の推定が 1.10 以下です
- 16 本の stream を同時に始めて、定常の速さの 90% に届くまでの時間が Inline の 1.10 倍以内です

### CPU の取り合い

- `--agent-load` を置いた時、速さの比が負荷の無い時の比の 0.9 倍以上で、UDP の線を満たします

### 長い RTT

- RTT 4 と 20 ms、ボトルネック 2,000 Mbit/s で、速さの比の推定が 0.98 以上、byte あたりの CPU の比は軽い負荷の線と同じです

### 公平

- 経路が上限の時:等しい 4 本と 16 本の flow の Jain の指数が 0.95 以上です
- CPU が上限の時 (最大の負荷):Jain の指数が 0.85 以上です。
  静かな接続を先に張った形でも同じ線を当てます

### 損失と順

- 0.5 倍以下の固定の速さで、engine の中で捨てた数が 0 です
- 最大の負荷で、相手の再送の数と D-SACK の数の比の推定が 1.10 以下です
- CPU の取り合いの時の暗号化し直しは、送った datagram の 10 万に 1 以下です。
  相手の replay の拒否は lab の server で直接数えられないので、相手の再送の数の線で代えます

### TCP の遅れ

- 通信量の少ない stream の p99 が、qbench と分けたラボで Inline の 1.10 倍以内で、[wgstack の性能の段階](../../userspace/wgstack-performance.md#目標と制約)の目標を満たし続けます

### 敵対的な入力

- n_cpu = 8 で、敵対的な保持の試験の確保の最大が上界の式の値を超えず、入力が止まった後に戻ります
- n_cpu = 8 で、1 つの unit に向けた洪水が、UDP の線とほかの unit の接続の速さを崩しません

### メモリ

- 利用できる CPU が 1 つ:上界の増分が 0 です
- n_cpu = 8:増分の線は P0 の測定の後に決めます。
  今の見込みは約 13.6 MiB に未測定の分を加えた値です([増える量の見込み](memory.md#増える量の見込み))
- すべての n_cpu:RSS が上界と決めた余裕の和以下で、executor のスレッドの packet あたりの確保が 0 です

## 報告の規則

- 結果の表は、利用できる CPU が 1 つの行、byte あたりの CPU、UDP の p50 と p99 と jitter を、速さと同じ表に並べます
- 受け入れの条件の 1 つでも満たさない組があれば、ほかの組の速さの向上と分けずに示します
- 未検証の組は、未検証と表に書きます
- A+ の値は研究の比べとして別の列に置き、受け入れの判定に使いません
- 測った条件 (build、置き方、round の数、除いた実行) を表ごとに書きます

## 未確認の点

- 外側の 1 つの流れのカーネルの受信の処理の上限と、外側のソケットへの並んだ送り出しの競合
- helper の数を n_cpu - 1 にするか n_cpu - 2 にするか
- SMT の対に 2 つの executor が乗る時の速さ
- `PendingEncapsulate` をスレッドの間で渡せること
- 輪と眠りの印に使える upstream の crate の有無
- 本物のホストで、送る向きの system call の費用のうちラボだけの受け手の処理を除いた割合
