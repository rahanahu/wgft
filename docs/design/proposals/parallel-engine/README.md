# 並列のパケットエンジンの提案

この提案は、wgft の次の世代のパケットエンジンを複数の CPU で動かす構成を定めます。
状態は未採用の提案です。
採用、製品の仕様の変更、マージは所有者の LGTM で決まります。
LGTM の前は、この提案の決定と数値はどれも確定しません。

## 要約

推奨は、構成 S「作成の時の配置」です([構成の比較](architecture.md#推奨の構成-s))。

- shard 0 は外側のソケットを読み、datagram の順にその場で復号し、4 つ組で持ち主へ振り分けます。
  接続を作る表 (待ち受け、握手の途中、TIME_WAIT の行、再組み立て)、UDP、WireGuard のセッションも shard 0 が持ちます
- TCP の接続は、握手の最後か dial の時に持ち主の shard に置き、閉じるまで動かしません。
  置く先は、生きている接続の数が最も少ない shard です
- 持ち主は、自分の接続の TCP の処理、中継、暗号化、送り出しを行います。
  送る counter と鍵は shard 0 から借り、錠を使いません
- N = 1 の時は今の Inline の経路そのものを使います

S を推す理由は次のとおりです。

- 1 コアの同等:N = 1 は Inline と同じ経路なので、出力が bit で一致し、byte あたりの CPU と遅れが同じです
- TCP の正しさ:確立した接続の状態を触るのは閉じるまで 1 つのスレッドで、持ち主が変わるのはデータを持たない 2 つの点 (確立と TIME_WAIT の行への移り) だけです。
  TCP の状態機械のコードを変えません([1 つの持ち主から多くの持ち主へ移しても TCP の状態機械が保たれる理由](ownership.md#1-つの持ち主から多くの持ち主へ移しても-tcp-の状態機械が保たれる理由))
- 単純さ:錠が無く、動いている接続の移しも無く、shard の間の捨てない知らせは容量が満ちない輪で運びます
- UDP の低い遅れ:UDP はスレッドを移らず、shard 0 は TCP の処理を持たないので (N が 3 以上)、Inline より待ちが短くなると見込みます(推定)
- 伸び方:多くの stream は持ち主の数まで、受ける 1 stream は shard 0 と持ち主の 2 段で伸びると見込みます(推定)

S が得ないものと危険は次のとおりです。

- 送る 1 stream:基本の設計では伸びません。
  1 本の大きな flow の暗号化を順序を保って手伝う形は、条件を満たした時の後の段です
- 大きな量の UDP:shard 0 の 1 つの CPU に収まる分までです
- 中くらいの負荷の CPU:N が 2 以上では、TCP の packet が shard 0 から持ち主へ移るので、持ち主の起床の費用が加わります。
  見積もりは 1.15 から 1.75 倍で、受け入れの線を超える恐れが高い項目です(推定、[N が 2 以上の軽い負荷](performance.md#n-が-2-以上の軽い負荷))。
  線を超えた時は、代わりの形の昇格を比べ直します
- 10 Gbit/s:届くかは未確認です([10 Gbit/s を決める上限](performance.md#10-gbits-を決める上限))

## 値の区別

文書の値には、次の区別を付けます。

- 測定:測った値です。
  公開の文書か PR にある値は、その出どころを書きます
- 測定 (未公開の記録):測った値で、公開の文書と PR にまだ無いものです。
  条件と値は、この提案を出す PR の本文に移します
- 推定:測定から導いた値か、測っていない見込みです
- 計算:書いた値から式で導いた値です
- 設計判断:この提案が選ぶ規則で、所有者の LGTM で確定します
- 未確認:確かめていない前提です

A+ (#808 から #810) の値は、研究の比べとして測った教訓で、S の基準ではありません。
測定の条件は[性能の模型の測定の条件](performance.md#測定の条件)にあります。

## 範囲の外

- dial の製品への実装:この提案は dial を TCP の仕様として整理するだけです([TCP の能動の open](api.md#tcp-の能動の-open))
- 多くのピアを持つ server:外側のアドレスでピアごとに shard に分ける形が自然ですが、設計していません
- link の queue を増やす形 (複数のセッション、AF_XDP):API で妨げないことだけを扱います
- Windows と macOS の複数の datagram の読み:今の 1 つずつの送受信のままです。
  持ち主への配置は働きます
- 受信の窓と待ち行列の長さの制御:持ち主ごとのデータの輪に CoDel を当てる形を後で比べる候補に挙げるだけです

## 所有者に決めてもらうこと

各項目は単独で判断できる形にしています。

1. 構成の採用:並列のエンジンの方向として、shard 0 が受信と復号と接続の作成を持ち、TCP の接続を作成の時に別の shard に置いて閉じるまで動かさない構成を採り、WireGuard の無い sans-IO の試作から始めるか。
   採る場合は、次の違いを受け入れます。
   - challenge ACK の速さの上限を shard ごとに 1/N に分けます。全体の上限は超えませんが、1 つの shard に偏った攻撃では今より早く尽きます
   - アプリケーションがまだ閉じていない TIME_WAIT の接続への新しい SYN は、閉じるまで捨てます。今は使い直します
2. 基本の設計で伸ばさないもの:送る 1 stream の速さと、大きな量の UDP の速さを基本の設計では伸ばさず、測って要ると分かった時に後の段で加える順序でよいか
3. 中くらいの負荷の CPU の線:CPU が 2 つ以上の時の、中くらいの負荷 (Inline の最大の 0.25 倍と 0.5 倍) の byte あたりの CPU を、Inline の何倍まで許すか。
   案は 1.10 倍です。
   見積もりは 1.15 から 1.75 倍で、線を超えた時は、全部の接続を 1 つのスレッドで始めて詰まった時だけ移す形を比べ直します。
   その形は、移した接続が静かになった後も費用を払い続ける問題と、移す手順の複雑さを持ちます
4. 受け入れの線:[受け入れの条件](verification.md#受け入れの条件)の線を採るか。
   主な値は、CPU が 1 つの時の byte あたりの CPU 1.02 倍以下、UDP の p50 と p99 と jitter をすべての負荷と CPU の取り合いの下で 1.10 倍以下、4 CPU で送る 4 stream 1.50 倍以上と受ける 1 stream 1.25 倍以上、送る 1 stream は 1.00 倍以上です
5. メモリの線:CPU が 8 つの時の上界の増分を 16 MiB 以内、CPU が 1 つの時を 0 とするか。
   見積もりは約 13 MiB に実行環境の分を加えた値で、A+ の 8.4 MiB より大きくなります
