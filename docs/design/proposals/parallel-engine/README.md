# 並列のパケットエンジンの提案

この提案は、wgft の次の世代のパケットエンジンを複数の CPU で動かす構成を定めます。
状態は未採用の提案です。
採用、製品の仕様の変更、マージは所有者の LGTM で決まります。
LGTM の前は、この提案の決定と数値はどれも確定しません。

## 要約

推奨は、構成 U「unit と executor」です([構成の比較](architecture.md#s-と-u-の比べ))。

- front のスレッドは、外側のソケットを読み、datagram の順にその場で復号し、4 つ組で振り分けます。
  接続を作る表、UDP、WireGuard のセッションも front が持ちます
- TCP の接続は、作成の時に unit (接続の状態の区画) に置かれ、閉じるまで動きません
- 積み残しが無い間は、front のスレッドが全 unit をその場で実行します。
  軽い負荷と中くらいの負荷では、Inline とほぼ同じ経路です
- 積み残しがある間だけ、helper のスレッドが unit を受け取って実行し、TCP の処理と暗号化と送り出しを分けます
- 利用できる CPU が 1 つの時は、今の Inline の経路そのものを使います

U を推す理由は次のとおりです。

- 軽い負荷:agent が多くの時間を過ごす負荷で、packet あたりの CPU は Inline の 1.05 倍以下、遅れの増分は 1 µs 未満と見込みます(推定)。
  比べた形 S (持ち主のスレッドが常に実行する形) は、同じ負荷で 2.3 から 4.3 倍の CPU と、起床の分の遅れを払います(推定、[軽い負荷と中くらいの負荷](performance.md#軽い負荷と中くらいの負荷))
- 最大の負荷:積み残しの間は S と同じ分担で、多くの stream と受ける 1 stream で伸びると見込みます(推定)
- TCP の正しさ:1 つの unit を実行するスレッドは常に 1 つで、接続の状態機械のコードを変えません([1 つの持ち主から多くの持ち主へ移しても TCP の状態機械が保たれる理由](ownership.md#1-つの持ち主から多くの持ち主へ移しても-tcp-の状態機械が保たれる理由))
- 単純さ:錠が無く、動いている接続の移しも無く、捨てない知らせは満ちない輪で運びます
- UDP:UDP はスレッドを移らず、積み残しの間は front が TCP の処理を持たないので、Inline より待ちが短くなると見込みます(推定)

U が得ないものと払うものは次のとおりです。

- 送る 1 stream:基本の設計では伸びません
- 大きな量の UDP:front の 1 つの CPU に収まる分までです
- 中継の作り直し:unit を別のスレッドで実行できるように、中継を tokio の外の状態機械に作り直します。
  P0 から P3 の間は、利用できる CPU が 1 つの時の今の中継と、2 つになります
- 10 Gbit/s:届くかは未確認です([10 Gbit/s を決める上限](performance.md#10-gbits-を決める上限))

## 言葉と値の区別

- 送る向き:agent が LAN から受けたデータをトンネルへ送る向きです
- 受ける向き:agent がトンネルから受けたデータを LAN へ渡す向きです
- 軽い負荷:Inline の最大の速さの 0.01 から 0.1 倍と、対話の往復です
- 中くらいの負荷:Inline の最大の速さの 0.25 から 0.5 倍です
- 積み残し:[積み残しの定義](ownership.md#積み残しの定義)の 1 つの意味だけに使います

### 値の区別

- 測定:測った値です。
  公開の文書か PR にある値は、その出どころを書きます
- 測定 (未公開の記録):測った値で、公開の文書と PR にまだ無いものです。
  条件と値は、この提案を出す PR の本文に移します
- 推定:測定から導いた値か、測っていない見込みです
- 計算:書いた値から式で導いた値です
- 設計判断:この提案が選ぶ規則で、所有者の LGTM で確定します
- 未確認:確かめていない前提です

A+ (#808 から #810) の値は、研究の比べとして測った教訓で、U の基準ではありません。
測定の条件は[性能の模型の測定の条件](performance.md#測定の条件)にあります。

## 範囲の外

- dial の製品への実装:この提案は dial を TCP の仕様として整理するだけです([TCP の能動の open](api.md#tcp-の能動の-open))
- Windows と macOS:利用できる CPU の数によらず、今の Inline の経路のままです
- 外のスレッドから接続を読み書きするライブラリの API:P0 から P3 の範囲の外です
- 多くのピアを持つ server と、link の queue を増やす形 (複数のセッション、AF_XDP):設計していません
- 受信の窓と待ち行列の長さの制御:unit の受け口の輪に CoDel を当てる形を、後で比べる候補に挙げるだけです

## 所有者に決めてもらうこと

各項目は単独で判断できる形にしています。

1. 構成の採用:並列のエンジンの方向として、1 つのスレッドが受信と復号と接続の作成を持ち、TCP の接続を作成の時に状態の区画に置き、負荷が 1 つのスレッドを超えた時だけ別のスレッドがその区画を実行する構成を採り、WireGuard の無い sans-IO の試作から始めるか。
   採る場合は、次の点を受け入れます。
   - 中継を、データプレーンで tokio を使わない状態機械に作り直します
   - CPU が 2 つ以上の時、challenge ACK の速さの上限を区画ごとに分けます。全体の上限は超えませんが、1 つの区画に偏った攻撃では今より早く尽きます
   - 受信のスレッドが詰まった時だけ、戻す SYN と最後の ACK を捨てることがあります。相手は送り直します
2. 軽い負荷と中くらいの負荷の後退:CPU が 2 つ以上の時に、Inline の最大の 0.5 倍以下の負荷で、byte あたりの CPU と対話の往復の遅れが Inline より悪くなることを受け入れるか。
   推奨は受け入れないことで、線は byte あたりの CPU 1.05 倍、往復の遅れ 1.10 倍です。
   試作で線を超えたら、この構成を採らずに見直します
3. 送る 1 stream:1 本の送る stream の速さは、基本の設計では Inline と同じです。
   伸ばす既知の方法は、1 本の flow の暗号化を別のスレッドで順序を保って手伝う形で、2026-11-05 に止めた暗号の worker (#808 から #810) と同じ種類です。
   その測った費用は "UDP p50 at 4 vCPU fixed load 0.13 to 0.39 ms, CPU per byte 1.10 to 1.19 times under data-plane CPU contention, and 8.4 MiB more resident memory at 8 vCPU" でした。
   1 本の送る stream を伸ばさないままにするか、この費用を持ちうる形を後で評価するか
4. 対応する OS:複数の CPU の経路を Linux だけで作り、Windows と macOS は今の Inline のままにするか
5. ライブラリの範囲:外のスレッドから接続を読み書きする API を P0 から P3 の範囲の外にし、アプリケーションは接続の区画の中で動く形 (agent の中継と同じ形) に限るか
6. 受け入れの線:[受け入れの条件](verification.md#受け入れの条件)を採るか。
   主な値は、CPU が 1 つの時の byte あたりの CPU 1.02 倍以下、UDP の p50 と p99 と jitter をすべての負荷と CPU の取り合いの下で 1.10 倍以下、4 CPU で送る 4 stream 1.50 倍以上と受ける 1 stream 1.25 倍以上 (相手が詰まらない形で判定)、送る 1 stream 1.00 倍以上です。
   メモリの増分の線は、CPU が 1 つの時は 0 とし、8 つの時は試作で測ってから決めます。
   今の見込みは約 13.6 MiB に未測定の分を加えた値です
