# 並列のパケットエンジンの提案

この提案は、wgft の次の世代のパケットエンジンを複数の CPU で動かす構成を定めます。
状態は未採用の提案です。
採用、製品の仕様の変更、マージは所有者の LGTM で決まります。
LGTM の前は、この提案の決定と数値はどれも確定しません。

## 要約

推奨は、構成 S「昇格と順序つきの暗号の分担」です([構成の比較](architecture.md#推奨の構成-s))。

- shard 0 は今の Inline のデータプレーンのスレッドの仕事をすべて持ち、UDP、接続を作る表、WireGuard のセッションも持ちます
- shard 0 が詰まった時だけ、最も多く運ぶ TCP の接続を 1 本ずつ別の shard へ一方向に移します (昇格)
- 読みや送りに積み残しがある時だけ、復号と暗号化を塊に分けて申し出て、起きている shard が引き取ります。
  順は塊の番号で保ち、誰もほかのスレッドの終わりを同期して待ちません
- N = 1 の時は Inline の経路そのものを使います

S を推す理由は次のとおりです。

- 1 コアの同等:N = 1 は Inline と同じ経路なので、byte あたりの CPU と遅れが同じです
- 中くらいの負荷:詰まっていない時は N によらず Inline と同じ経路なので、A+ が悪くした UDP の p50 と byte あたりの CPU の原因 (軽い負荷での受け渡しと起床) を経路から外せます
- 詰まった時:暗号、送り出し、重い TCP の flow を別の CPU に分けるので、1 stream と多くの stream の両方で伸びると見込みます(推定)
- TCP の正しさ:1 本の接続の状態を触るのは常に 1 つのスレッドで、flow の中の順は 1 つの振り分けの順と FIFO の queue で保つので、TCP の状態機械のコードを変えません([1 つの持ち主から多くの持ち主へ移しても TCP の状態機械が保たれる理由](ownership.md#1-つの持ち主から多くの持ち主へ移しても-tcp-の状態機械が保たれる理由))
- メモリ:接続を作る表を shard の数だけ持たず、受信の暗号文の置き場を 1 つに保つので、上界の増分は N = 8 で約 8.5 MiB と実行環境の分です(推定)
- 汎用:link の adapter とトンネルの変換を核から分けるので、WireGuard の無い汎用の sans-IO の TCP/IP スタックとしても使えます。
  変換が無い時は暗号の分担の費用を払いません

10 Gbit/s に届くかは未確認です。
同じラボのカーネルモードの最大が 9,083 Mbit/s (測定) なので、何が上限を決めるかを測定で見分ける計画を置きます([10 Gbit/s を決める上限](performance.md#10-gbits-を決める上限))。

## 値の区別

文書の値には、次の区別を付けます。

- 測定:測った値です。
  測った条件 (ラボの形、vCPU、負荷、round の数) を同じ表か同じ節に書きます
- 推定:測定から導いた値か、測っていない見込みです。
  試作で確かめる対象です
- 計算:書いた値から式で導いた値です
- 設計判断:この提案が選ぶ規則で、所有者の LGTM で確定します
- 未確認:確かめていない前提です

A+ (#808 から #810) の値は、研究の比べとして測った教訓で、S の基準ではありません。
測定の条件の詳しい形は[性能の模型の測定の条件](performance.md#測定の条件)にあります。

## 範囲の外

- dial の製品への実装:この提案は dial を TCP の仕様として整理するだけです([TCP の能動の open](api.md#tcp-の能動の-open))
- Windows と macOS の複数の datagram の読み:今の 1 つずつの送受信のままで、S の暗号の分担はこの OS では働きません。
  昇格は働きます
- link の queue を増やす形 (複数のセッション、AF_XDP):API で妨げないことだけを扱います
- 受信の窓と待ち行列の長さの制御:受け口の queue に CoDel を当てる形を後で比べる候補に挙げるだけです

## 所有者に決めてもらうこと

各項目は、前提を含めて単独で判断できる形にしています。

1. 構成の採用:並列のエンジンの方向として S (shard 0 を Inline のまま保ち、詰まった時だけ重い TCP の flow を別の shard へ一方向に移し、積み残しがある時だけ暗号を塊で分ける構成) を採り、WireGuard の無い sans-IO の試作から始めるか。
   推奨は採ることです。
   採らない場合の次の候補は、新しい flow を最初から shard 0 以外に置く「分散」の形で、中くらいの負荷の byte あたりの CPU が悪くなると見込みます([昇格を選んだ理由](architecture.md#昇格を選んだ理由))
2. 昇格の手順の複雑さ:昇格には、接続の状態を値として別の shard の核へ移すこと、タイマーと出力の付け替え、中継の task と LAN の側のソケットの移しが要ります。
   戻しは持たず、一方向にします。
   この複雑さを受け入れるか。
   推奨は受け入れることです
3. 受け入れの条件の数値:[受け入れの条件](verification.md#受け入れの条件)の線 (N = 1 の byte あたりの CPU 1.02 以下、UDP の p50 も p99 と同じ 1.10 の線、中くらいの負荷の byte あたりの CPU 1.03 以下、4 vCPU の送る 1 stream 1.45 倍以上、N = 8 のメモリの増分 12 MiB 以内など) を採るか
4. CPU の数と N の対応:N を起動の時の利用できる CPU の数 (上限 8) にし、2 CPU で N = 2 を使うかを測定で決めるか。
   SMT の論理の CPU を数えるか、物理の core で数えるかも測定で決めるか
5. challenge ACK の速さの bucket:N が 2 以上の時、全体の上限を shard ごとに 1/N ずつに分けるか。
   全体の上限は超えませんが、1 つの shard に偏った攻撃では今より早く尽きます
6. カーネルの保持の推定の行:外側のソケットと LAN の側のソケットのカーネルのバッファの推定を、起動のログに別の行として加えるか。
   公開のログの変更です
7. UDP の昇格:UDP は shard 0 に置いたままにし、接続した UDP のセッションを別の shard へ昇格させる形は、UDP が shard 0 を詰まらせると測った時に決めるか
8. 内側の checksum:復号した手伝いが内側の checksum を確かめる形にします。
   AEAD で認証した packet の内側の checksum の確かめを省く形 (挙動の変更) は採らない、でよいか
9. 需要で育つバッファとの順序:S の予算の設計は、決定済みで未実装の全体の予算 G を前提にします。
   G の実装を S の製品への実装の前に行うか
10. 複数のセッション (F):外側の 1 つの流れのカーネルの受信の処理が上限だと測った時に、agent が shard ごとにトンネルのアドレスと鍵を持つ形 (制御プレーンと wire の変更) を比べ直すか
