# 並列のパケットエンジンの提案

この提案は、wgft の次の世代のパケットエンジンを複数の CPU で動かす構成を、骨格の水準で定めます。
状態は未採用の提案で、細部は試作と実装の時に決めます。
採用、製品の仕様の変更、マージは所有者の LGTM で決まります。

## 要約

推奨は、構成 U「unit と executor」です([構成の比較](architecture.md#s-と-u-の比べ))。

- front のスレッドは、外側のソケットを読み、datagram の順にその場で復号し、4 つ組で振り分けます。
  接続を作る表、UDP、WireGuard のセッションも front が持ちます
- TCP の接続は、作成の時に unit (接続の状態の区画) に置かれ、閉じるまで動きません
- 積み残しが無い間は、front のスレッドが全 unit をその場で実行するので、軽い負荷と中くらいの負荷は Inline とほぼ同じ経路です
- front が詰まった間だけ、重い unit を helper のスレッドに渡し、TCP の処理と暗号化と送り出しを分けます。
  unit 0 は常に front が実行します
- 利用できる CPU が 1 つの時は、核が今の核そのものです

U を推す理由は次のとおりです。

- 軽い負荷:CPU は Inline の 1.02 から 1.06 倍、遅れの増分は 1 µs 未満と見込みます(推定)。
  比べた形 S (持ち主のスレッドが常に実行する形) は、同じ負荷で 1.3 から 1.9 倍の CPU と、起床の分の遅れを払います(推定、[軽い負荷と中くらいの負荷](performance.md#軽い負荷と中くらいの負荷))
- 最大の負荷:多くの stream と受ける 1 stream で伸び、CPU が 2 つの時も送る向きの仕事が 2 つのスレッドに分かれます(推定)
- TCP の正しさ:1 つの unit を実行するスレッドは常に 1 つで、接続の状態機械のコードを変えません([TCP の状態機械が保たれる理由](ownership.md#tcp-の状態機械が保たれる理由))
- UDP:UDP はスレッドを移りません。
  送る向きでも、helper の送りの前に UDP を出し、UDP の前に並ぶ byte を Inline と同じ 1 バッチまでにします

U が得ないものと払うものは次のとおりです。

- 送る 1 stream:基本の設計では伸びません
- 大きな量の UDP:front の 1 つの CPU に収まる分までです
- データプレーンの作り直し:unit を別のスレッドで実行できるように、データプレーンを tokio を使わない executor に作り直します
- 止まった helper:許容を超えて止まった helper の unit の TCP の segment を、engine の中で捨てます
- 10 Gbit/s:届くかは未確認です([10 Gbit/s を決める上限](performance.md#10-gbits-を決める上限))

## 言葉と値の区別

- 送る向き:agent が LAN から受けたデータをトンネルへ送る向きです。
  受ける向きはその逆です
- 軽い負荷:Inline の最大の速さの 0.01 から 0.1 倍と、対話の往復です。
  中くらいの負荷は 0.25 から 0.5 倍です
- 積み残し:[積み残し](ownership.md#積み残し)の 1 つの意味だけに使います
- 段:[需要で育つバッファ](../../userspace/wgstack-buffers.md#予約と予算)の、接続の受信と送信の予約の大きさの段です

### 値の区別

- 測定:測った値です。
  公開の文書か PR にある値は、その出どころを書きます
- 測定 (未公開の記録):測った値で、公開の文書と PR にまだ無いものです。
  条件と値は、この提案を出す PR の本文に移します
- 推定:測定から導いた値か、測っていない見込みです
- 計算:書いた値から式で導いた値です
- 設計判断:この提案が選ぶ規則で、所有者の LGTM で確定します
- 未確認:確かめていない前提です

測定の条件は[性能の模型の測定の条件](performance.md#測定の条件)にあります。

## 範囲の外

- dial の製品への実装:この提案は dial を TCP の仕様として整理するだけです([TCP の能動の open](api.md#tcp-の能動の-open))
- 外のスレッドから接続を読み書きするライブラリの API
- 多くのピアを持つ server と、link の queue を増やす形 (複数のセッション、AF_XDP)
- 受信の窓と待ち行列の長さの制御

## 所有者に決めてもらうこと

1. 構成の採用:1 つのスレッドが受信と復号と接続の作成を持ち、TCP の接続を作成の時に状態の区画に置き、そのスレッドが詰まった時だけ別のスレッドが重い区画を実行する構成を採り、本物の LAN の側のソケットを使う試作から始めるか。
   採ると、CPU が 2 つ以上の時に、受信のスレッドが詰まった時の SYN と最後の ACK の捨てと、全体の予算が尽きた時の回収の順が今と変わります([今との違い](ownership.md#今との違い))
2. 軽い負荷と中くらいの負荷の後退:CPU が 2 つ以上の時に、Inline の最大の 0.5 倍以下の負荷で、byte あたりの CPU (線 1.05 倍) と対話の往復の遅れ (線 1.10 倍) が Inline より悪くなることを受け入れるか。
   推奨は受け入れないことで、試作で線を超えたらこの構成を見直します
3. 送る 1 stream:基本の設計では Inline と同じ速さです。
   伸ばす既知の方法は 1 本の flow の暗号化を別のスレッドで手伝う形で、2026-11-05 に止めた暗号の worker (#808 から #810) と同じ種類です。
   その形は送る向きで 1.41 から 1.63 倍 (1 stream の組で 1.378 倍) を得て、"UDP p50 at 4 vCPU fixed load 0.13 to 0.39 ms, CPU per byte 1.10 to 1.19 times under data-plane CPU contention, and 8.4 MiB more resident memory at 8 vCPU" を払いました。
   暗号だけを移す形の上限は約 1.24 倍です(計算)。
   送る 1 stream を伸ばさないままにするか、この種類の形を後で評価するか
4. データプレーンの数:tokio を使わない executor のデータプレーンを全 OS で 1 つにするか (推奨)、今の tokio のデータプレーンを 1 つの CPU と Windows と macOS のために残して 2 つを持ち続けるか。
   1 つにすると Windows と macOS も作り直しの影響を受けますが、2 つの実装を保つ手間が無くなります。
   どちらでも、複数の CPU を使うのは Linux だけです
5. 止まりの許容:helper が止まった時に engine の中で TCP の segment を捨てずに耐える時間を、約 1.7 ms (メモリの増分約 4 MiB) にするか、長くしてメモリを増やすか。
   今は同じ止まりをカーネルのソケットのバッファが吸収し、捨てません([平文の置き場と unit の上限](memory.md#平文の置き場と-unit-の上限))
6. 受け入れの線:[受け入れの条件](verification.md#受け入れの条件)を採るか。
   主な値は、1 つの CPU の byte あたりの CPU の区間の上端 1.03 以下、UDP の p50 と p99 と jitter をすべての負荷と CPU の取り合いの下で 1.10 倍以下、2 CPU の送る 4 stream 1.25 倍以上、4 CPU の送る 4 stream 1.50 倍以上と受ける 1 stream 1.25 倍以上 (相手が詰まらない本物の I/O で判定) です。
   メモリの増分の線は P0 で測ってから決めます (今の見込みは 8 CPU で約 15.7 MiB)
