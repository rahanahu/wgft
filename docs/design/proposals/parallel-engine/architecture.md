# 並列のパケットエンジンの構成の比較 (N1)

この文書は、並列のパケットエンジンの構成の候補を比べ、推奨の構成 S を選んだ理由と、ほかの候補を採らない理由を示します。
未採用の提案で、採用は所有者の LGTM で決まります([提案の索引](README.md))。
値には、測定、推定、計算、設計判断の区別を付けます([値の区別](README.md#値の区別))。

## 構成を決める前提

構成を決める前提は、所有者の要件と、今の作りの事実です。

- 要件:TCP/IP の正しさ、UDP の低い遅れ、厳密なメモリの上界、byte あたりの CPU、flow の公平を守ります。
  今のコードとの互換、変更の大きさ、1 つの持ち主の設計との相性は制約にしません
- 1 コアの同等:CPU が 1 つの時は、今の Inline の経路と byte あたりの CPU と遅れが同じであることを求めます
- 用途:agent と server の WireGuard の経路に加えて、WireGuard の無い汎用の sans-IO の TCP/IP スタックと並列のエンジンとしても使えることを求めます
- agent の外側の流れ:agent のピアは server の 1 つだけで、外側の UDP の 4 つ組も 1 つです([WireGuard の device の層](../../v2/wireguard-device.md#キューと上界))。
  内側の TCP と UDP の流れは、すべて 1 つのセッションの暗号文として届きます
- server の外側の流れ:server の Device は多くの agent のピアに共有され、ピアごとにセッションを持ちます([dial の側](../../userspace/wgstack-dial.md#多くのエージェントが-1-つの-device-を分け合うこと))
- 今の核:wgstack の核は 1 つの持ち主が `&mut` で呼ぶ sans-IO の値で、錠と atomic を持ちません([スレッドと所有](../../v2/wgstack-rs.md#スレッドと所有))

## 判断を決める測った事実

次の値は構成の選択を直接左右します。
条件の詳しい形は[性能の模型](performance.md#模型に使う値)にあります。

| 事実 | 値 | 区別 |
|---|---|---|
| Inline の送る向きの壁 | 4 と 8 vCPU で 1 stream が 5,274 と 5,284 Mbit/s。agent の VM の CPU は約 1.0 で、1 つのスレッドが詰まりです | 測定 (分けたラボ、RTT 0、最大の負荷) |
| カーネルモードの送る向き | 8 vCPU の 4 stream で 9,083 Mbit/s | 測定 (同じ条件) |
| 暗号の割合 | 受ける向きのデータプレーンの CPU の 33.4%。送る向きはラボだけの受信の処理を除いた残りの約 3 分の 1 | 測定 (バッチの後の profile、1 回) |
| 1 packet の暗号 | 1,408 byte の暗号化 751 ns、復号 669 ns。64 byte は約 175 ns | 測定 (ホストの E コア、1 スレッドの microbench) |
| スレッドを起こす費用 | 起こしてから最初の命令まで p50 で VM の 4 vCPU 約 2.0 µs、8 vCPU 約 2.4 µs。10 ms 眠った後は 7 から 80 µs | 測定 (VM の中の microbench) |
| 受け渡しの往復 | 暗号の worker の起床 p50 3.3 µs と p99 8.4 µs、終わりに気付くまで p50 2.3 µs と p99 7.7 µs | 測定 (#810 の計測器つきの build、4 vCPU、送る向きの 0.25 倍の固定の負荷) |
| A+ の速さ | 4 と 8 vCPU で送る 1 stream が 1.41 から 1.49 倍、送る 4 stream が 1.61 から 1.63 倍、受ける 4 stream が 1.44 から 1.45 倍、受ける 1 stream が 1.02 から 1.04 倍 | 測定 (#808 から #810、Inline との組) |
| A+ の UDP の遅れ | 送る向きの 0.25 倍の負荷で UDP の往復の p50 が 0.130 ms から 0.392 ms (4 vCPU)、0.143 ms から 0.369 ms (8 vCPU) | 測定 (同じ組) |
| A+ の中くらいの負荷の CPU | 受ける向きの 0.5 倍の固定の負荷で byte あたりの CPU が 1.13 倍 (4 vCPU) と 1.21 倍 (8 vCPU)。VM の外の qemu の CPU も 1.05 から 1.16 倍 | 測定 (同じ組) |
| A+ のメモリ | 4 CPU 以上で 2 つ目の受信の置き場の分の約 8.4 MiB が増えます | 測定 (起動の時の確保の数え) |
| 分けた API の費用 | worker の無い 2 vCPU の送る 1 stream で byte あたりの CPU が 1.027 倍 | 測定 (同じ組、8 round) |

測った事実から、次の 5 点を構成の条件にします(設計判断)。

1. 外側の流れが 1 つなので、復号を並列にするには、1 つのセッションの datagram を複数のスレッドに分ける必要があります
2. スレッドを起こす費用は小さなバッチの暗号の費用より大きいので、軽い負荷の packet を別のスレッドへ渡しません
3. 中くらいの負荷で別のスレッドを使うと、byte あたりの CPU と VM の出入りが増えます。
   1 つのスレッドで足りる間は 1 つのスレッドで処理します
4. 持ち主が別のスレッドの終わりを同期して待つ形は、CPU の取り合いで待ちが延びるので採りません
5. 同時に持つバッチの置き場の数はメモリの上界に直接響くので、置き場を増やさずに重ねる形を選びます

## 候補

所有者が挙げた A から E に、F、G、H を加えて比べます。
A+ (#808 から #810) は候補ではなく、測った教訓の出どころとして扱います。

- A flow で分けた run-to-completion:各ワーカーが flow の集まりを持ち、読みから送り出しまで 1 つのスレッドで終えます
- B 全段の pipeline:読み、復号、TCP/IP、中継、暗号化、送り出しを段に分け、段ごとにスレッドを置きます
- C 混成の shard と pipeline:暗号を並列にし、TCP/IP を flow ごとに分け、UDP に低い遅れの道を置きます
- D 状態を共有する並列のスタック:どのワーカーもどの接続も処理し、接続の状態を錠で守ります
- E 独立した wgstack の複数のインスタンス:スタックを丸ごと N 個作り、flow を振り分けます
- F 複数のセッションへの分割:agent が複数の WireGuard のピア (外側の 4 つ組) を持ち、shard ごとに 1 つのセッションを使います
- G AF_XDP と DPDK の link の adapter:カーネルの UDP の経路を通らずに NIC の queue を読み書きします
- H 前段と後段の 2 段:前段が読みと復号と暗号化と送り出し、後段が TCP/IP と中継を持ちます

## 比較表

表の言葉は、良い、中程度、悪いの 3 段です。
理由は表の後の節にあります。

| 候補 | 実現性 | 期待の性能 | 同期の費用 | cache の効率 | メモリの効率 | 公平 | 低い遅れ |
|---|---|---|---|---|---|---|---|
| A | 良い | 1 つのセッションでは読み手が詰まり、Inline と同じ壁 | 良い | 良い | 良い | 中程度 | 良い |
| B | 中程度 | 最も遅い段が上限 | 悪い。packet ごとに段の数の受け渡し | 悪い。段ごとにデータが core を移ります | 中程度。段の間の queue の分 | 中程度 | 悪い。段ごとの起床が加わります |
| C | 中程度 | 暗号と TCP/IP の両方で伸びます | 中程度。バッチごとの受け渡し | 中程度 | 中程度 | 中程度 | 道の作りしだい |
| D | 悪い | 接続ごとの錠と状態の移動で伸びません | 悪い。packet ごとの錠 | 悪い | 中程度 | 中程度 | 中程度 |
| E | 中程度 | A と同じ壁。表が N 倍 | 良い | 良い | 悪い。固定の表と予算が N 倍か固定の分割 | 悪い。hash の偏り | 良い |
| F | 悪い。制御プレーンと wire の変更 | 多くの流れで伸びるが、1 stream は伸びません | 良い | 良い | 中程度 | 悪い。hash の偏り | 良い |
| G | 悪い。権限、driver、移植性 | link の費用を減らします | 構成による | 良い | 中程度。UMEM の分 | 構成による | 良い |
| H | 中程度 | 後段の 1 スレッドが上限 | 中程度。packet が必ず 1 回移ります | 中程度 | 中程度 | 中程度 | 悪い。軽い負荷でも受け渡し |
| S (C を詰めた形) | 中程度 | 詰まった時に暗号と重い flow で伸び、軽い負荷は Inline と同じ | 良い。詰まった時だけ塊ごと | 良い。軽い負荷は Inline と同じ | 中程度。平文の重なりとスタック | 中程度。昇格の偏り | 良い |

S の各欄は推定で、[段階の試作](verification.md#段階の試作)で確かめます。
S は、A の run-to-completion、E の独立性、H の平文の queue の利点を取り込みます。
G は S の link の adapter の 1 つとして、F は将来の link の形として、S の API が妨げないようにします。

## 推奨の構成 S

S は、shard 0 を今の Inline のまま保ち、shard 0 が詰まった時だけ、重い TCP の flow を別の shard へ一方向に移し (昇格)、暗号を順序つきで分ける構成です。
名前は「昇格と順序つきの暗号の分担」です。

### 役割

shard は、起動の時に CPU の数から決める N 本のワーカーのスレッドと、それぞれが持つ状態です([CPU の数ごとの動かし方](performance.md#cpu-の数ごとの動かし方))。
N は設定を持ちません。

- shard 0:今の Inline のデータプレーンのスレッドの仕事 (読み、復号、TCP/IP、UDP、中継、暗号化、送り出し) をすべて持ちます。
  加えて、昇格させた flow への振り分け、WireGuard のセッションの役、接続を作る表 (待ち受け、握手の途中、TIME_WAIT、再組み立て) を持ちます
- shard 1 から N-1:昇格を受けた TCP の接続の持ち主と、暗号の手伝いです
- 昇格:shard 0 が詰まった時だけ、最も多く運ぶ TCP の接続を 1 本ずつ別の shard へ移します。
  移すのは shard 0 からほかの shard への一方向で、戻しません
- 暗号の手伝い:読みや送りに積み残しがある時だけ、バッチを塊に分けて申し出ます。
  起きている shard が引き取り、引き取られなかった塊は申し出た shard が自分で行います

役割の持ち主と同期の点の正本は[所有の設計](ownership.md)です。

### 軽い負荷と中くらいの負荷

shard 0 が詰まっていない間は、昇格も申し出も起きず、データの経路は Inline と同じ 1 つのスレッドの run-to-completion です。
ほかの shard は眠ったままで、起こす費用も cache の移動も生じません。
A+ が UDP の p50 と中くらいの負荷の byte あたりの CPU を悪くした原因 (軽い負荷での受け渡しと起床) を、この規則で経路から外します(設計判断)。

### 詰まった時の受ける向き

1. shard 0 が外側のソケットからバッチを読み、datagram ごとに replay の前の確かめを行います
2. 読みがバッチの枠を満たしたか、遅れの予算の後にもデータが残った時だけ、バッチを byte の数で塊に分け、番号を付けて申し出ます
3. 起きている shard が塊を引き取って復号し、内側の checksum を確かめます。
   shard 0 は引き取られなかった塊を自分で復号します
4. shard 0 は番号の順に、終わった塊の replay を確定し、各 packet の 4 つ組を自分の接続の表で引きます
5. shard 0 の接続の packet は shard 0 の核がその場で処理し、昇格した接続の packet は持ち主の受け口の queue に載せます

### 詰まった時の送る向き

- shard 0 の接続:Inline と同じく shard 0 が作り、暗号化して送ります
- 昇格した接続:持ち主が segment を作り、セッションの錠の下で counter を予約し、暗号化して送ります。
  積み残しがある時は暗号化の塊を申し出て、持ち主の順の通りに送ります
- UDP:shard 0 が持ち、暗号化と送り出しをスレッドを移らずに行います

### 主な規則

- N = 1 の時は、今の Inline の経路そのものを使います。
  queue、申し出の板、atomic を経路に置きません(設計判断)
- UDP のセッションは、外側のソケットの準備で起きる shard 0 が持ちます。
  軽い負荷の UDP を別のスレッドへ渡すと、眠った後の起床の 7 から 80 µs (測定) が datagram ごとに加わるためです
- 誰もほかのスレッドの終わりを同期して待ちません
- 受信の暗号文の置き場は Inline と同じ 1 つです。
  復号を終えた枠から順に返し、空いた枠の数で次の読みの大きさを決めます(設計判断)
- flow の中の順は、shard 0 の 1 つの振り分けの順と、持ち主の 1 つの queue で保ちます([スレッドの間の packet の順](ownership.md#スレッドの間の-packet-の順))

### link と変換の層

S は、link の adapter (WireGuard の UDP、平らな UDP、TUN、ライブラリの直接の呼び出し、将来の AF_XDP) と、トンネルの変換 (WireGuard か何もしない変換) を、shard の核から分けます([API の境界](api.md))。
変換が無い時は暗号の分担が無くなり、昇格だけが残ります。
link が flow の hash で分けた複数の queue を持つ形は、将来の拡張として API で妨げません([link の queue の数と振り分け](ownership.md#link-の-queue-の数と振り分け))。

## 昇格を選んだ理由

shard へ flow を置く方式には、新しい flow を最初から shard 0 以外に置く「分散」と、S の「昇格」があります。
分散は、TCP の packet が負荷によらず必ず shard 0 から持ち主へ移るので、中くらいの負荷でも起床と cache の移動の費用を払います。
A+ の中くらいの負荷の測定 (byte あたりの CPU が 1.13 から 1.21 倍) は、軽い負荷での受け渡しがこの費用を生むことを示しています。
昇格は、1 つのスレッドで足りる間は Inline と同じで、足りない時だけ並列の費用を払います。

昇格の代わりに払うものは次のとおりです。

- 接続を移す手順:接続の状態を値として移すこと、タイマーと出力の list の付け替え、中継の状態の移しが要ります([昇格](ownership.md#昇格))
- 接続の入れ替わりが支配する負荷:短い接続は昇格する前に終わるので、shard 0 が上限になります(推定)。
  そのような負荷では、確立の時に昇格させる規則で分けます
- 公平:shard 0 に残る flow と昇格した flow で、CPU の取り分が違いえます([flow の公平とワーカーの公平](performance.md#flow-の公平とワーカーの公平))

## 採らない候補とその理由

### A flow で分けた run-to-completion

A は、外側の流れが 1 つの agent では、1 つのスレッドがすべての datagram を読んで復号するので、Inline と同じ壁に当たります。
暗号の割合 (受ける向きで 33.4%、測定) が読み手に残るためです。
S は A の run-to-completion と持ち主の 1 つの性質を保ち、暗号だけを順序つきで分けます。

### B 全段の pipeline

B は、N = 1 で成り立たないので、1 コアの同等を満たせません。
packet は段の数だけスレッドを移り、受け渡しの往復は暗号の worker で 15 から 20 µs かかりました (測定、#810 の計測器の段の和)。
軽い負荷の UDP は段ごとの起床を待つので、A+ で見た p50 の悪化 (2.3 から 2.9 倍、測定) より大きくなると見込みます(推定)。
段の費用の釣り合いは負荷の形で変わり、最も遅い段が全体の上限になります。

### D 状態を共有する並列のスタック

D は、大きな flow の連続した segment を別々のワーカーが処理するので、接続の状態 (TCB、受信と送信の輪、SACK の記録) の cache line が packet ごとに core の間を移ります。
接続ごとの錠は、同じ flow の packet が続く大きな flow では、ほぼ毎回競合します(推定)。
flow の中の順を保つには、結局ワーカーの間で順序を付ける仕組みが要り、錠の費用だけが残ります。
TCP の状態機械と回復の論理は今の 1 つの持ち主を前提に書かれていて、錠を入れると不変条件の検査と bit の一致の試験を作り直すことになります。

### E 独立した wgstack の複数のインスタンス

E は、スタックごとに固定の表 (待ち受けと UDP の endpoint の 65,536 行の表、TIME_WAIT の表、知らせの表) を作るので、固定の費用が N 倍になります([wgstack の上界の表](../../v2/wgstack-bound.md)の `listeners`、`udp_endpoints`、`tw`)。
予算を N 個に固定で分けると、1 つの大きな flow が使える予算が 1/N になり、分けなければ共有の予算が要ります。
IPv4 の 2 つ目以降の断片はポートを持たないので、インスタンスへの振り分けは再組み立ての後でしかできません。
WireGuard のセッションが 1 つなので、復号と replay は結局インスタンスの外で 1 か所に集まります。
S は E の独立性 (shard ごとの run-to-completion) を保ち、共有が要る部分を shard 0 と全体の予算に置きます。

### F 複数のセッションへの分割

F は、shard ごとに独立した外側の流れを持つので、カーネルの受信の処理も複数の CPU に分かれ、shard の間の同期がほぼ無くなります。
server の cryptokey routing は 1 つのトンネルのアドレスを 1 つのピアに結ぶので、F には agent が shard ごとにトンネルのアドレスと鍵を持ち、server が流れごとにアドレスを選ぶ変更が要ります。
wgft は両端を持つので実現はできますが、登録、wire、server の転送の規則、カーネルモードの server の設定を変えます(推定)。
1 つの TCP の stream は 1 つのセッションに乗るので、1 stream で暗号を並列にする要件を満たしません。
流れの hash の振り分けは、少数の大きな flow で偏ります。
たとえば 4 本の flow が 4 つの shard に 1 本ずつ乗る確率は 4! / 4^4 で約 9.4% です(計算)。
S を先に作り、外側の流れが 1 つであることがカーネルの受信の処理で上限になると測った時に、F を link の queue を増やす形として比べ直します([10 Gbit/s を決める上限](performance.md#10-gbits-を決める上限))。

### G AF_XDP と DPDK

G は、root か特別な権限、対応した driver、NIC の queue の専有を求め、Windows と macOS では使えません。
仮想の NIC では zero-copy の形が使えないことが多いと見込みます(推定、未確認)。
今の決定は AF_XDP と DPDK を使わないことです([バッチの作りの規則](../../v2/agent-throughput.md#バッチの作りの規則))。
S は link の adapter の境界で、AF_XDP の UMEM の枠を短い寿命の借用として受け、長く持つデータを予算のある置き場に写す形を許します([link の adapter](api.md#link-の-adapter))。

### H 前段と後段の 2 段

H は、復号の後の平文の queue を wgft が持つので、FQ-CoDel をそのまま当てられる形として検討されました。
しかし後段の TCP/IP が 1 つのスレッドなので、多くの stream でも後段が上限になり、軽い負荷でも packet が必ず 1 回スレッドを移ります。
S では、昇格した接続の持ち主の受け口の queue が wgft の持つ平文の queue になるので、詰まった時に限って H の利点を使えます([満ちた queue の扱い](performance.md#満ちた-queue-の扱い))。

## S が依存する未確認の前提

S の利点は次の前提に依存し、どれも[段階の試作](verification.md#段階の試作)で確かめます。

- 振り分けの packet あたりの費用 (4 つ組の検索と持ち主の判定、queue への載せ) が、今の核の入口の検索に 50 ns 以下しか加えないこと(推定)
- 申し出と引き取りの費用が塊あたり 1 µs 以下で、8 から 16 µs の大きさの塊で引き合うこと(推定)
- 復号したスレッドと持ち主が違う時の cache の移動の費用が、詰まった時の byte あたりの CPU の 10% 以下に収まること(推定)
- shard 0 の詰まりを、自分の時刻の読みから安く判定でき、昇格が振動しないこと(推定)
- 送る counter を shard の間で交互に予約しても、相手の replay の窓の内に収まること。
  相手の実装の窓の幅は未確認です([WireGuard のセッションと counter](ownership.md#wireguard-のセッションと-counter))
- 外側の 1 つの流れのカーネルの受信の処理が、10 Gbit/s より前に上限にならないこと(未確認)
