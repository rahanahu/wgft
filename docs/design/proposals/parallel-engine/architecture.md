# 並列のパケットエンジンの構成の比較 (N1)

この文書は、並列のパケットエンジンの構成の候補を比べ、推奨の構成 U を選んだ理由と、ほかの候補を採らない理由を示します。
未採用の提案で、採用は所有者の LGTM で決まります([提案の索引](README.md))。
値には、測定、推定、計算、設計判断の区別を付けます([値の区別](README.md#値の区別))。

## 構成を決める前提

- 要件:TCP/IP の正しさ、UDP の低い遅れ、厳密なメモリの上界、byte あたりの CPU、flow の公平を守ります。
  今のコードとの互換、変更の大きさ、1 つの持ち主の設計との相性は制約にしません
- 1 コアの同等:CPU が 1 つの時は、今の Inline の経路と byte あたりの CPU と遅れが同じであることを求めます
- 負荷の分布:家の回線の agent は、ほとんどの時間を Inline の最大の速さの 0.1 倍より下の軽い負荷 (SSH、web、ゲームの制御) で過ごすと見込みます(推定)。
  軽い負荷と中くらいの負荷で Inline より悪くならないことを、最大の負荷の伸びと同じ重さで扱います
- 範囲:agent の WireGuard の経路が対象で、Linux を先にします。
  Windows と macOS は今の Inline のまま動きます([範囲の外](README.md#範囲の外))
- agent の外側の流れ:agent のピアは server の 1 つだけで、外側の UDP の 4 つ組も 1 つです([WireGuard の device の層](../../v2/wireguard-device.md#キューと上界))
- 今の核:wgstack の核は 1 つの持ち主が `&mut` で呼ぶ sans-IO の値で、錠と atomic を持ちません([スレッドと所有](../../v2/wgstack-rs.md#スレッドと所有))

## 判断を決める測った事実

公開の文書か PR にある値は出どころを書きます。
公開されていない記録の値は「測定 (未公開の記録)」とし、条件を[模型に使う値](performance.md#模型に使う値)に書きます。

| 事実 | 値 | 区別 |
|---|---|---|
| Inline の送る向きの壁 | 4 と 8 vCPU で 1 stream が約 5.3 Gbit/s。agent の VM の CPU は約 1.0 | 測定 (未公開の記録) |
| 受信の暗号の手伝い | 25 µs の遅れの予算で受信の回は 12 から 16 datagram。8 KiB の閾値で速さが変わらずに byte あたりの CPU が 27% 増。「眠った worker を起こす費用が、20 µs の回の暗号で省ける分とほぼ同じ」 | 測定 (#808 のコメント) |
| スレッドを起こす費用 | 起こしてから最初の命令まで p50 で VM の 4 vCPU 約 2.0 µs、8 vCPU 約 2.4 µs (5 から 100 µs 眠った後) | 測定 (#809) |
| 長く眠った後の起床 | 10 ms 眠った後は 7 から 80 µs | 測定 (未公開の記録) |
| A+ の結果 | 閉じのコメントの文は "4 and 8 vCPU send throughput 1.41 to 1.63 times Inline; costs: UDP p50 at 4 vCPU fixed load 0.13 to 0.39 ms, CPU per byte 1.10 to 1.19 times under data-plane CPU contention, and 8.4 MiB more resident memory at 8 vCPU" です | 測定 (#808 から #810 の閉じのコメント) |
| packet あたりの CPU | バッチの前の Inline で、送る向き 6.5 µs、受ける向き 2.4 µs | 測定 ([CPU の行き先](../../v2/agent-throughput.md#cpu-の行き先)) |

測った事実から、次の 4 点を構成の条件にします(設計判断)。

1. 受信の暗号を datagram の塊で別のスレッドに分ける形は、今のバッチの大きさでは引き合いません (#808)。
   受信の復号は 1 つのスレッドがその場で行います
2. 起床の費用は小さなバッチの仕事より大きいので、軽い負荷の packet のために別のスレッドを起こしません
3. 誰もほかのスレッドの終わりを同期して待ちません
4. 同時に持つバッチの置き場の数はメモリの上界に直接響くので、受信の暗号文の置き場を 1 つに保ちます

## 候補

所有者が挙げた A から E に、F、G、H を加え、詰めた 2 つの形 S と U を比べます。

- A flow で分けた run-to-completion:各ワーカーが flow の集まりを持ち、読みから送り出しまで 1 つのスレッドで終えます
- B 全段の pipeline:段ごとにスレッドを置きます
- C 混成の shard と pipeline:暗号を並列にし、TCP/IP を flow ごとに分け、UDP に低い遅れの道を置きます
- D 状態を共有する並列のスタック:どのワーカーもどの接続も処理し、接続の状態を錠で守ります
- E 独立した wgstack の複数のインスタンス:スタックを丸ごと N 個作り、flow を振り分けます
- F 複数のセッションへの分割:agent が複数の WireGuard のピア (外側の 4 つ組) を持ちます
- G AF_XDP と DPDK の link の adapter:カーネルの UDP の経路を通らずに NIC の queue を読み書きします
- H 前段と後段の 2 段:前段が読みと暗号、後段が TCP/IP と中継を持ちます
- S 作成の時の配置:C を詰めた形で、front のスレッドが読みと復号と接続の作成を持ち、TCP の接続を作成の時に持ち主のスレッドに置き、持ち主のスレッドが常にその接続を実行します
- U unit と executor:S の状態の分け方を保ち、状態の区画 (unit) と実行のスレッド (executor) を分けます。
  積み残しが無い間は front のスレッドが全 unit をその場で実行し、積み残しがある間だけ helper のスレッドが unit を実行します

|---|---|---|---|---|---|---|---|

| B | 中程度 | 最も遅い段が上限 | 悪い | 悪い | 中程度 | 中程度 | 悪い |
| C | 中程度 | 暗号と TCP/IP の両方で伸びます | 中程度 | 中程度 | 中程度 | 中程度 | 道の作りしだい |

## S と U の比べ

S と U は、状態の持ち方 (front の表、unit ごとの接続、作成の時の配置、閉じるまで動かさない接続) が同じで、どのスレッドが unit を実行するかだけが違います。

| 負荷 | S | U | 区別 |
|---|---|---|---|
| 軽い負荷 (Inline の最大の 0.01 から 0.1 倍、対話) | 持ち主に届く TCP の受信のバッチごとに眠った持ち主を起こします。packet あたりの CPU は Inline の 2.3 から 4.3 倍、受けた segment の遅れは起床の 2 から 80 µs が加わります | front のスレッドがその場で実行します。packet あたりの CPU は Inline の 1.05 倍以下、遅れの増分は 1 µs 未満 | 推定 |
| 中くらいの負荷 (0.25 から 0.5 倍) | byte あたりの CPU が Inline の 1.15 から 1.75 倍 | 積み残しが無いので軽い負荷と同じで、1.05 倍以下 | 推定 |
| 最大の負荷 | 持ち主のスレッドが unit を実行します | helper のスレッドが unit を実行し、S と同じ分担になります | 推定 |
| 大きな flow が揃うまで | 0 | 積み残しに入る判定 (8 回の起床、約 0.4 ms) と、起床ごとに 1 つの unit の受け渡し | 推定 |
| 変更の大きさ | 中継は shard ごとの tokio の実行環境で今の形のまま | 中継を unit ごとの状態機械と、executor ごとの poller に作り直します | 設計判断 |

数の出どころは[軽い負荷と中くらいの負荷](performance.md#軽い負荷と中くらいの負荷)にあります。
U は軽い負荷と中くらいの負荷で S の後退を持たず、最大の負荷で S と同じ分担になるので、U を推します。
払うのは中継の作り直しと、unit を executor の間で受け渡す手順です。

## 推奨の構成 U

所有の正本は[所有と同期の設計](ownership.md)です。

### 状態と実行の分け方

- front の状態:外側のソケット、WireGuard のセッション、4 つ組の表、待ち受け、accept の待ち行列、握手の途中、TIME_WAIT と FIN_WAIT_2 の行、再組み立て、UDP を持ちます。
  front のスレッドだけが実行します
- unit:TCP の接続の区画です。
  接続の核の状態、タイマー、中継の状態、LAN の側のソケットを持ち、接続は作成の時に unit に置かれて閉じるまで動きません
- executor:unit を実行するスレッドです。
  front のスレッドと、n_cpu - 1 本の helper のスレッドがあります (n_cpu は利用できる CPU の数)
- 実行の権利:各 unit は、ある時点で 1 つの executor (持ち主の executor) だけが実行します。
  権利は積み残しの始まりと終わりにだけ、決まった手順で受け渡します
- n_cpu = 1:unit も helper も作らず、今の Inline の経路そのものを使います

### 軽い負荷と中くらいの負荷

積み残しが無い間は、全 unit の持ち主の executor は front のスレッドです。
front のスレッドは、復号した TCP の packet を unit の受け口の輪に載せ、同じ起床の中でその unit を実行します。
暗号化も今の `Device::handle_packet` の 1 回の呼び出しで行うので、Inline と違うのは unit の輪と unit ごとの表を通る費用だけです。

### 積み残しがある時

積み残しは、front のスレッドの起床が遅れの予算を使い切り、その後にも外側のソケットにデータが残ることが、続けて 8 回起きた状態です([積み残しの定義](ownership.md#積み残しの定義))。
積み残しの間、front のスレッドは直近の受信の packet が多い unit から順に、起床ごとに 1 つずつ helper に渡します。
helper は渡された unit を実行し、暗号化に使う counter を front から借ります。
積み残しが 100 ms 続けて無ければ、unit を 1 つずつ front のスレッドに戻します。

## 採らない候補とその理由

### S 作成の時の配置

S は最大の負荷で U と同じ分担を得ますが、軽い負荷と中くらいの負荷で、持ち主のスレッドの起床の CPU と遅れを払います。
agent が多くの時間を過ごす負荷で後退するので、採りません。

### 昇格 (以前の案)

全部の接続を front で始め、詰まった時に動いている接続を別のスレッドへ移す形です。
移した接続は負荷が下がった後も費用を払い続け、移す手順と閉じる手順がスレッドの間の知らせになるので、U の前の段の検討で採らないことにしました。

### A flow で分けた run-to-completion

外側の流れが 1 つの agent では、1 つのスレッドがすべての datagram を読んで復号するので、Inline と同じ壁に当たります。
U は A の run-to-completion を unit の中で保ちます。

### B 全段の pipeline

1 つの CPU では成り立たず、軽い負荷の packet が段ごとの起床を待ちます。

### C 混成の shard と pipeline

S と U は C を詰めた形です。
受信の暗号の並列は #808 の結果で基本の設計から外し、TCP の flow ごとの分割と UDP の低い遅れの道を保ちます。

### D 状態を共有する並列のスタック

大きな flow の連続した segment を別々のワーカーが処理するので、接続の状態の cache line が packet ごとに core の間を移り、接続ごとの錠がほぼ毎回競合します(推定)。

### E 独立した wgstack の複数のインスタンス

スタックごとに 65,536 行の待ち受けと UDP の endpoint の表を作るので、固定の費用が N 倍になります([wgstack の上界の表](../../v2/wgstack-bound.md))。
WireGuard のセッションが 1 つなので、復号と replay は結局 1 か所に集まります。
U は接続を作る表を front に 1 つだけ持ち、unit の核はポートの表を持ちません。

### F 複数のセッションへの分割

server の cryptokey routing は 1 つのトンネルのアドレスを 1 つのピアに結ぶので、agent が unit ごとにトンネルのアドレスと鍵を持つ変更が要ります。
1 つの TCP の stream は 1 つのセッションに乗るので 1 stream は伸びず、4 本の flow が 4 つの区画に 1 本ずつ乗る確率は 4! / 4^4 で約 9.4% です(計算)。
外側の 1 つの流れのカーネルの受信の処理が上限だと測った時に比べ直します([10 Gbit/s を決める上限](performance.md#10-gbits-を決める上限))。

### G AF_XDP と DPDK

root か特別な権限、対応した driver、NIC の queue の専有を求め、Windows と macOS では使えません。
今の決定は AF_XDP と DPDK を使わないことです([バッチの作りの規則](../../v2/agent-throughput.md#バッチの作りの規則))。

### H 前段と後段の 2 段

後段の TCP/IP が 1 つのスレッドなので、多くの stream でも後段が上限になり、軽い負荷でも packet が必ず 1 回スレッドを移ります。
U の積み残しの間の受ける 1 stream は H と同じ 2 段になりますが、積み残しが無い間は移りません。

## U が依存する未確認の前提

- front のスレッドが unit をその場で実行する費用が、packet あたり 0.1 µs 以下であること(推定)
- 積み残しの判定が小さな山で動かず、helper の起床が無駄にならないこと(推定)
- front のスレッドが復号と振り分けを続けても、多くの stream の受信で上限にならないこと([役ごとの費用の模型](performance.md#役ごとの費用の模型))
- 中継を tokio の外の状態機械に作り直しても、今の中継の挙動と上界を保てること(推定)
- 外側の 1 つの流れのカーネルの受信の処理と、外側のソケットへの並んだ送り出しが、10 Gbit/s より前に上限にならないこと(未確認)
