# 並列のパケットエンジンの構成の比較 (N1)

この文書は、並列のパケットエンジンの構成の候補を比べ、推奨の構成 U を選んだ理由と、ほかの候補を採らない理由を示します。
未採用の提案で、採用は所有者の LGTM で決まります([提案の索引](README.md))。
値には、測定、推定、計算、設計判断の区別を付けます([値の区別](README.md#値の区別))。

## 構成を決める前提

- 要件:TCP/IP の正しさ、UDP の低い遅れ、厳密なメモリの上界、byte あたりの CPU、flow の公平を守ります。
  今のコードとの互換と変更の大きさは制約にしません
- 1 コアの同等:CPU が 1 つの時は、今の Inline と byte あたりの CPU と遅れが同じであることを求めます
- 負荷の分布:家の回線の agent は、ほとんどの時間を Inline の最大の速さの 0.1 倍より下の軽い負荷で過ごすと見込みます(推定)。
  軽い負荷と中くらいの負荷で Inline より悪くならないことを、最大の負荷の伸びと同じ重さで扱います
- agent の外側の流れ:agent のピアは server の 1 つだけで、外側の UDP の 4 つ組も 1 つです([WireGuard の device の層](../../v2/wireguard-device.md#キューと上界))
- 今の核:wgstack の核は 1 つの持ち主が `&mut` で呼ぶ sans-IO の値です([スレッドと所有](../../v2/wgstack-rs.md#スレッドと所有))

## 判断を決める測った事実

| 事実 | 値 | 区別 |
|---|---|---|
| Inline の送る向きの壁 | 4 と 8 vCPU で 1 stream が約 5.3 Gbit/s。agent の VM の CPU は約 1.0 | 測定 (未公開の記録) |
| 受信の暗号の手伝い | 25 µs で区切る受信の回は 12 から 16 datagram。8 KiB の閾値で速さが変わらずに byte あたりの CPU が 27% 増 | 測定 (#808 のコメント) |
| スレッドを起こす費用 | 起こしてから最初の命令まで p50 で VM の 4 vCPU 約 2.0 µs、8 vCPU 約 2.4 µs。受け渡し 1 回あたり約 4 µs の CPU | 測定 (#808、#809 の本文) |
| 長く眠った後の起床 | 10 ms 眠った後は 7 から 80 µs | 測定 (未公開の記録) |
| Inline の起床ごとの仕事 | 起床ごとに約 8.5 µs、packet ごとに約 0.57 µs | 推定 ([受ける向きの達成](../../v2/agent-throughput.md#バッチの作り)の 2 点からの見積もり) |
| A+ の結果 | 閉じのコメントの文は "4 and 8 vCPU send throughput 1.41 to 1.63 times Inline; costs: UDP p50 at 4 vCPU fixed load 0.13 to 0.39 ms, CPU per byte 1.10 to 1.19 times under data-plane CPU contention, and 8.4 MiB more resident memory at 8 vCPU" です | 測定 (#808 から #810) |

測った事実から、次の 4 点を構成の条件にします(設計判断)。

1. 受信の暗号を datagram の塊で別のスレッドに分ける形は、今のバッチの大きさでは引き合いません (#808)。
   受信の復号は 1 つのスレッドがその場で行います
2. 起床の費用は小さなバッチの仕事より大きいので、軽い負荷の packet のために別のスレッドを起こしません
3. 誰もほかのスレッドの終わりを同期して待ちません
4. 受信の暗号文の置き場を 1 つに保ちます

## 候補

- A flow で分けた run-to-completion:各ワーカーが flow の集まりを持ち、読みから送り出しまで 1 つのスレッドで終えます
- B 全段の pipeline:段ごとにスレッドを置きます
- C 混成の shard と pipeline:暗号を並列にし、TCP/IP を flow ごとに分け、UDP に低い遅れの道を置きます
- D 状態を共有する並列のスタック:どのワーカーもどの接続も処理し、接続の状態を錠で守ります
- E 独立した wgstack の複数のインスタンス
- F 複数のセッションへの分割:agent が複数の WireGuard のピア (外側の 4 つ組) を持ちます
- G AF_XDP と DPDK の link の adapter
- H 前段と後段の 2 段:前段が読みと暗号、後段が TCP/IP と中継を持ちます
- S 作成の時の配置:C を詰めた形で、TCP の接続を作成の時に持ち主のスレッドに置き、そのスレッドが常に実行します
- U unit と executor:S の状態の分け方を保ち、状態の区画 (unit) と実行のスレッド (executor) を分けます。
  積み残しが無い間は front のスレッドが全 unit をその場で実行し、積み残しの間だけ helper が unit を実行します

## 比較表

表の言葉は、良い、中程度、悪いの 3 段で、S と U の欄は推定です。

| 候補 | 実現性 | 期待の性能 | 同期の費用 | cache の効率 | メモリの効率 | 公平 | 低い遅れ |
|---|---|---|---|---|---|---|---|
| A | 良い | 1 つのセッションでは読み手が詰まり、Inline と同じ壁 | 良い | 良い | 良い | 中程度 | 良い |
| B | 中程度 | 最も遅い段が上限 | 悪い | 悪い | 中程度 | 中程度 | 悪い |
| C | 中程度 | 暗号と TCP/IP の両方で伸びます | 中程度 | 中程度 | 中程度 | 中程度 | 道の作りしだい |
| D | 悪い | 錠と状態の移動で伸びません | 悪い | 悪い | 中程度 | 中程度 | 中程度 |
| E | 中程度 | A と同じ壁 | 良い | 良い | 中程度 | 悪い | 良い |
| F | 悪い。制御プレーンと wire の変更 | 1 stream は伸びません | 良い | 良い | 中程度 | 悪い | 良い |
| G | 悪い。権限、driver、移植性 | link の費用を減らします | 構成による | 良い | 中程度 | 構成による | 良い |
| H | 中程度 | 後段の 1 スレッドが上限 | 中程度 | 中程度 | 中程度 | 中程度 | 中程度 |
| S | 良い | 最大の負荷で伸び、軽い負荷で後退します | 悪い。軽い負荷でも受け渡しと起床 | 中程度 | 中程度 | 中程度 | 悪い |
| U | 中程度。データプレーンの作り直し | 最大の負荷で S と同じく伸び、軽い負荷は Inline に近い | 軽い負荷は良い。積み残しの間は S と同じ | 良い | 中程度 | 中程度 | 良い |

## S と U の比べ

S と U は、状態の持ち方が同じで、どのスレッドが unit を実行するかだけが違います。

| 負荷 | S | U | 区別 |
|---|---|---|---|
| 軽い負荷 (0.01 から 0.1 倍、対話) | 受けた TCP のバッチごとに眠った持ち主を起こします。1 packet の起床で Inline の 9.1 µs に 3 から 8 µs が加わり、CPU は 1.3 から 1.9 倍です。受けた segment には起床の 2 から 80 µs が加わります | front がその場で実行します。unit の輪と unit の epoll を読む system call で、CPU は Inline の 1.02 から 1.06 倍、遅れの増分は 1 µs 未満です | 推定 |
| 中くらいの負荷 (0.25 から 0.5 倍) | front の毎秒 2 万から 4 万回の起床ごとに持ち主を起こし、0.06 から 0.32 CPU が加わります。0.5 CPU の Inline に対し 1.12 から 1.64 倍です | 積み残しに入らないので、軽い負荷と同じです | 推定 |
| 積み残しの間 | 持ち主のスレッドが実行します | helper が実行し、S と同じ受け渡しと起床を払います。counter の在庫の補充の起床が 64 datagram ごとに最大 2 回加わります | 推定 |
| 大きな flow が揃うまで | 0 | 入る判定の約 0.6 ms と、起床ごとに 1 つの unit の受け渡し | 推定 |
| 変更の大きさ | 中継は shard ごとの tokio の実行環境で今の形のまま | データプレーンを tokio を使わない executor に作り直します | 設計判断 |

U は軽い負荷と中くらいの負荷で S の後退を持たず、積み残しの間は S と同じ分担になるので、U を推します。
払うのはデータプレーンの作り直しと、unit の受け渡しの手順です。
tokio を executor ごとに持つ形にしないのは、中継の future が `Rc` を持つので別のスレッドへ動かせず、tokio の task も実行環境の間を移れないためです。

## 推奨の構成 U

所有の正本は[所有と同期の設計](ownership.md)です。

- front のスレッド:外側のソケット、WireGuard のセッション、4 つ組の表、待ち受け、握手の途中、行の表、再組み立て、UDP と、unit 0 を持ちます
- unit:TCP の接続の区画で、接続は作成の時に置かれて閉じるまで動きません。
  unit の数は helper の数 H に 1 を加えた M = H + 1 です
- helper:helper i は unit i を、積み残しの間だけ実行します。
  unit 0 は常に front が実行するので、CPU が 2 つの時も積み残しの間に送る向きの仕事が 2 つのスレッドに分かれます
- 積み残し:front の起床が続けて予算を使い切った時に入り、front の時間の 10% 以上を使う unit を渡し、front と helper の忙しさの和が 0.6 CPU を下回った unit を戻します([積み残し](ownership.md#積み残し))
- CPU が 1 つの時:unit を分けず、front の核が今の核そのものです

## 採らない候補とその理由

### S 作成の時の配置

軽い負荷と中くらいの負荷で、持ち主のスレッドの起床の CPU と遅れを払います。
agent が多くの時間を過ごす負荷で後退するので、採りません。

### 昇格 (以前の案)

全部の接続を front で始め、詰まった時に動いている接続を別のスレッドへ移す形です。
移した接続は負荷が下がった後も費用を払い続け、移す手順と閉じる手順がスレッドの間の知らせになるので、採りません。

### A、B、C、D

- A:外側の流れが 1 つの agent では、1 つのスレッドがすべての datagram を読んで復号するので、Inline と同じ壁に当たります
- B:1 つの CPU では成り立たず、軽い負荷の packet が段ごとの起床を待ちます
- C:S と U は C を詰めた形です。
  受信の暗号の並列は #808 の結果で基本の設計から外しました
- D:大きな flow の segment を別々のワーカーが処理するので、接続の状態が packet ごとに core の間を移り、錠がほぼ毎回競合します(推定)

### E 独立した wgstack の複数のインスタンス

WireGuard のセッションが 1 つなので、復号、replay、counter は結局 1 か所に集まり、インスタンスの独立は受信の側で成り立ちません。
U はその 1 か所を front とし、接続の区画だけを分けます。

### F 複数のセッションへの分割

server の cryptokey routing は 1 つのトンネルのアドレスを 1 つのピアに結ぶので、agent が区画ごとにトンネルのアドレスと鍵を持つ変更が要ります。
1 つの TCP の stream は 1 つのセッションに乗るので 1 stream は伸びず、hash の振り分けは少数の大きな flow で偏ります。
4 本の flow が 4 つの区画に 1 本ずつ乗る確率は 4! / 4^4 で約 9.4% です(計算)。
U も、静かに張られて後で重くなる接続は作成の時に区別できないので、同じ種類の偏りを持ちます。
U が F より良いのは、作成の時に重さが分かる接続を分けられる点と、1 つのセッションのまま作れる点です。

### G AF_XDP と DPDK

root か特別な権限、対応した driver、NIC の queue の専有を求め、Windows と macOS では使えません。
今の決定は AF_XDP と DPDK を使わないことです([バッチの作りの規則](../../v2/agent-throughput.md#バッチの作りの規則))。

### H 前段と後段の 2 段

後段の TCP/IP が 1 つのスレッドなので、多くの stream でも後段が上限になり、軽い負荷でも packet が必ず 1 回スレッドを移ります。

## U が依存する未確認の前提

- データプレーンを tokio を使わない executor に作り直しても、CPU と遅れが Inline と同じであること(推定)
- 積み残しの出入りが、続く最大の負荷と短い山の両方で落ち着くこと(推定)
- front のスレッドが復号と振り分けを続けても、多くの stream の受信で上限にならないこと([積み残しの間](performance.md#積み残しの間))
- 外側の UDP の流れ 1 本をカーネルが受信する処理と、外側のソケットへの並んだ送り出しが、10 Gbit/s より前に上限にならないこと(未確認)
