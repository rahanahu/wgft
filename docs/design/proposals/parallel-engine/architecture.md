# 並列のパケットエンジンの構成の比較 (N1)

この文書は、並列のパケットエンジンの構成の候補を比べ、推奨の構成 S を選んだ理由と、ほかの候補を採らない理由を示します。
未採用の提案で、採用は所有者の LGTM で決まります([提案の索引](README.md))。
値には、測定、推定、計算、設計判断の区別を付けます([値の区別](README.md#値の区別))。

## 構成を決める前提

- 要件:TCP/IP の正しさ、UDP の低い遅れ、厳密なメモリの上界、byte あたりの CPU、flow の公平を守ります。
  今のコードとの互換、変更の大きさ、1 つの持ち主の設計との相性は制約にしません
- 1 コアの同等:CPU が 1 つの時は、今の Inline の経路と byte あたりの CPU と遅れが同じであることを求めます
- 用途:agent の WireGuard の経路と、WireGuard の無い汎用の sans-IO の TCP/IP スタックとしての利用です
- 範囲の外:多くのピアを持つ server は、外側のアドレスでピアごとに shard に分ける形が自然ですが、この提案では設計しません。
  将来の拡張として API で妨げないことだけを扱います
- agent の外側の流れ:agent のピアは server の 1 つだけで、外側の UDP の 4 つ組も 1 つです([WireGuard の device の層](../../v2/wireguard-device.md#キューと上界))。
  内側の TCP と UDP の流れは、すべて 1 つのセッションの暗号文として届きます
- 今の核:wgstack の核は 1 つの持ち主が `&mut` で呼ぶ sans-IO の値で、錠と atomic を持ちません([スレッドと所有](../../v2/wgstack-rs.md#スレッドと所有))

## 判断を決める測った事実

公開の文書か PR にある値は出どころを書きます。
公開されていない記録の値は「測定 (未公開の記録)」とし、条件を[模型に使う値](performance.md#模型に使う値)に書きます。

| 事実 | 値 | 区別 |
|---|---|---|
| Inline の送る向きの壁 | 4 と 8 vCPU で 1 stream が約 5.3 Gbit/s。agent の VM の CPU は約 1.0 | 測定 (未公開の記録) |
| 受信の暗号の手伝いの結果 | 25 µs の遅れの予算で、受信の回は 12 から 16 datagram (17 から 23 KB)。32 KiB の閾値では手伝いが動かず、8 KiB では速さが変わらずに byte あたりの CPU が 27% 増えました。「眠った worker を起こす費用が、20 µs の回の暗号で省ける分とほぼ同じ」 | 測定 (#808 のコメント) |
| 分けた API の費用 | 手伝いが動かない時の byte あたりの CPU が 2 から 3.5% 増、速さが 2% 減 | 測定 (#808 のコメント) |
| スレッドを起こす費用 | 起こしてから最初の命令まで p50 で VM の 4 vCPU 約 2.0 µs、8 vCPU 約 2.4 µs (5 から 100 µs 眠った後) | 測定 (#809) |
| 長く眠った後の起床 | 10 ms 眠った後は 7 から 80 µs | 測定 (未公開の記録) |
| A+ の結果 | 4 と 8 vCPU の送る向きの速さが Inline の 1.41 から 1.63 倍。費用は 4 vCPU の固定の負荷の UDP の p50 が 0.13 から 0.39 ms、データの経路の CPU を取り合う時の byte あたりの CPU が 1.10 から 1.19 倍、8 vCPU で常駐のメモリが 8.4 MiB 増 | 測定 (#808 から #810 の所有者の閉じのコメント) |
| 暗号の割合 | 受ける向きのデータプレーンの CPU の 33.4% | 測定 (未公開の記録) |

測った事実から、次の 4 点を構成の条件にします(設計判断)。

1. 受信の暗号を datagram の塊で別のスレッドに分ける形は、今のバッチの大きさでは引き合いません (#808)。
   受信の復号は shard 0 がその場で行います
2. 起床の費用は小さなバッチの仕事より大きいので、packet ごとの受け渡しをしません。
   受け渡しは起床ごとに 1 回にまとめます
3. 誰もほかのスレッドの終わりを同期して待ちません
4. 同時に持つバッチの置き場の数はメモリの上界に直接響くので、受信の暗号文の置き場を 1 つに保ちます

## 候補

所有者が挙げた A から E に、F、G、H を加えて比べます。
A+ (#808 から #810) は候補ではなく、測った教訓の出どころとして扱います。

- A flow で分けた run-to-completion:各ワーカーが flow の集まりを持ち、読みから送り出しまで 1 つのスレッドで終えます
- B 全段の pipeline:読み、復号、TCP/IP、中継、暗号化、送り出しを段に分け、段ごとにスレッドを置きます
- C 混成の shard と pipeline:暗号を並列にし、TCP/IP を flow ごとに分け、UDP に低い遅れの道を置きます
- D 状態を共有する並列のスタック:どのワーカーもどの接続も処理し、接続の状態を錠で守ります
- E 独立した wgstack の複数のインスタンス:スタックを丸ごと N 個作り、flow を振り分けます
- F 複数のセッションへの分割:agent が複数の WireGuard のピア (外側の 4 つ組) を持ち、shard ごとに 1 つのセッションを使います
- G AF_XDP と DPDK の link の adapter:カーネルの UDP の経路を通らずに NIC の queue を読み書きします
- H 前段と後段の 2 段:前段が読みと復号と暗号化と送り出し、後段が TCP/IP と中継を持ちます

## 推奨の構成 S

S は、shard 0 が受信の全部と接続の作成を持ち、TCP の接続を作成の時に持ち主の shard に置いて閉じるまで動かさない構成です。
名前は「作成の時の配置」です。
所有の正本は[所有と同期の設計](ownership.md)です。

### 役割

- shard 0:外側のソケットを読み、datagram の順にその場で復号し、replay を確定し、4 つ組で持ち主へ振り分けます。
  待ち受け、accept の待ち行列、握手の途中、TIME_WAIT の行、再組み立て、UDP、WireGuard のセッションも持ちます
- 持ち主の shard:握手の最後か dial の時に置かれた TCP の接続を、閉じるまで持ちます。
  TCP の処理、中継、LAN の側のソケット、暗号化、送り出しを run-to-completion で行います
- N は起動の時の CPU の数から決め、設定を持ちません([CPU の数ごとの動かし方](performance.md#cpu-の数ごとの動かし方))
- N = 1 は今の Inline の経路そのものです

### 受ける向き

shard 0 は、今と同じ遅れの予算でバッチを読み、`Device::handle_datagram` の 1 回の呼び出しで復号します。
UDP はその場で中継へ渡し、TCP の packet は記述子を持ち主のデータの輪に載せます。
持ち主への公開と起床は、shard 0 の起床ごとに 1 回です。

### 送る向き

持ち主は、自分の接続の segment を作り、shard 0 から借りた counter と鍵で暗号化して、外側のソケットへ送ります([WireGuard のセッションと counter](ownership.md#wireguard-のセッションと-counter))。
錠を使わず、shard 0 が止まっても持ち主は借りた在庫の分だけ送り続けられます。

### 得るものと得ないもの

- 多くの stream:TCP の処理と暗号化と送り出しが持ち主の数だけ分かれます
- 受ける 1 stream:shard 0 の読みと復号と、持ち主の TCP と LAN の側の書き込みの 2 段に分かれます。
  上限の見積もりは[役ごとの費用の模型](performance.md#役ごとの費用の模型)にあります
- 送る 1 stream:持ち主の 1 つのスレッドが今の Inline と同じ仕事をするので、基本の設計では伸びません。
  1 本の大きな flow の暗号化を順序を保って手伝う形は、後の段です([後の段](performance.md#後の段))
- 大きな量の UDP:shard 0 の 1 つの CPU に収まる分までです

## 作成の時に置く理由

接続を置く時機には、次の 3 つがあります。

| 時機 | 中身 | 判断 |
|---|---|---|
| 作成の時 (S) | 握手の最後か dial の時に持ち主を決め、閉じるまで動かしません | 採ります |
| 昇格 | 全部を shard 0 で始め、shard 0 が詰まった時に重い接続を別の shard へ移します | 代わりの形として残します |
| 作成の時の負荷 | SYN の時の byte の数で選びます | 採りません。同時に張る stream は作成の時にどれも 0 byte です |

作成の時に置く利点は次のとおりです。

- 渡すのはデータを持つ前の接続だけで、動いている接続の移しが要りません([接続を持ち主に渡す手順](ownership.md#接続を持ち主に渡す手順))
- 持ち主が変わらないので、接続の状態は常に 1 つのスレッドだけが触ります
- 大きな flow が持ち主に揃うまでの時間が 0 です

払うものは、軽い負荷でも TCP の packet が shard 0 から持ち主へ移ることです。
N が 2 以上の時に Inline と違う点と、その費用の見積もりは[N が 2 以上の軽い負荷](performance.md#n-が-2-以上の軽い負荷)にあります。
この費用が受け入れの線を超えた時だけ、代わりの形の昇格を比べ直します。

## 代わりの形として残す昇格

昇格は、全部の接続を shard 0 で始め、shard 0 が詰まった時だけ重い TCP の接続を別の shard へ一方向に移す形です。
中くらいの負荷で Inline と同じ経路を保てる利点がありますが、次の問題が分かっています。

- 戻れない状態:一度移した接続は、負荷が下がった後もスレッドを移り続けます。
  大きな転送の後に静かになった長い接続は、軽い負荷で毎回起床の費用を払います
- 方針の矛盾と枠の尽き:確立の時の昇格と速さの上限が食い違い、移し先の固定の枠が静かな接続で埋まると、それ以上移せなくなります。
  100 ms の窓ごとに 1 本の上限では、16 本の大きな flow が揃うまで 1.6 秒以上かかります(計算)
- 閉じ方:移した接続の終わりと TIME_WAIT の使い直しが、shard の間の 3 つの知らせの手順になり、知らせを失う道が残ります

採る場合に要るものは次のとおりです。

- 戻し:持ち主が窓の間静かで shard 0 が線より下の時に、接続を shard 0 に戻す手順
- shard の間の移し:移し先の間の偏りを直す手順
- 窓ごとの数え:接続ごとの byte を窓の番号付きで数え、全体の走査をしない形
- 閉じる時の戻し:FIN を送るか受けた時に接続を shard 0 に戻し、終わりを今の 1 つのスレッドの論理で行う形

## 採らない候補とその理由

### A flow で分けた run-to-completion

A は、外側の流れが 1 つの agent では、1 つのスレッドがすべての datagram を読んで復号するので、Inline と同じ壁に当たります。
S は A の run-to-completion を持ち主の shard で保ち、読みと復号だけを shard 0 に集めます。

### B 全段の pipeline

B は、N = 1 で成り立たないので、1 コアの同等を満たせません。
packet は段の数だけスレッドを移り、軽い負荷の UDP は段ごとの起床を待ちます。
A+ の受け渡しで UDP の p50 が 0.13 ms から 0.39 ms に増えたこと (#808 から #810) は、段を加える形の遅れの費用を示しています。

### C 混成の shard と pipeline

S は C を詰めた形です。
C のうち、受信の暗号の並列は #808 の結果で基本の設計から外し、TCP の flow ごとの分割と UDP の低い遅れの道を保ちます。

### D 状態を共有する並列のスタック

D は、大きな flow の連続した segment を別々のワーカーが処理するので、接続の状態の cache line が packet ごとに core の間を移ります。
接続ごとの錠は、同じ flow の packet が続く大きな flow では、ほぼ毎回競合します(推定)。
flow の中の順を保つには、結局ワーカーの間で順序を付ける仕組みが要り、錠の費用だけが残ります。

### E 独立した wgstack の複数のインスタンス

E は、スタックごとに固定の表 (待ち受けと UDP の endpoint の 65,536 行の表、TIME_WAIT の表、知らせの表) を作るので、固定の費用が N 倍になります([wgstack の上界の表](../../v2/wgstack-bound.md))。
IPv4 の 2 つ目以降の断片はポートを持たないので、振り分けは再組み立ての後でしかできません。
WireGuard のセッションが 1 つなので、復号と replay は結局 1 か所に集まります。
S は接続を作る表を shard 0 に 1 つだけ持ち、接続の枠だけを持ち主に分けます。

### F 複数のセッションへの分割

F は、shard ごとに独立した外側の流れを持つので、カーネルの受信の処理も複数の CPU に分かれます。
server の cryptokey routing は 1 つのトンネルのアドレスを 1 つのピアに結ぶので、agent が shard ごとにトンネルのアドレスと鍵を持ち、server が流れごとにアドレスを選ぶ変更が要ります。
1 つの TCP の stream は 1 つのセッションに乗るので、1 stream は伸びません。
4 本の flow が 4 つの shard に 1 本ずつ乗る確率は 4! / 4^4 で約 9.4% で、hash の振り分けは少数の大きな flow で偏ります(計算)。
外側の 1 つの流れのカーネルの受信の処理が上限だと測った時に比べ直します([10 Gbit/s を決める上限](performance.md#10-gbits-を決める上限))。

### G AF_XDP と DPDK

G は、root か特別な権限、対応した driver、NIC の queue の専有を求め、Windows と macOS では使えません。
今の決定は AF_XDP と DPDK を使わないことです([バッチの作りの規則](../../v2/agent-throughput.md#バッチの作りの規則))。
S は link の adapter の境界で、link が貸す枠を短い寿命の借用として受け、スレッドをまたぐ前に置き場に写す形を許します([link の adapter](api.md#link-の-adapter))。

### H 前段と後段の 2 段

H は、後段の TCP/IP が 1 つのスレッドなので、多くの stream でも後段が上限になります。
S の受ける 1 stream は H と同じ 2 段になりますが、多くの stream は持ち主の数だけ分かれます。
H の利点の、wgft が順を決められる平文の queue は、S の持ち主ごとのデータの輪で得られます([満ちた queue の扱い](performance.md#満ちた-queue-の扱い))。

## S が依存する未確認の前提

S の利点は次の前提に依存し、どれも[段階の試作](verification.md#段階の試作)で確かめます。

- N が 2 以上の軽い負荷の byte あたりの CPU の増え方が、受け入れの線の内に収まること(推定)
- 振り分けの packet あたりの費用 (持ち主の判定、記述子の書き込み、block の参照の数) が数十 ns であること(推定)
- 平文が shard 0 から持ち主へ移る cache の費用が、byte あたりの CPU の 10% 以下であること(推定)
- shard 0 の読み、復号、振り分け、貸し出しの和が、多くの stream で上限にならないこと([役ごとの費用の模型](performance.md#役ごとの費用の模型))
- 外側の 1 つの流れのカーネルの受信の処理と、外側のソケットへの並んだ送り出しが、10 Gbit/s より前に上限にならないこと(未確認)
