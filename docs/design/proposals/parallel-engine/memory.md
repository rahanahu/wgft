# メモリの上界 (N3)

この文書は、推奨の構成 U のプロセス全体のメモリの上界を式で示し、全体と unit ごとの予算、置き場、尽きた時の規則を定めます。
未採用の提案です([提案の索引](README.md))。
上界の考え方は今の設計と同じく、上限の設定値ではなく実際に持てる量で数えます([上界の式の写し方](../../v2/wgstack-rs.md#上界の式の写し方))。
I1 から I7 の[不変条件](../../userspace/wgstack.md#不変条件)をそのまま守ります。

## 上界の原則

- 予算の印と置き場の枠を 1 つの値にし、byte を持つことと予算を持つことを同じ値の所有にします(設計判断)
- 置き場はすべて起動の時に容量を決めます。
  例外は今と同じく、予約の内側でだけ確保する 16 KiB の chunk と、流れごとの中継の状態です
- 予算は全体で 1 つ持ち、unit は credit として一部を借ります。
  credit の補充と返却は実行の終わりに行います
- 接続は unit を移らず、chunk と中継のバッファは unit の状態の置き場に返ります
- 捨てない知らせの輪は、知らせの数の上界から容量を決め、超えた時は毒の印を立てて世代を終えます([front と unit の間の知らせ](ownership.md#front-と-unit-の間の知らせ))
- データの経路で packet ごとにヒープを確保しません

## 核の作り直し

今の核の型は、作成の時に 65,536 行の待ち受けの表と UDP の endpoint の表を必ず確保します (`crates/wgft-wgstack/src/tcp/listen.rs` の `PortTable::new`)。
上界の表では、1 つの核あたり `listeners` が 1.0 MiB、`udp_endpoints` が 2.3 MiB、ポートの知らせを含む `events` が 0.6 MiB です([wgstack の上界の表](../../v2/wgstack-bound.md))。
U では核を front の核と unit の核に分け、ポートで決まる表は front の核だけが持つように作り直します(設計判断)。

## 上界の式

H は helper の数で、unit の数は M = H + 1 です。
unit 0 は front が実行し、front の今の置き場を使うので、新しい項は unit 1 から H の分です。

```text
M_proc = M_base + M_fix + N_c × (f_s + f_r + r_f + h_f) + G
       + M_udp_rx + M_udp_tx + M_frag + N_ping × c_ping
       + M_ct + M_pt + M_tx,front + M_dev + M_relay
       + Σ_{u=1}^{H} M_unit,u + Σ_{h=1}^{H} M_helper,h + M_ring
```

| 項 | 中身 | 今の式との関係 |
|---|---|---|
| M_base、M_fix、N_c × (…)、G、M_udp_rx、M_udp_tx、M_frag、N_ping × c_ping、M_ct、M_tx,front、M_dev、M_relay | 今の項。M_fix は front と unit に分けても和が同じで、G は[需要で育つバッファ](../../userspace/wgstack-buffers.md#予約と予算)の全体の予算です | 今と同じ |
| M_pt | 平文の置き場:今の 1 バッチの平文の領域 W と、止まった unit のための共有の分 S | 今の `batch` の復号の行き先に S を加えます |
| M_unit,u | unit u の固定の値 | 新しい項 |
| M_helper,h | helper h の固定の値 | 新しい項 |
| M_ring | executor の間の捨てない輪 | 新しい項 |

## unit と helper と輪の項

値は MTU を受け付ける最大の 9,216 byte で数えます。

| 項 | 中身 | 見込み (推定) |
|---|---|---|
| M_unit,u | 制御の packet の出力の輪 16 枠 × MTU | 約 0.15 MiB |
| | 受け口の輪 2,048 記述子 × 32 byte | 64 KiB |
| | chunk の置き場に残す分 32 個 × 16 KiB | 0.5 MiB |
| | 中継の大きいバッファの残す分 8 個 × 32 KiB | 0.25 MiB |
| M_helper,h | スレッドのスタック (測った最大の使用量の 2 倍以上、仮の値は 256 KiB) | 0.25 MiB |
| | 送信の枠 16 組。1 組は核が書く平文の packet の枠と暗号文の枠の 2 つです | 約 0.3 MiB |
| | counter の在庫 64 × 64 byte | 4 KiB |
| M_ring | 知らせの輪と返却の輪 (Σ で 4 × N_c と 2 × N_c の知らせ) | N_c = 2,560 で約 1.1 MiB |

受け口の輪の記述子の上限を平文の置き場の上限とは別に置くのは、16 KiB の block が最小の 40 byte の packet を約 400 個持てるためです(計算)。
helper は経路の表を写さず、経路は接続を置く時に front が 1 回確かめます。
helper のスレッドは tokio の実行環境を持たないので、実行環境の項は poller の知らせの列だけです。

## 平文の置き場と unit の上限

平文の block は複数の unit の packet を含むことがあり、unit が押さえるメモリは参照を持つ block の数で決まります。

- 数え方:front は、作業の block に復号した packet を unit に渡す時に、その block への unit の参照を初めて持つなら unit の数を 1 つ増やし、unit が返した時に減らします
- 置き場:M_pt = W + S です。
  W は front の 1 バッチと unit 0 の分で、今の平文の領域と同じです。
  S は helper の unit が共有する分です
- unit の上限:helper の unit 1 つが参照を持てる量を C_u にします
- 上限に達した時:その unit には packet を渡さずに捨てて数えます。
  復号は渡す先が分かる前に作業の block で行うので、捨てるのは参照を持たせないことです。
  front は W を常に使えるので、読みを止めません
- 作成の知らせ:握手の最後の ACK の参照も unit の数に入れ、上限に達した unit には接続を置きません
- 大きな datagram:組み立てた IPv4 の datagram (最大 65,535 byte) は、続く block にまたがって置きます
- 変換の無い形:link が自分の枠を貸す link (AF_XDP の UMEM) は、スレッドをまたぐ前に block に写します

C_u と S は、helper が止まっても捨てずに耐える時間 (止まりの許容) から決めます。

| 止まりの許容 | C_u (10 Gbit/s で) | S | 区別 |
|---|---|---|---|
| 約 1.7 ms (案) | 2 MiB | 2 MiB × min(H, 2)。2 つの unit が同時に止まるまで耐えます | 設計判断の案 |

今は同じ止まりを、カーネルの外側のソケットの受信のバッファ (最大 14 MiB、上界の外) が吸収します。
U では止まった helper の unit の TCP の segment を engine の中で捨てるので、捨てる損失が新しく加わります。
許容を長くするとメモリが増え、短くすると止まりで捨てる損失が増えるので、許容の値は所有者が決めます([所有者に決めてもらうこと](README.md#所有者に決めてもらうこと))。

## 増える量の見込み

| n_cpu | H | 増分の見込み (推定) |
|---|---|---|
| 1 | 0 | 0 |
| 2 | 1 | 約 4.6 MiB |
| 4 | 3 | 約 9.7 MiB |
| 8 | 7 | 約 15.7 MiB |

内訳は、unit ごとに約 0.96 MiB、helper ごとに約 0.55 MiB、輪の合計の約 1.1 MiB、共有の分 S です(推定)。
A+ は 8 vCPU で常駐のメモリを 8.4 MiB 増やしました (#808 から #810)。
見込みには、poller の保持、核を作り直した後の型の大きさ、まだ数えていない知らせの源の輪 ([未決の項目](verification.md#未決の項目)) が残るので、メモリの線は P0 で測った後に決めます。
残す chunk の数と送信の枠の数は、減らすと確保と system call が増えるので、P0 で CPU と比べて決めます。

## 全体の予算と unit の credit

- 不変条件:全体の空き + Σ (credit の残り + 保有者が借りた量) = G
- 補充と返却:credit が下の線を下回ったら全体から 1 単位 (仮の値は 1 MiB) を CAS で取り、上の線を超えたら返します
- 尽きた時:段 (需要で育つバッファの予約の大きさの段) を大きくせずに今の段で続けます
- 回収:全体の空きが無い時は、ほかの unit の回収の印を立てます。
  印を見た unit の実行者は、需要の無い保有者を最初の段に戻し、空いた分を全体に返します。
  回収の印は止まった unit や眠った helper では働かないので、その扱いは[未決の項目](verification.md#未決の項目)です

段を変えるのは unit の実行者の 1 回の実行の中なので、段を変える間の一時の保持を接続の予約の内に収める今の論証はそのまま成り立ちます。

## 置き場の区分

| 区分 | 大きさ | 置き場 | 取る者と返す者 |
|---|---|---|---|
| chunk | 16 KiB | front と unit の状態の置き場 | 状態の実行者が取って返します |
| 平文の block | 仮の値は 16 KiB | M_pt | front が取り、unit の実行者が返します |
| 送信の枠 | MTU の最大 + 32 byte と header | executor ごと | 取った executor が返します |
| 受信の暗号文の枠 | 65,535 byte | M_ct | front が取り、復号の後に返します |
| 記述子と知らせ | 32 から 96 byte | 輪の配列 | 確保しません |

### chunk と大きいバッファの置き場

接続は unit を移らないので、chunk と中継の大きいバッファは unit の状態の置き場に返り、どの executor が実行していても同じ置き場を使います。
front は今と同じく chunk を 64 個、大きいバッファを 16 個まで残し、unit 1 から H はそれぞれ 32 個と 8 個まで残します(設計判断、値は P0 で決めます)。

## 所有者が挙げた領域と項の対応

| 領域 | 項 |
|---|---|
| TCP の状態と送受信のバッファ | M_fix の接続の枠と表、N_c × (f_s + f_r)、G |
| SACK、RACK、再送 | 送信の輪の chunk (f_s と G)、記録 (r_f と G)、区間 (h_f と G)、接続の枠の中の値 |
| TIME_WAIT と FIN_WAIT_2 | M_fix の行の表 |
| 再組み立て、UDP | M_frag、M_udp_rx、M_udp_tx、M_fix の endpoint の表 |
| WireGuard の暗号のバッファ | M_ct、M_pt、M_tx,front、M_helper,h の送信の枠と在庫 |
| WireGuard の状態とキュー | M_dev |
| 制御の message | M_ring、M_fix と M_unit,u の制御の packet の輪 |
| タイマー | M_fix のタイマーの節と、握手の途中と行の list |
| スレッドのスタックと実行環境 | M_base、M_helper,h、今と同じ名前の解決のスレッドの項 |
| 中継 | M_relay と M_unit,u の大きいバッファ |
| 割り当て器 | RSS の上界で数えます (次の節) |

二重の数えが無いことは、置き場の容量だけを項にし、平文の置き場の上限を M_pt の中だけで数え、枠の数で決まる配列の和を全体の数と等しくすることで示します。
数え漏れが無いことは、executor のスレッドの確保をすべて上の置き場から行い、置き場の外の確保を数えの試験で 0 と確かめることで示します([メモリの試験](verification.md#メモリの試験))。

## 論理の上界と RSS の上界

RSS の上界は、論理の上界に次の分を加えた値です。

- 割り当て器の丸めと管理の領域:確保の大きさに、割り当て器ごとに測った係数を掛けます
- 割り当て器の arena:製品の build は musl で、1 つの heap を持ちます。
  glibc の build はスレッドごとに arena を作り、unit の chunk と中継の状態を別の executor が解放すると、確保した arena と違うスレッドからの解放になります。
  その分の断片化は glibc の build で測ります (未確認)
- スタックとページの丸め

ラボの確認は今と同じく、RSS が上界と決めた余裕の和以下であることを n_cpu ごとに確かめます([agent の上界の表](../../v2/agent-bound.md))。
カーネルのソケットのバッファと poller の保持は、今と同じく上界に数えません。

## 尽きた時の規則

どの資源も、尽きた時に新しい保持を拒み、既存の保持を追い出しません([尽きたときの動作](../../userspace/wgstack.md#尽きたときの動作))。

| 資源 | 扱い |
|---|---|
| 接続の枠 | 空きのある unit に置きます。どの unit にも置けない時は、最後の ACK を捨てて握手の途中の行を残します |
| 握手の途中の表 | cookie を返します。今と同じです |
| 段の予算 | 今の段のまま続け、回収を求めます |
| 送信のバッファと記録 | アプリケーションの書き込みに `WouldBlock` を返します。再送のデータは捨てません (I4) |
| unit の上限と受け口の輪 | その unit の TCP の segment を捨てて数えます。経路での損失と同じ扱いです |
| 送信の枠と counter の在庫 | 実行者が核から引くのを止めます。データは核の送信の輪に残ります |
| 知らせの輪と返却の輪 | 毒の印を立てて世代を終えます |
| 戻しの輪 | SYN を捨てて数えます。相手が SYN を送り直します |
| UDP の予算と会計の不整合 | 今と同じです |

unit の上限で捨てる segment は、まだ確認していない受信のデータなので、I4 の「再送に要る未確認のデータを黙って捨てない」には当たりません。
入力が止まった後に保持が戻ることを、n_cpu が 2 以上の敵対的な保持の試験で確かめます([メモリの試験](verification.md#メモリの試験))。
