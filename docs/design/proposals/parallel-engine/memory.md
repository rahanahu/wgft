# メモリの上界 (N3)

この文書は、推奨の構成 S のプロセス全体のメモリの上界を式で示し、全体と shard ごとの予算、固定の置き場と大きさの区分、shard の間の貸し借り、尽きた時の規則を定めます。
未採用の提案です([提案の索引](README.md))。
上界の考え方は今の設計と同じく、上限の設定値ではなく実際に持てる量で数えます([上界の式の写し方](../../v2/wgstack-rs.md#上界の式の写し方))。
I1 から I7 の[不変条件](../../userspace/wgstack.md#不変条件)をそのまま守ります。

## 上界の原則

- 予算の印と置き場の枠を 1 つの値にします。
  byte を持つことと、その byte の予算を持つことが同じ値の所有になり、二重の数えと数え漏れが型で起きにくくなります(設計判断)
- 置き場はすべて起動の時に容量を決め、後から大きくしません。
  例外は今と同じく、予約の内側でだけ確保する 16 KiB の chunk です
- 予算は全体で 1 つ持ち、shard は credit として一部を借ります。
  credit の補充と返却はデータの経路の外 (起床の終わり) で行います
- shard の間で動くものは値の移動だけで、新しい数えは生じません
- データの経路で packet ごとにヒープを確保しません
- 接続を作る表と N_c 本の接続の枠は shard 0 だけが持ちます。
  shard k は昇格した接続を入れる P 本の枠だけを持ち、表を shard の数だけ複製しません([状態の置き場の原則](ownership.md#状態の置き場の原則))

## 上界の式

N は shard の数で、起動の時に CPU の数から決まります。

```text
M_proc = M_base
       + M_fix
       + N_c × (f_s + f_r + r_f + h_f)
       + G
       + M_udp_rx + M_udp_tx + M_frag + N_ping × c_ping
       + M_ct + M_pt + M_tx + M_dev
       + Σ_{s=1}^{N-1} (M_sh,s + S_stk + R_rt)
       + M_ring
       + M_relay
```

shard 0 のスレッドのスタックと実行環境は、今と同じく M_base に入ります。
新しい項は M_sh,s、S_stk、R_rt、M_ring、M_pt の重なりの分です。

| 項 | 中身 | 今の式との関係 |
|---|---|---|
| M_base | 実行ファイル、制御プレーン、制御ソケットのスレッド、shard 0 のスレッドと実行環境、stream と TLS の状態 | 今の `base` と同じ |
| M_fix | shard 0 の核の固定の表:接続の枠、4 つ組の表、握手の途中の表、TIME_WAIT の表、待ち受けと UDP の endpoint の表、タイマーの節、出力の list、制御の輪、知らせの表、chunk の置き場に残す分 | 今の `fix` と同じ |
| N_c × (f_s + f_r + r_f + h_f) | 接続の枠ごとの最初の予約と、記録の輪と区間の表 | 今の `floor_conn` と同じ |
| G | TCP の段を大きくする全体の予算 | [需要で育つバッファ](../../userspace/wgstack-buffers.md#予約と予算)の G。今の `boost` の項を置き換えます |
| M_udp_rx、M_udp_tx | UDP の受信と送信の予算と管理の配列 | 今と同じ |
| M_frag | 再組み立ての予算 | 今と同じ |
| N_ping × c_ping | ping の endpoint | 今と同じ |
| M_ct | 受信の暗号文の置き場 | 今の `batch` の受信の部分。置き場は 1 つのままです |
| M_pt | 平文の置き場 | 今の `batch` の復号の行き先を、重ねて処理する分だけ大きくします |
| M_tx | 送信の枠の置き場 | 今の `batch` の送信の部分を、shard の間で分けます。和は変えません |
| M_dev | WireGuard の device のキューとセッションの状態 | 今の `device` と同じ |
| M_sh,s | shard s の核の固定の値:P 本の枠 (P × c_conn とタイマーと list の節)、shard 0 の枠から自分の枠への表 (N_c × 2 byte)、タイマーの輪、出力と知らせの list、制御の輪 Q_ctl,s × s_ctl、数え | 新しい項 |
| S_stk | shard s のスレッドのスタック | 新しい項 |
| R_rt | shard s の event loop の実行環境の内部の保持 | 新しい項。測った定数です |
| M_ring | 受け口の queue、制御の知らせの輪、平文の block の返却の輪、申し出の板、送りの板 | 新しい項 |
| M_relay | TCP と UDP の中継の task、大きいバッファ、応答のバッファ、handle の層の表 | 今の `tcp relay`、`tcp bulk`、`udp relay`、`tables`、`driver` と同じ。表は枠で引く 1 つの配列のままです |

chunk の置き場に残す数は、今の全体の 64 個を shard に分けます。
和は変わらないので、M_fix の `chunk_pool` の項も変わりません。

## N が増えると増える項

N に比例して増えるのは、M_sh,s、S_stk、R_rt、M_ring の輪の分です。
N によらず 1 回だけ増えるのは、平文の重なりの分です。

| 増える項 | 見込み | 区別 |
|---|---|---|
| M_sh,s | shard あたり約 0.35 MiB。P = 128 本の枠 (約 1.4 KiB の枠と節) が約 0.2 MiB、制御の輪を 16 枠 × MTU の最大 9,216 byte とした値が約 0.15 MiB です | 推定 |
| S_stk | shard あたり 256 KiB を仮の値にします | 設計判断。値は測った最大の使用量の 2 倍以上にします |
| M_ring | shard あたり数十 KiB | 推定 |
| R_rt | 未測定 | 未確認 |
| M_pt の重なり | 最初の値は 1 バッチの平文の領域の 1 つ分 (約 4 MiB) | 推定 |

N = 8 での増分の見込みは、平文の重なりで約 4 MiB と、7 つの shard の M_sh,s とスタックと輪で約 4.5 MiB の和の約 8.5 MiB に、実行環境の未測定の分を加えた値です(推定)。
A+ は 2 つ目の受信の置き場で約 8.4 MiB を増やしました (測定)。
S は暗号文の置き場を 1 つに保つので、増えるのは平文の重なりの分です。
受け入れの線の案は、N = 8 で今の上界からの増分が 12 MiB 以内、N = 1 で増分 0 です([受け入れの条件](verification.md#受け入れの条件))。

平文の重なりの大きさは、持ち主が遅れた時に shard 0 が読み続けられる量で決まります。
最初の値で試作を流し、平文の置き場が尽きて読みを止めた回数と速さを測って決めます(設計判断)。

## 全体の予算と shard の credit

TCP の段の予算 G、UDP の予算、chunk の予約は、全体で 1 つの数と、shard ごとの credit で数えます。

- 不変条件:全体の空き + Σ_s (shard s の credit の残り + shard s の保有者が借りた量) = G
- 補充:shard の credit が下の線を下回ったら、起床の終わりに全体の空きから 1 単位 (1 MiB を仮の値にします) を CAS で取ります
- 返却:credit が上の線を超えたら、超えた単位を全体に返します。
  下の線と上の線の幅 (hysteresis) が、補充と返却の往復を抑えます
- 保有者の借り:接続の段を大きくする時は、自分の shard の credit から借ります。
  credit が足りず全体の空きも無い時は、段を大きくせずに今の段で続けます。
  今の尽きた時の扱いと同じです
- 回収の求め:全体の空きが無い時は、ほかの shard に回収の求めを制御の知らせで送ります。
  求めを受けた shard は、次の起床で需要の無い自分の保有者を最初の段に戻し、空いた分を全体に返します。
  ほかの shard の接続を直接戻すことはしません(設計判断)
- 昇格:接続が借りた量は、昇格の知らせで shard 0 から k へ動きます。
  shard 0 の借りた量が減り、k の借りた量が同じだけ増えるので、全体の空きは変わりません

credit の残りは G の内側なので、使われていない credit も上界の内にあり、二重に数えません。
今の上界は段を変える間の一時の保持を、接続ごとの予約の内に収めています([上界の式の写し方](../../v2/wgstack-rs.md#上界の式の写し方))。
段を変えるのは枠の持ち主の 1 回の呼び出しの中なので、この論証はそのまま成り立ちます。
今の論証が頼る「1 つのスレッド」は、「接続の持ち主の 1 つのスレッド」に替わります。

## 固定の置き場と大きさの区分

| 区分 | 大きさ | 置き場 | 取る者と返す者 |
|---|---|---|---|
| chunk | 16 KiB | shard ごとの置き場と予約の内の確保 | 枠の持ち主が取り、持ち主が返します。昇格では chunk の pointer の表ごと動きます |
| 平文の block | 塊の大きさ (32 KiB を仮の値にします) | 全体で 1 つの M_pt | shard 0 が取り、持ち主が返却の輪で返します |
| 送信の枠 | MTU の最大 + 32 byte と header | 全体の M_tx を shard の小分けの置き場に分けます | 持ち主が取り、送った shard が返します |
| 受信の暗号文の枠 | 65,535 byte (GRO の 1 つ) | 1 つの M_ct | shard 0 が取り、復号を終えたスレッドが返します |
| 記述子 | 32 byte 程度 | 輪の配列 | 輪の中を動くだけで、確保しません |
| 制御の知らせ | 32 byte 程度 | 輪の配列 | 同上 |

平文の block は、shard 0 の接続の packet と、昇格した複数の接続の packet を含むことがあります。
block は参照の数を持ち、shard 0 が持ち主ごとに 1 つ数え、持ち主がその block の packet をすべて処理した時に 1 つ減らします。
数の更新は block と持ち主の組ごとに 1 回で、packet ごとではありません。
詰まっていない時は塊に分けないので、平文は今と同じ連続した領域に復号し、参照の数を使いません。

## 予算と枠を 1 つにする値

置き場の枠と予算は、`Lease` (仮の名前) という 1 つの型の値で表します。

- `Lease` は複製できず、捨てると枠と予算を置き場に返します
- shard の間で `Lease` を動かすと、予算の数えも一緒に動きます
- 数えの和は、置き場ごとの「出した `Lease` の数 × 区分の大きさ」で、置き場の容量を超えません
- 上界の式の各項は置き場の容量で、`Lease` の行き先によりません

このため、平文の block が持ち主の queue にある間も、その byte は M_pt の内にだけ数えられます。

## 上限のある queue

| queue | 容量の決め方 | 満ちた時 |
|---|---|---|
| 受け口の queue (shard 0 から k) | 持ち主ごとの平文の byte の上限と記述子の数 | TCP の segment を捨てて数えます。昇格の知らせは queue に空きがある時だけ送り、空きが無ければ昇格を次の窓に延ばします |
| 制御の知らせの輪 (k から shard 0) | shard ごとの固定の数 | 送り手が知らせを自分の状態に残し、次の起床で送り直します。捨てません |
| 平文の block の返却の輪 | 平文の block の数以上 | 満ちません |
| 申し出の板 | 暗号文の置き場の枠の数以上 | 満ちません |
| 送りの板 | 持ち主の送信の枠の数以上 | 満ちません |

制御の知らせと昇格の知らせを捨てると、shard 0 の昇格した印と shard k の状態が食い違うので、捨てる扱いを許しません(設計判断)。
返却を遅らせると状態を長く持つだけで、上界は変わりません。
UDP は shard 0 の中で処理するので、受け口の queue を通りません。

## 所有者が挙げた領域と項の対応

| 領域 | 項 |
|---|---|
| TCP の状態 | M_fix の接続の枠、握手の途中の表、4 つ組の表と、M_sh,s の P 本の枠 |
| TCP の送受信のバッファ | N_c × (f_s + f_r) と G |
| SACK、RACK、再送 | 再送のデータは送信の輪の chunk (f_s と G)、記録は r_f と G の段の配列、区間は h_f と G の段の配列、RACK と TLP の値は接続の枠の中 |
| TIME_WAIT | M_fix の TIME_WAIT の表 |
| 再組み立て | M_frag |
| UDP | M_udp_rx、M_udp_tx、M_fix の endpoint の表 |
| WireGuard の暗号のバッファ | M_ct、M_pt、M_tx |
| WireGuard の状態とキュー | M_dev |
| 制御の message | M_ring の制御の知らせの輪、M_fix と M_sh,s の制御の輪 |
| タイマー | M_fix のタイマーの節、M_sh,s の輪の先頭、握手の途中と TIME_WAIT の list |
| スレッドのスタック | M_base の shard 0 と制御プレーンのスレッド、S_stk、今と同じ名前の解決のスレッドの項 |
| 実行環境 | M_base と R_rt |
| 割り当て器 | 論理の上界の外。RSS の上界の係数で数えます (次の節) |

二重の数えが無いことは、次の 3 点で示します。

- 置き場の容量だけを項にし、置き場の中を動く値 (記述子、`Lease`、昇格する枠) を別に数えません
- 接続を作る表は shard 0 だけが持ち、shard ごとに複製しません。
  昇格した接続の枠の構造体は shard 0 の昇格した印の枠と k の枠の 2 か所にありますが、どちらも起動の時に確保する別の置き場なので、2 つの項は別の memory を数えます。
  最初の予約、記録の輪、区間の表、chunk は接続と一緒に所有が動き、置き場は 1 つです
- credit は G の内側の数で、別の項を持ちません

数え漏れが無いことは、shard のスレッドの確保をすべて上の置き場から行い、置き場の外の確保を数えの試験で 0 と確かめることで示します([メモリの試験](verification.md#メモリの試験))。

## 論理の上界と RSS の上界

論理の上界は、上の式の和です。
プロセスが持てる状態とデータの byte を、要求した大きさで数えます。

RSS の上界は、論理の上界に次の分を加えた値です。

- 割り当て器の丸めと管理の領域:起動の時の確保の数と大きさに、使う割り当て器ごとに測った係数を掛けます([上界の式の写し方](../../v2/wgstack-rs.md#上界の式の写し方)の提案と同じ)
- スタック:触ったページだけが RSS に入りますが、上界はスタックの全体で数えます
- ページの丸め:大きな置き場の端の切り上げです

RSS は上界よりずっと小さいことが多く、置き場の触っていないページは RSS に入りません。
ラボの確認は今と同じく、RSS が上界と決めた余裕の和以下であることを確かめます([agent の上界の表](../../v2/agent-bound.md))。
定常の状態で packet ごとに確保しないので、割り当て器の断片化は流れの数で決まる確保 (中継の task) の分だけ増ええます。
その分は中継の項に丸めの係数を掛けて数えます。
昇格で中継の task を作り直す分も、流れごとの確保に入ります。

## カーネルの保持

今の上界は、カーネルのソケットのバッファ、割り当て器の丸め、スタックを数えません([agent の上界の表](../../v2/agent-bound.md)の起動の行の説明)。
S では、割り当て器とスタックを前の 2 つの節で数えます。

カーネルのソケットのバッファは、プロセスの RSS に入らないので、別の行として推定の上界を示します。

- 外側のソケット:受けたと読み返した受信と送信のバッファの大きさです。
  link の queue が複数なら queue の数を掛けます
- LAN の側の TCP のソケット:流れの数 K と、接続ごとの受信と送信のバッファの上限の積です
- LAN の側の UDP のソケット:セッションの数と、セッションごとのバッファの上限の積です

カーネルはバッファを packet ごとの管理の分を含めて数えるので、この行は保証ではなく推定です(未確認)。
起動の行にこの推定を加えるかどうかは、公開のログの変更なので所有者が決めます([所有者に決めてもらうこと](README.md#所有者に決めてもらうこと))。

## 尽きた時の規則

どの資源も、尽きた時に新しい保持を拒み、既存の保持を追い出しません([尽きたときの動作](../../userspace/wgstack.md#尽きたときの動作))。
S で加わる資源と、TCP と UDP の正しさを保つ扱いは次のとおりです。

### TCP の尽きた時

| 資源 | 扱い |
|---|---|
| 接続の枠 | 今と同じく新しい接続を拒みます。枠は shard に分けないので、ある shard だけが尽きることはありません |
| 握手の途中の表 | cookie を返します。今と同じです |
| 段の予算 | 今の段のまま続け、回収を求めます。窓を広げないので、相手は窓で送る量を抑えます |
| 送信のバッファと記録 | アプリケーションの書き込みに `WouldBlock` を返します。再送のデータは捨てません (I4) |
| 受け口の queue | データの segment を捨てて数えます。経路での損失と同じ扱いで、送り手が SACK と RACK で回復します |
| 平文の置き場 | shard 0 が読むのを止めます。外側のソケットの queue に溜まり、溢れた分はカーネルが捨てます。今の Inline が CPU で詰まる時と同じです |
| 送信の枠 | 持ち主が核から引くのを止めます。データは核の送信の輪に残るので失いません |
| 制御の知らせの輪 | 送り直します。捨てません |

受け口の queue で捨てる segment は、まだ確認していない受信のデータなので、I4 の「再送に要る未確認のデータを黙って捨てない」には当たりません。
I4 が守るのは送り手として持つデータです。

### UDP の尽きた時

| 資源 | 扱い |
|---|---|
| 受信の予算 | datagram を捨て、ICMP を返しません。今と同じです |
| 送信の予算 | 送信は `WouldBlock` を返し、応答の送信 (`send_to_latest`) は古いものから捨てます。今と同じです |
| 会計の不整合 | engine の UDP を止めます。TCP は止めません |

### 回復

入力が止まると、平文の block、送信の枠、受け口の queue の記述子は、持ち主の処理の後にすべて置き場に戻ります。
段の予算は、需要の無い保有者を最初の段に戻す今の回収の規則で戻ります。
昇格した接続は、閉じた時に枠と予算を shard 0 と全体に返します。
入力が止まった後に保持が戻ることを、shard を複数にした敵対的な保持の試験で確かめます([メモリの試験](verification.md#メモリの試験))。
