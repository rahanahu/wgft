# メモリの上界 (N3)

この文書は、推奨の構成 S のプロセス全体のメモリの上界を式で示し、全体と shard ごとの予算、固定の置き場と大きさの区分、shard の間の貸し借り、尽きた時の規則を定めます。
未採用の提案です([提案の索引](README.md))。
上界の考え方は今の設計と同じく、上限の設定値ではなく実際に持てる量で数えます([上界の式の写し方](../../v2/wgstack-rs.md#上界の式の写し方))。
I1 から I7 の[不変条件](../../userspace/wgstack.md#不変条件)をそのまま守ります。

## 上界の原則

- 予算の印と置き場の枠を 1 つの値にします。
  byte を持つことと、その byte の予算を持つことが同じ値の所有になり、二重の数えと数え漏れが型で起きにくくなります(設計判断)
- 置き場はすべて起動の時に容量を決め、後から大きくしません。
  例外は今と同じく、予約の内側でだけ確保する 16 KiB の chunk と、流れごとの中継の task です
- 予算は全体で 1 つ持ち、shard は credit として一部を借ります。
  credit の補充と返却はデータの経路の外 (起床の終わり) で行います
- 接続は shard を移らないので、接続の持つ chunk とバッファは取った shard が返します
- shard の間の輪は、捨ててよいデータの輪と、捨てない知らせの輪に分け、捨てない輪は容量を知らせの数の上界から決めます
- データの経路で packet ごとにヒープを確保しません

## 上界の式

N は shard の数で、起動の時に CPU の数から決まります。
shard 0 のスレッドは今のデータプレーンのスレッドで、そのスタックと実行環境は今と同じく M_base に入ります。

```text
M_proc = M_base
       + M_fix
       + N_c × (f_s + f_r + r_f + h_f)
       + G
       + M_udp_rx + M_udp_tx + M_frag + N_ping × c_ping
       + M_ct + M_pt + M_tx,0 + M_dev
       + M_relay
       + Σ_{k=1}^{N-1} M_sh,k
       + M_ring
```

| 項 | 中身 | 今の式との関係 |
|---|---|---|
| M_base | 実行ファイル、制御プレーン、制御ソケットのスレッド、shard 0 のスレッドと実行環境、stream と TLS の状態 | 今の `base` と同じ |
| M_fix | 核の固定の表:接続の枠とタイマーの節と知らせの印 (持ち主の shard に分けます)、4 つ組の表、握手の途中の表、TIME_WAIT の表、待ち受けと UDP の endpoint の表、出力の list、shard 0 の制御の輪、ポートの知らせ、shard 0 の chunk の置き場に残す分 | 今の `fix` と同じ。枠の数で決まる配列は shard に分けても和が同じです |
| N_c × (f_s + f_r + r_f + h_f) | 接続の枠ごとの最初の予約と、記録の輪と区間の表 | 今の `floor_conn` と同じ |
| G | TCP の段を大きくする全体の予算 | [需要で育つバッファ](../../userspace/wgstack-buffers.md#予約と予算)の G。今の `boost` の項を置き換えます |
| M_udp_rx、M_udp_tx、M_frag、N_ping × c_ping | UDP の予算、再組み立て、ping | 今と同じ。すべて shard 0 です |
| M_ct | 受信の暗号文の置き場 | 今の `batch` の受信の部分と同じ。置き場は 1 つです |
| M_pt | 平文の置き場:今の 1 バッチの平文の領域と、持ち主ごとの block の上限の和 | 今の `batch` の復号の行き先を広げます |
| M_tx,0 | shard 0 の送信の枠 | 今の `batch` の送信の部分と同じ |
| M_dev | WireGuard の device のキューとセッションの状態 | 今の `device` と同じ |
| M_relay | 中継の task、大きいバッファ、応答のバッファ、shard 0 の handle の層の表 | 今の `tcp relay`、`tcp bulk`、`udp relay`、`tables`、`driver` |
| M_sh,k | 持ち主の shard k の固定の値 (次の節) | 新しい項 |
| M_ring | shard の間の輪とライブラリの輪 (次の節) | 新しい項 |

## 持ち主の shard ごとの項

M_sh,k は次の和です。
値は MTU を受け付ける最大の 9,216 byte で数えます。

| 中身 | 大きさ | 見込み (推定) |
|---|---|---|
| スレッドのスタック S_stk | 測った最大の使用量の 2 倍以上。仮の値は 256 KiB | 0.25 MiB |
| event loop の実行環境 R_rt | 測った定数 | 未測定 |
| 送信の枠 M_tx,k | 16 枠 × (MTU + 32 byte と header) × 2 | 約 0.3 MiB |
| 制御の輪 Q_ctl,k × s_ctl | 16 枠 × MTU (持ち主の RST などの制御の packet) | 約 0.15 MiB |
| chunk の置き場に残す分 | 32 個 × 16 KiB | 0.5 MiB |
| 中継の大きいバッファの残す分 | 8 個 × 32 KiB | 0.25 MiB |
| handle の層の表と waker の列 | shard k の枠の数 N_c,k で決まる大きさ | 今の `tables` と `driver` を枠の数で分けた分で、和は今と同じです |
| タイマーの輪、出力と知らせの list の先頭、数え | 定数 | 小さい |

handle の層の表 (`wgft-netstack` の waker の表と LAN の側のソケットの表) は今 `Rc<RefCell<…>>` で、スレッドをまたげません。
S では shard ごとに作り、行の数を shard の枠の数 N_c,k にします。
Σ_k N_c,k = N_c なので、表の和は今の `tables` と `driver` の値にほぼ等しく、増えるのは shard ごとの定数の分です(推定)。
UDP の待ち受けのポートの表は shard 0 だけが持ちます。

## shard の間の輪

M_ring は次の和です。

| 輪 | 容量 | 1 つの大きさの見込み (推定) |
|---|---|---|
| データの輪 (shard 0 から k) | 持ち主の block の上限の packet を入れられる記述子の数 | 数十 KiB |
| 制御の輪 (shard 0 から k) | N_c,k + 定数。知らせは接続ごとに作成か dial と中継の開始の 2 つまでで、停止は 1 つ | 枠の数 × 64 byte |
| 返却の輪 (k から shard 0) | N_c,k。知らせは接続ごとに TIME_WAIT の行か解放の 1 つだけ | 枠の数 × 96 byte |
| block の返却の輪 (k から shard 0) | 平文の block の数 | 数 KiB |
| 貸し出しの輪 (shard 0 から k) | 在庫の上限 256 | 約 16 KiB |
| ライブラリの命令の輪 (利用者から各 shard) | 固定の数。満ちたら利用者に `WouldBlock` を返します | 数 KiB |
| ライブラリの知らせ | 枠ごとの知らせの印と順の list。印は重なるので枠の数で抑えられます | 今の知らせの表と同じ形 |

回収の求めは輪を使わず、shard ごとの atomic の印です。
重ねて立てても 1 つなので、保持は増えません。
持ち主から shard 0 へ packet を戻す道は持たないので、戻した packet が溜まることはありません([持ち主から shard 0 へ返すもの](ownership.md#持ち主から-shard-0-へ返すもの))。

## N が増えると増える項

持ち主の shard 1 つあたりの見込みは、スタック 0.25、送信の枠 0.3、制御の輪 0.15、chunk 0.5、大きいバッファ 0.25、輪 0.15、平文の block の上限 0.25 の和の約 1.85 MiB に、実行環境の未測定の分を加えた値です(推定)。

| N | 増分の見込み (推定、実行環境の分を除く) |
|---|---|
| 1 | 0 |
| 2 | 約 1.9 MiB |
| 4 | 約 5.6 MiB |
| 8 | 約 13 MiB |

A+ は 8 vCPU で常駐のメモリを 8.4 MiB 増やしました (測定、#808 から #810)。
S の増分はそれより大きく、大半は持ち主ごとの送信の枠と置き場に残す分です。
置き場に残す数と送信の枠の数を減らすと、大きな flow の chunk の確保と解放と、送り出しの system call の数が増えるので、値は試作で CPU と比べて決めます。
受け入れの線の案は、N = 8 で実行環境を含めて 16 MiB 以内、N = 1 で 0 です([受け入れの条件](verification.md#受け入れの条件))。

## 全体の予算と shard の credit

TCP の段の予算 G、UDP の予算、chunk の予約は、全体で 1 つの数と、shard ごとの credit で数えます。

- 不変条件:全体の空き + Σ_s (shard s の credit の残り + shard s の保有者が借りた量) = G
- 補充:shard の credit が下の線を下回ったら、起床の終わりに全体の空きから 1 単位 (仮の値は 1 MiB) を CAS で取ります
- 返却:credit が上の線を超えたら、超えた単位を全体に返します。
  眠りに入る shard は、下の線を超える credit を全体に返してから眠ります。
  眠った shard に credit が残り続けないためです
- 保有者の借り:接続の段を大きくする時は、自分の shard の credit から借ります。
  credit が足りず全体の空きも無い時は、段を大きくせずに今の段で続けます
- 回収:全体の空きが無い時は、求めた shard がほかの shard の回収の印を立てます。
  印を見た shard は、次の起床で需要の無い自分の保有者を最初の段に戻し、空いた分を全体に返します
- 需要で育つバッファの設計との違い:その設計は回収した借りを求めた接続へ直接渡し、ほかの接続が先に取らないようにしています([需要で育つバッファ](../../userspace/wgstack-buffers.md#育つ条件))。
  S では shard をまたぐ直接の受け渡しを持たず、全体の空きに返すので、別の shard が先に取ることがあります。
  求めた接続は次の需要の区間で求め直します(設計判断)

credit の残りは G の内側なので、二重に数えません。
段を変えるのは接続の持ち主の 1 回の呼び出しの中なので、段を変える間の一時の保持を接続の予約の内に収める今の論証 ([上界の式の写し方](../../v2/wgstack-rs.md#上界の式の写し方)) はそのまま成り立ちます。

## 固定の置き場と大きさの区分

| 区分 | 大きさ | 置き場 | 取る者と返す者 |
|---|---|---|---|
| chunk | 16 KiB | shard ごとの置き場と予約の内の確保 | 取った shard が返します |
| 平文の block | 仮の値は 16 KiB | 1 つの M_pt | shard 0 が取り、持ち主が返却の輪で返します |
| 送信の枠 | MTU の最大 + 32 byte と header | shard ごとの置き場 | 取った shard が返します |
| 受信の暗号文の枠 | 65,535 byte (GRO の 1 つ) | 1 つの M_ct | shard 0 が取り、復号の後に返します |
| 記述子と知らせ | 32 から 96 byte | 輪の配列 | 輪の中を動くだけで、確保しません |

### chunk と大きいバッファの置き場

接続は shard を移らないので、chunk と中継の大きいバッファは、取った shard の置き場に返ります。
shard をまたぐ解放は起きません。
shard 0 は今と同じく chunk を 64 個、大きいバッファを 16 個まで残し、持ち主の shard はそれぞれ 32 個と 8 個まで残します(設計判断、値は試作で決めます)。

### 持ち主ごとの block の上限

平文の block は、複数の持ち主の packet を含むことがあります。
持ち主が押さえるメモリは、queue の packet の byte ではなく、参照を持つ block の数で決まります。

- 数え方:shard 0 は持ち主ごとに、その持ち主が参照を持つ block の数を数えます。
  block に初めてその持ち主の packet を書いた時に 1 つ増やし、持ち主が block の返却の輪で返した時に減らします
- 上限:持ち主ごとに上限 (仮の値は 16 block、256 KiB) を置きます。
  上限に達した持ち主の TCP の segment は、新しい block に書かずに捨てて数えます
- 置き場の大きさ:M_pt は、shard 0 の 1 バッチ分の作業の block と、上限の和 (N-1) × 上限 以上にします。
  このため、遅い持ち主がいても shard 0 は常に空いた block を取れ、読みを止めません
- 遅い持ち主の影響:捨てるのはその持ち主の接続の segment だけで、ほかの持ち主と UDP は影響を受けません
- 変換の無い形:link の枠を engine の置き場から貸す link (TUN など) は、同じ block の数えに入れます。
  link が自分の枠を貸す link (AF_XDP の UMEM) は、スレッドをまたぐ前に block に写し、link の枠を持ち主に待たせません(設計判断)

## 予算と枠を 1 つにする値

置き場の枠と予算は、`Lease` (仮の名前) という 1 つの型の値で表します。

- `Lease` は複製できず、捨てると枠と予算を置き場に返します
- shard の間で `Lease` を動かすと、予算の数えも一緒に動きます
- 上界の式の各項は置き場の容量で、`Lease` の行き先によりません

## 所有者が挙げた領域と項の対応

| 領域 | 項 |
|---|---|
| TCP の状態 | M_fix の接続の枠、握手の途中の表、4 つ組の表 |
| TCP の送受信のバッファ | N_c × (f_s + f_r) と G |
| SACK、RACK、再送 | 再送のデータは送信の輪の chunk (f_s と G)、記録は r_f と G の段の配列、区間は h_f と G の段の配列、RACK と TLP の値は接続の枠の中 |
| TIME_WAIT | M_fix の TIME_WAIT の表 |
| 再組み立て | M_frag |
| UDP | M_udp_rx、M_udp_tx、M_fix の endpoint の表 |
| WireGuard の暗号のバッファ | M_ct、M_pt、M_tx,0、M_sh,k の送信の枠、貸し出しの輪 |
| WireGuard の状態とキュー | M_dev |
| 制御の message | M_ring の制御の輪と返却の輪、M_fix と M_sh,k の制御の輪 |
| タイマー | M_fix のタイマーの節と、握手の途中と TIME_WAIT の list |
| スレッドのスタック | M_base、S_stk、今と同じ名前の解決のスレッドの項 |
| 実行環境 | M_base と R_rt |
| 中継 | M_relay と、M_sh,k の大きいバッファと handle の層の表 |
| 割り当て器 | 論理の上界の外。RSS の上界で数えます (次の節) |

二重の数えが無いことは、次の 3 点で示します。

- 置き場の容量だけを項にし、置き場の中を動く値 (記述子、`Lease`) を別に数えません
- 枠の数で決まる配列と表は shard に分け、和を全体の数と等しくします
- credit は G の内側の数で、別の項を持ちません

数え漏れが無いことは、shard のスレッドの確保をすべて上の置き場から行い、置き場の外の確保を数えの試験で 0 と確かめることで示します([メモリの試験](verification.md#メモリの試験))。

## 論理の上界と RSS の上界

論理の上界は上の式の和で、プロセスが持てる状態とデータの byte を、要求した大きさで数えます。
RSS の上界は、論理の上界に次の分を加えた値です。

- 割り当て器の丸めと管理の領域:起動の時の確保と流れごとの確保の大きさに、割り当て器ごとに測った係数を掛けます
- 割り当て器の arena:製品の build は musl で、割り当て器は 1 つの heap を持ちます。
  glibc の build はスレッドごとに arena を作るので、arena の数と arena ごとの断片化の余裕を加えます。
  S では接続が shard を移らず、chunk と大きいバッファと中継の task は取った shard が返すので、別の arena への解放は起きません(推定)
- スタック:上界はスタックの全体で数えます
- ページの丸め:大きな置き場の端の切り上げです

RSS は上界よりずっと小さいことが多く、置き場の触っていないページは RSS に入りません。
ラボの確認は今と同じく、RSS が上界と決めた余裕の和以下であることを N ごとに確かめます([agent の上界の表](../../v2/agent-bound.md))。

## カーネルの保持

今の上界は、カーネルのソケットのバッファを数えません([agent の上界の表](../../v2/agent-bound.md)の起動の行の説明)。
カーネルのバッファはプロセスの RSS に入らないので、別の行として推定の上界を示せます。

- 外側のソケット:受けたと読み返した受信と送信のバッファの大きさ
- LAN の側の TCP のソケット:流れの数 K と、接続ごとの受信と送信のバッファの上限の積
- LAN の側の UDP のソケット:セッションの数と、セッションごとのバッファの上限の積

カーネルはバッファを packet ごとの管理の分を含めて数えるので、この行は保証ではなく推定です(未確認)。

## 尽きた時の規則

どの資源も、尽きた時に新しい保持を拒み、既存の保持を追い出しません([尽きたときの動作](../../userspace/wgstack.md#尽きたときの動作))。

### TCP の尽きた時

| 資源 | 扱い |
|---|---|
| 接続の枠 | 空きのある持ち主に置きます。どの持ち主にも空きが無ければ、今と同じく最後の ACK を捨てて握手の途中の行を残します |
| 握手の途中の表 | cookie を返します。今と同じです |
| 段の予算 | 今の段のまま続け、回収を求めます |
| 送信のバッファと記録 | アプリケーションの書き込みに `WouldBlock` を返します。再送のデータは捨てません (I4) |
| 持ち主の block の上限 | その持ち主の TCP の segment を捨てて数えます。経路での損失と同じ扱いで、送り手が回復します |
| 平文の置き場 | 上限の和より大きく取るので、持ち主のために尽きることはありません |
| 送信の枠と貸し出しの在庫 | 持ち主が核から引くのを止めます。データは核の送信の輪に残るので失いません |
| 制御の輪と返却の輪 | 容量を知らせの数の上界から決めるので、満ちません |

持ち主の block の上限で捨てる segment は、まだ確認していない受信のデータなので、I4 の「再送に要る未確認のデータを黙って捨てない」には当たりません。

### UDP の尽きた時

| 資源 | 扱い |
|---|---|
| 受信の予算 | datagram を捨て、ICMP を返しません。今と同じです |
| 送信の予算 | 送信は `WouldBlock` を返し、応答の送信 (`send_to_latest`) は古いものから捨てます。今と同じです |
| 会計の不整合 | engine の UDP を止めます。TCP は止めません |

### 回復

入力が止まると、平文の block、送信の枠、輪の記述子は持ち主の処理の後にすべて置き場に戻ります。
段の予算は、需要の無い保有者を最初の段に戻す今の回収の規則で戻ります。
入力が止まった後に保持が戻ることを、N が 2 以上の敵対的な保持の試験で確かめます([メモリの試験](verification.md#メモリの試験))。
