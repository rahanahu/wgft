# 停止した server の撤去

server の通常の停止は WireGuard と wgft のテーブルを残します。
撤去は停止した server が所有するものだけを明示して取り除きます。


撤去(アンインストール):

`vpsd` は停止しても wg0 と `table inet wgft` を残します(再起動で転送を途切れさせないため)。
やめるときは、`vpsd` が自分で作ったものだけを削除する撤去操作を CLI の 1 コマンドとして持ちます。
これは**停止した `vpsd` の後片付け**として行います。
`vpsd` が稼働中なら何も削除せずに拒否し、先に停止するよう案内します。
動いたまま削除すると、次のルール変更や systemd の再起動で作り直されます。
稼働の判定は、`vpsd` が起動時に状態ファイルへ取る flock(エージェントの状態ファイルと同じ形)で行います。

撤去の間の排他(2026-10-03、所有者の決定):何かを変える撤去は、ロックファイルが無ければ作ってロックを取り、サーバのデータベースを開く前から終わるまで持ちます。
取れなければ稼働中として拒否します。
判定の後に起動した `vpsd` が、撤去の途中で wg0 とテーブルを作り直すことと、`--purge` が削除するデータベースを使うことを防ぐためです。
`vpsd` もデータベースを開く前にこのロックを取る([9 節](../state.md#9-状態の保存と再起動))ので、ロックを持つ撤去の間に起動した `vpsd` はデータベースにも wg0 にもテーブルにも触れずに終了コード 1 で終わります。
同梱の unit が再起動を繰り返しても、撤去が終わるまでは同じ所で終わり、撤去が終わった後の再起動で起動します。
ロックファイルが無い場合も作って取るのは、取らずに進むと、撤去が不在を読んだ後に起動した `vpsd` がロックファイルを作って資源を作り、撤去がその資源を削除しうるためです。

ロックの状態を読めなければ、何も削除せずに止まります。
ロックファイルが symlink か FIFO である場合と、権限で開けない場合がこれに当たります。
以前は警告を出して撤去を続けていました。
稼働中の `vpsd` の資源を削除する危険を、撤去が進めないことより重く見ます。

撤去が作ったロックファイルは、持ち主とグループを、サーバのデータベースの置き場のディレクトリの持ち主とグループに合わせます。
同梱の unit は `vpsd` を `DynamicUser=yes` で動かします。
root の撤去が作った 0600 のロックファイルが root の持ち物のまま残ると、`vpsd` は次の起動でそれを開けず、終了コード 1 の再起動を繰り返します。
持ち主の正しい置き場の中にある root の持ち物のファイルを systemd が直さないことは、systemd 252 のラボで確かめました。
付け替えはロックを取った記述子に対して行い、既にあったロックファイルの持ち主は変えません。
作ってから付け替えるまでの短い間に撤去が強制終了された場合だけは、root の持ち物のロックファイルが残りえます。
この場合、`vpsd` の起動の誤りはロックファイルを開けないことを示すので、運用者はロックファイルを削除して起動し直します。

置き場のディレクトリそのものが無ければ、何かを変える撤去は、`vpsd` の起動と同じく 0700 で作ってからロックファイルを作ってロックを取り、その旨を出力に示します。
取らずに進むと、撤去の途中に起動した `vpsd` が、systemd の作った置き場でロックを取って資源を作り、撤去がその資源とデータベースを削除するためです。
撤去が作ったディレクトリとその中のロックファイルは root の持ち物のまま残します。
合わせる先の持ち主が無いためです。
同梱の unit では、systemd が次の起動で root の持ち物の `/var/lib/wgft` を `/var/lib/private/wgft` へ移し、中のファイルごと持ち主を付け替えるので、`vpsd` は起動します。
これはラボで確かめました。
`vpsd` を非 root の利用者で手で動かす配置で、`vpsd` が一度も置き場を作っていないうちに root が撤去を実行した場合は、運用者が置き場の持ち主を直す必要がありえます。
この場合は未確認です。
`--dry-run` と `--yes` の無い `--purge` は、置き場もロックファイルも作りません。
置き場のパスが行き先の無い symlink である場合、例えば `/var/lib/private/wgft` だけが削除されて `/var/lib/wgft` が残っている場合は、置き場を作れないので、撤去は何も削除せずに終了コード 1 で止まります。
この扱いは単体試験で確かめたもので、同梱の unit の上では未確認です。

撤去が途中で強制終了されると、ロックはカーネルが放し、ロックファイルは置き場の持ち主の持ち物のまま残ります。
`vpsd` はそのまま起動でき、撤去もそのまま実行し直せます。

撤去はサーバのデータベースを読むだけなので、読み取り専用で開き、スキーマの移行も権限の締め直しもしません。
`--purge` で削除するデータベースと、`--purge` の無い撤去が残すデータベースのどちらも、移行する理由がありません。
残すデータベースは、次に起動した `vpsd` が移行します。
以前は書き込みの形で開いていたので、`--dry-run` でも古い版のスキーマを移行し、その版の `vpsd` が開けないデータベースにしていました。

`--dry-run` は何も作らず、何も書きません。
ロックファイルを作らない `Inspect`([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))で同じ判定をし、稼働中なら拒否し、ロックの状態を読めなければ止まります。
ロックは取りません。
取ると、試しの間に起動した `vpsd` が終了コード 1 で終わるためです。
`--yes` の無い `--purge` も、削除するものを示して確認を求めるだけなので、同じ扱いにします。

削除する順序と対象は次のとおりです。
対象は `vpsd` が作ったものだけで、既に無いものはエラーにせず飛ばします。

1. `table inet wgft` を削除します。
   他のテーブルには触れません。
2. ルール 0 件で [6.1 節](../vps/kernel.md#61-カーネルモード)の conntrack 収束を実行し、wgft 由来の DNAT 済みエントリを削除します(テーブルを削除してもエントリは残るため)。
   順序はテーブルの削除、conntrack の収束、wg0 の削除です。
3. wg0 を削除します。
   削除するのは秘密鍵が状態ファイルのサーバ鍵と一致するインタフェースだけで、状態ファイルに鍵が無い(空)場合は相手の鍵が空でも所有とみなさず、`--adopt-existing` を要求します。
   `--adopt-existing` でも、同名でも WireGuard 以外のリンク(veth や bridge)は削除しません。
4. `--purge` のときだけ、状態ファイルを削除します。
   SQLite は WAL なので、`.sqlite` と `-wal`・`-shm` の 3 つです。
   最後にロックファイルを削除し、その後でロックを放します。
   放した後に起動した `vpsd` は新しいロックファイルとデータベースを作り、撤去の後の新しい起動と同じ結果になります。

wg インタフェース名は、`vpsd` が起動のたびに撤去用の手掛かりとしてサーバのデータベースへ記録します。
`--wg-interface` を変えても撤去が追従できるようにするためです。
teardown コマンド自身には名前を渡す手段がありません。
この記録が無い、または読めない場合、撤去は既定名 `wgft0` を仮定し、その旨を出力に示します([10.5 節](output.md#105-読み取り失敗の見せ方))。
黙って仮定すると、`--adopt-existing`(鍵の一致を見ずに削除する)と組み合わさったときに、実際とは別名の無関係な WireGuard インタフェースを削除しかねないためです。
この場合の対処は、実際のインタフェース名を確かめてから手で削除するか、記録が失敗する原因(サーバのデータベースへの書き込み)を直してから `vpsd` を再起動し、記録し直させることです。

可逆性:`--purge` を付けない撤去は元に戻せます。
`vpsd` を起動し直せば同じ鍵と証明書で wg0 とテーブルが戻り、エージェントは再接続だけで復旧します([9 節](../state.md#9-状態の保存と再起動))。
鍵が消えて再登録が要るのは `--purge` のときだけです。

自動では戻さないものは、「手で戻す一覧」として出すだけにします。
追加を自動で行わない原則の裏返しです。
一覧は一般論ではなく、状態ファイルと実状態から具体値を出します。

- VPS のファイアウォールで開けたポート。
  SQLite から出します(`wg-port` の UDP、エージェント用 API の TCP、全ルールの `listen_port`)。
- 他のテーブルに追加した wg0 を参照する行([6.1 節](../vps/kernel.md#61-カーネルモード)の提示で `DOCKER-USER` などに追加した `oifname "wg0" accept` の類)。
  実状態から所在を列挙します(`check` の検査の逆向き)。
- `ip_forward`。
  [6.1 節](../vps/kernel.md#61-カーネルモード)の 2 段の記録と、撤去が読んだ今の値から、次のどれかを出します(2026-10-03、所有者の決定)。
  他の転送が使っている可能性があるので自動では戻しません。
  - 確定の記録がある:`vpsd` が 0 から 1 にした日時と、他に転送を使っていなければ戻す手順を示します。
    予定の記録の有無は問いません
  - 確定の記録が無く、予定の記録がある:`vpsd` が 0 を読んで 1 を書き始めた日時と、結果を記録していないので `vpsd` が変えたかもしれないことを示します。
    今の値を添え、確かめて判断するよう案内し、`vpsd` が変えていて他に転送を使っていなければ戻す手順を示します。
    書いた直後に止まった場合と、書けなかった場合などを撤去は区別できないので、変えたとも変えていないとも言い切りません
  - どちらの記録も無い:`vpsd` は変えておらず、何もしなくてよいと示し、今の値を添えます。
    以前は今の値を読まずに「already 1」と示していました
  - 記録を読めない:どれとも言わず、読めなかった理由と今の値を示し、確かめて判断するよう案内します。
    以前は読めない記録を「変えていない」として示していました

  今の値を読めなければ、値の代わりに読めなかった理由を示します。
  今の値は読むだけで、書けるかの probe もしません。
  `--dry-run` も同じ行を出します。
  記録した `vpsd` と撤去が同じ network namespace で動くことを前提にします。
- systemd の unit・env、バイナリ、`/var/lib/wgft` ディレクトリは `vpsd` が置いたものではないので一覧に出します。

全体の順序:先に自宅エージェントを止めるか VPS 側で `agent revoke` し、その後 `vpsd` を停止して撤去します。
`agent revoke` は稼働中の `vpsd` に対してだけ動作します。
撤去後にエージェントが残っても、接続不能を [5.1 節](../control/registration.md#51-登録)の一時障害とみなしてバックオフ再接続を続けるだけで害はありませんが、止まりません。

ユーザー空間モードの自宅エージェントは wireguard-go と netstack なのでカーネルに何も残さず、プロセスを止めて `agent.json`(と隣の `.lock`・`.sock`)を削除すれば消えます。
VPS 側では、エージェントの削除が恒久トークンを使えなくし、ピア・conntrack・割り当てアドレスを回収します。

カーネルモードのエージェント([7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))は、停止しても wgft0 と `table inet wgft_agent` を残します。
これを削除するのが `wgft agent teardown` で、`server teardown` と同じく停止したエージェントの後片付けとして行います(2026-09-24、所有者の決定)。
稼働中のエージェントの 30 秒ごとの収束や外からの変更への収束は削除した資源を作り直しうるので、エージェントが稼働中なら撤去は何も削除せずに拒否し、先に停止するよう案内します。
この拒否は普通の誤りであり、終了コードは 1 です。
稼働の判定は、`rotate-key` と同じくロックファイルを作らない `Inspect`([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))で行います。
判定の後に起動したエージェントが撤去の途中で資源を作り直さないように、ロックファイルがあって誰も持っていなければ、撤去は flock を取って終わるまで持ちます。
取れなければ稼働中として拒否します。
ロックファイルが無ければ、`rotate-key` と同じ理由で flock を取らずに進めます([9 節](../state.md#9-状態の保存と再起動))。
ロックの状態を読めなければ、何も削除せずに止まります。

撤去が読む設定は、`agent run` と同じ `WGFT_DATA_DIR` と `WGFT_WG_INTERFACE` であり、`agent.env` とフラグの別名(`--data-dir`、`--wg-interface`、`--config`)から受け取ります。

削除する順序と対象は次のとおりです(2026-09-24)。
既に無いものは誤りにせず飛ばすので、途中で止まった撤去はそのまま実行し直せます。

1. WireGuard インタフェースのうち、秘密鍵が状態ファイルの鍵か 1 つ前の鍵([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))と一致するものを、名前によらず削除します。
   設定の名前のもの、作業用の名前 `wgftnew<CRC32>`([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))のもの、`WGFT_WG_INTERFACE` を変える前の名前で残ったものがこれに当たります。
   テーブルを先に削除すると、wgft0 が残っている間に filter_pre と input の守りが無くなるので、インタフェースを最初に削除します
2. conntrack のエントリのうち、wgft0 から入って wgft が DNAT したものを削除します。
   状態ファイルの公開の記録と、収束が済んでいない公開の列([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))を前の公開とし、空の公開を今の公開として、[7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止)の収束を実行します。
   撤去はこれらの記録を削除するので、後でカーネルモードで起動し直したときの収束は、撤去の前のフローを見分けられません。
   ここで削除しなければ、宣言から消えた宛先へ DNAT したエントリが conntrack の期限まで残ります。
   エージェントのトンネルアドレスは `last_state` から取ります。
   停止中の `rotate-key` の後のように `last_state` が無ければ、削除する前のインタフェースのアドレスを使います。
   前の公開の記録が無いか、どちらからもアドレスが分からなければ、wgft のフローを見分けられないので何も削除せず、その旨を示します。
   conntrack の読み出しか削除に失敗した場合は、警告を出して続けます
3. `table inet wgft_agent` を削除します。
   他のテーブルには触れません
4. 状態ファイル `agent.json` のカーネルモードの記録を削除して保存します。
   削除するのは、モード、1 つ前の鍵、`ip_forward` の記録、公開の記録、収束が済んでいない公開の列です。
   撤去の後にユーザー空間モードで起動し直せるように、登録の情報、今の鍵、`last_state` は残します。
   1 か 3 が失敗した場合は記録を削除せずに誤りを返すので、関門は残った資源を見落としません。
   保存は元のファイルの持ち主を保ちます([9 節](../state.md#9-状態の保存と再起動))

起動時のエージェントは、別の名前で今の鍵か 1 つ前の鍵を持つインタフェースを警告するだけで削除しません([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
撤去はこれを削除します(2026-09-24)。
所有の根拠は鍵であり、名前が変わっても所有は変わりません。
常駐のプロセスは運用者が `WGFT_WG_INTERFACE` を変えた意図を推し量らずに警告にとどめ、撤去は運用者が明示して実行する後片付けとして削除します。
削除する前の名前は `--dry-run` で確かめられます。

設定の名前か作業用の名前を持つリンクのうち、鍵が一致しない WireGuard インタフェース、鍵を持たない WireGuard インタフェース、WireGuard 以外のリンクには触れません。
撤去はその名前と理由を出力に示し、状態ファイルを失って鍵が一致しなくなった場合に `ip link del <名前>` で削除する手順を示します([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
ユーザー空間モードのエージェントはカーネルのインタフェースを使わず、残ったリンクは切り替えを妨げないので、この場合も撤去は成功として終えます。

特殊な場合の扱いは次のとおりです(2026-09-24)。

- 何も残っていないホスト:何も変えずに成功として終えます
- 記録だけが残ったホスト:ホストを再起動した後は wgft0 もテーブルも無く、状態ファイルの記録だけが [11a 節](../security/configuration.md#11a-設定の渡し方)の切り替えの関門を止めます。
  撤去は記録を削除して成功として終えます
- 状態ファイルが無いデータディレクトリ:何も削除せず、見つけた `table inet wgft_agent` と WireGuard インタフェースを示して、普通の誤りとして終了コード 1 で止まります(2026-09-24、所有者の決定)。
  インタフェースのうち、`WGFT_WG_INTERFACE` の名前と作業用の名前のものには wgft の設定の名前である印を付け、個人の VPN など他の WireGuard のリンクと見分けられるようにします。
  稼働の判定は指したデータディレクトリのロックファイルしか見ないので、`--data-dir` がエージェントの実際のデータディレクトリを指していないと、稼働中のエージェントを停止したものと取り違えます。
  そのまま削除すると、稼働中のエージェントのテーブルが消え、次の見直しまで転送が止まります。
  ラボで再現しました。
  文面は、指したディレクトリに認証情報が無いことと、`--data-dir` か `WGFT_DATA_DIR` で実際のデータディレクトリを指すことを示し、認証情報を本当に失った場合は、エージェントを止めて持ち主を確かめたうえで `nft delete table inet wgft_agent` と `ip link del <名前>` で手で削除する道を示します。
  [11b 節](../security/startup.md#11b-起動の失敗の意味論)の非対称の規則は、systemd の再起動を止める終了コード 3 を避けるための規則であり、1 回だけ実行するコマンドには当てはまりません。
  この場合も、稼働中のエージェントへの拒否や `server teardown` の誤りと同じく、何も削除せずに止まった普通の誤りとして終了コード 1 にします
- 未知のモードの記録:記録が `kernel` でも `userspace` でもなければ、何も削除せずに種別 `conflict` の拒否で止まります。
  その記録は新しい版が書いた可能性があり、この版はその版が残した資源を判定できません。
  記録を削除すると、その版の撤去が手掛かりを失います。
  文面は、記録を書いた版の撤去を使う道と、状態ファイルを控えから戻す道を示します
- 権限の不足:インタフェースとテーブルの読み書きには `CAP_NET_ADMIN` が要ります。
  足りなければ種別 `prerequisite` の拒否で止まります。
  `--dry-run` も同じ読み出しを行うので、同じく止まります

フラグは [11a 節](../security/configuration.md#11a-設定の渡し方)の 1 回限りの操作の規則に従い、設定の別名のほかに `--dry-run` だけを持ちます。
`--dry-run` は、削除するもの、触らないもの、手で戻す一覧を示し、何も変えません。
稼働中のエージェントに対しては、`--dry-run` も拒否します。
確認の `--yes` は持ちません。
`server teardown` が確認を求めるのは元に戻せない `--purge` だけです。
エージェントの撤去は登録の情報と鍵を残し、`WGFT_MODE=kernel` で起動し直せば wgft0 とテーブルが戻るので、確認を求めません。
消える `ip_forward` の記録の中身は、撤去の出力が示します。

自動では戻さないものは、状態ファイルの記録から具体値を出した「手で戻す一覧」として示します。

- `ip_forward`:他の用途で転送を使っているかもしれないので、自動では戻しません。
  状態ファイルの記録から「エージェントが 0→1 にした(日時)」か「0 から変えた記録が無い」かを示し、前者だけ戻し方を示します
- `WGFT_MODE`:`agent.env` の `WGFT_MODE=kernel` を外すか `userspace` にしてから起動します。
  残したまま起動すると、エージェントはカーネルモードで資源を作り直します
- `CAP_NET_ADMIN`:カーネルモードのためにエージェントの unit へ重ねた権限は、ユーザー空間モードでは要りません

出力は、削除するもの、触らないもの、実行の結果、手で戻す一覧を 1 行ずつ示します。
人が読む表示であり、[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の保証の外です。
Windows と macOS では、`server` の一群と同じく種別 `prerequisite` の拒否として終了コード 3 で止まります([11b 節](../security/startup.md#11b-起動の失敗の意味論))。
