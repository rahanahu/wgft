# 停止した server の撤去

server の通常の停止は WireGuard と wgft のテーブルを残します。
撤去は停止した server が所有するものだけを明示して取り除きます。


撤去(アンインストール):

`vpsd` は停止しても wg0 と `table inet wgft` を残す(再起動で転送を途切れさせないため)。
やめるときは、`vpsd` が自分で作ったものだけを消す撤去操作を CLI の 1 コマンドとして持ちます。
これは**停止した `vpsd` の後片付け**として行います。
`vpsd` が稼働中なら何も消さずに拒否し、
先に停止するよう案内する(動いたまま消すと、次のルール変更や systemd の再起動で
作り直される)。
稼働の判定は、`vpsd` が起動時に状態ファイルへ取る flock(エージェントの
状態ファイルと同じ形)で行います。

撤去の間の排他(2026-10-03、所有者の決定):何かを変える撤去は、ロックファイルが無ければ作ってロックを取り、サーバのデータベースを開く前から終わるまで持ちます。
取れなければ稼働中として拒否します。
判定の後に起動した `vpsd` が、撤去の途中で wg0 とテーブルを作り直すことと、`--purge` が消すデータベースを使うことを防ぐためです。
`vpsd` もデータベースを開く前にこのロックを取る([9 節](../state.md#9-状態の保存と再起動))ので、ロックを持つ撤去の間に起動した `vpsd` はデータベースにも wg0 にもテーブルにも触れずに終了コード 1 で終わる。
同梱の unit が再起動を繰り返しても、撤去が終わるまでは同じ所で終わり、撤去が終わった後の再起動で起動します。
ロックファイルが無い場合も作って取るのは、取らずに進むと、撤去が不在を読んだ後に起動した `vpsd` がロックファイルを作って資源を作り、撤去がその資源を消しうるためです。
ロックの状態を読めなければ、何も消さずに止まります。
ロックファイルが symlink か FIFO である場合と、権限で開けない場合がこれに当たる。
以前は警告を出して撤去を続けていました。
稼働中の `vpsd` の資源を消す危険を、撤去が進めないことより重く見る。

撤去が作ったロックファイルは、持ち主とグループを、サーバのデータベースの置き場のディレクトリの持ち主とグループに合わせる。
同梱の unit は `vpsd` を `DynamicUser=yes` で動かす。
root の撤去が作った 0600 のロックファイルが root の持ち物のまま残ると、`vpsd` は次の起動でそれを開けず、終了コード 1 の再起動を繰り返します。
持ち主の正しい置き場の中にある root の持ち物のファイルを systemd が直さないことは、systemd 252 のラボで確かめた。
付け替えはロックを取った記述子に対して行い、既にあったロックファイルの持ち主は変えません。
作ってから付け替えるまでの短い間に撤去が強制終了された場合だけは、root の持ち物のロックファイルが残りうる。
この場合、`vpsd` の起動の誤りはロックファイルを開けないことを示すので、運用者はロックファイルを消して起動し直す。
置き場のディレクトリそのものが無ければ、何かを変える撤去は、`vpsd` の起動と同じく 0700 で作ってからロックファイルを作ってロックを取り、その旨を出力に示します。
取らずに進むと、撤去の途中に起動した `vpsd` が、systemd の作った置き場でロックを取って資源を作り、撤去がその資源とデータベースを消すためです。
撤去が作ったディレクトリとその中のロックファイルは root の持ち物のまま残します。
合わせる先の持ち主が無いためです。
同梱の unit では、systemd が次の起動で root の持ち物の `/var/lib/wgft` を `/var/lib/private/wgft` へ移し、中のファイルごと持ち主を付け替えるので、`vpsd` は起動します。
これはラボで確かめた。
`vpsd` を非 root の利用者で手で動かす配置で、`vpsd` が一度も置き場を作っていないうちに root が撤去を実行した場合は、運用者が置き場の持ち主を直す必要がありうる。
この場合は未確認です。
`--dry-run` と `--yes` の無い `--purge` は、置き場もロックファイルも作りません。
置き場のパスが行き先の無い symlink である場合、例えば `/var/lib/private/wgft` だけが消されて `/var/lib/wgft` が残っている場合は、置き場を作れないので、撤去は何も消さずに終了コード 1 で止まります。
この扱いは単体試験で確かめたもので、同梱の unit の上では未確認です。
撤去が途中で強制終了されると、ロックはカーネルが放し、ロックファイルは置き場の持ち主の持ち物のまま残る。
`vpsd` はそのまま起動でき、撤去もそのまま実行し直せる。

撤去はサーバのデータベースを読むだけなので、読み取り専用で開き、スキーマの移行も権限の締め直しもしません。
`--purge` で消すデータベースと、`--purge` の無い撤去が残すデータベースのどちらも、移行する理由がありません。
残すデータベースは、次に起動した `vpsd` が移行します。
以前は書き込みの形で開いていたので、`--dry-run` でも古い版のスキーマを上げ、その版の `vpsd` が開けないデータベースにした。

`--dry-run` は何も作らず、何も書きません。
ロックファイルを作らない `Inspect`([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))で同じ判定をし、稼働中なら拒否し、ロックの状態を読めなければ止まります。
ロックは取らない。
取ると、試しの間に起動した `vpsd` が終了コード 1 で終わるためです。
`--yes` の無い `--purge` も、消すものを示して確認を求めるだけなので、同じ扱いにします。

消す順序と対象(`vpsd` が作ったものだけ。
既に無いものはエラーにせず飛ばす):

1. `table inet wgft` を削除します。
   他テーブルには触れない。
2. ルール 0 件で [6.1 節](../vps/kernel.md#61-カーネルモード)の conntrack 収束を走らせ、wgft 由来の DNAT 済みエントリを消す(テーブルを消してもエントリは残るため)。
   順序はテーブル削除・conntrack 収束・wg0 削除。
3. wg0 を削除します。
   消すのは秘密鍵が状態ファイルのサーバ鍵と一致するインタフェースだけで、状態ファイルに鍵が無い(空)場合は相手の鍵が空でも所有とみなさず、`--adopt-existing` を要求します。
   `--adopt-existing` でも、同名でも WireGuard 以外のリンク(veth や bridge)は消さない。
4. `--purge` のときだけ、状態ファイルを消す。
   SQLite は WAL なので `.sqlite` と `-wal`・`-shm` の 3 つ。
   最後にロックファイルを消し、その後でロックを放す。
   放した後に起動した `vpsd` は新しいロックファイルとデータベースを作り、撤去の後の新しい起動と同じ結果になります。

wg インタフェース名は、`vpsd` が起動のたびに撤去用の手掛かりとしてサーバのデータベースへ記録する(`--wg-interface` を変えても撤去が追従できるようにするため。
teardown コマンド自身には名前を渡す手段が無い)。
この記録が無い、または読めない場合、撤去は既定名 `wgft0` を仮定するとその旨を出力に示す([10.5 節](output.md#105-読み取り失敗の見せ方))。
黙って仮定すると、`--adopt-existing`(鍵の一致を見ずに削除する)と組み合わさったときに、実際とは別名の無関係な WireGuard インタフェースを消しかねないためです。
この場合の対処は、実際のインタフェース名を確かめてから手で消すか、記録が失敗する原因(サーバのデータベースへの書き込み)を直してから `vpsd` を再起動し、記録し直させることです。

可逆性:`--purge` を付けない撤去は元に戻せる。
`vpsd` を起動し直せば同じ鍵と証明書で
wg0 とテーブルが戻り、エージェントは再接続だけで復旧する([9 節](../state.md#9-状態の保存と再起動))。
鍵が消えて
再登録が要るのは `--purge` のときだけです。

自動では戻さないもの(「手で戻す一覧」を出すだけ。
追加を自動でやらない原則の裏返し)。
一覧は一般論ではなく、状態ファイルと実状態から具体値を出す:

- VPS のファイアウォールで開けたポート。
  SQLite から出す(`wg-port` の UDP、エージェント用 API の TCP、全ルールの `listen_port`)。
- 他テーブルに足した wg0 参照行([6.1 節](../vps/kernel.md#61-カーネルモード)の提示で `DOCKER-USER` などに足した `oifname "wg0" accept` の類)。
  実状態から所在を列挙する(`check` の検査の逆向き)。
- `ip_forward`。
  [6.1 節](../vps/kernel.md#61-カーネルモード)の 2 段の記録と、撤去が読んだ今の値から、次のどれかを出す(2026-10-03、所有者の決定)。
  他の転送が使っている可能性があるので自動では戻しません。
  - 確定の記録がある:`vpsd` が 0 から 1 にした日時と、他に転送を使っていなければ戻す手順を示します。
    予定の記録の有無は問わない
  - 確定の記録が無く、予定の記録がある:`vpsd` が 0 を読んで 1 を書き始めた日時と、結果を記録していないので `vpsd` が変えたかもしれないことを示します。
    今の値を添え、確かめて判断するよう案内し、`vpsd` が変えていて他に転送を使っていなければ戻す手順を示します。
    書いた直後に止まった場合と、書けなかった場合などを撤去は区別できないので、変えたとも変えていないとも言い切らない
  - どちらの記録も無い:`vpsd` は変えておらず、何もしなくてよいと示し、今の値を添える。
    以前は今の値を読まずに「already 1」と示していました
  - 記録を読めない:どれとも言わず、読めなかった理由と今の値を示し、確かめて判断するよう案内します。
    以前は読めない記録を「変えていない」として示していました

  今の値を読めなければ、値の代わりに読めなかった理由を示します。
  今の値は読むだけで、書けるかの probe もしません。
  `--dry-run` も同じ行を出す。
  記録した `vpsd` と撤去が同じ network namespace で動くことを前提にします。
- systemd の unit・env、バイナリ、`/var/lib/wgft` ディレクトリは `vpsd` が置いたものではないので一覧に出す。

全体の順序:先に自宅エージェントを止めるか VPS 側で `agent revoke` し(稼働中の `vpsd`
にしか効かない)、その後 `vpsd` を停止して撤去します。
撤去後にエージェントが残っても、
接続不能を [5.1 節](../control/registration.md#51-登録)の一時障害とみなしてバックオフ再接続を続けるだけで害はないが、止まらない。

ユーザー空間モードの自宅エージェントは wireguard-go と netstack なのでカーネルに何も残さず、
プロセスを止めて `agent.json`(と隣の `.lock`・`.sock`)を消せば消える。
VPS 側では、
エージェントの削除が恒久トークンを使えなくし、ピア・conntrack・割り当てアドレスを回収します。

カーネルモードのエージェント([7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))は、停止しても wgft0 と `table inet wgft_agent` を残します。
これを消すのが `wgft agent teardown` であり、`server teardown` と同じく停止したエージェントの
後片付けとして行う(2026-09-24、所有者の決定)。

外からの変更への収束は消した資源を作り直しうるので、エージェントが稼働中なら撤去は何も消さずに
拒否し、先に停止するよう案内します。
この拒否は普通の誤りであり、終了コードは 1 です。
稼働の判定は、
`rotate-key` と同じくロックファイルを作らない `Inspect`([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))で行います。
判定の後に起動した
エージェントが撤去の途中で資源を作り直さないように、ロックファイルがあって誰も持っていなければ、
撤去は flock を取って終わるまで持ちます。
取れなければ稼働中として拒否します。
ロックファイルが無ければ、
`rotate-key` と同じ理由で flock を取らずに進める([9 節](../state.md#9-状態の保存と再起動))。
ロックの状態を読めなければ、何も消さずに止まります。

撤去が読む設定は、`agent run` と同じ `WGFT_DATA_DIR` と `WGFT_WG_INTERFACE` であり、`agent.env` と
フラグの別名(`--data-dir`、`--wg-interface`、`--config`)から受け取ります。

   filter_pre と input の守りが無くなるので、インタフェースを最初に消す

   撤去はこれらの記録を消すので、後でカーネルモードで起動し直したときの収束は、撤去の前のフローを
   見分けられない。

   他のテーブルには触れない
4. 状態ファイル `agent.json` のカーネルモードの記録を消して保存します。
   消すのは、モード、1 つ前の鍵、
   `ip_forward` の記録、公開の記録、収束が済んでいない公開の列です。
   撤去の後にユーザー空間モードで
   起動し直せるように、登録の情報、今の鍵、`last_state` は残します。

   誤りを返すので、関門は残った資源を見落とさない。

フラグは [11a 節](../security/configuration.md#11a-設定の渡し方)の 1 回限りの操作の規則に従い、設定の別名のほかに `--dry-run` だけを持ちます。
`--dry-run` は、
消すもの、触らないもの、手で戻す一覧を示し、何も変えません。
稼働中のエージェントに対しては、`--dry-run`
も拒否します。
確認の `--yes` は持ちません。
`server teardown` が確認を求めるのは元に戻せない `--purge` だけで
あります。
エージェントの撤去は登録の情報と鍵を残し、`WGFT_MODE=kernel` で起動し直せば wgft0 とテーブルが
戻るので、確認を求めません。
消える `ip_forward` の記録の中身は、撤去の出力が示します。

自動では戻さないものは、状態ファイルの記録から具体値を出した「手で戻す一覧」として示します。

- `ip_forward`:他の用途で転送を使っているかもしれないので、自動では戻しません。
  状態ファイルの記録から
  「エージェントが 0→1 にした(日時)」か「0 から変えた記録が無い」かを示し、前者だけ戻し方を示します
- `WGFT_MODE`:`agent.env` の `WGFT_MODE=kernel` を外すか `userspace` にしてから起動します。
  残したまま
  起動すると、エージェントはカーネルモードで資源を作り直す
- `CAP_NET_ADMIN`:カーネルモードのためにエージェントの unit へ重ねた権限は、ユーザー空間モードでは要りません

出力は、消すもの、触らないもの、実行の結果、手で戻す一覧を 1 行ずつ示します。
