### ログ

ログは秘密を出さず、読み取りの失敗は黙って正常として扱いません。


`vpsd` とエージェントは、ログを標準エラー出力に 1 行ずつ書き、ファイルには書きません。
同梱の unit では journald が受け取るので、運用者は `journalctl -u wgft` と `journalctl -u wgft-agent` で読みます。
Docker では `docker logs` で読みます。
ログファイルとその回転は wgft が持ちません。

ログは、デバッグ用の設定なしで次の 5 つに答えられるだけの行を出す。

1. 起動に成功したか、どの版とモードで動いているか
2. どのエージェントが接続し、切断したか
3. どのルールの変更が適用されたか
4. どの世代がどのエージェントに届いたか
5. 転送が止まったとき、失敗が WireGuard、ルールの適用、待ち受け、中継先のどこで起きたか

行の種類は次のとおりです。

- 起動の行:`vpsd` は最初のルールとデータプレーンの適用が済み、管理用 API とエージェント用 API の待ち受けをすべて開けた時点で、版、モード、インタフェース名、世代、ルールとエージェントの件数を 1 行に出す。
  待ち受けを開けずに終わる場合は、この行を出さない。
  エージェントは起動時に版、名前、データの置き場所を出す
- ルールの変更の行:バッチ操作([5.4 節](../control/batches.md#54-ルールのバッチ操作))が成功するたびに、操作の出所、追加、変更、削除したルールの ID、結果の世代を 1 行に出す。
  出所は CLI のサブコマンド名か Web UI の操作名(追加、編集、削除、分割、統合、読み込み)で、バッチの要求の `op` で渡す。
  `op` は記録にだけ使い、挙動を変えません。
  `op` の無い要求は `api` と記録します。
  ID は種別ごとに 20 件までを出し、残りは件数で示します
- エージェントの出来事の行:登録、再登録、削除、鍵の再生成、stream の接続と切断、世代の配信と適用、窃取検知の警告(`ip-mismatch` は、警告の行を新しく作った回と、食い違いが連続 8 回に達した回に出す。
  同じ組の食い違いが続く間の更新では出さない)、`ip-mismatch` の確認済みの組の記録と破棄([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))を、エージェントの名前か世代とともに出す
- 失敗の行:WireGuard、nftables、ユーザー空間の転送、待ち受け、中継先のどれで起きたかと、元のエラーを含めます。
  ルールの変更を SQLite に確定した後でデータプレーンへの適用に失敗した場合は、変更の行に続けて失敗の行を出す
- 状態の行:エージェントは 30 秒ごとにトンネルとルールの状態を組み立てるが、前回と同じ内容なら出さない

パケットごと、成功したフローごとの行は出さない。
フローの上限での拒否と中継先への接続の失敗は、待ち受けごとに 1 分に 1 回までにします。
どちらも接続のたびに起きうる失敗で、中継先が落ちている間や不正な接続が続く間に journal を埋めるためです。
エージェントの stream の再接続の待ちの行も、前の行と同じ文面なら 1 分に 1 行までにし、文面が変われば、つまり待ちの長さか理由が変われば、すぐに出す。
間引いた数は次に出す行に添える。
`vpsd` のプロセスが止まっていてトンネルが新しい間は、待ちが 10 秒に留まり、同じ行が続くためである([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。

エージェント用 API の TLS のハンドシェイクの誤り(net/http が書く行のうち "TLS handshake error" を含む行)も同じ考え方で間引く(2026-10-01)。
この待ち受けは認証の前に TCP で届くので、相手は TLS のハンドシェイクを送らずに閉じるだけで行を出させられる。
行を、証明書を理由に拒んだもの(`bad certificate`。
[10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor)の運用の案内を添える)とその他の 2 つに分け、理由ごとに 1 分に 1 回まで間引く。
証明書を理由に拒んだ行を分けて持つのは、他の理由(ハンドシェイクを送らない接続など)が続いても、運用に要る案内の行が埋もれないようにするためです。
理由の文面そのものを鍵にした間引きは行いません。
相手が送った値(ALPN の一覧など)をそのまま埋め込む理由文があり、鍵の数を相手が増やせてしまうためです。
間引いた数は次に出す行に添える。
間引きの対象はこの行だけであり、同じ ErrorLog が書くほかの行(ハンドラの panic、Accept の誤りなど)はそのまま出す。

登録トークン、恒久トークン、秘密鍵、`Authorization` ヘッダ、接続文字列の全体はログに出さない。
公開鍵と、証明書の指紋の先頭は出してよい。
CI の検査(`scripts/check-log-tokens.sh`)は、トークンと接続文字列に触れるログの行を、人が確かめた行の一覧と照合します。

### 読み取り失敗の見せ方

サーバのデータベースやカーネルの wg 状態の読み取りが失敗したとき、失敗を「0 件」や「0」のような正常な結果に変えて見せてはなりません。
宛先ごとの見せ方は次のとおりです。

- サーバのログ:原因を記録します。
  同じ原因を要求のたびに際限なく記録しない(上の「パケットごと、成功したフローごとの行は出さない」と同じ考え方)。
  ただし 15 秒・30 秒間隔のような一定周期の監視ループ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の窃取検知など)は周期そのものが頻度の上限になるので、失敗するたびに 1 行出してよい
- 管理用 API:読み取りが失敗した応答は 5xx とし、本文にどの読み取りが失敗したかを含めます。
  世代 0 や空の一覧のような、捏造した値を 200 で返してはなりません
- CLI:管理用 API の 5xx は Client がそのままエラーとして返し、コマンドは 0 以外の終了コードで止まる([10.2 節](../interface.md#102-cli))。
  CLI 自身の側では別扱いを持ちません
- Web UI:ページや区画が依拠する読み取りが失敗したら、そのページ・区画はエラーの状態を出す。
  空の一覧や「0」のような、通常時と見分けの付かない値では描かない

セキュリティに関わる読み取りは、フェイルオープンかフェイルクローズかを次のとおり分ける。

- 窃取検知([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))の 15 秒ごとの監視は、wg のピア状態かエージェント一覧の読み取りに失敗すると、その回の判定を飛ばす(フェイルオープン)。
  判定を続ける他の手段が無いためで、原因はログに残します。
  この間は新たな不一致を検知できません
- ダッシュボードとルール詳細ページに出す適用状態(ok/pending/error/agent offline)、拒否数、拒否・許可リストは、運用者が「今は問題が無い」と判断する材料です。
  これらの元になる読み取りが失敗したら、正常に見える値を出さず、そのページ・区画をエラーの状態にする(フェイルクローズ)
- ルール読み込みの確認ページが使う世代とハッシュ([10.1 節](../interface.md#101-web-ui))は、読み取りに失敗した値をそのまま確認ページへ埋め込むと、後の一致判定を意図せず通してしまう(捏造した値どうしが偶然一致する)。
  世代の読み取りが失敗したら確認ページ自体を 500 で止め、確認や適用を進めない(フェイルクローズ)

一覧が 1 行の付随情報を欠いたまま続けてよいのは、その情報が他の計算に使われない、その行だけの補足であり、欠けたことをログに残すときに限る(admin_backend.go の `Agents()` が 1 エージェントの警告を読めなかった場合)。
エージェントのアドレスのように他の行や他の計算(wg のピア構成、アドレスの重複割り当ての判定)に使われる値では、読み取れない・解釈できない行があれば読み取り全体を失敗として返します。
半端な値で計算を続けるより、読み取りを丸ごと止める方が安全です。

`Agents()` の wg ピア状態(wgctrl の読み取り)は例外として、失敗してもエージェント一覧そのものは返す(フェイルオープン。
原因はログに残す)。
エンドポイント IP・最終ハンドシェイクの列が空欄になり、IP の食い違いの比較も出なくなるが、これは表示用の読み取りであり、窃取検知の正本は [5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の 15 秒ごとの監視です。
一覧全体を止めるほどの重みは無いと判断した。
