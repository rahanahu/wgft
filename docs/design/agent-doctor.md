# エージェント側の診断

### 10.2c エージェント側の診断 (`wgft agent doctor`)

`wgft agent doctor` は、エージェントを動かしているホストの上で、そのホストでしか分からない事実を調べるコマンドである。エージェントが止まっている間も、読める範囲だけを使って答える。10.2a 節の `server doctor` が server から見た転送の経路に答えるのに対し、`agent doctor` はエージェントのローカルの実行環境と現在の状態に答える (2026-09-23、所有者の決定)。エージェントが止まっていても成立する検査、稼働中のプロセスの制御ソケットから読む検査、`--json` の機械向けの出力は実装してある。

`server doctor` は既に、自分から見えない範囲として「エージェントのホストの環境」を名指ししている。エージェントの OS、権限、インタフェース、名前解決がその範囲に当たる (10.2a 節の「試していない範囲」)。`agent doctor` が埋めるのは、同じ範囲である。

#### この節が固定する範囲

この節が主に対象とするのは、7 節のユーザー空間の中継を持つエージェントである。`Relay` 群の検査と `tunnel.watchdog` の存在、および `tunnel.local` の判定規則は、その中継に紐づく。カーネルモードのエージェント (7b 節) の扱いは、後述の「カーネルモードのエージェント」の項が範囲を定める。

この節は骨格を固定し、細部は実装のときに確定する (2026-09-23、所有者の決定)。固定するのは、2 つのコマンドの境目、証拠の 2 つの出どころ、検査の一覧とその `id`、群の分け方、総合判定を動かす検査、終了コード 2 に倒す条件、状態の語とその意味、終了コードの意味、制御ソケットの拡張の形、そして実装が持つべき表のテストの要求である。機械が読むサーフェスについては、`checks[]` が `id`・`status`・`reason` の 3 つのフィールドを持つことと、その値が開いた集合であることまでを固定する。個々の理由の符号と `--json` の最上位の形は、`--json` を実装したときに確定し、後述の「機械向けの出力」の項に書いた (2026-09-23)。境界をここに引いたのは、規則どうしの組み合わせを網羅して確かめるのが実装とそのテストの役目であり、値の一覧まで固定すると実装が現実に合わせて 1 つ直すだけで設計の変更になるためである。v1.0 の後は機械が読むサーフェスの重みが増す (7a.11 節)。

実装は、この節が定めた規則をそのまま入力とする表のテストを持つ (2026-09-23、所有者の決定)。この節が定めた対応をそのままテストの入力に写せば、実装者が途中で意味を解釈し直す余地が減る。表の入力には、少なくとも次の場面を含める。

- エージェントが停止している
- 制御ソケットにファイルのパーミッションで繋げない
- 古い常駐プロセスが `error: unknown command` を返す
- 実行時の状態を守る排他を期限内に取れない
- トンネルのエンドポイントの初回の名前解決に失敗している
- 再解決に失敗しているが、解決済みのエンドポイントは保っている
- トンネルの構築が失敗している
- ハンドシェイクがまだ成立していない
- リスナーの開放に失敗している
- 総合判定を動かす検査の FAILED と、終了コード 2 に倒す条件が同時に成り立つ
- root で実行している
- カーネルモードのエージェントが停止しているが、wgft0、テーブル、`ip_forward` が揃っている
- カーネルモードのテーブルから、公開したルールの DNAT の行が消えている
- カーネルモードのホストで `ip_forward` が 0 である
- 停止しているカーネルモードのエージェントを、`CAP_NET_ADMIN` を持たない利用者で診断する
- ユーザー空間モードのエージェントで、カーネルモードの検査が NOT TESTED になる
- ユーザー空間モードのエージェントの WireGuard の UDP ソケットのバッファが、条件に届かない

場面ごとの結果は、この節が既に定める規則からテストが導く。固定するのは場面を入力として持つという要求であり、結果を新しく定めることではない。実装のときに確定したことと、そこで分かった事実は、改訂の記録に書く。この節の骨格を変える必要が出た場合は、設計文書を先に直す順序に従う。

#### 2 つのコマンドの境目

役割は次の 2 行で分ける。

- `server doctor`: server から見た転送の経路に答える
- `agent doctor`: エージェントのローカルの実行環境と現在の状態に答える

`agent doctor` は、server から既に見えている事実を自分で判定し直さない。同じ問いに対する 2 つ目の判定を持つと、片方の閾値や文言を変えたときにもう片方が置き去りになる。境目を「証拠がどちらのホストにあるか」で引いておけば、後から遠隔の診断 (10.2a 節) を加えるときにも、server が要求すべき情報の範囲がそのまま決まる。判定し直さない対象を名指しする。

- `tunnel.handshake` (10.2a 節): 最終ハンドシェイクが健全かどうかの判定と 3 分の閾値。`agent doctor` は観測した値を事実として示すだけとし、健全かどうかを言わない
- `server.dataplane`、`rule.public_port`、`rule.source_filter` (10.2a 節): server 側の適用と公開側の状態。エージェントの手元には証拠そのものが無い
- `agent.connection` (10.2a 節) と 10.2b 節の Agents 行: 制御ストリームが切れていることが、そのルールの転送や配置全体にとって何を意味するか。`agent doctor` は、つながっているかどうかとエージェント側が持つ理由を示すだけとする
- `rule.target` (10.2a 節) と `agent_rule_states` (7a.11 節): ルール 1 本が転送できているかどうかの総合判定
- 窃取検知の警告 (`GET /api/v1/warnings`) と 10.2b 節の Warnings 行

エージェントがハートビートのために既に計算している値を示す場合は、その結果をそのまま示し、`agent doctor` のための 2 つ目の計算を作らない。対象は、トンネルの状態 (`proto.TunnelStatus`) とルールごとの状態 (`proto.RuleStatus`) であり、どちらも `internal/agent` の `heartbeat` が組み立てている。実装は、トンネルの状態を実行時の排他の下で 1 回だけ読む共通の関数を切り出し、`heartbeat` と `agent doctor` の両方がその関数を使う (2026-09-23)。トンネルの送受信バイト数は `proto.TunnelStatus` に載らず `heartbeat` が捨てているので、doctor の側で読み直す形にすると、同じ応答の中に異なる時点の値が混ざる。

#### 2 つの証拠の出どころ

証拠は 2 か所から取る。

- 静的で永続する事実は、認証情報ファイル `agent.json` から読む。`Name`、`Endpoint`、`CertSHA256`、`UsedJoinTokenSHA256`、そして最後に処理した全体状態 `LastState` である (9 節)。稼働中のファイルは flock で守られているが、ロックは隣の `agent.json.lock` に掛かり、`agent.json` 自体の読み取りはロックを見ない。したがって、エージェントが動いていても止まっていても同じように読める
- 動的で今だけの事実は、稼働中のプロセスが持つ制御ソケットから読む。ソケットは認証情報ファイルの隣の `agent.json.sock` で、Unix では 0600、Windows では保護 DACL を持つ (`internal/agent/control`)。今の実装がプロセスの中に持っているのは、トンネルの送受信バイト数、ルールごとの現在の接続の数、フロー予算の拒否の累計、トンネルを作り直す watchdog の内部状態、そして制御ストリームの観測である。制御ストリームの観測が保つのは、今つながっているかどうか、直近の切断または失敗の理由、直近に待った再接続の間隔と次に試す時刻、直近の ping と pong の時刻である。どれもハートビートには載らないので、server 側には届かない (5.2 節、7a.10 節)。観測の保ち方は `internal/agent/streamobs.go` にあり、読み出しの入口が写しを返す (改訂の記録 2026-09-23)

稼働中かどうかは、`agent.json.lock` にロックファイルを作らずに判定する (2026-09-23、所有者の決定)。判定には `internal/flock` の `Inspect` を使う。`Inspect` は `os.O_CREATE` を渡さずに開き、ファイルが既にある場合だけ flock の状態を見る。この判定を検査の 1 つ目に置き、以降の分岐の根拠にする。ロックファイルを作る経路を使うと、エージェントを root で動かす配置で root が診断を実行しただけでロックファイルが root の所有で作られ、後から非特権で動くエージェントがそれを開けず起動できなくなる。`O_CREATE` を伴う判定は、既定が読み取りだけであるという宣言にも反する。読み取り専用の入口を用意する手間より、診断が状態を変えるかどうかのほうが重い。ただしこの保証が言う状態は、ロックファイルの有無に限る。

`agent.process` は、ロックファイルが無ければ、稼働している証拠が無い実行として FAILED とする。ロックファイルが無いのは、そのデータディレクトリでエージェントが一度も起動していない場合と、運用者がロックファイルを消した場合があり、診断はその 2 つを区別できない。どちらも稼働の証拠が無いという点では同じであり、「停止そのものは FAILED として扱う」という規則に従う。この判定が及ぶのはこのデータディレクトリに限り、別の `WGFT_DATA_DIR` で稼働中のエージェントがあっても見えない。ロックファイルがあるのに呼び出し元が権限で開けない場合は、稼働中か停止中かを判定できないので、次の前提が崩れている実行として扱い、終了コードの項に定める 2 の側に置く。

ロックの状態を見ている間に他のプロセスがロックを取れない期間、つまり競合しうる期間は、無くすのではなく最小にする (2026-09-23、所有者の決定)。共有ロックを一瞬だけ取って放つ形を許す。Linux、Windows、macOS のいずれでも、ロックを取らずに状態だけを問い合わせる手段が揃わないためである。調査の内容は改訂の記録にある。最も重い副作用は存在しないロックファイルを診断が作ることであり、それは `O_CREATE` を渡さないだけで消える。残る実害は、診断がロックの状態を見ている一瞬に起動したエージェントがロックを取れず、起動がそのまま終わることである。今の `deploy/agent.service` は `Restart=on-failure` を持つので、失うのは次の起動までの間だけである。同じ形の競合は `agent rotate-key` と `server teardown` に既にあり、この改訂が新しく作るものではない。どちらも最初に `Inspect` でロックを見る。

`agent doctor` は、エージェントと同じ実行主体で動かすことを前提とする (2026-09-23、所有者の決定)。エージェントが root で動く配置では、`agent doctor` も root で実行する。この前提の下では、呼び出し元がデータディレクトリと `agent.json` に対して持つ権限は、エージェント自身が持つ権限と同じものになる。`host.privileges` と `agent.credentials` が答えるのは、この前提が満たされたときのエージェント自身の権限であり、呼び出し元固有の事情ではない。前提が崩れる実行の扱いは、後述の「終了コード」の項と、次の root の実行の扱いで定める。

エージェントがシステムの利用者や systemd の `DynamicUser` で動く配置では、その利用者として `agent doctor` を実行するために、`sudo -u` や `systemd-run` を使うといった管理者の追加の操作が要る場合がある (2026-09-23、所有者の決定)。この実行を手軽にする方法は次のとおりとする (2026-09-24、所有者の決定)。root の実行で示す案内は、後述の `runuser -u wgft -- wgft agent doctor` のまま変えない。制御ソケットの `doctor` の応答に、稼働中のエージェントの実 uid と利用者名を加え、root で実行したときの所見に、稼働中のエージェントがどの uid とどの利用者で動いているかを添える。動いているエージェント自身に聞くので推測にならず、`DynamicUser` の配置でも正しい名前を示せる。unit の名前を推測して自動で実行し直す形は、11a 節の「環境を見て推測しない」に反するので持たない。`sudo` を持たない最小の構成も、前提に含めたままとする。応答に加える値は、後述の「カーネルモードの制御ソケットの応答」の項の `process` である。

root で実行した `agent doctor` では、`host.privileges` を UNKNOWN とし、理由の符号を `running_as_root` とする (2026-09-23、所有者の決定)。root はファイルのパーミッションを迂回するので、root が読めたことは、エージェントを動かす利用者が同じ証拠に届くかどうかについて何も述べない。OK を返すと、非 root で動くエージェントに対して前提が崩れていても、報告が健全に見える。FAILED にもせず、層 2 にも数えない。エージェントが root で動く配置では前提が満たされており、この UNKNOWN は想定どおりの結果だからである。終了コードは他の検査が決め、残りの検査は通常どおり行う。所見には root が権限を迂回するためにこの実行では答えられないことを述べ、次に見るものとして、エージェントと同じ利用者で実行し直すことを添える。同梱の systemd の unit ではその利用者が wgft なので、次の一手には `runuser -u wgft -- wgft agent doctor` を名指しする (2026-09-23、所有者の決定)。`deploy/agent.service` の `User=wgft` という配布物の事実を挙げるのであって、環境を見て推測するのではない (11a 節)。独自の配置では、実際にエージェントを動かしている利用者で実行し直す。root で動くなら想定どおりであることも添える。root でも拒まれた対象がある実行は、この扱いに含めず、層 2 の失敗とする。拒まれたという事実は root の迂回が及ばない範囲で得たものであり、答えられないのではなく届かなかったためである。カーネルモードのエージェントで `CAP_NET_ADMIN` を見る扱いは、後述の「カーネルモードのエージェント」の項で定める。

#### 証拠の鮮度の違い

エージェントが止まっていても、`agent doctor` の出力の意味は変わらない。変わるのは、取れる証拠の新鮮さだけである。止まっている間に読める値は `agent.json` が最後に保存した時点のものであり、今の値ではない。この違いは、10.2a 節の状態の語彙でそのまま表せる。新しい語を加えない。

- 稼働中のプロセスしか持たない項目は、エージェントが止まっている間は SKIPPED とし、理由の符号を `agent_not_running` とする。SKIPPED は「試せたはずだが、手前の失敗によって今回は試せなかった」であり、エージェントが動いてさえいれば取れた項目に当たる。NOT TESTED はこのコマンドがそもそも試さない項目に使う語なので、稼働中には取れる項目に当てると、同じ項目の状態が実行のたびに NOT TESTED と OK を行き来する。UNKNOWN は証拠があって判定に足りない場合の語なので、証拠が 1 つも無い状態には当たらない。例外は `relay.allow_targets` の停止中であり、この項目だけは UNKNOWN とする
- `agent.json` から読んだ値は、稼働中でも停止中でも、保存した時点の値である。人向けの出力では `agent ls` および 10.2a 節と同じ `last:` の接頭辞を付け、今の観測と区別する
- `agent.last_state` が示す、server がこのエージェントを無効にしているという所見も、この鮮度の制約を受ける(実装時に判明)。エージェントは、稼働中に全体状態を適用したときだけ `LastState` を書き換える(5.2 節)。無効化と有効化の配信は接続中のエージェントにしか届かない(前述の「エージェントの無効化と有効化」の項)ので、既に停止しているエージェントを server が無効にしても、または無効なまま停止しているエージェントを server が有効に戻しても、その agent.json は書き換わらない。前者では停止中の `agent doctor` は無効であることを示さず、後者では無効の所見を古いまま示し続ける。稼働中の `relay.listeners` は、稼働中のプロセスが最後に適用した値を見る。stream がつながっている間は、無効化と有効化がそのまま届く

停止そのものは FAILED として扱う。ユーザー空間の中継を持つエージェントは、常駐して転送を担うプロセスであり、止まっている間は 1 バイトも転送しないためである。無効なルールのような「宣言どおりの停止」は、エージェントには存在しない。カーネルモードのエージェントは停止中も転送を続けうるので、停止の状態は FAILED のまま、総合判定への効き方だけを変える (後述の「カーネルモードのエージェント」の項)。

#### 検査の一覧と証拠の出どころ

検査は次の表のとおりとする。「検査の ID」の列が `--json` の値である。「停止中」の列は、エージェントが止まっている実行でその検査が成立するかどうかを示す。「総合判定」の列は、その検査が総合判定と終了コード 1 を動かすかどうかを示す。

| 検査の ID | 見出し | 群 | 見るもの | 出どころ | 停止中 | 総合判定 |
|---|---|---|---|---|---|---|
| `host.platform` | platform | Host | OS、アーキテクチャ、wgft の版、メモリのソフト上限の予測 | OS と自分の版 | 成立する | 動かさない |
| `host.privileges` | privileges | Host | 実行している利用者、データディレクトリの読み取りと新規ファイルの作成、`agent.json` の読み取り、設定ファイルの読み取り | OS | 成立する | 動かさない |
| `host.interfaces` | interfaces | Host | このホストのネットワークインタフェースとアドレス | OS | 成立する | 動かさない |
| `host.resolve` | endpoint resolve | Host | `Endpoint` のホスト名の解決 | このホストの resolver | 成立する | 動かさない |
| `agent.credentials` | credentials | Credentials | `agent.json` の読み取り、そのパーミッション、登録の有無、`Endpoint`、`CertSHA256`、`UsedJoinTokenSHA256` | `agent.json` | 成立する | 動かす |
| `agent.process` | process | Credentials | 稼働中かどうか | `agent.json.lock` の flock | 成立する | 動かす。カーネルモードでは動かさない |
| `agent.last_state` | last state | Credentials | 最後に処理した全体状態の世代、wg 設定、ルールの本数、server がこのエージェントを無効にしているかどうか | `agent.json` の `LastState` | 成立する | 動かさない |
| `agent.control` | control socket | Connection | 稼働中のエージェントの制御ソケットに繋げるか | `agent.json.sock` | 成立しない | 動かさない |
| `stream.connection` | control connection | Connection | 制御ストリームが今つながっているか、つながっていない場合の直近の理由 | 制御ソケット | 成立しない | 直近の試みが鍵の変更の頻度の上限による拒否で終わった場合だけ動かす |
| `stream.backoff` | reconnect backoff | Connection | 直近に待った再接続の間隔と、待っている場合の次に試す時刻。WireGuard の最終ハンドシェイクが新しい間、間隔は 10 秒を超えない (5.2 節) | 制御ソケット | 成立しない | 動かさない |
| `stream.liveness` | liveness | Connection | 直近の ping と pong の時刻、pong を待っている最中かどうか | 制御ソケット | 成立しない | 動かさない |
| `tunnel.resolve` | wg endpoint resolve | Tunnel | WireGuard のピアの宛先 (`proto.WGConfig.Endpoint`) のホスト名の解決 | `agent.json` の `LastState` | 成立する | 動かさない |
| `tunnel.local` | tunnel | Tunnel | トンネルの有無、解決したエンドポイント、最終ハンドシェイク、エージェントが送るトンネルの状態 | 制御ソケット | 成立しない | 動かす |
| `tunnel.socket_buffers` | socket buffers | Tunnel | 今のトンネルを立てた直後に稼働中のエージェントが測った、WireGuard の UDP ソケットの実効の受信と送信のバッファと、ユーザー空間モードの条件(7 節) | 制御ソケット | 成立しない | 動かさない |
| `tunnel.udp_accounting` | UDP accounting | Tunnel | netstack の UDP の受信の会計が、不変条件の違反を検出してトンネルの UDP を止めていないか(7 節) | 制御ソケット | 成立しない | 動かす |

`agent.credentials` という `id` は、10.2a 節が既に使っている同名の `id` と衝突する。別のコマンドの別の模型に属するため規約には違反しないが、`checks[].id` だけを読む運用者やスクリプトにとっては、同じ文字列が 2 つの意味を持つ。

`tunnel.resolve` を `host.resolve` とは別の検査として立てる (2026-09-23、所有者の決定)。`host.resolve` が引くのはエージェント用 API の宛先であり、この検査が引くのは WireGuard のピアの宛先であって、用途も障害の意味も違う。`LastState` から停止中にも証拠が取れるので、エージェントのホストでしか分からない事実という範囲に収まる。

`agent.json` の場所は、`rotate-key` (9 節) と同じ経路、つまり `WGFT_DATA_DIR`、`--data-dir`、`agent.env` で決める。

どれも与えずに既定のデータディレクトリを見た実行は、エージェントが `--data-dir` か `WGFT_DATA_DIR` で別のディレクトリを使う配置では、エージェントの居ない場所について答える (2026-09-25、所有者の決定)。この実行が既定のディレクトリに登録済みの `agent.json` を見つけられなかった場合、`agent.credentials` と `agent.process` の所見は、ホストが未登録であるとも、エージェントが止まっているとも断定しない。見たディレクトリについて述べ、次の一手の先頭で、エージェントが別のデータディレクトリで動いているなら同じ `--data-dir` で打ち直すよう案内する。新しい招待の発行と起動の案内はその後に置く。新しい招待を先に案内すると、別のディレクトリで動いているエージェントと同じ名前の登録が拒まれ、その先で案内される `wgft agent revoke` は動いているエージェントを切るためである。`host.privileges` がデータディレクトリの権限の不足を示す場合も、既定のディレクトリを見た実行では同じ案内を、同じ利用者で打ち直す案内より先に置く。エージェントを動かす利用者で打っていても、既定のディレクトリはその利用者を拒みうるためである。終了の 1 行にも同じ句を添える。ディレクトリを明示した実行でも、見たディレクトリを名指して取り違えを先に疑う。登録済みの `agent.json` が見つかった実行は、そのディレクトリがエージェントのものなので疑わない。

理由の符号は状態と 1 対 1 ではない。`agent_not_running` は、`relay.allow_targets` の停止中では UNKNOWN に付き、他の稼働中専用の検査の停止中では SKIPPED に付く。

#### 示す値の定め方

いくつかの検査は、実装の足場を調べた結果を受けて、示す値そのものを定めた (2026-09-23)。

- `host.platform` のメモリのソフト上限: 今の設定から計算し直した予測を示す。`debug.SetMemoryLimit` は自分のプロセスに対する設定であり、稼働中のエージェントが最後に適用した値を外から読む手段が無い。`agent.json` 由来の値に付く `last:` とも性質が違うので、予測であることを所見の文で述べる。`GOMEMLIMIT` が設定されている配置では、`cmd/wgft/limits.go` の `applyMemoryLimit` が `debug.SetMemoryLimit` を呼ばずランタイムに任せるので、フロー数の上限から計算した値は当たらない。その場合は計算した値ではなく `GOMEMLIMIT` の設定を示す。設定ファイルを権限で読めない実行では、数を示さず、示せない理由を述べる (2026-09-23、所有者の決定)。予測が当たるのは、エージェントが読むのと同じ設定を同じ経路で読めた場合だけである。既定値から計算した数を示すと、上限を絞った配置で事実でない数を述べることになる。状態は UNKNOWN とする
- `tunnel.local` の最終ハンドシェイク: 今の device から読んだ値だけを示す。watchdog が別に持つ値はトンネルを閉じるときに消えず、立て直した直後は前のトンネルの値が残る。同じ応答に 2 つを混ぜない。今の device から読む値は、device が今持つ鍵で成立したハンドシェイクだけである。ユーザー空間モードは鍵を変えるたびに device を作り直す。カーネルモードの wgft0 は鍵を変えても残るが、鍵を変える収束が server のピアを置き直すので、前の鍵のハンドシェイクは読めない(7b.4 節の鍵の変更と最終ハンドシェイク)
- `tunnel.watchdog` の残り時間: 示さない。次の作り直しまでの残りは保持されておらず、示すには起点を求める規則を診断の側に写すことになる。写した規則が本体と食い違えば、診断が事実でないことを述べる。作り直しの間隔は、`internal/agent/watchdog.go` の `rebuildState.step` が判定に使う実効値を示す。実効値は保持している値と既定値の大きい方であり、既定値を下回らない。保持している値そのものは、ゼロでない最終ハンドシェイクを一度も観測しておらず作り直しも一度も起きていないトンネルでは 0 のままだが、その場合も watchdog は既定値で動く。実効値を示せば、示さない場合を設けずに済む
- `relay.listeners` の開けているかどうか: 実装は、開けているかどうかを表す項目をリスナーの状態に足す。今の状態は bind の失敗を宛先の失敗より優先して 1 つの誤りとして返すので、2 つを区別できない。bind の失敗はポートの衝突を、宛先の失敗は自宅の機器を指し、運用者の次の行動が違う。加算の変更であり、この型を共有する vpsd のユーザー空間モードにも効く
- `relay.sessions` の接続の数: フロー予算の上限の対象である公開側の接続の数を示す。今のセッション数は TCP では公開側と宛先側の両方を数えるため上限の対象と一致せず、上限の対象の数はどこにも公開されていない
- `relay.refusals` の累計: 今のトンネルを作ってからの累計とする。フロー予算はトンネルを立て直すたびに作り直され、拒否の累計はそのたびに 0 に戻る。立て直しは wg 設定の変更、watchdog による作り直し、構築に失敗した後の試し直し、`rotate-key` で起きる。doctor は、今のトンネルを作った時刻を累計と並べて示す。フロー予算をトンネルの外へ移して累計を連続させる案は採らない。中継の停止が未返却のフローを返さないので、共有すると立て直しで取り残されるフローが出うる

#### 判定できない場合と、手前の失敗で試せない場合

副作用なしには判定できない検査は、成功でも失敗でもない UNKNOWN とし、判定できない理由を添える (2026-09-23、所有者の決定)。Windows の `host.privileges` の「新しいファイルを作れるか」は、`unix.Access` に当たる呼び出しが無く、ACL を読んで判定を自前で組むほかに手段が無い。7a.11 節が Windows のエージェントを暫定としていた時点で、その判定は組まないことにした。Windows だけ黙って OK を返す形にもしない。Windows 11 の実機では、この項目が理由 `permission_not_determined` の UNKNOWN になり、終了コードを上げないことを確かめた(改訂の記録 2026-09-27)。`LastState` が無い場合の `tunnel.resolve` も同じ扱いとし、`agent.json` が全体状態を持たない事実を理由の符号 `no_last_state` で示す。停止中の `rotate-key` も全体状態を消すので、一度も受け取っていないとは限らない。

`agent.json` が無い場合、権限で読めない場合、読めるが壊れている場合、データディレクトリを権限で辿れず有無を判定できない場合のいずれでも、その中身に依存する検査は SKIPPED とする (2026-09-23、所有者の決定。最後の場合は 2026-09-25 の追加)。対象は、`Endpoint` を読む `host.resolve`、`agent.json` 全体を読む `agent.last_state`、`LastState` を読む `tunnel.resolve` である。試せたはずだが `agent.credentials` の失敗という手前の失敗によって今回は試せなかった項目であり、SKIPPED の定義に沿う。`agent.credentials` 自体の状態と終了コードは原因によって違うが (後述の「終了コード」の項)、手前の失敗によって試せなかったという点は変わらない。`agent.process` がロックファイルを権限で開けず稼働中かどうかを判定できない場合も、同じ考え方に揃える。稼働中でなければ成立しない検査は SKIPPED とし、`relay.allow_targets` は停止中の扱いと同じく UNKNOWN とする。理由の符号は、`agent.process` と同じ `lock_unreadable` とする。

エージェントが止まっている実行の `agent.control` も、同じく SKIPPED とし、理由の符号を `agent_not_running` とする (2026-09-23、所有者の決定)。`checks[]` から項目ごと落とす案は採らない。実行の状態によって `--json` の項目そのものが消えると、機械が処理しにくくなるためである。

#### 宛先の許可一覧の扱い

`relay.allow_targets` は、停止中は値を示さず、状態を UNKNOWN、理由の符号を `agent_not_running` とする (2026-09-23、所有者の決定)。`agent.env` と CLI 自身の環境変数から `WGFT_AGENT_ALLOW_TARGETS` を組み立て、次の起動で効く値として示す案は採らない。組み立てた値を次に起動するエージェントが実際に読むとは保証できず、診断は分からない値を推測で埋めないためである。稼働中は、常駐プロセスが実際に持っている一覧を制御ソケットから読む。稼働中でありながら制御ソケットに繋げない実行では SKIPPED とし、理由の符号を `control_socket_unreachable` とする。

稼働を判定できない実行の `relay.allow_targets` も UNKNOWN とするが、所見と次の一手は停止中のものと分ける (2026-09-23、所有者の決定、実機での確認を受けた追加)。同じ報告の `agent.process` が判定できなかったと述べている横で、この検査だけがエージェントは動いていないと述べると、稼働中のエージェントについて事実でないことを述べることになる。

この停止中の UNKNOWN は、「証拠の鮮度の違い」の項が定めた一般則の例外にあたる (2026-09-23、所有者の決定)。稼働中のプロセスしか持たない他の項目は、止まっていれば証拠が 1 つも無く SKIPPED が当たる。宛先の許可一覧は設定の値であり、稼働中かどうかに関わらず設定の出どころから原理的には読める。証拠になりうるものはあるが判定には使えないという点で、UNKNOWN の定義に当てはまる。

この一覧を検査に入れるのは、内容がエージェントの手元にしか無いためである。一覧に当たった拒否は `agent_rule_states` の理由として server まで届くが (7a.11 節)、一覧そのものは届かない。一覧の中身を示すことと、一覧に当たったルールを転送不能と判定し直すことは別の行いであり、`agent doctor` が行うのは前者だけである。

#### 能動的に試す範囲

既定は読み取りだけである。例外は `host.resolve` と `tunnel.resolve` で、どちらもホスト名を実際に解決する。名前の解決は宛先のサービスへ接続を作らないため、既定に入れてよい。`host.resolve` はエージェント用 API の宛先 (`Endpoint`) を、`tunnel.resolve` は WireGuard のピアの宛先 (`proto.WGConfig.Endpoint`) を解決し、対象が別である。

`agent.json` を読むときは、`credentials.Load` を使わない (2026-09-23)。`Load` は読み取りに続けて Windows の DACL を毎回書き直す。これは緩い権限のファイルを起動時に締め直すための意図した挙動であり (11a 節)、`credentials` の側は変えない。診断が副作用を持たないという本項の約束を保つため、doctor は締め直しを伴わない読み取りの経路を使う。

`tunnel.resolve` は、10.2a 節が「切り分けられない所見」として残した、最終ハンドシェイクが無い原因のうち、名前解決そのものの失敗を切り分ける。10.2a 節が挙げる原因のうち、VPS の WireGuard の UDP ポートが届かないこと、自宅のファイアウォールまたは ISP がトンネルの UDP を落としていること、その間の何かが落としていることは、名前解決が成功した後の経路を扱っている。残る 1 つ、エージェントが動いていないか別の鍵を持っていることは、経路ではなくエージェント自身の状態を指す。

LAN の宛先への試し接続は行わない。エージェントの中継が、リスナーを開いたときの試し接続 (7 節の `checkTarget`) と、5.2 節が定める 30 秒ごとの再試行 (`internal/dataplane/userspace/relay` の `Manager.Retry`) で既に試しており、`agent doctor` はその結果を `relay.listeners` から読むだけで足りるためである。`checkTarget` は TCP の `target` への試し接続であり、UDP は到達確認ができないため呼ばれない (7 節)。したがって UDP のルールについては、`relay.listeners` に宛先の到達性の証拠が無い。エージェントが止まっている実行では、宛先への接続を確かめる手段を持たない。停止中にも宛先を試す形を加えるかどうかは、手元で読める値で足りるかが分かってから決める。

#### 総合判定を動かす検査

`agent doctor` は、転送の経路を順にたどる形を持たない。したがって、10.2a 節の「経路の上の検査と経路の外の検査」の区別と、「最初に FAILED になった検査が転送の止まった位置である」という規則を持ち込まない。代わりに、総合判定と終了コードを動かす検査を名指しで定める。前掲の表の「総合判定」の列がその区別である。

動かすのは `agent.credentials`、`agent.process`、`tunnel.local`、`tunnel.udp_accounting`、`relay.listeners` である (2026-09-23、所有者の決定。`tunnel.udp_accounting` は 2026-09-27 に加えた)。どれも、失敗がそのまま「このホストのエージェントは今の状態では転送を担えない」を意味する。カーネルモードのエージェントでは、動かす検査の組が変わる。`agent.process` は動かさず、`dataplane.interface`、`dataplane.table`、`host.forwarding` が動かす。`relay.listeners` は NOT TESTED になる (後述の「カーネルモードのエージェント」の項)。どちらのモードでも、`stream.connection` は、直近の試みが鍵の変更の頻度の上限による拒否で終わった場合だけ動かす (2026-10-03、所有者の決定。後述の「個別の理由で動かさない検査」の項)。

動かさない検査のうち、`host.platform`・`host.interfaces`・`agent.last_state`・`stream.backoff`・`stream.liveness`・`tunnel.watchdog`・`relay.sessions`・`relay.refusals` は、累計か現在値を述べるだけで、エージェントが転送を担えるかどうかを述べないためである。10.2a 節が経路の外に置いた検査と同じ理由による。所見としては必ず出し、次に何をするかも添える。`relay.allow_targets` の理由は前述の「宛先の許可一覧の扱い」の項で述べた。残る検査には個別の理由があり、以下の項で述べる。

#### `relay.listeners` の粒度

`relay.listeners` は、判定も所見もルール単位とする (2026-09-23、所有者の決定)。FAILED になるのは、`heartbeat` が組み立てるルール単位の `proto.RuleStatus` が `error` の場合だけとする。1 つのルールに属するどれかのリスナーが `error` なら、そのルールの `RuleStatus` が `error` になる (7 節)。新しい閾値を持たないという方針のとおり、リスナー単位の値から独自の判定を組み立て直すことはしない。

所見にもリスナー 1 つずつを並べない (2026-09-23)。ポート範囲の幅に上限が無く、`listen_port=1-65535` のルール 1 本で 65535 個のリスナーができる。制御ソケットの応答にも大きさの上限が無いので、そのまま並べると 1 行が数 MB になる。

server がこのエージェントを無効にしている場合(5.1 節)、`relay.listeners` は SKIPPED とし、理由の符号を `agent_disabled` とする(2026-09-24、所有者の決定)。無効を示すための新しい検査は作らない。無効は宣言どおりの状態であり、SKIPPED は終了コードを動かさない。所見には、VPS で `wgft agent enable` を実行するまでリスナーを開かないことを添える。エージェントは、全体状態に加算された無効を示すフィールドから、無効であることを知る。理由の符号の表への `agent_disabled` の追加は、実装と同時に行う。表と実装の符号の一致をテストが確かめるためである。

#### `tunnel.local` の判定

`tunnel.local` は、エージェントがハートビートのために計算している状態が `error` の場合に、理由によって FAILED と UNKNOWN を分ける (2026-09-23、所有者の決定)。基準は、トンネルが無い場合と、トンネルがある場合で違う。

トンネルが無い場合は、理由ごとに定める。`no tunnel` と `no tunnel; full state not received` は UNKNOWN とする。前者は `rotate-key` や停止でトンネルを閉じた直後など正常な遷移でも生じる理由であり、後者はトンネルが無く stream にまだ繋がっていない通常の起動直後の状態である。FAILED にすると、この一過性の状態を故障として扱うことになる。`no tunnel; building it failed and will be retried` と `no tunnel; building it failed` は FAILED とする。どちらもトンネルの構築が実際に失敗した事実を指し、前者は試し直しを待っている状態、後者は wg 設定の誤りで構築が終わり次の全体状態を待っている状態である。UNKNOWN に弱めると、本当に壊れている場合まで見分けが付かなくなる。

トンネルがある場合は、`ts.Err` があることを先に見て、`LastHandshake` が無いことを後に見る。`heartbeat` の分岐がこの順であり、両方が成り立つ実行の理由は `ts.Err` の側になるためである。初回の名前解決に失敗したトンネルは、解決済みのエンドポイントを持たないまま `LastHandshake` も無いので、この順序がそのまま効く。順序を逆にすると、転送に使えるエンドポイントを一度も持たないトンネルが `handshake_pending` の UNKNOWN になり、前段の決定と食い違う。

`ts.Err` がある場合は、その時点で転送に使える解決済みのエンドポイントが残っているかどうかだけで分ける (2026-09-23)。残っていなければ FAILED、残っていれば UNKNOWN とする。誤りの種類でも、どの呼び出しが失敗したかでも分けない。`ts.Err` は印の無い `error` であり、`proto.TunnelStatus` の理由はその文字列なので、`internal/agent` の側に種類を判別する材料が無い。材料を作るには、トンネルの側に誤りの種類を足すか、`internal/agent` が wireguard-go を import することになり、診断のためにどちらも行わない。運用者に示す理由は `ts.Err` の文字列をそのまま用いる。判定に要る解決済みのエンドポイントの有無は、`internal/dataplane/userspace/tunnel` の `Status` が持つ `Endpoint` から今の実装でも分かる。FAILED と UNKNOWN のどちらについても、理由の符号は「機械向けの出力」の項の表のとおりである。第 1 段の判別を落とした結果、UNKNOWN の枝には名前解決の失敗以外の誤りも入るので、`resolve_failed` をそのまま当てない。

`LastHandshake` が無い場合は UNKNOWN とし、理由の符号を `handshake_pending` とする。トンネルを作り直した直後に必ず通る状態であり (7 節)、ハートビートの `error` にそのまま追随させると、`agent doctor` の側に事実上 0 秒のハンドシェイクの制限時間という別の判定が生まれ、10.2a 節が定める 3 分の閾値と二重管理になる。新しい閾値は持たない。

#### 個別の理由で動かさない検査

`host.resolve` と `tunnel.resolve` を動かさない側に置く (2026-09-23、所有者の決定)。名前解決に失敗しても、既に解決済みの IP で接続とトンネルが生きていて転送できる場合がある。名前解決の失敗は、今後の再接続が危ういという証拠ではあっても、今この瞬間に転送を担えないという証拠ではない。解決に失敗した場合、状態は FAILED ではなく UNKNOWN とし、理由の符号を `resolve_failed` とする。

`agent.control` も動かさない側に置く (2026-09-23、所有者の決定)。制御ソケットに繋げないことは、終了コード 1 が答える問い、つまり「このホストのエージェントが、今の状態では転送を担えない」に対して偽である。ソケットのパスが `sun_path` の上限を超えていても、エージェントは転送を担い続ける (11a 節)。動かす側に置くと、転送が健全な配置に対して「担えない」と答えることになり、問いと答えがずれる。ファイルのパーミッションで繋げない場合の終了コード 2 は、後述の項で別に定める。

`host.privileges` も動かさない側に置く (2026-09-23、所有者の決定)。エージェント自身の権限の不足と、`agent doctor` を実行した利用者が証拠に届かないことを、この検査だけでは区別できない。後者を終了コード 1 にしてはいけない以上、診断が成立するかどうかの問題として終了コード 2 の側に寄せるほうが素直である。稼働中の制御ソケットからエージェントのプロセス自身の権限を取り、判定の材料にする案は採らなかった。前提を課したうえで呼び出し元の権限をそのまま使う案の方が単純であり、この案はエージェントが止まっている実行では使えず、制御ソケットの応答に権限の情報を足すことにもなる。カーネルモードの `CAP_NET_ADMIN` だけは、後述の「カーネルモードのエージェント」の項がこの案を例外として採る。

`host.privileges` が見る権限を、実装が実際に要求する権限に合わせて絞る (2026-09-23、所有者の決定)。検査の対象は、データディレクトリを読めること、データディレクトリに新しいファイルを作れること、`agent.json` を読めること、設定ファイルがある場合にそれを読めることとする。`agent.json` 自体への書き込みの権限は見ない。`internal/agent/credentials` の `Save` は、一時ファイルを書いてから `rename` で置き換える方式であり (9 節)、`rename` が求めるのは、そのファイルを含むディレクトリへの書き込みの権限だからである。検査の対象が実装の要求より厳しければ、`agent.json` を 0400 に締めた配置のような正当な構成で終了コード 2 を毎回返すことになる。

設定ファイルを読めることを対象に加えるのは、エージェントが起動のたびに同じファイルを読み、読めなければ起動を拒むためである (2026-09-23、所有者の決定、実機での確認を受けた追加)。検査の対象が実装の要求より緩ければ、エージェントが起動できない配置に対して `host.privileges` が OK を返す。ファイルが無い配置は正しいので、無いことは失敗にしない。読めなかった実行だけを、他の対象と同じ層 2 の失敗として扱う。

`agent doctor` は、設定ファイルを権限で読めない実行でも報告を出す (2026-09-23、所有者の決定、実機での確認を受けた追加)。設定ファイルを読めないことは診断の結果であり、報告を拒む理由ではない。この場合、設定はフラグと環境変数と既定から解決し、ファイルの値を使えなかったことを `host.privileges` の所見に書く。`agent run` は同じ場合に起動を拒む形を保つ。宣言された設定を読めないまま転送を始める常駐プロセスは、運用者が意図した設定で動いていないためである。設定の値そのものの誤り、つまり構文の誤りと範囲外の値は、この扱いに含めない。値の誤りは呼び出し元の権限の問題ではなく、他のコマンドと同じ設定の拒否として終了コード 3 で止まる。

`host.privileges` は権限だけを見る検査であり、`agent.json` やデータディレクトリそのものが無いことを失敗にしない。この検査が失敗しうるのは、権限が足りない場合に限る。データディレクトリが無い実行では、それを作れる親ディレクトリの権限を見る。`agent.json` が無い実行では、他の 2 つの対象が満たされている限り OK とする。不在という事実そのものは `agent.credentials` が答える。前段でこの検査を終了コード 2 の側に寄せた判断と、後述の「終了コード」の項が `agent.json` の不在を終了コード 1 に置く判断は、この検査の失敗がすべて権限に起因するという前提の上に立つ。

`stream.connection` も動かさない側に置く (2026-09-23、所有者の決定)。制御ストリームが切れていることは、エージェントが受け取り済みのルールを転送し続けている間も起こる (5.2 節、7 節)。この状態を配置全体の劣化として数えるかどうかは 10.2b 節が定めており、同じ判定を重ねて持つと、切れている間の終了コードが 2 か所で決まることになる。`agent doctor` が加えるのは、エージェント側だけが持つ事実、つまり直近の切断の理由、直近に待った再接続の間隔、次に試す時刻である。状態は、つながっていれば OK、切れていれば UNKNOWN とし、理由の符号を `reconnecting` とする。示す理由には、接続が切れた理由だけでなく、接続に至らなかった試みの失敗も入る (2026-09-23)。どちらも「今つながっていない理由」を答えるものであり、2 つに分けると `agent doctor` の側で合成することになる。一方、登録の失敗はこの値に入らない。登録を呼ぶ経路は観測に書かないので、再登録に失敗しても、観測に残るのは直前の接続の失敗の理由のままである。再登録に失敗した後に常駐プロセスが止まるかどうかは経路によって違い、止まらずに再接続を続ける経路もある。

例外は、直近の試みが server の証明書と登録のときに固定したハッシュとの不一致で終わった場合である (2026-09-25、所有者の決定)。状態を FAILED とし、理由の符号を `server_cert_mismatch` とする。この場合の切断は、エージェントが待って試し直しても直らない。server が `server teardown --purge` などで作り直されたか、経路の途中で TLS を終端するものがあるためである。UNKNOWN のまま「再試行するので問題ではない」と案内すると、直らない状態を待たせることになる。次の一手は、エージェントのログと同じく、新しい招待で登録し直すことと、作り直していないなら経路を確かめることである。総合判定と終了コードは動かさない。終了コード 1 が答える問いは「このホストのエージェントが、今の状態では転送を担えない」であり、制御ストリームが切れている間も、受け取り済みのルールの転送はトンネルが保つ限り続くためである。TLS を終端するものが経路にある場合は、WireGuard の UDP は別の経路で届きうる。server を作り直した場合はトンネルも成立しなくなり、転送を担えないことは `tunnel.local` と `relay.listeners`、カーネルモードでは `Dataplane` の群の検査が答える。状態の語と終了コードは別のものとして扱う (「終了コード」の項)。このため `--json` では、最上位の `status` が `ok` のまま、`checks[]` にこの FAILED が並ぶ。`host.privileges` の `agent_lacks_cap_net_admin` と同じ形である。不一致の判定には、制御ソケットの `doctor` の応答の制御ストリームの観測に加えた `pin_mismatch` を使う。この値を送らない旧い版のエージェントには、記録された理由の文言で判定する。

直近の試みが鍵の変更の頻度の上限(5.2 節)による拒否で終わった場合も、理由の符号を分け、`key_change_limited` とする (2026-10-02、所有者の決定)。状態は FAILED とし、総合判定を動かす (2026-10-03、所有者の決定)。`stream.connection` が総合判定を動かすのは、この場合だけである。2026-10-02 の決定は、状態を UNKNOWN とし、総合判定を動かさなかった。この拒否は 1 回分が戻った後の再接続で解けるので、再試行で直らない `server_cert_mismatch` と分けたためである。この扱いでは、エージェントが転送できない間も、`agent doctor` は最上位の `status` を `ok`、終了コードを 0 として返した。終了コード 1 が答える問いは「このホストのエージェントが、今の状態では転送を担えない」であり、この場合はそれに当たる。エージェントが宣言するのは自分が今使っている鍵であり、断られた鍵は server の WireGuard のピアに入っていないので、エージェントは後の試みで鍵が通るまで転送できない。`server_cert_mismatch` について総合判定を動かさない理由に挙げた、受け取り済みのルールの転送がトンネルの保つ限り続くことは、この場合には当たらない。後の再接続で解けることは、総合判定を動かさない理由にならない。終了コード 1 は今の状態を答え、直るまでの見込みを答えないためである。

この場合の所見と案内は次のとおりである。所見は、直近の試みの終わった時刻と理由を示すだけで、今も断られ続けているとは述べない。`reconnecting` の案内は、受け取り済みのルールは stream が切れている間も転送を続けると述べるが、この場合はそれが当たらないので出さない。案内は、エージェントが同じ鍵で再接続を続けて 1 回分が戻った後の試みで鍵が通ること、`rotate-key` を繰り返さないこと、`agent rotate-key --help` の戻し方を示す。

判定には、直近の試みの結果だけを使う。制御ソケットの `doctor` の応答の制御ストリームの観測に加えた `key_change_limited` を使い、エージェントは、close の符号が 1008 で、理由の文言が `vpsd` の上限による拒否の文言と一致するときにこの値を立てる。この値を送らない旧い版のエージェントには、記録された理由の文言で判定する。文言は `vpsd` が送るものなので、エージェントの版に依らない。後の試みで鍵が通れば、`stream.connection` は OK に戻り、総合判定を動かさない。観測は公開鍵を送り終えた時点から接続をつながっているものとして扱うので、鍵を送ってから server が拒否で閉じるまでの間も OK を示す。後の試みが上限以外の理由で終わった場合は、`reconnecting` の UNKNOWN に戻り、総合判定を動かさない。観測が持つのは直近の試みの結果だけであり、その試みが鍵の判定まで届いたとは限らないためである。この場合、鍵がまだ通っていなくても `agent doctor` はそのことを示さない。拒否の後に鍵が通ったかどうかを保つ値は、エージェントにも制御ソケットの応答にも無い。鍵の変更の上限を持たない旧い版の `vpsd` はこの拒否を送らないので、そこにつながるエージェントの判定は変わらない。

`server doctor` の `agent.connection` (10.2a 節) は変えない。server は、断った宣言が正規のエージェントのものかどうかを見分けられないので、最終ハンドシェイクが新しい間は UNKNOWN とする。エージェントは自分の試みが断られたことを知っているので、`agent doctor` だけが、この拒否で総合判定を動かす。

server の側では、証明書を拒んだエージェントの接続は、net/http が書く TLS のハンドシェイクの誤りの行 (`remote error: tls: bad certificate`) としてしか残らない。この行に、証明書を固定したエージェントの拒否として読むことと、新しい招待が要ることを添える (2026-09-25)。どのエージェントかは示さない。相手は名乗る前にハンドシェイクを終え、作り直した server のデータベースにはそのエージェントの記録も無いためである。送信元のアドレスは元の行が既に持つ。

`tunnel.socket_buffers` も動かさない側に置く (2026-09-27、所有者の決定)。この検査は、ユーザー空間モードの動作条件である WireGuard の UDP ソケットのバッファ(7 節)を、稼働中のエージェントが今のトンネルを立てた直後に測った値と比べる。条件に届かなければ FAILED とし、理由の符号を `socket_buffer_below_requirement` とする。所見には測った値と条件の値を、次に見るものには 2 つの sysctl に書く値、コンテナではコンテナのホストで設定すること、エージェントを再起動することを示す。sysctl に書く値は条件の値の半分なので、Linux が要求の 2 倍を報告することも添える。7 MiB を設定した運用者が、14 MiB の条件を読み違えないためである。終了コード 1 は「このホストのエージェントが、今の状態では転送を担えない」と答える。条件に届かないエージェントも、負荷の軽い間は転送を担う。この検査を総合判定に加えると、終了コード 1 の意味が「支える条件の外にある」に変わり、更新しただけの既存のホストが終了コード 1 を返し始める。状態の語と終了コードは別のものとして扱う(「終了コード」の項)。このため `--json` では、最上位の `status` が `ok` のまま、`checks[]` にこの FAILED が並ぶ。`host.privileges` の `agent_lacks_cap_net_admin` と同じ形である。

`tunnel.socket_buffers` の他の状態は次のとおりである。条件を満たせば OK である。エージェントが止まっていれば、稼働中専用の他の検査と同じく SKIPPED で `agent_not_running` を持つ。トンネルが無ければ SKIPPED で `no_tunnel` を持つ。カーネルモードのエージェントはプロセスの中に WireGuard のソケットを持たないので、NOT TESTED で `kernel_mode` を持つ。Windows と macOS では測らないので、NOT TESTED で `not_measured_on_this_os` を持つ。稼働中のエージェントが測れなかった場合は UNKNOWN で `socket_buffers_unreadable` を、値を答えない旧い版のエージェントでは UNKNOWN で `socket_buffers_not_reported` を持つ。止まっているエージェントについて、試しのソケットで得る値を予測として示す形は採らない。試しのソケットの値は呼び出し元の権限で変わり、root で試すと、権限を持たないエージェントについても条件を満たして見えるためである。

`tunnel.udp_accounting` は動かす側に置く (2026-09-27、所有者の決定)。この扱いは、終了コード 1 の意味、つまり転送が止まっていることの機械的な検出を広げるものではない。既存の意味に、新しく検出できるようになった故障の状態を加えるものである。TCP のルールが転送を続けていても、UDP の dataplane が止まっている以上は正常と判定しない。`tunnel.socket_buffers` との違いは次のとおりである。ソケットのバッファの不足は、配置が動作条件を満たしていない状態であり、転送が止まっているとは限らないので終了コード 0 のままである。会計の停止は、UDP の転送が実際に止まった状態である。この検査は、netstack の UDP の受信の会計(7 節)が不変条件の違反を検出して、トンネルの UDP を止めていないかを見る。止めていれば FAILED とし、理由の符号を `udp_accounting_stopped` とする。止まった会計は、プロセスを再起動するまでこのエージェントの UDP のルールをすべて転送しない。UDP のルールを 1 本でも持つエージェントにとって、これは「今の状態では転送を担えない」に当たる。`relay.listeners` が 1 本のルールの `error` で FAILED になるのと同じ粒度である。予算による拒否は、この検査の状態を動かさない。拒否は資源の逼迫のときの通常の動作であり、ログの行で知らせる (7 節)。所見には検出した違反の内容と、TCP のルールは転送を続けることを、次に見るものにはエージェントの再起動と、ログを添えた不具合の報告を示す。止めていなければ OK である。エージェントが止まっていれば SKIPPED で `agent_not_running` を、トンネルが無ければ SKIPPED で `no_tunnel` を持つ。カーネルモードのエージェントはプロセスの中に netstack を持たないので、NOT TESTED で `kernel_mode` を持つ。会計の状態を答えない旧い版のエージェントでは、UNKNOWN で `udp_accounting_not_reported` を持つ。

`tunnel.transfer` は、server から見えないが転送の実際の通り具合を示す値の代表である。値は所見として必ず出す。状態は UNKNOWN とし、理由の符号を `no_threshold` とする。送受信バイト数の多い少ないは、それだけでは健全さを意味しない。利用者が誰も接続していないトンネルは、何時間も 0 バイトのまま正常である。値が判定に使えるのは、運用者が「今この瞬間に通っているはずだ」という外の知識を持っている場合だけであり、その知識はコマンドの側に無い。値は 1 回の実行で 1 回だけ読む。2 回読んで差を取れば今の通り具合を言えるが、待ち時間を伴うので、必要になった時点で明示のフラグの下に置く。

#### 出力の形

操作体系を `server doctor` (10.2a 節) に揃える。揃えるのは操作体系であって、検査の中身ではない。状態の語彙、`--json`、終了コードの考え方が揃っていれば、運用者は読み方もスクリプトも共通にできる。見る場所が違うことは、検査の一覧が違うことで表す。この項が定めるのは次のとおりである。`--json` と終了コードは、後続の 2 つの項で定める。

- 群分け: 検査を `Host`、`Credentials`、`Connection`、`Tunnel`、`Relay`、`Dataplane` の群に分けて示す。`Dataplane` はカーネルモードの検査の群である。10.2a 節が `Server`、`Tunnel`、`Agent` に分けるのと同じ形である
- 値だけを示す検査の節: 値だけを示し合否を持たない 6 つの検査 (`stream.backoff`、`stream.liveness`、`tunnel.watchdog`、`tunnel.transfer`、`relay.sessions`、`relay.refusals`) は群から抜き、群の後に「Observed values」という 1 つの節としてまとめて出す (2026-09-24、所有者の決定、改訂の記録に詳細)。値を読めた実行 (状態が UNKNOWN) は状態語も次に見るもの (Next) も出さず、ラベルと同じ行から値を示す。値の読み方は `--help` と、`--json` の `next` が持つ。値そのものを読めなかった実行は、SKIPPED のまま判定済みの検査と同じく状態語と次に見るものを出す。値に文脈を添えないと読み違えられる場合は、決まった `Check:` の行ではなく、その値に短い注記を付ける。人向けの出力だけの見せ方であり、内部の模型と `--json` の `checks[]` は変えない (7a.11 節)
- 状態の語彙: 10.2a 節の表の OK、FAILED、UNKNOWN、NOT TESTED、SKIPPED をそのまま使う。意味も同じとし、新しい語を加えない
- 次に見るもの: FAILED の所見には必ず次に見るものを添える。次の行動を伴わない所見は、10.2a 節と同じく機能の失敗として扱う
- 試していない範囲: 10.2a 節と同じく、何も壊れていない実行でも試していない範囲を必ず出力する (2026-09-23、所有者の決定)。項目の一覧は、実装のときに定める
- 履歴: 10.2a 節と同じく、診断のために保存の仕組みを追加せず、履歴を持たない。10.2a 節が持つ `History` のまとまりは同じ形で出力する。一方 `Result:` の行は持たない。転送の経路を順にたどる形を持たないため、「転送はここで止まった」という位置を言えないためである

#### 機械向けの出力

`--json` は、人向けの表の写しではなく、診断そのものの模型を出す。最上位はオブジェクトとし、`server doctor --json` とも `status --json` とも別の、このコマンド専用の模型とする (2026-09-23、所有者の決定)。同じ事実を表すフィールドには `server doctor --json` (10.2a 節) と同じ名前と同じ値の語彙を使う (2026-09-23)。運用者がスクリプトを共通にできるようにするためである。形は次のとおりである。例は、権限で証拠に届かない検査と総合判定を動かす検査の FAILED が同じ実行で成り立ち、終了コード 2 になる実行である。

```json
{"status":"unknown","checked_at":"...","data_dir":"/var/lib/wgft",
 "checks":[{"id":"host.privileges","status":"failed","reason":"permission_denied","evidence_unreachable":true,
            "group":"Host","label":"privileges","detail":"...","next":"..."},
           {"id":"agent.process","status":"failed","reason":"agent_not_running",...}],
 "history":{"available":false,"detail":"..."},"not_tested":[{"id":"...","detail":"..."}]}
```

各フィールドは次のとおりとする (2026-09-23)。

- `status`: 総合判定である。値は `ok`、`failed`、`unknown` で、報告を出した実行の終了コードの 0、1、2 に当たる。`failed` は総合判定を動かす検査に FAILED が 1 つ以上ある実行であり、`unknown` は終了コード 2 に倒す条件が成り立った実行である。両方が成り立つ実行は、終了コードと同じく `unknown` になる。`server doctor --json` の `status` と同じ名前にし、診断が成立しなかった実行には 10.2a 節の UNKNOWN の語を当てる。証拠が判定に足りない状態という定義にそのまま当たるので、新しい語を作らない
- `checked_at`: 診断した時刻で、RFC 3339 の UTC である
- `data_dir`: この報告が答えるデータディレクトリであり、実際に調べたディレクトリの絶対パスを正規化した形で示す。同じパスを相対パスや `..` を含む形で指定しても、値は同じになる。設定ファイルを読めずに既定値を使った実行でも、実際に見たディレクトリを示す
- `checks[]`: 前掲の表の検査すべてを表の順に持つ。実行の状態によって項目は消えない。各項目は `id`、`status`、`reason`、`evidence_unreachable`、`group`、`label`、`detail`、`next` を持つ。`reason` は OK の検査では省く。`evidence_unreachable` は終了コード 2 に倒す条件に当たった検査だけが `true` として持ち、他の検査では省く。`next` は次に見るものを持たない検査では省く
- `history`: 10.2a 節と同じ形で、`available` と `detail` を持つ。`available` はこの版では常に `false` である
- `not_tested[]`: 試していない範囲であり、各項目は `id` と `detail` を持つ。何も壊れていない実行でも必ず持つ

`server doctor --json` の `probed` と `rules`、および検査ごとの `rule_id`、`agent`、`observed_at`、`causes`、`internal` は持たない。このコマンドはルールごとの経路をたどらず、観測の古さで状態を変えることもしないためである。後から加えることは 7a.11 節の加算の規則に従う。

機械向けの保証は、最上位の `status`・`checked_at`・`data_dir`、`checks[]` の `id`・`status`・`reason`・`evidence_unreachable`、`history.available` である。`checks[].id` の値は前掲の表のとおりであり、`checks[].status` の値は 10.2a 節の 5 つであり、`checks[].reason` の値は次の表のとおりである。最上位の `status` と、この 3 つの値は、7a.11 節の規則に従う開いた集合として扱う。値を増やすことだけができ、既存の値の名前の変更も意味の変更も互換ではない。読み手は知らない `id` を読み飛ばし、知らない `status` と `reason` を「不明」として扱わなければならない。`group`・`label`・`detail`・`next`、`history.detail`、`not_tested[]` の `id` と `detail` は人向けの文であり、保証の対象ではない。

理由の符号は、1 つの符号が 1 つの事実だけを表す (2026-09-23)。同じ符号が複数の検査に付くことはあるが、どの検査に付いても同じ事実を指す。状態とは 1 対 1 ではない。`agent.credentials`、`agent.process`、`agent.control` が OK でないために SKIPPED になった検査は、その検査の符号をそのまま持つ。`agent.credentials` の失敗で試せなかった検査が `credentials_missing` を持ち、止まっているエージェントの稼働中専用の検査が `agent_not_running` を持つのは、この規則による。この規則の外にある SKIPPED は、自分の事実の符号を持つ。中継が無いために SKIPPED になる `relay.listeners`、`relay.sessions`、`relay.refusals` は、トンネルが無い原因が何であっても `no_relay` を持ち、`tunnel.local` の符号を引き継がない。実行時の排他を取れなかった実行の SKIPPED は、`agent.control` が OK なので `runtime_state_busy` を持つ。

#### 終了コード

| コード | 意味 |
|---|---|
| 0 | 総合判定を動かす検査に FAILED が 1 つも無い |
| 1 | 総合判定を動かす検査に FAILED が 1 つ以上ある |
| 2 | 報告を作れなかったか、診断に必要な証拠に権限で到達できず完全な判断ができなかった。引数の数が誤っている、知らないフラグを渡した場合、呼び出し元が権限で証拠に届かない場合が当たる (2026-09-23、所有者の決定) |
| 3 | 設定の誤り (11a 節) |

検査は、総合判定と終了コードへの効き方によって 3 つの層に分かれる (2026-09-23、所有者の決定)。

1. 総合判定を動かし、終了コード 1 に効く層。`agent.credentials`、`agent.process`、`tunnel.local`、`relay.listeners` である。カーネルモードでは `agent.credentials`、`tunnel.local`、`dataplane.interface`、`dataplane.table`、`host.forwarding` である。どちらのモードでも、直近の試みが鍵の変更の頻度の上限による拒否で終わった場合の `stream.connection` がこの層に入る (2026-10-03)
2. 権限で証拠に届かないときに終了コード 2 に倒す層。呼び出し元の権限の不足による `host.privileges` の失敗 (`permission_denied`)、`agent.credentials` が `agent.json` を権限で読めない場合とデータディレクトリを権限で辿れない場合、`agent.process` がロックファイルを権限で開けない場合、稼働中のエージェントの制御ソケットにファイルのパーミッションで繋げない場合、停止中のカーネルモードのエージェントのカーネルの状態を呼び出し元が `CAP_NET_ADMIN` を持たずに読めない場合 (`needs_cap_net_admin`) である。設定ファイルを権限で読めない場合は、`host.privileges` の失敗としてこの層に入る。root で実行した場合の `host.privileges` の UNKNOWN と、稼働中のカーネルモードのエージェントが `CAP_NET_ADMIN` を持たない場合の `host.privileges` の FAILED (`agent_lacks_cap_net_admin`) は、この層に入らない。後者はエージェント自身が答えた事実であり、呼び出し元が証拠に届かなかったことを示さないためである (「カーネルモードの `host.privileges` と root の実行」の項)
3. どちらにも効かない層。残りの検査であり、所見としては必ず出すが、総合判定にも終了コード 2 にも数えない

権限で証拠に届かない場合とは、`agent doctor` をエージェントと同じ実行主体で動かすという前提が崩れている実行を指す。層 2 の条件はいずれも、失敗の原因が呼び出し元の権限にあるのか、エージェント自身が転送を担えない状態にあるのかを区別できないため、診断できなかった側に倒す。出力では、エージェントと同じ実行主体で実行し直すことを示す (2026-09-23、所有者の決定)。root での実行し直しは案内しない。root はデータディレクトリと `agent.json` をすべて読めるため、root で実行すると `host.privileges` はエージェント自身の権限について答えられず、前提の崩れそのものを検出できなくなる。root で実行した場合の扱いは、前述の「2 つの証拠の出どころ」の項で定めた。

層 1 の FAILED と層 2 の条件が同じ実行で同時に成り立つ場合、終了コード 2 を優先する (2026-09-23、所有者の決定)。終了コード 2 は診断の結果を信頼できないことを表す。層 2 は推測で答えないために置いた層であり、診断が成立していないまま総合判定を終了コード 1 として返すことは、この層の趣旨と矛盾する。

層 2 に当たる実行でも、報告は出す (2026-09-23、所有者の決定)。どこまで読めてどこから権限で読めなかったかを示すほうが、運用者は直せる。そのかわり、終了コードの意味を「転送できない」ではなく「診断が成立しない」の側として分ける。`host.privileges` 自体の状態は FAILED でよい。状態の語と終了コードは別のものとして扱う。この検査は層 1 に無いので、状態が FAILED でも終了コードは 1 にならず、呼び出し元の権限の不足による FAILED は層 2 として終了コード 2 になる。

UNKNOWN、NOT TESTED、SKIPPED だけでは 0 のままとする。10.2a 節が定める同じ趣旨の規則は「UNKNOWN と NOT TESTED だけでは 0 のままとする」であり、SKIPPED を挙げていない。`agent doctor` は稼働中専用の検査が SKIPPED になりうるため、この節では SKIPPED も 0 を保つ対象に加える。この規則は終了コード 2 にも及ぶ。SKIPPED がいくつ並んでも終了コードは 0 のままであり、終了コード 2 は証拠そのものに権限で到達できなかった実行に限る。

`agent.json` が無いこと、まだ登録していないこと、中身が壊れていて JSON として読めないことは、2 ではなく `agent.credentials` の FAILED として 1 にする (2026-09-23、所有者の決定)。どれもエージェント自身の状態についての事実であり、診断を始められなかった失敗ではないためである。一方、`agent.json` があるのに権限で読めないことは 2 にする (2026-09-23、所有者の決定)。呼び出し元がエージェントと同じ実行主体で動いていないために起きる失敗であり、エージェントが転送を担えるかどうかについては何も述べない。この切り分けは、読み取りの誤りから `errors.Is` で `os.ErrNotExist` と `os.ErrPermission` を判定し、どちらでもなければ壊れた JSON として扱う形で行う。`os.ErrPermission` は、ファイルがあって読めない場合と、途中のディレクトリを辿れない場合の両方で返る。そこで `agent.json` 自身を stat し直し、stat も権限で拒まれれば、拒んでいるのはディレクトリであり有無は分からないとして `data_dir_unreadable` とする (2026-09-25)。ファイルがあると述べると、無いファイルについて事実でないことを述べるためである。層は `credentials_unreadable` と同じ 2 である。

`--json` は終了コードを変えない (2026-09-23)。報告を出した実行の終了コードは、`--json` の最上位の `status` と同じ判定から決まり、`ok` が 0、`failed` が 1、`unknown` が 2 に当たる。引数やフラグの誤りによる 2 と、設定の誤りによる 3 は、報告を作る前に止まる。この場合は `--json` を付けても標準出力に JSON を出さず、誤りを標準エラー出力に書く。

終了コード 1 が答える問いを、隣の 2 つと分けて書く。3 つとも問いが違う。

- `server doctor` の 1: ルールの転送の経路が壊れている
- `status` の 1: 配置全体に運用上の手当てが必要な劣化がある
- `agent doctor` の 1: このホストのエージェントが、今の状態では転送を担えない

#### 制御ソケットの拡張

制御ソケットに `doctor` を加える。既にあるのは `rotate-key` だけである (9 節、`internal/agent/control`)。

要求は今までどおり行ベースとし、`doctor` の 1 行を送る。応答の形式はコマンドごとに定める。`rotate-key` は今までどおり `ok <公開鍵>` の 1 行のテキストを返し、`doctor` は 1 つの JSON オブジェクトに改行を 1 つ付けたものを返す (2026-09-23、所有者の決定)。

**制御ソケットのプロトコル全体が JSON になったのではない。** `doctor` の応答だけが JSON である。ソケット全体の framing を変えると、`doctor` を加えるために既にある `rotate-key` の経路まで巻き込むことになる。`doctor` の応答を 1 行に収めておけば、今の行ベースの読み書きをほぼそのまま保てる。JSON は複数行にせず、pretty-print もしない。人が直接読む経路ではないためである。概念的には次の形になる。

```
doctor\n
{"status":"ok",...}\n
```

`\n` は改行を表す。上の 2 行は、要求が 1 行のテキストであり、応答が 1 行の JSON であることを示すだけの図であって、実際のフィールドの一覧ではない。

運用者が読む `agent doctor --json` の出力と、ソケットの上を流れる JSON は別のものである。前者は「出力の形」の項が定めた、10.2a 節に揃えた模型であり、後者はその材料にすぎない。両者が同じ Go の型かどうかは実装の判断とし、この節では決めない。

応答を組む処理には `recover` を置く (2026-09-23)。今の制御ソケットの受け口は `recover` を持たず、応答を組む処理が panic すると常駐プロセスごと落ちる。`rotate-key` が触る値は少ないが、`doctor` は多くの値を触る。診断のために転送を止めない。

加算で足りるのは、制御ソケットが 1 つのホストの中で閉じており、外部の実装がこの経路を使わないためである。`wgft agent doctor` が繋ぐ先は、同じホストで動く `wgft agent run` であり、どちらも同じ実行ファイルである。版が食い違いうるのは、新しいバイナリを置いてから常駐プロセスを再起動するまでの間だけである。その間に新しい CLI が `doctor` を送ると、古い常駐プロセスは既にある既定の分岐で `error: unknown command` を返す。CLI はこれを、稼働中の診断が取れない場合として扱い、静的な検査だけを示す。新しいコマンドの追加に、版の交渉も capability も要らない。

この場合、`agent.control` は UNKNOWN とする (2026-09-23、所有者の決定)。接続そのものは成功しているので SKIPPED には当たらず、FAILED にすると転送が健全な配置に対しても壊れている印象を与える。所見には、稼働しているエージェントが `doctor` に対応していないことと、新しい実行ファイルでエージェントを起動し直すことを添える。総合判定は動かさず、終了コード 2 の層にも入れない。古い常駐プロセスは接続できないのではなく `doctor` という機能に対応していないだけなので、権限の問題ではない。稼働中のプロセスからしか取れない検査は SKIPPED とし、理由の符号を `agent.control` と同じ `doctor_unsupported` とする。`control_socket_unreachable` は接続そのものができない場合の符号であり、この場合を押し込む符号ではない。終了コードは 0 のままとする。

7a.11 節の互換性の保証に、この経路が含まれるかどうかを確かめた。**含まれない。** 7a.11 節が列挙するサーフェスのうち、「agent-server の wire protocol」が拘束するのは stream の上を流れるメッセージであり、同じホストの中の Unix ソケットではない。「エージェントの認証情報ファイル」が保つのは置き場所とファイル名であり、隣のソケットの上を流れる形を扱わない。保証の対象外であることは、壊してよいという意味ではなく、版をまたいで固定する約束を負わないという意味である。

`doctor` の応答のトンネルの項目には、今のトンネルを立てた直後に測った WireGuard の UDP ソケットのバッファ `socket_buffers` を加えた (2026-09-27)。旧い CLI は知らないフィールドを読み飛ばすので、この追加も加算で足りる。新しい CLI は、このフィールドを持たない応答を、旧い常駐プロセスの応答として扱う。

同じトンネルの項目に、netstack の UDP の受信の会計の状態 `udp_accounting` を加えた (2026-09-27)。会計が止めたかどうかの `stopped` と、止めたときの違反の内容 `error` を持つ。追加と旧い版の扱いは `socket_buffers` と同じである。

#### 制御ソケットから実行時の状態を取れない場合

エージェントが稼働中でありながら、制御ソケットに繋げないことがある。原因は 3 つある。

- ソケットのパスが `sun_path` の上限を超えている。上限は終端の NUL を除いて Linux と Windows で 107 バイト、macOS で 103 バイトであり、`WGFT_DATA_DIR` が深い場合に超える (11a 節)。Go の `net` は上限を超える名前を OS を呼ぶ前に `invalid argument` で拒む
- エージェントがソケットを開けないまま動いている。`internal/agent/control` は、ソケットを開けなかった場合に `rotate-key` の稼働中経路だけを諦めてエージェントを動かし続ける。パーミッションを締められなかった場合も同じ扱いになるのは Windows だけである。Unix の `credentials.SecureSocket` は chmod の失敗を無視して常に成功を返すため、締め切れなくてもソケットは開いたまま残る
- ファイルのパーミッションで繋げない

どの場合も、`agent.control` を FAILED とし、原因と次に見るものを添える。`sun_path` の上限に当たる場合は、11a 節および `rotate-key` と同じ内容、つまりパスのバイト数、上限、短いデータディレクトリを使うという対処を添える。稼働中のプロセスからしか取れない検査はすべて SKIPPED とし、理由の符号を `agent.control` と同じ符号とする。符号は、`sun_path` の上限に当たる場合が `control_socket_path_too_long`、他の 2 つの場合が `control_socket_unreachable` である (2026-09-23)。静的な検査は通常どおり行う。健全な実行との差は `agent.control` にとどまらず、稼働中のプロセスからしか取れない検査の全体に及ぶ。

終了コードは、3 つの原因のうちファイルのパーミッションで繋げない場合だけ 2 とする (2026-09-23、所有者の決定)。制御ソケットへ権限の不足で接続できず、総合判定を動かす検査のうち `tunnel.local` と `relay.listeners` まで取れないなら、診断そのものが十分に成立しなかった場合に当たる。一方、`sun_path` の超過とソケットの未作成まで 2 にすると、エージェントは正常に転送しているのに診断の経路の都合だけで常に 2 になる配置を作れる。その 2 つは、終了コードを動かさない `agent.control` 自体の問題として所見にとどめるほうが、制御ソケットの障害は転送の障害ではないというこれまでの設計と一致する。診断が取れていないことは、出力の側で見落とせない形にする。

制御ソケットには繋げても、実行時の状態を取れない実行がある。`internal/agent` は実行時の状態を 1 つの排他で守っており、30 秒ごとの定期処理がその排他を取ったまま宛先への試し接続を一巡させる。応答を返さない宛先が多い配置では、一巡の長さが制御ソケットの期限に届きうる。`agent doctor` はトラブルの最中に繰り返し使うコマンドなので、その状況でこそ応答しなくなる。

`agent doctor` は、この排他を期限付きで待ち、取れなければ実行時の状態を取得できなかったという事実を返す (2026-09-23、所有者の決定)。黙って待たない。運用者には、エージェントは生きているが内部の処理で詰まっていることが分かる。稼働中のプロセスからしか取れない検査は SKIPPED とし、理由の符号は `runtime_state_busy` とする。所見には、内部の処理が詰まっていることと、次に見るものを添える。静的な検査は実行時の排他を要らないので、通常どおり行う。終了コードは 0 のままとする。証拠に権限で到達できなかった実行ではないためである。

この実行の `agent.control` は OK とする (2026-09-23)。制御ソケットに繋げて `doctor` の応答も得ているので、この検査が答える「制御ソケットに繋げるか」は満たされている。古い常駐プロセスが `doctor` に対応していない実行を UNKNOWN とするのとは扱いが違う。あちらは診断の応答そのものを得られないが、この実行では応答を得たうえで実行時の部分だけが欠ける。欠けたことは、続く検査の SKIPPED とその所見が述べる。

#### カーネルモードのエージェント

カーネルモードのエージェント (7b 節) の診断も、ユーザー空間モードと同じ問いに答える (2026-09-24、所有者の決定)。終了コード 1 は「このホストのエージェントが、今の状態では転送を担えない」を意味する。カーネルモードで転送を担うのは、エージェントのプロセスではなく、カーネルの wgft0、`table inet wgft_agent`、ホストの転送の設定である。そこで、この 3 つを見る検査 `dataplane.interface`、`dataplane.table`、`host.forwarding` を加え、群 `Dataplane` にまとめる。3 つとも総合判定を動かす。backend 全体の失敗とルール単位の失敗は、7a.3 節のとおり分けて扱い、混ぜない。

`agent doctor` はエージェントのモードを、稼働中のエージェントが制御ソケットで答えた `mode` から知り、その答えが無い実行では状態ファイル `agent.json` の記録から知る。記録は、エージェントが止まっていても読めるためである。`agent.json` を読めない実行ではモードが分からないので、3 つの検査を `agent.credentials` の符号を持つ SKIPPED とし、既存の検査は今までどおりに並べる。ユーザー空間モードの実行では、3 つの検査を NOT TESTED とし、理由の符号を `userspace_mode` とする。

カーネルモードの実行では、`relay.listeners`、`relay.sessions`、`relay.refusals`、`tunnel.watchdog`、`tunnel.socket_buffers`、`tunnel.udp_accounting` を NOT TESTED とし、理由の符号を `kernel_mode` とする。カーネルモードはリスナーも、中継の接続とそのフロー予算も、トンネルの作り直しも、プロセスの中の WireGuard のソケットと netstack も持たない (7b.1 節)。エージェントが止まっていても、この扱いは変わらない。`relay.listeners` を生かさないのは、存在しないリスナーについて答えないためであり、カーネルモードで問うべきは、nftables の dataplane がそのルールを公開しているかどうかである。`relay.allow_targets` は NOT TESTED にしない (2026-09-24、所有者の決定)。カーネルモードでも宛先の許可一覧を読んで守らせ、一覧の外には DNAT を作らない (7b.2 節) ので、この検査の意味はユーザー空間モードと同じである。読めない場合の状態と符号も、「宛先の許可一覧の扱い」の項と「制御ソケットから実行時の状態を取れない場合」の項のとおりとし、総合判定は動かさない。一覧に実際に拒まれたルールは、`dataplane.table` の FAILED として現れる。

`tunnel.local` と `tunnel.transfer` は、カーネルモードでも残す。`tunnel.local` は、ユーザー空間モードと同じくハートビートのトンネルの状態をそのまま判定する。カーネルモードのハートビートは、この状態を wgft0 の読み出しから組み立てる。`tunnel.transfer` は wgft0 のピアの送受信バイト数を示す。カーネルはこの数を wgft0 を作ったときから数え、エージェントの再起動では 0 に戻さないので、所見は数え始めた時刻を示さない。

#### カーネルモードの総合判定

`agent.process` の停止は、カーネルモードでも FAILED のままとする (2026-09-24、所有者の決定)。設定の更新、名前の引き直し、外からの変更への収束が止まるので、運用者の手当てが要る状態であることは変わらない。ただしカーネルモードでは、この FAILED だけで総合判定と終了コード 1 を決めない。停止中も wgft0 とテーブルが残っていれば転送は続くためである (7b.4 節)。所見には、カーネルの転送は続いている可能性があること、設定の更新と名前の引き直しと外からの変更への収束は止まっていること、転送の実体は `Dataplane` の群の検査が答えることを添える。

3 つの検査が FAILED にするのは、転送を担えないと確かに言える事実だけとする。それ以外の手掛かりは UNKNOWN の所見として示す。この分け方で、エージェントが止まっていても、wgft0、公開すべきルールの DNAT を持つテーブル、`ip_forward` が揃っていれば、終了コードは 1 にならない。逆に、どれかが欠けていれば、エージェントが動いていても終了コードは 1 になる。server がこのエージェントを無効にしている場合 (5.1 節) は、`relay.listeners` と同じく 3 つの検査を SKIPPED とし、理由の符号を `agent_disabled` とする (2026-09-24、所有者の決定)。無効かどうかは、稼働中は制御ソケットの答えから、停止中は `LastState` の無効を示すフィールドから知る。

#### カーネルモードの証拠の読み方

カーネルの状態は、エージェントが稼働中なら、エージェント自身が制御ソケットの `doctor` の応答で返す (2026-09-24、所有者の決定)。エージェントが停止している間だけ、呼び出し元がカーネルを直接読む。読む関数は 1 つで、稼働中のエージェントと停止中の診断が同じ関数を使う。稼働中のエージェントはメモリの上の鍵、全体状態、公開の記録を渡し、停止中の診断は `agent.json` にある同じ値を渡す。停止中に読む WireGuard インタフェースの名前は、設定の `WGFT_WG_INTERFACE` である。`runuser -u wgft` で実行した `agent doctor` には ambient の権限が付かず nftables を読めないが、エージェント自身は `CAP_NET_ADMIN` を持つので、同じ実行主体の前提のまま答えられる。稼働中でありながら制御ソケットから実行時の状態を取れない実行では、直接は読まず、3 つの検査を「制御ソケットから実行時の状態を取れない場合」の項と同じ状態と符号の SKIPPED とする。稼働を判定できない実行も、同じく SKIPPED `lock_unreadable` とする。

何を読むのに `CAP_NET_ADMIN` が要るかを、ラボで確かめた。WireGuard インタフェースの鍵とピアの読み出しと、nftables のテーブルとチェーンの読み出しは、`CAP_NET_ADMIN` を持たない呼び出し元では権限の誤りで拒まれた。リンクの有無、種別、up の印、経路の問い合わせ、`/proc/sys` の `ip_forward` と `rp_filter` は、権限なしで読めた。root、`runuser -u` で切り替えた利用者、ambient の `CAP_NET_ADMIN` だけを持つ利用者の 3 つで比べ、前の 2 つの読み出しに成功したのは root と `CAP_NET_ADMIN` を持つ利用者だけだった。エージェントが稼働中か停止中かで、この結果は変わらなかった。

呼び出し元が `CAP_NET_ADMIN` を持たないために直接読めない検査は UNKNOWN とし、理由の符号を `needs_cap_net_admin` とする。ただし、権限なしで読めた事実だけで FAILED と言える場合は FAILED を示す。wgft0 が無い、同名のリンクが WireGuard でない、wgft0 が down である、`ip_forward` が 0 である場合がこれに当たる。総合判定を動かす検査のこの UNKNOWN は、「終了コード」の項の層 2 に入り、終了コード 2 とし、`evidence_unreachable` を `true` にする。証拠に権限で届かない実行という層 2 の定義そのものに当たるためである。層 2 に入れなければ、止まったエージェントを同じ利用者で診断した実行が、転送の実体を何も観測しないまま終了コード 0 を返す。この場合の次の一手は、エージェントを起動すること、または root で実行してカーネルの状態を直接読むことである。「終了コード」の項は root での実行し直しを案内しないと定めるが、この場合はカーネルモードの例外とする。root での実行し直しを案内しない規則の理由は、root がファイルのパーミッションを迂回して `host.privileges` が前提の崩れを検出できなくなることである。`needs_cap_net_admin` の実行で欠けている証拠はファイルではなくカーネルの状態なので、この理由は当たらない。

#### `dataplane.interface` の判定

`dataplane.interface` は、エージェントの WireGuard インタフェースを見る。宣言は `LastState` の wg 設定であり、稼働中のエージェントはメモリの上の同じ値を使う。判定は次の順に行う。

- FAILED:wgft0 が無い (`interface_missing`)、同名のリンクが今の鍵か 1 つ前の鍵を持つ WireGuard インタフェースでない (`interface_not_ours`)、wgft0 が down である (`interface_down`)、server の公開鍵を持ち server のトンネルアドレスを AllowedIPs に含むピアが無い (`peer_missing`)。どれも、vpsd から届くパケットを wgft0 が受け取れないことを意味する。所有の判定は、エージェントの起動時の判定 (7b.4 節) と同じ関数で行う。判定はこの並びの順に行い、鍵を読めた実行では、所有の判定を down より先に行う。他の所有者の down のインタフェースを `interface_down` として示すと、起動すれば up になると案内することになるが、エージェントはそのインタフェースを他の所有者のものとして起動を拒むためである。鍵を読めない実行の down は、権限なしで読めた事実として `interface_down` の FAILED とし、所見に所有を読めなかったことを添え、次の一手は、エージェントが自分の鍵を持つインタフェースなら up に戻し、そうでなければ起動を拒むことと、root での実行を示す
- UNKNOWN `needs_cap_net_admin`:停止中で、呼び出し元が鍵とピアを読めない
- UNKNOWN `no_last_state`:`LastState` が無く、宣言が分からない
- UNKNOWN `route_not_via_interface`:server のトンネルアドレスへの経路が wgft0 を通らない。後述する
- UNKNOWN `interface_differs`:1 つ前の鍵を持つ、アドレス、MTU、keepalive が宣言と違う、余分なピアがある。転送が止まるとは言えないためである。稼働中のエージェントは宣言へ戻し (7b.4 節)、停止中は戻らないので、所見はどちらの実行かを示す。稼働中の戻し方は変わった点によって違う。アドレスと MTU の変更は変更の通知の後の見直しがすぐに戻す。鍵、keepalive、ピアの変更は通知が届かないので、30 秒ごとの見直しが戻す
- それ以外は OK とする

最終ハンドシェイク、エンドポイント、送受信バイト数は値として所見に示し、その健全さを判定しない。ハンドシェイクの判定は 10.2a 節の `tunnel.handshake` が持つ (「2 つのコマンドの境目」の項)。最終ハンドシェイクと送受信バイト数は、wgft0 が今持つ鍵で数えた値である。鍵を変える収束が server のピアを置き直すためである(7b.4 節の鍵の変更と最終ハンドシェイク)。鍵の書き換えがまだ済んでいない wgft0 は 1 つ前の鍵を持ち、所見はその値を 1 つ前の鍵のものとして示す。

server のトンネルアドレスへの経路が wgft0 を通らない場合、たとえば Tailscale のポリシールーティングがそのアドレスを別の表へ送る場合は、`dataplane.interface` の明示の所見とし、状態を UNKNOWN とする (2026-09-24)。経路は、エージェントの 30 秒ごとの見直しと同じく、カーネルに宛先の経路を問い合わせて読む (7b.1 節)。この問い合わせが答えるのはホスト自身が送るパケットの経路であり、ポリシールーティングの規則が入力のインタフェースや印を条件に持てば、LAN から戻る応答を転送する経路はこれと違いうる。転送を担えないと確かに言える事実ではないので、FAILED にしない。エージェントが同じ状態で起動を拒まない決定 (7b.1 節) とも揃う。所見は、経路が向かうインタフェースの名前と、その経路では応答が wgft0 を通らず転送が止まりうることを示す。

#### `dataplane.table` の判定

カーネルモードのルール単位の失敗は `dataplane.table` が示す (2026-09-24、所有者の決定)。`dataplane.table` は 2 つのことを判定する。1 つはテーブルそのものが正しいことであり、もう 1 つは、テーブルが公開すべき各ルールが実際に成り立っていることである。どちらも、直近の公開の記録と実際のテーブルを同じ関数で比べて判定する。比べるのは、`nat_pre` の DNAT の行から読んだルールとポートごとの宛先と、DNAT の行を含むすべてのチェーンの行の形と並びである (7b.4 節)。稼働中のエージェントはメモリの上の記録を、停止中の診断は `agent.json` の記録を渡す。記録は公開に成功するたびに両方で同じ値になるので、どちらの実行でも同じ比べ方になる。判定は次の順に行う。

- FAILED `table_missing`:`table inet wgft_agent` が無い
- FAILED `table_rows_missing`:記録から組む表の行かチェーンのうち、欠けると転送が止まるものが欠けている、または記録にある DNAT が無いか別の宛先を指している。どの行が当たるかは後述の表のとおりである。filter_pre の通す行、forward の通す行、MASQUERADE のどれかが欠けても転送は止まるので、DNAT の行だけでは足りない。エージェントが止まった後に行が消された場合も、ここで見つかる。守りの行も同時に欠けていれば、所見に併せて示す
- FAILED `listener_error`:ルール 1 本以上の状態が `error` である。7b.3 節の 1 つ目の種類 (許可一覧の外、名前の解決の失敗、ループバックの宛先、ブロードキャストかマルチキャストの宛先で、そのルールの DNAT が無い) と 2 つ目の種類 (TCP の宛先の接続確認の失敗で、DNAT はある) のどちらも当たる。`ip_forward` が 0 のために `error` を報告するルール (7b.1 節) も当たる。名前の解決に失敗して直前の解決の結果で転送を続けているルール (7b.2 節) は、理由の後ろに試し接続の誤りか `ip_forward` の誤りが続く場合だけ当たる。続かない場合は、次の `resolve_failed` である (2026-09-25)。この除外を別にすれば、ユーザー空間モードの `relay.listeners` が、ルールの `error` の出どころを問わず FAILED にするのと同じ扱いである。除くのは、そのルールの `error` が転送の停止を示さないためであり、ユーザー空間モードのエージェントはこの種類の `error` を報告しない。符号は `relay.listeners` と同じ `listener_error` とする。符号が表す事実、つまり転送の停止を示しうる `error` のルールが 1 本以上あることは、どちらのモードでも同じである
- UNKNOWN `guard_rows_missing`:欠けたのが、欠けても転送が止まらない行とチェーン (守りの行) だけである (2026-09-24、所有者の決定)。転送は続きうるので、終了コード 1 が答える問いに対して FAILED とは言えない。所見は、欠けた行の名前と、欠けた行の組み合わせで開きうる面を示す。drop の行は層になっているので、面は、その面を閉じる行がすべて欠けたときだけ開く (2026-09-24、所有者の決定)。1 行だけの欠けで面が開かないときは、残っている行がまだ閉じていることを示す。組み合わせは後述の守りの行の効果の表のとおりである。表に加わった行か位置の違う行が無ければ、転送は続きうることも添える。それらがあれば、その効果は分からないので、転送は続きうるとも、残っている行がまだ閉じているとも言わず、それらを所見に示す。加わった行は、残っている drop の行より前でパケットを通しうるためである。`input` の drop の行を消し、`filter_pre` の先頭に wgft0 から入るものを通す行を加えた表では、ホストのポートにも他のテーブルの DNAT にも届いた。ルールの `error` が同時にあれば、`listener_error` の所見に併せて示す
- UNKNOWN `publish_failed`:直近の全体状態の公開が失敗し (7b.3 節の 3 つ目の種類)、旧いテーブルが残っている。旧いテーブルが転送を続けているので、このホストのエージェントが今は転送を担えない、とは言えず、FAILED にはしない。所見に公開の誤りを示す。稼働中の実行だけが持つ事実である
- UNKNOWN `table_changed`:記録から組む表の行はすべてあるが、wgft が書かない行かチェーンが加わっているか、記録から組む行が同じチェーンの別の位置にある。どちらも、転送を止めるかどうかは分からない。所見に加わった行と位置の違う行を示す。稼働中のエージェントは変更の通知の後の見直しで公開し直し、公開し直しが失敗した後は 30 秒ごとの見直しでも試し直す (7b.4 節)。このため、稼働中の実行でこの所見が続くのは、公開し直しが失敗しているか、失敗の後の間隔のために通知の後の見直しが待っている間である
- UNKNOWN `resolve_failed`:稼働中の実行で、`error` のルールがどれも、名前の解決に失敗して直前の解決の結果で転送を続けているだけのルール (7b.2 節) である (2026-09-25、所有者の決定)。DNAT は直前のアドレスへ向いたまま残っており、転送の停止は観測していないので、終了コード 1 が答える問いに対して FAILED とは言えない。`host.resolve` と `tunnel.resolve` の `resolve_failed` と同じく、名前の解決の失敗は今この瞬間に転送を担えないという証拠ではない。`server doctor` の `rule.target_resolve` も同じルールを FAILED にせず、UNKNOWN の `target_resolve_failed` とする (10.2a 節)。所見は、直前の解決の結果で転送を続けているルールと、その解決の誤りを示す。判定の材料は理由の文言であり、`server doctor` と同じ関数で読む。転送の行の欠け、守りの行の欠け、公開の失敗、表の変更と同時にあれば、そちらの符号を採り、このルールを所見に併せて示す。`listener_error` の所見にも併せて示す。30 秒ごとの見直しの失敗は、OK の所見と同じく併せて示す。停止中の実行では、次の `agent_not_running` を採り、所見のルールの一覧に理由を示す
- UNKNOWN `agent_not_running`:停止中で、比べた部分がすべて一致した。後述する
- それ以外は OK とする

行とチェーンの分け方は、「その行が欠けたときに転送が止まるか」で決める (2026-09-24、所有者の決定)。欠けたときに転送が止まる行を転送の行、止まらない行を守りの行と呼ぶ。通す行は、同じチェーンでそれが通さなかったパケットを落とす drop の行があるときだけ転送に要る。その drop の行も欠けていれば、通す行が欠けても転送は止まらないので、守りの行として数える。チェーンごと無い場合は、そのチェーンの分け方に従う。判定は稼働中と停止中で同じ関数が行う。分け方は次の表のとおりである。

期待する行が同じチェーンの別の位置にある場合は、欠けに数えない (2026-09-24、所有者の決定)。行は順に照らし合わせ、順に見つからなかった行を、まだ当たっていない実際の行から探す。見つかれば位置の違う行とし、行が加わった場合と同じく効果の分からない変更として扱う。たとえば `filter_pre` の drop の行を消して先頭に入れ直した表では、その行は欠けておらず、公開した通す行より前で wgft0 からのパケットを落とす。本当に無い行と位置の違う行が両方あれば、欠けの判定 (転送の行なら `table_rows_missing`、守りの行だけなら `guard_rows_missing`) を保ち、位置の違う行と加わった行も所見に示す。

| チェーン | 行 | 分け方 | 欠けたときに止まる転送 |
|---|---|---|---|
| `filter_pre` | ルールごとの通す行 | 転送 (同じチェーンの drop の行があるとき) | そのルール |
| `filter_pre` | 成立済みのフローを通す行 | 守り | 無し |
| `filter_pre` | drop の行 | 守り | 無し |
| `filter_pre` | チェーンそのもの | 守り | 無し |
| `nat_pre` | ルールごとの DNAT の行と map の要素 | 転送 | そのルール |
| `nat_pre` | チェーンそのもの | 転送 | すべてのルール |
| `input` | DNAT したフローを通す行 | 転送 (drop の行があり、宛先がホスト自身のルールがあるとき) | 宛先がホスト自身のルール |
| `input` | 成立済みのフローを通す行 | 守り | 無し |
| `input` | drop の行 | 守り | 無し |
| `input` | チェーンそのもの | 守り | 無し |
| `forward` | 2 つの MSS のクランプの行 | 守り | 無し。ICMP を落とす経路の大きな TCP は止まりうる (7b.1 節) |
| `forward` | wgft0 から wgft0 への drop の行 | 守り | 無し |
| `forward` | DNAT したフローを通す行 | 転送 (wgft0 から入るものの drop の行があり、宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| `forward` | wgft0 へ出る成立済みのフローを通す行 | 転送 (wgft0 へ出るものの drop の行があり、宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| `forward` | 2 つの drop の行 | 守り | 無し |
| `forward` | チェーンそのもの | 守り | 無し |
| `postrouting` | MASQUERADE の行とチェーンそのもの | 転送 (宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| どれか | 見出し (種類、フック、優先度、policy) の違うチェーン | 転送 | 未確認 |
| どれか | 同じチェーンの別の位置にある行 | 欠けに数えない。`table_changed` の所見に示す | 移し方による。`filter_pre` と `forward` の wgft0 から入るものの drop の行をチェーンの先頭へ移すと、LAN の宛先への TCP が止まった |

守りの行が欠けたときに開きうる面は、欠けた drop の行の組み合わせで決まる。表の「確かめたこと」は、停止中のエージェントのテーブルから drop の行を消し、VPS の名前空間から wgft0 のアドレスへ試したラボの結果である。

| 欠けた行 | 開きうる面 | 残っている行が閉じているもの | 確かめたこと |
|---|---|---|---|
| `input` の drop の行だけ | 無し | `filter_pre` の drop の行が、ホストのポートを閉じている。表に加わった行か位置の違う行があれば、この閉じ方は言えない | ホストのポートにも他のテーブルの DNAT にも届かなかった |
| `filter_pre` の drop の行 | 他のテーブルの DNAT | `input` の drop の行がホストのポートを、`forward` の wgft0 から入るものの drop の行が LAN への面を閉じている | 他のテーブルの DNAT にだけ届いた |
| `filter_pre` と `input` の drop の行 | wgft が公開していないホストのポートと、他のテーブルの DNAT | | 両方に届いた |
| `forward` の wgft0 から入るものの drop の行だけ | 無し | `filter_pre` の drop の行が、LAN への面を閉じている。表に加わった行か位置の違う行があれば、この閉じ方は言えない | LAN のホストに届かなかった |
| `filter_pre` と `forward` の wgft0 から入るものの drop の行 | DNAT していないパケットの LAN への転送と、他のテーブルの DNAT | | LAN のホストに届いた。ラボでは server の側のピアの AllowedIPs に LAN のアドレスを加えて試した。wgft が設定するピアでは VPS はそのパケットを送らないが、守りの行が防ぐ相手は 11 節の奪われた VPS であり、VPS の root は自分のピアの AllowedIPs を自由に足せるので、この設定は緩和にならない |
| `forward` の wgft0 から wgft0 への drop の行 | wgft0 から入ったパケットの wgft0 への折り返し (宛先がトンネルの先にある DNAT など) | | 未確認。VPS のトンネルアドレスを宛先にしたルールでは、どの drop の行を消しても VPS の側に届かなかった |
| `forward` の wgft0 へ出るものの drop の行 | 転送したフローの返りでないパケットの wgft0 への転送 | | 未確認。LAN のホストから VPS のトンネルアドレスへの接続は、この行を消しても VPS の側に届かなかった |
| MSS のクランプの行 | ICMP を落とす経路での大きな TCP の停止 | | 7b.1 節のとおり、ラボで確かめた |

宛先がホスト自身かどうかは、記録の DNAT の宛先をホストのアドレスと比べて決める。ホストのアドレスは `CAP_NET_ADMIN` なしで読める。読めなければ、どちらの宛先もありうるので、転送の行として数える。表の分け方は、ラボで、停止中のエージェントのテーブルから行とチェーンを 1 種類ずつ消し、LAN の宛先への TCP と UDP、ホスト自身の宛先への TCP が通るかを見て確かめた。通す行とその drop の行を両方消した組み合わせも確かめた。見出しの違うチェーンは確かめておらず、転送が止まらないとは言えないので転送の側に置く。守りの行が欠けたときに実際に何が届くかは、`filter_pre` の drop の行を消すと、他のテーブルの DNAT が wgft0 から届くようになることだけを確かめた。

ルールの状態は、稼働中はハートビートと同じ 1 回の読みから来る値であり、停止中は記録が持つルールごとの理由である。所見はルール単位とし、ルールごとに DNAT を置いたポートの数を示す。DNAT を置いたまま `error` を報告するルールと、DNAT を持たないルールを、運用者が見分けられるようにするためである。直前の解決の結果で転送を続けているルールは、ルールの理由がそのことと転送先のアドレスを示す。

直前の公開の誤りと、直前の見直し(30 秒ごとの見直しか、変更の通知の後の見直し。7b.4 節)の誤りはエージェントのプロセスのメモリにだけあり、TCP の宛先の接続確認の結果はハートビートにだけある。このため、エージェントが停止している実行の `dataplane.table` は、次の形で判定する (2026-09-24、所有者の決定)。テーブルがあることだけでは OK にしない。停止中の診断が答えるのは、プロセスが止まっている間に実際に残っているカーネルの転送だからである。

エージェントが停止している実行の `dataplane.table` は、状態ファイル `agent.json` の記録と実際の `table inet wgft_agent` を比べる。材料は、最後に処理した全体状態 `LastState` と、カーネルモードで記録する直近の公開の結果である (9 節)。直近の公開の結果には、ルールごとに、公開したポートと、そのとき解決して DNAT に書いた宛先のアドレスとポート、または 7b.3 節の 1 つ目の種類で公開しなかった理由を持つ。ホスト名の解決の結果と、許可一覧を当てはめた結果は、`LastState` の宣言だけからは導けないためである。比べ方は次のとおりである。

- 公開すべきルール:直近の公開の結果が公開したと記録しているルールである。その各ポートの DNAT が、記録した宛先を指して実際のテーブルにあることを確かめる。1 つでも無いか別の宛先を指していれば FAILED とする
- 公開しなかったルール:直近の公開の結果が理由を記録しているルールは、稼働中と同じく FAILED とする
- 記録が無い場合:直近の公開の結果を持たない `agent.json` では、判定を宣言から導ける範囲に限る。有効なルールの各ポートに DNAT があること、IP リテラルの宛先ならその宛先を指すことを確かめ、ループバックの宛先とブロードキャストかマルチキャストの宛先(7 節)を持つルールは FAILED とする。帯のブロードキャストのアドレスは、`agent doctor` を実行した時点のホストのインタフェースの一覧で判定する。ホスト名の宛先の向き先、許可一覧の当てはめ、DNAT の行の外の行の形は確かめない。許可一覧を設定の出どころから組み立て直さないのは、「宛先の許可一覧の扱い」の項と同じ理由による。ユーザー空間モードで動いてきたエージェントをカーネルモードで起動し、最初の公開の前に止まった場合がこれに当たる
- 再現できない部分:TCP の宛先の接続確認の結果 (2 つ目の種類) と、直前の公開の誤りは、稼働中のプロセスなしには再現できない。この部分は判定せず、所見に比べた範囲と比べなかった範囲を示す

停止中の `dataplane.table` の状態は、比べた部分に FAILED があれば FAILED とし、無ければ UNKNOWN とし、理由の符号を `agent_not_running` とする。比べなかった部分が必ず残るので、停止中の実行で OK にはしない。終了コードは「終了コード」の項の層の規則からそのまま決まる。FAILED は層 1 の FAILED として終了コード 1 になる。比べた部分がすべて一致した UNKNOWN は、権限で証拠に届かなかった実行ではないので層 2 に入らず、他に FAILED が無ければ終了コードは 0 のままである。テーブルを権限で読めない場合は、前述の `needs_cap_net_admin` の規則が先に効く。

#### `host.forwarding` の判定

`host.forwarding` は、ホストの転送の設定を見る。

- FAILED `ip_forward_off`:`net.ipv4.ip_forward` が 1 でない。カーネルは wgft0 から入ったパケットを LAN へ転送しない。宛先がホスト自身のルールだけは届くが (7b.2 節)、転送を担えないと確かに言える事実である
- UNKNOWN `ip_forward_unreadable`:`ip_forward` を読めない
- UNKNOWN `needs_cap_net_admin`:停止中で、呼び出し元が他のテーブルを読めない。`ip_forward` が 1 のときだけ当たる
- UNKNOWN `forward_policy_drop`:他のテーブルの forward のチェーンが既定で落とす。明示の accept があれば転送は通るので、6.1 節と同じく手掛かりとして示し、FAILED にはしない。判定はエージェントが起動時にログへ出すものと同じ関数で行う (7b.1 節)
- UNKNOWN `rp_filter_strict`:`net.ipv4.conf.all.rp_filter` か `net.ipv4.conf.default.rp_filter` が 1 である。経路の組み方によっては転送が通るので、手掛かりとして示す
- それ以外は OK とする

#### カーネルモードの `host.privileges` と root の実行

root の実行の扱いは次のとおりとする (2026-09-24、所有者の決定)。ファイルの権限の検査は今のまま保ち、root の実行では `host.privileges` を UNKNOWN `running_as_root` とする。root がファイルのパーミッションを迂回する事情は、カーネルモードでも変わらないためである。所見には、制御ソケットの答えから、稼働中のエージェントの実 uid と利用者名を添える。これはモードによらない。利用者名を引けない uid では、uid だけを示す。

カーネルモードでは、`host.privileges` の対象に、稼働中のエージェントが実効として持つ `CAP_NET_ADMIN` を加え、制御ソケットの答えで判定する。これは「個別の理由で動かさない検査」の項が退けた、制御ソケットからエージェント自身の権限を取る案を、カーネルモードに限って採るものである。`runuser` で実行した呼び出し元は ambient の権限を持てないので、呼び出し元の権限を見てもエージェントの `CAP_NET_ADMIN` については何も分からないためである。エージェントがこの権限を持たなければ `host.privileges` を FAILED とし、理由の符号を `agent_lacks_cap_net_admin` とする。この判定の結果は、エージェント自身の性質をエージェントが答えたものであり、呼び出し元が証拠に届かなかったことを示さないので、実行を層 2 に入れない。呼び出し元の権限の不足 (`permission_denied`) と root の実行 (`running_as_root`) は、この判定より先に効く。同梱の unit はカーネルモードでもエージェントを root で動かさない。root で動くエージェントは、「2 つの証拠の出どころ」の項の root の実行の扱いをそのまま受ける。

#### カーネルモードの制御ソケットの応答

制御ソケットの `doctor` の応答に、次のものを加える。どれも加算であり、古い CLI は読み飛ばす。

- 最上位の `process`:稼働中のエージェントの実 uid、引ければ利用者名、Linux では実効の `CAP_NET_ADMIN` の有無。実行時の排他を要らないので、排他を取れなかった応答にも載る
- `runtime_state` の `kernel`:カーネルモードのエージェントだけが持つ。前述の読み方の関数の結果、つまり wgft0、テーブルと記録の比較、ホストの転送の設定である
- `runtime_state` の `publish_error` と `check_error`:公開できずに試し直している全体状態の誤りと、直前の見直しの誤りである。見直しは 30 秒ごとの見直しと変更の通知の後の見直し(7b.4 節)の両方を指し、どちらも同じテーブルと wgft0 を読むので、誤りを 1 つの控えに持つ
- ルールごとの `ports` と `dnat_ports`:ルールの宣言のポートの数と、DNAT を置いたポートの数である

`runtime_state` の `mode` が `kernel` なのに `kernel` を持たない応答は、この変更より前のカーネルモードのエージェントの応答である。この場合、3 つの検査は SKIPPED とし、理由の符号を `doctor_unsupported` とする。

#### 範囲外

遠隔の診断は含めない。server がエージェントに診断を要求し、その結果を併せて示す形であり、必要かどうかの判断を `agent doctor` ができてからにすることは 10.2a 節が既に定めている。手元で見えるものが分かって初めて、server 側から要求すべき情報が決まるという理由も変わらない。

Web UI からの呼び出しと `--report` も含めない。10.2a 節が定めた順序は `agent doctor`、Web UI、`--report`、遠隔の診断である。

エージェントの回線から VPS の WireGuard の UDP ポートとエージェント用 API のポートへ届くかどうかを、エージェント側から能動的に確かめる機能も含めない。10.2a 節が「切り分けられない所見」として残した穴、つまり最終ハンドシェイクが無い原因を VPS の側からは 1 つに決められないという穴を埋める候補ではある。`--probe` に当たるものをエージェント側に置くかどうかは、`agent doctor` を実際に使ってから決める。

`agent doctor` は、エージェントの設定の全体を出所付きで印字する機能を持たない。`wgft server check` に当たるものをエージェント側に置くかどうかは、この節では決めない。起動ログの先頭が有効な設定を出所付きで印字することは 11a 節のとおりであり、そちらで足りるかどうかは実際に使ってから判断する。

#### 置き場所

`agent doctor` は `agent` の一群の下に置く。`server doctor` が `server` の下にあるのと対称になり、7a.11 節が保つコマンドの構成 (`server`、`agent`、`rule`、`status`、`version` とその下位) にもそのまま収まる。`agent` の一群は build tag を持たず (`cmd/wgft/agent.go`)、Windows と macOS のバイナリにも入る。実装は `cmd/wgft` の専用のファイルに置き、build tag を持たせない。

ただし 7a.11 節のとおり、macOS のエージェントは暫定であり、v1.0 の保証に含まれない。この節の記述のうち、macOS での挙動は設計の意図であって、実機で確かめた事実ではない。Windows の `agent doctor` は、稼働中と停止中の実行と `--json` を Windows 11 の実機で確かめ、7a.11 節の保証に含めた(改訂の記録 2026-09-27)。管理者の権限での実行は期待する結果を定めておらず、`control socket` が OK、終了コードが 0 になったことを観察しただけである。

実装のときは、`cmd/wgft/doctor.go` にある 4 か所の `TODO(agent-doctor)` の案内を `wgft agent doctor` に向け直す。10.2a 節が「`agent doctor` ができた時点で案内し直す」と定めている箇所である。
