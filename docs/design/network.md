## ネットワーク

転送は IPv4 を対象とし、VPS がトンネルのアドレスと MTU を決めてエージェントへ配ります。
管理用 API は公開転送ポートとは別の接続経路を使います。


- `vpsd` の WireGuard インタフェースの既定名は `wgft0`(`--wg-interface` で変更可)。
  一般的な `wg0` を既定にすると、既に `wg0` を使っている VPS で既存の WireGuard を壊すため([9 節](state.md#9-状態の保存と再起動)の所有判定と併せた対策)。
  本書では読みやすさのため以降も `wg0` と書くが、実際の既定名は `wgft0` を指す
- wg0 のアドレス帯は `10.200.0.0/24`。
  `vpsd` が `.1`、エージェントには登録時に `.2` 以降を割り当てる。
  エージェントは vpsd を帯の先頭の次(`.1`)と決め打ちするので、`WGFT_WG_ADDRESS` のアドレス部分は帯の先頭の次でなければならず、帯は IPv4 で `/30` 以下の長さに限る。
  満たさない値は設定の誤りとして起動を拒否する([11b 節](security/startup.md#11b-起動の失敗の意味論))。
  stream に一度も来ないエージェントもアドレスを持ち、エージェントの削除で回収される
- VPS で外に開けるポートは次の 3 種類だけ。
  WireGuard の待ち受け(UDP 51820、変更可)、エージェント用 API(TCP 8443、変更可)、転送対象のポート
- 管理用 API と Web UI は Unix ソケット(既定)か Tailscale のアドレスで待ち受け、インターネットには開けない([11 節](security/admin-transport.md#11-セキュリティ))
- wg0 の MTU は `vpsd` が決め(既定 1420)、全体状態でエージェントに渡す。
  エージェントは netstack の tun に同じ値を使います。
  ユーザー空間モードのエージェントでは TCP はエージェントの netstack で終端され、netstack が自分の MTU から MSS を広告するので、この 2 つが揃っていれば wg0 の MTU を超える TCP は生まれず、VPS 側に MSS クランプは要りません。
  ずれると、PMTUD の ICMP が途中で落ちる経路で大きな TCP が止まります。
  カーネルモードのエージェントは TCP を終端しないので、エージェントが自分の WireGuard インタフェースを通る SYN の MSS をクランプする([7b 節](agent-kernel.md#7b-データプレーン自宅側カーネルモード))
- wg0 の MTU 1420 は、外側の回線の MTU が 1500 である前提の値です。
  自宅回線の MTU が小さい場合(PPPoE の 1454 など)でも、WireGuard の外側の UDP は DF なしなので途中でフラグメントされて動くが、大きなパケットがすべて 2 つに割れる。
  回線の MTU が分かっているなら `vpsd` の MTU を下げる方が効率がよい(全体状態でエージェントにも渡る)。
  また、トンネル一般の挙動として、DF 付きで 1393 バイト以上のペイロードの UDP を送る client は初回だけ ICMP fragmentation needed で失敗し、経路 MTU を学習した後は通る(実験で確認)
- エージェントは `PersistentKeepalive = 25` で NAT 越しに接続を維持します。
  keepalive の 5 倍の間ハンドシェイクが成功しなければ、エージェントはエンドポイントの名前を引き直してピアに設定し直す。
  この引き直しでも戻らない故障に備えた第 2 段の回復は [7 節](agent-dataplane.md#7-データプレーン自宅側)に定める
- VPS の conntrack の UDP タイムアウト 2 値(`nf_conntrack_udp_timeout` と `nf_conntrack_udp_timeout_stream`)は `vpsd` が起動時に読み、全体状態でエージェントに渡す
- `vpsd` は wg0 上で待ち受けをしません。
  エージェントへ張る接続(プロキシモードの中継、疎通確認)はすべて `vpsd` 側から外向きに開きます
- IPv4 のみ対応する(IPv6 は未決事項)
