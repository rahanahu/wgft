#### Phase 6 の移行の手順

各段は、7a.8 節の共通の完了条件を満たしてから次へ進む。
最初の 2 段は、並行した取得の超過を除いて挙動を変えない。

1. 型を分ける。
   `internal/flowcap` を `internal/resource` に改め、`AdmissionLimits` を `internal/policy` へ、`LogGate` を `internal/lograte` へ移す。
   `cmd/wgft`、`planner.Input`、`policy.Build`、userspace backend、`proxyrelay`、agent の `Options` を新しい型に書き換える。
   完了条件は、`MemoryLimit` の値(既定で 216 MiB、2048 と 1024 で 100 MiB)と、設定層の検査とエラーの文言が変わらないことである
2. `resource.Pool` を置き、ルールごとの上限を今の値のまま `Pool` で判定する。
   `relay.Manager` の `ruleFlows` による判定と、`proxyrelay` の listener ごとの `ConnsMax` の判定を置き換える。
   今の `relay.Manager` は、ルールごとの数を読んでからプロセス全体の枠を取るまでを 1 つの排他の中で行わないので、範囲のルールの複数の listener が同時に受け付けると、ルールごとの上限をわずかに超えうる。
   `Pool` は両方を 1 つの排他の中で判定するので、この超過が無くなる。
   拒否の理由ごとの数とログの文言もこの段で加える。
   完了条件は、同じ入力の列に対して、今の実装と通す・拒むが一致する単体テストを通すことである
3. `proxyrelay` が accept の後に拒む接続(Admission Policy の拒否と Resource Guard の拒否)を、`SetLinger(0)` による RST で閉じる。
   今は通常の `Close` で閉じており、6.3 節の「実ソケットでも拒否は `SetLinger(0)` の RST で閉じ」という記述と食い違っている。
   `relay` の TCP の拒否(`abortRefused`)と同じ閉じ方にそろえる
4. 判定を隔離予約の式(`C = ceil(T/2)`)に切り替え、コードから従来の下限の定数(`UDPPerRuleFloor`、`TCPPerRuleFloor`)を削除する(完了)。
   7 節の同時フロー数の上限の表と説明、6.2 節と 6.3 節の関連する記述、`lab/lifecycle.sh` の check 5 と `lab/connlimit.sh` の説明を同じコミットで改める。
   7 節の「ルールごとの上限はプロセス全体の上限の半分になるので、この目安でも 1024 UDP・512 TCP を 1 ルールが保持できる」は、置き換える前の実装(2048 と 1024)と食い違っていたので、「ルールが 2 本以上あると、ルール 1 本の上限はプロセス全体の上限の半分(切り上げ)になるので、この目安では 1 ルールが 1024 UDP・512 TCP を保持できる。
   ルールが 1 本なら、プロセス全体の上限のすべてを保持できる」の旨に書き改めた。
   7 節の表と説明からも、下限(4096、1024)の記述を除いた
5. `nf_conntrack_max` が 65536 未満のときの判定を、`ip_forward` と同じ起動時のログにも出す。
   `server check` と起動時の Finding の提示は、メモリの数値を出さず、65536 を wgft の運用上の推奨値として示す形に改めた。
   admin API に `flow_budget`(プロトコルごとの `in_use` と `limit`)と `resource_refusals`(ルール ID から理由ごとの拒否の数への表)を加える。
   `GET /api/v1/rules` と `POST /api/v1/rules/batch` は、どちらも同じ応答の型を返すので、Backend が Resource Guard の状態を持つときだけ両方に加わる(`ApplyStatusBackend` と同じ、報告が無ければ何も足さない別の interface)。
   kernel モードの server は UDP を Go の `resource.Pool` で数えないので `flow_budget` に "udp" は現れず、Go が判定しないルール(kernel モードの `Transparent`)は `resource_refusals` にも現れない。
   `rule ls` は REFUSED 列(理由を問わない合計)と、`generation` の行に続く flow budget の要約行(`flow budget: tcp 3/2048` の形)を出す。
   `rule ls --json` は応答をそのまま出すので同じキーが増える。
   Web UI は 7a.10 節のとおり変えない(完了)
6. 隔離予約の形を、登録ごとの最低分と予備の形に改める(前述の「共有プール、最低分と予備」と「退役した登録のフローの帰属」、2026-09-29 と 2026-09-30 の所有者の決定)。
   `resource.Pool` はフローを受け付けたときのルールの登録で数え、退役した登録のフローを帰属の規則で移し、登録ごとに listener が運ぶ数を保ち、受け付けていない listener からの取得を拒み、listener と登録の組を指す取得の手形を返す。
   拒否の理由に `floor` と `spare` を加え、拒否のログの文言を改める。
   `relay` の TCP の worker は今の順序(取得の後、listener ごとの排他の下で停止の印を確かめ、止まっていれば手形を返して接続を拒む)を保つ。
   止まっていたときと、受け付けていない listener からの取得を拒んだときは、どちらも RST で終える。
   前者はまだデータをやり取りしていない接続なので、ホストのソケットでも RST にする(7a.5 節)。
   `relay` の UDP の listener は、受け付けを止めるときも再開するときも今の順序(止めるときは listener の印を先に下ろし、再開するときは印を先に立ててから `Pool` の受け付けを始める)を保つ。
   再開と同時に所属ルールが変わるときは、受け付けを再開する前に付け替え、旧いセッションを宣言のルールの登録へ移す。
   印と `Pool` の状態が食い違うあいだの取得は `Pool` が受け付けていないとして拒むので、帳簿は崩れない。
   セッションを表に入れる前に listener が閉じていないことを確かめることも、今の順序を保つ。
   `proxyrelay` は、listener の排他の下で停止の印を確かめてから取得する今の順序を保つ。
   7 節の表と説明、`docs/manual/setup.md` と `docs/manual/setup.ja.md` のルールごとの上限の説明、`lab/lifecycle.sh` の check 5 から 5e の説明と期待値と拒否の理由、`agent doctor` の budget の表示と `refusals` の説明を同じ変更で改め、拒否の理由と分割元に残ったポートを確かめる check 5f と 5g を加える。
   admin API には、拒否の理由のキーのほかに何も加えない(完了)

#### 利用者から見て変わらないものと変わるもの

CLI のコマンドとフラグ、`WGFT_MAX_UDP_FLOWS`、`WGFT_MAX_TCP_FLOWS`、`WGFT_MAX_UDP_FLOWS_PER_SOURCE`、`WGFT_MAX_TCP_FLOWS_PER_SOURCE` の意味と既定値と範囲、`GOMEMLIMIT` の扱い、メモリのソフト上限の値、機械向けの CLI 出力、ルールの書き出しと読み込みの形式、admin API v1 の既存のフィールド、join string と agent/server の通信、drop の種類とカウンタは変わらない。
`T` が既定以上の構成でルールが 2 本なら、ルールごとに保持できる数も変わらない(`T` が奇数のときだけ 1 増える)。

次の挙動が変わる。

- ルールが 1 本の構成では、そのルールが予算 `T` のすべてを保持できる(既定で UDP 8192、TCP 2048。
  以前は 4096、1024)
- ルールが 3 本以上の構成では、2 本以上のルールがフラッドを受けても、残りのルールが予約の分だけ新しいフローを通せる
- `T` が既定より小さい構成でルールが 2 本以上なら、ルール 1 本の上限が `ceil(T/2)` に下がる。
  対象は、`T` が従来の固定値以下の構成(UDP 2048、TCP 1024 など。
  以前の上限は `T`)と、従来の固定値と既定のあいだの構成(UDP 4097 から 8191、TCP 1025 から 2047。
  以前の上限は従来の固定値)である。
  代わりに、1 本のルールへのフラッドの最中も、他のルールが新しいフローを通せる
- 上限で拒んだことのログの文言が、理由(`budget`、`rule_cap`、`reserve`)で分かれる
- `proxyrelay` が拒む接続は、クライアントから RST として見える
- admin API の応答に `flow_budget` と `resource_refusals` が加わり、`rule ls --json` の出力にも同じキーが増える
- `rule ls` の人が読む出力に、ルールごとの Resource Guard の拒否の総数を示す `REFUSED` の列と、`generation` の行の後の `flow budget: tcp 3/2048` の形の行が加わる。
  kernel モードの server は UDP を数えないので、`udp` は出ない
- `nf_conntrack_max` が 65536 未満なら、起動時のログにも警告が出る(管理用 API と Web UI は、他の nftables の Finding と同じく対象外)。
  `server check` が提示する値は 262144 から 65536 に変わり、メモリの数値 は出さない

手順 6 では、次の挙動が変わる。

- ルールが 1 本の構成では、保持できるのが予算 `T` から予備の 4 を除いた値になる
- ルールが 2 本以上の構成では、各ルールの最低分と 1 本の上限が隔離予約の形より高々 2 小さくなる。
  ルールが 2 本か 3 本の構成でフラッドを受けたルールの拒否の理由は、`rule_cap` ではなく `spare` になる
- 新しいルールは、加わる時点で予備の分の空きがあれば、予算が埋まっていても下限の 4 本をすぐ通せる
- 請求の合計が `T` を超えているあいだ、自分の最低分に届いていないルールが `floor` で拒まれることがある
- 分割で所属ルールが変わった listener の既存のフローは、分割元の登録が続くあいだ、最低分の判定では移動先のルールで数えない。
  分割元の登録が退役すると、移動先のルールで数える。
  ルール 1 本の上限は今までどおり listener が運ぶ数で判定する。
  統合、名前の変更、UDP の再開の後は、今までどおり旧い接続を今のルールで数える
- フラッドを受けたポートを分割で切り出すと、分割元が続くあいだ、分割元に残ったポートが新しいフローを通せないことがある(前述の「保証しないこと」)
- 1 回の適用の中の操作の順と、分割と統合の多数回の往復によって、無関係のルールが最低分を下回ることがある(前述の「保証しないこと」)
- 停止と重なって拒む `relay` の TCP の接続は、ホストのソケットでも RST で終わる
- 拒否の理由に `floor` と `spare` が加わる。
  `resource_refusals` の理由のキーは開いた集合なので(7a.11 節)、加算である。
  定常の状態(請求の合計が `T` 以下で、分割元が続いていない)で出る理由は `spare` と、前述の一部の構成の `rule_cap` だけになる
- 拒否のログの文言が、最低分、満たされていない最低分、予備を示す形になる。
  admin API のフィールドは増えない
