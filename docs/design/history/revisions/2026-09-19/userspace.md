# 2026-09-19: userspace

- Windows の UDP 中継をバッファなしで待つ形に修正(2026-09-19、Windows 11 実機の計測を受けて):前項で残した未確認のうち、UDP 中継のメモリ使用量を実機で測ったところ、Windows のエージェントは応答を待つ間もセッションごとに 65535 バイトを保持し続けており、UDP セッション 1 つが約 75 KiB を使うこと、既定の上限(8192 フロー)まで開くと私有メモリが約 660 MiB になり、Linux 向けの費用から計算するメモリのソフト上限(216 MiB、11a 節)を大きく超えるため GC が回り続け、既定の上限いっぱいでは 60 秒あたり CPU 21.8 秒を使うこと(`GOMEMLIMIT` を極端に大きくすると 1.6 秒まで下がる、メモリ量そのものは変わらない)が分かった。
  7 節の到着を待つ手段に、Windows のゼロバイト `WSARecv`(`MSG_PEEK` 付き)をオーバーラップ I/O で発行し完了通知で待つ経路を追加し、Windows のエージェントも Unix と同じくセッションごとのバッファを持たない形にした(`internal/agent/relay/readwait_windows.go`)。
  この経路は Go ランタイムの `RawRead`(`GOROOT/src/internal/poll/fd_windows.go`)が、渡した関数の 1 回目の `false` でゼロバイト peek を発行して待たせ、2 回目の呼び出しで `true` を返させて抜ける形を使うもので、OS スレッドは塞がない。
  あわせて、Go の net パッケージが Windows の UDP ソケットで `SIO_UDP_CONNRESET` と `SIO_UDP_NETRESET` を無効にしている(`net.Dial` で作った接続済みソケットは ICMP port unreachable を `WSAECONNRESET` として報告しない、https://go.dev/issue/5834)ことが分かった。
  この場合セッションは応答の無い相手と区別が付かず、待ち続けて無通信タイムアウト(7 節)で閉じられるだけであり、誤りとして扱う経路は追加していない。
  修正後、同じラボ構成(userspace モードの server と、この修正を入れた Windows のエージェント)で測り直し、既定の上限(8192 フロー)まで開いても私有メモリは 1 セッションあたり約 13 KiB となり、7 節で見積もっている UDP 1 セッションあたりの費用と同程度になり、CPU は 60 秒あたり 1.7 秒(修正前は 21.8 秒)まで下がることを確認した。
  メモリのソフト上限の式(12 KiB × UDP の全体上限、11a 節)と既定のフロー数上限は Windows にもそのまま当てはまるため、どちらも変更しなかった

- macOS のエージェントのメモリ使用量を測定(2026-09-19、同時フロー数の上限での確認):Apple シリコンの Mac のコンテナで server をユーザー空間モードで動かし、Mac 上の macOS のエージェントと、比較のためにコンテナ内の Linux のエージェントを、どちらも既定の上限(UDP 8192、TCP 2048)で確かめた。
  UDP のセッション 8192 件と無通信の TCP の接続 2048 本を保持した状態では、macOS のエージェントの RSS は約 130 から 140 MiB、同じ環境の Linux のエージェントは約 160 MiB で、どちらも 7 節のソフト上限(216 MiB)の内に収まった。
  保持の費用から、macOS のエージェントも UDP のセッションごとに 65535 バイトを持たず、到着だけを待つ経路を使っていることが分かった。
  保持した状態で上限を超える UDP のフラッドを加えても、macOS のエージェントは約 200 MiB に収まった。
  一方、上限を超える TCP の接続のフラッドを加えると、macOS と Linux のどちらのエージェントも約 650 から 700 MiB に達し、ソフト上限と 2026-09-18 のラボの実測の約 3 倍になった。
  この超過は macOS に固有ではない。
  macOS の `ps` の RSS は負荷が止んだ後も高いまま残ったが、物理フットプリント(`footprint`)は約 100 MB に下がった。
  macOS については設計を変えず、11a 節の未確認の点から上限でのメモリ使用量を外し、測定の結果を書いた。
  TCP の接続のフラッドでの超過は 13 節の未決事項に加えた(GitHub issue #25)。
  未確認:TCP の接続のフラッドでの超過の原因(拒んだ接続が netstack の TIME_WAIT に残ると推測している)、`vpsd` のユーザー空間モードへの影響、macOS に限り TCP の接続のフラッドの間に保持していた TCP の接続の一部が相手側から閉じられた原因
