# 2026-09-19: security

- 読み込み確認の拒否/許可リストの差分を内容で示す(2026-09-19、レビューの指摘):`equalPrefixSet` が長さと一方向の包含だけで集合を比べていたため、旧い CLI が許していた重複エントリ(同じ CIDR を 2 度持つ)がある場合に、実際には異なる集合を等しいと誤判定しうることが分かった。
  重複を払ったうえで両方向の包含を見る形に改め、`rule merge` の統合できない条件の判定と、10.1 節の読み込み確認の差分計算の両方で使う。
  加えて、拒否/許可リストの変更は Old/New に件数の文字列を持たせていたため、同じ件数のまま内容が入れ替わる変更(1 件を別の CIDR に差し替えるなど)が「変わらない」に見えていた不具合も併せて修正し、Old/New に CIDR そのものの一覧を持たせて確認ページには増減(`+198.51.100.0/24 -203.0.113.0/24` の形)を出すようにした。
  10.1 節を改訂

- プロキシモードの範囲を拒否します(2026-09-19、レビューの指摘):`vps_mode=proxy` は単一ポート運用ですが、`Rule.Validate` はそれを検査していませんでした。
  そのため、CLI・Web UI・読み込み・統合のどこからでも範囲のルールを作れてしまい、先頭ポート以外が黙って中継されない不具合につながっていました。
  `Rule.Validate` に範囲を拒否する検査を追加し、統合(範囲は隣接する 2 つを統合すると必ず 2 ポート以上になるため、常に不可)と分割(結果の両側が単一ポートになる場合だけ可)にも同じ制約を反映しました。
  ユーザー空間モード(6.3 節)でも `vps_mode=proxy` の中継は 6.2 節の `proxyrelay` を経由するため、同じ検査が両モードに効きます。
  バッチ操作(5.4 節)は変更後のルール集合全体を毎回検査するため、この検査を追加する前から保存されていた既存の範囲ルールがあると、無関係な操作まで失敗しかねません。
  これを避けるため、`proto.ValidateUpsert` を新設し、`before` と ID・内容が変わらない行は検査対象から外す形にしました。
  読み込みにも同じ除外を使います(Web UI の確認ページの扱いは次の項目)。
  5.3・5.4・6.2 節を改訂します
