# 2026-09-21: control-plane

- ルールごとの agent 側の状態を管理用 API に加える(2026-09-21、所有者の決定、5.2・7a.11 節):`rule ls` の REFUSED 列と `resource_refusals` は Resource Guard のフロー予算の拒否だけを数え、`WGFT_AGENT_ALLOW_TARGETS` によるエージェント側の宛先拒否、リスナーの開放失敗、TCP の接続確認の失敗は `agent ls` の RULES 列と Web UI にしか出ておらず(v0.5.0・v0.5.1 の Known issues)、`rule ls --json` だけを読む自動化が拒否・失敗の理由をすべて追うには `agent ls` との突き合わせが要った。
  `GET /api/v1/rules`・`POST /api/v1/rules/batch` の応答に、rule_id をキーにした `agent_rule_states`(`admin.AgentRuleStatus`。
  持ち主のエージェントが直近のハートビートで報告した `state`・`reason`、報告したエージェント名、報告日時、そのエージェントが今も接続しているか)を、`ApplyStatusBackend`・`ResourceStatusBackend` と同じ加算的な仕組み(`AgentRuleStatusBackend` を実装する Backend のときだけ加わる)で加えた。
  まだ報告が無いルールはキー自体が無い。
  持ち主のエージェントが未接続の間は、5.2 節の stream 切断時の規則どおり最後の報告のままで、`connected` を false にして区別する。
  この読み取り(登録済みエージェントの一覧)が失敗した場合は、適用状態と同じくフェイルクローズとし、応答全体を 500 にする(10.5 節)。
  人間向けの `rule ls` には AGENT_STATE 列を足し、`-`・`ok`・`error: <reason>` を、`agent ls` の RULES 列と同じ `last:` 接頭辞付きで示す。
  Web UI は変更していない。
  ルール詳細ページの適用状態(`ruleRunState`)は、以前からエージェントの直近のハートビート(`proto.RuleStatus`)を直接読んでおり、エージェント側の拒否理由も含めて正しく表示できていたため(今回の不足は管理用 API の JSON と CLI の表だけの話だった)。
  ホストの単体テストで、fake の Backend が拒否・拒否済み・全部 ok・エージェント切断後の 4 通りを報告する場合の JSON の形と、この interface を実装しない Backend(既存の `fakeBackend`、`tools/uidemo`)ではフィールドが現れないことを確かめた。
  CLI 側は `rule ls`・`rule ls --json` の両方で表示と JSON の中身を確かめた。
  v0.6.0 のリリースノートでは、v0.5.0・v0.5.1 の Known issues にあった「`rule ls` の REFUSED 列がエージェント側の拒否理由を含まない」旨を、この修正で解消したと書く

- `RuleApply.ActiveGeneration` を世代 0 と未公開が区別できる形に直す(2026-09-21、所有者の決定、7a.11 節):`rule_states[id].active_generation` は素の `uint64` で、0 を「一度も公開していない」に使っていたが、世代はルールが 1 つも無ければ 0 であり(9 節)、0 自体は届き得る値である。
  兄弟の `BatchResponse.DesiredGeneration`・`ActiveGeneration` はどちらも `*uint64` で「無い」と「0」を区別しているため、`RuleApply.ActiveGeneration` もこれに合わせて `*uint64` にし、一度も公開していないルールはキーの値自体を省く形にした。
  呼び出し元(`internal/vpsd/admin_backend.go` の `applyStatusToAdmin`)は 0 を nil に変える変換を 1 か所(`neverZero`)に持つ。
  この値を読んでいた箇所を洗ったが、CLI の表・Web UI のどちらも `rule_states[id].active_generation` を出力・参照しておらず、`lab/`・`scripts/` の中で `active_generation` を扱うのは `rule_states` の下ではなく `BatchResponse` 直下の(元から `*uint64` の)値だけだったため、直す必要のある読み手は無かった。
  ホストの単体テストで、未公開(キーが無い)・世代 0 で公開済み・世代 N で公開済みの 3 通りの JSON を確かめた

- `agent_rule_states` をルールの今の持ち主だけから引く形に直す(2026-09-21、レビュー指摘):直前の改訂で加えた `Daemon.AgentRuleStatuses` は、登録済みの全エージェントの最後のハートビートを順に調べ、ルール ID をキーに、最後に見つけたエージェントの報告で `out[id]` を上書きしていた。
  切断したエージェントは最後のハートビートの内容を保ち続ける(5.2 節)ため、この形には 2 つの誤りがあった。
  ルールが別のエージェントへ移った直後に元のエージェントが未接続のままだと、`d.st.Agents()` の行の順(名前順)次第で、移った先の生きた報告と元の古い報告のどちらが残るかが決まってしまう。
  削除したルールも、その ID を最後に報告したエージェントが未接続のままなら、ルール集合に無くなった後もキーとして残り続ける。
  直した形は、呼び出し元がその応答用に読んだ今のルール集合を順に調べ、各ルールの今の持ち主(`Rule.Agent`)のハートビートだけを見る。
  これにより、登録済みエージェントの一覧を読む必要が無くなり(呼び出し元がルール集合を渡す)、読み取りに失敗する経路そのものが無くなったので、`AgentRuleStatusBackend.AgentRuleStatuses` は誤りを返さない形に変えた。
  ホストの単体テストで、同じルール ID を 2 つのエージェント(今の持ち主と、未接続のまま同じ ID を古いハートビートに残す別のエージェント)の両方が報告する場合に、どちらを先に接続してももう一方を先に接続しても、必ず今の持ち主の生きた報告が残ることと、削除済みのルール ID が結果に残らないことを、本物の `stream.Hub` と WebSocket 接続で確かめた。
  5.2・7a.11 節に、この状態が必ずルールの今の持ち主から引かれることを明記した

- `agent_rule_states` に、報告がまだ無いルールも項目を持たせる(2026-09-21、所有者の決定):直前の改訂までは、持ち主がまだ報告していないルールのキー自体が無かった。
  これでは `rule ls --json` だけを見る自動化から、「まだ報告が無い」のか「この server(Backend)がそもそも agent 側の状態を報告しない」のかが区別できなかった。
  今あるルールは、持ち主が登録済みかどうかや報告の有無に関わらず必ず 1 件の項目を持つ形に変えた。
  まだ報告が無いときは `state`・`reason`・`at` を省き(`"unknown"` や `"pending"` のような server 発の値を新設しない。
  `state` はエージェント自身の語彙だけを持つ場所であり、既存の他のフィールドと同じ「観測していない値は省く」規則に従わせた)、`agent`・`connected` だけを持たせる。
  持ち主の名前が登録済みエージェントの一覧に無い(エージェントの削除。
  11 節)場合も、`stream.Hub` が知らない名前を引くだけなので、同じ形で `connected: false` の項目になる(`stream.Hub.Disconnect` は削除のときにその名前の記録を消し切るため、未登録の名前と削除された名前は hub から見て区別が無い)。
  ホストの単体テストで、一度も接続していないエージェントのルール(項目はあるが `state` が無く `connected` が false)と、接続中だが直近のハートビートにまだそのルールが載っていない場合(項目はあるが `state` が無く `connected` が true)の両方の JSON の形を確かめ、`rule ls` の人間向けの表は前者を `last:-`、後者を `-` と区別して示すようにした。
  5.2・7a.11 節に、`state` の有無と `connected` の組み合わせで読む 3 通りを明記した

- TCP ルールの `target` の定期的な接続確認を 5.2 節に明記(2026-09-21、ラボでの観測を受けて):5.2 節は接続確認を「適用時」と書き、30 秒ごとの再確認は `error` のルールについてだけ書いていた。
  実装は `ok` の TCP ルールも同じ周期で確認しており、ラボでは中継先に、データを伴わない TCP 接続が 30 秒ごとに届くことを観測した。
  トンネルが健全な間も、トンネルを作り直している間も同じ間隔だった。
  Windows の実機では、ネットワークアダプタを無効にすると該当のルールだけが `error` になり、回線が戻ると自動で消えることを確かめている。
  中継先から見える挙動であり、運用の上で意味を持つので、仕様として 5.2 節に加えた。
  周期の 30 秒は現在の値として書き、固定してはいない。
  挙動は変えていない

- kernel モードの一括適用が規模の大きいルール集合で丸ごと失敗する(2026-09-21、C3 規模の試験、lab/scale.sh):ルール数を 10 から 1000 まで段階的に増やしながら適用を確かめたところ、kernel モードは `internal/dataplane/linuxkernel/nft` がテーブル全体を 1 回の netlink メッセージに載せて差し替える作りのため(6.1 節)、ラボ VM の既定のソケットバッファの大きさでは、ルールが 100 本のバッチは適用そのものが失敗し、その世代のルールが 1 本も active にならないことを確かめた。
  10 本のバッチは通る。
  1 本ずつ追加した場合は 60 本前後から失敗が始まった。
  壊れ方は 2 通りで、受信側の recvmsg が ENOBUFS で失敗する場合と、送信自体が EMSGSIZE(message too long)で失敗し反映が丸ごと通らない場合がある。
  userspace モードは nftables を使わないため、同じ範囲ではこの壁に当たらない。
  設計文書は本節でも 7 節でも規模の約束をしていないため、この観測によって変える決定事項は無い。
  この変更は試験の追加だけで、適用の作りは変えていない。
  直し方と時期は未決である。
  未確認:壁の正確な本数はソケットバッファの設定とカーネルの版に依存するはずで、既定と異なる設定、別のディストリビューション(C4)、実機の VPS での値は確かめていない

- 全体状態の適用の中で失敗したトンネルの作成も試し直す(2026-09-21、所有者のレビュー、7 節):直前の改訂で入れた試し直しは、ハンドシェイクが新しくならないことによる作り直しが作成に失敗した場合だけを対象にしており、全体状態の適用(`apply`)の中で作成が失敗した場合は、次の世代が届くまでトンネルが無いままだった。
  世代は管理者がルールを変えるまで進まないので、一時的な資源の失敗 1 回で転送が長く止まりうる。
  対象を広げ、どちらの経路の作成の失敗も同じ予定で試し直すことにした。
  閾値も 1 回目は次の判定、以後は 300 秒から 900 秒までという同じ値を使う。
  合わせて 3 つを決めた。
  1 つ目は、試し直さない失敗の切り分けである。
  wg 設定が解釈できない失敗は同じ全体状態では何度作っても同じ結果になるので試し直さず、次の全体状態を待つ。
  作成そのものの失敗だけを試し直す。
  2 つ目は、試し直しが使う全体状態である。
  認証情報ファイルの `last_state` は適用を終えた全体状態しか指さないため、新しい全体状態の適用が失敗した後は 1 つ前の全体状態を指したままであり、そちらから立てるとサーバが想定していない wg 設定とルールのトンネルになる。
  失敗したときの全体状態をメモリの上に控え、試し直しはその控えから立て、成功した時点で適用を最後まで進めて処理済み世代と `last_state` を進める。
  3 つ目は、ハートビートの理由である。
  トンネルが無い理由を 4 つに分け、試し直しを待っている場合の文言は作り直しと適用で共通にした。
  `proto` の型も状態の値も変えていない。
  ホストの単体テストで確かめたことは次のとおりである。
  適用の作成を 1 回だけ失敗させると、世代も `last_state` も進まないまま試し直しが控えられ、次の判定で失敗したときの全体状態の wg 設定とルールで立ち、世代と保存がその時点で進む。
  wg 設定が誤っている全体状態では作成を試し直さず、直った全体状態が届けば立つ。
  `rotate-key` の適用の作成が失敗した場合は、新しい鍵で試し直す。
  試し直しを待っている間に停止したら何も立てない。
  未確認:ラボと実機での確認は行っていない。
  実際の `tunnel.New` の失敗(netstack の作成の失敗)は再現しておらず、失敗はテストの差し替えで起こしている

- ルールの持ち主を移すと世代が上がらない不具合の修正(2026-09-21):ルールの `agent` を別のエージェントへ変えても世代が上がらず、移す前のエージェントも移した先のエージェントも新しい全体状態を受け取らなかった。
  世代が上がるかどうかの判定が、行ごとの配る部分(`proto.AgentRule`)だけを並べて比べており、持ち主を判定の材料にしていなかったためである。
  `proto.AgentRule` に持ち主は入らないが、全体状態はエージェントごとに組み立てて持ち主の行だけを入れるので、持ち主の移動は配る内容の変化である。
  判定を、持ち主ごとにまとめた射影どうしの比較に改めた。
  エージェントに送る形は変えていない。
  5.2 節に、全体状態がエージェントごとに組み立てられることと、世代がルール集合全体に対して 1 つの値であることを追記し、5.3 節に `agent` の項目と、持ち主の移動で世代が上がることを追記した。
  ラボでは、カーネルモードとユーザー空間モードの両方で、2 台のエージェントを登録して `rule import` で持ち主を移し、修正の前と後を比べた。
  修正の前は世代が 1 のまま動かず、移す前のエージェントがリスナーを開いたままで、移した先のエージェントは開かず、公開ポートへの新しい接続が失敗した。
  修正の後は世代が 2 に上がり、移す前のエージェントがリスナーを閉じ、移した先のエージェントが開き、新しい接続が移した先を通った。
  配らないフィールド(`group`、`note`、`vps_mode`、`proxy_protocol`、接続元制限、3 つのレート)の変更で世代が上がらないことは、フィールドごとの単体テストで確かめた。
  `proto.RulesDigest` はルールの JSON 全体をハッシュするため以前から持ち主の変更を検出しており、読み込みと書き出しの流れと Web UI の確認画面の照合には影響しない。
  未確認:同じバッチの中で多数のルールの持ち主を一度に移した場合の、データプレーンの差し替えに掛かる時間
