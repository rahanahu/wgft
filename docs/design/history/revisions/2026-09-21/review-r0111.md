- 実サーバーへの経路上の ICMP が WinRingBind で WSAECONNRESET として現れるかどうかを実測する(2026-09-21、所有者の実測):直前までの改訂の記録は、この不具合の引き金が実サーバーに対する実運用でも実際に引くかどうかを未確認としていた。
  所有者の実 VPS に対し、インターネット越しに `conn.NewDefaultBind()`(`WinRingBind`)と `net.DialUDP` を並べ、生きた受信を確かめる loopback の対照試行を前後に挟んで測った。
  ループバックの閉じたポートに対しては `WinRingBind` が想定どおり WSAECONNRESET(errno 10054)を返し、対照試行も通った。
  実サーバーの閉じた UDP ポートに対しては、`WinRingBind` と `net.DialUDP` のどちらも受信せずタイムアウトし、WSAECONNRESET は現れなかった。
  対照試行は前後とも通っており、測定系が生きていたことを確かめている。
  ICMP が経路上のどこで失われているかは、この測定だけでは切り分けられない。
  VPS が拒否ではなく破棄するファイアウォールで ICMP port unreachable 自体を出していない可能性、経路上の何かが ICMP を落としている可能性、Windows がこのソケットに経路上の ICMP type 3 を反映しない可能性の 3 つが残る。
  LAN 上の別ホストが実際に ICMP を送出したことを確認済みの既知の試行(直前の改訂の記録)では、送信元が ICMP を送出したことまで確認しているため、その試行に限り「送信元が生成していない」は除外できる。
  ただし、その ICMP が経路上で失われたのか、Windows がソケットへ反映しなかったのかは、その試行でも切り分けていない。
  今回の実サーバーへの計測についても、3 つのどれかに絞り込む証明はしておらず、パケットキャプチャや昇格した権限を要する切り分けは行っていない。
  この結果は、この機構が引き金として実際に引かないことを万能に示すものではなく、この計測環境と経路では引かなかったことを示すにとどまる。

- 受信の経路が死んだトンネルをエージェントが作り直す(2026-09-21、GitHub issue #108):`device.RoutineReceiveIncoming` は `net.ErrClosed` 以外の非一時的な誤りを受けると戻り、起こし直す経路が無いため、一度止まった受信はプロセスを再起動するまで戻らない。
  既知の引き金の 1 つ(Windows の `WinRingBind` が WSAECONNRESET を上げる経路)は別の修正で塞いだが、非一時的な誤りを返す経路が他にも残りうるので、原因によらず回復する仕組みを 7 節に定めた。
  エージェントは、最終ハンドシェイクの値が 300 秒新しくならなければトンネルを作り直し、以後の間隔を 600 秒、900 秒と倍にし、900 秒を上限とし、ゼロでない新しいハンドシェイクを観測したら 300 秒に戻す。
  作り直しがトンネルの作成そのものに失敗した場合は、トンネルが 1 つも無い状態で止まらないよう、1 回目は次の判定で、以後は 300 秒から 900 秒まで広げながら作成を試し直す。
  試し直すのは作り直し自身の失敗で残った状態だけで、`rotate-key` や停止で閉じたトンネルは立て直さない。
  経過時間は、ハンドシェイクの値と現在時刻の差ではなく、その値を最初に観測してからの単調な時計での時間で測る。
  最終ハンドシェイクは壁時計の秒であり、値と現在時刻の差で測ると、NTP の補正や手動の変更による 155 秒以上前への飛びが、健全なトンネルを 300 秒古く見せてしまうためである。
  判定と作り直しはエージェントの本体が行い、トンネルの package の役割も wire の型(`proto.TunnelStatus`)も変えていない。
  issue の本文は転送量(rx/tx)をハートビートに載せる必要があると見ていたが、受信が死ねばハンドシェイクは永久に成立しないので、ハンドシェイクの時刻だけで判定できる。
  閾値の根拠は 7 節に書いたとおりで、健全なトンネルの最終ハンドシェイクが 145 秒より古くならないことと、180 秒を過ぎた鍵が送信にも使えないことによる。
  ホストの単体テストで確かめたことは次のとおりである。
  受信の関数が非一時的な誤りを返すバインドに差し替えて受信の goroutine を実際に終わらせたトンネルは、エンドポイントの引き直しとトンネル内への ping を繰り返しても戻らず、同じ鍵とエンドポイントで立て直したときだけ戻る。
  サーバに届かないエージェントは、間隔を広げながらトンネルを作り直し、古いトンネルを置き換えの前に閉じるので、閉じた後の goroutine は基準値へ戻る。
  サーバを止めてから同じ鍵とポートで戻すと、作り直したトンネルがハンドシェイクを済ませ、中継のリスナーも開き直り、間隔は初期値に戻る。
  判定そのものは、値が更新され続ける健全なトンネル、壁時計が前後どちらへ飛んだ場合、値が 1 時間古く見えるが観測したばかりの場合、作り直しをまたいで値がゼロのままの場合、一度も成立していないトンネル、バックオフの上限、新しい値の観測による間隔の初期化を、合成した時刻で別に確かめた。
  作成の失敗については、1 回だけ作成を失敗させて、トンネルの無い状態が残ること、次の判定で試し直して成功すること、リスナーが開き直り、新しいハンドシェイクで間隔と試し直しの予定が初期の状態に戻ることを確かめた。
  意図して閉じたトンネルと、試し直しを待っている状態で閉じたトンネルを、どちらも立て直さないことも確かめた。
  バインドの差し替え口はテストのためだけに `internal/dataplane/userspace/tunnel` へ加えた非公開の変数で、既定の値は GOOS ごとの選択(7 節)のままである。

- kernel モードのバッチを netlink のバッファに合わせる(2026-09-21、C3 規模の試験が見つけた未決の問題の解決):上の「kernel モードの一括適用が規模の大きいルール集合で丸ごと失敗する」の項が未決としていた、kernel モードの適用が 100 本前後のルールで丸ごと失敗する問題を直した。
  原因は、テーブル全体を 1 つの netlink のデータグラムとして送る作り(6.1 節)と、既定のソケットバッファの組み合わせである。
  `github.com/google/nftables` v0.3.0 の `Conn.Flush` は、バッチ全体を 1 回の `SendMessages` で送ってから、1 通ずつ応答を読み出す。
  カーネルはバッチの 1 通ごとに ACK を返し、同じライブラリがルールの追加に必ず `NLM_F_ECHO` を立てるのでルールの写しも返る。
  応答は送り終えるまで読み出されないため受信キューに積み上がり、既定の 212992 バイトを超えた時点でカーネルが ENOBUFS を立てて応答を捨てる。
  ホストでバッチを組み立てて数えたところ、ルール 1 本が 2 通(接続元ごとの同時フロー数の行と DNAT の行)で約 1264 バイトを占め、100 本のバッチは 217 通、129124 バイトになる。
  ACK と写しを合わせた応答は既定のバッファに収まらない。
  1 本ずつ追加したときに 60 本前後から失敗が始まったことも同じ計算で説明でき、137 通、78564 バイトのバッチに対する応答が既定のバッファをちょうど超える。
  160 本を超えるとバッチ自身が `sk_sndbuf` を超え、sendmsg が EMSGSIZE で拒む。
  直し方は、テーブルを組み立てながらバッチのメッセージ数と長さを数え、送る直前に `SO_SNDBUFFORCE` と `SO_RCVBUFFORCE` でソケットのバッファをその大きさに合わせる形である。
  `nft` コマンド自身も同じ手順を取ることを nftables 1.0.6 の `src/mnl.c` で確かめた。
  バッチを複数のデータグラムに分ける案は採らなかった。
  カーネルの `nfnetlink_rcv_batch` は 1 つの skb の中だけでバッチを読むので(Linux 6.1 の `net/netfilter/nfnetlink.c`)、分けた時点で別のトランザクションになり、差し替えの不可分性を失う。
  ラボで確かめたことは次のとおりである。
  1 回の `rule import` による 1000 本のルールが適用でき、10 本から 1000 本までのすべての段で転送が通る。
  1 本ずつの `rule add` でも 1000 本まで失敗が無い。
  修正の前は、100 本のバッチが ENOBUFS で失敗し、1 本ずつでは 100 本のうち 41 本が失敗していた。
  ENOBUFS で失敗したときの壊れ方も分かった。
  カーネルは応答を送る前に commit を終えているので、テーブルは差し替わっているのに `vpsd` は失敗と判断する。
  修正前の測定で、100 本のバッチが失敗した後のテーブルが 100 本分の行を持っていたことを `nft list` の行数から確かめた。
  この食い違いは 7a.3 節の収束が拾うので、別の仕組みは設けない。
  EMSGSIZE の場合はカーネルに何も届かず、旧いテーブルがそのまま残る。
  未確認:1000 本を超える規模、既定と異なる `net.core.rmem_max` と `net.core.wmem_max` を持つ配置、user namespace を分けたコンテナでの実測(FORCE が init の user namespace の CAP_NET_ADMIN を要することは Linux 6.1 の `net/core/sock.c` の `sockopt_capable` で確かめたが、その配置では動かしていない)、別のディストリビューションと別のカーネルの版での壁の位置、ENOBUFS の後に 7a.3 節の収束が実際に旧い世代を公開し直すまでの経路。
