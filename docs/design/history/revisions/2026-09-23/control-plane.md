# 2026-09-23: control-plane

- `stream.connection` が示す理由の範囲を広げ、その記述の誤りを正した (2026-09-23):制御ストリームの観測を実装したところ、理由の欄に入るのは `internal/agent/stream.go` の `streamOnce` が返す誤りそのものであり、接続が切れた理由だけでなく、接続に至らなかった試みの失敗も同じ欄に入ることが分かった。
  10.2c 節の `stream.connection` の行と段落は切断の理由だけを挙げていたので、接続に至らなかった試みの失敗を含む形に広げた。
  理由を 2 つの欄に分けると `agent doctor` の側で合成することになり、運用者が読む「今つながっていない理由」は 1 つで足りるためである。
  この決定を最初に書いたときの記述には誤りがあった。
  接続に至らなかった試みの例として「server に断られた登録」を挙げていたが、登録の失敗はこの欄に入らない。
  登録を呼ぶ経路は 3 つあり、いずれも `streamOnce` の外にある。
  初回登録の `ensureRegistered` は `runtime` を組む前に走って常駐プロセスの起動を止め、認証の拒否からの再登録 `rt.recover()` は `streamLoop` の戻り値になって常駐プロセスを止める。
  ピンの不一致からの再登録も同じ `rt.recover()` を `streamLoop` が呼ぶが、失敗しても常駐プロセスは止めず、ログを出して次の待ちに入るだけで、そのとき観測に残る理由は `ErrPinMismatch` のままである。
  実際に入る接続に至らなかった試みの失敗は 4 種類で、`agent.json` の `cert_sha256` が不正な場合、dial の失敗、`stream authentication rejected: the permanent token may have been revoked` として返る stream の認証の拒否、そして dial の後に公開鍵を送る `writeJSON` の失敗である。
  10.2c 節の本文はこの形に直した。
  未確認:3 つの登録の経路と 4 種類の失敗はどれもコードを読んで確かめただけで、ラボと実機では確かめていない。

- `stream.backoff` が示す値を、実装が記録する値に合わせて言い直した (2026-09-23):10.2c 節の検査の表と `stream.connection` の段落は、`stream.backoff` が示すものを「再接続の間隔の現在値」と書いていたが、`internal/agent/streamobs.go` の `streamObservation` が保つのは直近に待った間隔である。
  食い違う理由は 2 つある。
  第 1 に、`internal/agent/stream.go` の `streamLoop` は間隔を倍にする `backoff *= 2` を待ちの後に置くので、次の試みの間じゅう記録はローカル変数の倍加の前の値である。
  第 2 に、ローカル変数を初期値に戻す 5 か所のうち 4 か所は `continue` するので、記録を書く `noteStreamWaiting` を通らない。
  残る 1 か所(1 分以上つながっていたなら次の失敗はバックオフを最初からという経路)は `continue` せずに下へ落ちるので、この経路の変更はそのまま次の `noteStreamWaiting` に載る。
  例を挙げる。
  障害の間に間隔が 5 分まで伸びた後、WireGuard の新しいハンドシェイクが待ちを打ち切って接続が成立すると、その接続が続く間ずっと記録は 5 分のままである。
  表の記述と実装のコメントを、直近に待った間隔という事実に合わせた。
  記録の側を毎回そろえる案は採らなかった。
  そろえるには、倍加の後と、初期値に戻す 5 か所のそれぞれに記録を足すことになり、変えないと決めた再接続の経路に手を入れることになる。
  読み手から見た実害も限られる。
  待っている間の値は待つ間隔そのもので正しく、つながっている間は次に試す時刻がゼロなので、待っていないことは読み手に分かる。
  同じ日の「制御ストリームの観測を `runtime` の保持に加えた」の項にあった「再接続の間隔の現在値」という記述も、同じ言葉に直した。
  未確認:コードを読んで確かめただけで、ラボと実機では確かめていない。

- `rule.probe` と `agent.connection` の次の一手を UDP のルールで直した(2026-09-23):「Web UI の診断の画面の案内を、画面から実行できる形に揃えた」の改訂の記録が、UDP のルールについては共有の文そのものが CLI でも実行して意味のある案内になっておらず、この版では扱わないと記した点を、この版で解決した。
  `rule.probe` は、疎通の確認を試していない実行に `--probe` を付けるよう次の一手で案内してきたが、UDP のルールでは管理用 API が確認そのものを拒むため(10.2a 節、UDP の送信では成否が分からない)、この案内は意味を持たない。
  同じ案内は `agent.connection` の次の一手にもあった。
  制御の接続は切れているがトンネルの最終ハンドシェイクは新しい場合に、疎通の確認を試すよう勧める文を付け加えていたが、これも UDP のルールには当たらない。
  直し方は、UDP のルールでは `--probe` を勧めず、管理用 API が確認を拒んだ後の実行に返す文「target の行から判断し、サービスそのものは実際のクライアントから確かめる」を、試す前の実行にもそのまま使う形にした。
  試す前の実行と、既に拒まれた後の実行とで、UDP のルールについては同じ文になる。
  `agent.connection` の次の一手も、同じ文をそのまま繰り返す形にした。
  同じ事実を 2 つの文言で述べないためである。
  Web UI の `rule.probe` に添えていた画面の側の 1 文(`doctorProbeUDPNote`、上記の改訂で加えたもの)は、共有の次の一手がもう `--probe` を勧めなくなったことで役目を終えたので削った。
  共有の文が、添えていた 1 文と同じ内容(target の行から判断し、実際のクライアントで確かめる)を言うようになったためである。
  UDP のルールに疎通の確認のボタンが無い理由は、Probe の節の `doctorProbeUnavailable` が別に説明しており、これは変えていない。
  同じ案内は「試していない範囲」の内側の経路の項目にもあった(10.2a 節)。
  `--probe` は 1 本のルールにしか付けられないが、引数の無い実行や Web UI の一覧は複数のルールを一度に診断するので、診断の対象がすべて UDP のルールである実行でだけ、この項目自体を出さない形にした。
  1 本でも TCP のルールが混じっていれば、そのルールには `--probe` が意味を持つので出す。
  同節の「UDP の端から端まで」の項目が同じ事実を既に述べているので、2 つの項目が違う理由を挙げる形を避けた。
  `checks[].id`・`reason`・`status` だけが 10.2a 節の機械向けの保証であり、`not_tested[]` の要素はその対象に含まれていないので、UDP のルールだけの実行で `not_tested` から inner path が 1 件消えることも、`checks[].next` の文言が変わることも、互換性を破らない。
  未確認:実機では確かめていない。
  ラボの結合テストの一式は、マージ前に監督が流す。

- ルールの詳細ページの設定を 1 つの保存ボタンにまとめた(2026-09-23、所有者の決定):詳細ページは group と note、レート制限をそれぞれ別のフォームで保存しており、同じ「保存」のボタンが 2 つあった。
  group を書き換えた後にレート制限の側の保存を押すと、group の書き換えは知らせずに捨てられていた。
  区画を設定、アクセス制御、ルール操作の 3 つに組み直し、設定の区画を 1 つのフォームと 1 つの保存ボタンにした。
  1 つのフォームにすると、ページを開いた後に CLI で変えたレートを、説明だけを変えた保存が描いた時点の値で上書きしうる。
  これを防ぐため、描いた時点の保存値を hidden で持たせ、利用者が変えた欄だけを当てはめ、変えた欄が別の経路でも別の値に変わっていれば保存せずに示す形にした。
  Web UI のルートは 7a.11 節の保証の外なので、`/ui/rules/{id}/meta` と `/ui/rules/{id}/rates` は `/ui/rules/{id}/settings` の 1 つに置き換えた。
  10.1 節を改訂

- エージェントの行を有効なルールの検査から作るようにした(2026-09-23、独立レビューの指摘):`server doctor` の一覧の Agents の行は、エージェントを名指すルールのうち最初のルールの `agent.connection` を写していた。
  そのルールが無効だと、写す検査は `rule_disabled` の skipped であり、エージェントの状態を述べないのに、行は `SKIPPED rule_disabled` と出ていた。
  エージェントに属する検査は、有効なルールであればどのルールにも同じ値で入るので、有効なルールの検査を先に採り、有効なルールが無いときだけ最初の検査を使う形に直した。
  Web UI の診断の画面のエージェントの行も同じ関数を読むので、CLI と画面の行が揃う。
  `--json` の出力は変わらない。
  `checks[]` はルールごとの検査をすべてそのまま載せており、エージェントの行はそこから人向けの出力のために選んで作るだけで、JSON のどのフィールドにも入らないためである。
  CLI の単体テストで、無効なルールを先に置いた場合に行が OK になることを確かめた。

- `AgentCheck` の、エージェントを名指すルールがすべて無効な場合の分岐に単体テストを加えた(2026-09-23、独立レビューの指摘):「エージェントの行を有効なルールの検査から作るようにした」の改訂の記録は、有効なルールを優先して採ることは確かめていたが、有効なルールが 1 本も無く最初の検査へ落ちる分岐は単体テストが無かった。
  この分岐は `TestAgentCheckFallsBackToFirstWhenEveryRuleIsDisabled`(`internal/vpsd/doctor/doctor_test.go`)で固定した。
  あわせて、同じ改訂の記録の「有効なルールであればどのルールにも同じ値で入る」という記述を正す。
  `Check` は `RuleID` を持つのでルールごとに違う値もあり、実際に揃うのは `Status` と `Reason` である。
  確かめ方:`if first != nil { return *first, true }` を削り常に `Check{}, false` を返す変異を入れ、新設の単体テストが落ちることを確かめた。
