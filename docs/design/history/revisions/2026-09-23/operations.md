# 2026-09-23: operations

- 起動の保留をラボの実カーネルで確かめ、11b 節の転送の記述を直した(2026-09-23):保留はホストの単体テストでしか確かめていなかったので、使い捨ての VM で本物のカーネルに対して通した。**
  確かめられたことは次のとおりである。**
  適用が失敗しても 151 本の宣言はサーバのデータベースに残り、すべて `pending` として報告された。
  その状態で再起動すると、プロセスは終了せずに保留へ入り、`startup hold:` の行が 1 行だけ出て、起動完了の行は出なかった。
  保留の間、管理用 API は `rule ls`、`status`、`server doctor` のいずれにも応答し、`status` は Server 行を degraded、Rules 行を 151 本とも degraded として終了コード 1 で終わった。
  エージェント用 API は待ち受けておらず、接続は拒まれた。
  `rule rm` で宣言を小さくすると同じ秒のうちに保留が解け、エージェント用 API が開き、起動完了の行が出て、UDP の通しの転送が実際に通った。
  30 秒の再試行を待たずに解けることを確かめられた。**
  確かめられなかったことは次のとおりである。**
  30 秒ごとの再試行が周期的に動いていること自体は、理由が変わらない限りログを出さない規則のために観測できなかった。
  systemd の unit ではなく前面で実行したので、journal 経由の行は見ていない。**
  そのうえで、11b 節の転送の記述の誤りが見つかった。**
  「前回公開した宣言のまま転送を続ける」と書いていたが、これが成り立つのは適用の失敗が送信の側で起きた場合だけである。
  動いていたルールを含まない 150 本を読み込ませて `ENOBUFS` を起こすと、そのルールはカーネルのテーブルから消え、直前まで通っていた転送が実際に壊れた。
  保留の最中でも同じであった。
  失敗として報告された新しい宣言が、実際にはカーネルへ commit されていたためである。
  これは 6.1 節が受信側の壁として既に書いている挙動で、応答はバッチの commit の後に送られるので、テーブルが差し替わっているのに失敗と判断する。
  対照として、同じ構成で 700 本を読み込ませると失敗は `EMSGSIZE` に変わり、送信そのものが届かないためテーブルは本当に旧いまま残り、転送も続いた。
  保留が引き継いでいるのは、どちらが起きたかを `vpsd` が言い分けられないという 6.1 節の性質である。
  11b 節の転送の項と、`docs/manual/setup.md` の日英、`server run` のヘルプ、保留の行の文言を、どちらとも言い切らない形に改めた。**
  再現の条件について注意がある。**
  6.1 節が記録している「125 本で `ENOBUFS`」という実測値は、`SO_SNDBUFFORCE` と `SO_RCVBUFFORCE` が拒まれる環境の値である。
  root で動く通常の配置ではこの 2 つが成功するので受信の buffer は大きく、`ENOBUFS` の壁は数千本の側へ遠ざかる。
  その配置でどちらの壁に先に届くかは実測していない。
  受信側には 1 通ごとの ACK の分を上乗せして要求し、応答にはルールの写しも載るので(6.1 節)、受信側が先に届く可能性を否定できない。
  未確認である。
  今回は壁を再現するために、ラボの vps の netns の中にさらに user namespace を入れ子にして FORCE を拒ませた。
  ラボの正式な手順ではない。
