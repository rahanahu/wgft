# 2026-09-23: web-ui

- Web UI の doctor の骨組みをラボで動かし、設計に要る事実を取った(2026-09-23):`agent doctor` の設計(10.2c 節)は、実装に触れずに文章だけで詰めたため、独立レビューが何巡も要った。
  そこで Web UI の doctor は、設計節を書く前に使い捨ての骨組みをラボで動かし、事実を取る順序にした。
  骨組みは `internal/vpsd/admin` に一時的に足し、ラボの VM の中で server とエージェントを動かして確かめたもので、リポジトリには残していない。
  分かったことを挙げる。
  第 1 に、`internal/vpsd/admin` は `server doctor` が読む証拠のすべてに同じプロセスの中で届く。
  `s.backend` を直接呼べばよく、健全な状態と、エージェントを止めた状態の両方で、CLI 経由と同じ値が取れた。
  前例もあり、Web UI の接続テストのボタンが `s.backend.CheckConnectivity(id)` を同じプロセスの中で呼んでいる。
  第 2 に、`cmd/wgft` の報告を組み立てる部分は `internal/vpsd/admin` からは呼べない。
  `cmd/wgft` が既に `internal/vpsd/admin` を import しているので、逆向きは import の循環になる。
  規約ではなく Go の言語の制約である。
  第 3 に、`internal/dataplane/deps_test.go` の検査は `cmd/wgft` と `internal/vpsd/admin` の関係に触れていない。
  診断の仕組みをどこに置くかは 7a.7 節のどの規範にも抵触しない。
  第 4 に、エージェントが落ちている状態で `POST /api/v1/rules/{id}/check` を呼ぶと、応答に約 5 秒かかった。
  10.2 節が既に書いている、server 側の dial の期限が既定 5 秒であることと符合する。
  第 5 に、i18n はぶつからない。
  短いラベルは日英で切り替え、証拠になる自由文は英語のままにするという書き分けが、接続テストの結果とルールの状態表示に既にある。

  ラボでは落とし穴にも当たった。
  `lab/lab exec home pkill -x wgft` は VPS の server まで落とす。
  network namespace は PID を隔てないためである。
  `ip netns pids <ns>` で PID を特定する方式に切り替えて解決した。
  同じ注意は [lab/README.md](../../../../../lab/README.md) にある。

  `--from` と UDP のルールでの違いも再現しておらず、TCP のルール 1 本だけで確かめた。

- Web UI の診断の画面を実装し、節が実装に委ねていた細部を決めた(2026-09-23):10.2d 節は骨格だけを固定し、画面の構成、表示の文言、検査の並べ方を実装のときに確定すると定めていた。
  次のように決めた。
  画面は 2 枚である。
  `/ui/doctor` は server、エージェント、全ルールを 1 行ずつ出し、`/ui/doctor/{id}` は 1 本のルールを公開側から宛先まで順に出す。
  CLI の引数の有無による 2 つの粒度(10.2a 節)と同じ分け方である。
  検査 1 件は、見出し、状態、所見、切り分けられない原因、次に見るものの順に 1 つの行として出す。
  この 5 つは判定がそのまま持っているので、画面は判定を作り直さない。
  既定で隠す検査は落とさず、折りたたんだ区画に入れる。
  CLI の `--verbose` と同じ判定を共有する。
  wgft 自身を追うときだけ要る値も、行ごとの折りたたみに入れる。
  疎通の確認は 1 本のルールの画面にボタンとして置き、押した実行だけが `?probe=1` として dial する。
  入口はダッシュボードの見出しとルール詳細ページの 2 か所である。
  実装のときに分かった事実を挙げる。
  第 1 に、試していない範囲と履歴の文は CLI と同じものをそのまま出しているので、画面にも `--probe` という CLI のフラグの名前が出る。
  画面には同じことをするボタンがあるため、文を画面用に書き換える案も検討したが、CLI と画面で同じ事実を違う文で語ると、どちらが正しいかを読み手が確かめられなくなるので採らなかった。
  第 2 に、エージェントの stream が切れていてトンネルも古いルールは、経路の順でトンネルが先に来るので、画面の結論も `traffic stops at "WireGuard"` になる。
  エージェントの行が FAILED であっても、止まった位置はトンネルである。
  第 3 に、`agent.connection` が unknown かつ理由が `agent_disconnected` のときだけ画面の語を DEGRADED にする規則(10.2a 節)は、CLI と Web UI が同じ 1 つの関数を共有する。
  画面の語と JSON の値が食い違う箇所を 2 つに増やさないためである。
  第 4 に、判定が持つ所見の文は CLI のために書かれているので、画面にはそのままでは実行できない案内が残る。
  2 か所ある。
  一覧の画面の inner path の行は `--probe` を付けるよう案内するが、この画面にボタンは無い。
  ルールごとの画面へ進めば押せることが画面から読めるよう、一覧のルールの表に画面の語として 1 文を添えた。
  もう 1 か所は、1 本のルールの画面の `rule.source_filter` が `--from <アドレス>` を付けるよう案内する行であり、接続元を入力する欄が画面に無い。
  この版では直さない。
  欄を足すことは、画面から管理用 API を呼び直す新しい操作になるので、別に決める。
  変異を入れて確かめた範囲も記す。
  画面を開いたときに疎通を試す形、ラベルと状態の語を日本語に切り替える形、鮮度の判定を 1 つずらす形、エージェントの誤りを failed から unknown にずらす形、次に見るものを画面から落とす形、同じプロセスの中の証拠から報告を 1 つ落とす形、経路の順を逆にする形、隠した検査を画面から落とす形の 8 つを試し、いずれも単体テストが落ちることを確かめた

- Web UI の診断の画面の案内を、画面から実行できる形に揃えた(2026-09-23):10.2d 節の改訂の記録は、判定が持つ所見が CLI のために書かれているため、画面にはそのままでは実行できない案内が残ると記していた。
  そのうち 1 本のルールの画面の `rule.source_filter` は `--from <アドレス>` を付けるよう案内するが、接続元アドレスを入力する欄が画面に無い。
  次のように決めた。
  共有の文は書き換えず、画面の側に 1 文を添える。
  一覧の画面の疎通の案内が既にこの形であり、同じ形に揃えた。
  添える文は、画面に入力欄が無いことと、`sudo wgft server doctor <ルールの ID> --from <接続元アドレス>` という実行の形を示す。
  ルールの ID は 1 本のルールの画面の先頭に出ているので、運用者は読み取った値をそのまま打てる。
  採らなかった案は 2 つである。
  共有の文を CLI でも画面でも読める形に書き直す案は採らない。
  この文は `server doctor --json` の `checks[].next` にも出る値であり、機械向けの出力から画面の都合で語を薄めることになるためである。
  その検査だけ画面用の文を持たせる案も採らない。
  同じ事実を 2 つの面で違う文にすると、どちらが正しいかを読み手が確かめられなくなるためである。
  入力欄は設けない。
  欄を設けることは画面から管理用 API を呼び直す新しい操作になるという前の版の判断を保つ。
  実装では、画面の側の 1 文を検査ごとに持てる形にし、`rule.source_filter` が接続元アドレスを与えられずに not_tested になったときだけ出す。
  他の検査も同じ観点で見直した。
  `rule.probe` は、疎通の確認を試していない実行で `--probe` を付けるよう案内する。
  有効な TCP のルールの画面には疎通の確認の見出しとボタンがあるので、添える文を要しない。
  UDP のルールの画面にはボタンが無く、管理用 API も UDP のルールの確認を拒むので、同じ仕組みで 1 文を添える。
  添える文は、UDP のルールでは疎通の確認を実行できないことと、target の行から判断し、サービスそのものは実際のクライアントから確かめることを示す。
  後半は、CLI で UDP のルールに `--probe` を付けたときに判定が返す次の一手と同じ内容である。
  無効なルールの `rule.probe` は `--probe` ではなくルールの有効化を案内するので、当たらない。
  ここから分かった事実もある。
  UDP のルールについては、共有の文そのものが CLI でも実行して意味のある案内になっていない。
  `--probe` を付けても管理用 API が拒むためである。
  共有の文を直すと CLI の出力が変わるので、この版では扱わない。
  `--verbose` を案内する行は、既定で隠す検査の折りたたみと行ごとの折りたたみが画面の側の同じ手段になっている。
  `re-run this command` と書く行は、画面では再読み込みに当たる。
  節の本文は変えていない。
  画面の文言は節が実装のときに確定すると定めた範囲であり、7a.11 節も Web UI の文言を保証の対象にしていないためである。

- Web UI の診断の画面に経路の図を加えた(2026-09-23、所有者の決定):一覧の画面と 1 本のルールの画面に、ルールの経路を節点の図として出す。
  判定と `--json` は変えず、図は `internal/vpsd/admin` の中で判定の値を写すだけにする。
  決めたことを挙げる。
  第 1 に、ルールの節点は `public port`、`WireGuard`、`agent`、`listener / target` である。
  `public port` には `rule.enabled`、`rule.public_port`、`rule.source_filter` が入る。
  インターネットの側を観測する検査は無く、`rule.public_port` は正常なときも `not_tested` を返すので、インターネットと VPS を別の節点に分けない。
  分けて VPS を OK と描くと、`not_tested` を画面だけで読み替えることになり、JSON と画面の食い違いが DEGRADED のほかにもう 1 つ増える。
  `WireGuard` には `tunnel.handshake`、`agent` には `agent.connection` と `agent.rules_received` が入る。
  第 2 に、listener と target は 1 つの節点にまとめ、`rule.target_resolve`、`rule.target`、`rule.probe` を入れる。
  分けるには `rule.target` の reason で振り分ける表が要る。
  `target_not_allowed` のときにエージェントがリスナーを開くかどうかは未確認で、振り分けの根拠が揃っていないので、ラボで確かめるまで分けない。
  第 3 に、節点の状態は中の検査の最も悪いものとし、順序を failed、unknown、skipped、not_tested、ok とする。
  not_tested を ok より悪くするのは、試していない検査を含む節点を OK と描かないためである。
  表示のための読み替えを 2 つだけ持つ。
  `rule.probe` の not_tested は節点に数えない。
  数えると、疎通の確認を押していない TCP のルールの宛先が常に NOT TESTED になるためである。
  UDP のルールの `rule.target` の ok は、節点では not_tested として数え、「リスナーは開いているが UDP の宛先は試していない」旨を添える。
  UDP の ok はリスナーが開いたことしか意味しないので、宛先を確かめた形に描かない。
  検査の行には元の OK がそのまま残る。
  第 4 に、`StoppedAt` の検査が入る節点を止まった節点とし、それより後ろの節点は中の状態を問わず「届いていない」と描く。
  代替テキストには、止まった後ろなので状態を出していないことと、中の検査の元の状態を併せて書く。
  無効なルールは、すべての節点を「届いていない」と描き、`enabled / rule_disabled` の札を付ける。
  止まった節点の札は、既存の検査の見出し、reason、観測からの経過の時間から作り、新しい短文の表は持たない。
  第 5 に、`server.dataplane` は節点に入れない。
  ルールの検査ではなく `StoppedAt` にも入らないので、入れると行の状態と図が食い違う。
  一覧の画面では Server の行に、1 本のルールの画面では OK でないときだけ図の上の帯に出す。
  第 6 に、エージェントの行は `tunnel`、`stream`、`rules` の順に `tunnel.handshake`、`agent.connection`、`agent.rules_received` の状態をそのまま出す。
  エージェントには `StoppedAt` が無いので、「届いていない」への置き換えも集約もしない。
  3 つの検査は、そのエージェントを名指す有効なルールの検査から採り、有効なルールが無いときだけ最初のルールの検査を使う。
  CLI の Agents の行と同じ関数で選ぶので、画面と CLI の行は同じ検査を読む (次の項目)。
  3 つの検査の所見、切り分けられない原因、次に見るもの、内部の値は行ごとの折りたたみに入れ、どれかが OK でない行では既定で開く。
  ルールが WireGuard で止まると 1 本のルールの画面の agent の節点は「届いていない」で閉じるので、エージェントの次の一手は一覧の画面で読めるようにする。
  第 7 に、状態の図形は OK が円、FAILED が八角形、UNKNOWN と DEGRADED がひし形、NOT TESTED が点線の円、届いていないものが小さな中空の円、止まった節点より手前の SKIPPED (未登録のエージェントのトンネルなど) が横棒の入った中空の円であり、色だけに意味を頼らない。
  無効なルールの `enabled / rule_disabled` の札は、宣言どおりの状態であって故障ではないので、FAILED の色で描かない。
  図は CSS で描き、JavaScript も文字の罫線も使わない。
  記号は読み上げから外し、各節点の読み上げ用の文と title に英語の状態の語を入れる。
  第 8 に、一覧の画面は状態、ルール、縮めた図の 3 列にし、節点の名前は表の見出しに 1 回だけ出す。
  行の図は 1 本のルールの画面へのリンクで、これまでの所見の文は行ごとの折りたたみに移した。
  1 本のルールの画面は図を先頭に置き、その下に節点ごとの折りたたみを並べて、中に検査の行をこれまでどおり出す。
  止まった節点と UNKNOWN の節点は既定で開く。
  節点に入らない検査は「経路の外の検査」の折りたたみに入れ、dataplane の帯が出ているときは既定で開く。
  確かめたことを記す。
  図の規則は、判定の入力を組んで `BuildReport` を呼ぶ単体テストで、止まった節点だけが FAILED で後ろがすべて「届いていない」であること、UNKNOWN の行に FAILED が無く UNKNOWN が 1 つ以上あること、OK の行にどちらも無いことを、仕様の形で確かめた。
  止まった後ろの置き換え、UDP の宛先の読み替え、状態の重さの順序、dataplane を節点の外に置くこと、代替テキストが元の状態を持つことなど、規則ごとに変異を入れ、いずれも単体テストが落ちることを確かめた。
  画面は開発用のデモ (`tools/uidemo`) で、日英、広い幅とスマートフォンの幅、明暗の配色を目で確かめた。
  未確認の点を挙げる。
  ラボと実機の server での表示は確かめていない。
  表示は Firefox でしか確かめていない。
  狭い幅で止まった後ろの縦の線を点線にする CSS は `:has()` を使うので、それを持たない古いブラウザでは実線になる。
  `target_not_allowed` のときにエージェントがリスナーを開くかどうかは未確認で、listener と target を分けるかどうかはその確認を待つ。
