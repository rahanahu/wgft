- `agent doctor` の設計をさらに 3 点直した(2026-09-23、所有者の決定):第 1 に、稼働の判定を読み取りだけに改めた。
  `agent.process` が使う `credentials.IsLocked` は `internal/flock` の `Acquire` を呼び、`Acquire` は `os.OpenFile` に `os.O_CREATE` を渡すため、ロックファイルが無いホストで `agent doctor` を実行しただけでロックファイルが作られる。
  エージェントを root で動かす配置で root が診断を実行すると、後から非特権で動くエージェントがそのロックファイルを開けず起動できなくなる実害があるため、ロックファイルが既にある場合だけ開いて状態を見る形に改め、無ければ作らずにエージェントが一度も起動していない事実として扱う。
  実装のときは `internal/flock` に読み取り専用の入口を足す必要がある。
  ロックファイルが無い場合の `agent.process` は、既存の「停止そのものは FAILED として扱う」規則のとおり FAILED とする。
  第 2 に、`tunnel.local` の判定を、`heartbeat` が組み立てる `proto.TunnelStatus` の理由のうち、トンネルが無い場合の残る 2 つ、`no tunnel` と `no tunnel; building it failed` にも広げた。
  `no tunnel` は、`rotate-key` や停止でトンネルを閉じた直後など正常な遷移でも生じるため UNKNOWN とし、FAILED にすると一過性の状態を故障として扱う問題が戻る。
  `no tunnel; building it failed and will be retried` と `no tunnel; building it failed` はどちらもトンネルの構築が実際に失敗した事実を指すので FAILED のままとし、UNKNOWN に弱めると本当に壊れている場合まで見分けが付かなくなる。
  この時点で `proto.TunnelStatus` が `error` になる理由の文字列は、トンネルが無い場合の 4 つとハンドシェイク待ちの 1 つを合わせて 5 つになった。

  19 個すべての細かい符号を実装もテストも無い段階で先に固定すると、機械向けの仕様だけが過剰に固まるためである。
