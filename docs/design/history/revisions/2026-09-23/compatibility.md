# 2026-09-23: compatibility

- v1.0 までの内部構造の固定が終了した(2026-09-23、v1.0.0 のリリース):上の「移行の完了後の構造の点検と、v1.0 までの内部構造の固定」の項(2026-09-21、7a.7 節)が定めた固定は、v1.0.0 のリリースで終了した。
  終了後も効く制約は [CLAUDE.md](../../../../../CLAUDE.md) の「内部構造の固定の終了後も効く制約」に置く。
  v1.0 以降に内部構造をどう扱うかの方針は、この改訂では定めていない。

- 一発実行のコマンドの終了コードを v1.0 の互換性の保証に入れた(2026-09-23、所有者の決定):7a.11 節の横断する規則は「終了コードの意味の仕様は 11b 節で定める」と書いていたが、11b 節が定めるのは常駐プロセスの起動の失敗だけであり、一発実行のコマンドの終了コード 2 に言及が無い。
  実際の定めは複数の節に散っている。
  11b 節が常駐プロセスの起動を、10.2a 節が `server doctor` を、10.2b 節が `status` を、10.2c 節が `agent doctor` を、11a 節が `rule add` と `rule set` の `--dry-run` を定めている。
  さらに `rule ls`、`agent ls`、`server check` のように、どこにも定めが無いコマンドのほうが多い。
  これらは 10.5 節の「管理用 API の 5xx は 0 以外の終了コードで止まる」という規則しか持たず、値が 1 であることはどこにも書いていない。
  そこで規則を書き直し、どのコマンドの終了コードがどの節で定まるかを示した上で、定めが無いコマンドについては成功が 0、失敗が 0 以外であることだけを保証することにした。
  理由は 2 つの向きから来る。
  v1.0 以降に CLI の機械向けの挙動を保証するなら、一発実行のコマンドだけが保証の外にある状態は不自然である。
  一方、これまで意味を定義していないコマンドまで今から値を固定する必要も無い。
  今の実装がこの保証に反していないことを確かめた。
  `cmd/wgft/main.go` の `os.Exit(exitCode(err))` が唯一の終了の経路であり、`exitCode` は `*startup.Refusal` なら 3、`unavailableError` なら 2、それ以外は 1 を返す。
  各コマンドの `RunE` は誤りを上位へ返し、`os.Exit(0)` を明示的に呼ぶ経路は無い。
  ただし、誤りをそのまま返すわけではない箇所が続く。
  第 1 に、`server doctor`、`status`、`rule add` と `rule set` の `--dry-run` は、証拠に届かなかった誤りを `unavailable` に包み直して終了コード 2 に写す。
  第 2 に、`wgft server check` の `RunE` が呼ぶ `internal/vpsd` の `Check` は、どの経路でも `nil` を返す。
  所見を印字しても、nft の検査を実行できなくても、サーバのデータベースを開けなくても `nil` である。
  誤りを握りつぶす経路がここにある。
  この経路は、要求された操作、つまり設定と環境を印字することを完了しているので、共通の保証には反しない。
  共通の保証が言う成功を、結果が肯定であることではなく、要求された操作を完了できたことに狭めたのは、この経路が理由である(2026-09-23、所有者の決定)。
  `server check` の挙動は変えず、所見と部分的な読み取りの失敗は出力だけで伝える。
  成功しているのに 0 以外で終わる経路は `server doctor`、`status`、`rule add` と `rule set` の `--dry-run` にあるが、いずれも検査の失敗、配置の劣化、受理されない見込みという答えそのものを表しており、各節の定めのとおりである。
  未確認:実機の nftables と WireGuard を必要とする `server check`、`server teardown`、`server nft` の実際の終了コードは、コードを読んで矛盾が無いことを確かめただけで、ラボでも実機でも実行していない。
