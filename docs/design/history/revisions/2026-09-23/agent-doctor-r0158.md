- `agent doctor` の稼働の判定について、`internal/flock` への要求を実現できる形に弱めた (2026-09-23、所有者の決定):10.2c 節は、読み取り専用の入口に対して、ロックを取るのではなくロックの有無を問い合わせることと、競合しうる期間を小さくするのではなく無くすことを要求していた。
  後者を満たす手段が配布対象の OS で揃わないことを実測で確かめたので、要求を分けて弱めた。
  残す要求は、ロックファイルを作らないことである。
  `os.O_CREATE` を渡さずに開き、ファイルが既にある場合だけロックの状態を見る。
  弱める要求は競合しうる期間であり、無くすのではなく最小にするに改め、共有ロックを一瞬取る形を許す。
  後から読んだ人が同じ調査をやり直さずに済むよう、実現できない理由をここに残す。
  第 1 に、`flock(2)` には取得を試す以外の操作が無く、問い合わせに当たる操作を持たない。
  第 2 に、`fcntl` の `F_GETLK` と `F_OFD_GETLK` は別のロックの系統であり、`flock(2)` が取ったロックを見ないことを実測した。
  第 3 に、Windows には手段が無い。
  `LockFileEx` にも `NtQueryInformationFile` にも問い合わせの操作が無く、Microsoft の文書が示す唯一の方法は取ってすぐ放つ形である。
  第 4 に、Linux の `/proc/locks` は本当に取らずに読めるが、落とし穴が続く。
  1 つは、`/proc/locks` が出すのは superblock の値であり、`stat(2)` の `st_dev` と btrfs で食い違うことである。
  btrfs は Fedora と openSUSE の既定のファイルシステムなので、誤判定すると稼働中のエージェントを動いていないと答える。
  `/proc/self/mountinfo` で補正すれば一致することも実測した。
  もう 1 つは、Linux 4.9 以降の `/proc/locks` が PID namespace で絞られることであり、エージェントがコンテナの中で動き、診断をホストから打つ配置では見えない。
  macOS は実機が無いので未確認である。
  FreeBSD の man page は `flock` と `fcntl` が互換であると書いているが、Apple の man page は何も述べていない。
  第 5 に、共有ロックを一瞬取る案でも競合しうる期間は残る。
  `LOCK_SH` と `LOCK_EX` が双方向に競合することを実測した。
  一方、`O_CREATE` を渡すことによる実害はラボで再現した。
  `deploy/agent.service` の配置を模し、システムの利用者 `wgft` を作り、データディレクトリをその利用者の 0700 にし、`agent.json` を置かない状態、つまりエージェントが一度も起動していないホストを作った。
  root で `wgft agent rotate-key --data-dir` を実行すると、`agent.json` が無いのでコマンド自体は終了コード 1 で失敗するが、その前段の `credentials.IsLocked` の副作用で `root:root` の 0600 のロックファイルが残る。
  続けて同じデータディレクトリを非特権の利用者で `wgft agent run` に渡すと、`credentials.Acquire` が `EACCES` で失敗し、終了コード 1 で終わる。
  終了コード 1 は `RestartPreventExitStatus=3` の対象ではないので、`Restart=on-failure` を持つ unit は再起動を繰り返す。
  unit を実際に立てて再起動の繰り返しを観測したわけではなく、この部分は unit の記述から導いた。
  予想と違ったのは、`rotate-key` の失敗のメッセージが `agent.json` が無いことだけを述べ、ロックについて何も述べないことである。
  コマンドが失敗したのに副作用だけが残り、運用者がそれに気づく手がかりが無い。
