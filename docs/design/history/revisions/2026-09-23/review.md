  あわせて、`agent.json` があるのに権限で読めない場合と `agent.process` がロックファイルを権限で開けない場合に、稼働中でなければ成立しない検査を SKIPPED とすることを本文に明記し、`host.privileges` が `agent.json` やデータディレクトリの不在そのものを失敗にしないことも書いた。
  稼働中かどうかの判定の文を「flock が取れるかどうか」から「flock を誰かが持っているかどうか」に直し、SKIPPED の例が広すぎた点と `agent.control` の参照の曖昧さも直した。

  `internal/agent/agent.go` の `heartbeat` を読み、`ts.Err != nil` を先に見てから `else if` で `ts.LastHandshake.IsZero()` を見る順であることを確かめた。
  この順のとおり、`ts.Err` があることを先に見ると定めた。
  逆の順で `LastHandshake` の無いことを先に見ると、初回の名前解決に失敗して解決済みのエンドポイントを一度も持たないトンネルが `handshake_pending` の UNKNOWN になり、直前の段落が定める FAILED の判定と食い違う。

- 制御ストリームの観測を `runtime` の保持に加えた(2026-09-23):10.2c 節の `stream.connection`・`stream.backoff`・`stream.liveness` が読む 3 種の値は、それまで稼働中のプロセスのどこにも残っていなかった。
  制御ストリームがつながっているかどうかを表す値は無く、切断の理由は `streamLoop` がログの行に出すだけで捨て、再接続の間隔は `streamLoop` のローカル変数で、次に試す時刻と直近の ping と pong の時刻はどこにも無かった。
  同節の「2 つの証拠の出どころ」の項が、実装のときに `runtime` へ保持を加える必要があると書き残していた箇所である。
  加えたのは `internal/agent/streamobs.go` の `streamObservation` で、つながっているかどうか、直近の切断の時刻と理由、直近に待った再接続の間隔と次に試す時刻、直近の ping と pong の時刻、pong を待っている最中かどうかを持つ。
  書き手は 3 つで、接続の成立を `streamOnce` が、接続の終わりと再接続の待ちを `streamLoop` が、ping と pong を `pingLoop` が書く。
  読み手は後から制御ソケットの応答を組み立てる別の goroutine なので、値は `streamMu` で守り、読み出しは写しを返す `streamStatus` に一本化した。
  `rt.mu` を使わないのは、この mutex が全体状態の適用の間じゅう保たれ、適用が宛先 1 つにつき最長 10 秒の試し接続を含むためである。
  `streamMu` を取る区間はどれも値の代入だけで、この mutex を持ったまま他の mutex を取ることも時間のかかる処理を呼ぶこともしない。
  接続には通し番号を付け、前の接続の `pingLoop` が遅れて書いた ping と pong を捨てる。
  再接続の流れは変えていない。
  間隔の決め方も再接続の条件も以前のままで、記録は `streamLoop` が実際に使う値を写すだけである。
  制御ソケットの応答の形は変えていない。
  `doctor` の要求を制御ソケットに加えるのは別の変更である。
  確かめたのは、切断の理由が保持されて再接続で置き換わること、記録した間隔が `streamLoop` が実際に待つ値と一致すること、次に試す時刻がその間隔から導けること、ping と pong の時刻が周期ごとに進むこと、そして `go test -race ./internal/agent/...` が競合を報告しないことである。
  未確認:ラボと実機では確かめていない。
  この保持は稼働中のプロセスの中だけで完結し、カーネルにもネットワークにも触れない。

- Linux 以外のビルドの `server` の一群の終了コードを 3 にした(2026-09-23、所有者の決定):Windows と macOS のバイナリで `wgft server run` を打つと、`cmd/wgft/server_other.go` の差し替えが普通のエラーを返し、終了コード 1 で終わっていた。
  Linux でないことは再試行でも再起動でも消えない起動前提の不成立であり、11b 節の 4 つの種別では `prerequisite` に当たるので、拒否として終了コード 3 で終わる形に直した。
  あわせて、差し替えの側でもコマンドの木の形を保つ形にした。
  拒否の書き出しはコマンドごとに決まり、常駐プロセスを起動する旨の注記を持つコマンドだけが `refusing to start` を使う(11b 節)ので、一群を 1 つのコマンドに畳んでいると `server run` まで `cannot continue` になる。
  差し替えは `run`、`check`、`nft`、`teardown`、`doctor` の 5 つを持ち、注記を持つのは `run` だけである。
  この拒否が起きるホストには systemd が無いので、終了コード 3 が再起動を止める効果も働かない。
  それでも 1 にしないのは、Linux でないことが 4 つの種別のどれに当たるかという分類の問題だからである。
  確かめ方:`GOOS=windows` と `GOOS=darwin` のビルドと `go vet` をホストで流した。
  挙動そのものはホストでは実行できないので、build tag を入れ替えた木の写しを別の場所に作って `cmd/wgft` の試験を走らせ、5 つのコマンドと一群そのものが終了コード 3 で終わることと、`run` だけが `refusing to start` を使うことを確かめた。
  あわせて、拒否を普通のエラーに戻す変異、`run` の注記を落とす変異、種別を `config` にする変異、`run` を部分コマンドでなくす変異の 4 つを入れ、いずれも試験が落ちることを確かめた。
  実際の Windows と macOS での実行は、CI の `windows-test` と `macos-test` が行う。
  未確認:実機の Windows と macOS で監督するプロセスがこの終了コードをどう扱うかは確かめていない。

- `agent.rules_received` の FAILED の detail の言い過ぎを直した(2026-09-23、所有者の決定):ルール集合の世代は server が単一で持ち、変わるたびに、そのエージェントを名指す有効なすべてのルールの `agent.rules_received` を経由する。
  エージェントが新しい世代をまだ取っていない間は、そのエージェントの全ルールが FAILED になる。
  以前の detail「it still holds rule set N while this server serves M, so this rule has not reached it」は、この 1 本のルールが届いていないと述べていたが、世代の中身が変わっていないルールは、世代番号が古いままでも転送を続けており、この文言はそのルールについて誤りだった。
  detail をエージェントとルール集合の世代という、確かめている事実だけを述べる形に直し、個々のルールへの言及を外した。
  「this agent still holds rule set N while this server serves M; it has not taken the latest rule set yet」とする。
  status は FAILED、reason は `generation_behind` のまま変えておらず、7a.11 節の保証する値の範囲を変えない。
  短い遅れ(再送信中で数秒後に追いつく)と、いつまでも世代が追いつかないままの状態とを分ける境目は、この版では決めず、Web UI の経路の図(10.2d 節)が付けるダッシュボードの印と合わせて v1.2 で決める。
