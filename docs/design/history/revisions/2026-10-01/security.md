# 2026-10-01: security

- エージェント用 API の TLS ハンドシェイクの誤りの行を間引くようにした(2026-10-01、10.4 節、セキュリティ点検の指摘):この待ち受けは認証の前に TCP で届くので、相手は TLS のハンドシェイクを送らずに閉じるだけで net/http の誤りの行を 1 本につき 1 行出させられた。
  送信元ごとの上限(16)は同時の本数しか縛らないので、すぐ閉じる接続を繰り返せば行数は相手の接続の速さで決まり、Docker の既定の json-file のログ(回転しない)ではディスクを、systemd では journald の速度の制限を埋めうる。
  中継の接続ごとの行を待ち受けごとに 1 分に 1 回へ間引く方針(改訂の記録 2026-09-19)から、この経路が漏れていた。
  行を証明書を理由に拒んだもの(`bad certificate`)とその他の 2 つに分け、理由ごとに `lograte.Gate` で 1 分に 1 回まで間引くようにした。
  証明書を理由に拒んだ行は古い証明書を固定したエージェントへの運用の案内を持つので、他の理由の連続に埋もれないよう別の門を持つ。
  理由の文面そのものを鍵にした間引きは採らなかった。
  ALPN の一覧など相手が送った値をそのまま埋め込む理由文があり、鍵の数を相手が増やせてしまうためである。
  間引いた行があれば、次に出す行に件数を添える。
  間引きの対象は "TLS handshake error" を含む行だけであり、同じ ErrorLog が書くハンドラの panic や Accept の誤りの行は対象にしない。
  単体テストで、同じ理由の行を連続して送ると最初の 1 行だけが出ること、証明書を理由に拒んだ行は他の理由の門が閉じていても出ること、間引きの対象外の行は門が閉じていても出ること、gatedCount が渡す件数が門を通った行に付き、渡した後は 0 に戻ることを確かめた。
  あわせて `deploy/server.compose.yaml` と `deploy/agent.compose.yaml` に `logging`(`json-file` の `max-size`・`max-file`)を加え、Docker の既定の無回転のログに頼らないようにした。
  未確認:ラボまたは実機での、インターネット越しの実際の行の速さと、journald 側での効果
