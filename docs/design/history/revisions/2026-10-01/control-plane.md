# 2026-10-01: control-plane

- エージェント用 API の認証前の接続を、IPv6 のプレフィクスの段と全体の上限で抑え、確立の前の stream をエージェントごとに抑えた(2026-10-01、5.2・7・7a.11・11 節、セキュリティ点検の指摘):送信元ごとの上限は IPv6 を /64 で数え、11 節は既定の待ち受けの `0.0.0.0:8443` を IPv4 だけと書いていた。
  実際には Go がこの待ち受けを IPv4 と IPv6 の両方に応じるソケットで開くので、/56 を持つ 1 人が /64 を替えながら、認証を通らない接続で同時接続数の上限 4096 を埋め、その間の新しい登録と stream の再接続を止められた。
  1 本は ClientHello を送らずに 10 秒、ハンドシェイクの後に本文を少しずつ送って合わせて 25 秒まで枠を持てた。
  また、恒久トークンの確認を通った stream は送信元の数から外れ、最初のメッセージを 1 MiB の読みの上限で 30 秒待ち、エージェントごとの本数に上限が無かった。
  恒久トークンを 1 つ持つ者は、1 本ごとに読みの上限に近いメモリを持つ stream を、送信元を替えて多数持たせられた。
  送信元の段に IPv6 の /56(64 本)と /48(256 本)を加え、認証前の接続の全体の上限(1024 本)を同時接続数の上限の内側に置き、ハンドシェイクの期限を 5 秒、リクエストを読み終える期限を 10 秒にした。
  確立の前の stream はエージェントごとに 2 本までとし、最初のメッセージを 10 秒以内、4 KiB 以下に限り、確立した後は 1 MiB に戻す。
  待ち受けを IPv4 だけで開く案は、`WGFT_AGENT_API` の意味を変えるので採らなかった。
  IPv4 に /24 の段を置く案は、CGNAT の後ろの正規のエージェントを巻き込むので採らなかった。
  全体の上限を置いたので、IPv4 のアドレスでこの上限を埋めるのに要る数は 256 個から 64 個に減った。
  7 節の上界は、認証前の接続の項を 1024 本の分に改め、認証を通った stream の項をエージェントごとに加えて計算し直した。
  既定の上限の `vpsd` のホストに要るメモリは約 7.1 GiB から約 5.9 GiB に、上限を最小にしたときの値は約 4.1 GiB から約 2.9 GiB に下がった。
  README の日英、セットアップの文書の日英、同梱の compose ファイルの値も直した。
  単体テストで、IPv6 の /64、/56、/48 の段と IPv4 射影のアドレスの数え方、全体の上限、本番の上限で 1 つの /56 と /48 が持てる本数、ホストを指定しない待ち受けが IPv6 に応じること、ハンドシェイクの期限、最初のメッセージの大きさの上限と期限、エージェントごとの確立の前の stream の上限を確かめた。
  未確認:実際の IPv6 の /56 からの接続、遅い実回線での期限、置き換えられて閉じる途中の stream が持つメモリの量と時間。
