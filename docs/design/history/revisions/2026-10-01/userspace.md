# 2026-10-01: userspace

- ユーザー空間モードのエージェントが、server から届く wg.keepalive と wg.udp_timeout_stream を time.Duration に変える前に境目で拒むようにした(2026-10-01、11 節、セキュリティレビューの指摘):奪われた VPS はこの 2 つの秒の値を自由に選べる。
  大きすぎる値を `* time.Second` すると int64 のナノ秒が桁あふれし、極めて短いか負の time.Duration に巻き戻る。
  ユーザー空間モードは、無通信の掃除の goroutine の ticker と keepalive の ticker をこの値でそのまま回していたので、巻き戻った値は家のホストの CPU を使い切る。
  `internal/agent` に `secondsToDuration` を設け、0 以下の値、上限(keepalive はカーネルモードの checkWG と同じ 0 から 65535 秒。
  udp_timeout_stream は VPS の conntrack の sysctl が取りうる最大の値である math.MaxInt32 秒)を超える値、変換の結果が 1 秒に届かない値を拒み、既定値に落とす。
  値を送らない旧い server の 0 は既定値に落ちる正当な値として黙って扱い、それ以外の値を拒んだときは、build の時点でしか呼ばれないこの経路から英語で 1 行を記録する。
  無通信の掃除の ticker(`relay/udp.go` の `sweepInterval`)とキープアライブの ticker(`tunnel.go` の `New`)には、値の出どころによらない下限も別に置いた。
  `agent doctor` が読む `declaredAgentLink` も、同じ範囲の外の keepalive を拒む。
  11 節の「server から届く値の検証」に、ユーザー空間モードの keepalive と udp_timeout_stream はこの拒み方が違うと 1 文を加えた。
  範囲の外の値を拒む代わりに既定値に置き換える点だけがカーネルモードと違い、互換性の保証(7a.11 節)は変えていない。
  変異試験で、上限の比較、変換結果の下限、2 つの ticker の下限、`declaredAgentLink` の範囲の確認をそれぞれ外すと、単体テストが落ちることを確かめた。
  未確認:実機とラボでの確認。
  ホストの CPU への影響を直接測る変更ではなく、純粋な Go の変換と ticker の下限なので、単体テストで十分と判断した。


- ユーザー空間モードの TUN の入口で、引用したフローの宛先と送信元の合わない ICMP の誤りと、MTU の小さすぎる Fragmentation Needed を捨てるようにした(2026-10-01、7・11 節):`vpsd` のユーザー空間モードでは全エージェントのピアが 1 つの Device を共有する。
  wireguard-go は外側の送信元が送ってきたピアのトンネルのアドレスであることしか確かめず、TUN の入口は UDP 以外を検査せずに gVisor に渡し、固定版の gVisor は ICMP の誤りの外側の送信元と引用の宛先の一致も、引用された TCP のシーケンス番号も、Fragmentation Needed の MTU の下限も確かめない。
  このため登録済みのエージェントが、`vpsd` と別のエージェントの間のフローを引用した Port Unreachable でそのフローの UDP のセッションを閉じさせ、MTU 68 の Fragmentation Needed でそのフローの TCP の segment の payload を 1 byte にできた。
  11 節の「ピア同士は通信できない」の外にある経路である。
  入口で、外側の送信元が引用の宛先と一致しない ICMP の誤り(type 3、4、5、11、12)と、next-hop MTU が 552 より小さい Fragmentation Needed を捨てる。
  確認は再組み立ての後に行う。
  固定版の gVisor が transport に渡す誤りは type 3 だけだが、ほかの 4 つも同じ規則で捨てる。
  gVisor の更新で扱いが変わっても、別のピアの誤りが届かないようにするためである。
  下限は Linux の既定の `min_pmtu` にそろえ、576 は採らなかった。
  gVisor と wireguard-go は変えていない。
  Device の単体テストで、別のピアからの Port Unreachable、Host Unreachable、断片に分けた Port Unreachable、Fragmentation Needed が UDP のセッションと TCP の接続に届かないことと、引用の宛先からの Port Unreachable と Fragmentation Needed が今までどおり効くことを確かめた。
  引用の宛先からの Host Unreachable については、入口の判定の関数が捨てずに渡すことだけを単体テストで確かめ、それが TCP の接続を止めることは確かめていない。
  ラボで、カーネルモードのエージェントが LAN のホストの Port Unreachable を、外側の送信元と引用の宛先をどちらもエージェントのトンネルのアドレスにして送ることと、`vpsd` の中継がそれを受けてセッションを閉じることを確かめた。
  未確認:wireguard-go を通した別のピアからの偽の誤りのラボでの再現、エージェントのホスト自身が出す Fragmentation Needed の形、552 より小さい MTU の経路を実際に通る利用


- 中継が持つカーネルの TCP ソケットの受信のバッファを固定した(2026-10-01、7・13 節、所有者の決定):ユーザー空間モードの中継は、`vpsd` の公開側とエージェントの LAN 側でカーネルの TCP ソケットを持つ。
  ラボで、両端に読まない相手を置いた中継を同時フロー数の上限の近くまで保持させると、このソケットが受信のバッファを自動調整の上限まで広げ、ホスト全体の `tcp_mem` の上限に達した。
  上限に達したホストでは、別のルールの小さな転送が大きく遅れた。
  gVisor、WireGuard、UDP ではパケットが捨てられておらず、wgft を通さない TCP で `tcp_mem` を埋めても同じ遅れが出たので、原因はカーネルの TCP のメモリの上限と判断した。
  両側とも、受信のバッファを組にした netstack の接続の boost の枠に合わせて固定する。
  最初の案では、エージェントの LAN 側を枠に合わせない固定の値にしていた。
  ラボでその案を以前の製品と比べると、LAN に往復の時間を加えた宛先からの転送が大きく遅くなったので、所有者は LAN 側も枠に合わせる形に改めた。
  公開側を固定の値にしなかったのは、遠い利用者からの転送の速さを保つためである。
  握手の後に固定し、固定のたびに `TCP_WINDOW_CLAMP` を置くのは、窓の scale と窓の上限の扱いを Linux 6.1 と 7.2 で確かめた結果による。
  この変更が抑えるのは、中継が持つカーネルのソケットが受信の側に溜める量であり、ホスト全体の巻き添えをすべて防ぐものではない。
  確認の条件は、実行の前に決めてプルリクエストに書いた。
  ラボは試験のクライアントと宛先も同じカーネルに置く。
  `tcp_mem` の上限を引き上げた条件では、以前の製品は遅れ、この変更では別のルールの小さな転送が遅れなかった。
  `tcp_mem` を既定のままにした条件では、試験のクライアントと宛先のバッファを小さくしても、この変更の後に上限に達し、別のルールの小さな転送が大きく遅れた。
  このとき `vpsd` の namespace とエージェントの namespace が使った量は、どちらも単独では上限に届かなかった。
  エージェントの LAN 側を固定の値にした最初の案は、同じ条件で上限に達しなかった。
  差は、エージェントで boost の枠を持つ 16 本のソケットの受信のバッファである。
  同じ VM で以前の製品と比べると、LAN の宛先からの転送、単独の bulk の転送、遠い利用者からの転送、Web に相当する多数の小さい応答、SSH に相当する往復は以前より遅くならなかった。
  所有者は floor と既定の K を変えず、ホストの要件の表に受信の予算 K × 256 KiB + 128 MiB を加えることにした。
  この予算はホストの安全の十分な条件ではなく、ホストの実際の `tcp_mem` とページの大きさで判断し、収まらなければまず K を下げると書いた。
  表のホストに要るメモリと同じ大きさのホストで `tcp_mem` が Linux の既定の値なら、既定の K の予算が上限と圧迫の閾値を超えることも書いた。
  送信の側は Linux の自動調整のままにする。
  読むのを速く続けた後に止める相手では、両方のソケットの送信のバッファが自動調整の上限まで広がることを確かめた。
  中継が閉じた後に送り残しを持って残るソケットが長く保持を続けることも確かめた。
  送信の側を上界で抑える別の変更は取り下げ、この 2 つは残る危険を明記したうえで、上界を持たない保持として v1.3.0 の後に設計し直すことにした。
  単体テストで、固定が `vpsd` の公開側のソケットとエージェントの dial したソケットに置かれること、値が枠の取得と floor への戻りに合わせて上下すること、窓の上限が保たれることを確かめた。
  レビューで、枠を返した後もカーネルのソケットが floor を超える受信のデータを持ちうることが分かった。
  `SO_RCVBUF` を下げてもすでに持つデータは解放されない。
  穴を残して順序外のデータを送った後に黙る相手では、そのデータが中継に読まれずに残り、netstack の接続は需要の無い保有者として枠を返していた。
  このため 16 本の上限は、大きい受信のバッファを持つソケットの数には効いていたが、floor を超える受信のメモリを持つソケットの数には効いておらず、受信の予算も保持の上界になっていなかった。
  floor に戻す前に、カーネルのソケットの受信のメモリ(`SO_MEMINFO`、順序外のキューを含む)が floor 以下であることを求め、超えるか読めなければ枠を返さないようにした。
  ラボの試験(`lab/rcvwin.sh`)で、変更の前は穴を残した接続の公開側のソケットが floor を超える受信のメモリを持ったまま floor に戻ること、変更の後は戻らず枠を持ち続けること、穴が埋まると転送が終わり、その後に別の接続が枠を得ることを確かめた。
  単体テストで、受信のキューに floor を超えるデータがある間と受信のメモリを読めない間は戻らないこと、戻れなかった保有者が次の要求で改めて試されることを確かめた。
  ユーザー空間モードの通しのシナリオ(`lab/e2e.sh`)と `lab/lifecycle.sh` が通った。
  中継が閉じた後のソケットが穴の後ろの順序外の受信のデータを持ったまま残ることは、Linux 6.1 のソースと wgft を通さないソケットで確かめた。
  この保持も、送信の側と同じく v1.3.0 の後に設計し直す。
  レビューで、`vpsd` の公開側のソケットが accept から dial の後の最初の固定までの間は固定されておらず、穴の後に小さい順序外の segment を続ける相手に対して受信のバッファを `tcp_rmem` の最大値まで広げうることが分かった。
  dial の後の最初の固定は受信のメモリを確かめずに floor に下げるので、そのデータは K と 16 本の外に残っていた。
  7 節の、この間の溜めは既定の設定では起きないという記述は誤りだった。
  両方の accept のループで、accept の直後、接続元の確かめ、Admission、同時フロー数の上限、dial より前に受信のバッファを floor に固定して受信のメモリを読み、floor を超えるか固定か読み取りに失敗すれば、数えずに RST で切るようにした。
  待ち受けのソケットは変えていない。
  固定したソケットが広がらないことは、Linux 6.1 のソースと、wgft を通さないソケットの測定で、その測定の条件の下で確かめた。
  wgft の中の順序と、確かめが通さない接続が Admission にも dial にも進まないことは、両方の accept のループを通る単体テストで確かめた。
  ラボで、遠い利用者からの転送の速さと窓の scale がこの変更の前と変わらないこと、`lab/e2e.sh`、`lab/lifecycle.sh`、`lab/rcvwin.sh` が通り、その間にこの確かめが切った接続が無いことを確かめた。
  未確認:エージェントの LAN 側のソケットに穴の後ろのデータが残る場合の枠の扱い(ラボでは `vpsd` の公開側だけを確かめた)、中継が閉じた後のソケットが穴の後ろの順序外の受信のデータを持ったまま残る保持の、wgft の中継を通した再現と boost の大きさに近い量での再現、穴の後に小さい順序外の segment を続ける相手を `vpsd` の公開側に向けた測定、accept が返す前の待ち行列にあるソケットが溜める量(この変更は抑えない)、送信の側と閉じた後のソケットの保持を繰り返したときのホスト全体への影響、プロキシモードのルールの中継のラボでの効き目(単体テストだけで確かめた)、エージェントを LXC で動かした実機での効き目、`vpsd` とエージェントを別のホストに置いた場合の遅れ、宛先がエージェントと同じカーネルにある場合の全体の量、Windows と macOS のエージェント


- v1.3.0 のユーザー空間モードの資源の上界をソースで点検した独立レビューを受け、6.2 節、6.3 節と 7 節の記述を実装に合わせた(2026-10-01、6.2・6.3・7 節。
  コードは変えていない):レビューは設計文書とコードの食い違いを 5 つ示した。
  1 つめは、中継が通常の `Close` で閉じた netstack の接続を解放したと書いていた点である。
  送り残しを持つ接続は FIN_WAIT_1 などに残り、K に数えず、boost の枠を持たないものは 16 本にも数えない。
  この状態を終わらせる仕組みが無いことはコードから判断し、接続が残ることは別の試験で観察した。
  boost の枠を持つ接続が 16 本に数えたまま残ることと、中継の側から意図して切る経路が RST で切ることはコードで確かめた。
  7 節にこの保持点を書き、上界の式に入っていないことを明記した。
  2 つめは、警告の行を量の小さい保持点に入れていた点である。
  `ip-flapping` の行は IP の組ごとに別の行になり、行の数に上限が無いことをコードで確かめた。
  3 つめは、認証済みの stream の 1.5 MiB × A が測った形のハートビートでの値であることを書いていなかった点で、ハートビートの項目の数に上限が無いことをコードで確かめた。
  保存する量は推定のままである。
  4 つめは、K を 1 減らしたときのエージェントの上界の減り方が、`vpsd` とエージェントの K をそろえる前提の値であることを書いていなかった点である。
  エージェントの K だけを下げたときの値と、エージェントに残る送り残しを持った接続がエージェントの K に数えられないことを書き加えた。
  5 つめは、待ち受けの固定費を攻撃者から増やせないと書いていた点で、エージェントの待ち受けの数は `vpsd` が配る全体状態で決まり、エージェントはその数に上限を持たないことをコードで確かめた。
  エージェントの上界のうち待ち受けの数と accept の待ち行列の項が `vpsd` を信頼する前提に立つことを、1 つの段落にまとめて書いた。
  プロセスの上界は式に数えた保持点についての値であり、プロセスのメモリがこの値を超えないことは示せていないと書き改め、6.3 節のホストの要件の文も同じ意味に合わせた。
  未確認:送り残しを持って閉じた接続の長い保持、その数の上限と合計の量、プロキシモードの中継での再現、エージェントに残るこの接続の数、警告の行の増える速さとメモリの量、項目の多いハートビートが保存する量、エージェントが多数の待ち受けを開いたときの量。
