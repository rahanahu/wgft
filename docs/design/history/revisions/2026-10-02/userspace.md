# 2026-10-02: userspace

- 公開の文書のメモリの要件の言い回しを 7 節の定義に合わせた(2026-10-02、7 節、所有者の決定。
  設計は変えていない):`README.ja.md` と `docs/manual/setup-server-userspace.ja.md` は、ユーザー空間モードのホストに要るメモリを「最悪の場合にもメモリを使い切らない」「攻撃時の最悪値に耐える」のように、7 節の上界の定義より強く書いていた。
  7 節の上界は式に数えた保持点の値であり、プロセスのメモリがそれを超えないことは示せていない。
  これらの文書と英語の対の文書の言い回しを改め、この値が、計算に数えた保持点がそれぞれの上限まで同時に埋まった場合の最悪値の見積もりであることを書いた。
  `docs/development/testing.md` の C6 の「すべての保持点を埋めた場合の値」も、7 節の定義の「式に数えた保持点」に合わせた。


- 公開側のクライアントの RST を、VPS の中継がエージェントへ RST として伝えるようにした(2026-10-02、6.2 節、6.3 節、7 節):VPS の中継(プロキシのルールと、ユーザー空間モードの通常のルール)は、公開側のクライアントが接続を RST で切ると、エージェントへの接続を通常の `Close` で閉じていた。
  エージェントの中継はその FIN をハーフクローズとして扱うので、FIN を受けても閉じない宛先では、宛先への接続と枠が宛先が閉じるまで残った。
  VPS の中継の枠はすぐに返るので、このフローは VPS の接続元ごとの上限の外でエージェントに残った。
  2026-09-30 の改訂で決めていなかったこの点を、公開側のクライアントの RST だけをエージェントへの接続の RST として伝えると決めた。
  `internal/netpipe` の `PipeResetB` は、公開側の接続の読み取りか書き込みが RST の誤りで失敗したときに、両側を閉じる前に呼び出し側の関数を呼ぶ。
  VPS の中継はその関数で、エージェントへの接続を `Abort` か `SetLinger(0)` で RST にする。
  EOF とハーフクローズ、中継の側からの切断、エージェント側から届いた RST の扱いと、枠を返す時点は変えていない。
  エージェントの中継は、宛先への接続が実ソケットなので、今までどおり宛先への接続を通常の `Close` で閉じる。
  単体試験では、終わり方と向きごとに両側が見るものと枠を返す時点を固定し、変わるのは公開側のクライアントの RST でエージェントが見るものだけであることを、ユーザー空間モードの通常のルールと、プロキシのルールの両モードで確かめた。
  ラボでは、ユーザー空間モードのエージェントと FIN を受けても閉じない宛先を、ユーザー空間モードの VPS の通常のルールとプロキシのルール、カーネルモードの VPS のプロキシのルールで組み合わせ、クライアントが RST で切るとエージェントが宛先への接続を持たなくなることを確かめた。
  修正前のバイナリでは、同じ手順でエージェントが宛先への接続を持ち続けた。
  クライアントが通常に閉じた場合とハーフクローズの場合は、どちらのバイナリでもエージェントが宛先への接続を持ち続けた。
  宛先が書き続けている間にクライアントが RST を送ると、公開側への書き込みが RST の誤りを先に受け取り、公開側の読み取りは EOF を返すことが多い。
  この場合はエージェントへの接続に FIN が先に出て、その後に RST が出る。
  FIN を受けたエージェントの中継はトンネル側を読まないので、この RST に気付くのは宛先からのデータをトンネル側へ書いたときである。
  宛先が送り続ければ、エージェントの中継はその書き込みの失敗で終わる。
  宛先が送り終えた直後に黙り、FIN を受けても閉じない場合は、エージェントは従来どおり宛先への接続と枠を持ち続ける。
  宛先が黙っている間にクライアントが RST を送った場合は、RST が FIN より先に出る。
  クライアントが FIN を送った後の RST は伝わらない。
  公開側のソケットは FIN を受けて CLOSE_WAIT にあり、Linux はこの状態で受けた RST を ECONNRESET ではなく EPIPE として返すためである。
  このとき VPS とエージェントの中継は従来どおりハーフクローズのまま両方とも持ち続けるので、枠の帳尻は合う。
  FIN が RST より先に出る競合と、FIN の後の RST が伝わらないことは、network namespace の loopback で確かめた。
  カーネルモードのプロキシのルールで、エージェント側から届いた RST を公開側のものと区別できずにエージェントへの接続を RST で切るとき、追加の RST が出ないことは、Linux のコードから導き、network namespace の Tcp OutRsts の計数器でも確かめた。
  パケットのキャプチャでは確かめていない。
  RST は再送されないので、エージェントへの RST が経路の上か netstack の出力のキューで失われると、VPS の枠は返っているのに、エージェントは従来どおり宛先への接続と枠を持ち続ける。
  中継の側からの切断も同じである。
  これはコードから導いたもので、測定していない。
  network namespace での確かめはホストの kernel で行った。
  未確認:ラボの Debian 12 の kernel での同じ振る舞いと、RST の喪失が起こる頻度


- エージェントのユーザー空間モードの dataplane を `internal/agent/usermode` へ移した(2026-10-02、7a.7 節。
  挙動は変えていない):`internal/agent` の `dataplane_userspace.go` にあったユーザー空間モードの実装と、その単体試験を、下位の package `internal/agent/usermode` へ移した。
  カーネルモードの実装と実行時の状態は `internal/agent` に残した。
  実行時の状態が使う作成の関数を `New` として公開した。
  `internal/agent` の試験が使う型、フィールド、トンネルの作成と状態の読み取りの差し替え口、ルールごとの状態の合成、中継の調整値の組み立ても、名前を大文字に改めて公開した。
  Go には package をまたいで試験にだけ名前を見せる仕組みが無いためである。
  本番のコードが `usermode` の外からこれらを使わないことは、`TestAgentModeTestSeamsStayInTests` が型検査で確かめる。
  宣言の本文は、名前と package の修飾子と、注釈の中の名前を除いて変えていない。
  例外は試験の次の箇所である。
  カーネルモードの `agent doctor` の試験が使う 1 行の補助関数は、移した試験のファイルにあったので、その試験のファイルに写した。
  試験の失敗の文言の 1 つが移した型の名前を含んでいたので、新しい名前に直した。
  7a.7 節の配置の木と本文に `usermode` を加え、`TestAgentModesStayApart` が `usermode` の import を検査する。


- エージェントの制御ソケットを `internal/agent/control` へ移した(2026-10-02、7a.7 節。
  挙動は変えていない):制御ソケットのサーバと、エージェントのホストで動く CLI の側(`rotate-key` と `agent pubkey`)のファイルを、新しい package へそのまま移した。
  サーバは実行時の状態を新しい interface `control.Backend` を通じて呼び、`internal/agent` がそれを実装する。
  サーバの 2 つの関数は実行時の状態のメソッドから package の関数に変わり、認証情報ファイルのパスと `Backend` を引数で受け取る。
  `internal/agent` には、制御ソケットを開くメソッドを `control.Serve` を呼ぶ 1 行の橋渡しとして残した。
  鍵を作り直す処理と、`doctor` の応答を組んで panic を受け止める処理は `internal/agent` に残し、変えていない。
  `rotate-key` の枝が panic を受け止めないことと、その理由の注釈、ソケットを閉じて消す後片付けの順は、そのまま移した。
  `agent pubkey` と停止中の `rotate-key` は、ロックの取り方と順、エージェントが止まっているときの動作、誤りと出力を変えずに移した。
  パスが長すぎる場合の説明を添える関数は、サーバと CLI の側の両方が使うので `control` の非公開の関数とした。
  移した処理だけを使うテストは `control` のテストとして移し、実行時の状態を使うテストは `internal/agent` に残した。
  写したテストの補助は無い。
  `internal/agent` のテストのためだけに公開した名前は、接続を 1 つ処理する `ServeConn` だけである。
  `ServeConn` を `internal/dataplane/deps_test.go` の `modeTestSeams` に載せ、`TestAgentModeTestSeamsStayInTests` の対象を `control` に広げた。
  `control` の import の範囲は、新しい `TestAgentControlImportsNoRuntimeOrMode` が本番のファイルについて検査する。
  移した宣言は、移す前と比べて、名前の変更、修飾子、注釈と、サーバの 2 つの関数の受け取る値と実行時の状態の呼び方を除いて同じだった。
  変えたのは、`internal/agent` のテストのうち `ServeConn` を呼ぶ 2 件の呼び出しの形だけである。
  比べたのは Linux、Windows、macOS のビルドで、`lab` の build tag の有無の両方である。
  テストの名前の集合は移す前と同じだった。
  `ServeConn` を `internal/agent` または `cmd/wgft` の本番のコードが使うと `TestAgentModeTestSeamsStayInTests` が落ち、`control` に許していない import を加えると `TestAgentControlImportsNoRuntimeOrMode` が落ちた。
  ラボでは、制御ソケットを使う `rotate-key` と `agent doctor` の確認が通った。
  口の検査の外にあることは次のとおりである。
  公開した interface の型のメソッドは、2 つの一覧のどちらにも載せない。
  `control` の外の本番のコードが `Backend` を通じてそのメソッドを使うと、口の検査は、interface のメソッドを使ったことを述べる文言で落ちる。
  この文言は独立レビューの指摘を受けて分けた。
  未確認:次の点は移す前から単体テストが固定しておらず、移した後もラボで誤りを捉えるかどうかを確かめていない。
  サーバが止まるときにソケットを閉じて消すこと、開く前に古いソケットを消すこと、接続の期限、Windows でソケットを締められなかった場合にソケットを諦めること、稼働中の `rotate-key` が読む応答の大きさの上限の値、停止中の `rotate-key` がロックの判定にテストの差し替え口を通さず `credentials.Inspect` を直接使った場合、エージェントの起動が制御ソケットを開かなくなった場合である。
