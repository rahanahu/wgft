# 2026-10-02: control-plane

- `ip-flapping` の警告の行に、エージェントごとの上限を置いた(2026-10-02、5.2・7 節、所有者の決定):7 節は、`ip-flapping` の警告の行が (エージェント, 種類, detail) の組で重複を除くだけであり、行の数に上限が無いことを記録していた。
  detail は往復した 2 つの IP を含むので、恒久トークンか WireGuard の鍵の持ち主が多くのアドレスから往復を起こすと、行は管理者が警告を消すかエージェントを削除するまで増え続けた。
  往復を記録するたびに、そのエージェントの `ip-flapping` の行を、いま記録した行と最後に検出した日時が新しい行に絞ることにした。
  検知は止めず、管理者には直近の往復が見える。
  上限の値と選んだ理由は 5.2 節に書いた。
  スキーマは変えず、上限を超えた行を持つ既存のデータベースは、そのエージェントの次の往復の記録で上限まで減る。
  あわせて、管理用 API の agent の一覧が警告をエージェントごとに読むとき、全エージェントの行を読んで絞るのをやめ、そのエージェントの行だけを SQL で読むようにした。
  一覧の中身と順序は変えていない。
  同じ秒の警告は、以前と同じく記録した順に並べる。
  警告の文面、Web UI、`wgft agent warnings` と `wgft status` の出力は、古い行が消えることのほかは変えていない。
  上限に達したときのデータベースの大きさは測っていない(未確認)。


- `ip-mismatch` の警告の行に、エージェントごとの上限を置いた(2026-10-02、5.2・7 節、所有者の決定):7 節は、`ip-flapping` の行に上限を置いた後も、`ip-mismatch` の行には上限が無いことを記録していた。
  detail は stream の接続元 IP と wg エンドポイント IP を含むので、行は IP の組ごとに増え、管理者が警告を消すかエージェントを削除するまで残った。
  7 節は、1 行に 2 分の連続の観測が要るとして増える速さを推定していたが、この推定は誤りだった。
  確認済みの組が無い間は、組が変わっても連続回数を数え直さない(5.2 節)。
  このため、食い違いが 2 分続いた後は、15 秒ごとの観測のたびに新しい組の行が 1 行ずつ増えうる。
  これを単体テストで確かめ、7 節の推定を消した。
  食い違いを記録するたびに、そのエージェントの `ip-mismatch` の行を、いま記録した行と最後に検出した日時が新しい行に絞ることにした。
  上限は `ip-flapping` とは別に数え、値と選んだ理由は 5.2 節に書いた。
  上限で行を消す処理は管理者の「警告を消す」の経路を通らず、警告の行だけを消すので、確認済みの組を作ることも変えることもない。
  上限で行が消えた組は確認済みにならず、その組の食い違いを再び観測すれば警告になる。
  食い違いの連続回数、確認済みの組との照合と破棄、警告を記録する条件は変えていない。
  スキーマは変えず、上限を超えた行を持つ既存のデータベースは、そのエージェントの次の食い違いの記録で上限まで減る。
  警告の文面、Web UI、`wgft agent warnings` と `wgft status` の出力は、古い行が消えることのほかは変えていない。
  上限に達したときのデータベースの大きさは測っていない(未確認)。

- 置き換えられて閉じる途中の stream を、置き換えた stream の確立の前の枠で数えた(2026-10-02、5.2・7・11 節):2026-10-01 の記録で後で直すとした保持点である。
  旧接続を置き換えた stream は、接続の表に入った時点で確立の前の枠を返していたので、置き換えられて閉じる途中の stream はどの数にも入らなかった。
  恒久トークンの持ち主は置き換えを繰り返して、閉じる途中の stream を同時接続数の上限の残りまで積めた。
  置き換えた stream は、旧接続を扱う処理が終わるまで枠を返さないことにした。
  置き換えた stream が旧接続より先に終わった場合も、旧接続を扱う処理が終わるまで枠を返さない。
  先に返すと、置き換えと切断を繰り返して、どの枠にも数えない閉じる途中の stream を残せるためである。
  閉じる途中の stream は 1 つのエージェントにつき 2 本までになったので、7 節の「上界の式に入れない」一覧から外し、認証済みの stream の項を、確立した 1 本と、確立の前か閉じる途中の 2 本の分に改めた。
  閉じる途中の 1 本には、ハートビートを読んでいる途中の確立した 1 本の測定値を当てた。
  既定の上限の表の値は、表の桁では変わらない。
  置き換えた stream の確立と全体状態の送信は、旧接続を待たない。
  確立の前の stream と閉じる途中の stream が合わせて 2 本ある間は、次の試みは 429 で断られる。
  エージェントは接続を 1 本ずつ試み、429 を一時的な拒否として通常のバックオフで再接続する(5.2 節)。
  正規のエージェントがこの 429 に当たるのは、置き換えた stream が旧接続の閉じ終わる前に切れて、続けて再接続する場合などである。
  置き換えられる旧接続を close の手順なしに閉じる案は、エージェントに `superseded` の理由コードが届かなくなり、善意の二重起動どうしの振動を抑えるバックオフ(5.2 節)が変わるので採らなかった。
  WebSocket のメッセージの形と API は変えていない。
  単体試験で次を確かめた。
  旧接続のクライアントが close に応えない間も、置き換えた stream はすぐに確立して全体状態を受け取る。
  その間、確立の前の 1 本に加えた試みは 429 で断られ、他のエージェントの試みは断られない。
  旧接続のクライアントが close に応えると、旧接続は `superseded` で閉じ、枠が戻る。
  置き換えた stream が先に終わっても、旧接続が閉じるまで枠は戻らない。
  WebSocket への切り替えに失敗した要求も枠を返す。
  旧接続のクライアントが応えない場合も、ライブラリの期限で旧接続が閉じて枠が戻ることを、使い捨ての試験で確かめた。
  独立レビューの指摘を受け、TLS の close_notify の書き込みの期限で閉じる処理が延びうることを 11 節に書いた。
  未確認:TLS の close_notify の書き込みが詰まった場合の閉じる処理の長さ、TLS の接続での閉じる途中の 1 本のメモリの量、閉じる途中の 2 本の goroutine のスタックが前述の 55 KiB × A に収まるかどうか、実機の回線で正規のエージェントがこの 429 に当たる頻度。


- 恒久トークンの持ち主が起こせるテーブルの差し替えの回数を抑え、鍵の宣言で他のエージェントへ全体状態を配り直さないようにした(2026-10-02、5.2・6.1・7a.3・7a.4・7a.11・11・13 節、所有者の決定):エージェントが stream で宣言した公開鍵は、保存している鍵と違えば保存して適用しており、変更の回数に上限が無かった。
  保存している鍵での再接続と、最後に成功した鍵での再接続は省略するが、2 つの鍵を交互に宣言するとどちらの省略も効かない。
  カーネルモードの `vpsd` は適用のたびに `table inet wgft` の全体を差し替えるので、恒久トークンの持ち主は秘密鍵を持たずに、全エージェントのルールの meter と `ct count` の状態を接続の試みのたびに作り直させられた。
  配信の比較は写しの鍵を含むので、鍵の変更は配る内容の変化として扱われ、接続中の全エージェントへ全体状態が配られた。
  カーネルモードのエージェントは、同じ世代の全体状態でも wgft0 の収束、テーブルの差し替え、宛先への試し接続をやり直していた。
  設計文書も食い違っていた。
  6.1 節と 7a.4 節は差し替えを攻撃者から起こせないと書き、7a.3 節は鍵の宣言が差し替えを伴うと書いていた。
  所有者の決定に従い、次の 3 つを入れた。
  第 1 に、保存している鍵を変える宣言を登録ごとのトークンバケットで数え、続けて 3 回までと、その後は 10 分に 1 回までに限った。
  値の根拠は 5.2 節に書いた。
  上限を超えた宣言は既存の符号 1008 で閉じ、wire に符号もフィールドも加えていない。
  第 2 に、`vpsd` は適用の後に、配信用の写しが変わったエージェントにだけ全体状態を配る。
  第 3 に、エージェントは、接続の最初の全体状態より後に届いた、最後に適用した全体状態と同じ世代で同じ中身の全体状態を適用し直さない。
  直していないことがある。
  上限の内側の鍵の変更は、今もテーブルの全体を差し替え、全エージェントのルールの meter と `ct count` を作り直す。
  ピアだけを変えるトランザクションでテーブルを差し替えない形は、所有者の決定で 13 節に残した。
  単体試験で次を確かめた。
  初回の宣言、保存している鍵での再接続、適用に失敗している間の保存している鍵と最後に成功した鍵での再接続は数えない。
  適用に失敗した変更は数える。
  上限を超えた宣言は何も保存せず、公開せず、1008 で閉じ、確立した接続を置き換えない。
  登録をし直すと数え直す。
  鍵の宣言は宣言したエージェントにだけ配り、ルールの変更は全エージェントに配る。
  エージェントは同じ全体状態の繰り返しを適用せず、同じ世代で中身の違う全体状態と、新しい接続の最初の全体状態は適用する。
  ラボで、カーネルモードの `vpsd` とエージェント 2 台を動かし、一方の稼働中の `rotate-key` を続けて実行して、もう一方のルールの状態を修正の前と後で比べた。
  修正の前は、鍵の変更のたびにテーブルが差し替わり、もう一方のルールの meter と `flows_tcp` の要素が消えて、上限を超える新しい TCP の接続と UDP のフローが通った。
  差し替えの前の接続は残るので、同じ送信元が保持する TCP の接続は、鍵の変更のたびに上限 1 つ分ずつ増えた。
  もう一方のエージェントは同じ世代の全体状態を受け取り、カーネルモードのテーブルを公開し直した。
  修正の後は、もう一方のエージェントは全体状態を受け取らず、適用し直さなかった。
  上限の内側の変更では、修正の前と同じく状態が作り直された。
  上限を超えた変更は 1008 で断られ、テーブルは差し替わらず、meter と `flows_tcp` の要素と上限の効き目が残った。
  断られたエージェントの転送は、新しい鍵が通るまで止まった。
  断られたエージェントは通常のバックオフで再接続を続け、1 回分が戻った後の再接続で新しい鍵が通り、転送が戻った。
  その変更でもテーブルは差し替わった。
  ユーザー空間モードの `vpsd` では、鍵の変更の後も、もう一方のルールの送信元ごとのレートの状態が残った。
