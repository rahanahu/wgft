# 2026-10-02: review

- VPS のローカルの利用者についての前提を 11 節に書いた(2026-10-02、11 節、所有者の決定。
  コードは変えていない):11 節は、VPS の上のローカルの利用者やサービスについての前提を書いていなかった。
  VPS には信頼しないローカルの利用者やサービスを置かない前提とし、それらを wgft の脅威の範囲に含めないことと、既存の権限と鍵の守りはそのまま保つことを書いた。


- エージェントの dataplane の境目を `internal/agent/agentdp` へ移した(2026-10-02、7a.7 節。
  挙動は変えていない):`internal/agent` の `dataplane.go` にあった境目の interface、カーネルモードの実装だけが持つ任意の interface、1 回の読み取りの型、起動の失敗の型を、下位の package `internal/agent/agentdp` へ移して公開した。
  `doctor.go` にあった `agent doctor` のためのカーネルの読み取りの interface と、`dataplane_userspace.go` にあった `wg.keepalive` の上限の定数も同じ package へ移した。
  この定数はカーネルモードの実装も使うので、ユーザー空間モードの実装のファイルではなく境目に置いた。
  2 つのモードの実装は `internal/agent` に残した。
  移した型、フィールド、メソッドの名前を大文字に改め、実装と試験の偽物の同じ名前のメソッドも同じく改めた。
  宣言の本文は、名前と package の修飾子と、注釈の中の名前を除いて変えていない。
  試験の 2 つの偽物の dataplane が、全体状態の適用の前の準備の interface と変更の通知の interface をそれぞれ満たすことを、コンパイル時に検査するようにした。
  runtime はこれらの interface を型アサーションで探すので、名前がずれるとアサーションが黙って偽になる。
  偽物を使う試験が落ちるより先に、コンパイルの誤りとして気付けるようにした。
  7a.7 節の配置の木と本文に `agentdp` を加え、`TestAgentDataplaneBoundaryImports` が `agentdp` の import を検査する。


- `--admin-tailscale` の待ち受けがホスト自身からの接続を拒むようにした(2026-10-02、11 節、所有者の決定):この待ち受けは、VPS 自身から tailnet のアドレスへの接続を受け付けていた。
  この接続はループバックを通り、接続元が VPS 自身の tailnet のアドレスになるので、インタフェースへの縛りも接続元の検査も通る。
  11 節はこの到達を書いていた。
  所有者の決定により、VPS 上での管理は Unix ソケットに限り、tailnet の待ち受けは tailnet の他の端末だけを受ける。
  11 節の「ホスト自身からの接続の拒否」のとおり、接続元が接続の宛先かホストのどれかのアドレスと同じ接続を、HTTP を読まずに閉じる。
  CLI のフラグと HTTP の形は変えていない。
  ラボで、カーネルモードとユーザー空間モード(非特権の利用者)の両方について、tailscale0 という名前の veth に tailnet の帯のアドレスを付けて確かめた。
  修正前は VPS 自身から応答が返り、修正後は VPS 自身からの接続が、既定の接続元でも tailscale0 にある別のアドレスを接続元に選んでも閉じられ、veth の向こうの tailnet の端末からは応答が返った。
  縛ったインタフェースの外にある帯の内側のアドレスを接続元に選んだ接続は、修正の前から縛りで届かなかった。
  未確認:Tailscale そのものを動かしたホストでの確かめ


- 続いている `ip-mismatch` の検出を、観測のたびではなく、行を新しく作った回と連続 8 回に達した回だけログに書くようにした(2026-10-02、10.5 節。
  検知と保存は変えていない。
  変えたのはログの出方である):警告の記録は、同じ組の行があれば時刻を更新するだけだが、`vpsd` は更新でも `detected IP mismatch` を書いていた。
  食い違いが続く間は、15 秒ごとの観測のたびに同じ行が出た。
  記録は、確認済みの組での不記録、時刻の更新、行の新規作成を区別して返す。
  `vpsd` は、新規作成の回と、連続の観測が 8 回目に当たる回に書く。
  続く間は 1 回で、いったん止まった後の同じ組の再発と、再起動の後の検知(連続回数はメモリにしかない)でも 1 回ずつ書く。
  組が変われば行も新しくなるので、そのときも書く。
  確認済みの組は書かない。
  `ip-flapping` は往復を検出した回だけを記録するので、検出ごとに 1 行で変わらない。


- 許可一覧がどのアドレスも通さないホスト名の理由に並べるアドレスを、先頭の数個に絞った(2026-10-02、7b.2 節、10.2a 節。
  理由の文言は人が読む値で、7a.11 節の保証の外):カーネルモードのエージェントは、ホスト名が複数のアドレスに解決され、許可一覧がどれも通さないとき、解決のアドレスを全部並べた理由を書いていた。
  ホスト名は 253 バイトまで有効で、解決の結果は数十のアドレスになりうるので、hub の切り詰め(512 バイト)が、`server doctor` が `target_not_allowed` の分類に使う後半(許可一覧の設定の名前か `is not allowed`)を落とした。
  `server doctor` は `target_error` と判定し、許可一覧の設定を直す案内が出なかった。
  エージェントは先頭の 4 つのアドレスだけを並べ、残りは `and N more` と書く。
  4 つ以下のときの文言は変わらない。
  253 バイトのホスト名とポート範囲全体の拒否の追記を合わせても 512 バイトに収まることを、`internal/agent` の試験が実際の公開の組み立てと hub の切り詰めと `server doctor` を通して固定する。


- 接続文字列のポートを 10 進の数字に限り、エージェントに配るエンドポイントのポートを server の入口で番号に直し、接続文字列のホストを必須にした(2026-10-02、11b 節):入口の `validateHostPort` は `WGFT_WG_ENDPOINT` と `WGFT_AGENT_API_HOST` のポートを `net.LookupPort` で検査していたので、サービス名、符号付きのポート、0 を受け付けていた。
  エージェントの `ParseJoin` は 10 進の数字しか受け付けないので、`WGFT_AGENT_API_HOST` のこれらの値はエージェントが拒む接続文字列を作っていた。
  入口の検査を 1 から 65535 の 10 進の数字に改めた。
  `WGFT_WG_ENDPOINT` は、ユーザー空間モードのエージェントが 10 進の数字しか受け付けず、カーネルモードのエージェントが自分のホストのサービスの一覧で番号に直していた。
  所有者の決定により、拒まずに、入口でポートの部分だけを UDP として番号に直し、ホストは書かれたまま残すことにした。
  番号を引くホストが server のホストに移るので、古い設定が同じ番号で動き続けるとは限らない(11b 節)。
  `WGFT_AGENT_API_HOST` を省いた場合の接続文字列も、`WGFT_AGENT_API` のポートの部分をそのまま入れていたので、待ち受けと同じ規則で番号に直して書くようにした。
  エージェントの `ParseJoin` は、ホストが空の接続文字列を受け付けて自分のホストへ接続していたので、ホストを必須にした。
  誤りの値の一覧に `errJoinNoHost` を加え、どの誤りも接続文字列の断片を引用しない約束は保っている。
  今まで受け付けていた設定への影響は 11b 節に書いた。
  ホストの単体テストで次を確かめた。
  入口が `WGFT_AGENT_API_HOST` のサービス名、符号付き、0 のポートを終了コード 3 で拒み、範囲外のポートも拒むこと。
  `WGFT_WG_ENDPOINT` の数字、符号付き、先頭に 0 を付けた数字、サービス名、IPv6 の形を番号に直し、ホストを IP アドレスに置き換えないこと。
  番号に直せない名前、TCP にだけ定義のある名前、0、範囲外の値を終了コード 3 で拒むこと。
  直した値が `Options` に入り、配る値と管理用 API の値が同じであり、「値と出所」の表示が入力の値のままであること。
  接続文字列のポートの導き方。
  ホストが空の接続文字列の拒否と、その誤りがトークンを引用しないこと。
  未確認:ラボと実機での確認、更新の前にサービス名のエンドポイントで動いていたカーネルモードのエージェントが、配られる文字列の変化の後もトンネルを保つこと
