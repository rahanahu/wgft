# 2026-10-02: resource-guard

- 待ち受けのポートをホスト名やサービス名で書いた設定でも、管理用 API とエージェント用 API のポートを予約するようにした(2026-10-02、5.3 節、5.4 節、11a 節):予約ポートの組み立て(`internal/vpsd/admin` の `ReservedFromServerInfo`。
  `Daemon.reserved`、CLI の `--dry-run`、Web UI の読み込みの確認が共有する)は、`admin_addr` を `netip.ParseAddrPort` で解析し、`agent_api_port` も `0.0.0.0:` を前に付けて同じ関数で解析していた。
  この関数は IP アドレスと 10 進のポートしか受け付けないので、`localhost:8686`、`:8686`、`0.0.0.0:https` のような値は何も予約しなかった。
  一方で起動の入口(`cmd/wgft` の `validateListenAddr`)は `net.LookupPort` でポートを検査してこれらを受け付け、待ち受けはそのポートを bind する。
  このため、待ち受けと同じポートのルールを `vpsd` が受理していた。
  組み立てを待ち受けと同じ規則に揃え、ホストの部分を問わず、ポートを `net.LookupPort` で番号に直すようにした。
  番号に直せない場合は誤りにし、`vpsd` の起動、`--dry-run`、確認の画面をそれぞれ止める。
  そのポートを予約から外して続行すると、同じ欠陥が残るためである。
  この改訂の前に保存した、そのポートに重なるルールは、残したままのバッチを拒ませる(11a 節)。
  ホストの単体テストで、ホスト名とサービス名の形の予約、数字の形の予約が変わらないこと、名前を直せない場合の誤り、実際の待ち受けが bind したポートとの一致、保存済みのルールへの影響を確かめた。
  サービス名の形は、特権の要るポートに直るので実際の待ち受けでは確かめず、`net.ResolveTCPAddr` が返すポートとの一致で確かめた。
  未確認:ラボと実機での確認、別のホストから管理用 API に接続する CLI がサービスの名前を server と違う番号に直す場合


- 待ち受けのポートの予約と接続文字列のポートの検査が変える互換性の約束を、7a.11 節に書き足した(2026-10-02、7a.11 節。
  挙動は変えていない):待ち受けのポートをホスト名やサービス名で書いた設定でも予約する変更(5.3 節、5.4 節、11a 節)と、接続文字列のポートを数字に限り `WGFT_WG_ENDPOINT` のポートを入口で番号に直す変更(11b 節)は、挙動と理由を各節と改訂の記録に書いていたが、互換性の保証の節には載せていなかった。
  これまで受理していた `listen_port` が拒まれ、これまで起動していた設定が起動しなくなりうる変更なので、公開鍵の変更の頻度の上限と同じく、加算でない変更として並べた。
  書いたのは、保存済みのルールへの影響と解き方、起動の拒否の条件、設定の値の意味との関係、名前を番号に直すホストの移動、ホストが空の接続文字列の拒否、変えないサーフェスと変わる値である。
  内容は、既に 5.3 節、5.4 節、11a 節、11b 節に書いてある挙動と、それぞれの変更のコードに合わせた。
  新しい挙動は加えていない。
  未確認:更新の時点の挙動の、ラボと実機での確認
