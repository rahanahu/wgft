# 2026-09-20: control-plane

- `server check` がルールの listen port も input firewall で検査する(2026-09-20):同じ実機で、同じ input の構成のままユーザー空間モードのルール(TCP のポート、`vps_mode=kernel` 相当)を有効にすると、`active` のまま外部からの応答が無いことを確かめた。
  ユーザー空間モードは `vps_mode` の区別に意味を持たず、全ルールが `vpsd` 自身の host ソケットで受けるためである(6.3 節)。
  カーネルモードでは Transparent なルールが他テーブルの DNAT と forward を経由し input を通らないため、対象になるルールの範囲が両モードで異なる。
  6.2・6.3 節に、対象になるルールの listen port(範囲を含む)を input の `policy drop` に対して検査し、必要な accept の行を提示することを追記した。
  `internal/platform/linux.InputPortSuggestions` は、既存の accept 済みの規則と重ならない場合だけ提示するように改め、単一ポートと範囲の両方を扱えるようにした。
  あわせて、記録済みモードと設定が食い違うときの `server check` の警告文が分かりにくかったため、`server run` が起動時に持つモード変更の関門(3.3 節)を指す一文に書き直した。
  ラボ(wgft-lab2)で、同じ input policy drop のテーブルのまま、カーネルモードのプロキシルールとユーザー空間モードの通常ルールの両方について、`server check` が listen port の提示を出し、提示された行を足すと消えることを確認した。
  未確認:iptables-nft が翻訳した accept 規則(xt の match extension によるポート一致)からの既存 accept の検出。
  今回の実装はネイティブ nft の式(`meta l4proto` と `payload` の一致)の形だけを読む

- ルールごとの天井を条件として明記(2026-09-20、7a.10 節、レビュー反映):予約の判定だけでは、他のルールがフローを持たないときの 1 本の上限が `T - (N - 1) × q` になり、`q` の切り捨てのために `C = ceil(T/2)` を 1 超えることがあった(`T = 2048`、`N = 4` で 1025)。
  `N ≥ 2` のとき `u_r < C` を別の条件として置き、拒否の理由 `rule_cap` を加えた。
  単体テストは、1 本に受け付けを続けたときの最大がちょうど `C` になることを、すべての `T` と `N` で確かめる

- secret を含む dotenv の緩いパーミッションを警告する(2026-09-20、11a 節、セキュリティ点検の指摘):`agent.env` が group か other から読める状態のまま置かれても、agent は何も言わずに起動していた。
  secret な spec(`WGFT_JOIN`)の値がファイルから読まれていて、かつそのファイルが other から読めるとき、起動時に英語で 1 行だけ警告するようにした。
  判定は other のビット(`0o007`)だけを見て、group のビットは対象にしない。
  `agent.env` の推奨パーミッションはすでに 0640(root 所有、グループ `wgft`)であり、これは固定の `User=wgft` で動く unit のための意図した共有であって穴ではないため、点検の指摘にあった group も含む判定(`0o077`)をそのまま実装すると、この推奨どおりに設定した環境でも起動のたびに警告が出てしまう。
  secret を持たない `server.env` はどのパーミッションでも警告の対象にならない(その設定に `Secret: true` な spec が無いため)。
  Windows では行わない(11a 節に既にある DACL の扱いと別枠のため)。
  単体テストで、world 権限(0644、0602)は警告し、0640 と 0600 は警告しないこと、値が環境変数から来た場合と secret な spec を持たない config は警告しないこと、`loadConfig` から実際に呼ばれることを確かめた

- ルールを受け付けている集合に入れるのは bind の後にする(2026-09-20、7a.10 節の `A` の定義):エージェントの `Apply` の経路は、待ち受けの記録と Resource Guard の枠を作った後に bind していたため、bind の最中と bind に失敗した待ち受けのルールが、その間だけ受け付けているルールの集合 `A` に入っていた。
  `N` と `q` は admission の判定に使うので、この間は他のルールが新しいフローをルール 1 本の上限や予約で拒まれうる。
  `openLocked` を bind から始める形に改め、`resource.Pool` に受け付けていない状態の枠を作る `PendingListener` を加えて、bind が成功した待ち受けだけを、中継を始める前に受け付けにすることにした。
  bind に失敗した待ち受けの枠は受け付けないままなので、そのルールは `A` に入らない。
  `Prepare`/`Commit` の経路(server のユーザー空間モード)と `proxyrelay` は、bind の済んだ待ち受けにだけ枠を付けており、順序は変えていない。
  ホストの単体テストで、bind を止められる Network を使い、bind の最中は受け付けているルールの数と予約が動かないこと、その間も既にあるルールが予算のすべてを取れること、bind に失敗したルールがどの時点でも `A` に入らないこと、後から bind が成功した待ち受けはその時点で `A` に入ること、許可一覧の外の宛先で待ち受けを開かないルールが `A` に入らないことを確かめた。
  順序を元に戻す 2 通りの実験で、この確認が落ちることも確かめた
