# 2026-09-27: userspace

- ユーザー空間のトンネルの出力を pull に改め、gVisor と wireguard-go の間を深さ 1024 の FIFO 1 つにした(2026-09-27、所有者の決定):以前の `internal/nettun.Device` は、netstack が送り出すパケットを、gVisor が呼ぶ `WriteNotify` の中で同期して wireguard-go の読み取りへ渡していた(push)。
  この形では、送り出す側の goroutine が wireguard-go の読み取りを待つ。
  新しい形では、TUN の `Read` が gVisor の `channel.Endpoint` のキュー(深さ 1024。
  以前と同じ)から 1 件ずつ取り出し、キューが満杯なら新しいパケットを捨て、送り出す側を待たせない。
  受け渡しの channel と、閉じたことを知らせる channel(2026-09-24 の記録)は不要になり、`Close` は読み取りの取り消しで待っている `Read` を戻す。
  約束は 7 節の「netstack の出力」「出力のキューの隔離」「1 回の読み取りの件数」「ソケットのバッファの条件」の各項と、滞留のメモリの上限の段落に書き、6.3 節、7a.5 節、7a.10 節から参照した。
  プロトコルごとやルールごとのキュー、公平化、複数の件をまとめて返す `Read` は採らなかった。
  この構造は、評価した候補のうち利用者から見た基準を満たした、最も単純な上限のあるデータプレーンである。
  まとめて返す形を退けた理由は、wireguard-go の送信のキューがパケットではなく 1 回の `Read` の結果の入れ物を数えるので、k 件ずつ返すと滞留のメモリの上限が k 倍になることである。
  採用は、本番の unit と同じ権限(server は root でなく `CAP_NET_ADMIN` と `CAP_NET_BIND_SERVICE` だけを持ち、エージェントは root でなく capability を持たない)と、同じソケットのバッファの条件(`net.core.rmem_max` と `net.core.wmem_max` を 7 MiB にし、すべての WireGuard のソケットが受信と送信に実効 14 MiB を得たことを試行ごとに確かめた)のラボで、push の版と比べて決めた。
  分かったことは次のとおりである。
  通常の負荷では、軽い負荷と中程度の負荷の遅延の p95 と p99 が、あらかじめ決めた許容幅の中で push の版に劣らず、送る量の少ない通信の失敗はどちらの版にも無かった。
  何も流していない状態で、ICMP は pull の出力を通った(カーネルモードの server とユーザー空間モードのエージェントの組)。
  飽和させた状態では、pull の版は短い TCP の接続がすべて成立し、push の版は echo が期限切れになった。
  送る量の少ない UDP の欠落は、pull の版のほうが少なく、最も長く続いた欠落も短く、負荷を止めた後は欠落しなかった。
  負荷の間は散発的な欠落が続いた。
  欠落は主に下流のカーネルの UDP の受信ソケットで起きており、出力のキューではなかった。
  この受信ソケットはフローを区別しない。
  測った値は採用の判断の根拠であり、製品が保証する値ではない。
  単体試験では、キューから順に取り出すこと、読み手が止まっても送り出す側は待たずに戻り、キューが 1024 件を超えて受け付けないこと、`Read` と送り出しと `Close` が競合しても待ち合わないこと、読み手が止まったまま TCP の dial があっても `Close` が戻ること、キューが満杯の間は ICMP、UDP、TCP の応答が失われ、空けた後に戻ること、UDP の拒否の ICMP と TCP の RST が空けた後に届くことを確かめた。
  未確認:コンテナ、Windows、macOS でのソケットのバッファの条件の確かめ方と過負荷の見え方。
  ソケットのバッファの条件を満たさない環境での過負荷の見え方。
  飽和させた状態での ICMP は測っていない。
  ユーザー空間モードの server のホストにはトンネルのインタフェースが無く、ホストからトンネルのアドレスへ ICMP を送れないので、ユーザー空間モードの server とエージェントの組では ICMP の確認は当てはまらない

- ユーザー空間のトンネルの IPv4 の断片を gVisor の再組み立てに渡さず、TUN の入口の有限な表で組み立てるようにした(2026-09-27、所有者の決定):以前の `internal/nettun.Device` は、受け取った断片をそのまま gVisor に渡していた。
  固定版の gVisor の再組み立ては、表が空の状態で新しい datagram の断片が届くたびに、期限の処理のタイマーを前のものを取り消さずに作り直す。
  そのため、断片化された datagram ごとにタイマーが 1 つ期限の 30 秒まで残り、保持する量は再組み立ての上限ではなく断片の届く速さで決まる。
  1 プロセスの試験で、大きい UDP の中継の間にヒープが増え続け、増分がこのタイマーから割り当てられていることをヒーププロファイルで確かめた。
  新しい形では、TUN の `Write` が断片をすべて wgft の表に渡し、完成した datagram だけを gVisor に渡す(7 節)。
  完成した datagram はトンネルの MTU を超えるが、gVisor はそのまま受け取って配送する。
  表が満杯のときに新しい断片を拒む形を先に評価したところ、上流の損失で断片の欠けた少数の datagram が表を期限の 30 秒占め、その間は全ルールの断片化された UDP が完成しなかった。
  送信元ごとの上限は、その失敗が 1 つの送信元(エージェントのトンネルのアドレス)から起きるので直さない。
  期限の短縮は 1 秒の掃除の周期より短くできず、高い率では同じ結果になる。
  byte で数える上限は満杯になるまでの時間を延ばすだけである。
  そこで、最も古い未完成の datagram を追い出す形を採った。
  評価の版のラボでは、表が満杯のまま回り続ける間も、断片が続けて届く正常な datagram と、断片化しない UDP と TCP が通り、負荷を止めると表は期限の後に空に戻った。
  評価の版には、この変更に含めない部品も入っていた。
  この変更の版では、両モードの通しのシナリオ(`lab/e2e.sh`)の大きな UDP の確認が通った。
  ユーザー空間モードの server に 1、4、11、16 台のエージェントから大きい断片化された datagram を同時に送る観測では、どの台数でも追い出しは起きず、server の表が組み立てた datagram はすべて client に届いた。
  この観測には、表の計数をログに出すだけの観測用の版を使った。
  option の不正な断片への Parameter Problem は評価の版の振る舞いを保ち、固定版の gVisor との 3 つの既知の差を試験で固定した(7 節)。
  TUN の `Write` は、バッチの中の 1 件を処理できなくても残りを処理するようにし、捨てた断片を誤りとして返さないようにした。
  未確認:同時に組み立てを待つ datagram が表の枠を超えるほど多くのピアの断片が交互に届く条件での完成の割合(観測では追い出しが起きなかった)。

- ユーザー空間のトンネルの UDP の受信を、Device ごとの予算と endpoint 1 つの上限で数えるようにした(2026-09-27、所有者の決定):以前の `internal/nettun.Device` は、この Device 宛ての UDP をそのまま gVisor に渡し、`DialUDP` と `ListenUDP` は gVisor の `gonet.UDPConn` を返していた。
  固定版の gVisor の UDP の endpoint は受信のキューを payload の byte だけで制限するので、payload の無い datagram は件数の制限を受けず、1 件ごとの管理の構造もその byte に数えられない。
  新しい形では、TUN の入口がこの Device 宛ての完成した UDP を会計に通し、Device ごとの予算と endpoint 1 つの上限で予約してから gVisor に渡す(7 節)。
  受理は宛先の endpoint の公開の統計の差で判定する。
  評価の版では、この会計を Device 全体の 1 つのロックで守り、gVisor への配送の間もそのロックを持っていた。
  この形では、ロックを持つ処理が止められると全ピアの入力が待つので、ロックを帳簿の加減の間だけに狭め、同じ endpoint への配送、読み取り、閉鎖だけを endpoint ごとのロックで直列にした。
  公開の統計の差で受理を判定するかぎり、同じ endpoint への配送は直列にする必要がある。
  直列にしない場合に、拒まれた配送を受理と読む手順があることを、試験で固定した。
  endpoint 1 つの上限は、評価の版の Device ごとの予算だけの形で、エージェントの 1 つのルールの宛先の名前解決を応答しない DNS に向け、そのルールに小さい datagram を送り続けたところ、同じエージェントの別のルールの UDP の大半が失われたため加えた。
  同じ条件で、以前の形(gVisor の endpoint ごとの受信のキューだけ)では失われなかった。
  予算の 1/4 の上限を加えた評価の版と、この変更の版では、同じ条件で別のルールの UDP は失われなかった(各 1 回)。
  1/4 は 4 つの endpoint までを守る保証ではない(7 節)。
  会計の不変条件の違反を検出したら Device の UDP を止め、ログと `agent doctor` で知らせる形にした(所有者の決定)。
  `agent doctor` のこの検査は終了コード 1 を動かし、ユーザー空間モードの `vpsd` ではログだけで知らせる(所有者の決定。
  理由は 7 節と 10.2c 節)。
  IPv4 の Total Length より後ろの byte は、wireguard-go の切り捨てに頼らず wgft が切り捨てる。
  Device は gVisor の stack を外に出さなくなり、UDP の endpoint は登録表だけが作る。
  この 2 つは試験で固定した。
  `DialUDP` と `ListenUDP` が返す接続の期限、短い読み取り、誤りの形は、同じ手順を `gonet.UDPConn` と比べる試験で固定し、`Close` の後の読み取りが `net.ErrClosed` を返すことだけが違う。

  拒否は endpoint 1 つの上限ではなく Device 全体の byte で起き、同時に届く応答の合計が 1 MiB を超える形だった。
  UDP の経路の保持点の反例のレビューで、受信のキューの datagram 1 件の Go のヒープの費用を試験で測り、予算の byte との換算を得た(7 節の「予算と実際の費用の関係」)。

  4 MiB は、観測した通常の負荷を収める余地があり、資源の上界として十分に小さく、実際の費用も前述の換算で説明できる値として採った。

- wireguard-go に 1 回の受信で 1 件だけを渡す UDP のバインドの包みを入れた(2026-09-27、所有者の決定):以前は、wireguard-go の標準のバインドをそのまま device に渡していた。
  Linux の標準のバインドは 1 回に 128 件まで読み、wireguard-go は 1 回の受信の結果を 1 つの入れ物としてピアごとの受信のキュー(入れ物 1024 個)に入れ、1 件ごとに 64 KiB のバッファを持つので、受信の向きの滞留の構造の上限はピアごとに 1024 × 128 × 64 KiB(約 8 GiB)であった。
  有限ではあるが、プロセスの資源の上界として説明する値としては大きすぎ、外部の入力で大きく保持しうる経路として以前から塞ぐ予定の保持点であった。
  新しい形では、標準のバインドを包み、内側を内側の 1 回の件数と同じ数のバッファで読んで、wireguard-go の呼び出しごとに 1 件ずつ渡す(7 節の「WireGuard の受信の 1 回の件数」)。
  上限はピアごとに 1027 × 64 KiB 以下(約 64 MiB)になる。
  読み取りの syscall の数、内側の `recvmmsg` と GRO、sticky socket は変わらない。
  送信は変えない。
  送信側の GSO はもともと使われていない。
  TUN の `Read` が 1 件ずつなので、送信に渡るパケットが常に 1 件のためである。
  失うのは wireguard-go の Linux の経路の監視で、送信元の消去は wireguard-go のタイマーに残る。
  Linux のエージェントで古い送信元アドレスが残ったまま出口だけ変わる場合の回復がタイマーに依存することを、既知の trade-off として 7 節に書いた。
  ピアの受信のキューが満杯のときに同じ address family の他のピアの読み取りも待つ構造は包みの前後で同じで、包みで変わるのは待ちに入るまでにそのピアが保持できるパケットの数であることを、7 節と 6.3 節に書いた。
  退けた形は、自前のバインド(`recvmmsg`、GRO、sticky socket、経路の監視をすべて失う)、wireguard-go の改造(上流を改造しない方針に反する。
  pool に上限を置く形は、受信と送信が pool を取り合って止まる循環を作る)、包みの外で受信の件数を数える形(wireguard-go の中で捨てられる分を外から数えられない)、1 回に 2 件以上を渡す形(上限がその倍になる)、送信の失敗時に送信元を外して送り直す補い(送信側まで変えると 1 回の件数の変更の評価と原因の分離が難しくなる)である。
  単体試験では、内側に内側の 1 回の件数と同じ数のバッファを渡すこと、1 件ずつ順に渡すこと、内側の誤りを同じ値で返すこと、閉じた後は手持ちがあっても `net.ErrClosed` を返すこと、内側の 1 回の件数が 1 なら包まないこと、device に渡すバインドの 1 回の件数が 1 であることを固定した。
  ラボでは、この変更の前後を同じ使い捨ての VM で、実行前に固定した対称の順(前、後、後、前、前、後)と判定の線で比べた。
  場面は、通常の負荷の TCP の throughput の 2 方向、静かな状態と TCP と同時の UDP の往復の遅延と欠落、CPU 時間、CPU を絞ったエージェントへの洪水の後の回復と RSS、`vpsd` に 2 台のエージェントを置いて一方の応答の洪水の横で他方の低頻度の通信を測る場面(連続の洪水と短い burst の列)である。
  通常の利用の条件で判定できた場面では、明確な退行は無かった。
  TCP と同時の往復の遅延の p99 では、平均は線の内側だったが、変更後の 1 run が変更前の 3 run の幅を超えた。
  2 台のエージェントの連続の洪水の場面は、事前に決めた妥当性の条件(洪水を受けるルールの公開側ソケットで drop が無いこと)を前後の両方が満たさず、判定不能とした。
  どの場面でも、VM では wireguard-go の受信のキューを満杯にできなかった(CPU を絞った側では受信の goroutine も同じ上限で遅くなる)。
