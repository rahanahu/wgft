# 2026-09-27: security

- UDP の応答のバッファの貸し出しにプロセス全体の枠を置き、`vpsd` の公開側への送信を待たない形にした(2026-09-27、所有者の決定):以前の `relay` は、宛先からの応答が届いたセッションの goroutine が、共有プールから 65535 バイトのバッファを上限なしに借りていた。
  同時に借りる数はセッションの数で決まり、応答のバッファの保持の上限は同時フロー数の上限に比例していた。
  新しい形では、プロセス全体で同時に 64 個までの枠を置き、枠が無いセッションは空くか、そのセッションが閉じるまで待つ(7 節の「応答のバッファの枠」)。
  待つ間のデータグラムは宛先側の接続の受信のキューに留まる。
  同時に、`vpsd` の公開側のソケットへの送信を 1 回の試みに改め、送信バッファが満杯なら捨てて枠を直ちに返すようにした(7 節の「公開側への応答の送信」)。
  枠を有限にするだけで公開側の送信が待てるままだと、詰まった 1 つのルールのセッションが枠を全部持ち、無関係なルールが借りられなくなる、という有限の資源による新しい飢餓を作るためである。
  この形は、詰まった待ち受けのセッションが宛先側を読まずに UDP の受信の予算を占める経路も同時に閉じる。
  退けた案は、枠が無いときに捨てる(待てば失われないデータグラムを捨てる)、データグラムの大きさを先に知って小さいものを枠の外で扱う(OS ごとに手段が違い、Windows には無く、必要性が実測されていない)、セッションごとに小さいバッファを持ち続ける(切り詰めた応答は読み直せないので同じ手段が要り、その上で無通信のセッションもバッファを持つ)、待ち受けごとに枠を分ける(上限が待ち受けの数に比例する)である。
  ラボでは、ルール A の応答だけを `htb` の遅いクラスに入れて `vpsd` の公開側のソケットの送信バッファを満杯にし、無関係なルール B の成功率と往復の遅延を、以前の形、枠だけを入れた形、この形の 3 つで比べた。
  この形では B の応答は負荷の間も失われず、遅延の p99 は事前に決めた許容の内に収まり、負荷の後に戻った。
  以前の形でも、この条件では B の応答は失われず、詰まった待ち受けが UDP の受信の予算を使い切って B を止める経路は再現しなかった。
  UDP の受信の予算は datagram の費用が残りを超えるときに拒むので、A の応答で残りが尽きかけても、A の応答より小さい B の探りの応答は残りに収まって通る。
  この探りの作りでは、その経路の有無を判定できなかった。
  枠だけを入れた形では、A のセッションが枠を全部持つことと、B の往復に枠の待ちの分の遅れが現れることを観測した。
  通常の負荷として、多数のセッションが同時に応答を受けるルールと小さな往復のルールを同時に流し、枠の待ちの時間と B の遅延を以前の形と比べ、事前に決めた許容の内に収まることを確かめた。
  枠の待ちは多数起きたが、その最長は利用者に意味を持つ遅延の目安より短く、B の遅延と多数のセッションのルールの応答の損失は以前の形と同程度だった。
  判定の条件は流す前に固定し、結果を見て変えていない。
  測った値は採用の根拠であり、製品が保証する値ではない。
  混雑していない経路での応答の burst も、以前の形と比べた(7 節の「公開側への応答の送信」)。
  公開側のソケットの送信バッファが Linux の既定のままでは、送信バッファを超える burst で以前の形より多くを捨て、以前の形もその burst の一部を別の場所で失っていた。
  このため、公開側の UDP ソケットに固定の送信バッファ(`setsockopt` に 2 MiB)を要求する形を加えた(7 節の「公開側のソケットの送信バッファ」、所有者の決定)。
  この形で同じ burst の比較を流し直したところ、公開側の送信バッファでの drop は無くなり、以前の形と同程度に届く段と、以前の形より届かない段が残った。
  後者では送信バッファの drop も受信の会計の拒否も無かった。
  ルールをまたぐ波及の条件と通常の負荷の条件も同じ形で流し直し、波及の条件は保たれ、通常の負荷では事前に決めた線をわずかに外れる値があった。
  この 2 つの不成立は取り消さず記録に残し、原因を分けるための比較を 1 回行った(所有者の決定)。
  比較は、同じ VM で以前の形とこの形を実行前に固定した対称の順で交互に流し、経路の各地点の計数を同じ run から取るものである。
  以前の形より届かなかった burst について、固定した文言どおりの判定は「run の揺れで判定できず」で、平均はこの形の方が高かった。
  したがって、この形が以前の形より損失を増やしているとは言えない。
  損失の地点は、どちらの形でも主因がエージェントの LAN 側のカーネルのソケットの受信バッファで、残りは `vpsd` の gVisor の endpoint の受信バッファであり、この形が以前の形より多く失う地点は無かった。
  通常の負荷は事前に決めた 4 つの判定をすべて満たし、損失はどちらの形でも UDP の受信の予算による拒否とエージェントの netstack の出力のキューだった。
  固定の順で流した以前の 2 回では大きな差を観測したが、原因を分ける対称の比較では再現せず、この形に帰属する損失の地点も見つからなかった。
  以前の 2 回の不成立は読み替えずに並べて残す。
  未確認:Windows と macOS のエージェントでの枠の動作、実際の VPS の送信の経路で送信バッファが満杯になる条件、固定の順で見えた大きな差の原因、新しい送信バッファを超える burst の挙動、エージェントの公開側の送信の待ちが実際に続く時間。
  エージェントの LAN 側のカーネルのソケットの受信バッファは、この変更では変えない(所有者の決定。
  UDP の保持点の反例のレビューで扱う)
