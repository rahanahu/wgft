# 2026-09-30: review

- userspace backend の `Retiring` の UDP の listener が、競合の窓の中で新しい送信元のセッションを作らないようにした(2026-09-30、7a.3 節):UDP の読み取りのループは、受け付けの印をデータグラムを読んだ直後にだけ確かめていた。
  このため、その後の Admission Policy の判定や宛先への dial の間にルールが fail-closed になって listener が `Retiring` になると、新しい送信元のセッションが作られ、応答も返っていた。
  そのセッションは `Retiring` の listener を閉じずに残す理由にもなった。
  印を Admission Policy の判定の後と、セッションの表への登録の時点(listener のセッションの錠の下)でも確かめ、下りていればデータグラムを捨て、取った枠を返すようにした。
  `Retiring` への移行は印を下ろしてから同じ錠の下で接続元制限の判定をするので、登録の時点で印が立っていたセッションはその判定の対象になる。
  再開の順(受け付けの印を立ててから Resource Guard の枠を受け付けにする)は変えていない。
  単体テストで、判定の中、dial の中、登録でセッションの錠を取った直後のそれぞれで読み取りのループを止めている間に listener を `Retiring` にすると、新しい送信元に応答が返らず、宛先にもデータグラムが届かず、成立済みのセッションは中継を続けることを確かめた。
  判定の中で止めた場合は、フロー予算の枠を取らず、宛先へ dial もせず、送信元ごとの枠だけが 1 度返る。
  dial の中と錠を取った直後で止めた場合は、宛先への接続を閉じ、送信元ごとの枠とフロー予算の枠が 1 度ずつ返る。
  錠を取った直後で止める試験は、印を錠を取る前に読む形では落ちる。
  TCP の listener は変えていない。
  Admission Policy の判定の間に `Retiring` になった接続は、既存の登録の時点の確認(待ち受けを止めると閉じる印)で中継せずに切られる。
  登録を終えてから宛先への dial の間に `Retiring` になった接続は、成立済みの接続として接続元制限で判定され、残る。
  この 2 つは試験に残さない使い捨ての単体テストで確かめた。
  ラボのユーザー空間モードでは、通しテストと、fail-closed と UDP の中継を含むライフサイクルの確認が変わらず通ることを確かめた。
  未確認:netstack の UDP の listener での再現と、ラボでの競合の窓の再現。
