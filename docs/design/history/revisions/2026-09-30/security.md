# 2026-09-30: security

- 設定ファイルの構文の誤りの文言から値を除いた(2026-09-30、11a 節、セキュリティ点検の指摘):dotenv の構文の誤り(`KEY=value` の形でない行、キーの空白、引用符で始まる値、値の空白)の文言は、行の中身か値をそのまま示していた。
  `WGFT_JOIN` を引用符で囲んで書くと、接続文字列の全文が起動の失敗の文言としてジャーナルに残り、ジャーナルを読める利用者が、まだ使われていない接続文字列の期限の内に先に登録できた。
  文言はファイル名と行番号と、英数字と `_` だけからなるキーの名前だけを示すようにした。
  行が壊れていると `=` より前に値の一部が入りうるので、その形でないキーは名前も出さない。
  直し方の案内は保つ。
  単体テストで、引用符、値の空白、`=` の無い行、キーの空白、`=` の前に値の一部がある行のどれでも、文言に値が出ず、ファイル名と行番号が出て、終了コードが 3 のままであることを確かめた。


- エージェント用 API に、認証を通っていない接続の送信元ごとの上限を設けた(2026-09-30、11 節、セキュリティ点検の指摘):同時接続数の上限(4096)は全体に 1 つだけで、送信元ごとの試行制限は、TLS のハンドシェイクとリクエストのヘッダを読み終えた後のハンドラの中でしか効いていなかった。
  このため 1 つの送信元が、ハンドシェイクやヘッダを送り終えない接続と、応答の後に残る keep-alive の接続で全体の上限を埋め、その間、他のエージェントの登録と stream の再接続を止められた。
  既存の転送は止まらない。
  accept の時点で送信元ごとに認証を通っていない接続を数え、上限(16)を超える接続を TLS のハンドシェイクの前に閉じるようにした。
  stream は恒久トークンの確認の直後に数から外す。
  あわせて keep-alive をやめ、応答を返したら接続を閉じるようにした。
  エージェントは接続のたびに新しい HTTP のクライアントを作るので、keep-alive の接続は使い直されていなかった。
  単体テストで、上限を超えた接続が閉じられること、別の送信元の接続と IPv6 の同じ /64 の接続の扱い、閉じた接続の枠が戻ること、TLS の待ち受けの全体で認証を通った接続が数から外れること、恒久トークンの確認を通らなかった stream の要求は数から外れないこと、応答の後に接続が閉じることを確かめた。
  多数の送信元から全体の上限を埋める攻撃には効かない。
  ラボの結合テストで、同じ NAT の後ろにいる 5 台のエージェントの登録と stream が通ること、server の再起動の後にエージェントがつながり直すことを確かめた。
  5 台は上限より少ないので、認証を通った stream が上限に縛られないことは、上の単体テストで確かめた。
