# 2026-09-30: userspace

- 管理用 API の Unix ソケットの作り方を改めた(2026-09-30、11 節、セキュリティ点検の指摘):起動のときにソケットのパスにあるものを種別を見ずに消し、`net.Listen` が umask の権限で作った後に、パスで(symlink を辿って)0600 に chmod していた。
  `WGFT_ADMIN` を誤ってデータベースのファイルに向けると、そのファイルを黙って消した。
  他の利用者が書き込めるディレクトリに置くと、chmod までの間は umask の権限で開いており、chmod は差し替えられた symlink の先に効いた。
  root で動く `vpsd` では、その先は任意のファイルになりうる。
  同梱の unit(`RuntimeDirectoryMode=0700`、`UMask=0077`)の下では、どれも起きない。
  消すのはソケットだけにし、それ以外は symlink を含めて起動の誤りにした。
  ソケットは umask を 0177 に狭めて作り、bind が作った瞬間から 0600 にする。
  パスへの chmod はやめたので、symlink の先の権限を変えることは無くなった。
  作った直後に、0600 のソケットであることを symlink を辿らずに確かめ、違えば消さずに誤りにする。
  他の利用者が書き込めて sticky ビットの無いディレクトリは警告だけにした。
  起動を止めると、今まで動いていた配置を止めることになるためである。
  このディレクトリでは、作った後のソケットの差し替えは今も防げない。
  単体テストで次のことを確かめた。
  通常のファイル、symlink、ソケットを指す symlink を消さずに誤りにし、symlink の先の権限も変えないこと。
  前の起動のソケットは作り直すこと。
  umask 022 の下でも作った瞬間から 0600 であること。
  作った直後に通常のファイルや symlink に差し替えられたら誤りにし、差し替えられたものを消さないこと。
  警告がディレクトリの権限と sticky ビットに従うこと。
  bind が umask を除いた権限でソケットを作ることは、Linux と macOS の CI の単体テストで確かめた。

- VPS の中継が切った TCP のセッションを、エージェントの中継が宛先の閉じるのを待たずに終えるようにした(2026-09-30):VPS の中継が成立済みの TCP の中継を切ると(接続元制限の変更、Retire、ルールの削除と無効化、エージェントの削除、ユーザー空間モードの `CloseSessions`)、エージェントへの接続は通常の `Close` で閉じており、エージェントには FIN が届いていた。
  エージェントの中継はそれをハーフクローズとして扱い、宛先へ FIN を送った後も宛先からの読み取りを続けるので、FIN を受けても閉じない宛先では、宛先への接続と枠が宛先が閉じるまで残った。
  RST が届いた場合も、`internal/netpipe` は読み取りの誤りを EOF と区別せず、同じくハーフクローズとして扱っていた。
  `internal/netpipe` は、片方向が EOF 以外で終わったときに両側を閉じるようにした(6.2 節)。
  VPS の中継は、切るときにエージェントへの接続を RST で切るようにした(6.2 節、6.3 節)。
  プロキシの中継のカーネルモードの接続は `SetLinger(0)` で、ユーザー空間モードの netstack 越しの接続は `Abort` で切る。
  `Abort` のために、`internal/nettun` の `DialTCP` は `gonet.DialContextTCP` の手順を写し、`Abort` を持つ接続を返すようにした。
  EOF によるハーフクローズの扱いは変えていない。
  単体試験では、片側の RST と書き込みの失敗で両側が閉じること、EOF の後も反対向きが続くこと、netstack 越しに届いた RST でエージェントの中継が宛先への接続と枠を返すこと、VPS の中継が切った接続の相手に RST が届くことを確かめた。
  ラボでは、ユーザー空間モードのエージェントと FIN を受けても閉じない宛先を、ユーザー空間モードの VPS の通常のルールとプロキシのルール、カーネルモードの VPS のプロキシのルールで組み合わせ、VPS が接続元制限の変更で切ったセッションについて、エージェントが宛先への接続を持ち続けないことを確かめた。
  修正前のバイナリでは、同じ手順でエージェントが宛先への接続を持ち続けた。
  同じ組み合わせで、クライアントが送信側を閉じた後に宛先が返す応答がクライアントに届くことも確かめた。
  未確認:片方向がすでに EOF で終わった後に届く RST。
  この場合は反対向きの読み取りが続き、書き込みが失敗するか宛先が閉じるまで中継は終わらないと、コードから読み取れる。
  公開側のクライアントが接続を RST で切った場合は、この改訂でもエージェントに FIN が届く。
  VPS の中継(プロキシのルールと、ユーザー空間モードの通常のルール)の netpipe は、クライアント側の読み取りの失敗を受けて両側を通常の `Close` で閉じるので、エージェントの中継はハーフクローズとして扱い、FIN を受けても閉じない宛先では、宛先への接続と枠が宛先が閉じるまで残る。
  この改訂の前も `CloseWrite` で FIN を送っていたので、退行ではない。
  単体試験とラボで確かめた。
  クライアントの RST を RST としてエージェントへ伝えるかは決めていない。
  カーネルモードの VPS の通常のルール(nftables の DNAT)の切断はエージェントに何も届けないので、この改訂の対象外である


- userspace backend の UDP の中継が、実効宛先の変更か接続元制限の変更と重なった新しい送信元のセッションを登録しないようにした(2026-09-30、6.3 節):UDP の新しいセッションは、エージェントへの dial の後にセッションの表へ入る。
  読み取りのループが Admission Policy の判定を済ませてから、あるいは実効宛先を読んでから登録するまでの間に、`Commit` の実効宛先の変更か `CloseSessions` の sweep が走ると、sweep はそのセッションを見ない。
  セッションは旧い実効宛先へ、あるいは新しい方針が拒む送信元のまま登録されて中継を続けた。
  送り続ける送信元のセッションは、無通信の期限でも閉じない。
  TCP は dial の前に接続を表へ入れ、dial の間の sweep を印で伝えている。
  UDP でも、作っている途中のセッションの送信元を listener のセッションの錠の下で記すようにした。
  sweep はその送信元を閉じる判定をしたら印を立て、登録の時点で印があれば、セッションを登録せずにデータグラムを捨て、エージェントへの接続を閉じ、フロー予算の枠と送信元ごとの枠を返す。
  sweep がその送信元を残す判定をした場合は、登録して中継を続ける。
  途中のセッションを記すのはセッションの表を引く時点であり、所属ルールと実効宛先を読む前である。
  実効宛先の変更は送信元によらずすべてのセッションを閉じるので、表を引いた後に実効宛先が変われば、途中のセッションが新しい実効宛先を読んで dial した場合でも最初のデータグラムを捨てる。
  単体テストで、dial の中で止めている間に実効宛先を変えた場合と、判定の後と dial の中で止めている間に接続元制限を変えた場合に、新しい送信元のセッションが登録されず、旧い実効宛先にデータグラムが届かず、応答も返らず、エージェントへの接続が閉じ、2 つの枠が 1 度ずつ返ることを確かめた。
  実効宛先を変えた場合は、次のデータグラムが新しい実効宛先へ届くことも確かめた。
  修正前のコードでは、これらの場合にセッションが登録されて旧い実効宛先へ中継された。
  判定の中で止めている間に実効宛先を変えた場合は、ループが新しい実効宛先へ dial しても最初のデータグラムを捨て、次のデータグラムが新しい実効宛先へのセッションを作ることを確かめた。
  送信元を残す sweep と重なった場合は、判定の中と dial の中のどちらで止めても、登録して中継することを確かめた。
  ラボのユーザー空間モードでは、通しテストと、宛先の変更、fail-closed、エージェントの無効化を含むライフサイクルの確認が変わらず通ることを確かめた。
  未確認:netstack の UDP の listener での再現と、ラボでの競合の窓の再現


- ユーザー空間モードの TCP のバッファに floor と boost の上限を置いた(2026-09-30、7 節、所有者の決定):以前は netstack の TCP のバッファを gVisor の既定の自動調整に任せていた。
  送信のバッファの上限は受け入れた byte だけを数えるので、読まない相手へ 1 byte の書き込みを繰り返すと、接続 1 本の保持は byte の上限を大きく超えて増え、保持の上限を持たなかった。
  全接続を小さな固定の値にする案は、損失の無い経路の単独の転送を以前より大きく遅くするので採らなかった。
  そこで接続ごとの floor と、プロセスあたり 16 本の枠で貸す boost を組み合わせ、書き込みの数を送信のバッファ 1 KiB あたり 1 回に抑えた。
  実装の前の実験で分かったことは次のとおりである。
  枠を接続が CLOSED になるまで返さない形では、転送を終えて開いたままの接続と、閉じた側の TIME_WAIT の接続が枠を持ち続け、後続の転送が floor に留まり、1 MiB の Web の応答も遅れた。
  枠を TIME_WAIT で返し、空きが無いときだけ 1 秒需要の無い保有者から回収する形にすると、この 3 つの退行は消えた。
  boost の大きさは 1、2、4 MiB を同じ条件で比べ、単独の転送が以前と同じ速さになった 4 MiB を採った。
  1 と 2 MiB は以前より遅かった。
  4 MiB より大きい値は比べていない。
  製品の実装では、書き込みの長さの履歴を boost の間だけ広げるようにした。
  単体テストで確かめたことは次のとおりである。
  握手の後に両端が floor であること。
  SYN と SYN-ACK の窓の scale が boost の大きさから決まること。
  枠を得られない接続が bulk の転送の後も floor のままであること。
  boost を得た受信の側が floor を超える量を受け入れること。
  同時の転送が枠より多くても、枠が 16 を超えず、floor を下回る接続が無いこと。
  TIME_WAIT と CLOSED の接続の枠を返すこと。
  送ったデータの確認を待つ接続と FIN_WAIT_2 の接続は枠を返さないこと。
  需要の無い保有者から回収し、回収された接続が需要の戻ったときに枠を求め直すこと。
  転送を続ける保有者、キューにデータの残る保有者、書き込みの途中の保有者からは回収しないこと。
  読まない相手への 1 byte の書き込みの繰り返しで、送信の側に残る書き込みが、floor、boost、回収の後のそれぞれで上限以内に止まること。
  ラボでは、ユーザー空間モードの通しのシナリオ(`lab/e2e.sh`)と `lab/lifecycle.sh` がすべて通った。
  同じ VM で以前の製品と 1 回ずつ比べ、単独の bulk の転送、Web の応答、SSH に相当する往復のどれも、以前より遅くならなかった。
  枠より多い 20 本の同時の転送の合計は、以前より少し遅かった。
  送信の向きを閉じた保有者を回収しない規則は、レビューで見つかった反例(送信を閉じた保有者が、boost の大きさのデータを持ったまま floor に戻された)を受けて足し、単体テストで確かめた。
  受信のメモリが floor 以下の保有者だけを回収する規則も、レビューを受けて足した。
  穴の後ろに順序外のデータが floor を超えて積まれた接続を回収すると、穴を埋める再送を gVisor が受け入れなくなり、接続が止まることを単体テストで再現した。
  規則を足した後は、次の場面で穴が埋まって読み進むことを単体テストで確かめた。
  受信のバッファがこのメモリとちょうど等しい場合、1 segment 大きい場合、送り手が先を送り続ける場合、64 KiB の segment の場合である。
  受信のバッファがこのメモリより 1 byte 小さい場合は、何も受け入れず止まることも確かめた。

  1 秒を超えて間の空く利用での遅れ。
  ラボでの、読まない相手への 1 byte の書き込みの繰り返しによる保持の比較。
