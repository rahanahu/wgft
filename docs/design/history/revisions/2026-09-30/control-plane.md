# 2026-09-30: control-plane

- ルールの ID を URL のパスに埋めるときに escape するようにした(2026-09-30、10.2 節、セキュリティ点検の指摘):ルールの ID は `rule import` と管理用 API から空でない任意の文字列で入るが、Web UI のテンプレートはリンクとフォームの送信先に ID をそのまま埋め、html/template はパスの中の `/`、`..`、`?`、`#` を escape しない。
  このため `x/../r_b/delete?` のような ID の行の無効化のボタンが、ブラウザの解決によって別のルールの削除へ送信した。
  未登録のエージェントの帯の削除のボタンも、ルールの `agent` をそのまま埋めていた。
  `x/../home/disable?` のような名前の帯のボタンが登録済みのエージェントを無効にすることは、登録の確認を持たない試験用の backend でだけ再現した。
  本物のサーバでは、書き込むルールの `agent` は登録済みのエージェントの名前に限られる。
  このような名前の帯が出るのは、名前の文字種の検査ができる前に保存されたエージェントの名前か、データベースを直接書き換えた場合だけである。
  同一オリジンの送信なので、他オリジン発の変更の拒否には掛からない。
  取り込みの確認の画面は ID を示さないので、運用者は気付けなかった。
  テンプレートの送信先とリンク、保存の後の戻り先、パンくず、CLI の疎通確認の依頼で、ID をパスの 1 つの区切りとして escape するようにした。
  帯の送信先のエージェントの名前も、多重の守りとして同じく escape する。
  ID の文字種の制限は加えていない。
  10.2 節が任意の文字列を ID として受けると定めており、制限は既存のルールの取り込みを拒みうる変更になるためである。
  長い ID が nftables のコメントの上限を超える問題と、ログと CLI の表に改行が入る問題は、この改訂では扱っていない。
  単体テストで、そのような ID の行と別のルールの行の無効化のボタンを、リンクを RFC 3986 の規則(Go の `net/url`)で解決して押しても、それぞれ自分のルールだけを無効にし、別のルールも消えずエージェントも変わらないこと、ID をパスに埋めるどのページのリンクも別のルールの経路へ解決しないこと、保存の後の戻り先が同じルールの詳細ページであること、登録の確認を持たない試験用の backend で、そのような名前の未登録のエージェントの帯のボタンが、そのエージェントのルールだけを消し、登録済みのエージェントも別のルールも変えないこと、CLI の疎通確認の依頼が ID をそのままサーバに届けることを確かめた。
  未確認:実際のブラウザでの確認。


- ルールの ID と `agent` の `.` と `..` を拒むようにした(2026-09-30、10.2 節、所有者の決定):前項の escape は、`.` と `..` を `%2E` と `%2E%2E` の形にしていた。
  Go の `net/url` とサーバはこの形を区切りの `.` と見なさないが、ブラウザは WHATWG URL 標準に従って見なすので、`/ui/rules/%2E%2E/disable` は `/ui/disable` に解決する。
  そのような ID と `agent` のルールの Web UI のボタンは、escape では正しい経路に届かない。
  受けない値をこの 2 つに限り、`proto.Rule.Validate` で拒むことにした。
  文言は英語で、値が Web UI の URL で区切りとして読まれることを示す。
  7a.11 節の互換性について:ルールのスキーマ(5.3 節)が受ける値を狭める変更である。
  今まで通っていた `.` と `..` の ID を、新しく書き込むときに拒む。
  `agent` の `.` と `..` は、本物のサーバでは登録済みのエージェントでないとして既に拒まれていた。
  `agent` の検査は多重の守りであり、見える変化は、より早い段階で別の文言の誤りになることだけである。
  既に保存されたそのようなルールは、読み込みと転送を続け、他のルールの変更も妨げない。
  変更は拒み、CLI の `rule rm` や管理用 API のバッチでの削除はできる。
  Web UI の、そのようなルールの行のボタンは、この変更の前からブラウザでは別の経路へ送信していた。
  名前の文字種の検査ができる前に保存された `.` や `..` のエージェントがあれば、その帯のボタンも同じである。
  所有者は、版の上げ方ではこの変更を互換を崩す変更に数えないと判断した。
  受ける値を狭めるのは形の上だけで、実際の使い方を壊さないためである。
  `.` と `..` のルールは、Web UI のボタンが別の経路へ送信するので正しく扱えず、パスの走査に似た罠になっていた。
  この変更は、その罠を除く入力の守りである。
  単体テストで、ルール単体の検査、ルールのバッチ(保存の経路)、管理用 API のバッチ、Web UI の取り込みの確認、CLI の `rule add` と `rule import` が 2 つの値を拒み、`...` や `.a` は受けること、保存済みの `.` のルールが無関係なバッチを妨げず、変更は拒まれ、削除はできることを確かめた。
  未確認:実際のブラウザでの確認。
