# 2026-09-30: resource-guard

- フロー予算の隔離予約を、ルールの登録ごとの最低分と予備の形に改めた(2026-09-30、所有者の決定、6.2・6.3・7・7a.5・7a.10・7a.11・10.2c 節):所有者の決定により、wgft の資源予算を「利用単位ごとの小さな最低分の保証と、固定の上限の中の先着順の共有」とし、フロー予算には後から加わるルールのための空きを残すことにした。
  7a.10 節の隔離予約 `q` は、既存の隔離を大きく後退させないために残し、予算から予備を除いた `T - f` から求め直す。
  登録ごとの最低分を `max(f, q)` とし、最初の `f` を下限の部分として、予備より先に守る。
  予備は予約の部分より先に守る。
  後から加わるルールの下限が 0 本になる経路を残さないためである(所有者の決定)。
  予備 `P = f` は帳簿の値として持たず、予約の部分と共有分の条件に常に含める。
  `f` の値 4 は、`TotalMin` で `f ≤ C` と `3f ≤ T` を満たす最大の 2 のべきとして設計で定めた。
  ルール 1 本の上限 `C = ceil(T/2)` は残す。
  最低分と先着順の共有だけでは、1 本のルールへのフラッドで無関係なルールが最低分まで絞られ、今の隔離から大きく後退するためである(所有者の決定)。
  フローは受け付けたときのルールの登録で数える。
  ルールの登録が退役したときは、その登録のフローのうち受け付けている listener が運ぶものを、その listener の今の登録へ移す。
  受け付けていない listener が運ぶフローは移さず、生きている登録どうしでも移さない(所有者の決定)。
  統合、名前の変更、UDP の再開の後は改訂の前と同じく旧い接続を今のルールで数え、統合先が `C` を超えれば `C` を下回るまで新しいフローを拒む(所有者の決定)。
  移しは遷移の時点だけで行い、適用の終わりに退役をまとめて処理する操作は持たない(所有者の決定)。
  `C` は、登録に数えるフローの数ではなく、登録の listener が今運んでいるフローの数で判定する。
  この数は改訂の前のルールのフロー数と同じ数え方である。
  予約の部分の入口は、登録に数える数と listener が運ぶ数の大きいほうで判定し、下限の部分と請求の合計は登録に数える数のままとする(所有者の決定)。
  `rule_cap` の拒否の文言は、判定に使った listener が運ぶ数を示す(所有者の決定)。
  設定の変更は、最低分や予備が足りなくても拒まず、請求の合計が `T` を超える状態を許す。
  改訂の前の 7a.10 節も、予約の未使用分が空きを超える状態を許していた。
  受け付けていない listener からの取得は `Pool` が拒み、拒んだ接続は今までどおり RST で閉じる。
  拒否の理由に `floor`(自分の最低分に届いていないが、空きを他の登録の下限と予備に残す)と `spare`(自分の最低分に届いていて、空きを満たされていない最低分と予備に残す)を加え、`reserve` と `rule_cap` の意味は変えない。
  `spare` の説明は他のルールの最低分を含む形にする(所有者の決定)。
  ルールの登録で数えることは 7a.11 節の意味の変更に当たらないとし、同節にそう書いた(所有者の決定)。
  最低分、予備、登録ごとのフローの数は管理用 API に加えず、拒否の理由のキーとログの文言でだけ示す(所有者の決定)。
  分割元が続くあいだの制限は「保証しないこと」に隠さず書く(所有者の決定)。
  採らなかった形は次のとおりである。
  受け付けの前に枠を取っておく形は、範囲のルールで listener ごとに枠を使い、拒否が即時の RST ではなく応答の無い接続になる。
  予約が足りなければ設定の適用を拒む形は、7a.3 節の fail-closed の規則、7 節の閉じ直しと統合の規則、`Commit` が失敗しない約束と衝突し、フローが無くてもルールの数に上限ができる。
  同じ ID の退役した登録のフローを予約の部分に数えて緩める形は、効くのが実質 UDP の再開だけで統合には効かず、ルール ID ごとの集計を判定に使う。
  統合と UDP の再開の 2 つの場合だけ旧い接続を移す形は、分割の後に分割元を削除したときに無関係のルールを下限まで削る経路を残す。
  `C` を登録に数えるフローの数で判定する形は、フラッドを受けたポートを分割で切り出すことを重ねると、分割先が毎回最低分を新しく取り、無関係のルールが下限を下回り 0 本まで下がる経路を残す。
  下限の部分も listener が運ぶ数で判定する形は、分割先の最初のフローを拒み、新しい登録の下限の約束を崩す。
  `Pool` の帳簿だけを状態機械として書いた使い捨ての模型で、次のことを確かめた。
  予備を常に請求に含める形では予備が漏れない。
  `q` を改訂の前の式のまま最低分にすると、ルールが 1 本から 2 本に増えるときに新しいルールが下限を得られない場合があり、ルールが 2 本のときに予備が残らない。
  帰属の規則を入れると、受け付けている listener が運ぶフローが退役した登録に残らず、移しは請求の合計を増やさない。
  `C` を listener が運ぶ数で判定し、予約の部分の入口を前述の大きいほうで判定すると、統合、UDP の再開、分割の直後の分割元の削除、フラッドを受けたポートを分割で切り出すことを重ねる場面(フラッドが 1 ポートに集中する場合と範囲に一様な場合)、分割と統合を数回往復する場面で、無関係のルールが新しく通せる数は、改訂の前の形より少ない場合でもその差は数本以内だった。
  同じ模型で、1 回の適用の中の操作の順によって、無関係のルールが改訂の前より少なくしか通せない場合があること、分割と統合を多数回往復すると無関係のルールが最低分を下回り始めること、フラッドを受けた分割先が新しく通せる数が、分割の時点の請求の合計によって改訂の前より少ない場合と多い場合があることも確かめ、7a.10 節の「保証しないこと」に書いた。
  分割元が続くあいだに分割元に残ったポートが新しいフローを通せないことは、判定の式から計算して同じ模型でも確かめ、同じく「保証しないこと」に書いた。
  その状態を解く手順(分割の後に分割元のルールを 1 つのバッチで別の ID に置き換える)は、ラボで確かめてから同じ項に書いた。
  `relay` と `proxyrelay` の今のコードの上に、受け付けていない listener からの取得を拒む `Pool` と帰属の規則の帳簿(判定の式は改訂の前のまま)を載せた使い捨ての試作で、次のことを確かめた。
  `relay` の TCP と UDP、`proxyrelay` のどの経路でも、受け付けていない listener からの取得は拒否の数にもログにも入らず、TCP は RST で終わり UDP はデータグラムを捨てる。
  手形は 1 度だけ返る。
  錠の順序(`relay.Manager` の排他、listener ごとの排他、`Pool` の排他)は守られる。
  統合、UDP の再開、再開と同時の付け替えで、受け付けている listener が運ぶフローは退役した登録に残らない。
  `relay` の TCP の worker は Manager の排他を待った後に取得するので、取得は適用の途中にも入る。
  取得の後に停止の印を見て切る接続は、切り方を変えなければホストのソケットで FIN になるので、RST で終えるよう改めた。
  UDP の再開の順を `Pool` の受け付けを先に始める形に入れ替えると、再開の適用の最中に届いたデータグラムを捨てるので、今の順序を保つ。
  改訂の前の実装には、fail-closed で止めた UDP の listener に、止める直前に受け付けの確認を通った新しい送信元のセッションが作られる競合があることを、試験の差し込みで窓を開けて確かめた。
  この競合は、この改訂とは別の直しで先に塞いだ。
  受け付けていない listener からの取得を拒む `Pool` でも同じ窓が塞がることを、同じ試作で確かめた。
  実装では、判定の式をそのまま書き下した参照の実装と `Pool` に同じ無作為の操作の列を当て、判定と帳簿が毎手一致することを単体テストで確かめた。
  判定の順、予約の部分の入口、listener が運ぶ数の増減、帰属の規則の 2 つの発火をそれぞれ壊すと、単体テストか `relay` の適用の経路のテストが落ちることも確かめた。
  1 回の適用の中の順は、`relay` の同じ `Commit` を繰り返すと 2 通りとも起き、どちらの順でも受け付けている listener が運ぶフローが退役した登録に残らないことを確かめた。
  ユーザー空間モードの server とエージェントの TCP で、統合の後と、分割してすぐ分割元を削除した後に、フラッドを続けたまま無関係のルールが最低分まで新しい接続を通せること、分割元を残すと分割元に残ったポートが新しい接続を通せないこと、分割元のルールを 1 つのバッチで別の ID に置き換えるとそのポートが既存の接続を保ったまま最低分まで通せることを、ラボで確かめた。
  未確認:UDP のフラッドでの実際の中継の振る舞い、管理用 API の batch と Web UI の読み込みの経路での分割元の置き換え、1 回の適用の中の順が実際の適用で起きる頻度、範囲に一様なフラッドでの分割や分割と統合の多数回の往復が実際の運用で起きる頻度、閉じた listener の接続を切り終えるまでの実時間、`f = 4` が想定用途に足りるか、`floor` と `spare` の拒否を利用者がどう受け取るか、エージェントのトンネルの立て直しで旧い `Pool` が残るあいだのプロセス全体の上界、byte と RSS の上界
