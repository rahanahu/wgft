# 2026-09-22: operations

- 適用できない宣言から運用者が戻る経路として、起動の保留を定めた(2026-09-22、所有者の決定):カーネルへ適用できない宣言をサーバのデータベースに保存できてしまう一方で、それを直すための入口が失われる欠陥を塞ぐ。
  宣言の保存は適用の成否を待たず(`internal/vpsd/admin_backend.go` の `Daemon.Batch` は `store.ApplyBatch` で確定してから `applyNFT` を呼ぶ)、適用に失敗しても保存を取り消さない。
  稼働中はこれでよく、プロセスは生きたまま 30 秒ごとに試し直し、`apply_state` を `pending`、`apply_error` を理由として報告する(7a.3 節)。
  ところが起動時だけは、最初の適用の失敗が `internal/vpsd/vpsd.go` の `Run` からそのまま返り、`cmd/wgft` の `exitCode` が終了コード 1 を返して終わっていた。
  管理用 API の待ち受けはこの適用より後にあるため、unit は再起動して同じ場所で落ち続け、`wgft rule rm` は届かず、運用者に残る手段は `server teardown --purge` による全消しだけだった。
  2026-09-21 にラボで、適用が ENOBUFS で毎回失敗する大きさの宣言を保存して 5 分間観測し、この形を確かめている。
  ENOBUFS そのものは普通の配置では届かない壁だが、適用が毎回同じ失敗をする原因であれば何でも同じ形になる。
  設定の誤りを 1 つ保存しただけで、それを直すための入口まで失われることが問題の中心である。
  検討した案は 3 つで、起動時の適用の失敗でも管理用 API を開くこと、適用を飛ばして起動する 1 回限りのフラグ、デーモンを動かさずにルールを消すコマンドである。
  1 つ目を採った。
  稼働中の失敗の扱いが既にこの形であり、新しいフラグも、サーバのデータベースへの 2 本目の書き込み経路も増やさずに済むうえ、運用者が失敗の理由を管理用 API 越しに読んでから直せるためである。
  2 つ目は運用者に unit の書き換えか手での起動を求め、v1.0 で固定する外部仕様にフラグを 1 つ増やし、宣言と実際の転送が食い違った状態の意味論を別に定める必要がある。
  3 つ目は `Daemon.Batch` の検査を通らない 2 本目の書き込み経路を作り、運用者は原因を見ないまま消すことになる。
  エージェント用 API を保留の間に開かないことも決めた。
  転送していない間にエージェントが接続しても中継は起きず、エージェントへ配る conntrack の UDP タイムアウト 2 値も、その読み取りがテーブルの適用の後に置いてある(9 節)以上この時点では読めていない。
  開くと制御の接続だけが成立して転送は起きない状態になり、運用者から見て保留と正常の区別が付かなくなる。
  11b 節に「起動の保留」の項を新設し、9 節の起動時の突き合わせと 7a.3 節の再試行をこれに追随させた。
  ラボでの確認は、下の「起動の保留をラボの実カーネルで確かめ」の項にある。
  独立レビューが、新設した項と既存の記述の矛盾を 1 つ見つけたので、同じ改訂で解いた。
  11b 節の入る条件が「最初の適用が失敗したことだけ」と例外を持たない一方、9 節はカーネルモードの netlink の書き込みが権限で失敗することを種別 `prerequisite` の拒否(終了コード 3)と定めている。
  一度は保留の入る条件に権限の不足の例外を足したが、2 巡目の独立レビューが実測によってこれを覆したので、例外を取り下げた。
  権限が足りない配置は、最初の適用より前にある wg インタフェースの立ち上げで止まる。
  インタフェースを作る netlink の書き込みも、既存のインタフェースを読む `wgctrl` の呼び出しも `CAP_NET_ADMIN` を要求することを、user namespace を分けた環境で `CAP_NET_ADMIN` を落として確かめた。
  つまり 9 節の拒否と保留は同じ失敗を奪い合っておらず、矛盾は元から無かった。
  そのうえで例外を残すと害がある。
  最初の適用だけが権限で失敗する状態とは、`CAP_NET_ADMIN` を持ちながら nftables への書き込みだけを拒まれている状態であり、原因は権限そのものではない。
  これを終了コード 3 に写すと、7a.3 節が「30 秒ごとの再試行が拾う」と定めた `table inet wgft` の保持のように、待てば解ける原因まで永久に止めうる。
  11b 節が警告する誤った終了コード 3 そのものである。
  2 巡目のレビューは、保留の間の転送についての記述の誤りも見つけた。
  「転送:起きない」と書いていたが、これが成り立つのはホストごと再起動した後と初回の起動だけである。
  9 節が定めるとおり停止時にはテーブルも wg インタフェースも削除しないので、`systemctl restart` でプロセスだけを入れ替えた場合は前のプロセスが公開したテーブルとピアがカーネルに残り、最初の適用が失敗してもそれらは消えない。
  カーネルモードの transparent のルールは前回公開した宣言のまま転送を続ける。
  この文自体も、後にラボで覆った。
  適用の失敗が応答の受信の側で起きた場合は成り立たない(下の 2026-09-23 の項)。
  稼働中に backend 全体の失敗が起きたときと同じ残り方であり、挙動として誤っているのではなく、記述が誤っていた。
  保留を「転送が止まっている状態」と説明すると、運用者は `rule rm` の後も旧い行が転送していることに気付けない。
  設計文書、`docs/manual/setup.md` の日英、`server run` のヘルプ、保留の行のログの文言を、止まっているのは公開であって転送ではない、と読める形に直した。
  1 巡目のレビューが、保留の間の `wgft status` について 11b 節が書いた「Agents 行も degraded になる」が一般には成り立たないことも見つけた。
  `status` の Agents 行は登録済みのエージェントの数を見るので、1 台も登録していない配置の保留では degraded にならない。
  保留そのものを表すのは Server 行であると書き直した。
  あわせて、保留の間 unit が active のままであることを項に足した。
  従来の終了コード 1 の繰り返しは再起動として見えたが、保留は静かである。
  これは稼働中に `apply_error` を抱えたまま動き続ける場合と同じ見え方であり、公開が止まっていることを知る手段も同じく `wgft status` と `server doctor` の終了コード 1 である。
