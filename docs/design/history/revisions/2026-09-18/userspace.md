# 2026-09-18: userspace

- 中継のメモリ費用を実測(2026-09-18):`vpsd`(ユーザー空間モード)とエージェントが共有する `relay.Manager` は、UDP のセッションごとに 65535 バイトの読み取りバッファを持ち続け、TCP の接続数に上限を持たない。
  このため、帯域を使わずにフローを開いて保持するだけでメモリが増え続けることをラボで確認した。
  UDP はルール 1 本を上限まで埋めると約 290 MiB 増え、ルールの本数に比例する。
  接続を閉じても RSS はすぐには下がらない。
  7 節と 6.3 節にこの費用を追記し、13 節に上限の設け方を未決事項として追加した

- 中継のメモリ上限を決定(2026-09-18):7 節に同時フロー数の上限を、ルールごと、プロセス全体、接続元 IP ごとの 3 段で定め、プロセス全体の上限を `WGFT_MAX_UDP_FLOWS` と `WGFT_MAX_TCP_FLOWS` の設定項目にした(11a 節)。
  UDP のセッションは応答が届くまで読み取りバッファを持たず、TCP の中継は待つ間だけ小さいバッファを持つ形にして、フロー 1 本の費用を下げた。
  バッファを小さくして溢れた 1 個を捨てる案は、大きい応答が欠けるので採らなかった。
  上限から計算したメモリのソフト上限を起動時に設定し、GC が回収を待つ間の膨張を抑える。
  ラボで、全部の上限を埋めてフラッドを重ねた RSS の最大が既定の上限で約 210 MiB になること、上限を 2048 と 1024 に下げると 150 MiB の cgroup に OOM なしで収まること、通常時の速度が変更前と数パーセントしか違わないことを確認した。
  13 節の未決事項を、カーネルモードでの接続元 IP ごとの上限に置き換えた。
  未確認:256 MiB の実際の VPS、Windows と macOS のエージェント
