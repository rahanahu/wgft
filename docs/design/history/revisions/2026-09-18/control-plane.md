# 2026-09-18: control-plane

- `ip_forward` の警告をルールの件数で弱めない(2026-09-18):6.1 節は、カーネルモードのルールが 0 件なら `ip_forward` を書けなかった警告を情報レベルにとどめるとしていたが、実装は常に警告で、Finding に重大度の区別もない。
  Findings は起動時に 1 回だけ作り、ルールは起動後に追加できるので、実装の挙動を正として記述を改めた

- ルールの詳細ページ(2026-09-18):10.1 節に、接続元制限とレート制限を変えるルールの詳細ページと、追加フォームの「無効のまま追加」を追記した。
  それまで Web UI は一覧に件数と値を出すだけで、これらの変更は CLI でしかできなかった。
  group と note を変える以前のページは、詳細ページの 1 区画に取り込んだ。
  CIDR の解釈は CLI と共有し、CLI の `rule deny add` と `rule allow add` も既にある CIDR を重ねて加えない形にそろえた

- ルールの適用状態の表示(2026-09-18):それまで Web UI は有効なルールを一律「適用済み」と表示し、エージェントが報告する error や、世代が古く反映待ちの状態、エージェント未接続を見せていなかった。
  10.1 節に、持ち主のエージェントの直近のハートビートから 4 状態(applied/error/pending/agent offline)を判定する優先順位を明記し、一覧・詳細ページの両方に適用し、畳んだグループの見出しと全体ヘルスの要約に error のルール数を含めることにした。
  あわせて、エージェント一覧の名前欄に wg 公開鍵の先頭を追記した(全体は title 属性)。
  最終ハンドシェイクは既に 10.1 節にあったが実装が追随していなかったので、今回で埋めた。
  ラボで、TCP ルールの target に何も待ち受けていない状態でルールを足すと error が理由付きで出て、target 側に応答するプロセスを立てると 30 秒台の再試行とハートビートの間隔内に applied へ戻ること、エージェントを止めると即座に agent offline になることを確認した。
  エージェント側の listen は自分のトンネルの netstack 上(仕様 7 節)で、VPS 側の検証(5.3 節)が listen_port の重複を全ルールにわたって拒否するため、bind 失敗そのもの(もう一方の error の原因)は正当な操作では再現できず未確認。
  pending は世代を古くした状態を作って単体テストで確認した
