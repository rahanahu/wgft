# 2026-10-03: review

- ブロードキャストとマルチキャストの宛先を、エージェントの 2 つのモードで拒むようにした(2026-10-03、7・7a.11・7b.2・7b.3・7b.4・10.2a・10.2c・11 節、所有者の決定):エージェントの宛先の判定は、許可一覧に入るかどうかと、カーネルモードのループバックと未指定のアドレスだけを見ていた。
  許可一覧の無いエージェントは、全域のブロードキャスト、帯のブロードキャスト、IPv4 のマルチキャストのアドレスを宛先とするルールを `ok` として受け付けた。
  ラボでは、ユーザー空間モードはこれらの宛先へ UDP のデータグラムを送り、LAN のホストとグループの待ち受けに届いた。
  カーネルモードはこれらの宛先へ DNAT を組み、ブロードキャストへ向けたパケットは LAN へ出ずにエージェントのホスト自身の待ち受けに届き、マルチキャストへ向けたパケットはどこにも届かなかった。
  所有者の決定に従い、2 つのモードで同じ判定と同じ理由の文言で拒む。
  判定は `internal/agent/allowtargets` に置き、2 つのモードの dataplane に渡す。
  帯のブロードキャストのアドレスは、末尾が `.255` かどうかではなく、エージェントのホストのインタフェースのアドレスとプレフィクス長から求め、`/31` と `/32` の帯は除く。
  ホスト名は解決の結果のアドレスで判定する。
  インタフェースの一覧を読めない場合は、帯のブロードキャストの判定だけを行わない。
  `server doctor` の理由の符号に `target_not_unicast` を加えた。
  拒むのは `255.255.255.255`、マルチキャスト、エージェントのホストのインタフェースの帯から求めた帯のブロードキャストである。
  末尾が `.255` であることだけでは判定せず、`/31` の両端は通常のホストとして通す。
  Wake-on-LAN のマジックパケットをブロードキャストへ送る宛先はサポートしない。
  ユーザー空間モードでは、この変更の前はそのようなパケットが LAN に届いていた可能性があり、この変更がそれを止める。
  Wake-on-LAN の機能が必要になれば別に設計する。
  許可一覧が無いときのユーザー空間モードは、ホスト名の宛先を従来どおり名前のまま接続し、Go の接続が解決した各アドレスを接続の前に判定する。
  独立のレビューで、中継が自分で解決して順に試す形にすると、応えない AAAA を先に返す名前で接続ごとに約 10 秒かかり、ルールが `error` になることがラボで分かったためである。
  ラボでは、更新の後にこれらの宛先のルールが 2 つのモードで同じ理由の `error` になり、LAN にもホスト自身にも何も届かず、`server doctor` が `target_not_unicast` の FAILED と示し、`agent doctor` が既存の `listener_error` と示すことを確かめた。
  カーネルモードでは、更新の前の版が組んだ帯のブロードキャストへの DNAT とその UDP のフローが、更新の後の最初の公開で消えることも確かめた。
  Docker のブリッジのネットワークのコンテナで動くエージェントは、LAN の帯のブロードキャストを帯のブロードキャストとしては拒まない(7 節)。
  未確認:Wake-on-LAN のマジックパケットを帯のブロードキャストへ送る使い方が、この変更の前のユーザー空間モードで実際に機器を起こしていたか。
  インタフェースの一覧を読めない場合の挙動と、IPv6 のマルチキャストのアドレスに解決される名前の挙動の、ラボと実機での確認(単体試験だけで確かめた)。
  Windows と macOS のエージェントでの帯のブロードキャストの判定


- server が `net.ipv4.ip_forward` を変えたことを 2 段で記録するようにした(2026-10-03、6.1・7a.11・10.3・11b 節、所有者の決定):server は起動時に `net.ipv4.ip_forward` の 0 を読むと 1 を書き、書けた後に「wgft が 0 から 1 にした」記録を保存していた。
  記録の失敗はログに出すだけだった。
  書いた直後に止まるか記録に失敗すると記録が欠け、`server teardown` は wgft が 1 にした値を「wgft did not change it, already 1; no action needed」と示した。
  撤去は今の値を読まず、値が 0 の場合も「already 1」と示した。
  順序を入れ替えて書く前に記録すると、書く前に止まった場合に、変えていない値を「変えた」と示す逆向きの誤りになる。
  所有者の決定に従い、書く前に予定の記録を保存し、書けた後に確定の記録の保存と予定の記録の削除を 1 つのトランザクションで行うようにした。
  予定の記録を保存できなくても、警告して値は書く。
  撤去は今の値も読み、確定の記録があれば従来どおり示し、予定の記録だけがあれば「変えたかもしれない」と今の値を示し、どちらも無ければ「変えていない」に今の値を添える。
  記録を読めなければ、どれとも言わない。
  管理用 API の `ip_forward_set_at` は確定の記録だけを返す。
  スキーマの版は上げていない。
  エージェントの記録は変えていない。
  単体試験で次を確かめた。
  書く時点のデータベースには予定の記録だけがあり、書いた後は確定の記録だけが残る。
  値が 1 なら何も書かず、前の起動の予定の記録を消さない。
  値を読めなければ 1 を書き、記録を残さない。
  予定の記録の保存に失敗しても、書く前に警告して値を書く。
  予定の記録と確定の記録の両方に失敗した場合だけ記録が残らず、起動時の Finding を返す。
  書けなければ予定の記録を消し、消せなければ残して警告する。
  書いた直後に止まった場合と、確定のトランザクションに失敗した場合は、予定の記録だけが残る。
  確定のトランザクションは、削除が失敗すると保存も取り消す。
  管理用 API は予定の記録を返さない。
  撤去の行を、記録と今の値の組ごとに確かめた。
  ラボで、カーネルモードの server について次を確かめた。
  起動時に値が 0 なら確定の記録だけが残り、管理用 API の `ip_forward_set_at` がその日時を返し、撤去が「0 から 1 にした」と示す。
  値を書いた直後、確定の記録の前にプロセスを強制終了すると、値は 1 で予定の記録だけが残り、撤去は「変えたかもしれない」と今の値の 1 を示す。
  修正の前の版は同じ場面で「wgft did not change it, already 1」と示した。
  その後に値が 1 のまま起動し直すと、予定の記録は残り、`ip_forward_set_at` は空のままである。
  起動時に値が既に 1 なら記録は残らない。
  `--dry-run` はデータベースのファイルと値を変えない。
  修正の前の版の撤去は、予定の記録だけが残ったデータベースで従来の行を出した。
  修正の前の版の server はそのデータベースで起動し、確定の記録を保存した。
  未確認:予定の記録を保存できない場合と、確定のトランザクションに失敗した場合のラボでの振る舞い。
  単体試験だけで確かめた
