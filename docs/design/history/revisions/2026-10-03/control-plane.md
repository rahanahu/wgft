# 2026-10-03: control-plane

- 鍵を変えた後のカーネルモードのエージェントが、前の鍵の最終ハンドシェイクを今のトンネルの値として示していた不具合を直した(2026-10-03、5.2・7b.4・10.2c 節、所有者の決定):稼働中の `rotate-key` の後も、wgft0 の server のピアは前の鍵で成立した最終ハンドシェイクの時刻を持ち続けた。
  ラボで、カーネルモードの `vpsd` とカーネルモードのエージェントで鍵の変更の頻度の上限を超える `rotate-key` を実行すると、server が新しい鍵を断って転送が止まっている間も、`agent doctor` の `tunnel.local` と `dataplane.interface` は前の鍵の時刻を示して OK とし、ハートビートのトンネルの状態も同じ時刻を送った。
  断られている間にエージェントを止めた後の `agent doctor` の `dataplane.interface` と、起動し直した後の `tunnel.local` も同じ時刻を示した。
  断られた直後と、起動し直した後の最初のトンネルの点検で、エージェントは前の鍵の時刻を新しいハンドシェイクとして読み、stream の再接続の待ちを打ち切った。
  原因は、Linux の WireGuard がインタフェースの秘密鍵を変えてもピアの最終ハンドシェイクと送受信バイト数を残すことである。
  ラボの試験で、鍵だけを変えたピアから前の鍵の時刻と受信のバイト数が読めることを確かめた。
  所有者の決定は、前の鍵のハンドシェイクと今の鍵のハンドシェイクを区別して直し、最終ハンドシェイクの古さの閾値だけを変えて直さないことである。
  鍵を変える収束が、鍵と同じ wgctrl の設定で wgft0 のピアをすべて外し、server のピアだけを足し直すようにした。
  server 以外のピアはどの収束でも外すので、結果は変わらない。
  設定はピアを 1 つ、AllowedIPs を 1 つだけ持ち、wgctrl が設定を複数の netlink のメッセージに分けるのはピアが 32 を超えるか AllowedIPs が合わせて 256 を超える場合だけなので、鍵の書き換えとピアの置き直しは wgft0 にいくつピアがあっても 1 つのメッセージで送られる。
  外すピアを 1 つずつ並べて server のピアを外してから足し直す形は採らない。
  ピアの多い wgft0 では wgctrl が設定を分け、同じ公開鍵の 2 度目の指定からエンドポイントと keepalive を落とすことを、独立レビューのラボで確かめたためである。
  採らなかった他の案とあわせて 7b.4 節の「鍵の変更と最終ハンドシェイク」に書いた。
  読む側の挙動は変えていない。
  ラボで、同じ場面を修正の前と後のビルドで並べて実行した。
  修正の後は、受け入れられた `rotate-key` の直後に `tunnel.local` が `handshake_pending` の UNKNOWN になり、ハートビートも `handshake not established` を送り、新しい鍵のハンドシェイクが成立すると OK に戻った。
  転送が戻るまでの時間は修正の前と同じ桁だった。
  上限で断られている間は、`tunnel.local` が `handshake_pending` の UNKNOWN を、`dataplane.interface` がハンドシェイクの無いことを示した。
  停止中の `agent doctor` も、起動し直した後も同じで、再接続の待ちを打ち切る行は出なかった。
  `stream.connection` の FAILED と終了コード 1 は修正の前と同じである。
  server を起動し直して鍵が通った後は、新しい鍵のハンドシェイクが成立して OK に戻り、転送も戻った。
  ユーザー空間モードのエージェントで同じ場面を流し、修正の前と後で `agent doctor` とハートビートの表示が同じであることを確かめた。
  修正の後のカーネルモードの表示は、このユーザー空間モードの表示と揃った。
  ラボの試験で、余分なピアを持たない wgft0 と、wgctrl が設定を分ける境を越える数の余分なピアを持つ wgft0 の両方について、鍵を変えた直後の wgft0 が server のピア 1 つだけを持ち、そのピアが最終ハンドシェイクを持たないこと、名前を解決できていない収束でもカーネルが持っていたエンドポイントと keepalive を保つこと、試験用のサーバが新しい鍵を受け入れた後に新しい鍵のハンドシェイクが成立することを確かめた。
  同時に読む側については、カーネルのソースで設定の適用と読み出しがどちらも rtnl_lock とインタフェースの更新の排他を持つことと、独立レビューのラボで鍵の切り替えを繰り返す間に並行して読み続け、新しい鍵と前のピアの組を一度も読まなかったことを確かめた。
  どちらも証明ではない。
  未確認:カーネルが途中まで適用したメッセージを元に戻さず、ピアを足す処理が失敗すると新しい鍵と server のピアの無い wgft0 が次の収束まで残ること(カーネルのソースを読んだ判断で、ラボでは試していない)、鍵の書き換えが失敗して wgft0 が 1 つ前の鍵を持ったままの場合の表示(コードを読んで判断した)、この版より前のエージェントが鍵を変えた wgft0 を更新した後の表示、Debian 12 のカーネル 6.1 以外のカーネルでの挙動。
  server の `agent ls` は、断られている間は最後に届いたハートビートの値を示し続ける。
  この表示は変えていない


- ルールの ID の長さと文字を検査するようにした(2026-10-03、5.2・5.3・5.4・7a.11・10.2 節、所有者の決定):ルール単体の検査(`proto.Rule.Validate`)は、ID が空でないことと `.`・`..` でないことだけを見ていた。
  `rule import`、Web UI の読み込み、管理用 API のバッチは、長さと文字を問わず ID を受けた。
  server のハートビートの受け口は、エージェントが報告するルール ID のうち `unicode.IsGraphic` が偽の文字を置き換え、128 バイトで切り詰めて保存する。
  このため、128 バイトを超える ID と、そのような文字を含む ID のルールは、状態が永久に「報告なし」になった。
  改行を含む ID は、ID を載せるログの行を偽れた。
  nftables のカウンタのコメント `wgft:<ID>:<種類>` は 256 バイトの userdata に入るので、長い ID のルールはカーネルモードの公開を失敗させる見込みだった。
  所有者の決定に従い、ID を UTF-8 で 128 バイト以内の正しい UTF-8 とし、すべての文字で `unicode.IsGraphic` が真であることを求めた。
  受け口が手を加えない範囲と同じである。
  日本語、ASCII の空白、全角スペースのような Unicode の空白は受け、空白を削ることも、全角と半角をそろえることもしない。
  所有者は当初、文字の範囲を `unicode.IsPrint` とし、ASCII 以外の空白を拒むことにした。
  ラボで、全角スペースを含む ID のルールは更新の前の版でも転送が通り、報告も状態に届いていた。
  拒むことは不具合の修正に当たらないので、所有者は `unicode.IsGraphic` に改めた。
  検査はルール単体の検査に置いたので、CLI、管理用 API、Web UI、読み込みのどれにも効き、拒否は既存の 422 で返す。
  文言は英語で、長さか最初の違反の文字の符号位置を示す。
  検査の文言そのものは ID の中身を繰り返さないが、バッチの拒否は従来どおり `rule <ID>:` を前に付けるので、拒否の応答には受け取った ID がそのまま入る。
  受け口の切り詰めの長さは、ID の上限の定数を参照するようにした。
  この検査の前に保存された行は、v1.3.0 の `.` と `..` と同じく、変えない行に検査を掛け直さない規則(5.4 節)で扱う。
  7a.11 節の互換性について:受ける値を狭める変更で、所有者は版の上げ方では互換を崩す変更に数えないと判断した。
  扱いは 7a.11 節に個別に記した。
  保存済みの改行を含む ID が `rule ls` の表とログの行を崩す問題は、この改訂では扱っていない。
  単体試験で次を確かめた。
  128 バイトの ID が通り、129 バイトの ID が拒まれる。
  3 バイトと 4 バイトの文字が 128 バイトの境目をまたぐ値と、文字数では 128 に満たないがバイトでは超える値も拒まれる。
  不正な UTF-8、改行、復帰、タブ、縦タブ、改ページ、ESC、DEL、C1 の制御文字、双方向の上書き、ゼロ幅接合子、BOM、行区切り、段落区切り、私用領域の文字が拒まれる。
  日本語、ASCII の空白、全角スペース、ノーブレークスペースなどの Unicode の空白、記号、絵文字は通る。
  受ける ID は、全角スペースとノーブレークスペースを含むものも、ハートビートの受け口で変わらない。
  管理用 API のバッチは、全角スペースとノーブレークスペースを含む ID をそのまま保存する。
  保存の経路、管理用 API のバッチ、Web UI の読み込みの確認、CLI の `rule import` は新しい違反の ID を拒む。
  保存済みの違反の ID の行は読み込まれ、無関係な追加と、集合をそのまま戻すバッチと読み込みが通る。
  同じ ID のままの変更は拒まれる。
  管理用 API、Web UI の無効化と分割、CLI の `rule disable`・`rule set`・`rule split`、その ID を残す `rule merge` がこれに当たる。
  削除(`rule rm`、Web UI、管理用 API)、正しい ID への置き換え、その行を消す向きの `rule merge` は通る。
  ラボで、カーネルモードとユーザー空間モードの server について、更新の前の版で違反の ID のルールを読み込み、この改訂の版へ server を更新した。
  違反の ID は、128 バイトを超える日本語を含む ID と、改行を含む ID である。
  あわせて全角スペースを含む ID のルールも読み込んだ。
  更新の後もどのルールも転送が続き、一覧に出た。
  同じ ID のままの変更は CLI、管理用 API、Web UI のどれでも理由を示して拒まれた。
  無関係な追加、書き出しをそのまま読み込み直す操作、正しい ID への置き換え、削除は通った。
  全角スペースを含む ID のルールは、更新の後も変更が通った。
  全角スペースとノーブレークスペースを含む新しい ID の読み込みは通り、ID はそのまま保存されて、転送とエージェントの報告が状態に届いた。
  行区切りか改行を含む新しい ID の読み込みは拒まれた。
  日本語と空白を含む 128 バイトの ID と接続元ごとのレートを持つルールで、エージェントの報告が状態に届いた。
  カーネルモードでは、このルールのカウンタのコメントがテーブルに載った。
  更新の前の版のカーネルモードで、userdata の上限を超える長さの ID のルールを読み込むと、行は保存されたが、カーネルが nftables のバッチを拒んで公開に失敗した(`numerical result out of range`)。
  `rule rm` で消すと戻った。
  独立レビューは、そのような行を持つデータベースで server を起動する場合をラボで確かめた。
  server は同じ誤り(`numerical result out of range`)で既存の起動の保留(11b 節)に入り、管理用 API は開いたままで、カーネルに既に載っていたルールは転送を続けた。
  `rule rm` でその行を消すと、起動の保留が終わって server が起動した。
  未確認:保存済みの違反の ID の行を Web UI の統合で扱う操作(CLI の `rule merge` と同じ `proto.Merge` を使うことはコードから判断した)、Windows と macOS での確認。


- ハートビートの理由の長さの上限をエージェントの側にも置き、stream のメッセージの HTML 向けの書き換えをやめた(2026-10-03、5.2・7a.11・11 節、所有者の決定):`vpsd` は理由を受け取った後に 512 バイトで切り詰めていたが、接続を確立した後のメッセージの上限(1 MiB)はエージェントが送ったままのメッセージに掛かるので、受け口の切り詰めでは 1 通の大きさを抑えられなかった。
  エージェントの理由には長さの上限が無く、`json.Marshal` は `&` などを 6 バイトに書き換える。
  `&` を並べたホスト名の宛先を持つルールが失敗し続けると、1 通が上限を超え、stream は接続のたびに切れた。
  エージェントは理由の不正な UTF-8 のバイトを JSON の符号化と同じく U+FFFD に置き換え(`internal/textsafe` の `ReplaceInvalidUTF8`)、受け口と同じ変換(同じ package の `SanitizeAndClip`)にかけてから送り、メッセージを HTML 向けの書き換え無しに JSON にする。
  上限の値は `proto.ReasonMaxBytes` に置き、受け口と、カーネルモードの名前の解決の失敗の理由の組み立ても同じ定数を使う。
  エージェントのログには切り詰める前の理由を書く。
  単体試験で次を確かめた。
  512 バイトちょうどの理由は変わらず、超えた理由は rune の境目で切られて印が付き、境目にかかる多バイト文字は丸ごと落ちる。
  前のエージェントの送り方と今のエージェントの送り方をどちらも実際の JSON の往復に通して比べ、分類に使う語の終わりを 512 バイトの前後に 1 バイトずつずらし、前置きを膨らむ文字、不正なバイト、多バイト文字で埋めても、無作為に混ぜても、受け口が保存する値の印より前の文言と `server doctor` の判定は変わらない。
  不正なバイトで始まる理由は、最初の置き換えを省くと語が 512 バイトの外に出て判定が変わり、置き換えると前と同じ値を保存する。
  `ReplaceInvalidUTF8` は無作為のバイト列で JSON の往復と同じ結果を返す。
  512 本のルールのすべてが最も膨らむ理由で `error` のハートビートは、ID を 128 バイトの `"` としても 1 MiB に収まり、HTML 向けの書き換えを残すと超える。
  `vpsd` は書き換えた形と書き換えない形を同じ値に読んで保存する。
  エージェントが stream に実際に送るメッセージは、切り詰めた理由を持ち、書き換えをしない。
  ラボで、カーネルモードの `vpsd` に、ユーザー空間モードとカーネルモードのエージェントを順に 1 台ずつつなぎ、`&` を並べたホスト名の宛先のルールと、解決できない長いホスト名の宛先のルールを置いた。
  修正の前のエージェントは、どちらのモードでもハートビートが 1 通の上限を超えて `vpsd` に接続を閉じられ、`agent ls` は切断を、`agent doctor` は再接続中を示した。
  修正の後のエージェントは接続を保った。
  `agent ls` は全ルールの `error` と切り詰めた理由を示し、`server doctor` は両方の種類のルールの `rule.target_resolve` と `rule.target` を `target_resolve_failed` と判定した。
  `agent doctor` は stream の接続を OK とし、ルールの失敗をユーザー空間モードでは `relay.listeners`、カーネルモードでは `dataplane.table` に示した。
  独立レビューが、ユーザー空間モードの `vpsd` とこのエージェントの組でも同じ確認をラボで流し、stream が接続を保ち、保存する理由が切り詰めた値になり、`server doctor` が `target_resolve_failed` と判定することを確かめた。
  未確認:Windows と macOS のエージェント、ルール ID が 128 バイトを超える場合と表示できない文字を含む場合の 1 通の大きさ(ID の上限はこの変更の範囲外である)


- server が `net.ipv4.ip_forward` を読めず書けもしなかった場合の警告から、0 という断定を外した(2026-10-03、6.1 節):起動時に値を読めず、1 を書くことにも失敗すると、警告は「is 0 and could not be set to 1」と示していた。
  値を読めていないので 0 とは言えない。
  この警告は 2 段の記録の導入より前からあった。
  読めなかった誤りと書けなかった誤りの両方を示し、転送が動かないかもしれないことと、値の確かめ方と直し方を案内する警告に改めた。
  0 を読んで書けなかった場合の警告は変えていない。
  単体試験で、値を読めず書けもしない場合の警告が「is 0」を含まず両方の誤りを含むことと、0 を読んで書けない場合の警告が従来のままであることを確かめた。
  ラボで、`/proc/sys/net/ipv4` に tmpfs を重ねて `ip_forward` をディレクトリにした mount namespace の中でカーネルモードの server を起動すると、起動時のログに両方の誤りを示す警告と 2 つの案内が出て、起動は続いた。
  エージェントの同じ場面の文言(カーネルモードの `ip_forward` の警告)は、この変更では直していない。
  `server doctor` の理由の分類は、理由が `net.ipv4.ip_forward` を含むかだけを見るので、文言の後半を変えても分類は変わらない。
  ただし `server doctor` の `agent_ip_forward_off` の案内は、エージェントのホストの値を 0 と断定し、エージェントの再起動を勧める。
  この案内は、エージェントが値を読めず書けもしなかった場合の事実と合わない。
  再起動の勧めは、書けない場合には、読めなかった場合も 0 を読んで書けなかった場合も合わない。
  エージェントの文言と `server doctor` の案内の両方に及ぶので、別の変更にする


- エージェントあたりのルールの数を 512 本までにし、`target` を 259 バイトまでの表示できる文字に限った(2026-10-03、5.2・5.3・5.4・7a.11 節、所有者の決定):ルールの数にも `target` の長さにも上限が無かった。
  `vpsd` は全体状態をエージェントごとに 1 通で送り、エージェントは 1 通を 4 MiB までしか読まない。
  ハートビートはルールごとに 1 件の状態を持ち、`vpsd` は 1 通を 1 MiB までしか読まない。
  1 つのエージェントにルールを足し続けると、どちらかの 1 通が上限を超え、その全体状態かハートビートが届かなくなりえた。
  `target` は、ポートの先頭に 0 を並べていくらでも長くできた。
  所有者の決定に従い、上限を設定項目にしない 512 本とし、`target` を 259 バイトまでの `unicode.IsGraphic` が真の文字に限った。
  数の判定は、バッチの前後の本数を比べて `proto.ValidateUpsert` で行う。
  後の本数が 512 を超え、かつ前より多いときだけ拒むので、上限の導入の前に 512 本を超えて保存されたデータは、本数を増やさない変更で減らせる。
  `proto.ValidateUpsert` は保存の経路(`store.ApplyBatch`)と事前確認(`admin.PreflightBatch`)の両方が呼ぶので、CLI、管理用 API、Web UI のどの入口にも同じ判定が効く。
  所有者の決定は判定を `admin.AdmitBatch` と `admin.PreflightBatch` に置くことだったが、実装は両者の後に走る `proto.ValidateUpsert` に置いた。
  `store.ApplyBatch` を通るすべての保存と `PreflightBatch` に同じ判定が効き、後から `store.ApplyBatch` を通る経路が増えても判定が漏れないためである。
  `AdmitBatch` に置いた場合との違いは、bind 中のポートと他のテーブルの DNAT の検査(`vpsd` の `checkRule`)が数の判定より先に走る順序だけである。
  `PreflightBatch` は、行ごとの誤りか、ID の重複や `listen_port` の重なりなどの集合全体の誤りがあると、数の誤りを示さない。
  行ごとの誤りがあれば集合全体の検査を省き、集合全体の検査は最初の誤りだけを返す、既存の作りによる。
