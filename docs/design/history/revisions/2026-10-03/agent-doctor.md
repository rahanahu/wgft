# 2026-10-03: agent-doctor

- 鍵の変更の頻度の上限で直近の試みを断られたエージェントについて、`agent doctor` が終了コード 1 を返すようにした(2026-10-03、7a.11・10.2c 節、所有者の決定):稼働中の `rotate-key` が上限で断られると、エージェントは後の試みで鍵が通るまで転送できない。
  それでも `agent doctor` は `stream.connection` を UNKNOWN の `key_change_limited` とし、この検査は総合判定を動かさないので、最上位の `status` を `ok`、終了コードを 0 として返した。
  ラボで、カーネルモードの `vpsd` に対して、ユーザー空間モードとカーネルモードのエージェントで上限を超える `rotate-key` を実行した。
  どちらのモードでも、拒否から鍵が通るまでの間、TCP と UDP の転送が止まり、`agent doctor` は終了コード 0 を返し続けた。
  総合判定を動かす他の検査は、この状態を FAILED として示さなかった。
  ユーザー空間モードの `tunnel.local` はトンネルを新しい鍵で作り直すので `handshake_pending` の UNKNOWN になり、カーネルモードの `tunnel.local` と `dataplane.interface` は前の鍵の最終ハンドシェイクを示して OK だった。
  `server doctor` は、前の鍵の最終ハンドシェイクが閾値を越えるまで終了コード 0 を返した。
  所有者の決定に従い、直近の試みが上限による拒否で終わった場合の `stream.connection` を FAILED とし、この場合だけ総合判定を動かすようにした。
  判定に使うのは直近の試みの結果だけで、後の試みで鍵が通れば OK に戻り、上限以外の理由で終われば `reconnecting` に戻る。
  理由の符号、所見と案内の文言、旧い版のエージェントを理由の文言で判定することは変えていない。
  `server doctor` は変えていない。
  server は断った宣言が正規のエージェントのものかどうかを見分けられないためである。
  互換性の約束の変更は 7a.11 節に書いた。
  単体試験で次を確かめた。
  直近の試みが上限で断られた応答は、値を送るエージェントでも理由の文言だけを送る旧い版のエージェントでも、実行時の排他を取れなかった応答でも、カーネルモードでも、`stream.connection` を FAILED とし、終了コード 1 と `--json` の `status` の `failed` を返す。
  拒否の後に鍵が通った応答は OK で終了コード 0、拒否の後の試みが別の理由で終わった応答は `reconnecting` で終了コード 0 である。
  ラボで、修正の前と後の `agent doctor` を同じ場面で並べて実行し、修正の後は拒否から鍵が通るまでの間だけ終了コード 1 を返し、拒否の前、鍵が通った後、server を再起動した後の通常の再接続の間とその後は終了コード 0 を返すことを、ユーザー空間モードとカーネルモードのエージェントで確かめた。
  ラボで、ユーザー空間モードのエージェントについて、上限による拒否の後に server を止めて次の試みを接続できずに終わらせると、`stream.connection` が `reconnecting` の UNKNOWN に戻って終了コード 0 を返し、server を起動し直した後は鍵が通って終了コード 0 を返すことも確かめた。
  直していないこと:カーネルモードの `tunnel.local` と `dataplane.interface` が、鍵を変えた後も前の鍵の最終ハンドシェイクを示すこと

- `agent doctor` と `server doctor` の `net.ipv4.ip_forward` の次の一手から、再起動の勧めを外した(2026-10-03、6.1 節、10.2a 節、10.2c 節):`agent doctor` の `host.forwarding` は「sysctl -w で 1 にするか、エージェントを再起動する」と、`server doctor` の `ip_forward_off` は「sysctl -w で 1 にするか、server を再起動する」と案内していた。
  値が 0 で書き込みが塞がれている場合、つまり読み取り専用の `/proc` やコンテナの制限がある場合は、再起動しても起動時の書き込みが同じ原因で失敗するので直らない。
  案内は、`sysctl -w net.ipv4.ip_forward=1` で 1 にすること、書けない場合は再起動だけでは直らないので、読み取り専用の `/proc` やコンテナの制限などの原因を除いてから 1 にすること、後で 0 に戻るなら設定を探すことを述べる文に改めた。
  `agent doctor` は値を読んだ上での案内なので値が 0 であることは述べたままにし、起動時に書けなかったかどうかは `doctor` の材料に無いので案内を分けず、書けた場合と書けない場合の両方に当てはまる文にした。
  理由の符号、`--json` の形、終了コードは変えていない。
  単体試験で、2 つの案内が再起動を勧めず、書けない場合の手順を含むことと、分類が変わらないことを確かめた。
  ラボの使い捨て VM で、server と agent のそれぞれの mount namespace に、値が 0 で読み取り専用の tmpfs を `/proc/sys/net/ipv4` へ重ねた。
  この状態の `agent doctor` と `server doctor` の案内を、修正の前の版と後の版で比べ、前の版は再起動を勧め、後の版は書けない場合の手順を示すことを確かめた。
  設計文書は 6.1 節の戻す手順と 10.2a 節の次の一手の記述も、同じ理由で改めた。
  未確認:コンテナの制限による書き込みの失敗(読み取り専用のファイルでだけ確かめた)
