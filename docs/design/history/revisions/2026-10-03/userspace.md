# 2026-10-03: userspace

- 許可一覧があるときのユーザー空間モードの中継の接続を、一覧が無いときの Go の接続と同じ試し方にした(2026-10-03、7 節):`WGFT_AGENT_ALLOW_TARGETS` があるとき、中継はホスト名の `target` を自分で解決し、一覧が通すアドレスを解決の結果の順に 1 つずつ、それぞれ 10 秒の期限で試していた。
  一覧が無い経路は名前を `net.Dialer` に渡すので、2 つの族をずらして並行に試すことと、期限をアドレスの間で分けることが効いていた。
  一覧がある経路にはそのどちらも無かった。
  そのため、黙って捨てる IPv6 のアドレスが先に並ぶ名前では、接続に 10 秒かかり、5.2 節の 2 秒の接続確認がそのルールを `error` にした。
  一覧の判定は変えていない。
  判定は解決したアドレスごとに行い、判定したアドレスそのものへ接続する。
  変えたのは、通したアドレスの試し方だけである(7 節)。
  判定を `net.Dialer` の `Control` に任せる形は採らなかった。
  名前の解決が Go の接続の中に移り、すべてのアドレスが失敗したときに返る誤りが、通したアドレスの接続の失敗ではなく、先に並ぶアドレスの一覧による拒否になりうる。
  その場合はルールの報告が変わるためである。
  すべて失敗した場合に返す誤りは、前と同じく解決の結果の順で最後に試したアドレスの誤りとした。
  単体試験で次を確かめた。
  黙って捨てる IPv6 のアドレスと応える IPv4 のアドレスを持つ名前で、接続は IPv6 を先に試し、少し待ってから IPv4 で繋がり、適用のときの接続確認は `ok` になる。
  先の族がすぐに失敗すれば待たずにもう一方の族を試す。
  同じ族のアドレスには期限を残りのアドレスの数で分けて与え、1 つの持ち分は 2 秒を下回らない。
  一覧の外のアドレスへは接続を試みず、すべてのアドレスが一覧の外なら理由の文言は前と同じである。
  競争に負けた族の接続が後から繋がれば閉じる。
  ラボで、ユーザー空間モードのエージェントに、その名前を宛先とする TCP のルールを置き、IPv6 と IPv4 の両方のアドレスを許可一覧に入れた。
  名前はエージェントの network namespace の `/etc/hosts` で IPv6、IPv4 の順に引け、IPv6 の宛先への SYN は LAN の側で黙って捨てた。
  修正の前のエージェントでは、ルールは適用の直後も定期の確認の後も `error`(`did not answer within 2s`)で、client からの接続はどれも、IPv6 のアドレスの期限が切れてから IPv4 の宛先に届いた。
  修正の後のエージェントでは、ルールは `ok` のまま続き、接続は IPv6 のアドレスの期限を待たずに届いた。
  7a.11 節が保証するサーフェスは変わらない。
  変わるのは、該当する名前の宛先への接続にかかる時間と、それによるルールの `ok` と `error` の報告だけである。
  未確認:UDP の宛先と、解決の結果に 3 つ以上のアドレスがある名前のラボでの確認、DNS サーバから引く名前(ラボでは `/etc/hosts` だけで確かめた)、Windows と macOS のエージェント


- ユーザー空間モードの `vpsd` が、待ち受けを開くときに宛先へ試し接続しないようにした(2026-10-03、6.3 節):ユーザー空間モードの `vpsd` は、適用の `Commit`(`internal/dataplane/userspace/relay` の `Staged.Commit`)で新しく開く TCP の待ち受けごとに、エージェントのトンネルのアドレスの同じポートへ試し接続し、すべての結果を待ってから戻っていた。
  エージェントはそのポートを、この適用の後に配られる全体状態で開くので、試し接続は届かない。
  カーネルモードのエージェントは入口の守り(7b.1 節)で SYN を黙って捨てるので、試し接続は 1 件ごとに期限の 2 秒まで待った。
  同時に試す数は 32 までなので、新しいポートの数に比例して適用が遅れた。
  ラボでは、新しいポートへの数百本の `rule import` が CLI の待ちの 30 秒を超えて失敗し(バッチそのものは後で完了した)、同じ数のルールを持つ server の起動では、管理用 API が応答するまでの時間が延びた。
  起動の最初の適用も同じ試し接続を待ち、試し接続はエージェントとの WireGuard のハンドシェイクが成立するまで届かないためである。
  起動の遅れは、エージェントのどちらのモードでも起きた。
  新しいポートへの読み込みの遅れは、カーネルモードのエージェントの場合だけ起きた。
  ユーザー空間モードのエージェントは開いていないポートへの接続をすぐに拒むためである。
  カーネルモードの `vpsd` は中継を持たないので、どちらも起きない。
  試し接続の結果は待ち受けの記録に残るだけで、`vpsd` のどこからも読まれず、宛先に届かない旨のログの 1 行になるだけだった。
  ユーザー空間モードのエージェントでも、新しいポートごとにこの行が出ていた。
  `vpsd` はこの記録を確かめ直さないので、エージェントがポートを開いた後も、届くようになった旨のログは出なかった。
  `Staged.Commit` から試し接続を外した。
  ルールの状態、管理用 API の応答、`server doctor` の判定は変わらない。
  宛先に届くかどうかはエージェントの試し接続が報告し、エージェントの `Apply` と 30 秒ごとの確認は変えていない。
  7 節のエージェントの accept の待ち行列の上界は、`vpsd` の dial の数を「`vpsd` の K と試し接続の数」で抑えると書いていた。
  この試し接続が外した試し接続を指すのか、疎通確認を指すのかを読み分けられるように、`vpsd` がエージェントへ dial する場面を書き分け、上界の 96 の根拠が記録に無いことと推定を書いた。
  上界の式は変えていない。
  ハンドシェイクの前に届いた TCP の接続の扱いは、TCP の待ち受けの数で変わった。
  試し接続は同時に 32 件で 1 件 2 秒なので、旧版は 33 本以上の待ち受けを持つ `vpsd` で、起動の後しばらく公開ポートを bind したまま accept しなかった。
  その間に届いた接続はカーネルの待ち行列に溜まり、試し接続が終わってから accept された。
  ハンドシェイクが試し接続の終わりより先に来れば、その接続は中継された。
  新版はすぐ accept してエージェントへ dial し、dial の期限の 5 秒の内にハンドシェイクが成立しなければ切るので、クライアントは繋ぎ直す必要がある。
  期限の内に成立した場合に中継されるかどうかは未確認である。
  32 本以下の旧版も、起動の 2 秒後からは新版と同じ扱いだった。
  ラボで、カーネルモードのエージェントの 512 本のルールで起動の直後に繋いだ接続は、旧版ではハンドシェイクの後に中継され、新版では応答なしで切れた。
  8 本のルールでは旧版も応答なしで切れた。
  6.3 節の性質の違いの項に、ハンドシェイクの前に届いた接続の扱いを書いた。
  再レビューを受けて、ハンドシェイクの前に届いた接続が切れるのは dial の期限の内にハンドシェイクが成立しない場合であると条件を付け、エージェントの上界の前提の要約に疎通確認の同時の数の前提を加えた

- ユーザー空間モードの netstack の TCP の、短い障害の後の回復の遅さを既知の制限とした(2026-10-03、所有者の決定、6.3 節):プロセス内の試験の組で、netstack の TCP の送り手と受け手の間の経路を短く止めた後の転送を測り、パケットの記録と固定版の gVisor のソースで原因を調べた。
  障害の後の転送の完了は障害の長さを大きく超えて遅れ、送るデータの多い接続では試験の期限の内に転送が終わらなかった。
  完了したどの回でもデータの欠けは無く、netstack の出力のキューでの落ちも無かった。
  原因は gVisor の TCP の送り手の不具合で、6.3 節の項に書いた。
  wgft が gVisor に与える TCP の設定のうちこの挙動に関わるのは SACK の有効化だけで、RACK は gVisor の既定のまま使っている。
  対策の候補として、RACK を切り SACK を残す変更を、流す前に決めた確認項目と閾値で評価した。
  変更の前と後を同じ時間帯に交互に流して比べた。
  障害の後の回復は大きく改善し、改善を確かめるどの場面も合格の条件を満たした。
  一方で、パケットの並べ替えのある経路では転送が大きく遅くなり、事前に決めた許容を超えた。
  RACK は少しの順序の乱れを並べ替えとして待つが、RACK を切った送り手は後続の segment の確認の数でその乱れを損失と誤って判定し、損失の回復に入って送る速さを落とすためである。
  損失のある経路、応答の末尾の損失、障害の無い転送、送信のバッファの上界(floor と boost の大きさ)は、許容の内だった。
  この結果から、RACK は今のまま有効にし、短い障害の後の回復の遅さをユーザー空間モードの既知の制限とした。
  ユーザー空間モードは、カーネルモードと同等の損失の回復を保証しない。
  gVisor へのパッチ、SACK を切る案、ほかの設定の探索は、この判断からは再開しない。
  実際の利用でこの遅さが問題になった証拠が出たら、新しい調査として開き直す。
  プロセス内の試験の組の結果で採らないと決まったので、ラボの通しの構成での変更の前と後の比較は流していない。
  未確認:時計の分解能の粗い環境(Windows など)で、この不具合による送り手の止まり方が変わるか。
  実際のインターネットの経路とラボの通しの構成での回復。
  Windows と macOS の実機。
  `vpsd` がカーネルモードでエージェントがユーザー空間モードの組と、`vpsd` がユーザー空間モードでエージェントがカーネルモードの組が対象になることは、送り手の不具合であることからの判断で、測っていない
