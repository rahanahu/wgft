# 2026-09-25: review

- `agent pubkey` が稼働中のエージェントの状態ファイルを書かないようにした(2026-09-25):`agent pubkey` は稼働の判定もロックも持たずに状態ファイルを読み、鍵が無ければ作って保存していた。
  書くのは鍵が無いときだけである。
  定常の稼働中のエージェントの状態ファイルには常に鍵があるので、稼働中の `agent pubkey` はこれまでも読むだけだった。
  書き込みが起きうるのは、エージェントが鍵を保存する前の起動の途中である。
  一度も起動していないデータディレクトリでの最初の起動と、停止中の `rotate-key` の後の起動がこれに当たる。
  この区間に `agent pubkey` が重なると、エージェントが書いた登録の情報(恒久トークン、使用済みの接続文字列の印)、モードの記録、1 つ前の鍵を、`agent pubkey` が読んだ古い内容で上書きしうる。
  印字される鍵も、エージェントが使う鍵と食い違いうる。
  上書きされた項目はエージェントの次の保存が書き戻すが、その前にエージェントが止まると失われる。
  9 節に、状態ファイルを書く CLI は稼働の判定とロックの扱いを停止中の `rotate-key` とそろえ、稼働中なら書かないことを加え、`agent pubkey` の扱いを定めた。
  実装では、判定とロックの取り方を停止中の `rotate-key` と `agent pubkey` で共有する形にした。
  採らなかった案がある。
  CLI が flock の下で最新を読み直し、変える項目だけを書く案は、稼働中のエージェントがメモリの上の中身で全体を書き直すので CLI の変更を保てず、稼働中の書き込みを防げない。
  稼働中の `agent pubkey` を制御ソケット経由でエージェントに問い合わせる案は、制御ソケットに指示を加える必要があり、古い常駐プロセスは答えない。
  保存済みの鍵がエージェントの使う鍵なので、読むだけで足りる。
  ロックファイルが無いときの狭い隙間を閉じる案は、ロックファイルをエージェントの利用者の持ち物として作る仕組みが要るので、今回は採らない。
  別のプロセスがロックを持つ間に鍵がまだ無ければ、`agent pubkey` は鍵を作って保存する代わりに失敗するようになった。
  以前の振る舞いがこの不具合そのものであり、フラグの名前と意味は変えていないので、7a.11 節の保証には触れない。
  ラボで、停止中の `rotate-key` の後に起動するエージェントと並行して `agent pubkey` を繰り返し、直す前の `agent pubkey` がエージェントの使わない鍵を作って状態ファイルに書き、その鍵を印字することを確かめた。
  直した後は、印字する鍵がエージェントの使う鍵と一致するか、鍵がまだ保存されていないという誤りになることを確かめた。
  稼働中のエージェントに対する `agent pubkey` が状態ファイルを変えないこと、停止中の `rotate-key` の後に停止中の `agent pubkey` が作って保存した鍵を次の起動が使うことも確かめた。
  ロックファイルが無いときの隙間には、`rotate-key` の 3 つの場合に加えて、一度も起動していないデータディレクトリでの最初の起動も含まれ、その場合は印字する鍵がエージェントの使う鍵と食い違いうることを 9 節に書いた。
  ロックの持ち主は停止中に書いている別の CLI でもありうるので、ロックを持たれている間の案内を、稼働中のエージェントと言い切らない文言にした。
  起動時の一時ファイルの片付けの項と本節の記述が、flock を取らずに保存する書き手として `agent pubkey` を無条件に挙げていたので、ロックファイルの無いデータディレクトリでの場合に限る記述に直した。
  起動したエージェントが `agent pubkey` のロックに当たって終わる場面は、ラボの競合の再現で観測した。
  Windows では、状態ファイルを開いて読む別のプロセス(`agent pubkey`、`agent doctor`)と、エージェントの保存の rename による置き換えが重なると、読み手の open と rename のどちらかが共有違反で失敗しうる。
  この変更の前からの性質であり、この変更が持ち込んだものではない。
  並行する書き手と読み手の単体試験は、Windows でだけ共有違反とアクセス拒否の回をやり直す形にしており、この性質を試験の主張の外に置いている。
  未確認:ロックファイルが無いときの狭い隙間に `agent pubkey` が重なる場面は、ラボで作っていない。
  Windows の実機で、読み手がエージェントの保存を失敗させる頻度とその影響

- カーネルモードの server の稼働中に VPS の `ip_forward` が 0 にされたことを示すようにした(2026-09-25、所有者の決定):server は起動時にだけ `net.ipv4.ip_forward` を 1 にする。
  稼働中に外から 0 にされると転送は止まるのに、`status` は healthy、`server doctor` は失敗の無い報告、Web UI は「すべてのシステムが正常です」と「wgft が設定」、`server check` も書ける値には何も言わなかった。
  0 にされた値を `vpsd` が戻すかどうかを決め、戻さないことにした。
  稼働中に 0 にするのは運用者か運用者が置いた設定の明示の操作であり、書き戻すとその操作と争う。
  sysctl の変更には通知が無く、戻すには定期的な書き込みを常駐させることになる。
  エージェントのカーネルモードも戻さずに報告するので、両側で揃う。
  そのかわり黙らせない。
  6.1 節のとおり、管理用 API がカーネルモードの server の今の値を返し(7a.11 節)、10.2a 節のとおり `server doctor` はカーネルで転送する公開中のルールの `rule.public_port` と `server.dataplane` を新しい理由の符号 `ip_forward_off` の FAILED とし、10.2b 節のとおり `status` は Server 行を degraded とし、10.1 節のとおり Web UI は今の値を示し、`server check` は書ける値でも 0 なら所見にするようにした。
  プロキシのルールは `ip_forward` に依らないので、止まるルールが無い実行では FAILED にしない。
  ラボで、稼働中の server の横で VPS の `ip_forward` を 0 にすると転送が止まり、この変更の前の版では `status`、`server doctor`、`--probe`、Web UI、`server check` のどれも気付かないことを再現した。
  この版では、`status` が degraded、`server doctor` が TCP と UDP のルールの `public port` と `dataplane` を FAILED とし、Web UI が今の値を危険の色で示してヘッダが警告に変わり、`server check` が所見を出した。
  案内のとおり server を起動し直すと値が 1 に戻り、転送が戻った。
  `--probe` の疎通確認は、この状態でも OK だった。
  server 自身が wg0 へ接続し、カーネルの転送を経ないためである
