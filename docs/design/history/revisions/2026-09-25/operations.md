# 2026-09-25: operations

- root の CLI がデータディレクトリの中のパスを辿らないようにした(2026-09-25、所有者の決定):セキュリティのレビューで、root で実行する停止中の `rotate-key`、`agent pubkey`、`agent teardown` の保存が、一時ファイルのパーミッションと持ち主を名前で設定していることが分かった。
  データディレクトリはエージェントの利用者の持ち物なので、その利用者のコードが動いていれば、書き込みの途中で一時ファイルの名前を root のファイルへの symlink に差し替え、root の保存にその先の持ち主を自分に変えさせられる。
  持ち主を移す処理は直前の撤去の追加で入ったもので、まだリリースしていない。
  加えて、root で実行する CLI と `agent doctor` は、`agent.json` とロックファイルを symlink も種別も大きさも確かめずに開いていた。
  所有者の決定に従い、9 節と 11 節を次のように改めた。
  一時ファイルのパーミッションと持ち主は、作った一時ファイルの記述子に対して設定する。
  移す持ち主は置き換える前の状態ファイルを `lstat` で読み、通常のファイルでなければ保存を拒む。
  状態ファイルとロックファイルは最後の要素の symlink を辿らずに開き、開いた記述子で種別を確かめ、状態ファイルには大きさの上限を置く。
  11 節には、エージェントの利用者と root の境界と、root がデータディレクトリの中のパスを信頼しないことを書いた。
  root がデータディレクトリの持ち主の権限に落としてから触る案は、11 節に書いた理由で採らなかった。
  他に root がデータディレクトリの中のパスを扱う箇所を洗い、稼働中の `rotate-key` が制御ソケットから読む応答にも大きさの上限を置いた。
  一時ファイルの作成、rename、一時ファイルの削除、起動時の片付けは、名前を差し替えられても root の権限を貸さないので変えていない。
  撤去の記録の読み書きは状態ファイルの読み書きそのものなので、上の直しに含まれる。
  状態ファイルの上限は、制御ストリームの 1 通の上限と、収束が済んでいない前の公開の列の上限から見積もった最大の大きさを上回る値にし、その関係を単体テストで確かめる。
  この変更で、symlink の `agent.json` とロックファイルは、エージェント自身も読まずに拒むようになった。
  以前は symlink の `agent.json` を辿って読めたが、最初の保存がその symlink を通常のファイルで置き換えていたので、symlink のまま使い続けられる配置は無かった。
  ロックファイルは保存で置き換わらないので、エージェントとサーバのどちらでも、symlink のロックファイルはこれまで辿られたまま動き続けていた。
  そのような配置は、この変更の後は起動を拒まれる。
  大きさの上限の見積もりには、独立レビューの指摘を受けて、許可一覧が範囲のルールを多数の範囲に分ける場合と、公開しなかった理由の文言の長さを含めないことを 9 節に明記した。
  ラボの VM で、エージェントの利用者に見立てた利用者が inotify で一時ファイルの作成を待って root のファイルへの symlink に差し替える間に、root で停止中の `rotate-key`、`agent teardown`、`agent pubkey` を実行した。
  直す前はどれも差し替え先の持ち主がその利用者に変わり、`agent teardown` ではパーミッションも変わった。
  直した後はどれも変わらなかった。
  直す前の `agent doctor` は `agent.json` とロックファイルが FIFO だと止まり、`agent.json` が `/dev/zero` への symlink だと `agent pubkey` がメモリの上限まで読み続けた。
  直した後はどちらも誤りを示してすぐに終わった。
  未確認の点は次のとおりである。
  Windows の各点は Windows の実機で確かめていない。
  デバイスを root で開く経路は再現していない
