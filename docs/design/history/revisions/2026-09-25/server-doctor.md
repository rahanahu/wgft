# 2026-09-25: server-doctor

- 名前の解決に失敗して直前の解決の結果で転送を続けているルールを、`server doctor` が転送の停止と言わないようにした(2026-09-25):試験用の実機で、カーネルモードのエージェントのルールの宛先のホスト名が解決できなくなった場面を観測した。
  エージェントは 7b.2 節のとおり直前の解決の結果で DNAT を保って転送を続け、ルールの理由にそのことを書いていた。
  一方で `server doctor` はそのルールを `target resolve` で止まったと言い、要約で転送していないルールに数えていた。
  理由が名前の解決の失敗を示す文言を含むので、10.2a 節の場合分けで FAILED の `target_resolve_failed` になっていた。
  7b.2 節はこの `error` を 7b.3 節の 2 つ目の種類と同じく報告にだけ使うと定めており、10.2a 節の「FAILED は転送の停止そのものを観測した場合にだけ使う」とも食い違っていた。
  10.2a 節の `rule.target_resolve` の場合分けに、直前の解決の結果で転送を続けている場合を加えた。
  この場合は UNKNOWN とし、理由の符号は `target_resolve_failed` のままとする。
  人向けの出力では `agent.connection` と同じく `DEGRADED` と表示し、ルールの結論の行は転送を続けていることと名前の解決を直すことを述べる。
  あわせて、10.2a 節の `DEGRADED` を条件の列挙ではなく意味で定義し直した。
  転送の停止とは判定しないが、今の正常な状態から劣化していることは確かめている検査を表し、`agent_disconnected` とこの場合をその例とする(所有者の決定)。
  `rule.target` は、理由のうち直前の解決の結果で転送を続けている部分を除いた残りで判定する。
  エージェントの側も直した。
  カーネルモードのエージェントは、公開の記録の理由を持つルールでは、試し接続の誤りと `ip_forward` の誤りを報告していなかった。
  DNAT を公開したルールでは、この 2 つを理由の後ろに続けるようにした。
  直前のアドレスの宛先が応えない場合に、`server doctor` が止まった位置を `target` と言えるようにするためである。
  範囲の一部のポートだけを公開したルールにも同じく続く。
  DNAT の無いルールには続けない。
  直前のアドレスの宛先が拒む場合の次に見るものは、宣言の名前ではなく、エージェントが実際に繋いでいる直前のアドレスを名指す。
  判定は人の読む文言に依るので、カーネルモードのエージェントが組み立てる理由を `server doctor` の判定に通す単体試験をエージェントの側に置いた。
  どちらかの側だけで文言を変えると落ちる。
  ユーザー空間モードの中継は新しいセッションごとに名前を解決し、直前の解決の結果を持たないことをコードで確かめた。
  ユーザー空間モードで解決に失敗したルールは、今までどおり `target resolve` で止まる。
  7a.11 節との関係:変わる機械向けの値は、直前の解決の結果で転送を続けているという報告に対する `rule.target_resolve` と `rule.target` の `status`、`rule.target` の `reason`、`rules[].status` と `stopped_at`、報告全体の `status` と終了コードである。
  10.2a 節の場合分けを同じ変更で書き換えるので、7a.11 節の分類の訂正としては扱わず、v1.2 の明示の分類の変更として扱う。
  この報告を送るのはカーネルモードのエージェントだけであり、カーネルモードのエージェントはまだどのリリースにも含まれていないので、リリースされた版どうしの組み合わせで見える値は変わらない。
  v1.2 より前の server の CLI でカーネルモードのエージェントのこのルールを診断すると、今までどおり `target resolve` で止まったと言う。
  このことはリリースノートに記す。
  ラボのカーネルモードの server とエージェントで次を確かめた。
  エージェントの network namespace の hosts ファイルから名前を消すと、転送は直前のアドレスへ続いた。
  そのとき `server doctor --json` は `rule.target_resolve` を `unknown` の `target_resolve_failed`、`rule.target` を `ok`、ルールを止まった位置の無い `unknown` とし、終了コードは 0 だった。
  人向けの出力は `target resolve` を `DEGRADED` とし、結論の行で転送を続けていることを述べた。
  続けて直前のアドレスの宛先への TCP をリセットで拒ませると、エージェントの理由の後ろに試し接続の誤りが続き、`rule.target` は `failed` の `connection_refused`、ルールは `rule.target` で止まり、終了コードは 1 になった。
  一度も解決できていない名前のルールは、今までどおり `target resolve` で止まった。
  ラボでは、名前の解決の誤りの文言そのものが `connection refused` を含んだ。
  エージェントのホストのリゾルバに繋がらない場合である。
  `rule.target` は直前の解決の結果の部分を除いた残りで判定するので、この文言を宛先の拒否と取り違えなかった。
