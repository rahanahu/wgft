# 2026-09-25: kernel-agent

- エージェントのカーネルモードの前提の検査を、モードの記録と登録より前に移した(2026-09-25、所有者の決定):7b.5 節に「前提の検査の時点」の項を加え、11a 節の切り替えの関門と、11b 節の入口での判定の、値だけからは判定できない項目を合わせた。
  初見の利用者の通しのレビューで、`CAP_NET_ADMIN` を持たない利用者が `WGFT_MODE=kernel` で起動すると、登録で接続文字列を使い、`agent.json` にカーネルモードを記録してから、最初の収束で種別 `prerequisite` の拒否になることが分かった。
  拒否の文面の案内どおり `WGFT_MODE=userspace` にすると、記録を根拠に関門が拒否し、関門が案内する撤去は `CAP_NET_ADMIN` を要するので、カーネルに何も作られていないのに戻せなかった。
  同梱の `agent.service` に `WGFT_MODE=kernel` だけを足した場合も同じで、ユーザー空間モードで動いていたエージェントが止まったまま戻らなかった。
  決めたことを挙げる。
  第 1 に、前提の検査を記録と登録より前に置き、前提で止まる起動は `agent.json` を書き換えず、接続文字列も使わない。
  第 2 に、権限は nftables のテーブルの一覧という実際に `CAP_NET_ADMIN` を要する読み出しで確かめ、WireGuard は汎用 netlink のファミリの問い合わせで確かめる。
  どちらもカーネルに何も書かない。
  第 3 に、前提の欠如と言い切れる誤りだけを拒否にし、他の誤りは最初の収束に任せる。
  この検査が無かったときに起動できた配置を、新しく止めないためである。
  第 4 に、記録がカーネルモードでカーネルに wgft の資源が何も無い `agent.json` を救う経路、つまり root なしのユーザー空間モードの起動や記録だけを戻す撤去は加えない。
  ユーザー空間モードのエージェントも権限の無い撤去もテーブルを読めず、何も作られていないことを示せない。
  `agent.json` の中身から推す判定は、公開の記録を保存する前に落ちた場合と、変える前のインタフェース名に残ったインタフェースを見落とし、関門の根拠を弱める。
  第 1 の変更の後にこの状態を作れるのは前提を通った配置だけであり、権限の誤り以外の理由で検査を通った場合を除けば、同じ権限で撤去できる。
  `RestrictAddressFamilies` から `AF_NETLINK` を外した unit では、テーブルの一覧もファミリの問い合わせも、権限の誤りではなく対応しないアドレスファミリの誤りで失敗するので、権限が無くても検査を通る。
  この unit を書いた運用者は root を持つので、root で撤去できる。
  ラボで、変更の前の木では、一般の利用者の起動と、`WGFT_MODE=kernel` を足した `agent.service` の両方で、所見どおり登録と記録が起きて戻せないことを再現した。
  変更の後は、どちらも種別 `prerequisite` で止まり、接続文字列は使われず、`agent.json` は変わらず、ユーザー空間モードに戻せば登録するか元どおり動いて TCP と UDP を転送した。
  WireGuard のモジュールを読み込めないカーネルでは、root の起動が種別 `prerequisite` の `wireguard module` で止まり、登録も記録も `ip_forward` の書き換えも起きなかった。
  モジュールを外しただけで読み込める状態では、ファミリの問い合わせがモジュールを読み込み、カーネルモードで転送した。
  `CAP_NET_ADMIN` だけを重ねた `agent.service` の非 root のエージェントは検査を通り、カーネルモードで転送した。
  `AF_NETLINK` を外した配置での検査の結果は、独立レビューで確かめた。
  未確認:非特権の LXC の中でのファミリの問い合わせによるモジュールの読み込み

- エージェントのカーネルモードに変更の通知の購読を加えた(2026-09-25):カーネルモードのエージェントは、外から消されたテーブルと wgft0 に 30 秒ごとの見直しでしか追いつかず、その間の新しい接続は転送されなかった。
  7b.4 節に変更の通知の項を加え、`vpsd` と同じ nftables、リンク、IPv4 アドレスの通知を購読して、30 秒を待たずに直すようにした。
  購読の部品は `internal/dataplane/linuxkernel` の `vpsd` と同じもので、状態を持たない口を加えて `internal/agent` から使う。
  購読の張り直しと公開し直しの間隔は `internal/reconcile` の `Watch` と `RetryGate` をそのまま使い、通知のまとめ方も `vpsd` と同じ 250 ミリ秒にした。
  依存の向き(7a.7 節)は変わらない。
  `internal/agent` が `internal/dataplane/linuxkernel` と `internal/reconcile` を import するだけである。
  自分の書き込みの通知で公開し直しが続かないことは、`vpsd` と同じく、公開の直後に読み直した指紋との比較が担う。
  `vpsd` と変えた点が 2 つある。
  第 1 に、通知の後の見直しは名前を引かず、宛先への試し接続もしない。
  通知はホストの他のテーブルやインタフェースの変更でも届くので、そのたびに DNS へ問い合わせないためである。
  名前の解決し直しとエンドポイントの引き直しは 30 秒ごとの見直しに残した。
  第 2 に、同じ食い違いのログを 1 行に抑える区切りに、通知の後の見直しが食い違いを見つけない回を数えない。
  自分の公開の直後の通知の後の見直しは必ず一致を見つけるので、数えると、他のプロセスが同じ変更を繰り返すたびに 1 行出すためである。
  見直しの失敗のログの文言は、30 秒ごとの見直しに限らない文言に改めた。
  `reconcile.Watch` の購読の失敗のログから「数分ごと」の語を外した。
  エージェントの安全網は 30 秒ごとだからである。
  ユーザー空間モードのエージェントは購読しない。
  ラボの `lab/agentkernel.sh` に `notify` を加え、テーブルを外から 2 回続けて消しても、wgft0 を消しても、5 秒以内に戻り転送も戻ること、直した後の自分の公開の通知でテーブルが差し替わり続けないことを、両方のモードの `vpsd` で確かめた。
  購読を外す変異では、この確かめが落ちた。
  `drift` の見出しの「30 秒ごとの見直し」の語は、通知でも直るようになったので外した。
  `agent doctor` の `runtime_state` の `check_error`(10.2c 節)は、30 秒ごとの見直しと通知の後の見直しの誤りを 1 つの控えに持つので、意味を「直前の見直しの誤り」に広げ、`dataplane.table` の所見の文言も 30 秒ごとと言い切らない形に改めた。
  フィールドの名前と形は変えていない。
  独立したレビューで、間隔のために何も試さなかった通知の後の見直しが、この誤りを消して回復のログを出すことと、エンドポイントの引き直しの後の wgft0 の収束の誤りを通知の後の見直しが消すことを見つけて直した。
  続くレビューで、宛先の名前の解決し直しで変わった DNAT の公開の失敗も、通知の後の見直しが消すことを見つけて直した。
  誤りはテーブルと wgft0 の修復の誤り、名前の解決し直しの公開の誤り、エンドポイントの誤りに分けて持ち、つないだものを `check_error` とログに使う。
  `agent doctor` の稼働中の次の手の文言と 10.2c 節の `interface_differs` と `table_changed` の説明を、通知で直ることに合わせた。
  未確認:リンクや nftables の変更が頻繁なホストでの見直しの負荷(7b.7 節)、公開の失敗が続く間の間隔の空け方は単体テストだけで確かめた。
