# 2026-09-25: control-plane

- 稼働中の `agent rotate-key` で、新しい鍵のピアに古いピアのエンドポイントを引き継ぐようにした(2026-09-25、ラボでの観測を受けて):稼働中の `rotate-key` のたびに、転送が WireGuard の REKEY_TIMEOUT(5 秒)ほど止まっていた。
  エージェントは新しい鍵を設定してすぐに新しい鍵でハンドシェイクを始めるが、`vpsd` が新しいピアを足すのはその後なので、最初のハンドシェイクは捨てられ、エージェントの送り直しまでトンネルが無かった。
  `vpsd` の新しいピアはエンドポイントを持たないので、`vpsd` の側からもハンドシェイクを始められなかった。
  5.2 節のとおり、新しいピアに、同じアドレスを持っていた古いピアのエンドポイントを与える。
  判定は `internal/dataplane` の `InheritedEndpoint` に置き、カーネルモードの wg0(`internal/dataplane/linuxkernel/wg` の `Ensure`)とユーザー空間モードのトンネル(`internal/dataplane/userspace/utun` の `SetPeers`)の両方が、ピアを足すときに使う。
  エージェント側は変えていない。
  トランザクションの失敗で古いピアの集合に戻す場合も同じ規則が働き、戻した古い鍵のピアが新しい鍵のピアのエンドポイントを引き継ぐ(5.2 節)。
  引き継ぎの安全性は 11 節に書いた。
  エンドポイントは古い鍵で認証されたパケットの送信元であり、古い鍵の持ち主が別の場所にいても、新しい鍵を持たない相手とはトンネルが成立せず、転送の中身も渡らない。
  確かめたこと:ラボで、稼働中の `rotate-key` の間に UDP の転送を流し続け、応答が途切れた最長の間隔を `vpsd` とエージェントのモードの 4 通りで直す前と後に測った。
  直す前は 4 通りとも REKEY_TIMEOUT ほど途切れた。
  直した後は、カーネルモードのエージェントでは `vpsd` のどちらのモードでも途切れがほぼ無くなった。
  ユーザー空間モードのエージェントでは、`vpsd` のどちらのモードでも縮まなかった。
  このエージェントは `rotate-key` でトンネルを作り直し、`vpsd` が観測するエンドポイントのポートがそのたびに変わったので、引き継いだエンドポイントは新しいトンネルに届かない。
  この組み合わせで断を縮めるには、エージェント側の変更が要る。
  単体テストで、引き継ぎの判定と、ユーザー空間モードのトンネルでのピアの置き換えと古いピアの集合への戻しを確かめ、ラボのテストでカーネルモードの wg0 でのピアの置き換えを確かめた。
  未確認:実機の回線での効果、Debian 12 以外のカーネルでの効果。

- カーネルモードのエージェントが、登録時と違うトンネルのアドレスを拒むようにした(2026-09-25、所有者の決定、セキュリティレビューの所見を受けて):カーネルモードのエージェントは、server から届く `wg.address` を、IPv4 の帯であることだけを確かめて wgft0 に付けていた。
  アドレス帯の重なりの検査は、`vpsd` のトンネルアドレスを奪う相手だけを見ており、LAN の経路より細かい帯を配られる場合を見ていなかった。
  登録の応答で受け取ったアドレスは保存されず、以後の値と照合されなかった。
  このため VPS を奪った攻撃者は、LAN の帯の一部を覆う帯を配って、エージェントのホストから LAN へ向かう通信をトンネルへ引き込めた。
  影響が公開したポートの外へ広がるので、11 節の脅威のモデルの約束を破る。
  ユーザー空間モードは netstack の中に閉じるので影響を受けない。
  直し方の決定は 2 つである。
  第 1 に、登録で割り当てられたアドレスを `agent.json` の `tunnel_address` に記録し、カーネルモードのエージェントは記録と違う `wg.address` の全体状態を、wgft0、アドレス、経路に触る前に拒む。
  これが守りの境界である。
  第 2 に、アドレス帯の重なりの検査を両方向にし、wgft0 の帯が他のインタフェースのアドレスか既定経路以外の経路を含む場合も、それらに含まれる場合も拒む。
  これは多重の守りで、利用者の設定の誤りで帯が LAN と重なる場合も止める。
  帯を私用アドレスに限る案は、既存の設定を壊すおそれがあるので採らなかった。
  7b.1 節、9 節、11 節、7a.11 節を直した。
  実装で決めたことが 4 つある。
  登録の応答はアドレスだけを返すので、帯の長さは最初に適用できた全体状態から記録する。
  記録の無い `agent.json` でも最初に適用できた全体状態の値を記録し、起動時は `last_state` を先に適用するので、更新したエージェントは更新の前に受け取った値を記録する。
  拒んだ全体状態は適用せず、wgft0 とテーブルを直前の全体状態のまま残して 30 秒ごとの見直しも続け、拒んだことをハートビートのトンネルの状態に載せる。
  ユーザー空間モードは記録を持つが照合では拒まず、警告を出すだけにして、公開済みの挙動を変えない。
  検証は、server が配る wg 設定のうちホストに書く前に確かめる値をエージェントの中の 1 か所に集める形にした。
  この集約の副作用として、トンネルが立っている間に届いた形の誤った mtu、keepalive、server の公開鍵も、wgft0 とテーブルを残したまま拒み、見直しを続けるようになった。
  以前は同じ場合に wgft0 とテーブルを残したまま見直しを止めていた。
  重なりの検査からは、既定経路に加えて `0.0.0.0/1` と `128.0.0.0/1` を除外した。
  OpenVPN の `redirect-gateway def1` がこの 2 本を入れるので、除外しないとその VPN を使うホストではどの帯でもカーネルモードが起動できないためである。
  重なりのエラーの文面には、帯を移す案と並べてユーザー空間モードで動かす案を示した。
  独立レビューで、公開に失敗した古い世代の試し直しが通ると新しい世代の拒否の表示が消えることが見つかったので、拒んだ世代と同じか新しい世代を受け入れたときだけ表示を消すようにした。
  ラボで、乗っ取られた server を模して、server を止め、そのデータベースの帯とエージェントのアドレスを書き換えてから起動し直した。
  この変更の前のバイナリは、別の帯でも LAN の半分を覆う帯でも wgft0 のアドレスを書き換え、後者では LAN の上半分への経路が wgft0 へ向いた。
  変更の後は、どちらの帯も拒み、wgft0 のアドレス、ホストの経路、テーブルが変わらないこと、拒んだことがエージェントのログ、ハートビート、`agent doctor` に出ること、拒んでいる間も消したテーブルが戻ること、ホストから LAN の上半分のホストへ届くこと、server を元の帯へ戻すとエージェントを再起動せずに転送が戻ることを確かめた。
  server の側が別の帯で動く間は、通しの転送が止まることも確かめた。
  ホストに `0.0.0.0/1` と `128.0.0.0/1` の経路を加えた状態で、エージェントが起動し直して転送することも確かめた。
  未確認:重なりの検査を両方向にしたことで、ラボ以外のホストの既存の経路、たとえば VPN が入れる広い経路と重なって起動が止まる配置の有無

- トンネルが新しい間は、stream の再接続の待ちの上限を 10 秒にした(2026-09-25、所有者の決定、5.2 節):カーネルモードの `vpsd` は、プロセスを止めても wg0 と鍵を残す(9 節)。
  プロセスが止まっている間もトンネルは生きており、エージェントの待ちを打ち切る新しいハンドシェイクは、鍵の更新の周期で起きるだけで、プロセスが戻った時刻とは関係が無い。
  その間に待ちは倍々に伸びるので、プロセスが戻ってから stream が繋がるまでに、伸びた待ちの残りだけ遅れていた。
  その間、転送は続くがルールの変更は届かず、`agent ls` と Web UI はそのエージェントを未接続と示した。
  v1.1 からある挙動で、試験用の実機で観測した。
  所有者の決定は次のとおりである。
  通常の倍々の待ちと 5 分の上限は保ち、WireGuard の最終ハンドシェイクが新しいという証拠がある間だけ上限を 10 秒にする。
  データの経路が生きているという追加の証拠がある場合だけ、積極的に制御の経路を探すためである。
  一度新しかったというだけで 10 秒の上限を保ち続けてはならず、`vpsd` のホストごと消えた場合は通常の上限に戻る。
  新しいハンドシェイクで待ちを打ち切る挙動と、打ち切りによる試みが 2 分に 1 回を超えないことは保つ。
  実装で決めたことを挙げる。
  第 1 に、「新しい」の閾値には、新しい値を持ち込まず、`RejectAfterTime` の 180 秒を使う。
  `server doctor` の `tunnel.handshake` の 3 分の閾値と同じ値である。
  健全なトンネルの最終ハンドシェイクは 145 秒より古くならず、30 秒ごとの点検の遅れを足しても 180 秒に届かない。
  180 秒を過ぎた鍵は送信にも使えないので、それより古いハンドシェイクはデータの経路の証拠にならない。
  第 2 に、経過時間を、値を観測した時刻からと値そのものからの 2 つの起点で測り、両方が 180 秒未満のときだけ新しいとする。
  前者は壁時計が戻った場合に古い値を新しいと数え続けないため、後者は停止の間も wgft0 を残すカーネルモードのエージェントが起動の直後に読む古い値を新しいと数えないためである。
  観測はトンネルの点検が読む値をそのまま使うので、ユーザー空間モードとカーネルモードで同じ判定になる。
  第 3 に、上限は待ちの値そのものに当てる。
  トンネルが古くなった後の待ちは 10 秒から倍々に伸び、上限の下で伸び続けた値へ飛ばない。
  第 4 に、`vpsd` が応答したうえで、再試行では直らない食い違いを示した切断には上限を当てない。
  恒久トークンの拒否と取り消し、`superseded`、版の不一致(`vpsd` の理由コードと、エージェントが `vpsd` の選んだ版を拒む場合の両方)、証明書のピンの不一致、公開鍵の拒否(WebSocket の 1008)が当たる。
  `superseded` では善意の二重起動どうしの振動を抑えるバックオフの役目もある。
  ハートビートの期限切れ、版の宣言の形の誤り、`vpsd` の内部の誤り、429 のような一時的な拒否には当てる(独立レビューの指摘と監督の判断)。
  公開鍵の拒否は理由の文言ではなく符号で見分ける。
  第 5 に、`agent doctor` の `stream.backoff` の値の読み方に、待ちが 10 秒に留まるならトンネルは生きていて server が stream を受けていない、という読み方を加えた(10.2c 節)。
  第 6 に、再接続の待ちの行を、同じ文面なら 1 分に 1 行までに間引いた(10.4 節)。
  上限の下では同じ行が毎分 6 行ほど続くためである。
  第 7 に、健全なトンネルの最終ハンドシェイクが 145 秒より古くならないという根拠に、`vpsd` が鍵の更新を始める側の場合の但し書きを加えた(独立レビューの指摘)。
  この場合は一時的に上限が外れうるが、害は小さいので閾値は変えない。
  但し書きは未確認である。
  ラボで次を確かめた。
  カーネルモードの `vpsd` のプロセスを止め、鍵の更新による打ち切りから待ちが伸びた時点で起動し直すと、修正の前は伸びた待ちの残りだけ stream の再接続が遅れた。
  修正の後は、止めている間の待ちが 10 秒を超えず、起動し直してから待ちの上限の内に繋がった。
  エージェントのユーザー空間モードとカーネルモードで同じ結果だった。
  homerouter で WireGuard の UDP を落とし `vpsd` も止めると、待ちは初めは 10 秒で止まり、最後のハンドシェイクから 180 秒の内に 10 秒から倍々に伸び始めた。
  これも両方のモードで同じだった。
  ユーザー空間モードの `vpsd` を止めて起動し直す場合は、修正の前も後も、起動し直した後の新しいハンドシェイクによる打ち切りで繋がった。
  `vpsd` が止まっている間の `agent doctor` は、`stream.backoff` に 10 秒の待ちを示した。
  `lab/agentkernel.sh` に、この 2 つの場面を確かめる `reconnect` と `stale` の検査を加えた。
  未確認:実機、Windows と macOS のエージェント、多数のエージェントが同時に試す場合の `vpsd` の負荷、API のポートを黙って捨てるファイアウォールの下での試みの間隔

- そのまま打つコマンドとして示す場所に完全なルールの ID を使うようにした(2026-09-25、所有者の決定):`server doctor` の次の一手は `wgft rule enable r_01M3AWMEPZ…` のように省略記号付きの短い ID を埋めており、そのまま打つと `rule "r_01M3AWMEPZ…" not found` で拒まれた。
  `rule deny rm` と `rule allow add` の次の一手と、`server doctor` の終了の 1 行も同じ形だった。
  10.2 節に、表の ID の列は短い形でよく、コマンドとして示す場所には完全な ID を使うという境界を書き、次の一手と終了の 1 行を完全な ID にした。
  あわせて、ルールの ID を受け取るコマンドが末尾の省略記号を落として前方一致で受けるようにした。
  表の短い形を貼る運用者は、次の一手を直しても残るためである。
  前方一致が 2 つ以上のときは、これまでの「複数に一致する」だけの拒否をやめ、候補の完全な ID を挙げる。
  ラボで、この変更の前の版の次の一手をそのまま打つと not found で拒まれること、この版の次の一手と `rule ls` の短い形がそのまま通ること、前方一致が 2 つのときに候補の ID を挙げて拒むことを確かめた。
  独立レビューの指摘を受けて、省略記号の扱いを狭めた。
  `rule import` と管理用 API は任意の ID を受けるので、`web` と `web...` の 2 本があると `web...` が `web` を指し、ルールが 1 本の配置では `r_...` がそのルールを指していた。
  生の入力の完全一致を先に試し、省略記号を落とした残りには短い形の 12 文字を求めるようにした(10.2 節)

- 公開ポートを外から確かめる案内を、UDP のルールでは実際のクライアントに向けた(2026-09-25):`server doctor` は UDP のルールにも `nc -vz <this vps> <port>` を案内していた。
  `nc -vz` は TCP の接続を試すので、正常な UDP のルールが届かないように見える。
  10.2a 節の「試していない範囲」のとおり、`rule.public_port` の次の一手と、試していない範囲の「外からの到達」の項を、TCP には `nc -vz`、UDP には実際のクライアントを示す形に分けた。
  UDP のルールの次の一手には、宛先が応答すれば `rule.target` の補足の行に server が見た応答の時刻が出ることを添えた。
  ラボで、UDP のルールの次の一手と試していない範囲の項が実際のクライアントを示し、TCP のルールが `nc -vz` のままであることを確かめた

- エージェントのホストの `ip_forward` が 0 のルールを、VPS の値に読めない形で示すようにした(2026-09-25):カーネルモードのエージェントのホストで `net.ipv4.ip_forward` が 0 のとき、エージェントは LAN の宛先のルールを「`net.ipv4.ip_forward is 0; the kernel does not forward to a target that is not this host`」という理由の `error` で報告していた。
  `server doctor` はこれを `target_error` に分類して宛先のサービスを確かめるよう案内し、`status` も同じ文をどのエージェントの報告かを言わずに示していた。
  VPS で読むと「this host」は VPS に読める。
  10.2a 節のとおり、`rule.target` の理由の符号 `agent_ip_forward_off` を加え、所見はエージェントの名前を出してそのホストの値であることを述べ、次の一手はそのホストの sysctl、エージェントの再起動、そのホストの `agent doctor` を示すようにした。
  エージェントの理由の文言も「on the agent host,」で始めた(7b.1 節)。
  旧い版のエージェントの文言も同じ符号に分類する。
  `status` の Rules 行は、エージェント側の報告の失敗に、どのエージェントの報告かを添えるようにした(10.2b 節)。
  10.2b 節の混在の例は、同じ入力をこの版で動かし直した出力に改めた。
  ラボで、カーネルモードのエージェントのホストの `ip_forward` を 0 にすると、この変更の前の版の `server doctor` が宛先のサービスを確かめるよう案内することを再現し、この版が `agent_ip_forward_off` とエージェントの名前を示すこと、`status` がエージェントの名前を添えること、案内のとおりエージェントを起動し直すと値が 1 に戻ることを確かめた
