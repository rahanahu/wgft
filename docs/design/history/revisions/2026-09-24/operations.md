# 2026-09-24: operations

- `server check` が、新しい版が書いたスキーマを開けないことを見落としにくくした(2026-09-24、所有者の決定):`internal/vpsd` の `Check` は、サーバのデータベースを読み取り専用で開けなかった場合、所見を他の nft の検査などと同じ 1 行の `cannot open` の文言で示し、終了コードは 0 のままにしていた。
  ステージングで、新しい版が書いたスキーマのデータベースに対して旧い版の `server check` を動かすと、「server database schema is newer than this binary」の行が他の所見に紛れ、見落とされうることが分かった。
  7a.11 節は `server check` の終了コードが 0 のままであることを v1.0 の保証としており、サーバのデータベースを開けない場合もその一部である。
  ロールバックの最中に読むのは旧い版の `server check` であり、旧い版はこの改訂を持たないので、終了コードだけを変えてもロールバックの助けにはならない。
  終了コードは変えず、新しい版が書いたスキーマで開けない場合(`store.ErrSchemaNewer`)だけ、他の行に紛れない専用の見出し行を出すことにした。
  見出し行は版番号とこの版が対応する上限を名指しし、出力の最初のほうと最後の両方に同じ文言で現れるようにした。
  この見出し行にも同じ限界がある。
  ロールバックの最中に読む `server check` がこの改訂より前の版なら見出し行は出ないので、見出し行が助けになるのは、戻す先が v1.2 以降のロールバックに限られる。
  `internal/vpsd/store` に、`ErrSchemaNewer` の版番号を運ぶ型 `SchemaNewerError` を加え、`Open`(`server run` が使う)と `OpenReadOnly`(`server check` が使う)の両方がこれを返すようにした。
  `server run` 側の拒否の組み立て(9・11b 節)は変えていない。
  それ以外の理由でサーバのデータベースを開けない場合(権限、他プロセスによる保持、壊れたファイルなど)の文言は変えていない。
  7a.11 節の記述に、この専用行の 1 文を足した。
  確かめ方:ホストの単体テストで、新しい版が書いたスキーマを開けない場合に終了コードが 0 のままであること、専用の見出し行が出力の先頭付近と末尾の両方に現れること、それ以外の理由で開けない場合は終了コードが 0 のままで見出し行を出さないことを確かめた。
  専用の見出し行を出さない、終了コードを変える、出力の末尾に繰り返さないの各変異を入れ、対応するテストが落ちることも確かめた。
  未確認:実機とラボでの確認は行っていない。

- エージェントの撤去 `wgft agent teardown` を加えた(2026-09-24、所有者の決定を含む):カーネルモードからユーザー空間モードへの切り替えの関門は `agent teardown` を案内していたが、コマンドが無かった。
  10.3 節のとおり、停止したカーネルモードのエージェントが残した WireGuard インタフェース、conntrack のエントリ、`table inet wgft_agent`、`agent.json` のカーネルモードの記録を消すコマンドを加えた。
  所有者の決定は次のとおりである。
  稼働中のエージェントには何もせずに拒否する。
  所有の根拠は鍵とし、今の鍵か 1 つ前の鍵を持つインタフェースだけを消す。
  登録の情報と鍵は残し、撤去の後にユーザー空間モードで起動し直せるようにする。
  `ip_forward` は戻さず、戻すコマンドを示す。
  知らないモードの記録では何も消さずに止まる。
  1 回限りの操作としてフラグで受ける。
  実装で決めたことを挙げる。
  第 1 に、別の名前で今の鍵か 1 つ前の鍵を持つインタフェースも消す。
  起動時のエージェントは警告だけにとどめるが、撤去は運用者が明示して実行する後片付けであり、所有の根拠の鍵は名前が変わっても変わらない。
  第 2 に、インタフェースを最初に消し、テーブルを後に消す。
  逆の順では、wgft0 が残る間に入口の守りが無くなる。
  第 3 に、公開の記録と、収束が済んでいない前の公開の列から、wgft が DNAT した conntrack のエントリを見分けて消す。
  `last_state` が無ければ、消す前のインタフェースのアドレスでエージェントのフローを見分ける。
  撤去が記録を消した後は、カーネルモードで起動し直しても撤去の前のフローを見分けられないためである。
  第 4 に、確認の `--yes` は持たない。
  撤去は認証情報を残し、カーネルモードで起動し直せば資源が戻るので、`server teardown` が確認を求める元に戻せない操作に当たらない。
  第 5 に、設定の名前にある鍵の一致しないインタフェースは触らずに示し、撤去は成功として終える。
  ユーザー空間モードはカーネルのインタフェースを使わないので、残ったリンクは切り替えを妨げない。
  第 6 に、指したデータディレクトリに `agent.json` が無ければ何も消さずに終了コード 1 で止まる(所有者の決定)。
  稼働の判定はそのディレクトリのロックファイルしか見ないので、`--data-dir` を誤ると稼働中のエージェントのテーブルを消していたことが、独立レビューのラボでの再現で分かった。
  第 7 に、知らないモードの記録を種別 `conflict` の拒否とし、関門の文面から撤去の案内を外した。
  第 8 に、root のプロセスが状態ファイルを書き換えるときに元の持ち主を保つようにした(9 節)。
  移せなければ警告にとどめ、保存は続ける。
  同梱の unit はエージェントを `User=wgft` で動かすので、root の撤去が持ち主を root に変えると、エージェントは次の起動で状態ファイルを読めない。
  この直しは停止中の `rotate-key` にも効く。
  ラボで、サーバのカーネルモードとユーザー空間モードの両方について次を確かめた。
  稼働中のエージェントには何もせずに拒否すること。
  カーネルモードの残骸があるとユーザー空間モードの起動が関門で止まること。
  撤去が wgft0、別の名前で今の鍵を持つインタフェース、テーブル、記録を消し、wgft が DNAT した conntrack のエントリを閉じること。
  別の鍵の WireGuard インタフェースと関係の無いテーブルに触れないこと。
  root の撤去が `agent.json` の持ち主を保つこと。
  撤去の後にユーザー空間モードで TCP と UDP が転送されること。
  カーネルモードで起動し直せば転送が戻ること。
  停止中の `rotate-key` の後に 1 つ前の鍵を持つ wgft0 を消し、`last_state` が無くても conntrack のエントリを閉じること。
  `agent.json` の無いディレクトリを指した撤去が、稼働中のエージェントのテーブルとインタフェースを消さず、転送が続くこと。
  別の鍵の wgft0 を示して残し、成功として終えること。
  ホストの再起動の後のように記録だけが残る場合に記録を消すこと。
  知らないモードの記録では何も変えずに終了コード 3 で止まること。
  `CAP_NET_ADMIN` の無い実行が種別 `prerequisite` の拒否になること。
  2 回目の実行が何もせずに成功すること。
  カーネルモードで動いていたエージェントを止めてからユーザー空間モードで転送が戻るまでの断を測った。
  止めている間は転送が続き、断は撤去から始まる。
  Windows と macOS での拒否は、ホストの単体テストで OS を差し替えて確かめただけである。
  未確認:実機、非特権の LXC、root でなく `CAP_NET_ADMIN` だけを持つ利用者での撤去、Windows と macOS の実機での拒否
