# 2026-09-24: kernel-agent

- エージェントのカーネルモードを骨格として設計した(2026-09-24、所有者の決定):エージェントは `WGFT_MODE=kernel` を明示したときだけ、カーネルの WireGuard インタフェースと `table inet wgft_agent` の DNAT で LAN の宛先へ転送する。
  既定は今のユーザー空間モードのままである。
  7b 節を新設し、2 節、7 節の冒頭と末尾、7a.2・7a.7・7a.8・7a.11 節、9・10.2c・10.3・11・11a・11b・13 節を改めた。
  守る意味は、カーネルモードでもユーザー空間モードと同じ「転送できる」「転送できない」を保ち、backend 全体の失敗とルール単位の失敗を混ぜないことである。
  ルールの失敗は 3 つの種類に分けた。
  許可一覧の外、名前の解決の失敗、ループバックの宛先はルール単位の失敗で、そのルールの DNAT を作らない。
  TCP の宛先の接続確認の失敗は `error` の報告だけで、DNAT を残して転送を続ける。
  テーブル全体の公開の失敗は backend 全体の失敗で、処理済み世代と `last_state` を進めずに旧いテーブルを残して試し直す。
  `wgft agent teardown` は、`server teardown` と同じく稼働中のエージェントに対しては何も消さずに拒む。
  `agent doctor` では、カーネルモードの `agent.process` の停止を FAILED のまま総合判定から外し、`dataplane.interface`、`dataplane.table`、`host.forwarding` に総合判定を動かさせることにした。
  ルール単位の失敗は、7b.3 節の 1 つ目と 2 つ目の種類のどちらも `dataplane.table` の FAILED として示し、リスナーの無いカーネルモードでは `relay.listeners` を NOT TESTED とする。
  停止中の `dataplane.table` は、`agent.json` の `LastState` と直近の公開の記録を実際のテーブルと比べ、公開すべきルールの DNAT が欠けていれば FAILED とする。
  指紋の完全な一致と TCP の接続確認の結果は再現できないので、一致しても OK ではなく UNKNOWN とし、終了コードは 0 のままとする。
  テーブル全体の公開の失敗は、旧いテーブルが転送を続けるので、`dataplane.table` の所見にとどめる。
  `relay.allow_targets` はカーネルモードでも一覧を示す。
  終了コード 1 が「このホストのエージェントが、今の状態では転送を担えない」を意味し続けるためである。
  FAILED にするのは `ip_forward` が 0 であるような確かな事実だけとし、他のテーブルの `policy drop` と `rp_filter` は手掛かりとして示す。
  停止中のエージェントを `CAP_NET_ADMIN` の無い利用者で診断してカーネルの状態を読めない場合は、層 2 の終了コード 2 とし、例外として root での実行も案内する。
  ホスト名の解決の結果が変わっても、成立済みのフローは切らない。
  停止中の `rotate-key` と撤去は 1 つ前の鍵を扱い、状態ファイルを失った場合の手順を示す。
  `WGFT_MODE=kernel` を既にエージェントへ渡している配置と、カーネルモードから旧い版へ戻す場合は、リリースノートで知らせる。
  10.2c 節の表への行の追加は、表と実装を両方向に照合するテストがあるので、実装と同じ変更で行う。
  内部の構造は、エージェント全体を `reconcile.Runtime` へ移さず、`internal/agent` の中に dataplane の境目を切る形にした。
  7a.7 節の「reconcile を server と agent が共有する」という記述は実装と食い違っていたので、事実に合わせて書き直し、13 節の同じ項目を閉じた。
  13 節の「`agent doctor` を同じ利用者で手軽に実行する方法」も、稼働中のエージェントが自分の実行主体を答える形で閉じた。
  設計の前にラボで確かめたことを記す。
  範囲のずらしを表す無名の連結 map の DNAT と MSS のクランプを google/nftables で組め、`nft list` の表示が `nft` コマンドで入れた場合と一致し、通信も通ったので、`nft` コマンドへの依存は要らない。
  PMTUD の ICMP を落とす経路では、クランプが無いと大きな TCP が両方向とも止まり、片方の向きだけのクランプでは片方の向きが止まり、両方の向きを `rt mtu` でクランプすると両方向とも通った。
  非 root のプロセスが `CAP_NET_ADMIN` だけを持てば、WireGuard インタフェース、nftables、conntrack、`ip_forward` のすべてを操作でき、`DynamicUser` と `CAP_NET_ADMIN` の systemd の unit でも同じだった。
  `ProtectKernelTunables=yes` は `ip_forward` の書き込みを止める。
  非特権の LXC の中でも同じ操作ができ、`ip_forward` はコンテナの network namespace に閉じてホストの値を変えなかった。
  コンテナの `ip_forward` の初期値はホストの値を写すので、エージェントは常に明示して書く。
  ホスト自身の LAN のアドレスへの DNAT は input を通って届き、サービスには VPS のトンネルアドレスが送信元として見えた。
  `127.0.0.1` への DNAT は既定では届かず、wgft0 に `route_localnet` を立てると届いた。
  ユーザー空間モードのエージェントでは、ルールの変更の後、CLI が戻った直後にはエージェントが新しい世代を報告し終えていた。
  `server doctor` の理由の符号 `listener_bind_failed` には、ユーザー空間モードでも利用者の操作から届く経路が見つかっていない。
  符号は残し、カーネルモードの公開の失敗には既存の `target_not_allowed` と `target_resolve_failed`、新しい `target_loopback_unsupported` を使う(7b.3 節)。
  未確認:LAN の側に小さい MTU の区間がある場合とホスト自身の LAN のアドレスへの DNAT での MSS、入る向きの SYN でも `rt mtu` が wgft0 の MTU から決まる理由、固定の `User=wgft` の unit に `CAP_NET_ADMIN` を重ねた配置そのもの、SELinux と AppArmor、Proxmox と Incus のコンテナ、WireGuard のモジュールを自動で読み込めないホスト、`rotate-key` の途中で鍵がずれた場合、プロキシモードと疎通確認が DNAT を通って届くこと、カーネルモードのエージェントでの世代の遅れ、Docker でのカーネルモード。
  実装はまだ無い。

- エージェントのカーネルモードの WireGuard インタフェースを収束させる部品を実装した(2026-09-24):7b.1 節と 7b.4 節のとおり、`internal/dataplane/linuxkernel/wg` に、単一のピアのインタフェースの収束、鍵による所有の判定、診断のための読み取り、撤去を加えた。
  エージェントへの組み込みはこの変更に含めていない。
  インタフェースの作成、MTU、アドレスの扱いはサーバの wg0 と共有する。
  節が実装に委ねていた所有の判定の細部を 7b.4 節に書いた。
  空の鍵はどちらの鍵とも一致させない。
  1 つ前の鍵を持つインタフェースは、同じ収束で今の鍵に書き換える。
  同名の WireGuard 以外のリンクには触れない。
  鍵の一致しないインタフェースを引き継ぐ手段は持たない。
  この決め方には代償がある。
  インタフェースを作った直後、鍵を書く前にエージェントが落ちると、鍵の無いインタフェースが残り、次の起動は終了コード 1 で止まる。
  運用者が `ip link del` で消すまで戻らない。
  サーバの wg0 も同じ窓を持ち、鍵だけで所有を判定する 9 節の原則を崩さないため、この窓は許容する。
  エンドポイントについては、名前の解決をエージェントのプロセスに残し、収束には解決の結果を渡す形にした(7b.1 節)。
  解決できていない間の収束はカーネルの値を残すので、起動時に DNS が引けなくても、停止中に転送を続けていたエンドポイントを消さない。
  解決の結果を渡した収束は、カーネルの値がそれと違えば書き換える。
  待ち受けポートは収束させない。
  手で決めた待ち受けポートも書き換えないのは、ポートを設定し直すとソケットを開き直すためである。
  サーバの wg0 が行う待ち受けポートの衝突の検査は、エージェントのインタフェースには行わない。
  待ち受けポートを固定しないためである。
  アドレス帯の重なりは、レビューで初めは検査していなかったことが分かった。
  ラボで LAN のインタフェースに `10.201.0.50/24` を置き、エージェントのアドレスを `10.201.0.2/24` にすると、収束は黙って成功し、LAN の経路が勝って `vpsd` への応答が LAN へ出る形になった。
  他のインタフェースのアドレスか経路が `vpsd` のトンネルアドレスへの通信を wgft0 から奪う場合に、最初の書き込みの前に終了コード 1 で止めることにし、7b.1 節に書いた。
  再レビューを受けて、帯と重なるだけで拒む初めの規則を狭め、`vpsd` のトンネルアドレスを含まない細かいアドレスと経路は妨げないようにした。
  帯の上半分を使うコンテナのブリッジのような配置を拒まないためである。
  `vpsd` のトンネルアドレスを含むが wgft0 の帯より広い経路も、wgft0 の経路に負けるので拒まない。
  拒めば、エラーの文面が述べる「サーバへの通信が wgft0 を通らない」が事実でなくなる。
  鍵を持たないインタフェースを見つけたときの文面は、エージェント自身が作りかけて残したものである見込みが高いことと、`ip link del` での消し方を示し、ドライランに空の鍵を公開鍵として出さない。
  7b.1 節には、エージェントへの組み込みのための指針として、名前を引く契機と 30 秒ごとの収束に渡すエンドポイントの扱いも書いた。
  ラボで確かめたこと:作成と 2 回目の収束で何も変えないこと、外から変えた MTU、アドレス、up、余分なピア、AllowedIPs、keepalive、エンドポイントが宣言に戻ること、鍵の一致しないインタフェース、鍵を持たない WireGuard、同名の dummy のリンクに何も書かないこと、1 つ前の鍵のインタフェースを今の鍵に書き換えてピアと待ち受けポートを保つこと、1 つ前の鍵を渡さなければ同じインタフェースを他人のものとみなすこと、ループバックの UDP で実際にハンドシェイクが成立すること、古いエンドポイントではハンドシェイクが成立せず、引き直しの結果を渡すと数秒で成立すること、撤去が今の鍵と 1 つ前の鍵のインタフェースだけを消すこと、`vpsd` のトンネルアドレスを覆う LAN のアドレスでは何も作らずに止まり、広い経路では止まらないこと、作った直後の段で失敗した呼び出しがインタフェースを残さないこと、`CAP_NET_ADMIN` の無いプロセスの読み取りが権限の誤りとして見分けられ、収束がエージェントの文面の prerequisite の拒否になること。
  狭めた規則のうち、`vpsd` のトンネルアドレスを覆う細かい経路で止まり、覆わない細かい経路では止まらないことも、ラボで確かめた。
  未確認:実際の `rotate-key` の途中で落ちた場合の通しの動作(エージェントへの組み込みの後に確かめる)。
  レビューでは、`vpsd` の側がセッションを失った後、keepalive だけを送るエージェントがハンドシェイクをやり直すまでの時間をラボで測った。
  測ったのは、keepalive を 5 秒にし、エージェントがハンドシェイクを始めた側のセッションの 1 つだけで、123 秒だった。
  keepalive は WireGuard の 15 秒の再ハンドシェイクの契機を起こさず、鍵の寿命の REKEY_AFTER_TIME か REJECT_AFTER_TIME まで待つためである。
  エージェントが応じた側のセッションでの最長で約 180 秒という値は、REJECT_AFTER_TIME から導いた値であり、測っていない。
  ユーザー空間モードは keepalive ごとにトンネル内へ ping を送るので、同じ場面で 15 秒から 40 秒ほどで戻ると見込む。
  この値も keepalive の間隔から導いた値であり、未確認である。
  カーネルモードでもユーザー空間モードと同じ意味を保つため、keepalive ごとに UDP のデータグラムを送ることを 7b.1 節に定めた。
  実装はエージェントへの組み込みで行う。

- エージェントの `table inet wgft_agent` を組む部品を実装した(2026-09-24、所有者の決定を含む):`internal/dataplane/linuxkernel/nft` に、ルールと名前の解決の結果と宛先の許可一覧からポートごとに DNAT するかどうかと実効宛先を決める判定、その結果からテーブル全体を 1 つのバッチで差し替える組み立て、テーブルを読み戻して公開の記録と比べる読み戻しを加えた。
  判定の結果はそのまま 7b.4 節の公開の記録になる。
  記録はポートの範囲ごとに持ち、公開の元にした世代を持つ。
  7a.3 節の指紋はテーブル名を引数に取る形にし、server とエージェントで共有する。
  エージェントへの組み込みはまだ無い。
  所有者が 4 つの点を決めた。
  MASQUERADE の行に `iifname "wgft0"` を加え、wgft0 から入って DNAT したフローだけの送信元を書き換える。
  骨格の行は、エージェントのホストで他のテーブルが DNAT したフローにも掛かり、その宛先のサービスから見た送信元を変えていた。
  DNAT の前に入口の守り filter_pre を置き、wgft0 から入る新しい接続のうち公開した (プロトコル, ポート) の組だけを通す。
  守りの行が無いと、他のテーブルが全アドレスに公開したポートに VPS から wgft0 のアドレスで届いた。
  カーネルモードは IPv4 の宛先だけを扱い、ホスト名は A レコードだけで解決する。
  ホスト名が複数の A レコードに解決されたときは、ポートごとに許可一覧が通すアドレスだけを残してその中で最も小さいアドレスを使い、他のアドレスへの切り替えと振り分けは持たない。
  7b 節の骨格が実装に任せていた細部は次のとおり決めた。
  DNAT の行の並びとコメント、範囲のルールはずれが 0 でも map で書くこと、範囲の一部のポートを許可一覧が拒んだ場合は行を宣言の範囲で照合して map からそのポートを外すこと、未指定のアドレス `0.0.0.0` をループバックと同じく拒むこと、解決の結果に混ざるループバックと未指定のアドレスを使わないことである。
  ラボで確かめたことを記す。
  google/nftables で組んだ表は、同じ内容を `nft` コマンドで入れた表と `nft list` の表示も `nft --debug=netlink list` の式の列も一致し、server の `table inet wgft` を含む他のテーブルを変えず、google/nftables で読み戻せた。
  `nft list` の表示は、map の DNAT のポートを読むレジスタを誤っても変わらず、転送だけが壊れた。
  このため、ゴールデンテストは式の列も比べる。
  google/nftables v0.3.0 に map の要素を 1 通で渡すと、8,001 ポートの範囲では先頭の 1,857 個だけが黙って入り、60,000 ポートの範囲ではバッチ全体が拒まれた。
  要素を区切って送ると、8,001 ポート、60,000 ポート、全幅の範囲のどれも欠けずに入った。
  wgft0 に見立てた veth と LAN の network namespace の間では、TCP と UDP の単一ポートと範囲のルールが LAN のホストに届き、送信元はエージェントのホストの LAN のアドレスだった。
  許可一覧が拒んだポート、wgft0 のアドレスで待つホスト自身のサービス、DNAT しない LAN への転送、ループバックの宛先のルールは届かなかった。
  ホスト自身の LAN のアドレスへの DNAT は届き、送信元は VPS のトンネルアドレスだった。
  LAN のホストが受けた SYN と、VPS の側が受けた SYN-ACK の MSS は、どちらも wgft0 の MTU から決まる値にクランプされていた。
  filter_pre を置いた表では、Docker に見立てたホストの全アドレスの 8080 への DNAT に VPS の側から届かず、公開したポートには届き、公開を変えても成立済みの TCP のフローは続き、エージェントのホストが自分から wgft0 越しに繋いだ接続の返りも通った。
  未確認:本物の WireGuard インタフェースを通した転送(見立てた veth だけで確かめた)、Debian 12 の nftables v1.0.6 以外での表示の一致、Docker そのものを動かしたホストでの filter_pre の効き目(Docker に見立てた DNAT の行だけで確かめた)。

- エージェントのカーネルモードの dataplane を組み込んだ(2026-09-24、所有者の決定を含む):7a.7 節の境目の後ろに、カーネルモードの実装を加えた。
  `WGFT_MODE=kernel` のエージェントは、起動時に wgft0 の所有を判定し、`last_state` へ収束させてから stream に接続し、全体状態のたびに wgft0 を収束させてから `table inet wgft_agent` を 1 つのバッチで公開し、公開の記録を `last_state` と同じ保存で書く。
  所有者の決定を 4 つ加えた。
  第 1 に、このプロセスの最初の wgft0 の収束は stream に接続した後でも起動の一部とし、所有の衝突とアドレス帯の重なりは終了コード 1、前提の欠如は終了コード 3 で終える(7b.4・11b 節)。
  第 2 に、解決に失敗した名前は、宣言の宛先の文字列が同じ間、直前に解決できたアドレスで公開を続ける(7b.2 節)。
  第 3 に、TCP の接続確認は範囲ごとの先頭のポートだけを試す(7b.3・13 節)。
  第 4 に、別の名前で自分の鍵を持つインタフェースを起動時に警告し、消さない(7b.4 節)。
  実装で決めたことは次のとおりである。
  3 つ目の種類の失敗の控えを実行時の状態のメモリにだけ持ち、控えより古い全体状態では置き換えない。
  控えの試し直しが公開できたら、次の 30 秒を待たずにハートビートを送る。
  名前の解決は実行時の状態の排他の外で行い、宛先の名前は同時に引く。
  停止で取り消された名前の解決の結果では公開しない。
  `ip_forward` の記録は値を書く前に保存する(7b.1 節)。
  `agent doctor` の制御ソケットの応答にモードとルールごとの状態を載せる(10.2c 節)。
  ラボで、サーバとエージェントの両方をカーネルモードにして、TCP と UDP が LAN のホストへ届くこと、ルールの状態がサーバへ届くこと、エージェントの停止の間と再起動をまたいで成立済みの TCP のフローが続き、停止の間も新しいフローが通ること、関係の無いルールの追加と削除が成立済みのフローを切らないこと、許可一覧の外に DNAT を作らないこと、ループバックの宛先が `error` になること、エージェントのホスト自身の LAN のアドレスへの DNAT が届いてサービスから見た送信元が VPS のトンネルアドレスになること、公開していないホストのポートと他のテーブルの DNAT に wgft0 から届かないこと、他のテーブルの forward の `policy drop` が起動のログに出ること、ICMP の「フラグメントが必要」を両端で落とす経路で 2 MB の TCP が両方の向きに通り、MSS の 2 行を消すと両方の向きで止まることを確かめた。
  世代の遅れ、つまりルールの変更からエージェントのハートビートが新しい世代を報告するまでの時間をラボで測り、`server doctor` の 60 秒の閾値を大きく下回ることを確かめたので、7b.7 節の世代の遅れの項を外した。
