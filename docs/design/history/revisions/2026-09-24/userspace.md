# 2026-09-24: userspace

- 中継が切る TCP のセッションの netstack の側を RST で切るようにした(2026-09-24):エージェントの中継は、ポートが宣言から消えたとき(ルールの無効化と削除。
  5.1 節で設計したエージェントの無効化も同じ経路を通る)と、実効宛先が変わって閉じ直すときに、中継中の TCP 接続を通常の `Close` で閉じていた。
  エージェントが先に閉じると、netstack のエンドポイントは gVisor の既定の TIME_WAIT に 60 秒残り、相手が閉じなければ FIN_WAIT_2 にさらに長く残る。
  その間は同じポートで待ち受けを開けず、閉じ直したルールと、無効にした直後に有効に戻したルールは、保持が終わった後の 30 秒ごとの再試行まで転送できなかった。
  netstack 同士をつないだ試験で、グレースフルクローズの後は 60 秒のあいだ同じポートで待ち受けを開けないこと、`Abort` の後はすぐに開けること、新しい待ち受けに `SO_REUSEADDR` を付けても開けないことを確かめた。
  この経路の netstack の側の接続を、拒否と同じ `internal/nettun.TCPConn.Abort` で切るように改め、7 節を改訂した。
  エージェントの終了でも netstack 側は同じ経路で RST により切る。
  クライアントは、エージェントの再起動でも、次に送るまで何も気付かず、次に送ると RST を受け取ることを実際の VPS で確かめた。
  7 節の「RST は既存の接続を持つ相手には送らないので、この経路は拒否にだけ使う」は、成り立たなくなったので削った。
  レビューで、待ち受けを閉じる間に accept された接続を見つけた。
  この接続は、適用が `Manager` の錠を持つ間 accept のループで待たされるので、待ち受けを閉じる処理に見えず、その後に中継へ登録されて旧い宛先へつながり、ポートを保持し続けていた。
  accept のループが登録の前に待ち受けが閉じたかを確かめ、閉じていれば登録せずに切るように直した。
  この接続は閉じ直しの bind に間に合わないことがあり、その場合の待ち受けは次の再試行で開く。
  宛先側の実ソケットと、セッションが自然に終わる経路(ハーフクローズ、EOF)の閉じ方は変えない。
  この経路でエージェントが先に閉じた接続(宛先が先に閉じる HTTP のようなセッション)は、終わった時点で中継の管理から外れるので RST で切れず、TIME_WAIT の間ポートを保持する。
  すぐに解放されるのは中継が切るセッションだけである。
  実効宛先の変更については、待ち受けを開き直さずに宛先だけを差し替える方式(`vpsd` の Prepare/Commit の経路が既に使う)にすれば、この保持の影響を受けなくなる。
  この変更には含めず、今後の課題とする。
  接続元制限の変更で切る経路(`vpsd` だけが使う)も同じ閉じ方にしたが、切る接続がホストの実ソケットなので挙動は変わらない。
  `vpsd` のユーザー空間モードが netstack に持つ接続は dial した側で、`Abort` を持たず待ち受けのポートも塞がないので、`vpsd` の挙動も変わらない。
  UDP の待ち受けは閉じた直後に同じポートで開けることを、同じ形の単体試験で確かめた。
  gVisor のソースでは、TCP の待ち受けのソケットは閉じるとその場でポートを解放する。
  ラボでは、`lab/lifecycle.sh` の check 2 に、成立済みの TCP のセッションを実効宛先の変更で切る段と、ルールの無効化とその直後の有効化で切る段を加え、どちらも 10 秒以内に転送に戻ることを確かめる。
  修正前のエージェントは、両モードで実効宛先の変更の段に落ち、待ち受けを開き直せなかった。
  無効化の段は修正前でも両モードで通っていた。
  ユーザー空間モードでの理由は推測のままで未確認である。
  `vpsd` が公開の時点で中継を先にグレースフルに閉じるので、エージェントは後から閉じる側になり TIME_WAIT に入らないという見立てである。
  カーネルモードでの理由は、host の input firewall が既定で drop する実際の VPS で確認した(2026-09-24)。
  conntrack の収束がエントリを黙って消すので、エージェントの FIN は VPS の上で不正なパケットとして扱われる。
  ラボの VPS にはこの drop policy が無いため、不正なパケットに VPS 自身のスタックが RST で答え、ポートはすぐに空く。
  host の input firewall が既定で drop する実際の VPS では、この RST が返らず、修正前のエージェントの netstack 側の接続は FIN_WAIT_1 に残って再送を続けるため、無効化の直後に有効化してもルールが長時間戻らないことを実機で確かめた。
  #211 の修正後は、同じ実機で速やかに戻った。
  未確認:ユーザー空間モードでの無効化の段が修正前に通る理由(上の見立て)、エージェントの無効化の実装(5.1 節)で修正前の保持が起きること、accept を待つ握手済みの接続が、待ち受けを閉じたときにポートを保持しないこと、自然に終わった接続の TIME_WAIT による保持をラボで確かめること

- `rule.target` の理由の符号 `listener_bind_failed` の一致を、エージェントのユーザー空間モードの中継が実際に組み立てる文言の形にも広げ、次の一手の文言も直した(2026-09-24、実機での観測とラボでの再現を受けて):エージェントの userspace モードで、そのエージェント自身のリスナーの bind が失敗する場面で、`server doctor --json` が `rule.target` を `target_error` に分類し、人向けの所見が宛先のサービスを疑わせる案内になっていた。
  ソースコードを追ったところ、エージェントの中継は gVisor の netstack(`internal/nettun/listen.go` の `ListenTCP`、UDP のリスナーが経由する `gonet.DialUDP`)の上で待ち受けを開いており、bind の失敗は Go の `net.OpError` をそのまま経由するが、Op が `listen` ではなく `bind` になるため("bind tcp <トンネルのアドレス>: <err>" の形。
  net.Listen の "listen ...: bind: ..." とは組み立てが違うので、以前の判定には当たらなかった)、`target_error` に落ちていた。
  `looksLikeBindFailure`(`internal/vpsd/doctor/checks.go`)に "bind tcp "・"bind udp " への一致を足し、`listener_bind_failed` に分類されるようにした。
  この符号への分岐と次の一手は #191 で既に用意されていたが、次の一手の文言「Find what else on the agent host binds it」は userspace モードでは正確でなかった。
  エージェントの待ち受けはプロセス内の netstack にあり、ホストの他のプロセスとポート空間を共有しないので、他のプロセスを探しても見つからない。
  次の一手を、原因が agent 自身の前の待ち受けか接続にあること、エージェントの再試行(30 秒ごと)とエージェントの再起動のどちらでも空くことを述べる文言に直した。
  `rule.target` の理由の符号のうち、まだ本文に意味を書いていなかった `listener_bind_failed` と `target_error` を 10.2a 節に追記した。
  文言の形そのものと、その原因の一つは、試験用の実機(kernel モードの server、userspace モードの agent、v1.1.1 と v1.1.2)で観測されている。
  試験用の実機で、agent の報告が実際に "bind tcp <トンネルのアドレス>: port is in use" の形になったこと、その場面で `server doctor --json` が `rule.target` を誤って `target_error` に分類し、人向けの出力が宛先のサービスを案内していたこと、同じ場面で `agent doctor` は `relay.listeners` を FAILED `listener_error` とし、所見に "cannot bind" と "port is in use" を含めて正しく示していたことを観測した。
  起きていた経路は、stream が切れてもエージェントがリレーのポートを空けない不具合(#211 で修正済み)で、ルールを無効化してすぐ有効化するような操作の後、しばらく "port is in use" が続いた。
  これは #211 より前の版のエージェントでの観測である。
  #211 で直した今の版のエージェントで、利用者の操作から bind の失敗の経路に実際に至ることも、別の原因からラボで確かめた。
  7 節が本文で示す「宛先が先に閉じる HTTP のようなセッションの後、エージェントが先に閉じた接続は TIME_WAIT の間ポートを保持し、閉じ直したルールは保持が終わった後の再試行まで転送できない」という記述の、bind の失敗としての裏付けである。
  socat の `SYSTEM:` で、接続を受けて 1 行送ってから子プロセスの終了とともに閉じる待ち受け(宛先が先に閉じるセッション)を用意し、TCP のルールでそのセッションを 1 本通した直後にそのルールを削除して同じポートへ追加し直すと、今の版のエージェントで実際に `bind tcp <トンネルのアドレス>: port is in use` の報告と、`server doctor` の `rule.target` FAILED `listener_bind_failed`、直した次の一手の文言を観測した。
  クライアントがまだ開いている間に宛先が先に閉じた場合にだけ起き、クライアントが先に閉じた場合は起きなかった。
  gVisor の TIME_WAIT の既定(7 節、60 秒、`tcp.DefaultTCPTimeWaitTimeout`)が過ぎた後の再試行で自然に OK へ戻ることも確かめ、エージェントの再起動でも同じく戻ることを確かめた。

  元の条件に戻し、ホスト名の宛先で bind が失敗しても `rule.target_resolve` は NOT TESTED `resolved_by_agent` のままであることを固定する試験を足した。
  7a.11 節との関係(2026-09-24、所有者の決定):`listener_bind_failed` への分岐自体は #191 から存在したが、その符号と `target_error` の意味は 10.2a 節の本文には定義されていなかった。

- ユーザー空間のトンネルを閉じるときに、netstack の送り出しが panic しうる不具合を直した(2026-09-24):エージェントのユーザー空間モードのトンネルと `vpsd` のユーザー空間モードのトンネルは、`internal/nettun.Device` を wireguard-go の TUN として使う。
  netstack が送り出すパケットは gVisor の stack の goroutine が `WriteNotify` で受け渡しの channel へ送り、wireguard-go の読み取りが `Read` で受け取る。
  `Close` はこの channel を閉じていた。
  gVisor の `channel.Endpoint` の `RemoveNotify` は通知の途中の呼び出しを待たないので、`Close` の時点で受け渡しを待っている `WriteNotify`、または `Close` の後に送る `WriteNotify` は、閉じた channel への送信で panic し、プロセスごと落ちる。
  エージェントは設定の変更と watchdog の判定でトンネルを作り直すので、この `Close` は終了のときだけでなく稼働中にも起こる。
  依存する版の wireguard-go の `tun/netstack` も同じ形である。
  受け渡しの channel は閉じず、閉じたことを別の channel で知らせ、`WriteNotify` と `Read` はどちらもその合図を待つ形に改めた。
  閉じた後に届いたパケットは捨てる。
  `Close` の 2 回目以降の呼び出しは何もしない。
  単体試験で、`WriteNotify` が受け渡しを待つ間に `Close` を呼ぶと、修正前は閉じた channel への送信で panic し、修正後は panic せずに返ることを確かめた。
  netstack 同士をつないだ中継の試験は、この競合を race detector が報告するため `Device.Close` を呼ばずに後片付けしていたが、`Device.Close` を呼ぶ形に改め、`-race` で通ることを確かめた。
  未確認:実際のエージェントと `vpsd` でこの panic が起きた記録は無く、起きる頻度は分からない

- 中継の TCP の accept と UDP の読み取りの失敗で待ち受けを止めないよう直した(2026-09-24):ユーザー空間の中継(`internal/dataplane/userspace/relay`)の TCP の accept のループと UDP の読み取りのループは、待ち受けを閉じた場合以外の誤りでもログに 1 行出して抜けていた。
  抜けると、ソケットは bind されたまま新しい接続もデータグラムも受け付けず、`Manager` はその待ち受けを開いているものとして扱うので、適用も 30 秒ごとの再試行も開き直さない。
  この中継を公開側のホストの実ソケットで使う `vpsd` のユーザー空間モード(6.3 節)では、TCP の accept は、Go の runtime がやり直す EINTR、EAGAIN、ECONNABORTED 以外の誤り、例えばファイル記述子の枯渇(EMFILE、ENFILE)やメモリの不足(ENOBUFS、ENOMEM)で抜けうる。
  UDP の読み取りは、Go の runtime が EINTR と EAGAIN をやり直す。
  Linux 6.1 の `udp_recvmsg` を読むと、それ以外に返りうる誤りはソケットの `sk_err` とコピーの失敗であり、受信のメモリの不足はデータグラムを捨てるだけで読み取りの誤りにはならない。
  bind しただけの UDP のソケットの `sk_err` は、`IP_RECVERR` が無ければ ICMP では立たず(Go は `IP_RECVERR` を付けない)、立てるのは管理者によるソケットの破棄(sock_diag の `SOCK_DESTROY`、`ss -K`)だけである。
  ラボの VM で確かめると、`ss -K` で破棄した UDP のソケットは bind したポートを持ったまま残り、読み取りが 1 回 `ECONNABORTED` で失敗した。
  修正前の中継はそこで読むのをやめ、ソケットの受信キューが溜まって中継が止まった。
  修正後は次の読み取りから中継に戻った。
  TCP の待ち受けのソケットの破棄は、同じ VM のカーネルが Invalid argument で断り、待ち受けはそのまま残った。
  エージェントの待ち受けは netstack の上にある。
  依存する gVisor(v0.0.0-20250503011706-39ed1f5ac29c)のソースで、TCP の `Accept` が誤りを返すのは待ち受けの状態でないときだけであることを確かめた。
  UDP の待ち受けは `gonet.DialUDP` に相手のアドレスを渡さずに開く、接続していないエンドポイントである(`internal/nettun/listen.go`)。
  `gonet.UDPConn.ReadFrom` から `udp.endpoint.Read` までの誤りは、読みの期限(中継は `SetReadDeadline` を呼ばない)、`ErrClosedForReceive`(`io.EOF` になる。
  `Close`、`Shutdown` の読み側、stack の `Close` で立つ)、`LastError()` だけである。
  `LastError` を立てる `onICMPError` を呼ぶ `HandleError` は、エンドポイントが接続した状態(`DatagramEndpointStateConnected`)のときだけ呼ぶ。
  もう 1 つの立て方の `SocketOptions.SetLastError` は、`pkg/tcpip` の中に呼び出し元が無く、呼ぶのは wgft が使わない `pkg/sentry` だけである。
  したがってエージェントでは、TCP も UDP も、中継自身が閉じた場合を除いて起きない。
  6.2 節のプロキシモードの中継(`internal/vpsd/proxyrelay`)の accept は同じ形を既に直しており、待ち受けを閉じた場合以外は後退して試し直す。
  同じ扱い(5 ms から倍々に 1 秒まで後退し、成功したら 5 ms に戻し、失敗はリスナーごとに 1 分に 1 回までログに出す)をこの中継の TCP と UDP に入れ、6.2 節、6.3 節、7 節に書いた。
  失敗が続く間のルールの状態は変えない。
  6.2 節の中継と同じく、ログだけで知らせる。
