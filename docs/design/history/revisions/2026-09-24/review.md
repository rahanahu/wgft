- エージェントの無効化と有効化を設計し、revoke の日本語を「削除」に改めた(2026-09-24、所有者の決定):エージェントを登録したまま一時的に止める手段は、これまで無かった。
  止めるにはエージェントを削除するか、ルールを 1 本ずつ無効にするしかなかった。
  削除は登録と鍵を失い、ルールごとの無効化は各ルールの `enabled` の設定を失う。
  5.1 節に、登録、鍵、ピア、ルールの保存値を残したまま、そのエージェントのルールの転送だけを止める無効化を定めた。
  無効は、エージェントの行の `disabled_at` の 1 列だけで持ち、ルールの `enabled` を書き換えない。
  VPS 側では無効なエージェントのルールを dataplane に渡す宣言から外し、エージェントには既存の `enabled:false` として配るので、旧い版のエージェントも既存の扱いで止まる。
  スキーマの版を上げるのは、旧い版の server に戻したときに無効の印を読み飛ばして転送を再開することを防ぎ、起動の拒否で fail-closed にするためである。
  無効化は公開の成否を待たずに配り、有効化は公開が成功してから配る。
  止める向きの配信は先に届いても安全側だからである。
  保存は済んだが公開に失敗した場合は、ルールのバッチと同じく 422 を返す。
  有効化は、無効の間に他のテーブルやプロセスがポートを取った場合に備えて、ルールのバッチと同じ書き込みの時の検査を行い、拒んだ場合は何も保存しない。
  この場合も 422 なので、何も保存しなかったのか、保存は済んだが公開していないのかを、応答の本文で機械が区別できることを保証した。
  世代を進めるかどうかは、配る写しで比べる。
  無効なエージェントのルールの `enabled` だけを切り替えても、配る写しは変わらないためである。
  削除は無効化を前提にしない。
  Web UI のエージェントの削除は、一覧の行から新しいエージェントの詳細ページの「危険な操作」の区画へ移し、名前の入力で確認する。
  元に戻せない削除を、戻せる無効化と取り違えて選ばせないためである。
  警告のバナーの削除は、警告への対処なので残す。
  削除の確認にルールも削除する選択を置く(既定では選ばない)。
  持ち主が削除されたルールの扱いは次の項目に書いた。
  CLI の `agent revoke` の挙動は変えない。
  7a.11 節に、管理用 API の 2 つのルートとエージェント一覧の `disabled`・`disabled_at`、CLI の `agent disable`・`agent enable`、`server doctor` の検査 `agent.enabled` と理由の符号 `agent_disabled`、`agent doctor` の理由の符号 `agent_disabled`、`status --json` の `agents.disabled` と `rules.agent_disabled` を加算として加えた。
  `agents.total` は登録済みのエージェントの総数という意味を、`rules.total` は `Rule.Enabled` が真のルールの数という意味を変えず、それぞれの数え分けの和を総数とした。
  エージェントの無効化はルール自身の `enabled` を変えないので、無効なエージェントやそのルールを総数から外すと、既存のフィールドの意味を狭めることになるためである。
  10.2a・10.2b・10.2c 節には、それぞれの扱いの要点を加えた。
  あわせて、エージェントの無効化と区別するため、本書の日本語で revoke を「無効化」と書いていた箇所を「削除」に改めた。
  ルールの無効化、登録トークンの無効化、HTTP/2 の無効化のように revoke でない「無効化」は変えていない。
  英語の識別子、コマンド名、API のルートは変えていない。
  未確認:実装はまだ無く、ラボでも確かめていない。
  無効化の配信からエージェントがリスナーを閉じるまでの時間は測っていない。

- エージェントの無効化と有効化の server 側を実装した(2026-09-24):5.1 節の設計のとおり、サーバのデータベースのスキーマを版 9 に上げてエージェントの行に `disabled_at` を加え、管理用 API の `POST /api/v1/agents/{name}/disable` と `POST /api/v1/agents/{name}/enable`、エージェント一覧の `disabled` と `disabled_at`、全体状態の `agent_disabled` を実装した。
  CLI の `agent disable` と `agent enable`、`server doctor`・`status`・`agent doctor` での扱い、Web UI は、この変更に含めていない。
  それらが入るまでの間、無効なエージェントのルールは、`status` と `server doctor` と Web UI では公開されていないルールとして故障に数えられ、`server doctor` の次の一手はエージェントの有効化の管理用 API を案内する。
  設計が実装に委ねていた点は次のように定めた。
  422 の本文で「何も保存しなかった」と「保存は済んだが公開していない」を区別するフィールドは `saved` とし、2 つのルートの失敗の応答がすべて持つ(7a.11 節)。
  全体状態に加算するフィールドの名前は `agent_disabled` とした(7a.11 節)。
  エージェント一覧の `disabled_at` は、同じ行の `created_at` と同じく server のローカルの時差で書く。
  有効化の検査に要る読み取りの失敗を 500 とすること、`rule_states` の理由で自分の無効を先に示すこと、公開できなかった世代を後から公開した経路が配ることを 5.1 節に加えた。
  状態が変わらない操作は、7a.11 節のとおり、保存も配信も公開もせず、200 と `changed:false` を返す。
  前の操作が公開できなかった世代の公開は、30 秒ごとの再試行に任せる。
  配信は、公開した世代が進んだときに適用の 1 か所で行うようにした。
  それまでは、ルールのバッチは世代を進めたときだけ配り、公開した世代の進みで配るのは再試行だけだった。
  そのため、公開に失敗した有効化の世代を、変更の無いバッチや削除や登録が先に公開すると、再試行が要らなくなり、エージェントはその世代を受け取らなかった。
  配る写しを作る処理は 1 か所にまとめ、全体状態の組み立てと、ルールのバッチが世代を進めるかどうかの比較の両方がそれを使う。
  2 か所が別々に写すと、配る内容が変わったのに世代が進まないことが起きうるためである。
  ラボで確かめたこと:kernel と userspace の両モードで、2 台のエージェントのうち 1 台を無効にすると、そのエージェントの TCP と UDP のルールとプロキシモードのルールが転送をやめ、成立済みの TCP のセッションも切れ、もう 1 台のルールは転送を続けた。
  ルールの保存値は変わらず、無効にしたエージェントは接続したまま、ルールを 1 本も報告しなくなった。
  無効の間に加えたルールは転送しなかった。
  server を再起動しても無効のままだった。
  有効化すると、各ルールは自分の `enabled` のとおりに戻り、無効の間に加えたルールも転送した。
  kernel モードでは、VPS 上のプロセスがルールのポートを bind している間の有効化が 422 と `saved:false` で拒まれて何も保存されないことと、他のプロセスが `table inet wgft` を保持している間の無効化が 422 と `saved:true` を返し、エージェントには届き、保持が解けた後の再試行で公開されることを確かめた。
  v1.1.1 の server は、版 9 のデータベースを新しすぎるとして起動を拒んだ。
  v1.1.1 のエージェントは、kernel モードの server から `enabled:false` の写しを受け取ってリスナーを閉じ、有効化で開き直した(TCP のルール 1 本で、手で確かめた)。
  分かったこと:無効化で成立済みの TCP のセッションを切った直後に有効化すると、そのルールのエージェントのリスナーは、ラボでは保持が終わるまで開かなかった。
  エージェントが中継中の netstack の接続を通常の `Close` で先に閉じるので、その端が gVisor の既定で 60 秒の TIME_WAIT に入り、相手が閉じなければ FIN_WAIT_2 に留まり、その間は同じポートで待ち受けを開けないためである。
  エージェントの無効化はルールの無効化と違って公開より先にエージェントへ配るため、エージェントが FIN を送る時点でも VPS がまだそのフローを変換している可能性が高く、VPS がそのフローを変換しなくなって FIN が届かないという理由は当てはまらないと考えられるが、これは推測であり未確認である。
  エージェントの側で中継中の接続を閉じると、そのポートは少なくとも 60 秒塞がる。
  この保持は、直前の項目の変更(中継が切る TCP の接続を RST で切る)で解消した。
  その変更を含むビルドで確認を流し直し、有効化の直後に、そのルールのリスナーが bind の失敗なしに開き、転送が戻ることを両モードで確かめた。
  未確認:無効化の配信からエージェントがリスナーを閉じるまでの時間は測っていない。
  旧い版のエージェントとの組み合わせは、`lab/version-skew.sh` にまだ入れていない。

- 送信元の一覧の set の要素を分けて送り、差し替えの後に読み直すようにした(2026-09-24):ルールの `source_deny` と `source_allow` の set は、要素のすべてを 1 通の `NFT_MSG_NEWSETELEM` に入れて送っていた。
  要素の一覧を入れる netlink の属性の長さは 16 ビットで、依存するライブラリはあふれを検査しない。
  要素の数を検査する箇所も無かった。
  ラボ(Debian 12、カーネル 6.1)で、1 本のルールに重なり合わない /32 を並べた一覧を確かめた。
  一覧が属性の上限を超えると、set が空か一部だけのまま適用が誤りなく通り、テーブルの指紋も基準として受け入れられた。
  さらに大きい一覧では、カーネルがバッチ全体を拒んだ。
  空の `source_allow` はすべての送信元を落とし、欠けた `source_deny` は拒むべき送信元を通す。
  要素を 32 KiB 以下の通に分けて同じバッチで送るよう改め、差し替えの後に set を読み直して送った要素と比べ、食い違えば backend 全体の失敗とした(6.1 節、7a.3 節)。
  ラボで確かめたこと:上限の前後から 20000 個までの一覧が deny と allow の両方で全部載ること、一覧の最後のアドレスからのパケットが deny では落ち allow では通ること、分けずに送る以前の組み立てでは読み直しが欠けを見つけて適用を失敗させること、カーネルがバッチを拒んだ場合に直前の良いテーブルがそのまま残って転送に効くこと。
  レビューで、失敗した公開が自身の差し替えで生む変更の通知から、公開し直しが 0.3 秒ほどの間隔で繰り返されることが分かった。
  受信側の壁の ENOBUFS も同じ経路を持つ。
  通知による公開し直しの間隔を、1 秒から倍にして 30 秒で頭打ちにした(7a.3 節の再試行)。
  `Observe` が新しく見つけた食い違いは待たずに公開し直すので、失敗の続く期間はどれも、待たない公開し直しを 1 回だけ含んで始まる。
  未確認:読み直しが食い違いを見つけた後の `vpsd` の全体の動きと、間隔を空けた繰り返しは、単体テストだけで確かめ、ラボでは流していない。
  20000 個を超える一覧と、カーネル 6.1 以外では確かめていない。

- エージェントの wgft0 を作業用の名前で作る(2026-09-24):7b.4 節のとおり、エージェントのカーネルモードの WireGuard インタフェースを作業用の名前で作り、鍵を書いてから wgft0 の名前に変えるようにした。
  それまでの作り方では、作った直後、鍵を書く前にエージェントが落ちると鍵の無い wgft0 が残り、鍵の無いインタフェースを他人のものとする規則のため、以後の起動が運用者の手当てまで止まり続けた。
  ラボで、作成の 2 つの段、つまり作業用の名前のリンクを作った直後と鍵を書いた直後にプロセスを SIGKILL で落とし、wgft0 が残らないことと、次の作成が作業用の名前の残骸を消して wgft0 を作ることを確かめた。
  作業用の名前を他の鍵の WireGuard のインタフェースか WireGuard 以外のリンクが持つ場合に、触らずに作成を止めること、作業用の名前に 1 つ前の鍵を持つリンクが残っていれば消して作ること、名前を変える前に同じ名前のリンクが現れた場合にそのリンクに触れず作業用の名前のリンクを残さないことも確かめた。
  鍵の無いインタフェースの文面は、エージェントが残したものとする推測をやめ、他の道具が作ったものとして示すように改めた。
  サーバの wg0 の作り方は変えていない。
  同じ network namespace で同じインタフェース名の 2 つのエージェントが同時に作成を始めた場合の動作は未確認である。
  作業用の名前が同じなので、一方の作成が他方の作りかけのリンクを残骸として消しうる。
  1 つの状態ファイルは flock で 1 つのプロセスしか使えないが、別々のデータディレクトリで同じインタフェース名を使う配置はこの守りの外にある

- エージェントの `WGFT_MODE` の入口、記録、関門を実装した(2026-09-24):11a 節と 11b 節のとおり、エージェントが `WGFT_MODE`(`--mode`)と `WGFT_WG_INTERFACE`(`--wg-interface`)を読み、入口で値を判定し、`agent.json` のモードの記録と照合するようにした。
  カーネルモードからユーザー空間モードへの切り替えは、`WGFT_MODE` の省略を含めて種別 `mode-gate` で拒否する。
  決めたことを挙げる。
  第 1 に、ユーザー空間モードのエージェントはモードの記録を書かない。
  第 2 に、カーネルモードへの切り替えの記録は、鍵を作るよりも前に保存する。
  第 3 に、未知のモードの記録は種別 `conflict` で拒否する。
  第 4 に、稼働中の `rotate-key` も、カーネルモードでは今の鍵を 1 つ前の鍵として新しい鍵と同じ保存で残し、保存に失敗したらメモリの上の 2 つの鍵を元に戻す(7b.4 節)。
  第 5 に、停止中の `rotate-key` は、ロックファイルがあれば flock を取ってから書き換え、無ければロックファイルを作らずに書き換える(9 節)。
  ロックファイルが無い場合に、判定の直後に起動したエージェントの書き込みを上書きしうる狭い隙間は、既知のものとして許容した。
  カーネルモードの dataplane はこの変更に含めていないので、このビルドは関門を通った `kernel` の指定を、記録する前に種別 `prerequisite` で止める。
  確かめたのは単体テストの範囲で、ラボでは既存の結合テストがユーザー空間モードで変わらず通ることだけを確かめた
