# 2026-09-24: web-ui

- 持ち主が削除されたルールを、Web UI でだけ故障に数えないようにした(2026-09-24、所有者の決定):エージェントを削除しても、そのエージェントを持ち主とするルールは残る。
  削除の既定はルールを残すので、同じ名前で登録し直せばそのまま使える。
  このルールは登録を待つ正当な状態であり、故障ではない。
  Web UI は灰色の「エージェント未登録」と示してエラーに数えず、ダッシュボードのルール一覧の上に、ルールが残っている未登録のエージェントごとの帯を置き、その本数のルールをまとめて削除できるようにした(5.1・10.1 節)。
  ルールの詳細ページに置く案は採らなかった。
  問題の単位は削除したエージェントであり、操作の単位もそれに揃えるためである。
  同じ日に、`status` と `server doctor` でもこれらのルールを故障に数えない変更をいったん決めた。
  `status --json` に `rules.agent_unregistered` を加えて degraded から移し、`server doctor` では `agent.enabled` を SKIPPED `agent_not_registered` にして、`rule.public_port` と `agent.connection` の FAILED、ルールと最上位の `status`、それだけが理由の終了コード 1 を変える案である。
  この決定は取り下げた。
  既存の自動化が頼る機械向けの結果を変えるので、7a.11 節の保証では互換でない変更に当たり、同節に例外を設けることも、この 1 点のためにメジャー版を上げることもしないためである。
  `status` と `server doctor` は、次のメジャー版まで今の結果を保つ。
  `agent.enabled` は、登録されていないエージェントのルールで OK とし、既存の結果を動かさない。
  Web UI と CLI の違いは、この保証から来る意図したものとして 5.1・10.2a・10.2b 節に書いた。
  無効なエージェントのルールの `rules.agent_disabled` は、無効が新しい状態で既存の利用者の手元に現れないので、加算として残した。
  未確認:実装はまだ無く、ラボでも確かめていない。

- ダッシュボードのルール一覧に診断の印を置いた(2026-09-24、所有者の決定):ダッシュボードの一覧は適用状態、つまり宣言が適用されたかどうかだけを示していた。
  今転送しているかどうかと止まった位置は、診断の画面を開くまで分からなかった。
  10.1 節のとおり、状態の列の中で適用状態の右に印を置き、診断の画面のそのルールのページへのリンクにした。
  決めたことを挙げる。
  第 1 に、印は 10.2d 節の経路の図を作る関数の出力から選び、判定を作り直さない。
  第 2 に、UNKNOWN の印に添える節点は、図を公開側から見て最初の UNKNOWN の節点とした。
  doctor が持つ値ではなく画面が図から選ぶ値だが、`StoppedAt` と同じ向きの規則である。
  第 3 に、error の理由の文は一覧から外し、ルールの詳細ページと診断の画面で読む形にした。
  第 4 に、ヘッダの全体ヘルスとグループの見出しの error のルール数を、適用状態のバッジの色ではなく、印が FAILED のルールから数えるように改めた。
  バッジの色から数えると、適用済みのルールがハンドシェイクの古さで ✕ WireGuard を示していても件数に入らず、赤い ✕ の行が「エラー 0 件」の見出しの下に並ぶためである。
  件数の意味は変わるが、Web UI は 7a.11 節の保証の外にある。
  第 5 に、持ち主のエージェントが未登録のルールは、診断では FAILED だが、5.1 節のとおり灰色の「エージェント未登録」の印とし、件数に含めない。
  `agent.connection` の reason が `agent_not_registered` であることを契機に、画面が総合判定を読み替える。
  UNKNOWN の節点と並ぶ、画面が自ら決める 2 つ目の値である。
  診断の画面はこのルールを FAILED のまま描いており、揃えるのは後の変更に回した。
  無効なエージェントのルールは、診断が SKIPPED を返すので灰色の印になり、件数に入らない。
  適用状態のバッジも 10.1 節のとおり直した。
  エージェントが未登録なら「エージェント未登録」、無効なら「エージェント無効」を灰色で示す。
  それまでは未登録を「エージェント未接続」と示し、無効なエージェントのルールは server が報告する not_active のために赤の「公開していない」になっていた。
  第 6 に、ダッシュボードとその部分更新は、ルールとエージェントを `doctor.Read` の 1 回の読み取りから組み立てるように改めた。
  1 回の描画のストアの読み取り(ルール、世代、拒否数、エージェント、警告)の回数は、印を加える前と同じである。
  `doctor.Read` はほかに、メモリの上にある適用状態、Resource Guard の状態、エージェントが報告したルールの状態、UDP の応答の観測も読む。
  適用状態と印と件数は同じ時点の証拠から作られる。
  診断の組み立ては、ルールの検査をルールごとに 1 回で振り分け、ルールの本数に比例する費用にした。
  ルールごとに全ルールの検査をなめる形では、費用が本数の 2 乗で伸びた。
  エージェント一覧と警告の部分更新は、ルール一覧を描かないので診断を組み立てない。
  エージェント一覧には印を置かなかった。
  エージェントには `StoppedAt` に当たる止まった位置が無く、1 つの節点を選ぶには新しい判定が要るためである。
  ルールを変えた直後は、エージェントが新しいルール集合を受け取るまで、変えていないルールも含めてそのエージェントのルールの印が ? agent になる。
  `agent.rules_received` がエージェントの世代を server の全体の世代と比べ、閾値の内側の遅れを UNKNOWN の `generation_pending` とするためである(10.2a 節)。
  未確認:印が ? agent になる時間を実機でもラボでも測っていない。
  組み立ての費用はホストのベンチマークで測っただけで、実機の server では測っていない。
  描画は見本のデータを返すデモで確かめた。

- Web UI にエージェントの無効化と有効化を加え、削除を詳細ページの「危険な操作」へ移した(2026-09-24、所有者の決定):5.1 節の無効化と有効化は CLI と管理用 API にだけあり、Web UI のエージェント一覧の行は削除のボタンだけを持っていた。
  10.1 節のとおり、行の操作を「無効化」と「有効化」にし、削除を新しいエージェントの詳細ページ(`/ui/agents/{name}`)の末尾の「危険な操作」の区画へ移した。
  決めたことを挙げる。
  第 1 に、行の操作の語はルールの行の操作と同じ「無効化」と「有効化」にした。
  どちらも転送を止めて設定を残すという同じ意味だからである。
  確認のダイアログは無効化だけに出す。
  第 2 に、削除の名前の入力は server が照合する。
  ブラウザの JavaScript が一致するまでボタンを押せなくするのは補助である。
  警告のバナーの削除は残し、確認のダイアログの後に名前を hidden で送って同じ照合を通す。
  第 3 に、無効なエージェントの行は故障の色でない「無効」で示し、要対応にしない。
  トンネル、ハンドシェイク、ハートビートは控えめな色の参考の値とし、反映待ちの印も出さない。
  窃取の警告を持つ行だけは要対応にする。
  無効の間も恒久トークンは使えるためである。
  第 4 に、ヘッダの全体ヘルスは無効なエージェントをオンラインの分母から外し、「無効 N」を添える。
  第 5 に、持ち主のエージェントが無効か未登録のルールの適用状態は、頭に ● の代わりに横棒 (U+2014) を添えて「エージェント無効」と「エージェント未登録」と示すことにした。
  動いている状態の ● と見分けるためである。
  第 6 に、それらのルールには接続テストのボタンを出さない。
  server がそのルールの疎通確認を拒むためである。
  無効化と有効化の失敗は管理用 API と同じ分け方で 404、422、500 に写し、422 では、何も保存しなかったのか、保存は済んだがまだ反映していないのかを詳細ページに示す。
  削除が誤りを返した場合は、エージェントを読み直し、行が既に無ければ「削除は済んだが転送への反映はまだ」と、残っていれば「削除できなかった」と示す。
  server は行を消してから公開するので、公開の失敗を削除の失敗と示すと、消えたエージェントを消せなかったと誤って伝えるためである。
  Web UI は 7a.11 節の保証の外なので、`POST /ui/agents/{name}/revoke` が名前を求めるようになったことは互換性に触れない。
  削除の確認でルールも削除する選択と、未登録のエージェントの帯は、この変更に含めていない。
  未確認:Web UI からの無効化、有効化、削除をラボの実際の server に対して操作していない。
  ラボの結合テストは、同じ操作を管理用 API と CLI で確かめている。

- Web UI でエージェントの削除と一緒にルールを削除できるようにし、未登録のエージェントの帯を置いた(2026-09-24、所有者の決定):エージェントを削除しても、そのエージェントを持ち主とするルールは残る。
  Web UI でそれを消すには、ルールを 1 本ずつ削除するしかなかった。
  5.1 節と 10.1 節のとおり、詳細ページの削除の確認に「このエージェントのルール N 本も削除する」を置き(既定では選ばない)、選んだときはエージェントを削除した後に既存のルールのバッチ 1 回でそのルールを削除する。
  2 つは 1 つのトランザクションではないが、ルールの削除だけが失敗しても、残るのは転送しないルールなので安全側である。
  その場合は、エージェントは削除したことと、残ったルールを帯から削除し直せることを示す。
  ダッシュボードには、ルールが残っている未登録のエージェントごとに帯を出し、そのルールをルールのバッチ 1 回でまとめて削除するボタンを置いた。
  未登録のエージェントには詳細ページが無いので、帯がそれらのルールを片付ける場所になる。
  一括削除は、エージェントが登録されている場合と、帯が示した本数と今の本数が違う場合と、帯を描いた後にルール集合が変わった場合に、何も削除しない。
  前者は帯を描いた後に同じ名前で登録し直した場合に動いているルールを消さないため、後の 2 つは確かめたより多いルールや確かめた後に変わったルールを消さないためである。
  ルール集合の照合は、読み込みの適用と同じくルール集合のハッシュをバッチの `ExpectedDigest` に渡して行う。
  ルールも削除する削除も、描いた時点のハッシュを削除の前とバッチの両方で照合する。
  登録の確認からバッチまでのごく短い間に同じ名前で登録し直した場合は見分けず、受け入れる。
  登録はルール集合を変えないので、ハッシュでは捉えられない。
  未登録のエージェントのルールを灰色で示してエラーに数えない扱いは、ダッシュボードの診断の印の変更で既に入っており、この変更は帯と件数がそれと同じ規則に従うことを確かめた。
  CLI の `agent revoke`、`status`、`server doctor`、管理用 API の分類は変えていない(5.1 節)。
  未確認:ラボの実際の server に対して、Web UI からルールを伴う削除と帯の一括削除を操作していない。
