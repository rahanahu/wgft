# 2026-09-28: review

- エージェントの keepalive の ping ごとに ICMP の endpoint と identifier が残る不具合を直した(2026-09-28、所有者の決定):ユーザー空間モードのエージェントがトンネル内へ送る ping は、ping ごとに ICMP の endpoint を bind してから接続し、応答を読むと閉じていた。
  固定版の gVisor の ICMP の endpoint の接続は、bind で登録した identifier の登録を解かず、閉鎖は接続の登録だけを解く。
  このため ping ごとに endpoint と identifier が 1 つずつ残っていた。
  identifier の範囲を使い切ると ping は毎回失敗し、`Tunnel.Run` はその誤りを捨てるので、失敗は外から見えない。
  この状態で `vpsd` の側がセッションを失うと、再ハンドシェイクは ping ではなく鍵の寿命を待つ。
  所有者は、この不具合をメモリの少しの増加ではなく時間の経過で keepalive の機能が壊れる不具合として扱い、gVisor を改造せずに直すと決めた。
  endpoint を bind せずに接続する形にした(7 節「keepalive の ping の endpoint」)。
  トンネルの寿命の間 1 つの endpoint を使い回す形は、並行する ping と前の ping の遅れた応答の扱いが要るので採らなかった。
  単体試験では、identifier の範囲を小さくした Device で、範囲の何倍もの回数の ping が往復すること、閉じた後に ICMP の登録が残らないこと、送り出す echo の送信元が Device のアドレスであることを確かめた。
  ラボでは、ユーザー空間モードのエージェントを両方のモードの `vpsd` と組み合わせて確かめた。
  カーネルモードの `vpsd` の wg のインタフェースに届く ping の送信元は、エージェントのトンネルアドレスだった。
  カーネルモードの `vpsd` は wg のインタフェースから新しく入るパケットを捨てるので、修正の前も後も ping に応答しない。
  ping の目的はデータのパケットを送ることなので、応答は要らない。
  ユーザー空間モードの `vpsd` の組では、ping と同じ大きさのデータのメッセージが `vpsd` からエージェントへ返ることを、外側の UDP で確かめた。
  両方のモードで、`vpsd` の側がセッションを失った後に、修正前と同じ程度の時間でハンドシェイクが戻った。
  ping を送らないように改めたエージェントは、カーネルモードの `vpsd` の組だけで確かめた。
  戻るまでの時間は鍵の寿命の桁に延びた。
  この差から、この確認が ping の有無を見分けることが分かる。
  上流の gVisor の master の ICMP の接続も、2026-09-28 の時点で bind で登録した identifier の登録を解かない。
