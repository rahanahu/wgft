# server のメモリの上界

server のメモリの上界は、列挙した保持点ごとの量を合計して計算します。
式に含めない保持点があるため、プロセス全体に無条件のメモリ上限を保証しません。


<a id="プロセス全体のメモリの上界"></a>
プロセス全体のメモリの上界(式に数えた保持点がすべて同時に最悪になっても、それらが使うメモリがそれを超えないと示せる値)は、ユーザー空間モードのホストの要件として示す(2026-09-30、所有者の決定)。
既定の上限(`WGFT_MAX_TCP_FLOWS` が 2048、`WGFT_MAX_UDP_FLOWS` が 8192)で、エージェントが 1 つの `vpsd` の上界は約 8.6 GiB であり、この `vpsd` を動かすホストには約 9.8 GiB のメモリが要る。
式に数えた項は、TCP の宛先の数によりません。
TCP のポートごとの待ち受けと goroutine は、信頼された設定だけが作るので式の外です([TCP のポートごとの待ち受け](memory-limits.md#tcp-のポートごとの待ち受け))。
この値は、後述の式に数えた保持点(入力に応じてデータや状態を持つ場所)がすべて同時に最悪になった場合のものであり、普段の使用量の予想ではありません。
式に入れていない保持点が後述のとおりあり、その中には量の上限を定めていないものもあるので、プロセスのメモリがこの値を超えないことは示せていません。
wgft はメモリの量を見て新しいフローを断る仕組みを持たないので、上界がホストのメモリを超える構成では、すべての保持点を埋める攻撃を受けると OOM になりうる。
既定の上限は変えません。
メモリの小さいホストでは、運用者が後述の表を見て上限を下げる。
カーネルモードの `vpsd` のメモリの上界は、ここでは定めていません。
カーネルモードでも、エージェント用 API の認証前の接続と、プロキシモードのルールの TCP の中継は `vpsd` のプロセスが持ちます。

上界は、保持点ごとの生きているヒープの上界を合計し、それに (1 + GOGC/100) を掛けて数える(2026-09-27、所有者の決定)。
goroutine のスタックとランタイムの領域は、この積とは別の項として足す。
wgft は現在 GOGC を設定しないので、GOGC は Go の既定の 100 とし、生きているヒープの 2 倍を置く。
wgft は GOGC を明示して設定する方針であり、その値は未定です。
メモリのソフト上限は GC の目標なので、上界を下げる根拠にしない(前述)。
カーネルのソケットのバッファはプロセスの外の項であり、ホストに要るメモリを求めるときに別に足す。

`vpsd` の生きているヒープの上界は、次の表の項の和です。
記号の K は `WGFT_MAX_TCP_FLOWS`、U は `WGFT_MAX_UDP_FLOWS`、A はエージェントの数、R は `per_source_rate` を持つルールの数、L は UDP の待ち受けの数を表します。
閉じた後の netstack の TCP の接続は宛先の数によらない Device 全体の表で抑えるので、式は TCP の宛先の数を含みません。
出どころの列の「導出」はソースから読んだ件数と確保の大きさの積、「測定」はホストかラボで測った値、「推定」はソースの構造からの見積もりです。
測定は、どれも 1 つの版の 1 回の測定です。

| 保持点 | 生きているヒープの上界 | 出どころ |
|---|---|---|
| 固定の費用(ランタイム、データベース、管理用 API、トンネル 1 つ) | 17 MiB | 測定 |
| wireguard-go のピアごとのキュー(送信と受信の両方向) | 136.3 MiB × A | 導出 |
| wireguard-go の device 全体のキュー(ハンドシェイクのキューを含む) | 65 MiB | 導出。CPU が 4 個のときの値で、CPU の数に比例して少し増える |
| WireGuard のハンドシェイクの送信元の表 | `64 KiB + 256*(2051+2W)`、W は構築時の CPU 数 | 提案の実用上の見積もり。[件数の制限と残る費用](wireguard-sources.ja.md)を参照 |
| IPv4 の再組み立てと、ピア 1 つの待機の分 | 4 MiB + 0.15 MiB × A | 導出と測定 |
| UDP の受信の会計 | 10.4 MiB | 測定。前述の換算が最も大きくなる datagram の大きさの場合 |
| netstack の出力のキュー | 64 MiB | 導出。測った場面では 7 MiB 以下だった |
| 応答のバッファと UDP の待ち受けの読み取り | 7 MiB + 0.46 MiB × L | 導出と推定 |
| UDP のセッション | 4.5 KiB × U | 測定 |
| [TCP のフロー](#tcp-のフロー-1-本の上界)(固定の分、送信、確認を待つ segment、受信) | 1,598 KiB × K | 測定と導出の和 |
| [TCP の boost](#tcp-のフロー-1-本の上界) | 357 MiB | 測定と導出の和 |
| [閉じた後の netstack の TCP の接続](tcp-retention.md#閉じた後の接続の表) | 128 MiB | 導出。13,107 行 × 1 行の上限 10 KiB。1 行は単体テストで 7 から 8 KiB、ラボで約 5.4 から 6.6 KiB だった |
| 送信元ごとの新規フローの表 | 14 MiB × R | 推定 |
| エージェント用 API の認証前の接続 | 177 KiB × 1024 | 測定。測った要求の形のうち最大のもの |
| エージェント用 API の認証済みの stream | 3.9 MiB × A | 件数は導出、1 本の大きさは測定。確立した 1 本と、確立の前か置き換えられて閉じる途中の 2 本の分 |
| API の制限の表、設定、試し接続 | 12 MiB | 推定 |

goroutine のスタックは 3.2 KiB × U + 24 KiB × K + 16 KiB × 1024 + 55 KiB × A + 2 MiB とする(TCP の項は推定、ほかは測定)。
ランタイムの領域は、10 MiB に生きているヒープの 5% を足した値とする(測定から丸めた)。
プロセスの上界は、生きているヒープの 2 倍にこの 2 つを足した値です。
既定の上限で A、R、L がどれも 1 なら、生きているヒープの上界は約 4.1 GiB で、プロセスの上界は約 8.6 GiB になります。

<a id="tcp-のフロー-1-本の上界"></a>
TCP のフロー 1 本の生きているヒープは、固定の分、送信の側、送って確認を待つ segment、受信の側の和で数えます。
どの側でも、バッファの会計が数えるのは中身の byte であり、gVisor が持つメモリはそれより大きい。

- 固定の分:74 KiB です。
  中継のコピーのバッファと endpoint の分で、導出の 586 KiB から、バッファが数える floor の 512 KiB を引いた値です
- 送信の側:固定版の gVisor は、書き込みのたびに中身を 2 のべき乗の大きさ(64 byte から 64 KiB)の chunk に写します。
  chunk のメモリは、中身の約 2 倍と、書き込み 1 回あたり 64 byte の和までです。
  ほかに書き込み 1 回ごとに約 0.7 KiB の管理の構造(segment、PacketBuffer、view)を持ちます(測定から丸めた)。
  書き込みの数は、[書き込みの数の上限](tcp-buffers.md#書き込みの数の上限)が送信のバッファ 1 KiB あたり 1 回に抑えます。
  このため floor の接続の送信の側は、2 × 256 KiB + 64 byte × 256 + 0.7 KiB × 256 で約 707 KiB までです。
  boost の接続では、2 × 4 MiB + 64 byte × 4096 + 0.7 KiB × 4096 で約 11.05 MiB までです。
  大きさの違う書き込みを混ぜると、この値に近づきます。
  たとえば 1 byte の書き込み約 230 回と 16,385 byte の書き込み約 24 回は、書き込みの数と byte の上限の内側で約 705 KiB になります。
  1 回の書き込みは中継のバッファの 32 KiB までです。
  1 種類の大きさの書き込みで測った最大は、1,025 byte の書き込みで相手が何も確認しない場合の floor の 688 KiB と boost の 10.8 MiB でした(測定)。
  1,025 byte の中身は 2,048 byte の chunk に入ります
- 送って確認を待つ segment:gVisor は送るときに中身を MSS で分け、分けた segment ごとに書き込みと同じ管理の構造を持ちます。
  1 segment の中身は、入口の [TCP の MSS の下限](packet-validation.md#tcp-の-mss-の下限)により 472 byte 以上です。
  floor の接続では 256 KiB / 472 byte × 0.7 KiB で約 389 KiB、boost の接続では 4 MiB / 472 byte × 0.7 KiB で約 6.07 MiB です。
  1 segment の 0.7 KiB は書き込みの測定から導いた値で、送った後に分けた状態は測っていません。
  書き込みの数と送った byte はどちらも送信のキューの上限の内側にあるので、送信の側との和は上界です
- 受信の側:受信の packet も 2 のべき乗の chunk に写すので、生きているヒープは受信のメモリの会計より大きくなります。
  比は 1,025 byte の packet で最大の約 1.67 倍、MTU 1420 で約 1.36 倍でした(測定)。
  floor の受信を測った最大は 549 byte の packet の約 385 KiB でしたが、比の最大を受信のバッファに掛けた 256 KiB × 1.67 ≈ 428 KiB を使います。
  boost の接続では 4 MiB × 1.67 ≈ 6.68 MiB です

floor の接続は 74 + 707 + 389 + 428 で約 1,598 KiB、boost の接続は 74 KiB + 11.05 + 6.07 + 6.68 MiB で約 23.9 MiB です。
表の boost の項は、16 本が floor の分に代えて boost の分を持つ場合の 16 × (23.9 MiB - 1,598 KiB) です。
各側の最悪は別々の導出と測定の値であり、同時に起こして測ってはいません。
保守側に寄せて和を使います。
閉じた後の接続の表の行は、この送信と受信の分を持ちません。
中継の接続は末尾を届け終えた後に表に入るので、送信のキューが空です。
疎通確認のように K に数えない接続は、今の呼び出し元がデータを書かないので、送信のキューを持ちません。

エージェント用 API の認証前の接続は、プロセスあたり 1024 本(コードの定数で、設定項目ではない)までで、送信元の段ごとの上限もある([11 節](../security/admin-transport.md#11-セキュリティ))。
同時接続数の上限 4096 本の残りは認証を通った stream で、エージェントごとに、確立した 1 本と、確立の前か置き換えられて閉じる途中の 2 本までである([11 節](../security/admin-transport.md#11-セキュリティ))。
置き換えられて閉じる途中の stream は、それを置き換えた stream の確立の前の枠を、閉じ終わるまで占める([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
確立した 1 本は、1 MiB の上限に近いハートビートを読んでいる途中で約 1.3 MiB を持ち、確立の前の 1 本は、64 KiB のヘッダと 4 KiB の上限に近い最初のメッセージで約 124 KiB を持ちます。
どちらもホストで TLS の接続を張って測った値で、同じプロセスのクライアントの側の分を含む。
置き換えられて閉じる途中の 1 本は、ハートビートを読んでいる途中の確立した 1 本と同じ状態にあるので、同じ約 1.3 MiB と数えます。
表の 3.9 MiB × A は、3 本がどれも測った形のハートビートを読んでいる途中の場合の値です。
ハートビートのルールの状態の項目の数にはコードの上限が無く、`vpsd` は 1 MiB の読み取りの上限の内側の項目を、文字列を切り詰めたうえですべて保存します。
小さい項目を多数並べた形では、保存する量だけで測った値を大きく超えうる。
その量はソースの構造から 1 エージェントあたり約 17 MiB と推定しており、測っていません。
この形のハートビートを送れるのは、そのエージェントの恒久トークンの持ち主だけです。
