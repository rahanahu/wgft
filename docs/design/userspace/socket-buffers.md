# WireGuard のソケットの動作条件

ユーザー空間モードは、実際の WireGuard ソケットが要求された受信と送信のバッファを得ることを動作条件とします。
wgft はホストの sysctl を自動では変更しません。


<a id="動作条件"></a>
- 動作条件:エージェントのプロセスは特権も `NET_ADMIN` も要らず、Docker のコンテナ 1 つでも動く。
  ただし、ホストが次の項のソケットのバッファの条件を満たすことを要します。
  コンテナで動かす場合、条件を満たすのはコンテナのホストの設定である(後述の[「コンテナでのバッファの条件」](socket-buffers.md#コンテナでのバッファの条件)の項)
<a id="ソケットのバッファの条件"></a>
- ソケットのバッファの条件:ユーザー空間モードは、WireGuard の UDP ソケットが、wireguard-go の要求する受信と送信のバッファを実際に得ることを動作条件とします。
  推奨ではなく条件です。
  後述の[「netstack の出力」](udp-accounting.md#netstack-の出力)の構造は、この条件を満たす環境での評価に基づいて採用しており([以前の検証 2026-09-27](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L667))、満たさない環境での過負荷の見え方は未確認であるためです。
  その後、満たさない環境では、WireGuard のソケットの受信の溢れが TCP の転送を[短い障害の後と同じ遅い回復](../vps/userspace.md#63-ユーザー空間モード)に入れることを、ラボで観測しました(2026-10)。
  条件は `vpsd` のユーザー空間モード([6.3 節](../vps/userspace.md#63-ユーザー空間モード))にも同じく当てはまる
<a id="linux-でのバッファの条件"></a>
- Linux でのバッファの条件:wireguard-go は、UDP ソケットを開くときに受信と送信のバッファをそれぞれ 7 MiB 要求します。
  カーネルはこの要求を `net.core.rmem_max` と `net.core.wmem_max` の値で切り詰める。
  wireguard-go は続けて `SO_RCVBUFFORCE` と `SO_SNDBUFFORCE` でも同じ値を要求し、どちらの誤りも無視します。
  この要求は、初期の user namespace で `CAP_NET_ADMIN` を持つプロセスでは上限を超えて通り、持たないプロセスでは失敗してバッファは上限の値に留まる。
  コンテナや LXC ベースの VPS の中で与えた `CAP_NET_ADMIN` は、そのコンテナの user namespace の中に限られるので、この要求を通さない([6.1 節](../vps/kernel.md#61-カーネルモード))。
  wireguard-go はそのことを報告しません。
  Linux はソケットのバッファの大きさを要求の 2 倍に設定し、`getsockopt` もその 2 倍の値を返します。
  この大きさはソケットに溜められる量の上限であり、ソケットは開いた時点でその量のメモリを使うのではありません。
  ラボでは、14680064 を得たソケットが、何も溜めていない間は `ss -m` で 0 バイトを使っていました。
  溜まったときに使うのはカーネルのメモリであり、ソフト上限の式の外の項である(後述の[「プロセス全体のメモリの上界」](memory-server.md#プロセス全体のメモリの上界)の段落)。
  Linux での条件は、実際の WireGuard のソケットの実効の受信と送信のバッファが、どちらも 14680064 バイト以上であることとする(2026-09-27、所有者の決定)。
  7 MiB の要求が通ったソケットの実効の値がこれに当たる。
  判定に sysctl の値を使わないのは、初期の user namespace で `CAP_NET_ADMIN` を持つプロセスが sysctl の値より大きいバッファを得られるためです。
  その権限を持たないプロセスがこの値を得るには、`net.core.rmem_max` と `net.core.wmem_max` がどちらも 7340032 以上である必要があります。
  エージェントは capability を持たずに動くので、エージェントのホストではこの sysctl の値が得られるバッファを決める。
  wgft はこの sysctl を書き換えない。
  書き換えはホスト全体の設定の変更であり、wgft が管理する範囲の外にあるためです
<a id="バッファを測る時点"></a>
- バッファを測る時点:エージェントとユーザー空間モードの `vpsd` は、トンネルを立てるたびに自分の WireGuard のソケットを測る(2026-09-27、所有者の決定)。
  ソケットのバッファは開いたときに決まり、後から sysctl を変えても変わりません。
  一方で、エージェントは同じプロセスの中で、起動、`rotate-key`、トンネルの作り直し、wg 設定の変更のたびに新しいソケットを開きます。
  起動のときだけ測ると、後から開いたソケットの値を見落とす。
  `rotate-key` で開き直したソケットが、その時点の sysctl の値で新しいバッファを得ることは、ラボで確かめた。
  作り直しと wg 設定の変更の経路は、トンネルを立てる同じ関数を通ることをコードで確かめたが、その経路で開き直すことはラボで観測していません
<a id="バッファの測り方"></a>
- バッファの測り方:トンネルを立てたプロセスは、自分のファイル記述子のうち、wireguard-go の `IpcGet` が返す listen port に bind した UDP ソケットを探し、`getsockopt` で `SO_RCVBUF` と `SO_SNDBUF` を読みます。
  IPv4 と IPv6 のソケットのうち小さい方の値を使います。
  wireguard-go の UDP バインドは置き換えず、ソケットの値も変えません。
  この読み取りは権限を要りません。
  付属の systemd の unit と同じ設定の砂箱の中と、付属の compose ファイルのコンテナの中でも読めることを確かめた。
  測る手段を持つのは Linux だけです
<a id="条件に届かないときの知らせ方"></a>
- 条件に届かないときの知らせ方:エージェントと `vpsd` は、測った値が条件に届かない場合と測れなかった場合に、英語の警告の行をログに出す。
  行は丸括弧を使わず、測った値、条件の値、2 つの sysctl に書く値を含む。
  警告は 1 分に 1 回までに絞り、トンネルを続けて作り直しても行が並ばないようにします。
  wire protocol には載せず、`wgft status` を degraded にもしません。
  起動は拒まない。
  拒むと、既定の値が条件に届かないディストリビューションで、更新しただけの配置が止まるためです。
  エージェントの測った値は、`agent doctor` の `tunnel.socket_buffers` が示す([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))
<a id="server-check-が示す材料"></a>
- `server check` が示す材料:`server check` は、`vpsd` のソケットを測れない。
  これから起動する `vpsd` の権限も知らない。
  付属の systemd の unit は `CAP_NET_ADMIN` を与えるが、その権限で上限を超えられるのは VM や専用のホストの上だけです。
  LXC ベースの VPS やコンテナの中では超えられず、独自の配置では権限を与えないこともあります。
  そのため `server check` は判定をせず、人が判断する材料として 3 つの値を示します。
  今の `net.core.rmem_max` と `net.core.wmem_max`、`CAP_NET_ADMIN` を持たないプロセスが得る値、条件の値です。
  2 つ目の値は、`SO_RCVBUF` と `SO_SNDBUF` だけで 7 MiB を要求する試しのソケットで得ます。
  FORCE を使わないので、root で実行しても権限を持たないプロセスの値になります。
  wireguard-go と同じ手順の試しのソケットは使いません。
  `server check` は root で実行することが多く、root ではその手順の FORCE が通って、必ず条件を満たして見えるためです。
  付属の unit を理由に示す材料を省くこともしません。
  決め手は、稼働中の `vpsd` が自分のソケットを測った値とその警告の行です。
  管理用 API、`server doctor` の JSON、Web UI には何も加えない。
  終了コードは他の所見と同じく 0 のままである([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))
<a id="コンテナでのバッファの条件"></a>
- コンテナでのバッファの条件:コンテナの中のプロセスは、この 2 つの sysctl を変えられない。
  値はホスト全体で 1 つであり、初期の network namespace の側でだけ変えられる([6.1 節](../vps/kernel.md#61-カーネルモード))。
  コンテナで動かすエージェントと `vpsd` では、コンテナのホストがこの sysctl を設定し、条件を満たしたかどうかは、コンテナの中の実際の WireGuard のソケットの実効の値、たとえば `agent doctor` で確かめる(2026-09-27、所有者の決定)。
  付属の compose ファイルは、uid 65532 と `cap_drop: [ALL]` の非特権のまま保つ。
  `CAP_NET_ADMIN` をコンテナに加えることと root で動かすことは、この条件の解決策にしません。
  確かめた範囲は次のとおりです。
  ラボの Debian 12 の VM(カーネル 6.1)では、Docker 20.10 で付属の `agent.compose.yaml` を動かした。
  イメージは、配布物と同じ最終段でラボのバイナリから作った。
  エージェントは、ホストの既定の値のまま `agent doctor` でこの条件の未達を示し、ホストで両方の sysctl を 7340032 にしてコンテナを再起動すると条件を満たした。
  同じ作り方のイメージで付属の `server.compose.yaml` を動かした `vpsd` も、既定の値では警告を出し、ホストの値を上げて再起動すると出さなかった。
  同じ VM で、Docker の `--sysctl` による設定は失敗した。
  実装の前には、wireguard-go と同じ手順で UDP ソケットを開いて値を読む使い捨てのプログラムで、次を確かめた。
  同じ Debian 12 の VM の rootful の podman 4.3 でも、ホストの値を上げるとコンテナの中のソケットが条件を満たした。
  Fedora 44 のホスト(カーネル 7.2)の Docker 29 では、`--sysctl` と特権のコンテナの中からの書き込みがどちらも拒まれ、付属の compose ファイルと同じ権限のコンテナはホストの値の 2 倍を得た。
  user namespace を分けた `unshare` と rootless の podman では、`CAP_NET_ADMIN` を持たせても FORCE が拒まれた。
  非特権の Incus のコンテナ(Incus の既定のままで、security の設定も nesting も無い)では、付属の `agent.service` で capability を持たずに動くエージェントが、既定の値では条件の未達を示し、コンテナのホストで両方の sysctl を 7340032 にしてエージェントを再起動すると条件を満たした([以前の検証 2026-09-27](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L667))。
  Proxmox VE のコンテナ、nesting を有効にしたコンテナ、rootless のコンテナ、非特権の LXC や Incus のコンテナの中のユーザー空間モードの `vpsd` は対象から外さないが、条件を満たせるかどうかは未確認です
<a id="linux-以外でのバッファの条件"></a>
- Linux 以外でのバッファの条件:Windows と macOS の wireguard-go も 7 MiB を要求するが、FORCE を使いません。
  得られる値を決める仕組み、その値での過負荷の見え方、2 倍の値を報告するかどうかは未確認です。
  この 2 つの OS には、Linux の仕組み(sysctl、FORCE、capability、要求の 2 倍の報告)を当てはめない。
  wgft はこの 2 つの OS でソケットを測らず、試しのソケットによる予測も条件の判定に使いません。
  `agent doctor` の `tunnel.socket_buffers` は NOT TESTED を示します
