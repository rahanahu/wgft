# トンネルの回復と作り直し

エージェントは、名前の再解決だけでは戻らないトンネルの故障に備えて、条件を満たした場合にトンネルを作り直します。
作り直しはルールのセッションを切る操作です。


<a id="netstack-の-tcp-の短い障害の後の回復"></a>
- netstack の TCP の短い障害の後の回復:エージェントの netstack の TCP も、送る向きでは経路の短い障害の後の回復がカーネルの TCP より遅い。
  ユーザー空間モードはこれを既知の制限とする([6.3 節](../vps/userspace.md#63-ユーザー空間モード)の性質の違いの項)
<a id="1-回の読み取りの件数"></a>
- 1 回の読み取りの件数:`Read` は 1 回に 1 件だけを返し(`BatchSize` は 1)、複数の件をまとめて返さない。
  wireguard-go の送信のキューは、パケットではなく 1 回の `Read` の結果を入れる入れ物を数えます。
  k 件ずつ返すと、後述の滞留のメモリの上限が k 倍になるためです
<a id="wireguard-の受信の-1-回の件数"></a>
- WireGuard の受信の 1 回の件数:wireguard-go に渡す UDP のバインドは、1 回の受信で 1 件だけを渡す包み(`internal/dataplane/userspace/wgbind`)である(`BatchSize` は 1)。
  wireguard-go の受信のキューは、送信のキューと同じく、パケットではなく 1 回の受信の結果を入れる入れ物を数え、1 件ごとに `MaxMessageSize` のバッファを持ちます。
  Linux の標準のバインドは 1 回に 128 件まで読むので、そのままでは後述の受信の向きの滞留の上限が 128 倍になります。
  包みは標準のバインドを内側に持ち、内側の 1 回の件数と同じ数のバッファで内側を読み、wireguard-go の呼び出しごとに 1 件ずつ写して渡す。
  読み取りの syscall の数は変わらず、内側の 1 回の読み取り(`recvmmsg`、GRO)と sticky socket の送信元の固定はそのまま使います。
  内側のバインドの 1 回の件数が既に 1 の Windows と macOS では包まない。
  内側の誤りは同じ値のまま返します。
  wireguard-go は `net.Error` への直接の型の判定で一時的な誤りかどうかを見るので、包んだ誤りは非一時的なものでも一時的と読まれるためです。
  閉じた後の受信は、手持ちの datagram を捨てて `net.ErrClosed` を返します。
  送信は内側にそのまま渡す。
  包みは wireguard-go の Linux の経路の監視を止めます。
  監視は、バインドの型が標準のバインドそのものであるときだけ始まり、経路の変化のたびに、ピアの宛先への経路の出口のインタフェースが sticky の送信元のものと違えば次の送信で送信元を消す。
  監視が経路の変化の直後に直せるのは、古い送信元アドレスがホストに残ったまま出口のインタフェースが変わる場面だけです。
  アドレスごと消える場面では、監視があってもタイマーで回復する(コードを読んだ判断で、未確認)。
  `vpsd` のようにピアが複数あるときは、監視のピアの走査が送信元を記録していないピアで止まる作りのため、監視は元から確実ではありません。
  送信元を消す経路は wireguard-go のタイマーにも残っています。
  データを送って応答が無いときと、ハンドシェイクの再送のたびです。
  エージェントは keepalive ごとにトンネル内へ ping を送るので、Linux のエージェントで古い送信元アドレスが残ったまま出口だけ変わる場合の回復は、通信があれば最大 15 秒程度、無ければ ping の間隔を含めて最大 40 秒程度になりうる。
  これは既知の trade-off であり、送信の失敗時の送り直しや送信元の解除は持ちません。
  据え置きのエージェントと VPS が主な用途で、送信側まで変えると 1 回の件数の変更の評価と原因の分離が難しくなるためである(2026-09-27、所有者の決定)。
  実機や通常の利用でこの回復の時間が問題として確認されたら、送信側の補いを別に検討します。
  `vpsd` はピアの endpoint を設定に持たず、相手から認証されたパケットが届くたびに endpoint を sticky の送信元ごと置き換える。
  したがって `vpsd` では、経路の監視を失う影響は事実上ありません
- wireguard-go の UDP バインドは、Windows では `conn.NewDefaultBind()` ではなく `conn.NewStdNetBind()` を明示して使います。
  既定の `NewDefaultBind()` は Windows では Registered I/O を使う `WinRingBind` を返すが、`WinRingBind` は `SIO_UDP_CONNRESET` を無効にしません。
  このため、到達できない宛先へ送った UDP に対して Windows 自身のスタックが生成する ICMP port unreachable では、Windows の非同期受信が WSAECONNRESET として報告し、`device.RoutineReceiveIncoming` がこれを回復不能な誤りと判定して受信ループを止め、そのトンネルは以後受信できなくなる(改訂の記録 2026-09-21)。
  `conn.NewStdNetBind()` は Go の `net` パッケージ経由でソケットを開き、同じ状況でも受信を続けます。
  この選択は Windows でのバッチサイズを変えません。
  依存するこの版の `golang.zx2c4.com/wireguard` では、`WinRingBind.BatchSize()` も `StdNetBind.BatchSize()` も Windows で 1 を返し、差が無いためです。
  残る差は、自前のリングバッファと Go の netpoller 経由の UDP ソケットとの間の、パケットごとの syscall や I/O 完了通知のオーバーヘッドであり、その大きさは未測定です。
  受信が止まらないことを優先します。
  前述の[「WireGuard の受信の 1 回の件数」](tunnel-recovery.md#wireguard-の受信の-1-回の件数)の包みは、内側の 1 回の件数が 1 なので Windows では使われない。
  この WSAECONNRESET は Windows 自身のスタックが答える ICMP で再現できる一方、実サーバーの到達不能な UDP ポートへインターネット越しに送る計測では現れなかった(改訂の記録 2026-09-21)。
  ICMP がその経路のどこで失われているかと、他の経路でなら届きうるかは未確認です
<a id="トンネルの作り直し"></a>
- トンネルの作り直し:エージェントは、WireGuard のハンドシェイクが 300 秒新しくならない状態が続いたら、`device.Device` と netstack ごとトンネルを作り直す。
  回復は 2 段です。
  第 1 段は [4 節](../network.md#4-ネットワーク)の軽い回復で、ハンドシェイクが keepalive の 5 倍(既定で 125 秒)の間成立しなければ、エンドポイントの名前を引き直し、トンネル内へ ping を 1 つ送る。
  第 2 段が作り直しであり、第 1 段を繰り返しても戻らない故障に備える。
  対象の故障は、wireguard-go の受信の goroutine が終わったまま戻らない状態です。
  `device.RoutineReceiveIncoming` は `net.ErrClosed` 以外の非一時的な誤りを受けると戻り、起こし直す経路がありません。
  この状態のトンネルは送信を続けるが二度と受信しないので、ハンドシェイクは永久に成立せず、第 1 段のどちらの操作でも戻りません。
  エージェントは受信の停止そのものを観測できないため、判定にはハンドシェイクの成立だけを使います。
  転送量をハートビートに載せる必要は無い([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
  この点検が 30 秒ごとに読む最終ハンドシェイクの値は、stream の再接続の待ちを打ち切る判定にも使う([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))
<a id="作り直しを決める位置"></a>
- 作り直しを決める位置:判定と作り直しはエージェントの本体(`internal/agent`)が行います。
  作り直しにはリスナーの開き直しと最後に受け取った全体状態が要り、トンネルの package はどちらも持たないためです。
  手順は、wg 設定が変わったときの張り直しと同じものを使います
<a id="作り直しの閾値"></a>
- 作り直しの閾値:300 秒とします。
  WireGuard の時定数から決めた値です。
  エージェントは送信の側なので、鍵を作ってから 120 秒(`RekeyAfterTime`)を過ぎた最初の送信で新しいハンドシェイクを始め、keepalive が 25 秒ごとに送信を起こすので、健全なトンネルの最終ハンドシェイクは 145 秒以内に必ず新しい値になります。
  180 秒(`RejectAfterTime`)を過ぎた鍵は送信にも使えないので、300 秒の時点のトンネルは既に 120 秒以上まったく通信していません。
  ハンドシェイクの再送の打ち切り(`RekeyAttemptTime`、90 秒)も済んでいる。
  閾値を keepalive の倍数にしないのは、この 3 つの時定数が keepalive の値によらず一定だからです
<a id="経過時間の測り方"></a>
- 経過時間の測り方:エージェントは、`IpcGet` が返す最終ハンドシェイクの値そのものと、その値を最初に観測した時刻を覚え、観測してからの経過時間で判定します。
  最終ハンドシェイクは壁時計の秒であり、NTP の補正や手動の変更で飛ぶ。
  値と現在時刻の差で測ると、155 秒以上前への飛びが健全なトンネルを 300 秒古く見せ、中継中のフローを 1 度無駄に切ってしまう。
  観測してからの経過時間は Go の単調な時計で測るので、壁時計がどちらへ飛んでも作り直しは起きず、抑えられもしません。
  健全なトンネルの値は 145 秒以内に必ず新しくなるので、観測の時刻もその周期で進む。
  値が新しくなり、かつゼロでなければ、作り直しの間隔も初期値に戻します。
  判定の起点には、値を観測した時刻とトンネルを立てた時刻の遅い方を使います。
  作り直した直後の device はハンドシェイクがゼロで、前の値もゼロだったときは値が変わらず、観測の時刻が更新されないためです。
  ハンドシェイクが一度も成立していないトンネルの起点はトンネルを立てた時刻になり、起動の直後に受信が止まる場合も作り直しの対象に入ります
<a id="サスペンドの扱い"></a>
- サスペンドの扱い:`time.Now` が持つ単調な読みの出どころは GOOS ごとに違う。
  Go 1.27.1 の runtime では、Linux が `CLOCK_MONOTONIC`(`runtime/sys_linux_amd64.s`)、macOS が `mach_absolute_time`(`runtime/sys_darwin_amd64.s`)、Windows が `KUSER_SHARED_DATA` の `InterruptTime`(`runtime/time_windows.h`、`runtime/sys_windows_amd64.s`)です。
  Linux の `CLOCK_MONOTONIC` と macOS の `mach_absolute_time` はサスペンド中に進まないので、復帰した後のエージェントは、第 1 段の回復に 300 秒の起きている時間を与えてから作り直す。
  Windows の `InterruptTime` は unbiased ではない方であり、スリープとハイバネートの時間を含むので、300 秒を超えるスリープからの復帰では最初の判定で 1 回作り直す。
  どちらの場合も、300 秒を超える中断の後のセッションは `RejectAfterTime` を過ぎて既に使えず、作り直しで切れるのは死んだフローだけです。
  Go の runtime がどの時計を読むかはこの版の原典で確かめた。
  macOS の `mach_absolute_time` がサスペンド中に進まないことは、実機の Mac で時計そのものを測って確かめた(改訂の記録 2026-09-21、issue #124)。
  Windows の `InterruptTime` がスリープの時間を含むことは、Windows 11 の実機でエージェントの挙動から確かめた。
  約 11 分 32 秒のスリープから復帰したエージェントは、新しいハンドシェイクの無い期間をスリープを含めて 11 分 36 秒と数え、復帰の直後にトンネルを 1 回作り直した。
  時計そのものを測るプログラムは使っていない(改訂の記録 2026-09-27、issue #280)。
  ハイバネートの時間を含むことは OS の文書に拠るもので、実機では未確認です。
  Linux の `CLOCK_MONOTONIC` がサスペンド中に進むかどうかは OS の文書に拠るものであり、実機では未確認です
<a id="作り直しの間隔"></a>
- 作り直しの間隔:サーバが停止しているだけの場合も、エージェントから見た症状は受信の停止と同じであり、区別できません。
  そこで作り直しの間隔をバックオフで広げる。
  1 回目は 300 秒で、以後は 600 秒、900 秒と倍にし、900 秒を上限とします。
  ゼロでない新しいハンドシェイクを観測したら間隔を 300 秒に戻します。
  サーバが長く停止した後に戻った場合、トンネルが健全なら作り直しを待たずにハンドシェイクで復旧し、受信が死んでいる場合は最長 900 秒で作り直す
<a id="作成に失敗したときの再試行"></a>
- 作成に失敗したときの再試行:トンネルを立てる手順は古いトンネルを閉じてから新しいものを作るので、作成そのものが失敗するとトンネルが 1 つも無い状態で残る。
  エージェントは、その状態を予定の時刻に試し直す。
  1 回目は次の 30 秒の判定で試し、続けて失敗するほど 300 秒、600 秒、900 秒と間隔を広げ、900 秒を上限とします。
  トンネルが無い間は転送が全部止まっているので、1 回目だけは間隔を置かない。
  対象は、ハンドシェイクが新しくならないことによる作り直しの作成が失敗した場合と、全体状態の適用の中で作成が失敗した場合の 2 つです。
  `rotate-key` と停止で閉じたトンネルも、最初の全体状態を受け取る前のトンネルの無い状態も対象にしません。
<a id="試し直さない失敗"></a>
- 試し直さない失敗:wg 設定そのものが誤っている全体状態は対象にしません。
  サーバの公開鍵やアドレスが解釈できない場合、同じ全体状態では何度作っても同じ結果になるためです。
  エージェントはトンネルを立てないまま次の全体状態を待ち、ハートビートでは試し直しを待っていない理由を送る。
<a id="試し直しが使う全体状態"></a>
- 試し直しが使う全体状態:エージェントは、作成に失敗したときの全体状態をメモリの上に控え、試し直しはその全体状態から立てる。
  認証情報ファイルの `last_state` は適用を終えた全体状態しか指さず、新しい全体状態の適用が作成で失敗した場合は 1 つ前の全体状態を指したままです。
  そちらから立てると、サーバが想定していない wg 設定とルールのトンネルになります。
  控えは保存せず、再起動の後は保存済みの `last_state` で立て、stream が今の全体状態を配り直す。
  試し直しが成功したら、その全体状態の適用を最後まで進め、処理済み世代と `last_state` もその時点で進めます。
  適用が終わるまで世代を進めないので、ハートビートの世代は実際に適用した内容と食い違わない。
<a id="rotate-key-との関係"></a>
- `rotate-key` との関係:`rotate-key` は古いトンネルを閉じてから新しい鍵で全体状態を適用し直す。
  閉じた時点で試し直しの控えは消えるので、閉じてから適用し直すまでの競合可能期間に watchdog がトンネルを立てることはありません。
  その適用の作成が失敗した場合は、失敗そのものが控えを付け直すので、試し直しは新しい鍵で立てる。
<a id="作り直しの費用"></a>
- 作り直しの費用:鍵、アドレス、`AllowedIPs`、エンドポイントは同じ値で立て直すので、VPS 側のピアの設定は変えなくてよい。
  認証情報ファイルも書き換えない。
  リスナーは閉じて開き直すので、中継中の TCP 接続と UDP のセッションは切れる。
  切れるのは、閾値の時点で既に 120 秒以上パケットの通っていないフローだけです。
  制御プレーンは wg を通らない([5 節](../control/README.md#5-制御プレーン))ので、作り直しの間も stream の接続と全体状態の受信は続く。
  古いトンネルは新しいものを作る前に閉じます。
  ただし、閉じたトンネルは、それを使っていた処理がすべて戻るまで参照が残り、GC されない。
  このため古い世代と新しい世代は、古い世代の処理が終わるまで重なりうる。
  閉じたトンネルが残す量は、後述の[「プロセス全体のメモリの上界」](memory-server.md#プロセス全体のメモリの上界)の段落で扱う
<a id="作り直しの見せ方"></a>
- 作り直しの見せ方:1 回の作り直しにつき、理由と次の間隔を含む英語のログを 1 行出す。
  作成に失敗したときは、理由と、次に試すまでの時間か試し直さない旨を 1 行出し、試し直すときにも 1 行出す。
  判定は 30 秒ごとに行うが、ログは作り直しと作成のときだけ出す。
  ハートビートのトンネルの状態は、作り直した直後はハンドシェイク待ちなので、既存の `error` と `handshake not established` になります。
  作成に失敗してトンネルが無い間は `error` を送り、理由で 4 つの場合を区別します。
  試し直しを待っている場合、試し直さない失敗で終わった場合、全体状態をまだ受け取っていない場合、`rotate-key` や停止で閉じた直後の場合です。
  試し直しを待っている理由の文言は作り直しと適用で共通にします。
  運用者から見てどちらも「作成に失敗して試し直す」であり、区別する意味が無いためです。
  理由は人が読む文言であり、新しい状態も新しい項目も加えない([7a.6 節](../architecture/wire-compatibility.md#7a6-維持する外部仕様と互換性))
