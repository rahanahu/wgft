# 7.2 で変わった Linux の受け手

この文書は、wgstack の受信の経路が手本にした Linux の受け手の挙動が、6.1 から 7.2 でどう変わったかを、実装する人が Linux のコードを読まずに分かる形で定めます。
手本にした 6.1 の挙動は[溢れた後の Linux の受け手](wgstack-performance.md#溢れた後の-linux-の受け手)にあります。
参照の Linux は 2026-11-01 にラボの Debian の 7.2 に移りました([参照の Linux の設定](wgstack-verification.md#参照の-linux-の設定))。
各変化に、wgstack が採るかの推奨を付けます。
推奨は案で、採るかどうかは後で決めます。
関数の名前は、Linux の挙動を確かめる人のための目印です。

## 参照のカーネル

6.1 はラボの Debian 12 の `6.1.0-53-amd64`(package の版 6.1.187-1)です。
この版は `v6.1` のタグの後の受け手の修正のうち、受け手の RTT の推定の最小の取り方と、受動の open の自動調整の最初の値の修正を含みます。
この 2 つは VM の `changelog.gz` で確かめました。
後に挙げる 7.2 の変化は、どれも 6.1.0-53 の changelog にありません。

7.2 はラボの Debian 13 の `7.2.11+deb13-amd64`(package の版 7.2.11-1~bpo13+1)です。
変化は `v7.2` のタグのソースから読み、最初の版を mainline のタグで示します。
Debian の 7.2.11 の stable の修正に、この文書の受け手の挙動を変えるものは見当たりませんでした(VM の `changelog.Debian.gz` の 7.2 の節で確かめました)。
ラボで観測した値は、[wgstack の検証](wgstack-verification.md)の受信の台本の結果です。

## 変化の一覧

| 変化 | 6.1 | 7.2 | 最初の版 | wgstack への推奨 |
|---|---|---|---|---|
| メモリを窓に換算する比 | 半分 | segment の中身と確保の大きさの比 | v6.6 | 採らない |
| 握手の後の最初の窓 | 64 KB で抑える | 抑えない | v6.10 | 今のまま |
| 自動調整の目標 | 読んだ量の 2 倍に 16 MSS を足す | 未読を除いた読んだ量の 2 倍で、16 MSS の余裕は無し | v6.16、v6.18 | 未読を除くことを採る候補 |
| 自動調整の順序外の項 | 無し | 順序外のデータの幅を足し、順序外の segment でも調整する | v6.16 | 採る候補 |
| RTT の短い経路の抑え | 無し | 受け手の RTT が 1 ms より短ければ伸びを抑える | v6.19 | 採らない |
| 受け手の RTT の標本 | 0 の差を 1 ms と数え、大きな標本を常に平滑する | 0 の差を捨て、未読がある間は大きな標本を捨てる | v6.16 | 未読の間の標本を捨てることを採る候補 |
| SACK の圧縮の時間 | RTT の 5%、猶予 100 µs | RTT の約 41%、猶予 10 µs、どちらも 1 ms まで | v6.19 | 採らない(今のまま) |

| 最大の右端の追跡 | 無し | 広告した最大の右端までの segment を受け入れる | v7.1 | 今のまま |

## メモリを窓に換算する比

6.1 は受信のメモリの半分を窓に換算しました(`tcp_adv_win_scale=1`)。
7.2 はソケットごとの比を持ちます(`scaling_ratio`)。

- 最初の値は半分です
- 推定した MSS 以上の大きさの segment を受け、その大きさが今の推定と違う時に、中身の長さを確保の大きさ(truesize)で割った比に置き換えます(`tcp_measure_rcv_mss`)
- 比が変わると、窓の上限を rcvbuf のその比の量に置き直し、自動調整の前の区間の値を窓の上限以下に抑えます(v6.14)
- v7.2 から、比の変化は rcv_ssthresh を縮めません。
  v6.14 から v7.2 の前までは、比が下がるたびに rcv_ssthresh も縮み、中身の大きさが揺れる流れで窓が低く留まりました
- `SO_RCVBUF` を設定すると、その時に窓の上限を新しい rcvbuf の比の量に置き直します(v7.1)
- `tcp_adv_win_scale` の sysctl は残りますが、窓の計算に使いません

理由は、NIC の driver が受けた frame ごとに page を確保するようになり、確保の大きさと中身の比が MTU と driver で大きく変わるためです。
半分の換算は、比の小さい環境で大きすぎる窓を広告してまとめ直し(collapse)の重い処理を招き、比の大きい環境では窓を小さくしすぎました。

ラボの観測では、固定の値(待ち受けの `SO_RCVBUF` が 256 KiB、rcvbuf が 512 KiB)の最大の窓が、6.1 の 203,512 byte から 7.2 の 295,448 byte に増えました。
性能の族の最初の窓の上限も、64 KB 前後から約 73 KB から 77 KB に増えました。

推奨:採りません。
wgstack の受信の輪は segment の中身だけを持ち、予算と窓を中身の byte で数えるので、確保の大きさとの比がありません。
窓の上限を Linux の rcvbuf の窓の換算と同じ量として扱う今の扱い([受信の窓と boost の方針](wgstack-performance.md#受信の窓と-boost-の方針))のままで、比が 1 の Linux と同じになります。
適合の台本は窓の大きさではなく関係を確かめるので、この差は台本に影響しません。

## 握手の後の最初の窓

6.1 は受信の窓の最初の値を 65535 で抑え、窓は握手の後に rcv_ssthresh の歩みで開きました。
7.2 はこの上限を外しました(v6.10)。
SYN と SYN-ACK の窓の欄は scale を掛けない値なので、65535 を超えません(RFC 7323 2.2)。
握手の後の最初の ACK から、最初の窓の全体を広告します。

理由は、長い RTT の経路で最初の往復の窓が 64 KB に留まり、短い転送が遅くなるためです。

ラボの観測では、待ち受けの `SO_RCVBUF` が 256 KiB の接続で最初のデータへの ACK が広告する窓は、6.1 の 65,536 byte から 7.2 の 261,192 byte になりました(`early-ack` の `first-data.window`)。
wgstack は最初の ACK から floor の 256 KiB を広告します(262,016 byte)。

推奨:今のままにします。
7.2 は wgstack の選んだ形に近づきました。

## 自動調整の目標

6.1 の自動調整は、受け手の RTT の 1 回の間にアプリケーションが読んだ量(copied)から、2 × copied + 16 MSS を基本の窓とし、増え方の比で 2 倍を足して目標にしました。
目標を MSS の数に直し、MTU の segment の確保の大きさを掛けて rcvbuf にしました。
wgstack の窓の上限は、この 6.1 の式に従います([受信の窓と boost の方針](wgstack-performance.md#受信の窓と-boost-の方針))。

7.2 の自動調整(`tcp_rcv_space_adjust`、`tcp_rcvbuf_grow`)は次のとおりです。

- 読んだ量:区間の間に読んだ byte から、測る時点で受信の待ち行列に残る未読の byte を引きます(v6.16)。
  アプリケーションが読み切れずに待ち行列が伸びる間は、読んだ量が小さく出ます
- 基本の窓:読んだ量の 2 倍です。
  6.1 の 16 MSS の余裕は v6.16 で外れ、v6.18 でも戻っていません
- 伸び:前の区間からの増え方の比を基本の窓に掛け、その 2 倍を足します。
  6.1 と同じ形で、v6.16 で外れ、v6.18 で戻りました。
  v6.16 から v6.18 の前までは目標が読んだ量の 2 倍だけで、送り手が往復ごとに窓を倍にできませんでした
- rcvbuf:目標を前節の比で確保の大きさに直し、`tcp_rmem` の上限で抑えます。
  上げる時だけ上げ、窓の上限をその比の量にします
- 6.1 と同じく、読んだ量が前の区間の値を超えた時だけ目標を求め、前の区間の値を読んだ量に置き換えます

理由は、6.1 の目標が損失の見込みと余裕で rcvbuf を大きくしすぎ、遅い読み手の接続でも rcvbuf を上限まで上げて、cache の効率を落としたためです(v6.16)。
その後、伸びを 1 倍にした形が slow start の送り手を抑えたので、伸びの 2 倍を戻しました(v6.18)。

ラボの観測では、`rcv-window-pacing`(往復 100 ms、すぐに読むアプリケーション)の最大の窓が、6.1 の 401 から 737 KB から、7.2 の 329,856 から 372,480 byte に下がりました。

推奨:未読を除いた読んだ量を採る候補にします。
wgstack は boost の予約を需要で取り、読まない接続の窓を floor に留めます。
読み切れない接続で窓の上限を上げないことは、同じ向きの規則です。
16 MSS の余裕を外すことは採りません。
適合の台本の帯は 6.1 から決めた値で、余裕を外した 7.2 も帯の内側に止まるので、どちらでも台本は通ります。
余裕は小さな窓での立ち上がりを助け、wgstack の窓は floor の 256 KiB から始まるので、外して得る節約は小さいためです。

## 自動調整の順序外の項

7.2 は、順序外のデータがある時、目標に RCV.NXT から最も先の順序外の byte までの幅を足します(v6.16)。
さらに、順序外の segment を待ち行列に入れるたびに、前の区間の値のまま自動調整を流し、順序外の幅の分だけ rcvbuf を上げます。
受け付ける前の接続と、アプリケーションが閉じた接続では、この調整をしません(v6.16)。

理由は、損失の後に穴を埋める間、順序外のデータが rcvbuf を占め、窓が閉じて送り手が止まることがあるためです。
読んだ量だけの目標は、穴がある間は読めるデータが増えないので、この占める分を見込みません。

推奨:採る候補にします。
wgstack の空きは保持する順序外のデータで減るので([受信の窓と boost の方針](wgstack-performance.md#受信の窓と-boost-の方針))、損失の後に窓の上限が順序外のデータで埋まると、Linux と同じく窓が閉じます。
窓の上限に順序外の幅を足すことは、予約(boost の 4 MiB)の内側で行えば、上界の式を変えません。
採るときは、溢れの後の回復が遅くならないことを qbench の受ける向きの損失の場合で確かめます。
窓の上限を上げても、広告する窓は rcv_ssthresh の歩みで開くので、右端を一度に進める以前の問題([受信の窓と boost の方針](wgstack-performance.md#受信の窓と-boost-の方針)の採った理由)は起きないと見込みます。
この見込みは未確認です。

## RTT の短い経路の抑え

7.2 は、受け手の RTT が `tcp_rcvbuf_low_rtt`(既定 1 ms)より短い時、伸びの項を、基本の窓に RTT と 1 ms の比を掛けた量にします(v6.19)。

理由は、データセンターの中の短い RTT の流れで rcvbuf が速く大きくなりすぎ、NIC の page の再利用と cache を損なうためです。

推奨:採りません。
wgstack の相手はトンネルの先で、RTT は普通 1 ms を超えます。
1 ms より短い経路でも、予約が boost の 4 MiB で抑えます。

## 受け手の RTT の標本

7.2 は受け手の RTT の推定を次のように変えました(v6.16)。

- timestamp による標本:TSecr と今の時刻の差が 0 の標本を捨てます。
  6.1 は 0 を 1 ms と数えました
- 大きな標本の平滑:今の推定より大きい timestamp の標本は、受信の待ち行列に未読のデータがある間は捨てます。
  6.1 は常に 8 分の 1 の重みで平滑しました
- 窓による標本は 6.1 と同じく、推定より小さい時だけ推定を下げます

理由は、読むのが遅い間の標本は読み手の遅れを含み、推定を大きくして自動調整の区間を延ばし、目標を膨らませるためです。

推奨:未読がある間の大きな標本を捨てることを採る候補にします。
前節の未読を除いた読んだ量と同じく、遅い読み手で窓の上限を上げない向きの規則です。
0 の差の扱いは、wgstack の timestamp の単位と時計によるので、wgstack の時計の刻みで差が 0 になる場合があるかを確かめてから決めます。

## SACK の圧縮の時間

SACK の圧縮の規則(RCV.NXT ごとの最初の 3 つをすぐに返し、4 つ目から遅らせる)は 6.1 と同じです。
遅らせる時間が変わりました(v6.19)。

- 時間:受け手の RTT の推定と SRTT の小さい方の、`tcp_comp_sack_rtt_percent`(既定 33)% を 1.25 倍した量、つまり約 41% です。
  6.1 は 5% でした。
  どちらも `tcp_comp_sack_delay_ns`(1 ms)で抑えます
- 猶予:`tcp_comp_sack_slack_ns` の既定が 100 µs から 10 µs になりました

片道 25 ms の qbench の経路では、6.1 でも 7.2 でも時間は 1 ms で、変わるのは RTT が約 20 ms より短い経路です。

理由は、5% では短い RTT の流れで圧縮がほとんど効かず、ACK の数を減らせなかったためです。
33% は、1 往復に ACK と送信の単位が 3 つずつある状態を保つ値として選ばれました。

推奨:採りません。
wgstack は SACK の圧縮を持たず、順序外の segment ごとにすぐ ACK を返す RFC 5681 の側にいます([今の wgstack との比べ](wgstack-performance.md#今の-wgstack-との比べ)の違い 3)。
この判断を変える材料は増えていません。

## 窓を超える segment

7.2 は、終わりの番号が RCV.NXT に今の受信の窓を足した位置を超える segment を、受信の待ち行列が空でなければ捨てます(v6.17、`tcp_sequence`)。
受信の待ち行列が空なら、6.1 と同じく受け入れます。
中身が窓に収まり FIN だけが窓を超える segment は、後で確かめるために通します。
捨てた segment には、窓の外の ACK の速さの制限の内側で重複した ACK を返します。
6.1 は、始まりが窓の内側なら、窓を超えた分も受け入れました。

理由は、窓を守らない送り手がメモリを使いすぎないようにするためです。
待ち行列が空のときに受け入れるのは、欠陥のある送り手との流れを止めないためです。

推奨:採りません。
RFC 9293 3.10.7.4 は、窓を超えた部分を切って窓の内側を処理することを定めます。
wgstack は窓を超えた分を予約の内側で扱い、窓の欄の丸めの分だけ受け入れることを適合の台本で測っています([受信のバッファの溢れ](wgstack-verification.md#受信のバッファの溢れ))。
適合の台本は窓を超える segment の受け入れを確かめないので、どちらの扱いでも台本は通ります。

## 最大の右端の追跡

7.2 は、自分が広告した最大の右端(rcv_mwnd_seq)を接続の間覚え、segment の受け入れの判定に、今の窓ではなくこの右端を使います(v7.1)。
RFC 7323 2.4 の、受け手が送ったどの ACK の窓にも入る segment を受け入れる求め(MUST)に従うためです。
窓を縮める設定(`tcp_shrink_window=1`)と、次節のメモリ不足の 0 の窓で右端が後ろへ戻った時に、相手の送った segment と ACK をすべて捨て続けることを防ぎます。

推奨:今のままにします。
wgstack は右端を後ろへ戻さないので、今の窓の右端が広告した最大の右端です。

## メモリ不足の 0 の窓

7.2 は、順序どおりの segment をメモリの不足で受信の待ち行列に入れられない時、すぐに ACK を返し、その ACK で 0 の窓を広告し、0 の窓を広告した窓として覚えます(v6.6、v6.14)。
受信の待ち行列が空なら segment は受け入れますが、その前にまとめ直しと順序外のデータの取り消しを試みます。
6.1 は segment を捨てるだけで、窓の欄は前の右端を保ちました。
前節の最大の右端の追跡があるので、相手が前の窓に送った segment は、空きができれば受け入れられます。

理由は、捨てた後も前の窓を広告し続けると、相手が窓に送るデータを受け手が捨て続け、相手には理由が見えないためです。
v6.14 の修正は、0 の窓を広告した後に、覚えた窓が前の値のままで、空きができても窓を開く ACK を送らなかった不具合を直しました。

推奨:採りません。
wgstack は広告した窓の内側のデータを予算の内側で必ず受け入れるので(I1、I2)、メモリの不足で窓の内側の segment を捨てる場面がありません。

## 順序外のデータを捨てる範囲

受信のメモリが上限を超えた時に順序外のデータを捨てる処理(`tcp_prune_ofo_queue`)は、6.1 では最も先の segment から rcvbuf の 8 分の 1 以上を捨てました。
7.2 は、届いた segment より先の segment だけを捨て、届いた segment が順序外の待ち行列の最後に入るなら何も捨てません(v6.2)。
捨てた時に SACK の block を忘れるのは 6.1 と同じです(RFC 2018 8 節の取り消し)。

理由は、届いた segment より前の順序外のデータは穴を先に埋めるので、残す方が損失から速く回復するためです。

推奨:SACK で知らせたデータを取り消す時に採る候補にします。
wgstack がデータを取り消すのは、枠の取り合いで需要の無い保有者を floor に戻す時だけで、その時に届いた segment はありません([boost の取得と floor への戻り](wgstack.md#boost-の取得と-floor-への戻り))。
取り消す範囲を最も先のデータから選ぶ規則にするなら、7.2 と同じ向きです。

## 窓 0 の FIN

7.2 は、受信の窓が 0 の時に届いた中身の無い FIN を受け入れます(v7.0)。
多くの場合、FIN は受信の待ち行列の最後の segment に合わさり、メモリを使いません。
理由は、窓 0 を広告しても中身の無い FIN を繰り返し送る送り手があるためです。
RFC 9293 3.10.7.4 は窓 0 の時に ACK、URG、RST の受け入れを求め、FIN は挙げません。

推奨:適合の台本 `fin-zero-window` の期待に従います。
6.1 と 7.2 はどちらもこの台本を通ります。

## 受け手の MSS の推定

7.2 は、順序外の segment でも受け手の MSS の推定と前々節の比を更新します(v6.17)。
6.1 は順序どおりの segment だけで更新しました。
推定は 2 segment の規則と自動調整に使います([受け手の MSS の推定](wgstack-performance.md#受け手の-mss-の推定))。

理由は、最初から多くの順序外の segment を受ける接続で、推定と比を早く合わせるためです。

推奨:採る候補にします。
推定が早く合うと、穴を埋めた後の 2 segment の規則が正しく働きます。
効果は小さいと見込むので、優先は低くします。

## 変えていないもの

次の挙動は 6.1 と 7.2 で同じです。

- 窓を縮めない規則と、`tcp_shrink_window` の既定 0
- quickack の数の補い方と上限
- 2 segment の規則と、読み取りの後の ACK の条件
- まとめ直し(`tcp_collapse`)の規則
- rcv_ssthresh の歩み(`tcp_grow_window`)

[溢れた後の Linux の受け手](wgstack-performance.md#溢れた後の-linux-の受け手)のこれらの節は、7.2 にもそのまま当てはまります。
