# エージェントの wgft の netstack

wgstack は、ユーザー空間モードのエージェントが gVisor の netstack の代わりに選べる、wgft が持つ netstack です。
wgstack は実装の途中です。
TCP の核と Device は `internal/wgstack` に実装し、UDP、ICMP の echo、断片の再組み立ての共有、`WGFT_AGENT_NETSTACK` の設定、トンネルへの組み込みは未実装です。
構造と上界の形をここで決め、値と細部は実装の時に決めます。
検証の計画は[wgstack の検証](wgstack-verification.md)に分けます。

## 目的と範囲

ユーザー空間モードのエージェントは、トンネルから届く利用者の TCP を gVisor の netstack で終端します。
前に立つ VPS はカーネルモードで DNAT と MASQUERADE を行うので、利用者と運用者が受け取る TCP の品質とメモリの挙動は、エージェントの netstack の品質と挙動です。
`vpsd` がユーザー空間モードの組でも、エージェントは `vpsd` の netstack からの接続を受け付けるだけなので、wgstack の範囲は変わりません。
gVisor の netstack には、構造上の上限を持たない保持点と、短い障害の後の遅い回復が残ります([上界に含めない保持点](memory-limits.md#中身の無い-segment-の処理待ち)、[短い障害の後の回復](../vps/userspace.md#63-ユーザー空間モード)、[netstack の依存の固定](netstack-dependency.ja.md))。
wgft は依存にパッチを当てません。
smoltcp、lwIP、既存の fork を調べた結果はどれも採らず、wgft が Go で netstack を書くことを所有者が決めました。
Go で書くので、リリースは `CGO_ENABLED=0` の単一のバイナリのままです。

wgstack が扱う範囲は次のとおりです。

- 対象:エージェントのトンネルだけです。
  `vpsd` のユーザー空間モード(`internal/dataplane/userspace/utun`)は gVisor の netstack を使い続けます
- 開き方:受動の open だけです。
  エージェントはトンネルからの接続を受け付け、LAN の宛先へは今までどおり OS のソケットで接続します
- プロトコル:IPv4 だけで、トンネルの MTU は Device を作るときに固定します。
  UDP、ICMP、IPv4 の断片の再組み立ては、今の `internal/nettun` が扱う範囲を扱います。
  gVisor を置き換えると、これらもすべて置き換わるためです
- アドレス:宛先は設定したプレフィックスの集合に入るアドレスを受け付け、送信元はどのアドレスでも受け付けます。
  今の集合はエージェントのトンネルのアドレスの /32 の 1 つです。
  将来、拠点ごとの仮想の /16 をエージェントが受け付ける可能性があります。
  wgstack はその機能を作りませんが、表のキーと待ち受けの束縛は集合を前提にし、その機能を妨げない形にします

### 完成と性能の目標

最初の目標を「完成」と呼び、次の 3 つの条件で判定します。

- 正しさ:Linux を参照の実装とする適合の試験で、期待した差だけを残して一致します([wgstack の検証](wgstack-verification.md#適合の試験))
- 保持の上界:空の segment、順序外の洪水、読まない相手、SYN の洪水、TIME_WAIT の入れ替わりのような敵対的な入力の下で、保持する量が導いた上界で止まります
- 退行が無いこと:CLI、API、終了コード、ラボの一式に退行がありません

性能の目標は完成の後に追います。
スループットは Linux の 80% 以上かつ gVisor 以上、短い障害からの回復は Linux の回復の時間に RTO 1 回分を足した時間以内、通信量の少ない stream の遅れの p99 は Linux の 1.5 倍以内、CPU は gVisor の 1.2 倍以内です。
完成は NewReno で判定します。
SACK の scoreboard、RACK の時刻、CUBIC は性能の段階で加え、そのときにデータ構造を作り直さずに済む形を今の段階で選びます([後の段階の機能](#後の段階の機能))。

wgstack は、ユーザー空間モードのエージェントの実験的な選択肢として、明示した場合だけ使います。
既定は gVisor のままとし、ステージングの環境で長く動かして確かめるまで既定を変えません。
この設計と実装を載せる長期のブランチは、性能の目標を満たすまで main にマージしません。

### 不変条件

wgstack は次の不変条件を守ります(所有者の草稿)。

- I1 有限:論理的な資源のすべてに、入力の量、種類、順序によらない、設定から決まる有限の上限があります
- I2 保持の前の予約:保持する前に予約し、上限の無い代わりの置き場を持ちません
- I3 所有:保持するものはすべて、持ち主、容量、作る条件、返す条件を 1 つずつ持ちます
- I4 TCP の正しさ:再送に要る未確認のデータを黙って捨てません。
  義務を果たせないときは、安全に閉じる方を選びます
- I5 自己増殖の禁止:タイマー、再送、誤りの処理は、外からの入力なしに、上限の無い持続するオブジェクトを作りません
- I6 制御できること:停止、`Close`、予算の枯渇、誤りは資源を回収します
- I7 隔離:wgstack の失敗はカーネルモードに影響しません

尽きたときの方針も所有者が決めました。
枠が無ければ新しい接続を拒み、受信は広告する窓で絞り、再送の容量を予約できなければ新しいアプリケーションのデータを拒み、再組み立ての予算を超える断片を捨て、バッファを見えないところで増やしません。
各資源への当てはめは[尽きたときの動作](#尽きたときの動作)に書きます。

## トンネルとの境目と選択

### 今の境目

エージェントのトンネル(`internal/dataplane/userspace/tunnel`)と、その上の中継と `internal/netpipe` は、`internal/nettun` の次の面と挙動だけに頼ります。
wgstack は同じ面と挙動を持ち、トンネルの中で差し替えます。

- 作成:`nettun.Create(addr, mtu)` が Device を作ります
- wireguard-go との境目:Device は `tun.Device` を満たし、`wgbind.NewDevice` が wireguard-go の device に組み込みます。
  使うのは `Name`、`File`(nil)、`Events`、`MTU`、`BatchSize`(1)、`Read`、`Write`、`Close` です。
  `Events` は作成の直後に `EventUp` を 1 つ持ち、`Close` で閉じます
- `Read`:1 回に 1 件を返します。
  誤りを返すのは `Close` の後の `os.ErrClosed` だけです。
  wireguard-go は `Read` がほかの誤りを返すと device を閉じるので、packet を作れなかったときは誤りにせず、その packet を飛ばして次を待ちます
- `Write`:バッチの 1 件が失敗しても残りを処理し、受け取った件数と最初の誤りを返します。
  長さ 0 の packet は受け取った件数に数えて何もしません。
  誤りにするのは閉じた後の `Write` と IPv4 でない packet だけで、捨てた断片、UDP の会計による拒否、MSS の下限による拒否は誤りにしません([TUN の Write の誤り](packet-validation.md#tun-の-write-の誤り))
- TCP の待ち受け:`ListenTCP(netip.AddrPort)` が `net.Listener` を返します。
  `Accept` が返す接続は `net.Conn` に加えて、中継と `internal/netpipe` が型アサーションで探す `Abort`、`CloseWrite`、`Delivered`、`CloseForDelivery`、`OnBoost` を持ちます。
  待ち受けの `Close` は、その待ち受けの accept の待ち行列の接続と握手の途中の行に RST を送って返し、ポートをその場で空けます
- TCP の接続の読み取り:期限を過ぎた読み取りは `Timeout()` が真の `net.Error` を返し、相手の FIN の後は `io.EOF` を返します。
  `internal/netpipe` の写しは、期限の誤りでデータの途切れを、`io.EOF` で向きの終わりを見分けます
- `OnBoost(f)`:f を登録し、その場で今の状態を 1 回渡します。
  boost を得たときに `f(true)` を、需要の無い保有者として floor に戻るときに `f(false)` を呼びます。
  `f(false)` が偽を返したら戻りを取り消し、boost の枠を持ち続けます。
  `internal/netpipe` の `FollowBoost` は、登録のときの呼び出しで LAN 側のカーネルのソケットを floor に固定し、カーネルのソケットが floor を超える受信のデータを持つ間は `f(false)` に偽を返します。
  `f(true)` の戻り値は使いません。
  閉じた接続の枠を返すときには呼びません。
  f は接続の排他の中で呼ぶので、f は待たずに戻り、その接続を呼びません
- 古い接続の値:接続の枠が TIME_WAIT の表の行に移った後か、枠が別の接続に使われた後も、中継は元の接続の値を持ち続けます。
  この値では `Delivered` が真を返し、`Close` は何もせずに nil を返し、`Read` と `Write` は `net.ErrClosed` を返します。
  `Abort` は、元の接続の行が表に残っていれば行を外して RST を送り、残っていなければ何もしません。
  固定版の gVisor の `Abort` が TIME_WAIT でも RST を送ってポートを返す挙動([閉じた後の接続の表](tcp-retention.md#閉じた後の接続の表))と同じ結果です
- UDP の待ち受け:`ListenUDP(netip.AddrPort)` が `net.PacketConn` を返します。
  `ReadFrom` が返す送信元は `*net.UDPAddr` で、`String()` は `a.b.c.d:port` の形です。
  中継はこの文字列をセッションの表の鍵にし、同じ値を `WriteTo` に渡します。
  `WriteTo` は送信の余地ができるまで待ち、`Close` の後の操作は `net.ErrClosed` を返します([UDP の接続](udp-accounting.md#udp-の接続))
- keepalive の ping:`DialPing(laddr, raddr)` が、echo を 1 つ書き、応答を 1 つ期限つきで読む `net.Conn` を返します([keepalive の ping の endpoint](udp-accounting.md#keepalive-の-ping-の-endpoint))
- 会計の故障:`UDPReceiveFault()` が、`agent doctor` の `tunnel.udp_accounting` の判定に使う誤りを返します

トンネルの外の package は `internal/nettun` を名指さず、中継と `internal/netpipe` は前述のメソッドを型アサーションで探します。
本番のファイルで `internal/nettun` を import するのは、トンネルと `utun` だけです。
このため、トンネルの中に 2 つの実装が満たす非公開の interface を置けば、中継と `internal/agent` を変えずに差し替えられます。

`Write` の入口で今の Device が行う検査は、wgstack でも同じ規則で行います。
IPv4 の Total Length より後ろの byte の切り捨て、[断片の入口と再組み立ての表](packet-validation.md#再組み立ての表)、[ICMP の誤りの送信元の確認](packet-validation.md#icmp-の誤りの入口)、[Fragmentation Needed の MTU の下限 552](packet-validation.md#fragmentation-needed-の-mtu-の下限)、[SYN の MSS の下限 536](packet-validation.md#tcp-の-mss-の下限)、[UDP の受信の予算](udp-accounting.md#udp-の受信の予算)、自分宛ての packet を中で折り返さないことがこれに当たります。
MSS の下限の検査は、gVisor の option の読み方ではなく、wgstack 自身が TCP の処理で使う読み方で行います。
捨てた数の数え方と、1 分に 1 回までのログも同じにします。

次の仕組みは gVisor の挙動を抑えるためのものなので、wgstack には移しません。

- 中身の無い ACK の予算:wgstack は segment を処理待ちに積まず、`Write` の中で同期して処理します。
  1 つの ACK の処理は送り残しの segment の数によらない手間で済むので、予算が抑えていた処理待ちの増加が構造上起きません
- 閉じた後の接続の表:後述の [TIME_WAIT の表](#time_wait-の表)に置き換えます
- 書き込みの数の上限:送信のバッファは byte の輪であり、書き込み 1 回ごとの管理の構造を持ちません
- 受信のメモリの非公開のフィールドの読み取り:wgstack は自分の会計を持ちます

### 中継から見える違い

中継が今の gVisor の挙動を前提にしている点のうち、wgstack で変わる点は次のとおりです。
どれも、中継の試験を両方の実装に流して確かめます。

- 待ち受けの開き直し:TIME_WAIT の接続は待ち受けの束縛と衝突しません。
  gVisor では TIME_WAIT の間に同じポートを開けませんでした([TCP の中継と終了](tcp-relay.md))。
  wgstack の挙動は、`SO_REUSEADDR` を付けた Linux の待ち受け(Go の `net.Listen` の既定)と同じです
- `CloseForDelivery`:wgstack では通常の `Close` と同じです。
  送り残しを持つ接続は接続の枠に残り、TIME_WAIT の表に入るのは[行に移る条件](#行に移る条件)を満たした後だけなので、表の追い出しで末尾を失いません
- accept の待ち行列の RST:握手を終えて待ち行列にいる接続が RST を受けたら、wgstack は待ち行列から外して枠を返します。
  gVisor は待ち行列に残して `Accept` で返し、その `RemoteAddr` は nil でした
- `Delivered` の判定:最後の `Close` か `Abort` の後で、CLOSED、TIME_WAIT、受信のバッファが空の FIN_WAIT_2 を届け終えたとします。
  条件は今と同じで、判定に gVisor の非公開のフィールドを使いません

### 実装の選択

実装の選択は `WGFT_AGENT_NETSTACK` で受け取り、フラグ `--agent-netstack` はその別名です([設定の渡し方](../security/configuration.md#11a-設定の渡し方))。
値は `gvisor` と `wgstack` で、省略と空の値は `gvisor` です。
環境から推測せず、値を指定したときだけ wgstack を使います。

- エージェントだけが読みます。
  `vpsd` は他のプロセス向けの `WGFT_*` として無視します
- 知らない値は、どちらのモードでも設定の誤りとして終了コード 3 で止めます
- カーネルモード(`WGFT_MODE=kernel`)は netstack を使わないので、値を使いません。
  値が設定されていれば、使わない旨を起動時に英語の 1 行で出して起動を続けます。
  拒否にしないのは、モードを切り替えても同じ `agent.env` を使えるようにするためです。
  カーネルモードの同時フロー数の上限([カーネルに置くもの](../kernel-agent/installation.md#7b1-カーネルに置くもの)、`cmd/wgft/agent.go` の `logUnusedKernelLimits`)と同じ扱いです
- 選択はプロセスで 1 つで、トンネルを作り直しても変わりません。
  wgstack の作成に失敗しても gVisor に切り替えず、今のトンネルの作成の失敗と同じく試し直します
- 起動ログの有効な設定の印字に値と出所が載ります。
  wgstack のときは、実験的な選択肢であることを英語の 1 行で出します
- `wgft status`、管理用 API、wire protocol、`agent doctor` の JSON は変えません

選択の値は、`usermode` が受け取ってトンネルの宣言に渡します。
トンネルの宣言は wgstack の接続の枠の数を導くために、同時フロー数のプロセス全体の上限 K(`WGFT_MAX_TCP_FLOWS`)も受け取ります。
`WGFT_AGENT_NETSTACK` の名前と値は、このブランチが main に入るときに公開のサーフェスになります。
[設定の互換性](../compatibility/surfaces.md)は `WGFT_*` の名前と意味を保証するので、main に入った後は `gvisor` と `wgstack` の 2 つの値を受け付け続けます。
「実験的」が意味するのは、`wgstack` を選んだときの転送の品質と資源の挙動を互換性の保証に含めないことです。
この扱いは、[互換性の保証](../compatibility.md)が macOS のエージェントを暫定として保証の外に置く扱いに倣います。
保証の文言を互換性の文書に足すかどうかは、main に入れる時に所有者が決めます。
後で既定を `wgstack` に替えると、値を省略した配置の挙動が変わります。
このため既定の変更はそれ自体を所有者の決定とし、リリースノートで知らせ、`gvisor` を明示すれば元の実装を選べる状態を保ちます。
[設定の渡し方](../security/configuration.md#11a-設定の渡し方)と互換性の文書への記載は、実装と同じ変更で行います。

## package の配置

[package の配置](../architecture/packages.md#7a7-package-配置)と `internal/dataplane/deps_test.go` の規則に合わせ、次のように置きます。

- `internal/wgstack`:wgstack の本体です。
  後述の決定的な核と、それを `tun.Device` として動かす Device を持ちます。
  モジュールの外からは標準ライブラリと `golang.zx2c4.com/wireguard/tun`(`tun.Device` と `tun.Event` の型)だけを import し、モジュールの中の package は import しません。
  拒否のログを 1 分に 1 回までに絞る門は、核の時刻で数える wgstack 自身の門です。
  `internal/lograte` の門は壁時計を読み、核は時計を直接読まないので、使いません
  `gvisor.dev/gvisor`、`internal/nettun`、`internal/dataplane` とその下位、`internal/agent`、`internal/vpsd` を import しません
- 再組み立ての表:今の `internal/nettun` の再組み立ての表は gVisor を import しないので、葉の package に移して 2 つの実装で共有します。
  移すのは表だけで、gVisor の Time Exceeded の経路は `internal/nettun` に残ります
- `internal/dataplane/userspace/tunnel`:2 つの実装が満たす非公開の interface を持ち、宣言の値で実装を選びます。
  `internal/nettun` と `internal/wgstack` の両方を import する唯一の package です

`internal/wgstack` は `internal/dataplane` の下に置かないので、`TestDependencyDirection` の「dataplane の実装どうしは import しない」規則に触れません。
トンネルは `internal/dataplane/userspace` の下にあり、制御プレーンでも別の dataplane の実装でもない package を import するだけです。
`internal/dataplane/deps_test.go` の `TestWgstackImports` が、`internal/wgstack` の import の制限と、`internal/agent/kernelmode` と `internal/agent/agentdp` が推移的にも `internal/wgstack` に依存しないことを検査します。
後者がカーネルモードの側の I7 を構造で支えます。
プロセスの中の隔離として、カーネルモードのエージェントは wgstack を作らず、wgstack のコードはカーネルモードの経路で動きません。

## 並行性と時計

wgstack は、Device ごとに 1 つの goroutine だけを持ちます。
この goroutine はタイマーを動かし、再組み立ての表の期限の掃除も行います。
ほかの処理は呼び出し側の goroutine で動きます。

- 入力:wireguard-go が呼ぶ `Write` の中で、packet を同期して処理します。
  入力の待ち行列を持たないので、入力の洪水は wgstack の中に積もらず、wireguard-go の有限のキューとソケットのバッファで止まります
- 出力:wireguard-go が呼ぶ `Read` の中で、次に送る packet をその場で作り、wireguard-go のバッファに直接書きます([出力](#出力))
- アプリケーションの操作:中継の goroutine が呼ぶ `Read`、`Write`、`Accept`、`Close` は、接続ごとの通知の channel(容量 1)で待ちます。
  期限は接続ごとに向きあたり 1 つの runtime のタイマーを、作成の時に作って置き直します

接続ごと、packet ごと、タイマーごとの goroutine は作りません。
`Close` はこの 1 つの goroutine の終了を待ちます。

TCP、UDP、ICMP、再組み立ての状態は決定的な核が持ちます。
核は goroutine を作らず、時計と乱数を直接読みません。
核の操作は「packet と時刻を受けて状態を変え、出力を返す」「時刻を受けてタイマーを進める」「アプリケーションの操作」の 3 種類だけです。
時計(単調な時刻)と乱数(ISN の鍵、表の hash の種、challenge ACK の揺らぎ)は作成の時に渡し、本番は単調な時計と暗号論的な乱数を使います。
試験は手で進める時計と固定の種を渡し、Device の goroutine を使わずに核を直接進めます。
核が時計を読む例外は boost の回収だけです。
枠の集まりはプロセスで 1 つなので、回収の要求は別の Device の保有者の需要の無い時間を、その保有者の Device の時計で確かめます。
本番の Device はすべてプロセスで 1 つの起点を持つ単調な時計を使うので、Device の間で時刻を比べられます。
手で進める時計は Device ごとに起点が違うので、Device の間で枠の集まりを分け合う試験はこの比べ方に頼れません。

錠は Device の表の錠と接続ごとの錠の 2 段です。
表の錠は検索、追加、削除の間だけ持ち、表の錠を持ったまま接続の錠を取りません。
接続の枠は世代の番号を持ち、表の錠を離した後に古い検索の結果を見分けます。
boost の回収や TIME_WAIT の表の追い出しのように、ある接続の処理が別の接続に触れるときは、自分の錠を離してから取るか、相手の錠を `TryLock` で取り、取れなければその相手を見送ります。
アプリケーションの操作は、錠を離してから待ちます。
package の初期化の時には何もしません。
錠の細部と CPU の目標に向けた分け方は、実装と性能の段階で決めます。

## メモリの模型

wgstack が保持するものは、すべて作成の時に容量を決めた表か、作成の時に決めた予算から予約するバッファのどちらかです。
表は作成の時に確保し、後から大きくしません。
バッファの中身は 16 KiB の chunk で持ち、予約した量まで必要になった時に確保します。
送信と受信の輪は、byte の位置を予約の容量で割った余りの位置に置きます。
容量は floor も boost も chunk の倍数の 2 のべき乗なので、輪が持つ chunk は予約を 16 KiB で割った数を超えません。
位置で置かない輪では、境目のそろわない 256 KiB の範囲が 17 個の chunk に掛かります。
16 KiB は Go のメモリの大きさの区分と一致するので、chunk の確保に切り上げの無駄がありません。
TCP のバッファの floor と boost の値と規則は、[boost の取得と floor への戻り](#boost-の取得と-floor-への戻り)に書く違いを除いて、今の[TCP バッファ](tcp-buffers.md)と同じにします。
`internal/netpipe` の `FollowBoost` が、LAN 側のカーネルのソケットの受信のバッファを boost の知らせに合わせるためです。

### 接続の表

接続の表は、作成の時に数 N_c を決めた固定の枠の配列と、4 つ組から枠を引く固定の大きさの開番地法の hash の表です。
hash は作成の時の乱数の種で鍵を付け、相手が選ぶ送信元のアドレスとポートで衝突を集められないようにします。
キーはローカルのアドレスを含む 4 つ組で、ローカルのアドレスが集合のどれでも同じ形です。
N_c は K と accept の待ち行列の全体の数 Q の和で、設定項目にしません。
中継は K を超えた接続を `Abort` で即座に終えるので、定常の状態で枠を持つ接続は、中継が数える K 本と accept の待ち行列の Q 本までです。
送り残しを届けている接続も中継が K に数えます([中継が終わった後の末尾の配送](tcp-retention.md#中継が終わった後の末尾の配送))。

### 接続ごとのバッファ

確立した接続は、確立の時に受信の floor を予約し、送信の floor を予約します。
予約は accept の待ち行列にいる間にも持ちます。
Linux と同じく、`Accept` の前に届いたデータも受信のバッファに入るためです。
boost は今と同じくプロセスで 16 本の枠から予約し、得られなければ floor のまま続けます。

- 送信のバッファ:予約した容量の byte の輪です。
  中身は累積の確認で外し、SACK で確認された分も累積の確認まで保持します。
  再送はこの輪から segment を作り直します
- 送信の記録:送った segment ごとに、開始の番号、長さ、送った時刻、印(再送、後の段階の SACK 済みと損失)を持つ固定の容量の輪です。
  記録は、後の段階の RACK が送った時刻の順にたどるための list の節も今から持ちます。
  容量は送信のバッファの予約を、送り残しを分ける大きさの下限の 472 byte([TCP の MSS の下限](packet-validation.md#tcp-の-mss-の下限))で割った数です。
  記録の輪が満杯なら、確認で空くまで新しい segment を送りません
- 受信のバッファ:予約した容量の byte の輪で、順序どおりの未読のデータと順序外のデータを同じ輪に置きます。
  順序外のデータは輪の中の自分の位置に書き、届いた範囲を区間の表で持ちます。
  区間の数の上限 H は受信の予約から決め、MSS の下限の 536 byte の segment が 1 つおきに失われる最悪の場合を覆う H = ceil(予約 / (2 × 536)) とします。
  floor の 256 KiB では 245 個、boost の 4 MiB では 3,913 個です。
  MSS の下限以上の segment では、区間が尽きるのは受信のバッファが満ちた後だけで、バッファに入る順序外のデータを区間の数で捨てることはありません。
  MSS の下限より小さい segment を穴を空けて送る相手は、バッファが満ちる前に区間を使い切れます。
  そのとき捨てるのは SACK で知らせていない segment だけなので、I4 に反しません
  決まった数を置いた最初の段階では、MTU の大きさの segment が途中の待ち行列の溢れでまとめて失われると 32 個の区間が先に尽き、受信が止まりました。
  区間の表は予約の段ごとの固定の配列で、floor の表は枠と共に持ち、boost の表は受信の向きの boost を得た時に確保して floor に戻る時に返します。
  記録の輪と同じく、段を変える時に区間を写します。
  区間は最後に伸びた時の順も持ち、RFC 2018 が求める順(最も新しく受けた segment を含む block が先頭)で SACK の block を作ります。
  H 個を超える区間を作る segment は捨て、穴を埋めるか既存の区間を伸ばす segment は受け入れます。
  広告する窓の右端は後ろへ戻しません

中身の無い segment と小さな segment は、受信の側で中身の byte の外に何も残しません。
小さな書き込みも送信の輪に byte として入るだけです。

### boost の取得と floor への戻り

boost の値、枠の数、需要の判定(250 ms の区間に 64 KiB 以上)は今の[TCP バッファ](tcp-buffers.md#boost-を求める条件)と同じです。
受信の窓を floor より先へ開くのは、受信の向きの需要で boost を得た後だけです。
送信の向きの需要だけで boost を得た接続は、送信のバッファだけを広げ、受信の窓を floor の内側に保ちます。
送信の向きの需要で boost を持つ接続に後から受信の向きの需要が生じたときは、同じ枠のまま受信の窓を floor より先へ開きます。
枠は 1 本の接続の両方の向きに 1 つなので、新しい枠は求めません。

floor へ戻るのは、今と同じく、空きの枠も返せる枠も無いときの取得の要求が、1 秒の間どちらの向きにも需要の無い保有者を見つけたときです([需要の無い保有者からの回収](tcp-buffers.md#需要の無い保有者からの回収))。
戻すのは、次の条件がすべて成り立つときだけです。

- 受信:保持する最も右の byte(順序外のデータを含みます)が、最も古い未読の byte から数えて floor の内側にあります。
  受信のバッファは位置で中身を置くので、条件も位置で確かめます。
  合計の byte で確かめると、例えば 3 MiB 先にある 10 KiB の SACK 済みの順序外のデータを持つ接続が戻り、そのデータを取り消す(I4 に反します)か floor の外に持ち続けるかのどちらかになります
- 送信:送信の輪の byte(送り残しと未送信の和)が floor 以下で、確認を待つ送信の記録の数が floor の記録の輪の容量(556 件)以下です。
  小さな書き込みを `TCP_NODELAY` で送る接続は、byte が floor より少なくても数千の記録を持ちうるので、記録の数も確かめます
- 組のカーネルのソケット:`OnBoost` で登録した関数が `f(false)` に真を返します

条件の一つでも成り立たなければ boost に戻り、枠を持ち続けます。
需要の無い保有者は受信の窓の右端を floor より先へ広告したままのことがあるので、wgstack は戻した後も広告済みの右端を縮めて知らせません。
代わりに、受信のバッファに入るのは floor の内側のデータだけにし、その先に届いたデータは ACK せずに捨てます。
捨てたときは重複した ACK を返し、相手が RTO だけに頼らずに損失を知れるようにします。
TCP は確認していないデータを受け手が捨てることを許し、送り手は再送します。
RFC 9293 が避けるよう求めるのは広告した窓を縮めて知らせることで、この方式はそれを避けます。
捨てるのは 1 秒以上黙った後に古い窓へ送り直した相手のデータだけで、その相手の需要は boost を求め直します。
広告する右端は、広告済みの右端と、次に受ける番号に floor の空きを足した位置の大きい方なので、次に受ける番号が古い右端を越えた後は floor の窓に戻ります。
この方式を採るのは、需要の無い保有者が枠を持ち続けないことを、相手の挙動によらず保証するためです。
この方式は I4 と RFC 9293 に反せず、固定版の gVisor が今行う回収と同じ結果です。
残る危険は[未確認の点と未決の点](#未確認の点と未決の点)に書きます。
窓の右端が floor の内側に入るのを待つ方式では、黙った相手が右端を進めないので、枠を返せません。

### TIME_WAIT の表

TIME_WAIT と FIN_WAIT_2 の接続は、[行に移る条件](#行に移る条件)を満たした後に、バッファを持たない小さな行の表に移します。
行は 4 つ組、送受信の次の番号、相手の最後の timestamp、期限、状態、元の接続の世代だけを持ちます。
表の行の数 M は固定で、設定項目にしません。
期限は状態ごとに一定(どちらも 60 秒)で、行を固定の配列の上の両方向の list に入れた順で並べ、先頭から期限を過ぎた行を外します。
接続の枠で TIME_WAIT に入った後に行に移る接続は、枠に残った時間を引いた残りの期限を持って list の末尾に入ります。
このため list は期限の順になりません。
先頭からの掃除は、先頭の行が期限を過ぎるまで後ろの行を外しません。
前の行はどれもこの行より前に入ったので、その期限は、この行を入れた時から 60 秒以内に来ます。
このため期限を過ぎた行も、表に入れてから 60 秒以内に掃除で外れ、期限を過ぎてから外れるまでの時間は最長で 60 秒から残りの期限を引いた時間です。
引くときにも期限を確かめ、過ぎた行はその場で外して、その segment をどの接続にも当たらない segment として扱います。
期限を過ぎて残る行も表の行に数えるので、行の数は M を超えません。
FIN_WAIT_2 の行が相手の FIN で TIME_WAIT に移ったときは、list の末尾に付け直します。
満杯のときは最も古い行を外して数え、1 分に 1 回までログに出します。
外した行の 4 つ組にその後届いた segment は、どの接続にも当たらない segment として扱います。

TIME_WAIT の行は再送された FIN に ACK を返し、Linux と同じく期限を 60 秒から数え直して list の末尾に付け直します。
RFC 6191 の条件を満たす新しい SYN を受けたら、行を外して待ち受けに渡します。
[行に移る条件](#行に移る条件)を満たさずに枠に残る TIME_WAIT の接続も、同じ SYN を同じ規則で扱います。
このとき枠の接続は CLOSED になり、アプリケーションの読み取りには、それまでに受けたデータと `io.EOF` を返します。
CLOSED になってアプリケーションがまだ閉じていない枠は、4 つ組の hash の表から外れるので、同じ 4 つ組の新しい SYN を妨げません。
FIN_WAIT_2 の行にデータが届いたら、Linux と同じく RST を返して行を外します。

#### 行に移る条件

接続の枠が行に移るのは、次の 3 つがすべて成り立つときだけです。

- アプリケーションが `Close` で接続を閉じています。
  `CloseWrite` だけでは移りません
- 受信のバッファが空です。
  未読のデータは、アプリケーションが読んだか、`Close` が捨てたかのどちらかです。
  `Close` が未読の順序どおりのデータを捨てるときは RST で終えるので、行は作りません
- 送ったデータと自分の FIN がすべて確認されています

`CloseWrite` で FIN を送った接続に相手のデータと FIN が届き、プロトコルの状態が TIME_WAIT になっても、接続は枠に残り、アプリケーションはそのデータと `io.EOF` を読めます。
中継は片方向の EOF を `CloseWrite` で伝え(`internal/netpipe` の `Pipe`)、もう一方の向きの写しが相手の最後のデータをまだ読んでいないことがあります。
このとき行に移すと、確認済みのデータが読まれないまま消え、中継する byte の列が途中で切れます。
TIME_WAIT の期限は状態に入った時から数え、枠に残った時間も含めます。
期限を過ぎてもアプリケーションが閉じなければ、接続は CLOSED になって枠に残り、`Close` で枠を返します。
今の gVisor の枠を返す条件(`internal/nettun` の `returnable`)も、閉じていることと受信のキューが空であることを求めます。

### 握手の途中の表と accept の待ち行列

握手の途中の接続(SYN-RCVD)は、接続の枠とは別の、バッファを持たない固定の数 N_syn の表に置きます。
行は 4 つ組、両方の ISN、交渉した option、SYN-ACK の再送の回数、期限だけを持ちます。
待ち受け 1 つが使える行は N_syn の半分までです。
SYN-ACK の再送の間隔は回数ごとに一定なので、再送の回数ごとに 1 つの順序つきの list を持ち、各 list の先頭から期限を見ます。
握手の最後の ACK が届いた時に接続の枠と送受信の floor を予約し、確立した接続を accept の待ち行列に入れます。
SYN に載ったデータは受け入れません。

accept の待ち行列は Device 全体で Q 本、待ち受け 1 つで Q の半分までです。
待ち受けごとに backlog の分を持たないので、待ち受けの数を増やしても待ち行列の保持は増えません。

### UDP、ICMP、再組み立て

- UDP の受信:Device の予算(4 MiB と 4096 件)と endpoint 1 つの上限(予算の 1/4)を今と同じ値で持ちます([UDP の受信の予算](udp-accounting.md#udp-の受信の予算))。
  datagram の中身は、chunk を大きさの区分ごとの枠(例えば 256 byte、2 KiB、16 KiB と、それを超える datagram のための chunk の列)に分けて置きます。
  chunk は 1 つの endpoint だけが持ち、endpoint の間で共有しません。
  会計は chunk の単位で数え、chunk の中に生きている枠が 1 つでもある間は、その chunk 全体を endpoint と Device の予算に数えます。
  生きている枠 1 つが 16 KiB の chunk を留めても、留めた分は予算の内側にあるので、生きているヒープの上界は崩れません。
  endpoint は datagram を届いた順に読ませるので、使い終わった chunk は順に空き、一部だけ使う chunk は区分ごとに少数に留まります。
  小さな datagram 4096 件が 4096 個の chunk を使い、4 MiB の予算に対して 64 MiB を持つことを防ぐためです。
  管理の情報は 4096 件の固定の配列に置きます。
  会計は保持そのものなので、gVisor の統計の差から受理を判定する手順は要りません。
  枠の大きさで数えるので、予算に入る datagram の数は今の会計(中身に 64 byte を足して数える)と異なります
- UDP の送信:Device の予算(4 MiB と 1024 件)と endpoint 1 つの上限(予算の 1/4)を持ち、受信と同じ枠と chunk の単位で数えます。
  `WriteTo` は予約できるまで待ちます。
  MTU を超える datagram は、DF を立てず、0 でない ID で断片に分けて送ります(今の[UDP の送信時の断片化](udp-accounting.md#udp-の送信時の断片化)と同じ結果です)
- ICMP の echo:`DialPing` の endpoint は固定の数の表に置き、識別子を `Close` で返します。
  endpoint 1 つが持つ応答は 1 つだけで、読まれる前に届いた次の応答は捨てます。
  表が満杯なら `DialPing` は誤りを返します。
  自分のアドレス宛ての echo request には、後述の制御の出力の輪から応答します
- ICMP の誤り:Fragmentation Needed は、引用された TCP の番号が SND.UNA から SND.NXT の範囲にあるときだけ受け入れます(RFC 5927)。
  範囲の外の誤りは、送信元の確認を通っても捨てます
- 再組み立て:今の表(未完成の datagram 128 件、断片 512 個、保持 4 MiB、期限 30 秒)を共有して使います([再組み立ての表](packet-validation.md#再組み立ての表))。
  Time Exceeded と Parameter Problem は wgstack が自分で作ります

### 出力

出力は次の 4 つの組に分かれます。

- 接続の組:接続の枠が送る segment です。
  data、ACK、FIN、窓の probe、確立した接続の challenge ACK がこれに当たります
- 行の組:握手の途中の行が送る SYN-ACK(最初の送信と再送)と、TIME_WAIT の行が送る ACK と challenge ACK です
- UDP の組:UDP の送信の予算に入った datagram とその断片です
- 制御の組:どの接続にも行にも当たらない segment への RST、ICMP の誤り、echo の応答と、送った後に枠か行をその場で返す RST です。
  後者は `Abort`、再送の回数を使い切った接続、未読のデータを持った `Close`、待ち受けの `Close` が終える待ち行列の接続と握手の途中の行、データを受けた FIN_WAIT_2 の行、TIME_WAIT の行への `Abort` が送る RST です

接続の組と行の組は packet を待ち行列に積みません。
接続の枠と行は「送るものがある」印と順番の list の節を自分の中に持ち、`Read` の時に順番の list の先頭が 1 つの packet を作ります。
節は枠と行の中にあるので、出力の保持は接続と行の数で決まります。
制御の組だけが、MTU の大きさの枠を固定の数だけ持つ制御の輪に packet を積みます。
どの接続にも当たらない segment の洪水が埋めるのは制御の輪だけで、SYN-ACK と TCP の data は制御の輪を使いません。
洪水が制御の輪を埋めている間は、枠か行を返す RST も捨てられることがあります。
この損失は受け入れます。
枠か行はすでに返しているので、相手の次の segment はどの接続にも当たらない経路を通り、そこで RST を受けるためです。
行を追い出すときは、その行の順番の list の節も外します。

`Read` は 4 つの組を、送る packet のある組の間で byte の deficit round robin で選びます。
1 回に 1 つの組が得る量は MTU 1 つ分で、送るものの無い組は飛ばします。
組の間に厳密な優先を置かないのは、どの組も他の組に飢えさせられないようにするためです。
厳密に TCP を UDP より先にすると、遅れに敏感な UDP が TCP の転送の間に止まります。
今の gVisor の出力は 1 つの FIFO なので、組の間の順は今と異なります。
組の中の順は、接続の組と行の組が順番の list の順、UDP の組と制御の組が入った順です。

### タイマー

接続の枠は、再送、窓の probe、遅延 ACK、keepalive、閉じた後の期限のタイマーの節を枠の中に固定で持ちます。
節はタイマーの輪(timing wheel)に入れ直すだけで、タイマーを張るたびに確保しません。
TIME_WAIT の表と握手の途中の表は、前述の順序つきの list で期限を管理し、行ごとのタイマーを持ちません。
このため、タイマーの数は N_c と枠の中の節の数の積を超えず、入力が止まった後に新しいタイマーは生まれません。

## 上界の式

wgstack が保持する量の上界を、次の項の和とします。
byte の項は、予約と固定の配列が生きているヒープに持つ量を数えます。

```
M_wgstack = M_fix
          + N_c x (c_conn + f_s + f_r + r_f + h_f)
          + B x (d_s + d_r + d_rec + d_h)
          + N_syn x c_syn + M x c_tw + Q_ctl x s_ctl
          + M_udp_rx + M_udp_tx + M_frag + N_ping x c_ping
```

| 項 | 意味 | 決め方 |
|---|---|---|
| M_fix | Device の固定の構造、hash の表、タイマーの輪、順番の list の頭 | 実装で測って定数にします |
| N_c | 接続の枠の数 | K + Q。Q は Device 全体の accept の待ち行列の数で、初期の値は 512 です |
| c_conn | 接続の枠 1 つの構造(状態、タイマーの節、chunk の表) | 実装で測ります |
| f_s、f_r | 送信と受信の floor | どちらも 256 KiB([TCP バッファ](tcp-buffers.md)) |
| r_f | floor の送信の記録の輪 | 256 KiB / 472 byte の 556 件に記録 1 件の大きさを掛けた値です |
| h_f | floor の順序外の区間の表 | 256 KiB / (2 × 536 byte) の 245 個に区間 1 つの大きさを掛けた値です |
| B | boost の枠の数 | プロセスで 16 本 |
| d_s、d_r | boost が floor に加える送信と受信の分 | どちらも 4 MiB - 256 KiB |
| d_rec | boost が加える送信の記録の分 | 4 MiB / 472 byte の 8,887 件と 556 件の差に記録 1 件の大きさを掛けた値です |
| d_h | boost が加える区間の表の分 | 4 MiB / (2 × 536 byte) の 3,913 個に区間 1 つの大きさを掛けた値です |
| N_syn、c_syn | 握手の途中の表の行の数と 1 行の大きさ | 初期の値は 1024 行です |
| M、c_tw | TIME_WAIT の表の行の数と 1 行の大きさ | 初期の値は 65,536 行です |
| Q_ctl、s_ctl | 制御の出力の輪の枠の数と 1 枠の大きさ | 初期の値は 256 枠で、1 枠は MTU です |
| M_udp_rx | UDP の受信の予算の中身と、4096 件の管理の配列 | 4 MiB と配列の大きさの和 |
| M_udp_tx | UDP の送信の予算の中身と、1024 件の管理の配列 | 4 MiB と配列の大きさの和 |
| M_frag | 再組み立ての表 | 4 MiB(表の管理領域と完成の複製 1 つを含む、今の数え方) |
| N_ping、c_ping | echo の endpoint の表 | 初期の値は 16 件です |

初期の値は動作を確かめるための値であり、最適値として探した値ではありません。
どの値も設定項目にしません。

linux/amd64 の build で測った大きさは、c_conn が 4,864 byte、記録 1 件が 24 byte、区間 1 つが 12 byte、握手の途中の行が 80 byte、TIME_WAIT の行が 64 byte、hash の表の 1 項目が 24 byte です。
既定の K の 2048 では、Device の `Bound` が返す項の和は約 1,465 MiB です。
内訳は M_fix が約 21.6 MiB、floor の項が約 1,319.8 MiB、boost の項が約 123.7 MiB です。
区間の表は floor の項に約 7.2 MiB、boost の項に約 0.7 MiB を加えます。
M_fix は接続の枠、3 つの hash の表、行の表、空きの list、タイマーの節、出力の list、制御の輪、chunk の置き場に残す 1 MiB を数えます。
本番の大きさの表(K は 256)で 256 本の接続に floor いっぱいの受信のデータを持たせた試験では、生きているヒープの増加は約 83.8 MB で、会計が数えた chunk、記録、M_fix の和の約 84.7 MB に収まりました。
今のエージェントの上界の式では、カーネルモードの `vpsd` の後ろで、TCP の待ち受け 1 つごとに accept の待ち行列の項(約 1,790 MiB)が加わります([エージェントとホストのメモリの条件](memory-agent-host.md#accept-の待ち行列))。
wgstack の accept の待ち行列は Device 全体で Q 本なので、この式に待ち受けの数に比例する項はありません。

式は次のものを含みません。

- boost の取得と floor への戻りの間の一時の保持:送信と受信の輪は位置で中身を置くので、容量を変えるときに生きている範囲を新しい chunk へ写し、写す間は古い chunk と合わせて持ちます。
  写すのは boost の枠を得るか返す接続だけで、その接続の錠の中で行うので、同時に持つ量は B × (f_s + f_r) の 8 MiB 以下です。
  Device の `Bound` は、この量を式の和とは別の `Transient` として返します
- Go のランタイムの費用:GC が回収を待つ間の余裕、span の断片化、ランタイムの管理の構造です。
  RSS は生きているヒープより大きく、その係数は[フロー数とメモリのソフト上限](flow-limits.md)と[上界に含めない保持点](memory-limits.md)の数え方で扱います
- OS のソケット:LAN の宛先への TCP と UDP のソケット、WireGuard の UDP のソケットのバッファです
- wireguard-go:ピアと device のキュー、TUN の読み書きのバッファ、受信の包みの固定のバッファです([フロー数とメモリのソフト上限](flow-limits.md))
- 中継と `internal/netpipe`:コピーのバッファ、goroutine のスタック、セッションの表です
- 待ち受け 1 つあたりの小さな構造:待ち受けの数は信頼された設定で決まり、今の式でも外にあります([TCP のポートごとの待ち受け](memory-limits.md#tcp-のポートごとの待ち受け))

## 尽きたときの動作

どの資源も、尽きた時に新しい保持を拒み、既存の保持を追い出しません。
例外は TIME_WAIT の表と再組み立ての表の追い出しで、どちらも追い出した数を数えます。
数えた拒否は種類ごとに Device で数え、1 分に 1 回まで英語の 1 行をログに出します。
`wgft status`、管理用 API、wire protocol には載せません。

| 資源 | 尽きたときの動作 |
|---|---|
| 握手の途中の表 | 新しい SYN を、状態を作らずに捨てます。待ち受けの無いポート宛ての SYN には RST を返します |
| accept の待ち行列と接続の枠 | 握手の最後の ACK を捨てます。握手の途中の行は残り、SYN-ACK の再送の回数を使い切ると消えます。Linux の `tcp_abort_on_overflow=0` と同じ挙動です |
| 受信のバッファ | 窓を広げません。窓の外のデータは捨てて ACK で窓を知らせます。H 個を超える区間を作る順序外の segment は捨てます。H は受信の予約から決めるので、区間が尽きるのはバッファが満ちた後だけです |
| 送信のバッファと送信の記録 | `Write` はバッファに空きができるまで待ちます。記録の輪が満杯なら新しい segment を送らず、データは送信の輪に残ります |
| boost の枠 | floor のまま続け、次の需要の区間で求め直します |
| TIME_WAIT の表 | 最も古い行を外して新しい行を入れ、外した数を数えます |
| 再組み立ての表 | 今と同じく、同じ datagram 以外の最も古い未完成の項目を外し、1 つの datagram だけで満ちるときはその断片を捨てます([表が満杯のときの扱い](packet-validation.md#表が満杯のときの扱い)) |
| UDP の受信の予算 | datagram を捨て、ICMP を返しません。endpoint の上限と Device の予算の拒否を分けて数えます |
| UDP の送信の予算 | `WriteTo` は予約できるまで待ち、期限と `Close` で解けます |
| 制御の出力の輪 | 新しい制御の packet を捨てます。SYN-ACK、TCP の data と ACK はこの輪を使わないので影響を受けません。枠か行を返した後の RST を捨てても、相手の次の segment が RST を受けます |
| echo の endpoint の表 | `DialPing` が誤りを返します |
| challenge ACK と ICMP の速さの制限 | 速さを超えた分を送りません |

TCP の義務を果たせない時は、接続を安全に閉じます。
再送の回数を使い切った接続と、wgstack が自分の会計の不整合を検出した接続は、RST を送り、アプリケーションの読み書きに誤りを返します。
アプリケーションがすでに閉じた接続と、accept の待ち行列にいる接続は、その場で枠を返します。
アプリケーションがまだ接続を持つ間は、相手の RST を受けた接続と、枠に残って TIME_WAIT の期限を過ぎた接続と同じく、枠は CLOSED になります。
CLOSED の枠は 4 つ組の hash の表から外れ、送信の輪を返します。
アプリケーションの読み取りには、それまでに受けた順序どおりの未読のデータを返した後に、誤りか `io.EOF` を返します。
枠を返すのはアプリケーションの `Close` か `Abort` です。
この扱いは、閉じていない接続を枠に残す[行に移る条件](#行に移る条件)と同じ規則です。
中継はこの接続を K に数えるので、上界は変わりません。
データを黙って捨てて接続を続けることはしません。

## 不変条件と設計の対応

| 不変条件 | 設計の対応 |
|---|---|
| I1 有限 | 表はすべて作成の時の固定の容量で、バッファは予約の量までしか確保しません。上限は K と固定の定数から決まり、入力によりません |
| I2 保持の前の予約 | 接続の枠と floor は確立の時に、boost は枠の取得の時に、UDP の datagram は配送の前に予約します。予約できなければ前節の動作になり、代わりの置き場はありません |
| I3 所有 | 接続の枠、TIME_WAIT の行、握手の途中の行、chunk、datagram の枠は、それぞれ 1 つの表か 1 つの接続が持ち、作る条件と返す条件を前節までに定めます |
| I4 TCP の正しさ | 送信の輪は累積の確認まで中身を保持し、記録の輪の満杯は送信を止めるだけです。順序外のデータは、接続が開いている間、SACK を知らせた後は捨てません |
| I5 自己増殖の禁止 | タイマーの節は枠と行に固定で埋め込み、再送は既存の輪から segment を作り直すだけです。出力は待ち行列を持たず、`Read` の時に作ります |
| I6 制御できること | `Abort` は RST を送って即座に枠を返します。`Close` の後、未送信か未確認のデータを持つ接続は、届け終えるか再送の回数を使い切るまで枠に残り、使い切れば RST で終えて枠を返します。窓が 0 のまま probe に応える相手には、閉じた接続の probe を、応答で戻らない後退の回数が 8 以上で、後退を含めた RTO が上限の 120 秒に届いたときに打ち切り、RST で終えます。届け終えた接続の保持は TIME_WAIT の表の行だけです。Device の `Close` は待っている操作を `net.ErrClosed` で解き、すべての予約を返します |
| I7 隔離 | カーネルモードは wgstack を作らず、package の依存も持ちません。選択は明示で、既定は gVisor です |

## TCP の機能

### 完成に含める機能

参照の実装は Linux です。
規格が値を幅で定めるところは Linux の既定の値に合わせ、合わせない点は[期待した差](wgstack-verification.md#期待した差の一覧)に記録します。

- RFC 9293:受動の open からの状態の遷移、同時の close、segment の受け入れの判定、窓の更新の規則、送り手と受け手の SWS の回避、RST の処理、ハーフクローズ(`CloseWrite` で FIN を送った後も読み続けます)を持ちます。
  未読のデータを持ったまま閉じた接続は Linux と同じく RST で終えます。
  緊急のデータは、通常のデータとして扱い、知らせません
- RFC 6298:SRTT と RTTVAR から RTO を求め、再送ごとに倍にします。
  最小の RTO は Linux と同じ 200 ms、最大は 120 秒です
- RFC 7323:窓の scale、timestamp による RTT の測定、PAWS を持ちます。
  窓の scale は boost の 4 MiB を広告できる値を握手の時に決めます。
  広告する窓の欄は、窓の右端までの byte を scale で割って切り下げた値です。
  右端そのものは後ろへ戻さず、切り下げで右端が最大 2^scale - 1 byte 手前に見えることは窓の scale の性質として受け入れます。
  Linux は今の窓を切り上げて欄にします。
  読み手の止まった間に切り上げを繰り返すと、広告する右端が受信のバッファの外へ少しずつ伸びるので、wgstack は切り下げます。
  これは Linux との差で、[期待した差の一覧](wgstack-verification.md#期待した差の一覧)に入れるかは試験の書き手と所有者が決めます
- RFC 5961:窓の内側で番号が一致しない RST と確立後の SYN に challenge ACK を返し、ACK の受け入れの範囲を確かめます。
  challenge ACK の速さは Device 全体の token bucket で抑えます
- MSS:相手の MSS に従い、MSS の option の無い SYN では 536 を使います。
  入口の[MSS の下限](packet-validation.md#tcp-の-mss-の下限)と、Fragmentation Needed による PMTU の引き下げ(下限 552)を持ちます。
  自分が示す MSS は MTU から 40 byte を引いた値です
- 輻輳の制御:RFC 5681 の slow start と輻輳の回避、RFC 6582 の NewReno の高速の再送と回復を持ちます。
  初期の輻輳の窓は Linux と同じ 10 segment(RFC 6928)にし、黙った後の窓は RFC 5681 の 4.1 節に従って戻します。
  SYN か SYN-ACK を再送した接続の初期の窓は、RFC 5681 の 3.1 節と Linux と同じく 1 segment です
- SACK:握手で SACK を交渉し、受け手として区間の表から SACK の block を返します。
  D-SACK(RFC 2883)は返しません。
  送り手としては受け取った SACK の block を検査するだけで、回復には使いません。
  RFC 2018 は送り手が SACK の情報を使わないことを許すので、後の段階で送り手の側だけを足せます
- 窓の probe:相手の窓が 0 の間は persist のタイマーで probe を送り、相手が probe に応える間は打ち切りません。
  persist に入るときと persist の間の ACK で、再送の打ち切りを数える起点と RTO の後退を消します。
  前の RTO の起点が残ると、長い persist の後の最初の RTO で打ち切りの時間を過ぎたと数えるためです
- FIN と窓:FIN は番号を 1 つ使うので、Linux と同じく相手の窓に 1 byte の余地があるときだけ送ります。
  RFC 9293 の受け入れの判定では、窓が 0 の受け手は長さ 1 の segment を捨てるので、窓が 0 の間に送った FIN は届きません。
  窓が 0 の間は FIN を持ったまま窓の probe を続け、窓が開いてから FIN を送ります。
  中身の後ろに FIN を付けるのも、FIN の 1 が窓に入るときだけです。
  アプリケーションが閉じた接続の probe は、後退の回数が 8 以上で、後退を含めた RTO が上限の 120 秒に届いたときに RST で終えます。
  これは Linux の `tcp_probe_timer` が閉じた接続を打ち切る条件(`tcp_orphan_retries` の既定の 0 が表す 8 回と、生きていないことを表す RTO の後退の上限)と同じです。
  最小の RTO の 200 ms では、10 回目の probe を約 205 秒に送り、その後の 120 秒の期限で打ち切るので、打ち切りは窓が 0 になってから約 325 秒の後です。
  窓が開くと後退が戻るので、窓が 0 と小さな窓を行き来する相手には打ち切りません
  この後退は相手の ACK で戻らず、窓が開いたときだけ戻ります。
  打ち切らなければ、窓を 0 のまま probe に応える相手が、送れない FIN を持つ閉じた接続の枠をいつまでも持たせ、中継は `Delivered` まで K を持ち続けます。
  閉じていない接続の probe は、相手が応える間は打ち切りません
- 閉じた後の窓:`Close` の後も、広告する窓は閉じる前と同じ規則で決めます。
  Linux も `tcp_close` の後の segment の窓を `tcp_select_window` の通常の規則で決めると読めます。
  窓の右端は後ろへ戻さないので、閉じた時に広告済みの窓は縮められません。
  閉じた後に届く新しいデータには RST を返して接続を終えるので、窓が大きくても受信のバッファは増えません
- 遅延 ACK:Linux と同じく、MSS 2 つ分ごとか遅延の期限で ACK を返します
- Nagle:使いません。
  Go の `net.TCPConn` の既定の `TCP_NODELAY` と同じ扱いで、適合の試験の Linux の側にも同じ設定を与えます
- 再送の打ち切り:握手の後は Linux の `tcp_retries2`、SYN-ACK は `tcp_synack_retries` の既定の回数で打ち切ります
- ISN:RFC 6528 の鍵付きの hash で作ります。
  TIME_WAIT の 4 つ組を新しい SYN が使い直すときは、Linux と同じく ISN を前の接続の SND.NXT の 65537 先より前に置きません。
  前の接続の古い segment が新しい接続の番号の空間に入らないためです(RFC 1122 4.2.2.13)。
  待ち受けの握手の途中の行の取り分か表が満ちていて新しい行を作れないときは、TIME_WAIT の行と枠を外さずに SYN を捨てます。
  相手が再送した SYN も、行が残るので前の接続の番号の先から ISN を受けます。
  Linux は同じ順で行を外しますが、SYN cookie で応えるので番号を失いません。
  SYN cookie を持たない wgstack は、行を作れるときだけ TIME_WAIT を外します。
  開いた待ち受けが無いときは、Linux と同じく TIME_WAIT の ACK を返して行を残し、握手の途中の表の満杯には数えません。
  新しい握手の途中の行が後で RST か期限で消えると、前の接続の番号は残りません([未確認の点と未決の点](#未確認の点と未決の点))
- timestamp の offset:Linux の `secure_tcp_ts_off` と同じく、アドレスの組の鍵付きの hash から作ります。
  同じ相手との接続の TSval は接続を作り直しても増え続け、相手の PAWS が前の接続の segment を捨てられます

keepalive は、今の中継が無通信のタイムアウトを持たず([TCP の中継と終了](tcp-relay.md))、今の gVisor の接続も keepalive を使わないので、完成に含めません。
タイマーの節は枠に用意し、必要になった時に有効にします。
ECN は交渉しません。

### 後の段階の機能

次の機能は完成に含めず、性能の段階で加えます。

- SACK による損失の回復(RFC 2018、RFC 6675):送信の記録の輪の印を scoreboard にします。
  印を付けるのは SACK の block が全体を覆う記録だけです。
  ACK 1 つの印付けと次に送る segment の選択(RFC 6675 の NextSeg)は、前回の位置の手がかりを持って、送り残しの記録の数に比例しない手間に均します。
  均せない場合は、中身の無い ACK の予算([中身の無い ACK の予算](packet-validation.md#中身の無い-ack-の予算))を wgstack に戻すことを、その時に判断します
- RACK-TLP(RFC 8985):送信の記録の輪の送った時刻と、記録が今から持つ送った時刻の順の list の節を使います。
  最小の RTT を持つ欄は、RTT の推定の構造に今から置きます
- D-SACK(RFC 2883):受け手として返す側を加えます
- CUBIC(RFC 9438):輻輳の制御は、ACK、損失、RTO の 3 つの知らせを受ける interface の後ろに置き、NewReno をその最初の実装にします

次の機能は性能の目標とは別に、既定を gVisor から替える判断の前に要否を決めます。

- SYN cookie(RFC 4987):握手の途中の表が満杯の時に状態を持たずに応える仕組みです。
  gVisor と Linux はどちらも使うので、持たない wgstack は SYN の洪水の間の新しい接続の成功率が両者より低くなります。
  保持の上界には影響しません

## 未確認の点と未決の点

- 実際の量:c_conn、記録 1 件、表の 1 行の大きさは linux/amd64 の build で測りました([上界の式](#上界の式))。
  ほかの OS と CPU での大きさは未確認です
- 会計の不整合の検出:TCP の核は、自分の会計の不整合を検出して接続を閉じる検査を、まだ持ちません
- 使い直しの後の握手の失敗:TIME_WAIT の 4 つ組を使い直す握手の途中の行が RST か期限で消えると、前の接続の SND.NXT は残らず、相手の次の SYN は時計だけの ISN を受けます。
  期限で消えるのは SYN-ACK の再送を使い切った 63 秒の後で、TIME_WAIT の 60 秒を過ぎているので、前の接続の segment が網に残る危険は小さいと見込みます。
  RST で消えるのは相手が窓の内側の RST で自分の握手を終えたときで、その後 60 秒の内に同じ 4 つ組で SYN を送り直すと危険が残ります。
  行が消えるときに番号を短い間だけ覚える案は、表を 1 つ増やすので、この危険が実際に起きるかを確かめてから決めます。

- 初期の値:Q の 512、N_syn の 1024、M の 65,536 が通常の利用で足りるかは未確認です
- CPU:同期の入力と 2 段の錠で、CPU の目標(gVisor の 1.2 倍以内)を満たせるかは未確認です
- Windows と macOS:時計の分解能とスケジューラの違いが遅延 ACK と RTO に与える影響は未確認です
- 会計の不整合の知らせ方:wgstack が自分の会計の不整合を検出した時に、接続を閉じることに加えて `agent doctor` に示すかは未決です。

- 実装の見え方:どちらの実装で動いているかを `agent doctor` と制御ソケットに示すかは未決です。
  今の設計では起動ログだけで示します

- UDP の枠の大きさの区分:区分の大きさと、枠の大きさで数えたときに予算に入る datagram の数が通常の利用で足りるかは未確認です
- 閉じた後の再送の打ち切り:アプリケーションが閉じた後の接続の窓の probe は、Linux と同じく後退の回数が 8 以上で、後退を含めた RTO が上限の 120 秒に届いたときに打ち切ります([TCP の機能](#完成に含める機能)の FIN と窓)。
  再送を `tcp_orphan_retries` に合わせて早く打ち切るか、`tcp_retries2` のままにするかは未決で、今は `tcp_retries2` の時間の模型(924.6 秒)を使います。
  前者は中継の枠を早く返し、後者は今の gVisor の挙動([中継が終わった後の末尾の配送](tcp-retention.md#中継が終わった後の末尾の配送))に近いです
- 初期の輻輳の窓:RFC 5681 の値ではなく Linux と同じ 10 segment を選んだのは、参照の実装との差を減らすためです。

- floor に戻った後の回復:広告済みの右端が floor の先に残る間は、相手がその先へ送ったデータを捨て続けるので、回復は遅いままです。
  遅れの大きさは未確認です
- floor に戻った後の読み手の停止:広告済みの右端が floor の先に残る間に読み手が止まると、相手は窓の probe ではなく RTO の後退に入ります。

  移さずに写す案は、規則の正本が 2 つになるので採りません
- 中継の前提:中継とその試験が、前述の 4 点のほかに gVisor の挙動を前提にしているかは未確認です。

- 緊急のデータ:Linux の既定(`SO_OOBINLINE` を付けない)は緊急の 1 byte を stream から外します。
  wgstack はその byte を通常のデータとして渡すので、緊急のデータを使う相手では中継される byte の列が Linux と違います
- 拠点ごとの /16:待ち受けを集合のすべてのアドレスに束縛するか、アドレスごとに束縛するか、ping の送信元をどう選ぶかは、その機能の設計の時に決めます

### Linux との一致を確かめていない選択

実装の時に次の点を選びました。
どれも Linux で流した試験で確かめていないので、適合の試験の書き手が台本で狙えるように挙げます。
差が出たときに直すか期待した差にするかは、試験の書き手と所有者が決めます。

- MSS の値 0:MSS の option の値が 0 の SYN は、option が無いものとして 536 を使います。
  1 から 535 は入口の下限で捨てます
- SND.NXT より先を確認する ACK:RFC 9293 と RFC 5961 5.2 に従い、速さの制限の内側で ACK を返して捨てます。
  Linux は黙って捨てると読めます
- 再送の打ち切り:設計どおり RST を送ります。
  Linux の `tcp_write_err` は RST を送らないと読めます
- SYN-RCVD への別の番号の SYN:窓の内側なら RST を返して行を外し、窓の外なら ACK を返します。
  Linux の `tcp_check_req` を読んで選び、流していません
- quickack:接続の始めと黙った後も、遅延 ACK の規則で ACK します([参照の Linux の設定](wgstack-verification.md#参照の-linux-の設定)の外せない差)
- 握手の後の窓:最初の ACK から受信の floor の 256 KiB を広告します。
  Linux は約 64 KiB から広げます
- IP の ID:Device 全体の 1 つの数え上げを乱数の値から始めます。
  Linux はソケットごとに数え、SYN-ACK では 0 を使います
- 順序外のデータだけを持った `Close`:RST を送らずに FIN を送ります。
  FIN_WAIT_2 の接続は枠に残り、Linux の `tcp_fin_timeout` と同じ 60 秒の後に終えます。
  その間に相手が新しいデータを送れば RST で終えます
- 閉じた後の再送の打ち切り:再送は閉じていない接続と同じ `tcp_retries2` の時間の模型(924.6 秒)を使い、窓の probe だけを Linux と同じ条件で打ち切ります(前述の未決の点)
- 制御の組の配分:byte の deficit round robin で 1 回の番に MTU 1 つ分を使うので、MTU 1420 では中身の無い RST が 1 回の番で約 35 個出てから次の組に移ります
- challenge ACK の速さ:Device 全体の 1 つの token bucket で、1 秒に 1000 を基にした数までに抑えます。
  Linux 6.x の既定は全体の上限を `INT_MAX` にし、`tcp_oow_rate_limited` で接続ごとに 500 ms に 1 回までに抑えると読めます
- 待ち受けへの SYN と FIN の組:SYN と FIN の両方を持つ segment にも握手の途中の行を作ります。
  Linux はこの segment を捨てると読めます
- TIME_WAIT の 4 つ組の使い直し:前の接続が timestamp を使い、SYN が timestamp を持つときは、timestamp が大きいことだけを求めます([RFC 6191](#time_wait-の表))。
  Linux は番号か timestamp のどちらかが大きければ受け入れると読めます。
  適合の試験にこの場合の台本があります
- FIN_WAIT_2 の行への窓の内側の SYN:challenge ACK を返します。
  Linux は RST を返すと読めます
- 回復の終わりの後の RTO:累積の確認がちょうど `recover` に届いて NewReno の回復を終えた後に、余分な RTO が 1 回起きる場合があります。
  起きる条件と Linux の挙動は確かめていません
