# WireGuard のハンドシェイクの送信元の保持

[English](wireguard-sources.md)

このブランチは、ユーザー空間の WireGuard Device ごとに、送信元 IP の受付の閾値を既定で 1024 件とすることを提案します。
閾値と、上限で新しい送信元のハンドシェイクを失う挙動は、マージの前に製品の判断としてレビューします。
この制限は、wireguard-go を変更せず、Linux、Windows、macOS の server とエージェントに適用します。

## 受付と回復

外側のバインドは 1 回に 1 件の datagram を受け、148 byte の initiation と 92 byte の response だけを検査します。
固定した版の wireguard-go の制限の表は IPv4 と IPv6 を合わせた 1 つの map であり、検査はその実際の `sync.RWMutex` を使います。
キーには `StdNetEndpoint.DstIP()` の値を正規化せずに使います。
既存のキーは通し、表が 1024 件以上なら新しいキーを捨てます。
表のロックを取れない場合と、対象の endpoint の型を扱えない場合も、その対象の datagram だけを捨てます。
cookie reply、transport data、形が不正な packet、受信の誤りは、依存ライブラリの処理を保ちます。
この制限は packet を認証せず、WireGuard の暗号やトークンバケットを置き換えません。
送信元ごとの別の表や診断の履歴は持ちません。

上限では、新しいエージェントや公開 IP が変わったエージェントのハンドシェイクを失うことがあります。
既存の送信元からのハンドシェイクが続く場合、表の占有が続くことがあります。
表を更新するのは、負荷が高い状態で limiter の Allow に届くハンドシェイクだけです。
対象の入力が止まり、件数が有限の処理待ちが終わると、依存ライブラリの既存の GC が使われなくなった項目を消し、Device を作り直さずに受付が戻ります。
回復は scheduler とキューの進行を前提とし、一定時間内の回復や公平性は保証しません。

## 件数と実用上の見積もり

`C=1024`、ハンドシェイクのキュー `Q=1024`、構築時の worker 数 `W=runtime.NumCPU()`、動作中の受信関数の数 `R<=2` とします。
表のキーと、通した後で処理待ちにある送信元のキーを合わせた集合は、`H=C+Q+W+R` 件までです。
既存の送信元を通しても集合は増えません。
新しい送信元を通すときは表が C 件未満であり、表に無いほかの受付済みのキーは、有限の処理待ちに含まれます。
後の limiter の挿入は、処理待ちのキーを表に移すだけです。
GC による削除と作り直しも、超過の項を増やしません。
したがって、生きている表は H 件までであり、worker と GC が一時的に持つものを含む entry object は `H+W+1` 個までです。

実用上の見積もりとして、`64 KiB + 256*(H+W+1)` byte を提案します。
C1024、R2 では `64 KiB + 256*(2051+2W)` であり、W64 で約 609 KiB、W256 で約 705 KiB、W512 で約 833 KiB です。
係数は余裕を置いた設計上の見積もりであり、allocator の定理ではありません。
map の裏の領域、以前の拡張の確保、Go の GC の余白は、運用上の残る費用です。
この結果が抑えるのは送信元と entry の件数であり、どの環境でも 1 MiB に収まることや、プロセスの厳密な RSS の上限は保証しません。
BatchOne の内側にある未検査の datagram は、別に件数を抑えた受信の保持に数えます。

## 固定した版の観測とライフサイクル

読み取りだけの shim は、内側のバインドを開く前に、limiter、mutex、map の型の一致を検査します。
型を保つアドレスの reflection で実際の mutex を読み、mutex のコピーや依存ライブラリの非公開のフィールドへの書き込みは行いません。
map の件数とキーの有無は、1 回の成功した `TryRLock` の間に読みます。
扱えない構造では、観測せずに通すことを避け、構築を失敗にします。
Open は毎回、1 件の batch の契約と、1 本か 2 本の nil でない受信関数を検査します。

構築は、NewDevice が戻った後で、観測の準備の結果を公開します。
それより前に TUN の起動イベントが Open を呼びうるため、Open は結果を待ってから内側のバインドを開きます。
BindUpdate は最初の Open の前にも Close を呼ぶため、通常のバインドの Close は準備を取り消しません。
準備の失敗では、Device.Close の前に待っている Open を起こします。
管理付きの Close は、Device.Close が受信の関数の終了を待った後で、観測の参照を永久に外します。
Device.Close はハンドシェイクの worker の終了を待ちません。
終了した Device に残る有限の処理待ちは、別の寿命の項として数えます。
この制限だけでは、依存ライブラリの終了が panic しないことは示しません。

通常の入力を使う単体の fixture は、packet とキーの境界、実際の limiter のロック、上限と GC 後の回復、早い準備、開き直し、永久の参照の解放を確かめます。
各 OS の実行時の挙動と allocator の係数の十分性は未測定であり、各 OS 向けの静的な検査だけでは実行時の試験を置き換えません。
