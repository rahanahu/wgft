# WireGuard のハンドシェイクの送信元の保持

[English](wireguard-sources.md)

ユーザー空間の WireGuard Device は、wireguard-go のハンドシェイクの limiter のキーに、送信元 IP の代わりに `K=1024` 個の bucket のアドレスのどれかを使います。
このため limiter の表は、送信元の数や依存ライブラリが使われなくなった項目を消す時期にかかわらず K 件までです。
この仕組みは、Linux、Windows、macOS のユーザー空間モードの server とエージェントに同じく適用します。
wireguard-go の公開 API だけを使い、依存ライブラリは変更しません。

## bucket のキー

外側のバインドは、受信した 148 byte の initiation と 92 byte の response の endpoint を包みます。
wireguard-go の受信の経路がハンドシェイクのキューに入れるのはこの 2 種類の packet だけであり、limiter を呼ぶのはハンドシェイクの worker だけです。
包みの `DstIP()` は、`240.0.0.0/4` の中の K 個の合成のアドレスのどれかを返します。
アドレスは、送信元の鍵付きのハッシュで選びます。
ハッシュは `hash/maphash` で、seed は Device ごとの乱数です。
1 台のホストが /64 全体を持つことが多いので、IPv6 の送信元は /64 の prefix でハッシュします。
カーネルの WireGuard の limiter と同じ単位です。
IPv4 と IPv4-mapped IPv6 のアドレスはアドレス全体でハッシュし、両者を別の入力として扱います。
IPv6 の zone は使いません。
endpoint のほかの method は、受信した endpoint のものをそのまま使います。
MAC2 の検査と cookie reply が使う `DstToBytes()`、UAPI とログが使う `DstToString()`、`ClearSrc()` も含みます。

バインドの `Send` は、内側のバインドを呼ぶ前に包みを外します。
標準のバインドは `*conn.StdNetEndpoint` を前提にし、`DstIP()` で IPv4 と IPv6 のソケットを選ぶためです。
ハンドシェイクの後、ピアは包みを自分の endpoint として保存するので、そのピアへの送信はすべてこの処理を通ります。
合成のアドレスは予約済みの範囲にあり、送信先には使いません。

固定した版の wireguard-go では、Device が受信した endpoint の `DstIP()` を使うのは limiter のキーだけです。
Linux の経路の監視も `DstIP()` を読みますが、監視はバインドが `*conn.StdNetBind` のときだけ始まり、wgft のバインドはこの型になりません。
`go.mod` の wireguard-go の版が変わると単体テストが失敗します。
版を上げるときは、これらの使い方を確かめ直してから固定の値を変えます。

このバインドは packet を捨てず、送信元ごとの状態を持ちません。
transport data、cookie reply、形が不正な packet、受信の誤りは、依存ライブラリの処理を保ちます。
包みは packet を認証せず、WireGuard の暗号を置き換えません。

## 守る範囲と代償

Device が負荷の高い状態にないとき、依存ライブラリは limiter を使わないので、ハンドシェイクは影響を受けません。
負荷の高い状態でも、limiter に届くのは MAC1 と MAC2 がどちらも正しいハンドシェイクだけです。
MAC2 の cookie は本当の送信元のアドレスとポートに結び付くので、送信者はそのアドレスで cookie reply を受け取る必要があります。
この節の送信元は、IPv4 のアドレスか IPv6 の /64 を指します。
同じ bucket に入る送信元は、毎秒 20 回、一度に最大 5 回のトークンバケットを 1 つ共有します。

このため、ある送信元から MAC2 の正しいハンドシェイクを大量に送る者は、負荷の高い状態で、同じ bucket に入るピアのハンドシェイクを絞ります。
洪水の送信元が S 個のとき、あるピアが洪水と bucket を共有する確率は `1-(1-1/K)^S` で、S が小さければ約 `S/K` です。
対応は Device ごとの seed で決まり外から分からないので、送信者は送信元を増やす以外に特定のピアを狙えません。
すべての bucket を覆うには、応答を受け取れる IPv4 のアドレスか IPv6 の /64 がおよそ `K*ln(K)`、約 7,100 個要り、それぞれの bucket に毎秒 20 回を超えて送り続ける必要があります。
洪水のない bucket のピアは、遅れなくハンドシェイクを続けます。
受付の状態を持たないので、洪水が止まった後に回復を待つ状態もありません。
limiter は bucket ごとに毎秒約 20 回までしか通さないので、負荷の高い状態で limiter を通るハンドシェイクも、毎秒約 `20*K` 回と一度に通る分までに収まります。

## 件数と実用上の見積もり

ハンドシェイクのキュー `Q=1024`、構築時の worker 数 `W=runtime.NumCPU()`、動作中の受信関数の数 `R<=2` とします。
limiter の表は K 件までです。
worker が表の外に 1 つずつ持ちうる項目と、GC の処理が一時的に持つ項目を含めて、生きている entry object は `K+W+1` 個までです。
包みは 1 つあたり 48 byte の確保 1 回です。
この値は Linux の amd64 で測った 1 回あたりの byte 数です。
処理待ちのハンドシェイクが持つ包みは `Q+W+R` 個までです。
ピアが endpoint として保存する包みは、そのピアの前の endpoint と置き換わります。

実用上の見積もりには、`64 KiB + 256*(K+W+1) + 48*(Q+W+R)` byte を使います。
K1024、R2 では `64 KiB + 256*(1025+W) + 48*(1026+W)` であり、W64 で約 387 KiB、W256 で約 444 KiB、W512 で約 520 KiB です。
係数 256 は余裕を置いた設計上の見積もりであり、allocator の定理ではありません。
map の裏の領域、以前の拡張の確保、Go の GC の余白は、運用上の残る費用です。
この結果が抑えるのはキー、entry、包みの件数であり、プロセスの厳密な RSS の上限は保証しません。
BatchOne の内側にある未検査の datagram は、別に件数を抑えた受信の保持に数えます。
Device.Close はハンドシェイクの worker の終了を待たないので、終了した Device に残る処理待ちは別の寿命の項として数えます。
この設計だけでは、依存ライブラリの終了が panic しないことは示しません。
Device.Close はハンドシェイクがキューに残りうる間に limiter を閉じます。
その後の `Allow` が空の表に最初のキーを入れると、閉じた channel に送って panic します。

## 採らなかった方法

limiter の表を reflection で読む方法は、依存ライブラリの非公開のフィールドに依存します。
型を保ったまま意味が変わる更新を検出できません。
通した送信元を期限付きで持つ外側の集合は、公開 API から表を観測できません。
このため、上限は limiter の GC が期限内に項目を消すことに依存します。
新しい項目と、使われずにトークンが満ちた項目は `Allow` に同じ結果を返し、limiter の時計も差し替えられないので、トークンの試験では保持の時間が延びたことを検出できません。
この集合は MAC2 も検証できないので、応答を受け取れない偽装の送信者が集合を埋められます。
MAC1 の正しい packet だけを数えても、この問題は残ります。
MAC1 は送信元のアドレスに結び付かず、捕らえたハンドシェイクを偽の送信元から送り直せば MAC1 を通るためです。
この検査は最大 2 本の受信の goroutine で行うことになるので、initiation の形の packet の洪水がデータの受信を遅くします。
送信する cookie reply を追って MAC2 を推定する方法は、追跡の表に上限が要り、洪水でその表が埋まります。
ピアの現在の endpoint を集合から除く方法は、上限にピアの数が加わります。

## 確認の範囲

単体テストは、packet の大きさの境界、そのまま使う method、送信の前に包みを外すこと、200,000 個の送信元を入れ替えたときの K 件の上限、Device ごとの鍵、IPv6 の /64 ごとのまとめ方を確かめます。
実際の limiter では、洪水のない bucket のピアが通り、洪水と bucket を共有するピアが絞られることを確かめます。
並行のテストは、2 本の受信関数と送信を race detector の下で動かします。
実際の Device 2 台を IPv4 と IPv6 の loopback で向かい合わせ、ハンドシェイク、UAPI の endpoint、待ち受けのポートの変更を確かめます。
MAC1 の正しい initiation を大量に送り、実際の Device を負荷の高い状態にします。
そのうえで、cookie reply が本当の送信元に届くことを確かめます。
その cookie の MAC2 を付けた initiation を一度に 20 件送り、ハンドシェイクの処理に届くのが 1 件以上 10 件以下であること、つまり残りを limiter が捨てたことを確かめます。
上記の終了の競合があるので、Device を閉じる前にハンドシェイクの worker が処理を終えるまで待ちます。
race detector の下では、initiation を処理するまで洪水が Device を負荷の高い状態に保てないことがあり、その場合は失敗にせず skip します。
開発機では、受信の経路が増やす処理はハンドシェイクの datagram 1 件あたり約 34 ns で、ほかの datagram には確保がありません。
allocator の係数の十分性は未測定です。
