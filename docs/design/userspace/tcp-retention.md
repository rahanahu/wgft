# TIME_WAIT と中継後の netstack の保持

TIME_WAIT の数は一時ポートの範囲で制限されます。
送り残しを持って閉じた netstack 接続の数を抑える仕組みはありません。


`vpsd` が中継のためにエージェントの待ち受けへ dial した TCP の接続は、`vpsd` の側が先に閉じると、gVisor の TIME_WAIT(60 秒)の間、送信元のポートを宛先ごとに予約し続けます。
予約できるポートは gVisor の一時ポートの範囲の 49,536 個なので、宛先 1 つあたりの TIME_WAIT は 49,536 本以下です。
1 本は TIME_WAIT の間に約 10 KiB を持ち(測定)、宛先 1 つあたり約 0.5 GiB になります。
この量まで積むには、1 つの宛先へ毎秒約 826 本の新しいフローを 60 秒続ける必要があります。
ポートを使い切ると、その宛先への新しい接続だけが失敗し、他の宛先と既存の接続には及ばない。
このときクライアントに何が届くかは未確認です。
この量は受け入れ、上界の項として数える(2026-09-30、所有者の決定)。
一時ポートの範囲を狭めて宛先あたりの量を減らす案は採らなかった。
狭めると、通常の通信で `vpsd` の dial の失敗が約 3 倍に増えたためです。
この失敗は、宛先が先に閉じた接続がエージェントの側に TIME_WAIT の 4 つ組を残し、同じ 4 つ組を使う新しい SYN を gVisor が捨てることで起きる。
今の範囲でも、同じ失敗はより低い頻度で起きる。
この失敗は既知の制限として残します。

<a id="送り残しを持って閉じた-netstack-の接続"></a>
送り残しを持って閉じた netstack の接続は、中継が終わった後も残る保持点であり、wgft はその数を抑える仕組みを持ちません。
中継は、両方向が閉じたときと片方向が誤りで終わったときに、netstack の接続を通常の `Close` で閉じる([6.2 節](../vps/proxy.md#62-プロキシモード))。
gVisor は送信の向きを閉じるとき(`CloseWrite` か `Close`)、送信のキューの残りの後ろに FIN を置き、相手の FIN を受けていなければ FIN_WAIT_1 に、受けていれば LAST_ACK に移る。
FIN_WAIT_1 の間に相手の FIN が届くと CLOSING に移る。
`Close` は、受信のキューが空なら RST を送らない。
同時フロー数の枠は中継が終わった時点で返るので、この接続は K に数えません。
中継の書き込みが netstack の接続の送信で待つ間は、反対向きが誤りで終わるか、接続が RST で切られない限り、中継は終わらず、その接続は K に数えたまま残る。
反対向きが誤りで終わると、`Close` がこの待ちを解き、中継は終わる。
boost の枠を持っていた接続は、送ったデータが確認されるまで枠を返さないので、16 本に数えたまま残る(前述の[「TCP のバッファで保証しないこと」](tcp-buffers.md#tcp-のバッファで保証しないこと))。
枠を持たない接続は 16 本にも数えません。
中継の側から意図して切る経路(待ち受けを閉じるとき、接続元制限の変更で切るとき、プロキシモードの中継を切るときなど)は RST で切るので、この状態を作りません。
同じ経路は `vpsd` とエージェントのどちらの netstack にもあります。

この状態を終わらせる仕組みは無いと、コードから判断しています。
相手が受信の窓を 0 のまま zero window probe に ACK を返す限り、gVisor は送信を打ち切らない。
FIN_WAIT_1、CLOSING、LAST_ACK を期限で終わらせるタイマーは gVisor に無く、FIN_WAIT_2 の 60 秒の期限はこれらの状態に効きません。
wgft は netstack の接続に keepalive、user timeout、linger、再送の回数を設定しません。
相手が読み始めれば、接続は残りのデータを送りきって TIME_WAIT に移る。
1 本が持つ送り残しは、枠を持たない接続では送信の floor の 256 KiB を超えないとコードから判断しています。

VM を使わない 1 プロセスの Go の試験では、この状態の接続が観察を終えた 118 秒の時点まで残り、1 本が持つ送り残しは最大 213 KiB だった。
213 KiB はその試験の 1 本の値であり、全体の上限ではありません。

この保持は、前述の上界の式にも表にも、後述の[「上界の式に入れない」](memory-limits.md#上界の式に入れない)一覧にも入っていません。
前述のプロセスの上界はこの保持を含まない。
未確認:118 秒を超える保持、LAST_ACK に残る場合の再現、プロキシモードの中継での再現、トンネルの作り直しでこの接続が解放されるかどうか、gVisor の管理の構造を含めた 1 本あたりのメモリの量、接続の数の上限と多数の接続での合計の量。
