# TIME_WAIT と中継後の netstack の保持

TIME_WAIT の数は一時ポートの範囲で制限されます。
中継が終わった後も、末尾を届け終えるまでフローの枠を保持します。


`vpsd` が中継のためにエージェントの待ち受けへ dial した TCP の接続は、`vpsd` の側が先に閉じると、gVisor の TIME_WAIT(60 秒)の間、送信元のポートを宛先ごとに予約し続けます。
予約できるポートは gVisor の一時ポートの範囲の 49,536 個なので、宛先 1 つあたりの TIME_WAIT は 49,536 本以下です。
1 本は TIME_WAIT の間に約 10 KiB を持ち(測定)、宛先 1 つあたり約 0.5 GiB になります。
この量まで積むには、1 つの宛先へ毎秒約 826 本の新しいフローを 60 秒続ける必要があります。
ポートを使い切ると、その宛先への新しい接続だけが失敗し、他の宛先と既存の接続には及ばない。
このときクライアントに何が届くかは未確認です。
この量は受け入れ、上界の項として数える(2026-09-30、所有者の決定)。
一時ポートの範囲を狭めて宛先あたりの量を減らす案は採らなかった。
狭めると、通常の通信で `vpsd` の dial の失敗が約 3 倍に増えたためです。
この失敗は、宛先が先に閉じた接続がエージェントの側に TIME_WAIT の 4 つ組を残し、同じ 4 つ組を使う新しい SYN を gVisor が捨てることで起きる。
今の範囲でも、同じ失敗はより低い頻度で起きる。
この失敗は既知の制限として残します。

## 中継が終わった後の末尾の配送

ユーザー空間モードの中継は、書き込んだデータを相手が確認するまで、終わった組を同時フロー数の上限 K に数えます。
対象はエージェントの中継と、ユーザー空間モードの `vpsd` の Transparent の TCP と Relay のルールです。
`vpsd` の送信元ごとの枠も K と同じ期間保持し、組の資源を保持しなくなったときに両方を 1 回ずつ返します。
送信元ごとの枠を先に返すと、同じ送信元が上限を超えて末尾を残させ、K を埋められるためです。

中継は netstack の接続を通常の `Close` で閉じます。
gVisor は送信のキューの後ろに FIN を置き、相手の FIN を受けていなければ FIN_WAIT_1、受けていれば LAST_ACK に移ります。
FIN_WAIT_1 の間に相手の FIN が届くと CLOSING に移ります。
受信のキューが空なら `Close` は RST を送りません。
boost の枠を持つ接続は、送ったデータが確認されるまで 16 本にも数えます。
boost を持たない接続も K に数えるので、送り残しを持つ接続の数は K 以下です。
この保持は、[メモリの上界](memory-server.md#プロセス全体のメモリの上界)の TCP のフローの項に入ります。

届け終えたかは、接続の種類ごとに次の条件で判定します。

- netstack の接続: endpoint が CLOSED、ERROR、TIME_WAIT、または受信のメモリが 0 の FIN_WAIT_2 になったときです。
  TIME_WAIT と FIN_WAIT_2 では自分の FIN が確認され、送ったデータもすべて確認されています。
  FIN_WAIT_2 に受信のメモリが残る接続は、閉じる前に届いた順序外のデータを持つので、gVisor の 60 秒の期限で CLOSED になるまで K に数えます。
  固定版の gVisor は読み取りを閉じた後に届いたデータで接続を打ち切るので、閉じた後の受信のメモリは増えません(ソースで確認しました)。
  受信のメモリを読めない版では FIN_WAIT_2 を届け終えたとしません。
  エージェントが宛先への dial に失敗して閉じる接続にも、この条件を使います。
- Linux のカーネルのソケット:中継の終わりに、受信のメモリを `SO_MEMINFO` の `SK_MEMINFO_RMEM_ALLOC` で読みます。
  この値は受信のキューと順序外のキューを含みます。
  0 でないか読めなければ、`SetLinger(0)` と `Close` で RST を送り、即座に終えます。
  `SIOCINQ` は順序外のキューを数えず、通常の `Close` も順序外のデータだけでは RST を送らないため、両方ともこの判定には使いません。
  受信のメモリが 0 なら `shutdown(SHUT_RDWR)` で読み書きを止めて、送信のキューの後ろに FIN を置いたままプロセスが持ちます。
  判定から停止までの間に届いたデータを見落とさないように、停止の直後も受信のメモリを読み、0 でないか読めなければ RST で終えます。
  停止の後に届くデータには Linux が RST を返して CLOSE に移ります。
  読み取りは EOF を、書き込みは誤りを受け取るので、中継は期限を使わずに止まります。
  中継の写しが読みの期限を置き直して消すため、期限で止めません。
  送信のキューの量(`SIOCOUTQ`、自分の FIN を含みます)が 0、`TCP_INFO` の状態が CLOSE、またはソケットを読めなくなったときに届け終えたとし、閉じます。
  相手の RST と再送の打ち切りでは、送信のキューが残っても CLOSE になります。
  止めた読み取りは常に EOF を返すので、読み取りの失敗を配送の判定に使いません。
- 片方向の誤り:netstack の接続を先に閉じてから、カーネルのソケットを止めます。
  逆順では、もう一方の向きが EOF を受けて netstack に FIN を送り、RST より前に FIN が出る可能性があります。

組の中継の goroutine は終わりの直後に状態を調べ、その後は 50 ms から 2 秒まで間隔を倍に伸ばして見直します。
枠が返るのは、届け終えた後で最大 2 秒遅れます。
待ち受けと Manager の錠を持たずに待ち、新しい goroutine は作りません。
timer は待つ組ごとに 1 つで、K 以下です。
`Status.Flows`、管理用 API の `flow_budget.in_use`、送信元ごとの同時フロー数は配送中の組を含み、`Status.Sessions` は含みません。
Retiring の TCP の待ち受けは、末尾を届け終えるまで残ります。

ポートの削除、実効宛先の変更、`Manager.Close`、接続元制限の変更、Retiring の再判定は、配送中の組も切り、待ちを起こして枠を返します。
エージェントの watchdog がトンネルを作り直す経路も `Manager.Close` を通ります。
netstack は RST で切るので、残る末尾は失われます。
カーネルのソケットは通常の `Close` で閉じるため、送り残しを持つ孤児が 1 回の切断につき K 本まで残り得ます。

配送には期限を置きません。
受信の窓を 0 のまま zero window probe に応える相手は、K を占め続けられます。
応答を止めた相手は、gVisor の再送の打ち切りで ERROR、Linux の再送の打ち切りで CLOSE になり、枠が返ります。
打ち切りまでの時間はソースからは netstack が約 30 分、カーネルが約 15 分と読めますが、実際の時間は未確認です。
[短い障害の後の回復](../vps/userspace.md#63-ユーザー空間モード)を待つ間も K を持ちます。
以前のカーネルの孤児は probe の回数とメモリの圧迫で打ち切られましたが、今はプロセスが持つので、数を K 以下にする代わりにその打ち切りを受けません。
中継中のフローも読まない相手への送信のキューを無期限に持てるので、最悪の場合の保持時間は変わりません。

カーネルモードの `vpsd` の Relay の中継は、終わりに両側を閉じて枠を返します。
Windows と macOS のエージェントは LAN 側を終わりに閉じ、netstack だけを届け終えるまで K に数えます。
この 2 つの OS で送信のキューの量を確かめる手段は未確認です。
実際の利用で K の消費がどれだけ増えるか、LAST_ACK の再現、切断を繰り返したときにカーネルの孤児がどれだけ溜まるか、Windows と macOS の挙動も未確認です。
