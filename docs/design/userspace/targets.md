# 待ち受けの失敗と宛先の許可

待ち受けの失敗をルールの状態として報告し、宛先の許可一覧を適用します。
ブロードキャストとマルチキャストの宛先は、許可一覧の設定にかかわらず拒否します。


- TCP の待ち受けの accept と UDP の待ち受けの読み取りが、待ち受けを閉じた場合以外の理由で失敗したときは、[6.3 節](../vps/userspace.md#63-ユーザー空間モード)の `vpsd` の中継と同じ部品なので同じく試し直し、ルールの状態は変えません。
  エージェントの待ち受けは netstack の上にあり、gVisor の TCP の `Accept` が誤りを返すのはエンドポイントが待ち受けの状態でないときだけです。
  中継自身が待ち受けを閉じた場合は試し直さずに終える。
  それ以外にエージェントで TCP の試し直しに至る経路は見つかっていません。
  エージェントの UDP の待ち受けは接続していない netstack のエンドポイントで、読み取りが誤りを返すのは、読みの期限(中継は設けない)、受信が閉じたこと(`Close`、`Shutdown`、stack の `Close`)、ICMP などで立つ直前の誤りだけです。
  直前の誤りは、接続したエンドポイントでしか立たない。
  このため UDP も、中継自身が待ち受けを閉じた場合を除いてこの試し直しに至らない(gVisor v0.0.0-20250503011706-39ed1f5ac29c のソースで確かめた。
  [以前の検証 2026-09-24](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L744))
- TCP の待ち受けを開いたときは、`target` へ 1 回だけ試し接続し、すぐ閉じる(`internal/dataplane/userspace/relay` の `checkTarget`)。
  繋がらない宛先を、フローが来る前にルールの `error` として報告するためです。
  宛先からは中身の無い接続 1 本に見える。
  UDP は送信だけでは到達を確かめられないので行いません
- `vpsd` からの PROXY protocol ヘッダは中身を見ずに素通しします
<a id="宛先の許可一覧"></a>
- 宛先の許可一覧:エージェントは、接続してよい宛先の一覧を `WGFT_AGENT_ALLOW_TARGETS` で受け取る([11a 節](../security/configuration.md#11a-設定の渡し方))。
  一覧があるとき、中継は一覧に入らない宛先へ接続しません。
  判定は、TCP の接続 1 本ごとと UDP のセッション 1 つごとに、実際に接続するアドレスと実効宛先のポートに対して行います。
  `target` がホスト名のときの名前解決の結果も判定の対象なので、DNS の変更で一覧の外へ向かうことはありません。
  一覧があるとき、中継はホスト名の `target` を自分で解決し、一覧が通すアドレスだけへ接続します。
  判定したアドレスそのものへ接続するので、判定と接続の間に名前を引き直すことはありません。
  通したアドレスの試し方は、一覧が無いときに使う Go の接続(`net.Dialer`)に合わせる。
  TCP では、解決の結果の先頭のアドレスと同じ族のアドレスを先に試す。
  300 ミリ秒のうちに繋がらなければ、もう一方の族のアドレスも並行して試し始め、先に繋がった接続を使います。
  同じ族の中では解決の結果の順に 1 つずつ試し、接続の期限の 10 秒の残りを、まだ試していないアドレスの数で分ける。
  1 つのアドレスの持ち分は 2 秒を下回らない。
  UDP は族を分けずに順に試す。
  Go の接続と違い、接続の期限は名前の解決の後から数え、名前の解決には別に 5 秒の期限を持ちます。
  通したアドレスへの接続がすべて失敗した場合は、解決の結果の順で最後に試したアドレスの誤りを返します。
  一覧が通すアドレスが 1 つも無い場合は、最初に拒んだアドレスの理由を返します。
  この試し方の前は、通したアドレスを解決の結果の順に 1 つずつ、それぞれ 10 秒の期限で試していました。
  黙って捨てる IPv6 のアドレスが先に並ぶ名前では、接続に 10 秒かかり、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の 2 秒の接続確認がそのルールを `error` にしえた([以前の検証 2026-10-03](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L747))。
  `target` が IP リテラルのルールは適用のときにも判定し、一覧の外にあればそのポートの待ち受けを開かず、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)のルールの `error` として理由を報告します。
  収束の単位はポートなので、判定もポートごとに行います。
  ポートの範囲を持つルールで、範囲の一部のポートの実効宛先だけが一覧の外にある場合は、そのポートの待ち受けだけを開かず、範囲の他のポートは転送を続け、ルール全体は `error` として報告される。
  `target` がホスト名のルールの待ち受けは開き、接続のときに拒みます。
  拒んだ TCP の接続は RST で終え、UDP のデータグラムは捨て、リスナーごとに 1 分に 1 回までログに出す。
  [10.1 節](../interface.md#101-web-ui)の疎通確認は、エージェントの中継を通って宛先へ接続する経路なので、同じ一覧に従います。
  一覧が無いときは制限しません。
  狭める経路は、VPS を奪った攻撃者が `target` を書き換えてエージェントを自宅の LAN への踏み台にする経路である([11 節](../security/admin-transport.md#11-セキュリティ))
<a id="ブロードキャストとマルチキャストの宛先"></a>
- ブロードキャストとマルチキャストの宛先:エージェントは、ブロードキャストとマルチキャストのアドレスへ転送しない(2026-10-03、所有者の決定)。
  拒むのは、全域のブロードキャストのアドレス `255.255.255.255`、IPv4 のマルチキャストのアドレス(`224.0.0.0/4`)、IPv6 のマルチキャストのアドレス(`ff00::/8`)と、エージェントのホストの帯のブロードキャストのアドレスです。
  ユーザー空間モードの中継は IPv6 のアドレスを書いた宛先の待ち受けを開かないので、IPv6 のマルチキャストのアドレスはホスト名の解決の結果にだけ現れる。
  帯のブロードキャストのアドレスは、ホストのインタフェースの IPv4 のアドレスとプレフィクス長から求めます。
  プレフィクス長が 30 以下の帯の末尾のアドレスがこれに当たる。
  `/31` と `/32` の帯には帯のブロードキャストのアドレスが無いので、`/31` の両端のアドレスは拒まない。
  末尾が `.255` のアドレスでも、ホストのどの帯の末尾でもなければ拒まない。
  たとえば `/23` の帯の中ほどにある `.255` のアドレスはホストのアドレスとして扱う。
  インタフェースの一覧は、読んでから 5 秒の間は読み直さずに使います。
  一覧を読めなかった場合は、帯のブロードキャストのアドレスかどうかを判定できないので、その判定だけを行わずに転送し、読めなかったことと再び読めたことをログに 1 行ずつ出す。
  全域のブロードキャストとマルチキャストの判定は一覧に依らないので、この場合も拒みます。
  判定の単位と報告は宛先の許可一覧と同じです。
  `target` が IP リテラルのルールは適用のときに判定し、該当すればそのポートの待ち受けを開かず、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)のルールの `error` として理由を報告します。
  `target` がホスト名のルールは、TCP の接続 1 本ごとと UDP のセッション 1 つごとに名前解決の結果のアドレスで判定し、該当するアドレスへは接続しません。
  解決の結果にほかのアドレスがあれば、そちらへ接続します。
  どのアドレスへも接続しなかった場合の扱いは、許可一覧で拒んだ場合と同じです。
  この判定は許可一覧の有無に依らない。
  許可一覧があるときは、中継が自分で解決したアドレスを判定します。
  許可一覧が無いときは、中継はこの判定の導入の前と同じく宛先を名前のまま Go の接続に渡し、Go の接続が解決した各アドレスを、ソケットを作ってから接続する前に判定する(`net.Dialer` の `Control`)。
  名前の解決、TCP で IPv6 と IPv4 のアドレスを少しずらして並べて試すこと、接続の期限をアドレスの間で分けることは、ユニキャストの宛先では導入の前と変わりません。
  理由の文言は 2 つのモードで同じであり([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い))、`server doctor` はこれを `target_not_unicast` に分類する([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))。
  拒む理由は 2 つあります。
  カーネルモードでは、帯と全域のブロードキャストへ向けた DNAT のパケットは LAN へ出ず、エージェントのホスト自身の待ち受けに届いた(ラボで確認)。
  公開したポートの外にあるホスト自身の待ち受けへの経路になります。
  IPv4 のマルチキャストへ向けた DNAT のパケットは、LAN のグループにもホスト自身のグループの待ち受けにも届かなかった(ラボで確認)。
  ユーザー空間モードでは、この変更の前は、全域のブロードキャスト、帯のブロードキャスト、IPv4 のマルチキャストのどの宛先へも UDP のデータグラムが送られ、LAN のホストに届いていた(ラボで確認)。
  VPS を奪った攻撃者は、1 つのルールで LAN のすべてのホストかマルチキャストのグループへ届けられる。
  Wake-on-LAN のマジックパケットをブロードキャストへ送る宛先は、どちらのモードでもサポートしません。
  ユーザー空間モードでは、この変更の前はそのようなパケットが LAN に届いていた可能性があり、この変更がそれを止めます。
  マジックパケットとそれを受ける機器では確かめておらず、この変更の前に機器を起こしていたかは未確認です。
  Wake-on-LAN の機能が必要になれば、別に設計します。
  エージェントを Docker のブリッジのネットワークのコンテナで動かす場合(`deploy/agent.compose.yaml` の既定)、帯のブロードキャストの判定に使うインタフェースはコンテナ自身のネットワークのものです。
  LAN の帯のブロードキャストのアドレス(たとえば `192.168.50.255`)は、その帯のインタフェースをコンテナが持たないので、帯のブロードキャストとしては拒まない
