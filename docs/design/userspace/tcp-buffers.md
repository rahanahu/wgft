# netstack の TCP バッファ

TCP のバッファは floor と、需要のある接続が取得する boost の枠で制限します。
資源の上限は、最低速度や遅延の上限を保証しません。


<a id="netstack-の-tcp-のバッファ"></a>
- netstack の TCP のバッファ:netstack の TCP の接続は、送信と受信のバッファの大きさに上限を持つ(2026-09-30、所有者の決定)。
  全接続に小さな最低分(以下 floor。
  送信 256 KiB、受信 256 KiB)を保証し、大きなバッファ(以下 boost。
  送信と受信のどちらも 4 MiB)は、プロセスあたり同時に 16 本の接続までの枠で貸す。
  `vpsd` もエージェントもプロセスで 1 つの枠の集まりを持ち、トンネルを作り直しても数は変わりません。
  `vpsd` のユーザー空間モードでは、全エージェントへの接続が同じ 16 本を分け合う。
  `vpsd` とエージェントの枠は別々であり、1 本の接続の両端の予約を調停しません。
  片側だけが枠を得た接続の速さは、得ていない側の floor で決まる。
  値はどれも設定項目にしません。
  4 MiB は gVisor の既定の自動調整の上限と同じ値です。
  以前はバッファを gVisor の自動調整に任せていました。
  送信のバッファの上限は受け入れた byte だけを数え、書き込み 1 回ごとに gVisor が持つ管理の構造を数えないので、読まない相手へ 1 byte の書き込みを繰り返すと、接続 1 本の保持が byte の上限を大きく超えて増えた
<a id="書き込みの数の上限"></a>
- 書き込みの数の上限:接続が送信のキューに持つ書き込みの数を、送信のバッファ 1 KiB あたり 1 回に抑えます。
  floor では 256 回、boost では 4096 回です。
  byte の上限だけでは前項の保持を抑えられないためです。
  wgft の接続は gVisor に書く前に、送信のキューに残る byte が、直前の 255 回(boost では 4095 回)に受け入れた長さの和より少ないことを確かめる。
  確かめ方は、送信のバッファをその和に設定し、書き込める状態かを見て、設定した値を読み返すことです。
  送信のキューは送った byte の列の末尾なので、この条件が成り立てば、それより前の書き込みはすべて相手が確認しており、キューに残る書き込みは今回の 1 回を含めて上限以内になります。
  成り立たなければ、書き込める状態になるまで待つ。
  そのため wgft の接続は `gonet.TCPConn` の書き込みを使わず、書き込みの期限と、`Close` による待ちの解除を自分で持ちます。
  長さの履歴は、boost を持たない間は直前の 255 回分を持ち、boost を得たときに 4095 回分に広げ、boost を返すと 255 回分に戻します。
  広げた直後の、覚えていない古い長さは 0 として数えます。
  和を小さく見積もるので、条件は成り立ちにくくなる側にだけずれ、上限は崩れない
<a id="boost-を求める条件"></a>
- boost を求める条件:読み取りと書き込みのどちらかの向きで、250 ms の区間に 64 KiB 以上を実際に読めたか gVisor が受け入れた接続は、枠を 1 つ求めます。
  区間は入出力が成功したときに時計を読んで区切り、タイマーは使いません。
  枠は 1 本の接続の両方の向きに 1 つです。
  空きの枠が無く、後述の返せる枠も回収できる枠も無いときは、待たず、切らず、floor のまま続け、次の区間で条件を満たしたときに求め直す。
  boost を得た接続は、受信のバッファをその場で 4 MiB にし、送信のバッファを次の書き込みで 4 MiB にします
<a id="握手と-floor-の設定"></a>
- 握手と floor の設定:Device は、TCP の endpoint を 1 つも作る前に、gVisor の stack に送信の範囲(既定と上限が 256 KiB)と受信の範囲(既定 256 KiB、上限 4 MiB)を設定します。
  設定に失敗したら stack を閉じ、Device を作りません。
  受信の上限を 4 MiB にするのは、gVisor が握手のときの受信の窓の scale を受信の上限から決めるためです。
  握手を終えた接続には、`Accept` と `DialTCP` が呼び出し側へ返す前に、floor を固定の値として設定して読み返します。
  固定すると gVisor の自動調整が止まります。
  握手の前に固定すると、窓の scale が floor から決まり、後で boost を得ても広い窓を広告できません。
  gVisor は受信のバッファを接続の読み取りのときにだけ自動で広げるので、最初の読み取りの前に固定すれば、枠の外で広がることはありません。
  SYN cookie で成立した接続も gVisor の `Accept` から同じ経路を通ることは、ソースで確かめた。
  この経路を通る SYN cookie の接続は試験していません。
  `DialTCP` は `gonet` の dial を使わず、endpoint を自分で持って接続し、取り消しと失敗のどの出口でも endpoint を 1 回だけ閉じます。
  floor を設定できなかった接続は、`Accept` では RST で閉じて次の接続を待ち、`DialTCP` では RST で閉じて誤りを返します
<a id="枠を返す時機"></a>
- 枠を返す時機:接続の最後の `Close` か `Abort` が戻り、その接続の読み取りと書き込みが実行中でなく、endpoint が CLOSED か ERROR、または TIME_WAIT で受信のキューが空のとき、その枠は返せる。
  返すのは、空きの無い枠の集まりへの取得の要求が枠を調べるときです。
  枠を返すためのタイマーと goroutine は持ちません。
  TIME_WAIT を返せる状態に含めるのは、固定版の gVisor が、自分の FIN が確認されたときにだけ TIME_WAIT に入り、相手の FIN を受けたときに順序外の受信のキューを捨て、読み取りを閉じた後に届いたデータでは接続を中断するためである(ソースで確かめた)。
  TIME_WAIT の接続が送った byte は、すべて確認済みです。
  受信のキューが空という条件は、固定版の gVisor では `Close` が受信のキューを捨てるので常に成り立つ。
  gVisor の更新でこの性質が変わっても、返した枠の後に受信のデータを残さないために置いています。
  FIN_WAIT_2 は返せる状態に含めません。
  `Close` の前に届いた順序外の受信のデータが残りうるためです。
  FIN_WAIT_2 の接続は、gVisor の期限(既定で 60 秒)の後に CLOSED になってから返せる
<a id="需要の無い保有者からの回収"></a>
- 需要の無い保有者からの回収:取得の要求は、空きの枠も返せる枠も無いときだけ、1 秒の間どちらの向きにも前述の条件を満たしていない保有者を探し、1 本を floor に戻して枠を受け取ります。
  戻す手順は次のとおりで、どれかが成り立たなければ、その保有者のバッファを boost の大きさに戻して枠を持たせたまま、次の保有者を見る。
  書き込みが実行中の保有者は戻しません。
  書き込みは待つ間も書き込みの排他を持つので、この排他を待たずに取れなければ見送る。
  受信は、バッファを先に floor に縮め、その後で endpoint が受信の segment に使っているメモリが floor 以下であることを求めます。
  このメモリは、読まれていない受信のキューの segment、順序外の segment、処理を待つ segment を含む。
  gVisor は、データのある segment を、このメモリが受信のバッファ以下のときだけ受け入れる。
  順序外のデータが floor を超えたまま縮めると、穴を埋める再送も受け入れられず、正常な相手でも接続が止まる(単体テストで再現した)。
  floor 以下で縮めた後に新しく順序外に積めるのは、gVisor の規則(順序外の byte と segment の長さの和が受信のバッファの 3/4 未満)の分だけです。
  このため、処理を待つ segment が処理されれば、このメモリは floor 以下に戻り、穴を埋める segment は大きさによらず受け入れられる。
  gVisor はこのメモリを公開しないので、wgft は endpoint の非公開のフィールドを読みます。
  読むだけで書きません。
  フィールドの名前と型は起動時に確かめ、go.mod の固定の版と合わなければ回収をしません。
  合わないことは 1 回だけログに出す。
  gVisor の更新でフィールドが変われば単体テストが落ちる。
  gVisor の内部に依存する代わりに、公開の TCP probe で全 segment の状態を写す方法と、回収をやめる方法があるが、前者は全 TCP の費用が大きく、後者は通常の利用の性能の退行を戻すので採らなかった(2026-09-30、所有者の決定)。
  送信は、キューに残る byte が floor と直前の 255 回の書き込みの長さの和の小さい方より少ないことを、書き込みと同じ方法で確かめる。
  成り立てば、floor の byte と書き込みの数の上限がその時点から成り立つ。
  送信の向きを閉じた(`CloseWrite`)保有者は戻しません。
  固定版の gVisor は、送信を閉じた endpoint を、キューにデータが残っていても書き込める状態と答えるので、送信の確かめが何も示さないためです。
  中継は片方向の EOF を `CloseWrite` で伝えるので、相手が読むのを止めた転送の後に起こる。
  このような保有者は、返せる状態になるまで枠を持ちます。
  floor に戻った接続は、需要が戻ると枠を求め直す。
  1 秒は、転送を終えて開いたままの接続が boost を持ち続けて後続の転送を floor に留めないための値であり、最適値として探した値ではありません
<a id="tcp-のバッファの上界"></a>
- TCP のバッファの上界:boost の分は、プロセスあたり 16 本 × (送信 4 MiB + 受信 4 MiB) の 128 MiB を名目の上限とし、floor を超える増分は 120 MiB です。
  floor の分は接続 1 本あたり送信 256 KiB と受信 256 KiB で、書き込みの数は 256 回、長さの履歴は 1 KiB です。
  boost を得た接続は書き込みを 4096 回まで持ち、長さの履歴は 16 KiB になります。
  byte の値はバッファが数える量であり、Go のヒープの上限ではありません。
  書き込み 1 回ごとに gVisor が持つ管理の構造と、受信の segment の管理の費用は、書き込みの数と segment の数に応じて byte の外にかかる。
  TCP のバッファの仕組みは接続の数を抑えない。
  プロセス全体の TCP のバッファの量は、接続の数に floor を掛けた量と boost の分の和で抑えられる。
  接続の数には、同時フロー数の上限が数える中継の接続のほかに、accept の待ち行列の接続と、閉じた後に TIME_WAIT などで残る接続と、送り残しを持って閉じた接続が入ります。
  accept の待ち行列と TIME_WAIT の数の上限は、後述の[「プロセス全体のメモリの上界」](memory-server.md#プロセス全体のメモリの上界)の段落に書きます。
  送り残しを届けている途中の接続も K に数えます([中継後の配送](tcp-retention.md#中継が終わった後の末尾の配送))。
<a id="tcp-のバッファで保証しないこと"></a>
- TCP のバッファで保証しないこと:floor と boost は資源の上限であり、最低の速さも遅れの上限も保証しません。
  17 本目以降の同時の転送は、需要のある 16 本が枠を持つ間 floor のまま進む。
  相手が読まない保有者は、送信のキューが floor の確かめを通らないので回収されず、枠を持ち続けます。
  接続を閉じても、送ったデータが確認されるまでは返りません。
  1 秒を超えて間の空く転送は、その間に枠を回収されうるので、再開のたびに floor から始まることがあります。
  回収した接続の受信のメモリは、回収の時点で floor 以下であることを確かめてあります。
  その後は、処理を待つ segment が一時的に floor を超えさせることはあるが、処理が済めば floor 以下に戻る。
  穴を埋めない相手は、順序外のデータを floor 以下の量で持たせ続けられる。
  順序外が floor を超えている保有者は回収しないので、その保有者は枠を持ち続けます。
  枠は、返すまで閉じた接続を参照します。
  取得の要求が来なければ最大 16 本の閉じた接続が残り、トンネルを作り直した後なら古い Device の stack も GC されずに残る。
  取得の要求は、枠の写しを調べる間も写しに載る接続を参照し、この参照は要求が戻ると消える。
  Windows と macOS のエージェントでの速さは確かめていません
