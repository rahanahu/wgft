# UDP の中継と応答のバッファ

UDP の中継は送信元の組ごとにセッションを持ち、無通信の期限で閉じます。
応答のバッファと公開側の送信にも独立した予算を設けます。


- ルールの各ポートごとにリスナーを netstack 上に開き、LAN 内の `target` へ自分で接続して中継します
- エージェントから見た送信元は VPS の masquerade により常に `10.200.0.1` で、フローは送信元ポートで区別される。
  したがって全ルール共通の UDP 同時フロー上限は約 64k になります
- UDP は `(送信元 IP, 送信元ポート)` の組ごとにセッションを持ち、無通信が全体状態の `udp_timeout_stream` 続いたら閉じます。
  VPS の conntrack は assured になる前のフローを `udp_timeout`(既定 30 秒)で消すので、数パケットで終わるフローではエージェント側に死んだセッションが最長 90 秒残る。
  害は小さいので、この非対称は許容します。
  セッション数の上限は後述の「同時フロー数の上限」に従い、超えた新規パケットは捨てます。
  宛先からの応答を待つ間、セッションは読み取りバッファを持ちません。
  データグラムの到着だけを先に待ち、届いてから共有プールの 65535 バイトのバッファを借りて全体を読み、公開側へ送り終えたら返します。
  したがって応答の大きさによらずデータグラムは欠けない。
  共有プールが同時に貸すバッファの数はプロセス全体で 64 個までであり、その意味は後述の[「応答のバッファの枠」](udp-relay.md#応答のバッファの枠)の項に書きます。
  到着を待つ手段は、カーネルのソケット(エージェントの宛先側)では、Unix は 1 バイトの `MSG_PEEK`、Windows はゼロバイトの `WSARecv`(`MSG_PEEK` 付き)をオーバーラップ I/O で発行し完了通知で待つ(Go ランタイムの `RawRead` が行います。
  スレッドは塞がない)。
  netstack の接続(`vpsd` のエージェント側)ではエンドポイントの待ち行列(`waiter.Queue`)です。
  wireguard-go の `tun/netstack`(`netstack.Net`)は stack を公開しないため、エージェントと `vpsd` はどちらも netstack と TUN の接続部分を写して自前で持つ共通の内部パッケージ(`internal/nettun`)を使います。
  stack への直接アクセスは、`vpsd` はこの `waiter.Queue` のため、エージェントは後述の TCP の拒否のために、それぞれ要る。
  この 3 つ以外の GOOS のエージェントでは到着だけを待つ手段を使わず、セッションごとに 65535 バイトを持ち続けます。
  2026-09-18 までは Windows を含む全セッションが 65535 バイトを保持し、上限いっぱいの 4096 セッションがルール 1 本で約 292 MiB になっていた(改訂の記録 2026-09-18 の実測)。
  macOS のエージェントは、宛先へのカーネルのソケットを開くたびに送信バッファ(`SO_SNDBUF`)を 65535 バイトに上げる。
  macOS の UDP の送信バッファの既定は `net.inet.udp.maxdgram` の 9216 バイトで、これを超えるデータグラムの書き込みは `EMSGSIZE` で失敗するためです。
  BSD 系のカーネルは UDP の送信バッファにデータを溜めず、この値は 1 個のデータグラムの最大長として効くだけなので、上げてもセッションごとのメモリは増えません。
  Linux の既定(約 208 KiB)は 65535 バイトより大きいので変えません。
  netstack の接続も変えません。
  宛先への書き込みが失敗したらセッションを閉じ、そのことをリスナーごとに 1 分に 1 回までログに出す
<a id="応答のバッファの枠"></a>
- 応答のバッファの枠:宛先からの応答を読むバッファは、プロセス全体で同時に 64 個(4 MiB)までしか貸さない。
  `vpsd` もエージェントもプロセスで 1 つの枠の集まりを持ち、エージェントがトンネルを作り直しても数は変わりません。
  上限がかかるのは同時に貸し出しているバッファの数であり、借りている分の保持はこの数 × 65535 バイトを上限に持ち、セッション数、ルールの本数、OS によらない。
  返されて誰も借りていないバッファは共有プールが一時的に持ち、GC が回収します。
  以前はセッションごとの goroutine が上限なしに借りられたので、この保持の上限はセッション数に比例していた(改訂の記録 2026-09-27)。
  枠が無いセッションは、枠が空くか、そのセッションか待ち受けが閉じるまで待つ。
  待つ間、応答のデータグラムは宛先側の接続の受信のキュー(`vpsd` では前述の UDP の受信の予算の中の endpoint のキュー、エージェントではカーネルのソケットの受信バッファ)に留まるので、この待ちでデータグラムは失われない。
  待ちの間に届く新しい応答は、それぞれのキューの既存の上限が捨てます。
  枠を持つ間の仕事は、バッファへの読み取り 1 回と公開側への送信の試み 1 回だけです。
  `vpsd` は後述の[「公開側への応答の送信」](udp-relay.md#公開側への応答の送信)のとおり公開側で待たないので、`vpsd` では 1 つの待ち受けの詰まりが枠を持ち続けることはありません。
  エージェントの公開側の送信が待つ条件は同じ項の末尾に書きます。
  待つセッションはフローの予算(後述の「同時フロー数の上限」)を持ったまま待つが、枠の保持がこの短い区間に限られるので、待ちもその範囲に収まる。
  待ちを取り消すのは、待ち受けを閉じたとき(ルールの削除と無効化、`vpsd` とエージェントの停止)と、セッションを閉じたとき(無通信、接続元制限の変更による sweep)です。
  ルールごとや待ち受けごとに枠を分けない。
  分けると上限が待ち受けの数に比例するためです。
  64 は設定項目にしません。
  この値は、通常の負荷で正常な通信が枠を待つ時間が利用者に意味を持たないことをラボで確かめて採った値であり、この数までなら安全という保証の数ではありません。
  枠の待ちは回数と時間を内部で数えるだけで、ログ、`wgft status`、Web UI、wire protocol、管理用 API には出さない。
  セッションの終了で取り消された待ちは回数だけを数え、時間の合計と最長には入れません。
  無通信で閉じたセッションの長い待ちが最長の観測値にならないためです。
  到着だけを待つ手段を持たない GOOS(unix でも Windows でもない)のエージェントは、セッションごとに持ち続けるバッファを枠の外で使うので、この上限はその GOOS には当てはまらない
<a id="公開側への応答の送信"></a>
- 公開側への応答の送信:`vpsd` のユーザー空間モードは、公開側のホストのカーネルの UDP ソケットへ応答を 1 回だけ送ろうとします。
  ソケットの送信バッファが満杯(`EAGAIN`)なら、そのデータグラムを捨てて枠を直ちに返し、セッションは続けます。
  書けるようになるまで待ちません。
  カーネルモードでは転送される応答はソケットの送信バッファを持たず、経路が詰まればカーネルが qdisc で捨てるので、ユーザー空間モードも捨てるという同じ意味にします。
  ただし捨てる場所の深さは違う。
  カーネルモードが捨てるのは qdisc の待ち行列(既定の `pfifo_fast` で 1000 件)であり、ユーザー空間モードが捨てるのは待ち受けごとのソケットの送信バッファ(Linux の既定 `net.core.wmem_default` で約 208 KiB。
  1300 バイトの datagram なら skb の管理の領域を含めて 90 件ほど、65535 バイトの datagram なら 2 個ほど)です。
  以前の形では、送信の待ちの間に宛先側の endpoint のキュー(UDP の受信の予算)も burst を吸収していたので、待たない送信だけでは 1 つの待ち受けが吸収できる burst が小さくなる。
  混雑していない経路でも、1 回の入力に対する応答の burst が送信バッファを超えれば、超えた分を捨てます。
  このため公開側のソケットには固定の送信バッファを要求する(後述の[「公開側のソケットの送信バッファ」](udp-relay.md#公開側のソケットの送信バッファ))。
  ラボでは、混雑していない経路の代わりに公開側を 100 Mbit に絞り、1 回の入力に対する応答の burst の大きさを段階的に変えて以前の形と比べた。
  送信バッファに収まる burst では差が無く、送信バッファを超える burst では、この形は以前の形より多くを捨てた。
  以前の形も同じ大きさの burst の一部を別の場所で失っており、その場所は未確認である(改訂の記録 2026-09-27)。
  待つ形では、詰まった 1 つの待ち受けのセッションが枠を持ち続け、無関係なルールのセッションが枠を借りられず、プロセス全体の UDP の応答が止まります。
  混雑している公開側で応答を待ち続けることに、接続する利用者にとっての価値は無く、混雑が去れば次のデータグラムから戻る方が UDP として自然である(2026-09-27、所有者の決定)。
  待たないので、そのセッションは宛先側の接続を読み続け、公開側の詰まりが前述の UDP の受信の予算を占めることもありません。
  `EINTR` はやり直す。
  それ以外の送信の誤りは、今までどおりセッションを閉じます。
  満杯で捨てた応答は累計で数え、英語の 1 行のログに 1 分に 1 回まで出す。
  捨てた応答も宛先からは読めているので、待ち受けの最後の応答の時刻([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))には記す。
  `wgft status`、Web UI、wire protocol、管理用 API には載せない。
  エージェントの公開側は netstack の待ち受けであり、この 1 回だけの送信は使いません。
  その送信は、endpoint の送信バッファ(gVisor の既定 212 KiB)が使われている間は書けるようになるまで待つ。
  使われたままになるのは、後述の[「netstack の出力」](udp-accounting.md#netstack-の出力)のキューにパケットが留まっている間、つまりトンネルの送信(wireguard-go の TUN の読み取り)が止まっているときです。
  そのときは全ルールの応答が同じく止まるので、この待ちが枠によるルール間の新しい飢餓を作ることはありません。
  待ちは、トンネルの送信が進むか、待ち受けを閉じると解ける。
  セッションを閉じても、この送信の待ちは解けない
<a id="公開側のソケットの送信バッファ"></a>
- 公開側のソケットの送信バッファ:`vpsd` のユーザー空間モードは、公開側の UDP ソケットを開くたびに、固定の送信バッファ(`SO_SNDBUF` に 2 MiB)を要求します。
  設定項目にしません。
  応答の送信は待たないので、1 回の入力に対する正常な応答の burst を吸収するのはこのバッファだけであり、Linux の既定(`net.core.wmem_default` で約 208 KiB)では、混雑していない経路でも 1 回の入力に対する大きい応答の burst を捨てた(改訂の記録 2026-09-27)。
  このバッファは Go のヒープの予算ではなく、公開側の UDP ソケットごとのカーネルの資源です。
  プロセス全体では、おおむね「該当する公開側のソケットの数 × ソケットごとの上限」がカーネル側の保持点になります。
  ソケットごとの上限は kernel から読んだ実効の値で、Linux では要求の 2 倍の 4 MiB です。
  実際にメモリを使うのは送信が滞留している間だけで、ソケットを開いた時点でその量を使うのではありません。
  Linux は `setsockopt` に渡した値の 2 倍をソケットに割り当て、`getsockopt` もその 2 倍の値を返します。
  要求は `net.core.wmem_max` で切り詰められ、切り詰められた場合は burst の許容がその分だけ下がる。
  `vpsd` は開いたソケットの実効の値を `getsockopt` で読み返し、要求の 2 倍に届かなければ、WireGuard のソケットのバッファの警告と同じ形の英語の 1 行を、プロセスで 1 分に 1 回まで出す。
  行は実効の値、要求の値、書き換える sysctl を含む。
  `vpsd` はこの sysctl を書き換えない。
  ユーザー空間モードの `vpsd` の動作条件(前述の[「ソケットのバッファの条件」](socket-buffers.md#ソケットのバッファの条件))は `net.core.wmem_max` を 7340032 以上とするので、条件を満たすホストではこの要求は切り詰められない。
  WireGuard のソケットは `CAP_NET_ADMIN` の FORCE で上限を超えられるが、この公開側のソケットの要求は FORCE を使わないので、上限が小さいホストでは WireGuard の警告が出ずにこの警告だけが出ることがあります。
  このバッファはルール間の隔離ではなく、待たない送信を保ったまま正常な burst を吸収するためのものです。
  「setsockopt に渡した値」と「kernel から読んだ実効の値」は、この文書でも試験でも区別します
<a id="エージェントの-lan-側のソケットの受信バッファ"></a>
- エージェントの LAN 側のソケットの受信バッファ:ユーザー空間モードのエージェントは、UDP のセッションごとに LAN の宛先へのカーネルの UDP ソケットを 1 つ開き、その受信バッファ(`SO_RCVBUF`)を設定しません。
  受信バッファの大きさは OS の既定の値で、Linux では `net.core.rmem_default` です。
  宛先からの応答は、セッションが読むまでこのバッファに溜まる。
  溜まったときに使うのはカーネルのメモリであり、Go のヒープにもソフト上限の式にも入りません。
  この段の上界は、セッション数と 1 つのソケットの受信バッファの大きさの積です。
  Linux ではさらに、`net.ipv4.udp_mem` がホスト全体の UDP のソケットのメモリの上限として効く。
  この上限はホストの全ての UDP のソケットに共通なので、ここに溜まる量が大きいと、同じホストの WireGuard のソケットの受信も巻き込みうる。
  1 つのセッションに届く応答の burst がセッションの読み取りに追いつかず受信バッファを超えると、超えた分はそのセッションで捨てられうる。
  カーネルモードのエージェントにはこの段がありません。
  カーネルが応答をそのまま転送し、ユーザー空間のソケットを通さないためです。
  受信バッファは大きくしません。
  大きくすると、セッション数との積でカーネルのメモリの上界が大きくなり、ホスト全体の UDP のメモリを圧迫しうる一方で、得られる利点は大きな burst をさらに守れることだけだからです。
  通常の利用で明確な退行が確認された場合に限り、大きくする比較を改めて行う(2026-09-27、所有者の決定)。
  macOS と Windows での既定の値と数え方は未確認です
