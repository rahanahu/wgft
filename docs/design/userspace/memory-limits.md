# 上界に含めない保持点と測定の限界

上界の式には、件数の構造上の制限が無い保持点と、未確認の小さい保持点を含めません。
ラボの RSS の測定値は、攻撃に対する上限を示す値ではありません。


<a id="上界の式に入れない"></a>
<a id="wireguard-go-の送信元ごとのハンドシェイクの制限の表"></a>
wireguard-go の送信元ごとのハンドシェイクの制限の表は、[送信元の件数の制限と実用上の見積もり](wireguard-sources.ja.md)で扱います。
このブランチは、公開鍵を持つ者からの入力も件数の制限に含めることを提案します。
map の裏の領域と GC の余白は、厳密な byte の保証としては未確認です。

次の保持点は件数に構造の上限を持たないが、上界の式に入れない(2026-09-30、所有者の決定)。

<a id="設定の変更で止めた-transparent-の-tcp-の待ち受けの世代"></a>
- 設定の変更で止めた `Transparent` の TCP の待ち受けの世代:1 世代はソケット 1 本で、作るのは信頼された設定の変更だけです
<a id="エージェントの古いトンネルの世代"></a>
- エージェントの古いトンネルの世代:閉じたトンネル 1 つが残す量は約 0.31 MiB だった(測定)。
  式は、前述のエージェントの 4.4 MiB の項で少数の世代の分だけを持ちます。
  作り直しを起こすのは、`vpsd` の全体状態、管理者の操作、[作り直しの判定](tunnel-recovery.md#トンネルの作り直し)です。
  作り直しの判定は、ハンドシェイクが新しくならない経路の故障でも働くので、信頼された操作だけが起こすものではありません。
  古い世代が少数に留まるのは、判定がトンネルを立ててから 300 秒以上の[間隔](tunnel-recovery.md#作り直しの間隔)を置いて作り直すためです(`internal/agent/watchdog.go` の `defaultRebuildAfter`)。
  例外として、トンネルの作成に失敗した後の最初の試し直しは、次の 30 秒の判定で行います([作成に失敗したときの再試行](tunnel-recovery.md#作成に失敗したときの再試行))
<a id="管理用-api-と-web-ui-の疎通確認"></a>
- 管理用 API と Web UI の疎通確認:起こすのは信頼された管理者だけです

<a id="tcp-のポートごとの待ち受け"></a>
TCP のポートごとの待ち受けと、その accept の goroutine も上界の式に入れません。
待ち受けは全体状態のルールのポートごとに 1 つで、範囲のルールはポートの数だけ作ります。
作るのは信頼された設定だけです。
1 ポートあたりの量は、エージェントでは netstack の待ち受けの endpoint 1 つと goroutine 1 つと記録で約 10 から 20 KiB、`vpsd` では goroutine 1 つと記録とホストのソケットで数 KiB とソースから推定しており、測っていません。
この推定では、範囲が 1-65535 の TCP のルール 1 本で、エージェントの生きているヒープが約 0.6 から 1.3 GiB 増えます。

設定と履歴に比例して増える小さい保持点(観測の履歴、拒否の数の記録、データベースのキャッシュと WAL、エージェントの制御ソケットの接続)は、式にも前述の一覧にも入れていません。
どれも量は小さいと推定しているが、未確認です。

警告の行は、この小さい保持点に入れません。
警告の行は (エージェント, 種類, detail) の組で重複を除く。
`ip-flapping` の detail は往復した 2 つの IP を含み、`ip-mismatch` の detail は stream の接続元 IP と wg エンドポイント IP を含むので、どちらも IP の組が違えば別の行になります。
行の数はエージェントごと、種類ごとに 64 行までで、記録するたびに、最後に検出した日時が古い行から消す([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)。
2026-10-02 の 2 つの改訂の前は、どちらの種類にも上限が無かった)。
stream の接続元 IP を観測するのは認証を通った stream だけであり、wg の endpoint を動かせるのは WireGuard の鍵の持ち主だけです。
このため、上限までの行を新しい IP の組で入れ替えられるのは、そのエージェントの恒久トークンの持ち主か WireGuard の鍵の持ち主です。
管理用 API の agent の一覧は、エージェントごとに、そのエージェントの警告の行だけを読みます。
上限に達したときのデータベースの大きさと、一覧を返すときのメモリの量は測っていません。
これらの行は、式にも前述の一覧にも入れていません。

<a id="中身の無い-segment-の処理待ち"></a>
中身の無い TCP の segment の endpoint ごとの処理待ちは、上界の式に入れません。
固定版の gVisor はこの segment を受信のメモリの判定とは別に受け入れるので([netstack の依存の固定](netstack-dependency.ja.md))、処理待ちの件数は処理の速さで決まります。
ラボでは、中身の無い ACK の洪水と、WireGuard の受信の詰まりをそれぞれ起こしました。
その間、他のフローの遅れの p99 は約 0.2 から 0.27 秒、最大は 0.46 秒で、他のフローは失敗しませんでした。
負荷を止めた後、生きているヒープは負荷の前の値に戻りました。
この結果は、1 つの経路が共有の処理を長く止めないことの根拠です。
保持の量の上限を示すものではないので、上界の項は加えません。
握手の途中の接続の segment の処理待ちが、処理されるまでの短い間に持つ中身([accept の待ち行列](memory-agent-host.md#accept-の待ち行列))も、同じ種類の短い保持として上界の項に加えません。

ラボ(4 vCPU の VM)で、ユーザー空間モードの `vpsd` に、floor を満たした TCP のフロー、エージェント用 API の認証前の接続(当時の上限は 4096 本)、UDP のセッションを、それぞれ上限の近くまで同時に保持させた。
生きているヒープの最大は 1.66 GiB だった。
既定のソフト上限の下で、RSS の最大は 1.88 GiB、cgroup のメモリの最大は 2.68 GiB だった。
cgroup の値は、cgroup に数えられたカーネルのソケットのバッファ約 0.2 GiB を含む。
さらに約 0.6 GiB は、transparent huge pages を always にしたホストの設定によると推定しています。
madvise にした同じ負荷では 2.05 GiB だった。
どの値も、測った生きているヒープにこの数え方を当てはめた値の内側だった。
ソフト上限を外した同じ負荷の実行(`GOMEMLIMIT=off`)では、生きているヒープの最大は 1.87 GiB で、RSS は生きているヒープの約 2.2 倍まで増えた。
RSS の最大は、その実行の生きているヒープの最大 1.87 GiB にこの数え方を当てはめた値の内側だったが、差は約 0.6% だった。
既定のソフト上限は RSS を生きているヒープの近くに保ったが、保持している間、GC が 4 個の CPU の約 30% を使った。
ソフト上限は保証ではないので(前述)、表はソフト上限の効果を見込まない。
このラボでは、boost、wireguard-go のキュー、出力のキュー、再組み立ての表、送信元ごとの新規フローの表、管理用 API を埋めていません。
すべての項を同時に埋めた場合の RSS、エージェントのプロセスの実測、係数のばらつき、この数え方の値が RSS の厳密な上界になるかどうかは未確認です。
WireGuard のソケットのバッファが cgroup のメモリに数えられるかも未確認です。
