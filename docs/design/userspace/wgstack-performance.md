# wgstack の性能の段階

[エージェントの wgft の netstack](wgstack.md)(wgstack)は完成の段階を NewReno で判定し、性能の目標を完成の後に追います([完成と性能の目標](wgstack.md#完成と性能の目標))。
性能の段階のうち実装したのは、観測の段の wgstack の側(`Stats` の数、接続の記録、boost の切り替え)、SACK による回復の段、RACK-TLP の段、CUBIC の段、HyStart++ の段、輻輳の窓の検証の段、受け手の ACK と D-SACK の段、並べ替えの下の不要な再送の取り消しの段、受信の窓の自動調整の段です。
測った差の診断の方法、変更の優先順位、判定の測定、段階の順序をここで決め、値と個々の構造の細部は実装の時に決めます。
正しさの検証は[wgstack の検証](wgstack-verification.md)に従い、この文書は性能のために足す試験と測定だけを定めます。

## 目標と制約

性能の目標は所有者が決めた次の 4 つで、すべてを同じ測定の行列で判定します。

- スループット:Linux の 90% 以上で、かつ gVisor 以上です
- 短い障害からの回復:Linux の回復の時間に RTO 1 回分を足した時間以内です
- 通信量の少ない stream の遅れ:p99 が Linux の 1.5 倍以内です
- CPU:byte あたりの CPU が、エージェントが送る向きと受ける向きの両方で gVisor の 0.6 倍以下です。
  この値は所有者が 2026-10-31 に決めました

性能の段階の変更は、完成の段階の制約をすべて保ちます。
保持の上界は導けるままにし、新しい構造はどれも[上界の式](wgstack.md#上界の式)に項を持ちます。
I1 から I7 の[不変条件](wgstack.md#不変条件)を崩す変更は、性能が上がっても採りません。
受信の窓を受信の向きの需要が生じるまで floor の内側に保つ規則([boost の取得と floor への戻り](wgstack.md#boost-の取得と-floor-への戻り))も保ちます。
[需要で育つバッファ](wgstack-buffers.md#決めたこと)の段を実装するときに、この規則を、受信の窓の自動調整の測定が窓の上限を上げるまで始めの目標の内側に保つ規則に替えます(2026-10-31、所有者の決定)。

## 測った差の診断

### 測った値

測定は `internal/tcpharness/qbench` で行いました。
qbench は 1 つのプロセスの中で、wireguard-go の gVisor の netstack が接続を開き、DUT が受け付けます。
経路は片道 25 ms の遅延、20 Mbit/s、200 packet の drop-tail の待ち行列、種で固定した無作為の損失を持ち、8 MiB を転送します。

| 場合 | DUT が送る(download) | DUT が受ける |
|---|---|---|
| 損失 0% | 7.93 / 18.21 | 6.58 / 11.52 |
| 損失 1% | 2.65 / 3.71 | 2.67 / 3.43 |
| 損失 5% | 60 秒の上限までに終わらない / 1.44 | 1.17 / 1.40 |
| 2 秒の途絶 | 5.73 / 9.48 | 未測定 |

値は wgstack / gVisor の Mbit/s の中央値です。
DUT が受ける損失 0% の実行は、wgstack で 2.71 から 6.58 まで揺れました。
待ち行列を溢れない大きさ(`QBENCH_QUEUE_PKTS=100000`)にした損失 0% の 4 MiB の 1 回では、2 つの実装は両方の向きで一致しました。
DUT が受ける向きは 17.67 と 17.70、DUT が送る向きは 17.76 と 17.72 で、再送と待ち行列の溢れはどちらも 0 でした。

### 損失 0% の差の原因

損失 0% の差は、定常のスループットと CPU からは生じていません。
待ち行列が溢れない経路で 2 つの実装が一致したので、既定の 200 packet の経路での差は、slow start が待ち行列を溢れさせて生じるまとまった損失と、その損失からの回復の違いから生じます。
20 Mbit/s と往復 50 ms の BDP は約 125 KB で、200 packet の待ち行列を足しても約 409 KB です。
窓がこの量を超えて slow start を続けると、1 往復の間に多数の segment が待ち行列で失われます。

この結論から、損失 0% の差に効く変更は 3 つに絞れます。
送る向きでは、まとまった損失を速く直す SACK による回復と RACK-TLP、溢れそのものを避ける HyStart++ です。
受ける向きでは送り手が qbench の gVisor なので、wgstack が左右できるのは、送り手が溢れさせる量を決める受信の窓の開き方と、送り手に返す ACK と SACK の内容です。

### 送り手の差

DUT が送る向きの差は、今のコードの次の仕組みで説明できます。
各項の因果は仮説で、[安く確かめる手順](#安く確かめる手順)で確かめます。

- NewReno の回復:部分の確認ごとに穴を 1 つだけ再送するので、1 つの窓の中の n 個の損失を直すのに n 往復かかります。
  slow start の溢れは 1 往復に多数の損失を作るので、損失 0% の差の主因の候補です
- RTO の後の送り直し:`onRTO` は SND.NXT を SND.UNA に戻して送信の記録を消すので、受け手が持っているデータも含めて送り残しをすべて送り直します
- RTO の後の高速の再送の禁止:`onRTO` が `recover` を SND.MAX にするので、RTO の時に送っていたデータがすべて確認されるまで、3 つの重複した ACK でも高速の再送をしません(RFC 6582 4 節)。
  再送した segment の損失も RTO でしか見つけられません。
  損失 5% で RTO が続き、60 秒の上限までに終わらなかった原因の候補です
- Limited Transmit が無いこと:最初の 2 つの重複した ACK で新しい segment を送らないので(RFC 3042)、窓の小さな間は 3 つの重複した ACK が揃わずに RTO を待ちます
- slow start の終わり方:遅延の増加で slow start を終える仕組みが無く、損失が起きるまで窓を倍にし続けます
- 損失への応じ方:NewReno は窓を半分にし、1 往復に 1 segment ずつ戻します。
  Linux の CUBIC は 0.7 倍にするので、無作為の損失 1% では窓の平均が大きくなります
- 送信の floor:送信の向きの boost を得るまでは、送信の floor の 256 KiB が送り残しの量を抑えます。
  256 KiB は前述の約 409 KB より小さいので、floor の間の slow start は待ち行列を溢れさせません。
  溢れの大きさは、送信の boost を得た時の輻輳の窓でも決まります

2 秒の途絶の場合の差は、途絶の前の slow start の溢れと、途絶の後の RTO からの立ち上がりの合計と考えます。
途絶の終わりから最初の byte までの時間は、途絶の終わりの後に来る最初の再送の期限で決まります。
期限の列は最初の期限と倍化で決まるので、途絶の長さとの位相で数百 ms 単位で変わります。
最初の期限(RTO の値と、その時刻に送るのが probe か RTO か)を Linux に合わせると、同じ長さの途絶では期限の列が Linux に近づきます([RACK-TLP](#rack-tlp)のタイマーの規則)。
揃いはしません。wgstack は最初の期限を最後の確認から数え(RFC 6298 5.3)、Linux の記録は確認の途絶えた先頭の segment を送った時刻から数えた値に合います。
SRTT が約 50 ms の経路では、最後の確認から wgstack は約 250 ms、Linux は約 228 ms です。

### 受け手の差

DUT が受ける向きでは送り手が gVisor なので、回復の仕組みは送り手のものです。
wgstack の側で差を生む候補は次のとおりです。

- 受信の窓の急な拡大:受信の窓の自動調整の段の前は、受信の向きの boost を得ると、`growRecv` が受信の容量を 4 MiB にして ACK をすぐに送り、`windowField` が右端を最も古い未読の byte から 4 MiB 先へ一度に進めました。
  受信の窓に抑えられていた間に送り手の輻輳の窓が育っていれば、送り手は開いた窓へまとめて送り、待ち行列を溢れさせます。
  溢れる量は boost を得た時の送り手の輻輳の窓で決まるので、この仕組みは損失 0% の揺れを説明できます
- ACK の間隔:遅延 ACK の判定は、相手の segment の大きさを観測せず、自分の MSS から求めた値で 2 segment 分を数えます。
  相手の segment が自分の MSS より小さいと、3 segment ごとか遅延の期限ごとの ACK になります。
  Linux は受けた segment から大きさを推定し、接続の始めに quickack で segment ごとに ACK を返します
- D-SACK を返さないこと:送り手は不要な再送を見分けられず、並べ替えへの耐性を広げられません

boost の時期についての仮説は 2 つあります。
1 つ目は、boost が遅れて届くか、floor に戻った後に古い窓へ届いたデータが捨てられて(`RecvTrimmed`)止まるという仮説です。
2 つ目は、前述の窓の急な拡大が溢れを作るという仮説です。
qbench の実行は接続が 1 本なので、floor への戻りは別の接続の取得の要求が無ければ起きません。
このため、仮説は次の順で確かめます。

1. 実行ごとに `BoostGranted`、`BoostReclaimed`、`RecvTrimmed` を記録します。
   遅い実行でも後の 2 つが 0 なら、1 つ目の仮説はこの bench については外れます
2. 経路の記録で、DUT が広告した窓の右端、待ち行列の溢れの時刻、boost を得た時刻を並べます。
   溢れが窓の拡大の直後の往復に集まれば、2 つ目の仮説を支持します
3. 試験だけが使う切り替えで、boost を受け付けの時に与える実行と、boost を与えない実行を比べます。
   floor の 256 KiB は前述の 409 KB より小さいので、2 つ目の仮説が正しければ、boost を与えない実行は溢れずに経路の速さに近づきます

### 安く確かめる手順

コードの挙動を変える前に、観測を足して各仮説を確かめます。
観測の追加は挙動を変えないので、適合の試験と上界の試験に影響しません。

- Device の数:`Stats` に送り手の事象を足します。
  数は Device の atomic なので、M_fix に定数として入ります。
  欄は次のとおりです
  - `RTOs`:再送のタイマーの期限で送り直した回数です。窓の probe は数えません
  - `RTOsBackedOff`:累積の確認が進む前に続いた RTO で、再送した segment も失われたことを示します
  - `RTOsShortOfDupThresh`:回復の外で、重複した ACK を 1 つか 2 つ受けた後の RTO です
  - `FastRecoveries`、`PartialAcks`:高速の回復に入った回数と、回復の中の部分の確認です
  - `RetransFast`、`RetransPartial`、`RetransRTO`、`RetransPMTU`:原因ごとの再送の segment です。
    後の 2 つは、RTO と PMTU の引き下げで SND.NXT を戻した後に SND.MAX より手前を送り直した segment で、受け手が持っていたデータも含みます
  - `DupAcksIn`:受けた重複した ACK です
  - `AcksDelayed`、`AcksImmediate`:求められた ACK を運んだ segment を、遅延 ACK のタイマーが求めたものと即座に求めたものに分けて数えます。
    中身と共に運んだ ACK も含み、遅延 ACK を待つ間に中身と共に運んだ確認は数えません
- 接続の記録:試験だけが設定する観測の関数(`Config.Trace`)を核に持たせ、ACK を処理するたびと RTO のたびに `TraceEvent` を渡します。
  欄は種類(`TraceAck` か `TraceRTO`)、核の時刻、接続の両端、輻輳の窓、ssthresh、送り残しの量(SND.MAX - SND.UNA)、SND.UNA、SND.NXT、SND.MAX、回復の状態、重複した ACK の数、相手の窓、自分が広告した窓、SRTT、後退を含めた RTO です。
  途絶の終わりの時点の RTO は、途絶の終わりより前の最後の `TraceRTO` の RTO です。
  関数は接続の錠を持ったまま呼ぶので、Device を呼び返しません。
  本番では nil のままで、確認 1 回の手間だけを加えます
- 経路の記録:qbench の経路が packet ごとに時刻、向き、番号、確認の番号、広告の窓、待ち行列の長さ、捨てた理由を書きます。
  経路は 3 つの実装に共通なので、Linux の挙動も同じ形で比べられます。
  経路はすでに届けた範囲を知っているので、受け手が持っていたデータの再送(不要な再送)も数えます
- bench の切り替え:待ち行列の長さ、速さ、損失は環境変数で変えられます。
  並べ替え(`Impair.Reorder`)の環境変数、試験だけの boost の切り替え、実行の時間の上限を足します。
  boost の切り替えは wgstack の `Config.TestBoost` で、既定の `BoostOnDemand`、`Accept` が接続を返す時に両方の向きの boost を求める `BoostAtAccept`、boost を求めない `BoostNever` です
- 相手の統計:qbench の相手を、wireguard-go の `netstack` ではなく gVisor の stack を直接作る形にし、相手の設定(SACK、RACK、輻輳の制御)を固定して、再送と RTO の統計を読めるようにします

診断で確かめる組は次のとおりです。

| 問い | 確かめ方 | 仮説どおりなら |
|---|---|---|
| 送る向きの損失 0% の差は溢れからの回復か | 経路の記録で溢れの数と、溢れの後に最後の穴が埋まるまでの往復の数を数えます | 穴の数と同じ往復の数がかかり、その間の速さが落ちます |
| 損失 5% の上限は RTO の連続か | `Stats` の RTO の回数と、RTO の間の再送の segment の損失を数えます | RTO が連続し、再送した segment の損失ごとに RTO を待ちます |
| 窓の小さな間に RTO を待っているか | 重複した ACK が 3 つに届かずに RTO になった回数を数えます | 窓の小さな間の損失が RTO になります |
| 受ける向きの揺れは窓の拡大か | 前節の 3 つの手順で確かめます | 溢れが拡大の直後に集まり、boost の無い実行が揺れません |
| ACK の間隔は Linux と違うか | 経路の記録で、ACK 1 つあたりの data の segment の数を 3 つの実装で比べます | 接続の始めと小さな segment で wgstack の ACK が少なくなります |

## 変更の優先順位

変更は、download の向きの差への効果の大きい順に並べます。
[段階の順序](#段階の順序)は、この優先順位を検証できる単位に分けたものです。
期待する効果はどれも見込みで、各変更の後の測定で確かめます。
上界の項は[上界の式への項](#上界の式への項)にまとめます。

### SACK による回復

- 規格:RFC 6675 の SACK による損失の回復、RFC 6937 の PRR による回復の間の送る量、RFC 3042 の Limited Transmit です。
  RecoverFS だけは RFC 6937 を置き換えた RFC 9937 に従います([CUBIC](#cubic)の「回復の間に届く量」)。
  RTO の後は RFC 6675 5.1 節に従い、SACK で確認された segment を送り直しません
- 使う構造:送信の記録の輪の印(SACK 済み、損失)を scoreboard にします。
  記録の扱いと ACK 1 つの手間の上界は、この節の後に定めます
- 不変条件:I4 では、SACK で確認されたデータも累積の確認まで送信の輪に残します(今と同じ)。
  相手が SACK を取り消した場合も、RTO で送り直せます。
  I1 では、範囲の外の block を 1 つでも含む ACK の SACK の block をすべて捨てます(完成の段階の `checkSACK` と同じ検査)。
  ACK 1 つの手間は後述の上界に留め、上界を満たせない入力が見つかった場合の備えとして、中身の無い ACK の予算を wgstack に戻す案を残します
- 危険:送り残しの量(pipe)の誤りは窓を超える送信か止まりを生み、NextSeg の誤りは SACK 済みの再送か穴の見落としを生みます。
  番号の折り返し、PMTU の引き下げ、SACK の取り消しとの組み合わせも誤りやすい点です
- 期待する効果:送る向きの損失 0%、1%、5% のすべてで最も大きく効きます。
  溢れによる n 個の損失を 1 往復ほどで直せるので、損失 0% は gVisor の値に近づくと考えます

#### scoreboard の記録の扱い

完成の段階のコードは、`onRTO` と `pmtuDrop` が送信の記録を消し、SND.NXT を SND.UNA に戻して送り直していました。
このままでは RTO のたびに SACK 済みの印が消え、RFC 6675 5.1 節の規則(RTO の後に SACK 済みの segment を送り直さない)を守れないので、記録を次の規則で扱います。

- RTO:記録を消さずに残します。
  SACK 済みでない記録をすべて損失にし、再送は既存の記録を番号の順にたどって、SACK 済みの記録を飛ばします。
  再送した記録には再送の印を付け、送った時刻を更新します。
  新しい記録を積むのは、SND.MAX より先の新しいデータを送るときだけです。
  SND.NXT は戻さず、いつも SND.MAX と等しくなります
- PMTU の引き下げ:記録の境目は送った時のまま残します。
  SACK 済みでない記録を損失にし、新しい segment の大きさを超える記録は、1 つの記録を複数の segment に分けて再送します。
  記録を分けないので、記録の輪の容量は変わりません。
  輻輳の窓は変えません。
  記録に SACK 済みの印を付けるのは、SACK の block が記録の全体を覆ったときだけです
- SACK の取り消し:Linux の `tcp_check_sack_reneging` と同じ時期で扱います。
  SND.UNA を進める ACK の後に先頭の記録が SACK 済みのままなら、相手が SACK 済みのデータを捨てた疑いとして、再送のタイマーを max(SRTT/2, 10 ms) の後に早めます。
  期限までに先頭を確認する ACK が来れば、次の ACK が再送のタイマーを張り直すので何もしません。
  期限が来ると RTO の処理に入り、先頭の記録がまだ SACK 済みか、同じ SND.UNA で 2 回目の RTO なら、すべての記録の SACK 済みの印を世代の番号で消します(Linux の `tcp_timeout_mark_lost`)。
  ACK の時点で印を消さないのは、輻輳の窓を下げないまま全部の記録を損失にしないためです。
  印を消した記録は RTO の規則で損失になり、送信の輪にあるデータから送り直します
- 窓と再送:窓の外から始まる記録は再送しません。
  先頭の記録は、窓が 0 でも窓の probe を兼ねて再送します(Linux の `tcp_retransmit_skb`)。
  RTO の後に失われた記録だけが残り、窓が 0 の間は、窓の probe に移ります
- RTT の測定:ACK が再送した記録を 1 つでも確認したときは、timestamp の無い接続の RTT を測りません(Linux の `FLAG_RETRANS_DATA_ACKED`)。
  記録が RTO の後も残るので、再送を待つ間に届いていた元の segment で測ると、穴が埋まるまでの時間を RTT に含めるためです

#### ACK 1 つの手間の上界

wgstack の核は中身の無い ACK の予算を持たないので、相手は ACK の洪水で 1 つの ACK の処理の手間を何度でも起こせます。
RFC 6675 の pipe と IsLost を記録を順に調べて求めると、1 回の問いが記録の数に比例し、boost では記録が最大 8,887 件になります。
このため、ACK 1 つの手間の上界を次のとおりに定めます。

- 上界の形:ACK 1 つの手間は、SACK の block の数 × log(記録の数) と、印付けの均した手間と、定数の更新の和を超えません
- 数の欄:SACK 済みの記録の byte の和、今の世代で再送した記録の byte の和を接続の欄に持ち、印を付けるときと外すときに増減します。
  pipe は SND.MAX - SND.UNA から、SACK 済みの byte と、損失の境目より手前の SACK 済みでない byte を引き、再送した byte を足して求め、記録を調べません。
  SACK を交渉しない接続では、回復の外で重複した ACK 2 つまでを受け手が受けた segment として pipe から引き、RFC 3042 の Limited Transmit にします(Linux の `tcp_add_reno_sack`)
- IsLost:損失の境目の位置と、その位置から先にある SACK 済みの byte の和と記録の数を持ちます。
  境目の記録より先の SACK 済みの量が RFC 6675 の閾値(DupThresh 個の記録か (DupThresh - 1) × SMSS byte を超える量)に届く間、境目を先へ進めます。
  境目は後ろへ戻らないので、記録ごとに 1 回だけ通り過ぎます。
  IsLost の答えは、境目より手前の SACK 済みでない記録では真で、境目から先では偽です。
  RTO と PMTU の引き下げは境目を記録の末尾に置き、手間は記録の数によりません
- 印付け:block の端を二分探索で探し、まだ SACK 済みでない記録だけをたどります。
  SACK 済みの記録は、次の SACK 済みでないかもしれない記録までの数を持ち、たどった記録の数を書き直して経路を縮めます。
  数と 2 つの世代の番号は記録 1 件の中に置くので、記録は 24 byte から 32 byte になり、r_f と d_rec が増えます。
  SACK の取り消しで印を消す処理と、RTO で再送の印を消す処理は、世代の番号で定数の手間にします。
  世代の番号が 1 周した時だけ、記録の輪の印を消し直します
- NextSeg:再送の手がかり(RFC 6675 の HighRxt)は、回復に入る時と RTO と PMTU の引き下げで SND.UNA に戻し、ほかは前にだけ進みます。
  規則 1(失われた記録)、規則 2(新しいデータ)、規則 3(最も右の SACK 済みの byte より手前の、まだ再送していない記録)の順に選びます。
  規則 3 は回復の中だけで使い、規則 4(rescue の再送)は使いません
- 回復:SACK を交渉した接続は、3 つの重複した ACK か IsLost(SND.UNA) で回復に入り、先頭の記録を損失とみなします。
  回復の間の輻輳の窓は RFC 6937 の PRR-SSRB で決め、回復に入った時の最初の再送は Linux と同じく窓によらず送ります。
  回復の終わりの輻輳の窓は ssthresh です。
  SACK を交渉しない接続は、完成の段階の NewReno のままです

上界を満たせない入力が見つかった場合の備えとして、中身の無い ACK の予算([中身の無い ACK の予算](packet-validation.md#中身の無い-ack-の予算))を wgstack に戻す案を残します。

### RACK-TLP

- 規格:RFC 8985 です。
  RACK-TLP は SACK を前提にし、SACK を交渉した接続だけで使います。
  SACK を交渉しない相手では、完成の段階の NewReno と RTO だけで直します
- 使う構造:送り残しの記録を、送った時刻の順の list と、RACK が失われたとみなしてまだ送り直していない記録の待ち行列のどちらかに置きます。
  2 つの list は記録の prev と next の節を共用し、節は自分の位置からの記録の数の差で持つので、輪の大きさを変えても先頭の記録を外しても変わりません。
  SACK 済みの記録と、損失の境目より手前で送り直しを待つ記録は、どちらの list にも入りません。
  新しく送った記録と再送した記録を送った時刻の順の list の末尾に足し、RACK の判定は先頭から行います。
  list に入っている印と RACK の損失の印は再送の世代の番号で有効にし、RTO と PMTU の引き下げは世代を進めて 2 つの list を一度に空にします。
  RACK の状態(届いた記録のうち最も後に送った記録の時刻と端、RACK の RTT、届いた最も右の端、並べ替えを見たか)、最小の RTT、TLP の状態は接続の欄に置きます
- RACK の判定:累積の確認と SACK で新しく届いた記録で RACK の状態を更新し、再送した記録のうち元の segment への確認かもしれないものは使いません(RFC 8985 6.2 の手順 2)。
  元の segment への確認かは Linux の `tcp_rack_advance` と同じく最小の RTT だけで見分け、RFC 8985 の TSecr による判定は使いません。
  穴のある間の SACK の TSecr は受け手の TS.Recent で穴より前の segment の時刻のままなので、再送への SACK をすべて元の segment への確認とみなし、再送の損失を見つけられなくなるためです。
  並べ替えの窓は、並べ替えを見ていない間は回復の中か SACK 済みの記録が DupThresh 個以上なら 0 で、ほかは min(最小の RTT / 4, SRTT) です。
  D-SACK を受けた往復ごとに並べ替えの窓の倍率を 1 つ上げ(1 往復に 1 回)、16 回の回復の間保ってから 1 に戻します(RFC 8985 6.2 の手順 4)。
  D-SACK は、先頭の block が SND.UNA より前にあるか、2 つ目の block の内側にある ACK です(RFC 2883 4 節)。
  送った時刻の順の list を先頭からたどり、期限の来た記録を失われたとみなして待ち行列に移し、期限の来ない最初の記録で止めて、その期限を並べ替えの期限にします。
  RFC 8985 は期限の来ない記録の期限のうち最も遅いものを張りますが、wgstack は ACK 1 つの手間を均すために最も早いものを張ります。
  期限の処理は記録に印を付けるか、新しい期限を張るので、印の付く記録の数と ACK の数を超えて起きません。
  失われたとみなした記録があれば、回復の外では回復に入ります
- NextSeg の規則 1:RACK の待ち行列の先頭と、損失の境目より手前の番号の順の手がかりのうち、番号の小さい方を送ります。
  Linux と同じく番号の小さい穴から直すためで、待ち行列を先にすると、先頭の穴の再送が後の穴の再送の後ろに遅れ、前の累積の確認から数えた RTO が起きました
  待ち行列の先頭の記録を MSS より大きな記録として分けて送る間は、送った位置を接続の欄に持ちます。
  先頭の記録が SACK、累積の確認、損失の印の付け直しのどれで待ち行列を出ても、その位置を 0 に戻します。
  戻さないと、位置が次の記録に持ち越されて長さが巻き戻り、SND.MAX の先の輪の中身を送ります
- TLP:SACK を交渉し、回復の外で、RTO の後の回復の外で、SACK 済みの記録が無く、probe の確認を待っていない接続は、新しいデータを送った後と累積の確認が進んだ後に PTO を張ります(RFC 8985 7.2)。
  SACK 済みの記録がある間は、RACK の並べ替えの期限と、相手が SACK を取り消した疑いで早めた RTO が損失を扱います。
  張ると、PTO が早めた RTO の期限に揃い、その時刻の RTO が probe に替わって 1 RTO 遅れます。
  PTO は 2 × SRTT で、送り残しが 1 segment なら max(2 × SRTT, 1.5 × SRTT + 200 ms)、RTT を測る前は 1 秒です。
  PTO が RTO の期限より遅くなるなら、RFC 8985 7.2 のとおり RTO の期限に PTO を張ります。
  その時刻には RTO ではなく probe を送り、RFC 8985 7.3 のとおり probe を送れたかによらず RTO を今から張り直します。
  PTO の期限には、窓が許せば新しいデータを、許さなければ最も番号の大きい記録を、輻輳の窓によらず 1 つ送ります。
  前の probe の後(probe が無ければ接続の始めの後)に RTT を測っていなければ、RFC 8985 7.3 の条件 2 のとおり probe を送りません。
  timestamp の無い接続で再送した記録だけを確認した ACK は Karn の規則で RTT を測らないので、RTT の伸びた経路で再送の probe が続くのをこの条件が止めます。
  このとき RTO の期限は動かさず、RTO が張られていないときだけ今から張ります。
  RTO の期限に揃えた PTO でも probe を送らず、その期限に RTO を起こします。
  7.3 の RTO の張り直しは、probe が失敗しても RTO が最後の手段として残るためのもので、RFC 6298 が決めた期限を後ろへ送るためのものではありません。
  probe を送らないたびに RTO を今から張り直すと、新しいデータが PTO を張り直し続ける間は RTO が起きません。
  確認の無いまま 100 ms ごとに 20 byte を書く接続(SRTT 50 ms、初めの窓 10 segment)では、輻輳の窓が埋まるまでの約 56 秒になり、その間は再送の打ち切りの時間も数えません
  probe の確認を待つ間は次の PTO を張りません。
  probe が再送で、累積の確認が probe の先まで進んだときは、probe が損失を直したとみなし、[CUBIC](#cubic)の輻輳の事象として ssthresh を決め、輻輳の窓をその値にします。
  probe を送った後に回復か RTO が始まっていれば、その応答が probe の前の損失への輻輳の事象なので、TLP では下げません(RFC 8985 7.4.1)。
  probe の確認を待つ間に RACK が回復に入り、回復を終える ACK が probe の先まで確認する場合がこれに当たります。
  基準の送り残しと輻輳の窓は、この ACK を処理する前の値です。
  RFC 8985 7.4.2 は高速の回復と同じ応答を求めるので、損失の時の窓で下げます。
  ACK の後の値では、この ACK が probe の後のデータまで確認したときに送り残しが 0 になり、窓が下限まで落ちます。
  この縮小は、その時の SND.MAX までに送ったデータの輻輳の事象です(RFC 8985 7.4 と、1 つの窓の損失に 1 回の縮小とする RFC 5681 3.2 と RFC 6582)。
  wgstack はこの番号を接続の欄(`tlpCutSeq`)に覚え、SND.UNA が届くまで印(`tlpCut`)を残します。
  SND.UNA がその番号に届く前に回復に入るときは、ssthresh を下げ直さず、PRR は今の ssthresh を目指し、回復はその番号で終わります。
  その番号より先に送ったデータの損失は、次の回復で窓を下げます。
  probe の確認と同じ ACK で RACK が別の損失を見つけた場合も同じで、縮小は 1 回だけです。
  probe を送った時の SND.NXT の確認が、SND.UNA を進めず新しい SACK も無い重複した ACK なら、損失は無かったとみなします(Linux の `tcp_process_tlp_ack`)
- タイマーの規則:RTO の期限は接続の欄に別に持ち、再送のタイマーの節には、RTO、並べ替えの期限、TLP の probe の期限のうち最も早いものを張ります。
  並べ替えの期限で起きたときは、処理の後に残る期限のうち最も早いものを張り直すので、RTO の期限を後ろへずらしません。
  TLP の probe を送った後は、RFC 8985 7.3 と Linux の `tcp_send_loss_probe` と同じく RTO を今から張り直します。
  前の累積の確認から数えた RTO の期限を保つと、PTO が 2 × SRTT なので、SRTT が RTO の 3 分の 1 を超える経路(RTO が SRTT + 200 ms なら SRTT が 100 ms より長い経路)では、probe の確認が戻る前に RTO が起きて輻輳の窓を 1 segment にします。
  先頭の記録を再送したときは、Linux の `tcp_xmit_retransmit_queue` と同じく RTO を張り直します。
  PTO を RTO の期限に揃えたときは probe を先に処理し、その時刻の RTO は起きません。
  確認の途絶えた通信量の少ない stream では、最後の確認から RTO の後に probe を送り、その後に RTO、2 × RTO、4 × RTO の間隔で再送します。
  RTO は SRTT に 4 × RTTVAR と 200 ms の大きい方を足した値です([TCP の機能](wgstack.md#完成に含める機能)の RFC 6298)。
  根拠は qbench の `thin-send/outage2s` の packet の記録で、外から見た Linux 6.1 の振る舞いです。
  SRTT が約 50 ms で RTTVAR の小さな経路で、Linux は確認の途絶えた先頭の segment を送ってから約 256 ms 後に probe を送り、その後 256、512、1024 ms の間隔で再送しました。
  変更の前の wgstack は、最後の確認から 200 ms 後に probe ではなく RTO を起こし、200、400、800、1600 ms の列で再送していました。
  RTO を 200 ms の下限に丸める式は、RTTVAR の小さな経路で Linux より SRTT の分だけ早く RTO を起こし、PTO より早い RTO の期限で probe を省くのは RFC 8985 7.2 と違うため、どちらも改めました。
  Linux の RTO の下限が RTTVAR の項に掛かることは、この経路の値と、bulk の `send/outage2s` で途絶の終わりの RTO が 1424 ms(SRTT が待ち行列で約 150 ms に伸びた経路の約 356 ms の 4 倍)であることからの推定で、ほかの経路の値は未確認です
  窓の probe(persist)は確認を待つデータの無いときだけ使うので、RACK と TLP の期限と同時には張りません。
  使っていない keepalive の節は、keepalive を有効にするときのために残します
- 不変条件:I5 では、TLP の probe は送り残しの末尾ごとに 1 つだけで、外からの ACK が無ければ RTO に移ります
- 危険:並べ替えの窓が狭すぎると不要な再送が増え、広すぎると損失の発見が遅れます。
  窓に下限は置きません(RFC 8985 と同じ)。
  RTT が数 ms より短い経路では、1 つ目の重複した ACK の直後に穴を再送するので、Limited Transmit の新しい segment より先に再送が出ます
- 期待する効果:再送した segment の損失を RTO なしに見つけるので、損失 5% の RTO の連続を断ちます。
  通信量の少ない stream では、末尾の損失を RTO(200 ms 以上)ではなく約 2 往復で直すので、遅れの p99 の目標に効く主な変更です。
  並べ替えへの耐性も、重複した ACK の数で判定する今の方式より高くなります

### HyStart++

- 規格:RFC 9406 です。
  輻輳の制御の種類によらないので、NewReno のままでも使えます
- 使う構造:slow start の往復ごとの最小の RTT と、慎重な slow start(CSS)の状態を接続の欄に置きます。
  RTT の測定は timestamp と送信の記録で ACK ごとに測った値を使います
- 規則:最初の slow start(ssthresh が初期の値のまま)だけで使い、損失か RTO の後の slow start では使いません。
  往復は、往復を始めた時の SND.NXT を確認した ACK で終えます。
  往復の RTT の標本が 8 つ以上あり、往復の最小の RTT が前の往復の最小より max(4 ms, min(前の最小 / 8, 16 ms)) 以上大きければ CSS に入ります。
  CSS の間の窓の増え方は slow start の 4 分の 1 で、往復の最小の RTT が CSS に入った時の値より小さくなれば slow start に戻り、5 往復続けば ssthresh を今の窓にして輻輳の回避に移ります。
  slow start の 1 ACK の増え方は RFC 3465 の L = 2 のままにします。
  RFC 9406 は pacing の無い送り手に L = 8 を勧めますが、遅延 ACK の 2 segment ごとの ACK では L = 2 で窓が往復ごとに 2 倍になり、L は相手がまとめて確認する場合の送り出す量だけを変えるためです
- 不変条件:新しい保持を作らず、影響は輻輳の窓の値だけです
- 危険:正しさへの危険は低いです。
  早く終えすぎると立ち上がりが遅くなります。
  Linux は RFC 9406 ではなく元の HyStart を使うので、slow start の終わる位置は Linux と一致しません
- 期待する効果:損失 0% の溢れそのものを減らし、SACK による回復と合わせて損失 0% の差を埋めます

### 受信の窓と boost の方針

- 規格:RFC 9293 の窓の規則と受け手の SWS の回避に従い、広告した右端を後ろへ戻さない規則を保ちます
- 方針(実装済み):boost で予約を 4 MiB にしても、広告する右端は一度に進めません。
  [溢れた後の Linux の受け手](#溢れた後の-linux-の受け手)の[広告する窓](#広告する窓)と[受信の窓の自動調整](#受信の窓の自動調整)と同じく、窓を次の 2 つの上限で決めます
  - 窓の上限(Linux の窓の上限と rcvbuf):アプリケーションの読み取りのたびに、受け手の RTT の 1 回の間に読んだ量を測ります。
    読んだ量が前の区間の値を超えたときだけ、目標まで上げます。
    目標は、基本の窓 W = 2 × 読んだ量 + 16 MSS に、W × 増え方の比の 2 倍を足した量です。
    増え方の比は、読んだ量と前の区間の値の差を前の区間の値で割った比です。
    測定では下げず、floor と予約の間に収めます。
    受け手の RTT は、窓による標本(推定より小さいときだけ下げます)と timestamp による標本(小さい標本はそのまま、大きい標本は 8 分の 1 の重みで平滑します)で推定します
  - 歩みの上限(Linux の rcv_ssthresh):順序どおりの 128 byte 以上の segment と、SACK を交渉した接続の順序外の segment を受けるたびに、自分の MSS の 2 倍と中身の 2 倍の大きい方だけ広げます。
    広げた値は、窓の上限と後述の空きの小さい方を超えません。
    最初の値は floor です

  広告する窓は、窓の上限から保持するデータ(未読のデータと順序外のデータ)を引いた空きと、歩みの上限の小さい方で、次に受ける番号から測ります。
  右端は後ろへ戻さず、SWS の回避の量は窓の上限の半分と MSS の小さい方です。
  boost を得るまでは 2 つの上限がどちらも floor なので、窓は今までの floor の窓と同じで、順序外のデータが空きを減らす点だけが違います。
  floor に戻す時は歩みの上限も floor 以下に戻し、測定の値は保ちます。
  Linux は rcvbuf を segment の確保の大きさで数えますが、wgstack の受信の輪は中身だけを持つので、窓の上限を Linux の rcvbuf の窓の換算と同じ量として扱います。
  rcv_ssthresh を広げた segment ごとの quickack([今の wgstack との比べ](#今の-wgstack-との比べ)の違い 4)は入れていません。
  boost を求める時期を早めるか(例えば接続の始めの需要の区間を短くする)は、別の測定で決めます。
  floor に戻った後に古い窓へ届いたデータを捨てる今の方式による止まりは、qbench の 1 本の接続では起きないはずなので、診断で `RecvTrimmed` が 0 でなかった場合だけ直します
- 使う構造:受信の輪と区間の表はそのまま使います。
  2 つの上限、読んだ量の測定の区間、受け手の RTT の推定を接続の欄に置き、区間が持つ順序外の byte の合計を受信のバッファに置きます
- 不変条件:I1 と I2 では、右端を広げるときに、最も古い未読の byte に窓の上限を足した位置を超えず、窓の上限は予約以下なので、受信の保持は増えません(floor に戻した後は、広告済みの右端が縮まずに残ります。その外に届いたデータは受信のバッファに入れずに捨てます)。
  上界の式に新しい項は要らず、足した欄は c_conn に入ります。
  I4 では、SACK を知らせた順序外のデータを捨てない今の規則を保ちます
- 危険:窓を小さく保ちすぎると速さが落ちます。
  測定の区間の間に読まない接続は、窓の上限が floor のままなので、窓も floor を超えません。
  Linux も読み取りで rcvbuf を上げるので、同じ振る舞いです
- 採った理由:以前に試した広げ方は、受け手の RTT ごとの目標を広告する窓の上限に直接使い、右端を最も古い未読の byte から測りました。
  届いた segment ごとの歩みは持たず、順序外のデータは窓を減らしませんでした。
  この形では、受ける向きの損失 0% の gVisor の送り手が 5 回の内 4 回で約 1.6 から 2.5 Mbit/s に止まりました。
  経路の記録では、送り手が窓に抑えられている間に、目標の更新で右端が 1 回に約 1 MB 進みました。
  gVisor の送り手は次の 20 ms に約 200 segment を経路の速さを超えてまとめて送り、その約 150 が待ち行列で失われ、その後は 約 250 ms ごとに 2 segment だけ送る状態に止まりました。
  右端の一度の伸びが約 160 KB だった 1 回は、18.6 Mbit/s で回復しました。
  今の形では、溢れの前の右端の 1 回の伸びは約 12 KB 以下(Linux の受け手で約 5 KB)で、溢れは slow start の普通の溢れになり、溢れの後の回復は Linux の受け手と同じ程度でした。
  時間で区切る関門の行列の受ける向きの場合は、9 回の実行では損失 5% の Linux の送り手の 2 つの場合が未確定になり、36 回の実行で 2 つとも通りました。
  ほかの場合は今までの判定を保ちました。
  測った値は PR の本文にあります

### 受け手の ACK と D-SACK

- 規格:RFC 9293 と RFC 1122 の遅延 ACK、RFC 2883 の D-SACK です
- 方針(実装済み):受けた segment から相手の MSS を推定し、確認していない byte が推定を超えたら ACK を遅らせずに返します(Linux の `__tcp_ack_snd_check`)。
  Linux と同じく、接続の始めの最初のデータと、RTO より長く黙った後のデータで、遅らせずに返す ACK の数(quickack)を広告した窓の 2 MSS ごとに 1 つ、2 から 16 の間で補い、対話の流れでない間は ACK を遅らせません。
  重複した segment(RCV.NXT より前の重複と、順序外の区間の内側の重複)には、その範囲を D-SACK の block として次の ACK の先頭に 1 回だけ載せ、quickack を 2 以上に補います
- 使う構造:推定した MSS、quickack の残り、返す D-SACK の block 1 つを接続の欄に置きます
- 読み終えた時の ACK(実装済み):遅延 ACK を待つ間にアプリケーションの読み取りが受信のバッファを空にしたときは、対話の流れでなければ、segment の大きさによらず ACK をすぐ送ります。
  RFC 1122 4.2.3.2 の遅延 ACK は、アプリケーションが窓を更新し、応答を同じ segment に載せる機会を作るために待ちます。
  読み取りで窓は更新済みで、対話の流れでなければ応答も来ないので、待つ理由が残りません。
  読み手が追いつく間は segment ごとに ACK を返し、これは RFC 5681 4.2 と RFC 9293 3.8.6.3 の「少なくとも 2 つ目の full-sized segment ごと」の規則の内側です。
  読み手が遅れて受信のバッファにデータが残る間は、推定した MSS による 2 segment ごとの規則と遅延 ACK のタイマーに戻ります。
  順序外の segment と穴を埋める segment には、今までどおり遅らせずに ACK を返します(RFC 5681 3.2 と 4.2)。
  Linux はこの ACK を推定した MSS より小さな segment を受けた後に限るので、この規則は Linux との意図した違いです。
  経路の記録では、gVisor と Linux の受け手は順序どおりの ACK の約 45% を 1 segment ごとに返し、wgstack は約 5% でした。
  Linux の受け手が 1 segment ごとに返す原因は確かめていません。
  受ける向きの損失 1%(gVisor の相手)は gVisor と Linux の値に近づきました。
  gVisor の相手の 2 秒の途絶は、どの実装でも約 4.3 か約 10.5 Mbit/s の 2 つの値に分かれ、中央値は 7.37 から 4.40 Mbit/s になりましたが、種ごとの比の区間は前後のどちらも約 0.44 から 1.02 で重なります。
  ほかの受ける向きの場合は下がりませんでした(測った値は #542 にあります)
  対話の流れは、データを受けてから遅延 ACK の時間の内にデータを送ったときに印を付け、遅延 ACK の期限で印を外します(Linux の pingpong)。
  推定した MSS は初期の値を min(536, 自分の MSS) とし、推定以上の segment で更新します(Linux の `tcp_measure_rcv_mss`)。
  この規則が無いと、通信量の少ない stream の受け手は 2 つ目の segment を待たずに遅延 ACK の期限でだけ ACK を返し、送り手の ACK の数が半分になります。
  gVisor の送り手は、輻輳の窓が埋まって新しいデータを送れない間もアプリケーションの書き込みのたびに PTO を張り直すので、末尾の損失と ACK の損失が重なると、書き込みが止まるまで probe も RTO も送らず、損失 5% の通信量の少ない stream の p99 が数秒になりました
- 不変条件:ACK の数は受けた segment の数を超えないので、I5 に触れません
- 測った結果:gVisor の送り手は ACK の数で窓を増やすので、ACK の数が速さを左右します。
  読み終えた時の ACK の後、関門の行列の受ける向きの損失 1% と 5% の種ごとの比の中央値は、Linux の相手で 1.00 になりました。
  関門が判定しない gVisor の相手では、損失 1% が 0.92、損失 5% が 0.98 です
- 危険:低いです。
  quickack と D-SACK は今の[期待した差の一覧](wgstack-verification.md#期待した差の一覧)の行を消すので、一覧の更新を試験の書き手と所有者が行います
- 期待する効果:受ける向きの相手の slow start と不要な再送の扱いを Linux に近づけます
- 未確認:速い経路での ACK の数と、受けた byte あたりの CPU は測っていません。
  ACK 1 つごとに WireGuard の暗号化と送信が 1 回かかります

### 溢れた後の Linux の受け手

[受信の窓と boost の方針](#受信の窓と-boost-の方針)の測った結果では、Linux と同じ窓の広げ方を wgstack に入れると、溢れの後の gVisor の送り手の回復が長く続き、受ける向きの損失 0% が 2.51 Mbit/s に落ちました。
参照の Linux は同じ広げ方で 18.48 Mbit/s に届きます。
この節は、溢れの後の Linux の受け手の挙動を、実装する人が Linux のコードを読まずに作れる形で定めます。
窓の広げ方を採る条件は、この節の挙動を wgstack に入れ、後述の適合の場面で Linux と一致することです。
wgstack との違いと適合の場面は、決定ではなく計画と未確認の点として書きます。

#### 参照のカーネル

参照は、ラボの VM のカーネルの Debian の 6.1.0-53 の TCP の受け手です。
基の版は mainline の `v6.1` のタグで、Debian の bookworm の changelog では 6.1.0-38 が 6.1.147-1 なので、6.1.0-53 は `v6.1` の後の次の修正を含みます。

- `tcp: fix delayed ACKs for MSS boundary condition`(6.1.64-1 から):推定した MSS と同じ大きさで PSH を持つ segment も、読み終えた時の ACK の「小さな segment」に数えます
- `tcp: enforce receive buffer memory limits by allowing the tcp window to shrink`(6.1.64-1 から):`tcp_shrink_window` を足し、既定の 0 では窓を縮めない今までの規則のままです
- `tcp: fix mishandling when the sack compression is deferred.`(6.1.37-1 から):圧縮した ACK のタイマーが、アプリケーションがソケットを持つ間に切れた場合も ACK を送ります
- `tcp: always seek for minimal rtt in tcp_rcv_rtt_update()`(6.1.147-1 から):受け手の RTT の推定の平滑が変わります(後述)
- `tcp: fix initial tp->rcvq_space.space value for passive TS enabled flows`(6.1.147-1 から):受信の窓の自動調整の最初の値が少し小さくなります(後述)
- `tcp: fix tcp_ofo_queue() to avoid including too much DUP SACK range`(6.1.148-1 から):順序外のデータを順序どおりにする時の D-SACK の範囲を重なりだけにします

関数の名前は、Linux の挙動を確かめる人のための目印です。

#### 受け手の MSS の推定

Linux は ACK の判定に、相手が送る segment の大きさの推定(rcv_mss)を使います。
最初の値は、自分の MSS、相手の MSS、最初の窓の半分、536 の最小で、88 を下限にします(`tcp_initialize_rcv_mss`)。
推定以上の大きさの segment を受けると、推定をその大きさ(自分の広告した MSS 以下)にします。
推定より小さい segment は、PSH の無い segment か 536 byte 以上の segment が同じ大きさで 2 つ続いたときだけ推定を下げます(`tcp_measure_rcv_mss`)。
推定より小さい segment を受けた事実は、読み取りの時の ACK の判定に残します。
wgstack は推定を実装済みで([受け手の ACK と D-SACK](#受け手の-ack-と-d-sack))、この節の規則はこの推定を使います。

#### ACK を返す時期

Linux は data を持つ segment を処理するたびに、次の順で ACK を返すかを決めます(`__tcp_ack_snd_check`)。
前に ACK を送ってから data を送った場合は、その segment が ACK を運んだので判定しません。

1. 2 segment の規則:前に窓を広告した時の RCV.NXT から、推定した MSS より多く受けていて、かつ今広告できる窓が前に広告した窓の大きさ以上なら、すぐに ACK を返します。
   後半の条件は、読み手が遅れて受信のバッファが埋まる間、右端が受けた分だけ進められないときに ACK を遅らせ、読み取りの時の ACK に任せるためのものです。
   アプリケーションが SO_RCVLOWAT を未読の量より大きくしているときは、後半の条件を見ません。
   qbench と適合の試験は SO_RCVLOWAT を変えないので、この例外に当たりません
2. quickack:quickack の残りが 1 以上で、対話の流れでないなら、すぐに ACK を返します(次節)。
   rcv_ssthresh を広げた segment は残りを持つので、順序外の segment も含めてこの規則で ACK を返します
3. 一度だけの即時の印:穴を埋めた segment が順序外のデータをすべて順序どおりにした時に付けた印があれば、すぐに ACK を返します(RFC 5681 4.2)
4. 遅延 ACK:順序外のデータが無ければ、遅延 ACK のタイマーを張ります
5. 順序外のデータがある場合:SACK を交渉していなければ、すぐに ACK を返します。
   SACK を交渉していれば、後述の SACK の圧縮に従います。
   SACK の圧縮に届くのは、2 の規則に当たらない ACK だけです

穴の一部だけを埋めた segment は、RCV.NXT を進めるので、1 か 5 の規則ですぐに ACK を返します。
5 の規則の数は RCV.NXT の値ごとに数え直すためです。
SACK を交渉した接続では、順序外の segment も rcv_ssthresh を広げます(後述の広告する窓)。
このため、rcv_ssthresh を広げる余地がある間は、Linux はすべての順序外の segment に 2 の規則ですぐに ACK を返します。
SACK の圧縮が働くのは、rcv_ssthresh が窓の上限に届いたか、順序外のデータと未読のデータが空きを使って広げる余地が無くなった後です。

Linux 4.18 から入った SACK の圧縮は、順序外のデータがある間の ACK の数を減らします。

- 即時の 3 つ:RCV.NXT が同じ値の間の最初の 3 つの ACK は、すぐに返します。
  RCV.NXT が変わると数を 0 に戻します
- 圧縮:4 つ目からは ACK を遅らせ、遅らせた数を数えます。
  遅らせた数が `tcp_comp_sack_nr`(44)に届くとすぐに返します。
  そうでなければ、最初に遅らせた時に、1 ms と、受け手の RTT の推定と SRTT の小さい方の 5% の小さい方の時間(猶予 100 µs)のタイマーを張り、期限で 1 つの ACK を返します。
  受け手の RTT の推定がまだ無い間は 5% の項が 0 になり、タイマーは猶予の内に切れます。
  タイマーが切れた時にアプリケーションがソケットを持っていれば、ソケットを離した時に ACK を送ります
- 前の ACK の先送り:届いた順序外の segment が、最近の順で 3 つ目以降の SACK の block を伸ばすときと、block を 2 つ以上覚えている間に新しい block を作るときは、遅らせていた ACK をその前にすぐ返します
- 打ち消し:ACK を運ぶ segment を送ると、遅らせた数とタイマーを消します

片道 25 ms、20 Mbit/s の qbench の経路では、タイマーは 1 ms で、MTU の segment の間隔は約 0.6 ms です。
このため、rcv_ssthresh を広げる余地が無い間の Linux は、RCV.NXT が変わった直後の 3 つの後に、約 2 segment に 1 つの ACK を返します。
RFC 5681 3.2 と 4.2 は、順序外の segment ごとにすぐに重複した ACK を返すことを SHOULD とするので、圧縮は Linux の RFC からの逸脱です。
各 ACK は最新の SACK の block を運ぶので、受けた byte で損失を決める RFC 6675 の送り手は情報を失いません。
重複した ACK の数で決める送り手は、最初の 3 つで閾値に届きます。

遅延 ACK のタイマーの長さは、データの到着の間隔から決める ato です。
ato の最初の値と下限は 40 ms です。
間隔が 20 ms 以下なら ato を半分にして 20 ms を足し、間隔が ato より短ければ半分にして間隔を足し(RTO を上限)、間隔が RTO より長ければ quickack の数を補います(`tcp_event_data_recv`)。
タイマーの長さは ato です。
ato が 40 ms より大きいときは、SRTT(40 ms 以上)で抑えます。
どの場合も 200 ms(`TCP_DELACK_MAX`)を上限にします。
すでに張ったタイマーの期限が今から ato の 4 分の 1 以内なら、タイマーを待たずにすぐ ACK を返します。
タイマーが切れた時に対話の流れでなければ ato を 2 倍(RTO まで)にし、対話の流れなら対話の流れの印を外して ato を 40 ms に戻します。
対話の流れの印は、data を受けてから ato の内に data を送った時に付きます。

読み取りの後にも、次の条件で ACK を返します(`tcp_cleanup_rbuf`)。

- 2 segment 分:ACK を待つ間に、前に窓を広告した時から推定した MSS より多く受けていれば返します
- 読み終えた時:ACK を待つ間に、読み取りで受信のメモリがすべて空になり、推定より小さい segment を受けていて、対話の流れでなければ返します。
  推定より小さい segment を 2 つ続けて受けていれば、対話の流れでも返します。
  受信のメモリは順序外のデータを含むので、穴の後ろにデータを持つ間は、読めるデータをすべて読んでもこの ACK は出ません
- 窓の更新:前の 2 つに当たらず、受信の向きが閉じていなければ、残りの窓(広告した右端から RCV.NXT まで)を確かめます。
  残りの窓の 2 倍が窓の上限以下のときだけ、新しく選べる窓を求めます。
  新しい窓が 0 でなく、残りの窓の 2 倍以上なら返します

次の segment には、quickack の数を最大 16 まで補い、すぐに ACK を返します。

- RCV.NXT より前の data だけを持つ segment:D-SACK を付けます(後述)
- 窓の右端ちょうどから始まる segment:segment を捨てます。
  窓が 0 の時に RCV.NXT から送られた segment(1 byte の窓の probe を含みます)がこれに当たります

窓の右端より先から始まる segment は、番号の確かめで捨て、窓の外の ACK の速さの制限(`tcp_invalid_ratelimit`、既定で 500 ms に 1 つ)の内側で重複した ACK を返します。
この ACK は quickack の数を補わず、D-SACK を付けません。
PAWS で捨てた segment も同じ速さの制限の内側で重複した ACK を返し、RCV.NXT より前の data を持つときだけ quickack の数を補い、D-SACK を付けます。

#### quickack の数

quickack の残りは、遅らせずに返す ACK の数です。
補う時は、今の受信の窓を推定した MSS の 2 倍で割った数を、上限(16 か 2)で抑え、0 なら 2 にし、残りより大きいときだけ置き換えます(`tcp_incr_quickack`)。
補う時と上限は次のとおりです。

- 接続の最初の data:上限 16
- RTO より長い間の後の data:上限 16
- RCV.NXT より前の data と、窓の右端ちょうどから始まる data:上限 16 で、対話の流れの印を外し、ato を 40 ms に戻します(`tcp_enter_quickack_mode`)
- ECN の CE:上限 2(wgstack は ECN を交渉しないので当たりません)
- rcv_ssthresh を広げた segment:順序外の segment を含み、残りの最も下の bit を立てます(`tcp_grow_window`)。
  残りが偶数なら 1 増え、奇数ならそのままです。
  rcv_ssthresh を広げている間は、広げた segment のたびに ACK をすぐに返します

ラボのカーネルでは、ACK を返す必要がある間に送った ACK を運ぶ segment ごとに、残りを 1 つ減らします。
`v6.1` のタグは、送った segment の数だけ減らしていました。
新しいデータを確認する ACK では、どちらも同じです。
ACK を返す必要の無い間に送る中身の無い ACK(窓の更新など)は、ラボのカーネルでは残りを減らさず、`v6.1` のタグでは減らしていました。
残りが尽きた時は ato を 40 ms に戻します。
今広告できる空きが窓の上限の半分より少なくなった時と、受信のバッファの上限を超えた時(後述)は、残りを 0 にします。

[受け手の ACK と D-SACK](#受け手の-ack-と-d-sack)の経路の記録で、Linux の受け手が順序どおりの ACK の約 45% を 1 segment ごとに返した原因は確かめていません。
rcv_ssthresh を広げた segment ごとの quickack は、この原因の候補です。

#### SACK の block

Linux は最近の順の SACK の block を 4 つまで覚えます(`tcp_sack_new_ofo_skb`)。

- 順序外の segment:segment の範囲が覚えた block に接するか重なれば、その block を伸ばして先頭に移し、伸ばした block が後ろの block に接するか重なればまとめます。
  接する block が無ければ、新しい block を先頭に置き、4 つを超えた最も古い block を忘れます
- 順序外の区間の内側の重複:segment を捨て、範囲を含む block を先頭に移します
- RCV.NXT が進んだ時:RCV.NXT までに入った block を消し、順序外のデータが無くなればすべて消します(`tcp_sack_remove`)
- 順序外のデータを捨てた時:すべての block を忘れます(後述の受信のバッファの圧迫)

ACK に載せる block は、D-SACK の block、覚えた block の最近の順の並びで、option の残りの空きに入るだけです。
timestamp を使う接続では 3 つ、使わない接続では 4 つです。
timestamp を使う接続で D-SACK があれば、SACK の block は最近の 2 つになります。
忘れた block は、その範囲に segment がまた届くまで知らせません。
覚えた block の外の区間で残りの欄を埋めることはしません。
RFC 2018 4 節は、先頭の block を ACK を起こした segment を含む block にすること(MUST)と、最近に知らせた block を繰り返して欄を埋めること(SHOULD)を求め、Linux はその内側です。

#### D-SACK

D-SACK(RFC 2883)は SACK を交渉した接続だけで、`tcp_dsack=1` のときに返します(`tcp_dsack_set`、`tcp_dsack_extend`)。
範囲は次のとおりです。

- RCV.NXT より前の data だけを持つ segment:segment の範囲です
- RCV.NXT より前から始まり先へ続く segment:segment の始まりから RCV.NXT までで、残りは受け入れます
- 順序外の区間の内側の重複:segment の範囲です
- 順序外の segment の前の部分が、順序外の既存の segment に重なるとき:segment の始まりから、重なる segment の終わりまでです
- 順序外の segment が後ろの既存の segment を覆うとき:覆った segment の範囲を D-SACK に足します。
  足すのは、今の D-SACK の block に接するか重なる範囲だけで、block は 1 つのままです
- 順序外のデータを順序どおりにする時に、すでに届けた範囲と重なるとき:重なりだけを D-SACK に足します。
  `v6.1` のタグは、ここで重なりより広い範囲を知らせることがありました

D-SACK の block は次の ACK の先頭に 1 回だけ載せ、載せた時に消します。
RFC 2883 4 節は、D-SACK の block が最も新しく受けた packet の重複だけを知らせ、重複した 1 つの範囲を 1 つの D-SACK の block でだけ知らせることを求めます。
このため Linux は data を持つ segment を処理する初めに、まだ送っていない D-SACK を消します。
RCV.NXT より前の data だけを持つ重複は quickack ですぐに ACK を返すので、その D-SACK は必ず送ります。
RCV.NXT をまたぐ segment の D-SACK は quickack を伴いません。
穴が無く、新しいデータが推定した MSS より少ないと ACK が遅れ、その間に次の data が届くと D-SACK を送らずに失います。
順序外の区間の内側の重複も、SACK の圧縮で ACK が遅れる間に次の data が届くと、D-SACK を失います。
順序外の重複では、範囲を含む block を先頭に移すので、D-SACK の次の block は重複を含む区間になります(RFC 2883 4 節の 2 つ目の block の規則)。

#### 受信のバッファの圧迫

Linux は受信のメモリを segment の確保の大きさ(truesize)で数え、ソケットの受信のバッファの上限(rcvbuf)と比べます。
`tcp_adv_win_scale=1` では、メモリの半分を窓に換算します。
6.6 から、この換算はソケットごとの比に替わりました(`tcp: get rid of sysctl_tcp_adv_win_scale`)。
ラボの 6.1 は半分の換算です。

segment を受信の待ち行列か順序外の待ち行列に入れる前に、使っているメモリが rcvbuf を超えているか、メモリを確保できなければ、次の順に空けます(`tcp_try_rmem_schedule`、`tcp_prune_queue`)。
受信の待ち行列が空の時の順序どおりの segment は、この確かめをせずに必ず受け入れます。

1. 窓の締め付け:使っているメモリが rcvbuf 以上なら、quickack の残りを 0 にします。
   rcvbuf が `tcp_rmem` の上限より小さく、ソケットに SO_RCVBUF が設定されておらず、システム全体のメモリの圧迫が無ければ、rcvbuf を使っている量(上限まで)に上げます。
   それでも使っている量が rcvbuf を超えていれば、rcv_ssthresh を窓の上限と自分の MSS の 2 倍の小さい方にします(`tcp_clamp_window`)。
   システム全体のメモリの圧迫の間は、rcv_ssthresh を MSS の 4 倍以下にします
2. まとめ直し:順序外の待ち行列の連続した範囲と、未読のデータを、確保の無駄の少ない buffer に写し直します(`tcp_collapse`)。
   1 つの segment だけからなり中身が 1 page より小さい順序外の範囲は写しません。
   そのような範囲の確保の合計が rcvbuf の 8 分の 1 を超えると、順序外の待ち行列のまとめ直しをそこでやめます
3. 順序外のデータの取り消し:それでも上限を超えていれば、最も大きな番号の segment から順に、rcvbuf の 8 分の 1 以上を捨て、上限を下回るまで続けます。
   捨てた後は、すべての SACK の block を忘れます(`tcp_prune_ofo_queue`)。
   最も遠いデータから捨てるのは、穴が埋まる見込みを残し、多数の segment が待つ遅れを避けるためです
4. 届いた segment の破棄:それでも上限を超えれば、届いた segment を捨てます

メモリの不足で捨てた順序外の segment には、ACK も D-SACK も返しません。
3 は SACK で知らせたデータの取り消し(reneging)で、RFC 2018 8 節は受け手のバッファが尽きた場合に許します。
送り手は RTO の後にそのデータを送り直します。
wgstack は SACK で知らせた順序外のデータを捨てず(I4)、この挙動を真似ません。

#### 広告する窓

Linux は ACK を送るたびに窓を選びます(`__tcp_select_window`、`tcp_select_window`)。

- 空き:rcvbuf から使っているメモリを引いた量の半分です。
  順序外のデータと未読のデータは、確保の大きさで空きを減らします
- 全体:窓の上限と rcvbuf の半分の小さい方です
- 空きが全体の半分より少ないとき:quickack の残りを 0 にし、空きを窓の scale の単位に切り下げます。
  空きが rcvbuf の半分の 16 分の 1 より少ないか、推定した MSS より少なければ、0 の窓を選びます
- 窓:空きと rcv_ssthresh の小さい方を、窓の scale の単位に切り上げます
- 縮めない規則:`tcp_shrink_window=0` では、選んだ窓が前に広告した右端までの残りより小さければ、残りを窓の scale の単位に切り上げて広告します。
  右端は後ろへ戻りません(RFC 9293 3.8.6 の SHLD-14)

窓を選んだ時に、その時の RCV.NXT と窓を覚え、[ACK を返す時期](#ack-を返す時期)の 2 segment の規則の基準にします。
穴がある間は RCV.NXT が進まず、順序外のデータが空きを減らします。
空きが rcv_ssthresh より小さい間は、選んだ窓が前の残りより小さくなりやすく、そのときは縮めない規則で前と同じ右端を広告するので、重複した ACK の窓の欄は変わりません。
rcv_ssthresh が小さい方の間は、順序外の segment が rcv_ssthresh を約 2 MSS ずつ広げるので、選んだ窓が前の残りを超え、重複した ACK ごとに窓の欄が大きくなります。
RFC 5681 2 節の重複した ACK の定義(e)は窓の欄が変わらないことを求め、gVisor の送り手はこの定義で重複した ACK を数えます。
SACK を交渉しない接続で Linux が順序外の segment で rcv_ssthresh を広げないのは、窓の欄を変えずに重複した ACK を数えさせるためです(`tcp_data_queue_ofo`)。

rcv_ssthresh は、窓を一度に広げないための窓の上限です。

- 最初の値:握手で決めた最初の窓です。
  受動の open では rcvbuf の最初の値(`tcp_rmem` の 2 つ目の値、既定 128 KiB)の半分を MSS の倍数に切り下げた値で、約 64 KB です
- 広げる時:順序どおりの 128 byte 以上の data と、SACK を交渉した接続の順序外の data を受けた時です(`tcp_grow_window`)。
  広げる余地は、窓の上限と空きの小さい方から rcv_ssthresh を引いた量で、余地が無いか、システム全体のメモリの圧迫の間は広げません
- 広げる量:segment の確保の大きさが中身の 2 倍以下なら、自分の MSS の 2 倍と中身の 2 倍の大きい方です。
  確保の大きさが中身の 2 倍を超えるなら、rcv_ssthresh が `tcp_rmem` の上限に中身と確保の大きさの比(2 のべきに切り下げた比)を掛けた値以下の間だけ、推定した MSS の 2 倍(中身の 2 倍以上)です。
  どちらも余地を超えません
- 縮める時:前節の窓の締め付けと、システム全体のメモリの圧迫の時です

窓の scale は、`tcp_rmem` の上限と `rmem_max` の大きい方を表せる値で、4 MiB では 7 です。
最初の窓は約 64 KB で、wgstack は最初から floor の 256 KiB を広告します([変えないもの](#変えないもの))。

#### 受信の窓の自動調整

この節の規則は、`tcp_moderate_rcvbuf=1` で、アプリケーションが SO_RCVBUF を設定していない接続だけに働きます。
性能の参照の Linux(`linuxdut.PinPerformance` と、待ち受けに SO_RCVBUF を与えない `linuxdut.NewPerformance`)はこの条件を満たします。
適合の試験の固定の値(`tcp_moderate_rcvbuf=0` と待ち受けの SO_RCVBUF)では、自動調整も、窓の締め付けでの rcvbuf の引き上げも働きません。

Linux の受信の窓の自動調整(`tcp_rcv_space_adjust`、Dynamic Right-Sizing)は、rcvbuf と窓の上限だけを広げ、広告する窓を直接は広げません。
広告する窓は前節の空きと rcv_ssthresh で決まるので、窓は届いた segment ごとに rcv_ssthresh が広がる分だけ開きます。

受け手の RTT の推定(`rcv_rtt_est`)は 2 つの標本で決めます。

- 窓による標本:どの接続でも、data を受けるたびに、標本の始めの RCV.NXT に窓を足した番号を RCV.NXT が越えたかを見て、越えるまでの時間を標本にします(`tcp_rcv_rtt_measure`)。
  この標本は、今の推定より小さいときだけ推定を下げます
- timestamp による標本:timestamp を使う接続では加えて、推定した MSS 以上の data を持ち、前の標本と違う TSecr を持つ segment ごとに、今の時刻と TSecr の差を標本にします(`tcp_rcv_rtt_measure_ts`)。
  ラボのカーネルでは、今の推定より小さい標本をそのまま推定にし、大きい標本は 8 分の 1 の重みで平滑します。
  `v6.1` のタグは、timestamp による標本を、小さい標本も含めて平滑していました。
  窓による標本は、`v6.1` のタグでも今と同じく最小だけを取ります

アプリケーションが読むたびに、次の規則で rcvbuf を決めます。

- 測る区間:前の区間の始めから受け手の RTT の推定より短ければ、何もしません。
  推定が無い間も何もしません
- 読んだ量:区間の間にアプリケーションが読んだ byte を copied とします。
  copied が前の区間の値以下なら、区間を始め直すだけです。
  最初の前の区間の値は、rcv_ssthresh、最初の窓、MSS の 10 倍の最小です。
  ラボのカーネルでは、受動の open で timestamp を使う接続のこの MSS を、timestamp の option の 12 byte を引いた値にします
- 目標:copied の 2 倍に MSS の 16 倍を足した量を基本の窓にします。
  損失の回復の間に 2 倍、揺れに 16 MSS を見込む量です。
  前の区間からの増え方の比(copied と前の値の差を前の値で割った比)を基本の窓に掛け、その 2 倍を足します。
  slow start の送り手が次の往復で 2 倍に増やす分を見込む量です
- rcvbuf:目標を MSS の数に直し、MTU の大きさの segment 1 つの確保の大きさ(窓に換算して MSS 以上になる大きさ)を掛け、`tcp_rmem` の上限で抑えます。
  今の rcvbuf より大きいときだけ rcvbuf を上げ、窓の上限を rcvbuf の窓の換算(半分)にします。
  rcvbuf と窓の上限を下げることはありません
- 前の区間の値:copied を次の区間の比べの値にします

例えば、前の区間の値が 64 KiB で、次の往復に 128 KiB を読むと、基本の窓は約 279 KiB、増え方の比は 1 で、目標は約 837 KiB です。
この時に広告する窓は、rcv_ssthresh が届いた segment ごとに MSS の 2 倍ずつ広がる量に留まります。

#### 溢れた後に送り手を助ける挙動

前の各節のうち、まとまった損失の後の送り手の回復に効く挙動を、効き方とともにまとめます。

- 重複した ACK の窓の欄を変えないこと:空きが rcv_ssthresh より小さい間は、縮めない規則で右端が止まり、重複した ACK の窓の欄が変わりません。
  RFC 5681 2 節の定義で重複した ACK を数える送り手が、閾値に届きます。
  rcv_ssthresh が小さい方の間は、窓の欄は ACK ごとに大きくなります
- 順序外の segment への即時の ACK:rcv_ssthresh を広げる余地がある間はすべての順序外の segment に、余地が無い間は RCV.NXT ごとの最初の 3 つに、すぐに ACK を返します。
  送り手は 1 往復の内に損失を検出し、部分の確認ごとに次の穴を送り直せます
- 穴を埋めた時の即時の ACK:最後の穴を埋めた segment と、穴の一部を埋めた segment には、すぐに ACK を返します(RFC 5681 4.2)
- 窓の伸びを届いた segment に結ぶこと:rcv_ssthresh は届いた segment ごとにしか広がらず、穴がある間は順序外のデータが空きを減らすので、溢れの間に送り手へ新しい窓を開きにくくなります。
  送り手が回復の間に送る新しいデータは、穴ができた時に広告済みの右端の近くまでに限られ、溢れを重ねにくくなります
- 不要な再送の D-SACK:送り手は不要な再送を見分け、窓の縮小を取り消せます(RFC 2883、RFC 3708)
- SACK の圧縮:rcv_ssthresh を広げる余地が無い間だけ ACK の数を減らし、各 ACK は最新の block を運びます。
  ACK の数で窓を増やす送り手と、ACK ごとに送る量を決める送り手には、ACK の数の差が効きます

#### 今の wgstack との比べ

今の wgstack の受け手を、コードを読まずに、設計の文書と qbench の経路の記録(`QBENCH_TRACE`)で比べました。
記録は、ホストで受ける向きの損失 0% を gVisor の送り手と Linux の送り手で 1 回ずつ流したもので、値は #566 の本文にあります。
ホストのカーネルは Fedora の 7.2 で、SACK の圧縮の既定と窓の換算がラボの 6.1 と違うので、Linux の値は参考です。
今の一度の拡大の wgstack は、gVisor の送り手の溢れからの回復で Linux とほぼ同じ速さと再送の数でした。
SACK の block の数と順、順序外の重複の D-SACK、穴を埋めた時の即時の ACK にも違いは見えませんでした。
遅い回復は、試した窓の広げ方を入れた時だけ起きます。

試した広げ方は、受け手の RTT ごとの目標を広告する窓の上限に直接使い、右端をアプリケーションの読んだ位置から測ります。
届いた segment ごとの rcv_ssthresh の歩みは持たず、順序外のデータは広告する窓を減らしません。
この形は、実装する人が試した広げ方を戻す時に確かめます。

次の違いは、前の各節の Linux の挙動と、wgstack の挙動の差です。
遅い回復を説明しうる順に並べ、どれも未確認の仮説です。

1. 窓の上限と広告する窓の分け方:Linux の自動調整は rcvbuf と窓の上限だけを上げ、下げません。
   広告する窓は空きと rcv_ssthresh の小さい方で、届いた segment ごとに開き、順序外のデータが空きを減らす間は右端が止まります。
   試した広げ方は目標を窓に直接使い、順序外のデータで窓を減らさないので、溢れの間も送り手に新しい窓を開き、溢れを重ねると考えます
2. 2 segment の規則の窓の条件:Linux は、今広告できる窓が前の窓より小さい間は、2 segment の規則で ACK を急ぎません。
   wgstack の設計は推定した MSS による 2 segment ごとの規則だけを定め、窓の条件を持ちません。
   窓が小さい間に、右端の進まない ACK を多く返すことになります
3. 穴がある間の ACK の数:Linux は rcv_ssthresh を広げる余地がある間はすべての順序外の segment に、余地が無くなると RCV.NXT ごとの最初の 3 つの後に約 2 segment に 1 つの ACK を返します。
   wgstack は順序外の segment ごとに ACK を返します。
   gVisor の送り手は ACK ごとに pipe で送る量を決めるので、ACK の数の差で送る量は変わらないと見込みます。
   遅い回復の原因である見込みは低く、Linux との一致と ACK 1 つあたりの暗号化の CPU に関わります
4. rcv_ssthresh を広げる時の quickack:Linux は窓を開く間、広げた segment ごとに ACK を返します。
   ACK の数で窓を増やす送り手は slow start で速く育つので、この挙動は溢れを大きくする向きに効き、回復を速める向きには効きません。
   3 の SACK の圧縮が働くかもこの挙動で決まります
5. 読み取りの後の ACK:wgstack はすでに Linux の読み取りの時の確かめに倣い、残りの窓が容量の半分以下で、新しい窓が残りの窓の 2 倍以上になると窓の更新を返します。
   この規則は設計の文書に無く、実装する人が確かめ、[受け手の ACK と D-SACK](#受け手の-ack-と-d-sack)に規則を記録します。
   Linux の読み終えた時の ACK は、順序外のデータを持つ間は出ません。
   wgstack の読み終えた時の ACK が順序外のデータを数えるかは、設計の文書に無く未確認です

#### 確かめる手順

違い 1 は、適合の場面を書く前に、qbench の A/B の実行で確かめます。

- A:試した窓の広げ方を、そのままの形で戻します
- B:同じ広げ方で、広告する窓を Linux と同じ形で選びます。
  空きは保持する順序外のデータで減り、広告する窓は空きと、届いた segment ごとに広がる rcv_ssthresh の小さい方です

どちらも `recv/loss0%` を `QBENCH_TRACE` 付きで流し、gVisor の送り手の再送、待ち行列の溢れ、回復の長さ、穴がある間の右端と窓の欄を比べます。
B が Linux と同じように回復すれば、違い 1 が遅い回復の原因と決まり、適合の場面を待たずに次の段に進めます。
Linux の記録はラボの VM で取り、Fedora の 7.2 のホストでは取りません。

確かめた結果、B は Linux の受け手と同じように回復しました。
遅い回復の原因は、違い 1 のうち、測定の目標を広告する窓に直接使い、窓を届いた segment ごとに開かないことでした。
A では、送り手が窓に抑えられている間に、受け手の RTT ごとの目標の更新で右端が 1 回に約 1 MB 進み、gVisor の送り手がまとめて送った segment の大半が待ち行列で失われ、送り手が 約 250 ms ごとに 2 segment だけ送る状態に止まりました。
B と Linux では、溢れの前の右端の 1 回の伸びが届いた segment 数個分に留まり、溢れは slow start の溢れになります。
違い 1 のもう一つの点(順序外のデータで空きを減らすこと)を外した B でも、5 回とも Linux と同じ程度に回復したので、この場合の回復には効いていません。
この点は Linux の挙動として残します([受信の窓と boost の方針](#受信の窓と-boost-の方針))。
B は違い 2 から 5 を持ったまま回復したので、これらはこの場合の回復を左右しません。
一致は適合の場面で確かめます。

#### 適合の場面の案

次の場面は、前の違いを Linux を参照にして捉えるための案です。
台本の名前と確かめの名前は仮で、確かめの範囲は Linux で測った値から試験の書き手が決めます。
今の参照の Linux の設定は `tcp_dsack=0`、`tcp_moderate_rcvbuf=0` と待ち受けの SO_RCVBUF の固定を持つので、各場面は族の値を重ねます。
SACK の圧縮は今の設定でも既定のまま有効です。
どの場面も、timestamp と SACK と窓の scale を握手で許します。

- `rcv-window-pacing`(違い 1 と 4):族は性能の参照の Linux で、`linuxdut.PinPerformance` の値と、待ち受けに SO_RCVBUF を与えない `linuxdut.NewPerformance` を使います。
  wgstack は受け付けの時に boost を与え(`BoostAtAccept`)、窓の広げ方を入れた後に流します。
  試験の側は往復 50 ms の経路として振る舞い、5 つの往復に 10、20、40、80、80 個の segment を 0.5 ms の間隔で送ります。
  80 個の往復は 40 ms で終わるので、往復は重なりません。
  アプリケーションはすぐにすべてを読みます。
  確かめは 3 つです。
  1 つ目は、どの ACK でも右端の前の最大からの伸びが、前の ACK から届いた segment の数の 3 MSS 倍と窓の scale の単位 1 つ以下であることです(Linux の rcv_ssthresh の歩み)。
  前の ACK から新しい segment が届かずに読み取りの後に出た窓の更新の ACK は、この確かめから外します。
  2 つ目は、右端が後ろへ戻らないことです。
  3 つ目は、往復 5 の最初の segment を失わせ、穴がある間の重複した ACK の右端の伸びと窓の欄の変わった数が、Linux で測った範囲に入ることです。
  最後に穴を埋め、すべてを確認する ACK がすぐに出ることを確かめます。
  測る値は、往復ごとの最大の右端、quickack の ACK(1 segment で返した ACK)の数、穴がある間の ACK の数です
- `ofo-ack-pattern`(違い 3 と D-SACK):族の値は今の固定の値に `tcp_dsack=1` を重ねたものです。
  待ち受けの SO_RCVBUF は 256 KiB なので、rcvbuf は 512 KiB、窓の上限は約 256 KiB(`tcp_app_win` が 1 segment を残すので 256 KiB から 1 MSS を引いた値)、最初の rcv_ssthresh は約 64 KB です。
  場面は rcv_ssthresh の 2 つの状態を順に確かめます。
  広げる余地のある状態では、接続の始めに順序どおりの 10 segment の後に 1 segment を失わせ、20 個の順序外の segment を 0.6 ms の間隔で送ります。
  確かめは、どの順序外の segment もすぐに重複した ACK を起こすことです。
  重複した ACK の窓の欄は、この状態では大きくなるので測るだけにします。
  接続の始めは最初の quickack の残り(16 まで)もすぐに ACK を返させるので、この状態の ACK の数を比べるときは、rcv_ssthresh を広げた quickack と最初の quickack を分けられません。
  確かめの結果はどちらでも同じです
  次に穴を埋め、アプリケーションが読む間に順序どおりの segment を送り、広告された窓が窓の上限の 256 KiB に届いて変わらなくなるまで続けます。
  広げる余地の無い状態では、アプリケーションは読まず、1 segment を失わせて 20 個の順序外の segment を同じ間隔で送ります。
  確かめは、最初の 3 つの順序外の segment がそれぞれすぐに重複した ACK を起こすこと、どの順序外の segment もそれを含む block を先頭に持つ ACK で 2 ms 以内に知らされること、すべての重複した ACK の窓の欄が同じであることです。
  残りの 17 の segment への ACK の数と ACK の間の最大の時間は、SACK の圧縮を採るかの決定まで測るだけにします。
  どちらの状態でも、ACK の SACK の block が 3 つ以下であることを確かめます。
  続けて、順序外の区間の内側の重複、RCV.NXT より前の重複、RCV.NXT をまたぐ重複を 1 つずつ送り、D-SACK の範囲、2 つ目の block が重複を含む区間であること、D-SACK が 1 つの ACK にだけ載ることを確かめます。
  広げる余地の無い状態では、順序外の区間の内側の重複への ACK が SACK の圧縮で遅れ、その間に次の segment が届くと D-SACK を失います。
  このため、重複の segment どうしの間を圧縮のタイマーより長い 2 ms 以上空けます。
  RCV.NXT をまたぐ重複は、D-SACK を失わないように、次の segment を遅延 ACK の期限の後に送ります。
  最後に穴を埋め、すべてを確認し SACK の block を持たない ACK がすぐに出ることを確かめます
- `read-window-update`(違い 2 と 5):今の固定の値のまま流します。
  試験の側は、アプリケーションが読まない間に、窓の上限の 256 KiB(wgstack では floor の 256 KiB)の 4 分の 3 の 192 KiB まで、または広告された窓が閉じるまで segment を送ります。
  Linux が 192 KiB の未読のデータを 512 KiB の rcvbuf に持てるのは、segment の確保の大きさが中身の約 2 倍以下のときだけで、それより大きければ 192 KiB の前に窓を閉じるかまとめ直しをします。
  このため、Linux の実行ではソケットのメモリ(`ss -m`)を記録します。
  空きが窓の上限の半分を下回るまでは、rcv_ssthresh を広げる quickack で segment ごとに ACK が出ることがあるので、違い 2 の窓の条件は空きが半分を下回った後の ACK でだけ測ります。
  その後アプリケーションがすべてを読みます。
  確かめは、読み取りの後、壁時計では 100 ms 以内、手で進める時計では時計を進める前に、窓の欄が読み取りの前の残りの窓の 2 倍以上の ACK が出ることです(Linux の `tcp_cleanup_rbuf`)。
  読み取りで受信のバッファが空になる場合と、半分だけ読む場合の 2 つを流します。
  3 つ目の場合として、穴の後ろに順序外のデータを持ったまま読めるデータをすべて読ませ、読み終えた時の ACK が出ないことを Linux で測り、wgstack の値と比べます。
  この場合も読み取りの後の窓の更新の ACK は出うるので、残りの窓を窓の上限の半分より大きく保つか、出た ACK を窓の欄で窓の更新と見分けます

`read-window-update` の読み取りの後の窓の更新(違い 5)と、`ofo-ack-pattern` の広げる余地の無い状態の順序外の segment への ACK と窓の欄は、[受信のバッファの溢れ](wgstack-verification.md#受信のバッファの溢れ)の台本で確かめます。
どちらも、窓の scale の丸めを除いて Linux と wgstack の挙動が一致しました。
穴の後ろにデータを持ったまま読む場合は、Linux も wgstack も読み取りの後にすぐ窓の更新を返し、その ACK は保持した区間を先頭の SACK の block に持ちます。
読み終えた時の ACK と窓の更新は、ACK からは見分けていません。
`rcv-window-pacing`、SACK の圧縮の数、D-SACK、違い 2 の窓の条件は、まだ台本がありません。

### CUBIC

- 規格:RFC 9438 です。
  fast convergence を使い、β は 0.7、C は 0.4 です
- 使う構造:輻輳の制御を interface の後ろに置き、CUBIC を既定、NewReno を試験だけが選べる実装にします(`Config.TestCongestion`)。
  interface が受ける知らせは、輻輳の回避の ACK、輻輳の事象の ssthresh、RTO、送り残しの無い間の休みの 4 つです。
  slow start(RFC 3465 の L = 2)、回復の間の窓(PRR と NewReno の窓の膨らませ方)、RTO の後の 1 segment は共通の処理のままです。
  CUBIC の状態(W_max、cwnd_prior、epoch の始まり、K、3 次の式の原点、W_est、byte の端数)は接続の枠の中に値として埋め込み、接続ごとの確保を作りません。
  NewReno は状態を持たず、完成の段階の `caAcc` を使います
- 輻輳の事象:回復に入る時、TLP の probe が損失を直した時、最初の RTO で、ssthresh を送り残しと送り手の窓の小さい方の β 倍(下限 2 SMSS)にし、W_max と cwnd_prior を記録して epoch を終えます。
  窓が前の W_max より小さければ、W_max を (1 + β) / 2 倍に縮めます(4.7 節)。
  NewReno も同じ量の半分を ssthresh にします
- 送り手の窓:回復の外では輻輳の窓です。
  高速の回復の中と RTO の後の回復の中(SND.UNA が RTO の時の SND.MAX に届く前)では、回復が目指す ssthresh です。
  RTO の後の回復の印(`rtoEpisode`)は、SACK を交渉したかによらず、SND.UNA が RTO の時の SND.MAX に届いた ACK で消し、SND.UNA がそこから 2^31 先へ進んだ後に番号の比べで回復の中に戻ったとみなさないようにします。
  回復の中の輻輳の窓は PRR が送る量を刻む途中の値で、まとまった損失の後は pipe とともに数 segment に落ちます。
  RTO の後の回復の中の輻輳の窓は slow start の途中の値です。
  どちらも窓の見積もりではないので、回復の中の RTO と、新しい ACK が後退を 0 に戻した後の RTO は ssthresh を β 倍します
- 基準の量の理由:RFC 5681 の 3.1 と 3.2 は、ssthresh を FlightSize の半分の式の値「以下」にすることを求めます。
  小さい方を使う ssthresh は送り残しの β 倍を超えないので、RFC 5681 の規則の内側にあり、RFC 9438 4.6 の送り残しの β 倍も超えません。
  wgstack は回復の内でも外でも pipe で送る量を抑えるので、穴がある間の送り残しは穴の先の SACK 済みのデータを含み、送り手の窓を超えます。
  例えば、回復を終えた ACK でそのまま次の回復に入る場合です。
  最初の回復の間に回復の点より先へ送ったデータが失われると、その穴より先の SACK 済みのデータは累積で確認されないまま送り残しに残ります。
  送り残しだけを β 倍すると ssthresh が送り手の窓を超え、PRR が pipe を ssthresh まで満たすので、輻輳の事象が送る量を増やします
- 回復の間に届く量:PRR の RecoverFS は RFC 9937 6.1 に従い、回復に入る時の SND.MAX - SND.UNA から SACK 済みの byte を引き、回復に入る ACK が届けた byte を足します。
  回復の前に SACK 済みの byte は回復の間に届いたと数えないので、RFC 6937 の SND.MAX - SND.UNA のままでは、ssthresh と RecoverFS の比が β より小さくなり、回復の始めに送る量を減らしすぎます。
  RFC 9937 の SafeACK による PRR-SSRB と PRR-CRB の切り替えは持たず、送る量は RFC 6937 の PRR-SSRB のままです
- 輻輳の回避:epoch の最初の ACK で K と原点を決め、1 RTT 先の W_cubic を [cwnd, 1.5 cwnd] に収めた目標へ ACK ごとに近づけます。
  W_cubic(t) が W_est より小さい間は W_est に従います(4.3 節)。
  RTO の後は Linux の `bictcp_reset` と同じく状態を消し、送り残しの無い休みの後は Linux の `CA_EVENT_TX_START` と同じく休んだ時間だけ epoch を後ろへずらし、今より先へはずらしません
- 不変条件:影響は輻輳の窓の値だけで、送る量は今と同じく相手の窓と送信の輪で抑えます
- 危険:正しさへの危険は低く、主な危険は窓の急な増加によるまとまった送信です
- 期待する効果:20 Mbit/s と往復 50 ms では BDP が小さいので、主に損失への応じ方(0.7 倍)で損失 1% の速さに効きます。
  BDP の大きな経路では窓の戻りの速さにも効きます。
  参照の Linux が CUBIC を使うので、Linux の 90% の目標には要ると考えます

### ACK のまとまりと遅れた送り出し

wgstack は Device の Read の時に segment を作ります(wgstack.md の「出力」)。
wireguard-go は受けたバッチを Write で書き込んでから読むので、往復の ACK がまとめて届くと、処理する間は SND.NXT が進まず、送り残しが空になることもあります。
ACK のたびに送る送り手を前提にした規則は、この時に次の 2 つを誤ります。

- HyStart++ の往復の境:往復の終わりの ACK で取る SND.NXT が ACK の値と同じになり、次の ACK 1 つで往復が終わります。
  その 1 つの ACK の往復の最小の RTT が次の比較の基準になるので、RTT が増えても CSS に入りません
- 黙った後の規則:送り残しが空のまま次の Read で送り始めるので、最後に送ってからの時間を黙った時間に数えます。
  CUBIC が往復ごとに epoch を 1 RTT ずつ後ろへずらし、窓が W_cubic ではなく W_est で増えます。
  RTO より長ければ、輻輳の窓も初めの窓に戻ります

- 規格:RFC 9406 の windowEnd(往復を始めた時の SND.NXT)、RFC 9438 と RFC 5681 4.1 の黙った後の規則です
- 規則:HyStart++ は、ACK を処理する前に、ACK のたびに送る送り手なら送り終えていた番号を取り、往復を始めた時の SND.NXT にします。
  この番号は、今の SND.NXT に、輻輳の窓と送り残しの差、相手の窓、書き込まれて未送信のデータが許す分を足したものです。
  ACK が送り残しを空にした時に、相手の窓が許す未送信のデータがあれば、その時刻を最後に送った時刻にします。
  この送り手は、この時に送っていたはずだからです
- 使う構造:往復の始まりの番号を HyStart++ の状態に 1 つ足します(c_conn)
- 不変条件:送る量は変わらず、影響は輻輳の窓の値と HyStart++ の往復の境だけです
- ACK 1 つの手間:定数です
- 危険:未送信のデータがあるのに Read されない時間が長いと、その間を黙った時間に数えません
- 試験:試験の書き手の CUBIC と HyStart++ の場面(往復の ACK をまとめて渡すもの)と、`lazyegress_test.go` で確かめます

### CPU の仕事

CPU の目標は、qbench の待ち行列の大きな測定で定常の速さが一致したので、20 Mbit/s の経路では差の原因ではありません。
速い経路と順序外の多い入力で確かめ、プロファイルで裏付けた順に直します。

- 区間の数に比例する手間(実装済み):相手の順序外の segment で CPU を使わせる攻撃になるので、性能の段階を待たずに完成の条件として直しました。
  最近触れた区間の短い list で block を選び、区間の表を固定の配列を置き場にした treap にしました([接続ごとのバッファ](wgstack.md#接続ごとのバッファ))。
  表は予約の段ごとの固定の配列のままで、節は 16 byte になり、h_f と d_h はその大きさで数えます
- バッチと segment のまとめ:`BatchSize` を 1 より大きくし、`Read` が 1 回に複数の packet を作り、`Write` が複数の packet を受けます。
  受信では 1 本の接続の続く segment を連なりとして処理し、送信では 1 本の接続の segment をまとめて作ります。
  wireguard-go との約束、ACK の決め方、wireguard-go の滞留の上界、OS ごとの挙動、実装の順序は[wgstack のバッチと segment のまとめ](wgstack-batching.md)に分けます
- 錠の競合:入力、出力、アプリケーション、タイマーの goroutine が接続の錠を取り合います。
  mutex のプロファイルで競合を確かめてから分け方を決め、錠の順(接続の錠、表の錠、末端の錠)は変えません
- checksum:今の `checksum` は 2 byte ずつ足します。
  プロファイルで目立てば、8 byte ずつ足す形にします

危険は、区間の構造の誤りによる受信の byte の列の誤りと、錠の変更による競合と止まりです。
区間の構造は今の fuzzing と受信の模型の試験で、錠の変更は `-race` の負荷の試験で確かめます。

### 並べ替えと不要な再送

日常の行列の送る向きの並べ替え(packet の 1% を 3 ms 遅らせる)は、wgstack が 4 から 5 Mbit/s で、Linux の 18.8 Mbit/s に遠く届きませんでした。
この場合は損失が無いので、再送はすべて不要です。
`Stats` で数えると、受け手の SACK は D-SACK を返さず(gVisor の受け手)、8 秒の実行ごとに 9 から 10 回の高速の回復に入り、そのたびに輻輳の窓を下げていました。
原因は、並べ替えを見た後も RFC 6675 の DupThresh の境目が、3 つの SACK 済みの segment の手前の記録を損失とみなすことです。
Linux は RACK を使う間は DupThresh で損失を決めず(`tcp_time_to_recover`)、並べ替えの窓(最小の RTT の 4 分の 1)より短い遅れでは回復に入りません。

- 規格:RFC 8985、RFC 3708(D-SACK による不要な再送の発見)、RFC 3522 と RFC 4015(timestamp による Eifel の発見と応答)、RFC 5682(F-RTO)です
- RACK だけで決める損失:並べ替えを見た(`reorderSeen`)後は、DupThresh の境目を進めず、3 つの重複した ACK でも回復に入りません。
  損失は RACK の時刻だけで決めます。
  並べ替えを見る前は今と同じく RFC 6675 の規則も使うので、並べ替えの無い経路の振る舞いは変わりません
- 取り消しの印:回復に入る時と、回復の外の最初の RTO の時に、その時の輻輳の窓と ssthresh と SND.UNA を覚え、取り消しの印を付けます(Linux の `tcp_init_undo`)。
  その後の最初の再送の時刻(自分の TSval)と、まだ D-SACK で知らされていない再送の数を数えます。
  印の後にまだ再送していなければ、数による取り消しはしません
- D-SACK の数え方:D-SACK の block は、範囲が相手の窓の最大より広いものと、接続の D-SACK の累計が再送の累計を超えたものを疑わしいとして使いません。
  使う block は、MSS で割り上げた segment の数を重複の数とします。
  確認済みの範囲の block は、印の SND.UNA より後に終わり、この ACK の前の SND.UNA までに終わるときだけ数えます。
  SND.UNA より先の block は、範囲の中の再送した記録を数えます。調べる記録は ACK ごとに 4 つまでです。
  TLP の probe の再送の D-SACK(probe の時の SND.MAX で終わる 1 segment 以下の block)は、取り消しにも並べ替えの窓にも数えません。
  これで、再送していないデータの偽の D-SACK、前の回復の遅れた D-SACK、probe の D-SACK が本当の損失の縮小を取り消さなくなります
- 不要と分かる条件:再送の数がすべて D-SACK で知らされたか(RFC 3708)、確認の TSecr が最初の再送の時刻より前(元の segment への確認、RFC 3522)のときです(Linux の `tcp_may_undo`)
- 取り消し:回復を終える ACK で不要と分かれば、輻輳の窓と ssthresh を覚えた値以上に戻し、並べ替えを見たことにします(Linux の `tcp_try_undo_recovery`、RFC 4015 の応答)。
  回復の途中の取り消しと、D-SACK だけによる回復の途中の取り消しは持ちません
- RTO の後の回復の終わり:SND.UNA が RTO の時の SND.MAX に届いた ACK で、不要と分かれば窓を戻し、F-RTO の段階と取り消しの印を終えます。
  1 つの ACK がこの境を越えた場合も F-RTO の段階を残しません
- F-RTO:SACK を交渉した接続の回復の外の最初の RTO では、すべての記録を損失にせず、先頭の記録だけを損失にして送り直します(RFC 5682 の SACK を使う形)。
  次の ACK が SND.UNA を進め、送り直した記録の先まで届いていなければ、新しいデータを送ります。
  その次の ACK が再送していないデータを確認すれば RTO は不要だったとみなし、輻輳の窓と ssthresh を戻して RTO の回復を終えます。
  重複した ACK か、確認が進まない ACK なら、残りの記録を損失にして今の RTO の規則で送り直します
- 使う構造:覚えた窓、ssthresh、取り消しの印、最初の再送の時刻、数えた再送の数、F-RTO の段階を接続の欄に置きます(c_conn)。
  記録の大きさと固定の配列は変わりません
- 不変条件:I5 では、F-RTO の新しいデータは輻輳の窓と相手の窓の内側だけで送り、タイマーの節を増やしません。
  取り消しは窓の値を戻すだけで、保持を増やしません(I1、I2)。
  I4 では、記録と送信の輪の扱いは変わりません
- ACK 1 つの手間:取り消しの判定は定数の手間です。
  F-RTO で不要でないと決めた時の残りの記録の損失の印は、今の RTO と同じく境目を末尾に置くので定数の手間です
- 危険:本当の損失を不要とみなすと、輻輳の窓を戻して溢れを続けます。
  TSecr による判定は相手が RFC 7323 に従って timestamp を返すことを前提にします
- 測った結果:日常の行列の送る向きの並べ替えは、この段の前の 5.52 Mbit/s から 18.63 Mbit/s になり、参照の Linux(18.79 Mbit/s)に近づきました。
  8 秒の実行(各 5 回)ごとの高速の回復は 8 から 11 回から 3 回に減りました。
  一方、RACK が損失とした記録は実行ごとに 23 から 80 あり、高速の再送の segment は 8 から 11 から 78 から 110 に増えました。
  この行列の経路は並べ替えのほかに待ち行列の溢れでも packet を失い、再送の数は溢れの数とほぼ一致します(91 と 88、100 と 97 など、レビューでの照合)。
  このため再送のほとんどは本当の損失の修復で、不要な再送は実行ごとに 3 から 6 ほどです。
  gVisor の受け手は D-SACK を返さないので、並べ替えの窓の倍率は 1 のままで、窓は最小の RTT の 4 分の 1 の 12.75 ms でした。
  D-SACK の取り消しの検査を強めた後も、各実行で 1 回の取り消しがあり、中央値は 18.67 Mbit/s でした。
  同じ行列の損失 1% は 4.18 から 4.72 Mbit/s、損失 5% は 1.42 から 1.66 Mbit/s(gVisor 以上)になりました

### 必要なら加える変更

次の変更は、前の変更の後の測定で要ると分かった場合だけ加えます。

- pacing:窓が開いた時と RTO の後のまとまった送信が、待ち行列の溢れを作り続ける場合に加えます。
  Linux の CUBIC は fq の qdisc が無ければ pacing しないと読めるので、参照の Linux との差の原因にはならないはずです。
  接続ごとの次に送れる時刻とタイマーの節が 1 つ増え、中身の無い ACK を遅らせない規則を要します
- 不要な RTO の発見:F-RTO(RFC 5682)は[並べ替えと不要な再送](#並べ替えと不要な再送)の段に入れます

### 変えないもの

- 初期の輻輳の窓:今の 10 segment は Linux の既定と同じなので、変えません
- 握手の後の受信の窓:最初の ACK から floor を広告する今の挙動は、送り手の速さを妨げないので、変えません

## 上界の式への項

新しい構造は、次のどれかの項に入ります。
各段階は `Bound` と上界の試験(`bound_test.go`)を、入れた項に合わせて同じ変更で直します。

| 変更 | 新しく持つもの | 入る項 |
|---|---|---|
| SACK による回復、RACK-TLP、HyStart++、CUBIC、受信の窓の広げ方、受け手の ACK と D-SACK | 接続の欄(位置の手がかり、時刻、輻輳の制御の状態、推定した MSS、D-SACK の block) | c_conn。印と送った時刻の順の節は記録 1 件にあります |
| SACK 済みの範囲を飛ばす構造 | 記録 1 件の中の、飛ばす記録の数と 2 つの世代の番号。記録は 24 byte から 32 byte になります | r_f と d_rec |
| `Stats` の数と接続の記録の関数 | Device の atomic と関数の値 | M_fix |
| 区間の構造 | 区間の節の大きさ | h_f と d_h |
| バッチと segment のまとめ | 接続ごとの ACK の控えの固定の配列、送信の向きの台帳、固定の作業の値 | 控えは新しい項 a_ack、台帳と作業の値は M_fix。wireguard-go の滞留は式の外の項で、送信の向きは予算 P_max の関数です([上界の式への項](wgstack-batching.md#上界の式への項)) |
| pacing | 接続ごとのタイマーの節 | M_fix(タイマーの輪の節の数が N_c に比例して増えます) |
| 需要で育つバッファ | 始めの予約、プロセスで 1 つの予算、保有者の list、段の配列の置き場 | f_s、f_r、r_f、h_f を始めの段の値にし、B × (d_s + d_r + d_rec + d_h) と `Transient` を予算 G に替えます([上界の計算](wgstack-buffers.md#上界の計算)) |

どの変更も入力の量に比例する保持を作らず、表と輪は作成の時の容量のままです。

## 測定の計画

### 参照の Linux

Linux の値は 2 つの経路で測ります。

- qbench の Linux の DUT:ラボの VM の network namespace の中で、`internal/tcpharness/linuxdut` の TUN を qbench の経路の DUT の側に繋ぎ、Linux のソケットで受け付けます。
  相手と経路は wgstack と gVisor の実行と同じ gVisor の stack と qbench の経路です。
  3 つの実装を同じ VM で流し、CPU と時計の違いを比べる値に混ぜません
- ラボの `lab/tcpquality.sh`:エージェントのカーネルモード(TCP の終点は LAN のホストの Linux)、gVisor のユーザー空間モード、wgstack のユーザー空間モードを同じ経路で比べます。
  2 つのユーザー空間モードは、モードの名前 `gvisor` と `wgstack` で選びます。
  相手は client の namespace の Linux なので、gVisor ではない相手での値を得られます

性能の参照の Linux は、適合の試験の固定の値([参照の Linux の設定](wgstack-verification.md#参照の-linux-の設定))ではなく、Linux の既定の回復と輻輳の制御を使います。
CUBIC、RACK-TLP、SACK、D-SACK、F-RTO、受信のバッファの自動調整を既定のまま有効にします。
`tcp_no_metrics_save=1` と `tcp_ecn=0` を固定し、`tcp_rmem` と `tcp_wmem` の上限を boost と同じ 4 MiB にします。
ソケットに `SO_RCVBUF` と `SO_SNDBUF` を与えると自動調整が止まるので、与えません。
`linuxdut` は値を書き込んで読み戻し、VM のカーネルの版と値を結果と共に記録します。

### 判定の行列

日常の行列は、変更のたびに wgstack だけを流し、保存した gVisor と Linux の中央値と比べます。
段階の関門の行列は、3 つの実装を同じ VM で流します。

| 軸 | 日常 | 段階の関門 |
|---|---|---|
| 向き | DUT が送る向きを中心にし、受ける向きは損失 0% と 1% | 両方の向き |
| 損失 | 0%、1%、5% | 0%、1%、5% |
| RTT | 片道 25 ms | 片道 5 ms、25 ms、75 ms |
| 速さと待ち行列 | 20 Mbit/s、200 packet | 加えて 100 Mbit/s と、BDP より短い待ち行列 |
| 並べ替え | 1 つの場合(並べ替えの遅れは重複した ACK を 3 つ作る長さ) | 並べ替えの割合を変えた場合 |
| 途絶 | 2 秒 | 2 秒と 5 秒 |
| 通信量の少ない stream | DUT が送る向き、損失 1% | 両方の向き、損失 0%、1%、5% |
| CPU | 記録だけ | 判定 |

指標と目標の対応は次のとおりです。

- スループット:受け手が読んだ byte の速さを、最初の byte から実行の終わりまでで求めます。
  slow start の差が今の差の主因なので、立ち上がりを測定から外しません
- 回復:途絶の終わりから受け手の次の読み取りまでの時間(qbench の `Recovery` と同じ定義)で判定します。
  途絶の終わりの時点で送り手が使っている RTO(後退を含みます)を実行ごとに読み、回復の値の横に記録します。
  wgstack は `Stats` か接続の記録から、gVisor は endpoint の TCP の情報から、Linux は `TCP_INFO` の `tcpi_rto` から読みます
  途絶の後に決まった量を読み終えるまでの時間も記録し、判定に加えるかは所有者が決めます
- 遅れの p99:送り手が 200 byte の書き込みを 20 ms ごとに行い、書き込みの予定の時刻から受け手の読み取りまでの時間を書き込みごとに測ります。
  書き込みが止まった間の予定の分も、止まった時間を遅れに含めて測ります。
  同じ実装と場合のすべての実行の標本を合わせて p99 を求め、合わせた標本は 1,000 以上にします。
  受け手に届かなかった書き込みは、まだ書いていない予定の分を含めて、受け手が読むのをやめた時点(実行の終わりの 5 秒後)までの遅れとして標本に入れ、届かなかった数も記録します
- CPU:段階の関門では、`lab/tcpquality.sh` の経路で、エージェントのプロセスの CPU 時間を転送した byte で割った値を比べます。
  `CPU=1` を与えると、スクリプトはエージェントを専用の cgroup に移し、client が接続する直前から client のプロセスが終わった直後までの `cpu.stat` の差を CPU 時間にします。
  エージェントの起動の分は含みません。
  受ける向きでは、LAN のホストの返事がエージェントを通って client に届くまでの短い時間も含みます。
  この間のエージェントの仕事は返事の 1 行の中継だけですが、時間と CPU の割合の値はこの分を含みます。
  速さを固定した場合と、経路の速さを制限しない場合の両方で測ります。
  向きは、エージェントが送る向き(client の取得)と受ける向き(`DIRECTION=up`)の両方です。
  受ける向きの値は、エージェントが返す ACK の暗号と送信の CPU を含みます。
  速さを固定した場合は片道 25 ms、20 Mbit/s、200 packet の待ち行列で、損失と途絶を入れません。
  速さを制限しない場合は経路に netem を置きません。
  送り手のプロセス(送る向きでは LAN のホスト、受ける向きでは client)の CPU も記録します。
  送り手が 1 つの CPU の 0.7 以上を使った実行は送り手の速さを測ったとみなし、判定に使いません。
  gVisor と wgstack は同じ VM の同じ時間帯に流します。
  `lab/tcpquality-cpu.sh` は `tcpquality.sh` を `RUNS=3` で 3 回呼び、呼ぶたびに 2 つの netstack の順を入れ替え、比の bootstrap の区間も出します。
  値は wireguard-go の暗号と UDP の処理の CPU を含みます。
  qbench の 1 つのプロセスの中の値は相手と経路の CPU を含むので、DUT の側の goroutine に pprof の label を付けて分けるか、DUT だけを替えた差で求め、目安として記録します

### 回数と中央値

- 日常:場合ごとに 5 回流し、中央値を前の段階の中央値と保存した参照の中央値と比べます
- 段階の関門:実装と場合ごとに 9 回流し、中央値で判定し、四分位も記録します
- 境目の場合:中央値の比が目標の境目から 5% 以内なら、回数を倍にして判定し直します。
  通信量の少ない stream では、後述の p99 の区間が判定の線を含む場合に倍にします
- 揺れの大きな場合:同じ実装と場合の最大と最小の比が 2 を超える場合は、中央値で判定せず、揺れの原因を診断してから流し直します。
  通信量の少ない stream には、この比を使いません。
  1 回の実行の p99 は 400 の標本の上から 4 番目ほどで、損失の当たり方で実行ごとに大きく動き、Linux でも比が 2 を超えるためです
- 失敗した実行:中央値から除き、その場合を判定しません。
  途絶から回復しなかった実行は、最大と最小の比を無限大として扱います。
  wgstack の実行が途絶から回復しなかった場合は、その場合を不合格にします
- wgstack の明らかな失敗:wgstack の実行が 1 つも終わらない場合、まとまった転送の中央値が 0 Mbit/s の場合、途絶の無い通信量の少ない stream で届かなかった書き込みがある場合は、揺れによらず不合格にします

### 判定の規則

段階の関門の行列は、すべての場合が通ったときだけ通ります。
所有者の目標に従い、監督が次の規則を決めました。
場合ごとに、関門の実行の中央値で判定します。

- スループット:wgstack が Linux の 0.9 倍以上で、かつ gVisor 以上です。
  線は、カーネルの 90% と、wgstack が置き換える実装の両方です。
  gVisor が Linux の 0.9 倍より速い場合は、gVisor の値が判定の線になります。
  例外は `send/loss1%` と `send/loss5%` の 2 つの場合で、線は Linux の 0.9 倍だけにし、gVisor の値は測って表示するだけで判定に使いません。
  この 2 つの場合で gVisor が速いのは、回復の後の輻輳回避で窓が往復ごとにほぼ倍になり、連鎖した回復で 2 回目の縮小をしないためです。
  どちらも RFC と Linux の外の輻輳制御で、[損失への応答](wgstack-verification.md#損失への応答)の `chained-recovery` と `reorder-wait-recovery` が示しています。
  3 つの実装は同じ種の列で流し、経路の損失は[経路の損失の模型](#経路の損失の模型)のとおり、種ごとに stream の同じデータに当たります。
  そこで種ごとに、wgstack の値をその種の線(Linux の 0.9 倍と gVisor の大きい方。例外の 2 つの場合は Linux の 0.9 倍)で割った比を求め、比の中央値を実行の単位の bootstrap で求めた 95% の区間とともに 0.99 と比べます。
  区間の下端が 0.99 以上なら通り、上端が 0.99 より小さければ不合格で、区間が 0.99 を含めば判定せずに回数を倍にします。
  0.99 は測定の許容で、3 つの実装がどれも経路の速さに届く場合に、測定の揺れで落ちないようにするためです。
  この許容はスループットだけに使います。
  比は、種が引いた損失の数による揺れを打ち消すので、まとまった転送の場合には後述の最大と最小の比の規則を使いません。
  bootstrap は種ごとの 3 つの実行(wgstack、gVisor、Linux)の組を 1 つの単位として引き直します。
  種が共有するのは失う stream のデータと並べ替えの並びだけです。
  Linux の DUT は種を使わず、gVisor と wgstack の乱数も経路の種とは別なので、残りの揺れは比に残ります。
  種ごとの線は 2 つの揺れる値の大きい方なので、中央値から作る線より高めに出ます。
  このため、この規則は中央値の線の規則より不合格の側に傾きます。
  種ごとの値を持たない参照(この規則の前に保存した参照)と比べる時は、中央値の線と比べます
- 回復:途絶の後の回復が、Linux の回復に RTO 1 回分を足した値以下です。
  RTO は前述の、途絶の終わりの時点で動いている RTO で、Linux の実行で記録した値の中央値を使います
- 通信量の少ない stream:合わせた標本の wgstack の p99 を、実行の単位の bootstrap(実行を復元抽出で 1,000 回引き直し、引いた実行の標本を合わせる)で求めた 95% の区間とともに Linux の p99 の 1.5 倍と比べます。
  1 回の実行の標本は同じ損失を共有して独立でないので、標本の単位で引き直すと区間が狭くなりすぎ、種の組を替えた時の p99 を外しました。
  区間の上端が 1.5 倍以下なら通り、下端が 1.5 倍を超えれば不合格で、区間が線を含めば判定しません
- CPU:`lab/tcpquality.sh` の経路で測った byte あたりの CPU 時間が、両方の向きで gVisor の 0.6 倍以下です

場合を判定から外せるのは所有者だけです。

### 経路の損失の模型

qbench の経路の無作為の損失は、既定では packet が運ぶデータで決めます。
以前の模型は、向きごとに届いた順に packet 1 つにつき 1 つの乱数を引き、同じ種なら n 番目に届いた packet を落としました。
最初の損失の後は、再送、ACK の並び、segment の境目が実装ごとに変わるので、n 番目の packet が運ぶデータは実装ごとに違います。
このため同じ種でも、実装ごとに失う stream の部分と回数が違いました。
データで決める模型は、損失を無作為のまま保ち、3 つの実装に同じデータを失わせます。

- データの segment:向きごとに SYN の番号を ISN として覚え、payload を ISN からの stream の位置に直します。
  stream を block に分け、segment が block の先頭の byte を運ぶたびに、その byte の送信の回数を数えます。
  種、向き、block の番号、送信の回数から 0 以上 1 未満の値を決め、segment が運ぶ先頭のどれかの値が境目より小さければ segment を落とします。
  境目は、運ぶ先頭が 1 つなら損失の確率 p で、k 個なら 1-(1-p)^(1/k) です
- block の大きさ:2 つの SYN の MSS の小さい方です。
  両方の SYN が timestamp の option を持つ時は、option の 12 byte を引きます。
  同じ MTU なら 3 つの実装の SYN は同じ値を持つので、block も同じになります。
  通信量の少ない stream では、1 回の書き込みの 200 byte を 1 つの block にします
- 先頭の byte で決める理由:1 回の送信では、block の先頭の byte を運ぶ segment はちょうど 1 つです。
  このため、segment の境目が違う実装も同じ block を失います。
  まとまった転送では、wgstack は 1368 byte の segment を送り、gVisor は 32 KiB の書き込みごとに 1340 byte の segment と 608 byte の残りを送ります。
  block より短い segment は、先頭の byte を運ばなければ落ちません
- 複数の先頭を運ぶ segment:通信量の少ない stream では、止まった後の送り手がたまった書き込みを 1 つの segment にまとめます。
  境目を 1-(1-p)^(1/k) にするので、先頭を k 個運ぶ segment も、その中の各 block も、確率 p で失います。
  境目を p のままにすると segment を 1-(1-p)^k で失い、まとめる実装だけが設定より多く失います
- 再送:送信の回数ごとの値は互いに独立で、どれも損失の確率で落とします。
  最初の送信で失った block も次の送信では損失の確率でだけ失うので、同じ block を失い続けません。
  同じ block の n 回目の送信の運命は、すべての実装で同じです
- データの無い packet:pure ACK、SYN、FIN、RST は、種、向き、flags、相手の ISN からの確認の位置、同じ flags と位置の packet の何番目かで決めます。
  同じ byte を確認する ACK は、間にほかの packet があっても同じ運命になります。
  実装ごとに ACK を返す位置と数が違うので、ACK の損失は実装の間で揃いきりません。
  到着の順の乱数に残すと、データの損失で ACK の数がずれた後の運命がすべてずれるので、確認の位置で決めます
- 数える時点:途絶で落とした packet は数えず、損失を決める段に届いた送信だけを数えます。
  待ち行列の溢れは損失の段の後で決めるので、溢れた送信は数えます。
  途絶と待ち行列の溢れは今のままで、実装ごとに違ってよい差です
- そのほかの packet:測る接続のものでない packet と、向きの ISN を知る前の packet は、以前と同じ向きごとの乱数で決めます
- 以前の模型:`QBENCH_LOSS_MODEL=arrival` で選べます。
  模型を比べるために残します
- 経路の記録:記録の `loss` は、どちらの模型でも無作為の損失で落とした packet です

2 つの模型を、2026-10-31 にラボの VM(E-core の 8 CPU に固定)で同じ時期に比べました。
測った binary は、wgstack の ACK の方針の変更(#543 から #548)より前の wgstack を含みます。
複数の先頭を運ぶ segment の境目は、この測定の後に入れました。
測ったまとまった転送の segment は block 以下で、先頭を 1 つまでしか運ばないので、境目は測った値を変えません。
測定の細部はこの変更の PR にあります。

- 失うデータ:場合ごとに 1 つの種の経路の記録で、3 つの実装は共通の stream の範囲で同じ block を同じ送信の回数で失いました
- 受ける向き:`recv/loss1%/linux-client` を 12 の種で 3 回ずつ流すと、同じ種の揺れ(Mbit/s の対数の標準偏差)は wgstack で 0.088 から 0.015 に、種ごとの比で 0.143 から 0.018 に下がりました。
  データで決める模型で、受ける向きの実行は種ごとにほぼ再現します
- 送る向き:`send/loss1%` の同じ種の揺れは、同じ 12 の種と 3 回で、どちらの模型でも 0.02 から 0.07 と小さく、種ごとの比の揺れは種の間の違いから生じます。
  この揺れは、同じ損失に対する実装ごとの応じ方が種によって違うことから生じるので、損失の模型では消せません。
  36 の種の比の区間は縮みませんでした

### 種と参照の値

種の列は 3 つの実装で同じにします。
経路の損失は種と運ぶデータで決まりますが、goroutine の順は実行ごとに変わるので、同じ種でも結果は揺れます。
ラボの netem は種を受け付けないので、`lab/tcpquality.sh` の損失の位置は実行ごとに変わります。
保存した参照の中央値は、qbench、Go、gVisor、VM のカーネルの版のどれかが変わった時と、各段階の関門で測り直します。
関門の行列(`TestQBenchGate`)は、gVisor と Linux の中央値を `internal/tcpharness/qbench/testdata/reference.json` に書き出せます。
失敗した実行を含む場合と、最大と最小の比が 2 を超える場合は書き出さず、前の値を残して警告を出します。
書き出す値は、測った commit、Go と gVisor の版、読み戻した sysctl、損失の模型を場合ごとに持ちます。
損失の模型を持たない場合は、以前の模型で測った値です。
日常の行列は、損失のある場合の参照の模型が今の模型と違う時に警告を出します。
commit が分からない時は書き出しを始めず、作業中の変更がある時は commit に `-dirty` を付けます。
日常の行列(`TestQBenchRoutine`)は wgstack だけを測り、この値と比べます。

### 1 回の長さ

日常の行列は 1 回の実行を数秒に抑え、全体を約 5 分以内にします。
今の qbench は決まった量を送り、`QBENCH_LIMIT_S`(既定は 150 秒)で 1 回の実行を打ち切ります。
損失 5% の測定は `QBENCH_LIMIT_S=60` で流したので、wgstack の実行が 60 秒で打ち切られました。
決まった量の転送は遅い実装ほど長くかかり、上限の値で結果が変わるので、実行を決まった時間で区切ります。
1 回の長さは場合ごとに決め、3 つの実装で同じにします。
今の値は、bulk の転送が 6 秒、途絶のある転送が 8 秒、通信量の少ない stream が 8 秒です。
途絶は、送り手の側の最初の data の byte から 2 秒後に始まり、2 秒続きます。
決まった量の転送は、短い転送の立ち上がりを見るための場合として残します。
受け手は種から同じ byte の列を作って読んだ byte と比べるので、時間で区切った実行でも byte の列の一致を確かめられます。
通信量の少ない stream の場合は、合わせた標本が 1,000 以上になるように、ほかの場合より長く流します。
関門の行列は段階の関門の時だけ流します。
`QBENCH_PARALLEL` の数の実行を同時に流します。
実行ごとに相手、経路、DUT は別々で、Linux の DUT と Linux の client はそれぞれ自分の network namespace に置くので、同時の実行が共有するのは機械だけです。
関門の既定は 8 で、機械の CPU が 8 より少なければその数です。
日常の行列の既定は 1 です。
関門は 8 つの vCPU を与えたラボの VM で流し、2026-10-30 の行列(27 の場合、945 回の実行)は、ホストの負荷が 24 CPU に約 20 の時に 17 分で終わりました。
同じ行列を 1 つずつ流すと、7 つの場合の 243 回に 32 分かかった速さから、2 時間を超えると見込みます。

同時に流す数は次のように選びます。
- 数は VM の vCPU の数を超えないようにします。1 回の実行は相手、経路、DUT の goroutine を持ち、経路の遅れと速さの制限を壁時計で作るので、CPU が足りないと経路の時間がずれます
- 数を変えた時と、VM の vCPU の数、Go、gVisor が変わった時は、後述の確かめを流し直してから使います
- 確かめで数によって値が動いた場合と、中央値が判定の線から 5% 以内の通信量の少ない stream の p99 のように時間に敏感な場合を詰めて判断する時は、その場合だけ `QBENCH_PARALLEL=1` と `QBENCH_CELLS` で流し直し、その値で判定します

同時に流しても値が動かないことは、次のように確かめました(2026-10-30、ラボの VM、8 vCPU、ホストの負荷は 24 CPU に約 4)。
7 つの場合(`send/loss1%`、`send/outage2s`、`recv/loss1%/linux-client`、`thin-send/loss1%`、`thin-send/outage2s`、`thin-recv/loss1%/linux-client`、`thin-recv/loss5%/linux-client`)を、3 つの実装でそれぞれ 9 回、同時に流す数を 4 と 8 にして流しました。
1 つずつ流した値は、ホストがほかの重い仕事と重なる前の、初めの 4 つの場合の分だけを比べます。
同じ種の 9 回の中央値の差は、まとまった転送と途絶では 1 つの時の四分位の幅(小さければ中央値の 2%)以内に、通信量の少ない stream では p99 の区間が重なる範囲に収まりました。
4 と 8 の間では、7 つの場合のすべてがこの範囲に収まりました。
外れは Linux の `send/outage2s` の 1 つで、回復が約 440 ms と約 970 ms の 2 つの値に分かれ、短い値の回数が 1 つの時に 9 回中 2 回、4 つで 4 回、8 つで 0 回でした。
1 つで流した時にも 2 つの値に分かれるので、同時に流すことによる差ではなく、RTO の後退が途絶の終わりのどちら側に当たるかによる揺れと見ます。
後の 3 つの場合は、ホストのほかの重い仕事を止めた時に、場合の名前から決めた種で 1 つと 8 つを流し直し、9 つの値のすべてで p99 の区間が重なりました。
壁時計の区間を使うので、[壁時計で測る区間を使うテストの規範](../../development/testing.md#壁時計で測る区間を使うテストの規範)に従い、握手の完了を確かめてから測る区間に入ります。

## 段階の順序

各段は 1 つの PR で、次の確かめをすべて通してから次の段に進みます。

- 適合の試験:wgstack の台本の実行(`WGFT_TEST_WGSTACK_CONFORMANCE=1`)と、ラボの Linux での新しい台本の実行です
- stream の一致:受信と送信の乱数の stream の試験です。
  段階の関門では `WGFT_WGSTACK_STREAM_SEEDS=full` を付けます
- 上界:上界の試験と fuzzing で、予約の合計が `Bound` の値以下に留まり、`Close` の後に 0 に戻ることを確かめます。
  新しい項は同じ PR で `Bound` に入れます
- 競合:`-race` の負荷の試験です
- 退行:日常の行列のどの場合も、前の段の中央値を下回りません。
  下回った場合は、原因を PR に書いて所有者が受け入れるか、段を直します

段の順は次のとおりです。

1. 観測:`Stats` の数、接続の記録、経路の記録、bench の切り替え、相手の統計、qbench の Linux の DUT、時間で区切る実行を加えます。
   挙動を変えずに 3 つの実装の基準の値を測り、[測った差の診断](#測った差の診断)の仮説を確かめます
2. SACK による回復:Limited Transmit と PRR を含みます
3. RACK-TLP
4. 輻輳の制御の interface と CUBIC:RACK-TLP の後の日常の行列で、損失 1% と 5% の送る向きの差が損失への応じ方に残ったので、HyStart++ より前に置きます
5. HyStart++
6. 輻輳の窓の検証(RFC 7661):送り残しが輻輳の窓より少ない、アプリケーションに制限された間は、Linux の `tcp_is_cwnd_limited` と同じく slow start と輻輳の回避で窓を増やしません。
   通信量の少ない stream の間に使わない窓が育ち、後のまとまった転送を一度に送るのを防ぎます。
   CUBIC と NewReno の両方で、2 segment ずつ送る 60 秒の間に窓が 10 から 70 segment に育つことをレビューで確かめたので加えます。
   窓の使い方は 1 往復(その窓の間に送った最後の番号の確認まで)ごとに数え、その往復の間に輻輳の窓が新しいデータを止めたか、slow start の間は窓が送り残しの最大の 2 倍に届いていないときだけ窓を増やします(Linux の `tcp_cwnd_validate` と `tcp_is_cwnd_limited`)。
   窓を下げる RFC 7661 の pipeACK の仕組みは持ちません
7. 受信の窓と boost の方針:前の段と独立しているので、診断の結果によっては 2 の段と並べて進めます
8. 受け手の ACK と D-SACK
9. 並べ替えの下の不要な再送の取り消し:[並べ替えと不要な再送](#並べ替えと不要な再送)に従います。
   あわせて、まとめて届く ACK への補正を[ACK のまとまりと遅れた送り出し](#ack-のまとまりと遅れた送り出し)に従って加えます
10. CPU の仕事:区間の数に比例する手間が損失の場合のプロファイルで目立てば、2 の段の後に前倒しします。
    バッチと segment のまとめの段の順は[実装の順序](wgstack-batching.md#実装の順序)に従います
11. 必要なら加える変更:4 と 10 の段の後の関門の行列で要否を決めます
12. 需要で育つバッファ:保持の上界を下げる段で、[需要で育つバッファ](wgstack-buffers.md)に従って進めます。
    受信の窓の自動調整の段の後に置きます

適合の試験の新しい台本は、試験の書き手が規格と Linux の挙動から書き、wgstack を実装する人は書きません([検証の原則](wgstack-verification.md#検証の原則))。
台本は Linux で通ってから試験の一式に入ります。
台本ごとに参照の Linux の設定を選べるようにし、例えば RACK の台本では `tcp_recovery=1` を与えます。
段ごとに足す台本は次のとおりです。

- SACK による回復:1 つの窓の中の複数の穴を RTO なしに順に再送すること、SACK 済みの範囲を再送しないこと、回復が `recover` で終わること、回復の間の送信が窓を超えないこと、RTO の後に SACK 済みの範囲を送り直さないこと、PMTU の引き下げの後に大きな記録を分けて再送すること、相手が SACK を取り消した場合に印を消して累積の確認まで再送できること、Limited Transmit で新しい segment を送ること
- RACK-TLP:並べ替えの窓の内側の遅れで再送しないこと、窓を超えた遅れで再送すること、再送した segment の損失を RTO なしに見つけること、末尾の損失で TLP の probe を PTO の後に送ること、probe が失われた場合に RTO に移ること
- HyStart++:Linux は RFC 9406 を使わないので台本では比べず、試験の書き手が RFC 9406 から核の単体の試験を書きます。
  slow start の終わる位置の差は期待した差として扱います
- 受信の窓:広告する右端が予約を超えず、後ろへ戻らず、往復ごとの広がりが範囲に収まること
- 受け手の ACK と D-SACK:接続の始めの quickack、自分の MSS より小さな segment での遅延 ACK の間隔、重複した segment への D-SACK の block の内容と順
- CUBIC:損失の後の輻輳の窓の値は台本で比べず、試験の書き手が RFC 9438 の式から単体の試験を書きます

HyStart++ と CUBIC の試験は `tcpharness.CongestionScenarios` にあり、wgstack の手で進める時計の上で流します(`WGFT_TEST_WGSTACK_CONFORMANCE=1` の `TestCongestion`)。
試験台は経路として ACK を決めた往復の時間だけ止め、1 往復に送られたデータの量を窓として読みます。
CUBIC は、損失の後の窓と往復ごとの窓を RFC 9438 の式(4.2 節の W_cubic、4.3 節の W_est、4.7 節の fast convergence)から求めた値と比べます。
HyStart++ は、RTT を閾値より上げた後の CSS の窓の増え方と往復の数、RTT を戻した後の slow start への戻りを確かめます。
どちらも、トンネルが ACK ごとに読む場合と、往復の ACK をまとめて渡してから読む場合を持ちます。
後者は、wireguard-go が受けたバッチを Device に書いてから読む場合に当たります。

stream の一致の試験も、SACK を交渉する相手と並べ替える相手を含むように試験の書き手が広げます。

## 未確認の点と未決の点

- 損失のある場合の判定:Linux の値は 2026-10-30 の関門の行列で測りました。
  損失 1% と 5% の送る側の場合が Linux の 0.9 倍の線を満たすかは、現在の実装で関門を流し直すまで確定しません
- gVisor の受ける側の窓:gVisor の DUT も boost を得た時に窓を一度に広げるのか、なぜ揺れが小さいのかは未確認です
- qbench の相手の設定:wireguard-go の `netstack` が使う gVisor の stack で、RACK と輻輳の制御の既定が何かは未確認です。
  観測の段で相手の設定を固定します
- 溢れた後の受け手:以前に試した窓の広げ方で gVisor の送り手の回復が遅くなった原因は、右端の一度の大きな伸びでした([確かめる手順](#確かめる手順))。
  違い 5 のうち読み取りの後の窓の更新は、[受信のバッファの溢れ](wgstack-verification.md#受信のバッファの溢れ)の台本で Linux と一致しました。
  読み終えた時の ACK が順序外のデータを数えるかと、違い 2 から 4 と、rcv_ssthresh を広げた segment ごとの quickack を入れるかは、[適合の場面の案](#適合の場面の案)の残りの台本で Linux と比べるまで未確認です。
  ラボの 6.1.0-53 が含む `v6.1` の後の修正は、Debian の changelog の値で、VM の上ではまだ確かめていません
- 受け手の RTT の推定の初期:timestamp を持たない相手では、推定が出来るまで読んだ量の区間を始め直さないので、最初の測定は最初の読み取りからの全量を MSS の 10 倍と比べます。
  窓の上限は最初の測定で予約まで届きえます(試験では 256 KiB から 4 MiB)。
  Linux の挙動に合わせ、予約の内側なので保持の上界は守られますが、この相手では窓の上限が窓を抑えにくいことを確かめる測定はまだありません
- 窓による標本:窓が閉じかけている間の標本は RTT でなく packet の間隔を測りえ、標本は推定を下げるだけなので、timestamp を持たない相手の推定が低いまま残りうると考えます。
  影響は小さいと見ていて、推定が低すぎて窓の上限が崩れる例は再現していません。測っていません
- 穴を埋める segment の伸び:順序外の segment が多い接続で穴を埋めると、右端は読み取りなしで大きく進みえます(試験の探査では、順序外の 2,506 segment のあとの穴埋めで約 764 KB)。
  空きの式のとおりの結果で、「届いた segment ごとに 3 MSS 以下」は順序どおりの segment の規則です。
  この伸びが送り手に溢れを起こさせるかは測っていません
- 受ける向きの損失のある場合:損失 1% と 5% の受ける向きの差の原因は、診断の段の後まで分かりません
- 損失の模型と参照:`testdata/reference.json` は以前の到着の順の模型で測った値です。
  データで決める模型で測り直すまで、日常の行列は損失のある場合で警告を出します
- 損失 1% のやや速い種:輻輳の事象の基準を送り手の窓にした後、損失のある場合に経路の速さに近づく実行は無くなりました([CUBIC](#cubic))。
  損失 1% の一部の種では、wgstack が約 6 Mbit/s で、同じ種の gVisor と Linux(3 から 6 Mbit/s)をわずかに上回ります。
  CUBIC の通常の窓の増え方によるのか、窓を下げない別の経路があるのかは未確認です
- 時間で区切る実行:決まった量の転送から時間で区切る実行に替えて、今の測定との比べ方が変わらないかは未確認です
- CPU の分け方:qbench の中で DUT の CPU を pprof の label で分ける方法が、gVisor の内部の goroutine を含められるかは未確認です
- バッチの費用:`BatchSize` を大きくしたときの wireguard-go の滞留は[wireguard-go の滞留の上界](wgstack-batching.md#wireguard-go-の滞留の上界)で導きます。
  送信の向きは予算で抑え、受信の向きの件数は連なりの段の測定の後に所有者が決めます
- 最小の RTT の窓:最小の RTT は接続の始めからの最小で、経路が変わっても大きくなりません。
  Linux の `tcp_min_rtt_wlen`(300 秒)のような窓のある最小にするかを、後の段で決めます
- SACK の手間の均し:相手が選ぶ SACK の block で、ACK 1 つの手間を均せない入力があるかは未確認です
- RTO の後の SACK 済みの範囲:Linux が RTO の後に SACK の印を保つかどうかは、試験の書き手が Linux で確かめます
- pacing:要否は、前の段の後の測定で決めます
- 実機の相手:Windows、macOS、スマートフォン、ゲーム機の TCP を相手にした値は、[実機の OS との相互運用](wgstack-verification.md#実機の-os-との相互運用)の試験まで分かりません
- 小さく始める受信の窓:予約の floor は変えずに、広告する窓を約 64 KB から始め、アプリケーションが 1 往復に読んだ量で 1 往復に 2 倍までずつ floor まで広げる案です。
  測っていません
- 需要で育つバッファ:設計と、その危険と未決の点は[需要で育つバッファ](wgstack-buffers.md)にあります。
  所有者が 2026-10-31 に採用を決め、実装は今の性能の段階の後に行います
- 初期の値と出力の配分:wgstack の接続の待ち行列(512)、握手の途中の表(1024 行)、TIME_WAIT の表(65,536 行)、出力の組の間の deficit round robin、UDP の枠の大きさの区分が、通常の利用で足りるかを、実機と qbench の測定で確かめます
