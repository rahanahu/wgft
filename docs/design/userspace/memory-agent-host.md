# エージェントとホストのメモリの条件

エージェントとホストに要るメモリは、フロー数に加えて、accept の待ち行列、待ち受け、OS の保持を数えます。
同じカーネルを使うプロセスの受信予算は、ホストの TCP メモリを共有します。


エージェントの生きているヒープの上界も同じ形の和で、`vpsd` と次の点が違う。
既定の上限で、`vpsd` がユーザー空間モードであり、`vpsd` とエージェントの K が同じなら、既定の gVisor の netstack を使うエージェントのプロセスの上界は約 12.2 GiB です。
wgstack を使う場合の上界は、後述の[wgstack を使うエージェントの上界](#wgstack-を使うエージェントの上界)で約 3.9 GiB です。
式に数えた項は、エージェントの TCP の待ち受けの数によりません。
待ち受けごとの endpoint と goroutine は式の外です([TCP のポートごとの待ち受け](memory-limits.md#tcp-のポートごとの待ち受け))。

<a id="固定の費用"></a>
- 固定の費用:ランタイムとトンネル 1 つの分として 20 MiB とする(推定)。
  トンネル 1 つの分は、WireGuard の受信の包み(`internal/dataplane/userspace/wgbind` の `BatchOne`)が Linux で固定で持つ受信のバッファ約 16 MiB を含みます。
  包みは、トンネルを開くときに、受信の関数(IPv4 と IPv6 に 1 つずつ)ごとに、標準のバインドが 1 回に読む 128 件分の 64 KiB のバッファを作ります。
  ホストでの 1 回の測定では、エージェントのトンネル 1 つを立てた直後の生きているヒープは約 17.2 MiB でした。
  `vpsd` のトンネルも同じ包みを使い、`vpsd` の表では固定の費用の項がこの分を持ちます
<a id="wireguard-go-のキュー"></a>
- wireguard-go のキュー:ピアは `vpsd` の 1 つだけなので、ピアごとのキューと device 全体のキューの 1 組を持ちます
<a id="udp-のセッション"></a>
- UDP のセッション:1.2 KiB × U とする(測定)。
  LAN の宛先へのカーネルの UDP ソケットは別にあり、ホストの項です
<a id="エージェント用-api-と送信元ごとの新規フローの表"></a>
- エージェント用 API と送信元ごとの新規フローの表:エージェントはどちらも持ちません
<a id="accept-の待ち行列"></a>
- accept の待ち行列:`vpsd` がユーザー空間モードの組では、438 KiB ×(`vpsd` の K + 96)とする(推定)。
  1 本の 438 KiB は、受信の floor の 256 KiB に TCP のフローと同じ受信の比 1.67 を掛けた 428 KiB と([TCP のフロー 1 本の上界](memory-server.md#tcp-のフロー-1-本の上界))、endpoint の構造の 10 KiB の和です。
  待ち行列の接続は `vpsd` の dial だけが作る。
  `vpsd` がエージェントへ dial するのは、中継(プロキシモードの中継を含む)と、運用者が管理用 API か Web UI から起こす疎通確認([10.1 節](../interface.md#101-web-ui)。
  1 回につき 1 本)です。
  中継の dial の数は `vpsd` の K で抑えられる。
  96 の内訳は記録に残っていません。
  2026-10-03 の改訂までは、`vpsd` は待ち受けを開くときにも試し接続を同時に 32 件まで行っていた([6.3 節](../vps/userspace.md#63-ユーザー空間モード))。
  1 件の待ちを打ち切った後も下の dial は 5 秒の期限まで残るので、96 はその分(32 の 3 倍)と推定しているが、確かめていません。
  今はこの 96 を疎通確認の分の余裕として残します。
  疎通確認の同時の数を抑える仕組みは、コードを読んだ範囲では見つからなかった。
  この項は、疎通確認を同時に 96 本を超えて起こさない運用も前提とします。
  この上界は `vpsd` が信頼された相手であることを前提とします。
  構造の上限は、Accept を待つ接続が待ち受け 1 つあたり backlog の 4096 本で、待ち受け 1 つで約 1.67 GiB(4096 × 428 KiB)です。
  固定版の gVisor は、握手を終える `synRcvdState` で待ち行列の満杯を確かめ、その後の `deliverAccepted` では確かめずに待ち行列へ入れます。
  この 2 つの間の競合で、ほかに最大 GOMAXPROCS - 1 本が加わります。
  この分は CPU が 4 個で約 1.3 MiB(3 × 438 KiB)であり、項に含めません。
  握手の途中の接続(SYN-RCVD)は、これとは別に待ち受け 1 つあたり 4095 本までありえます。
  固定版の gVisor は受信の側を ESTABLISHED に入るときに作ります。
  SYN-RCVD の間に届いたデータは、窓の外なら ACK を返して捨て、窓の内で ACK を持たなければ捨て、ACK を持てば握手を終えてから新しい接続で処理し直します。
  握手の途中の接続も TCP の endpoint 1 つであり、その segment の処理待ちは、処理されるまでの短い間、受信のバッファまでの中身を持ちえます([短い間の保持](memory-limits.md#中身の無い-segment-の処理待ち))。
  このため、握手の途中の接続には受信の floor の分を数えず、endpoint の構造の分だけを数えます(ソースから読んだ)。
  カーネルモードの `vpsd` の後ろでは、待ち行列の接続を作るのは公開側の利用者なので、この構造の上限で数えます。
  さらに、Accept を待つ 4096 本と握手の途中の 4095 本の endpoint の構造を 1 つ 10 KiB で数え、待ち受け 1 つあたり約 80 MiB を足します。
  10 KiB は保守側の値で、閉じた後の接続の endpoint の測定は 5.4 から 8 KiB でした。
  ラボでは、カーネルモードの `vpsd` の後ろで既定の上限のまま 1 つのルールへ接続を開き続けた間、中継の前の接続の最大は実行ごとに約 1,140 本から約 1,290 本でした。
  1,140 本の実行では 2,044 本を中継し、エージェントの生きているヒープの最大は 179 MiB でした。
  実際の長さは到着の速さと中継の Accept の遅れで決まり、測定は上限を示さないので、上界には使いません
<a id="試し接続boost-の枠が参照する古い-stack少数の古いトンネルの世代"></a>
- 試し接続、boost の枠が参照する古い stack、少数の古いトンネルの世代:合わせて 4.4 MiB とする(推定)。
  boost の枠が参照する古い stack は最大 16 個です
<a id="goroutine-のスタック"></a>
- goroutine のスタック:2.2 KiB × U + 24 KiB × K + 2 MiB とする(TCP の項は推定、ほかは測定)

エージェントの上界のうち、待ち受けの数に比例する項(UDP の待ち受けの読み取り)と、accept の待ち行列の `vpsd` の K による項は、`vpsd` が信頼された相手であることを前提とします。
accept の待ち行列の項は、運用者が疎通確認を同時に 96 本を超えて起こさないことも前提とする(前述の一覧の項)。
エージェントの待ち受けは `vpsd` が配る全体状態のルールのポートごとに 1 つ開き、エージェントは待ち受けの数に上限を持ちません。
範囲のルールはポートの数だけ待ち受けを開くので、範囲が 1-65535 の UDP のルール 1 本で、待ち受けの受信用のバッファだけで約 4 GiB(65535 × 64 KiB)になります。
この値はソースから導いたもので、測っていません。
[11 節](../security/admin-transport.md#11-セキュリティ)は、VPS を奪った攻撃者が全体状態の値を自由に選べることを脅威に含めます。
その攻撃者に対するエージェントのメモリの上界は定めていません。

accept の待ち行列を `vpsd` の K で抑える前提は、`vpsd` がユーザー空間モードの組だけで成り立ちます。
カーネルモードの `vpsd` の後ろでは、公開側の利用者の接続が DNAT でエージェントの netstack に届くので、相手は信頼されない利用者です。
[閉じた後の接続の表](tcp-retention.md#閉じた後の接続の表)、[TCP の MSS の下限](packet-validation.md#tcp-の-mss-の下限)、[中身の無い ACK の予算](packet-validation.md#中身の無い-ack-の予算)は相手によらず効きます。
このため、閉じた後の接続、TCP のフロー 1 本の確認を待つ segment、中身の無い ACK の処理待ちは、この組でも `vpsd` と同じ項で抑えます。
この組では、中身の無い ACK の処理待ちのうち上界の式に入れない残り([既知の制限](memory-limits.md#中身の無い-segment-の処理待ち))を、信頼しない利用者が起こせます。
accept の待ち行列の項は、TCP の待ち受け 1 つあたり、受信の約 1,710 MiB と endpoint の構造の約 80 MiB の和(約 1,790 MiB)に置き換えます(前述の一覧の項)。
既定の上限で TCP の待ち受けが 1 つなら、エージェントのプロセスの上界は約 13.9 GiB です。
TCP の待ち受けが 1 つ増えるごとに、プロセスの上界は約 1,790 MiB の 2.05 倍の約 3,670 MiB(約 3.6 GiB)増えます。
末尾の配送は、この組でもエージェントの K で抑えます。
VPS の `ct count` は conntrack の項目がある間は配送中の接続も数えるとソースから読めますが、その点はラボでは未確認です。
ラボでは、利用者が FIN を送って読まずに末尾を残させると、CLOSE_WAIT の conntrack の項目が、エージェントが K を持つ間に期限で消えました。
その後、同じ送信元が上限を超えて新しい接続を開けました。
`nf_conntrack_tcp_loose=1` では、利用者が読むと項目が作り直され、末尾が届きました。
0 では、項目が消えた後にエージェントの接続が打ち切られ、K が返って末尾が失われました。
この打ち切りの原因は未確認です。
この組では送信元ごとの上限が配送中の接続を最後まで数えないことを、既知の制限として残します。

<a id="syn-cookie-の経路の受信のメモリの会計"></a>
固定版の gVisor には、待ち受けの受信のメモリの会計に既知の制限があります。
待ち受けが segment を新しい endpoint に渡すとき、`segment.setOwner` は前の持ち主の受信のメモリの会計から、その segment の分を引きません。
SYN cookie の経路では、待ち受けの会計が受信のバッファを超えることがあり、その後の待ち受けは payload を持つ segment を拒み続けます。
既定の構成では backlog が 4096 で、ユーザー空間モードの `vpsd` が同時に dial するのは K + 96 本(既定で 2,144 本)までなので、SYN cookie は使われません。
これは K + 96 が 4095 より小さい間だけ成り立ちます。
`WGFT_MAX_TCP_FLOWS` をそれより大きくすると、ユーザー空間モードの `vpsd` 自身の dial で SYN cookie の経路に入りえます。
カーネルモードの `vpsd` の後ろでは、待ち受け 1 つあたり 4095 本を超える握手の途中の接続を作る SYN の洪水で、この制限が起きえます。
backlog を 256(待ち受け 1 つあたりの受信の floor で約 64 MiB)に下げるには、前の持ち主の会計を返す版の gVisor が要ります。
gVisor を更新するときに、この点を確かめ直します。

ホストに要るメモリは、プロセスの上界に、カーネルの固定の分と、OS と他のプロセスのための余白 256 MiB(推定)を足し、1 - 0.093 で割った値とします。
カーネルの固定の分は、`vpsd` では WireGuard のソケットの 56 MiB と、公開側の UDP の待ち受け 1 つあたり約 4.2 MiB です。
公開側の TCP とエージェント用 API のソケットのバッファは、名目では K と接続の数に比例して大きい。
ホスト全体の TCP のバッファは、上限 `net.ipv4.tcp_mem` を超えて増えません。
0.093 は、この上限の既定の値がメモリに占める割合である(ラボのホストの値からの推定。
Linux の既定の値はメモリの量に比例する)。
ホストに要るメモリは今までどおりこの割合で数えます。
この数え方が示すのは、TCP のバッファが上限まで使われてもメモリが足りることだけです。
上限に達すると前述の巻き添えが起きるので、`tcp_mem` の上限は TCP を遅らせずに使える量ではない(次の段落)。
エージェントのホストでは、LAN 側の UDP のソケットの受信のキュー(名目で U × `net.core.rmem_default`)をホスト全体の `net.ipv4.udp_mem` が抑え、LAN 側の TCP のバッファを `tcp_mem` が抑えます。
この分はホストの設定で決まるので、次の表ではエージェントのホストに要るメモリを示さない。

中継のカーネルの TCP ソケットの受信の予算は、前述の[「中継のカーネルの TCP ソケットの受信のバッファ」](tcp-host-sockets.md#中継のカーネルの-tcp-ソケットの受信のバッファ)の固定から決まる K × 256 KiB + 128 MiB です。
`vpsd` では公開側のソケットの、エージェントでは LAN 側のソケットの予算であり、どちらもそのプロセスの K で決まる。
この予算は、動いている中継のソケットが受信の側に溜める量の上限であり、ホストが安全であるための十分な条件ではありません。
送信の側、末尾を届けている途中のソケット、中継が閉じた後に残るソケット(前述の[「固定しないもの」](tcp-host-sockets.md#固定しないもの))、エージェント用 API、同じホストの他の TCP には、別にメモリが要る。
予算は、ホストの実際の `net.ipv4.tcp_mem` と比べる。
`tcp_mem` はページの数で表した 3 つの値で、順に、圧迫を始めない量、圧迫の閾値、上限です。
byte に直すにはページの大きさ(`getconf PAGESIZE`、多くのホストで 4096)を掛ける。
使用量が圧迫の閾値を超えると、カーネルは TCP のバッファの使い方を抑え始め、上限に達すると前述の巻き添えが起きる。
このため予算は上限より小さいだけでなく、圧迫の閾値と比べて余裕があることを見る。
Linux の既定の `tcp_mem` は、起動時にカーネルが数えた空きのページから決まる。
上限はそのページの数の約 3/32、圧迫の閾値は 1/16 で、圧迫の閾値は上限の 2/3 です。
空きのページはメモリの量より少ないので、既定の値はメモリの量にこの割合を掛けた値より小さい。
次の表のホストに要るメモリと同じ大きさのホストで `tcp_mem` が既定の値なら、既定の K の予算 640 MiB は、上限(約 1,210 MiB)を下回り、圧迫の閾値(約 810 MiB)を約 170 MiB 下回る。
K が 1024 の行では、予算は圧迫の閾値を 120 から 126 MiB 下回る。
どちらの行でも、余裕は圧迫の閾値の 21 から 25% です。
実際の上限と圧迫の閾値は空きのページから決まり、メモリの量から数えた値より小さい。
実際のホストでこの余裕が残るかは確かめていません。
この比較は 1 つのプロセスの予算だけで数えたものです。
1 つのカーネルを共有するプロセスの予算は合算します。
`vpsd` とエージェントを同じホストで動かす場合や、LXC のようなコンテナで動かす場合がこれに当たる。
予算が収まらないときは、まず K(`WGFT_MAX_TCP_FLOWS`)を下げる。
`tcp_mem` を変えるかどうかは、ホストの管理者がメモリの量と他の用途を確かめて決めることであり、LXC の中から変えるものではありません。
上限を引き上げると、TCP が使える回収できないカーネルのメモリが増えるので、引き上げることは無条件の解決になりません。

次の表は、エージェントが 1 つ、TCP の宛先が 1 つ、`per_source_rate` を持つルールが 1 本、UDP の待ち受けが 1 つの場合の値です。
式に数えた項は、TCP の宛先の数とエージェントの TCP の待ち受けの数によりません。
ポートごとの待ち受けと goroutine は式の外です([TCP のポートごとの待ち受け](memory-limits.md#tcp-のポートごとの待ち受け))。
単位は GiB で、受信の予算の列だけ MiB です。
エージェントの列は、`vpsd` がユーザー空間モードで、`vpsd` とエージェントの K と U が同じ場合の値です。

| K | U | `vpsd` のプロセスの上界 | `vpsd` のホストに要るメモリ | エージェントのプロセスの上界 | 中継のカーネルのソケットの受信の予算(プロセスごと、MiB) |
|---|---|---|---|---|---|
| 2048(既定) | 8192(既定) | 11.2 | 12.7 | 12.2 | 640 |
| 2048 | 2048 | 11.1 | 12.6 | 12.2 | 640 |
| 1024 | 8192 | 6.9 | 7.96 | 7.1 | 384 |
| 1024 | 2048 | 6.8 | 7.9 | 7.0 | 384 |
| 512 | 8192 | 4.8 | 5.6 | 4.5 | 256 |
| 512 | 2048 | 4.7 | 5.5 | 4.5 | 256 |
| 256 | 8192 | 3.7 | 4.4 | 3.2 | 192 |
| 256 | 2048 | 3.7 | 4.4 | 3.2 | 192 |

エージェントが 1 つ増えるごとに、`vpsd` のプロセスの上界は約 0.60 GiB、ホストに要るメモリは約 0.66 GiB 増える。
U を下げても上界はほとんど減らず、8192 から 2048 に下げて減るのは `vpsd` で約 0.07 GiB、エージェントで約 0.03 GiB です。
`vpsd` とエージェントの K をそろえて 1 減らすと、`vpsd` の上界は約 4.3 MiB、エージェントの上界は accept の待ち行列の分を含めて約 5.1 MiB 減る。
accept の待ち行列の項は `vpsd` の K で決まるので、エージェントの K だけを 1 減らしたときにエージェントの上界が減るのは約 4.3 MiB です。
[末尾を届けている途中](tcp-retention.md#中継が終わった後の末尾の配送)の netstack の接続はエージェントの K に数えるので、この保持は K の項に入ります。
表の構成で、既定の上限のホストに要るメモリは約 12.7 GiB です。
メモリが 12 GiB のホストでは足りません。
メモリが 8 GiB のホストは、表の構成で K を 1024 まで下げれば、式に数えた保持点の分が収まる。
ただし、U が既定の 8192 なら要るメモリは約 7.96 GiB で、余裕は約 40 MiB しかありません。

K に比例しない部分は、エージェントが 1 つで U が既定なら、GC の余裕を含めて約 2.7 GiB あります。
K と U を設定できる最小の 16 にしても、`vpsd` のホストに要るメモリは約 3.2 GiB です。
したがって、メモリが 1 から 2 GiB のホストでは、上限を下げるだけでは、すべての保持点を埋める攻撃に耐えると示せない。
メモリが 4 GiB のホストは、表の構成で K を 128 まで下げれば、式に数えた保持点の分が収まる。
K に比例しない項のうち生きているヒープが大きいのは、TCP の boost(約 0.35 GiB)、エージェント用 API の認証前の接続(約 0.17 GiB)、エージェントごとのハートビートの保存と stream の受信(約 0.15 GiB)、エージェントごとの wireguard-go のキュー(約 0.13 GiB)、中身の無い ACK の処理待ちの boost の分(約 0.11 GiB)です。

<a id="wgstack-を使うエージェントの上界"></a>
エージェントの netstack に wgstack を選んだ場合(`WGFT_AGENT_NETSTACK=wgstack`)の上界は、前述の式の gVisor の項を wgstack の `Bound` の項に置き換えて数えます([上界の式](wgstack.md#上界の式))。
置き換える gVisor の項は、TCP のフローの gVisor の分(送信の側、確認を待つ segment、受信の側)、TCP の boost、中身の無い ACK の処理待ち、閉じた後の netstack の TCP の接続、accept の待ち行列、netstack の出力のキュー、UDP の受信の会計、IPv4 の再組み立ての表です。
wgstack は、接続の枠(K + 512 本)、floor と boost の予約、握手の途中の表、TIME_WAIT の表、制御の出力の輪、UDP の予算、再組み立ての表を `Bound` の 1 つの和で数えます。
wgstack は受けた packet を Write の中で処理し、処理待ちの行列を持たないので、中身の無い ACK の処理待ちに当たる項はありません。
accept の待ち行列は Device 全体の 512 本で、接続の枠に含まれるので、上界は TCP の待ち受けの数によりません。

残す共有の項と、wgstack での値は次のとおりです。

| 項 | 生きているヒープの上界 | 出どころ |
|---|---|---|
| 固定の費用(ランタイムとトンネル 1 つ) | 20 MiB | 推定。gVisor の行と同じ |
| wireguard-go のピアごとと device 全体のキュー | 136.3 MiB + 65 MiB | 導出。gVisor の行と同じ |
| ピア 1 つの待機の分 | 0.15 MiB | 導出と測定。gVisor の行の再組み立ての項から、ピアの分だけを残します |
| 応答のバッファと UDP の待ち受けの読み取り | 7 MiB + 0.46 MiB × L | 導出と推定。gVisor の行と同じ |
| UDP のセッション | 1.2 KiB × U | gVisor で測った値をそのまま使います(wgstack では測っていません) |
| TCP のフローの中継の分 | 74 KiB × K | 導出。gVisor の行のフロー 1 本の固定の分です。中継のコピーのバッファと gVisor の endpoint の分を含み、endpoint の分を保守側に残します |
| 試し接続と少数の古いトンネルの世代 | 4.4 MiB + M_fix | 推定。閉じた Device を参照が残す間は、接続の枠と表の M_fix(K = 2048 で約 25.4 MiB)が残りえるので、1 世代分を足します。wgstack の閉じた世代が残す量は測っていません |
| wgstack の `Bound` の `Total` と `Transient` | K = 2048 で約 1,498.4 MiB + 8 MiB | 導出。`Device.Bound` が構造の大きさと表の数から求める値です |

`Total` の内訳は、K = 2048 で M_fix が約 25.4 MiB、floor の項が約 1,335.0 MiB、boost の項が約 125.4 MiB、UDP の予算が約 8.6 MiB、再組み立ての表が 4 MiB です。
K が 1024、512、256 では、`Total` は約 958.0、687.7、552.6 MiB で、M_fix は約 19.0、15.8、14.2 MiB です。
floor の項の会計は、完成の段階の測定(K = 256 の 256 本に floor いっぱいの受信のデータを持たせた試験)で生きているヒープの増加を上から抑えました([上界の式](wgstack.md#上界の式))。
boost の項の会計は、両方の向きの boost を持たせて送信と受信の輪を満たした接続の試験で、生きているヒープの増加を上から抑えました(同じ節)。
エージェントのプロセス全体で、すべての項を同時に最悪にして測ってはいません。
goroutine のスタックは gVisor の行と同じ 2.2 KiB × U + 24 KiB × K + 2 MiB とします。
wgstack は接続ごとの goroutine を持たないので、TCP の項は中継の goroutine の分です(推定)。
ランタイムの領域と GC の係数は gVisor の行と同じく、生きているヒープの 2 倍に、10 MiB と生きているヒープの 5% を足します。
この係数と項は gVisor を使うプロセスの測定から丸めた値で、wgstack を使うプロセスでは測っていません。
wgstack を使うエージェントのプロセス全体の RSS を測った値はまだ無く、ラボでの測定を進めています。

既定の上限で L が 1 なら、wgstack を使うエージェントの生きているヒープの上界は約 1,923 MiB で、プロセスの上界は約 3.9 GiB です。
この値は、`vpsd` がユーザー空間モードの組でも、カーネルモードの `vpsd` の後ろでも同じです。
TCP の待ち受けが 1 つでも複数でも変わりません。
gVisor を使うエージェントの同じ構成の値は、`vpsd` がユーザー空間モードで約 12.2 GiB、カーネルモードの `vpsd` の後ろで TCP の待ち受けが 1 つなら約 13.9 GiB で、待ち受けが 1 つ増えるごとに約 3.6 GiB 増えます(前述)。
中継のカーネルの TCP ソケットの受信の予算は netstack によらないので、前述の値のままです。

| K | U | `vpsd` がユーザー空間モード(GiB) | カーネルモードの `vpsd` の後ろ、TCP の待ち受けが 1 つ(GiB) | 同じく待ち受けが 4 つ(GiB) |
|---|---|---|---|---|
| 2048(既定) | 8192(既定) | 3.92 | 3.92 | 3.92 |
| 2048 | 2048 | 3.90 | 3.90 | 3.90 |
| 1024 | 8192 | 2.66 | 2.66 | 2.66 |
| 1024 | 2048 | 2.63 | 2.63 | 2.63 |
| 512 | 8192 | 2.03 | 2.03 | 2.03 |
| 512 | 2048 | 2.00 | 2.00 | 2.00 |
| 256 | 8192 | 1.71 | 1.71 | 1.71 |
| 256 | 2048 | 1.68 | 1.68 | 1.68 |

表の値は wgstack を使うエージェントのプロセスの上界です。
後の 2 列は、カーネルモードの `vpsd` の後ろで、信頼しない利用者が待ち受けごとに握手と accept の待ち行列を埋める場合の値です。
wgstack では握手の途中の表(1024 行)と accept の待ち行列(512 本)が Device 全体の大きさなので、待ち受けの数で上界が変わりません。
待ち受けごとの小さな構造と accept の goroutine は、gVisor の行と同じく式の外です。

<a id="エージェントのメモリの測定"></a>
## 測定: 敵対的な負荷の下のエージェントのメモリ

2026-10-30 に、ユーザー空間モードのエージェントの RSS と生きているヒープの最大を、既定の gVisor と wgstack(`WGFT_AGENT_NETSTACK=wgstack`)で測りました(測定。1 つの版の、負荷ごとに 1 回の実行です)。
設定は `lab/agentmem.sh` のとおり、K を 256、U を 256 とし、メモリ 2 GiB の Debian 12 のラボの VM で、カーネルモードの server の後ろにエージェントを 1 つ置きました。
負荷ごとに server とエージェントを起動し直し、エージェントの `VmHWM`、0.5 秒ごとの RSS、0.5 秒ごとの Go のランタイムの生きているヒープ、`GODEBUG=gctrace=1` の最大を読んでいます。
wgstack の Device の `Stats` と `Bound` は、測定用の build tag `labmemprobe` の build だけが記録します。
製品の build は `Stats` を載せません。
生きているヒープは GC の後の値(`/gc/heap/live`)で、大きなバッファの未使用のゼロページはヒープに数えても RSS に数えないので、RSS より大きくなることがあります。

比べる上界は、前述の式を同じ設定で数えた値です(`lab/agentmem.py`)。
gVisor は K = 256、U = 256 で、TCP の待ち受けが 1 つなら生きているヒープの上界が約 3,223 MiB、プロセスの上界が約 6,626 MiB です。
待ち受けが 8 つなら、それぞれ約 15,753 MiB と約 32,312 MiB です。
wgstack は、[wgstack を使うエージェントの上界](#wgstack-を使うエージェントの上界)の式を使い、build が返した `Bound` の `Total` 549.8 MiB と `Transient` を使い、待ち受けの数によらず生きているヒープの上界が約 823 MiB、プロセスの上界が約 1,706 MiB です。
測った build は、区間の表を treap にした変更より前の版で、区間 1 つが 12 byte でした。
負荷(c)は、その前の区間の表に対して測った値です。
その build の `Bound` には 3 つの数え落としがありました。
1 つ目は boost の枠を持つ接続が持ち続ける floor の記録の輪と区間の表で、16 × 20,732 byte(約 0.32 MiB)です。
2 つ目は配列の確保の丸め([上界の式](wgstack.md#上界の式))で、約 1.11 MiB です。
3 つ目は接続の枠 1 つが表の外に持つ構造で、0.5 KiB の推定を測った値の 1 KiB に改めた分の 768 × 512 byte(約 0.38 MiB)です。
今の数え方でその build の `Total` を数え直すと約 551.6 MiB で、生きているヒープの上界は約 826 MiB、プロセスの上界は約 1,712 MiB です。
表の上界と比は測ったときの値のままです。
数え直した上界で比を求めても、変化はどれも 0.001 未満です。
UDP の待ち受けは、どの負荷でも 1 つです。

| 負荷 | netstack | RSS の最大(MiB) | 生きているヒープの最大(MiB) | プロセスの上界(MiB) | RSS / 上界 | ヒープ / 上界 |
|---|---|---|---|---|---|---|
| (a) SYN の洪水 | gVisor | 45 | 39 | 6,626 | 0.007 | 0.012 |
| (a) SYN の洪水 | wgstack | 33 | 33 | 1,706 | 0.019 | 0.040 |
| (b) LAN 側が読まない確立済みの接続 | gVisor | 179 | 192 | 6,626 | 0.027 | 0.060 |
| (b) LAN 側が読まない確立済みの接続 | wgstack | 172 | 208 | 1,706 | 0.101 | 0.253 |
| (c) 順序外の segment と穴埋め | gVisor | 97 | 168 | 6,626 | 0.015 | 0.052 |
| (c) 順序外の segment と穴埋め | wgstack | 54 | 104 | 1,706 | 0.032 | 0.126 |
| (d) TIME_WAIT の入れ替わり | gVisor | 110 | 104 | 6,626 | 0.017 | 0.032 |
| (d) TIME_WAIT の入れ替わり | wgstack | 47 | 42 | 1,706 | 0.028 | 0.051 |
| (e) 多数の送信元ポートからの UDP | gVisor | 46 | 27 | 6,626 | 0.007 | 0.008 |
| (e) 多数の送信元ポートからの UDP | wgstack | 38 | 34 | 1,706 | 0.022 | 0.041 |
| (f) 待ち受け 1 つへの 2,048 接続の同時の開始 | gVisor | 72 | 132 | 6,626 | 0.011 | 0.041 |
| (f) 待ち受け 1 つへの 2,048 接続の同時の開始 | wgstack | 49 | 114 | 1,706 | 0.029 | 0.138 |
| (f) 待ち受け 8 つへの 2,048 接続の同時の開始 | gVisor | 55 | 128 | 32,312 | 0.002 | 0.008 |
| (f) 待ち受け 8 つへの 2,048 接続の同時の開始 | wgstack | 60 | 141 | 1,706 | 0.035 | 0.171 |

どの負荷でも、測った値は上界の内側でした。
最も上界に近いのは wgstack の(b)で、生きているヒープが上界の 25%、RSS が 10% でした。
(b)で wgstack の Device が数えた保持は、chunk が約 122 MiB、送信の記録が約 9.5 MiB、区間の表が約 1.6 MiB で、合わせて約 133 MiB でした。
`Boosted` は 16(boost の枠の数の上限)に達し、`Total` の 549.8 MiB の内側に収まっています。
wgstack の `Stats` の最大は、(a)で握手の途中の行が 512、`SynTableFull` が 5,543、(c)で `OOODropped` が約 433 万、(d)で TIME_WAIT の行が 60,003(表の 65,536 行には届かなかった)でした。
(f)の待ち受けが 1 つから 8 つに増えても、wgstack の最大の RSS は 49 から 60 MiB、生きているヒープは 114 から 141 MiB で、上界は変わりません。
gVisor の上界は 6,626 から 32,312 MiB に増えますが、測った値は待ち受けの数でほとんど変わりませんでした。

この測定は上界を確かめる試験ではありません。
負荷は式に数えた保持点をすべて同時に埋めておらず、gVisor の上界に対する測定値は、RSS が最大 2.7%、生きているヒープが最大 6% です。
次の点は確かめていません。

- (e)で、UDP のセッションの表(U = 256)が実際に満たされたかは確かめていません。
  送り手は 30 秒で 599,985 個を送り、送信の失敗は 0 でした。
  wgstack の UDP の受信の保持は最大 0 byte で、VPS の conntrack の項目は約 8,200 件でした。
- (a)で gVisor が握手の途中に持った接続の数は読んでいません。
  wgstack は握手の途中の表が満杯になり、新しい SYN を `SynTableFull` として数えました。
- (d)で gVisor の閉じた後の接続の表(13,107 行)が満杯になったかは、`Stats` が無いので読んでいません。
- 各負荷は 1 回の実行で、実行の間のばらつきは測っていません。
- 比べた上界は、前述のとおり式に数えた保持点の和で、式の外の保持点(待ち受けごとの endpoint、中身の無い ACK の処理待ちの残りなど)は含みません。
