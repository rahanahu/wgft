# エージェントとホストのメモリの条件

エージェントとホストに要るメモリは、フロー数に加えて、宛先、待ち受け、OS の保持を数えます。
同じカーネルを使うプロセスの受信予算は、ホストの TCP メモリを共有します。


エージェントの生きているヒープの上界も同じ形の和で、`vpsd` と次の点が違う。
既定の上限で、`vpsd` とエージェントの K が同じで、エージェントの TCP の待ち受けが 1 つなら、エージェントのプロセスの上界は約 5.6 GiB です。

<a id="固定の費用"></a>
- 固定の費用:ランタイムとトンネル 1 つの分として 20 MiB とする(推定)
<a id="wireguard-go-のキュー"></a>
- wireguard-go のキュー:ピアは `vpsd` の 1 つだけなので、ピアごとのキューと device 全体のキューの 1 組を持ちます
<a id="udp-のセッション"></a>
- UDP のセッション:1.2 KiB × U とする(測定)。
  LAN の宛先へのカーネルの UDP ソケットは別にあり、ホストの項です
<a id="エージェント用-api-と送信元ごとの新規フローの表"></a>
- エージェント用 API と送信元ごとの新規フローの表:エージェントはどちらも持ちません
<a id="accept-の待ち行列"></a>
- accept の待ち行列:256 KiB ×(`vpsd` の K + 96)とする(推定)。
  待ち行列の接続は `vpsd` の dial だけが作る。
  `vpsd` がエージェントへ dial するのは、中継(プロキシモードの中継を含む)と、運用者が管理用 API か Web UI から起こす疎通確認([10.1 節](../interface.md#101-web-ui)。
  1 回につき 1 本)です。
  中継の dial の数は `vpsd` の K で抑えられる。
  96 の内訳は記録に残っていません。
  2026-10-03 の改訂までは、`vpsd` は待ち受けを開くときにも試し接続を同時に 32 件まで行っていた([6.3 節](../vps/userspace.md#63-ユーザー空間モード))。
  1 件の待ちを打ち切った後も下の dial は 5 秒の期限まで残るので、96 はその分(32 の 3 倍)と推定しているが、確かめていません。
  今はこの 96 を疎通確認の分の余裕として残します。
  疎通確認の同時の数を抑える仕組みは、コードを読んだ範囲では見つからなかった。
  この項は、疎通確認を同時に 96 本を超えて起こさない運用も前提とします。
  この上界は `vpsd` が信頼された相手であることを前提とします。
  gVisor の構造だけで見ると、待ち行列は待ち受け 1 つあたり 8,191 本まで伸びうる
<a id="time_wait"></a>
- TIME_WAIT:487 MiB × エージェントの TCP の待ち受けの数とします。
  受けた側でも 4 つ組の一意性から宛先あたりと同じ件数になるという推定による
<a id="試し接続boost-の枠が参照する古い-stack少数の古いトンネルの世代"></a>
- 試し接続、boost の枠が参照する古い stack、少数の古いトンネルの世代:合わせて 4.4 MiB とする(推定)。
  boost の枠が参照する古い stack は最大 16 個です
<a id="goroutine-のスタック"></a>
- goroutine のスタック:2.2 KiB × U + 24 KiB × K + 2 MiB とする(TCP の項は推定、ほかは測定)

エージェントの上界のうち、待ち受けの数に比例する項(TIME_WAIT と UDP の待ち受けの読み取り)と accept の待ち行列の項は、`vpsd` が信頼された相手であることを前提とします。
accept の待ち行列の項は、運用者が疎通確認を同時に 96 本を超えて起こさないことも前提とする(前述の一覧の項)。
エージェントの待ち受けは `vpsd` が配る全体状態のルールのポートごとに 1 つ開き、エージェントは待ち受けの数に上限を持ちません。
範囲のルールはポートの数だけ待ち受けを開くので、範囲が 1-65535 の UDP のルール 1 本で、待ち受けの受信用のバッファだけで約 4 GiB(65535 × 64 KiB)になります。
この値はソースから導いたもので、測っていません。
[11 節](../security/admin-transport.md#11-セキュリティ)は、VPS を奪った攻撃者が全体状態の値を自由に選べることを脅威に含めます。
その攻撃者に対するエージェントのメモリの上界は定めていません。

エージェントの accept の待ち行列と TIME_WAIT を信頼された相手に限る前提は、`vpsd` がユーザー空間モードの組だけで成り立ちます。
カーネルモードの `vpsd` の後ろでは、公開側の利用者の接続が DNAT でエージェントの netstack に届くので、相手は信頼されない利用者です。
利用者が accept の待ち行列と TIME_WAIT を作れるため、この組の両方の上界は定めていません。
末尾の配送は、この組でもエージェントの K で抑えます。
VPS の `ct count` は conntrack の項目がある間は配送中の接続も数えるとソースから読めますが、その点はラボでは未確認です。
ラボでは、利用者が FIN を送って読まずに末尾を残させると、CLOSE_WAIT の conntrack の項目が、エージェントが K を持つ間に期限で消えました。
その後、同じ送信元が上限を超えて新しい接続を開けました。
`nf_conntrack_tcp_loose=1` では、利用者が読むと項目が作り直され、末尾が届きました。
0 では、項目が消えた後にエージェントの接続が打ち切られ、K が返って末尾が失われました。
この打ち切りの原因は未確認です。
この組では送信元ごとの上限が配送中の接続を最後まで数えないことを、既知の制限として残します。

ホストに要るメモリは、プロセスの上界に、カーネルの固定の分と、OS と他のプロセスのための余白 256 MiB(推定)を足し、1 - 0.093 で割った値とします。
カーネルの固定の分は、`vpsd` では WireGuard のソケットの 56 MiB と、公開側の UDP の待ち受け 1 つあたり約 4.2 MiB です。
公開側の TCP とエージェント用 API のソケットのバッファは、名目では K と接続の数に比例して大きい。
ホスト全体の TCP のバッファは、上限 `net.ipv4.tcp_mem` を超えて増えません。
0.093 は、この上限の既定の値がメモリに占める割合である(ラボのホストの値からの推定。
Linux の既定の値はメモリの量に比例する)。
ホストに要るメモリは今までどおりこの割合で数えます。
この数え方が示すのは、TCP のバッファが上限まで使われてもメモリが足りることだけです。
上限に達すると前述の巻き添えが起きるので、`tcp_mem` の上限は TCP を遅らせずに使える量ではない(次の段落)。
エージェントのホストでは、LAN 側の UDP のソケットの受信のキュー(名目で U × `net.core.rmem_default`)をホスト全体の `net.ipv4.udp_mem` が抑え、LAN 側の TCP のバッファを `tcp_mem` が抑えます。
この分はホストの設定で決まるので、次の表ではエージェントのホストに要るメモリを示さない。

中継のカーネルの TCP ソケットの受信の予算は、前述の[「中継のカーネルの TCP ソケットの受信のバッファ」](tcp-host-sockets.md#中継のカーネルの-tcp-ソケットの受信のバッファ)の固定から決まる K × 256 KiB + 128 MiB です。
`vpsd` では公開側のソケットの、エージェントでは LAN 側のソケットの予算であり、どちらもそのプロセスの K で決まる。
この予算は、動いている中継のソケットが受信の側に溜める量の上限であり、ホストが安全であるための十分な条件ではありません。
送信の側、末尾を届けている途中のソケット、中継が閉じた後に残るソケット(前述の[「固定しないもの」](tcp-host-sockets.md#固定しないもの))、エージェント用 API、同じホストの他の TCP には、別にメモリが要る。
予算は、ホストの実際の `net.ipv4.tcp_mem` と比べる。
`tcp_mem` はページの数で表した 3 つの値で、順に、圧迫を始めない量、圧迫の閾値、上限です。
byte に直すにはページの大きさ(`getconf PAGESIZE`、多くのホストで 4096)を掛ける。
使用量が圧迫の閾値を超えると、カーネルは TCP のバッファの使い方を抑え始め、上限に達すると前述の巻き添えが起きる。
このため予算は上限より小さいだけでなく、圧迫の閾値と比べて余裕があることを見る。
Linux の既定の `tcp_mem` は、起動時にカーネルが数えた空きのページから決まる。
上限はそのページの数の約 3/32、圧迫の閾値は 1/16 で、圧迫の閾値は上限の 2/3 です。
空きのページはメモリの量より少ないので、既定の値はメモリの量にこの割合を掛けた値より小さい。
次の表のホストに要るメモリと同じ大きさのホストで `tcp_mem` が既定の値なら、既定の K の予算 640 MiB は、上限(約 560 MiB)と圧迫の閾値(約 375 MiB)のどちらも超える。
K が 1024 と 512 の行も、予算が圧迫の閾値を超える。
圧迫の閾値を下回るのは K が 256 の行だけで、その差も小さい。
実際の圧迫の閾値は空きのページから決まり、メモリの量から数えた値より小さいので、ホストによっては K が 256 の行も圧迫の閾値を超える。
この比較は 1 つのプロセスの予算だけで数えたものです。
1 つのカーネルを共有するプロセスの予算は合算します。
`vpsd` とエージェントを同じホストで動かす場合や、LXC のようなコンテナで動かす場合がこれに当たる。
予算が収まらないときは、まず K(`WGFT_MAX_TCP_FLOWS`)を下げる。
`tcp_mem` を変えるかどうかは、ホストの管理者がメモリの量と他の用途を確かめて決めることであり、LXC の中から変えるものではありません。
上限を引き上げると、TCP が使える回収できないカーネルのメモリが増えるので、引き上げることは無条件の解決になりません。

次の表は、エージェントが 1 つ、TCP の宛先が 1 つ、`per_source_rate` を持つルールが 1 本、UDP の待ち受けが 1 つの場合の値です。
単位は GiB で、受信の予算の列だけ MiB です。
エージェントの列は、`vpsd` とエージェントの K と U が同じ場合の値です。

| K | U | `vpsd` のプロセスの上界 | `vpsd` のホストに要るメモリ | エージェントのプロセスの上界 | 中継のカーネルのソケットの受信の予算(プロセスごと、MiB) |
|---|---|---|---|---|---|
| 2048(既定) | 8192(既定) | 5.0 | 5.9 | 5.6 | 640 |
| 2048 | 2048 | 4.9 | 5.8 | 5.6 | 640 |
| 1024 | 8192 | 3.7 | 4.4 | 3.8 | 384 |
| 1024 | 2048 | 3.6 | 4.3 | 3.7 | 384 |
| 512 | 8192 | 3.0 | 3.7 | 2.9 | 256 |
| 512 | 2048 | 2.9 | 3.6 | 2.8 | 256 |
| 256 | 8192 | 2.7 | 3.3 | 2.4 | 192 |
| 256 | 2048 | 2.6 | 3.2 | 2.4 | 192 |

エージェントが 1 つ増えるごとに、`vpsd` のプロセスの上界は約 0.28 GiB、ホストに要るメモリは約 0.3 GiB 増える。
TCP の宛先が 1 つ増えるごとに、プロセスの上界は約 1.0 GiB、ホストに要るメモリは約 1.1 GiB 増える。
エージェントの TCP の待ち受けが 1 つ増えるごとに、エージェントのプロセスの上界は約 1.0 GiB 増える。
U を下げても上界はほとんど減らず、8192 から 2048 に下げて減るのは `vpsd` で約 0.07 GiB、エージェントで約 0.03 GiB です。
`vpsd` とエージェントの K をそろえて 1 減らすと、`vpsd` の上界は約 1.3 MiB、エージェントの上界は accept の待ち行列の分を含めて約 1.8 MiB 減る。
accept の待ち行列の項は `vpsd` の K で決まるので、エージェントの K だけを 1 減らしたときにエージェントの上界が減るのは約 1.3 MiB です。
[末尾を届けている途中](tcp-retention.md#中継が終わった後の末尾の配送)の netstack の接続はエージェントの K に数えるので、この保持は K の項に入ります。
表の構成で、既定の上限のホストに要るメモリは約 5.9 GiB です。
6 GiB のホストでは余裕がほとんどありません。

K に比例しない部分は、エージェントが 1 つ、宛先が 1 つで U が既定なら、GC の余裕を含めて約 2.4 GiB あります。
K と U を設定できる最小の 16 にしても、`vpsd` のホストに要るメモリは約 2.9 GiB です。
したがって、メモリが 1 から 2 GiB のホストでは、上限を下げるだけでは、すべての保持点を埋める攻撃に耐えると示せない。
メモリが 4 GiB のホストは、表の構成で K を 512 まで下げれば、式に数えた保持点の分が収まる。
K に比例しない項のうち生きているヒープが大きいのは、宛先ごとの TIME_WAIT(約 0.5 GiB)、エージェント用 API の認証前の接続(約 0.17 GiB)、エージェントごとの wireguard-go のキュー(約 0.13 GiB)です。
