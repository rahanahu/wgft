# TCP の中継と終了

TCP は接続ごとに宛先へ接続し、ハーフクローズを保って中継します。
拒否と既存フローの終了では、接続の状態に応じた閉じ方を使います。


- TCP は接続ごとに `target` へ接続し、ハーフクローズを保って中継する([6.2 節](../vps/proxy.md#62-プロキシモード)と同じ)。
  接続数の上限は後述の「同時フロー数の上限」に従い、超えた接続は accept の直後に閉じます。
  この拒否は RST を送って即座に終える(`internal/nettun.TCPConn.Abort`。
  実ソケットでは `SetLinger(0)`)。
  netstack 上で通常の `Close` を使うと、graceful shutdown を経て gVisor の既定の TIME_WAIT(60 秒、`tcp.DefaultTCPTimeWaitTimeout`)にエンドポイントが残り、同時フロー数の上限を超える接続のフラッドでは、上限が抑えるはずの保持分を超えてメモリが増え続ける(GitHub issue #25)。
  中継の側から成立済みの接続を切るときも、netstack の側の接続は同じ `Abort` の RST で切る。
  切るのは、ポートが宣言から消えたとき、実効宛先が変わって閉じ直すとき(後述の収束の規則)と、エージェントの終了で中継を閉じるときです。
  中継中のクライアントに何が届くかは、VPS のモードと切る理由で変わる。
  ユーザー空間モードの VPS では、クライアントとエージェントの間に `vpsd` 自身の中継(`internal/netpipe`)が挟まる。
  エージェント側の読み取りが RST で失敗すると、`vpsd` はクライアント側の接続を通常の `Close` で閉じる([6.2 節](../vps/proxy.md#62-プロキシモード))ので、クライアントは切る理由によらず通常 FIN を見る。
  これは `internal/netpipe` の実装を読んで確かめたもので、ラボでは確かめていません。
  カーネルモードの VPS では、パケットがそのまま届くので理由ごとに違う。
  実効宛先の変更で切るときは、クライアントに RST が即座に届くことを実際の VPS で確かめた。
  ポートが宣言から消えたとき、つまりルールを無効化または削除したときは、VPS 側が該当の DNAT と conntrack を公開の時点ですでに取り除いているため、この RST は切った直後はクライアントに届かない([6.1 節](../vps/kernel.md#61-カーネルモード))。
  その後の届き方は、無効化や削除がそのまま続くか、直後に元へ戻るかで変わる。
  無効化や削除がそのまま続く場合、host の input firewall が既定で drop する実際の VPS では、次に送るパケットもおそらく同じく drop され、RST も届かないと考えられるが、これはコードから導かれるだけで、未確認です。
  無効化した直後に有効化する場合と、削除した直後に同じポートへ追加し直す場合は、クライアントは次に送るまで何も気付かず、次に送ると RST を受け取ることを、実際の VPS で確かめた。
  この RST はおそらく開き直した待ち受けから送られたものだが、これは推測であり未確認です。
  この届き方は、ルールの無効化と削除が公開してからエージェントへ配ることを前提にします。
  [5.1 節](../control/registration.md#51-登録)のエージェントの無効化はエージェントへ配ってから公開するため、この前提が成り立たず、クライアントへの届き方は別に未確認です。
  エージェントの再起動で切るときも、クライアントは次に送るまで何も気付かず、次に送ると RST を受け取ることを実際の VPS で確かめた。
  エージェントが止まったままの場合は試しておらず、届き方は未確認です。
  待ち受けを閉じるときに accept の途中で、まだ中継に登録していなかった接続も、登録せずに同じく切る。
  この接続は閉じ直しの bind に間に合わないことがあり、その場合の待ち受けは次の 30 秒ごとの再試行([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))で開きます。
  通常の `Close` で切ると、エージェントのエンドポイントが TIME_WAIT に 60 秒残り、相手が閉じなければ FIN_WAIT_2 にさらに長く残る。
  その間は同じポートで待ち受けを開けず(`port is in use`)、閉じ直したルールと、無効にした直後に有効に戻したルールは、保持が終わった後の再試行まで転送できません。
  クライアントに届くのが FIN でなく RST になる、または届かないことがあるのは前述のとおりだが、切ることが決まっているセッションなので、この届き方の違いは許容します。
  カーネルモードの conntrack の収束([6.1 節](../vps/kernel.md#61-カーネルモード))も、フローを FIN で閉じずに断つ。
  宛先側の接続は実ソケットで待ち受けのポートを塞がないので、通常の `Close` のままにします。
  VPS の中継が切ったセッションは、エージェントには RST として届く([6.2 節](../vps/proxy.md#62-プロキシモード))。
  公開側のクライアントが RST で切ったセッションも、VPS の中継からはエージェントに RST として届く([6.2 節](../vps/proxy.md#62-プロキシモード))。
  エージェントの中継は、読み取りの失敗で終わった後も[末尾を届け終えるまで](tcp-retention.md#中継が終わった後の末尾の配送)組を持ち、枠を保持します。
  セッションが自然に終わる経路(クライアントか宛先のハーフクローズ、EOF)は、グレースフルクローズで終える。
  エージェントが先に閉じた接続も配送中は中継が管理します。
  配送を終えた接続は管理から外れ、TIME_WAIT の間ポートを保持します。
  宛先が先に閉じる HTTP のようなセッションがこれに当たる。
  すぐに解放されるのは中継が切るセッションだけで、このような接続が残っている間にルールを閉じ直すと、待ち受けは保持が終わった後の再試行まで開かない。
  無通信のタイムアウトは持ちません。
  カーネルモードの conntrack が established の TCP を 5 日間保つのと同じく、長く黙る正規の接続(SSH など)を切らないためです
