# 中継のカーネル TCP ソケット

Linux の中継は、組にした netstack の boost の枠に合わせて、カーネル TCP ソケットの受信バッファを固定します。
送信キューや中継終了後のソケットの保持には、残る制限があります。


<a id="中継のカーネルの-tcp-ソケットの受信のバッファ"></a>
- 中継のカーネルの TCP ソケットの受信のバッファ:ユーザー空間モードの中継は、カーネルの TCP ソケットを 2 か所で持ちます。
  `vpsd` が公開側で accept する接続(`Transparent` の TCP のルールとプロキシモードのルールの中継)と、エージェントが LAN の宛先へ dial する接続です。
  中継の反対側が進まなくなると、このソケットには読まれないデータが溜まり、Linux は受信のバッファを自動調整の上限(`net.ipv4.tcp_rmem` の最大値。
  既定で 6 MiB)まで広げる。
  カーネルの TCP のメモリの上限(`net.ipv4.tcp_mem`)はホスト全体で 1 つであり、network namespace ごとには分かれない。
  使用量がこの上限に達すると、カーネルは受信のキューが空の接続にしか新しい segment を受け入れないので、同じホストの無関係な TCP(別のルール、SSH、エージェント用 API)まで、再送の時間ごとに 1 segment ずつしか進まなくなる。
  エージェントを LXC のようなコンテナで動かすと、カーネルを共有する他のコンテナの TCP も同じく遅くなる。
  ラボでは、読まない相手を両端に置いた中継を同時フロー数の上限の近くまで保持させると上限に達し、別のルールの小さな転送が数秒かかった([以前の検証 2026-10-01](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L731))。
  このため中継は、この 2 か所のソケットの受信のバッファを、組にした netstack の接続の boost の枠(前述)に合わせて固定する(2026-10-01、所有者の決定)。
  固定したソケットでは Linux の自動調整が止まります。
  値はどれも設定項目にしません。
  この固定が抑えるのは、中継が持つカーネルのソケットが受信の側に溜める量だけです。
  ホスト全体の TCP のメモリを使い切ることによる巻き添えは、この固定だけでは防げない。
  ラボでは、1 つのカーネルを共有する `vpsd` とエージェントの受信の予算(後述の[「プロセス全体のメモリの上界」](memory-server.md#プロセス全体のメモリの上界)の段落)の和が `tcp_mem` に収まる条件では、遅れが無くなった。
  `tcp_mem` を既定のままにした条件では、この固定の後も上限に達し、別のルールの小さな転送が数秒かかった
<a id="枠に合わせた固定"></a>
- 枠に合わせた固定:中継は、組のうちカーネルの TCP ソケットの側の受信のバッファを中継を始める前に固定し、組にした netstack の接続が boost の枠を持つかどうかに合わせて固定し直す。
  カーネルの側は、`vpsd` では公開側で accept した接続、エージェントでは LAN の宛先へ dial した接続です。
  netstack の側は、`vpsd` ではエージェントへ dial した接続、エージェントでは `vpsd` から accept した接続です。
  枠を持たない間は `SO_RCVBUF` で 128 KiB(実効の値 256 KiB)を、枠を持つ間は 4 MiB(実効の値 8 MiB)を要求します。
  固定し直すのは、netstack の接続が枠を得たときと、需要の無い保有者として floor に戻るときです。
  floor に戻るときの条件は次の項に書きます。
  枠を得て返すのは netstack の接続だけなので、この固定は枠の数を増やさず、大きいバッファを持つカーネルのソケットはプロセスあたり 16 本までです。
  遠い利用者からの転送と LAN の宛先からの転送は、枠を得るまでは floor の窓で進み、枠を得た後は以前と同じ程度の窓を使える(ラボで確かめた)。
  宛先への試し接続は中継をしないので固定しません。
  UDP のソケットは変えない(前述の[「エージェントの LAN 側のソケットの受信バッファ」](udp-relay.md#エージェントの-lan-側のソケットの受信バッファ))
<a id="floor-に戻す前の確かめ"></a>
- floor に戻す前の確かめ:`SO_RCVBUF` を下げても、カーネルのソケットがすでに持つ受信のデータは解放されない。
  受信のメモリが下げた値を超えていても、Linux は次の segment を受け入れるかを決めるときまで減らさない。
  減らすときに捨てるのは順序外のキューだけで、受信のキューの順序内のデータはまとめ直す(`tcp_collapse`)だけで捨てない(6.1 と 2026-10 の開発版のソースで確かめた)。
  穴を残して順序外のデータを送り、その後は何も送らない相手では、データは中継に読まれないまま残り、netstack の接続は需要の無い保有者に見える。
  そこで中継は、netstack の接続が floor に戻る前に、カーネルのソケットの受信のメモリが floor の実効の値(256 KiB)以下であることを求めます。
  受信のメモリは `SO_MEMINFO` の `SK_MEMINFO_RMEM_ALLOC`(`sk_rmem_alloc`)で読みます。
  この値は受信のキューと順序外のキューの segment の truesize の和であり、Linux が segment を受け入れるかを決めるときに受信のバッファの実効の値と比べる量である(同じソースで確かめた)。
  今読めるデータの量(`SIOCINQ`)は順序外のキューを含まないので使いません。
  中継は受信のメモリを先に読み、floor を超えていればバッファに触らない。
  超えていなければ受信のバッファを floor に下げてからもう一度読み、受信のバッファと受信のメモリがどちらも floor 以下のときだけ戻します。
  超えるか読めなければ、カーネルのソケットを boost に戻し、netstack の接続は boost のまま枠を持ち続けます。
  この扱いは、gVisor の側の受信のメモリが floor を超える保有者を戻さない規則(前述の[「需要の無い保有者からの回収」](tcp-buffers.md#需要の無い保有者からの回収))と同じ形です。
  この保有者は、別の接続が枠を求めるたびに改めて試される。
  穴が埋まって中継がデータを読むと受信のメモリが減り、戻せるようになる(`vpsd` の公開側についてラボで確かめた)。
  穴を残したまま黙る相手は、その間は枠を持ち続けるが、boost の大きさで持つソケットは枠の数を超えません。
  確かめの読み書きは、netstack の接続の排他の中で行います。
  下げた後の Linux は、segment を受け入れる前に受信のメモリを受信のバッファと比べ、超えていれば減らし、減らせなければその segment を捨てます。
  比べるのは加える前なので、受け入れた後に 1 skb 分を超えうる。
  6.1 は、受信のキューが空のときの順序内の segment を比べずに受け入れるので、超過はおよそ 2 skb 分になりうる。
  GRO でまとめた skb は 64 KiB 程度になりうる。
  このため floor に戻したソケットの受信のメモリは、floor に数 skb を加えた量に収まる。
  この量はソースから読み取ったもので、測定では未確認です。
  この確かめにより、floor を超える受信のメモリを持つカーネルのソケットも、この超過を除いてプロセスあたり 16 本までになります。
  `SO_MEMINFO` は Linux 4.12 で加わった
<a id="エージェントの-lan-側の値"></a>
- エージェントの LAN 側の値:エージェントの LAN 側を固定の 256 KiB にして枠に合わせない形は採らなかった(2026-10-01、所有者の決定)。
  固定の窓は、宛先からクライアントへの向きの速さを、窓の大きさを LAN の往復の時間で割った値までに抑えます。
  ラボでは、LAN に往復の時間を加えると、この向きの転送が以前より大きく遅くなった。
  所有者はこれを通常の利用での退行と判断した。
  宛先がエージェントと同じカーネルで動く場合(同じホストの別のコンテナなど)、宛先が送れずに待つデータは宛先の送信のバッファに残り、同じ `tcp_mem` に数えられます。
  この量は宛先の設定で決まり、wgft は抑えない
<a id="要求の通り方"></a>
- 要求の通り方:要求は `SO_RCVBUFFORCE` で行い、権限が無ければ `SO_RCVBUF` に落ちる。
  `SO_RCVBUF` は `net.core.rmem_max` で切り詰められるためです。
  ユーザー空間モードの動作条件(前述の[「ソケットのバッファの条件」](socket-buffers.md#ソケットのバッファの条件))を満たすホストでは、`rmem_max` が 7340032 以上か、初期の user namespace の `CAP_NET_ADMIN` で FORCE が通るので、4 MiB の要求はどちらかで通る。
  条件を満たさないホストでは、boost の値が `rmem_max` の 2 倍に切り詰められ、遠い利用者からの転送と LAN の宛先からの転送が以前より遅くなりうる
<a id="窓の-scale-と窓の上限"></a>
- 窓の scale と窓の上限:カーネルの側の接続の握手は Linux の既定のまま行います。
  窓の scale は握手のときに `tcp_rmem` の最大値と `rmem_max` の大きい方から決まり、既定の値では 4 MiB の窓を広告できます。
  握手の前に受信のバッファを固定すると、scale が固定した値から決まり、後で boost の枠を得ても広い窓を広告できません。
  一方、握手の後に受信のバッファを固定すると、窓の上限(Linux の `window_clamp`)が自動調整で広がらなくなる。
  Linux 6.1 は握手の時点の受信のバッファから決めた窓の上限を持ち続け、7.2 は受信のバッファを固定するたびに窓の上限をそのバッファに合わせて置き直す(ラボの 6.1 と開発のホストの 7.2 で確かめた)。
  そこで中継は、受信のバッファを固定するたびに `TCP_WINDOW_CLAMP` で窓の上限を 4 MiB に置く。
  窓はこの上限と受信のバッファから決まる窓の小さい方になり、枠を持たない間は受信のバッファが、枠を持つ間は 4 MiB の上限が窓を決める。
  窓の上限だけで窓を抑える形は採らない。
  受信のバッファの自動調整が窓の上限を上書きし、上限が保たれないためです
<a id="固定する受信のバッファの上界"></a>
- 固定する受信のバッファの上界:`vpsd` の公開側の受信のバッファは、プロセスあたり K × 256 KiB + 16 × 8 MiB を上限とします。
  既定の K の 2048 では 640 MiB です。
  この上界が数えるのは、動いている中継のソケットの受信の側だけです。
  ソケットが溜める受信のメモリにこの上界が効くのは、前述の floor に戻す前の確かめと、次の項の accept の直後の確かめによる。
  ソケットごとに数 skb の超過がありうる(前述)。
  accept が返す前のソケットはこの上界に入らない(次の項)。
  エージェントの LAN 側は、エージェントの K × 256 KiB + 16 × 8 MiB を上限とします。
  エージェントの boost の枠はエージェントのプロセスの 16 本です。
  どちらも名目の上限であり、実際に使うのはデータが溜まっている間だけです
<a id="accept-の直後の固定"></a>
- accept の直後の固定:`vpsd` の公開側では、中継は accept した接続の受信のバッファを、接続元の確かめ、Admission Policy、同時フロー数の上限、エージェントへの dial より前に floor に固定します。
  `Transparent` の TCP のルールの中継とプロキシモードのルールの中継で、accept の扱いは同じです。
  固定していないソケットでは、受信のメモリが受信のバッファを超えたときに、Linux が受信のバッファを `net.ipv4.tcp_rmem` の最大値まで広げうる。
  ホスト全体の TCP のメモリが `tcp_mem` の最初の値より少ない間に、受信のバッファを広げる経路(`tcp_clamp_window`)が働くためである(6.1 のソースで確かめた)。
  穴の後に小さい順序外の segment を続ける相手は、この広がりを起こし得ます。
  dial の後の最初の固定は、枠を持たない接続を受信のメモリを確かめずに floor に下げるので、固定が dial の後だけなら、dial を待つ間に溜めたデータが K と 16 本の外に残る。
  中継は固定の直後に `SO_MEMINFO` で受信のメモリと受信のバッファを読みます。
  どちらかが floor の実効の値を超えるか、固定か読み取りに失敗すれば、その接続を Admission Policy にも同時フロー数にも数えずに `SetLinger(0)` の RST で切り、頻度を絞ったログを 1 行出す。
  固定しても、ソケットがすでに持つデータは解放されないためである(前述の[「floor に戻す前の確かめ」](tcp-host-sockets.md#floor-に戻す前の確かめ))。
  通った接続は floor に固定されたまま Admission と dial を待ち、dial の後は前述の枠に合わせた固定に移る。
  待ち受けのソケットには固定を置かないので、窓の scale は前述の[「窓の scale と窓の上限」](tcp-host-sockets.md#窓の-scale-と窓の上限)と同じく握手のときの Linux の既定から決まる。
  netstack の接続、カーネルモードのプロキシモードの中継、Linux 以外では何もしません。
  この固定が守るのは、accept が返した後のソケットだけです。
  握手を終えて accept の待ち行列にあり、まだ accept が返していないソケットは固定されておらず、同じ広がりで溜めうる。
  この待ち行列のソケットが溜める量は、この固定では抑えない。
  この固定は、ホスト全体の TCP のメモリを守るものでもない。
  固定したソケットを 6.1 の受信のバッファを広げる経路が広げず、受信のメモリが floor に数 skb を加えた量に留まることは、6.1 のソースと、wgft を通さないソケットの測定で、その測定の条件の下で確かめた。
  その測定では、穴の後に小さい順序外の segment を続ける相手に対して、固定しないソケットは受信のバッファを広げて溜め、固定したソケットは floor の近くに留まった。
  wgft の中の順序(accept、固定、受信のメモリの確かめ、Admission、dial)と、確かめが通さない接続を RST で切って Admission にも dial にも進めないことは、両方の accept のループを通る単体テストで確かめた。
  同じ相手を wgft の公開側に向けた測定は未確認です
<a id="固定しないもの"></a>
- 固定しないもの:送信のバッファは固定せず、Linux の自動調整のままにします。
  これは送信の側を安全と判断したのではなく、上界を持たない保持を残したまま先送りする判断である(2026-10-01、所有者の決定。
  [13 節](../roadmap.md#制限と未実装の提案))。
  残る保持とその危険は次のとおりです。
  - 送信のキュー:最初から読まない相手を置いたラボの再現では、中継の送信の側に溜まる量は受信の側より小さかった。
    一方、読むのを速く続けた後に止める相手では、送信のバッファが自動調整の上限(`net.ipv4.tcp_wmem` の最大値。
    既定で 4 MiB)まで広がり、`vpsd` の公開側のソケットとエージェントの LAN 側のソケットは、どちらもその上限の近くまで溜めた(ラボで確かめた)。
    送信のバッファを boost の枠に合わせて固定するだけでは上界になりません。
    中継の書き込みが終わった後もデータは送信のキューに残り、その間に netstack の接続の枠は回収されうるためです
  - 閉じた後のソケット:Linux のユーザー空間モードでは、中継が終わった組と中継開始前の通常の失敗で終わった組について、ソケットを閉じずに持ち、[配送が終わるまで](tcp-retention.md#中継が終わった後の末尾の配送) K に数えます。
    これらの終了経路では、受信のメモリを持つソケットを順序外のキューも含めて RST で終えます。
    閉じたソケットは、中継が意図して切った組、カーネルモードの `vpsd` の Relay の中継、Windows と macOS の LAN 側にも残ります。
    通常の `Close` で閉じたカーネルのソケットは、送り残しを持ったままプロセスから離れて残り、K と boost の 16 本の外にあります。
    ラボでは、送り残しを持つ 20 本が合わせて 54 MiB を 200 秒以上持ち続けました。
    Linux 6.1 は閉じるときに受信のキューを捨てますが、順序外のデータだけでは RST を送らず、FIN を送ってソケットを孤児にします。
    順序外のキューはソケットの破棄、`tcp_disconnect`、相手の FIN の処理で捨てるとソースから確認しました。
    黙った相手を持つソケットを通常の `Close` で閉じると、閉じたときの受信バッファまでの順序外のデータも FIN の再送が尽きるまで残り得ます。
    wgft を通さないソケットでは、順序外のデータが閉じた後も残り、FIN の再送が尽きた後に消えることをラボで確かめました。
    boost の大きさに近い量での再現は未確認です。
  - 残る危険:相手が読むのを止める操作を繰り返すと、どちらの保持もホスト全体の `tcp_mem` を使い、前述の巻き添えを起こし得ます。
    1 本の保持が長く続くことはラボで確かめた。
    繰り返したときにホスト全体へ及ぶ影響は未確認です。
    自然に終わった組と中継開始前の通常の失敗で配送を待つ組の数は K 以下になりますが、1 本の送信の量の上界と、意図して切った後の孤児は未解決です。
<a id="linux-以外の-os-とカーネルモード"></a>
- Linux 以外の OS とカーネルモード:Linux 以外では固定しません。
  Windows と macOS のエージェントは OS の自動調整のままであり、固定したときの速さと、ホスト全体の TCP のメモリの上限の働き方を確かめていないためです。
  カーネルモードの `vpsd` のプロキシモードの中継は、両側がカーネルのソケットであり、固定の対象にしません。
  カーネルモードのエージェントは中継を持たないので、LAN 側の固定の対象がありません
