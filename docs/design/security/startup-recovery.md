### 起動の保留

起動の拒否、一時的な保留、起動を止めない記録の失敗を区別します。
監督するプロセスとエージェントの再試行には、それぞれ効果の範囲があります。


起動時の最初のルールの適用の失敗は、終了コード 1 でも 3 でもなく、起動の保留とします。
`vpsd` は終了せず、管理用 API だけを開いた状態で起動の残りを止め、適用を試し直す。
適用が成功した時点で起動の残りに進む(2026-09-22、所有者の決定)。

この扱いにする理由は、カーネルへ適用できない宣言をサーバのデータベースに保存できてしまう点にあります。
宣言の保存は適用の成否を待たない([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))ので、適用が毎回同じ失敗をする宣言が記録に残りうる。
従来はこの記録を読んだ起動時の最初の適用が終了コード 1 で終わり、unit が再起動して同じ場所で落ちた。
管理用 API はこの適用より後に開くので、`wgft rule rm` で宣言を小さくする経路が開かず、運用者に残る手段は `server teardown --purge` による全消しだけだった。
設定の誤りを 1 つ保存しただけで、それを直すための入口まで失われる。
本節の非対称の規則は、再起動で直りうる失敗を終了コード 1 とするものだが、この失敗は原因が記録にある以上、再起動では直らない。
かといって終了コード 3 で止めると、運用者が直すための管理用 API も開かない。
保留は、この失敗に対して再起動を繰り返さず、直すための入口だけを開ける 3 つ目の扱いです。

起動の保留の規則は次のとおりです。

- 入る条件:起動時の最初の適用が失敗したことです。
  サーバのデータベースを開くこと、モードとアドレス帯の照合、wg インタフェースの立ち上げは、この適用より前にあり、保留の対象にしません。
  これらの失敗と、起動の拒否(`*startup.Refusal`)は、従来どおり終了コード 3 か 1 で終わる
- 権限の不足との関係:カーネルモードで権限が足りない配置は、この保留に届かない。
  wg インタフェースの立ち上げが最初の適用より前にあり、そこで `EPERM` が種別 `prerequisite` の拒否になって終了コード 3 で止まるためである([9 節](../state.md#9-状態の保存と再起動))。
  インタフェースを作る netlink の書き込みも、既存のインタフェースを読む `wgctrl` の呼び出しも `CAP_NET_ADMIN` を要求します。
  したがって [9 節](../state.md#9-状態の保存と再起動)の権限の拒否と本節の保留は、同じ失敗を奪い合わない。
  最初の適用だけが権限で失敗する配置は、`CAP_NET_ADMIN` を持ちながら nftables への書き込みだけを拒まれている状態であり、原因は権限そのものではありません。
  この場合を権限の拒否に写して終了コード 3 で止めると、[7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)が「30 秒ごとの再試行が拾う」と定めた `table inet wgft` の保持のような、待てば解ける原因まで永久に止めることになります。
  最初の適用の失敗は、権限で失敗したかどうかを問わず保留とします。
  上の入る条件が定めるとおり、最初の適用が起動の拒否(`*startup.Refusal`)を返した場合だけは保留にしません
- 開く待ち受け:管理用 API だけです。
  エージェント用 API は開かない。
  転送していない間にエージェントが接続しても中継は起きず、エージェントへ配る全体状態に入る conntrack の UDP タイムアウト 2 値も、この時点では読めていない([9 節](../state.md#9-状態の保存と再起動)。
  この読み取りはテーブルの適用の後に置いてある)ためです。
  エージェント用 API を開くと、制御の接続だけが成立して転送は起きない状態になり、運用者から見て保留と正常の区別が付かなくなる
- 転送:保留の間、`vpsd` は宣言を公開できていないと判断しています。
  ただしカーネルが実際に何を転送しているかは、適用がどこで失敗したかで変わり、`vpsd` の側からは確定できません。
  初回の起動と、ホストごと再起動した後では、`table inet wgft` も wg インタフェースのピアも無いので何も転送されない。
  プロセスだけを入れ替えた起動では、前のプロセスが公開したテーブルとピアがカーネルに残る([9 節](../state.md#9-状態の保存と再起動)。
  停止時にはどちらも削除しない)。
  このとき、カーネルが差し替えを行わないまま失敗した場合、つまりバッチが `EMSGSIZE` で送れなかった場合([6.1 節](../vps/kernel.md#61-カーネルモード)の送信側の壁)と、カーネルがバッチを拒んだ場合は、テーブル全体が旧のまま残り、カーネルモードの transparent のルールは前回公開した宣言のまま転送を続けます。
  一方、カーネルは差し替えを終えたのに `vpsd` が応答を受け取れなかった場合、つまり `ENOBUFS` で応答を取りこぼした場合([6.1 節](../vps/kernel.md#61-カーネルモード)の受信側の壁)は、テーブルは既に差し替わっています。
  このとき転送しているのは、`vpsd` が失敗として報告した新しい宣言のほうです。
  差し替えの後に読み直した送信元の一覧の set が送った要素を持たなかった場合([6.1 節](../vps/kernel.md#61-カーネルモード))も、テーブルは既に差し替わっています。
  この 2 つが逆の結果になることは、ラボで実測した([以前の検証 2026-09-23](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L3779))。
  プロキシモードの待ち受けはプロセスと一緒に消えるので、どちらの場合も止まります。
  したがって、保留を「転送が止まっている状態」とも「前回の宣言のまま転送している状態」とも説明してはなりません。
  実際のカーネルの内容を読む手段は `wgft server nft` であり、管理用 API が開いているので保留の間も使える。
  この不確かさは保留が作ったものではなく、[6.1 節](../vps/kernel.md#61-カーネルモード)の受信側の壁がもともと持っているものを、保留が引き継いでいるだけです。
  この残り方が、稼働中に backend 全体の失敗が起きたときと同じであることも変わらない([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))
- 試し直し:[7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)の再試行と同じ 30 秒ごとです。
  管理用 API のバッチ操作は、従来どおりその場で適用を試すので、運用者が宣言を直せば次の 30 秒を待たずに保留が解ける
- 出る条件:適用が成功したことだけです。
  その時点で conntrack の UDP タイムアウトを読み、エージェント用 API を開き、起動完了の行を出し、収束のループを始める。
  以後の挙動は保留を経ていない起動と変わりません
- ログ:保留に入るときに 1 行、解けるときに 1 行を出す。
  入るときの行は、適用の失敗の理由と、`wgft server nft` でカーネルの実際の内容を読めることと、`wgft status` で状態を読めることと、`wgft rule rm` か `wgft rule disable` で宣言を小さくできることを示します。
  試し直しが同じ理由で失敗するあいだは何も出さず、理由が変わったときだけもう 1 行出す。
  [7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)の抑制と同じ規則です。
  起動完了の行は、保留が解けるまで出さない
- 終了コード:起動の保留は終了しないので終了コードを持ちません。
  管理用 API の待ち受けそのものが失敗した場合は、従来どおり終了コード 1 で終わる
- 保留の間の conntrack の UDP タイムアウト 2 値:まだ読んでいないので 0 です。
  この値は全体状態に載せてエージェントへ配るものだが([4 節](../network.md#4-ネットワーク))、保留の間はエージェント用 API を開かないので配られることはありません。
  保留が解けた時点で読み、エージェント用 API の待ち受けはその後に開きます。
  管理用 API の `GET /api/v1/server` と `GET /api/v1/agents/{name}/state` は、保留の間この 2 値を 0 のまま示します
- 保留の間の管理用 API:ルール一覧は読め、すべてのルールの `apply_state` は `pending`、`apply_error` に適用の失敗が入る([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))。
  `wgft status` は、`apply_error` があるので Server 行を degraded とし、有効なルールが 1 本でもあればすべて `pending` なので Rules 行も degraded とする([10.2b 節](../status.md#102b-状態の要約wgft-status)。
  無効なルールは総数に数えない)。
  ただし、最初の適用が `Reconcile` に入る前の読み取り(wg の設定の組み立て、世代の読み取り)で失敗した場合は、適用状態を持つ節点がまだ無いので Server 行は unknown になります。
  Agents 行は、登録済みのエージェントがあれば、その stream が繋がらないので degraded になるが、1 つも登録されていない保留では 0 台のまま degraded になりません。
  保留そのものを表すのは Server 行です
- 監督するプロセスから見た見え方:保留の間、unit は active のままです。
  従来の終了コード 1 の繰り返しは `Restart=on-failure` によって再起動として見えたが、保留は 1 行を出した後は静かになります。
  これは稼働中に `apply_error` を抱えたまま動き続ける場合([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))と同じ見え方であり、公開が止まっていることを知る手段も同じく `wgft status` と `server doctor` の終了コード 1 です。
  unit の状態だけを見る監視は、保留も稼働中の適用の失敗も捉えられない

### 起動を止めない記録の失敗

撤去の案内にだけ使う記録の保存の失敗は、起動を止めず、警告して続けます。
`net.ipv4.ip_forward` の 2 段の記録([6.1 節](../vps/kernel.md#61-カーネルモード))と、撤去の手掛かりの記録([10.3 節](../operations/setup.md#103-運用の流れ))がこれに当たる。
どちらも転送には効かないためです。
`net.ipv4.ip_forward` の予定の記録を保存できない場合も、値は書きます。
起動を止めると、サーバのデータベースに書けない間は、ホストの再起動のたびに転送が戻りません。
値を書かずに続けても、同じく転送が止まります。
騒がしい再起動の繰り返しより転送が落ちたままになることのほうが悪い、という本節の規則に従います。
記録の失敗は警告のログで知らせ、値を書いた後、[6.1 節](../vps/kernel.md#61-カーネルモード)の手順が 5 まで進み、記録がどちらの段でも残らなかった場合は、起動時の Finding でも知らせる(2026-10-03、所有者の決定)。
予定の記録を保存できず、書いた後に確定の記録の前で止まった場合は、Finding を出せず、予定の記録の警告のログだけが残る。

### 入口での判定

値だけから判定できる失敗は、wg インタフェース、待ち受け、サーバのデータベース、認証情報ファイルのいずれにも触れる前に判定します。
この場所を入口と呼ぶ。
server の入口は `cmd/wgft` の `buildServerOptions`、エージェントの入口は同じ package の `buildAgentOptions` です。
入口を通り抜けた値が起動の後半で初めて失敗すると、そこでは環境由来の失敗と区別が付かず、終了コード 1 の再起動の繰り返しになります。
この形の穴は 3 つの設定項目で続けて見つかっている([以前の検証 2026-09-20 と 2026-09-21](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L3794))。

server の入口が判定する項目は次のとおりです。
`WGFT_MODE` の値(`kernel` か `userspace` か)、`WGFT_DATA_DIR` が空でないこと、`WGFT_WG_INTERFACE` がカーネルの受け付ける名前であること、`WGFT_WG_PORT` が 1 から 65535 の整数であること、`WGFT_MTU` が 576 から 9216 の整数であること、`WGFT_WG_ADDRESS` が `netip.ParsePrefix` の通る形であること、`WGFT_AGENT_API` と `WGFT_ADMIN` が待ち受けられる形であること、`WGFT_WG_ENDPOINT` と `WGFT_AGENT_API_HOST` が `host:port` の形でホストが空でないこと、`WGFT_AGENT_API_HOST` のポートが 1 から 65535 を 10 進の数字で書いた値であること、`WGFT_WG_ENDPOINT` のポートが UDP のポートとして 1 から 65535 の番号に直せること、`WGFT_ADMIN_TAILSCALE` が真偽値であること、同時フロー数の 4 つの上限が範囲内であること、`run` では `WGFT_WG_ENDPOINT` があることです。
エージェントの入口は、`WGFT_DATA_DIR` が空でないこと、`WGFT_MODE` の値、Linux 以外のビルドで `kernel` を指定したこと、`WGFT_WG_INTERFACE` がカーネルの受け付ける名前であること、同時フロー数の上限、`WGFT_AGENT_ALLOW_TARGETS` の構文を判定します。
Linux 以外のビルドでの `kernel` の指定は種別 `prerequisite` の拒否で、他は種別 `config` の拒否です。
`WGFT_WG_INTERFACE` はカーネルモードでだけ使うが、値だけで判定できるので、モードによらず判定します。
後でカーネルモードへ切り替えたときに、起動の後半で初めて失敗しないためです。

`WGFT_AGENT_API_HOST` のポートにサービス名、符号、0 を許さないのは、値が接続文字列にそのまま入り、エージェントの `ParseJoin` が 1 から 65535 を 10 進の数字で書いたポートしか受け付けないからです。
2026-10-02 の改訂の前は、入口がこのポートを `net.LookupPort` で検査していたので、`vps.example.com:https`、`vps.example.com:+443`、`vps.example.com:0` を受け付けていました。
これらの値はエージェントが拒む接続文字列を作るだけで、どのエージェントでも動いていなかった。
改訂の後は、これらの設定で server は起動せず、種別 `config` の拒否(終了コード 3)で止まります。
値を数字に書き換えれば起動します。

`WGFT_WG_ENDPOINT` は、入口でポートの部分だけを `net.LookupPort("udp", ...)` で番号に直し、10 進の数字で書いた値をこの起動の設定として使います。
`+51820` と `051820` は 51820 に、サービス名は server のホストのサービスの一覧が示す番号になります。
ホストの部分は書かれたまま残し、IP アドレスに引かない。
名前の引き直しはエージェントが行います。
番号に直すのは起動のときの 1 回だけで、全体状態の配信や管理用 API の読み取りのたびには引き直さない。
エージェントに配る値と管理用 API の `wg_endpoint` は、どちらも直した値です。
設定ファイルは書き換えず、起動ログと `wgft server check` の「値と出所」の表示は入力の値のままです。
UDP として番号に直せない名前は TCP で引き直さない。
番号に直せない値、番号が 0 の値、65535 を超える値は、ポートを数字で書くよう例(`vps.example.com:51820`)を添えて、種別 `config` の拒否(終了コード 3)で止めます。

この正規化は、エージェントの側の解釈がモードで違うことによる。
ユーザー空間モードのエージェントは 10 進の数字のポートしか受け付けないので、改訂の前は、サービス名と符号付きのポートを書いた設定ではトンネルを張れなかった。
カーネルモードのエージェントは `net.LookupPort("udp", ...)` で、エージェントのホストのサービスの一覧から番号に直していました。
改訂の後は番号を決める場所が server の入口の 1 か所になり、どちらのモードのエージェントも同じ数字のポートを受け取ります。
ただし、古い設定が同じ番号で動き続けるとは限らない。
番号を引くホストがエージェントのホストから server のホストへ移るので、サービスの定義がエージェントのホストと違う server のホストでは、別の番号になるか、番号に直せずに起動が止まります。
改訂の前の入口は TCP として引いていたので、TCP にだけ定義のある名前と番号が 0 の値も通っていました。
これらはどちらのモードのエージェントでも接続できない値で、改訂の後は起動を止めます。

`WGFT_AGENT_API_HOST` を省いた場合、接続文字列のポートは `WGFT_AGENT_API` の待ち受けが bind するポートを 10 進の数字で書きます。
`WGFT_AGENT_API` は待ち受けの値なので、入口はサービス名を許す。
接続文字列を作るときに、待ち受けと同じ `net.LookupPort` で番号に直す。
番号に直せない場合と、番号が 0(カーネルが選ぶポート)の場合は、接続文字列を発行せずに誤りを返し、`WGFT_AGENT_API_HOST` の設定を案内します。
改訂の前はポートの部分をそのまま接続文字列に入れていたので、サービス名を書いた設定ではエージェントが拒む接続文字列を発行していました。

接続文字列のホストは必須です。
エージェントの `ParseJoin` は、ホストが空の接続文字列(`wgft://:8443/...`)を拒みます。
改訂の前はこれを受け付け、エージェントは自分のホストの、接続文字列に書いたポートへ接続していました。
server はホストが空の接続文字列を発行しないので、影響を受けるのは手で書き換えた接続文字列だけです。
登録済みのエージェントは `WGFT_JOIN` を読まないので、入口の警告が 1 行出るだけで止まらない。

値だけからは判定できない項目は次のとおりで、判定の場所とその理由を定める。

- `WGFT_MODE` の初回の必須: 記録の有無で必須かどうかが決まるので、記録を読める `internal/vpsd` が判定します
- `WGFT_JOIN` の構文: 登録済みのエージェントは、compose に残った古い値を読まない([11a 節](configuration.md#11a-設定の渡し方)が意図的に許す居座り)。
  入口で構文を拒否すると、動いていたエージェントが使われない値の誤りだけで止まるので、登録の直前に判定します。
  誤りに気付けるよう、入口では警告を 1 行出す
- `WGFT_NAME` の文字種: 名前の規則は server の側(`internal/vpsd/store`)にあり、エージェントはその規則を持ちません。
  登録の応答(HTTP 400)を種別 `config` の拒否に写す
- エージェントのカーネルモードの前提: `CAP_NET_ADMIN` と WireGuard のモジュールの有無は、値ではなくホストで決まる。
  `internal/agent` が、認証情報ファイルの排他を取った後、モードの記録と登録より前に判定する([7b.5 節](../kernel-agent/operations.md#7b5-権限と配置))。
  記録との照合の後に置くのは、モードの関門と記録の矛盾による拒否を先に示すためです

設定項目を足すときは、入口の検査と、その終了コードのテストを同時に足す。
`cmd/wgft` の `TestEveryServerSettingIsCheckedAtTheDoor` は `serverSpecs` のすべての項目に壊れた値を 1 つ持ち、終了コード 3 で止まることと、データベースも待ち受けも作られていないことを確かめる。
値だけからは壊せない項目は理由付きで表に書きます。
表に無い項目を足すとこのテストが落ちる。

### 登録の応答の扱い

エージェントの登録と再登録では、server の応答が再試行の可否を決める。
HTTP 401(トークンが無効、期限切れ、名前違い)、400(名前の文字種)、409(その名前が登録済み)は、送った値に対する server の判定であり、再起動では変わらないので拒否にします。
401 と 409 は種別 `conflict`、400 は `config` です。
429(レート制限)、5xx、到達できない場合は普通のエラーとし、unit の再起動に任せる。

### 監督するプロセスから見た効果の範囲

終了コード 3 が再起動を止める効果は、同梱の systemd の unit(`server.service` と `agent.service`)の `RestartPreventExitStatus=3` によるものであり、wgft 自身の性質ではありません。

macOS の launchd には `RestartPreventExitStatus` に当たる設定がありません。
同梱の plist は `KeepAlive` の `SuccessfulExit` を偽にしているので、終了コード 3 でも `ThrottleInterval` の間隔で再起動を繰り返します。
実機で確認した挙動は [11a 節](configuration.md#11a-設定の渡し方)にあります。
Docker の `restart: unless-stopped` も終了コードを見ません。
したがって macOS とコンテナでは、拒否の効果は運用者がログで原因を選り分けられることだけであり、再起動は止まらない。
種別と文言は、どの監督するプロセスの下でも同じ手がかりになります。
