# ブラウザとエージェント API の守り

ブラウザ経路は Host とリクエストのオリジンを検査します。
エージェント API には認証前の接続と送信元の制限を設けます。


ブラウザ経路の守りは、パスワードの代わりに次の 2 つで行います。
CLI は影響を受けない。

- `Host` の検査:`localhost`、`127.0.0.1`、`[::1]`、`--admin-tailscale` で検出した自分の tailnet 名と IP、`--admin-host` で追加した名前、以外の `Host` を持つリクエストを拒否します。
  攻撃者のドメインを `127.0.0.1` に向ける DNS リバインディングは、ここで `Host` が合わずに落ちる
- 他オリジン発の変更の拒否:`GET` と `HEAD` 以外のリクエストで、`Sec-Fetch-Site` が `same-origin` でも `none` でもないもの、または `Origin` のホストが上の許可リストにないものを拒否します。
  CLI はどちらのヘッダも送らないので通る。
  Web UI のフォーム送信は同一オリジンなので通る
- 応答のヘッダ:Web UI と JSON のどちらの応答にも `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer` を付ける。
  `Content-Security-Policy` はテンプレートが実際に読み込むものだけを許す(`default-src 'self'` で自オリジンの `/static/app.js` と `/static/styles.css` を許し、インラインの `style` 属性のために `style-src` にだけ `'unsafe-inline'` を足す。
  画像・フォント・外部ドメインの読み込みは無いので、他はすべて `'self'` の範囲で足りる)。
  `/static/` 以外の応答には `Cache-Control: no-store` も付け、接続文字列などが載る画面がブラウザやプロキシのキャッシュに残らないようにします

- エージェント用 API は公開するが、登録と stream のエンドポイントしか持たず、認証は登録トークンか恒久トークンだけです。
  トークンの生成、保存、比較、試行制限は [5.1 節](../control/registration.md#51-登録)のとおり
- エージェント用 API は TLS 1.2 以上、HTTP/1.1 だけで応じる。
  通信は登録の POST と WebSocket だけなので、HTTP/2 は ALPN で広告しません。
  鍵交換の曲線は固定せず Go の既定に従います。
  既定には耐量子のハイブリッド鍵交換が含まれ、固定するとそれが外れるためです
- エージェント用 API は同時接続数を固定の上限(4096)で抑えます。
  数百台のエージェントが 1 本ずつ stream(WebSocket)を張っても十分な余裕がある値であり、[11a 節](configuration.md#11a-設定の渡し方)の設定項目にはしません。
  上限に達した接続は accept を待つだけで、拒否や RST にはせず、すでに動いている stream を切ることもない
- エージェント用 API は、認証を通っていない接続の数を、全体と送信元の段ごとに固定の上限で抑えます。
  全体の上限は 1024 本で、同時接続数の上限(4096)の内側に置く。
  送信元の段と上限は、IPv4 のアドレスか IPv6 の /64 に 16 本、IPv6 の /56 に 64 本、IPv6 の /48 に 256 本です。
  どれかの上限に達した接続は、TLS のハンドシェイクの前に閉じます。
  認証を通っていない接続は、TLS のハンドシェイクの途中の接続、登録の要求、恒久トークンの確認の前の stream の要求です。
  stream は恒久トークンの確認を通り、エージェントごとの確立前の数(下記)に入れたところで、送信元と全体の未認証の数から外れる。
  この数に入れられなかった 3 本目は 429 で断られ、未認証の数に残ったまま閉じます。
  同じ NAT やプレフィクスの後ろにいるエージェントの台数は、これらの未認証の上限に縛られない。
  上限は [11a 節](configuration.md#11a-設定の渡し方)の設定項目にはしません
- 送信元の段は、1 人が安く持てるアドレスのまとまりに合わせる。
  IPv6 を /64 だけで数えると、/56(/64 が 256 個)を持つ 1 人が 256 × 16 本を持てるためです。
  /56 は家庭の回線に、/48 は拠点やトンネルのサービスに払い出される大きさなので、/56 には /64 の 4 つ分、/48 には /56 の 4 つ分を置き、1 つの /48 が持てるのは全体の上限の 4 分の 1 までとした。
  IPv4 には /24 のような段を置かない。
  IPv4 のアドレスは 1 人が安く多数を持てず、/24 で数えると同じ範囲から払い出される CGNAT の後ろの正規のエージェントを巻き込むためです。
  同じ理由で、1 つの IPv4 のアドレスの上限も 16 のまま変えません。
  下げれば全体の上限を埋めるのに要るアドレスの数は増えるが、CGNAT の後ろで同じアドレスを共有する正規のエージェントの同時の再接続が上限に当たりやすくなる(2026-10-01、所有者の決定)
- 全体の上限は、認証を通っていない接続が持つメモリを抑え([7 節](../agent-dataplane.md#7-データプレーン自宅側))、同時接続数の上限の残りを認証を通った stream に残します。
  この上限を埋めるには、IPv4 のアドレスなら 64 個、IPv6 なら /48 が 4 つ要る。
  全体の上限を置く前に同時接続数の上限を埋めるには IPv4 のアドレスが 256 個要ったので、IPv4 での必要な数は減った。
  多数の送信元から全体の上限を埋める攻撃は、以前と同じくこれらの上限では防げず、その間は新しい登録と stream の再接続が止まります。
  既存の転送は止まらない
- 既定の待ち受けの `0.0.0.0:8443` は、IPv4 と IPv6 の両方に応じる。
  Go は、ホストを指定しないアドレスを、IPv6 を使えるホストでは IPv4 射影を許す IPv6 のソケットで開くためです。
  IPv4 の相手は、IPv4 射影のアドレスで届いても IPv4 のアドレスとして数えます。
  待ち受けを IPv4 だけに変えることはしません。
  `WGFT_AGENT_API` の意味が変わるためである([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))
- 認証を通っていない接続が読みの期限で枠を持つのは最長 15 秒です。
  TLS のハンドシェイクの期限は 5 秒で、ハンドシェイクの後はリクエスト全体を 10 秒で読み終える必要があり、この 15 秒は 2 つの期限の和です。
  Go の HTTP のサーバはハンドシェイクの期限にヘッダの期限を使うので、ヘッダの期限を 5 秒にしてあります。
  この 15 秒は読みの期限だけで、読み終えた後の枠の保持は含まない。
  登録の要求では、正しい登録トークンの登録のようなハンドラの処理の間と、応答を返した後に Go の net/http が行う書き込み側の半クローズと最長 500 ミリ秒の待ち(`closeWriteAndWait`)の間も、接続は未認証の枠に残る。
  エージェントは TCP の接続の直後にハンドシェイクを始め、ヘッダと 4 KiB 以下の登録の本文をその直後に送る。
  ハンドシェイクは往復 1 回か 2 回で終わるので、往復に 1 秒かかる回線でも期限に収まると推測しています。
  遅い実回線では未確認です
- 恒久トークンの確認を通って最初のメッセージを待つ stream は、接続を確立するまで、エージェントごとに 2 本までです。
  3 本目は 429 で断り、未認証の接続のまま閉じます。
  最初のメッセージの期限と大きさの上限は [5.2 節](../control/connection.md#52-全体状態の配信とハートビート)にあります。
  この上限が無いと、恒久トークンを 1 つ持つ者は、送信元の上限から外れた確立の前の stream を送信元を替えて多数持ち、1 本ごとに読みかけのメッセージのメモリを持たせられる。
  2 本にするのは、半開きの 1 本が期限を待つ間も、つなぎ直しの 1 本が通るためです
- 旧接続を置き換えた stream は、旧接続の閉じる処理が終わるまで、前項の枠を返さない([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
  置き換えられた旧接続の読み手は、読みかけのメッセージを持ったまま、閉じる処理の期限まで残りうる。
  WebSocket のライブラリの close の期限は約 5 秒で、close のフレームの書き込みが詰まると最長約 10 秒になります。
  TLS の接続では、接続を閉じるときの close_notify の書き込みにも 5 秒の期限があり、送信のバッファが詰まっていれば閉じる処理はその分も延びうる。
  この延びはコードを読んだ推定であり、再現は未確認です。
  置き換えた時点で枠を返すと、恒久トークンの持ち主は、ハートビートを途中まで送って止めた stream を新しい stream で置き換える操作を繰り返し、閉じる途中の stream をエージェントごとの数の上限なく積める。
  枠で数えるので、置き換えられて閉じる途中の stream は、1 つのエージェントにつき 2 本までです。
  正規の再接続は、置き換えた時点で確立して全体状態を受け取り、旧接続を待ちません。
  確立の前の stream と閉じる途中の stream が合わせて 2 本ある間は、次の試みは 429 で断られる。
  閉じる途中の旧接続が 1 本なら確立の前の 1 本までは通り、2 本なら次の試みがすぐに断られる。
  エージェントは 429 を一時的な拒否として扱い、通常のバックオフで再接続する([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))
- 恒久トークンの持ち主は、公開鍵を変える宣言で、カーネルモードの `vpsd` に `table inet wgft` を差し替えさせられる。
  秘密鍵は要りません。
  差し替えは全エージェントのルールの meter と `ct count` の状態を作り直し、同じ送信元は差し替えのたびに上限 1 つ分多くのフローを保持できる([6.1 節](../vps/kernel.md#61-カーネルモード))。
  2 つの鍵を交互に宣言すると、保存している鍵と同じ鍵の省略は効きません。
  `vpsd` は鍵の変更を登録ごとの頻度の上限([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))で抑え、鍵の変更で他のエージェントへ全体状態を配り直さない。
  上限の内側の変更による差し替えと、それによる全エージェントの状態の作り直しは残る。
  ユーザー空間モードの `vpsd` では、鍵の変更は Admission Policy の評価器の状態を作り直さない([7a.4 節](../architecture/admission-resources.md#7a4-admission-policy-と入口の分岐))。
  送信元ごとのレートの状態が残ることはラボで確かめ、送信元ごとの同時フロー数が残ることはコードから判断した
- エージェント用 API は keep-alive を使わず、応答を返したら接続を閉じます。
  エージェントは登録と stream の接続のたびに新しい HTTP のクライアントを作るので、応答の後に残した接続は使い直されず、認証を通っていない接続として送信元の枠を占めるだけだからです。
  WebSocket への切り替えの応答の後の接続(stream)は閉じない
- エージェントは削除できます。
  削除すると、`vpsd` はそのエージェントの恒久トークンを使えなくし、wg ピア、そのピア宛の conntrack エントリ、進行中の中継を消し、割り当てアドレスを回収します。
  名前は新しい接続文字列で再利用できます
- wg0 上のピア同士は通信できず、wg0 から VPS 自身への新規接続もできません
- ユーザー空間モードの `vpsd` では、全エージェントのピアが 1 つの netstack を共有します。
  netstack は転送しないのでピア同士は通信できないが、ICMP の誤りは別のピアと `vpsd` の間のフローを引用できます。
  TUN の入口は、外側の送信元が引用の宛先と一致しない ICMP の誤りと、next-hop MTU が 552 より小さい Fragmentation Needed を捨てる([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「ICMP の誤りの入口」)。
  エージェントが自分のフローに誤りを送ることは、MTU の下限を除いて防がありません。
  自分のフローを妨げるだけだからです
- 鍵の置き換えで引き継ぐエンドポイント([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))は、古い公開鍵で認証されたパケットの送信元です。
  WireGuard は認証を通ったパケットでしかエンドポイントを変えず、その送信元に移す。
  この値を動かせるのは、古い秘密鍵の持ち主と、経路上で捕まえた認証済みのパケットを本物より先に届けられる者だけです。
  古い鍵が盗まれて持ち主が別の場所にいる場合は、引き継いだエンドポイントがその場所を指し得ます。
  その場合も、`vpsd` がそこへ送るのは新しい公開鍵へのハンドシェイクの開始だけです。
  新しい秘密鍵を持たない相手は応答を作れないのでトンネルは成立せず、WireGuard はハンドシェイクの成立の前に転送のデータを送らないので、転送の中身も渡らない。
  引き継いだ後のエンドポイントを動かせるのは新しい鍵で認証されたパケットだけなので、古い鍵の持ち主はエンドポイントを自分に留められない。
  本物のエージェントのハンドシェイクが届いた時点で、エンドポイントは本物の送信元に移る。
  この場合に転送が戻るのは、引き継ぎの無い場合と同じく、エージェントの送り直しの時点です。
  古い鍵の持ち主が新たに知るのは、`vpsd` がそのアドレスへハンドシェイクを試みたことだけです。
  登録の取り消しで回収したアドレスを別のエージェントに割り当て、古いピアの削除が修復([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))として残っていた場合も、同じ理由で害はありません。
  攻撃者が古い鍵でエンドポイントを任意のアドレスに向け、`vpsd` のハンドシェイクの開始をそこへ送らせることは、古いピアに対して今でもできることであり、引き継ぎはこれを広げない
- `vpsd` は転送対象のポート以外を開けない。
  VPS のファイアウォール設定そのものは扱わない
