## 起動の失敗の意味論

設定や環境の拒否は終了コード 3 で停止します。
起動を始められる状態になるまで、監督するプロセスに同じ試行を繰り返させません。


起動の失敗の分類の中心は、終了コードの番号ではなく次の 2 つの問いです。

- 再試行で直るか
- 人が手を入れなければ直らないか

判定は非対称です。
既定は「再試行で直りうる」とみなして終了コード 1 で終わる。
終了コード 3 は、原因が設定された値そのものであると示せる場合、または運用者の操作なしには消えないと示せる場合だけに使います。
示せない失敗は終了コード 1 とします。
誤った終了コード 3 は systemd の再起動を永久に止めるので、原因が消えた後も転送が戻りません。
騒がしい再起動の繰り返しより、転送が落ちたままになることのほうが悪い。

終了コード 3 で終わる失敗を起動の拒否と呼ぶ。
拒否は `internal/startup` の 1 つの型 `*startup.Refusal` で表し、`cmd/wgft` の `exitCode` はこの型の有無だけを見て終了コードを決める。
型を 1 つにする目的は、新しい失敗を足すときに終了コードへの写し忘れが起きないことにあります。

拒否は原因の種別を持ちます。
種別はログの文言と `wgft server check` の表示に出し、運用者が直し方を選べるようにします。
文言の書き出しは、その拒否が止めた行いによって 2 つに分かれる (2026-09-23、所有者の決定)。
常駐プロセスの起動を止めた拒否は `refusing to start [種別 対象]: 理由` とし、常駐プロセスを起動しない一発実行のコマンドを止めた拒否は `cannot continue [種別 対象]: 理由` とします。
設定を読む層は両者で共有しており、同じ誤りがどちらの経路にも出る。
`wgft status` や `wgft agent doctor` が起動を拒んだと述べると、何も起動しないコマンドについて事実でないことを述べることになります。
終了コードはどちらも 3 です。

どちらの書き出しを使うかは、コマンドの側が決める。
読む層の側は呼び出し元を知らず、`buildServerOptions` のように `server run` と `server check` が共有する入口もあるためです。
既定は一発実行の側とし、常駐プロセスを起動する `server run` と `agent run` だけが自分でその旨を名乗る。
既定を逆にすると、コマンドを足すたびに印を付け忘れた分だけ事実でない文言が残る。

| 種別 | 意味 | 例 |
|---|---|---|
| `config` | 設定された値そのものの誤り。構文、範囲、必須の値の欠落 | `WGFT_MTU` が範囲外、初回の `WGFT_MODE` の欠落、`WGFT_JOIN` の構文の誤り |
| `prerequisite` | ホストが備えるべきものの欠如で、再試行では現れないもの | カーネルの WireGuard モジュール、`CAP_NET_ADMIN`、新しい版が書いたサーバのデータベース、Linux でないホスト、Linux でないホストでのエージェントの `WGFT_MODE=kernel` |
| `conflict` | 設定された値や認証情報が、すでにある記録と矛盾するもの | 記録済みのアドレス帯との食い違い、使用済みの登録トークン、登録済みの名前 |
| `mode-gate` | モードの切り替えの関門を通らないこと | `kernel` から `userspace` への切り替えで、wg インタフェースか `table inet wgft` が残っている。エージェントでは、wg インタフェースか `table inet wgft_agent` かカーネルモードの記録が残っている |

Linux 以外のビルドの `server` の一群は、種別 `prerequisite` の拒否を返す (2026-09-23、所有者の決定)。
Windows と macOS のバイナリはエージェントと CLI だけを持ち、server はカーネルの WireGuard と nftables を使うので Linux でしか動かない。
この前提の不成立は再試行でも再起動でも消えず、運用者が Linux のホストへ移すまで同じ結果になるので、本節の非対称の規則では拒否の側に当たる。
終了コードは 3 とします。
書き出しは他の拒否と同じ規則で分かれる。
`server run` は常駐プロセスの起動なので `refusing to start`、`server check`・`server nft`・`server teardown`・`server doctor` は何も起動しないので `cannot continue` です。
この書き分けを保つため、Linux 以外のビルドでも `server` の一群はコマンドの木の形を保ち、常駐プロセスを起動する旨の注記を持つのは `run` だけとします。
一群を 1 つのコマンドに畳むと、`server run` まで一発実行の文面になります。

この拒否が起きるホストには systemd が無いので、終了コード 3 が再起動を止める効果も働かない。
効果は、本節の末尾が述べる macOS とコンテナの場合と同じく、運用者と監視が原因を選り分けられることにとどまる。
それでも 1 にしないのは、Linux でないことが 4 つの種別のどれに当たるかという分類の問題であり、値を監督するプロセスごとに変えると分類そのものが揺れるためです。

エージェントのカーネルモード([7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))の起動の失敗は、`vpsd` のカーネルモードと同じ種別に写す(2026-09-24、所有者の決定)。
Windows と macOS のエージェントで `WGFT_MODE=kernel` を指定した場合は、上の Linux 以外のビルドの `server` と同じ理由で種別 `prerequisite` の拒否とし、終了コード 3 で止めます。
カーネルの WireGuard のリンク種別が無い場合と `CAP_NET_ADMIN` が無い場合も、[9 節](../state.md#9-状態の保存と再起動)の `vpsd` と同じく `prerequisite` です。
`kernel` から `userspace` への切り替えで残骸が残っている場合は `mode-gate` であり、`wgft agent teardown` を案内する([11a 節](configuration.md#11a-設定の渡し方))。
同名の WireGuard インタフェースが別の鍵を持つ場合は、他の所有者の資源との衝突として終了コード 1 で終わる(後述)。
これらの扱いは、このプロセスの最初の wgft0 の収束が stream に接続した後に行われる場合にも当てはまり、その後の同じ失敗はプロセスを終えずに試し直す([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止)、2026-09-24、所有者の決定)。

`wgft agent teardown` は常駐プロセスを起動しない一発実行のコマンドです。
Windows と macOS では、Linux 以外のビルドの `server` の一群と同じく種別 `prerequisite` の拒否とし、`cannot continue` の書き出しで終了コード 3 で止めます。
エージェントが稼働中のときに何も消さずに拒否する扱いは起動の拒否ではなく、`server teardown` と同じ普通の誤りであり、終了コードは [7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の共通の保証に従って 0 以外になります。
未知のモードの記録で止まる場合は種別 `conflict`、`CAP_NET_ADMIN` が足りない場合は種別 `prerequisite` の拒否とし、どちらも `cannot continue` の書き出しで終了コード 3 で止める([10.3 節](../operations/setup.md#103-運用の流れ))。
指したデータディレクトリに `agent.json` が無く、何も消さずに止まる場合は、稼働中の拒否と同じ普通の誤りとして終了コード 1 で止める([10.3 節](../operations/setup.md#103-運用の流れ))。

`wgft server teardown` が、稼働中の `vpsd` のロックで拒否する場合と、ロックの状態を読めずに何も消さずに止まる場合は、どちらも起動の拒否ではなく普通の誤りであり、終了コードは 1 である([10.3 節](../operations/setup.md#103-運用の流れ)、2026-10-03)。

再試行で直りうる失敗は拒否にせず、普通のエラーとして終了コード 1 で返します。
他の所有者が持っている資源との衝突はこちら側に入ります。
同名のインタフェースが別の鍵を持っている場合、他の WireGuard が `WGFT_WG_PORT` を使っている場合、他のプロセスがその UDP ポートを bind している場合、アドレス帯が他のインタフェースと重なっている場合、`net.Listen` が `EADDRINUSE` を返す場合、サーバのデータベースを他のプロセスが保持している場合が当たる。
撤去がロックを持つ間に起動した `vpsd` も最後の場合に当たり、データベースを開く前に終わる([10.3 節](../operations/setup.md#103-運用の流れ))。
いずれも相手が資源を手放せば次の再起動で起動できます。
何も書き換える前に中止する事前検査そのものは残します。
半端な状態を作らないことと、再起動を止めることは別の目的です。

この 2 つの扱いに収まらない失敗が 1 つあります。
起動時の最初のルールの適用の失敗であり、原因が記録した宣言そのものにあるため再起動では直らない一方、運用者がその宣言を直す経路は管理用 API にあります。
この失敗だけは終了せず、管理用 API だけを開いて適用を試し直す(次項)。
