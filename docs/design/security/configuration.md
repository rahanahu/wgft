## 設定の渡し方

設定は WGFT_* の環境変数、dotenv、対応するフラグで受け取ります。
フラグ、環境変数、ファイル、既定値の順に優先します。


wgft のどのプロセス(`vpsd`、`agent`、CLI)も `WGFT_*` の環境変数で設定を受け取ります。
ファイルはその dotenv、フラグはその別名であり、優先順位はフラグ、プロセスの環境変数、ファイルの順です。

ファイルの既定の置き場所は `vpsd` と CLI が `/etc/wgft/server.env`、`agent` が `/etc/wgft/agent.env` で、`--config` で変更できます。
同じファイルは systemd の読み込み、Docker の `--env-file`、compose の `env_file` の 3 つの経路で扱われ、この 3 者は構文の解釈が一致しないため、3 者で一致する範囲だけの構文を許す。
1 行に `KEY=value` を 1 つ書き、行頭の `#` だけをコメントとして扱う。
値の途中の `#` は値の一部として扱い、引用符は使わず、値に空白を含めることもできません。
引用符で始まる値は警告ではなくエラーにします。
3 つの経路それぞれで解釈が異なり、たとえば Docker では引用符ごと 1 つの値として扱われ、黙って認証エラーになるなどの事故につながるためです。
この規則の下では、`WGFT_JOIN` の接続文字列(`wgft://host:port/token#sha256:...`)は引用符なしでそのまま書ける。

systemd の unit では `EnvironmentFile=` を使いません。
バイナリが既定で同じファイルを自分で読むため不要であり、`EnvironmentFile=` を使うと値の出所がすべて「環境変数」になり、出所付き印字(下記)が意味を失う。

`server.env` には秘密の値を置かない。
`vpsd` の設定項目に秘密は無く、サーバ鍵、証明書、トークンはすべて SQLite にあります。
同梱の unit は `DynamicUser=yes` の非特権の利用者で動く([10.3 節](../operations/setup.md#103-運用の流れ))ため、`server.env` はその利用者が読める 0644 にします。
`agent.env` は `WGFT_JOIN` を含むので、root 所有、グループ `wgft` の 0640 にし、固定の `User=wgft` で動く unit から読ませる。
ファイルが無い場合はエラーにせず、環境変数と既定値だけで動く。
unit に `LoadCredential=` でファイルを渡す方法は採らない。
0600 のままでも動くが、`--config` で別の場所を指す必要があり、root の CLI が読む既定の場所と二重になり、起動ログの出所の見え方も変わる。
秘密の無いファイルに対しては重いためです。

設定ファイルから読んだ値に秘密(`WGFT_JOIN`)が含まれ、そのファイルが other(このホストの誰からでも)読めるパーミッションのときは、起動時にファイル名と推奨するパーミッションを添えて英語で 1 行だけ警告します。
止めはしません。
この判定は Unix だけで行い、Windows では行わない([11a 節](configuration.md#11a-設定の渡し方)後段の DACL による別の扱いのため)。
group のビットは対象にしません。
`agent.env` の推奨である 0640(root 所有、グループ `wgft`)は意図した共有であり、これに対して起動のたびに警告すると、正しく設定した環境でもログが埋まるだけになります。
値がファイルではなく環境変数やフラグから来た場合、および `server.env` のように秘密な設定項目を持たないファイルには、パーミッションに関わらず警告しません。

設定の誤りによる起動の失敗は終了コード 3 で止め、直し方をエラーに添える。
対象は設定ファイルが読めないこと、その構文の誤り、値の誤り、必須の値の欠落です。
値ごとの規則は本節の各項目にあり、終了コードの決め方と、設定以外の原因による起動の失敗の扱いは [11b 節](startup.md#11b-起動の失敗の意味論)に定める。
Docker の `restart: unless-stopped` は終了コードを見ないので、コンテナでは設定の誤りでも再起動を繰り返します。
設定ファイルの構文の誤りの文言は、ファイル名と行番号と、名前の形をしたキーだけを示し、行の中身と値を出さない。
文言は起動の失敗としてジャーナルに残り、行の中身は `WGFT_JOIN` の接続文字列のような秘密の値を含みうるためです。

起動ログの先頭と `wgft server check` の出力は、有効な設定を値と出所(フラグ、環境変数、ファイル、既定値のいずれか)付きですべて印字します。
トークンなど秘密の値は伏せ字にします。

他のプロセス向けの `WGFT_*` はエラーにせず無視します。
知らない名前だけでなく、`vpsd` から見た `WGFT_AGENT_ALLOW_TARGETS` のように「知っているが自分には関係ない」名前も対象です。
この規則により、同じ Docker イメージや同じ設定ファイルで `agent` と `vpsd` を切り替えて使える。
`WGFT_MODE` と `WGFT_WG_INTERFACE` は、`vpsd` とエージェントがどちらも同じ名前で読む(下記)。
既定のファイルは `server.env` と `agent.env` に分かれているので、同じファイルを両方に渡す配置でだけ、同じ値が両方に効く。
この配置では、今のエージェントが無視している `WGFT_MODE=kernel` が、更新の後はエージェントにも効く。
リリースノートはこの挙動の変化を知らせる([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。

同時フロー数のプロセス全体の上限([7 節](../agent-dataplane.md#7-データプレーン自宅側))は `WGFT_MAX_UDP_FLOWS`(既定 8192)と `WGFT_MAX_TCP_FLOWS`(既定 2048)で、`vpsd` とエージェントの両方が受け取ります。
値は 16 から 65535 の整数で、範囲外は起動時のエラーにします。
メモリの小さいホストで下げるための設定であり、ホストのメモリの量から自動では決めない。
ルールごとの上限はこの 2 つから導く値であり、独立した設定項目ではありません。

接続元 IP ごとの上限([7 節](../agent-dataplane.md#7-データプレーン自宅側))は `WGFT_MAX_UDP_FLOWS_PER_SOURCE`(既定 256)と `WGFT_MAX_TCP_FLOWS_PER_SOURCE`(既定 128)で、`vpsd` だけが受け取ります。
エージェントから見た接続元は常に `10.200.0.1` で接続元ごとに数える意味がないため、エージェントの設定項目には加えない。
値は 0 から 65535 の整数で、0 はそのプロトコルの上限を無効にする(プロセス全体の上限と違い、0 は正当な値である)。
範囲外や負の値は起動時のエラーにします。
プロセス全体の上限と連動して自動で変わることはなく、上げたい場合は明示して設定します。

宛先の許可一覧([7 節](../agent-dataplane.md#7-データプレーン自宅側))は `WGFT_AGENT_ALLOW_TARGETS` で、エージェントだけが受け取ります。
値はコンマ区切りの一覧で、各項目は `CIDR`、`CIDR:ポート`、`CIDR:下限-上限` のいずれかです。
アドレスだけを書いた項目は `/32` か `/128` として扱う。
ポートを書かない項目はそのアドレスの全ポートを許す。
IPv6 のアドレスにポートを付ける項目は `[2001:db8::/32]:8080` の形で角括弧で囲む。
ポートを書かない IPv6 の項目に角括弧は要りません。
項目の前後の空白は無視します。
構文の誤りは起動時のエラー(終了コード 3)にします。
省略した場合と、値が空白だけの場合は制限せず、`vpsd` が配るどの宛先へも接続します。
値があるのに項目が 1 つも無い場合(コンマだけを書いた場合など)は構文の誤りとして起動を止めます。
守りの設定であり、書いたつもりの一覧が黙って「制限なし」になるより、起動を止めるほうが安全なためです。
項目があって 1 つも一致しない一覧は正当な値で、すべての宛先を拒みます。
IPv4 と IPv6 のどちらのアドレスも書ける。
ルールの `target` は v1 では IPv4 とホスト名だけを受け取る([4 節](../network.md#4-ネットワーク))ので、IPv6 の項目が効くのはホスト名が IPv6 のアドレスに解決される場合です。

データの置き場所は `WGFT_DATA_DIR`(既定 `/var/lib/wgft`)に統一します。
この下に `vpsd` は SQLite ファイルを、`agent` は状態ファイルを置く([9 節](../state.md#9-状態の保存と再起動))。

既定の置き場所は OS ごとに決める。
Linux は上のとおりです。
Windows は設定ファイルもデータも `%ProgramData%\wgft` に、macOS は `~/Library/Application Support/wgft` に置く。
どの OS でも `--config` と `WGFT_DATA_DIR` で変更できます。
Linux 以外のバイナリが持つのはエージェントと CLI だけで、`server` サブコマンドは「Linux でしか動かない」と答えて終わる。
`vpsd` はカーネルの WireGuard と nftables に依存するためです。
ユーザー空間モードのエージェントは wireguard-go と netstack だけで動くので OS を選ばない設計であり(カーネルモードは Linux だけです。
[7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))、Windows は 2026-09-19 に Windows 11(非管理者権限での実行)から実機の VPS に対して確認した。
ホームルータの NAT を越えた join string による登録、トンネルの確立、LAN サービスへの UDP と TCP の中継、server の再起動と agent の強制終了からの復帰、2 つ目の `agent run` の拒否、認証情報ファイルの書き換え、稼働中の `rotate-key` が通ったため、Windows 版のエージェントと CLI は Releases に含め、README にも対応として書きます。
macOS は 2026-09-19 に macOS 27(Apple シリコン、arm64)から、ホームルータの NAT の内側で実機の VPS(v0.3.0、カーネルモード)に対して確認した。
join string による登録、トンネルの確立、Mac 自身と LAN の他のホストへの UDP と TCP の中継、Mac の再起動と server の再起動からの復帰、2 つ目の `agent run` の拒否、稼働中の `rotate-key`、データディレクトリ(0700)と `agent.json`・`agent.json.lock`・`agent.json.sock`(0600)の権限が通ったため、macOS 版のエージェントと CLI も Releases に含め、README にも対応として書きます。
macOS で公開するのは darwin/arm64 だけです。
Intel Mac は対象にせず、amd64 の自宅マシンには Linux 版で対応します。

Windows での常駐は、`agent run` をそのときの利用者の権限で起動するところまでを wgft が提供し、サービス、タスクスケジューラ、通知領域への常駐は提供しません。
ログオン時の自動起動(スタートアップフォルダへの登録など)は利用者に任せる。
Windows のゲームサーバの多くがユーザー権限で動いており、agent も管理者権限を必要としないことに合わせた判断であり、サービス化には Program Files への配置、SYSTEM と対話利用者の間の ACL の取り合い、SCM(サービス制御マネージャ)対応のコードが新たに要ることを理由に見送った。

Windows Defender Firewall は、初回起動時に `wgft.exe` の受信を許可するかどうかのダイアログを表示します。
wireguard-go が UDP を `0.0.0.0` で待ち受けるためです。
実機では、このダイアログで許可した場合はもちろん、キャンセルして受信拒否の規則が作られた場合でも、agent は外向きの接続しか使わないため、トンネルと中継は WireGuard の鍵の再交換をまたいで動作し続けることを確認した。
ダイアログは許可してもキャンセルしてもよい。

未確認の点は、Windows サービスまたは SYSTEM としての実行です。

macOS での常駐には、`UserName` に利用者を指定した LaunchDaemon(`/Library/LaunchDaemons` に置き、システムの launchd が起動するジョブ)を推奨し、その例を `deploy/io.github.rahanahu.wgft.agent.plist` として配る。
プロセスは root ではなくその利用者の権限で動き、`WGFT_DATA_DIR` で利用者の `~/Library/Application Support/wgft` を指すので、ターミナルから起動した `agent run` と同じ認証情報ファイルを使います。
launchd は `UserName` を持つジョブの環境に `HOME` を設定する(実機で、その利用者のホームディレクトリが入ることを確認した)が、plist の文字列の中の `~` は展開しないため、plist はログのパスを書き下す。
`WGFT_DATA_DIR` も明示し、既定の置き場所の解決に依らず、ターミナルから起動した `agent run` と同じディレクトリを LaunchDaemon が使うようにします。
plist は root 所有の 0644 で置かれ全員が読めるため、`WGFT_JOIN` を書きません。
初回登録は、ターミナルから `WGFT_JOIN` を付けて `agent run` を起動し、登録できたら止めてから LaunchDaemon を読み込む手順とした。
launchd には systemd の `RestartPreventExitStatus` に当たる設定が無いため、`KeepAlive` の `SuccessfulExit` を偽にして異常終了と強制終了のときに再起動させ、間隔は `ThrottleInterval` で空ける。
設定の誤りで終了コード 3 になった場合も、launchd はこの間隔で再起動を繰り返す(2026-09-21 に実機で確認。
60 秒のあいだに 6 回起動し、`launchctl print` は `last exit code = 3` と `state = spawn scheduled` を示した)。
systemd の `agent.service` は同じ場合に再起動を止めるので、macOS では設定の誤りに気付く手段がログだけになります。
root での実行は必要が無いため試していません。

LaunchAgent(`~/Library/LaunchAgents` に置き、利用者のログインセッションで動くジョブ)は推奨しません。
実機では、LaunchAgent として起動した agent はデフォルトゲートウェイには接続できたが、LAN の他のホストへの接続は `connect: no route to host`(`EHOSTUNREACH`)で失敗し、許可を求めるダイアログも出なかった。
同じバイナリをターミナルから起動した場合(ターミナルのアプリの許可を引き継ぐ)と、`UserName` 付きの LaunchDaemon として起動した場合は、他のホストへ UDP と TCP で接続できた。
この失敗を macOS 15 以降のローカルネットワークのプライバシー保護によるものとするのは症状からの推測であり、システムログには該当する記録が見つからなかった。
LaunchAgent を使う `brew services` も同じ問題に当たる可能性があるが、未確認です。
macOS 27 の実機では、`/usr/local/bin/wgft` に新しいバイナリを置いた直後の LaunchDaemon の 1 回目の試し接続だけが、LAN の他のホストに対して同じ `no route to host` で失敗し、その後は同じ宛先へ繰り返し接続できた(2026-09-21)。
1 回だけ失敗した理由は未確認です。

FileVault を有効にした Mac では、再起動後に LaunchDaemon が起動したのはカーネルの起動時ではなく最初のログインの時点だった。
最初のログインまでデータボリュームがロックされたままであるためと推測します。
起動した agent は `network is unreachable` で再試行し、その後は自力で接続した。
再試行が続く長さは、その Mac のネットワークが上がるまでの時間で決まる。
2026-09-19 の確認では十数秒、2026-09-21 の確認では約 60 秒であり、後者は Wi-Fi の接続もログインの後に始まる Mac だった。
この制約には対処せず、文書に書くにとどめる。
想定する利用者はその Mac で遊び、ゲームサーバもその利用者のセッションで動くため、ログインまで agent が動かないことによる不都合は小さい。
`fdesetup authrestart` は試していないため、手順として勧めない。

macOS のバイナリは Apple の公証を受けない。
ブラウザで取得したファイルには隔離の属性が付き、Gatekeeper は隔離の属性を持つ公証の無いバイナリの起動を止めるため、README とセットアップガイドは `curl` での取得を案内します。
`curl` で取得したファイルに隔離の属性が付かないことは確認したが、ブラウザで取得した場合の挙動は試していません。

macOS のエージェントのメモリ使用量は、同時フロー数の上限(既定の UDP 8192、TCP 2048)まで UDP のセッションと無通信の TCP の接続を保持した状態で、Linux のエージェントと同じく [7 節](../agent-dataplane.md#7-データプレーン自宅側)のソフト上限(216 MiB)を下回った([以前の検証 2026-09-19](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L3687))。
この結果はその条件での測定であり、ソフト上限はメモリの上限ではない([7 節](../agent-dataplane.md#7-データプレーン自宅側))。
同じ測定では、上限を超える TCP の接続のフラッドで、macOS と Linux のどちらのエージェントもソフト上限を大きく超えた。
原因は拒んだ接続が netstack の TIME_WAIT に残ることであり、拒否を RST で終える形に直した([7 節](../agent-dataplane.md#7-データプレーン自宅側)、[以前の検証 2026-09-19](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L3687))。
直した効果は、Linux のエージェントのラボで生きているヒープを測って確かめた。
macOS のエージェントでは未確認です。
macOS の `ps` の RSS は負荷が止んだ後も高いまま残るので、macOS でのメモリ使用量は物理フットプリント(`footprint`)で見る。

macOS の未確認の点は、保持していた TCP の接続の一部が相手側から閉じられた原因([以前の検証 2026-09-19](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L3687))、FileVault を無効にした Mac でログインせずに起動時から動くかどうか、ログアウト後も動き続けるかどうか、darwin/amd64、Homebrew での配布です。
この閉鎖は、コンテナを使う試験環境で、トンネルを通る多数の UDP のセッションと同時に TCP の接続を張っている間だけ起き、張り終えた後には起きなかった。
その一部は試験の宛先の listen キューの溢れによるもので、残りは試験環境の UDP のポート転送によるものと推測しています。

二重起動を止める排他ロック([9 節](../state.md#9-状態の保存と再起動))は、Unix では `flock`、Windows では `LockFileEx` で取り、どちらもファイルを閉じるかプロセスが終わると消える。

Windows の `%ProgramData%\wgft` は、既定では親ディレクトリから `BUILTIN\Users` の読み取りと実行を継承します。
状態ファイルの `Chmod(0o600)` は Windows では読み取り専用属性の切り替えにしかならず、この継承を止めないため、`agent.json` を PC の他の利用者が読める状態のまま残し得ます。
`agent.json.lock` と `agent.json.sock` は秘密を持たないが、同じ継承を受ける。
agent はこれを、データディレクトリ全体ではなく、自分が書く 3 つのファイルだけを対象に締める。
`WGFT_DATA_DIR` は利用者が任意の場所を指せる設定であり、ディレクトリそのものや直下の無関係なファイルまで毎起動で書き換えると、管理者が意図して加えた ACL(バックアップ用アカウントへの読み取りなど)を消しかねず、Unix の `MkdirAll` が既存のディレクトリを chmod しない設計とも食い違うためです。
`agent.json` は `Save` が一時ファイルを作る瞬間に、SYSTEM・`BUILTIN\Administrators`・実行中プロセスの利用者の 3 者だけにフルアクセスを許す保護 DACL(継承を切ったもの)を付けて作る(Windows の `CreateFile` に `SECURITY_ATTRIBUTES` として渡す)。
作ってから付け直すのでは、付け直すまでの間その一時ファイルが親ディレクトリから継承した緩い ACL のままになり、Windows はハンドルを開く瞬間にしかアクセス可否を見ないため、その間に別の利用者がハンドルを開けてしまえば後から DACL を締めてもその接続は取り消せない。
同じディレクトリ内での rename はこの DACL をそのまま持ち越すので、緩い ACL の期間は生じない。
緩い ACL の下で既に作られている `agent.json` は、起動時に読むたびに同じ DACL を単独で付け直して締める。
Windows 11 の実機で見つかった環境がこれに当たる。
`agent.json.lock` は `Acquire` が開く・作るたびに、`agent.json.sock` は制御ソケットを開くたびに、同じ DACL を単独で付け直す。
データディレクトリ自体は、agent が新規に作った場合だけ同じ DACL(継承可能な形)を付けて作り、既に存在するディレクトリは変更しません。
DACL を付け直せない場合(所有者でも Administrators でもない利用者で実行した場合など)は、その処理(読み込み・保存・ロック取得)を失敗として扱い起動を止めます。
制御ソケットだけは、開けない場合と同じく `rotate-key` の稼働中経路だけを諦め、agent 自体は動き続けます。
[9 節](../state.md#9-状態の保存と再起動)の SQLite の権限の扱い(グループとその他の権限だけを外し、それ以外は変えない)と同じ、変更を対象自身に限る考え方です。

制御ソケットには、agent.json の一時ファイルとは違い、緩い ACL のままの短い期間が残る。
`Listen` がソケットのファイルを作った瞬間から `SecureSocket` で締め直すまでの間、親ディレクトリから継承した緩い ACL のままであり、この期間に接続した相手はその後の締め直しでは切断されない。
この期間を完全になくすには、専用のディレクトリを起動のたびに新規に作って先に締め、その中でだけソケットを開く必要があるが、制御ソケットが受け付けるコマンドは `rotate-key` の 1 つだけで、応答も新しい公開鍵かエラー文言のみであり秘密は一切やり取りしません。
この期間に接続された最悪の場合でも、利用者の意図しない鍵の作り直し(次のハンドシェイクから新しい鍵になるだけ)にとどまり、恒久トークンや wg 秘密鍵の漏えいには至らない。
この非対称性から、この期間はなくさず既知の制約として残します。

制御ソケットのパスには長さの上限があります。
Unix ソケットのアドレスは `sockaddr_un` の `sun_path` に収めるため、終端の NUL を除いて Linux と Windows では 107 バイト、macOS では 103 バイトまでしか使えない。
パスは `WGFT_DATA_DIR` に `agent.json.sock` を付けたものなので、深いデータディレクトリを指すと上限を超える。
超えた場合、Go の `net` は OS を呼ぶ前に `invalid argument` を返します。
agent は制御ソケットを開けない他の場合と同じく `rotate-key` の稼働中経路だけを諦めて動き続け、ログにはパスのバイト数と上限、短いデータディレクトリを使うという対処を添える。
稼働中の agent に向けた `rotate-key` も同じ原因で接続できないので、同じ説明を添える。
ソケットを別の短い場所へ移すことはしません。
制御ソケットが認証情報ファイルの隣にあることは、`rotate-key` が稼働中の agent を見つける唯一の手掛かりだからです。

この既存ファイルの締め直しは Windows だけで行います。
Unix では `Chmod(0o600)` で足りるので、既存ファイルの締め直しは行いません。
既存の `agent.json`・`agent.json.lock` を起動のたびに 0600 へ揃え直すと、管理者が意図して 0400 のように絞った権限を緩めてしまい、[9 節](../state.md#9-状態の保存と再起動)の「余分な権限だけを外し、それ以外は変えない」という原則に反します。
さらに、agent を非特権で動かす構成(`deploy/agent.compose.yaml` の `cap_drop: [ALL]` など)でボリューム上のファイルを所有していない場合、chmod は `EPERM` で失敗し、起動できなくなる。
したがって、既存ファイルの締め直しと、制御ソケットを開けない場合に `rotate-key` の稼働中経路だけを諦める扱いは、Windows に限る。
`Save` の一時ファイルへの `Chmod(0o600)` は失敗を呼び出し元に伝え、Unix の挙動は Windows の対応によって変えません。

SYSTEM と対話ユーザーの関係は次のとおりです。
DACL は毎回そのときの実行者を含めて作り直すため、agent を Windows サービスとして SYSTEM で動かす場合は、SYSTEM 自身の項目が常に含まれるので読み書きできます。
対話ユーザーによる実行では、UAC の昇格を伴わない管理者アカウントのトークンは `BUILTIN\Administrators` が拒否専用(deny-only)になり、このグループへの許可が効かないため、直前にそのファイルを書いた本人(同じ SID)でなければ読み書きできません。
したがって、SYSTEM のサービス実行と対話ユーザーの実行を交互に行き来する運用では、最後に書き込んだ側と異なる非昇格の利用者は読み書きできず、昇格した管理者(「管理者として実行」)か SYSTEM だけが例外的に読める。
wgft は Windows サービスや常駐の仕組みを持たず、`agent run` を対話利用者の権限で起動する運用だけを提供する方針とした(本節前段)ため、SYSTEM でのサービス実行と対話利用者の実行を行き来する運用そのものが生じない設計です。
対話利用者どうしの間での UAC の昇格の有無によるこの挙動は上記のとおり成り立つが、SYSTEM としての実行との組み合わせは実機で確かめていません。

設定と状態の線引きは、「変えるのに片付けが要る、または保存済みの値と矛盾しうるもの」を状態として SQLite に置き、それ以外を設定としてファイルに置く、という基準による。
エンドポイントやポート、MTU などは編集して再起動すれば変わる設定であり、サーバ鍵、証明書、ルール、エージェントの情報は状態です。
動作モード(`WGFT_MODE`)と wg のアドレス帯(`WGFT_WG_ADDRESS`)は値そのものは設定だが、初回起動時に SQLite へ記録し、以後は起動のたびに env の値と照合するという扱いを受ける。
どちらも変えると片付けが要る、または保存済みの値と矛盾しうるためです。
設定を状態として持たない理由は、人がファイルとして読め、構成管理に置け、SQLite が壊れても復旧できる状態を保つためです。

`WGFT_MODE` は初回の起動で必須です。
初回に省略すると、`kernel` か `userspace` かを指定するよう求めて起動を止め、環境を見て推測することはしません。
初回に指定した値は SQLite に記録します。
2 回目以降に省略した場合は、記録したモードで起動します。
指定した場合は記録と照合し、一致すれば通常どおり起動します。
食い違った場合は関門を通し、通れば記録を書き換えて起動し、通らなければ起動を拒否します。
関門の中身は次のとおりです。
`kernel` から `userspace` へ切り替えるときは、wg インタフェースと `table inet wgft` の残骸が無いことを確かめる。
残骸があれば、先に `teardown` するよう案内して拒否します。
残骸の有無を確かめるには `CAP_NET_ADMIN` が要るため、確かめられない環境では「確認できない」と警告したうえで、wireguard-go の UDP bind を試みる。
この bind がカーネル側の `wgft0` に既に使われているポートと衝突して失敗した場合は、残骸の疑いとして host 上での `teardown` を案内します。
`userspace` から `kernel` へ切り替えるときは残骸が生じないため、そのまま通す。
モードの記録が無い既存の SQLite は、これまで `kernel` しか存在しなかったことから `kernel` とみなして記録します。
`wgft server teardown` はモードの記録に触れない。
切り替えの判断は起動時の照合と関門だけで完結します。

エージェントも `WGFT_MODE`(`--mode`)を読む(2026-09-24、所有者の決定)。
[7a.6 節](../architecture/wire-compatibility.md#7a6-維持する外部仕様と互換性)が `WGFT_MODE` を server と agent 全体の転送方式(`DataplaneMode`)の外部名と定めているので、エージェント専用の名前は作りません。
値は `userspace` か `kernel` で、それ以外は入口で種別 `config` の拒否にする([11b 節](startup.md#11b-起動の失敗の意味論))。
扱いは `vpsd` と次の点で違う。

- 既定:省略すると `userspace` です。
  `kernel` は明示したときだけ選ばれる。
  初回の必須にはしません。
  既存のエージェントはモードの記録を持たず、既定を今の動作と同じ `userspace` にすれば推測にならないためです。
  モードの記録が無い `agent.json` は `userspace` の記録とみなす([9 節](../state.md#9-状態の保存と再起動))。
  `WGFT_MODE` を渡していない配置は、設定を変えずにそのまま動く
- 記録と照合:モードは状態ファイル `agent.json` に記録し、起動のたびに設定と照合する([9 節](../state.md#9-状態の保存と再起動))。
  `agent.json` の内部の形は [7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の保証の外なので、項目の追加は自由です
- 切り替えの関門:`userspace` から `kernel` への切り替えは残骸を生まないので、そのまま通す。
  `kernel` から `userspace` への切り替えは、カーネルモードの残骸が残っていれば種別 `mode-gate` で拒否し、先に `wgft agent teardown`([10.3 節](../operations/setup.md#103-運用の流れ))を実行するよう案内します。
  残骸は、鍵の一致する WireGuard インタフェース、`table inet wgft_agent`、`agent.json` のカーネルモードの記録です。
  ユーザー空間モードのエージェントは `CAP_NET_ADMIN` を持たずテーブルを読めないので、関門は記録を根拠に判定します。
  ホストを再起動した後は記録だけが残骸として残り、`wgft agent teardown` がそれを消す([10.3 節](../operations/setup.md#103-運用の流れ))。
  記録が無いのに同じ名前の WireGuard のリンクがある場合は、拒否せずに警告を出す形を取りうるが、未確認です。
  `WGFT_MODE` を省略した起動も `userspace` への切り替えに当たるので、同じく拒否します。
  この拒否の文面は、`WGFT_MODE=kernel` を設定してカーネルモードを続ける道と、撤去してから切り替える道の両方を示します。
  関門で止まる起動は `agent.json` に何も書きません。
  `kernel` への切り替えは、[7b.5 節](../kernel-agent/operations.md#7b5-権限と配置)の前提の検査を通った後、鍵を作るよりも、登録よりも、カーネルに何かを書くよりも前に記録を書き換える。
  途中で落ちても、関門が残骸を見落とさないためです。
  前提で止まる起動も `agent.json` に何も書きません。
  記録がカーネルモードで、カーネルに wgft の資源が何も無い場合も、関門は記録を根拠に拒否し、撤去は `CAP_NET_ADMIN` を要する(2026-09-25)。
  ユーザー空間モードのエージェントも、`CAP_NET_ADMIN` を持たない撤去も、テーブルを読めず、何も作られていないことを示せないためです。
  `agent.json` の中身から何も作られていないと推す判定は、公開の記録を保存する前に落ちた場合や、`WGFT_WG_INTERFACE` を変える前の名前に残ったインタフェースを見落とす。
  前提の検査を記録より前に置いたので、この状態が生じるのは、前提を通った起動が最初の書き込みの前に止まった場合と、ホストの再起動の後です。
  前者を起こした配置は、権限の誤り以外の理由で検査を通った場合を除き `CAP_NET_ADMIN` を持つので、同じ権限で撤去できます。
  除かれる場合の例は、`RestrictAddressFamilies` から `AF_NETLINK` を外した unit です。
  検査の 2 つの読み出しがどちらも権限の誤りではない誤りで失敗するので、権限が無くても検査を通り、登録と記録の後に最初の収束で止まります。
  この unit を書いた運用者は root を持つので、root で撤去できます。
  ユーザー空間モードのエージェントはモードの記録を書かないので、その `agent.json` は旧い版と同じ形のまま残る。
  記録が `kernel` でも `userspace` でもない値なら、状態ファイルと設定の矛盾として種別 `conflict` で拒否します。
  撤去もこの記録を消さずに止まるので([10.3 節](../operations/setup.md#103-運用の流れ))、文面は、記録を書いた版で起動する道と、状態ファイルを控えから戻す道を示します
- 旧い版への戻し:旧い版のエージェントは `agent.json` の知らない項目を保存し直さない([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))ので、カーネルモードから旧い版へ戻すと記録が消え、wgft0 とテーブルだけが残る。
  リリースノートは、カーネルモードから旧い版へ戻す前に `wgft agent teardown` を実行するよう知らせる
- Linux だけ:Windows と macOS で `kernel` を指定すると、種別 `prerequisite` の拒否として終了コード 3 で止まる([11b 節](startup.md#11b-起動の失敗の意味論))
- 同時フロー数の上限:カーネルモードでは使わない旨を起動時に 1 行出し、拒否にはしない([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))

wg のアドレス帯(`WGFT_WG_ADDRESS`、既定 `10.200.0.1/24`)も初回起動時に記録し、以後は env の値と照合します。
アドレス部分は帯の先頭の次でなければなりません。
エージェントが vpsd をそこと決め打ちするためです。
`10.200.0.5/24` のような値は入口で設定の誤りとして拒否します。
記録済みの帯がこの条件を満たさない SQLite は、値を直しても記録との食い違いで止まるので、最初の拒否のメッセージが `teardown --purge` と再登録を案内します。
省略した場合は既定値を照合の対象にするので、省略しても起動は止まらない。
記録済みの値と食い違えば、エージェントの割り当てアドレスと矛盾するため起動を拒否し、変えるには `wgft server teardown --purge` と全エージェントの再登録が要ると案内します。

インタフェース名(`WGFT_WG_INTERFACE`、既定 `wgft0`)は記録しないが、変更すると旧インタフェースが鍵ごと残ることがあるため、`wgft server check` と起動時に、自分のサーバ鍵を持つ別名の WireGuard デバイスが無いかを検査し、あれば警告します。
エージェントも `WGFT_WG_INTERFACE`(`--wg-interface`、既定 `wgft0`)を読み、カーネルモードのインタフェース名に使います。
ユーザー空間モードでは使いません。
同じホストの同じ network namespace で `vpsd` とエージェントがどちらもカーネルモードで既定名を使うと名前が衝突するが、鍵による所有の判定([9 節](../state.md#9-状態の保存と再起動)、[7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))が相手のインタフェースに触れずに止めるので、安全側に倒れる。

環境変数とファイルに置けるのは設定だけであり、その 1 回の起動や実行にだけ意味を持つ操作はフラグでしか渡さない。
対象は `--adopt-existing`、`--force`、`--purge`、`--yes`、`--dry-run` です。
たとえば `WGFT_ADOPT_EXISTING=true` のような値がファイルに残ると、再起動のたびに他人の WireGuard インタフェースを引き継いでしまうためです。
例外は 2 つあり、どちらも居座っても害が無いことを仕様で保証しています。
1 つは `WGFT_MODE` と `WGFT_WG_ADDRESS` で、初回に記録された後は照合にしか使われない。
もう 1 つは `WGFT_JOIN`(エージェントの初回登録)で、これは 1 回限りの操作でありながら、compose ファイルに残ることを前提に設計してあります。
エージェントは使用済みの登録トークンのハッシュを状態ファイルに残し、`WGFT_JOIN` の値がそれと同じであれば登録を試みずに止まる([5.1 節](../control/registration.md#51-登録))。
エージェントが削除され、恒久トークンの認証が拒否された場合だけ、この値を使って再登録します。

`rule add` と `rule set` の `--dry-run` は、管理 API から観測可能な範囲で、実際の `Batch` が保存前に行う admission 判定と一致させる。
予約ポートは `ServerInfo` から構成し、`ValidateUpsert` に渡す。
組み立ての規則は `internal/vpsd/vpsd.go` が起動時に `Daemon.reserved` を作る規則と同じにします。
WireGuard のポートは常に予約します。
`admin_addr` は `net.SplitHostPort` で `host:port` に分けられたときだけ予約し、Unix ソケットはポートを予約しません。
`agent_api_port` は `GET /api/v1/server`(`admin.ServerInfo`)が既に `net.SplitHostPort` 済みの文字列として返す値を使います。
どちらも待ち受けが実際に bind するポートを予約します。
ホストの部分は問わないので、`localhost:8686` と `:8686` もポート 8686 を予約します。
ポートの部分は `net.Listen` と同じ `net.LookupPort` で番号に直すので、`0.0.0.0:https` はサービスの一覧が示す番号を予約し、`+8686` と `08686` は 8686 を予約します。
番号が 0 になるポートはカーネルが選ぶポートであり、どのルールも使えないので予約しません。
行ごとには `GET /api/v1/agents` が返す名前の集合による `--agent` の登録の検査を行います。
行の形の検査(`Rule.Validate`)は、`rule add` と `rule set` のどちらも `--dry-run` の有無に関わらず先に行います。
落ちた行は `--dry-run` の実装に届かないため、`--dry-run` の実装は行の形の検査を行いません。
全体には、現在のルール集合にこの upsert を当てはめた後の集合に対して、`ValidateUpsert` による ID の重複・予約ポート・listen_port の重なりの検査を行います。
`Batch` は呼びません。
誤りが無ければ終了コードは 0 とし、何も保存していないことを出力に明記します。
誤りがあれば終了コードは 1 とします。
この判定は Web UI の読み込みの確認([10.1 節](../interface.md#101-web-ui))とも共有しているが、一致させる基準は実際の `Batch` であって Web UI ではありません。

ポートの名前を番号に直せない場合は、予約ポートを組めなかったものとして止め、そのポートを予約から外して続行しません。
続行すると、そのポートに重なる変更を受理されるものとして示すためです。
`vpsd` は起動を止める(終了コード 1)。
入口([11b 節](startup.md#11b-起動の失敗の意味論))が同じ `net.LookupPort` で値を検査しているので、これが起きるのは検査の後にサービスの一覧が変わった場合だけです。
`--dry-run` は `GET /api/v1/server` が読めない場合と同じ終了コード 2 で止め、Web UI の読み込みの確認は確認の画面を止めます。
CLI はサービスの名前を自分のホストのサービスの一覧で番号に直すので、別のホストから管理用 API に接続する CLI では、server と違う番号になりうる。
この食い違いは未確認です。

2026-10-02 の改訂の前は、ホスト名やサービス名で書いた API のポートを予約していなかった。
予約ポートの検査は変更の無い行にも掛かる([5.4 節](../control/batches.md#54-ルールのバッチ操作))ので、そのポートに重なるルールを保存していた場合、更新の後はそのルールを残すバッチが、そのルールに触れない変更も含めてすべて拒まれる。
保存済みのルールの転送は続き、そのルールの `listen_port` を変えるか削除するバッチは通る。

`GET /api/v1/server` が失敗した場合、旧い版の server がこの節点を持たず 404 になる場合を含め、予約ポートを `nil` として続行しません。
続行すると、予約ポートに重なる変更を誤って accepted と示し、直後の実 `Batch` に拒まれる誤りが戻るためです。
この場合、`server doctor` と同じ終了コード 2(`unavailable`)で止め、この変更が受理されるかどうかを判定できなかったことを示します。
同じ理由で、`--dry-run` が読む `GET /api/v1/rules`・`GET /api/v1/agents` の失敗も終了コード 2 とします。
`rule add`・`rule set` の通常の実行(`--dry-run` を付けない場合)はこれらの節点を読まないため影響を受けない。

`target` への到達可能性は確かめず、`wgft server doctor <rule>` の対象です。
VPS 上で待ち受けポートが既に他のプロセスに使われていないかと、他のテーブルの DNAT(`internal/vpsd/apply.go` の `DNATConflicts`)との衝突は確かめない。
前者は `--force` で上書きできるが後者はできない一方、どちらも root と nft を要し CLI から admin API 越しには判定できないためです。
