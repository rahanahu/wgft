# VPS、エージェント、表示の信頼の境界

VPS の上の信頼しないローカル利用者は、脅威の範囲に含めません。
奪われた VPS から自宅へ向く経路、エージェント利用者と root、表示に使う文字列は別の境界で扱います。


VPS には、信頼しないローカルの利用者やサービスを置かない前提とする(2026-10-02、所有者の決定)。
VPS の上の信頼しないローカルの利用者やサービスは、wgft の脅威の範囲に含めません。
既存の権限と鍵の守りは、この前提を理由に緩めず、そのまま保つ。
保つ守りは、管理用 API の Unix ソケットを 0600 で作ること(前述)、サーバのデータベースを 0600 で作り、起動時にグループとその他の権限を外すこと([9 節](../state.md#9-状態の保存と再起動))、同梱の unit が `vpsd` を `DynamicUser=yes` の非特権の利用者で動かすこと([10.3 節](../operations/setup.md#103-運用の流れ))です。

奪われた VPS からエージェントを踏み台にする経路も脅威として扱う。
エージェントは `vpsd` が配る `target` へ自分から接続するので、VPS を奪った攻撃者はルールの `target` を `192.168.1.1:22` のような自宅の別のホストに書き換え、自宅の LAN 全体への踏み台に使える。
エージェント用 API の認証と証明書のピン留めは `vpsd` になりすます第三者を防ぐだけで、`vpsd` 自身が奪われた場合には効きません。
v1 はこの経路を、エージェント側の宛先の許可一覧([7 節](../agent-dataplane.md#7-データプレーン自宅側)の `WGFT_AGENT_ALLOW_TARGETS`)で狭める。
一覧はエージェントのホストの設定だけにあり、`vpsd` は一覧の内容を知らず、wire protocol にも現れない。
一覧を設定しない既定では制限が無いので、自宅の LAN に転送の宛先以外のホストがある運用では、一覧の設定を勧める。
一覧が守るのは宛先の範囲だけであり、一覧の中の宛先に対する不正な転送は防げない。
一覧とは別に、エージェントはブロードキャストとマルチキャストの宛先へ転送しない([7 節](../agent-dataplane.md#7-データプレーン自宅側))。
一覧の有無に依らず、1 つのルールで LAN の多数のホストへ届けることと、カーネルモードでホスト自身の待ち受けへ届けることを防ぐ。

エージェントのカーネルモード([7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))は、自宅のホストに新しい面を加える(2026-09-24、所有者の決定)。

- 自宅のホストの転送:カーネルモードでは、パケットを LAN へ送るのはエージェントのプロセスではなく自宅のホストのカーネルです。
  ユーザー空間モードの netstack は宣言したリスナーしか晒さないが、カーネルモードの wgft0 はホストのインタフェースなので、守りの行が無ければ、VPS からトンネルのアドレス(`10.200.0.x`)でホスト自身のサービス(sshd など)や LAN の任意のホストに届く。
  `table inet wgft_agent` の filter_pre は、wgft0 から入る新しい接続のうち公開したポートのものだけを DNAT の前で通す。
  forward は、DNAT したフローとその返り以外で wgft0 が絡む転送を落とす。
  宛先の許可一覧は DNAT を組むときに効くので([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い))、VPS を奪った攻撃者が `target` を書き換えても、一覧の外へ向かう DNAT は作られない。
  守りの強さはユーザー空間モードと同じです
- ホスト自身の入力の守り:`table inet wgft_agent` の input は、wgft0 から入る新規の接続のうち DNAT していないものを落とす。
  [6.1 節](../vps/kernel.md#61-カーネルモード)の VPS の input と同じ考え方です。
  DNAT した接続は、ホスト自身の LAN のアドレスを宛先に書いたルールの分だけ input を通る
- `ip_forward`:エージェントが 1 にすると、自宅のホストはルータとして振る舞える状態になります。
  wgft 以外の転送を止めるのは既存のファイアウォールの役目であり、`wgft_agent` の forward は wgft0 が絡む転送にしか触れない。
  家の LAN の中からこのホストを経由するよう仕向けられたパケットが転送されうる点は、[6.1 節](../vps/kernel.md#61-カーネルモード)の VPS と同じです。
  影響は利用者向けの文書で説明します
- server から届く値の検証:VPS を奪った攻撃者は、全体状態の値を自由に選べる。
  カーネルモードのエージェントは、ホストに書く前に、ルールの宛先を宛先の許可一覧で([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い))、トンネルのアドレスを登録時の記録で([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))確かめる。
  トンネルのアドレスは wgft0 の接続経路としてホストの経路表に入るので、確かめなければ、LAN の帯の一部を覆う帯を配ってホストから LAN へ向かう通信をトンネルへ引き込める。
  この場合、影響は公開したポートの外へ広がる。
  記録と違うアドレスの全体状態は、何も書かずに拒みます。
  wg 設定のほかの値は形だけを確かめる。
  トンネルが立っている間は、形の誤った mtu、keepalive、server の公開鍵も、アドレスと同じく wgft0 とテーブルを残したまま拒み、ハートビートに示します。
  ユーザー空間モードのトンネルのアドレスは netstack の中にだけあるので、ユーザー空間モードのエージェントは記録と違うアドレスも使います。
  keepalive と udp_timeout_stream は、ユーザー空間モードのエージェントも形を確かめるが、拒み方が違う。
  範囲の外の値は拒まず、既定値に置き換えて使います
- テーブルが無い間:`systemctl reload nftables` などで `table inet wgft_agent` だけが消えると、wgft0 と `ip_forward`=1 は残るので、VPS のピアからホスト自身と LAN への通信を止める行が無くなる。
  この間は、上の 2 つの守りがどちらも効きません。
  エージェントが稼働中なら 30 秒ごとの収束([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))が最長 30 秒で戻すが、停止中は戻りません。
  この隙間を使えるのは VPS を奪った攻撃者だけであり、`agent doctor` の `dataplane.table` が検出する([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))

エージェントの利用者と root の境界も脅威として扱う(2026-09-25、所有者の決定)。
同梱の unit はエージェントを `User=wgft` で動かし、データディレクトリはその利用者の持ち物です。
エージェントのプロセスが乗っ取られると、攻撃者はデータディレクトリの中の名前を自由に作り、消し、差し替えられる。
一方、停止中の `rotate-key`、`agent pubkey`、`agent teardown`、`agent doctor` は root で実行されうる。
乗っ取られたエージェントがサービスを動かしたままロックを放すと、管理者が普通に打った `sudo wgft agent rotate-key` は停止中と判断し、root で状態ファイルを書き換える。
root がデータディレクトリの中のパスを信頼すると、エージェントの利用者が root の権限を借りられる。
例えば root が一時ファイルの持ち主を名前で移すと、書き込みの途中で一時ファイルの名前を root のファイルへの symlink に差し替えられたとき、その先の持ち主がエージェントの利用者に変わる。
root がデータディレクトリの中のファイルを symlink も種別も確かめずに開くと、`/dev/zero` への symlink でメモリを使い切り、FIFO で止まり、デバイスを root で開きます。

そこで、root はデータディレクトリの中のパスを信頼しません。
[9 節](../state.md#9-状態の保存と再起動)のとおり、状態ファイルとロックファイルは symlink を辿らずに開いて種別を確かめ、状態ファイルの大きさに上限を置き、一時ファイルのパーミッションと持ち主は記述子に対して設定します。
稼働中の `rotate-key` が制御ソケットから読む応答にも大きさの上限を置く。
稼働中の `agent doctor` が制御ソケットから読む応答の上限は、この変更では扱わず、別の変更(下記のエージェントが送る文字列の項)で置く。
他の操作は、名前を差し替えられても root の権限を貸さない。
一時ファイルは既存の名前を開かずに新しく作る。
起動時の片付けは symlink を辿らずに名前そのものを消す。
rename と一時ファイルの削除は名前を置き換えるか消すだけであり、差し替えられて変わるのは、攻撃者自身が書けるデータディレクトリの中だけです。
守るのはデータディレクトリの中の名前であり、データディレクトリまでのパスは root と管理者のものとして信頼します。
`/var/lib` のようなデータディレクトリの親は、エージェントの利用者には書けない。

root がデータディレクトリの持ち主の権限に落としてから触る案は採らなかった。
Go のプロセスでは利用者の切り替えがプロセス全体に効き、root 以外の実効 uid に切り替えている間は、`agent teardown` が同じプロセスで行う netlink の操作に要る `CAP_NET_ADMIN` も実効の権限から外れる。
権限を落としても、FIFO で止まる問題と大きすぎるファイルでメモリを使う問題は残るので、種別と大きさの確認はどちらの案でも要る。

macOS は Unix と同じ実装を使います。
推奨の LaunchDaemon([11a 節](configuration.md#11a-設定の渡し方))はエージェントを利用者の権限で動かすので、同じ境界があり、同じ守りが効く。
Windows は持ち主を移さないので、持ち主を変えられる穴はありません。
Windows の一時ファイルの DACL は、作った一時ファイルを共有を許さずに開いている間に設定するので、その名前は差し替えられない。
状態ファイルとロックファイルは reparse point を辿らずに開いて種別を確かめ、既存のファイルの DACL の締め直し([11a 節](configuration.md#11a-設定の渡し方))は、削除の共有を許さずに開いている間に行います。
締め直しの DACL が許すのは SYSTEM、`BUILTIN\Administrators`、実行者だけであり、エージェントの利用者に権限を与えない。
データディレクトリそのものを junction に差し替えられた場合は守らない。
Windows で wgft が提供するのは `agent run` を対話利用者の権限で起動する運用だけであり([11a 節](configuration.md#11a-設定の渡し方))、別の管理者が昇格した CLI をその利用者のデータディレクトリに向ける運用は想定していません。
未確認:Windows の各点は Windows の実機では確かめていません。

エージェントが送る文字列を、運用者の端末に対する脅威としても扱う(2026-09-25、所有者の決定)。
エージェントは自宅側のホストで動き、そのホストが乗っ取られてエージェントの実行ファイルやプロセスが攻撃者の管理下に入る場合を想定します。
ハートビートのトンネルの理由・解決したエンドポイント・ルールごとの状態と理由・ルール ID は、エージェントが選ぶ文字列であり、`vpsd` はこれを 1 MiB の上限だけで受け取っていました。
`wgft agent ls`・`rule ls`・`status`・`server doctor` は、これらの文字列を人向けの出力にそのまま出す。
ESC で始まる端末の制御文字の並びをこの中に混ぜると、root で実行する運用者の端末の表示を隠したり偽ったりでき、対応する端末では貼り付け用の緩衝やクリップボードへの書き込みも起こし得ます。
`agent doctor` と `rotate-key` は、稼働中のエージェント自身の制御ソケットの応答と `agent.json` の内容を同じように端末へ出すので、エージェントのプロセスが乗っ取られている場合は同じ脅威が当たる。
制御ソケットの応答を読む箇所は、大きさの上限を持たずに読んでいた。

守りは 2 段に分ける。
受け口(`vpsd` の stream がハートビートを受け取る所)で、この文字列の長さを切り詰め、表示できない文字を読める形に置き換えてから保存する([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
エージェントも送る前に理由に同じ変換をかけるが、これは 1 通の大きさを抑えるためで、この守りには数えません。
乗っ取られたエージェントは変換を飛ばせるためです。
エージェント側でも、制御ソケットの応答を読む箇所に大きさの上限を置く。
表示の側では、`agent ls`・`rule ls`・`status`・`server doctor` の人向けの出力と、エージェント側の `agent doctor`・`rotate-key` の出力が、同じ 1 つの関数(`internal/textsafe.SanitizeForTerminal`)で表示できない文字を無害化してから出す。
2 段に分けるのは、受け口の守りが直さない経路(エージェント自身の制御ソケットの応答、受け口の修正より前の版の `vpsd` と話す rolling upgrade の最中)を、表示の側の守りが独立に塞ぐためです。

機械向けの出力への影響は経路によって違う。
`agent ls --json`・`rule ls --json` が返す値は、受け口の切り詰めと置き換えの分だけ変わる([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
`agent doctor --json` は制御ソケットの応答が受け口を経由しないので、`internal/textsafe.SanitizeStrings` による無害化がこの応答の文字列のほぼすべてに及び、稼働中のエージェントに対する `agent doctor --json` の `detail`・`next` にも表れる。
停止中のエージェントに対する `agent doctor --json`(`agent.json` を直接読む経路)は制御ソケットも受け口も経由しないため、`detail`・`next` を JSON へ写す直前(`agentDoctorJSONOf`)でも同じ関数を掛け、稼働中と停止中のどちらでも同じ守りが及ぶようにします。
`status --json`・`server doctor --json` の `detail`・`next`・`internal` は、これらを組み立てる値がすでに受け口で安全になっているので変えていません。
いずれの経路でも、`id`・`status`・`reason`・`evidence_unreachable` のような列挙値は判定の側が選ぶ固定の語であり、エージェントの文字列を経由しないので変わりません。
`detail`・`next`・`internal` はどの節でも人向けの文であり保証の対象ではない([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor)、[10.2b 節](../status.md#102b-状態の要約wgft-status)、[10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor)、[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))ので、これらの変更は互換の約束には触れない。

JSON へ書き出すときのエスケープ(`encoding/json` の既定の書式)は、C0 の制御文字と `U+2028`・`U+2029` は `\u00XX` の形で逃がすが、DEL(`U+007F`)や C1 の制御文字(`U+0080`-`U+009F`)は生のまま出す。
したがって `--json` の端末での安全さは、値そのものが上記のとおりすでに無害化されていることに支えられており、`encoding/json` 自身のエスケープには支えられていない(2026-09-26、レビューの指摘)。
