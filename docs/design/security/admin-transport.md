## セキュリティ

管理用 API は Unix ソケット、ループバック、明示した tailnet の経路で待ち受けます。
独自のパスワードを持たず、接続経路の境界でアクセスを制限します。


管理用 API と Web UI の待ち受け先は `--admin` で選ぶ。
独自のパスワードは持ちません。
ユーザー空間モード([6.3 節](../vps/userspace.md#63-ユーザー空間モード))では、転送対象の公開ポートで `vpsd` の Go のコードがインターネットに直接さらされる。
カーネルモードではその面はカーネルの DNAT だけで、`vpsd` 自身が受けるのはエージェント用 API とプロキシモードのポートに限られる。

- Unix ソケット(既定 `unix:///run/wgft/admin.sock`、0600。
  systemd の unit では `vpsd` の実行利用者が所有し、置き場のディレクトリは 0700 なので、開けるのは root と `vpsd` 自身だけ):VPS 上の CLI は root で直接叩く。
  手元のブラウザからは SSH のポート転送でソケットを引く([10.3 節](../operations/setup.md#103-運用の流れ))。
  到達できるのは「VPS の root」と「SSH でその root に入れる人」だけで、どちらも SQLite と wg の鍵を読める立場なので、パスワードを足しても守れる範囲は広がらない
- `--admin-tailscale`:加えて Tailscale のアドレスでも待ち受ける。
  起動時にまず `tailscale status --json` を実行し、`Self.TailscaleIPs` の最初の IPv4 アドレスと `Self.DNSName`(MagicDNS 名)を使います。
  `tailscale` コマンドが PATH にない、または失敗したときは、名前が `tailscale` で始まるインタフェース(Linux 版 Tailscale の既定は `tailscale0`)にある `100.64.0.0/10` のアドレスを使います。
  `100.64.0.0/10` は Tailscale 専用の帯ではなく VPS 事業者が内部網に使っていることがあるため、この帯を持つだけの他のインタフェースは使いません。
  検出した MagicDNS 名は `Host` の許可リストに自動で加わり、`--admin-host` は追加の名前のためだけに使います。
  認証、TLS、総当たり対策を Tailscale に任せられ、`vpsd` 側に追加の実装が要らないので、外から触りたい場合はこれを推奨します。
  tailnet が落ちても SSH で代替できます。
  VPS 自身からの接続はこの待ち受けに届かず、VPS 上の管理は Unix ソケットで行います。
  この待ち受けの到達の境界は後述の「tailnet の待ち受けの閉じ方」と「ホスト自身からの接続の拒否」による
- TCP(`--admin 127.0.0.1:8686` など):Unix ソケットの転送に対応しない SSH クライアントや、ラボ向けに残します。
  ループバック以外の TCP アドレスに開いた場合、`vpsd` は起動ログに警告を出すだけで止めません
- `public`:インターネットに公開します。
  ACME による正規の TLS 証明書、パスキーか TOTP、ログイン試行のレート制限、セッション期限と CSRF 対策を `vpsd` に実装したうえでなければ選べない。
  v1 では実装しない([13 節](../roadmap.md#制限と未実装の提案))

Unix ソケットの作り方(2026-09-30)。
ソケットのパスに対する操作は、どれも symlink を辿らない。
起動のときにパスにあるものがソケットなら、前の起動が残したものとして消す。
ソケットでないもの(誤って指したデータベースのファイルや symlink など)は、symlink の先がソケットであっても消さず、起動の誤りにします。
ソケットは umask を 0177 に狭めて作る。
bind は 0777 から umask を除いた権限でソケットを作るので、ソケットは作った瞬間から 0600 であり、パスへの chmod はしません。
作った直後に、パスにあるものが 0600 のソケットであることを確かめ、違えばパスにあるものを消さずに起動の誤りにします。
置き場のディレクトリが既にあって他の利用者が書き込め、sticky ビットも無い場合は、起動ログに警告します。
起動は止めません。
このディレクトリでは、その利用者が作った後のソケットを消して別のものに差し替えられ、CLI とブラウザの接続は差し替えた先に届く。
作った直後の確認で見つかるのは、確認より前の差し替えだけです。

tailnet の待ち受けの閉じ方(2026-09-25、所有者の決定)。
`--admin-tailscale` の待ち受けは、tailnet のアドレスに bind するだけでは tailnet に閉じない。
Linux は、宛先がホスト自身のアドレスであれば、どのインタフェースから届いたパケットも受け取ります。
このため、事業者の網で隣り合うホストが VPS の tailnet のアドレス宛ての経路を持てば、公開のインタフェースから管理用 API に届く。
`Host` の許可リストには `localhost` と tailnet の IP が入っているので、`Host` の検査はこの到達を止めません。
`vpsd` はこの待ち受けを次の 2 つで tailnet に閉じます。

- インタフェースへの縛り:待ち受けのソケットを、検出したアドレスを持つインタフェースの番号(ifindex)に `SO_BINDTOIFINDEX` で縛る。
  他のインタフェースから届いた接続の要求は、待ち受けが無いものとして RST で拒まれる。
  起動の時点で、検出したアドレスを持つインタフェースが無い場合と、縛れない場合は、待ち受けを開かずに起動の誤りとします。
  `net.ipv4.ip_nonlocal_bind` が 1 のホストでは、ローカルに無いアドレスへの bind が通り、縛る先の無い待ち受けになるためです。
  名前ではなく番号で縛るのは、見つけたインタフェースが縛るまでの間に作り直された場合に、後述の見張りが覚えた番号と縛り先を食い違わせないためです。
  インタフェースへの縛りは Linux 5.7 以降は特権なしで設定できるので、カーネル 6.1 以上を対象とする wgft では、非特権で動くユーザー空間モードの `vpsd` でも使える
- 接続元の検査:受け付けた接続の接続元が Tailscale の割り当ての帯に無ければ、HTTP を読まずに閉じます。
  `Host` の検査より前の段です。
  帯は IPv4 の `100.64.0.0/10` と IPv6 の `fd7a:115c:a1e0::/48` で、Tailscale のソースの `net/tsaddr` にある `CGNATRange` と `TailscaleULARange` に合わせた。
  IPv4 を写した IPv6 の形は IPv4 に戻してから比べる。
  閉じた接続は、接続を繰り返すだけでログを溢れさせられないよう、最初の 1 件だけをログに書きます

主の守りはインタフェースへの縛りで、接続元の検査は縛りが効かない場合の二重の守りです。
接続元の検査だけでは、`100.64.0.0/10` を内部網に使う事業者の網の隣人を区別できません。
Tailscale 自身のファイアウォールの規則(`ts-input`)は、Tailscale のソースの `util/linuxfw` によれば、tailscale0 以外から届いた `100.64.0.0/10` の送信元を落とすが、それ以外の送信元は宛先が tailnet のアドレスでも落とさない。
Tailscale の規則が無い構成、たとえば netfilter の管理を切った tailscaled では、`100.64.0.0/10` の送信元を持つ隣人を接続元の検査だけでは止められない。
tailscale0 から届く接続でも、送信元を書き換えずに転送するサブネットルータを経た LAN のアドレスからの接続は、接続元の検査で閉じます。

ホスト自身からの接続の拒否(2026-10-02、所有者の決定)。
`--admin-tailscale` の待ち受けは、接続元がホスト自身のアドレスである接続を、帯の内側のアドレスであっても HTTP を読まずに閉じます。
VPS 上での管理は、管理用 API の Unix ソケット(0600)が受け持ちます。
tailnet の待ち受けは、tailnet の他の端末から管理するための入口です。
ホスト自身から tailnet のアドレスへの接続はループバックを通り、接続元は既定で宛先と同じ tailnet のアドレスになります。
このため、この接続はインタフェースへの縛りも接続元の検査も通る。

- 判定の方法:受け付けた接続の接続元を、まず接続の宛先のアドレスと比べ、次にホストのすべてのインタフェースのアドレスと比べる。
  どちらかと同じなら閉じます。
  ホストのアドレスは、宛先と一致しなかった接続ごとに読み直すので、起動の後に加わったアドレスも比べる対象に入ります。
  IPv4 を写した IPv6 の形は IPv4 に戻してから比べる。
  ホストのアドレスを読めなかった場合は、ホスト自身からの接続かどうかを決められないので閉じます
- 比べる範囲:ラボでは、縛ったインタフェースにある別のアドレスを接続元に選んだ接続が縛りを通ることと、縛ったインタフェースの外にあるホストのアドレスを接続元に選んだ接続が、帯の内側のアドレスでも縛りで届かないことを確かめた。
  それでも比べる範囲を縛ったインタフェースのアドレスに限らず、ホストのすべてのアドレスにします。
  ループバックを通る接続をどのインタフェースから届いたものとみなすかは、カーネルの内部の扱いだからです
- ログ:閉じた接続は、帯の外の接続元と同じく、最初の 1 件だけをログに書きます

縛りはインタフェースの番号に付くので、tailscaled の再起動や更新でインタフェースが同じ名前とアドレスで作り直されると、待ち受けは消えた番号に縛られたまま残り、tailnet の側から届かなくなる。
`vpsd` はこれを次のように見張る(2026-09-25)。

- 見張りの方式:2 秒ごとに、縛ったインタフェースを名前で引き、番号が縛ったときと同じか、検出したアドレスをまだ持つかを確かめる。
  インタフェースが消えたとき、番号が変わったとき、アドレスを失ったときは、待ち受けを閉じます。
  リンクの変更の通知は使いません。
  カーネルの backend がすでに購読しているが、ユーザー空間モードにはありません。
  `vpsd` 自身が購読すると、購読が途切れたときの張り直しを含めて、2 秒の遅れを縮めるためだけの仕組みが増える
- 開き直し:閉じている間は、見張りのたびに、縛っていた名前のインタフェースか `tailscale` で始まる名前のインタフェースが `100.64.0.0/10` のアドレスを持つかを確かめる。
  持てば、起動時と同じ検出(`tailscale status --json`、無ければインタフェース)で tailnet のアドレスを選び直し、同じ縛りと接続元の検査で開き直す。
  見込みの無い間は `tailscale status --json` を起こさない。
  見込みがあるのに開き直しの試みが続けて失敗する間、たとえば `tailscale status --json` がどのインタフェースも持たないアドレスを返し続ける間は、次の試みまでの間隔を失敗のたびに倍にし、30 秒で止めます。
  このため `tailscale status --json` を起こす頻度は、失敗が続く間は 30 秒に 1 回までに下がる。
  待ち受けを閉じたときと、見込みが無くなったときに、間隔を 2 秒に戻します。
  開いている間の見張りは常に 2 秒ごとで、`tailscale status --json` を起こさない閉じている間は、公開の側からもどこからも届かない。
  インタフェースが戻る前に開き直すことはありません
- tailnet のアドレスが変わった場合:再ログインなどで tailnet のアドレスが変わると、古いアドレスはインタフェースから消えるので、見張りは待ち受けを閉じ、選び直した新しいアドレスで開き直す。
  `Host` の許可リストの tailnet の IP と MagicDNS 名は、選び直した値に差し替え、古い IP と名前は許可しません。
  検出が `tailscale status --json` の失敗でインタフェースに落ちた場合は、MagicDNS 名が分かりません。
  この場合、選び直したアドレスが前と同じなら前の MagicDNS 名を保ち、違うなら前の名前を外す。
  前の名前を外すと、待ち受けが戻った後も wgft を再起動するまで名前で開けなくなるためです。
  `tailscale status --json` が答えた場合は、名前が空でもその答えに従います。
  `--admin-host` で加えた名前はそのまま残る。
  起動時に tailnet のアドレスが見つからず待ち受けを開かなかった場合は、見張りを始めない。
  この場合は従来どおり警告だけを出す
- 古い待ち受けと新しい待ち受け:開き直しは古い待ち受けを閉じてから新しい待ち受けを開きます。
  同じ goroutine が順に行うので、2 つが同時に開くことはありません。
  見張りが閉じた待ち受けの応答の終わりは、`vpsd` を止める誤りにしません。
  見張りが閉じたのではない終わりは、従来どおり `vpsd` を止めます
- 接続中の要求:閉じるのは待ち受けだけで、受け付け済みの接続は閉じない。
  接続はそのまま応答を続け、相手に届かなくなった接続は上の TCP の期限で切れる
- ログ:閉じたときと開き直したときに 1 行ずつ書きます。
  閉じている間の検出や開き直しの失敗は、直前と同じ理由なら繰り返し書きません

TCP で開いた管理用 API(`--admin` のループバック、`--admin-tailscale`)には ReadHeaderTimeout・ReadTimeout・WriteTimeout・IdleTimeout を付ける。
管理用 API の応答はどれも束縛されている(JSON はバッチの本文の上限、書き出しはルール一覧、読み込みの確認は importMaxBytes・importApplyMaxBytes に収まる)ので、WriteTimeout を付けても中断しません。
Unix ソケットには期限を付けない。
相手はすでに「VPS の root」か「SSH でその root に入れる人」に限られる境界の内側だからです。

管理用 API が破られると VPS を任意の自宅ホストへの中継器にできるため、エージェント用 API より守る優先度が高い。
その守りは独自の認証ではなく、すでに信頼している境界(VPS の root、SSH、tailnet)に置く。
以前の管理者パスワード(Basic 認証)は、ハッシュが root の読める SQLite にある以上 root には効かず、ブラウザは Basic 認証の資格情報を他サイト発のリクエストにも自動で付けるため CSRF にも効かなかった。
守れていたのは「VPS 上の root でないプロセスからループバックへの到達」だけで、それは Unix ソケットのパーミッションで代えられる。
