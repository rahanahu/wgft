<a id="8-接続元-ip-の扱い"></a>
## 接続元 IP の扱い

サービスから見た接続元は、VPS 側の masquerade のため、利用者の IP にはなりません。
ユーザー空間モードでは自宅側の中継のため、常にエージェントのアドレスになります。
カーネルモードでは、LAN の別のホストのサービスからは MASQUERADE の後のエージェントのホストの LAN のアドレスに、ホスト自身のサービスからは VPS のトンネルアドレス(`10.200.0.1`)に見える([7b.2 節](kernel-agent/targets.md#7b2-宛先の扱い))。
接続元 IP を使いたい処理は、実 IP が見える VPS 側で行います。

- 拒否と許可:[5.3 節](control/rules.md#53-ルールのスキーマ)の `source_deny` と `source_allow`
- レート制限:[5.3 節](control/rules.md#53-ルールのスキーマ)の `new_flow_rate`、`packet_rate`、`per_source_rate`
- TCP で自宅側のアプリケーションに元 IP を渡したい場合:`vps_mode = proxy` と `proxy_protocol = true`。
  受け側が PROXY protocol に対応している必要があります

UDP で自宅側のサービスに元 IP を渡す機能は持ちません。
実現には VPS 側と自宅側の両方で masquerade をやめ、サービスのホストで応答を wgft0 へ戻す経路を設定する必要があり、v1.2 の範囲の外にあるためです。

送信元を偽装した UDP は L4 では区別できません。
ルール全体の上限(`new_flow_rate`、エージェントのセッション上限)で VPS、トンネル、エージェントを守る以外にない。
上限いっぱいの偽装フラッドが続けばエージェントのセッション表が埋まり、正規の新規参加が止まります。
既存のセッションは、`new_flow_rate` と `per_source_rate` では影響を受けない。
`packet_rate` は全パケットに効くので、帯域を守る代わりに正規の既存セッションも巻き込む。
これは UDP サービス一般の限界で、このツールの守備範囲はここまでとします。

<a id="9-状態の保存と再起動"></a>
## 状態の保存と再起動

`vpsd` 側:

- SQLite 1 ファイルにエージェント、ルール、登録トークンのハッシュ、世代、自己署名証明書と秘密鍵、wg0 のサーバ秘密鍵、累積カウンタ、窃取検知の警告と確認済みの組([5.2 節](control/connection.md#52-全体状態の配信とハートビート))を保存します
- SQLite の本体は、所有者だけが読み書きできる 0600 で作る。
  サーバ秘密鍵と証明書の秘密鍵を含むためです。
  既存の本体と WAL の補助ファイル(`-wal`、`-shm`)にグループかその他の権限があれば、起動時にその権限だけを外す。
  所有者の権限は変えないので、0644 は 0600 になり、管理者が 0400 にしたファイルは 0400 のまま残る。
  `wgft server check` は各ファイルの権限を表示するが、データベースを読み取り専用で開き、権限、内容、スキーマの版を変えません
- `vpsd` は起動時に、サーバのデータベースを開く前に、隣のロックファイル(`wgft.sqlite.lock`)に flock をかける。
  取れなければ二重起動として終了コード 1 で終わる([11b 節](security/startup.md#11b-起動の失敗の意味論))。
  データベースを開く前に取るのは、ロックを持つ撤去([10.3 節](operations/setup.md#103-運用の流れ))や別の `vpsd` がある間に、データベースを作ることもスキーマを上げることもしないためである(2026-10-03、所有者の決定)。
  以前はデータベースを開いてスキーマを上げてからロックを取っていました。
  このため、撤去が `--purge` でデータベースを消した後に、ロックを取れずに終わる `vpsd` が空のデータベースを作って残しえた。
  この筋書きはコードから判断したもので、ラボでは再現していません。
  ロックを取った後は、取ったファイルが今もロックファイルのパスの指すファイルかを、記述子の fstat とパスの lstat で比べる。
  違えば閉じて開き直す。
  撤去の `--purge` がロックファイルを消してからロックを放す([10.3 節](operations/setup.md#103-運用の流れ))ので、消される前に古いファイルを開いた `vpsd` が放された後にロックを取ると、誰も守らない消されたファイルのロックを持つことになるためです。
  この照合はエージェントのロック(`agent.json.lock`)にも同じく効く。
  この筋書きはコードから判断したもので、照合は単体試験だけで確かめた
- SQLite を開く接続は、busy_timeout を journal_mode の変更や foreign_keys の設定より先に効かせる(`modernc.org/sqlite` の DSN パラメータ `_busy_timeout`・`_journal_mode`・`_foreign_keys` を使い、この 3 つを別々の `PRAGMA` 文で順に送らない)。
  ただし、journal_mode を初めて WAL に切り替える 1 手だけは、busy_timeout を先に効かせても SQLite 自身がリトライしません。
  再起動やバイナリの入れ替え、`wgft server teardown`、CLI の一操作など、他のプロセスがファイルを数ミリ秒だけ保持している瞬間にこの接続確立がぶつかると、待たずに `SQLITE_BUSY`(`database is locked`)で失敗していた(改訂の記録 2026-09-20)。
  この 1 手だけは `Open` が `SQLITE_BUSY` を検出して自前で最大 5 秒待ち直す
- 新しい版が書いた SQLite(`PRAGMA user_version` がこの版の移行の数より大きい)は、この版では読めないので起動を拒否します。
  運用者がその新しい版を入れ直すか、この版で取った控えを戻すまで同じ結果になるので、種別 `prerequisite` の拒否として終了コード 3 で止まる([11b 節](security/startup.md#11b-起動の失敗の意味論))
- 設定のうち「変えるのに片付けが要る、または保存値と矛盾しうるもの」は初回起動で SQLite に記録し、以後は起動のたびに設定の値と照合します。
  対象は動作モード(`kernel`。
  `userspace` は [13 節](roadmap.md#制限と未実装の提案))と wg のアドレス帯。
  アドレス帯が食い違えば、エージェントの割り当てアドレスと矛盾するので起動を拒否し、変えるには `teardown --purge` と再登録が要ると案内します。
  モードが食い違えば切り替えの関門(旧モードの残骸の有無)を通し、通れば記録を書き換えて起動します。
  記録の無い既存の SQLite は `kernel` とみなして記録します。
  設定の渡し方(`WGFT_*` の環境変数、その dotenv、フラグ、優先順位、出所の印字)の規則は [11a 節](security/configuration.md#11a-設定の渡し方)に定める
- 起動時に、既存の wg0 と `wgft` テーブルがあれば SQLite と突き合わせて差分だけを直す。
  突き合わせの対象はピア集合だけでなく、wg0 の秘密鍵、アドレス、MTU、待ち受けポートも含む。
  停止時にはどちらも削除しません。
  ユーザー空間モード([6.3 節](vps/userspace.md#63-ユーザー空間モード))にはカーネルに残るものが無く、`vpsd` を止めると転送も止まります
- ただし wg0 は、**`vpsd` が作ったインタフェースだけを収束対象にする**。
  nft テーブルは名前 `wgft` で隔離できるが、wg インタフェースは同名なら誰のものでも同じ netlink 操作が通るので、隔離は「名前」ではなく「鍵」でしか作れない。
  起動時、既存の同名インタフェースの現在の秘密鍵を SQLite のサーバ秘密鍵と比べ、**一致する場合だけ収束させる**。
  この比較は `LinkByName` の直後、アドレス・MTU・鍵・ピアを書き換えるより前に行う(後で読むと、他人のインタフェースを一部書き換えてから気づくことになる)
- 鍵が一致しなければ、他人の WireGuard(例:先に上がった別の `wg-quick@wg0`)とみなし、**何も書き換えずに起動を中止する**。
  エラーには「`--wg-interface` で別名を使う」「相手の unit を無効化する」「意図的に引き継ぐなら `--adopt-existing`」を示し、収束するはずだった差分もドライランで出す。
  `--adopt-existing`(既定 false)のときだけ従来どおり収束させ、その際 `vpsd` が鍵を自分のものに書き換えるので、以後の起動は一致します。
  この中止の終了コードは 1 であり、unit の再起動に任せる([11b 節](security/startup.md#11b-起動の失敗の意味論))。
  相手のインタフェースが消えれば次の起動で収束できるので、再起動を止めると衝突が消えた後も転送が戻らないためです
- SQLite を失った場合(バックアップからの復元、`/var/lib/wgft` の削除)は、自分が作ったインタフェースでもサーバ鍵が変わって一致しなくなるため中止します。
  復元経路として `--adopt-existing` で引き継ぐ
- 起動時に、既存の他の WireGuard インタフェースと `--wg-port`・`--wg-address` の衝突を検査します。
  `wgctrl` の `Devices()` で全 WireGuard の待ち受けポートを列挙し、`--wg-port` が既に使われていれば(そのまま起動しても `ConfigureDevice` が `EADDRINUSE` で失敗する)中止します。
  WireGuard 以外のプロセスが同じ UDP ポートを bind している場合も、`/proc/net/udp` で検出してインタフェースを作る前に中止する(作ってから失敗すると半端な状態が残る)。
  作った直後に後段の設定で失敗した場合は、作ったインタフェースを消してから中止します。
  `--wg-address` の `/24` が既存インタフェースのアドレスや経路と重なる場合も、経路の衝突に加え [6.1 節](vps/kernel.md#61-カーネルモード)の conntrack 収束が他人の DNAT 済みフローを消しうるので中止します。
  この 3 つの中止はどれも終了コード 1 であり、所有判定による中止と同じ理由で unit の再起動に任せる([11b 節](security/startup.md#11b-起動の失敗の意味論))
- カーネルモードが要求するのは、カーネルの WireGuard モジュール(Linux 5.6 から本体に含まれる)と `nft` コマンドです。
  `wireguard-tools`(`wg`、`wg-quick`)は要りません。
  `vpsd` は netlink でカーネルを直接操作し、これらのコマンドを実行しません。
  カーネルが wireguard のリンク種別を知らない場合(独自の最小カーネル、コンテナ型の VPS など)、インタフェースの作成は `EOPNOTSUPP` で失敗します。
  `LinkAdd` 自体がモジュールの自動ロードを試した後なので再起動では現れず、運用者がモジュールを入れるか別のカーネルで起動するまで同じ結果になります。
  原因とユーザー空間モード([6.3 節](vps/userspace.md#63-ユーザー空間モード))への案内を出し、種別 `prerequisite` の拒否として終了コード 3 で止まる([11b 節](security/startup.md#11b-起動の失敗の意味論))
- カーネルモードは `root` か `CAP_NET_ADMIN` を要求します。
  起動時に権限そのものを確かめることはせず(環境を見て推測しない、[11a 節](security/configuration.md#11a-設定の渡し方))、インタフェースの作成やその後の差分の書き込みという実際の netlink・wgctrl の書き込みが `EPERM`/`EACCES` で返ってきた時点で判定します。
  プロセスの権限は実行の時点で決まり、同じ unit は毎回同じ権限で実行するので、この失敗は再起動では変わりません。
  WireGuard モジュールが無い場合と同じ種別 `prerequisite` の拒否とし、`root` かその権限で動かすこと、または `WGFT_MODE=userspace`(権限を要らない)への案内を出して終了コード 3 で止まる([11b 節](security/startup.md#11b-起動の失敗の意味論))
- `vpsd` は起動時に conntrack の UDP タイムアウト 2 値(`nf_conntrack_udp_timeout`、`nf_conntrack_udp_timeout_stream`。
  [4 節](network.md#4-ネットワーク))を読むが、この読み取りは `table inet wgft` を適用した**後**に行います。
  このテーブルは `ct` 式を持つため、適用の netlink 書き込みが、`nft` コマンドで同じテーブルを書いたときと同じく、カーネルに `nf_conntrack`(と `nft_ct`、`nf_nat`)を初めて自動ロードさせる。
  適用より前に読むと、他に何もこのモジュールをロードしないホスト(新規インストール、モジュール状態を毎起動で失うホスト)でこの読み取りが失敗し、カーネルモードの起動そのものが止まっていた(改訂の記録 2026-09-20)。
  テーブルの適用後もなおこの sysctl が読めない場合(この sysctl 自体が無いカーネル、読む権限が無いなど)は、終了コード 1 で終わり、unit の再起動に任せる。
  適用の後に読めないことが永続する環境は実機でもラボでも見ていない一方で、別の network namespace への登録やコンテナの `/proc/sys` の隠蔽のように、再起動で変わりうる原因を否定できません。
  [11b 節](security/startup.md#11b-起動の失敗の意味論)の非対称の規則により、示せない失敗は終了コード 1 とします。
  この時点ではテーブルの適用が済んでいるので、再起動の間もカーネルモードの転送は続く。
  `wgft server check` はテーブルを何も適用しないため、この値を起動前には表示できません。
  カーネルモードの `server check` は、読めない場合をこの理由とともに示し、まだ起動していないだけであって問題ではないと明記します
- 起動時の最初のルールの適用が失敗した場合は、終了せずに管理用 API だけを開き、適用を試し直しながら起動の残りを止める(起動の保留。
  [11b 節](security/startup.md#11b-起動の失敗の意味論))。
  conntrack の UDP タイムアウトの読み取り、エージェント用 API の待ち受け、起動完了の行は、適用が成功してからです。
  適用できない宣言を記録に残せる以上([7a.3 節](architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))、起動の失敗で管理用 API まで閉じると、運用者がその宣言を直す経路が無くなるためです
- ピアの公開鍵の正本はエージェント側にあり、SQLite の値はそのコピーです。
  stream 接続時にエージェントの宣言で更新する([5.2 節](control/connection.md#52-全体状態の配信とハートビート))
- VPS 再起動で wg0 が消えたときは、SQLite のサーバ秘密鍵で作り直す。
  公開鍵が変わらないので、エージェント側は再接続だけで復旧します
- 手作業で変更されたピアやルールは、起動時の突き合わせで SQLite の値に戻します。
  ピアの公開鍵については、その後の stream 再接続でエージェントの宣言値により再度上書きされる。
  ただしこの「戻す」は自分のインタフェース内の変更(ピア・アドレス・MTU・待ち受けポート)に限る。
  wg0 の秘密鍵そのものを手で変えられた場合だけは、上の所有判定で別人のインタフェースと区別できないため、戻さずに起動を中止する(許容する後退)

エージェント側:

- 状態ファイル 1 つに `{name, endpoint, cert_sha256, permanent_token, used_join_token_sha256, wg_private_key, last_state}` を保存します。
  `name` は登録の応答で確定した名前、`last_state` は最後に処理した全体状態、`used_join_token_sha256` は使用済み登録トークンのハッシュ([5.1 節](control/registration.md#51-登録)の復帰経路で使う)
- 起動時は状態ファイルの鍵と `last_state` でトンネルとリスナーを先に立て、その後 stream に接続します。
  `vpsd` が停止中でも、VPS 側にピアが残っていれば転送は復旧します
- カーネルモード([7b 節](agent-kernel.md#7b-データプレーン自宅側カーネルモード))では、状態ファイル `agent.json` にモード、`ip_forward` を 0 から 1 に変えた事実と日時、1 つ前の wg の秘密鍵、直近の公開の結果と、conntrack の収束が済んでいない前の公開の列([7b.4 節](kernel-agent/lifecycle.md#7b4-収束と停止))も保存します。
  直近の公開の結果は、ルールごとに、公開したポートと DNAT に書いた宛先、または公開しなかった理由を持ち、テーブルの公開に成功するたびに書き換える。
  エージェントが止まっている間の `agent doctor` が、残っているテーブルと比べるために使う([10.2c 節](diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))。
  1 つ前の鍵は次に鍵を変えるまで残し、停止中の `rotate-key` も消す鍵を 1 つ前の鍵として移す([7b.4 節](kernel-agent/lifecycle.md#7b4-収束と停止))。
  モードは起動のたびに設定と照合する([11a 節](security/configuration.md#11a-設定の渡し方))。
  モードの記録が無い `agent.json` は、ユーザー空間モードの記録とみなす。
  停止しても wgft0 と `table inet wgft_agent` を残し、起動時は wgft0 の所有を判定してから `last_state` へ収束させる
- 状態ファイルには、登録で割り当てられたトンネルのアドレスの記録 `tunnel_address` も保存する([7b.1 節](kernel-agent/installation.md#7b1-カーネルに置くもの))。
  値は帯の長さまでの形か、登録の応答から記録したアドレスだけの形です。
  アドレスだけの記録は、最初に適用できた全体状態で帯の長さまでの形になります。
  記録の無いファイルでは、最初に適用できた全体状態の値を記録します。
  記録を置き換えるのは登録のし直しだけです。
  カーネルモードのエージェントは、記録と違う `wg.address` の全体状態を拒みます。
  モードによらず記録し、撤去は記録を消さない
- wg 鍵対は状態ファイルにないときだけ生成します。
  鍵を作り直したいときは `agent rotate-key` を使います。
  エージェントが稼働中なら、`rotate-key` は Unix ソケット経由で稼働中プロセスに指示し、プロセス自身が鍵を作り直して stream を張り直す。
  停止中なら状態ファイルの鍵と `last_state` を直接消す。
  稼働中のファイルは flock で保護されているので、外から書き換えない。
  稼働の判定は、ロックファイルを作らない `Inspect`([10.2c 節](diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))で行います。
  ロックファイルがあって誰も持っていなければ、停止中の書き換えも flock を取ってから行い、取れなければ稼働中として制御ソケットへ指示します。
  判定の後に起動したエージェントが書いた記録を、古い内容で上書きしないためです。
  既にあるロックファイルを開くだけなので、持ち主は変わりません。
  ロックファイルが無ければ、flock を取らずに書き換える。
  判定の時点でそのパスのロックを持つエージェントはおらず、取ろうとするとロックファイルを呼び出し元の権限で作ってしまい、非特権で動くエージェントの起動を塞ぐためです。
  バックアップからの戻し、ホストの移し替え、運用者がロックファイルを消した後が、この場合に当たる。
  判定の直後にエージェントが起動してロックファイルを作り、状態ファイルを書いた場合は、`rotate-key` の書き換えがその内容を古い内容で上書きし得ます。
  この狭い隙間は許容します。
  起こるのはこの 3 つの場合の後の最初の起動だけで、失われた項目はエージェントの次の保存が書き戻します
- 状態ファイルを書く CLI は、停止中の `rotate-key` と `agent pubkey` です。
  稼働中のエージェントは状態ファイルの中身をメモリの上に持ち、保存のたびに全体を書き直す。
  CLI が稼働中のエージェントの状態ファイルを外から書くと、エージェントが書いた新しい内容を CLI が読んだ古い内容で上書きし得ます。
  CLI の変更も、エージェントの次の保存で消える。
  そこで、状態ファイルを書く CLI は稼働の判定とロックの扱いを停止中の `rotate-key` とそろえ、稼働中なら書きません。
  `agent pubkey` は、エージェントが止まっていて鍵が無ければ、鍵を作って保存します。
  ロックファイルがあって誰も持っていなければ、flock を取ってから読み、書き終えるまで持ちます。
  取れなければ稼働中として扱う。
  ロックファイルが無ければ、`rotate-key` と同じ理由で flock を取らずに書きます。
  `agent pubkey` では、`rotate-key` の 3 つの場合に加えて、一度も起動していないデータディレクトリもロックファイルが無い場合に当たる。
  判定の直後にエージェントが起動すると、`agent pubkey` の書き込みがエージェントの書いた内容を古い内容で上書きし、印字する鍵がエージェントの使う鍵と食い違いうる。
  この狭い隙間も許容します。
  起こるのはこれらの場合の後の最初の起動だけで、上書きされた項目はエージェントの次の保存が書き戻します。
  稼働中なら、状態ファイルの鍵を読むだけで書きません。
  稼働中のエージェントは起動の途中で鍵を作って保存し、稼働中の `rotate-key` でも新しい鍵を保存してから使うので、保存済みの鍵はエージェントが使う鍵です。
  別のプロセスがロックを持っていて状態ファイルに鍵がまだ無ければ、状態ファイルがまだ無い場合も含めて、鍵を作らずに失敗し、少し後に実行し直すよう案内します。
  ロックの持ち主は、起動の途中で鍵をまだ保存していないエージェントのほか、停止中に書いている別の CLI でもありうる。
  案内は稼働中のエージェントと言い切らず、データディレクトリを別のプロセスが使っていると述べる。
  停止中にロックファイルがあるとき、`agent pubkey` と停止中の `rotate-key` は保存のためにロックを短い間持ちます。
  その間に起動したエージェントは `credentials file is in use by another process` で終わる。
  同梱の systemd の unit は終了コード 1 で再起動するが、端末から起動した `agent run` は止まったままで、launchd は間隔を空けて再起動します。
  以前の `agent pubkey` はロックを取らなかったので起動を妨げず、この性質は `agent pubkey` については運用者から見える変化です
- 状態ファイルは一時ファイルに書いて rename し、パーミッションは 0600。
  全体状態のたびに書き換わるので、途中でクラッシュしても壊れないようにします。
  Windows では 0600 相当の chmod がファイルの ACL には効かないため、別途の保護を [11a 節](security/configuration.md#11a-設定の渡し方)に定める
- 一時ファイルは状態ファイルと同じディレクトリに、`.wgft-credentials-` で始まる乱数の名前で作る。
  書き込みから rename までの間にプロセスが強制終了されると(`kill -9`、停電、コンテナの強制停止)、一時ファイルは wg の秘密鍵と恒久トークンを含んだまま残る。
  エージェントは起動時に状態ファイルの flock を取った後、そのディレクトリの直下にある `.wgft-credentials-` で始まる通常ファイルだけを消す。
  再帰はせず、symlink は辿らず、名前の合うディレクトリと symlink は消さない。
  消した件数を 1 行のログに出す。
  消せないファイルがあれば、その件数と最初の誤りの種類を 1 行の警告に出し、起動を続けます。
  ディレクトリを読めなければ、残りの有無を確かめられなかったことを 1 行の警告に出し、起動を続けます。
  どのログにも一時ファイルのパスと中身は出さない。
  flock の下で消すのは、flock を持つ別のプロセスが保存している途中の一時ファイルを消さないためです。
  flock を取らずに保存する書き手もあります。
  ロックファイルの無いデータディレクトリでの `wgft agent pubkey` と停止中の `rotate-key` です。
  この書き手の保存の途中に起動時の片付けが重なると、Unix では、その書き手の rename が失敗してコマンドは誤りを返します。
  Windows では、書き手が一時ファイルを共有を許さずに開いている間は片付けの削除が失敗して警告になり、書き手の rename は成功します。
  書き手が一時ファイルを閉じてから rename するまでの間に重なった場合だけ、書き手の rename が失敗します。
  Windows の向きはコードから推したもので、実機では確かめていません。
  どちらの OS でも状態ファイルは壊れない。
  この向きの失敗は許容します。
  片付けは起動時だけに行います
- root のプロセスが状態ファイルを書き換えるときは、元のファイルの持ち主とグループを新しいファイルに移す(2026-09-24)。
  同梱の unit はエージェントを `User=wgft` で動かすので、root で実行した停止中の `rotate-key` や撤去([10.3 節](operations/setup.md#103-運用の流れ))が持ち主を root に変えると、エージェントは次の起動で状態ファイルを読めなくなる。
  持ち主を移せなければ警告を出し、保存は続けます。
  root で常駐するエージェントも同じ保存を使うので、移せないことを保存の失敗にすると、全体状態や鍵を保存できなくなるためです。
  Windows では行いません
- 一時ファイルのパーミッションと持ち主は、名前ではなく、作った一時ファイルの記述子に対して設定する(2026-09-25、所有者の決定)。
  移す持ち主は、置き換える前の状態ファイルを symlink を辿らない `lstat` で読みます。
  置き換える前の状態ファイルが通常のファイルでなければ、何も書かずに拒みます。
  データディレクトリはエージェントの利用者の持ち物であり、その利用者は書き込みの途中で一時ファイルの名前を別のファイルへの symlink に差し替えられる。
  名前で `chmod` と `chown` を行うと、root の保存が差し替え先のパーミッションと持ち主を変えてしまう([11 節](security/admin-transport.md#11-セキュリティ))
- 状態ファイルとロックファイル(`agent.json.lock`)は、最後の要素が symlink でも辿らず、開いた記述子で種別を確かめ、通常のファイルでなければ拒む(2026-09-25、所有者の決定)。
  Unix では、FIFO を開く時点で止まらないよう非ブロックで開きます。
  状態ファイルは、大きさの上限を超えれば読まずに拒み、上限を超える中身は書かずに拒むので、wgft が書いたファイルを wgft が読めなくなることはありません。
  上限は、エージェントが書きうる状態ファイルの大きさの見積もりを上回る値にします。
  見積もりは、`last_state` が収まる制御ストリームの 1 通の上限と、並ぶ公開の記録の数(直近の公開と、収束が済んでいない前の公開の列の上限の数。
  [7b.4 節](kernel-agent/lifecycle.md#7b4-収束と停止))から、ルールごとに DNAT の範囲を 1 つ持つ公開について求めます。
  値はコードの定数に置き、この見積もりを上回ることを単体テストが確かめる。
  見積もりの外が 2 つあります。
  1 つは、宛先の許可一覧が範囲のルールを多数の DNAT の範囲に分ける場合です。
  もう 1 つは、公開しなかった理由の文言で、許可一覧の拒否は解決したアドレスをすべて並べるので、名前の解決の結果の数とともに長くなる。
  後者は wgft の定数からは上限を決められないので、見積もりを範囲の総数で抑える形に直しても外に残る。
  この 2 つを見積もりに含めず、除外として明記します。
  上限に届くには、並外れた数のルール、範囲を細かく分ける許可一覧、多数のアドレスを返す名前のどれかに、conntrack の収束が失敗し続けて公開の記録が列の上限まで並ぶことが重なる必要があります。
  届いた場合も保存が誤りとして報告され、ディスクの状態ファイルは上限の内の直前の内容のまま読める。
  上限を見積もりの外まで広げると、上限の役目である、乗っ取られたエージェントの利用者が作る疎なファイルから root の CLI を守る効果が薄れる。
  この規則は、エージェント自身の読み書き、root で実行する CLI、`agent doctor` のどれにも効く。
  サーバのロックファイルも同じ `internal/flock` で開くので、同じ規則に従います。
  データディレクトリそのものが symlink であることは妨げない
- 起動時に状態ファイルに flock をかけ、取れなければ二重起動として終了します
- 鍵を状態ファイルに置く理由は、恒久トークンと同じディスクにある以上、鍵を分けても守れる範囲が変わらず、一方で `vpsd` 不在時の可用性が上がるためです
