## 11. セキュリティ

管理用 API と Web UI の待ち受け先は `--admin` で選ぶ。独自のパスワードは持たない。ユーザー空間モード(6.3 節)では、転送対象の公開ポートで `vpsd` の Go のコードがインターネットに直接さらされる。カーネルモードではその面はカーネルの DNAT だけで、`vpsd` 自身が受けるのはエージェント用 API とプロキシモードのポートに限られる。

- Unix ソケット(既定 `unix:///run/wgft/admin.sock`、0600。systemd の unit では `vpsd` の実行利用者が所有し、置き場のディレクトリは 0700 なので、開けるのは root と `vpsd` 自身だけ):VPS 上の CLI は root で直接叩く。手元のブラウザからは SSH のポート転送でソケットを引く(10.3 節)。到達できるのは「VPS の root」と「SSH でその root に入れる人」だけで、どちらも SQLite と wg の鍵を読める立場なので、パスワードを足しても守れる範囲は広がらない
- `--admin-tailscale`:加えて Tailscale のアドレスでも待ち受ける。起動時にまず `tailscale status --json` を実行し、`Self.TailscaleIPs` の最初の IPv4 アドレスと `Self.DNSName`(MagicDNS 名)を使う。`tailscale` コマンドが PATH にない、または失敗したときは、名前が `tailscale` で始まるインタフェース(Linux 版 Tailscale の既定は `tailscale0`)にある `100.64.0.0/10` のアドレスを使う。`100.64.0.0/10` は Tailscale 専用の帯ではなく VPS 事業者が内部網に使っていることがあるため、この帯を持つだけの他のインタフェースは使わない。検出した MagicDNS 名は `Host` の許可リストに自動で加わり、`--admin-host` は追加の名前のためだけに使う。認証、TLS、総当たり対策を Tailscale に任せられ、`vpsd` 側に追加の実装が要らないので、外から触りたい場合はこれを推奨する。tailnet が落ちても SSH で代替できる。VPS 自身からの接続はこの待ち受けに届かず、VPS 上の管理は Unix ソケットで行う。この待ち受けの到達の境界は後述の「tailnet の待ち受けの閉じ方」と「ホスト自身からの接続の拒否」による
- TCP(`--admin 127.0.0.1:8686` など):Unix ソケットの転送に対応しない SSH クライアントや、ラボ向けに残す。ループバック以外の TCP アドレスに開いた場合、`vpsd` は起動ログに警告を出すだけで止めない
- `public`:インターネットに公開する。ACME による正規の TLS 証明書、パスキーか TOTP、ログイン試行のレート制限、セッション期限と CSRF 対策を `vpsd` に実装したうえでなければ選べない。v1 では実装しない(13 節)

Unix ソケットの作り方(2026-09-30)。ソケットのパスに対する操作は、どれも symlink を辿らない。起動のときにパスにあるものがソケットなら、前の起動が残したものとして消す。ソケットでないもの(誤って指したデータベースのファイルや symlink など)は、symlink の先がソケットであっても消さず、起動の誤りにする。ソケットは umask を 0177 に狭めて作る。bind は 0777 から umask を除いた権限でソケットを作るので、ソケットは作った瞬間から 0600 であり、パスへの chmod はしない。作った直後に、パスにあるものが 0600 のソケットであることを確かめ、違えばパスにあるものを消さずに起動の誤りにする。置き場のディレクトリが既にあって他の利用者が書き込め、sticky ビットも無い場合は、起動ログに警告する。起動は止めない。このディレクトリでは、その利用者が作った後のソケットを消して別のものに差し替えられ、CLI とブラウザの接続は差し替えた先に届く。作った直後の確認で見つかるのは、確認より前の差し替えだけである。

tailnet の待ち受けの閉じ方(2026-09-25、所有者の決定)。`--admin-tailscale` の待ち受けは、tailnet のアドレスに bind するだけでは tailnet に閉じない。Linux は、宛先がホスト自身のアドレスであれば、どのインタフェースから届いたパケットも受け取る。このため、事業者の網で隣り合うホストが VPS の tailnet のアドレス宛ての経路を持てば、公開のインタフェースから管理用 API に届く。`Host` の許可リストには `localhost` と tailnet の IP が入っているので、`Host` の検査はこの到達を止めない。`vpsd` はこの待ち受けを次の 2 つで tailnet に閉じる。

- インタフェースへの縛り:待ち受けのソケットを、検出したアドレスを持つインタフェースの番号(ifindex)に `SO_BINDTOIFINDEX` で縛る。他のインタフェースから届いた接続の要求は、待ち受けが無いものとして RST で拒まれる。起動の時点で、検出したアドレスを持つインタフェースが無い場合と、縛れない場合は、待ち受けを開かずに起動の誤りとする。`net.ipv4.ip_nonlocal_bind` が 1 のホストでは、ローカルに無いアドレスへの bind が通り、縛る先の無い待ち受けになるためである。名前ではなく番号で縛るのは、見つけたインタフェースが縛るまでの間に作り直された場合に、後述の見張りが覚えた番号と縛り先を食い違わせないためである。インタフェースへの縛りは Linux 5.7 以降は特権なしで設定できるので、カーネル 6.1 以上を対象とする wgft では、非特権で動くユーザー空間モードの `vpsd` でも使える
- 接続元の検査:受け付けた接続の接続元が Tailscale の割り当ての帯に無ければ、HTTP を読まずに閉じる。`Host` の検査より前の段である。帯は IPv4 の `100.64.0.0/10` と IPv6 の `fd7a:115c:a1e0::/48` で、Tailscale のソースの `net/tsaddr` にある `CGNATRange` と `TailscaleULARange` に合わせた。IPv4 を写した IPv6 の形は IPv4 に戻してから比べる。閉じた接続は、接続を繰り返すだけでログを溢れさせられないよう、最初の 1 件だけをログに書く

主の守りはインタフェースへの縛りで、接続元の検査は縛りが効かない場合の二重の守りである。接続元の検査だけでは、`100.64.0.0/10` を内部網に使う事業者の網の隣人を区別できない。Tailscale 自身のファイアウォールの規則(`ts-input`)は、Tailscale のソースの `util/linuxfw` によれば、tailscale0 以外から届いた `100.64.0.0/10` の送信元を落とすが、それ以外の送信元は宛先が tailnet のアドレスでも落とさない。Tailscale の規則が無い構成、たとえば netfilter の管理を切った tailscaled では、`100.64.0.0/10` の送信元を持つ隣人を接続元の検査だけでは止められない。tailscale0 から届く接続でも、送信元を書き換えずに転送するサブネットルータを経た LAN のアドレスからの接続は、接続元の検査で閉じる。

ホスト自身からの接続の拒否(2026-10-02、所有者の決定)。`--admin-tailscale` の待ち受けは、接続元がホスト自身のアドレスである接続を、帯の内側のアドレスであっても HTTP を読まずに閉じる。VPS 上での管理は、管理用 API の Unix ソケット(0600)が受け持つ。tailnet の待ち受けは、tailnet の他の端末から管理するための入口である。ホスト自身から tailnet のアドレスへの接続はループバックを通り、接続元は既定で宛先と同じ tailnet のアドレスになる。このため、この接続はインタフェースへの縛りも接続元の検査も通る。

- 判定の方法:受け付けた接続の接続元を、まず接続の宛先のアドレスと比べ、次にホストのすべてのインタフェースのアドレスと比べる。どちらかと同じなら閉じる。ホストのアドレスは、宛先と一致しなかった接続ごとに読み直すので、起動の後に加わったアドレスも比べる対象に入る。IPv4 を写した IPv6 の形は IPv4 に戻してから比べる。ホストのアドレスを読めなかった場合は、ホスト自身からの接続かどうかを決められないので閉じる
- 比べる範囲:ラボでは、縛ったインタフェースにある別のアドレスを接続元に選んだ接続が縛りを通ることと、縛ったインタフェースの外にあるホストのアドレスを接続元に選んだ接続が、帯の内側のアドレスでも縛りで届かないことを確かめた。それでも比べる範囲を縛ったインタフェースのアドレスに限らず、ホストのすべてのアドレスにする。ループバックを通る接続をどのインタフェースから届いたものとみなすかは、カーネルの内部の扱いだからである
- ログ:閉じた接続は、帯の外の接続元と同じく、最初の 1 件だけをログに書く

縛りはインタフェースの番号に付くので、tailscaled の再起動や更新でインタフェースが同じ名前とアドレスで作り直されると、待ち受けは消えた番号に縛られたまま残り、tailnet の側から届かなくなる。`vpsd` はこれを次のように見張る(2026-09-25)。

- 見張りの方式:2 秒ごとに、縛ったインタフェースを名前で引き、番号が縛ったときと同じか、検出したアドレスをまだ持つかを確かめる。インタフェースが消えたとき、番号が変わったとき、アドレスを失ったときは、待ち受けを閉じる。リンクの変更の通知は使わない。カーネルの backend がすでに購読しているが、ユーザー空間モードには無い。`vpsd` 自身が購読すると、購読が途切れたときの張り直しを含めて、2 秒の遅れを縮めるためだけの仕組みが増える
- 開き直し:閉じている間は、見張りのたびに、縛っていた名前のインタフェースか `tailscale` で始まる名前のインタフェースが `100.64.0.0/10` のアドレスを持つかを確かめる。持てば、起動時と同じ検出(`tailscale status --json`、無ければインタフェース)で tailnet のアドレスを選び直し、同じ縛りと接続元の検査で開き直す。見込みの無い間は `tailscale status --json` を起こさない。見込みがあるのに開き直しの試みが続けて失敗する間、たとえば `tailscale status --json` がどのインタフェースも持たないアドレスを返し続ける間は、次の試みまでの間隔を失敗のたびに倍にし、30 秒で止める。このため `tailscale status --json` を起こす頻度は、失敗が続く間は 30 秒に 1 回までに下がる。待ち受けを閉じたときと、見込みが無くなったときに、間隔を 2 秒に戻す。開いている間の見張りは常に 2 秒ごとで、`tailscale status --json` を起こさない閉じている間は、公開の側からもどこからも届かない。インタフェースが戻る前に開き直すことはない
- tailnet のアドレスが変わった場合:再ログインなどで tailnet のアドレスが変わると、古いアドレスはインタフェースから消えるので、見張りは待ち受けを閉じ、選び直した新しいアドレスで開き直す。`Host` の許可リストの tailnet の IP と MagicDNS 名は、選び直した値に差し替え、古い IP と名前は許可しない。検出が `tailscale status --json` の失敗でインタフェースに落ちた場合は、MagicDNS 名が分からない。この場合、選び直したアドレスが前と同じなら前の MagicDNS 名を保ち、違うなら前の名前を外す。前の名前を外すと、待ち受けが戻った後も wgft を再起動するまで名前で開けなくなるためである。`tailscale status --json` が答えた場合は、名前が空でもその答えに従う。`--admin-host` で加えた名前はそのまま残る。起動時に tailnet のアドレスが見つからず待ち受けを開かなかった場合は、見張りを始めない。この場合は従来どおり警告だけを出す
- 古い待ち受けと新しい待ち受け:開き直しは古い待ち受けを閉じてから新しい待ち受けを開く。同じ goroutine が順に行うので、2 つが同時に開くことはない。見張りが閉じた待ち受けの応答の終わりは、`vpsd` を止める誤りにしない。見張りが閉じたのではない終わりは、従来どおり `vpsd` を止める
- 接続中の要求:閉じるのは待ち受けだけで、受け付け済みの接続は閉じない。接続はそのまま応答を続け、相手に届かなくなった接続は上の TCP の期限で切れる
- ログ:閉じたときと開き直したときに 1 行ずつ書く。閉じている間の検出や開き直しの失敗は、直前と同じ理由なら繰り返し書かない

TCP で開いた管理用 API(`--admin` のループバック、`--admin-tailscale`)には ReadHeaderTimeout・ReadTimeout・WriteTimeout・IdleTimeout を付ける。管理用 API の応答はどれも束縛されている(JSON はバッチの本文の上限、書き出しはルール一覧、読み込みの確認は importMaxBytes・importApplyMaxBytes に収まる)ので、WriteTimeout を付けても中断しない。Unix ソケットには期限を付けない。相手はすでに「VPS の root」か「SSH でその root に入れる人」に限られる境界の内側だからである。

管理用 API が破られると VPS を任意の自宅ホストへの中継器にできるため、エージェント用 API より守る優先度が高い。
その守りは独自の認証ではなく、すでに信頼している境界(VPS の root、SSH、tailnet)に置く。
以前の管理者パスワード(Basic 認証)は、ハッシュが root の読める SQLite にある以上 root には効かず、ブラウザは Basic 認証の資格情報を他サイト発のリクエストにも自動で付けるため CSRF にも効かなかった。守れていたのは「VPS 上の root でないプロセスからループバックへの到達」だけで、それは Unix ソケットのパーミッションで代えられる。

ブラウザ経路の守りは、パスワードの代わりに次の 2 つで行う。CLI は影響を受けない。

- `Host` の検査:`localhost`、`127.0.0.1`、`[::1]`、`--admin-tailscale` で検出した自分の tailnet 名と IP、`--admin-host` で追加した名前、以外の `Host` を持つリクエストを拒否する。攻撃者のドメインを `127.0.0.1` に向ける DNS リバインディングは、ここで `Host` が合わずに落ちる
- 他オリジン発の変更の拒否:`GET` と `HEAD` 以外のリクエストで、`Sec-Fetch-Site` が `same-origin` でも `none` でもないもの、または `Origin` のホストが上の許可リストにないものを拒否する。CLI はどちらのヘッダも送らないので通る。Web UI のフォーム送信は同一オリジンなので通る
- 応答のヘッダ:Web UI と JSON のどちらの応答にも `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer` を付ける。`Content-Security-Policy` はテンプレートが実際に読み込むものだけを許す(`default-src 'self'` で自オリジンの `/static/app.js` と `/static/styles.css` を許し、インラインの `style` 属性のために `style-src` にだけ `'unsafe-inline'` を足す。画像・フォント・外部ドメインの読み込みは無いので、他はすべて `'self'` の範囲で足りる)。`/static/` 以外の応答には `Cache-Control: no-store` も付け、接続文字列などが載る画面がブラウザやプロキシのキャッシュに残らないようにする

- エージェント用 API は公開するが、登録と stream のエンドポイントしか持たず、認証は登録トークンか恒久トークンだけである。トークンの生成、保存、比較、試行制限は 5.1 節のとおり
- エージェント用 API は TLS 1.2 以上、HTTP/1.1 だけで応じる。通信は登録の POST と WebSocket だけなので、HTTP/2 は ALPN で広告しない。鍵交換の曲線は固定せず Go の既定に従う。既定には耐量子のハイブリッド鍵交換が含まれ、固定するとそれが外れるためである
- エージェント用 API は同時接続数を固定の上限(4096)で抑える。数百台のエージェントが 1 本ずつ stream(WebSocket)を張っても十分な余裕がある値であり、11a 節の設定項目にはしない。上限に達した接続は accept を待つだけで、拒否や RST にはせず、すでに動いている stream を切ることもない
- エージェント用 API は、認証を通っていない接続の数を、全体と送信元の段ごとに固定の上限で抑える。全体の上限は 1024 本で、同時接続数の上限(4096)の内側に置く。送信元の段と上限は、IPv4 のアドレスか IPv6 の /64 に 16 本、IPv6 の /56 に 64 本、IPv6 の /48 に 256 本である。どれかの上限に達した接続は、TLS のハンドシェイクの前に閉じる。認証を通っていない接続は、TLS のハンドシェイクの途中の接続、登録の要求、恒久トークンの確認の前の stream の要求である。stream は恒久トークンの確認を通り、エージェントごとの確立前の数(下記)に入れたところで、送信元と全体の未認証の数から外れる。この数に入れられなかった 3 本目は 429 で断られ、未認証の数に残ったまま閉じる。同じ NAT やプレフィクスの後ろにいるエージェントの台数は、これらの未認証の上限に縛られない。上限は 11a 節の設定項目にはしない
- 送信元の段は、1 人が安く持てるアドレスのまとまりに合わせる。IPv6 を /64 だけで数えると、/56(/64 が 256 個)を持つ 1 人が 256 × 16 本を持てるためである。/56 は家庭の回線に、/48 は拠点やトンネルのサービスに払い出される大きさなので、/56 には /64 の 4 つ分、/48 には /56 の 4 つ分を置き、1 つの /48 が持てるのは全体の上限の 4 分の 1 までとした。IPv4 には /24 のような段を置かない。IPv4 のアドレスは 1 人が安く多数を持てず、/24 で数えると同じ範囲から払い出される CGNAT の後ろの正規のエージェントを巻き込むためである。同じ理由で、1 つの IPv4 のアドレスの上限も 16 のまま変えない。下げれば全体の上限を埋めるのに要るアドレスの数は増えるが、CGNAT の後ろで同じアドレスを共有する正規のエージェントの同時の再接続が上限に当たりやすくなる(2026-10-01、所有者の決定)
- 全体の上限は、認証を通っていない接続が持つメモリを抑え(7 節)、同時接続数の上限の残りを認証を通った stream に残す。この上限を埋めるには、IPv4 のアドレスなら 64 個、IPv6 なら /48 が 4 つ要る。全体の上限を置く前に同時接続数の上限を埋めるには IPv4 のアドレスが 256 個要ったので、IPv4 での必要な数は減った。多数の送信元から全体の上限を埋める攻撃は、以前と同じくこれらの上限では防げず、その間は新しい登録と stream の再接続が止まる。既存の転送は止まらない
- 既定の待ち受けの `0.0.0.0:8443` は、IPv4 と IPv6 の両方に応じる。Go は、ホストを指定しないアドレスを、IPv6 を使えるホストでは IPv4 射影を許す IPv6 のソケットで開くためである。IPv4 の相手は、IPv4 射影のアドレスで届いても IPv4 のアドレスとして数える。待ち受けを IPv4 だけに変えることはしない。`WGFT_AGENT_API` の意味が変わるためである(7a.11 節)
- 認証を通っていない接続が読みの期限で枠を持つのは最長 15 秒である。TLS のハンドシェイクの期限は 5 秒で、ハンドシェイクの後はリクエスト全体を 10 秒で読み終える必要があり、この 15 秒は 2 つの期限の和である。Go の HTTP のサーバはハンドシェイクの期限にヘッダの期限を使うので、ヘッダの期限を 5 秒にしてある。この 15 秒は読みの期限だけで、読み終えた後の枠の保持は含まない。登録の要求では、正しい登録トークンの登録のようなハンドラの処理の間と、応答を返した後に Go の net/http が行う書き込み側の半クローズと最長 500 ミリ秒の待ち(`closeWriteAndWait`)の間も、接続は未認証の枠に残る。エージェントは TCP の接続の直後にハンドシェイクを始め、ヘッダと 4 KiB 以下の登録の本文をその直後に送る。ハンドシェイクは往復 1 回か 2 回で終わるので、往復に 1 秒かかる回線でも期限に収まると推測している。遅い実回線では未確認である
- 恒久トークンの確認を通って最初のメッセージを待つ stream は、接続を確立するまで、エージェントごとに 2 本までである。3 本目は 429 で断り、未認証の接続のまま閉じる。最初のメッセージの期限と大きさの上限は 5.2 節にある。この上限が無いと、恒久トークンを 1 つ持つ者は、送信元の上限から外れた確立の前の stream を送信元を替えて多数持ち、1 本ごとに読みかけのメッセージのメモリを持たせられる。2 本にするのは、半開きの 1 本が期限を待つ間も、つなぎ直しの 1 本が通るためである
- 旧接続を置き換えた stream は、旧接続の閉じる処理が終わるまで、前項の枠を返さない(5.2 節)。置き換えられた旧接続の読み手は、読みかけのメッセージを持ったまま、閉じる処理の期限まで残りうる。WebSocket のライブラリの close の期限は約 5 秒で、close のフレームの書き込みが詰まると最長約 10 秒になる。TLS の接続では、接続を閉じるときの close_notify の書き込みにも 5 秒の期限があり、送信のバッファが詰まっていれば閉じる処理はその分も延びうる。この延びはコードを読んだ推定であり、再現は未確認である。置き換えた時点で枠を返すと、恒久トークンの持ち主は、ハートビートを途中まで送って止めた stream を新しい stream で置き換える操作を繰り返し、閉じる途中の stream をエージェントごとの数の上限なく積める。枠で数えるので、置き換えられて閉じる途中の stream は、1 つのエージェントにつき 2 本までである。正規の再接続は、置き換えた時点で確立して全体状態を受け取り、旧接続を待たない。確立の前の stream と閉じる途中の stream が合わせて 2 本ある間は、次の試みは 429 で断られる。閉じる途中の旧接続が 1 本なら確立の前の 1 本までは通り、2 本なら次の試みがすぐに断られる。エージェントは 429 を一時的な拒否として扱い、通常のバックオフで再接続する(5.2 節)
- 恒久トークンの持ち主は、公開鍵を変える宣言で、カーネルモードの `vpsd` に `table inet wgft` を差し替えさせられる。秘密鍵は要らない。差し替えは全エージェントのルールの meter と `ct count` の状態を作り直し、同じ送信元は差し替えのたびに上限 1 つ分多くのフローを保持できる(6.1 節)。2 つの鍵を交互に宣言すると、保存している鍵と同じ鍵の省略は効かない。`vpsd` は鍵の変更を登録ごとの頻度の上限(5.2 節)で抑え、鍵の変更で他のエージェントへ全体状態を配り直さない。上限の内側の変更による差し替えと、それによる全エージェントの状態の作り直しは残る。ユーザー空間モードの `vpsd` では、鍵の変更は Admission Policy の評価器の状態を作り直さない(7a.4 節)。送信元ごとのレートの状態が残ることはラボで確かめ、送信元ごとの同時フロー数が残ることはコードから判断した
- エージェント用 API は keep-alive を使わず、応答を返したら接続を閉じる。エージェントは登録と stream の接続のたびに新しい HTTP のクライアントを作るので、応答の後に残した接続は使い直されず、認証を通っていない接続として送信元の枠を占めるだけだからである。WebSocket への切り替えの応答の後の接続(stream)は閉じない
- エージェントは削除できる。削除すると、`vpsd` はそのエージェントの恒久トークンを使えなくし、wg ピア、そのピア宛の conntrack エントリ、進行中の中継を消し、割り当てアドレスを回収する。名前は新しい接続文字列で再利用できる
- wg0 上のピア同士は通信できず、wg0 から VPS 自身への新規接続もできない
- ユーザー空間モードの `vpsd` では、全エージェントのピアが 1 つの netstack を共有する。netstack は転送しないのでピア同士は通信できないが、ICMP の誤りは別のピアと `vpsd` の間のフローを引用できる。TUN の入口は、外側の送信元が引用の宛先と一致しない ICMP の誤りと、next-hop MTU が 552 より小さい Fragmentation Needed を捨てる(7 節の「ICMP の誤りの入口」)。エージェントが自分のフローに誤りを送ることは、MTU の下限を除いて防がない。自分のフローを妨げるだけだからである
- 鍵の置き換えで引き継ぐエンドポイント(5.2 節)は、古い公開鍵で認証されたパケットの送信元である。WireGuard は認証を通ったパケットでしかエンドポイントを変えず、その送信元に移す。この値を動かせるのは、古い秘密鍵の持ち主と、経路上で捕まえた認証済みのパケットを本物より先に届けられる者だけである。古い鍵が盗まれて持ち主が別の場所にいる場合は、引き継いだエンドポイントがその場所を指しうる。その場合も、`vpsd` がそこへ送るのは新しい公開鍵へのハンドシェイクの開始だけである。新しい秘密鍵を持たない相手は応答を作れないのでトンネルは成立せず、WireGuard はハンドシェイクの成立の前に転送のデータを送らないので、転送の中身も渡らない。引き継いだ後のエンドポイントを動かせるのは新しい鍵で認証されたパケットだけなので、古い鍵の持ち主はエンドポイントを自分に留められない。本物のエージェントのハンドシェイクが届いた時点で、エンドポイントは本物の送信元に移る。この場合に転送が戻るのは、引き継ぎの無い場合と同じく、エージェントの送り直しの時点である。古い鍵の持ち主が新たに知るのは、`vpsd` がそのアドレスへハンドシェイクを試みたことだけである。登録の取り消しで回収したアドレスを別のエージェントに割り当て、古いピアの削除が修復(7a.3 節)として残っていた場合も、同じ理由で害は無い。攻撃者が古い鍵でエンドポイントを任意のアドレスに向け、`vpsd` のハンドシェイクの開始をそこへ送らせることは、古いピアに対して今でもできることであり、引き継ぎはこれを広げない
- `vpsd` は転送対象のポート以外を開けない。VPS のファイアウォール設定そのものは扱わない

VPS には、信頼しないローカルの利用者やサービスを置かない前提とする(2026-10-02、所有者の決定)。VPS の上の信頼しないローカルの利用者やサービスは、wgft の脅威の範囲に含めない。既存の権限と鍵の守りは、この前提を理由に緩めず、そのまま保つ。保つ守りは、管理用 API の Unix ソケットを 0600 で作ること(前述)、サーバのデータベースを 0600 で作り、起動時にグループとその他の権限を外すこと(9 節)、同梱の unit が `vpsd` を `DynamicUser=yes` の非特権の利用者で動かすこと(10.3 節)である。

奪われた VPS からエージェントを踏み台にする経路も脅威として扱う。エージェントは `vpsd` が配る `target` へ自分から接続するので、VPS を奪った攻撃者はルールの `target` を `192.168.1.1:22` のような自宅の別のホストに書き換え、自宅の LAN 全体への踏み台に使える。エージェント用 API の認証と証明書のピン留めは `vpsd` になりすます第三者を防ぐだけで、`vpsd` 自身が奪われた場合には効かない。v1 はこの経路を、エージェント側の宛先の許可一覧(7 節の `WGFT_AGENT_ALLOW_TARGETS`)で狭める。一覧はエージェントのホストの設定だけにあり、`vpsd` は一覧の内容を知らず、wire protocol にも現れない。一覧を設定しない既定では制限が無いので、自宅の LAN に転送の宛先以外のホストがある運用では、一覧の設定を勧める。一覧が守るのは宛先の範囲だけであり、一覧の中の宛先に対する不正な転送は防げない。一覧とは別に、エージェントはブロードキャストとマルチキャストの宛先へ転送しない(7 節)。一覧の有無に依らず、1 つのルールで LAN の多数のホストへ届けることと、カーネルモードでホスト自身の待ち受けへ届けることを防ぐ。

エージェントのカーネルモード(7b 節)は、自宅のホストに新しい面を加える(2026-09-24、所有者の決定)。

- 自宅のホストの転送:カーネルモードでは、パケットを LAN へ送るのはエージェントのプロセスではなく自宅のホストのカーネルである。ユーザー空間モードの netstack は宣言したリスナーしか晒さないが、カーネルモードの wgft0 はホストのインタフェースなので、守りの行が無ければ、VPS からトンネルのアドレス(`10.200.0.x`)でホスト自身のサービス(sshd など)や LAN の任意のホストに届く。`table inet wgft_agent` の filter_pre は、wgft0 から入る新しい接続のうち公開したポートのものだけを DNAT の前で通す。forward は、DNAT したフローとその返り以外で wgft0 が絡む転送を落とす。宛先の許可一覧は DNAT を組むときに効くので(7b.2 節)、VPS を奪った攻撃者が `target` を書き換えても、一覧の外へ向かう DNAT は作られない。守りの強さはユーザー空間モードと同じである
- ホスト自身の入力の守り:`table inet wgft_agent` の input は、wgft0 から入る新規の接続のうち DNAT していないものを落とす。6.1 節の VPS の input と同じ考え方である。DNAT した接続は、ホスト自身の LAN のアドレスを宛先に書いたルールの分だけ input を通る
- `ip_forward`:エージェントが 1 にすると、自宅のホストはルータとして振る舞える状態になる。wgft 以外の転送を止めるのは既存のファイアウォールの役目であり、`wgft_agent` の forward は wgft0 が絡む転送にしか触れない。家の LAN の中からこのホストを経由するよう仕向けられたパケットが転送されうる点は、6.1 節の VPS と同じである。影響は利用者向けの文書で説明する
- server から届く値の検証:VPS を奪った攻撃者は、全体状態の値を自由に選べる。カーネルモードのエージェントは、ホストに書く前に、ルールの宛先を宛先の許可一覧で(7b.2 節)、トンネルのアドレスを登録時の記録で(7b.1 節)確かめる。トンネルのアドレスは wgft0 の接続経路としてホストの経路表に入るので、確かめなければ、LAN の帯の一部を覆う帯を配ってホストから LAN へ向かう通信をトンネルへ引き込める。この場合、影響は公開したポートの外へ広がる。記録と違うアドレスの全体状態は、何も書かずに拒む。wg 設定のほかの値は形だけを確かめる。トンネルが立っている間は、形の誤った mtu、keepalive、server の公開鍵も、アドレスと同じく wgft0 とテーブルを残したまま拒み、ハートビートに示す。ユーザー空間モードのトンネルのアドレスは netstack の中にだけあるので、ユーザー空間モードのエージェントは記録と違うアドレスも使う。keepalive と udp_timeout_stream は、ユーザー空間モードのエージェントも形を確かめるが、拒み方が違う。範囲の外の値は拒まず、既定値に置き換えて使う
- テーブルが無い間:`systemctl reload nftables` などで `table inet wgft_agent` だけが消えると、wgft0 と `ip_forward`=1 は残るので、VPS のピアからホスト自身と LAN への通信を止める行が無くなる。この間は、上の 2 つの守りがどちらも効かない。エージェントが稼働中なら 30 秒ごとの収束(7b.4 節)が最長 30 秒で戻すが、停止中は戻らない。この隙間を使えるのは VPS を奪った攻撃者だけであり、`agent doctor` の `dataplane.table` が検出する(10.2c 節)

エージェントの利用者と root の境界も脅威として扱う(2026-09-25、所有者の決定)。同梱の unit はエージェントを `User=wgft` で動かし、データディレクトリはその利用者の持ち物である。エージェントのプロセスが乗っ取られると、攻撃者はデータディレクトリの中の名前を自由に作り、消し、差し替えられる。一方、停止中の `rotate-key`、`agent pubkey`、`agent teardown`、`agent doctor` は root で実行されうる。乗っ取られたエージェントがサービスを動かしたままロックを放すと、管理者が普通に打った `sudo wgft agent rotate-key` は停止中と判断し、root で状態ファイルを書き換える。root がデータディレクトリの中のパスを信頼すると、エージェントの利用者が root の権限を借りられる。例えば root が一時ファイルの持ち主を名前で移すと、書き込みの途中で一時ファイルの名前を root のファイルへの symlink に差し替えられたとき、その先の持ち主がエージェントの利用者に変わる。root がデータディレクトリの中のファイルを symlink も種別も確かめずに開くと、`/dev/zero` への symlink でメモリを使い切り、FIFO で止まり、デバイスを root で開く。

そこで、root はデータディレクトリの中のパスを信頼しない。9 節のとおり、状態ファイルとロックファイルは symlink を辿らずに開いて種別を確かめ、状態ファイルの大きさに上限を置き、一時ファイルのパーミッションと持ち主は記述子に対して設定する。稼働中の `rotate-key` が制御ソケットから読む応答にも大きさの上限を置く。稼働中の `agent doctor` が制御ソケットから読む応答の上限は、この変更では扱わず、別の変更(下記のエージェントが送る文字列の項)で置く。他の操作は、名前を差し替えられても root の権限を貸さない。一時ファイルは既存の名前を開かずに新しく作る。起動時の片付けは symlink を辿らずに名前そのものを消す。rename と一時ファイルの削除は名前を置き換えるか消すだけであり、差し替えられて変わるのは、攻撃者自身が書けるデータディレクトリの中だけである。守るのはデータディレクトリの中の名前であり、データディレクトリまでのパスは root と管理者のものとして信頼する。`/var/lib` のようなデータディレクトリの親は、エージェントの利用者には書けない。

root がデータディレクトリの持ち主の権限に落としてから触る案は採らなかった。Go のプロセスでは利用者の切り替えがプロセス全体に効き、root 以外の実効 uid に切り替えている間は、`agent teardown` が同じプロセスで行う netlink の操作に要る `CAP_NET_ADMIN` も実効の権限から外れる。権限を落としても、FIFO で止まる問題と大きすぎるファイルでメモリを使う問題は残るので、種別と大きさの確認はどちらの案でも要る。

macOS は Unix と同じ実装を使う。推奨の LaunchDaemon(11a 節)はエージェントを利用者の権限で動かすので、同じ境界があり、同じ守りが効く。Windows は持ち主を移さないので、持ち主を変えられる穴は無い。Windows の一時ファイルの DACL は、作った一時ファイルを共有を許さずに開いている間に設定するので、その名前は差し替えられない。状態ファイルとロックファイルは reparse point を辿らずに開いて種別を確かめ、既存のファイルの DACL の締め直し(11a 節)は、削除の共有を許さずに開いている間に行う。締め直しの DACL が許すのは SYSTEM、`BUILTIN\Administrators`、実行者だけであり、エージェントの利用者に権限を与えない。データディレクトリそのものを junction に差し替えられた場合は守らない。Windows で wgft が提供するのは `agent run` を対話利用者の権限で起動する運用だけであり(11a 節)、別の管理者が昇格した CLI をその利用者のデータディレクトリに向ける運用は想定していない。未確認:Windows の各点は Windows の実機では確かめていない。

エージェントが送る文字列を、運用者の端末に対する脅威としても扱う(2026-09-25、所有者の決定)。エージェントは自宅側のホストで動き、そのホストが乗っ取られてエージェントの実行ファイルやプロセスが攻撃者の管理下に入る場合を想定する。ハートビートのトンネルの理由・解決したエンドポイント・ルールごとの状態と理由・ルール ID は、エージェントが選ぶ文字列であり、`vpsd` はこれを 1 MiB の上限だけで受け取っていた。`wgft agent ls`・`rule ls`・`status`・`server doctor` は、これらの文字列を人向けの出力にそのまま出す。ESC で始まる端末の制御文字の並びをこの中に混ぜると、root で実行する運用者の端末の表示を隠したり偽ったりでき、対応する端末では貼り付け用の緩衝やクリップボードへの書き込みも起こしうる。`agent doctor` と `rotate-key` は、稼働中のエージェント自身の制御ソケットの応答と `agent.json` の内容を同じように端末へ出すので、エージェントのプロセスが乗っ取られている場合は同じ脅威が当たる。制御ソケットの応答を読む箇所は、大きさの上限を持たずに読んでいた。

守りは 2 段に分ける。受け口(`vpsd` の stream がハートビートを受け取る所)で、この文字列の長さを切り詰め、表示できない文字を読める形に置き換えてから保存する(5.2 節)。エージェントも送る前に理由に同じ変換をかけるが、これは 1 通の大きさを抑えるためで、この守りには数えない。乗っ取られたエージェントは変換を飛ばせるためである。エージェント側でも、制御ソケットの応答を読む箇所に大きさの上限を置く。表示の側では、`agent ls`・`rule ls`・`status`・`server doctor` の人向けの出力と、エージェント側の `agent doctor`・`rotate-key` の出力が、同じ 1 つの関数(`internal/textsafe.SanitizeForTerminal`)で表示できない文字を無害化してから出す。2 段に分けるのは、受け口の守りが直さない経路(エージェント自身の制御ソケットの応答、受け口の修正より前の版の `vpsd` と話す rolling upgrade の最中)を、表示の側の守りが独立に塞ぐためである。

機械向けの出力への影響は経路によって違う。`agent ls --json`・`rule ls --json` が返す値は、受け口の切り詰めと置き換えの分だけ変わる(7a.11 節)。`agent doctor --json` は制御ソケットの応答が受け口を経由しないので、`internal/textsafe.SanitizeStrings` による無害化がこの応答の文字列のほぼすべてに及び、稼働中のエージェントに対する `agent doctor --json` の `detail`・`next` にも表れる。停止中のエージェントに対する `agent doctor --json`(`agent.json` を直接読む経路)は制御ソケットも受け口も経由しないため、`detail`・`next` を JSON へ写す直前(`agentDoctorJSONOf`)でも同じ関数を掛け、稼働中と停止中のどちらでも同じ守りが及ぶようにする。`status --json`・`server doctor --json` の `detail`・`next`・`internal` は、これらを組み立てる値がすでに受け口で安全になっているので変えていない。いずれの経路でも、`id`・`status`・`reason`・`evidence_unreachable` のような列挙値は判定の側が選ぶ固定の語であり、エージェントの文字列を経由しないので変わらない。`detail`・`next`・`internal` はどの節でも人向けの文であり保証の対象ではない(10.2a・10.2b・10.2c 節、7a.11 節)ので、これらの変更は互換の約束には触れない。

JSON へ書き出すときのエスケープ(`encoding/json` の既定の書式)は、C0 の制御文字と `U+2028`・`U+2029` は `\u00XX` の形で逃がすが、DEL(`U+007F`)や C1 の制御文字(`U+0080`-`U+009F`)は生のまま出す。したがって `--json` の端末での安全さは、値そのものが上記のとおりすでに無害化されていることに支えられており、`encoding/json` 自身のエスケープには支えられていない(2026-09-26、レビューの指摘)。

## 11a. 設定の渡し方

wgft のどのプロセス(`vpsd`、`agent`、CLI)も `WGFT_*` の環境変数で設定を受け取る。ファイルはその dotenv、フラグはその別名であり、優先順位はフラグ、プロセスの環境変数、ファイルの順である。

ファイルの既定の置き場所は `vpsd` と CLI が `/etc/wgft/server.env`、`agent` が `/etc/wgft/agent.env` で、`--config` で変更できる。同じファイルは systemd の読み込み、Docker の `--env-file`、compose の `env_file` の 3 つの経路で扱われ、この 3 者は構文の解釈が一致しないため、3 者で一致する範囲だけの構文を許す。1 行に `KEY=value` を 1 つ書き、行頭の `#` だけをコメントとして扱う。値の途中の `#` は値の一部として扱い、引用符は使わず、値に空白を含めることもできない。引用符で始まる値は警告ではなくエラーにする。3 つの経路それぞれで解釈が異なり、たとえば Docker では引用符ごと 1 つの値として扱われ、黙って認証エラーになるなどの事故につながるためである。この規則の下では、`WGFT_JOIN` の接続文字列(`wgft://host:port/token#sha256:...`)は引用符なしでそのまま書ける。

systemd の unit では `EnvironmentFile=` を使わない。バイナリが既定で同じファイルを自分で読むため不要であり、`EnvironmentFile=` を使うと値の出所がすべて「環境変数」になり、出所付き印字(下記)が意味を失う。

`server.env` には秘密の値を置かない。`vpsd` の設定項目に秘密は無く、サーバ鍵、証明書、トークンはすべて SQLite にある。同梱の unit は `DynamicUser=yes` の非特権の利用者で動く(10.3 節)ため、`server.env` はその利用者が読める 0644 にする。`agent.env` は `WGFT_JOIN` を含むので、root 所有、グループ `wgft` の 0640 にし、固定の `User=wgft` で動く unit から読ませる。ファイルが無い場合はエラーにせず、環境変数と既定値だけで動く。unit に `LoadCredential=` でファイルを渡す方法は採らない。0600 のままでも動くが、`--config` で別の場所を指す必要があり、root の CLI が読む既定の場所と二重になり、起動ログの出所の見え方も変わる。秘密の無いファイルに対しては重いためである。

設定ファイルから読んだ値に秘密(`WGFT_JOIN`)が含まれ、そのファイルが other(このホストの誰からでも)読めるパーミッションのときは、起動時にファイル名と推奨するパーミッションを添えて英語で 1 行だけ警告する。止めはしない。この判定は Unix だけで行い、Windows では行わない(11a 節後段の DACL による別の扱いのため)。group のビットは対象にしない。`agent.env` の推奨である 0640(root 所有、グループ `wgft`)は意図した共有であり、これに対して起動のたびに警告すると、正しく設定した環境でもログが埋まるだけになる。値がファイルではなく環境変数やフラグから来た場合、および `server.env` のように秘密な設定項目を持たないファイルには、パーミッションに関わらず警告しない。

設定の誤りによる起動の失敗は終了コード 3 で止め、直し方をエラーに添える。対象は設定ファイルが読めないこと、その構文の誤り、値の誤り、必須の値の欠落である。値ごとの規則は本節の各項目にあり、終了コードの決め方と、設定以外の原因による起動の失敗の扱いは 11b 節に定める。Docker の `restart: unless-stopped` は終了コードを見ないので、コンテナでは設定の誤りでも再起動を繰り返す。設定ファイルの構文の誤りの文言は、ファイル名と行番号と、名前の形をしたキーだけを示し、行の中身と値を出さない。文言は起動の失敗としてジャーナルに残り、行の中身は `WGFT_JOIN` の接続文字列のような秘密の値を含みうるためである。

起動ログの先頭と `wgft server check` の出力は、有効な設定を値と出所(フラグ、環境変数、ファイル、既定値のいずれか)付きですべて印字する。トークンなど秘密の値は伏せ字にする。

他のプロセス向けの `WGFT_*` はエラーにせず無視する。知らない名前だけでなく、`vpsd` から見た `WGFT_AGENT_ALLOW_TARGETS` のように「知っているが自分には関係ない」名前も対象である。この規則により、同じ Docker イメージや同じ設定ファイルで `agent` と `vpsd` を切り替えて使える。`WGFT_MODE` と `WGFT_WG_INTERFACE` は、`vpsd` とエージェントがどちらも同じ名前で読む(下記)。既定のファイルは `server.env` と `agent.env` に分かれているので、同じファイルを両方に渡す配置でだけ、同じ値が両方に効く。この配置では、今のエージェントが無視している `WGFT_MODE=kernel` が、更新の後はエージェントにも効く。リリースノートはこの挙動の変化を知らせる(7a.11 節)。

同時フロー数のプロセス全体の上限(7 節)は `WGFT_MAX_UDP_FLOWS`(既定 8192)と `WGFT_MAX_TCP_FLOWS`(既定 2048)で、`vpsd` とエージェントの両方が受け取る。値は 16 から 65535 の整数で、範囲外は起動時のエラーにする。メモリの小さいホストで下げるための設定であり、ホストのメモリの量から自動では決めない。ルールごとの上限はこの 2 つから導く値であり、独立した設定項目ではない。

接続元 IP ごとの上限(7 節)は `WGFT_MAX_UDP_FLOWS_PER_SOURCE`(既定 256)と `WGFT_MAX_TCP_FLOWS_PER_SOURCE`(既定 128)で、`vpsd` だけが受け取る。エージェントから見た接続元は常に `10.200.0.1` で接続元ごとに数える意味がないため、エージェントの設定項目には加えない。値は 0 から 65535 の整数で、0 はそのプロトコルの上限を無効にする(プロセス全体の上限と違い、0 は正当な値である)。範囲外や負の値は起動時のエラーにする。プロセス全体の上限と連動して自動で変わることはなく、上げたい場合は明示して設定する。

宛先の許可一覧(7 節)は `WGFT_AGENT_ALLOW_TARGETS` で、エージェントだけが受け取る。値はコンマ区切りの一覧で、各項目は `CIDR`、`CIDR:ポート`、`CIDR:下限-上限` のいずれかである。アドレスだけを書いた項目は `/32` か `/128` として扱う。ポートを書かない項目はそのアドレスの全ポートを許す。IPv6 のアドレスにポートを付ける項目は `[2001:db8::/32]:8080` の形で角括弧で囲む。ポートを書かない IPv6 の項目に角括弧は要らない。項目の前後の空白は無視する。構文の誤りは起動時のエラー(終了コード 3)にする。省略した場合と、値が空白だけの場合は制限せず、`vpsd` が配るどの宛先へも接続する。値があるのに項目が 1 つも無い場合(コンマだけを書いた場合など)は構文の誤りとして起動を止める。守りの設定であり、書いたつもりの一覧が黙って「制限なし」になるより、起動を止めるほうが安全なためである。項目があって 1 つも一致しない一覧は正当な値で、すべての宛先を拒む。IPv4 と IPv6 のどちらのアドレスも書ける。ルールの `target` は v1 では IPv4 とホスト名だけを受け取る(4 節)ので、IPv6 の項目が効くのはホスト名が IPv6 のアドレスに解決される場合である。

データの置き場所は `WGFT_DATA_DIR`(既定 `/var/lib/wgft`)に統一する。この下に `vpsd` は SQLite ファイルを、`agent` は状態ファイルを置く(9 節)。

既定の置き場所は OS ごとに決める。Linux は上のとおりである。Windows は設定ファイルもデータも `%ProgramData%\wgft` に、macOS は `~/Library/Application Support/wgft` に置く。どの OS でも `--config` と `WGFT_DATA_DIR` で変更できる。Linux 以外のバイナリが持つのはエージェントと CLI だけで、`server` サブコマンドは「Linux でしか動かない」と答えて終わる。`vpsd` はカーネルの WireGuard と nftables に依存するためである。ユーザー空間モードのエージェントは wireguard-go と netstack だけで動くので OS を選ばない設計であり(カーネルモードは Linux だけである。7b 節)、Windows は 2026-09-19 に Windows 11(非管理者権限での実行)から実機の VPS に対して確認した。ホームルータの NAT を越えた join string による登録、トンネルの確立、LAN サービスへの UDP と TCP の中継、server の再起動と agent の強制終了からの復帰、2 つ目の `agent run` の拒否、認証情報ファイルの書き換え、稼働中の `rotate-key` が通ったため、Windows 版のエージェントと CLI は Releases に含め、README にも対応として書く。macOS は 2026-09-19 に macOS 27(Apple シリコン、arm64)から、ホームルータの NAT の内側で実機の VPS(v0.3.0、カーネルモード)に対して確認した。join string による登録、トンネルの確立、Mac 自身と LAN の他のホストへの UDP と TCP の中継、Mac の再起動と server の再起動からの復帰、2 つ目の `agent run` の拒否、稼働中の `rotate-key`、データディレクトリ(0700)と `agent.json`・`agent.json.lock`・`agent.json.sock`(0600)の権限が通ったため、macOS 版のエージェントと CLI も Releases に含め、README にも対応として書く。macOS で公開するのは darwin/arm64 だけである。Intel Mac は対象にせず、amd64 の自宅マシンには Linux 版で対応する。

Windows での常駐は、`agent run` をそのときの利用者の権限で起動するところまでを wgft が提供し、サービス、タスクスケジューラ、通知領域への常駐は提供しない。ログオン時の自動起動(スタートアップフォルダへの登録など)は利用者に任せる。Windows のゲームサーバの多くがユーザー権限で動いており、agent も管理者権限を必要としないことに合わせた判断であり、サービス化には Program Files への配置、SYSTEM と対話利用者の間の ACL の取り合い、SCM(サービス制御マネージャ)対応のコードが新たに要ることを理由に見送った。

Windows Defender Firewall は、初回起動時に `wgft.exe` の受信を許可するかどうかのダイアログを表示する。wireguard-go が UDP を `0.0.0.0` で待ち受けるためである。実機では、このダイアログで許可した場合はもちろん、キャンセルして受信拒否の規則が作られた場合でも、agent は外向きの接続しか使わないため、トンネルと中継は WireGuard の鍵の再交換をまたいで動作し続けることを確認した。ダイアログは許可してもキャンセルしてもよい。

未確認の点は、Windows サービスまたは SYSTEM としての実行である。

macOS での常駐には、`UserName` に利用者を指定した LaunchDaemon(`/Library/LaunchDaemons` に置き、システムの launchd が起動するジョブ)を推奨し、その例を `deploy/io.github.rahanahu.wgft.agent.plist` として配る。プロセスは root ではなくその利用者の権限で動き、`WGFT_DATA_DIR` で利用者の `~/Library/Application Support/wgft` を指すので、ターミナルから起動した `agent run` と同じ認証情報ファイルを使う。launchd は `UserName` を持つジョブの環境に `HOME` を設定する(実機で、その利用者のホームディレクトリが入ることを確認した)が、plist の文字列の中の `~` は展開しないため、plist はログのパスを書き下す。`WGFT_DATA_DIR` も明示し、既定の置き場所の解決に依らず、ターミナルから起動した `agent run` と同じディレクトリを LaunchDaemon が使うようにする。plist は root 所有の 0644 で置かれ全員が読めるため、`WGFT_JOIN` を書かない。初回登録は、ターミナルから `WGFT_JOIN` を付けて `agent run` を起動し、登録できたら止めてから LaunchDaemon を読み込む手順とした。launchd には systemd の `RestartPreventExitStatus` に当たる設定が無いため、`KeepAlive` の `SuccessfulExit` を偽にして異常終了と強制終了のときに再起動させ、間隔は `ThrottleInterval` で空ける。設定の誤りで終了コード 3 になった場合も、launchd はこの間隔で再起動を繰り返す(2026-09-21 に実機で確認。60 秒のあいだに 6 回起動し、`launchctl print` は `last exit code = 3` と `state = spawn scheduled` を示した)。systemd の `agent.service` は同じ場合に再起動を止めるので、macOS では設定の誤りに気付く手段がログだけになる。root での実行は必要が無いため試していない。

LaunchAgent(`~/Library/LaunchAgents` に置き、利用者のログインセッションで動くジョブ)は推奨しない。実機では、LaunchAgent として起動した agent はデフォルトゲートウェイには接続できたが、LAN の他のホストへの接続は `connect: no route to host`(`EHOSTUNREACH`)で失敗し、許可を求めるダイアログも出なかった。同じバイナリをターミナルから起動した場合(ターミナルのアプリの許可を引き継ぐ)と、`UserName` 付きの LaunchDaemon として起動した場合は、他のホストへ UDP と TCP で接続できた。この失敗を macOS 15 以降のローカルネットワークのプライバシー保護によるものとするのは症状からの推測であり、システムログには該当する記録が見つからなかった。LaunchAgent を使う `brew services` も同じ問題に当たる可能性があるが、未確認である。macOS 27 の実機では、`/usr/local/bin/wgft` に新しいバイナリを置いた直後の LaunchDaemon の 1 回目の試し接続だけが、LAN の他のホストに対して同じ `no route to host` で失敗し、その後は同じ宛先へ繰り返し接続できた(2026-09-21)。1 回だけ失敗した理由は未確認である。

FileVault を有効にした Mac では、再起動後に LaunchDaemon が起動したのはカーネルの起動時ではなく最初のログインの時点だった。最初のログインまでデータボリュームがロックされたままであるためと推測する。起動した agent は `network is unreachable` で再試行し、その後は自力で接続した。再試行が続く長さは、その Mac のネットワークが上がるまでの時間で決まる。2026-09-19 の確認では十数秒、2026-09-21 の確認では約 60 秒であり、後者は Wi-Fi の接続もログインの後に始まる Mac だった。この制約には対処せず、文書に書くにとどめる。想定する利用者はその Mac で遊び、ゲームサーバもその利用者のセッションで動くため、ログインまで agent が動かないことによる不都合は小さい。`fdesetup authrestart` は試していないため、手順として勧めない。

macOS のバイナリは Apple の公証を受けない。ブラウザで取得したファイルには隔離の属性が付き、Gatekeeper は隔離の属性を持つ公証の無いバイナリの起動を止めるため、README とセットアップガイドは `curl` での取得を案内する。`curl` で取得したファイルに隔離の属性が付かないことは確認したが、ブラウザで取得した場合の挙動は試していない。

macOS のエージェントのメモリ使用量は、同時フロー数の上限(既定の UDP 8192、TCP 2048)まで UDP のセッションと無通信の TCP の接続を保持した状態で、Linux のエージェントと同じく 7 節のソフト上限(216 MiB)を下回った(改訂の記録 2026-09-19)。この結果はその条件での測定であり、ソフト上限はメモリの上限ではない(7 節)。同じ測定では、上限を超える TCP の接続のフラッドで、macOS と Linux のどちらのエージェントもソフト上限を大きく超えた。原因は拒んだ接続が netstack の TIME_WAIT に残ることであり、拒否を RST で終える形に直した(7 節、改訂の記録 2026-09-19)。直した効果は、Linux のエージェントのラボで生きているヒープを測って確かめた。macOS のエージェントでは未確認である。macOS の `ps` の RSS は負荷が止んだ後も高いまま残るので、macOS でのメモリ使用量は物理フットプリント(`footprint`)で見る。

macOS の未確認の点は、保持していた TCP の接続の一部が相手側から閉じられた原因(改訂の記録 2026-09-19)、FileVault を無効にした Mac でログインせずに起動時から動くかどうか、ログアウト後も動き続けるかどうか、darwin/amd64、Homebrew での配布である。この閉鎖は、コンテナを使う試験環境で、トンネルを通る多数の UDP のセッションと同時に TCP の接続を張っている間だけ起き、張り終えた後には起きなかった。その一部は試験の宛先の listen キューの溢れによるもので、残りは試験環境の UDP のポート転送によるものと推測している。

二重起動を止める排他ロック(9 節)は、Unix では `flock`、Windows では `LockFileEx` で取り、どちらもファイルを閉じるかプロセスが終わると消える。

Windows の `%ProgramData%\wgft` は、既定では親ディレクトリから `BUILTIN\Users` の読み取りと実行を継承する。状態ファイルの `Chmod(0o600)` は Windows では読み取り専用属性の切り替えにしかならず、この継承を止めないため、`agent.json` を PC の他の利用者が読める状態のまま残しうる。`agent.json.lock` と `agent.json.sock` は秘密を持たないが、同じ継承を受ける。agent はこれを、データディレクトリ全体ではなく、自分が書く 3 つのファイルだけを対象に締める。`WGFT_DATA_DIR` は利用者が任意の場所を指せる設定であり、ディレクトリそのものや直下の無関係なファイルまで毎起動で書き換えると、管理者が意図して加えた ACL(バックアップ用アカウントへの読み取りなど)を消しかねず、Unix の `MkdirAll` が既存のディレクトリを chmod しない設計とも食い違うためである。`agent.json` は `Save` が一時ファイルを作る瞬間に、SYSTEM・`BUILTIN\Administrators`・実行中プロセスの利用者の 3 者だけにフルアクセスを許す保護 DACL(継承を切ったもの)を付けて作る(Windows の `CreateFile` に `SECURITY_ATTRIBUTES` として渡す)。作ってから付け直すのでは、付け直すまでの間その一時ファイルが親ディレクトリから継承した緩い ACL のままになり、Windows はハンドルを開く瞬間にしかアクセス可否を見ないため、その間に別の利用者がハンドルを開けてしまえば後から DACL を締めてもその接続は取り消せない。同じディレクトリ内での rename はこの DACL をそのまま持ち越すので、緩い ACL の期間は生じない。緩い ACL の下で既に作られている `agent.json` は、起動時に読むたびに同じ DACL を単独で付け直して締める。Windows 11 の実機で見つかった環境がこれに当たる。`agent.json.lock` は `Acquire` が開く・作るたびに、`agent.json.sock` は制御ソケットを開くたびに、同じ DACL を単独で付け直す。データディレクトリ自体は、agent が新規に作った場合だけ同じ DACL(継承可能な形)を付けて作り、既に存在するディレクトリは変更しない。DACL を付け直せない場合(所有者でも Administrators でもない利用者で実行した場合など)は、その処理(読み込み・保存・ロック取得)を失敗として扱い起動を止める。制御ソケットだけは、開けない場合と同じく `rotate-key` の稼働中経路だけを諦め、agent 自体は動き続ける。9 節の SQLite の権限の扱い(グループとその他の権限だけを外し、それ以外は変えない)と同じ、変更を対象自身に限る考え方である。

制御ソケットには、agent.json の一時ファイルとは違い、緩い ACL のままの短い期間が残る。`Listen` がソケットのファイルを作った瞬間から `SecureSocket` で締め直すまでの間、親ディレクトリから継承した緩い ACL のままであり、この期間に接続した相手はその後の締め直しでは切断されない。この期間を完全になくすには、専用のディレクトリを起動のたびに新規に作って先に締め、その中でだけソケットを開く必要があるが、制御ソケットが受け付けるコマンドは `rotate-key` の 1 つだけで、応答も新しい公開鍵かエラー文言のみであり秘密は一切やり取りしない。この期間に接続された最悪の場合でも、利用者の意図しない鍵の作り直し(次のハンドシェイクから新しい鍵になるだけ)にとどまり、恒久トークンや wg 秘密鍵の漏えいには至らない。この非対称性から、この期間はなくさず既知の制約として残す。

制御ソケットのパスには長さの上限がある。Unix ソケットのアドレスは `sockaddr_un` の `sun_path` に収めるため、終端の NUL を除いて Linux と Windows では 107 バイト、macOS では 103 バイトまでしか使えない。パスは `WGFT_DATA_DIR` に `agent.json.sock` を付けたものなので、深いデータディレクトリを指すと上限を超える。超えた場合、Go の `net` は OS を呼ぶ前に `invalid argument` を返す。agent は制御ソケットを開けない他の場合と同じく `rotate-key` の稼働中経路だけを諦めて動き続け、ログにはパスのバイト数と上限、短いデータディレクトリを使うという対処を添える。稼働中の agent に向けた `rotate-key` も同じ原因で接続できないので、同じ説明を添える。ソケットを別の短い場所へ移すことはしない。制御ソケットが認証情報ファイルの隣にあることは、`rotate-key` が稼働中の agent を見つける唯一の手掛かりだからである。

この既存ファイルの締め直しは Windows だけで行う。Unix では `Chmod(0o600)` で足りるので、既存ファイルの締め直しは行わない。既存の `agent.json`・`agent.json.lock` を起動のたびに 0600 へ揃え直すと、管理者が意図して 0400 のように絞った権限を緩めてしまい、9 節の「余分な権限だけを外し、それ以外は変えない」という原則に反する。さらに、agent を非特権で動かす構成(`deploy/agent.compose.yaml` の `cap_drop: [ALL]` など)でボリューム上のファイルを所有していない場合、chmod は `EPERM` で失敗し、起動できなくなる。したがって、既存ファイルの締め直しと、制御ソケットを開けない場合に `rotate-key` の稼働中経路だけを諦める扱いは、Windows に限る。`Save` の一時ファイルへの `Chmod(0o600)` は失敗を呼び出し元に伝え、Unix の挙動は Windows の対応によって変えない。

SYSTEM と対話ユーザーの関係は次のとおりである。DACL は毎回そのときの実行者を含めて作り直すため、agent を Windows サービスとして SYSTEM で動かす場合は、SYSTEM 自身の項目が常に含まれるので読み書きできる。対話ユーザーによる実行では、UAC の昇格を伴わない管理者アカウントのトークンは `BUILTIN\Administrators` が拒否専用(deny-only)になり、このグループへの許可が効かないため、直前にそのファイルを書いた本人(同じ SID)でなければ読み書きできない。したがって、SYSTEM のサービス実行と対話ユーザーの実行を交互に行き来する運用では、最後に書き込んだ側と異なる非昇格の利用者は読み書きできず、昇格した管理者(「管理者として実行」)か SYSTEM だけが例外的に読める。wgft は Windows サービスや常駐の仕組みを持たず、`agent run` を対話利用者の権限で起動する運用だけを提供する方針とした(本節前段)ため、SYSTEM でのサービス実行と対話利用者の実行を行き来する運用そのものが生じない設計である。対話利用者どうしの間での UAC の昇格の有無によるこの挙動は上記のとおり成り立つが、SYSTEM としての実行との組み合わせは実機で確かめていない。

設定と状態の線引きは、「変えるのに片付けが要る、または保存済みの値と矛盾しうるもの」を状態として SQLite に置き、それ以外を設定としてファイルに置く、という基準による。エンドポイントやポート、MTU などは編集して再起動すれば変わる設定であり、サーバ鍵、証明書、ルール、エージェントの情報は状態である。動作モード(`WGFT_MODE`)と wg のアドレス帯(`WGFT_WG_ADDRESS`)は値そのものは設定だが、初回起動時に SQLite へ記録し、以後は起動のたびに env の値と照合するという扱いを受ける。どちらも変えると片付けが要る、または保存済みの値と矛盾しうるためである。設定を状態として持たない理由は、人がファイルとして読め、構成管理に置け、SQLite が壊れても復旧できる状態を保つためである。

`WGFT_MODE` は初回の起動で必須である。初回に省略すると、`kernel` か `userspace` かを指定するよう求めて起動を止め、環境を見て推測することはしない。初回に指定した値は SQLite に記録する。2 回目以降に省略した場合は、記録したモードで起動する。指定した場合は記録と照合し、一致すれば通常どおり起動する。食い違った場合は関門を通し、通れば記録を書き換えて起動し、通らなければ起動を拒否する。関門の中身は次のとおりである。`kernel` から `userspace` へ切り替えるときは、wg インタフェースと `table inet wgft` の残骸が無いことを確かめる。残骸があれば、先に `teardown` するよう案内して拒否する。残骸の有無を確かめるには `CAP_NET_ADMIN` が要るため、確かめられない環境では「確認できない」と警告したうえで、wireguard-go の UDP bind を試みる。この bind がカーネル側の `wgft0` に既に使われているポートと衝突して失敗した場合は、残骸の疑いとして host 上での `teardown` を案内する。`userspace` から `kernel` へ切り替えるときは残骸が生じないため、そのまま通す。モードの記録が無い既存の SQLite は、これまで `kernel` しか存在しなかったことから `kernel` とみなして記録する。`wgft server teardown` はモードの記録に触れない。切り替えの判断は起動時の照合と関門だけで完結する。

エージェントも `WGFT_MODE`(`--mode`)を読む(2026-09-24、所有者の決定)。7a.6 節が `WGFT_MODE` を server と agent 全体の転送方式(`DataplaneMode`)の外部名と定めているので、エージェント専用の名前は作らない。値は `userspace` か `kernel` で、それ以外は入口で種別 `config` の拒否にする(11b 節)。扱いは `vpsd` と次の点で違う。

- 既定:省略すると `userspace` である。`kernel` は明示したときだけ選ばれる。初回の必須にはしない。既存のエージェントはモードの記録を持たず、既定を今の動作と同じ `userspace` にすれば推測にならないためである。モードの記録が無い `agent.json` は `userspace` の記録とみなす(9 節)。`WGFT_MODE` を渡していない配置は、設定を変えずにそのまま動く
- 記録と照合:モードは状態ファイル `agent.json` に記録し、起動のたびに設定と照合する(9 節)。`agent.json` の内部の形は 7a.11 節の保証の外なので、項目の追加は自由である
- 切り替えの関門:`userspace` から `kernel` への切り替えは残骸を生まないので、そのまま通す。`kernel` から `userspace` への切り替えは、カーネルモードの残骸が残っていれば種別 `mode-gate` で拒否し、先に `wgft agent teardown`(10.3 節)を実行するよう案内する。残骸は、鍵の一致する WireGuard インタフェース、`table inet wgft_agent`、`agent.json` のカーネルモードの記録である。ユーザー空間モードのエージェントは `CAP_NET_ADMIN` を持たずテーブルを読めないので、関門は記録を根拠に判定する。ホストを再起動した後は記録だけが残骸として残り、`wgft agent teardown` がそれを消す(10.3 節)。記録が無いのに同じ名前の WireGuard のリンクがある場合は、拒否せずに警告を出す形を取りうるが、未確認である。`WGFT_MODE` を省略した起動も `userspace` への切り替えに当たるので、同じく拒否する。この拒否の文面は、`WGFT_MODE=kernel` を設定してカーネルモードを続ける道と、撤去してから切り替える道の両方を示す。関門で止まる起動は `agent.json` に何も書かない。`kernel` への切り替えは、7b.5 節の前提の検査を通った後、鍵を作るよりも、登録よりも、カーネルに何かを書くよりも前に記録を書き換える。途中で落ちても、関門が残骸を見落とさないためである。前提で止まる起動も `agent.json` に何も書かない。記録がカーネルモードで、カーネルに wgft の資源が何も無い場合も、関門は記録を根拠に拒否し、撤去は `CAP_NET_ADMIN` を要する(2026-09-25)。ユーザー空間モードのエージェントも、`CAP_NET_ADMIN` を持たない撤去も、テーブルを読めず、何も作られていないことを示せないためである。`agent.json` の中身から何も作られていないと推す判定は、公開の記録を保存する前に落ちた場合や、`WGFT_WG_INTERFACE` を変える前の名前に残ったインタフェースを見落とす。前提の検査を記録より前に置いたので、この状態が生じるのは、前提を通った起動が最初の書き込みの前に止まった場合と、ホストの再起動の後である。前者を起こした配置は、権限の誤り以外の理由で検査を通った場合を除き `CAP_NET_ADMIN` を持つので、同じ権限で撤去できる。除かれる場合の例は、`RestrictAddressFamilies` から `AF_NETLINK` を外した unit である。検査の 2 つの読み出しがどちらも権限の誤りではない誤りで失敗するので、権限が無くても検査を通り、登録と記録の後に最初の収束で止まる。この unit を書いた運用者は root を持つので、root で撤去できる。ユーザー空間モードのエージェントはモードの記録を書かないので、その `agent.json` は旧い版と同じ形のまま残る。記録が `kernel` でも `userspace` でもない値なら、状態ファイルと設定の矛盾として種別 `conflict` で拒否する。撤去もこの記録を消さずに止まるので(10.3 節)、文面は、記録を書いた版で起動する道と、状態ファイルを控えから戻す道を示す
- 旧い版への戻し:旧い版のエージェントは `agent.json` の知らない項目を保存し直さない(7a.11 節)ので、カーネルモードから旧い版へ戻すと記録が消え、wgft0 とテーブルだけが残る。リリースノートは、カーネルモードから旧い版へ戻す前に `wgft agent teardown` を実行するよう知らせる
- Linux だけ:Windows と macOS で `kernel` を指定すると、種別 `prerequisite` の拒否として終了コード 3 で止まる(11b 節)
- 同時フロー数の上限:カーネルモードでは使わない旨を起動時に 1 行出し、拒否にはしない(7b.1 節)

wg のアドレス帯(`WGFT_WG_ADDRESS`、既定 `10.200.0.1/24`)も初回起動時に記録し、以後は env の値と照合する。省略した場合は既定値を照合の対象にするので、省略しても起動は止まらない。記録済みの値と食い違えば、エージェントの割り当てアドレスと矛盾するため起動を拒否し、変えるには `wgft server teardown --purge` と全エージェントの再登録が要ると案内する。

インタフェース名(`WGFT_WG_INTERFACE`、既定 `wgft0`)は記録しないが、変更すると旧インタフェースが鍵ごと残ることがあるため、`wgft server check` と起動時に、自分のサーバ鍵を持つ別名の WireGuard デバイスが無いかを検査し、あれば警告する。エージェントも `WGFT_WG_INTERFACE`(`--wg-interface`、既定 `wgft0`)を読み、カーネルモードのインタフェース名に使う。ユーザー空間モードでは使わない。同じホストの同じ network namespace で `vpsd` とエージェントがどちらもカーネルモードで既定名を使うと名前が衝突するが、鍵による所有の判定(9・7b 節)が相手のインタフェースに触れずに止めるので、安全側に倒れる。

環境変数とファイルに置けるのは設定だけであり、その 1 回の起動や実行にだけ意味を持つ操作はフラグでしか渡さない。対象は `--adopt-existing`、`--force`、`--purge`、`--yes`、`--dry-run` である。たとえば `WGFT_ADOPT_EXISTING=true` のような値がファイルに残ると、再起動のたびに他人の WireGuard インタフェースを引き継いでしまうためである。例外は 2 つあり、どちらも居座っても害が無いことを仕様で保証している。1 つは `WGFT_MODE` と `WGFT_WG_ADDRESS` で、初回に記録された後は照合にしか使われない。もう 1 つは `WGFT_JOIN`(エージェントの初回登録)で、これは 1 回限りの操作でありながら、compose ファイルに残ることを前提に設計してある。エージェントは使用済みの登録トークンのハッシュを状態ファイルに残し、`WGFT_JOIN` の値がそれと同じであれば登録を試みずに止まる(5.1 節)。エージェントが削除され、恒久トークンの認証が拒否された場合だけ、この値を使って再登録する。

`rule add` と `rule set` の `--dry-run` は、管理 API から観測可能な範囲で、実際の `Batch` が保存前に行う admission 判定と一致させる。予約ポートは `ServerInfo` から構成し、`ValidateUpsert` に渡す。組み立ての規則は `internal/vpsd/vpsd.go` が起動時に `Daemon.reserved` を作る規則と同じにする。WireGuard のポートは常に予約する。`admin_addr` は `net.SplitHostPort` で `host:port` に分けられたときだけ予約し、Unix ソケットはポートを予約しない。`agent_api_port` は `GET /api/v1/server`(`admin.ServerInfo`)が既に `net.SplitHostPort` 済みの文字列として返す値を使う。どちらも待ち受けが実際に bind するポートを予約する。ホストの部分は問わないので、`localhost:8686` と `:8686` もポート 8686 を予約する。ポートの部分は `net.Listen` と同じ `net.LookupPort` で番号に直すので、`0.0.0.0:https` はサービスの一覧が示す番号を予約し、`+8686` と `08686` は 8686 を予約する。番号が 0 になるポートはカーネルが選ぶポートであり、どのルールも使えないので予約しない。行ごとには `GET /api/v1/agents` が返す名前の集合による `--agent` の登録の検査を行う。行の形の検査(`Rule.Validate`)は、`rule add` と `rule set` のどちらも `--dry-run` の有無に関わらず先に行う。落ちた行は `--dry-run` の実装に届かないため、`--dry-run` の実装は行の形の検査を行わない。全体には、現在のルール集合にこの upsert を当てはめた後の集合に対して、`ValidateUpsert` による ID の重複・予約ポート・listen_port の重なりの検査を行う。`Batch` は呼ばない。誤りが無ければ終了コードは 0 とし、何も保存していないことを出力に明記する。誤りがあれば終了コードは 1 とする。この判定は Web UI の読み込みの確認(10.1 節)とも共有しているが、一致させる基準は実際の `Batch` であって Web UI ではない。

ポートの名前を番号に直せない場合は、予約ポートを組めなかったものとして止め、そのポートを予約から外して続行しない。続行すると、そのポートに重なる変更を受理されるものとして示すためである。`vpsd` は起動を止める(終了コード 1)。入口(11b 節)が同じ `net.LookupPort` で値を検査しているので、これが起きるのは検査の後にサービスの一覧が変わった場合だけである。`--dry-run` は `GET /api/v1/server` が読めない場合と同じ終了コード 2 で止め、Web UI の読み込みの確認は確認の画面を止める。CLI はサービスの名前を自分のホストのサービスの一覧で番号に直すので、別のホストから管理用 API に接続する CLI では、server と違う番号になりうる。この食い違いは未確認である。

2026-10-02 の改訂の前は、ホスト名やサービス名で書いた API のポートを予約していなかった。予約ポートの検査は変更の無い行にも掛かる(5.4 節)ので、そのポートに重なるルールを保存していた場合、更新の後はそのルールを残すバッチが、そのルールに触れない変更も含めてすべて拒まれる。保存済みのルールの転送は続き、そのルールの `listen_port` を変えるか削除するバッチは通る。

`GET /api/v1/server` が失敗した場合、旧い版の server がこの節点を持たず 404 になる場合を含め、予約ポートを `nil` として続行しない。続行すると、予約ポートに重なる変更を誤って accepted と示し、直後の実 `Batch` に拒まれる誤りが戻るためである。この場合、`server doctor` と同じ終了コード 2(`unavailable`)で止め、この変更が受理されるかどうかを判定できなかったことを示す。同じ理由で、`--dry-run` が読む `GET /api/v1/rules`・`GET /api/v1/agents` の失敗も終了コード 2 とする。`rule add`・`rule set` の通常の実行(`--dry-run` を付けない場合)はこれらの節点を読まないため影響を受けない。

`target` への到達可能性は確かめず、`wgft server doctor <rule>` の対象である。VPS 上で待ち受けポートが既に他のプロセスに使われていないかと、他のテーブルの DNAT(`internal/vpsd/apply.go` の `DNATConflicts`)との衝突は確かめない。前者は `--force` で上書きできるが後者はできない一方、どちらも root と nft を要し CLI から admin API 越しには判定できないためである。

## 11b. 起動の失敗の意味論

起動の失敗の分類の中心は、終了コードの番号ではなく次の 2 つの問いである。

- 再試行で直るか
- 人が手を入れなければ直らないか

判定は非対称である。既定は「再試行で直りうる」とみなして終了コード 1 で終わる。終了コード 3 は、原因が設定された値そのものであると示せる場合、または運用者の操作なしには消えないと示せる場合だけに使う。示せない失敗は終了コード 1 とする。誤った終了コード 3 は systemd の再起動を永久に止めるので、原因が消えた後も転送が戻らない。騒がしい再起動の繰り返しより、転送が落ちたままになることのほうが悪い。

終了コード 3 で終わる失敗を起動の拒否と呼ぶ。拒否は `internal/startup` の 1 つの型 `*startup.Refusal` で表し、`cmd/wgft` の `exitCode` はこの型の有無だけを見て終了コードを決める。型を 1 つにする目的は、新しい失敗を足すときに終了コードへの写し忘れが起きないことにある。

拒否は原因の種別を持つ。種別はログの文言と `wgft server check` の表示に出し、運用者が直し方を選べるようにする。文言の書き出しは、その拒否が止めた行いによって 2 つに分かれる (2026-09-23、所有者の決定)。常駐プロセスの起動を止めた拒否は `refusing to start [種別 対象]: 理由` とし、常駐プロセスを起動しない一発実行のコマンドを止めた拒否は `cannot continue [種別 対象]: 理由` とする。設定を読む層は両者で共有しており、同じ誤りがどちらの経路にも出る。`wgft status` や `wgft agent doctor` が起動を拒んだと述べると、何も起動しないコマンドについて事実でないことを述べることになる。終了コードはどちらも 3 である。

どちらの書き出しを使うかは、コマンドの側が決める。読む層の側は呼び出し元を知らず、`buildServerOptions` のように `server run` と `server check` が共有する入口もあるためである。既定は一発実行の側とし、常駐プロセスを起動する `server run` と `agent run` だけが自分でその旨を名乗る。既定を逆にすると、コマンドを足すたびに印を付け忘れた分だけ事実でない文言が残る。

| 種別 | 意味 | 例 |
|---|---|---|
| `config` | 設定された値そのものの誤り。構文、範囲、必須の値の欠落 | `WGFT_MTU` が範囲外、初回の `WGFT_MODE` の欠落、`WGFT_JOIN` の構文の誤り |
| `prerequisite` | ホストが備えるべきものの欠如で、再試行では現れないもの | カーネルの WireGuard モジュール、`CAP_NET_ADMIN`、新しい版が書いたサーバのデータベース、Linux でないホスト、Linux でないホストでのエージェントの `WGFT_MODE=kernel` |
| `conflict` | 設定された値や認証情報が、すでにある記録と矛盾するもの | 記録済みのアドレス帯との食い違い、使用済みの登録トークン、登録済みの名前 |
| `mode-gate` | モードの切り替えの関門を通らないこと | `kernel` から `userspace` への切り替えで、wg インタフェースか `table inet wgft` が残っている。エージェントでは、wg インタフェースか `table inet wgft_agent` かカーネルモードの記録が残っている |

Linux 以外のビルドの `server` の一群は、種別 `prerequisite` の拒否を返す (2026-09-23、所有者の決定)。Windows と macOS のバイナリはエージェントと CLI だけを持ち、server はカーネルの WireGuard と nftables を使うので Linux でしか動かない。この前提の不成立は再試行でも再起動でも消えず、運用者が Linux のホストへ移すまで同じ結果になるので、本節の非対称の規則では拒否の側に当たる。終了コードは 3 とする。書き出しは他の拒否と同じ規則で分かれる。`server run` は常駐プロセスの起動なので `refusing to start`、`server check`・`server nft`・`server teardown`・`server doctor` は何も起動しないので `cannot continue` である。この書き分けを保つため、Linux 以外のビルドでも `server` の一群はコマンドの木の形を保ち、常駐プロセスを起動する旨の注記を持つのは `run` だけとする。一群を 1 つのコマンドに畳むと、`server run` まで一発実行の文面になる。

この拒否が起きるホストには systemd が無いので、終了コード 3 が再起動を止める効果も働かない。効果は、本節の末尾が述べる macOS とコンテナの場合と同じく、運用者と監視が原因を選り分けられることにとどまる。それでも 1 にしないのは、Linux でないことが 4 つの種別のどれに当たるかという分類の問題であり、値を監督するプロセスごとに変えると分類そのものが揺れるためである。

エージェントのカーネルモード(7b 節)の起動の失敗は、`vpsd` のカーネルモードと同じ種別に写す(2026-09-24、所有者の決定)。Windows と macOS のエージェントで `WGFT_MODE=kernel` を指定した場合は、上の Linux 以外のビルドの `server` と同じ理由で種別 `prerequisite` の拒否とし、終了コード 3 で止める。カーネルの WireGuard のリンク種別が無い場合と `CAP_NET_ADMIN` が無い場合も、9 節の `vpsd` と同じく `prerequisite` である。`kernel` から `userspace` への切り替えで残骸が残っている場合は `mode-gate` であり、`wgft agent teardown` を案内する(11a 節)。同名の WireGuard インタフェースが別の鍵を持つ場合は、他の所有者の資源との衝突として終了コード 1 で終わる(後述)。これらの扱いは、このプロセスの最初の wgft0 の収束が stream に接続した後に行われる場合にも当てはまり、その後の同じ失敗はプロセスを終えずに試し直す(7b.4 節、2026-09-24、所有者の決定)。

`wgft agent teardown` は常駐プロセスを起動しない一発実行のコマンドである。Windows と macOS では、Linux 以外のビルドの `server` の一群と同じく種別 `prerequisite` の拒否とし、`cannot continue` の書き出しで終了コード 3 で止める。エージェントが稼働中のときに何も消さずに拒否する扱いは起動の拒否ではなく、`server teardown` と同じ普通の誤りであり、終了コードは 7a.11 節の共通の保証に従って 0 以外になる。未知のモードの記録で止まる場合は種別 `conflict`、`CAP_NET_ADMIN` が足りない場合は種別 `prerequisite` の拒否とし、どちらも `cannot continue` の書き出しで終了コード 3 で止める(10.3 節)。指したデータディレクトリに `agent.json` が無く、何も消さずに止まる場合は、稼働中の拒否と同じ普通の誤りとして終了コード 1 で止める(10.3 節)。

`wgft server teardown` が、稼働中の `vpsd` のロックで拒否する場合と、ロックの状態を読めずに何も消さずに止まる場合は、どちらも起動の拒否ではなく普通の誤りであり、終了コードは 1 である(10.3 節、2026-10-03)。

再試行で直りうる失敗は拒否にせず、普通のエラーとして終了コード 1 で返す。他の所有者が持っている資源との衝突はこちら側に入る。同名のインタフェースが別の鍵を持っている場合、他の WireGuard が `WGFT_WG_PORT` を使っている場合、他のプロセスがその UDP ポートを bind している場合、アドレス帯が他のインタフェースと重なっている場合、`net.Listen` が `EADDRINUSE` を返す場合、サーバのデータベースを他のプロセスが保持している場合が当たる。撤去がロックを持つ間に起動した `vpsd` も最後の場合に当たり、データベースを開く前に終わる(10.3 節)。いずれも相手が資源を手放せば次の再起動で起動できる。何も書き換える前に中止する事前検査そのものは残す。半端な状態を作らないことと、再起動を止めることは別の目的である。

この 2 つの扱いに収まらない失敗が 1 つある。起動時の最初のルールの適用の失敗であり、原因が記録した宣言そのものにあるため再起動では直らない一方、運用者がその宣言を直す経路は管理用 API にある。この失敗だけは終了せず、管理用 API だけを開いて適用を試し直す(次項)。

### 起動の保留

起動時の最初のルールの適用の失敗は、終了コード 1 でも 3 でもなく、起動の保留とする。`vpsd` は終了せず、管理用 API だけを開いた状態で起動の残りを止め、適用を試し直す。適用が成功した時点で起動の残りに進む(2026-09-22、所有者の決定)。

この扱いにする理由は、カーネルへ適用できない宣言をサーバのデータベースに保存できてしまう点にある。宣言の保存は適用の成否を待たない(7a.3 節)ので、適用が毎回同じ失敗をする宣言が記録に残りうる。従来はこの記録を読んだ起動時の最初の適用が終了コード 1 で終わり、unit が再起動して同じ場所で落ちた。管理用 API はこの適用より後に開くので、`wgft rule rm` で宣言を小さくする経路が開かず、運用者に残る手段は `server teardown --purge` による全消しだけだった。設定の誤りを 1 つ保存しただけで、それを直すための入口まで失われる。本節の非対称の規則は、再起動で直りうる失敗を終了コード 1 とするものだが、この失敗は原因が記録にある以上、再起動では直らない。かといって終了コード 3 で止めると、運用者が直すための管理用 API も開かない。保留は、この失敗に対して再起動を繰り返さず、直すための入口だけを開ける 3 つ目の扱いである。

起動の保留の規則は次のとおりである。

- 入る条件:起動時の最初の適用が失敗したことである。サーバのデータベースを開くこと、モードとアドレス帯の照合、wg インタフェースの立ち上げは、この適用より前にあり、保留の対象にしない。これらの失敗と、起動の拒否(`*startup.Refusal`)は、従来どおり終了コード 3 か 1 で終わる
- 権限の不足との関係:カーネルモードで権限が足りない配置は、この保留に届かない。wg インタフェースの立ち上げが最初の適用より前にあり、そこで `EPERM` が種別 `prerequisite` の拒否になって終了コード 3 で止まるためである(9 節)。インタフェースを作る netlink の書き込みも、既存のインタフェースを読む `wgctrl` の呼び出しも `CAP_NET_ADMIN` を要求する。したがって 9 節の権限の拒否と本節の保留は、同じ失敗を奪い合わない。最初の適用だけが権限で失敗する配置は、`CAP_NET_ADMIN` を持ちながら nftables への書き込みだけを拒まれている状態であり、原因は権限そのものではない。この場合を権限の拒否に写して終了コード 3 で止めると、7a.3 節が「30 秒ごとの再試行が拾う」と定めた `table inet wgft` の保持のような、待てば解ける原因まで永久に止めることになる。最初の適用の失敗は、権限で失敗したかどうかを問わず保留とする。上の入る条件が定めるとおり、最初の適用が起動の拒否(`*startup.Refusal`)を返した場合だけは保留にしない
- 開く待ち受け:管理用 API だけである。エージェント用 API は開かない。転送していない間にエージェントが接続しても中継は起きず、エージェントへ配る全体状態に入る conntrack の UDP タイムアウト 2 値も、この時点では読めていない(9 節。この読み取りはテーブルの適用の後に置いてある)ためである。エージェント用 API を開くと、制御の接続だけが成立して転送は起きない状態になり、運用者から見て保留と正常の区別が付かなくなる
- 転送:保留の間、`vpsd` は宣言を公開できていないと判断している。ただしカーネルが実際に何を転送しているかは、適用がどこで失敗したかで変わり、`vpsd` の側からは確定できない。初回の起動と、ホストごと再起動した後では、`table inet wgft` も wg インタフェースのピアも無いので何も転送されない。プロセスだけを入れ替えた起動では、前のプロセスが公開したテーブルとピアがカーネルに残る(9 節。停止時にはどちらも削除しない)。このとき、カーネルが差し替えを行わないまま失敗した場合、つまりバッチが `EMSGSIZE` で送れなかった場合(6.1 節の送信側の壁)と、カーネルがバッチを拒んだ場合は、テーブル全体が旧のまま残り、カーネルモードの transparent のルールは前回公開した宣言のまま転送を続ける。一方、カーネルは差し替えを終えたのに `vpsd` が応答を受け取れなかった場合、つまり `ENOBUFS` で応答を取りこぼした場合(6.1 節の受信側の壁)は、テーブルは既に差し替わっている。このとき転送しているのは、`vpsd` が失敗として報告した新しい宣言のほうである。差し替えの後に読み直した送信元の一覧の set が送った要素を持たなかった場合(6.1 節)も、テーブルは既に差し替わっている。この 2 つが逆の結果になることは、ラボで実測した(改訂の記録 2026-09-23)。プロキシモードの待ち受けはプロセスと一緒に消えるので、どちらの場合も止まる。したがって、保留を「転送が止まっている状態」とも「前回の宣言のまま転送している状態」とも説明してはならない。実際のカーネルの内容を読む手段は `wgft server nft` であり、管理用 API が開いているので保留の間も使える。この不確かさは保留が作ったものではなく、6.1 節の受信側の壁がもともと持っているものを、保留が引き継いでいるだけである。この残り方が、稼働中に backend 全体の失敗が起きたときと同じであることも変わらない(7a.3 節)
- 試し直し:7a.3 節の再試行と同じ 30 秒ごとである。管理用 API のバッチ操作は、従来どおりその場で適用を試すので、運用者が宣言を直せば次の 30 秒を待たずに保留が解ける
- 出る条件:適用が成功したことだけである。その時点で conntrack の UDP タイムアウトを読み、エージェント用 API を開き、起動完了の行を出し、収束のループを始める。以後の挙動は保留を経ていない起動と変わらない
- ログ:保留に入るときに 1 行、解けるときに 1 行を出す。入るときの行は、適用の失敗の理由と、`wgft server nft` でカーネルの実際の内容を読めることと、`wgft status` で状態を読めることと、`wgft rule rm` か `wgft rule disable` で宣言を小さくできることを示す。試し直しが同じ理由で失敗するあいだは何も出さず、理由が変わったときだけもう 1 行出す。7a.3 節の抑制と同じ規則である。起動完了の行は、保留が解けるまで出さない
- 終了コード:起動の保留は終了しないので終了コードを持たない。管理用 API の待ち受けそのものが失敗した場合は、従来どおり終了コード 1 で終わる
- 保留の間の conntrack の UDP タイムアウト 2 値:まだ読んでいないので 0 である。この値は全体状態に載せてエージェントへ配るものだが(4 節)、保留の間はエージェント用 API を開かないので配られることはない。保留が解けた時点で読み、エージェント用 API の待ち受けはその後に開く。管理用 API の `GET /api/v1/server` と `GET /api/v1/agents/{name}/state` は、保留の間この 2 値を 0 のまま示す
- 保留の間の管理用 API:ルール一覧は読め、すべてのルールの `apply_state` は `pending`、`apply_error` に適用の失敗が入る(7a.3 節)。`wgft status` は、`apply_error` があるので Server 行を degraded とし、有効なルールが 1 本でもあればすべて `pending` なので Rules 行も degraded とする(10.2b 節。無効なルールは総数に数えない)。ただし、最初の適用が `Reconcile` に入る前の読み取り(wg の設定の組み立て、世代の読み取り)で失敗した場合は、適用状態を持つ節点がまだ無いので Server 行は unknown になる。Agents 行は、登録済みのエージェントがあれば、その stream が繋がらないので degraded になるが、1 つも登録されていない保留では 0 台のまま degraded にならない。保留そのものを表すのは Server 行である
- 監督するプロセスから見た見え方:保留の間、unit は active のままである。従来の終了コード 1 の繰り返しは `Restart=on-failure` によって再起動として見えたが、保留は 1 行を出した後は静かになる。これは稼働中に `apply_error` を抱えたまま動き続ける場合(7a.3 節)と同じ見え方であり、公開が止まっていることを知る手段も同じく `wgft status` と `server doctor` の終了コード 1 である。unit の状態だけを見る監視は、保留も稼働中の適用の失敗も捉えられない

### 起動を止めない記録の失敗

撤去の案内にだけ使う記録の保存の失敗は、起動を止めず、警告して続ける。`net.ipv4.ip_forward` の 2 段の記録(6.1 節)と、撤去の手掛かりの記録(10.3 節)がこれに当たる。どちらも転送には効かないためである。`net.ipv4.ip_forward` の予定の記録を保存できない場合も、値は書く。起動を止めると、サーバのデータベースに書けない間は、ホストの再起動のたびに転送が戻らない。値を書かずに続けても、同じく転送が止まる。騒がしい再起動の繰り返しより転送が落ちたままになることのほうが悪い、という本節の規則に従う。記録の失敗は警告のログで知らせ、値を書いた後、6.1 節の手順が 5 まで進み、記録がどちらの段でも残らなかった場合は、起動時の Finding でも知らせる(2026-10-03、所有者の決定)。予定の記録を保存できず、書いた後に確定の記録の前で止まった場合は、Finding を出せず、予定の記録の警告のログだけが残る。

### 入口での判定

値だけから判定できる失敗は、wg インタフェース、待ち受け、サーバのデータベース、認証情報ファイルのいずれにも触れる前に判定する。この場所を入口と呼ぶ。server の入口は `cmd/wgft` の `buildServerOptions`、エージェントの入口は同じ package の `buildAgentOptions` である。入口を通り抜けた値が起動の後半で初めて失敗すると、そこでは環境由来の失敗と区別が付かず、終了コード 1 の再起動の繰り返しになる。この形の穴は 3 つの設定項目で続けて見つかっている(改訂の記録 2026-09-20 と 2026-09-21)。

server の入口が判定する項目は次のとおりである。`WGFT_MODE` の値(`kernel` か `userspace` か)、`WGFT_DATA_DIR` が空でないこと、`WGFT_WG_INTERFACE` がカーネルの受け付ける名前であること、`WGFT_WG_PORT` が 1 から 65535 の整数であること、`WGFT_MTU` が 576 から 9216 の整数であること、`WGFT_WG_ADDRESS` が `netip.ParsePrefix` の通る形であること、`WGFT_AGENT_API` と `WGFT_ADMIN` が待ち受けられる形であること、`WGFT_WG_ENDPOINT` と `WGFT_AGENT_API_HOST` が `host:port` の形でホストが空でないこと、`WGFT_AGENT_API_HOST` のポートが 1 から 65535 を 10 進の数字で書いた値であること、`WGFT_WG_ENDPOINT` のポートが UDP のポートとして 1 から 65535 の番号に直せること、`WGFT_ADMIN_TAILSCALE` が真偽値であること、同時フロー数の 4 つの上限が範囲内であること、`run` では `WGFT_WG_ENDPOINT` があることである。エージェントの入口は、`WGFT_DATA_DIR` が空でないこと、`WGFT_MODE` の値、Linux 以外のビルドで `kernel` を指定したこと、`WGFT_WG_INTERFACE` がカーネルの受け付ける名前であること、同時フロー数の上限、`WGFT_AGENT_ALLOW_TARGETS` の構文を判定する。Linux 以外のビルドでの `kernel` の指定は種別 `prerequisite` の拒否で、他は種別 `config` の拒否である。`WGFT_WG_INTERFACE` はカーネルモードでだけ使うが、値だけで判定できるので、モードによらず判定する。後でカーネルモードへ切り替えたときに、起動の後半で初めて失敗しないためである。

`WGFT_AGENT_API_HOST` のポートにサービス名、符号、0 を許さないのは、値が接続文字列にそのまま入り、エージェントの `ParseJoin` が 1 から 65535 を 10 進の数字で書いたポートしか受け付けないからである。2026-10-02 の改訂の前は、入口がこのポートを `net.LookupPort` で検査していたので、`vps.example.com:https`、`vps.example.com:+443`、`vps.example.com:0` を受け付けていた。これらの値はエージェントが拒む接続文字列を作るだけで、どのエージェントでも動いていなかった。改訂の後は、これらの設定で server は起動せず、種別 `config` の拒否(終了コード 3)で止まる。値を数字に書き換えれば起動する。

`WGFT_WG_ENDPOINT` は、入口でポートの部分だけを `net.LookupPort("udp", ...)` で番号に直し、10 進の数字で書いた値をこの起動の設定として使う。`+51820` と `051820` は 51820 に、サービス名は server のホストのサービスの一覧が示す番号になる。ホストの部分は書かれたまま残し、IP アドレスに引かない。名前の引き直しはエージェントが行う。番号に直すのは起動のときの 1 回だけで、全体状態の配信や管理用 API の読み取りのたびには引き直さない。エージェントに配る値と管理用 API の `wg_endpoint` は、どちらも直した値である。設定ファイルは書き換えず、起動ログと `wgft server check` の「値と出所」の表示は入力の値のままである。UDP として番号に直せない名前は TCP で引き直さない。番号に直せない値、番号が 0 の値、65535 を超える値は、ポートを数字で書くよう例(`vps.example.com:51820`)を添えて、種別 `config` の拒否(終了コード 3)で止める。

この正規化は、エージェントの側の解釈がモードで違うことによる。ユーザー空間モードのエージェントは 10 進の数字のポートしか受け付けないので、改訂の前は、サービス名と符号付きのポートを書いた設定ではトンネルを張れなかった。カーネルモードのエージェントは `net.LookupPort("udp", ...)` で、エージェントのホストのサービスの一覧から番号に直していた。改訂の後は番号を決める場所が server の入口の 1 か所になり、どちらのモードのエージェントも同じ数字のポートを受け取る。ただし、古い設定が同じ番号で動き続けるとは限らない。番号を引くホストがエージェントのホストから server のホストへ移るので、サービスの定義がエージェントのホストと違う server のホストでは、別の番号になるか、番号に直せずに起動が止まる。改訂の前の入口は TCP として引いていたので、TCP にだけ定義のある名前と番号が 0 の値も通っていた。これらはどちらのモードのエージェントでも接続できない値で、改訂の後は起動を止める。

`WGFT_AGENT_API_HOST` を省いた場合、接続文字列のポートは `WGFT_AGENT_API` の待ち受けが bind するポートを 10 進の数字で書く。`WGFT_AGENT_API` は待ち受けの値なので、入口はサービス名を許す。接続文字列を作るときに、待ち受けと同じ `net.LookupPort` で番号に直す。番号に直せない場合と、番号が 0(カーネルが選ぶポート)の場合は、接続文字列を発行せずに誤りを返し、`WGFT_AGENT_API_HOST` の設定を案内する。改訂の前はポートの部分をそのまま接続文字列に入れていたので、サービス名を書いた設定ではエージェントが拒む接続文字列を発行していた。

接続文字列のホストは必須である。エージェントの `ParseJoin` は、ホストが空の接続文字列(`wgft://:8443/...`)を拒む。改訂の前はこれを受け付け、エージェントは自分のホストの、接続文字列に書いたポートへ接続していた。server はホストが空の接続文字列を発行しないので、影響を受けるのは手で書き換えた接続文字列だけである。登録済みのエージェントは `WGFT_JOIN` を読まないので、入口の警告が 1 行出るだけで止まらない。

値だけからは判定できない項目は次のとおりで、判定の場所とその理由を定める。

- `WGFT_MODE` の初回の必須: 記録の有無で必須かどうかが決まるので、記録を読める `internal/vpsd` が判定する
- `WGFT_JOIN` の構文: 登録済みのエージェントは、compose に残った古い値を読まない(11a 節が意図的に許す居座り)。入口で構文を拒否すると、動いていたエージェントが使われない値の誤りだけで止まるので、登録の直前に判定する。誤りに気付けるよう、入口では警告を 1 行出す
- `WGFT_NAME` の文字種: 名前の規則は server の側(`internal/vpsd/store`)にあり、エージェントはその規則を持たない。登録の応答(HTTP 400)を種別 `config` の拒否に写す
- エージェントのカーネルモードの前提: `CAP_NET_ADMIN` と WireGuard のモジュールの有無は、値ではなくホストで決まる。`internal/agent` が、認証情報ファイルの排他を取った後、モードの記録と登録より前に判定する(7b.5 節)。記録との照合の後に置くのは、モードの関門と記録の矛盾による拒否を先に示すためである

設定項目を足すときは、入口の検査と、その終了コードのテストを同時に足す。`cmd/wgft` の `TestEveryServerSettingIsCheckedAtTheDoor` は `serverSpecs` のすべての項目に壊れた値を 1 つ持ち、終了コード 3 で止まることと、データベースも待ち受けも作られていないことを確かめる。値だけからは壊せない項目は理由付きで表に書く。表に無い項目を足すとこのテストが落ちる。

### 登録の応答の扱い

エージェントの登録と再登録では、server の応答が再試行の可否を決める。HTTP 401(トークンが無効、期限切れ、名前違い)、400(名前の文字種)、409(その名前が登録済み)は、送った値に対する server の判定であり、再起動では変わらないので拒否にする。401 と 409 は種別 `conflict`、400 は `config` である。429(レート制限)、5xx、到達できない場合は普通のエラーとし、unit の再起動に任せる。

### 監督するプロセスから見た効果の範囲

終了コード 3 が再起動を止める効果は、同梱の systemd の unit(`server.service` と `agent.service`)の `RestartPreventExitStatus=3` によるものであり、wgft 自身の性質ではない。

macOS の launchd には `RestartPreventExitStatus` に当たる設定が無い。同梱の plist は `KeepAlive` の `SuccessfulExit` を偽にしているので、終了コード 3 でも `ThrottleInterval` の間隔で再起動を繰り返す。実機で確認した挙動は 11a 節にある。Docker の `restart: unless-stopped` も終了コードを見ない。したがって macOS とコンテナでは、拒否の効果は運用者がログで原因を選り分けられることだけであり、再起動は止まらない。種別と文言は、どの監督するプロセスの下でも同じ手がかりになる。
