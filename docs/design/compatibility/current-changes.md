# 既存の値に対する例外と変更の範囲

加算フィールドと入力の検査には、既存データを引き継ぐための規則があります。
個別に許容した変更は、他の変更を許容する一般規則にはしません。


エージェントのカーネルモード([7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード))は、次のものを加える(2026-09-24、所有者の決定)。
どれも加算であり、設定を変えない既存の配置の挙動は変わりません。

- 設定:エージェントが `WGFT_MODE`(`--mode`)と `WGFT_WG_INTERFACE`(`--wg-interface`)を読みます。
  名前は `vpsd` と同じで、エージェントでの意味は [11a 節](../security/configuration.md#11a-設定の渡し方)が定める。
  `WGFT_MODE` の既定は `userspace` なので、`WGFT_MODE` を渡していないエージェントは今と同じモードで動く。
  例外は、server と共有するファイルなどを通して `WGFT_MODE=kernel` を既にエージェントへ渡している配置です。
  今のエージェントはこの値を無視するが、更新の後はカーネルモードで起動しようとし、権限の無い unit では種別 `prerequisite` の拒否で止まります。
  リリースノートはこの配置を名指しして知らせる
- CLI:コマンド `wgft agent teardown` を加える([10.3 節](../operations/setup.md#103-運用の流れ))。
  フラグは `--dry-run` と、設定の別名の `--data-dir`、`--wg-interface`、`--config` です。
  `--json` を持たず、終了コードは共通の保証だけを持ちます
- `agent doctor --json`:`checks[].id` に `dataplane.interface`、`dataplane.table`、`host.forwarding` を、`checks[].reason` に `needs_cap_net_admin` と、[10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor)の理由の符号の表が挙げるカーネルモードの符号を加える([10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor))。
  どれも開いた集合への値の加算です。
  カーネルモードで `relay.listeners`、`relay.sessions`、`relay.refusals`、`tunnel.watchdog` が NOT TESTED になり、ルール単位の失敗を `dataplane.table` が示すこと、`agent.process` の FAILED だけでは最上位の `status` が `failed` にならないことは、カーネルモードのエージェントにだけ起きる。
  ユーザー空間モードのエージェントでの値の意味は変わりません。
  ユーザー空間モードのエージェントの `--json` も 3 つの新しい `id` を持ち、状態は NOT TESTED です。
  `checks[]` の項目は実行の状態で消えないという [10.2c 節](../diagnosis/agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor)の約束に従います。
  `agent doctor` はモードを、稼働中のエージェントの答えから、その答えが無ければ状態ファイル `agent.json` の記録から知る
- `server doctor --json`:`checks[].reason` に `target_loopback_unsupported` を加える([7b.3 節](../kernel-agent/targets.md#7b3-ルールの状態と失敗の種類))。
  開いた集合への値の加算です
- wire protocol と管理用 API:変えません。
  server にはエージェントのモードを知らせない([7b.6 節](../kernel-agent/operations.md#7b6-server-との関係))。
  モードで変わるのはハートビートの理由の文言だけで、文言は保証の対象ではありません
- `deploy/` の同梱物:`agent.service` は変えません。
  カーネルモード用の設定の例 `agent.kernel.conf` を加えることは加算であり、そのファイル名は上の `deploy/` の同梱物の項の保つものに入ります
- 認証情報ファイル:モード、`ip_forward` の記録、1 つ前の鍵、直近の公開の結果、conntrack の収束が済んでいない前の公開の列を加えます。
  内部の形は保証の外です
- トンネルのアドレスの記録(2026-09-25、所有者の決定):認証情報ファイルに `tunnel_address` を加え、カーネルモードのエージェントは記録と違う `wg.address` の全体状態を拒む([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))。
  カーネルモードは未リリースなので、公開済みの挙動の変更ではなく、未リリースの挙動の変更として扱う。
  ユーザー空間モードは記録と違うアドレスも使い、警告を出すだけなので、公開済みの挙動は変わりません。
  新しいエージェントが古い版の書いた `agent.json` を読むと、記録が無いので、最初に適用できた全体状態の値を記録します。
  起動時は `last_state` があれば先に適用するので、その適用が成功すれば、値は更新の前に受け取ったものです。
  `last_state` が無いか、その適用が失敗した場合は、stream から最初に適用できた全体状態の値になります。
  古い版のエージェントが新しい `agent.json` を読むと、知らない項目として無視し、次の保存で項目を落とす(上の認証情報ファイルの段落)。
  その後に新しい版へ戻すと、記録の無いファイルとして最初に適用できた値を記録し直す。
  記録が落ちている間に server が配った値は照合されない。
  wire protocol は変えません。
  登録の応答はこれまでどおりアドレスだけを返し、エージェントはアドレスの付いた帯の形も受け付ける

待ち受けのポートの予約と、接続文字列のポートの検査([5.3 節](../control/rules.md#53-ルールのスキーマ)、[5.4 節](../control/batches.md#54-ルールのバッチ操作)、[11a 節](../security/configuration.md#11a-設定の渡し方)、[11b 節](../security/startup.md#11b-起動の失敗の意味論)、2026-10-02、所有者の決定)は、次のものを変えます。

- ルールの検査:管理用 API のホストを IP アドレス以外で書いた設定(`localhost:8686`、`:8686`)と、どちらかの API のポートをサービス名や符号付きの数字で書いた設定でも、そのポートを予約します。
  ポートは待ち受けと同じ `net.LookupPort("tcp", ...)` で番号に直す。
  これまで受理していた `listen_port` が拒まれる変更であり、加算ではありません。
  予約ポートの検査は変更の無い行にも掛かるので、新しく予約に加わったポートに重なるルールを保存していた場合、更新の後はそのルールを残すバッチがすべて拒まれる。
  重なるルールが複数あれば(TCP と UDP、または 2 つの API のポート)、すべて直さないとバッチは通らない。
  保存済みのルールの転送は止めず、削除もしません。
  拒みを解くには、そのルールの `listen_port` を変えるか、ルールを削除します。
  重なりを解く変更は通る。
  予約は `listen_port` の番号だけで判定するので、UDP のルールも同じ番号で拒まれる。
  この点は変わりません
- 起動:`WGFT_AGENT_API_HOST` のポートが 1 から 65535 を 10 進の数字で書いた値でなければ、server は種別 `config` の拒否(終了コード 3)で起動しません。
  ホストが空の値は従来どおり起動しません。
  これまで受け付けていたサービス名と符号付きの値は、エージェントが拒む接続文字列を作るだけで、どのエージェントでも動いていなかった。
  ポート 0 は、エージェントが接続文字列を受け付けても接続できない値だった。
  `WGFT_WG_ENDPOINT` のポートは、入口で `net.LookupPort("udp", ...)` により番号に直す。
  ホストは書かれたまま残します。
  番号に直せない値と 0 は、種別 `config` の拒否(終了コード 3)で起動を止め、数字で書くよう案内します。
  これまで起動していた設定が起動しなくなりうる変更であり、加算ではありません
- 設定の値の意味との関係:上の「設定(`WGFT_*`)」の段落のとおり、構文の検査を終了コード 3 の原則に沿って新設し、強化することは、互換を保つ変更です。
  `WGFT_AGENT_API_HOST` の拒否はこれに当たる。
  一方、`WGFT_WG_ENDPOINT` のポートの名前を番号に直すホストを、カーネルモードのエージェントのホストから server のホストへ移すことは、値の意味の変更であり、互換ではありません。
  所有者がこの変更を決めた
- エージェントに配る値:カーネルモードのエージェントは、名前を自分のホストのサービスの一覧で番号に直していました。
  改訂の後は server のホストが番号に直す。
  サービスの定義が違うホストでは、同じ名前が別の番号になるか、番号に直せずに起動が止まります。
  ユーザー空間モードのエージェントは名前を番号に直さず拒んでいた。
  `WGFT_AGENT_API_HOST` を省いた場合の接続文字列には、`WGFT_AGENT_API` のポートを TCP として番号に直して書きます。
  番号に直せない場合と 0 の場合は、接続文字列を発行せず、`WGFT_AGENT_API_HOST` の設定を案内します。
  更新の前にサービス名のエンドポイントで動いていたエージェントの、更新の時点の挙動は、ラボでも実機でも確かめていません
- 接続文字列の解釈:エージェントは、ホストが空の接続文字列(`wgft://:8443/...`)を拒みます。
  これまでは受け付け、自分のホストへ接続していました。
  server はこの形を発行しないので、影響を受けるのは手で書き換えた接続文字列だけです。
  登録済みのエージェントは `WGFT_JOIN` を使わないので、警告の行を 1 行出すだけで止まらない
- wire protocol、`status`、`server doctor`:変えません。
  管理用 API はルートとフィールドの形を変えません。
  値と拒否は上の項のとおり変わる。
  `GET /api/v1/server` の `wg_endpoint` と Web UI のサーバのページは、直した後の値を示します。
  接続文字列の発行(管理用 API、Web UI、`agent join-string`)は上の条件で誤りを返します。
  Web UI の読み込みの確認は、予約ポートの名前を番号に直せない場合に確認の画面を止めます。
  `rule add` と `rule set` の `--dry-run` は、予約ポートの組み立てを実際のバッチと共有するので、新しく予約に加わったポートへの重なりも拒みます。
  サービス名を番号に直せない場合は、`GET /api/v1/server` が読めない場合と同じ終了コード 2 で止まります
