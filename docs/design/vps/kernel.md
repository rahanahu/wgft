### カーネルモード

VPS のカーネルモードは、nftables の DNAT と WireGuard で転送します。
wgft のテーブルは全体を差し替え、他のテーブルの衝突は検査して提示します。


`vpsd` は `table inet wgft` を自分専用に持ち、ルール変更のたびにテーブル全体を 1 トランザクションで差し替える。
他のテーブルには一切触れない。
conntrack のエントリは差し替えの影響を受けないので、既存のセッションは切れない。

接続元制限とレート制限は nat ではなく filter の prerouting に置く。
nat のチェーンはフローの最初のパケットしか通らないので、そこに置いた `drop` は通信中のフローに効かないためです。

```
table inet wgft {
  set deny_1  { type ipv4_addr; flags interval; elements = { 203.0.113.0/24 } }
  set meter_1 { type ipv4_addr; flags dynamic; timeout 1m; size 65535; }
  # 接続元 IP ごとの同時フロー数の上限(7 節の設定値。既定は次の例のとおり UDP 256、TCP 128)。
  # プロトコルごとに 1 つで、そのプロトコルの全ルールが共有する。値を 0 にしたプロトコルには
  # 作らない。timeout は持たせない(ct count と組み合わせると nftables が拒む)
  set flows_udp { type ipv4_addr; flags dynamic; size 65535; }
  set flows_tcp { type ipv4_addr; flags dynamic; size 65535; }
  # source_allow が空でないルールなら、次の set と行が加わる(空なら生成しない。空の set に != を書くと全送信元が落ちる)
  #   set allow_1 { type ipv4_addr; flags interval; elements = { ... } }
  #   iifname != "wg0" udp dport 2456-2457 ip saddr != @allow_1 counter drop

  chain filter_pre {
    type filter hook prerouting priority -150; policy accept;
    iifname != "wg0" udp dport 2456-2457 ip saddr @deny_1 counter drop
    iifname != "wg0" udp dport 2456-2457 ct state new add @meter_1 { ip saddr limit rate over 10/second } counter drop
    iifname != "wg0" udp dport 2456-2457 ct state new add @flows_udp { ip saddr ct count over 256 } counter drop
    # 送信元を読まない集約のレートの行も IPv4 のパケットにだけ一致させる(7a.9 節)。無いと IPv6 のパケットがトークンを使う
    iifname != "wg0" udp dport 2456-2457 ct state new meta nfproto ipv4 limit rate over 100/second counter drop
    # packet_rate を設定したルールの場合(5.3 節の例は null なので、実際には生成しない)
    iifname != "wg0" udp dport 2456-2457 meta nfproto ipv4 limit rate over 5000/second counter drop
    iifname != "wg0" tcp dport 25565 ct state new add @flows_tcp { ip saddr ct count over 128 } counter drop
  }
  chain nat_pre {
    type nat hook prerouting priority dstnat - 1; policy accept;
    iifname != "wg0" udp dport 2456-2457 dnat ip to 10.200.0.2
    iifname != "wg0" tcp dport 25565 dnat ip to 10.200.0.2
  }
  chain input {
    type filter hook input priority filter - 10; policy accept;
    iifname "wg0" ct state new drop
  }
  chain forward {
    type filter hook forward priority filter - 10; policy accept;
    iifname "wg0" oifname "wg0" drop
    oifname "wg0" ct status dnat accept
    # UDP のルールがあるときだけ置く(本節の UDP の応答のカウンタの項目)
    iifname "wg0" meta l4proto udp ct direction reply ct status dnat jump udp_reply
    iifname "wg0" ct state established,related accept
    iifname "wg0" drop
    oifname "wg0" drop
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "wg0" ct status dnat masquerade
  }
  chain udp_reply {
    udp sport 2456-2457 counter return comment "wgft:<ルール ID>:reply"
  }
}
```

- 評価順は deny、allow、接続元ごとの meter、接続元ごとの同時フロー数の上限、新規フローの集約上限、パケットの集約上限、DNAT の順。
  `allow` が空のルール、`packet_rate` が未設定のルールでは対応する行を生成しません。
  `packet_rate` は UDP のデータグラムだけに効くので、TCP のルールでは値が設定されていてもパケットの集約上限の行を作らない([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)「TCP の packet_rate」)
- 判定の行を付けるポートは、カーネルモードのルールのポートと、`vpsd` が待ち受けを開けているプロキシモードのルールのポート([6.2 節](proxy.md#62-プロキシモード))です。
  どちらのポートにも同じ段の行を同じ順で付ける。
  プロキシモードのルールの拒否も、そのため nftables で行われる
- set 名はルール ID ではなく `vpsd` が振る連番を使います。
  古いカーネルの set 名の長さ制限(32 文字)を避けるためです。
  連番は判定の行を付けるポートの順に振るので、プロキシモードのルールも連番を進めます
- meter は集約上限より前に置く。
  送信元を偽装したフラッドで meter の set が `size` まで埋まると、その間は `add` が失敗して接続元ごとの制限だけが外れ、集約上限で守る状態になります。
  順序を入れ替えれば set は埋まらないが、単一の乱用者が集約枠を食い尽くしてから接続元ごとの制限が評価される順になり、正規利用者を守る目的を失うので、この順序と劣化の仕方を採る
- 接続元 IP ごとの同時フロー数の上限は、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の設定値(`WGFT_MAX_UDP_FLOWS_PER_SOURCE`、`WGFT_MAX_TCP_FLOWS_PER_SOURCE`。
  既定 UDP 256、TCP 128)をカーネルモードにも適用します。
  値が 0 のプロトコルには `flows_udp` / `flows_tcp` の set も対応する行も生成しません。
  `flows_udp` と `flows_tcp` はプロトコルごとに 1 つだけ作り、そのプロトコルの有効なルールすべてが同じ set を使います。
  プロキシモードのルール([6.2 節](proxy.md#62-プロキシモード))は DNAT を持たないが、`vpsd` が待ち受けを開けている場合に限り、この上限の行も Admission Policy の他の段の行も持ち、この上限はカーネルモードのルールと同じ `flows_tcp` で数えます。
  bind に失敗したポートに行を置くと、同じポートで待ち受ける別のプロセスへの通信に wgft の上限を掛けてしまうためです。
  適用は 2 段で行います。
  まず新しい待ち受けだけを開き、旧い待ち受けは閉じずに残す(新しい待ち受けはまだ中継しない)。
  次に、残る待ち受けと新しく開けた待ち受けのポートだけを行の対象にして nftables を差し替える。
  差し替えが失敗したら新しい待ち受けを閉じ、旧い待ち受けと旧いテーブルを揃えたまま残します。
  成功したら新しい待ち受けで中継を始め、宣言から消えた待ち受けを閉じます。
  こうすると、差し替えの失敗で、閉じた待ち受けの行だけがテーブルに残ることも、開いた待ち受けに行が無いこともない。
  SQLite には新しいルールが入ったまま差し替えだけが失敗した場合、宣言と実際の転送が食い違うが、次の適用(次のルールの変更、`vpsd` の再起動、30 秒ごとの再試行。
  [7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))で収束します。
  起動時も同じ手順で、bind に失敗したポートは次の適用で開き直し、開けたときに行が付く。
  `vpsd` の中継の側では接続元ごとに数えない(数えると二重になる)。
  set の要素は送信元 IP だけをキーにするため、複数のルールが同じ送信元から `add` しても `ct count` は 1 つの値に合算され、これが「全ルールの合計」を成立させる。
  ルールごとに別の set を作ると合計にならないので、共有が要件です
- この上限も `ct state new` の一致条件を持つ行にします。
  既存のフローの継続パケットは `ct state new` に一致しないため素通りし、既存のフローを追い出すことはありません。
  meter と同じ理由(前項)で集約上限より前、meter と同じ並びに置く
- `ct count` を使う set には timeout を持たせない。
  timeout を持つ set に `ct count` を組み合わせると、カーネルが `Operation not supported` で規則を拒む(ラボで確かめた)。
  要素は conntrack のエントリに従って消える。
  TCP は接続を閉じた後、UDP は conntrack のエントリが消えた後に、送信元の要素が set から消えることをラボで確かめた
- set が `size`(65535)まで埋まると、meter と同じく新しい送信元の `add` が失敗し、その間は接続元ごとの上限だけが外れて集約上限に委ねる劣化になります。
  UDP の meter は短命なトークンバケットの状態を都度作るのに対し、この set の要素は生きた conntrack のフローに紐付くため、埋めるには実際にそれだけのフローを維持する必要があり、埋めにくい
- UDP の `ct count` は conntrack のエントリ数を数えるため、[7 節](../agent-dataplane.md#7-データプレーン自宅側)で述べた `udp_timeout` / `udp_timeout_stream` とエージェント側のセッションタイムアウトの非対称の影響を受ける。
  エージェントがセッションを閉じた後も、そのぶんの conntrack エントリが `udp_timeout` の間は数に残ることがあります。
  既存の非対称と同じ許容範囲とします
- テーブルの差し替えは `flows_udp` と `flows_tcp` を作り直す。
  差し替え前から続くフローは新しい set の数に入らないので、その送信元は差し替えの後にさらに上限まで新しいフローを開ける。
  ラボで、TCP の 128 本を保持したままルールを 1 本足すと、同じ送信元から新しい接続がさらに通った。
  この超過は差し替え前のフローが閉じるまで続く。
  差し替えは、管理者のルールの変更、`vpsd` の起動、wgft の外で変えられたテーブルやインタフェースの公開し直し([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))のほかに、エージェントの登録と公開鍵の変更([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))でも起きる。
  ピアの変更もトランザクションの一部で、トランザクションはテーブルの全体を差し替えるためである([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))。
  公開鍵の変更は、そのエージェントの恒久トークンの持ち主が起こせるので、攻撃者から起こせない差し替えとは言えない。
  差し替えはテーブルの全体に及ぶので、鍵を変えたエージェントのルールだけでなく、全エージェントのルールの meter と `flows_udp`/`flows_tcp` が作り直される。
  超過は 1 回の差し替えにつき上限 1 つ分で、差し替えを重ねると重なる。
  ラボで、別のエージェントが鍵を変えるたびに、同じ送信元が上限 1 つ分ずつ多くの TCP のフローを保持できた。
  恒久トークンの持ち主が起こせる差し替えの回数は、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の鍵の変更の頻度の上限で抑えます。
  この上限と、エージェントのルールごとの上限([7 節](../agent-dataplane.md#7-データプレーン自宅側))がその外側で効くので、許容します。
  set を差し替えの対象から外すには上限の行を別のテーブルに分ける必要があり、差し替えの原子性を失う。
  ピアだけを変えるトランザクションでテーブルを差し替えない形は [13 節](../roadmap.md#制限と未実装の提案)に残します
- 落としたパケットのカウンタは、ほかの行と同じ `wgft:<ルール ID>:src_flow` という形式のコメントを付け、既存の drop カウンタと同じ経路(本節の最後の項目)でルールごとに累積します。
  上限は全ルールで共有するため、この累積値は「そのルールの行が拒んだ回数」であり、送信元がどのルールで最初に上限へ達したかを示す近似値になります
- `ct count` は nftables 0.9.0 と Linux カーネル 4.19.10 以降が必要である(nftables wiki の記述による)。
  対応する最小構成の Debian 12(kernel 6.1、nftables 1.0.6)のラボで動作を確かめた
- DNAT では宛先アドレスだけを書き換え、ポートは書き換えない。
  エージェントは VPS と同じポートで待ち受け、`target` のポートへの写し替え([5.3 節](../control/rules.md#53-ルールのスキーマ)の連番)はエージェント側で行う([7 節](../agent-dataplane.md#7-データプレーン自宅側)の実効宛先)
- 公開インタフェース名を特定せず `iifname != "wg0"` で書きます
- nat prerouting の優先度を `dstnat - 1` にして、既存の nat チェーンより先に評価されるようにします。
  先に評価されるのは標準の優先度(`dstnat`。
  iptables の nat、firewalld、Docker が使う)のチェーンに対してだけで、それより小さい優先度(-199 まで付けられる)のチェーンには負ける。
  そのため後述の「他テーブルの同じポートの DNAT」の検査は優先度に関係なく行います
- input で wg0 からの新規接続を全部落とす。
  `vpsd` が wg0 上で待ち受けないので([4 節](../network.md#4-ネットワーク))、VPS 上の他サービスが wg0 から見える経路をここで塞ぐ
- forward では、先頭でピア同士の通信を遮断し、DNAT 済みのフローとその返りを通した後、wg0 が絡む残りの転送をすべて落とす。
  対象は wg0 から VPS の他のインタフェース(private NIC、別の VPN)へ出るフローと、他のインタフェースから wg0 へ入る DNAT 以外のフローです。
  これにより、既存のファイアウォールの forward が accept のままの VPS でも、認証情報を盗んだピアが VPS の内側のネットワークへ届かない。
  wg0 が絡まない転送には触れない
- masquerade は DNAT された接続に限定し、VPS 自身の通信には触れない
- UDP のルールごとに、応答のカウンタの行を通常のチェーン `udp_reply` に 1 つ置く([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor)「UDP の応答の観測」)。
  forward の入口の行が、wg0 から戻る DNAT 済みの UDP の応答だけを `udp_reply` へ送るので、他のパケットは 1 行の評価で抜ける。
  `udp_reply` の行は応答の送信元ポートでルールを見分ける。
  DNAT はポートを書き換えず、forward の時点では応答の送信元の逆変換(postrouting で行う)がまだ済んでいないので、送信元ポートは公開ポートのままです。
  行が持つ判定は、入口のチェーンへ戻る `return` だけであり、転送の結果を変える判定を持ちません。
  wg0 から戻る UDP の応答は、パケットごとに `udp_reply` の行を順に評価します。
  行は UDP のルールごとに 1 つなので、この費用は UDP のルールの数に比例し、公開側から入るパケットがルールごとの判定の行を評価する既存の費用と同じ桁です。
  この費用が問題になれば、送信元ポートから名前付きのカウンタを引く map にすれば、ルールの数に依らない 1 回の検索にできます。
  宛先が返す ICMP の誤りは同じ conntrack のエントリの応答の向きに一致するが、`meta l4proto udp` で外す。
  コメントは `wgft:<ルール ID>:reply` とし、drop の行とは別のチェーンに置くので、次の項目の drop の累積に混ざらない。
  カウンタは差し替えで 0 に戻るので、drop のカウンタと同じく差し替えの直前に読みます。
  UDP のルールが無ければ、チェーンも入口の行も作りません
- 各 drop のカウンタは、テーブル差し替えの直前に `vpsd` が読み、差し替えが成功したときだけ SQLite に累積します。
  差し替えが失敗すると旧いテーブルがカウンタを持ち続けるので、次の成功した差し替えの直前にもう一度読まれ、1 回だけ累積される([7a.2 節](../architecture/model.md#7a2-層と責務))。
  commit の後の応答の受信に失敗した場合([6.1 節](kernel.md#61-カーネルモード)の受信側の壁)と、差し替えの後の送信元の一覧の set の検査(本節)に失敗した場合だけは、テーブルが差し替わった後で失敗と判断するので、その回に読んだ分は累積されずに失われる。
  meter の状態は差し替えでリセットされるが、短時間のすり抜けにとどまるので許容します

テーブルの差し替えは、nftables のバッチ 1 つ、つまり netlink のデータグラム 1 つとして送る。
カーネルの `nfnetlink_rcv_batch` は 1 つの skb の中だけでバッチを読むので、`NFNL_MSG_BATCH_BEGIN` から `NFNL_MSG_BATCH_END` までを複数のデータグラムに分ける余地はありません。
差し替えの不可分性はこの 1 つのデータグラムが担う。
大きなルール集合をデータグラムごとに分ける案は、分けた時点で別のトランザクションになるので採らない。

そのため、バッチ自身の長さと、カーネルが返す応答の量の両方が、1 つの netlink ソケットのバッファに収まらなければなりません。
応答は 2 種類あります。
バッチの 1 通ごとに返る ACK と、ルールの追加に立つ `NLM_F_ECHO` に対するルールの写しです。
`vpsd` はバッチを送り終えてから応答を読み出すので、応答は受信キューに積み上がる。
既定のバッファのままだと、ルール数を増やしたときに 2 つの壁に当たる。

- 受信側の壁:応答が `sk_rcvbuf` を超えると、カーネルは ENOBUFS を立てて応答を捨てます。
  応答はバッチの commit の後に送られるため、テーブルは差し替わっているのに `vpsd` は失敗と判断します
- 送信側の壁:バッチの長さが `sk_sndbuf` を超えると、sendmsg が EMSGSIZE で拒みます。
  カーネルには何も届かないので、旧いテーブルがそのまま残る

`vpsd` はテーブルを組み立てながらバッチのメッセージ数と長さを数え、送る直前に、その大きさに合わせた送信側と受信側のバッファを要求します。
受信側には 1 通ごとの ACK の分を上乗せします。
要求する値の下限は 1 MiB、上限は 64 MiB です。
`nft` コマンドも同じ手順を取り、バッチの長さと命令の数からバッファを決めてから 1 回の sendmsg で送る。

要求は `SO_SNDBUFFORCE` と `SO_RCVBUFFORCE` で行い、権限が足りなければ `SO_SNDBUF` と `SO_RCVBUF` に落ちる。
前者は init の user namespace での CAP_NET_ADMIN を必要とします。
`deploy/server.service` はこの権限を与えるので、systemd から動かす VPS では要求が通る。
user namespace を分けた非特権のコンテナは、自分の netns の nftables を操作できても FORCE の側は拒まれ、`SO_SNDBUF` と `SO_RCVBUF` に落ちる。
落ちた配置では `net.core.rmem_max` と `net.core.wmem_max` の 2 倍が上限になり、壁は既定の 2 倍ほど遠のくだけで残る。
ラボでは `unshare --user --map-root-user --net` の中でカーネルモードの `vpsd` を動かして確かめた。
WireGuard のインタフェースの作成、`net.ipv4.ip_forward` の書き込み、テーブルの適用は通る。
両方の sysctl が既定の 212992 のとき、1 回の `rule import` は 120 本まで適用でき、125 本で ENOBUFS になり、500 本からは EMSGSIZE になった。
両方を 8388608 にすると 2000 本まで適用できた。
この 2 つの sysctl は network namespace ごとの値ではなく、ホスト全体で 1 つです。
分けた namespace の中での見え方はカーネルによって違う。
Debian 12 のカーネル 6.1 と Ubuntu 24.04 のカーネル 6.8 では、分けた namespace の中の `/proc/sys/net/core` に現れない。
Ubuntu のカーネル 6.17 と Fedora 44 のカーネル 7.2 では、初期の network namespace の値が読み取り専用で現れ、root が書き込んでも拒まれる。
6.8 と 6.17 は非特権の Incus のコンテナで確かめ、6.17 のコンテナに現れる値はホストの値の変更をそのまま追った。
6.17 のコンテナの root が実行した `sysctl -w` は `Invalid argument` を表示したが、終了コードは 0 だった。
どのカーネルでも、値を変えられるのは初期の network namespace の側だけです。
文書にある配置で当てはまるものはありません。
コンテナの配置はユーザー空間モードだけを対象にしている(`deploy/server.compose.yaml`)。

確かめた範囲は Debian 12 のラボです。
1 回の `rule import` による 1000 本と、1 本ずつの `rule add` による 1000 本のどちらも適用でき、10 本から 1000 本までのすべての段で転送が通った。
適用だけなら 2000 本まで通った。
2000 本を超える規模は確かめていません。

この壁で適用が失敗したときの意味論は、他の差し替えの失敗と同じです。
失敗した世代は active になりません。
ENOBUFS の場合は実際のテーブルだけが新しい世代に進むので、`vpsd` が持つ active な世代と食い違う。
この食い違いは [7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)の「実際の状態への収束」が拾い、`Observe` がテーブルの指紋の違いを drift として報告し、次のトランザクションを起こす。
ただし、そのトランザクションが公開し直すのは Desired であり、直前に成功していた世代ではありません。
Desired が壁を越える大きさのままなら、公開し直しは同じ壁で同じ失敗を繰り返します。
繰り返しに終端は無く、運用者が Desired を小さくするか、バッファの上限を引き上げるまで続く。
食い違っている間も、DNAT の宛先のエージェントが新しいルールを受け取っていないため、新しい世代のポートへの転送は通らない。
新しい宣言にも同じ内容で残っているルールの転送は続く。
新しい宣言から外れたルールの転送は、テーブルが既に差し替わっているので続かない(改訂の記録 2026-09-23)。

繰り返しの間、運用者から見える手掛かりは薄い。
`vpsd` は同じ文言の誤りを繰り返し出さないので([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))、ログは最初の 1 行で止まります。
`wgft rule ls` の表は適用の状態を持たないため、何も異常を示さない。
食い違いが出たことを示すのは、`rule ls --json` の `active_generation` と `desired_generation` の差、`rule_states` の `apply_state`、および Web UI の「反映待ち」の表示です。
drift を見つけた後は、宣言の変わっていないルールも含めて `apply_state` が `pending` になります。
カーネルへの通知を受け取るソケットも同じ受信側の壁に当たりうるので、繰り返しを進めるのは主に 30 秒ごとの再試行です。

起動時の最初の適用([9 節](../state.md#9-状態の保存と再起動))が同じ壁に当たった場合の扱いは、稼働中の再試行とは違う。
起動時の最初の適用が失敗しても、プロセスは終了しません。
管理用 API だけを開いて起動の残りを止め、30 秒ごとに適用を試し直す([11b 節](../security/startup.md#11b-起動の失敗の意味論)の起動の保留)。
運用者は `wgft rule rm` か `wgft rule disable` で Desired を小さくでき、適用が成功した時点で起動の残りに進む。
2026-09-22 まではこの失敗が終了コード 1 で終わり、管理用 API がこの適用より後に開くために回復の経路そのものが失われていました。

送信元の一覧(`source_deny`、`source_allow`)の set の要素は、1 通の `NFT_MSG_NEWSETELEM` にまとめずに、複数の通に分けて同じバッチで送る。
1 通の要素は `NFTA_SET_ELEM_LIST_ELEMENTS` という 1 つの入れ子の属性に入ります。
netlink の属性の長さは 16 ビットなので、この属性は 65535 バイトを超えられない。
依存する google/nftables と mdlayher/netlink は超えたことを検査せず、長さの下位 16 ビットだけを書きます。
カーネルはその短い長さの分だけを要素として読むので、要素の欠けた set が誤りなく公開される(改訂の記録 2026-09-24)。
`vpsd` は 1 通の要素の一覧を 32 KiB 以下にし、区間の開始と終端の印を同じ通に入れる。
分けた通も同じバッチの中にあるので、差し替えの不可分性は変わりません。
set には大きさ(`NFTA_SET_DESC_SIZE`)を付けないので、カーネルは要素の数を制限しません。

差し替えの後、`vpsd` は送信元の一覧の set をカーネルから読み直し、送った要素と比べる。
要素の数か中身が違えば、その差し替えを backend 全体の失敗とする([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論))。
テーブルは既に差し替わっているので、扱いは受信側の壁の ENOBUFS と同じです。
失敗した世代は active にならず、読み直したテーブルを `Observe` の基準にもしません。
差し替わったテーブルは drift として報告され、公開し直しが同じ検査で失敗を繰り返します。
繰り返しの間隔は、30 秒を上限に失敗のたびに倍になる([7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)の再試行)。
この間は要素の欠けた set が転送に効いています。
`source_deny` が欠ければ拒むはずの送信元が通り、`source_allow` が欠ければ許すはずの送信元が落ちる。
要素を分けて送る組み立てでは、この食い違いは起きない想定です。
読み直しは、同じ種類の取りこぼしが別の経路で起きた場合に、それを成功として扱わないための検査です。
運用者には、他の backend 全体の失敗と同じく、`apply_error` とルールの `pending` の理由で示します。
どちらも食い違った set の名前と、読み直した set の要素の数と送った数を含む。
この数は一覧の CIDR の数ではなく、区間ごとの開始と終端の印を数えた set の要素の数です。

`vpsd` は起動時に `net.ipv4.ip_forward` を確認し、1 でなければ 1 にします。
これは firewalld や nftables の設定ではなくカーネルの sysctl で、Docker や firewalld(masquerade を使うゾーン)も同じように 1 にします。
転送する以上ここに正しい値は 1 の一つしかなく、他に異論を持つ主体がいない設定なので、ポート開放や `policy drop`(提示だけして触らない、後述)と違い `vpsd` 自身が設定します。
手順は次のとおり。

- まず現在値を読みます。
  すでに 1 なら何も書きません。
- 0 なら 1 にし、書けたことをログに残す(起動のたびに黙って上書きしない)。
- 書き込みに失敗しても `vpsd` は落ちない。
  読み取り専用の `/proc` や seccomp/LSM で `/proc/sys` への書き込みが塞がれていても、値がすでに 1 なら問題なく動く。
  0 のまま書けない場合は、`policy drop` の提示と同じ流儀で「`net.ipv4.ip_forward=1` にせよ」という警告を残して起動を続けます。
- 値を読めず、書けもしない場合は、0 とは言わず、読めなかった誤りと書けなかった誤りの両方を示す警告にする(2026-10-03)。
  値が分からないので、転送が動かないかもしれないことと、`sysctl net.ipv4.ip_forward` で値を見て 0 なら `sysctl -w net.ipv4.ip_forward=1` にする手順を案内します。
  起動は続けます。
- この警告は他テーブルの `policy drop` の提示と同じ起動時 Findings として UI とログに出し、単なるログ 1 行にとどめない。
  カーネルモードのルールが 1 つも無いとき(プロキシ専用やルール 0 件)も同じ警告を出す。
  Findings は起動時に 1 回だけ作り、ルールは起動後に追加できるので、起動時の件数で警告を弱めると、追加した時点で転送が動かない理由が見えなくなるためです。
- いったん 1 にした値を 0 に戻すことはありません。
- 稼働中に外から 0 にされた値を、`vpsd` は 1 に戻さない (2026-09-25、所有者の決定)。
  1 にするのは起動時だけです。
  理由は 3 つあります。
  第 1 に、稼働中に 0 にするのは運用者か、運用者が置いた sysctl の設定や堅牢化のスクリプトの明示の操作であり、`vpsd` が黙って書き戻すとその操作と争う。
  第 2 に、sysctl の変更には通知が無いので、戻すには定期的な読み取りと書き込みを常駐させることになります。
  第 3 に、エージェントのカーネルモードも 30 秒ごとに値を読み直すが、戻さずに報告だけする ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの)) ので、両側で扱いが揃う。
  そのかわり、0 にされたことを黙らせない。
  管理用 API はカーネルモードの server の今の値を返し ([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))、`server doctor` はカーネルで転送する公開中のルールがあれば FAILED とし ([10.2a 節](../diagnosis/server-observations.md#102a-転送の診断-server-doctor))、`wgft status` は Server 行を degraded とし ([10.2b 節](../status.md#102b-状態の要約wgft-status))、Web UI は今の値を示し ([10.1 節](../interface.md#101-web-ui))、`server check` は書ける場合も所見にします。
  戻す手順は、`sysctl -w net.ipv4.ip_forward=1` か server の起動し直しです。
  ただし書き込みが塞がれている場合は、起動時の書き込みも同じ原因で失敗するので、起動し直しでは直らない。
  `server doctor` の案内は再起動を勧めず、塞ぐ原因を除いてから `sysctl -w` で 1 にすることを述べる(2026-10-03)

conntrack の表の上限(`net.netfilter.nf_conntrack_max`)は `vpsd` が変えません。
転送するフローは 1 本につき表の 1 件を使い、表が埋まるとカーネルはホスト全体の新規接続を落とす。
上限はメモリの量から決まり、小さい VPS では 16384 のような値になります。
`server check` は現在の件数と上限を表示し、上限が 65536 未満なら、上げる sysctl と `new_flow_rate` の設定を提示します。
`new_flow_rate` と `per_source_rate` の drop は prerouting の優先度 -150 で行われ、その時点のフローはまだ表に登録されていないので、落としたフローは表を消費しません。
- `vpsd` が 0 を読んで 1 にするときは、状態ファイルの meta に 2 段の記録を残す(2026-10-03、所有者の決定)。
  撤去([10.3 節](../operations/setup.md#103-運用の流れ))のとき、運用者に「`vpsd` が変えたので戻す候補」か「元から 1 だった」かを具体的に示すためです。
  予定の記録は「この日時に `vpsd` が値 0 を読み、1 を書き始めた」という記録であり、書けたかどうかは述べない。
  確定の記録は「この日時に `vpsd` が 0 を 1 に書き換えた」という記録であり、管理用 API の `ip_forward_set_at` はこの記録だけを返す([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
  手順は次のとおりです。
  1. 値を読みます。
     1 なら何も書かず、記録も変えません。
     前の起動の予定の記録が残っていても消さない。
     前の起動が書いたかもしれない証拠だからです
  2. 値を読めなければ 1 を書き、どちらの記録も残さない。
     0 だったとは言えないためです。
     書けなければ、0 とは言わず、読めなかった誤りと書けなかった誤りを示す Finding を出す
  3. 0 なら、書く前に予定の記録を保存します。
     保存できなければ警告をログに出し、値は書きます。
     記録は撤去の案内にだけ使い、転送には効きません。
     記録できないことで値を書かずにおくと、サーバのデータベースに書けない間は転送が戻りません。
     転送が落ちたままになることのほうが悪い([11b 節](../security/startup.md#11b-起動の失敗の意味論))
  4. 1 を書きます。
     書けなければ、「0 のまま書けない」ことを示す起動時の Finding を出し、予定の記録を消す。
     消せなければ警告だけを出す。
     残った予定の記録について、撤去は今の値を添えて示します
  5. 書けたら、確定の記録の保存と予定の記録の削除を 1 つのトランザクションで行います。
     失敗すれば警告を出し、予定の記録が残る

  記録を 2 段にする理由は、1 段の記録ではどちらの順序でも、止まる時点によって誤った記録が残ることにあります。
  書いた後に記録する形では、書いた直後に止まるか記録に失敗すると記録が欠け、撤去は `vpsd` が 1 にした値を「変えていない」と示します。
  2026-10-03 までの実装はこの形だった。
  書く前に記録する形では、書く前に止まるか、書けずに記録の取り消しにも失敗すると、撤去は変えていない値を「変えた」と示し、運用者に 0 へ戻すよう勧める。
  その間に別の仕組みが 1 にしていれば、その転送を止めます。
  2 段の記録では、これらの場合に予定の記録だけが残り、撤去は「変えたかもしれない」と今の値を示して、判断を運用者に任せる。

  0 を読んで 1 を書き、手順が 5 まで進んだ場合に、どちらの記録も残らないのは、3 と 5 の両方が失敗したときだけです。
  この場合は起動時の Finding で、`vpsd` が値を 1 にしたことと、撤去がそれを知らないかもしれないことを示します。
  3 だけが失敗して 5 が成功した場合は、確定の記録が残るので Finding は出さず、3 の警告がログに残る。
  3 が失敗して値を書いた後、5 の前に止まった場合も記録は残りません。
  このときは 3 の警告がログに残るだけで、Finding は出ない。

運用者が sysctl を自分で管理していても、その管理も 1 にするのが普通なので衝突しません。
値を触られたくない配置では 1 にしておけば `vpsd` は読むだけになります。
この振る舞いで足りるため、設定するかを切り替えるフラグは持ちません。
1 にすると VPS はルータとして振る舞える状態になります。
wgft 以外の転送を止めるのは既存のファイアウォール(ufw、Docker、firewalld の既定の drop / reject)の役目で、`wgft` の forward チェーンは自分の DNAT 済みフローを accept するだけで他の転送を drop しません。
ファイアウォールのない VPS では、VPS を経由するよう仕向けられたパケットが転送されうるが、公開 IP が 1 つの VPS では現実にはほぼ起きない。

conntrack の操作は「宣言状態に収束させる」1 手順だけを持ちます。

1. `status` に DNAT フラグが立ち、orig 側の宛先が `10.200.0.0/24` の外で、かつ reply 側の送信元が `10.200.0.0/24` のエントリをすべて Dump します。
   外から入って DNAT されたフローだけが対象になり、`vpsd` 自身が wg0 へ張ったフロー(プロキシモードの中継、疎通確認)は最初から含まれない
2. 各エントリについて、現在有効なカーネルモードのルールのいずれかで、その proto と宛先ポートが DNAT され、エントリの reply 側の送信元(アドレスとポート)がそのルールの DNAT 先と一致し、かつ送信元が `source_deny` に含まれず `source_allow` を満たすかを判定します。
   DNAT 先を見るのは、ルールの `agent` を変えたとき旧エージェントへの既存フローを消すためです
3. 満たさないエントリを削除します

収束は nftables テーブルの差し替えの後に走らせる。
先に走らせると、旧テーブルで許可されたフローが差し替えまでの間に入ります。
起動時の突き合わせも同じ順序です。
手作業で nftables を触られた場合も、この手順で不要なフローが拾える。
フロー数は多くないので、毎回全走査でよい。

契機は次の 3 つです。

- ルールテーブルまたは接続元制限への書き込みが 1 件でもあったとき(フィールドの種類を問わない)
- エージェントの削除
- `vpsd` の起動時(手作業で nftables を触られた後の復旧のため)

契機を変更の種類ごとに列挙しません。
編集できるフィールドが増えるたびに漏れるためです。

起動時と `rule add` 時に次を検査し、問題があれば警告します。
自動では書き換えない。

- `ip` `ip6` `inet` の全ファミリで forward フックの base chain を列挙し、`policy drop` があれば、そのチェーンに足す 2 行(`oifname "wg0" accept` と `iifname "wg0" ct state established,related accept`)を提示します。
  ufw の残骸が `ip filter FORWARD` にある場合もこれで拾う。
  この手作業は 1 回きりでポートに依存しません
- input フックの base chain で `ct state established` が accept されているかを確認し、されていなければ提示します。
  `vpsd` から wg0 経由で張る接続の返りが通るために必要です
- 他テーブルの nat prerouting チェーンに同じポートの DNAT があれば、そのルールの追加を拒否します。
  ポートが multiport や読めない無名 set、未知の式の形で判定できない規則は、拒否せずに Finding として警告します。
  黙って見逃すと、優先度で先に評価される wgft の DNAT(`dstnat - 1`)がそれと知らずに勝つため
- VPS 上で bind 中のポートとの衝突は [5.3 節](../control/rules.md#53-ルールのスキーマ)のとおり拒否します

`vpsd` 自身が待ち受ける 2 つのポート([4 節](../network.md#4-ネットワーク)の WireGuard の UDP とエージェント用 API の TCP)も、
起動時と `server check` で input フックの `policy drop` を検査し、塞がれていれば
`udp dport <port> accept` / `tcp dport <port> accept` を提示する(実機の Debian 13、input が
policy drop で SSH の TCP 22 しか accept していない構成で見つかった。
改訂の記録参照)。
host の input firewall はデータプレーンのモードに関係しない層なので、ユーザー空間モード
([6.3 節](userspace.md#63-ユーザー空間モード))でも同じ検査を行います。
管理用 API(既定 Unix ソケット。
[5 節](../control/README.md#5-制御プレーン))は対象から外す。
外部に公開しない設計であり、host の input を開ける提示を出す理由が無いためです。
