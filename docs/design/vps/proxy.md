### プロキシモード

プロキシモードは TCP の接続を server のプロセスで中継します。
PROXY protocol は明示したルールだけで使用します。


`vps_mode = proxy` のルールは、`vpsd` が Go の TCP リスナー(IPv4 だけで開きます。
[7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ))で受け、wg0 経由でエージェントの `10.200.0.x:listen_port`(エージェントが開いているリスナー)へ接続して中継します。
`proxy_protocol = true` なら接続先に PROXY protocol v2 ヘッダを先頭に送る。

公開ポートごとの accept ループが、受け付けた接続の Admission Policy と Resource Guard をこの順に同期して判定します。
予算の取得前に接続ごとの goroutine は作らず、判定中の公開側ソケットはポートごとに高々 1 個を保持します。
停止中のポートも数に含め、同じポートの古い accept ループが終了するまで新しいループを開始しません。
停止は判定中のソケットを閉じ、停止と、予算取得直前の確認・取得・引き渡しを同じ排他で順序付ける。
停止した接続がその後の予算取得で資源不足の拒否に数えられることも防ぐ。
引き渡し済みの接続は、その処理が終わるまで既存の予算を保持します。
複数ポートを止めるときは全ポートへ停止を要求してからループの終了を待つ。
同期したポリシー判定そのものは中断できないため、停止と設定適用の完了時間の上界は保証しません。
判定を待つ間の追加接続はカーネルの listen backlog で待ち、溢れると接続の遅延や失敗になりうる。
処理できた拒否は従来どおり RST で閉じます。
これは予算取得前の保持の制限であり、カーネルのソケットのメモリを含むプロセス全体のメモリ上界ではありません。
既に引き渡されて接続中の処理について、Retire と接続元制限だけの変更では接続完了時のポリシー再判定を行わない既存の制約が残ります。
ユーザー空間モードでは、接続中の処理から中継中か失敗後の配送中への登録と、接続中の数を減らす操作を同じ排他で行います。
接続中に停止や実効宛先の変更があれば、接続とヘッダの処理が戻った後に両側を意図した切断の順序で閉じ、配送待ちを登録しません。
引き渡し済みの dial は停止が先に起きても 1 回行い、接続やヘッダの書き込みそのものを中断する機能や期限は追加しません。
通常の失敗で配送を登録するときも、先に起きた Retire と接続元制限だけの変更は再判定しません。
登録後の再判定と切断は配送中の組に作用し、待ちを起こします。

プロキシモードのルールも、カーネルモードのルールと同じ Admission Policy のすべての段を受ける([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ))。
段を評価する場所はモードで決まる。
カーネルモードでは、`vpsd` が待ち受けを開けているポートの行を nftables が評価する([6.1 節](kernel.md#61-カーネルモード))ので、レートと接続元ごとの同時フロー数で拒んだパケットはリスナーに届かない。
この場合、中継に残るのは deny と allow による状態を持たない確認だけで、その拒否は drop カウンタに数えません。
ユーザー空間モードでは、中継が Go の評価器([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ))を受け付け時に呼び、IR の `Order` の順(deny、allow、`per_source_rate`、接続元ごとの同時フロー数の上限、`new_flow_rate`、`packet_rate`)に判定し、拒んだ段の drop カウンタを数えます。
プロキシモードのルールは TCP なので、`packet_rate` の段はどちらのモードでも効かない([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)の「TCP の packet_rate」)。
中継はハーフクローズを保ち、片方向の EOF は `CloseWrite` で反対側に伝え、両方向が閉じたら両側を通常の `Close` で閉じて中継を終える。
片方向が EOF 以外で終わったとき、つまり読み取りが RST などの誤りで失敗したときと書き込みが失敗したときは、ハーフクローズとして扱わず、すぐに両側を通常の `Close` で閉じて中継を終える。
ハーフクローズとして扱うと、反対向きは黙ったままの相手を読み続けるので、相手が閉じるまで接続と同時フロー数の枠が残る。
公開側のクライアントの RST で終わったとき、つまり公開側の接続の読み取りか書き込みが RST(`ECONNRESET`)で失敗したときだけは、エージェントへの接続を通常の `Close` ではなく RST で切る。
切り方は後述の中継を閉じるときと同じで、公開側の接続は通常の `Close` で閉じます。
エージェントへの接続を FIN で閉じると、エージェントの中継はハーフクローズとして扱うので、FIN を受けても閉じない宛先では、エージェント側の宛先への接続と同時フロー数の枠が宛先が閉じるまで残る。
カーネルの TCP 同士の中継(カーネルモードのプロキシのルール)は、RST による誤りが公開側とエージェント側のどちらの接続のものかを区別できないので、どちらの場合もエージェントへの接続を RST で切る。
誤りがエージェント側の接続のものなら、その接続は RST を受けて既に閉じた状態にあり、RST で切っても何も送らない。
これは Linux のコードから導き、network namespace の Tcp OutRsts の計数器が増えないことでも確かめた。
パケットのキャプチャでは確かめていません。
EOF とハーフクローズ、後述の中継の側からの切断、エージェント側から届いた RST の扱いは変えません。
この規則は同じ部品(`internal/netpipe`)を使う [6.3 節](userspace.md#63-ユーザー空間モード)と [7 節](../agent-dataplane.md#7-データプレーン自宅側)の中継にも効く。
ただし [7 節](../agent-dataplane.md#7-データプレーン自宅側)のエージェントの中継では、宛先への接続が実ソケットなので、トンネル側の RST で終わったときも宛先への接続を通常の `Close` で閉じます。
通常の `Close` は接続を閉じた時点で資源を解放するとは限りません。
ユーザー空間モードは[末尾を届け終えるまで](../userspace/tcp-retention.md#中継が終わった後の末尾の配送)組を管理し、同時フロー数に数えます。
カーネルモードの `vpsd` の Relay の中継は終わりに枠を返し、送り残しを持つソケットはカーネルに残ります。
同時に中継する接続の数は、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の「同時フロー数の上限」の TCP の値(ルールごと、プロセス全体、接続元 IP ごと)で抑え、拒んだ接続は accept の直後に閉じます。
ルールごとの上限と最低分は、プロセス全体の予算を共有するプールが判定する([7a.10 節](../resource/admission.md#7a10-resource-guard-の再設計))。
カーネルモードでは、接続元 IP ごとの数だけは中継ではなく [6.1 節](kernel.md#61-カーネルモード)の `flows_tcp` で、カーネルモードのルールと合わせて数えます。
ユーザー空間モードでは、接続元 IP ごとの数を Go の評価器が、[6.3 節](userspace.md#63-ユーザー空間モード)の中継の TCP の接続と合わせて数え、上限で拒んだ接続を `src_flow` の drop に数えます。
どちらのモードでも、接続元 IP ごとの上限はルールごととプロセス全体の上限より先に判定します。
接続元制限、レート、同時フロー数の上限のどの拒否も、accept の直後、まだデータをやり取りしていない接続を `SetLinger(0)` の RST で即座に閉じ、通常の Close によるグレースフルクローズ(FIN、TIME_WAIT)にはしない([6.3 節](userspace.md#63-ユーザー空間モード)、[7 節](../agent-dataplane.md#7-データプレーン自宅側)と同じ考え方)。
フラッドの間に不要な TIME_WAIT の TCP 状態を大量に残さず、その分のカーネル資源を保持し続けないためで、成立した中継の通常のクローズ(前段のハーフクローズ)は変えません。
カーネルモードでは、レートと接続元ごとの同時フロー数で拒む接続は nftables がパケットを捨てるので、クライアントには RST ではなく時間切れとして見える([7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ)の許容差)。

進行中の中継を閉じる契機は次のとおり。
conntrack の操作([6.1 節](kernel.md#61-カーネルモード))は `vpsd` 自身のソケットには効かないので、別の部品として持ちます。

- ルールの削除と `enabled = false`:リスナーと進行中の全中継を閉じます
- 実効宛先の変更:リスナーは残したまま、そのリスナーの進行中の全中継を閉じます
- 接続元制限の変更:条件を満たさなくなった接続元の中継を閉じます
- エージェントの削除:そのエージェント宛の全中継を閉じます

中継を閉じるときは、エージェントへの接続を RST で切る。
カーネルモードの接続は実ソケットなので `SetLinger(0)` の後に閉じ、ユーザー空間モードの接続は netstack の接続なので `Abort` で切る。
公開側の接続は通常の `Close` で閉じます。
FIN で閉じると、エージェントの中継はそれをハーフクローズとして扱い、宛先へ FIN を送った後も宛先からの読み取りを続けるので、FIN を受けても閉じない宛先では、エージェント側の宛先への接続と同時フロー数の枠が宛先が閉じるまで残る。
RST を受けたエージェントの中継も、前述の規則で終わった後の末尾を届け終えるまで枠を保持します。
エージェントへの接続を先に切るのは、公開側を先に閉じると、中継がその読み取りの失敗を受けてエージェントへの接続を通常の `Close` で閉じ、RST の前に FIN が出ることがあるためです。

実効宛先は、ルールを割り当てたエージェントのトンネルのアドレスと、エージェント側の待ち受けポートの組です。
ルールを別のエージェントへ移した場合と、エージェントのトンネルのアドレスが変わった場合に変わる。
成立済みの接続は accept の時点の実効宛先へ張った上流の接続を持つので、宣言の値を書き換えても新しいエージェントへは向かない。
[7 節](../agent-dataplane.md#7-データプレーン自宅側)の収束の表の「実効宛先が違う:閉じてから開きます。
セッションは切れる」と同じ扱いであり、`vpsd` 側のリスナーを開き直さない点だけが異なる。
開き直しの bind が失敗する余地を残さないためで、この点は [6.3 節](userspace.md#63-ユーザー空間モード)の中継と同じです。
所属ルール ID だけが変わった場合と、`proxy_protocol` だけが変わった場合は中継を閉じない。
[7 節](../agent-dataplane.md#7-データプレーン自宅側)の表が所属ルール ID の変更でセッションを残すと定めており、`proxy_protocol` のヘッダは接続の先頭で 1 回だけ送るものなので、成立済みの接続に後から付ける手段が無いためです。

公開ポートの accept が、リスナーを閉じた場合以外の理由で失敗したときは、リスナーを開いたまま後退して試し直し、失敗をリスナーごとに 1 分に 1 回までログに出す。
失敗が続く間も、ルールの状態は変えず、ログだけで知らせる。
ファイル記述子の枯渇のような失敗で accept をやめると、ソケットは bind されたまま新しい接続を受け付けない状態で残る。
適用はそのポートを開いているものとして扱い、リスナーを開き直さないので、`vpsd` を再起動するまでそのポートの中継が戻りません。

このモードは `vpsd` 自身が待ち受けるので、既存ファイアウォールの input チェーンでそのポートが通る必要があります。
`rule add` 時に input フックの base chain に `policy drop` があれば、必要な行(`tcp dport <port> accept`)を提示します。
`server check` も、保存済みの全ルールのうち有効なプロキシモードのルールについて同じ検査を行います。
Transparent なルールは他テーブルの DNAT と forward を経由し input を通らないため対象にしません。

用途は接続元 IP を自宅側の Caddy に伝えたい HTTPS で、UDP には使いません。
