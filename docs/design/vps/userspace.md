### ユーザー空間モード

VPS のユーザー空間モードは、wireguard-go と netstack のトンネルから中継します。
フローの予算とソケットの条件は、ユーザー空間の共通仕様に従います。


`WGFT_MODE=userspace` は、VPS 側にも root、カーネル WireGuard、nftables を要求しない動作モードです。
`vpsd` は自宅側と同じ wireguard-go と gVisor の netstack でトンネルを持ち、公開ポートを自分のソケットで受けて netstack 越しにエージェントへ中継します。
root の取れない VPS、OpenVZ 系や LXC ベースの VPS、compose で全部を管理したい人のための選択肢で、カーネルモードを置き換えるものではありません。
モードは `vpsd` 全体で 1 つであり、ルール単位で混ぜません([11a 節](../security/configuration.md#11a-設定の渡し方)の記録と照合)。

構成は次のとおりです。

- サーバ側トンネル:wireguard-go の `device` と、エージェントと共通の netstack の TUN(`internal/nettun`、[7 節](../agent-dataplane.md#7-データプレーン自宅側))で、`listen_port` を開き `10.200.0.1` を持ちます。
  サーバ鍵は SQLite の同じ鍵を使います。
  ピアの追加と削除は `IpcSet`(`public_key`、`allowed_ip`、`remove`)で行います。
  エンドポイントは原則として指定せず、エージェントのハンドシェイクで学習します。
  例外は鍵の置き換えで、新しいピアには [5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の引き継ぎのエンドポイントを `endpoint` で与えます。
  ピアの状態(エンドポイント、最終ハンドシェイク、転送量)は `IpcGet` から読み、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の窃取検知と [10.1 節](../interface.md#101-web-ui)の表示に使います。
  wgctrl は使いません。
  UDP バインドの選び方は [7 節](../agent-dataplane.md#7-データプレーン自宅側)と同じ理由で Windows だけ変えます。
  `vpsd` 自体は Linux でしか動きませんが、この実装(`internal/dataplane/userspace/utun`)は CI の `windows-test` の単体テストと、cross-build の `go vet`(windows/amd64、windows/arm64)の対象なので、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の選択にそろえます
- 中継:全ルールがプロキシモード相当になります。
  UDP と TCP は自宅側の中継部品([7 節](../agent-dataplane.md#7-データプレーン自宅側)の `relay.Manager`)の向きを反転して使い、ホストのソケットで listen し、netstack の dial でエージェントの `10.200.0.x:listen_port` へ接続します。
  ホストのソケットは IPv4 だけで開きます(`udp4`、`tcp4`、[7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ))。
  エージェントから見た送信元は `10.200.0.1` の一時ポートになり、カーネルモードの masquerade と同じ見え方です。
  PROXY protocol 付きの TCP は [6.2 節](proxy.md#62-プロキシモード)の中継をそのまま使います。
  `vps_mode` の kernel と proxy の区別はこのモードでは意味を持たず、PROXY protocol を付けるかどうかだけが残ります
- 宛先への試し接続:`vpsd` は、TCP の待ち受けを開くときに宛先へ試し接続しません。
  [7 節](../agent-dataplane.md#7-データプレーン自宅側)の試し接続(`checkTarget`)はエージェントが LAN の宛先を確かめるためのもので、`vpsd` の中継の宛先はエージェントのトンネルのアドレスです。
  エージェントがそのポートを開くのは、`vpsd` が待ち受けを開いた後に配る全体状態を受け取ってからなので、待ち受けを開いた時点の試し接続は届かないのが普通です。
  起動の直後は、すでにそのポートを開いているエージェントにも届きません。
  起動した `vpsd` はピアにエンドポイントを与えず、エージェントのハンドシェイクが新しいプロセスに届くまでトンネルが通らないためです(後述の性質の違いの項)。
  カーネルモードのエージェントは、公開していないポートへの新しい接続を入口の守り([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))で黙って捨てるので、試し接続は 1 件ごとに期限まで待ち、適用と起動を遅らせます。
  宛先に届くかどうかは、エージェントが自分の試し接続の結果をルールの状態として報告します([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))
- 接続元制限とレート制限:nftables が無いので、Admission Policy の IR から作る Go の評価器(`internal/policy/goengine`、[7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ))で判定します。
  deny、allow、接続元ごとの新規フロー上限(`per_source_rate`)、接続元ごとの同時フロー数の上限([7 節](../agent-dataplane.md#7-データプレーン自宅側))、ルール全体の新規フロー上限(`new_flow_rate`)、UDP のデータグラム上限(`packet_rate`)の順で、[6.1 節](kernel.md#61-カーネルモード)と同じ評価順です。
  `per_source_rate` の表の項目は最後に触れてから 1 分で期限切れになり、表の上限は 65535 件で、最も長く触れていないものから落とします。
  ある段で拒んだフローは、後の段のトークンと同時フロー数の枠を使いません。
  新しいフロー(TCP の接続、UDP の新しいセッションの最初のデータグラム)はすべての段で判定し、成立済みの UDP セッションのデータグラムは `packet_rate` だけで判定します。
  したがって deny と allow で拒む送信元のデータグラムは `packet_rate` のトークンを使いません。
  `proxy_protocol` を付ける TCP の中継([6.2 節](proxy.md#62-プロキシモード))の新しい接続も、同じ評価器の同じ段で判定します。
  `packet_rate` は UDP にだけ適用され、TCP には適用されません。
  3 つのレートとも、nftables の `limit rate over` と同じく burst 5 のトークンバケットです。
  ラボで両モードの通過数と drop の累計が一致することを確かめました(2026-09-17、`lab/rates.sh`)
- 拒否のカウンタ:Go で数え、カーネルモードと同じ累積の経路(SQLite への加算)に渡します。
  UI と CLI の表示は変わりません
- 進行中の中継を閉じる契機は [6.2 節](proxy.md#62-プロキシモード)と同じです(ルールの削除と無効化、接続元制限の変更、エージェントの削除)。
  conntrack による収束の代わりに、この契機で中継を閉じる処理を全ルールに適用します。
  閉じるときにエージェントへの接続を RST で切ることも [6.2 節](proxy.md#62-プロキシモード)と同じで、netstack 越しに張った接続なので `Abort` を使います。
  公開側のクライアントの RST で終わった中継のエージェントへの接続を RST で切ることも、[6.2 節](proxy.md#62-プロキシモード)と同じです。
  UDP の新しいセッションは、エージェントへの dial の後にセッションの表へ入ります。
  読み取りのループが新しい送信元のデータグラムを読んでセッションの表を引いてから、表へ登録するまでの間に、実効宛先の変更か接続元制限の変更でその listener の中継を閉じ、その判定がこの送信元を閉じるものであれば、セッションを登録せずに最初のデータグラムを捨て、取った枠を返します。
  この間は所属ルールと実効宛先を読む前から始まります。
  実効宛先の変更は送信元によらずすべてのセッションを閉じるので、表を引いた後、実効宛先を読む前に実効宛先が変われば、ループが新しい実効宛先を読んで dial した場合でも最初のデータグラムを捨てます。
  次のデータグラムは新しいセッションとして今の宣言で扱います
- 公開ポートの TCP の accept と UDP の読み取りが、リスナーを閉じた場合以外の理由で失敗したときの扱いは [6.2 節](proxy.md#62-プロキシモード)の accept と同じで、リスナーを開いたままバックオフして試し直し、失敗をリスナーごとに 1 分に 1 回までログに出します。
  失敗が続く間も、ルールの状態は変えません。
  この中継の公開側はホストの実ソケットなので、TCP ではファイル記述子の枯渇のような失敗が起こり得ます。
  UDP では、管理者がソケットを破棄したとき(`ss -K`)に読み取りが 1 回 `ECONNABORTED` で失敗し、ソケットは bind したポートを持ったまま残ります。
  試し直さずにやめると、リスナーは bind されたまま新しい接続もデータグラムも受け付けない状態で残り、適用はそのポートを開いているものとして扱って開き直しません
- 起動時と `server check` の検査:input チェーンが `policy drop` の場合の「`tcp/udp dport <port> accept`(範囲は `<lo>-<hi>`)を追加する」提示を、`vpsd` 自身の 2 つのポート([6.1 節](kernel.md#61-カーネルモード))と、有効な全ルールの listen port(範囲を含む)について行います。
  `vps_mode` の区別に意味を持たないため、`kernel`/`proxy` のどちらの値でも対象にします。
  forward、`ip_forward`、他テーブルの DNAT、bind 中ポートの `/proc` の検査は行いません(bind の失敗で分かります)
- ソケットのバッファ:`vpsd` はトンネルを作った直後に自分の WireGuard の UDP ソケットを測り、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の「ソケットのバッファの条件」に届かなければ警告の 1 行をログに出します。
  公開側の UDP ソケットには開くたびに固定の送信バッファを要求し、切り詰められたら同じ形の警告を出します([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「公開側のソケットの送信バッファ」)。
  `server check` は、判断の材料として 3 つの値を示します。
  今の `net.core.rmem_max` と `net.core.wmem_max`、`CAP_NET_ADMIN` を持たないプロセスが得る値、条件の値です。
  `server check` は条件の判定をせず、終了コードも変えません。
  理由は [7 節](../agent-dataplane.md#7-データプレーン自宅側)の「`server check` が示す材料」の項に書きます
- `server teardown` は `--purge` 以外にすることが無く、`server nft` は「ユーザー空間モードでは nftables を使わない」と出力します

カーネルモードとの性質の違いは次のとおりで、文書では入れ方の分岐(systemd ならカーネル、Docker ならユーザー空間)の下にこの違いを先に書きます。

- `vpsd` を止めると転送も止まります。
  カーネルモードは wg0 とテーブルが残るので、更新や再起動の間も転送が続きます
- `vpsd` を再起動すると、転送はエージェントの次の WireGuard のハンドシェイクの後に戻り、それまで数十秒かかります。
  起動した `vpsd` はピアにエンドポイントを与えないので(上の構成のサーバ側トンネルの項)、自分からはハンドシェイクを始めません。
  v1.1.3 でも同じであることを、ラボで確かめました。
  ハンドシェイクの前に公開ポートへ届いた TCP の接続は、`vpsd` がすぐ accept してエージェントへ dial します。
  dial の期限の 5 秒の内にハンドシェイクが成立しなければ、dial が失敗して接続は切れ、クライアントは繋ぎ直す必要があります。
  期限の内に成立した場合に中継されるかどうかは未確認です
- TCP は `vpsd` が終端して 2 本になります。
  エージェントが停止しているとき、カーネルモードでは SYN に応答が返りませんが、ユーザー空間モードでは接続してから切れます
- フラッド耐性はユーザー空間のプロキシ一般(Traefik など)と同じ弱さを持ちます。
  フローを開いて保持するだけの攻撃に対しては、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の「同時フロー数の上限」で `vpsd` が保持するフローの数を抑えます。
  1 つのルールへのフラッドが他のルールの新しいフローまで止めることは、ルール 1 本の上限とルールごとの最低分([7a.10 節](../resource/admission.md#7a10-resource-guard-の再設計))が防ぎます。
  宛先からの応答を読むバッファは、プロセス全体で 64 個までの枠で借り、公開側のソケットの送信バッファが満杯の応答は待たずに捨てます([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「応答のバッファの枠」と「公開側への応答の送信」)。
  `vpsd` では接続元 IP ごとの上限も適用されます。
  PROXY protocol 付きの TCP([6.2 節](proxy.md#62-プロキシモード)の中継)も同じ上限で数えます。
  公開側の accept はホストの実ソケット(`net.Listen`)で行うため、上限を超えた接続を拒否しても netstack の TIME_WAIT([7 節](../agent-dataplane.md#7-データプレーン自宅側))は残りません。
  実ソケットでも拒否は `SetLinger(0)` の RST で閉じ、フラッドの間にエフェメラルポートを浪費しません。
  スループットの目安は、ラボ(2 vCPU の VM、veth 越し)で TCP 1 本の 100 MB 転送がカーネルモード約 2.3 Gbit/s、ユーザー空間モード約 1.3 Gbit/s であり(2026-09-17)、想定用途の数 Mbps から数十 Mbps に対して余裕があります
- 公開ポートで `vpsd` の Go のコードがインターネットに直接さらされます([11 節](../security/admin-transport.md#11-セキュリティ))
- ユーザー空間モードは、パケットの水準の隔離を持ちません。
  netstack の出力は、ルールとプロトコルで分けない FIFO のキュー 1 つを通ります([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「netstack の出力」の項)。
  過負荷のときは、他のルールの通信にも少量のパケットの欠落が起こることがあり、欠落は負荷が終われば止まります。
  ユーザー空間モードは、カーネルモードと同等の QoS と DoS の隔離を保証しません。
  wireguard-go の送信と受信のキューに滞留するパケットはピアごとに構造の上限を持ち、`vpsd` ではその値にピアの数を掛けたものになります。
  1 つのピアの受信のキューが満杯になると、同じ address family の他のピアの読み取りも待ちます([7 節](../agent-dataplane.md#7-データプレーン自宅側)の滞留のメモリの上限の段落)
- ユーザー空間モードの netstack の TCP は、経路の短い障害の後の回復がカーネルの TCP より遅いです。
  障害が終わっても、送り手は障害の間に失った segment を再送のタイマーが切れるたびに少しずつしか送り直さないので、転送の完了は障害の長さを大きく超えて遅れます。
  障害の時点で送信中のデータの多い接続ほど長く止まります。
  データは失われません。
  回復を待つ間、接続は送り直すデータを送信のバッファに持ち続けます。
  中継が終わった後の組も、[末尾を届け終えるまで](../userspace/tcp-retention.md#中継が終わった後の末尾の配送)同時フロー数の枠を保持します。
  boost の枠を持っていれば、その枠も、送信のキューが floor の確かめを通るまでは回収されません([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「TCP のバッファで保証しないこと」)。
  原因は固定版の gVisor の TCP の送り手にあります。
  障害の後の再送が確認されると、RACK(送った時刻に基づく損失の検出、RFC 8985)は障害の前に送った残りの segment を損失と判定します。
  一方で、送り手が送信中と見なす量の計算はこの判定を差し引きません。
  このため送り手は輻輳ウィンドウが送信中の segment で埋まっていると見て、次の再送のタイマーが切れるまで送りません。
  RACK の回復の処理は、次に送る位置の手前の segment だけを再送します。
  再送のタイマーが切れると次に送る位置は未確認の先頭まで戻り、送り直した分だけ進むので、その先で損失と判定した segment はこの処理では再送されません。
  同じ状態は、経路の障害のほかに、WireGuard のソケットの受信のバッファが溢れてパケットを失った後にも起きます。
  ラボでは、[ソケットのバッファの条件](../userspace/socket-buffers.md#ソケットのバッファの条件)を満たさずに権限なしで動く `vpsd` で、通常の転送がときどきこの状態に入りました。
  既定の値の VM で `lab/usage.sh userspace` を単独で 10 回実行すると、6 回で遅い転送が現れました。
  条件を満たした同じ確認では、単独の 35 回で `vpsd` の受信のバッファの溢れは起きませんでした。
  遅い転送は、単独と並列を合わせた 40 回のうち 1 回でした。
  この 1 回は `vpsd` の溢れを伴わず、原因は未確認です(2026-10)。
  設計の推論では、条件を満たしても、持続する過負荷では受信のバッファが溢れることがあります([フロー数とメモリのソフト上限](../userspace/flow-limits.md))。
  この溢れはラボでは観測していません。
  対象は、netstack が TCP の接続の端になる区間で、netstack が送る向きです。
  `vpsd` とエージェントがどちらもユーザー空間モードの組では 2 つの netstack の間が対象になります。
  `vpsd` がカーネルモードでエージェントがユーザー空間モードの組では、`vpsd` が DNAT でエージェントの netstack へ転送するので、エージェントの netstack と公開側のクライアントのカーネルの TCP の間が対象になります。
  `vpsd` がユーザー空間モードでエージェントがカーネルモードの組では、`vpsd` の netstack と LAN の宛先のカーネルの TCP の間が対象になります。
  ユーザー空間モードだけで動く Windows と macOS のエージェントも対象です。
  公開側のクライアントと `vpsd` の公開側のソケットの間や、エージェントの LAN 側のソケットと宛先の間のように、両端がカーネルの TCP である区間は対象になりません。
  ユーザー空間モードは、カーネルモードと同等の損失の回復を保証しません([以前の検証 2026-10-03](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L653))
- ユーザー空間モードは、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の上界の式に数えた保持点が最悪になった場合のメモリの量を、ホストの要件として持ちます。
  既定の上限で、エージェントが 1 つ、TCP の宛先が 1 つなら、`vpsd` のホストに約 12.7 GiB のメモリが要ります。
  上限を下げても、要るメモリは約 3.2 GiB より小さくなりません([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「プロセス全体のメモリの上界」の段落)
- ユーザー空間モードは、netstack の TCP の接続が中身の無い ACK を処理する待ち行列に、構造上の上限を持ちません。
  入口の予算が抑えるのは予算の上限までで、それを超えた分は上界の式の外です([既知の制限](../userspace/memory-limits.md#中身の無い-segment-の処理待ち))。
  このため、ユーザー空間モードはプロセスのメモリが上界の式の値を超えないことを保証しません。
  ユーザー空間モードの `vpsd` では netstack の TCP の相手はエージェントだけなので、この制限を起こすにはエージェントの WireGuard の鍵が要ります。
  エージェントを信頼できない場合は、`vpsd` をカーネルモードで動かします。
  カーネルモードの server の後ろのユーザー空間モードのエージェントでは、TCP のルールの公開側の利用者がこの制限を起こせます
- ユーザー空間モードは、動作条件として [7 節](../agent-dataplane.md#7-データプレーン自宅側)の「ソケットのバッファの条件」を要します。
  カーネルモードの WireGuard はカーネルの中で動くので、カーネルモードにこの条件はありません。
  付属の systemd の unit は `CAP_NET_ADMIN` を与えるので、VM や専用のホストでは、その `vpsd` のソケットは sysctl の値によらず条件を満たし得ます。
  LXC ベースの VPS とコンテナでは、unit が与える `CAP_NET_ADMIN` はコンテナの user namespace の中に限られ、FORCE は通りません([6.1 節](kernel.md#61-カーネルモード))。
  条件はコンテナのホストの sysctl で決まります。
  付属の compose ファイルの `vpsd` は、ホストの値を上げて条件を満たしました([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「コンテナでのバッファの条件」)。
  LXC のコンテナの中と LXC ベースの VPS の `vpsd` が条件を満たせるかどうかは未確認であり、利用者がホストの sysctl を変えられないこともあります。
  root の取れない VPS で unit を使わずに動かす `vpsd` は、`CAP_NET_ADMIN` を持ちません。
  どの配置でも、決め手は `vpsd` が自分のソケットを測った値とその警告の行です
- ピアを追加する前に届いたハンドシェイクは捨てられ、エージェントの再送は 5 秒後になります。
  接続時のハンドシェイクでは、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の順(stream の接続時に公開鍵を宣言してからピアを追加する)でこの問題を避けます

稼働中の `agent rotate-key` では、新しい鍵のハンドシェイクがピアを追加する前に届いて捨てられることがあります。
`vpsd` は [5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の引き継ぎで新しいピアに古いピアのエンドポイントを与え、自分の側からハンドシェイクを始めます。
この扱いはカーネルモードと共通です。
ユーザー空間モードのエージェントは `rotate-key` でトンネルを作り直して送信元のポートが変わるので、引き継いだエンドポイントは使えず、エージェントの再送を待ちます([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))

エージェントとプロトコルは変えません。
サーバ鍵と証明書は SQLite にあるので、同じ SQLite で別のモードで起動すれば、エージェントは再登録なしに再接続します。
1024 未満のポートは、Docker の bridge ネットワーク(`ports:` で公開)ではコンテナの名前空間で非特権の bind が許されるので使えます(443 で確認済みです)。
`network_mode: host` ではホストの名前空間の制限が適用され、非 root では bind できません。
systemd で非 root なら、`AmbientCapabilities=CAP_NET_BIND_SERVICE` で権限を追加します。
コンテナに `NET_ADMIN` と host ネットワークを付けてカーネルモードを動かすことには対応しません。
