### ユーザー空間モード

VPS のユーザー空間モードは、wireguard-go と netstack のトンネルから中継します。
フローの予算とソケットの条件は、ユーザー空間の共通仕様に従います。


`WGFT_MODE=userspace` は、VPS 側にも root、カーネル WireGuard、nftables を要求しない動作モードです。
`vpsd` は自宅側と同じ wireguard-go と gVisor の netstack でトンネルを持ち、公開ポートを自分のソケットで受けて netstack 越しにエージェントへ中継します。
root の取れない VPS、OpenVZ 系や LXC ベースの VPS、compose で全部を管理したい人のための入口で、カーネルモードを置き換えるものではありません。
モードは `vpsd` 全体で 1 つであり、ルール単位で混ぜない([11a 節](../security/configuration.md#11a-設定の渡し方)の記録と照合)。

構成は次のとおり。

- サーバ側トンネル:wireguard-go の `device` と、エージェントと共通の netstack の TUN(`internal/nettun`、[7 節](../agent-dataplane.md#7-データプレーン自宅側))で、`listen_port` を開き `10.200.0.1` を持ちます。
  サーバ鍵は SQLite の同じ鍵を使います。
  ピアの追加と削除は `IpcSet`(`public_key`、`allowed_ip`、`remove`)で行います。
  エンドポイントは原則として指定せず、エージェントのハンドシェイクで学習します。
  例外は鍵の置き換えで、新しいピアには [5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の引き継ぎのエンドポイントを `endpoint` で与える。
  ピアの状態(エンドポイント、最終ハンドシェイク、転送量)は `IpcGet` から読み、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の窃取検知と [10.1 節](../interface.md#101-web-ui)の表示に使います。
  wgctrl は使いません。
  UDP バインドの選び方は [7 節](../agent-dataplane.md#7-データプレーン自宅側)と同じ理由で Windows だけ変えます。
  `vpsd` 自体は Linux でしか動かないが、この実装(`internal/dataplane/userspace/utun`)は CI の `windows-test` の単体テストと、cross-build の `go vet`(windows/amd64、windows/arm64)の対象であるため、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の選択にそろえる
- 中継:全ルールがプロキシモード相当になります。
  UDP と TCP は自宅側の中継部品([7 節](../agent-dataplane.md#7-データプレーン自宅側)の `relay.Manager`)の向きを反転して使い、ホストのソケットを IPv4 だけで開いて(`udp4`、`tcp4`。
  [7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ))listen し、netstack の dial でエージェントの `10.200.0.x:listen_port` へつなぐ。
  エージェントから見た送信元は `10.200.0.1` の一時ポートになり、カーネルモードの masquerade と同じ見え方です。
  PROXY protocol 付きの TCP は [6.2 節](proxy.md#62-プロキシモード)の中継をそのまま使います。
  `vps_mode` の kernel と proxy の区別はこのモードでは意味を持たず、PROXY protocol を付けるかどうかだけが残る
- 宛先への試し接続:`vpsd` は、TCP の待ち受けを開くときに宛先へ試し接続しません。
  [7 節](../agent-dataplane.md#7-データプレーン自宅側)の試し接続(`checkTarget`)はエージェントが LAN の宛先を確かめるためのもので、`vpsd` の中継の宛先はエージェントのトンネルのアドレスです。
  エージェントがそのポートを開くのは、`vpsd` が待ち受けを開いた後に配る全体状態を受け取ってからなので、待ち受けを開いた時点の試し接続は届かないのが普通です。
  起動の直後は、すでにそのポートを開いているエージェントにも届かない。
  起動した `vpsd` はピアにエンドポイントを与えず、エージェントのハンドシェイクが新しいプロセスに届くまでトンネルが通らないためである(後述の性質の違いの項)。
  カーネルモードのエージェントは、公開していないポートへの新しい接続を入口の守り([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))で黙って捨てるので、試し接続は 1 件ごとに期限まで待ち、適用と起動を遅らせる。
  宛先に届くかどうかは、エージェントが自分の試し接続の結果をルールの状態として報告する([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))
- 接続元制限とレート制限:nftables が無いので、Admission Policy の IR から作る Go の評価器(`internal/policy/goengine`、[7a.9 節](../policy.md#7a9-admission-policy-のコンパイラ))で判定します。
  deny、allow、接続元ごとの新規フロー上限(`per_source_rate`。
  表は最後に触れてから 1 分で期限切れ、上限 65535 件で最も長く触れていないものから落とす)、接続元ごとの同時フロー数の上限([7 節](../agent-dataplane.md#7-データプレーン自宅側))、ルール全体の新規フロー上限(`new_flow_rate`)、UDP のデータグラム上限(`packet_rate`)の順で、[6.1 節](kernel.md#61-カーネルモード)と同じ評価順です。
  ある段で拒んだフローは、後の段のトークンと同時フロー数の枠を使いません。
  新しいフロー(TCP の接続、UDP の新しいセッションの最初のデータグラム)はすべての段で判定し、成立済みの UDP セッションのデータグラムは `packet_rate` だけで判定します。
  したがって deny と allow で拒む送信元のデータグラムは `packet_rate` のトークンを使いません。
  `proxy_protocol` を付ける TCP の中継([6.2 節](proxy.md#62-プロキシモード))の新しい接続も、同じ評価器の同じ段で判定します。
  `packet_rate` は UDP にだけ効き、TCP には効きません。
  3 つのレートとも nftables の `limit rate over` と同じく burst 5 のトークンバケットで、ラボで両モードの通過数と drop の累計が一致することを確かめた(2026-09-17、`lab/rates.sh`)
- 拒否のカウンタ:Go で数え、カーネルモードと同じ累積の経路(SQLite への加算)に流す。
  UI と CLI の表示は変わりません
- 進行中の中継を閉じる契機は [6.2 節](proxy.md#62-プロキシモード)と同じ(ルールの削除と無効化、接続元制限の変更、エージェントの削除)。
  conntrack 収束の代わりに、これが全ルールに効く。
  閉じるときにエージェントへの接続を RST で切ることも [6.2 節](proxy.md#62-プロキシモード)と同じで、netstack 越しに張った接続なので `Abort` を使います。
  公開側のクライアントの RST で終わった中継のエージェントへの接続を RST で切ることも、[6.2 節](proxy.md#62-プロキシモード)と同じです。
  UDP の新しいセッションは、エージェントへの dial の後にセッションの表へ入ります。
  読み取りのループが新しい送信元のデータグラムを読んでセッションの表を引いてから、表へ登録するまでの間に、実効宛先の変更か接続元制限の変更でその listener の中継を閉じ、その判定がこの送信元を閉じるものであれば、セッションを登録せずに最初のデータグラムを捨て、取った枠を返します。
  この間は所属ルールと実効宛先を読む前から始まる。
  実効宛先の変更は送信元によらずすべてのセッションを閉じるので、表を引いた後、実効宛先を読む前に実効宛先が変われば、ループが新しい実効宛先を読んで dial した場合でも最初のデータグラムを捨てます。
  次のデータグラムは新しいセッションとして今の宣言で扱う
- 公開ポートの TCP の accept と UDP の読み取りが、リスナーを閉じた場合以外の理由で失敗したときの扱いは [6.2 節](proxy.md#62-プロキシモード)の accept と同じで、リスナーを開いたまま後退して試し直し、失敗をリスナーごとに 1 分に 1 回までログに出す。
  失敗が続く間も、ルールの状態は変えません。
  この中継の公開側はホストの実ソケットなので、TCP ではファイル記述子の枯渇のような失敗が起こりうる。
  UDP では、管理者がソケットを破棄したとき(`ss -K`)に読み取りが 1 回 `ECONNABORTED` で失敗し、ソケットは bind したポートを持ったまま残る。
  試し直さずにやめると、リスナーは bind されたまま新しい接続もデータグラムも受け付けない状態で残り、適用はそのポートを開いているものとして扱って開き直さない
- 起動時と `server check` の検査:input チェーンが `policy drop` の場合の「`tcp/udp dport <port> accept`(範囲は `<lo>-<hi>`)を足す」提示を、`vpsd` 自身の 2 つのポート([6.1 節](kernel.md#61-カーネルモード))と、有効な全ルールの listen port(範囲を含む)について行います。
  `vps_mode` の区別に意味を持たないため、`kernel`/`proxy` のどちらの値でも対象にします。
  forward、`ip_forward`、他テーブルの DNAT、bind 中ポートの `/proc` の検査は行わない(bind の失敗で分かる)
- ソケットのバッファ:`vpsd` はトンネルを立てた直後に自分の WireGuard の UDP ソケットを測り、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の「ソケットのバッファの条件」に届かなければ警告の 1 行をログに出す。
  公開側の UDP ソケットには開くたびに固定の送信バッファを要求し、切り詰められたら同じ形の警告を出す([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「公開側のソケットの送信バッファ」)。
  `server check` は、判断の材料として 3 つの値を示します。
  今の `net.core.rmem_max` と `net.core.wmem_max`、`CAP_NET_ADMIN` を持たないプロセスが得る値、条件の値です。
  `server check` は条件の判定をせず、終了コードも変えません。
  理由は [7 節](../agent-dataplane.md#7-データプレーン自宅側)の「`server check` が示す材料」の項に書きます
- `server teardown` は `--purge` 以外にすることが無く、`server nft` は「ユーザー空間モードでは nftables を使わない」と出す

カーネルモードとの性質の違いは次のとおりで、文書では入れ方の分岐(systemd ならカーネル、Docker ならユーザー空間)の下にこの違いを先に書きます。

- `vpsd` を止めると転送も止まります。
  カーネルモードは wg0 とテーブルが残るので、更新や再起動の間も通る
- `vpsd` を再起動すると、転送はエージェントの次の WireGuard のハンドシェイクの後に戻り、それまで数十秒かかる。
  起動した `vpsd` はピアにエンドポイントを与えないので(上の構成のサーバ側トンネルの項)、自分からはハンドシェイクを始めない。
  v1.1.3 でも同じであることを、ラボで確かめた。
  ハンドシェイクの前に公開ポートへ届いた TCP の接続は、`vpsd` がすぐ accept してエージェントへ dial します。
  dial の期限の 5 秒の内にハンドシェイクが成立しなければ、dial が失敗して接続は切れ、クライアントは繋ぎ直す必要があります。
  期限の内に成立した場合に中継されるかどうかは未確認です
- TCP は `vpsd` が終端して 2 本になります。
  エージェントが落ちているとき、カーネルモードは SYN が返らないが、ユーザー空間モードは接続してから切れる
- フラッド耐性はユーザー空間のプロキシ一般(Traefik など)と同じ弱さを持ちます。
  フローを開いて保持するだけの攻撃に対しては、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の「同時フロー数の上限」で `vpsd` が保持するフローの数を抑えます。
  1 つのルールへのフラッドが他のルールの新しいフローまで止めることは、ルール 1 本の上限とルールごとの最低分([7a.10 節](../resource/admission.md#7a10-resource-guard-の再設計))が防ぐ。
  宛先からの応答を読むバッファは、プロセス全体で 64 個までの枠で借り、公開側のソケットの送信バッファが満杯の応答は待たずに捨てる([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「応答のバッファの枠」と「公開側への応答の送信」)。
  `vpsd` では接続元 IP ごとの上限も効く。
  PROXY protocol 付きの TCP([6.2 節](proxy.md#62-プロキシモード)の中継)も同じ上限で数えます。
  公開側の accept はホストの実ソケット(`net.Listen`)で行うため、上限を超えた接続を拒否しても netstack の TIME_WAIT([7 節](../agent-dataplane.md#7-データプレーン自宅側))は残りません。
  実ソケットでも拒否は `SetLinger(0)` の RST で閉じ、フラッドの間にエフェメラルポートを浪費しません。
  スループットの目安は、ラボ(2 vCPU の VM、veth 越し)で TCP 1 本の 100 MB 転送がカーネルモード約 2.3 Gbit/s、ユーザー空間モード約 1.3 Gbit/s であり(2026-09-17)、想定用途の数 Mbps から数十 Mbps に対して余裕があります
- 公開ポートで `vpsd` の Go のコードがインターネットに直接さらされる([11 節](../security/admin-transport.md#11-セキュリティ))
- ユーザー空間モードは、パケットの水準の隔離を持ちません。
  netstack の出力は、ルールとプロトコルで分けない FIFO のキュー 1 つを通る([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「netstack の出力」の項)。
  過負荷のときは、他のルールの通信にも少量のパケットの欠落が起こることがあり、欠落は負荷が終われば止まります。
  ユーザー空間モードは、カーネルモードと同等の QoS と DoS の隔離を保証しません。
  wireguard-go の送信と受信のキューに滞留するパケットはピアごとに構造の上限を持ち、`vpsd` ではその値にピアの数を掛けたものになります。
  1 つのピアの受信のキューが満杯になると、同じ address family の他のピアの読み取りも待つ([7 節](../agent-dataplane.md#7-データプレーン自宅側)の滞留のメモリの上限の段落)
- ユーザー空間モードの netstack の TCP は、経路の短い障害の後の回復がカーネルの TCP より遅い。
  障害が終わっても、送り手は障害の間に失った segment を再送のタイマーが切れるたびに少しずつしか送り直さないので、転送の完了は障害の長さを大きく超えて遅れる。
  障害の時点で送信中のデータの多い接続ほど長く止まります。
  データは失われない。
  回復を待つ間、接続は送り直すデータを送信のバッファに持ち続けます。
  boost の枠を持っていれば、その枠も、送信のキューが floor の確かめを通るまでは回収されない([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「TCP のバッファで保証しないこと」)。
  原因は固定版の gVisor の TCP の送り手にあります。
  障害の後の再送が確認されると、RACK(送った時刻に基づく損失の検出、RFC 8985)は障害の前に送った残りの segment を損失と判定します。
  一方で、送り手が送信中と見なす量の計算はこの判定を差し引かない。
  このため送り手は輻輳の窓が送信中の segment で埋まっていると見て、次の再送のタイマーが切れるまで送らない。
  対象は、netstack が TCP の接続の端になる区間で、netstack が送る向きです。
  `vpsd` とエージェントがどちらもユーザー空間モードの組では 2 つの netstack の間が対象になります。
  `vpsd` がカーネルモードでエージェントがユーザー空間モードの組では、`vpsd` が DNAT でエージェントの netstack へ転送するので、エージェントの netstack と公開側のクライアントのカーネルの TCP の間が対象になります。
  `vpsd` がユーザー空間モードでエージェントがカーネルモードの組では、`vpsd` の netstack と LAN の宛先のカーネルの TCP の間が対象になります。
  ユーザー空間モードだけで動く Windows と macOS のエージェントも対象です。
  公開側のクライアントと `vpsd` の公開側のソケットの間や、エージェントの LAN 側のソケットと宛先の間のように、両端がカーネルの TCP である区間は対象になりません。
  ユーザー空間モードは、カーネルモードと同等の損失の回復を保証しない(改訂の記録 2026-10-03)
- ユーザー空間モードは、[7 節](../agent-dataplane.md#7-データプレーン自宅側)の上界の式に数えた保持点が最悪になった場合のメモリの量を、ホストの要件として持ちます。
  既定の上限で、エージェントが 1 つ、TCP の宛先が 1 つなら、`vpsd` のホストに約 5.9 GiB のメモリが要る。
  上限を下げても、要るメモリは約 2.9 GiB より小さくならない([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「プロセス全体のメモリの上界」の段落)
- ユーザー空間モードは、動作条件として [7 節](../agent-dataplane.md#7-データプレーン自宅側)の「ソケットのバッファの条件」を要します。
  カーネルモードの WireGuard はカーネルの中で動くので、カーネルモードにこの条件はありません。
  付属の systemd の unit は `CAP_NET_ADMIN` を与えるので、VM や専用のホストでは、その `vpsd` のソケットは sysctl の値によらず条件を満たし得ます。
  LXC ベースの VPS とコンテナでは、unit が与える `CAP_NET_ADMIN` はコンテナの user namespace の中に限られ、FORCE は通らない([6.1 節](kernel.md#61-カーネルモード))。
  条件はコンテナのホストの sysctl で決まる。
  付属の compose ファイルの `vpsd` は、ホストの値を上げて条件を満たした([7 節](../agent-dataplane.md#7-データプレーン自宅側)の「コンテナでのバッファの条件」)。
  LXC のコンテナの中と LXC ベースの VPS の `vpsd` が条件を満たせるかどうかは未確認であり、利用者がホストの sysctl を変えられないこともあります。
  root の取れない VPS で unit を使わずに動かす `vpsd` は、`CAP_NET_ADMIN` を持ちません。
  どの配置でも、決め手は `vpsd` が自分のソケットを測った値とその警告の行です
- ピアを足す前に届いた握手は捨てられ、エージェントの再送は 5 秒後になります。
  接続時の握手は、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の順(stream の接続時に公開鍵を宣言してからピアを足す)で吸収します

稼働中の `agent rotate-key` では、新しい鍵の握手がピアを足す前に届いて捨てられうる。
`vpsd` は [5.2 節](../control/connection.md#52-全体状態の配信とハートビート)の引き継ぎで新しいピアに古いピアのエンドポイントを与え、自分の側から握手を始める。
この扱いはカーネルモードと共通です。
ユーザー空間モードのエージェントは `rotate-key` でトンネルを作り直して送信元のポートが変わるので、引き継ぎは効かず、エージェントの再送を待つ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))

エージェントとプロトコルは変えません。
サーバ鍵と証明書は SQLite にあるので、同じ SQLite で別のモードに上げれば、エージェントは再登録なしに再接続します。
1024 未満のポートは、Docker の bridge ネットワーク(`ports:` で公開)ではコンテナの名前空間で非特権の bind が許されるので使える(443 で確認済み)。
`network_mode: host` ではホストの名前空間の制限が効き、非 root では bind できません。
systemd で非 root なら `AmbientCapabilities=CAP_NET_BIND_SERVICE` で足す。
コンテナに `NET_ADMIN` と host ネットワークを付けてカーネルモードを動かすことには対応しません。
