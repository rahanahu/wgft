# Rust の agent のメモリの上界の表

この文書は、Rust の agent の[メモリの上界の行](agent-parity.md#メモリの上界の行)の値を、代表のフロー数の上限で示します。
表は `crates/wgft-agent` の試験 `memory::tests::bound_table_is_up_to_date` が生成し、印の間だけを書き直します。
手で直さず、`WGFT_UPDATE_GOLDEN=1 cargo nextest run -p wgft-agent bound_table` で作り直します。
印を付けずに流すと、試験は表が計算と違うときに失敗します。

値は byte で、括弧の中は MiB です。
K は `WGFT_MAX_TCP_FLOWS`、U は `WGFT_MAX_UDP_FLOWS` です。
列は、既定の上限、ラボの `lifecycle.sh` の check 5 の上限、ラボのメモリの測定の上限、受け付ける最小の上限です。
核の項は起動の行と同じく、受け付ける最大の MTU の 9216 で数えます。
核の項の内訳は[wgstack の Rust 版の上界の表](wgstack-bound.md)にあり、そちらは MTU が 1420 の値です。

中継の future と表の項の大きさは target と最適化の段で変わるので、表は Linux の x86_64 の試験の build の値で、ほかの target では試験が比べません。
起動の行は、動いている build の型の大きさで同じ式を数えます。
型の大きさは rustc と依存の版で変わりうるので、toolchain や tokio を上げるときは同じ変更で表を作り直し、差分を PR に書きます。

行の名前は起動の 2 行目 (`memory bound terms:`) の項の名前で、中身は次のとおりです。

- `base`:実行ファイル、tokio の実行環境、制御ソケットのスレッド、stream と TLS の状態です。ラボで測った RSS から決めた定数です
- `core fixed`:核が作成の時に作る構造と表で、核の `Bound::fix` です
- `core arrays`:接続の枠ごとの floor の送信の記録の輪と区間の表で、N_c × (r_f + h_f) です (核の `Bound::floor_arrays`)。
  N_c は K と accept の待ち行列の 512 の和です。
  枠を初めて使う時に確保して枠と共に持つので、データを運ばない接続もこの分を持ちます
- `core flows`:核の残りの項で、次の 3 行の和です
- `core flows`: the floors:接続の枠ごとの送信と受信の floor で、N_c × (f_s + f_r) です
- `core flows`: `boost`:boost の枠の分です
- `core flows`: the rest:再組み立ての表、UDP の予算、ping の表です
- `tables`:handle の層の waker の表と、LAN の側のソケットの表です
- `driver`:データプレーンの駆動が waker を移す列です
- `device`:WireGuard の device のキューと、データプレーンの受信と送り出しのバッファです
- `batch`:トンネルのバッチのバッファです。データプレーンは datagram を 1 つずつ読み書きするので 0 です
- `tcp relay`:TCP の中継の接続ごとの task と I/O の登録です
- `tcp bulk`:TCP の中継の両方の向きの大きいバッファと、使い回しに残す分です
- `udp relay`:UDP の応答のバッファの枠と、セッションごとの項です
- `resolver`:名前の解決のスレッドです
- `state`:server が配る全体状態の写しと stream のバッファです
- `total`:上の項の和で、起動の行の値です。`core flows` の 3 行は `core flows` に含まれるので、二重に足しません
- one TCP listener と one UDP listener:待ち受け 1 つの項で、起動の行に含めず、適用の後の行が開いた数だけ足します
