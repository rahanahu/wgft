# データプレーンの暗号の作業者

この文書は、Rust の agent のデータプレーンが WireGuard の暗号 (ChaCha20-Poly1305) を別のスレッドでも行う設計を定めます。
[速さの作業の順](agent-throughput.md#作業の順)の 2 番目の仕事で、データプレーンを複数のスレッドに分ける最初の候補です。
設計は評価中で、採ると決めていません。

形は 2 つあります。

- 回ごとに待つ形:持ち主のスレッドがバッチの暗号を作業者と分け、その回の中で作業者の終わりを待ちます ([作業者と受け渡し](#作業者と受け渡し))。
  ラボでは速くならなかったので、単独では採りません ([回ごとに待つ形のラボの結果](#回ごとに待つ形のラボの結果))
- 重ねる形:持ち主は作業者の終わりを待たず、作業者が次のバッチを復号する間に前のバッチを核と中継に渡し ([受信の重ね](#受信の重ね))、作業者が次のバッチを暗号化する間に前のバッチを送ります ([送信の重ね](#送信の重ね))。
  評価の中心の候補です。
  重ねられないバッチは、回ごとに待つ形で扱います

所有者の決定 (2026-11-02) で、1 つのスレッドの無駄 (受信の輪の零埋めなど) を先に減らし、その後で重ねる形を、同じ条件でその変更の有る場合と無い場合で比べて採否を決めます。
比べる値は、最大の速さ、通常の頭打ちの負荷での CPU の効率、UDP の p99 と jitter、メモリ、複雑さです。
判定の線は緩めません。
この文書の測った値は、その比べの前の途中の値です。

## 範囲

- 対象:Linux でバッチを使うデータプレーン ([バッチの作り](agent-throughput.md#バッチの作り)) の、トンネルの受信の復号と送信の暗号化です
- 対象の外:Windows、macOS、`WGFT_AGENT_BATCH_MIB=0` の 1 つずつ送受信する道は、作業者を持たず、振る舞いを変えません。
  これらの道は 1 回に 1 つの datagram しか読まないので、並べる仕事がありません
- 変えないもの:wgstack の核、中継、device の層の sans-IO の形、sanstun の版と使い方、WireGuard の番号と再送の窓の意味です
- 比べなかった形:核の前後でスレッドを分ける形 (device の層のスレッドと核のスレッド)、送信の system call だけを別のスレッドにする形、流れごとに核を分ける形です。
  暗号の作業者で足りないと測ったときに、測った詰まりに応じて比べます

## 前提の値

バッチの後の profile (ラボ、1 stream、4 vCPU) で、暗号はエージェントの CPU の、受ける向きで 33.4%、送る向きで 19.3% でした。
送る向きの値は、ラボの経路だけで起こる送った後の softirq (送る向きの 41.9%、[測り方](agent-throughput.md#測り方)) を含みます。
ホストの E コアで、1408 byte の packet の暗号化は約 751 ns、復号は約 669 ns、64 byte は約 175 ns でした。
暗号をすべて別のスレッドに移した場合の速さの上限は、受ける向きで約 1.50 倍、送る向きで約 1.24 倍です。
受け渡しの費用を 0 とした見積もりは、作業者 1 つで受ける向き 1.20 倍と送る向き 1.11 倍、作業者 2 つで 1.29 倍と 1.15 倍です。
受ける向きの方が効果が大きいので、受ける向きから試します。

## device の層の分け方

sanstun 0.1.0 は、暗号の前後の状態の変更と、純粋な暗号の計算を分けた API を持ちます。
device の層 (`wgft-wireguard`) は、これを wgft の型で 3 つの段に分けて公開します。
sanstun の型は外に出しません ([sanstun の隔離](wireguard-device.md#sanstun-の隔離))。

- 受信:`Device::begin_datagram` が datagram を検査し、データの message で復号の前の検査 (今のセッションと、番号の再送の窓の先の検査) を通ったものを、復号の仕事 `OpenJob` として返します。
  ハンドシェイク、cookie、捨てる datagram はこの呼び出しの中で済ませます。
  `OpenJob::open` は呼び手の buffer に復号するだけで、ほかの状態に触れません。
  `Device::finish_datagram` が、再送の窓の本当の検査、endpoint の更新、timer、内側の packet の検査を行います
- 送信:`Device::begin_packet` が経路と MTU を確かめ、番号を取り、送るバイト数を数えて、暗号化の仕事 `SealJob` を返します。
  `SealJob::seal` は呼び手の buffer に暗号化するだけです
- 1 つずつの呼び出し:`Device::handle_datagram` と `Device::handle_packet` は、この段を続けて呼ぶ形で、振る舞いは前と同じです

仕事は、セッションの鍵の写し、index、番号だけを持ちます。
鍵の写しは drop で 0 に戻ります。
仕事は 1 回のバッチの間 (数十 µs) だけ生き、バッチの終わりまでにすべて drop します。

### 番号と再送の窓

Linux の WireGuard と wireguard-go と同じく、暗号の計算だけを並べ、状態の変更は届いた順と送る順に 1 つのスレッドで行います。
再送の窓は [WireGuard の論文](https://www.wireguard.com/papers/wireguard.pdf) の 5.4.6 節のとおり、認証の後に検査します。

- 受信:`finish_datagram` はデータプレーンのスレッドで、datagram の届いた順に呼びます。
  再送の窓、endpoint の更新、セッションの確認、keepalive の timer は、1 つずつ扱う道と同じ順の入力を受けます
- 受け付ける前の写し:`begin_datagram` の窓の先の検査は、まだ受け付けていない写しを通します。
  写しの元は、同じバッチの datagram と、重ねる形 ([受信の重ね](#受信の重ね)) で作業者にある前のバッチの datagram です。
  受け付けは `finish_datagram` の 2 度目の検査で最初の 1 つだけになり、結果は 1 つずつの道と同じです。
  違うのは数え方だけで、まだ受け付けていない番号を持つ偽の datagram は、再送 (`replayed`) ではなく認証の失敗 (`unauthenticated`) に数えます
- ハンドシェイクの順:データでない datagram (ハンドシェイク、cookie、壊れた短い datagram) の前に届いたデータの仕事は、その datagram を扱う前にすべて受け付けます。
  ハンドシェイクが新しいセッションを今のセッションにした後に、古いセッションのデータを受け付けて今のセッションを戻すことはありません
- トンネルの取り替え:仕事を始めた後に期限切れでトンネルを取り替えた場合、その仕事は 1 つずつの道と同じく、知らないピアとして捨てます
- 送信:番号はデータプレーンのスレッドで送る順 (UDP を先に) に取り、`sendmmsg` も同じ順に送ります。
  wire の上の順は番号の順のままです。
  暗号化に失敗した仕事 (buffer が短いときだけで、データプレーンでは起こりません) の番号は使わずに飛ばし、使い回しません

## 作業者と受け渡し

作業者は、トンネルの世代ごとに起動の時に作る少数の OS のスレッドです (`wgft-udp-batch` の `pool`)。
世代の始めに、作業者がそれぞれ待ちの loop に着くまで待ちます。
スレッドの始まりの確保を、データの経路の前に済ませるためです。
世代の終わりに止めて join します。
データプレーンのスレッドが持ち主で、作業者に渡す呼び出しは持ち主のスレッドだけが行います。
仕事の無いレーン (割り振られた仕事が無いか、すべて捨てられたレーン) は、作業者に渡さず、作業者を起こしません。

1 回の受け渡しは、バッチの暗号の仕事を作業者の数より 1 つ多いレーンに分けて行います。

1. 持ち主は、レーン 1 から先を作業者ごとの枠に 1 つずつ置き、その作業者を起こします
2. 持ち主はレーン 0 を自分で行います
3. 持ち主は、まだどの作業者も取っていないレーンを枠から取り戻し、自分で行います
4. 持ち主は、作業者が取ったレーンの終わりを待ちます

眠っている作業者が起きるのを待たないので、作業者の起床の遅れはバッチを 1 つのスレッドの場合より長くしません。
待つのは、作業者が既に始めたレーンの終わりだけです。

- 同期:バッチごとに、枠ごとの錠を数回取り、作業者を起こし (`unpark`)、終わりを知らせるだけです。
  packet ごとの同期はありません
- 持ち物:レーン (平文や暗号文の buffer と仕事の列) は、持ち主と作業者の間を値で動きます。
  作業者が読む datagram と packet の領域は `Arc` で分け、持ち主は次のバッチの前に `Arc::get_mut` で書く権利を取り戻します。
  作業者が借用を持たないので、unsafe は要りません。
  依存も足しません。
  `rayon` は、プールの外のスレッドが待つ間に仕事を取り戻せず、空いた作業者が回り続けて CPU を使うので採りません
- cache:作業者ごとの枠は別の cache line に置き、持ち主と作業者が同じ line に書かないようにします
- panic:作業者の中の panic は毒の印を付け、持ち主はその世代を終えます。
  核の中の panic と同じく、agent はトンネルを作り直します ([世代と予算の受け渡し](wgstack-rs.md#世代と予算の受け渡し))

### 作業者の数

作業者の数は起動の時に 1 回だけ、プロセスが使える CPU の数から決めます (仮の答え)。
CPU が 3 つ以上なら 2 つ、2 つ以下なら 0 (作業者を使わない) です。
Rust の `available_parallelism` は CPU の affinity と cgroup の CPU の上限に従います。
設定は設けません。

- 上限の 2:前提の値の見積もりで作業者 2 つが上限の大半に届き、作業者を足すたびにバッチごとの起こしが増えるためです
- 1 つを使わない理由:ホストの測定 ([ホストの測定の結果](#ホストの測定の結果)) で、作業者 1 つの受信は、バッチの終わりが持ち主だけの場合より遅くなりました。
  持ち主が自分の半分を終えた後、起きるのが遅れた作業者の半分を待つためです

作業者を作れなかった場合は、持ち主がすべてのレーンを行い、1 つのスレッドと同じ速さで動きます。

## 受信の重ね

受信の相は、受信の置き場を 2 つ持ち、交互に使います (`dataplane::driver` の `receive_pipelined`)。

1. 持ち主は置き場の片方にバッチを読みます
2. 読んだバッチが求めた枠をすべて満たし (ソケットにまだ待つものがあり)、作業者のレーンに収まるときは、重ねて扱います。
   持ち主はそのバッチの datagram を届いた順に `begin_datagram` に渡し、作業者のレーンに割り振ります
3. 作業者にある前のバッチを取り戻し、届いた順に `finish_datagram` で受け付けます
4. 始めたバッチを作業者に渡し、その終わりを待ちません
5. 受け付けた前のバッチを、UDP を先に核と中継に渡し、次を読みます。
   作業者は、この核と中継の仕事と次の読みの間に復号します

作業者に渡すのは 1 度に 1 つのバッチだけです。
作業者ごとの枠は 1 つで、前のバッチを取り戻す前に次を渡すと、枠を取り合います。
試作でこの順を誤り、データプレーンが止まったので、`Crypto` が 2 つ目を渡す呼び出しを拒み、試験がこの順を見張ります。

重ねないバッチは、次のとおりに扱います。

- 求めた枠を満たさない短い読み (ソケットが空になった) と、2 つより少ない datagram のバッチ:何もしていない時の datagram を待たせないためです
- データの message でない datagram (ハンドシェイク、cookie、壊れた datagram) を含むバッチ:ハンドシェイクを、それより前に届いたデータを受け付けた後に扱うためです
- 受信の枠の 2 つの部分にまたがる datagram を含むバッチと、作業者のレーンに収まらないバッチ

これらでは、作業者にあるバッチを先に受け付けて核と中継に渡し、その後でそのバッチを回ごとに待つ形で扱います。
受信の相の終わりには、作業者にバッチを残しません。
このため、相の終わりと何もしていない時には、重ねることによる待ちはありません。

収まる条件は次のとおりで、割り振りと同じ規則で数えます (`Crypto::can_pipeline`)。
作業者のレーンは、置き場の平文の領域の 2 番目から後のレーンです。
レーンはほぼ同じ byte を受け持ち、1 つのレーンの仕事が 128 に達するか平文のレーンに次の datagram の場所が無ければ、次のレーンに移ります。
最後のレーンにも入らなければ、収まりません。

番号と再送の窓は、[番号と再送の窓](#番号と再送の窓)の規則のままです。
次のバッチの `begin_datagram` は前のバッチの `finish_datagram` より前に呼ばれますが、受け付けは届いた順で、前のバッチの写しは 2 度目の検査で捨てます。
始めた後にトンネルを取り替えた場合は、そのバッチの仕事を知らないピアとして捨てます。

## 送信の重ね

送信の相は、送信の置き場を 2 つ持ち、交互に使います (`dataplane::driver` の `send_pipelined`)。
作業者のいる Linux のバッチの道だけで使います。

1. 先に、device の層の datagram と、送る順を待つバッチを送ります。
   送れなければ、核から引きません
2. セッションがあれば、空いた置き場に、核から作業者のレーンの枠の数までの packet を引きます
3. 求めた数を引けた (核にまだ送るものがある) バッチで、2 つ以上の packet があれば、重ねます。
   引いた packet を、UDP を先に、残りを引いた順に `begin_packet` に渡して番号を取り、送る順のまま作業者のレーンに続けて、ほぼ同じ数ずつ割り振ります
4. 作業者にある前のバッチを取り戻し、message に並べて、送る順の最後に置きます
5. 重ねるバッチを作業者に渡し、その終わりを待ちません
6. 前のバッチを `sendmmsg` で送ります。
   作業者は、この送信と次の引き出しの間に暗号化します

求めた数を引けないバッチ (核に送るものが残っていない) は重ねません。
作業者にある前のバッチを取り戻して送る順に並べ、引いたバッチは持ち主が暗号化して、その後ろに並べ、両方を送ります。
バッチが 32 KiB 以上なら、この暗号化は回ごとに待つ形で作業者と分けます。
このため、何もしていない時のゲームの応答のような 1 つの datagram は、作業者を起こさず、待たずにその相で出ます。

前のバッチの番号は、次のバッチの番号より先に取ったので、送る順は番号の順です。
ソケットが書けなくなったときは、前のバッチと、相の終わりに取り戻したバッチの両方を、古いものから送る順に持ち、書けるようになったら同じ順に送ります。
その間は核から引きません。
送信の相の終わりには、作業者にあるバッチを取り戻し、送れるだけ送ります。
作業者にバッチを残しません。
受信と送信の重ねは同じ作業者を使い、どちらも 1 度に 1 つのバッチしか渡しません。
受信の相と送信の相は交互に来て、どちらも相の終わりに作業者を空けるので、取り合いません。

セッションが無いとき、止めるときの最後の送り出し、重ねられないときは、今の送り出し (`send_batch`) を使います。
その道は、送る順を待つ 2 つの置き場のバッチを先に送ってから引きます。

## レーン

### 受信

平文の領域 (受信の枠の数 × 65535 byte) を、作業者の数より 1 つ多いレーンに分けます。
1 つのレーンは最大の datagram が入る大きさで、枠の数がレーンの数より少ないときはレーンを減らします。

1. 持ち主は、読んだバッチの datagram を届いた順に `begin_datagram` に渡し、復号の仕事をレーンに続けて割り振ります。
   GRO がまとめた枠は segment ごとに割り振ります。
   1 つの枠が 1 つのバッチの全部になりうるためです
2. 回の byte がしきい値以上なら、レーンごとにほぼ同じ byte になるように分けます。
   しきい値より小さい回は、作業者を起こさず、持ち主がすべてを行います
3. 復号はレーンごとに、datagram の領域から平文のレーンに直接書きます。
   写しはありません。
   受信の枠の 2 つの部分にまたがる datagram (GRO の segment の長さが枠の先頭の部分と違うときだけ起こります) は、持ち主が作業の領域に写して、割り振る時に復号します
4. 持ち主は、レーンの順 (届いた順) に `finish_datagram` を呼びます
5. 回の packet を UDP を先に上の層に渡します ([バッチの作りの規則](agent-throughput.md#バッチの作りの規則)の UDP を先に)

1 つのレーンが持つ仕事は 128 までです。
仕事の数か平文のレーンが尽きたら、その回をそこで閉じ、残りを次の回にします。
回ごとに packet を上の層に渡すので、平文のレーンは回ごとに先頭から使い直します。
UDP を先にする規則は回ごとに効きます。
時間の予算で区切ったバッチは、ラボと loopback の packet あたりの費用では 1 回に収まると見込みます (確かめていません)。

### 送信

送信の置き場の暗号文の領域もレーンに分けます。
重ねない送り出し (送信の重ねの、求めた数を引けないバッチと、`send_batch` の道) では、バッチが 32 KiB 以上なら回ごとに待つ形で作業者と分け、それより小さければ持ち主がすべてを暗号化します。

1. 持ち主は、核から引いた packet を送る順 (UDP を先に、残りは引いた順) に `begin_packet` に渡し、番号を取ります
2. 仕事を、送る順のままレーンに続けて、ほぼ同じ数ずつ割り振ります
3. 暗号化はレーンごとに、packet の枠から暗号文のレーンの枠に直接書きます
4. 持ち主は、レーンの順に datagram を送る列に並べます。
   この順は番号の順です。
   `sendmmsg` と UDP の GSO は暗号文の枠を datagram ごとの `iovec` で指すので、レーンをまたぐ GSO の message もそのまま送れます

### しきい値

回の暗号の byte が内部の定数 (`PARALLEL_MIN_BYTES`、32 KiB) より小さい回は、作業者を起こしません。
1 つのゲームの datagram、ACK だけのバッチ、速さを固定した経路の小さなバッチは、受け渡しの費用を払いません。
ホストの測定では、作業者 2 つの受け渡しは、全スレッドの和で 1 回に約 4 µs の CPU を使いました。
バッチの終わりが早くなるのは約 11 KB (1408 byte の packet 8 つ) からです。
32 KiB からは、全スレッドの CPU の和の増えが約 15% 以下になります。
時間の予算で区切る受信と送信のバッチは、作業者が速くするほど 1 回の枠の数が増えるので、詰まった転送では 1 回の byte はこの値を大きく超えると見込みます (確かめていません)。

## 遅れ

- 何もしていない時:バッチは短い読みで終わるので重ねず、しきい値より小さいので作業者も起こしません
- 負荷の下:重ねたバッチは、次のバッチを読んで始めるまで受け付けを待ちます。
  待つのはバッチ 1 つ分 (読みと始めの時間) までで、受信の相の終わりには残りません
- UDP を先に:バッチごとに、受け付けたバッチの UDP を TCP より先に中継に渡します。
  次のバッチの UDP は、前のバッチの TCP の後になります
- 送る向き:重ねたバッチは、次のバッチを引いて番号を取るまで送るのを待ちます。
  待つのはバッチ 1 つ分までで、送信の相の終わりには残りません。
  重ねるのは核にまだ送るものがあるときだけなので、何もしていない時の datagram は待ちません。
  バッチの中では UDP を先に送ります

## メモリ

置き場の buffer は増えません。
平文の領域と暗号文の領域を、同じ大きさのままレーンに分けるだけです。
割り切れない分の切り上げで、平文の領域はレーンの数より少ない byte、暗号文の領域は最大で (レーンの数 - 1) × 暗号文の枠 1 つ分だけ大きくなります。
[メモリの上界の行](agent-parity.md#メモリの上界の行)には次を足します。

- `batch` の項:レーンに分けた置き場の大きさです (`wgft_udp_batch::store_bytes` のレーンの数の引数)。
  重ねる形の 2 つ目の受信の置き場 (`wgft_udp_batch::rx_store_bytes`) と送信の置き場 (`wgft_udp_batch::tx_store_bytes`) を足します。
  既定の上限で、受信の置き場で約 8.1 MiB、送信の置き場で約 1.2 MiB 増えます。
  正確な値は[メモリの上界の表](agent-bound.md)にあります
- `crypto` の項:作業者ごとのスタック (明示の 128 KiB) とスレッドの状態の許容 (4 KiB)、作業者ごとの枠、回のレーンと、受信と送信の重ねる 2 つの置き場ごとの作業者のレーンの仕事の列です (`Crypto::bytes`)

どちらの項も、ホストの CPU の数に依らず、このビルドが作る最も多い作業者 (2 つ) で数えます。
起動の行と上界の表がホストで変わらないためで、作業者の少ないホストは項より少なく持ちます。
既定の上限で `crypto` の項は 1 MiB より小さい値です。

## 起動の行

データプレーンは、作業者を作った世代の始めに `tunnel crypto: <N> worker threads beside the data plane for rounds of 32 KiB or more` を書きます。
重ねるバッチはしきい値によらず作業者に渡すので、この行の値は回ごとに待つ形のしきい値です。
作業者を使わない道では書きません。
行の形は保証の外です。

## 判定

判定の線は所有者が決めた線で、緩めません。
回ごとに待つ形は、ホストの測定 (`wgft-agent-perf --crypto-workers N`、`wgft-heavy --timing` の車線、測るスレッド、相手、作業者を同じ L2 の塊と別の塊に固定) で次をすべて満たしたので、agent で試しました。

- 測るスレッドの byte あたりの CPU:1408 byte と burst 64 で、作業者の無い split の道の値の (1 - 0.8 × c × N / (N + 1)) 倍以下です。
  c は同じ道の暗号の割合で、道具が同じ CPU で測った 1 packet の暗号の時間から求めます
- すべてのスレッドの byte あたりの CPU の和:同じ道の 1.10 倍以下です
- burst ごとの経過の時間の p99:同じ道以下です
- burst 1 と 64 byte:burst ごとの経過の時間の p99 が、同じ道の値に 1 µs を足した値以下です
- 作業者を使う間も、データプレーンのスレッドの packet あたりの確保が 0 です

ラボ (`lab/lab paired`、`cpu-paired.sh`、`base:rust` は作業者の無い build) では、次をすべて満たすことを採る条件にします。
重ねる形も同じ線で判定します。

- 8 vCPU で、暗号が 25% 以上の向きの `MBITRATIO` が 1.15 以上です
- 既定の 4 vCPU で、`MBITRATIO` が 0.97 以上です
- エージェントの `RATIO` (byte あたりの CPU) が 1.10 以下です。
  1.00 を超える分は、速さと引き換えの費用として所有者に示します
- UDP の遅れ:[判定の手順](agent-throughput.md#判定の手順)の非劣性の線を、頭打ちの転送と、送る向きの頭打ちにしない転送で満たします
- 速さを固定した経路の `RATIO` が 1.05 以下です
- ラボの一式が通ります

## ホストの測定の結果

この節は回ごとに待つ形の値です。

`wgft-agent-perf --crypto-workers N` を、`wgft-heavy --timing` の E コアの車線で、測るスレッド、相手、作業者を別の CPU に固定して流しました (2026-11-02、組ごとに 7 回の中央値)。
比べる相手は、同じ段に分けた口を持ち主だけで行う形 (`--crypto-workers 0`) です。
1408 byte、burst 64 の値は次のとおりです (byte あたりの CPU は ns、経過の時間は µs)。

| 向き | 形 | 持ち主の CPU | 全スレッドの CPU | burst の経過の p50 | p99 |
|---|---|---|---|---|---|
| 受ける | 持ち主だけ | 0.591 | 0.591 | 53.8 | 63.3 |
| 受ける | 作業者 1 つ | 0.427 | 0.617 | 56.1 | 65.5 |
| 受ける | 作業者 2 つ | 0.285 | 0.631 | 26.8 | 34.5 |
| 受ける | 作業者 2 つ、別の L2 の塊 | 0.309 | 0.690 | 29.7 | 40.9 |
| 送る | 持ち主だけ | 0.677 | 0.677 | 62.7 | 72.0 |
| 送る | 作業者 1 つ | 0.416 | 0.705 | 41.0 | 50.4 |
| 送る | 作業者 2 つ | 0.337 | 0.723 | 32.6 | 45.9 |
| 送る | 作業者 2 つ、別の L2 の塊 | 0.371 | 0.822 | 37.5 | 47.0 |

- 作業者 2 つ、同じ L2 の塊:判定の線をすべて満たしました。
  暗号の割合 c は、持ち主だけの形の packet あたりの CPU と、前提の値の 1 packet の暗号の時間から、受ける向き約 0.80、送る向き約 0.79 です

- 別の L2 の塊:全スレッドの CPU が受ける向きで 1.17 倍、送る向きで 1.21 倍になり、1.10 倍の線を超えました。
  平文と暗号文の cache line が L2 の塊の間を動くためと考えます (確かめていません)。
  ラボの 8 vCPU は 2 つの塊にまたがります
- 段に分けた口の費用:持ち主だけの形は、前の 1 つの呼び出しの形より、持ち主の CPU が 1408 byte で約 3%、64 byte で約 8% 多くなりました。
  仕事の列への出し入れと、回の 3 つの走査の分です
- burst 1 と 64 byte:しきい値より小さいので作業者は動かず、p99 は持ち主だけの形とほぼ同じでした
- 確保:作業者を使う受信と送信で、プロセスの確保の呼び出しが packet あたり 0 であることを試験 (`wgft-udp-batch` の `alloc_crypto`) で確かめています

## 起床の遅れの測定

眠った作業者を起こす費用を、ホストとラボの VM で直接測りました (2026-11-02、標準ライブラリだけの小さな道具、`wgft-heavy --timing` の車線 a)。
値は、起こす側が `unpark` を呼ぶ直前から、起こされたスレッドの最初の命令までの時間と、`unpark` の呼び出しの時間の中央値です。
起こされる側の CPU は、その前に 5 µs から 100 µs の間何もしていません。

| 場所 | 起きるまで | `unpark` の呼び出し |
|---|---|---|
| ホストの E コア 4 つ | 約 1.0 µs | 約 0.35 µs |
| VM、4 vCPU (同じ E コア) | 約 2.0 µs | 約 0.4 µs |
| VM、8 vCPU | 約 2.4 µs | 約 0.6 µs |

1 ms 何もしていなかった後は VM で約 3.5 µs、10 ms の後は休止の深さにより 7 µs から 80 µs でした。
条件変数で起こしても同じでした。
測ったのは何もしていない VM で、負荷の下の値は測っていません。

## 回ごとに待つ形のラボの結果

`lab/lab paired` (受ける向き、iperf3、`base:rust` は作業者の無い build) の値です (2026-11-02)。

| 形 | vCPU | `MBITRATIO` | `RATIO` |
|---|---|---|---|
| しきい値 32 KiB (作業者は動きません) | 8 | 0.976 | 1.025 |
| しきい値 32 KiB | 4 | 0.974 | 1.035 |
| しきい値 8 KiB の試し | 8 | 0.987 | 1.270 |
| しきい値 8 KiB と、眠る前に 50 µs 回り続ける作業者の試し | 8 | 1.176 | 2.478 |

- ラボの受信のバッチは、時間の予算 (25 µs) で約 12 から 16 個の datagram (約 17 から 23 KB) になり、32 KiB のしきい値に届きません。
  このため作業者は動かず、段に分けた口の費用だけが残りました
- 作業者を動かすと、速さは変わらず、byte あたりの CPU が 27% 増えました。
  1 回の起床は 2 µs から 2.4 µs ですが、回ごとに `unpark` 2 回、起床、遅いレーンの終わりの待ちを払い、20 µs の回で暗号を移して得る約 5 µs の大半を使います
- 作業者を回り続けさせると速くなりますが、作業者が持ち主の暗号でない仕事の間も回るので、byte あたりの CPU が 2.5 倍になります

## 重ねる形のラボの途中の値

途中の値で、判定ではありません。
`lab/lab paired` (iperf3、`base:rust` は `feat/agent-parallel` の作業者の無い build、4 round × 3 回) の値です (2026-11-02)。
受ける向きの速さと CPU は、この変更の commit で測りました。
遅れは、収まる条件が粗い試作の build で測りました。

| 向き | vCPU | stream | `MBITRATIO` | `RATIO` | `VMRATIO` |
|---|---|---|---|---|---|
| 受ける | 8 | 1 | 1.356 | 1.078 | 1.001 |
| 受ける | 8 | 4 | 1.312 | 1.089 | 1.015 |
| 受ける | 4 | 1 | 1.240 | 1.045 | 0.975 |
| 受ける | 4 | 4 | 1.173 | 1.050 | 0.998 |
| 送る (受信だけ重ねる) | 8 | 1 | 0.987 | 1.012 | 1.013 |
| 送る (送信も重ねる試作) | 8 | 1 | 1.378 | 0.978 | 0.965 |

送信も重ねる試作は、送る向きの判断のための 1 組だけで、ほかの組と遅れは測っていません。
暗号は送る向きの CPU の約 19% で、暗号だけを移す上限の見積もりは 1.24 倍ですが、測った速さはそれを超えました。
理由は確かめていません。
時間の予算で区切るバッチが大きくなり、UDP の GSO の message が長くなることが効いていると考えます。

UDP の往復の遅れ (受信を重ねる試作、4 vCPU、8 round):

- 受ける向きを 3050 Mbit/s に頭打ちにした転送:非劣性の線をすべて満たしました (転送の間の p99 0.996、jitter 1.024、何もしていない時の p99 0.974、jitter 0.953、失った数 0)。
  この固定の速さでの `RATIO` は 1.199 です
- 受ける向きの頭打ちにしない転送 (記録):速さ 1.241 倍、転送の間の p50 0.819 倍、p99 0.935 倍、jitter 1.184 倍 (区間の下端 1.094) で、jitter は悪くなりました

## 引き換え

重ねる形が速さと引き換えにするものは次のとおりです (途中の値)。

- byte あたりの CPU:速さを制限しない転送で 1.05 倍から 1.09 倍、3050 Mbit/s の頭打ちの転送で 1.20 倍です。
  仮の線 1.10 倍を、頭打ちの負荷で超えます
- メモリ:2 つ目の受信と送信の置き場で、既定の上限で約 9.3 MiB 増えます
- 遅れ:負荷の下で、受信の受け付けと送信の送り出しに、それぞれバッチ 1 つ分の待ちが増えます。
  速さを制限しない受信の UDP の jitter が 1.18 倍になりました。
  p50 と p99 は良くなりました
- 複雑さ:向きごとに 2 つの置き場の交互の使い方と、作業者に渡す順の規則、送る順を待つ 2 つのバッチの扱いが加わります
