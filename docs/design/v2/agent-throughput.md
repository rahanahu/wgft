# 速さを制限しない経路の agent の性能

この文書は、Rust の agent の転送の速さと byte あたりの CPU を、速さを制限しない経路で測った基準の値と、送受信をまとめる段 (バッチの段) の目標を定めます。
バッチの段の実装は、この文書の目標と測り方で判定します。
[wgstack の性能の段階](../userspace/wgstack-performance.md#目標と制約)の 4 つの目標は、この段でもその行列で必達の条件のままです。

## 範囲

- 対象:Rust の agent のユーザー空間モードの、WireGuard の UDP のソケットとデータプレーンの 1 つのスレッドです ([データプレーンの駆動](wgstack-rs.md#データプレーンの駆動))
- バッチの段の手段:Linux の `recvmmsg` と `sendmmsg`、UDP の GSO と GRO、`WGFT_AGENT_BATCH_MIB` を実際に使うこと、それに伴う device の層の受け渡しの形の変更 (packet ごとの確保をやめ、呼び手の buffer に書く形) です
- 受信の窓の段:バッチの作業は、遅れの目標で wgstack の受信の窓を頭打ちにする段も含みます ([受信の窓の段](#受信の窓の段))
- Linux だけ:Windows と macOS は 1 つずつの送受信のままにし、build と CI を通します
- 比べる相手:今の Rust の agent (必達の目標の基準)、Go の v1 の agent の gVisor (置き換えた製品)、agent のカーネルモードのカーネルの WireGuard とカーネルの TCP (上限で、努力の目標の基準) です
- 1 つのスレッドのまま:バッチの段の目標は、データプレーンを 1 つのスレッドで動かす今の作り ([スレッドと所有](wgstack-rs.md#スレッドと所有)) のための目標です。
  データプレーンを複数のスレッドに分けることは、バッチの段の範囲の外です

### 作業の順

所有者の決定 (2026-11-02) により、速さの作業は次の順に進めます。

1. 1 つのデータプレーンのスレッドを速くします。
   byte と packet ごとの仕事を減らす変更で、まずバッチ、次に割り当て器とそれに類する変更です
2. その後で、データプレーンを複数のスレッドに分ける (暗号を別のスレッドで行うなど) かを、測った遅れとメモリで決めます

## 測り方

測定は `lab/lab paired` で 2 つの腕を 2 台の VM で同時に流し、round ごとに VM を入れ替えます。
理由と解析は [CPU の比べ方](../userspace/wgstack-performance.md#cpu-の比べ方)にあります。
この文書の値は次の条件で測ります。

- 経路:`fast` (netem なし) です。
  エージェントの namespace の `eth0` の UDP の segmentation offload は切ります ([ラボの経路の UDP の GSO](../userspace/wgstack-performance.md#ラボの経路の-udp-の-gso))
- 転送:`--tool iperf3` で、1 回の実行は 10 秒の iperf3 の転送です。
  stream は `--streams 1` と `--streams 4` です。
  `tcpquality.py` の送り手と受け手は byte ごとに乱数と SHA-256 を計算するので、カーネルの速さでは測る道具の CPU が VM 全体の値を占めます
- 向き:エージェントが送る向き (`--direction down`、client の取得) と受ける向き (`--direction up`) です
- 回数:既定の 4 round、round ごとに 3 回で、12 組です
- VM:Debian 13 のカーネル 7.2.11、4 vCPU、2 GiB です。
  vCPU は Core Ultra 7 270K Plus の E コアの 1 つの L2 の塊 (4 個) に 1 対 1 で固定します (`WGFT_LAB_PAIR_CPUS`)
- 腕:`rust` (Rust の agent)、`gvisor` (Go の agent と gVisor)、`kernel` (agent のカーネルモード)、`base:rust` (`--base` の commit の Rust の agent) です。
  server はどの腕でもカーネルモードの Go の `wgft` です
- Rust の agent の build:ラボの build は `cargo zigbuild` の `x86_64-unknown-linux-musl` で、libc と割り当て器は zig の同梱のもの (`c.malloc`、`heap.SmpAllocator`) です。
  glibc の build との比べは [割り当て器と libc](#割り当て器と-libc) にあります

測る量は次のとおりです。

- 速さ:受け手の iperf3 が読んだ byte を、その iperf3 の転送の時間で割った値 (Mbit/s) です。
  解析の `MBITRATIO` の行が組にした速さの比です
- UDP の往復の遅れ:`--udp-ping` の値です ([UDP の往復の遅れ](#udp-の往復の遅れ))。
  解析の `LAT` と `LATRATIO` の行に出ます
- エージェントの byte あたりの CPU:エージェントのプロセスの cgroup の `cpu.stat` の差を、受け手が読んだ byte で割った値 (GB あたりの秒) です。
  解析の `RATIO` の行がこの値の比です
- VM 全体の byte あたりの CPU:VM の `/proc/stat` の user、nice、system、irq、softirq の和の差を、同じ byte で割った値です。
  解析の `VMRATIO` の行がこの値の比です。
  5 つの namespace は 1 つの VM にあるので、この値は client、LAN のホスト、server、ルータの分も含みます。
  同じ経路の 2 つの腕では、違うのはエージェントの側だけです。
  カーネルモードの agent はプロセスが仕事をしないので、`kernel` の腕はこの値だけで比べます
- 詰まりの目安:エージェントの CPU の割合 (1 つの CPU に対する割合)、送り手のスレッドの CPU の割合、VM 全体で忙しい CPU の数 (4 個のうち) です

ラボの経路には実際のホストと違う点が 1 つあります。
エージェントが UDP の datagram を送る system call は、veth の反対側のルータと server の namespace の受信の処理 (softirq) を、同じ文脈でそのまま実行します。
この処理はエージェントの cgroup に数えられ、送る向きのエージェントの CPU の約 36% を占めます ([CPU の行き先](#cpu-の行き先))。
実際のホストでは、この処理は別のホストで行われます。
同じ処理はどの腕でも起こるので比には残りますが、バッチで減らない分として目標の見積もりに入れます。

### 詰まりの場所

- Rust の agent:どのセルでも、エージェントは 1 つの CPU の 0.86 から 0.90 を使い、VM 全体は 4 個のうち 2.1 から 2.3 個の CPU を使います。
  送り手の iperf3 のスレッドは 1 つの CPU の 0.19 以下です。
  データプレーンは 1 つのスレッドなので、速さはエージェントのスレッドで決まります。
  stream を 4 本にしても速くなりません
- gVisor:エージェントは送る向きで 1.7 から 1.8 個、受ける向きで約 2.0 個の CPU を使います。
  受ける向きでは VM 全体が 4 個のうち約 3.4 個を使うので、エージェントと VM の両方が詰まりに近い状態です。
  受ける向きの速さは、複数のスレッドで動く gVisor が Rust の agent を上回ります
- カーネルモード:VM 全体が 4 個のうち 3.27 から 3.50 個の CPU を使い、送り手は 0.15 以下です。
  速さは、client、server、ルータ、LAN のホストと 4 vCPU を分け合う VM の容量で決まります。
  このため、カーネルモードの値はエージェントの上限ではなく、このラボの VM の上限です
- 測る道具:どのセルでも送り手のスレッドは 1 つの CPU の 0.19 以下で、iperf3 が詰まりではありません

受ける向きでは、Rust の agent の VM 全体の byte あたりの CPU がカーネルモードを下回ります。
カーネルモードは VM がほぼ埋まった状態で測った値で、CPU が混み合う時の手間 (待ちと切り替え) を含むと考えますが、内訳は確かめていません。

### UDP の往復の遅れ

`--udp-ping` を付けた組で、UDP の中継を通る往復を測りました。
client は 100 byte の datagram を 10 ms ごとに送り、LAN のホストの echo が送り返します。
各実行は、何もしていない時に 5 秒測り、続けて 1 stream の大きな TCP の転送の間に 9 秒測ります。
jitter は、続けて送った datagram の往復の時間の差の絶対値の平均です。
値は ms で、p50、p99、jitter は実行ごとの値の中央値です。

判定に使うのは、TCP の転送を `--bulk-mbit` で頭打ちにした組です。
頭打ちの値は、どの腕にも同じ負荷を掛けるため、`base:rust` (今の Rust の agent) のその向きの速さの約 0.75 倍にしました (送る向き 1250 Mbit/s、受ける向き 3050 Mbit/s)。
速さを制限しない転送では、詰まりの腕の前に待ち行列が溜まり、VM の CPU の埋まり方も腕ごとに違うので、遅れの差が仕組みの差でなく待ち行列と VM の負荷の差になります ([受ける向きの待ちの確かめ](#受ける向きの待ちの確かめ))。
速さを制限しない組は記録として残し、判定に使いません。

  負荷の下の p50 が何もしていない時より小さいのは、忙しい vCPU が休止しないためと考えます (確かめていません)
- 速さを制限しない転送では、受ける向きの Rust の agent の遅れが最も大きく、p50 が約 7 ms です ([受ける向きの待ちの確かめ](#受ける向きの待ちの確かめ))

### 受ける向きの待ちの確かめ

速さを制限しない受ける向きの転送では、UDP の datagram は、TCP のデータと同じ WireGuard の UDP のソケットの受信の待ち行列に並びます。
エージェントの 1 つのスレッドが受ける速さの詰まりなので、client の TCP が送り込んだ分がこの待ち行列に溜まります。
1 台の VM で確かめた値 (2026-11-02、1 回ずつ、15 秒の転送) は次のとおりです。
`ss -uamn` はエージェントの WireGuard のソケットを 0.5 秒ごとに読んだ値で、待ち行列 (Recv-Q) は skb の大きさで数えるので、中身の byte より大きくなります。

| 場合 | 速さ (Mbit/s) | UDP の転送の間の p50 と p99 (ms) | Recv-Q の中央値と最大 (byte) | `UdpRcvbufErrors` の増え | iperf3 の再送 |
|---|---|---|---|---|---|
| Rust の agent、1 stream | 4023 | 7.1、10.2 | 5,024,484、6,104,236 | 0 | 89 |
| Rust の agent、4 stream | 3899 | 13.2、17.3 | 10,008,320、10,860,544 | 254 | 415 |
| gVisor、1 stream | 4466 | 3.2、5.8 | 0、2,745,344 | 0 | 3,913 |

- 1 stream の Rust の agent では、ソケットに約 5 MB (skb の大きさ) が溜まり、約 4 Gbit/s で読む時間は UDP の待ちと合います。
  溜まる量は wgstack が広告する受信の窓 (boost の 4 MiB) で決まると考えます
- 4 stream では窓が 4 本分になるので待ちは約 4 倍になると予想しましたが、実際は約 1.9 倍でした。
  待ち行列がソケットの受信のバッファ (14,680,064 byte) の近くで上限に達し、溢れた datagram (`UdpRcvbufErrors`) が TCP の再送になったためです
- gVisor はソケットからすぐに読むので、ソケットの待ち行列は空のことが多く、待ちは gVisor の中の別の所にあります (場所は確かめていません)
- 同じ負荷 (3050 Mbit/s) では待ち行列が溜まらず、p50 は約 0.19 ms です。
  この遅れは、エージェントが詰まりになった時だけ現れます
- エージェントが速く読めば待ちは縮みますが、待ち行列を短く保つ変更は [受信の窓の段](#受信の窓の段) で行います

### カーネルモードの遅れを決める仕組みの確かめ

カーネルモードの大きな転送の間の UDP の遅れが何で決まるかを、1 台の VM (4 vCPU、1 つの車線) で設定を 1 つずつ替えて確かめました (2026-11-02、設定ごとに 10 秒の転送を 2 回、速さを制限しない転送)。
替えた設定は、client と LAN のホストの namespace の TCP Small Queues の上限 (`net.ipv4.tcp_limit_output_bytes`、既定 4194304 を 65536 に)、両者の `eth0` の qdisc (既定は veth の `noqueue`、`fq` と `fq_codel` に)、受信のバッファの上限 (`net.ipv4.tcp_rmem` の最大、既定 14021088 を 1048576 と 16777216 に) です。
仕組みの説明は公開の文書 (`tc-fq(8)`、`tc-fq_codel(8)`、`ip-sysctl` の文書) によります。
値は 2 回の UDP の往復の p50 と p99 (ms) と速さ (Mbit/s) です。

| 向き | 腕 | 既定 | TSQ 64 KiB | `fq` | `fq_codel` | `tcp_rmem` の最大 1 MiB | 16 MiB |
|---|---|---|---|---|---|---|---|
| 受ける | カーネルモード | 3.0 から 3.1、3.8 から 4.2、約 5880 | 4.4 から 4.5、5.5 から 6.1 | 4.6 から 4.7、5.4 から 6.4 | 3.3 から 4.5、4.5 から 6.4 | 0.84 から 0.87、1.09、約 5830 | 2.2 から 4.6、3.3 から 6.8 |
| 送る | カーネルモード | 3.3 から 5.3、4.5 から 6.6、約 5360 | 3.1 から 3.6、4.3 から 6.4 | 3.2 から 4.8、4.5 から 5.6 | 3.4 から 3.8、4.6 から 4.9 | 0.89 から 0.93、1.11 から 1.15、約 5440 | 3.2 から 4.7、4.4 から 5.9 |
| 受ける | Rust の agent | 7.3 から 7.5、8.9 から 9.9、約 4060 | 7.4 から 7.5、9.4 から 10.5 | 6.2 から 6.3、7.7 から 8.1 | 3.9 から 7.6、6.9 から 9.1 | 4.3 から 6.5、5.6 から 8.3 | 6.5 から 7.2、7.9 から 9.1 |
| 送る | Rust の agent | 1.49 から 1.50、2.00 から 2.06、約 1660 | 1.52 から 1.53、2.06 | 1.51、2.04 から 2.14 | 1.50 から 1.52、2.26 から 2.34 | 1.45 から 1.49、1.71 から 2.07 | 1.52 から 1.53、1.94 から 2.09 |

測ったこと:

- カーネルモードの遅れは、受け手の TCP の受信のバッファの上限で決まります。
  上限を 1 MiB にすると、速さはほぼ変わらずに (約 1% 以内)、p50 が約 3 から 5 ms から約 0.9 ms に、p99 が約 4 から 6.6 ms から約 1.1 ms に下がりました
- TCP Small Queues、`fq` の pacing、`fq_codel` は、どれも遅れを下げませんでした。
  この経路の待ち行列は、送り手と受け手の `eth0` の qdisc 以外の場所にあります
- Rust の agent の受ける向きでは、client と LAN のホストの設定はどれも、遅れをはっきりとは変えませんでした。
  この向きの受け手は wgstack で、受信の窓はカーネルの設定ではなく wgstack が決めるためです

推定したこと (確かめていません):

- どの腕でも、速さを制限しない転送の間の UDP の遅れは、詰まりの所に溜まったデータを流し切る時間で、溜まる量は受け手が広告する窓の大きさで決まります。
  カーネルモードの受信のバッファの自動調整は、この経路では窓を上限まで広げ、Rust の agent の wgstack は boost の 4 MiB まで広げます。
  同じ負荷の比べ ([UDP の往復の遅れ](#udp-の往復の遅れ)) ではカーネルモードの遅れが Rust の agent より小さく、この差は窓ではなく、UDP の中継がユーザー空間を通り、同じスレッドの TCP の仕事の後ろで待つことによると考えます。
  速さを制限しない転送でのカーネルモードの遅れは窓で決まり、その下ではユーザー空間を通らない利点が見えなくなります
- 受ける向きの 7 ms の直し方の設計の入力:wgstack の受信の窓を、帯域と往復の時間の積に小さな余裕を足した値で頭打ちにすれば (遅れを目標にした窓)、速さを保ったまま待ち行列を約 1 ms に保てる見込みです ([受信の窓の段](#受信の窓の段))。
  決まった小さな上限は、往復の時間の長い実際の経路で速さを落とすので採りません
- バッチの設計の入力:送り手の側の設定 (TSQ、pacing、qdisc) で UDP の遅れは下がらなかったので、遅れの予算はエージェントの中の待ち (1 回の起床の長さ) だけを対象にすれば足ります

### 遅れの予算の既定の値

バッチの時間の上限 (遅れの予算) の既定の値は 50 µs にします。
理由は次のとおりです。

- 今のデータプレーンは 1 回の起床で核から 64 packet まで引きます ([送り出しと受信の値](agent-parity.md#送り出しと受信の値))。
  ラボの送る向きの packet あたり約 6.5 µs では、1 回の起床が約 0.4 ms スレッドを占め、その間は同じスレッドの UDP の中継の task が動けません。
  速さを制限しない送る向きの転送の間の UDP の往復の p50 は約 1.5 ms で、同じ負荷 (1250 Mbit/s) では約 0.3 ms です
- 予算は今の 1 回の起床 (ラボで最大約 0.4 ms) を置き換えるので、UDP の datagram が TCP の仕事の後ろで待つ時間は今より短くなります。
  50 µs の予算で残る待ちは、エージェントを 1 回通るたびに最大 0.05 ms、往復で最大 0.1 ms です。
  これは、同じ負荷での Rust の agent とカーネルモードの p50 の差 (送る向きで約 0.24 ms) の半分以下です
- 50 µs は、今のラボの packet あたりの費用で約 8 packet、バッチで費用が下がればそれより多くの packet です。
  system call の固定の費用の大半は 8 から 16 packet のまとめで均せると見込みますが、確かめていません
- 予算を時間で決めるのは、packet あたりの費用が経路、CPU、暗号で数倍変わり、packet の数で決めると遅い CPU で待ちが延びるためです

### 割り当て器と libc

同じ commit を glibc 2.41 の target (`x86_64-unknown-linux-gnu.2.41`) で build し、musl の build と組にして比べました (`--base HEAD --base-rust-target x86_64-unknown-linux-gnu.2.41`、腕 `rust base:rust`、1 stream)。

| 向き | glibc / musl の速さ | musl / glibc の byte あたりの CPU (`RATIO`) | `VMRATIO` |
|---|---|---|---|
| 送る | 1.06 倍 (1792 と 1698 Mbit/s) | 1.065 (1.045 から 1.072) | 1.038 (1.006 から 1.074) |
| 受ける | 1.22 倍 (4897 と 4021 Mbit/s) | 1.245 (1.217 から 1.256) | 1.120 (1.084 から 1.139) |

musl の build の profile では、`calloc` と `free` (zig の `c.malloc` と `heap.SmpAllocator`) が送る向きで 6.1%、受ける向きで 14.6% を占めます ([CPU の行き先](#cpu-の行き先))。
glibc の build の profile では、同じ確保が送る向きで 1.4%、受ける向きで 3.1% でした。
glibc の `memset` と `memcpy` は記号の無い libc の中にあり、内訳には `[unknown]` として出るので、零埋めの分は分けられていません。
差の大部分は datagram ごとの確保なので、バッチの段で確保をやめると、build の違いによる差も大部分が消えると見込みます。
ただし、device の層の確保をやめた試作 ([割り当て器と libc の比べ](wgstack-rs.md#割り当て器と-libc-の比べ)の build E) でも、glibc の build は受ける向きの byte あたりの CPU が 8% 少ないままでした。
残る差は主に `memcpy` の速さと考えます ([割り当て器と libc の比べ](wgstack-rs.md#割り当て器と-libc-の比べ))。

製品の割り当て器はこの段で変えません。
割り当て器と libc は、2026-11-02 に所有者が決めました ([割り当て器と libc の比べ](wgstack-rs.md#割り当て器と-libc-の比べ))。
割り当て器は OS の標準、Linux の build は musl の静的な build のままです。
この文書の目標は、今のラボの build (musl) の値を基準にします。
受ける向きの見積もりの多くは今の割り当て器の `calloc` の費用なので、ラボの build の libc か割り当て器を変えたときは、基準の値を測り直し、目標を導き直します。

## CPU の行き先

1 stream の転送の最中に、エージェントのプロセスを `perf record` (`task-clock` の 997 Hz、DWARF の呼び出しの列) で 4 秒ずつ記録し、`perf stat` で system call の数を 5 秒ずつ数えました。
ラボの VM の CPU は PMU を仮想化しないので、数えられるのはソフトウェアの event と tracepoint だけです。
記録には、同じ commit を記号の表と行の情報を残して build した Rust の agent を使いました。
1 回の測定で、1 つの VM の 4 vCPU を 1 つの車線に固定しました。

musl の build の値は次のとおりです。
割合はエージェントのプロセスの標本に占める割合で、分け方は呼び出しの列で決めました。

| CPU の行き先 | 送る向き | 受ける向き |
|---|---|---|
| 送った後の softirq (veth、ブリッジ、ルータ、server の受信) | 36.3% | 4.7% |
| UDP の送信の system call (`sendto` の中のエージェントの分) | 16.0% | 1.2% |
| UDP の受信の system call (`recvfrom`) | 0.4% | 8.7% |
| ChaCha20-Poly1305 (`ring`) | 13.8% | 28.2% |
| 待ち、起床、スケジューラ | 7.3% | 8.8% |
| `malloc` と `free` | 6.1% | 14.6% |
| wgstack の核 (checksum を含みます) | 5.8% | 9.4% |
| `memset` | 2.4% | 8.7% |
| WireGuard の device の層 | 3.3% | 3.9% |
| `memcpy` | 2.2% | 3.2% |
| libc の system call の包み (`sccp` など) と tokio | 2.8% | 2.8% |
| LAN 側の TCP のソケット | 1.6% | 3.6% |
| そのほか | 2.0% | 2.2% |

packet あたりの値は次のとおりです。

| 値 | 送る向き | 受ける向き |
|---|---|---|
| データの datagram の数 (毎秒) | 約 135,000 | 約 368,000 |
| データの datagram あたりの CPU | 6.5 µs | 2.4 µs |
| データの datagram あたりの system call | 1.55 | 1.08 |
| エージェントが受ける ACK の datagram | データの 2 つに 1 つ | - |
| エージェントが返す ACK の datagram | - | データの約 64 に 1 つ |

内訳から次のことが分かります。

- 送る向き:datagram ごとに 1 回の `sendto` を呼びます。
  `sendto` の中の時間の 7 割は、veth の反対側の受信の処理です。
  前の項のとおり、これはラボの経路だけで起こる分です。
  待ちとスケジューラの分の大半は、`sendto` から戻る所での切り替えです。
  送った datagram が server の側のカーネルの WireGuard の worker を起こし、同じ vCPU を取るためです
- 受ける向き:datagram ごとに 1 回の `recvfrom` を呼び、復号の前に datagram ごとに 1 回 `calloc` を呼びます。
  `calloc` は WireGuard の device の層の受信 (`Protocol::receive`) の packet の確保で、零で埋める分を含みます
- 送る向きの `calloc` は、device の層の暗号化 (`Device::handle_packet` の encapsulate) の packet の確保です
- これらの確保と写しは (最初の段階の前の値)、sanstun ではなく wgft 自身の `wgft-wireguard` のコードにありました。
  受信は `Protocol::receive` が datagram ごとに零で埋めた buffer を確保して復号し (`protocol.rs`)、`Device` が詰め物を除いた平文を `to_vec` で別の buffer に写して待ち行列に積みます (`device.rs`)。
  送信は `Device::handle_packet` が packet を `to_vec` で写し (`device.rs`)、`Protocol` が暗号文の buffer を確保します (`protocol.rs`)
- `memset` の大半は wgstack の受信と送信の輪の `trim` で、16 KiB の chunk を返す時の零埋めです。
  qbench の segment ごとのベンチで見つけた費用 ([qbench での測定](wgstack-rs.md#qbench-での測定)) と同じもので、バッチでは減りません
- 暗号は送る向きで 14%、受ける向きで 28% です。
  バッチは暗号の手間を変えません

送る向きのエージェントのスレッドは 1 つの CPU の約 0.89 を使い、VM 全体では 4 個のうち約 2.2 個の CPU が忙しくなります。
送り手の iperf3 のスレッドは 1 つの CPU の 0.02 しか使いません。
このため送る向きの速さはエージェントの 1 つのスレッドで決まります。
受ける向きもエージェントのスレッドは約 0.85 で、glibc の build で byte あたりの CPU が減ると速さが上がった ([割り当て器と libc](#割り当て器と-libc)) ので、同じくエージェントで決まると考えます。
1 を下回る分は、同じ vCPU の softirq と worker に取られる時間と考えますが、確かめていません。

## バッチで減らせる分の見積もり

バッチの段で減る分を、[CPU の行き先](#cpu-の行き先)の musl の build の内訳から見積もります。
バッチで減らない分は、暗号、wgstack の核、`memset` (輪の零埋め)、LAN 側の TCP のソケット、送った後の softirq です。

| 減る分 | 送る向き | 受ける向き | 理由 |
|---|---|---|---|
| UDP の送信の system call | 16.0% のうち約 2/3 | 1.2% のうち約 2/3 | `sendmmsg` と UDP の GSO で、system call の出入り、宛先の経路の検索、skb の確保を 64 datagram までまとめて 1 回にします。datagram ごとに残るのは写しと分割です |
| UDP の受信の system call | - | 8.7% のうち約 1/3 | `recvmmsg` で system call の出入りとソケットの錠をまとめます。ラボの veth は GRO を行わないので、UDP の GRO による datagram の結合はラボでは起こらないと見込みます |
| `malloc` と `free` | 6.1% | 14.6% | device の層が呼び手の buffer に書く形にし、datagram ごとの確保と零埋めをやめます |
| libc の包みと tokio | 2.8% のうち約 2.5% | 2.8% のうち約 2.5% | system call の回数に比例する分です |
| 合計 (必達の見積もり) | 約 19% | 約 21% | |
| 待ちとスケジューラ (努力の分) | 7.3% のうち約半分 | 8.8% のうち約半分 | `sendto` から戻る所の切り替えと起床の回数が減る分です。回数がどれだけ減るかは測っていません |
| 合計 (努力の見積もり) | 約 25% から 28% | 約 25% から 28% | 送信と受信の system call の残りの一部も含めます |

送った後の softirq (送る向きの 36%) はラボの経路の分で、UDP の segmentation offload を切った経路では datagram ごとに残ります。
ラボは、腕の間で CPU を比べられるように、エージェントの namespace の `eth0` の UDP の segmentation offload を切ります。
offload を残すと、UDP の GSO の packet は分割されないまま veth とルータを通るので、この 36% の多くも減ると見込みます。
このため、この見積もりは減る分を少なめに見積もっている可能性があります (確かめていません)。
バッチの段の判定では、目的の組を offload を切った既定の形 (判定に使います) と `--agent-gso on` (2 つの腕で同じ設定、記録します) の両方で流し、両方の値を PR に書きます。
今の Rust の agent は GSO を使わないので、今の基準の値は offload の設定に依らないと見込みます (確かめていません)。
このため、送る向きの byte あたりの CPU は、バッチだけでは約 0.8 倍が見込みの中心で、約 0.72 倍が上の端です。
受ける向きも同じく約 0.8 倍が中心です。
受ける向きの `memset` (8.7%) は輪の零埋めで、バッチの段の外の変更 ([qbench での測定](wgstack-rs.md#qbench-での測定)の最適化の候補) で減ります。

速さは、エージェントの 1 つのスレッドが詰まりなので、byte あたりの CPU に逆比例して上がると見込みます。
byte あたりの CPU が 0.8 倍なら、速さは約 1.25 倍です。
送る向きの 1 stream では今の約 1.7 Gbit/s が約 2.1 Gbit/s になり、カーネルモードの約 5.7 Gbit/s の約 0.37 倍です。
カーネルモードに近づくには、データプレーンを複数のスレッドに分けるか暗号を速くする必要があり、バッチの段の外です。

### カーネルモードとの送る向きの差の内訳

送る向きの 1 stream の速さの差 (カーネルモード 5659 Mbit/s と Rust の agent 1684 Mbit/s、約 3.4 倍) は、VM 全体で 2 つに分けられます。
速さは、VM で忙しい CPU の数を VM 全体の byte あたりの CPU で割った値です。

| 項 | Rust の agent | カーネルモード | 比 |
|---|---|---|---|
| VM 全体の byte あたりの CPU (GB あたりの秒) | 10.41 | 4.64 | 約 2.24 倍 |
| VM で忙しい CPU の数 (4 個のうち) | 2.17 | 3.27 | 約 1.51 倍 |
| 速さ (Mbit/s) | 1684 | 5659 | 2.24 × 1.51 ≈ 3.4 倍 |

- byte あたりの CPU の差 (約 2.24 倍):バッチの段が減らせるのはこの項のうちエージェントの分です。
  エージェントの分 (4.26 秒) が約 2 割減ると、VM 全体は約 9.6 秒になり、差は約 2.06 倍に縮みます
- 使える CPU の数の差 (約 1.51 倍):Rust の agent は 1 つのスレッドが約 0.9 個の CPU で頭打ちになり、VM の残りの CPU を使えません。
  カーネルモードは暗号と転送を複数の CPU で並べて行い、VM のほぼ全体を使います。
  この項はバッチでは縮まず、[作業の順](#作業の順)の 2 番目の段 (データプレーンを複数のスレッドに分けること) の対象です

## 目標

バッチの段の目標は、遅れとメモリを制約とし、CPU を目的とします (2026-11-01、所有者の決定)。
制約はすべて必達で、目的の値は制約を満たした上で判定します。

### 制約

- UDP の遅れ:UDP の中継を通る往復の p99 と jitter が、今の Rust の agent より悪くならないことです。
  何もしていない時と、同じトンネルで TCP の転送が走る時 (送る向きと受ける向き) の両方で判定します ([判定の手順](#判定の手順))。
  TCP の転送は、2 つの腕に同じ負荷を掛けるため、`base:rust` の速さの約 0.75 倍に頭打ちにします ([UDP の往復の遅れ](#udp-の往復の遅れ))。
  加えて、エージェントが送る向きでは、頭打ちにしない転送の間の遅れも同じ線で判定します。
  頭打ちの負荷では大きなバッチができないことがあり、UDP の datagram が大きな TCP のバッチの後ろで待つ場面は、スレッドが埋まる時に現れるためです。
  この向きの p99 は 3 つの組で 1.99 から 2.11 ms と揃い、ping が忙しいスレッドに当たるので、遅れの予算が狙う待ちを測れます。
  エージェントが受ける向きの頭打ちにしない転送は記録だけにします。
  その遅れはソケットの待ち行列で決まり ([受ける向きの待ちの確かめ](#受ける向きの待ちの確かめ))、バッチの規則ではなく [受信の窓の段](#受信の窓の段) の対象です。
  本番の主な流れはゲームの UDP の中継なので、遅れの判定は UDP を先にします
- TCP の遅れ:[wgstack の性能の段階](../userspace/wgstack-performance.md#目標と制約)の通信量の少ない stream の p99 の目標を、その行列で満たし、今の Rust の agent の qbench の値 ([qbench での測定](wgstack-rs.md#qbench-での測定)) より悪くならないことです。
  速さを制限しない経路の TCP の遅れは、この文書の道具では測っていません
- メモリ:バッチの buffer はすべて、起動の時に `WGFT_AGENT_BATCH_MIB` の予算の内で確保し、[メモリの上界の行](agent-parity.md#メモリの上界の行)のトンネルのバッチの項 (`batch_bytes`、行の `batch`) に数えます。
  同じ変更で上界の表を作り直します。
  上界の式が導けないバッチの構造は採りません
- 既存の目標:[wgstack の性能の段階](../userspace/wgstack-performance.md#目標と制約)の 4 つの目標 (スループット、回復、通信量の少ない stream の遅れ、CPU) を、その判定の行列で満たし続けます
- 速さを固定した経路:`rate` の経路の byte あたりの CPU が、今の Rust の agent より悪くならないことです (`lab/lab paired` の `RATIO` の推定が 1.05 以下で、`ci95_low` が 1.00 以下)
- Windows と macOS:1 つずつの送受信のまま build と CI を通し、振る舞いを変えません

### バッチの作りの規則

バッチの段の実装は次の規則を守ります。
規則は制約と同じく必達の条件です。

- 待たない:バッチは、その時点でもう揃っているものだけをまとめます。
  `recvmmsg` は読める datagram だけを読み、`sendmmsg` と UDP の GSO は送り出す準備のできた packet だけを送り、UDP の GRO はカーネルがもう持つ datagram だけを結合します。
  バッチを満たすために待つことも、タイマーを張ることもしません
- UDP を先に:UDP の中継の datagram は、大きな TCP のバッチの後ろに並べません。
  送り出しの順は、UDP の中継の datagram を先にするか、TCP のバッチを送るのにかかる時間で区切り、UDP の datagram が待つのは小さなバッチ 1 つの間までにします。
  受信の側では、カーネルのソケットの待ち行列の順は変えられないので、読んだバッチをまず復号し、その中の UDP の中継の datagram を、同じバッチの TCP の segment より先に中継へ渡します。
  この並べ替えは wgstack の核の外のデータプレーンで行い、核に渡す TCP の segment の順は変えません。
  このため、凍結した Go の wgstack の記録との bit の一致 ([Go の wgstack の記録との bit の一致](wgstack-rs.md#go-の-wgstack-の記録との-bit-の一致)) には影響しません。
  UDP の経路はバッチを満たすために待ちません
- 時間で区切る:データプレーンの 1 回の起床で行う仕事の全体を、時間の上限 (遅れの予算) で区切ります。
  今の仮の上限 (1 回の起床で 64 packet まで、[送り出しと受信の値](agent-parity.md#送り出しと受信の値)) はこの上限に置き換えます。
  時間はバッチごとに `CLOCK_MONOTONIC` で読み、起床の始めからの経過が予算を超えたら、次のバッチを始めずに順を譲ります。
  上限は受信のバッチ (`recvmmsg` と復号) と送信のバッチ (核から引く packet、暗号、`sendmmsg` と GSO) の両方に掛かります。
  予算はデータプレーンの 1 か所の内部の定数とし、既定の値は 50 µs です。
  理由は [遅れの予算の既定の値](#遅れの予算の既定の値) にあります。
  後で `WGFT_*` の設定にできる形にしますが、今は公開の設定を足しません
- 起動の時に決める:遅れの予算、`WGFT_AGENT_BATCH_MIB` から導くバッチの大きさ、バッチの数は起動の時に 1 回だけ読み、動いている間は変えません。
  データの経路に atomic と錠を置きません。
  CPU の側の値に設定を設けません
- packet ごとに確保しない:データの経路 (トンネルの受信と送信、TCP と UDP の中継) は、定常の状態で packet ごとにヒープを確保しません。
  最初の段階の前は、packet ごとの確保が device の層だけにあり、受けた datagram 1 つにつき 2 回、送る packet 1 つにつき 2 回でした (2026-11-02 のコードの読み取り)。
  場所は、受信の復号の行き先 (`protocol.rs` の datagram ごとの buffer)、受信の平文の写し (`device.rs` の待ち行列に積む `to_vec`)、送信の側の写し (`device.rs` の `handle_packet` の `to_vec`)、送信の暗号文の buffer (`protocol.rs`) の 4 つです。
  中継の経路、`wgft-netstack`、wgstack の核は packet ごとに確保しません。
  最初の段階の状態は次のとおりです。
  device の層は呼び手の buffer を受け取る形で、4 つの場所は packet ごとに確保しません。
  受けた datagram は呼び手の buffer に復号して、その先頭の長さを返します。
  送る packet は呼び手の buffer に暗号化して、宛先と長さを返します。
  データの packet は、待ち行列にも一時の `Vec` にも入りません。
  ハンドシェイクと cookie の message、ハンドシェイクを待っていた packet の暗号文は、定常の経路ではないので、device の有限のキューを通ります。
  データプレーンのスレッドでのヒープの確保が packet あたり 0 であることを、トンネルの受信と送信、TCP と UDP の中継の試験が許容 0 で確かめます。
  最初の段階は、この試験が通ったので閉じます
- 確保の数え方:試験だけが使う crate `wgft-alloc-count` の割り当て器で、成功した `alloc`、`alloc_zeroed`、`realloc` の呼び出しをスレッドごとに数えます。
  数は device を通った datagram の数で割り、datagram の数は台本の相手の側で数えます。
  ACK の数は起床の時機で変わるので、message ごとの数は決まった値になりません。
  遅延 ACK のタイマーが切れた後に数を読み、最後の ACK の分を含めます。
  PR #771 (マージせずに閉じた) に試しの実装があり、参考にできます (使わなくても構いません)
- device の層の使い回しのバッファ:バッチの段が入るとき、データプレーンが device の層に渡す使い回しのバッファ (受ける datagram、復号の行き先、核が書く packet、暗号文の行き先の 4 つ) がバッチの置き場になります。
  device の層の API は呼び手の buffer を取るので、バッチでは同じ呼び出しに、バッチの配列の 1 枠を渡します。
  起動の時に 1 回、`WGFT_AGENT_BATCH_MIB` の内の上限のある置き場として確保し、`batch` の項に正確な項として数えます。
  バッチの段の最初の段階 (確保をやめ、まだ 1 packet ずつ送受信する間)は、この 4 つを `device` の項に数えます (`data_plane_buffers`)。
  バッチの段が入った後は、データプレーンの受信と送信のバッファも `device` の項から `batch` の項に移します ([agent-parity.md](agent-parity.md#メモリの上界の行))
- buffer は起動の時の有限の置き場から:buffer はすべて起動の時に確保する上限のある置き場から借り、置き場はそれぞれメモリの上界の行の `batch` の項に正確な項として数えます
- 写さない:借用か、その場での復号と組み立てで済む所では写しをやめます。
  sanstun の復号と暗号化は呼び手の buffer を受けるので、受け手が読む buffer に直接復号することと、核の segment から送信のバッチの buffer に直接暗号化することは、sanstun を直さずにできます
- CPU のキャッシュ:`mmsghdr` と `iovec` の配列と packet の buffer は、起動の時に 1 回連続して確保します。
  バッチごとに触る値を 1 か所にまとめて、触らない値と分けます。
  packet ごとにポインタをたどりません。
  受信と送信を別のスレッドにする場合は、ほかのスレッドが読む数を別のキャッシュラインに置き、false sharing を起こしません
- Linux だけ:`recvmmsg`、`sendmmsg`、UDP の GSO と GRO は Linux だけで使います

### `WGFT_AGENT_BATCH_MIB` の意味

`WGFT_AGENT_BATCH_MIB` は、バッチの段でもバッチの予算 (MiB) のままにします。
[互換性の保証](../compatibility.md)の、既存の設定の意味を変えない規則の内で、意味を次のように定めます。

- 予算の範囲:トンネルのバッチの buffer の全体です。
  受信と送信の両方の向きのバッチの buffer をこの予算に数えます
- `0`:トンネルのバッチを両方の向きで切り、1 つずつ送受信します
- 空 (設定しない):今と同じく、フロー数の上限から導く値です
- 受け付ける値、丸め、誤りの文面:[WGFT_AGENT_BATCH_MIB](../spec/cli-config.md#wgft_agent_batch_mib) の今の規則のままです
- 起動の時に 1 回だけ読み、動いている間は変えません

今の Rust の agent は値を受けて、まだ使っていないことを 1 行出します ([CLI と設定](agent-parity.md#cli-と設定))。
バッチの段の変更は、この行を外し、ヘルプの文 (`send batch budget in MiB ...`) を両方の向きのバッチの予算を表す文に直し、生成するリファレンスを同じ変更で作り直します。
誤りの文面の `0 turns send batching off` を変えるなら、仕様を同じ変更で直します。

### 受信の窓の段

所有者の決定 (2026-11-02) により、エージェントが受ける向きの速さを制限しない転送の間の UDP の待ち ([受ける向きの待ちの確かめ](#受ける向きの待ちの確かめ)) を縮める変更を、バッチの作業の 1 つの段にします。

- 理由:Rust の agent の p50 は約 7.3 ms で、gVisor の約 3.0 ms、カーネルモードの約 3.3 ms より長く、本番のゲームの UDP の流れでは、置き換える前の gVisor より遅れが悪くなっています。
  カーネルモードでは受け手の受信のバッファの上限を 1 MiB に下げると、速さを保ったまま p50 が約 0.9 ms、p99 が約 1.1 ms になりました ([カーネルモードの遅れを決める仕組みの確かめ](#カーネルモードの遅れを決める仕組みの確かめ))
- 変更:wgstack が広告する受信の窓を、今の受信の窓の自動調整 ([受信の窓の自動調整](../userspace/wgstack-performance.md#受信の窓の自動調整)) の上で、遅れの目標で頭打ちにします。
  上限は、推定した届く速さ × (往復の時間 + 目標の待ちの時間) です。
  届く速さは、受け手のアプリケーション (中継) が往復の時間あたりに読んだ byte から、往復の時間は timestamp (RFC 7323) から推定します。
  決まった byte の上限にしないのは、往復の時間の長い実際の経路で速さを落とすためです。
  式と測り方は [遅れの目標の窓](#遅れの目標の窓) にあります
- 窓を縮めない:上限が今の窓より小さくなっても、窓の右の端を左に動かしません (RFC 9293)。
  右の端を進めるのを止め、上限が追いつくまで待ちます
- 目標の待ちの時間:CoDel (RFC 8289) と AQM の推奨 (RFC 7567) と同じく、待ち行列の長さを byte でなく時間で決めます。
  値は 0.5 ms で、この段で測って決めました ([目標の待ちの時間の選び方](#目標の待ちの時間の選び方))
- 参考:RFC 9293、RFC 7323、Dynamic Right-Sizing (Fisk と Feng の受け手の窓の自動調整の論文)、rLEDBAT (受け手の側で遅れに基づいて窓を決める方式。RFC になったかは確かめていません)、RFC 7567、RFC 8289、BBR の公開の草案 (draft-cardwell-iccrg-bbr-congestion-control)
- 判定:エージェントが受ける向きの頭打ちにしない転送の UDP の p50 と p99 が、受け手の受信のバッファを下げたカーネルモードの値に近づき、速さが測った揺れを超えて落ちないことです。
  同じ遅れの道具 (`lab/lab paired --tool iperf3 --udp-ping --rounds 8 --direction up`) で測ります。
  比べる値は、同じ仕事の中で受信のバッファの上限を 1 MiB に下げて測ったカーネルモードの値です。
  この段は、そのための設定 `--kernel-rmem-max` を `lab/lab paired` に足しました ([lab/README.md](../../../lab/README.md))。
  線は、Rust の agent の p50 と p99 がそれぞれその値の 1.5 倍以下、`base:rust` との `MBITRATIO` の推定が 0.95 以上で `ci95_high` が 1.00 以上です。
  線の値はこの文書の提案で、確かめていません
- 凍結した Go の wgstack との関係:[Go の wgstack の記録との関係](#go-の-wgstack-の記録との関係) で決めました
- 既存の目標:[wgstack の性能の段階](../userspace/wgstack-performance.md#目標と制約)の 4 つの目標を、その行列で満たし続けます

#### 遅れの目標の窓

wgstack は、受信の窓の自動調整が決める窓の上限と歩みの上限に加えて、遅れの目標の窓の上限 (以下、遅れの上限) で、広告する右端を抑えます。
遅れの上限は次の式で、受け手の RTT の 1 回の区間ごとに決め直します。
区間は、受信の窓の自動調整の測定と同じ区間です。

```text
遅れの上限 = 読んだ速さ × (往復の時間の最小 + 目標の待ちの時間 + 伸びの余地)
```

- 読んだ速さ:区間の間に中継が読んだ byte を、区間の長さで割った値です。
  詰まりがエージェントの手前にあれば詰まりの速さに、中継の先が遅ければその速さになります
- 往復の時間の最小:[往復の時間の測り方](#往復の時間の測り方)の標本の最小です。
  置き直しの規則は [最小の置き直し](#最小の置き直し) にあります
- 目標の待ちの時間:内部の定数の 0.5 ms と、往復の時間の最小の 16 分の 1 の大きい方です。
  CoDel (RFC 8289) が目標を往復の時間の数 % (100 ms に 5 ms) にするのと同じく、往復の時間の長い経路では、往復ごとの標本の揺れより広く取ります。
  ラボの往復の時間 (1 ms より短い) では 0.5 ms です
- 伸びの余地:最後の標本から最小を引いた待ちが、目標より短いほど大きくします。
  待ちが 0 の時は最小と同じ長さ、待ちが目標以上の時は 0 です。
  待ちの無い間は窓を往復ごとに約 2 倍まで広げられるので、往復の時間の長い経路でも送り手の slow start を抑えません。
  待ちが目標に近づくと伸びが止まり、窓は帯域と往復の時間の積に目標の分を足した量に落ち着きます
- 下限:窓に使う時は、遅れの上限を floor (256 KiB) より小さくしません。
  floor は boost を得るまでの窓と同じ量なので、遅れの上限が窓を変えるのは boost を得た後だけです。
  floor の窓が作る待ちは、ラボの受ける向きの速さ (約 4 Gbit/s) で約 0.5 ms です。
  帯域と往復の時間の積が floor より小さい経路 (例えば qbench の片道 25 ms、20 Mbit/s) では、floor の窓が待ちを作り、遅れの上限はその待ちを縮めません

広告する右端は、今の規則の目標 (空きと歩みの上限の小さい方を RCV.NXT に足した位置) を、さらに RCV.NXT に遅れの上限を足した位置で抑えます。
遅れの上限が今の窓より小さくなった時は、右端を左へ動かさず、RCV.NXT が追いつくまで右端を進めません (RFC 9293 3.8.6 の SHLD-14)。
受け手の SWS の回避 (右端を MSS と窓の上限の半分の小さい方より少なくは進めない規則) は今のままです。

#### 往復の時間の測り方

標本は RFC 7323 の timestamp で取り、時刻は核の ns で測ります。

- 始め:新しい TSval を初めて運ぶ segment を送った時に、測っている標本が無ければ、その TSval と送った時刻を覚えます
- 終わり:その TSval を TSecr に返す data を受け入れた時に、今の時刻との差を標本にします
- やめる時:TSecr がその TSval より新しい data が先に届いた時です。
  その TSval への応答はもう来ません

相手は、受けた segment のうち最も新しい TSval を TSecr に返します (RFC 7323 4.3)。
このため、覚えた TSval を初めて返す data は、覚えた segment を相手が受けた後に送られており、標本は往復の時間より短くなりません。
標本は詰まりの待ちを含み、最小は待ちの無い時の値に近づきます。

- 時計の細かさ:受信の窓の自動調整の受け手の RTT の推定は ms の単位の timestamp の差を使い、1 ms より短くなりません。
  ラボの往復の時間は 1 ms より短く、ms の単位では目標の待ちを測れないので、この標本は送った時刻を ns で覚えます
- 数:標本は往復ごとに最大 1 つで、TSval が進む 1 ms ごとに 1 つを超えません
- 接続で最初に送る segment:測り始めません。
  握手の SYN-ACK が同じ TSval を先に運んでいることがあるためです
- 中身の無い segment:標本にしません。
  相手の遅延 ACK の待ちが入るためです
- 右端を止めている間:測りません ([最小の置き直し](#最小の置き直し))

#### 最小の置き直し

最小は、標本が今の最小より小さい時に下げます。
最小が実際の往復の時間からずれる場合は 2 つあり、それぞれ次の規則で置き直します。

最小が短すぎる場合は、経路の往復の時間が延びた時と、ほかの流れが詰まりの待ち行列を保つ時です。
遅れの上限が帯域と往復の時間の積を下回ると、読んだ速さが下がり、遅れの上限も下がり続けます。

- 遅れの上限が floor 以上で今の窓が遅れの上限以内なら、自分の窓が詰まりに作る待ちは目標の内です
- それでも待ちが目標の 2 倍を超える区間が 4 つ続けば、その待ちは自分の窓が作ったものではありません。
  最小を最後の標本に置き直します
- 遅れの上限が floor より小さい間は、floor の窓が待ちを作るので、この規則を使いません。
  使うと、置き直すたびに伸びの余地が窓を広げ、待ち行列が延び続けます

最小が長すぎる場合は、測り始めた時に待ち行列が空でなかった時です。
例えば送り手が初めに窓をまとめて送ると、最初の標本は待ちを含みます。
遅れの上限はその待ちを含む最小で窓を決め続け、待ち行列は空にならないので、より小さな標本も来ません。

- 最小を測り始めてから 10 秒ごとに、最小を捨てて測り直します。
  BBR の公開の草案の ProbeRTT と同じく、遅れの上限が floor 以上なら、右端を止めて待ち行列を空にしてから測ります
- 右端を止めるのは、残りの窓が MSS の 2 倍を下回るか、200 ms が過ぎるまでです。
  窓の欄が 0 にならないので、送り手は窓の probe を始めません。
  終わりは届いた data を受け入れる時に確かめ、タイマーを足しません
- 止めている間は標本を取りません。
  この間に届く data は止める前に送られたもので、待ちを含むためです
- 再開の ACK から測った最初の標本が新しい最小になります。
  止めている間の送り手は窓を使い切って送れないので、再開の ACK の TSval を返す最初の data は空の待ち行列を通ります。
  それまで遅れの上限は止める前の値のままです
- 費用:10 秒に 1 回、最大で往復の時間の約 1 回分だけ送り手が止まります。
  ラボの経路では 1 ms 未満で、往復の時間が 50 ms の経路では約 1% の速さです

最小を時間で古くするだけで待ち行列を空にしない方式は採りません。
遅れの上限が働く間は待ち行列が目標の分だけ残るので、古くした後の最初の標本は待ちを含み、置き直すたびに待ちが目標の分ずつ延びます。

白箱の試験 (`crates/wgft-wgstack/src/lat_tests.rs`) は、核の手前に一定の速さの待ち行列と片道の遅れを置いた模擬の経路で、次のことを確かめます。
模擬の送り手は輻輳の窓を持たず、開いた窓をまとめて送ります。

- 片道 5 ms、800 Mbit/s の経路で、待ち行列が目標の近くに保たれ、10 秒の後の測り直しを含めて速さが落ちないこと
- timestamp の無い相手では遅れの上限が働かないこと
- 片道の遅れが 5 ms から 8 ms に延びた後に、速さが戻ること
- 片道 25 ms、240 Mbit/s の経路で、遅れの上限の働かない流れと詰まりを分け合う時に、floor の窓まで縮み続けないこと
- 片道 25 ms、20 Mbit/s の経路で、初めの待ちを含んだ最小が測り直しで正され、待ち行列が floor の窓の作る長さに留まること

短すぎる最小の置き直しの規則を外すと、経路が延びる試験と流れを分け合う試験が落ちます。
測り直しを外すと、floor の窓の試験が落ちます。

#### 手間と状態

- segment ごとの仕事:送る segment ごとに TSval の比べを 1 回、受け入れた data ごとに TSecr の比べと右端を止めているかの確かめを 1 回ずつします。
  接続の走査、タイマー、確保を足しません
- 区間ごとの仕事:遅れの上限の計算 (128 bit の整数の掛け算と割り算を 1 回) を、受信の窓の自動調整と同じ時に行います
- 状態:遅れの上限、測っている TSval と送った時刻、最後に送った TSval、右端を止めているかは、segment ごとに触る接続の欄に置きます。
  最小、最後の標本、続いた区間の数、最小を測り始めた時刻、右端を止め始めた時刻は、冷たい欄に置きます。
  どれも上界の式の c_conn に入り、上界の表 ([wgstack の Rust 版の上界の表](wgstack-bound.md)、[Rust の agent のメモリの上界の表](agent-bound.md)) を作り直しました
- timestamp の無い相手:標本が無いので遅れの上限を持たず、窓は今までと同じです。
  受ける向きの送り手が timestamp を示さない時 (例えば Windows の既定の設定。確かめていません) は、この段の効果がありません

#### Go の wgstack の記録との関係

この段の始めに、遅れの上限を入れた核で凍結した Go の wgstack の記録を照らしました。
git の記録と、手元の cache の大きな記録の集まり (関門の `wgstack-rs-replay-full` が照らす集まり) のすべてが Go と一致しました。
遅れの上限が窓を変えるのは、boost を得た後に、遅れの上限が空きと歩みの上限より小さくなった時だけで、今の記録の台本にはその場面がありません。
どの台本がどの条件で外れるかの内訳は調べていません。

このため、bit の一致を求める期間との関係は次のように決めます。

- 遅れの上限は今入れ、bit の一致の条件 ([Go の wgstack の記録との bit の一致](wgstack-rs.md#go-の-wgstack-の記録との-bit-の一致)) は今のまま保ちます
- 意図した違いの一覧 (`testdata/wgstack-rec/divergences.json`) は空のままです
- 遅れの上限のために Go と違う出力になる記録を後で足した時は、SYN cookie と同じく、その記録を理由と共に一覧に載せます。
  多くの記録が外れて照合の意味が薄れる場合は、一覧に載せる前に所有者に諮ります

### 目的:byte あたりの CPU と速さ

目的の値は、変更した build を腕 `rust`、変更の前の commit の build を腕 `base:rust` にした `lab/lab paired` の組で判定します ([判定の手順](#判定の手順))。
必達の目標は、見積もりの中心 (約 0.8 倍) より控えめな値で、バッチの段だけで届くと見込む値です。
努力の目標は、見積もりの上の端で、計画した手段をすべて入れても届かない場合はそこで止めます。
必達の目標に届いたとは、制約をすべて満たし、表の必達の列のすべての行を満たすことです。
行が向きと stream の数を挙げるものは、挙げたすべての組み合わせで満たします。
カーネルモードとの行は 1 stream だけです。
努力の目標も同じ形で判定します。

| 値 | 必達の目標 | 努力の目標 |
|---|---|---|
| エージェントの byte あたりの CPU (`RATIO`、`rust` / `base:rust`)、両方の向き、1 stream と 4 stream | 95% の区間の上端が 0.85 以下 | 95% の区間の上端が 0.75 以下 |
| 速さ (`MBITRATIO`、`rust` / `base:rust`)、両方の向き、1 stream と 4 stream | 推定が 1.15 以上 | 推定が 1.30 以上 |
| 送る向きの 1 stream の速さ (`MBITRATIO`、`rust` / `kernel`、腕 `rust kernel` の組) | 目標にしません (記録します) | 推定が 0.38 以上 |

キャッシュと命令の数の確かめ:ラボの VM は PMU を仮想化しないので、ラボでは数えられません。
バッチの段の実装は、PMU のあるホストで道具を流し、変更の前と後の値を PR に書きます。
道具は crate `crates/wgft-agent-perf` (試験の道具で、製品の build に入りません) と、それを `perf stat` の下で流す `scripts/agent-perf-stat.sh` です。
道具は、WireGuard の device の層 (`wgft-wireguard`) とデータプレーンと同じ開き方の UDP のソケットを、ホストの network namespace の loopback の中の 2 つのソケットの間で動かし、wgstack の核の代わりに決まった大きさの packet を作る相手を置きます。
network namespace は `unshare -rn` の権限の要らないもので、root も TUN も要りません。
向きは 2 つで、`send` は測るスレッドが暗号にして `sendto` で送り、`recv` は測るスレッドが `recvfrom` で読んで復号します。
相手は別のスレッドで、`perf stat --no-inherit` が数えから外します。
packet の大きさは device の層が運ぶ最大の内側の packet (MTU 1420 で 1408 byte) と小さな packet (64 byte) です。
バッチの段が使う `recvmmsg`、`sendmmsg`、GSO、GRO は、今の道具には入っていません。
今の道具は、今のデータプレーンと同じく datagram を 1 つずつ `sendto` と `recvfrom` で運びます。
段がそれらを入れるときに、道具の差し替える場所と数え方を道具の doc comment に書いてあります。

測る値は、packet あたりのキャッシュの miss (`cache-misses`、`L1-dcache-load-misses`)、byte あたりの命令の数 (`instructions`)、packet あたりの system call の数、byte あたりの CPU の時間です。
system call の数は道具が自分で数え、データの経路の `sendto` と `recvfrom` と、burst ごとの起床の確認 1 回です。
CPU の時間は測るスレッドの値で、burst の間の待ちを含みません。

```sh
# 変更した commit の作業ツリーで。--base を付けると <base> を一時的な worktree で build し、
# base と head を交互に (base、head、base、head) 流して、中央値と比を出す
notes/scripts/wgft-heavy --timing --vm-mem 0 -- scripts/agent-perf-stat.sh --base <base>
```

出力は、向き、packet の大きさ、値ごとに 1 行です。
`--base` が無ければ head の中央値と範囲、あれば base と head の中央値と範囲、`ratio=head/base` を出します。
測る側と相手に、車線の最初の 2 つの CPU を使います。
E コアの車線は `L1-dcache-load-misses` を数えないので、そこでは同じ意味の `mem_load_uops_retired.l1_miss` を数えて、同じ名前で出します。

道具の限界は次のとおりです。

- `perf_event_paranoid` が 2 のホストでは、権限の無い `perf stat` はユーザー空間だけを数えます。
  命令の数とキャッシュの miss にカーネルの UDP と loopback の処理は入らず、system call の数と CPU の時間には入ります。
  そのためバッチの段の `sendmmsg` と `recvmmsg` の効果は、前者の 2 つより後者の 2 つに現れます
- ソケットのバッファは、`CAP_NET_ADMIN` の要る `FORCE` の指定を使わないので、新しい network namespace の `net.core.rmem_max` で頭打ちになります。burst の大きさはそれに収まる値にしてあります
- loopback は送り手の `sendto` の中で受け手のキューに入れるので、`send` の CPU の時間に受信側のキューへの積みが入ります。ラボの veth の経路が送った後の softirq を数えるのと同じ形です
- 道具の socket の loop は、データプレーンの経路の写しです。`dataplane::socket` は `pub(crate)` で tokio を使うので、道具から呼べません。前と後の値は、道具の loop と本物の device の層を合わせたものを測ります。PR には、どちらが変わったかを書きます
- `--base` は、道具を持たない base に head の道具を重ねます。device の層の API が base と head で違えば build に失敗するので、道具の差し替えが要る API の変更は、比べる base より前の commit に分けます
- ゆらぎ:同じ commit の base と head を比べた結果は、L1 の miss と `cache-misses` の比が 0.97 から 1.32 まで揺れ、命令の数、system call の数、byte あたりの CPU の時間は約 1% で収まりました。L1 と `cache-misses` の差は、出力の範囲より大きいときだけ読みます
- E コアの車線の `L1-dcache-load-misses` は `mem_load_uops_retired.l1_miss` なので、P コアの値とは比べられません。比べるのは同じ車線の base と head だけです
- `syscalls/packet` が数えるのは `sendto` と `recvfrom` (最後の `WouldBlock` を含みます) と burst ごとの `poll` 1 回で、futex、`clock_gettime`、`getrusage` を含みません
- 準備 (握手と thread の起動) は `perf stat` の数えに入りますが、packet と byte の数には入りません。定数で小さい分です
- burst ごとの `clock_gettime` と `getrusage` の費用は `cpu-ns/byte` に入るので、64 byte の packet では比を少し 1 に近づけます

### 判定の手順

判定は、変更した commit の作業ツリーで、変更の前の commit (`<base>`) を `--base` にして次の組を流します。
遅れの組は 8 round、ほかの組は 4 round で、どれも round ごとに 3 回です。
`WGFT_LAB_PAIR_CPUS` には、2 つの車線の E コアの集合を与えます。

```sh
# 目的:byte あたりの CPU と速さ (向きと stream の数の 4 つの組)
lab/lab paired --base <base> --tool iperf3 --streams 1 --direction down fast rust base:rust
lab/lab paired --base <base> --tool iperf3 --streams 1 --direction up   fast rust base:rust
lab/lab paired --base <base> --tool iperf3 --streams 4 --direction down fast rust base:rust
lab/lab paired --base <base> --tool iperf3 --streams 4 --direction up   fast rust base:rust
# 記録:エージェントの UDP の segmentation offload を残した形
lab/lab paired --base <base> --tool iperf3 --agent-gso on --direction down fast rust base:rust
lab/lab paired --base <base> --tool iperf3 --agent-gso on --direction up   fast rust base:rust
# 制約:UDP の遅れ (向きの 2 つの組)。<down> と <up> は、上の 1 stream の組の base:rust の速さの
# 中央値 (CPU arm=y の mbit) の 0.75 倍を 50 Mbit/s 単位に切り下げた値
lab/lab paired --base <base> --tool iperf3 --udp-ping --bulk-mbit <down> --rounds 8 --direction down fast rust base:rust
lab/lab paired --base <base> --tool iperf3 --udp-ping --bulk-mbit <up>   --rounds 8 --direction up   fast rust base:rust
# 制約:UDP の遅れ、エージェントが送る向きの頭打ちにしない転送
lab/lab paired --base <base> --tool iperf3 --udp-ping --rounds 8 --direction down fast rust base:rust
# 努力の目標の速さ:カーネルモードとの比
lab/lab paired --tool iperf3 --direction down fast rust kernel
# 制約:速さを固定した経路
lab/lab paired --base <base> --direction down rate rust base:rust
lab/lab paired --base <base> --direction up   rate rust base:rust
# 受信の窓の段:受ける向きの頭打ちにしない転送の UDP の遅れと速さ
lab/lab paired --base <base> --tool iperf3 --udp-ping --rounds 8 --direction up fast rust base:rust
lab/lab paired --tool iperf3 --udp-ping --rounds 8 --kernel-rmem-max 1048576 --direction up fast rust kernel
```

- byte あたりの CPU:`RATIO` の行の `ci95_high` を表の線と比べます。
  区間が線をまたぐ場合は `--rounds` を倍にして 1 回だけ流し直し、流し直した結果で判定します
- 速さ:`MBITRATIO` の行 (組にした速さの比の推定と 95% の区間) を表の線と比べます。
  `kernel` の腕との組では、各腕の値は `VMCPU arm=` の行にあります (`CPU arm=` の行はありません)。
  推定が線から 5% 以内なら、`--rounds` を倍にして 1 回だけ流し直し、流し直した結果で判定します
- UDP の遅れ:両方の向きで次のすべてを満たすことです。
  遅れの組は `--rounds 8` を既定にします。
  線は非劣性の線で、同じ build を 2 つの腕にした組 ([UDP の往復の遅れ](#udp-の往復の遅れ)) の揺れから決めました。
  同じ build の組の推定は 0.92 から 1.03 で、区間は 0.78 から 1.16 まで広がるので、推定の線を 1.10 にし、加えて区間の全体が悪くなる側にある場合 (`ci95_low` が 1.00 を超える場合) は、推定が線の内でも落とします。
  この線は、測った揺れのために p99 の約 10% までの悪化 (頭打ちの負荷で約 0.1 ms) を見逃します。
  これは所有者が見て変えられる選択です。
  線を下げるには、round を増やして揺れを狭める必要があります
  - `LATRATIO key=udp_load_p99_ms` の推定が 1.10 以下で、`ci95_low` が 1.00 以下
  - `LATRATIO key=udp_load_jitter_ms` の推定が 1.10 以下で、`ci95_low` が 1.00 以下
  - `LATRATIO key=udp_idle_p99_ms` と `key=udp_idle_jitter_ms` も同じ線
  - `LAT` の行の `lost` が、`base:rust` の `lost` に `sent` の 0.1% を足した数以下
  - どれかの推定が線から 5% 以内か、`ci95_low` が 1.00 を超えて 1.05 以下なら、`--rounds 16` で 1 回だけ流し直し、流し直した結果で判定します
  - `LATRATIO` の行が `TOO FEW` なら判定せず、原因を直して流し直します
- 受信の窓の段:`rust kernel` の組の `LATRATIO key=udp_load_p50_ms` と `key=udp_load_p99_ms` の推定がそれぞれ 1.5 以下で、`rust base:rust` の組の `MBITRATIO` の推定が 0.95 以上で `ci95_high` が 1.00 以上であることです ([受信の窓の段](#受信の窓の段))
