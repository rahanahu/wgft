#### `dataplane.table` の判定

公開の記録と実際のテーブルを比べ、転送の行と守りの行を区別します。
停止中は再現できない証拠が残るため、一致した部分だけで OK にしません。


カーネルモードのルール単位の失敗は `dataplane.table` が示します (2026-09-24、所有者の決定)。
`dataplane.table` は 2 つのことを判定します。
1 つはテーブルそのものが正しいことであり、もう 1 つは、テーブルが公開すべき各ルールが実際に成り立っていることです。
どちらも、直近の公開の記録と実際のテーブルを同じ関数で比べて判定します。
比べるのは、`nat_pre` の DNAT の行から読んだルールとポートごとの宛先と、DNAT の行を含むすべてのチェーンの行の形と並びです ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
稼働中のエージェントはメモリの上の記録を、停止中の診断は `agent.json` の記録を渡します。
記録は公開に成功するたびに両方で同じ値になるので、どちらの実行でも同じ比べ方になります。
判定は次の順に行います。

- FAILED `table_missing`:`table inet wgft_agent` がありません
- FAILED `table_rows_missing`:次のどちらかに当たる場合です。
  - 記録から組む表の行かチェーンのうち、欠けると転送が止まるものが欠けています
  - 記録にある DNAT が無いか、別の宛先を指しています

  どの行が当たるかは後述の表のとおりです。
  filter_pre の通す行、forward の通す行、MASQUERADE のどれかが欠けても転送は止まるので、DNAT の行だけでは足りません。
  エージェントが止まった後に行が削除された場合も、ここで見つかります。
  記録にループバックの宛先の DNAT があり、wgft0 の `route_localnet` が 1 でないか読めない場合も、ここに数えます。
  カーネルがその DNAT のパケットを捨てるので、欠けた転送の行と同じく扱います ([7b.2 節](../kernel-agent/targets.md#ループバックの宛先))。
  所見は、値を 1 にする必要があることと、今の値か読み出しの誤りを示します。
  守りの行も同時に欠けていれば、所見に併せて示します
- FAILED `listener_error`:ルール 1 本以上の状態が `error` です。
  次のルールが当たります。
  - [7b.3 節](../kernel-agent/targets.md#7b3-ルールの状態と失敗の種類)の 1 つ目の種類のルール:許可一覧の外、名前の解決の失敗、許可一覧が名指さないループバックの宛先、ブロードキャストかマルチキャストの宛先で、そのルールの DNAT がありません
  - 7b.3 節の 2 つ目の種類のルール:TCP の宛先の接続確認の失敗で、DNAT はあります
  - `ip_forward` が 0 のために `error` を報告するルール ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))
  - wgft0 の `route_localnet` を 1 にできないために `error` を報告するループバックの宛先のルール ([7b.2 節](../kernel-agent/targets.md#ループバックの宛先))

  名前の解決に失敗して直前の解決の結果で転送を続けているルール ([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い)) は、理由の後ろに試し接続の誤りか `ip_forward` の誤りが続く場合だけ当たります。
  続かない場合は、次の `resolve_failed` です (2026-09-25)。
  この除外を別にすれば、ユーザー空間モードの `relay.listeners` が、ルールの `error` の出どころを問わず FAILED にするのと同じ扱いです。
  除くのは、そのルールの `error` が転送の停止を示さないためです。
  ユーザー空間モードのエージェントは、この種類の `error` を報告しません。
  符号は `relay.listeners` と同じ `listener_error` とします。
  符号が表す事実、つまり転送の停止を示しうる `error` のルールが 1 本以上あることは、どちらのモードでも同じです
- UNKNOWN `guard_rows_missing`:欠けたのが、欠けても転送が止まらない行とチェーン (守りの行) だけです (2026-09-24、所有者の決定)。
  転送は続きうるので、終了コード 1 が答える問いに対して FAILED とは言えません。
  所見は、欠けた行の名前と、欠けた行の組み合わせで開きうる面を示します。
  drop の行は層になっているので、面は、その面を閉じる行がすべて欠けたときだけ開きます (2026-09-24、所有者の決定)。
  1 行だけの欠けで面が開かないときは、残っている行がまだ閉じていることを示します。
  組み合わせは後述の守りの行の効果の表のとおりです。
  表に加わった行か位置の違う行が無ければ、転送は続きうることも添えます。
  それらがあれば、その効果は分からないので、転送は続きうるとも、残っている行がまだ閉じているとも言わず、それらを所見に示します。
  加わった行は、残っている drop の行より前でパケットを通しうるためです。
  `input` の drop の行を削除し、`filter_pre` の先頭に wgft0 から入るものを通す行を加えた表では、ホストのポートにも他のテーブルの DNAT にも届きました。
  ルールの `error` が同時にあれば、`listener_error` の所見に併せて示します
- UNKNOWN `publish_failed`:直近の全体状態の公開が失敗し ([7b.3 節](../kernel-agent/targets.md#7b3-ルールの状態と失敗の種類)の 3 つ目の種類)、旧いテーブルが残っています。
  旧いテーブルが転送を続けているので、このホストのエージェントが今は転送を担えない、とは言えず、FAILED にはしません。
  所見に公開の誤りを示します。
  稼働中の実行だけが持つ事実です
- UNKNOWN `table_changed`:記録から組む表の行はすべてありますが、wgft が書かない行かチェーンが加わっているか、記録から組む行が同じチェーンの別の位置にあります。
  どちらも、転送を止めるかどうかは分かりません。
  所見に加わった行と位置の違う行を示します。
  稼働中のエージェントは変更の通知の後の見直しで公開し直し、公開し直しが失敗した後は 30 秒ごとの見直しでも試し直します ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
  このため、稼働中の実行でこの所見が続くのは、公開し直しが失敗しているか、失敗の後の間隔のために通知の後の見直しが待っている間です
- UNKNOWN `resolve_failed`:稼働中の実行で、`error` のルールがどれも、名前の解決に失敗して直前の解決の結果で転送を続けているだけのルール ([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い)) です (2026-09-25、所有者の決定)。
  DNAT は直前のアドレスへ向いたまま残っており、転送の停止は観測していないので、終了コード 1 が答える問いに対して FAILED とは言えません。
  `host.resolve` と `tunnel.resolve` の `resolve_failed` と同じく、名前の解決の失敗は今この瞬間に転送を担えないという証拠ではありません。
  `server doctor` の `rule.target_resolve` も同じルールを FAILED にせず、UNKNOWN の `target_resolve_failed` とします ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor))。
  所見は、直前の解決の結果で転送を続けているルールと、その解決の誤りを示します。
  判定の材料は理由の文言であり、`server doctor` と同じ関数で読みます。
  転送の行の欠け、守りの行の欠け、公開の失敗、表の変更と同時にあれば、そちらの符号を採り、このルールを所見に併せて示します。
  `listener_error` の所見にも併せて示します。
  30 秒ごとの見直しの失敗は、OK の所見と同じく併せて示します。
  停止中の実行では、次の `agent_not_running` を採り、所見のルールの一覧に理由を示します
- UNKNOWN `agent_not_running`:停止中で、比べた部分がすべて一致しています。
  後述します
- それ以外は OK とします

行とチェーンの分け方は、「その行が欠けたときに転送が止まるか」で決めます (2026-09-24、所有者の決定)。
欠けたときに転送が止まる行を転送の行、止まらない行を守りの行と呼びます。
通す行は、同じチェーンでそれが通さなかったパケットを落とす drop の行があるときだけ、転送に必要です。
その drop の行も欠けていれば、通す行が欠けても転送は止まらないので、守りの行として数えます。
チェーンごと無い場合は、そのチェーンの分け方に従います。
判定は稼働中と停止中で同じ関数が行います。
分け方は次の表のとおりです。

期待する行が同じチェーンの別の位置にある場合は、欠けに数えません (2026-09-24、所有者の決定)。
行は順に照らし合わせ、順に見つからなかった行を、まだ当たっていない実際の行から探します。
見つかれば位置の違う行とし、行が加わった場合と同じく効果の分からない変更として扱います。
たとえば `filter_pre` の drop の行を削除して先頭に入れ直した表では、その行は欠けておらず、公開した通す行より前で wgft0 からのパケットを落とします。
本当に無い行と位置の違う行が両方あれば、欠けの判定 (転送の行なら `table_rows_missing`、守りの行だけなら `guard_rows_missing`) を保ち、位置の違う行と加わった行も所見に示します。

| チェーン | 行 | 分け方 | 欠けたときに止まる転送 |
|---|---|---|---|
| `filter_pre` | ルールごとの通す行 | 転送 (同じチェーンの drop の行があるとき) | そのルール |
| `filter_pre` | 成立済みのフローを通す行 | 守り | 無し |
| `filter_pre` | drop の行 | 守り | 無し |
| `filter_pre` | チェーンそのもの | 守り | 無し |
| `nat_pre` | ルールごとの DNAT の行と map の要素 | 転送 | そのルール |
| `nat_pre` | チェーンそのもの | 転送 | すべてのルール |
| `input` | DNAT したフローを通す行 | 転送 (drop の行があり、宛先がホスト自身のルールがあるとき) | 宛先がホスト自身のルール |
| `input` | 成立済みのフローを通す行 | 守り | 無し |
| `input` | drop の行 | 守り | 無し |
| `input` | チェーンそのもの | 守り | 無し |
| `forward` | 2 つの MSS のクランプの行 | 守り | 無し。ICMP を落とす経路の大きな TCP は止まることがあります ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの)) |
| `forward` | wgft0 から wgft0 への drop の行 | 守り | 無し |
| `forward` | DNAT したフローを通す行 | 転送 (wgft0 から入るものの drop の行があり、宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| `forward` | wgft0 へ出る成立済みのフローを通す行 | 転送 (wgft0 へ出るものの drop の行があり、宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| `forward` | 2 つの drop の行 | 守り | 無し |
| `forward` | チェーンそのもの | 守り | 無し |
| `postrouting` | MASQUERADE の行とチェーンそのもの | 転送 (宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| どれか | 見出し (種類、フック、優先度、policy) の違うチェーン | 転送 | 未確認 |
| どれか | 同じチェーンの別の位置にある行 | 欠けに数えません。`table_changed` の所見に示します | 移し方によります。`filter_pre` と `forward` の wgft0 から入るものの drop の行をチェーンの先頭へ移すと、LAN の宛先への TCP が止まりました |

守りの行が欠けたときに開きうる面は、欠けた drop の行の組み合わせで決まります。
表の「確かめたこと」は、停止中のエージェントのテーブルから drop の行を削除し、VPS の名前空間から wgft0 のアドレスへ試したラボの結果です。

| 欠けた行 | 開きうる面 | 残っている行が閉じているもの | 確かめたこと |
|---|---|---|---|
| `input` の drop の行だけ | 無し | `filter_pre` の drop の行が、ホストのポートを閉じています。表に加わった行か位置の違う行があれば、この閉じ方は言えません | ホストのポートにも他のテーブルの DNAT にも届きませんでした |
| `filter_pre` の drop の行 | 他のテーブルの DNAT | `input` の drop の行がホストのポートを、`forward` の wgft0 から入るものの drop の行が LAN への面を閉じています | 他のテーブルの DNAT にだけ届きました |
| `filter_pre` と `input` の drop の行 | wgft が公開していないホストのポートと、他のテーブルの DNAT。wgft0 の `route_localnet` が 1 の間は、ループバックだけで待ち受けるポートも含みます | | 両方に届きました。`route_localnet` を 1 にした wgft0 では、宛先を `127.0.0.1` に書き換えたパケットがループバックの待ち受けに届き、片方の行だけを削除した表では届きませんでした |
| `forward` の wgft0 から入るものの drop の行だけ | 無し | `filter_pre` の drop の行が、LAN への面を閉じています。表に加わった行か位置の違う行があれば、この閉じ方は言えません | LAN のホストに届きませんでした |
| `filter_pre` と `forward` の wgft0 から入るものの drop の行 | DNAT していないパケットの LAN への転送と、他のテーブルの DNAT | | LAN のホストに届きました。ラボでは server の側のピアの AllowedIPs に LAN のアドレスを加えて試しました。wgft が設定するピアでは VPS はそのパケットを送りませんが、守りの行が防ぐ相手は [11 節](../security/admin-transport.md#11-セキュリティ)の奪われた VPS です。VPS の root は自分のピアの AllowedIPs を自由に追加できるので、この設定は緩和になりません |
| `forward` の wgft0 から wgft0 への drop の行 | wgft0 から入ったパケットの wgft0 への折り返し (宛先がトンネルの先にある DNAT など) | | 未確認です。VPS のトンネルアドレスを宛先にしたルールでは、どの drop の行を削除しても VPS の側に届きませんでした |
| `forward` の wgft0 へ出るものの drop の行 | 転送したフローの返りでないパケットの wgft0 への転送 | | 未確認です。LAN のホストから VPS のトンネルアドレスへの接続は、この行を削除しても VPS の側に届きませんでした |
| MSS のクランプの行 | ICMP を落とす経路での大きな TCP の停止 | | [7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの)のとおり、ラボで確かめました |

宛先がホスト自身かどうかは、記録の DNAT の宛先をホストのアドレスと比べて決めます。
ホストのアドレスは `CAP_NET_ADMIN` なしで読めます。
読めなければ、どちらの宛先もありうるので、転送の行として数えます。
表の分け方は、ラボで、停止中のエージェントのテーブルから行とチェーンを 1 種類ずつ削除し、LAN の宛先への TCP と UDP、ホスト自身の宛先への TCP が通るかを見て確かめました。
通す行とその drop の行を両方削除した組み合わせも確かめました。
見出しの違うチェーンは確かめておらず、転送が止まらないとは言えないので転送の側に置きます。
守りの行が欠けたときに実際に何が届くかは、`filter_pre` の drop の行を削除すると、他のテーブルの DNAT が wgft0 から届くようになることだけを確かめました。

ルールの状態は、稼働中はハートビートと同じ 1 回の読みから来る値であり、停止中は記録が持つルールごとの理由です。
所見はルール単位とし、ルールごとに DNAT を置いたポートの数を示します。
DNAT を置いたまま `error` を報告するルールと、DNAT を持たないルールを、運用者が見分けられるようにするためです。
直前の解決の結果で転送を続けているルールは、ルールの理由がそのことと転送先のアドレスを示します。

直前の公開の誤りと直前の見直しの誤りは、エージェントのプロセスのメモリにだけあります。
ここでの見直しは、30 秒ごとの見直しか、変更の通知の後の見直しです ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
TCP の宛先の接続確認の結果は、ハートビートにだけあります。
このため、エージェントが停止している実行の `dataplane.table` は、次の形で判定します (2026-09-24、所有者の決定)。
テーブルがあることだけでは OK にしません。
停止中の診断が答えるのは、プロセスが止まっている間に実際に残っているカーネルの転送だからです。

エージェントが停止している実行の `dataplane.table` は、状態ファイル `agent.json` の記録と実際の `table inet wgft_agent` を比べます。
材料は、最後に処理した全体状態 `LastState` と、カーネルモードで記録する直近の公開の結果です ([9 節](../state.md#9-状態の保存と再起動))。
直近の公開の結果には、ルールごとに、公開したポートと、そのとき解決して DNAT に書いた宛先のアドレスとポート、または [7b.3 節](../kernel-agent/targets.md#7b3-ルールの状態と失敗の種類)の 1 つ目の種類で公開しなかった理由を持ちます。
ホスト名の解決の結果と、許可一覧を当てはめた結果は、`LastState` の宣言だけからは導けないためです。
比べ方は次のとおりです。

- 公開すべきルール:直近の公開の結果が公開したと記録しているルールです。
  その各ポートの DNAT が、記録した宛先を指して実際のテーブルにあることを確かめます。
  1 つでも無いか別の宛先を指していれば FAILED とします
- 公開しなかったルール:直近の公開の結果が理由を記録しているルールは、稼働中と同じく FAILED とします
- 記録が無い場合:直近の公開の結果を持たない `agent.json` では、判定を宣言から導ける範囲に限ります。
  有効なルールの各ポートに DNAT があること、IP リテラルの宛先ならその宛先を指すことを確かめ、ループバックの宛先とブロードキャストかマルチキャストの宛先 ([7 節](../agent-dataplane.md#7-データプレーン自宅側))を持つルールは FAILED とします。
  ループバックの宛先は、許可一覧が名指すときだけ公開します ([7b.2 節](../kernel-agent/targets.md#ループバックの宛先))。
  この場合は許可一覧を当てはめないので、公開されなかったものとして扱います。
  帯のブロードキャストのアドレスは、`agent doctor` を実行した時点のホストのインタフェースの一覧で判定します。
  ホスト名の宛先の向き先、許可一覧の当てはめ、DNAT の行の外の行の形は確かめません。
  許可一覧を設定の出どころから組み立て直さないのは、「宛先の許可一覧の扱い」の項と同じ理由によります。
  ユーザー空間モードで動いてきたエージェントをカーネルモードで起動し、最初の公開の前に止まった場合がこれに当たります
- 再現できない部分:TCP の宛先の接続確認の結果 (2 つ目の種類) と、直前の公開の誤りは、稼働中のプロセスなしには再現できません。
  この部分は判定せず、所見に比べた範囲と比べなかった範囲を示します

停止中の `dataplane.table` の状態は、比べた部分に FAILED があれば FAILED とし、無ければ UNKNOWN とし、理由の符号を `agent_not_running` とします。
比べなかった部分が必ず残るので、停止中の実行で OK にはしません。
終了コードは「終了コード」の項の層の規則からそのまま決まります。
FAILED は層 1 の FAILED として終了コード 1 になります。
比べた部分がすべて一致した UNKNOWN は、権限で証拠に届かなかった実行ではないので層 2 に入らず、他に FAILED が無ければ終了コードは 0 のままです。
テーブルを権限で読めない場合は、前述の `needs_cap_net_admin` の規則を優先します。
