#### `dataplane.table` の判定

公開の記録と実際のテーブルを比べ、転送の行と守りの行を区別します。
停止中は再現できない証拠が残るため、一致した部分だけで OK にしません。


カーネルモードのルール単位の失敗は `dataplane.table` が示す (2026-09-24、所有者の決定)。
`dataplane.table` は 2 つのことを判定します。
1 つはテーブルそのものが正しいことであり、もう 1 つは、テーブルが公開すべき各ルールが実際に成り立っていることです。
どちらも、直近の公開の記録と実際のテーブルを同じ関数で比べて判定します。
比べるのは、`nat_pre` の DNAT の行から読んだルールとポートごとの宛先と、DNAT の行を含むすべてのチェーンの行の形と並びである ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
稼働中のエージェントはメモリの上の記録を、停止中の診断は `agent.json` の記録を渡す。
記録は公開に成功するたびに両方で同じ値になるので、どちらの実行でも同じ比べ方になります。
判定は次の順に行います。

- FAILED `table_missing`:`table inet wgft_agent` がありません
- FAILED `table_rows_missing`:記録から組む表の行かチェーンのうち、欠けると転送が止まるものが欠けている、または記録にある DNAT が無いか別の宛先を指しています。
  どの行が当たるかは後述の表のとおりです。
  filter_pre の通す行、forward の通す行、MASQUERADE のどれかが欠けても転送は止まるので、DNAT の行だけでは足りない。
  エージェントが止まった後に行が消された場合も、ここで見つかる。
  守りの行も同時に欠けていれば、所見に併せて示します
- FAILED `listener_error`:ルール 1 本以上の状態が `error` です。
  [7b.3 節](../kernel-agent/targets.md#7b3-ルールの状態と失敗の種類)の 1 つ目の種類 (許可一覧の外、名前の解決の失敗、ループバックの宛先、ブロードキャストかマルチキャストの宛先で、そのルールの DNAT が無い) と 2 つ目の種類 (TCP の宛先の接続確認の失敗で、DNAT はある) のどちらも当たる。
  `ip_forward` が 0 のために `error` を報告するルール ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの)) も当たる。
  名前の解決に失敗して直前の解決の結果で転送を続けているルール ([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い)) は、理由の後ろに試し接続の誤りか `ip_forward` の誤りが続く場合だけ当たる。
  続かない場合は、次の `resolve_failed` である (2026-09-25)。
  この除外を別にすれば、ユーザー空間モードの `relay.listeners` が、ルールの `error` の出どころを問わず FAILED にするのと同じ扱いです。
  除くのは、そのルールの `error` が転送の停止を示さないためであり、ユーザー空間モードのエージェントはこの種類の `error` を報告しません。
  符号は `relay.listeners` と同じ `listener_error` とします。
  符号が表す事実、つまり転送の停止を示しうる `error` のルールが 1 本以上あることは、どちらのモードでも同じです
- UNKNOWN `guard_rows_missing`:欠けたのが、欠けても転送が止まらない行とチェーン (守りの行) だけである (2026-09-24、所有者の決定)。
  転送は続きうるので、終了コード 1 が答える問いに対して FAILED とは言えない。
  所見は、欠けた行の名前と、欠けた行の組み合わせで開きうる面を示します。
  drop の行は層になっているので、面は、その面を閉じる行がすべて欠けたときだけ開く (2026-09-24、所有者の決定)。
  1 行だけの欠けで面が開かないときは、残っている行がまだ閉じていることを示します。
  組み合わせは後述の守りの行の効果の表のとおりです。
  表に加わった行か位置の違う行が無ければ、転送は続きうることも添える。
  それらがあれば、その効果は分からないので、転送は続きうるとも、残っている行がまだ閉じているとも言わず、それらを所見に示します。
  加わった行は、残っている drop の行より前でパケットを通しうるためです。
  `input` の drop の行を消し、`filter_pre` の先頭に wgft0 から入るものを通す行を加えた表では、ホストのポートにも他のテーブルの DNAT にも届いた。
  ルールの `error` が同時にあれば、`listener_error` の所見に併せて示します
- UNKNOWN `publish_failed`:直近の全体状態の公開が失敗し ([7b.3 節](../kernel-agent/targets.md#7b3-ルールの状態と失敗の種類)の 3 つ目の種類)、旧いテーブルが残っています。
  旧いテーブルが転送を続けているので、このホストのエージェントが今は転送を担えない、とは言えず、FAILED にはしません。
  所見に公開の誤りを示します。
  稼働中の実行だけが持つ事実です
- UNKNOWN `table_changed`:記録から組む表の行はすべてあるが、wgft が書かない行かチェーンが加わっているか、記録から組む行が同じチェーンの別の位置にあります。
  どちらも、転送を止めるかどうかは分かりません。
  所見に加わった行と位置の違う行を示します。
  稼働中のエージェントは変更の通知の後の見直しで公開し直し、公開し直しが失敗した後は 30 秒ごとの見直しでも試し直す ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
  このため、稼働中の実行でこの所見が続くのは、公開し直しが失敗しているか、失敗の後の間隔のために通知の後の見直しが待っている間です
- UNKNOWN `resolve_failed`:稼働中の実行で、`error` のルールがどれも、名前の解決に失敗して直前の解決の結果で転送を続けているだけのルール ([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い)) である (2026-09-25、所有者の決定)。
  DNAT は直前のアドレスへ向いたまま残っており、転送の停止は観測していないので、終了コード 1 が答える問いに対して FAILED とは言えない。
  `host.resolve` と `tunnel.resolve` の `resolve_failed` と同じく、名前の解決の失敗は今この瞬間に転送を担えないという証拠ではありません。
  `server doctor` の `rule.target_resolve` も同じルールを FAILED にせず、UNKNOWN の `target_resolve_failed` とする ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor))。
  所見は、直前の解決の結果で転送を続けているルールと、その解決の誤りを示します。
  判定の材料は理由の文言であり、`server doctor` と同じ関数で読みます。
  転送の行の欠け、守りの行の欠け、公開の失敗、表の変更と同時にあれば、そちらの符号を採り、このルールを所見に併せて示します。
  `listener_error` の所見にも併せて示します。
  30 秒ごとの見直しの失敗は、OK の所見と同じく併せて示します。
  停止中の実行では、次の `agent_not_running` を採り、所見のルールの一覧に理由を示します
- UNKNOWN `agent_not_running`:停止中で、比べた部分がすべて一致した。
  後述します
- それ以外は OK とします

行とチェーンの分け方は、「その行が欠けたときに転送が止まるか」で決める (2026-09-24、所有者の決定)。
欠けたときに転送が止まる行を転送の行、止まらない行を守りの行と呼ぶ。
通す行は、同じチェーンでそれが通さなかったパケットを落とす drop の行があるときだけ転送に要る。
その drop の行も欠けていれば、通す行が欠けても転送は止まらないので、守りの行として数えます。
チェーンごと無い場合は、そのチェーンの分け方に従います。
判定は稼働中と停止中で同じ関数が行います。
分け方は次の表のとおりです。

期待する行が同じチェーンの別の位置にある場合は、欠けに数えない (2026-09-24、所有者の決定)。
行は順に照らし合わせ、順に見つからなかった行を、まだ当たっていない実際の行から探す。
見つかれば位置の違う行とし、行が加わった場合と同じく効果の分からない変更として扱う。
たとえば `filter_pre` の drop の行を消して先頭に入れ直した表では、その行は欠けておらず、公開した通す行より前で wgft0 からのパケットを落とす。
本当に無い行と位置の違う行が両方あれば、欠けの判定 (転送の行なら `table_rows_missing`、守りの行だけなら `guard_rows_missing`) を保ち、位置の違う行と加わった行も所見に示します。

| チェーン | 行 | 分け方 | 欠けたときに止まる転送 |
|---|---|---|---|
| `filter_pre` | ルールごとの通す行 | 転送 (同じチェーンの drop の行があるとき) | そのルール |
| `filter_pre` | 成立済みのフローを通す行 | 守り | 無し |
| `filter_pre` | drop の行 | 守り | 無し |
| `filter_pre` | チェーンそのもの | 守り | 無し |
| `nat_pre` | ルールごとの DNAT の行と map の要素 | 転送 | そのルール |
| `nat_pre` | チェーンそのもの | 転送 | すべてのルール |
| `input` | DNAT したフローを通す行 | 転送 (drop の行があり、宛先がホスト自身のルールがあるとき) | 宛先がホスト自身のルール |
| `input` | 成立済みのフローを通す行 | 守り | 無し |
| `input` | drop の行 | 守り | 無し |
| `input` | チェーンそのもの | 守り | 無し |
| `forward` | 2 つの MSS のクランプの行 | 守り | 無し。ICMP を落とす経路の大きな TCP は止まりうる ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの)) |
| `forward` | wgft0 から wgft0 への drop の行 | 守り | 無し |
| `forward` | DNAT したフローを通す行 | 転送 (wgft0 から入るものの drop の行があり、宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| `forward` | wgft0 へ出る成立済みのフローを通す行 | 転送 (wgft0 へ出るものの drop の行があり、宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| `forward` | 2 つの drop の行 | 守り | 無し |
| `forward` | チェーンそのもの | 守り | 無し |
| `postrouting` | MASQUERADE の行とチェーンそのもの | 転送 (宛先がホスト自身でないルールがあるとき) | 宛先がホスト自身でないルール |
| どれか | 見出し (種類、フック、優先度、policy) の違うチェーン | 転送 | 未確認 |
| どれか | 同じチェーンの別の位置にある行 | 欠けに数えない。`table_changed` の所見に示す | 移し方による。`filter_pre` と `forward` の wgft0 から入るものの drop の行をチェーンの先頭へ移すと、LAN の宛先への TCP が止まった |

守りの行が欠けたときに開きうる面は、欠けた drop の行の組み合わせで決まる。
表の「確かめたこと」は、停止中のエージェントのテーブルから drop の行を消し、VPS の名前空間から wgft0 のアドレスへ試したラボの結果です。

| 欠けた行 | 開きうる面 | 残っている行が閉じているもの | 確かめたこと |
|---|---|---|---|
| `input` の drop の行だけ | 無し | `filter_pre` の drop の行が、ホストのポートを閉じている。表に加わった行か位置の違う行があれば、この閉じ方は言えない | ホストのポートにも他のテーブルの DNAT にも届かなかった |
| `filter_pre` の drop の行 | 他のテーブルの DNAT | `input` の drop の行がホストのポートを、`forward` の wgft0 から入るものの drop の行が LAN への面を閉じている | 他のテーブルの DNAT にだけ届いた |
| `filter_pre` と `input` の drop の行 | wgft が公開していないホストのポートと、他のテーブルの DNAT | | 両方に届いた |
| `forward` の wgft0 から入るものの drop の行だけ | 無し | `filter_pre` の drop の行が、LAN への面を閉じている。表に加わった行か位置の違う行があれば、この閉じ方は言えない | LAN のホストに届かなかった |
| `filter_pre` と `forward` の wgft0 から入るものの drop の行 | DNAT していないパケットの LAN への転送と、他のテーブルの DNAT | | LAN のホストに届いた。ラボでは server の側のピアの AllowedIPs に LAN のアドレスを加えて試した。wgft が設定するピアでは VPS はそのパケットを送らないが、守りの行が防ぐ相手は [11 節](../security/admin-transport.md#11-セキュリティ)の奪われた VPS であり、VPS の root は自分のピアの AllowedIPs を自由に足せるので、この設定は緩和にならない |
| `forward` の wgft0 から wgft0 への drop の行 | wgft0 から入ったパケットの wgft0 への折り返し (宛先がトンネルの先にある DNAT など) | | 未確認。VPS のトンネルアドレスを宛先にしたルールでは、どの drop の行を消しても VPS の側に届かなかった |
| `forward` の wgft0 へ出るものの drop の行 | 転送したフローの返りでないパケットの wgft0 への転送 | | 未確認。LAN のホストから VPS のトンネルアドレスへの接続は、この行を消しても VPS の側に届かなかった |
| MSS のクランプの行 | ICMP を落とす経路での大きな TCP の停止 | | [7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの)のとおり、ラボで確かめた |

宛先がホスト自身かどうかは、記録の DNAT の宛先をホストのアドレスと比べて決める。
ホストのアドレスは `CAP_NET_ADMIN` なしで読める。
読めなければ、どちらの宛先もありうるので、転送の行として数えます。
表の分け方は、ラボで、停止中のエージェントのテーブルから行とチェーンを 1 種類ずつ消し、LAN の宛先への TCP と UDP、ホスト自身の宛先への TCP が通るかを見て確かめた。
通す行とその drop の行を両方消した組み合わせも確かめた。
見出しの違うチェーンは確かめておらず、転送が止まらないとは言えないので転送の側に置く。
守りの行が欠けたときに実際に何が届くかは、`filter_pre` の drop の行を消すと、他のテーブルの DNAT が wgft0 から届くようになることだけを確かめた。

ルールの状態は、稼働中はハートビートと同じ 1 回の読みから来る値であり、停止中は記録が持つルールごとの理由です。
所見はルール単位とし、ルールごとに DNAT を置いたポートの数を示します。
DNAT を置いたまま `error` を報告するルールと、DNAT を持たないルールを、運用者が見分けられるようにするためです。
直前の解決の結果で転送を続けているルールは、ルールの理由がそのことと転送先のアドレスを示します。

直前の公開の誤りと、直前の見直し(30 秒ごとの見直しか、変更の通知の後の見直し。
[7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))の誤りはエージェントのプロセスのメモリにだけあり、TCP の宛先の接続確認の結果はハートビートにだけあります。
このため、エージェントが停止している実行の `dataplane.table` は、次の形で判定する (2026-09-24、所有者の決定)。
テーブルがあることだけでは OK にしません。
停止中の診断が答えるのは、プロセスが止まっている間に実際に残っているカーネルの転送だからです。

エージェントが停止している実行の `dataplane.table` は、状態ファイル `agent.json` の記録と実際の `table inet wgft_agent` を比べる。
材料は、最後に処理した全体状態 `LastState` と、カーネルモードで記録する直近の公開の結果である ([9 節](../state.md#9-状態の保存と再起動))。
直近の公開の結果には、ルールごとに、公開したポートと、そのとき解決して DNAT に書いた宛先のアドレスとポート、または [7b.3 節](../kernel-agent/targets.md#7b3-ルールの状態と失敗の種類)の 1 つ目の種類で公開しなかった理由を持ちます。
ホスト名の解決の結果と、許可一覧を当てはめた結果は、`LastState` の宣言だけからは導けないためです。
比べ方は次のとおりです。

- 公開すべきルール:直近の公開の結果が公開したと記録しているルールです。
  その各ポートの DNAT が、記録した宛先を指して実際のテーブルにあることを確かめる。
  1 つでも無いか別の宛先を指していれば FAILED とします
- 公開しなかったルール:直近の公開の結果が理由を記録しているルールは、稼働中と同じく FAILED とします
- 記録が無い場合:直近の公開の結果を持たない `agent.json` では、判定を宣言から導ける範囲に限る。
  有効なルールの各ポートに DNAT があること、IP リテラルの宛先ならその宛先を指すことを確かめ、ループバックの宛先とブロードキャストかマルチキャストの宛先([7 節](../agent-dataplane.md#7-データプレーン自宅側))を持つルールは FAILED とします。
  帯のブロードキャストのアドレスは、`agent doctor` を実行した時点のホストのインタフェースの一覧で判定します。
  ホスト名の宛先の向き先、許可一覧の当てはめ、DNAT の行の外の行の形は確かめない。
  許可一覧を設定の出どころから組み立て直さないのは、「宛先の許可一覧の扱い」の項と同じ理由による。
  ユーザー空間モードで動いてきたエージェントをカーネルモードで起動し、最初の公開の前に止まった場合がこれに当たる
- 再現できない部分:TCP の宛先の接続確認の結果 (2 つ目の種類) と、直前の公開の誤りは、稼働中のプロセスなしには再現できません。
  この部分は判定せず、所見に比べた範囲と比べなかった範囲を示します

停止中の `dataplane.table` の状態は、比べた部分に FAILED があれば FAILED とし、無ければ UNKNOWN とし、理由の符号を `agent_not_running` とします。
比べなかった部分が必ず残るので、停止中の実行で OK にはしません。
終了コードは「終了コード」の項の層の規則からそのまま決まる。
FAILED は層 1 の FAILED として終了コード 1 になります。
比べた部分がすべて一致した UNKNOWN は、権限で証拠に届かなかった実行ではないので層 2 に入らず、他に FAILED が無ければ終了コードは 0 のままです。
テーブルを権限で読めない場合は、前述の `needs_cap_net_admin` の規則が先に効く。
