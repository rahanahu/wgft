### 転送の診断 (`server doctor`)

server doctor は、server から見た転送の経路を診断します。
古い観測、適用世代の遅れ、UDP の応答、VPS の転送設定を区別します。


`wgft server doctor` は、転送が通らないときに、どこまで通ってどこで止まったか、運用者が次に何を見るかを答えるコマンドです。
内部の状態を並べる機能ではありません。
成功の条件は、利用者が次に見る場所を知らないまま残らないことです。
次の行動を伴わない所見は、この機能の失敗として扱う。

対象とする場面は次の 5 つです。
ポートを開いたのに接続できません。
昨日まで通っていたのに今日は通らない。
エージェントは接続しているのに転送されない。
1 本のルールだけが通らない。
server、トンネル、エージェント、宛先のどれが原因か分かりません。

#### 名前と置き場所

コマンドは `server` の下の `doctor` です。
理由は 3 つあります。
CLI は名詞で束ねており (`server`、`rule`、`agent`)、最上位の動詞は `version` だけなので、最上位の `doctor` は他と揃わない。
`server check` の隣に置くと、`check` が「このホストの設定は正しいか」に、`doctor` が「なぜ転送が通らないか」に答える対になります。
後述の自宅側の `agent doctor` と対称になります。

この配置には、明らかでない結果が 1 つあります。
`server` の一群は Linux 以外のビルドでは拒否する代替に置き換わる (`cmd/wgft/server_other.go`) ため、Windows と macOS のバイナリは、管理用 API しか必要としない `server doctor` を持ちません。
[10.3 節](../operations/setup.md#103-運用の流れ)のとおり CLI は VPS 上で root として使い、SSH で転送したソケットはブラウザのためのものなので、この制約は受け入れる。
手元の端末から使いたくなった場合の出口は、診断の実装を Linux の build tag の付いたファイルの外へ移すことだけです。
実装は既に build tag を持たない `cmd/wgft/doctor.go` にあり、登録だけが `server.go` にあるので、移すのは登録の位置を変える作業に収まる。
現時点では `server` の一群の構造を変更しません。

#### server と手元の診断の責務

`server doctor` は、server が持つ宣言と既に届いている観測から、転送の経路を診断します。
`--probe` は内側の TCP の経路だけを能動的に試します。
`agent doctor` は、server と通信できない場合も、エージェントのホストで現在の状態を調べます。
Web UI の診断画面は、server の CLI と同じ診断ロジックを使います ([10.2d 節](../web-doctor.md#102d-web-ui-の診断の画面))。

`--report` と、server がエージェントに診断を要求する遠隔の診断は未実装の提案です。
遠隔の診断を追加する場合は、wire と capability の交渉を使います ([7a.6 節](../architecture/wire-compatibility.md#7a6-維持する外部仕様と互換性))。
エージェント側の確認が要る所見では、`wgft agent doctor`、ログ、名前の解決、公開鍵の突き合わせを案内します。

<a id="5-つの状態"></a>
#### 5 つの状態

検査 1 件の結果は次の 5 つのいずれかです。
意味はこの表のとおりであり、他の読み方をしません。

| 状態 | 意味 |
|---|---|
| OK | その項目が成功することを実際に観測した |
| FAILED | その項目が失敗することを実際に観測した |
| UNKNOWN | 証拠はあるが、古い、食い違う、または判定に足りない |
| NOT TESTED | その到達性や条件をこのコマンドがそもそも試さない |
| SKIPPED | 試せたはずだが、手前の失敗によって今回は試せなかった |

OK は実際に検証したものだけに使います。
公開ポートは、server がそのポートを扱えていても、外からの到達性を試していないので NOT TESTED です。

```
public port        NOT TESTED
                   serving tcp 2456; reachability from outside was not tested
```

UDP のルールの宛先 (`rule.target`) も、同じ規則により、エージェントの新しい報告が `ok` であっても NOT TESTED とします。
理由の符号は `udp_listener_only` とします。
UDP のルールの `ok` は、エージェントがリスナーを開けたことしか意味しない ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
宛先がデータグラムを受け取ったことも、応答したことも示さないので、OK の定義に当たらない。
報告が古い場合の UNKNOWN と、報告が `error` の場合の FAILED は、TCP のルールと同じです。
NOT TESTED はルールの総合判定も終了コードも動かさないので、健全な UDP のルールの総合判定は OK のままであり、終了コードは 0 のままです。

```
target             NOT TESTED
                   not tested: the agent has its listener open, last report 12s ago, but a
                   UDP send cannot tell whether the target received it or answered
```

能動的な確認が通った宛先は OK です。

```
target             OK
                   connected to 192.168.1.50:2456 through the tunnel and the agent, observed just now
```

無効なルールは宣言どおりの状態であり、失敗ではありません。
検査はすべて SKIPPED になり、理由の符号は `rule_disabled` になります。
終了コードは 0 のままとします。
意図して無効にしたルールで監視が鳴り続けることを避けるためです。

#### 観測の古さ

OK は永続しません。
OK の所見は必ず観測の古さを伴い、閾値を越えた項目は OK でなくなる。

```
connected          OK         heartbeat 12s ago
WireGuard          OK         handshake 32s ago
target             UNKNOWN
                   the agent last reported this rule ok, but that was 2m14s ago
```

越えたときにどの状態へ移るかは、その値がどこから来るかで 2 つに分かれる。
`ObservedAt` が古いことと、観測した内容そのものが古いことは、別の事柄です。

**エージェントが過去に送った報告**は、古くなると UNKNOWN になり、理由の符号は `stale_report` になります。
値は報告した時点のものであり、その後どうなったかを server は知らないためです。

- エージェントの接続 (`agent.connection`): 90 秒とします。
  エージェントは 30 秒ごとにハートビートを送る ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)) ので、3 回分の沈黙を越えたら、接続しているという表示を今の値として扱わない
- エージェントが報告したルールの状態 (`rule.target`): 90 秒とします。
  TCP の `target` への接続確認は 30 秒ごとに行われる ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)) ので、接続の判定と同じ長さを使います

**server が今読む値**は、古くなると FAILED になります。
`tunnel.handshake` の 1 つだけが当たり、閾値は 3 分、理由の符号は `no_recent_handshake` です。
最終ハンドシェイクはエージェントの報告ではなく、server が WireGuard から今読む値です。
「最終ハンドシェイクは 181 秒前」という値は、今この瞬間に読んだ現在の観測であり、そのトンネルが健全の条件を満たしていないことを示します。
判定に足りない古い証拠ではないので、UNKNOWN ではなく FAILED とします。

閾値の 3 分は [7 節](../agent-dataplane.md#7-データプレーン自宅側)の時定数から決まる。
server が配る keepalive は 25 秒 (`internal/vpsd/admin_backend.go`) で、`RekeyAfterTime` は 120 秒なので、健全なトンネルの最終ハンドシェイクは 145 秒より古くなりません。
`RejectAfterTime` の 180 秒を過ぎた鍵は送信にも使えない。
したがって 3 分を越えた値は、健全なトンネルでは生じない。
窃取検知が生きている wg エンドポイントを 3 分以内のものに限る ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)) のとも同じ値です。

この規則が防ぐのは、2026-09-21 に実測した 2 つの区間で、診断が誤って安心させることです。
1 つは、転送を続けているエージェントを server が切断と表示する区間です。
もう 1 つは、受信の経路が死んだトンネルの最終ハンドシェイクが 3 分間は新しいままである区間である ([7 節](../agent-dataplane.md#7-データプレーン自宅側))。
後者の区間の長さは `tunnel.handshake` の閾値そのものであり、別の値ではありません。
エージェントが device と netstack を作り直す 300 秒 ([7 節](../agent-dataplane.md#7-データプレーン自宅側)) はエージェント側の watchdog の閾値であって、診断が気付けない期間ではありません。

#### ルール集合の世代の遅れ

`agent.rules_received` は互換性のため ID を保つが、検査するのはエージェントがハートビートで報告した世代番号と server の世代番号だけです。
人向けの名前は「rule generation」とし、番号が等しい場合の OK は番号の比較に限る。
番号が等しくても、エージェントが適用した State の内容が server の公開した State と同一かどうかは UNKNOWN です。
現在の wire には内容の確認値や受領の確認が無く、この変更で wire と認証情報の保存形式を変えません。
診断の所見は、この限界を世代番号の一致、不一致のどちらでも明示します。
適用済み State の内容は継続して検証不能であり、番号がそろっても OK と報告しません。

ルール別の CLI と Web UI では、この検査の詳細に内容の UNKNOWN を記す。
一覧では同じ制約をルールごとに繰り返さず、「この診断が試していない範囲」に一度示します。
内容の検証不能は転送失敗の証拠ではないので、ルールの総合判定、終了コード、ダッシュボードの印を変えません。
検査の ID、status、reason の機械向けの値と管理用 API のフィールドも変えません。

`agent.rules_received` は、接続中のエージェントの世代が server の世代と違うとき、その遅れが続いている長さで判定を 2 つに分ける (2026-09-24、所有者の決定)。
60 秒未満は UNKNOWN とし、理由の符号を `generation_pending` とします。
60 秒以上は FAILED とし、理由の符号を `generation_behind` とします。
世代はルール集合全体に 1 つだけあり ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))、どのルールを変えても、そのエージェントを名指す有効なすべてのルールがこの検査を経由します。
遅れを直ちに FAILED にすると、ルールを 1 本変えるたびに、そのエージェントのすべてのルールが一時的に FAILED になります。
ラボではエージェントは新しい世代を 1 秒未満で取り、取った直後にハートビートを送る ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)) ので、60 秒続く遅れは届く途中の遅れではありません。
このため 60 秒以上の FAILED は、原因の候補にも次の手順にも、届く途中であることや数秒後の再実行を挙げない。

遅れの長さは、server がエージェントごとにメモリに持つ遅れの始まりの時刻から測る。
管理用 API のエージェント一覧は、この時刻を `generation_behind_since` として返し、遅れていないエージェントでは省く。
一覧は、直近のハートビートの内容 (`last_heartbeat`、`generation`) とこの時刻を、ハートビートの記録が済んだ後の 1 つの時点の組として返します。
別々に読むと、ハートビートの内容だけが新しく、始まりの時刻の記録がまだの途中を返すことがあり、その形は `generation_behind_since` を返さない旧い server の応答と区別できません。
診断は管理用 API だけを読むので、この値を経由します。
始まりの時刻は次の規則で決める。

- 記録の契機:server の世代が進んだときと、ハートビートが届いたときに、エージェントの世代が server の世代より古ければ、始まりの時刻が無い場合に限りその時刻を記録します
- 遅れの間に世代がさらに進んだ場合の扱い:始まりの時刻を動かさない。
  動かすと、ルールの変更が続く間は遅れがいつまでも閾値に届かない
- 始まりの時刻が消える条件:エージェントが server の今の世代を報告したときだけです
- server の再起動の後の扱い:始まりの時刻はメモリにしか無いので失われる。
  起動の後に初めて遅れを観測した時刻から数え直す。
  起動の前から続いていた遅れの長さを server は知らないので、その分だけ FAILED になる時刻が遅れる

接続してからまだハートビートが届いていないエージェントは、世代を比べず UNKNOWN とし、理由の符号を `not_reported` とします。
hub は接続ごとにエージェントの状態を作り直すので、この間の管理用 API の応答は `last_heartbeat` を省き、`generation` を 0 とします。
この 0 は報告された世代ではありません。
判定の条件は `agent.connection` と同じく `last_heartbeat` が無いことであり、2 つの検査は同じ判定を返します。
再接続の前から遅れの始まりの時刻が記録されていても、この判定を先に行います。
最初のハートビートが届いた後は、記録されている始まりの時刻から遅れの長さを測る。

応答に `generation_behind_since` が無いまま世代が違う場合は、v1.1 と同じく FAILED とし、理由の符号を `generation_behind` とします。
この値を返さない旧い server を新しい CLI で診断する場合が当たる。
遅れの長さが分からないまま UNKNOWN にすると、止まった遅れを見逃すためです。

`generation_behind` の意味は v1.1 から変えず、止まった遅れを表します。
`generation_pending` は、理由の符号の開いた集合への加算である ([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
`generation_pending` の UNKNOWN は、経路の上の他の UNKNOWN と同じく、ルールの総合判定を UNKNOWN にし、終了コードを動かさない。

#### UDP の応答の観測

UDP のルールの `rule.target` には、server 自身が見た宛先の応答を補足の 1 行として添える(2026-09-24、所有者の決定)。
エージェントの報告はリスナーを開けたことしか示さないので、宛先が応答しているかどうかの手掛かりを、server が転送の途中で受動的に観測します。
wire、ハートビート、capability は変えないので、観測はエージェントの版とモードに依らない。

観測する事実は、そのルールの UDP の応答がトンネルを通ってこの server に最後に届いた時刻です。
応答を返せるのはそのルールの宛先だけなので、この時刻は宛先からの応答の時刻と読める。
観測の方法はモードごとに次のとおりです。

- ユーザー空間モード:中継([6.3 節](../vps/userspace.md#63-ユーザー空間モード))は、宛先の側から応答を 1 つ読むたびに、待ち受けごとの最後の応答の時刻を記す。
  記すのは 1 秒に 1 回までで、時刻にはセッションの無通信の判定が既に読む値を使います。
  読み取りの誤りは応答として数えないので、宛先の側が ICMP で拒んだ場合も数えません。
  範囲のルールの値は、そのルールの待ち受けのうち最も新しいものです
- カーネルモード:`table inet wgft` に、UDP のルールごとの応答のカウンタの行を置く([6.1 節](../vps/kernel.md#61-カーネルモード))。
  行は `meta l4proto udp` を持つので、ICMP の誤りを数えません。
  `vpsd` は 10 秒ごとにカウンタを読み、前回より増えたルールの最後の応答の時刻を、その読み取りの時刻にします。
  パケットごとに Go を起こさないので、時刻は最大で 10 秒ほどの誤差を持ちます

カーネルモードでは、起動の後とテーブルの差し替えの後の最初の読み取りは基準にしかなりません。
0 でない値から過去の応答の時刻を推定しない(所有者の決定)。
差し替えはカウンタを 0 に戻すので、drop のカウンタ([6.1 節](../vps/kernel.md#61-カーネルモード))と同じく差し替えの直前に読み、直後にもう一度読んで基準にします。
2 つの読み取りの間には、数えない短い区間が残る。
その区間にだけ届いた応答は見落とされるが、無かった応答を作ることはありません。
この区間があっても、差し替えでは `since` を保つ。
連続性が途切れたときは、観測を捨てて次の読み取りを基準に始め直す。
読み取りの失敗、wgft の外でのカウンタの減少、成否の分からない差し替えがこれに当たる。

観測はメモリだけに持つので、server を再起動すると観測を始め直す。
ルールの ID が変わった場合(分割と統合)、ルールが別のエージェントへ移った場合、宛先が変わった場合も、応答の主が変わるので観測を捨てて始め直す(所有者の決定)。
公開ポートとエージェントのアドレスが変わった場合も始め直す。
この 2 つは、安全側に倒すために実装で加えた条件です。
無効にしたルールと削除したルールの観測は消える。
宛先を変えた直後は、エージェントが新しいルールを適用するまでの間、古い宛先が返した応答が新しい観測に数えられうる。
この区間はカーネルモードとユーザー空間モードの両方にあります。

観測は状態を変えません。
最近の応答があっても NOT TESTED は OK になりません。
応答が無いことや古いことも UNKNOWN や FAILED にならず、閾値も持ちません。
使われていないルールと応答しないサービスは、どちらも応答が無いように見えるためです。
ルールの総合判定、報告全体の状態、終了コードも動かさない。
カウンタを読めない場合は、応答が無いことと区別して、観測できないことをその理由とともに示します。
この場合も状態は動かさない。

```
target             NOT TESTED
                   not tested: the agent has its listener open, last report 12s ago, but a
                   UDP send cannot tell whether the target received it or answered
                   last UDP reply seen by this server 18s ago
```

応答を見ていない場合の行は `no UDP reply seen since this server started watching the rule 3h12m0s ago; an idle rule looks the same`、観測できない場合の行は `UDP replies are not observed: <理由>` です。
`--json` では `rule.target` の検査に任意の項目 `last_reply_at`・`reply_since`・`reply_not_observed` を加え、新しい検査の `id` は作りません。
新しい `id` は 5 つの状態のどれかを返す必要があり、観測を状態に写さない決定と両立しないためです。
管理用 API には `udp_replies` を加える([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
`rule ls` の表とダッシュボードのルール一覧には出さない。

この観測は、宛先の応答とトンネルの戻りの経路を切り分けられない。
戻りの経路だけが壊れた場合も観測は止まるが、観測が無いことを失敗にしないので、誤った判定にはなりません。
宛先とトンネルの切り分けは `tunnel.handshake` と `agent.connection` が担う。
TCP のルールには加えない。
TCP の宛先は 30 秒ごとの接続確認を既に持つためです。

#### この VPS の ip_forward

カーネルモードの server は、起動時にだけ `net.ipv4.ip_forward` を 1 にする([6.1 節](../vps/kernel.md#61-カーネルモード))。
稼働中に外から 0 にされると、DNAT を公開したままカーネルは wg0 へ転送しなくなり、カーネルで転送するルールはすべて止まります。
2026-09-25 まで、この状態の `server doctor` は `server.dataplane` を OK とし、失敗の無い報告を返していました。

管理用 API の `GET /api/v1/rules` は、カーネルモードの server が応答を組むときに読んだ今の値を `ip_forward` として返す([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))。
ユーザー空間モードの server は返さない。
カーネルで転送しないので、値がルールについて何も述べないためです。
読む節点は増えません。
値が 1 でないとき、次のとおり判定する(2026-09-25、所有者の決定)。

- `rule.public_port`:カーネルで転送するルール、つまり `vps_mode` がプロキシでないルールで、`apply_state` が `active` なら FAILED とし、理由の符号を `ip_forward_off` とします。
  server が今読んだ値であり、転送が止まっていることの観測です。
  プロキシのルールは `vpsd` が受けて自分から wg0 へ接続し直すので、`ip_forward` に依らず、判定を変えません
- `server.dataplane`:カーネルで転送する公開中のルールが 1 本以上あれば FAILED とし、理由の符号を `ip_forward_off` とします。
  1 本も無ければ、止まる転送が無いので状態は変えず、所見に値と、後から加えるカーネルモードのルールは転送されないことを添える。
  世代の遅れが同時にあれば、世代の遅れの FAILED を先に示し、所見に `ip_forward` を併せて示します。
  世代の遅れが無く、保存済みの全体 State が未公開でも、観測した転送停止の FAILED を優先し、その所見に未公開の事実も添える

次の一手は、`sysctl -w net.ipv4.ip_forward=1` で 1 にすることと、0 にしたもの(`/etc/sysctl.d` の設定や堅牢化のスクリプト)を探すことです。
書けない場合は、起動時の書き込みも同じ原因で失敗するので再起動だけでは直らない。
読み取り専用の `/proc` やコンテナの制限などの原因を除いてから 1 にする(2026-10-03)。
`--probe` の疎通確認は、この状態でも成功します。
server 自身が wg0 へ接続し、カーネルの転送を経ないためです。
止まった位置は `rule.public_port` が示します。
稼働中の server は自分では戻さない([6.1 節](../vps/kernel.md#61-カーネルモード))。
値を読めなかった場合は状態を変えず、`--verbose` の内部の値に読めなかった理由を示します。
