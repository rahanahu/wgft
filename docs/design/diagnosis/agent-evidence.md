# エージェント側の診断

agent doctor は、エージェントのホストで、停止中も読める事実と稼働中の制御ソケットの応答を組み合わせます。
能動的な宛先への接続確認は行いません。


<a id="102c-エージェント側の診断-wgft-agent-doctor"></a>
### エージェント側の診断 (`wgft agent doctor`)

`wgft agent doctor` は、エージェントを動かしているホストの上で、そのホストでしか分からない事実を調べるコマンドです。
エージェントが止まっている間も、読める範囲だけを使って答えます。
[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)の `server doctor` が server から見た転送の経路に答えるのに対し、`agent doctor` はエージェントのローカルの実行環境と現在の状態に答えます (2026-09-23、所有者の決定)。
エージェントが止まっていても成立する検査、稼働中のプロセスの制御ソケットから読む検査、`--json` の機械向けの出力は実装してあります。

`server doctor` は既に、自分から見えない範囲として「エージェントのホストの環境」を挙げています。
エージェントの OS、権限、インタフェース、名前解決がその範囲に当たります ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor)の「試していない範囲」)。
`agent doctor` が埋めるのは、同じ範囲です。

#### この節が固定する範囲

この節が主に対象とするのは、[7 節](../agent-dataplane.md#7-データプレーン自宅側)のユーザー空間の中継を持つエージェントです。
`Relay` 群の検査と `tunnel.watchdog` の存在、および `tunnel.local` の判定規則は、その中継に紐づきます。
カーネルモードのエージェント ([7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード)) の扱いは、後述の[「カーネルモードのエージェント」](agent-kernel.md#カーネルモードのエージェント)の項が範囲を定めます。

検査の ID、群、総合判定、終了コード、制御ソケットの応答は、後続の各項に定める規則に従います。
機械向けの出力は `checks[]` の `id`、`status`、`reason` と、確定した最上位の形式を持ちます。
個々の理由の符号と JSON の形は「機械向けの出力」の表に定め、[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の保証を維持します。

実装は、この節が定めた規則をそのまま入力とする表のテストを持ちます (2026-09-23、所有者の決定)。
この節が定めた対応をそのままテストの入力に写せば、実装者が途中で意味を解釈し直す余地が減ります。
表の入力には、少なくとも次の場面を含めます。

- エージェントが停止しています
- ファイルのパーミッションのため、制御ソケットに接続できません
- 古い常駐プロセスが `error: unknown command` を返します
- 実行時の状態を守る排他を期限内に取れません
- トンネルのエンドポイントの初回の名前解決に失敗しています
- 再解決に失敗していますが、解決済みのエンドポイントは保っています
- トンネルの構築が失敗しています
- ハンドシェイクがまだ成立していません
- リスナーの開放に失敗しています
- 総合判定を動かす検査の FAILED と、終了コード 2 に倒す条件が同時に成り立ちます
- root で実行しています
- カーネルモードのエージェントが停止していますが、wgft0、テーブル、`ip_forward` が揃っています
- カーネルモードのテーブルから、公開したルールの DNAT の行が消えています
- カーネルモードのホストで `ip_forward` が 0 です
- 停止しているカーネルモードのエージェントを、`CAP_NET_ADMIN` を持たない利用者で診断します
- ユーザー空間モードのエージェントで、カーネルモードの検査が NOT TESTED になります
- ユーザー空間モードのエージェントの WireGuard の UDP ソケットのバッファが、条件に届きません

場面ごとの結果は、判定の規則から導きます。
規則を変える場合は、設計文書を先に直します。

<a id="2-つのコマンドの境目"></a>
#### 2 つのコマンドの境目

役割は次の 2 行で分けます。

- `server doctor`: server から見た転送の経路に答えます
- `agent doctor`: エージェントのローカルの実行環境と現在の状態に答えます

`agent doctor` は、server から既に見えている事実を自分で判定し直しません。
同じ問いに対する 2 つ目の判定を持つと、片方の閾値や文言を変えたときに、もう片方が古いまま残ります。
境目を「証拠がどちらのホストにあるか」で引いておけば、後から遠隔の診断 ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor)) を加えるときにも、server が要求すべき情報の範囲がそのまま決まります。
判定し直さない対象は次のとおりです。

- `tunnel.handshake` ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor)): 最終ハンドシェイクが健全かどうかの判定と 3 分の閾値。
  `agent doctor` は観測した値を事実として示すだけとし、健全かどうかを言いません
- `server.dataplane`、`rule.public_port`、`rule.source_filter` ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor)): server 側の適用と公開側の状態。
  エージェントの手元には証拠そのものがありません
- `agent.connection` ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor)) と [10.2b 節](../status.md#102b-状態の要約wgft-status)の Agents 行: 制御ストリームが切れていることが、そのルールの転送や配置全体にとって何を意味するか。
  `agent doctor` は、つながっているかどうかとエージェント側が持つ理由を示すだけとします
- `rule.target` ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor)) と `agent_rule_states` ([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)): ルール 1 本が転送できているかどうかの総合判定
- 窃取検知の警告 (`GET /api/v1/warnings`) と [10.2b 節](../status.md#102b-状態の要約wgft-status)の Warnings 行

エージェントがハートビートのために既に計算している値を示す場合は、その結果をそのまま示し、`agent doctor` のための 2 つ目の計算を作りません。
対象は、トンネルの状態 (`proto.TunnelStatus`) とルールごとの状態 (`proto.RuleStatus`) であり、どちらも `internal/agent` の `heartbeat` が組み立てています。
実装は、トンネルの状態を実行時の排他の下で 1 回だけ読む共通の関数を切り出し、`heartbeat` と `agent doctor` の両方がその関数を使います (2026-09-23)。
トンネルの送受信バイト数は `proto.TunnelStatus` に載らず `heartbeat` が捨てているので、doctor の側で読み直す形にすると、同じ応答の中に異なる時点の値が混ざります。

<a id="2-つの証拠の出どころ"></a>
#### 2 つの証拠の出どころ

証拠は 2 か所から取ります。

- 静的で永続する事実は、認証情報ファイル `agent.json` から読みます。
  `Name`、`Endpoint`、`CertSHA256`、`UsedJoinTokenSHA256`、そして最後に処理した全体状態 `LastState` です ([9 節](../state.md#9-状態の保存と再起動))。
  稼働中のファイルは flock で守られていますが、ロックは隣の `agent.json.lock` に掛かり、`agent.json` 自体の読み取りはロックを見ません。
  したがって、エージェントが動いていても止まっていても同じように読めます
- 動的で今だけの事実は、稼働中のプロセスが持つ制御ソケットから読みます。
  ソケットは認証情報ファイルの隣の `agent.json.sock` で、Unix では 0600、Windows では保護 DACL を持ちます (`internal/agent/control`)。
  今の実装がプロセスの中に持っているのは、トンネルの送受信バイト数、ルールごとの現在の接続の数、フロー予算の拒否の累計、トンネルを作り直す watchdog の内部状態、そして制御ストリームの観測です。
  制御ストリームの観測が保つのは、今つながっているかどうか、直近の切断または失敗の理由、直近に待った再接続の間隔と次に試す時刻、直近の ping と pong の時刻です。
  どれもハートビートには載らないので、server 側には届きません ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)、[7a.10 節](../resource/admission.md#7a10-resource-guard-の再設計))。
  観測の保ち方は `internal/agent/streamobs.go` にあり、観測を読み出す関数は写しを返します ([以前の検証 2026-09-23](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L2717))

稼働中かどうかは、`agent.json.lock` にロックファイルを作らずに判定します (2026-09-23、所有者の決定)。
判定には `internal/flock` の `Inspect` を使います。
`Inspect` は `os.O_CREATE` を渡さずに開き、ファイルが既にある場合だけ flock の状態を見ます。
この判定を検査の 1 つ目に置き、以降の分岐の根拠にします。
ロックファイルを作る経路を使うと、エージェントを root で動かす配置で root が診断を実行しただけでロックファイルが root の所有で作られ、後から非特権で動くエージェントがそれを開けず起動できなくなります。
`O_CREATE` を伴う判定は、既定が読み取りだけであるという宣言にも反します。
読み取り専用の経路を用意する手間より、診断が状態を変えるかどうかのほうが重要です。
ただし、この保証が対象とする状態は、ロックファイルの有無に限ります。

`agent.process` は、ロックファイルが無ければ、稼働している証拠が無い実行として FAILED とします。
ロックファイルが無いのは、そのデータディレクトリでエージェントが一度も起動していない場合と、運用者がロックファイルを削除した場合があり、診断はその 2 つを区別できません。
どちらの場合も稼働の証拠は無く、「停止そのものは FAILED として扱う」という規則に従います。
この判定が及ぶのはこのデータディレクトリに限り、別の `WGFT_DATA_DIR` で稼働中のエージェントがあっても見えません。
ロックファイルがあるのに呼び出し元が権限で開けない場合は、稼働中か停止中かを判定できないので、次の前提が崩れている実行として扱い、終了コードの項に定める 2 の側に置きます。

ロックの状態を見ている間に他のプロセスがロックを取れない期間、つまり競合しうる期間は、無くすのではなく最小にします (2026-09-23、所有者の決定)。
共有ロックを一瞬だけ取って放つ形を許します。
Linux、Windows、macOS のいずれでも、ロックを取らずに状態だけを問い合わせる手段が揃わないためです。
最も重い副作用は、存在しないロックファイルを診断が作ることです。
この副作用は、`O_CREATE` を渡さないだけで無くなります。
残る実害は、診断がロックの状態を見ている一瞬に起動したエージェントがロックを取れず、起動がそのまま終わることです。
今の `deploy/agent.service` は `Restart=on-failure` を持つので、失うのは次の起動までの間だけです。
同じ形の競合は `agent rotate-key` と `server teardown` に既にあり、この改訂が新しく作るものではありません。
どちらも最初に `Inspect` でロックを見ます。

`agent doctor` は、エージェントと同じ実行主体で動かすことを前提とします (2026-09-23、所有者の決定)。
エージェントが root で動く配置では、`agent doctor` も root で実行します。
この前提の下では、呼び出し元がデータディレクトリと `agent.json` に対して持つ権限は、エージェント自身が持つ権限と同じものになります。
`host.privileges` と `agent.credentials` が答えるのは、この前提が満たされたときのエージェント自身の権限であり、呼び出し元固有の事情ではありません。
前提が崩れる実行の扱いは、後述の[「終了コード」](agent-output.md#終了コード)の項と、次の root の実行の扱いで定めます。

エージェントがシステムの利用者や systemd の `DynamicUser` で動く配置では、その利用者として `agent doctor` を実行するために、`sudo -u` や `systemd-run` を使うといった管理者の追加の操作が要る場合があります (2026-09-23、所有者の決定)。
この実行を手軽にする方法は次のとおりとします (2026-09-24、所有者の決定)。
root の実行で示す案内は、後述の `runuser -u wgft -- wgft agent doctor` のまま変えません。
制御ソケットの `doctor` の応答に、稼働中のエージェントの実 uid と利用者名を加え、root で実行したときの所見に、稼働中のエージェントがどの uid とどの利用者で動いているかを添えます。
動いているエージェント自身に聞くので推測にならず、`DynamicUser` の配置でも正しい名前を示せます。
unit の名前を推測して自動で実行し直す形は、[11a 節](../security/configuration.md#11a-設定の渡し方)の「環境を見て推測しない」に反するので持ちません。
`sudo` を持たない最小の構成も、前提に含めたままとします。
応答に加える値は、後述の[「カーネルモードの制御ソケットの応答」](agent-kernel-host.md#カーネルモードの制御ソケットの応答)の項の `process` です。

root で実行した `agent doctor` では、`host.privileges` を UNKNOWN とし、理由の符号を `running_as_root` とします (2026-09-23、所有者の決定)。
root はファイルのパーミッションを迂回するので、root が読めたことからは、エージェントを動かす利用者が同じ証拠に届くかどうかは分かりません。
OK を返すと、非 root で動くエージェントに対して前提が崩れていても、報告が健全に見えます。
FAILED にもせず、層 2 にも数えません。
エージェントが root で動く配置では前提が満たされており、この UNKNOWN は想定どおりの結果だからです。
終了コードは他の検査が決め、残りの検査は通常どおり行います。
所見には root が権限を迂回するためにこの実行では答えられないことを述べ、次に見るものとして、エージェントと同じ利用者で実行し直すことを添えます。
同梱の systemd の unit ではその利用者が wgft なので、次の一手として `runuser -u wgft -- wgft agent doctor` を示します (2026-09-23、所有者の決定)。
これは `deploy/agent.service` の `User=wgft` という配布物の事実を挙げるもので、環境を見て推測するものではありません ([11a 節](../security/configuration.md#11a-設定の渡し方))。
独自の配置では、実際にエージェントを動かしている利用者で実行し直します。
root で動くなら想定どおりであることも添えます。
root でも拒まれた対象がある実行は、この扱いに含めず、層 2 の失敗とします。
拒まれたという事実は root の迂回が及ばない範囲で得たものであり、答えられないのではなく届かなかったためです。
カーネルモードのエージェントで `CAP_NET_ADMIN` を見る扱いは、後述の[「カーネルモードのエージェント」](agent-kernel.md#カーネルモードのエージェント)の項で定めます。

#### 証拠の鮮度の違い

エージェントが止まっていても、`agent doctor` の出力の意味は変わりません。
変わるのは、取れる証拠の新鮮さだけです。
止まっている間に読める値は `agent.json` が最後に保存した時点のものであり、今の値ではありません。
この違いは、[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)の状態の語彙でそのまま表せます。
新しい語は加えません。

- 稼働中のプロセスしか持たない項目は、エージェントが止まっている間は SKIPPED とし、理由の符号を `agent_not_running` とします。
  SKIPPED は「試せたはずだが、手前の失敗によって今回は試せなかった」であり、エージェントが動いてさえいれば取れた項目に当たります。
  NOT TESTED はこのコマンドがそもそも試さない項目に使う語なので、稼働中には取れる項目に当てると、同じ項目の状態が実行のたびに NOT TESTED と OK を行き来します。
  UNKNOWN は証拠があって判定に足りない場合の語なので、証拠が 1 つも無い状態には当たりません。
  例外は `relay.allow_targets` の停止中であり、この項目だけは UNKNOWN とします
- `agent.json` から読んだ値は、稼働中でも停止中でも、保存した時点の値です。
  人向けの出力では `agent ls` および [10.2a 節](server-observations.md#102a-転送の診断-server-doctor)と同じ `last:` の接頭辞を付け、今の観測と区別します
- `agent.last_state` が示す、server がこのエージェントを無効にしているという所見も、この鮮度の制約を受けます (実装時に判明)。
  エージェントは、稼働中に全体状態を適用したときだけ `LastState` を書き換えます ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
  無効化と有効化の配信は、接続中のエージェントにしか届きません (前述の「エージェントの無効化と有効化」の項)。
  このため、既に停止しているエージェントを server が無効にしても、または無効なまま停止しているエージェントを server が有効に戻しても、その agent.json は書き換わりません。
  前者では停止中の `agent doctor` は無効であることを示さず、後者では無効の所見を古いまま示し続けます。
  稼働中の `relay.listeners` は、稼働中のプロセスが最後に適用した値を見ます。
  stream がつながっている間は、無効化と有効化がそのまま届きます

停止そのものは FAILED として扱います。
ユーザー空間の中継を持つエージェントは、常駐して転送を担うプロセスであり、止まっている間は 1 バイトも転送しないためです。
無効なルールのような「宣言どおりの停止」は、エージェントには存在しません。
カーネルモードのエージェントは停止中も転送を続けることがあるので、停止の状態は FAILED のまま、総合判定を動かすかどうかだけを変えます (後述の[「カーネルモードのエージェント」](agent-kernel.md#カーネルモードのエージェント)の項)。

#### 検査の一覧と証拠の出どころ

検査は次の表のとおりとします。
「検査の ID」の列が `--json` の値です。
「停止中」の列は、エージェントが止まっている実行でその検査が成立するかどうかを示します。
「総合判定」の列は、その検査が総合判定と終了コード 1 を動かすかどうかを示します。

| 検査の ID | 見出し | 群 | 見るもの | 出どころ | 停止中 | 総合判定 |
|---|---|---|---|---|---|---|
| `host.platform` | platform | Host | OS、アーキテクチャ、wgft の版、メモリのソフト上限の予測 | OS と自分の版 | 成立する | 動かさない |
| `host.privileges` | privileges | Host | 実行している利用者、データディレクトリの読み取りと新規ファイルの作成、`agent.json` の読み取り、設定ファイルの読み取り | OS | 成立する | 動かさない |
| `host.interfaces` | interfaces | Host | このホストのネットワークインタフェースとアドレス | OS | 成立する | 動かさない |
| `host.resolve` | endpoint resolve | Host | `Endpoint` のホスト名の解決 | このホストの resolver | 成立する | 動かさない |
| `agent.credentials` | credentials | Credentials | `agent.json` の読み取り、そのパーミッション、登録の有無、`Endpoint`、`CertSHA256`、`UsedJoinTokenSHA256` | `agent.json` | 成立する | 動かす |
| `agent.process` | process | Credentials | 稼働中かどうか | `agent.json.lock` の flock | 成立する | 動かす。カーネルモードでは動かさない |
| `agent.last_state` | last state | Credentials | 最後に処理した全体状態の世代、wg 設定、ルールの本数、server がこのエージェントを無効にしているかどうか | `agent.json` の `LastState` | 成立する | 動かさない |
| `agent.control` | control socket | Connection | 稼働中のエージェントの制御ソケットに接続できるか | `agent.json.sock` | 成立しない | 動かさない |

| `tunnel.resolve` | wg endpoint resolve | Tunnel | WireGuard のピアの宛先 (`proto.WGConfig.Endpoint`) のホスト名の解決 | `agent.json` の `LastState` | 成立する | 動かさない |

| `relay.allow_targets` | target allowlist | Relay | 宛先の許可一覧の有無と内容 | 制御ソケット | 成立しない | 動かさない |

| `host.forwarding` | forwarding | Dataplane | `ip_forward`、他のテーブルの forward の既定の落とし、`rp_filter` | 稼働中は制御ソケット、停止中は OS とカーネル | 成立する | カーネルモードで動かす |

`agent.credentials` という `id` は、[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)が既に使っている同名の `id` と衝突します。
別のコマンドの別の模型に属するため規約には違反しませんが、`checks[].id` だけを読む運用者やスクリプトにとっては、同じ文字列が 2 つの意味を持ちます。

`tunnel.resolve` を `host.resolve` とは別の検査として立てます (2026-09-23、所有者の決定)。
`host.resolve` が解決するのはエージェント用 API の宛先で、この検査が解決するのは WireGuard のピアの宛先です。
用途も障害の意味も違います。
`LastState` から停止中にも証拠が取れるので、エージェントのホストでしか分からない事実という範囲に収まります。

`agent.json` の場所は、`rotate-key` ([9 節](../state.md#9-状態の保存と再起動)) と同じ経路、つまり `WGFT_DATA_DIR`、`--data-dir`、`agent.env` で決めます。

どれも与えずに既定のデータディレクトリを見た実行は、エージェントが `--data-dir` か `WGFT_DATA_DIR` で別のディレクトリを使う配置では、エージェントの居ない場所について答えます (2026-09-25、所有者の決定)。
この実行が既定のディレクトリに登録済みの `agent.json` を見つけられなかった場合、`agent.credentials` と `agent.process` の所見は、ホストが未登録であるとも、エージェントが止まっているとも断定しません。
見たディレクトリについて述べ、次の一手の先頭で、エージェントが別のデータディレクトリで動いているなら同じ `--data-dir` で打ち直すよう案内します。
新しい招待の発行と起動の案内はその後に置きます。
新しい招待を先に案内すると、別のディレクトリで動いているエージェントと同じ名前の登録が拒まれ、その先で案内される `wgft agent revoke` は動いているエージェントを切るためです。
`host.privileges` がデータディレクトリの権限の不足を示す場合も、既定のディレクトリを見た実行では同じ案内を、同じ利用者で打ち直す案内より先に置きます。
エージェントを動かす利用者で打っていても、既定のディレクトリはその利用者を拒むことがあるためです。
終了の 1 行にも同じ句を添えます。
ディレクトリを明示した実行でも、見たディレクトリを示して取り違えを先に疑います。
登録済みの `agent.json` が見つかった実行は、そのディレクトリがエージェントのものなので疑いません。

理由の符号は状態と 1 対 1 ではありません。
`agent_not_running` は、`relay.allow_targets` の停止中では UNKNOWN に付き、他の稼働中専用の検査の停止中では SKIPPED に付きます。

#### 示す値の定め方

いくつかの検査は、実装の足場を調べた結果を受けて、示す値そのものを定めました (2026-09-23)。

- `host.platform` のメモリのソフト上限: 今の設定から計算し直した予測を示します。
  `debug.SetMemoryLimit` は自分のプロセスに対する設定であり、稼働中のエージェントが最後に適用した値を外から読む手段がありません。
  `agent.json` 由来の値に付く `last:` とも性質が違うので、予測であることを所見の文で述べます。
  `GOMEMLIMIT` が設定されている配置では、`cmd/wgft/limits.go` の `applyMemoryLimit` が `debug.SetMemoryLimit` を呼ばずランタイムに任せるので、フロー数の上限から計算した値は当たりません。
  その場合は計算した値ではなく `GOMEMLIMIT` の設定を示します。
  設定ファイルを権限で読めない実行では、数を示さず、示せない理由を述べます (2026-09-23、所有者の決定)。
  予測が当たるのは、エージェントが読むのと同じ設定を同じ経路で読めた場合だけです。
  既定値から計算した数を示すと、上限を絞った配置で事実でない数を述べることになります。
  状態は UNKNOWN とします
- `tunnel.local` の最終ハンドシェイク: 今の device から読んだ値だけを示します。
  watchdog が別に持つ値はトンネルを閉じるときに消えず、立て直した直後は前のトンネルの値が残ります。
  同じ応答に 2 つを混ぜません。
  今の device から読む値は、device が今持つ鍵で成立したハンドシェイクだけです。
  ユーザー空間モードは鍵を変えるたびに device を作り直します。
  カーネルモードの wgft0 は鍵を変えても残りますが、鍵を変える収束が server のピアを置き直すので、前の鍵のハンドシェイクは読めません ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止)の鍵の変更と最終ハンドシェイク)
- `tunnel.watchdog` の残り時間: 示しません。
  次の作り直しまでの残りは保持されておらず、示すには起点を求める規則を診断の側に写すことになります。
  写した規則が本体と食い違えば、診断が事実でないことを述べます。
  作り直しの間隔は、`internal/agent/watchdog.go` の `rebuildState.step` が判定に使う実効値を示します。
  実効値は保持している値と既定値の大きい方であり、既定値を下回りません。
  保持している値そのものは、ゼロでない最終ハンドシェイクを一度も観測しておらず作り直しも一度も起きていないトンネルでは 0 のままですが、その場合も watchdog は既定値で動きます。
  実効値を示せば、示さない場合を設けずに済みます
- `relay.listeners` の開けているかどうか: 実装は、開けているかどうかを表す項目をリスナーの状態に追加します。
  今の状態は bind の失敗を宛先の失敗より優先して 1 つの誤りとして返すので、2 つを区別できません。
  bind の失敗はポートの衝突を、宛先の失敗は自宅の機器を指し、運用者の次の行動が違います。
  項目を加えるだけの変更で、この型を共有する vpsd のユーザー空間モードにも同じ項目が加わります
- `relay.sessions` の接続の数: フロー予算の上限の対象である公開側の接続の数を示します。
  今のセッション数は TCP では公開側と宛先側の両方を数えるため上限の対象と一致せず、上限の対象の数はどこにも公開されていません
- `relay.refusals` の累計: 今のトンネルを作ってからの累計とします。
  フロー予算はトンネルを立て直すたびに作り直され、拒否の累計はそのたびに 0 に戻ります。
  立て直しは wg 設定の変更、watchdog による作り直し、構築に失敗した後の試し直し、`rotate-key` で起きます。
  doctor は、今のトンネルを作った時刻を累計と並べて示します。
  フロー予算をトンネルの外へ移して累計を連続させる案は採りません。
  中継の停止が未返却のフローを返さないので、共有すると、立て直しで取り残されるフローが出ることがあります

#### 判定できない場合と、手前の失敗で試せない場合

副作用なしには判定できない検査は、成功でも失敗でもない UNKNOWN とし、判定できない理由を添えます (2026-09-23、所有者の決定)。
Windows の `host.privileges` の「新しいファイルを作れるか」は、`unix.Access` に当たる呼び出しが無く、ACL を読んで判定を自前で組むほかに手段がありません。
[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)が Windows のエージェントを暫定としていた時点で、その判定は組まないことにしました。
Windows だけ黙って OK を返す形にもしません。
Windows 11 の実機では、この項目が理由 `permission_not_determined` の UNKNOWN になり、終了コードを上げないことを確かめました ([以前の検証 2026-09-27](https://github.com/rahanahu/wgft/blob/c5a6dc454468733e9ff4b2a4eb2b5a17ed4bdf4e/docs/design.md#L2795))。
`LastState` が無い場合の `tunnel.resolve` も同じ扱いとし、`agent.json` が全体状態を持たない事実を理由の符号 `no_last_state` で示します。
停止中の `rotate-key` も全体状態を消すので、一度も受け取っていないとは限りません。

`agent.json` が無い場合、権限で読めない場合、読めるが壊れている場合、データディレクトリを権限で辿れず有無を判定できない場合のいずれでも、その中身に依存する検査は SKIPPED とします (2026-09-23、所有者の決定)。
このうち最後の場合は、2026-09-25 に追加しました。
対象は、`Endpoint` を読む `host.resolve`、`agent.json` 全体を読む `agent.last_state`、`LastState` を読む `tunnel.resolve` です。
試せたはずだが `agent.credentials` の失敗という手前の失敗によって今回は試せなかった項目であり、SKIPPED の定義に沿います。
`agent.credentials` 自体の状態と終了コードは原因によって違いますが (後述の[「終了コード」](agent-output.md#終了コード)の項)、手前の失敗によって試せなかったことは変わりません。
`agent.process` がロックファイルを権限で開けず稼働中かどうかを判定できない場合も、同じ考え方に揃えます。
稼働中でなければ成立しない検査は SKIPPED とし、`relay.allow_targets` は停止中の扱いと同じく UNKNOWN とします。
理由の符号は、`agent.process` と同じ `lock_unreadable` とします。

エージェントが止まっている実行の `agent.control` も、同じく SKIPPED とし、理由の符号を `agent_not_running` とします (2026-09-23、所有者の決定)。
`checks[]` から項目ごと落とす案は採りません。
実行の状態によって `--json` の項目そのものが消えると、機械が処理しにくくなるためです。

#### 宛先の許可一覧の扱い

`relay.allow_targets` は、停止中は値を示さず、状態を UNKNOWN、理由の符号を `agent_not_running` とします (2026-09-23、所有者の決定)。
`agent.env` と CLI 自身の環境変数から `WGFT_AGENT_ALLOW_TARGETS` を組み立て、次の起動で使われる値として示す案は採りません。
組み立てた値を次に起動するエージェントが実際に読むとは保証できず、診断は分からない値を推測で埋めないためです。
稼働中は、常駐プロセスが実際に持っている一覧を制御ソケットから読みます。
稼働中でありながら制御ソケットに接続できない実行では SKIPPED とし、理由の符号を `control_socket_unreachable` とします。

稼働を判定できない実行の `relay.allow_targets` も UNKNOWN としますが、所見と次の一手は停止中のものと分けます (2026-09-23、所有者の決定、実機での確認を受けた追加)。
同じ報告の `agent.process` が判定できなかったと述べている横で、この検査だけがエージェントは動いていないと述べると、稼働中のエージェントについて事実でないことを述べることになります。

この停止中の UNKNOWN は、「証拠の鮮度の違い」の項が定めた一般則の例外にあたります (2026-09-23、所有者の決定)。
稼働中のプロセスしか持たない他の項目は、止まっていれば証拠が 1 つも無く、SKIPPED が当たります。
宛先の許可一覧は設定の値であり、稼働中かどうかに関わらず、設定の出どころから原理的には読めます。
証拠になりうるものはあるが判定には使えないので、UNKNOWN の定義に当てはまります。

この一覧を検査に入れるのは、内容がエージェントの手元にしか無いためです。
一覧に当たった拒否は `agent_rule_states` の理由として server まで届きますが ([7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧))、一覧そのものは届きません。
一覧の中身を示すことと、一覧に当たったルールを転送不能と判定し直すことは別の行いであり、`agent doctor` が行うのは前者だけです。

#### 能動的に試す範囲

既定は読み取りだけです。
例外は `host.resolve` と `tunnel.resolve` で、どちらもホスト名を実際に解決します。
名前の解決は宛先のサービスへ接続を作らないため、既定に入れてよいとします。
`host.resolve` はエージェント用 API の宛先 (`Endpoint`) を、`tunnel.resolve` は WireGuard のピアの宛先 (`proto.WGConfig.Endpoint`) を解決し、対象が別です。

`agent.json` を読むときは、`credentials.Load` を使いません (2026-09-23)。
`Load` は読み取りに続けて Windows の DACL を毎回書き直します。
これは緩い権限のファイルを起動時に締め直すための意図した挙動であり ([11a 節](../security/configuration.md#11a-設定の渡し方))、`credentials` の側は変えません。
診断が副作用を持たないという本項の約束を保つため、doctor は締め直しを伴わない読み取りの経路を使います。

`tunnel.resolve` は、[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)が「切り分けられない所見」として残した、最終ハンドシェイクが無い原因のうち、名前解決そのものの失敗を切り分けます。
[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)が挙げる原因のうち、VPS の WireGuard の UDP ポートが届かないこと、自宅のファイアウォールまたは ISP がトンネルの UDP を落としていること、その間の何かが落としていることは、名前解決が成功した後の経路を扱っています。
残る 1 つ、エージェントが動いていないか別の鍵を持っていることは、経路ではなくエージェント自身の状態を指します。

LAN の宛先への試し接続は行いません。
エージェントの中継が、リスナーを開いたときの試し接続 ([7 節](../agent-dataplane.md#7-データプレーン自宅側)の `checkTarget`) と、[5.2 節](../control/connection.md#52-全体状態の配信とハートビート)が定める 30 秒ごとの再試行 (`internal/dataplane/userspace/relay` の `Manager.Retry`) で既に試しており、`agent doctor` はその結果を `relay.listeners` から読むだけで足りるためです。
`checkTarget` は TCP の `target` への試し接続であり、UDP は到達確認ができないため呼ばれません ([7 節](../agent-dataplane.md#7-データプレーン自宅側))。
したがって UDP のルールについては、`relay.listeners` に宛先の到達性の証拠がありません。
エージェントが止まっている実行では、宛先への接続を確かめる手段を持ちません。
停止中にも宛先を試す形を加えるかどうかは、手元で読める値で足りるかが分かってから決めます。
