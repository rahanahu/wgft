#### 制御ソケットの拡張

稼働中のエージェントから制御ソケットで診断の証拠を取得します。
古いプロセスの未対応と、排他を取れない応答を区別します。


制御ソケットに `doctor` を加えます。
既にあるのは `rotate-key` だけである ([9 節](../state.md#9-状態の保存と再起動)、`internal/agent/control`)。

要求は今までどおり行ベースとし、`doctor` の 1 行を送る。
応答の形式はコマンドごとに定める。
`rotate-key` は今までどおり `ok <公開鍵>` の 1 行のテキストを返し、`doctor` は 1 つの JSON オブジェクトに改行を 1 つ付けたものを返す (2026-09-23、所有者の決定)。

**制御ソケットのプロトコル全体が JSON になったのではない。**
`doctor` の応答だけが JSON です。
ソケット全体の framing を変えると、`doctor` を加えるために既にある `rotate-key` の経路まで巻き込むことになります。
`doctor` の応答を 1 行に収めておけば、今の行ベースの読み書きをほぼそのまま保てる。
JSON は複数行にせず、pretty-print もしません。
人が直接読む経路ではないためです。
概念的には次の形になります。

```
doctor\n
{"status":"ok",...}\n
```

`\n` は改行を表します。
上の 2 行は、要求が 1 行のテキストであり、応答が 1 行の JSON であることを示すだけの図であって、実際のフィールドの一覧ではありません。

運用者が読む `agent doctor --json` の出力と、ソケットの上を流れる JSON は別のものです。
前者は「出力の形」の項が定めた、[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)に揃えた模型であり、後者はその材料にすぎない。
両者が同じ Go の型かどうかは実装の判断とし、この節では決めない。

応答を組む処理には `recover` を置く (2026-09-23)。
今の制御ソケットの受け口は `recover` を持たず、応答を組む処理が panic すると常駐プロセスごと落ちる。
`rotate-key` が触る値は少ないが、`doctor` は多くの値を触る。
診断のために転送を止めません。

加算で足りるのは、制御ソケットが 1 つのホストの中で閉じており、外部の実装がこの経路を使わないためです。
`wgft agent doctor` が繋ぐ先は、同じホストで動く `wgft agent run` であり、どちらも同じ実行ファイルです。
版が食い違いうるのは、新しいバイナリを置いてから常駐プロセスを再起動するまでの間だけです。
その間に新しい CLI が `doctor` を送ると、古い常駐プロセスは既にある既定の分岐で `error: unknown command` を返します。
CLI はこれを、稼働中の診断が取れない場合として扱い、静的な検査だけを示します。
新しいコマンドの追加に、版の交渉も capability も要りません。

この場合、`agent.control` は UNKNOWN とする (2026-09-23、所有者の決定)。
接続そのものは成功しているので SKIPPED には当たらず、FAILED にすると転送が健全な配置に対しても壊れている印象を与える。
所見には、稼働しているエージェントが `doctor` に対応していないことと、新しい実行ファイルでエージェントを起動し直すことを添える。
総合判定は動かさず、終了コード 2 の層にも入れません。
古い常駐プロセスは接続できないのではなく `doctor` という機能に対応していないだけなので、権限の問題ではありません。
稼働中のプロセスからしか取れない検査は SKIPPED とし、理由の符号を `agent.control` と同じ `doctor_unsupported` とします。
`control_socket_unreachable` は接続そのものができない場合の符号であり、この場合を押し込む符号ではありません。
終了コードは 0 のままとします。

[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の互換性の保証に、この経路が含まれるかどうかを確かめた。**含まれない。** [7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)が列挙するサーフェスのうち、「agent-server の wire protocol」が拘束するのは stream の上を流れるメッセージであり、同じホストの中の Unix ソケットではない。「エージェントの認証情報ファイル」が保つのは置き場所とファイル名であり、隣のソケットの上を流れる形を扱わない。保証の対象外であることは、壊してよいという意味ではなく、版をまたいで固定する約束を負わないという意味である。

`doctor` の応答のトンネルの項目には、今のトンネルを立てた直後に測った WireGuard の UDP ソケットのバッファ `socket_buffers` を加えた (2026-09-27)。
旧い CLI は知らないフィールドを読み飛ばすので、この追加も加算で足りる。
新しい CLI は、このフィールドを持たない応答を、旧い常駐プロセスの応答として扱う。

同じトンネルの項目に、netstack の UDP の受信の会計の状態 `udp_accounting` を加えた (2026-09-27)。
会計が止めたかどうかの `stopped` と、止めたときの違反の内容 `error` を持ちます。
追加と旧い版の扱いは `socket_buffers` と同じです。

#### 制御ソケットから実行時の状態を取れない場合

エージェントが稼働中でありながら、制御ソケットに繋げないことがあります。
原因は 3 つあります。

- ソケットのパスが `sun_path` の上限を超えています。
  上限は終端の NUL を除いて Linux と Windows で 107 バイト、macOS で 103 バイトであり、`WGFT_DATA_DIR` が深い場合に超える ([11a 節](../security/configuration.md#11a-設定の渡し方))。
  Go の `net` は上限を超える名前を OS を呼ぶ前に `invalid argument` で拒みます
- エージェントがソケットを開けないまま動いています。
  `internal/agent/control` は、ソケットを開けなかった場合に `rotate-key` の稼働中経路だけを諦めてエージェントを動かし続けます。
  パーミッションを締められなかった場合も同じ扱いになるのは Windows だけです。
  Unix の `credentials.SecureSocket` は chmod の失敗を無視して常に成功を返すため、締め切れなくてもソケットは開いたまま残る
- ファイルのパーミッションで繋げない

どの場合も、`agent.control` を FAILED とし、原因と次に見るものを添える。
`sun_path` の上限に当たる場合は、[11a 節](../security/configuration.md#11a-設定の渡し方)および `rotate-key` と同じ内容、つまりパスのバイト数、上限、短いデータディレクトリを使うという対処を添える。
稼働中のプロセスからしか取れない検査はすべて SKIPPED とし、理由の符号を `agent.control` と同じ符号とします。
符号は、`sun_path` の上限に当たる場合が `control_socket_path_too_long`、他の 2 つの場合が `control_socket_unreachable` である (2026-09-23)。
静的な検査は通常どおり行います。
健全な実行との差は `agent.control` にとどまらず、稼働中のプロセスからしか取れない検査の全体に及ぶ。

終了コードは、3 つの原因のうちファイルのパーミッションで繋げない場合だけ 2 とする (2026-09-23、所有者の決定)。
制御ソケットへ権限の不足で接続できず、総合判定を動かす検査のうち `tunnel.local` と `relay.listeners` まで取れないなら、診断そのものが十分に成立しなかった場合に当たる。
一方、`sun_path` の超過とソケットの未作成まで 2 にすると、エージェントは正常に転送しているのに診断の経路の都合だけで常に 2 になる配置を作れる。
その 2 つは、終了コードを動かさない `agent.control` 自体の問題として所見にとどめるほうが、制御ソケットの障害は転送の障害ではないというこれまでの設計と一致します。
診断が取れていないことは、出力の側で見落とせない形にします。

制御ソケットには繋げても、実行時の状態を取れない実行があります。
`internal/agent` は実行時の状態を 1 つの排他で守っており、30 秒ごとの定期処理がその排他を取ったまま宛先への試し接続を一巡させる。
応答を返さない宛先が多い配置では、一巡の長さが制御ソケットの期限に届きうる。
`agent doctor` はトラブルの最中に繰り返し使うコマンドなので、その状況でこそ応答しなくなる。

`agent doctor` は、この排他を期限付きで待ち、取れなければ実行時の状態を取得できなかったという事実を返す (2026-09-23、所有者の決定)。
黙って待ちません。
運用者には、エージェントは生きているが内部の処理で詰まっていることが分かる。
稼働中のプロセスからしか取れない検査は SKIPPED とし、理由の符号は `runtime_state_busy` とします。
所見には、内部の処理が詰まっていることと、次に見るものを添える。
静的な検査は実行時の排他を要らないので、通常どおり行います。
終了コードは 0 のままとします。
証拠に権限で到達できなかった実行ではないためです。

この実行の `agent.control` は OK とする (2026-09-23)。
制御ソケットに繋げて `doctor` の応答も得ているので、この検査が答える「制御ソケットに繋げるか」は満たされています。
古い常駐プロセスが `doctor` に対応していない実行を UNKNOWN とするのとは扱いが違う。
あちらは診断の応答そのものを得られないが、この実行では応答を得たうえで実行時の部分だけが欠ける。
欠けたことは、続く検査の SKIPPED とその所見が述べる。
