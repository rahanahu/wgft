#### `agent.connection` が測るもの

制御の経路の劣化と、転送の経路の失敗を区別します。
エージェントのホストや外からの到達性には、server だけでは切り分けられない所見が残ります。


`agent.connection` は、制御の経路の健全さと、新しい設定を配れるかどうかを測ります。
転送が止まった位置を測るのではありません。
両者は普段は一致しますが、1 つの状態だけで食い違います。
stream が切れていて、なお最終ハンドシェイクが新しい状態です。
エージェントは受け取り済みのルールを保持したまま転送を続けられる一方、新しいルールだけが届きません ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)、[7 節](../agent-dataplane.md#7-データプレーン自宅側))。

この状態を FAILED にすると、`agent.connection` は `rule.probe` より経路の順で前にあるので、疎通確認が実際にトンネルとエージェントを通って `target` まで届いた場合でも、「転送はここで止まった」と報告してしまいます。
同じ所見の文が「転送は続いている」と述べながら止まった位置を主張する、自己矛盾した報告になります。

したがって `ai.Connected` が偽のときを次のように分けます。

- 最終ハンドシェイクが新しい (`tunnel.handshake` の閾値の内側): UNKNOWN とします。
  理由の符号は `agent_disconnected` のままとします。
  stream が切れていること自体は確かであり、確かでないのはそれがこのルールの転送に与える結果だからです。
  所見は両方を述べます。
  制御の経路が切れていること、トンネルは生きていること、受け取り済みのルールは転送を続けているかもしれないこと、新しいルールは届いていないことです
- 最終ハンドシェイクが新しくない: FAILED のままとします。
  この場合は `tunnel.handshake` も FAILED であり、経路の順でそちらが先に来るので、ルールはトンネルで止まります。
  止まった位置としては、それが正しい結果です
- そのエージェントが登録されていない: FAILED のままとします。
  `tunnel.handshake` は SKIPPED になるので、`agent.connection` が最初の失敗になるのが正しい結果です
- 直近に鍵の変更の上限で宣言を断り、その後にそのエージェントの公開鍵の宣言を受け付けておらず、その記録が試みを続けるエージェントのものと読める: 理由の符号を `key_change_limited` とします (2026-10-02、所有者の決定)。
  記録が試みを続けるエージェントのものと読めるのは、管理用 API の `key_change_refused_at` が、1 回分の戻る間隔とエージェントの再接続の待ちの上限の和より新しい場合です ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
  状態は最初の 2 項と同じく、最終ハンドシェイクが新しければ UNKNOWN、新しくなければ FAILED とします。
  所見は、断った時刻と、その後に公開鍵の宣言を受け付けていないことを述べます。
  今も断り続けているとは述べません。
  受け取り済みのルールが転送を続けているかもしれないとも述べません。
  断った鍵はこの VPS の WireGuard のピアに入っていないので、稼働中の `rotate-key` のようにその鍵へ替えたエージェントは、鍵が通るまで転送できないためです。
  最終ハンドシェイクが新しくても、それはエージェントの前の鍵によるものである可能性があります。
  最終ハンドシェイクが新しい間を FAILED にしないのは、断った宣言が正規のエージェントのものかどうかを server が見分けられないためです。
  恒久トークンを持つ別の者が宣言した場合は、前の鍵のままのエージェントが転送を続けていることがあります。
  次に見るものは、エージェントが同じ鍵で再接続を続け、1 回分が戻った後の試みで鍵が通ること、`rotate-key` を繰り返さないこと、`agent rotate-key --help` の戻し方です
- 前項の記録が、1 回分の戻る間隔とエージェントの再接続の待ちの上限の和より古い: 前項に当たらず、最初の 2 項の判定、理由の符号 `agent_disconnected`、原因と次に見るものをそのまま使います。
  所見には、断った時刻を過去の事実として 1 文だけ添えます。
  記録は直近の拒否の時刻です。
  断られた試みは 1 回分を使わず、試みを続けるエージェントの記録は、試みのたびに新しい拒否で更新されるか、鍵が通って消えます。
  エージェントは 5 分より長くは待たないので、試みを続けるエージェントの記録は、再接続の待ちの上限に 1 回の試みに要する時間を加えた長さより古くなりません。
  閾値に加えた 1 回分の戻る間隔の 10 分は、この判断に必要な長さではなく余裕です。
  閾値より古い記録は、エージェントの試みが鍵の判定まで届いていないことを示します。
  古い記録から今の拒否を述べないためです。
  余裕を持たせた分、断られた後に止まったエージェントについても、拒否から 15 分ほどの間は `server doctor` が `key_change_limited` を示し続けます (2026-10-02、所有者の決定)

`agent.connection` を経路の外の検査にはしません。
本当に停止しているエージェントは、ルールの要約を動かさなければならないためです。
UNKNOWN でも要約は動きます。
ルールは OK ではなく UNKNOWN になり、要約から消えません。
同時に、転送が止まった位置だという主張だけを取り下げます。

この訂正は `agent.credentials` と `rule.flow_budget` と同じ種類ですが、そこに至った理由が違います。
あの 2 つは今の経路をそもそも述べないので、経路の外に置きました。
`agent.connection` は経路を述べており、ただ 1 つの食い違う状態でだけ述べ方を誤っていたので、その状態の判定だけを変えました。

人向けの出力では、この状態を `DEGRADED` と表示します(本節「`DEGRADED` の意味」)。
機械向けの出力は変えず、`status` は `unknown`、`reason` は `agent_disconnected` のままとします。
この検査の見出しは `connected` から `control connection` に改めました。
`connected DEGRADED` は 1 行の中で矛盾して読めるためであり、状態の語ではなく対象の名前を見出しにしました。

この結果として、stream が切れていてトンネルが生きているルールは、総合判定が UNKNOWN になり、終了コードは 0 になります。
転送が止まったことを観測していない以上、監視が警告を出す根拠が無いためです。
この区間は長く続きません。
エージェントが本当に停止していれば最終ハンドシェイクもやがて閾値を越え、`tunnel.handshake` が FAILED になって終了コードは 1 になります。
区間の長さは `tunnel.handshake` の閾値で上から抑えられています。

#### `DEGRADED` の意味

`DEGRADED` は人向けの出力だけで使う語であり、転送の停止とは判定しないが、今の正常な状態から劣化していることは確かめている検査を表します(2026-09-25、所有者の決定)。
劣化そのものは観測しているので、「判定に足りない」と読める `UNKNOWN` より、人には正確に伝わります。
終了コードが 0 であっても、出力はこの劣化を省かずに示します。
転送の停止は観測していないので FAILED にはせず、機械向けの `status` は `unknown` のままとし、状態は 5 つから増やしません。
ルールの総合判定は UNKNOWN、終了コードは 0 です。

今この意味に当たる検査の例は次のとおりです。

- `agent.connection` の `agent_disconnected`:制御の経路は切れていますが、トンネルは生きており、受け取り済みのルールで転送が続いていることがあります(本節「`agent.connection` が測るもの」)
- `agent.connection` の `key_change_limited` のうち、最終ハンドシェイクが新しい場合:制御の経路は切れており、鍵の変更を断った記録が残っています。
  転送が止まったかどうかは、server の証拠からは決まりません(本節「`agent.connection` が測るもの」)
- `rule.target_resolve` の `target_resolve_failed` のうち、直前の解決の結果で転送を続けている場合:名前の解決は失敗していますが、DNAT は直前のアドレスへ向いたまま残っています(本節「検査の一覧と証拠の出どころ」)。
  同じ符号でも、直前の解決の結果を持たない場合は転送の停止を観測しているので FAILED であり、`DEGRADED` ではありません

他の `unknown` は、証拠が古いか判定に足りないだけで劣化を確かめていないので、`UNKNOWN` のまま表示します。
画面の語と JSON の値は、この意味の検査でだけ意図して食い違います。
両方を並べて読む人が片方を誤りと判断しないよう、決定としてここに書き残します。
機械は `status` と `reason` を読み、画面の語は人のためのものです。
[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)のとおり、人向けの表示は保証の対象ではありません。

#### 検査どうしの優先順位

所見が互いに矛盾しないよう、順序と扱いを次のとおり定めます。

- ルールが無効なら、`rule.enabled` を SKIPPED にし、下流の検査もすべて SKIPPED にします
- ルールが有効で、持ち主のエージェントが無効([5.1 節](../control/registration.md#51-登録))なら、`agent.enabled` を SKIPPED にし、理由の符号を `agent_disabled` とし、下流の検査もすべて SKIPPED にします。
  次に見るものは `wgft agent enable` です。
  無効なルールと同じく宣言どおりの状態なので、終了コードは 0 のままとします。
  ルール自身も無効なら、前項の `rule_disabled` を先に示します。
  `rule enable` と `agent enable` のどちらで直すかが違うので、`rule_disabled` を流用しません
- エージェントが登録されていないなら、`agent.connection` を FAILED にし、トンネルとエージェントに属する他の検査を SKIPPED にします。
  `agent.enabled` は、無効の印を持つ登録済みの行が無いので OK とし、既存の検査の結果、ルールの総合判定、終了コードを動かしません。
  この OK は観測に基づきます。
  `agent.enabled` が答えるのは、そのルールを止める無効の印があるかどうかであり、server は無効の印の正本である自分のデータベースを読むので、エージェントが登録済みかどうかに関わらず、そのルールに無効の印が無いことを直接観測しています。
  登録の有無は、この検査ではなく `agent.connection` が判定します。
  `rule.public_port` は FAILED `not_published` のまま、`agent.connection` は FAILED `agent_not_registered` のままです。
  Web UI はこれらのルールを灰色の「エージェント未登録」と示し故障に数えませんが、`server doctor` は次のメジャー版まで今の結果を保ちます。
  この違いは [7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の互換性の保証による意図したものです([5.1 節](../control/registration.md#51-登録))
- エージェントの stream が切れている間は、そのエージェントが報告した値を今の値として扱いません ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))。
  `agent.rules_received` と `rule.target` は UNKNOWN とし、理由の符号を `stale_report` とし、人向けの出力では `agent ls` と同じ `last:` の接頭辞を付けます。
  古い宛先の誤りを今の原因として示しません
- 最終ハンドシェイクは server が WireGuard から直接読む今の値なので、stream が切れていてもトンネルの判定に使います。
  エージェント自身のトンネルの報告は履歴として添えるにとどめます
- stream が切れていてトンネルが生きている間は、`agent.connection` も UNKNOWN とします。
  理由は前項のとおりです
- 「転送は止まった」と読む位置は、経路の順で最初に FAILED になった検査です。
  したがって FAILED は、その検査が転送の停止そのものを観測した場合にだけ使います

#### 切り分けられない所見

VPS の側からは原因を 1 つに決められない所見があります。
決めつけずに、切り分けられない原因を並べ、何をすれば決まるかを示します。
最終ハンドシェイクが無いことには、少なくとも次の原因があります。

- この VPS の WireGuard の UDP ポートがエージェントの回線から届かないこと
- 自宅のファイアウォールまたは ISP がトンネルの UDP を落としていること
- エージェントが動いていないか、別の鍵を持っていること
- その間の何かが落としていること

決めるにはエージェントのホストで確かめる必要があり、出力はそのとおりに示します。

#### 試していない範囲

何も壊れていない実行でも、試していない範囲を必ず出力します。
黙っていると運用者が沈黙を健全と読むためであり、沈黙する診断は無いほうがましです。
次のうち「内側の経路」以外の項目は常に出し、最後の「内側の経路」だけは条件に応じて出します。

- 外から公開ポートへの到達: DNAT は外部からの入力にしか適用されないので、`vpsd` は自分の公開ポートに自分から到達できません ([10.1 節](../interface.md#101-web-ui))。
  見えない原因は、事業者のセキュリティグループ、このホストの input のファイアウォール、ISP、そしてユーザー空間モードでエフェメラルポートの範囲に入った待ち受けポート (docs/manual/setup.md) です。
  別のホストから試すよう示します。
  試し方はプロトコルで分けます (2026-09-25)。
  TCP のポートには `nc -vz` を、UDP のポートには実際のクライアントを示します。
  `nc -u` のような UDP の送信は届いたかどうかを知らせないので、正常な UDP のルールも届かないように見えるためです。
  `rule.public_port` の次の一手も同じ分け方をし、UDP のルールでは、宛先が応答すれば `rule.target` の補足の行に server が見た応答の時刻が出ることを添えます
- UDP の端から端まで: 疎通確認は TCP だけです。
  UDP の送信では成否が分からないため、UDP のルールは静的な信号だけで判定します。
  エージェントがリスナーを開けたと報告している間も、`rule.target` は OK にならず NOT TESTED にとどまります。
  server が見た宛先の応答を補足の行に示しても、状態は変わりません(本節「UDP の応答の観測」)
- MTU とフラグメント: ハンドシェイクが成立し小さなパケットが通るトンネルでも、大きなデータグラムだけが失われることがあります。
  「ときどき動く」と言われる故障がこれに当たります
- 負荷に依存する故障: レート制限、フロー予算、conntrack の表は、ある瞬間の値しか読みません。
  負荷のときだけ達する上限は現れません
- 宛先の先にあるサービス: どの確認も接続して閉じるだけで、プロトコルで対話しません。
  ポートは受け付けるがアプリケーションが拒む場合、満員の場合、別のサービスである場合は、健全に見えます
- 片方向だけのトンネルの故障の最初の 3 分: 受信が止まったトンネルも、最終ハンドシェイクは `tunnel.handshake` の閾値のあいだは新しいままです
- 適用済み State の内容: 世代番号が一致しても、エージェントが server の公開した State と同じ内容を適用したかどうかは UNKNOWN です。
  現在の通信には内容の確認がありません
- エージェントのホストの環境: OS、権限、インタフェース、名前解決は、ハートビートが運ぶ範囲しか見えません。
  自宅側の診断を動かすよう示します
- 内側の経路: `--probe` を付けない実行は何も dial しません。
  この項目が外れるのは、`--probe` を付けた実行と、診断の対象がすべて UDP のルールである実行の 2 つです。
  後者は、UDP のルールが `--probe` を付けても管理用 API に確認そのものを拒まれ、この項目の案内が意味を持たないためであり、同じ一覧の「UDP の端から端まで」が同じ事実を既に述べています。
  1 本でも TCP のルールが混じっていれば、そのルールには `--probe` が意味を持つので出します

さらに、server 自身の観測の古さを常に示します。
エージェントについて読む値はすべてハートビート経由で届くので、最大で 1 周期ぶん古く、転送しているエージェントが切断と表示される区間も実在します。
