#### 履歴

--json の検査 ID と理由は互換性の保証の対象です。
FAILED の有無で 0 と 1 を分け、報告を作れない場合と設定の拒否を別の終了コードにします。


この版は履歴を持ちません。
診断のために保存の仕組みを追加することはしません。
出力はその事実を明示します。

```
History
  when it broke      NOT AVAILABLE
                     this command only evaluates the current state. To find when a rule stopped
                     working, read the server log and the agent's log.
```

他の目的で実際に履歴を保存するようになった場合に限り、「最後に健全だった時刻」と「最初に異常を観測した時刻」へ育てる。

#### 機械向けの出力

`--json` はこの版から持ちます。
出力は人向けの表の写しではなく、診断そのものの模型です。
形は次のとおりです。

```json
{"status":"failed","checked_at":"...","probed":false,
 "checks":[{"id":"agent.connection","status":"ok","observed_at":"..."},
           {"id":"rule.target","rule_id":"r_01J...","status":"failed","reason":"connection_refused"}],
 "rules":[...],"history":{...},"not_tested":[...]}
```

検査の `id` と `reason` の値は、公開した時点で機械向けの保証になります。
[7a.11 節](../compatibility.md#7a11-v10-の互換性の保証サーフェスごとの一覧)の規則に従い、開いた集合として扱う。
項目を増やすことだけができ、既存の `id` の名前の変更も意味の変更も互換ではありません。
読み手は知らない `id` を読み飛ばし、知らない `reason` を「不明」として扱わなければなりません。
v1 が定める `id` は前掲の表のとおりです。
`status` の 5 つの値は本節の表のとおりで、これも増えうる開いた集合とします。
`group`・`label`・`detail`・`next` は人向けの文であり、保証の対象ではありません。

#### 終了コード

このコマンドの終了コードは次のとおりです。

| コード | 意味 |
|---|---|
| 0 | FAILED の検査が 1 つも無い |
| 1 | FAILED の検査が 1 つ以上ある |
| 2 | 報告を作れなかったか、診断に必要な証拠に権限で到達できず完全な判断ができなかった。管理用 API が応答しない、指定したルールが無い、`--from` の値が読めない、引数の数が誤っている、知らないフラグを渡した場合が当たる (2026-09-23、所有者の決定) |
| 3 | 設定の誤り ([11a 節](../security/configuration.md#11a-設定の渡し方)) |

終了コード 2 の意味は `agent doctor` ([10.2c 節](agent-evidence.md#102c-エージェント側の診断-wgft-agent-doctor)) と揃えて広げたが、`server doctor` が読む証拠のほとんどは管理用 API への呼び出しが成功するか失敗するかの二値であり、権限によって証拠に部分的にしか届かない場合を今は持ちません。
唯一の例外は `--probe` です。
`c.CheckConnectivity` の誤りは `unavailable` に包まず `probeResult` へ畳み込み、報告そのものは出す (`cmd/wgft/doctor.go`)。
この経路でも権限の事例は作らないので、この改訂で挙動は変わりません。

UNKNOWN と NOT TESTED だけでは 0 のままとします。
外からの到達性を決して試さない以上、これらを非零にすると監視が鳴り続けるためです。
この規則は終了コード 2 にも及ぶ。
UNKNOWN と NOT TESTED がいくつ並んでも終了コードは 0 のままであり、終了コード 2 は証拠そのものに権限で到達できなかった実行に限る。

終了コードが答える問いを 1 つに保つため、次を規則として定める。

> 制御の経路の故障だけでは `server doctor` を失敗にしません。
今の転送の経路が健全だと確かめられている限り、制御の経路の故障は運用上の劣化であり、転送の故障ではありません。
劣化は状態とエージェントのサーフェスが報告します。

この規則を置く理由は、終了コードに 2 つの意味を混ぜないことにあります。
終了コードが「転送が止まった」と「管理の経路が壊れた」の両方を指すようになると、それを見ている側はどちらが起きたのかを区別できません。
責任は次のように分ける。

- `server doctor`: このルールの転送の経路が壊れているかどうかに答える
- `wgft status`: 配置全体の運用の状態が健全かどうかに答える。
  制御の経路が切れている状態は、そこでは配置全体の劣化として終了コードを動かす。
  この関係を [10.2b 節](../status.md#102b-状態の要約wgft-status)が実装として定める
- `wgft agent ls`: エージェント 1 台ごとの詳細を担う

引数の数の誤りとフラグの誤りも 2 で終わる。
どちらも診断そのものを始められなかった失敗であり、「壊れた検査があった」の 1 と混ぜると監視から見分けが付かなくなるためです。
包む場所は 2 か所あります。
引数の数は引数を検査する関数が、フラグはフラグの誤りを扱う関数が包む。
フラグの解析は引数の検査より前に行われるので、片方だけでは入口の違いで終了コードが分かれる。

[11b 節](../security/startup.md#11b-起動の失敗の意味論)との関係を明示する。[11b 節](../security/startup.md#11b-起動の失敗の意味論)が定めるのは、監督するプロセスに起動の失敗を伝える意味論であり、終了コード 3 だけが起動の拒否に対応する。`server doctor` は常駐しないので、0 と 1 と 2 は起動の失敗とは別の層の値である。実装では、起動の拒否を表す `*startup.Refusal` に加えて、報告を作れなかったことを表す型を 1 つだけ持ち、`cmd/wgft` の `exitCode` はこの 2 つの型の有無だけを見る。新しい失敗を足すときの写し忘れを防ぐ [11b 節](../security/startup.md#11b-起動の失敗の意味論)の考え方は変えない。
