#### カーネルモードのエージェント

kernel モードでは、プロセスが停止していても残った転送面を検査します。
実際に読めたインタフェースと転送設定に基づいて総合判定を決めます。


カーネルモードのエージェント ([7b 節](../agent-kernel.md#7b-データプレーン自宅側カーネルモード)) の診断も、ユーザー空間モードと同じ問いに答える (2026-09-24、所有者の決定)。
終了コード 1 は「このホストのエージェントが、今の状態では転送を担えない」を意味します。
カーネルモードで転送を担うのは、エージェントのプロセスではなく、カーネルの wgft0、`table inet wgft_agent`、ホストの転送の設定です。
そこで、この 3 つを見る検査 `dataplane.interface`、`dataplane.table`、`host.forwarding` を加え、群 `Dataplane` にまとめる。
3 つとも総合判定を動かす。
backend 全体の失敗とルール単位の失敗は、[7a.3 節](../architecture/lifecycle.md#7a3-状態遷移と失敗の意味論)のとおり分けて扱い、混ぜない。

`agent doctor` はエージェントのモードを、稼働中のエージェントが制御ソケットで答えた `mode` から知り、その答えが無い実行では状態ファイル `agent.json` の記録から知る。
記録は、エージェントが止まっていても読めるためです。
`agent.json` を読めない実行ではモードが分からないので、3 つの検査を `agent.credentials` の符号を持つ SKIPPED とし、既存の検査は今までどおりに並べる。
ユーザー空間モードの実行では、3 つの検査を NOT TESTED とし、理由の符号を `userspace_mode` とします。

カーネルモードの実行では、`relay.listeners`、`relay.sessions`、`relay.refusals`、`tunnel.watchdog`、`tunnel.socket_buffers`、`tunnel.udp_accounting` を NOT TESTED とし、理由の符号を `kernel_mode` とします。
カーネルモードはリスナーも、中継の接続とそのフロー予算も、トンネルの作り直しも、プロセスの中の WireGuard のソケットと netstack も持たない ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))。
エージェントが止まっていても、この扱いは変わりません。
`relay.listeners` を生かさないのは、存在しないリスナーについて答えないためであり、カーネルモードで問うべきは、nftables の dataplane がそのルールを公開しているかどうかです。
`relay.allow_targets` は NOT TESTED にしない (2026-09-24、所有者の決定)。
カーネルモードでも宛先の許可一覧を読んで守らせ、一覧の外には DNAT を作らない ([7b.2 節](../kernel-agent/targets.md#7b2-宛先の扱い)) ので、この検査の意味はユーザー空間モードと同じです。
読めない場合の状態と符号も、「宛先の許可一覧の扱い」の項と「制御ソケットから実行時の状態を取れない場合」の項のとおりとし、総合判定は動かさない。
一覧に実際に拒まれたルールは、`dataplane.table` の FAILED として現れる。

`tunnel.local` と `tunnel.transfer` は、カーネルモードでも残します。
`tunnel.local` は、ユーザー空間モードと同じくハートビートのトンネルの状態をそのまま判定します。
カーネルモードのハートビートは、この状態を wgft0 の読み出しから組み立てる。
`tunnel.transfer` は wgft0 のピアの送受信バイト数を示します。
カーネルはこの数を wgft0 を作ったときから数え、エージェントの再起動では 0 に戻さないので、所見は数え始めた時刻を示さない。

#### カーネルモードの総合判定

`agent.process` の停止は、カーネルモードでも FAILED のままとする (2026-09-24、所有者の決定)。
設定の更新、名前の引き直し、外からの変更への収束が止まるので、運用者の手当てが要る状態であることは変わりません。
ただしカーネルモードでは、この FAILED だけで総合判定と終了コード 1 を決めない。
停止中も wgft0 とテーブルが残っていれば転送は続くためである ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))。
所見には、カーネルの転送は続いている可能性があること、設定の更新と名前の引き直しと外からの変更への収束は止まっていること、転送の実体は `Dataplane` の群の検査が答えることを添える。

3 つの検査が FAILED にするのは、転送を担えないと確かに言える事実だけとします。
それ以外の手掛かりは UNKNOWN の所見として示します。
この分け方で、エージェントが止まっていても、wgft0、公開すべきルールの DNAT を持つテーブル、`ip_forward` が揃っていれば、終了コードは 1 になりません。
逆に、どれかが欠けていれば、エージェントが動いていても終了コードは 1 になります。
server がこのエージェントを無効にしている場合 ([5.1 節](../control/registration.md#51-登録)) は、`relay.listeners` と同じく 3 つの検査を SKIPPED とし、理由の符号を `agent_disabled` とする (2026-09-24、所有者の決定)。
無効かどうかは、稼働中は制御ソケットの答えから、停止中は `LastState` の無効を示すフィールドから知る。

#### カーネルモードの証拠の読み方

カーネルの状態は、エージェントが稼働中なら、エージェント自身が制御ソケットの `doctor` の応答で返す (2026-09-24、所有者の決定)。
エージェントが停止している間だけ、呼び出し元がカーネルを直接読みます。
読む関数は 1 つで、稼働中のエージェントと停止中の診断が同じ関数を使います。
稼働中のエージェントはメモリの上の鍵、全体状態、公開の記録を渡し、停止中の診断は `agent.json` にある同じ値を渡す。
停止中に読む WireGuard インタフェースの名前は、設定の `WGFT_WG_INTERFACE` です。
`runuser -u wgft` で実行した `agent doctor` には ambient の権限が付かず nftables を読めないが、エージェント自身は `CAP_NET_ADMIN` を持つので、同じ実行主体の前提のまま答えられる。
稼働中でありながら制御ソケットから実行時の状態を取れない実行では、直接は読まず、3 つの検査を「制御ソケットから実行時の状態を取れない場合」の項と同じ状態と符号の SKIPPED とします。
稼働を判定できない実行も、同じく SKIPPED `lock_unreadable` とします。

何を読むのに `CAP_NET_ADMIN` が要るかを、ラボで確かめた。
WireGuard インタフェースの鍵とピアの読み出しと、nftables のテーブルとチェーンの読み出しは、`CAP_NET_ADMIN` を持たない呼び出し元では権限の誤りで拒まれた。
リンクの有無、種別、up の印、経路の問い合わせ、`/proc/sys` の `ip_forward` と `rp_filter` は、権限なしで読めた。
root、`runuser -u` で切り替えた利用者、ambient の `CAP_NET_ADMIN` だけを持つ利用者の 3 つで比べ、前の 2 つの読み出しに成功したのは root と `CAP_NET_ADMIN` を持つ利用者だけだった。
エージェントが稼働中か停止中かで、この結果は変わらなかった。

呼び出し元が `CAP_NET_ADMIN` を持たないために直接読めない検査は UNKNOWN とし、理由の符号を `needs_cap_net_admin` とします。
ただし、権限なしで読めた事実だけで FAILED と言える場合は FAILED を示します。
wgft0 が無い、同名のリンクが WireGuard でない、wgft0 が down である、`ip_forward` が 0 である場合がこれに当たる。
総合判定を動かす検査のこの UNKNOWN は、「終了コード」の項の層 2 に入り、終了コード 2 とし、`evidence_unreachable` を `true` にします。
証拠に権限で届かない実行という層 2 の定義そのものに当たるためです。
層 2 に入れなければ、止まったエージェントを同じ利用者で診断した実行が、転送の実体を何も観測しないまま終了コード 0 を返します。
この場合の次の一手は、エージェントを起動すること、または root で実行してカーネルの状態を直接読むことです。
「終了コード」の項は root での実行し直しを案内しないと定めるが、この場合はカーネルモードの例外とします。
root での実行し直しを案内しない規則の理由は、root がファイルのパーミッションを迂回して `host.privileges` が前提の崩れを検出できなくなることです。
`needs_cap_net_admin` の実行で欠けている証拠はファイルではなくカーネルの状態なので、この理由は当たらない。

#### `dataplane.interface` の判定

`dataplane.interface` は、エージェントの WireGuard インタフェースを見る。
宣言は `LastState` の wg 設定であり、稼働中のエージェントはメモリの上の同じ値を使います。
判定は次の順に行います。

- FAILED:wgft0 が無い (`interface_missing`)、同名のリンクが今の鍵か 1 つ前の鍵を持つ WireGuard インタフェースでない (`interface_not_ours`)、wgft0 が down である (`interface_down`)、server の公開鍵を持ち server のトンネルアドレスを AllowedIPs に含むピアが無い (`peer_missing`)。
  どれも、vpsd から届くパケットを wgft0 が受け取れないことを意味します。
  所有の判定は、エージェントの起動時の判定 ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止)) と同じ関数で行います。
  判定はこの並びの順に行い、鍵を読めた実行では、所有の判定を down より先に行います。
  他の所有者の down のインタフェースを `interface_down` として示すと、起動すれば up になると案内することになるが、エージェントはそのインタフェースを他の所有者のものとして起動を拒むためです。
  鍵を読めない実行の down は、権限なしで読めた事実として `interface_down` の FAILED とし、所見に所有を読めなかったことを添え、次の一手は、エージェントが自分の鍵を持つインタフェースなら up に戻し、そうでなければ起動を拒むことと、root での実行を示します
- UNKNOWN `needs_cap_net_admin`:停止中で、呼び出し元が鍵とピアを読めません
- UNKNOWN `no_last_state`:`LastState` が無く、宣言が分かりません
- UNKNOWN `route_not_via_interface`:server のトンネルアドレスへの経路が wgft0 を通らない。
  後述します
- UNKNOWN `interface_differs`:1 つ前の鍵を持つ、アドレス、MTU、keepalive が宣言と違う、余分なピアがあります。
  転送が止まるとは言えないためです。
  稼働中のエージェントは宣言へ戻し ([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止))、停止中は戻らないので、所見はどちらの実行かを示します。
  稼働中の戻し方は変わった点によって違う。
  アドレスと MTU の変更は変更の通知の後の見直しがすぐに戻します。
  鍵、keepalive、ピアの変更は通知が届かないので、30 秒ごとの見直しが戻します
- それ以外は OK とします

最終ハンドシェイク、エンドポイント、送受信バイト数は値として所見に示し、その健全さを判定しません。
ハンドシェイクの判定は [10.2a 節](server-observations.md#102a-転送の診断-server-doctor)の `tunnel.handshake` が持つ (「2 つのコマンドの境目」の項)。
最終ハンドシェイクと送受信バイト数は、wgft0 が今持つ鍵で数えた値です。
鍵を変える収束が server のピアを置き直すためである([7b.4 節](../kernel-agent/lifecycle.md#7b4-収束と停止)の鍵の変更と最終ハンドシェイク)。
鍵の書き換えがまだ済んでいない wgft0 は 1 つ前の鍵を持ち、所見はその値を 1 つ前の鍵のものとして示します。

server のトンネルアドレスへの経路が wgft0 を通らない場合、たとえば Tailscale のポリシールーティングがそのアドレスを別の表へ送る場合は、`dataplane.interface` の明示の所見とし、状態を UNKNOWN とする (2026-09-24)。
経路は、エージェントの 30 秒ごとの見直しと同じく、カーネルに宛先の経路を問い合わせて読む ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの))。
この問い合わせが答えるのはホスト自身が送るパケットの経路であり、ポリシールーティングの規則が入力のインタフェースや印を条件に持てば、LAN から戻る応答を転送する経路はこれと違いうる。
転送を担えないと確かに言える事実ではないので、FAILED にしません。
エージェントが同じ状態で起動を拒まない決定 ([7b.1 節](../kernel-agent/installation.md#7b1-カーネルに置くもの)) とも揃う。
所見は、経路が向かうインタフェースの名前と、その経路では応答が wgft0 を通らず転送が止まりうることを示します。
