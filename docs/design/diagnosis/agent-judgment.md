#### 総合判定を動かす検査

総合判定を動かす検査を限定し、転送を担えない事実と判断できない所見を区別します。


`agent doctor` は、転送の経路を順にたどる形を持ちません。
したがって、[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)の「経路の上の検査と経路の外の検査」の区別と、「最初に FAILED になった検査が転送の止まった位置である」という規則を持ち込まない。
代わりに、総合判定と終了コードを動かす検査を名指しで定める。
前掲の表の「総合判定」の列がその区別です。

動かすのは `agent.credentials`、`agent.process`、`tunnel.local`、`tunnel.udp_accounting`、`relay.listeners` である (2026-09-23、所有者の決定。
`tunnel.udp_accounting` は 2026-09-27 に加えた)。
どれも、失敗がそのまま「このホストのエージェントは今の状態では転送を担えない」を意味します。
カーネルモードのエージェントでは、動かす検査の組が変わる。
`agent.process` は動かさず、`dataplane.interface`、`dataplane.table`、`host.forwarding` が動かす。
`relay.listeners` は NOT TESTED になる (後述の[「カーネルモードのエージェント」](agent-kernel.md#カーネルモードのエージェント)の項)。
どちらのモードでも、`stream.connection` は、直近の試みが鍵の変更の頻度の上限による拒否で終わった場合だけ動かす (2026-10-03、所有者の決定。
後述の[「個別の理由で動かさない検査」](agent-judgment.md#個別の理由で動かさない検査)の項)。

動かさない検査のうち、`host.platform`・`host.interfaces`・`agent.last_state`・`stream.backoff`・`stream.liveness`・`tunnel.watchdog`・`relay.sessions`・`relay.refusals` は、累計か現在値を述べるだけで、エージェントが転送を担えるかどうかを述べないためです。
[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)が経路の外に置いた検査と同じ理由による。
所見としては必ず出し、次に何をするかも添える。
`relay.allow_targets` の理由は前述の[「宛先の許可一覧の扱い」](agent-evidence.md#宛先の許可一覧の扱い)の項で述べた。
残る検査には個別の理由があり、以下の項で述べる。

#### `relay.listeners` の粒度

`relay.listeners` は、判定も所見もルール単位とする (2026-09-23、所有者の決定)。
FAILED になるのは、`heartbeat` が組み立てるルール単位の `proto.RuleStatus` が `error` の場合だけとします。
1 つのルールに属するどれかのリスナーが `error` なら、そのルールの `RuleStatus` が `error` になる ([7 節](../agent-dataplane.md#7-データプレーン自宅側))。
新しい閾値を持たないという方針のとおり、リスナー単位の値から独自の判定を組み立て直すことはしません。

所見にもリスナー 1 つずつを並べない (2026-09-23)。
ポート範囲の幅に上限が無く、`listen_port=1-65535` のルール 1 本で 65535 個のリスナーができます。
制御ソケットの応答にも大きさの上限が無いので、そのまま並べると 1 行が数 MB になります。

server がこのエージェントを無効にしている場合([5.1 節](../control/registration.md#51-登録))、`relay.listeners` は SKIPPED とし、理由の符号を `agent_disabled` とする(2026-09-24、所有者の決定)。
無効を示すための新しい検査は作りません。
無効は宣言どおりの状態であり、SKIPPED は終了コードを動かさない。
所見には、VPS で `wgft agent enable` を実行するまでリスナーを開かないことを添える。
エージェントは、全体状態に加算された無効を示すフィールドから、無効であることを知る。
理由の符号の表への `agent_disabled` の追加は、実装と同時に行います。
表と実装の符号の一致をテストが確かめるためです。

#### `tunnel.local` の判定

`tunnel.local` は、エージェントがハートビートのために計算している状態が `error` の場合に、理由によって FAILED と UNKNOWN を分ける (2026-09-23、所有者の決定)。
基準は、トンネルが無い場合と、トンネルがある場合で違う。

トンネルが無い場合は、理由ごとに定める。
`no tunnel` と `no tunnel; full state not received` は UNKNOWN とします。
前者は `rotate-key` や停止でトンネルを閉じた直後など正常な遷移でも生じる理由であり、後者はトンネルが無く stream にまだ繋がっていない通常の起動直後の状態です。
FAILED にすると、この一過性の状態を故障として扱うことになります。
`no tunnel; building it failed and will be retried` と `no tunnel; building it failed` は FAILED とします。
どちらもトンネルの構築が実際に失敗した事実を指し、前者は試し直しを待っている状態、後者は wg 設定の誤りで構築が終わり次の全体状態を待っている状態です。
UNKNOWN に弱めると、本当に壊れている場合まで見分けが付かなくなる。

トンネルがある場合は、`ts.Err` があることを先に見て、`LastHandshake` が無いことを後に見る。
`heartbeat` の分岐がこの順であり、両方が成り立つ実行の理由は `ts.Err` の側になるためです。
初回の名前解決に失敗したトンネルは、解決済みのエンドポイントを持たないまま `LastHandshake` も無いので、この順序がそのまま効く。
順序を逆にすると、転送に使えるエンドポイントを一度も持たないトンネルが `handshake_pending` の UNKNOWN になり、前段の決定と食い違う。

`ts.Err` がある場合は、その時点で転送に使える解決済みのエンドポイントが残っているかどうかだけで分ける (2026-09-23)。
残っていなければ FAILED、残っていれば UNKNOWN とします。
誤りの種類でも、どの呼び出しが失敗したかでも分けない。
`ts.Err` は印の無い `error` であり、`proto.TunnelStatus` の理由はその文字列なので、`internal/agent` の側に種類を判別する材料がありません。
材料を作るには、トンネルの側に誤りの種類を足すか、`internal/agent` が wireguard-go を import することになり、診断のためにどちらも行いません。
運用者に示す理由は `ts.Err` の文字列をそのまま用いる。
判定に要る解決済みのエンドポイントの有無は、`internal/dataplane/userspace/tunnel` の `Status` が持つ `Endpoint` から今の実装でも分かる。
FAILED と UNKNOWN のどちらについても、理由の符号は「機械向けの出力」の項の表のとおりです。
第 1 段の判別を落とした結果、UNKNOWN の枝には名前解決の失敗以外の誤りも入るので、`resolve_failed` をそのまま当てない。

`LastHandshake` が無い場合は UNKNOWN とし、理由の符号を `handshake_pending` とします。
トンネルを作り直した直後に必ず通る状態であり ([7 節](../agent-dataplane.md#7-データプレーン自宅側))、ハートビートの `error` にそのまま追随させると、`agent doctor` の側に事実上 0 秒のハンドシェイクの制限時間という別の判定が生まれ、[10.2a 節](server-observations.md#102a-転送の診断-server-doctor)が定める 3 分の閾値と二重管理になります。
新しい閾値は持ちません。

#### 個別の理由で動かさない検査

`host.resolve` と `tunnel.resolve` を動かさない側に置く (2026-09-23、所有者の決定)。
名前解決に失敗しても、既に解決済みの IP で接続とトンネルが生きていて転送できる場合があります。
名前解決の失敗は、今後の再接続が危ういという証拠ではあっても、今この瞬間に転送を担えないという証拠ではありません。
解決に失敗した場合、状態は FAILED ではなく UNKNOWN とし、理由の符号を `resolve_failed` とします。

`agent.control` も動かさない側に置く (2026-09-23、所有者の決定)。
制御ソケットに繋げないことは、終了コード 1 が答える問い、つまり「このホストのエージェントが、今の状態では転送を担えない」に対して偽です。
ソケットのパスが `sun_path` の上限を超えていても、エージェントは転送を担い続ける ([11a 節](../security/configuration.md#11a-設定の渡し方))。
動かす側に置くと、転送が健全な配置に対して「担えない」と答えることになり、問いと答えがずれる。
ファイルのパーミッションで繋げない場合の終了コード 2 は、後述の項で別に定める。

`host.privileges` も動かさない側に置く (2026-09-23、所有者の決定)。
エージェント自身の権限の不足と、`agent doctor` を実行した利用者が証拠に届かないことを、この検査だけでは区別できません。
後者を終了コード 1 にしてはいけない以上、診断が成立するかどうかの問題として終了コード 2 の側に寄せるほうが素直です。
稼働中の制御ソケットからエージェントのプロセス自身の権限を取り、判定の材料にする案は採らなかった。
前提を課したうえで呼び出し元の権限をそのまま使う案の方が単純であり、この案はエージェントが止まっている実行では使えず、制御ソケットの応答に権限の情報を足すことにもなる。
カーネルモードの `CAP_NET_ADMIN` だけは、後述の[「カーネルモードのエージェント」](agent-kernel.md#カーネルモードのエージェント)の項がこの案を例外として採る。

`host.privileges` が見る権限を、実装が実際に要求する権限に合わせて絞る (2026-09-23、所有者の決定)。
検査の対象は、データディレクトリを読めること、データディレクトリに新しいファイルを作れること、`agent.json` を読めること、設定ファイルがある場合にそれを読めることとします。
`agent.json` 自体への書き込みの権限は見ません。
`internal/agent/credentials` の `Save` は、一時ファイルを書いてから `rename` で置き換える方式であり ([9 節](../state.md#9-状態の保存と再起動))、`rename` が求めるのは、そのファイルを含むディレクトリへの書き込みの権限だからです。
検査の対象が実装の要求より厳しければ、`agent.json` を 0400 に締めた配置のような正当な構成で終了コード 2 を毎回返すことになります。

設定ファイルを読めることを対象に加えるのは、エージェントが起動のたびに同じファイルを読み、読めなければ起動を拒むためである (2026-09-23、所有者の決定、実機での確認を受けた追加)。
検査の対象が実装の要求より緩ければ、エージェントが起動できない配置に対して `host.privileges` が OK を返します。
ファイルが無い配置は正しいので、無いことは失敗にしません。
読めなかった実行だけを、他の対象と同じ層 2 の失敗として扱う。

`agent doctor` は、設定ファイルを権限で読めない実行でも報告を出す (2026-09-23、所有者の決定、実機での確認を受けた追加)。
設定ファイルを読めないことは診断の結果であり、報告を拒む理由ではありません。
この場合、設定はフラグと環境変数と既定から解決し、ファイルの値を使えなかったことを `host.privileges` の所見に書きます。
`agent run` は同じ場合に起動を拒む形を保つ。
宣言された設定を読めないまま転送を始める常駐プロセスは、運用者が意図した設定で動いていないためです。
設定の値そのものの誤り、つまり構文の誤りと範囲外の値は、この扱いに含めません。
値の誤りは呼び出し元の権限の問題ではなく、他のコマンドと同じ設定の拒否として終了コード 3 で止まります。

`host.privileges` は権限だけを見る検査であり、`agent.json` やデータディレクトリそのものが無いことを失敗にしません。
この検査が失敗しうるのは、権限が足りない場合に限る。
データディレクトリが無い実行では、それを作れる親ディレクトリの権限を見る。
`agent.json` が無い実行では、他の 2 つの対象が満たされている限り OK とします。
不在という事実そのものは `agent.credentials` が答える。
前段でこの検査を終了コード 2 の側に寄せた判断と、後述の[「終了コード」](agent-output.md#終了コード)の項が `agent.json` の不在を終了コード 1 に置く判断は、この検査の失敗がすべて権限に起因するという前提の上に立つ。

`stream.connection` も動かさない側に置く (2026-09-23、所有者の決定)。
制御ストリームが切れていることは、エージェントが受け取り済みのルールを転送し続けている間も起こる ([5.2 節](../control/connection.md#52-全体状態の配信とハートビート)、[7 節](../agent-dataplane.md#7-データプレーン自宅側))。
この状態を配置全体の劣化として数えるかどうかは [10.2b 節](../status.md#102b-状態の要約wgft-status)が定めており、同じ判定を重ねて持つと、切れている間の終了コードが 2 か所で決まることになります。
`agent doctor` が加えるのは、エージェント側だけが持つ事実、つまり直近の切断の理由、直近に待った再接続の間隔、次に試す時刻です。
状態は、つながっていれば OK、切れていれば UNKNOWN とし、理由の符号を `reconnecting` とします。
示す理由には、接続が切れた理由だけでなく、接続に至らなかった試みの失敗も入る (2026-09-23)。
どちらも「今つながっていない理由」を答えるものであり、2 つに分けると `agent doctor` の側で合成することになります。
一方、登録の失敗はこの値に入りません。
登録を呼ぶ経路は観測に書かないので、再登録に失敗しても、観測に残るのは直前の接続の失敗の理由のままです。
再登録に失敗した後に常駐プロセスが止まるかどうかは経路によって違い、止まらずに再接続を続ける経路もあります。

例外は、直近の試みが server の証明書と登録のときに固定したハッシュとの不一致で終わった場合である (2026-09-25、所有者の決定)。
状態を FAILED とし、理由の符号を `server_cert_mismatch` とします。
この場合の切断は、エージェントが待って試し直しても直らない。
server が `server teardown --purge` などで作り直されたか、経路の途中で TLS を終端するものがあるためです。
UNKNOWN のまま「再試行するので問題ではない」と案内すると、直らない状態を待たせることになります。
次の一手は、エージェントのログと同じく、新しい招待で登録し直すことと、作り直していないなら経路を確かめることです。
総合判定と終了コードは動かさない。
終了コード 1 が答える問いは「このホストのエージェントが、今の状態では転送を担えない」であり、制御ストリームが切れている間も、受け取り済みのルールの転送はトンネルが保つ限り続くためです。
TLS を終端するものが経路にある場合は、WireGuard の UDP は別の経路で届きうる。
server を作り直した場合はトンネルも成立しなくなり、転送を担えないことは `tunnel.local` と `relay.listeners`、カーネルモードでは `Dataplane` の群の検査が答える。
状態の語と終了コードは別のものとして扱う (「終了コード」の項)。
このため `--json` では、最上位の `status` が `ok` のまま、`checks[]` にこの FAILED が並ぶ。
`host.privileges` の `agent_lacks_cap_net_admin` と同じ形です。
不一致の判定には、制御ソケットの `doctor` の応答の制御ストリームの観測に加えた `pin_mismatch` を使います。
この値を送らない旧い版のエージェントには、記録された理由の文言で判定します。

直近の試みが鍵の変更の頻度の上限([5.2 節](../control/connection.md#52-全体状態の配信とハートビート))による拒否で終わった場合も、理由の符号を分け、`key_change_limited` とする (2026-10-02、所有者の決定)。
状態は FAILED とし、総合判定を動かす (2026-10-03、所有者の決定)。
`stream.connection` が総合判定を動かすのは、この場合だけです。
2026-10-02 の決定は、状態を UNKNOWN とし、総合判定を動かさなかった。
この拒否は 1 回分が戻った後の再接続で解けるので、再試行で直らない `server_cert_mismatch` と分けたためです。
この扱いでは、エージェントが転送できない間も、`agent doctor` は最上位の `status` を `ok`、終了コードを 0 として返した。
終了コード 1 が答える問いは「このホストのエージェントが、今の状態では転送を担えない」であり、この場合はそれに当たる。
エージェントが宣言するのは自分が今使っている鍵であり、断られた鍵は server の WireGuard のピアに入っていないので、エージェントは後の試みで鍵が通るまで転送できません。
`server_cert_mismatch` について総合判定を動かさない理由に挙げた、受け取り済みのルールの転送がトンネルの保つ限り続くことは、この場合には当たらない。
後の再接続で解けることは、総合判定を動かさない理由になりません。
終了コード 1 は今の状態を答え、直るまでの見込みを答えないためです。

この場合の所見と案内は次のとおりです。
所見は、直近の試みの終わった時刻と理由を示すだけで、今も断られ続けているとは述べない。
`reconnecting` の案内は、受け取り済みのルールは stream が切れている間も転送を続けると述べるが、この場合はそれが当たらないので出さない。
案内は、エージェントが同じ鍵で再接続を続けて 1 回分が戻った後の試みで鍵が通ること、`rotate-key` を繰り返さないこと、`agent rotate-key --help` の戻し方を示します。

判定には、直近の試みの結果だけを使います。
制御ソケットの `doctor` の応答の制御ストリームの観測に加えた `key_change_limited` を使い、エージェントは、close の符号が 1008 で、理由の文言が `vpsd` の上限による拒否の文言と一致するときにこの値を立てる。
この値を送らない旧い版のエージェントには、記録された理由の文言で判定します。
文言は `vpsd` が送るものなので、エージェントの版に依らない。
後の試みで鍵が通れば、`stream.connection` は OK に戻り、総合判定を動かさない。
観測は公開鍵を送り終えた時点から接続をつながっているものとして扱うので、鍵を送ってから server が拒否で閉じるまでの間も OK を示します。
後の試みが上限以外の理由で終わった場合は、`reconnecting` の UNKNOWN に戻り、総合判定を動かさない。
観測が持つのは直近の試みの結果だけであり、その試みが鍵の判定まで届いたとは限らないためです。
この場合、鍵がまだ通っていなくても `agent doctor` はそのことを示さない。
拒否の後に鍵が通ったかどうかを保つ値は、エージェントにも制御ソケットの応答にもありません。
鍵の変更の上限を持たない旧い版の `vpsd` はこの拒否を送らないので、そこにつながるエージェントの判定は変わりません。

`server doctor` の `agent.connection` ([10.2a 節](server-observations.md#102a-転送の診断-server-doctor)) は変えません。
server は、断った宣言が正規のエージェントのものかどうかを見分けられないので、最終ハンドシェイクが新しい間は UNKNOWN とします。
エージェントは自分の試みが断られたことを知っているので、`agent doctor` だけが、この拒否で総合判定を動かす。

server の側では、証明書を拒んだエージェントの接続は、net/http が書く TLS のハンドシェイクの誤りの行 (`remote error: tls: bad certificate`) としてしか残りません。
この行に、証明書を固定したエージェントの拒否として読むことと、新しい招待が要ることを添える (2026-09-25)。
どのエージェントかは示さない。
相手は名乗る前にハンドシェイクを終え、作り直した server のデータベースにはそのエージェントの記録も無いためです。
送信元のアドレスは元の行が既に持ちます。

`tunnel.socket_buffers` も動かさない側に置く (2026-09-27、所有者の決定)。
この検査は、ユーザー空間モードの動作条件である WireGuard の UDP ソケットのバッファ([7 節](../agent-dataplane.md#7-データプレーン自宅側))を、稼働中のエージェントが今のトンネルを立てた直後に測った値と比べる。
条件に届かなければ FAILED とし、理由の符号を `socket_buffer_below_requirement` とします。
所見には測った値と条件の値を、次に見るものには 2 つの sysctl に書く値、コンテナではコンテナのホストで設定すること、エージェントを再起動することを示します。
sysctl に書く値は条件の値の半分なので、Linux が要求の 2 倍を報告することも添える。
7 MiB を設定した運用者が、14 MiB の条件を読み違えないためです。
終了コード 1 は「このホストのエージェントが、今の状態では転送を担えない」と答える。
条件に届かないエージェントも、負荷の軽い間は転送を担う。
この検査を総合判定に加えると、終了コード 1 の意味が「支える条件の外にある」に変わり、更新しただけの既存のホストが終了コード 1 を返し始める。
状態の語と終了コードは別のものとして扱う(「終了コード」の項)。
このため `--json` では、最上位の `status` が `ok` のまま、`checks[]` にこの FAILED が並ぶ。
`host.privileges` の `agent_lacks_cap_net_admin` と同じ形です。

`tunnel.socket_buffers` の他の状態は次のとおりです。
条件を満たせば OK です。
エージェントが止まっていれば、稼働中専用の他の検査と同じく SKIPPED で `agent_not_running` を持ちます。
トンネルが無ければ SKIPPED で `no_tunnel` を持ちます。
カーネルモードのエージェントはプロセスの中に WireGuard のソケットを持たないので、NOT TESTED で `kernel_mode` を持ちます。
Windows と macOS では測らないので、NOT TESTED で `not_measured_on_this_os` を持ちます。
稼働中のエージェントが測れなかった場合は UNKNOWN で `socket_buffers_unreadable` を、値を答えない旧い版のエージェントでは UNKNOWN で `socket_buffers_not_reported` を持ちます。
止まっているエージェントについて、試しのソケットで得る値を予測として示す形は採らない。
試しのソケットの値は呼び出し元の権限で変わり、root で試すと、権限を持たないエージェントについても条件を満たして見えるためです。

`tunnel.udp_accounting` は動かす側に置く (2026-09-27、所有者の決定)。
この扱いは、終了コード 1 の意味、つまり転送が止まっていることの機械的な検出を広げるものではありません。
既存の意味に、新しく検出できるようになった故障の状態を加えるものです。
TCP のルールが転送を続けていても、UDP の dataplane が止まっている以上は正常と判定しません。
`tunnel.socket_buffers` との違いは次のとおりです。
ソケットのバッファの不足は、配置が動作条件を満たしていない状態であり、転送が止まっているとは限らないので終了コード 0 のままです。
会計の停止は、UDP の転送が実際に止まった状態です。
この検査は、netstack の UDP の受信の会計([7 節](../agent-dataplane.md#7-データプレーン自宅側))が不変条件の違反を検出して、トンネルの UDP を止めていないかを見る。
止めていれば FAILED とし、理由の符号を `udp_accounting_stopped` とします。
止まった会計は、プロセスを再起動するまでこのエージェントの UDP のルールをすべて転送しません。
UDP のルールを 1 本でも持つエージェントにとって、これは「今の状態では転送を担えない」に当たる。
`relay.listeners` が 1 本のルールの `error` で FAILED になるのと同じ粒度です。
予算による拒否は、この検査の状態を動かさない。
拒否は資源の逼迫のときの通常の動作であり、ログの行で知らせる ([7 節](../agent-dataplane.md#7-データプレーン自宅側))。
所見には検出した違反の内容と、TCP のルールは転送を続けることを、次に見るものにはエージェントの再起動と、ログを添えた不具合の報告を示します。
止めていなければ OK です。
エージェントが止まっていれば SKIPPED で `agent_not_running` を、トンネルが無ければ SKIPPED で `no_tunnel` を持ちます。
カーネルモードのエージェントはプロセスの中に netstack を持たないので、NOT TESTED で `kernel_mode` を持ちます。
会計の状態を答えない旧い版のエージェントでは、UNKNOWN で `udp_accounting_not_reported` を持ちます。

`tunnel.transfer` は、server から見えないが転送の実際の通り具合を示す値の代表です。
値は所見として必ず出す。
状態は UNKNOWN とし、理由の符号を `no_threshold` とします。
送受信バイト数の多い少ないは、それだけでは健全さを意味しません。
利用者が誰も接続していないトンネルは、何時間も 0 バイトのまま正常です。
値が判定に使えるのは、運用者が「今この瞬間に通っているはずだ」という外の知識を持っている場合だけであり、その知識はコマンドの側にありません。
値は 1 回の実行で 1 回だけ読みます。
2 回読んで差を取れば今の通り具合を言えるが、待ち時間を伴うので、必要になった時点で明示のフラグの下に置く。
