## 7b. データプレーン(自宅側、カーネルモード)

エージェントのカーネルモードは、Linux のエージェントが、カーネルの WireGuard インタフェースと nftables の DNAT で LAN の宛先へ転送するモードである(2026-09-24、所有者の決定)。エージェントのプロセスは制御プレーンとカーネルの設定の収束を担い、パケットを中継しない。このため、エージェントの停止中や更新の間も、カーネルに残した設定で転送が続く。この節は決定と外部から見える面を骨格として定め、内部の作りは各段の実装がこの節に書き加える。

カーネルモードは、ユーザー空間モード(7 節)と同じ「転送できる」「転送できない」の意味を保つ。ルールの `ok` と `error`(5.2 節)、宛先の変更と削除で成立済みのフローが切れるかどうか(7 節の収束の表)、宛先の許可一覧が守る範囲は、モードで変わらない。backend 全体の失敗とルール単位の失敗は 7a.3 節のとおり分けて扱い、混ぜない。

### 7b.1 カーネルに置くもの

エージェントは次の 2 つを自分の資源としてカーネルに置く。

- WireGuard インタフェース:既定名は `wgft0` で、`WGFT_WG_INTERFACE` で変えられる(11a 節)。ピアは VPS の 1 つだけで、AllowedIPs は `vpsd` のトンネルアドレスの /32 である。エンドポイントと keepalive(4 節)を持ち、決まった待ち受けポートは持たない。鍵は認証情報ファイルの鍵を、アドレスと MTU は全体状態の値を使う
- nftables のテーブル:名前は `table inet wgft_agent` に固定する。同じホストに `vpsd` の `table inet wgft` があっても名前は衝突しない。6.1 節と同じく、宣言が変わるたびにテーブル全体を 1 つの netlink のバッチで差し替える

テーブルの形は次のとおりである。`192.168.1.20` と `192.168.1.22` は LAN の宛先の例である。例は行のコメントを省いている。

```
table inet wgft_agent {
  chain filter_pre {
    type filter hook prerouting priority mangle; policy accept;
    iifname "wgft0" ct state established,related accept
    iifname "wgft0" tcp dport 25565 accept
    iifname "wgft0" udp dport 2456-2457 accept
    iifname "wgft0" drop
  }
  chain nat_pre {
    type nat hook prerouting priority dstnat - 1; policy accept;
    iifname "wgft0" tcp dport 25565 dnat ip to 192.168.1.22:25565
    # 範囲のずらしは無名の連結 map で表す(5.3 節の実効宛先)
    iifname "wgft0" udp dport 2456-2457 dnat ip to udp dport map { 2456 : 192.168.1.20 . 2456, 2457 : 192.168.1.20 . 2457 }
  }
  chain input {
    type filter hook input priority filter - 10; policy accept;
    iifname "wgft0" ct status dnat accept
    iifname "wgft0" ct state established,related accept
    iifname "wgft0" drop
  }
  chain forward {
    type filter hook forward priority filter - 10; policy accept;
    iifname "wgft0" tcp flags syn / syn,rst tcp option maxseg size set rt mtu
    oifname "wgft0" tcp flags syn / syn,rst tcp option maxseg size set rt mtu
    iifname "wgft0" oifname "wgft0" drop
    iifname "wgft0" ct status dnat accept
    oifname "wgft0" ct state established,related accept
    iifname "wgft0" drop
    oifname "wgft0" drop
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    iifname "wgft0" oifname != "wgft0" ct status dnat masquerade
  }
}
```

- DNAT:wgft0 から入るパケットを宛先ポートで照合し、実効宛先(7 節)へ書き換える。範囲のルールのずらしは、無名の連結 map でポートごとの宛先アドレスとポートを引く。範囲のルールは、ずれが 0 でも map で書く。DNAT の行はルールごとに 1 行で、(プロトコル、待ち受けポートの先頭、ルール ID)の順に並べ、コメント `wgft:<ルール ID>:dnat` で持ち主を示す。範囲のルールの行は宣言の範囲で照合し、map には許可一覧が通したポートだけを入れる(7b.2 節)。一覧の外のポートのパケットは filter_pre で落ちる。map の要素は、1 通の netlink のメッセージに入れる数を区切って送る。google/nftables v0.3.0 は要素をすべて 1 つの属性に入れ、属性の長さは 16 ビットなので、約 1,800 ポートを超える範囲では長さがあふれる。ラボでは、8,001 ポートの範囲で先頭の 1,857 個だけが黙って入り、60,000 ポートの範囲ではバッチ全体が拒まれて他のルールの公開も止まった。区切って送れば、全幅の範囲(1 から 65535)まで欠けずに入る
- 入口の守り(filter_pre):wgft0 から入る新しい接続のうち、公開した (プロトコル, ポート) の組だけを DNAT の前で通し、残りを落とす(2026-09-24、所有者の決定)。成立済みのフローと、その関連のパケットは通す。通す行はルールの公開したポートの範囲ごとに 1 行で、コメント `wgft:<ルール ID>:pass` で持ち主を示す。チェーンは conntrack の後、DNAT の前の優先度(`mangle`、-150)に置く。VPS の側から触れる面を入口で閉じるためである。この守りは他のテーブルの DNAT にも Docker の実装にも依らず、ct mark や ct label を使わないので他の用途のビットとも衝突しない。これが無いと、エージェントのホストで他のテーブルが全アドレスに公開したポート(Docker の `-p 8080:80` など)に、VPS から wgft0 のアドレスで届く。ラボで確かめた
- MASQUERADE:wgft0 から入って DNAT したフローのうち、wgft0 以外へ出るものだけに掛ける(2026-09-24、所有者の決定)。表を wgft0 の側だけで書くので、エージェントは LAN のインタフェース名を知る必要が無く、そのための設定項目も持たない。LAN のセグメントを複数持つ家でも、出口は経路表が決める。LAN のインタフェースを環境から推測しない(11a 節)。`iifname "wgft0"` の条件が無いと、エージェントのホストで他のテーブルが DNAT したフロー(Docker が公開したポートなど)にも一致し、その宛先のサービスから見た送信元をエージェントのホストのアドレスに変える。転送されるパケットの postrouting では、入力のインタフェースを照合できる。wgft の MASQUERADE が他のプログラムの DNAT のフローに触れる理由は無く、wgft 自身の経路はこの条件でも覆える
- forward:DNAT したフローとその返りだけを通し、wgft0 が絡む残りの転送を落とす。wgft0 が絡まない転送には触れない
- input:wgft0 から入る新規の接続のうち、DNAT していないものを落とす(11 節)。filter_pre の後ろの二重の守りである。エージェントのホスト自身の LAN のアドレスへの DNAT は forward ではなく input を通るので、input は `ct status dnat` のフローを通す(7b.2 節)
- MSS:wgft0 を通る SYN の MSS を、入る向きと出る向きの両方で `rt mtu` にクランプする。カーネルモードは TCP を終端しないので、LAN のサーバと利用者は自分のインタフェースの MTU から MSS を合意し、wgft0 の MTU を超えるセグメントを送りうる。この場合、PMTUD の ICMP を落とすホストが経路に 1 台あるだけで、大きな TCP がその向きで止まる。片方の向きだけをクランプすると、もう片方の向きが止まる。固定の値ではなく `rt mtu` を使うのは、wgft0 の MTU の変更に追従させるためである
- DF の付いた大きな UDP の応答:カーネルモードは UDP も終端しないので、LAN の宛先が DF を付けて返す UDP のデータグラムは、大きさを変えずに wgft0 へ送られる。IP のパケットが wgft0 の MTU を超え、LAN の MTU に収まる応答は、エージェントのホストのカーネルが捨て、宛先へ ICMP fragmentation needed を返す。MTU が 1420 と 1500 なら、ペイロードが約 1393 から 1472 バイトの応答である。宛先がこの ICMP を受けて経路 MTU を学習すれば次の応答から通るが、その大きさの最初の応答は失われる。宛先のホストがこの ICMP を落とす場合は、その大きさの応答が失われ続ける。ユーザー空間モードのエージェントは UDP を終端して中継するので、この影響を受けない。以上をラボで確かめた。client から VPS への向きの同じ現象は 4 節に書いた

テーブルは google/nftables の式で組み、`nft` コマンドを実行しない。6.1 節と同じく 1 つのバッチで送り、7a.3 節の指紋で外からの変更を見つけられるようにするためである。指紋の関数は、server とエージェントで同じものをテーブル名を渡して使う。google/nftables v0.3.0 は MSS の行の `rt` と `byteorder` の式を読み戻せず、誤りを出さずに読み飛ばす。このため指紋はこの 2 つの式を見ない。`nft replace rule` は行の handle を保つので、MSS の行をこの 2 つの式だけが違う行へ差し替えても指紋は変わらない。固定の値への差し替えのように他の式が変わる差し替えは、指紋に表れる。組み立ては `internal/dataplane/linuxkernel` の側に置くので、7a.9 節の import の境界は変わらない。

エージェントは起動のたびに `net.ipv4.ip_forward` を読み、1 でなければ 1 にする。新しい network namespace の初期値は環境によって違い、コンテナの中の値はホストの値を写すことがあるので、初期値を当てにしない。0 から 1 に変えたときは、その事実と日時を状態ファイル `agent.json` に記録し、撤去(10.3 節)で戻す候補として示す。記録は値を書く前に保存する。書いた後に保存すると、その間に落ちたとき、wgft が変えた値の記録が残らないためである。記録を保存できなければ値を書かずに起動を終える。値を書けなかったときは記録を元に戻す。今の値を読めなかったときは、0 だったとは言えないので、1 を書いても記録しない。いったん 1 にした値を自分では 0 に戻さない。値を書く前に記録を保存する点は 6.1 節の `vpsd` と同じだが、違いが 2 つある。`vpsd` は書く前の予定の記録と書いた後の確定の記録の 2 段で、エージェントは書く前の 1 段だけである。`vpsd` は予定の記録を保存できなくても警告して値を書くが、エージェントは記録を保存できなければ値を書かずに起動を終える。書き込みに失敗した場合は、`vpsd` と同じく警告を出して起動を続ける。値を読めず書けもしなかった場合は、1 でないとは言えないので、理由は値が分からないことと、読みの誤りと書きの誤りの両方を示し、「転送しない」ではなく「転送しないかもしれない」と述べる(2026-10-03)。値が分かっていて 1 でない間は、宛先がホスト自身でないルールは転送されないので、それらのルールを `error` として報告する。値が分からない間も、転送されないかもしれないので同じく `error` として報告する。30 秒ごとの読み直しで値が 0 と分かれば、理由を値が 0 と述べる文に置き換える。起動時に書けなかったことが分かっていれば、0 を読んで書けなかった場合と同じ理由にして、その事実を保つ。この `error` は 7b.3 節の 2 つ目の種類と同じく報告だけに使い、DNAT は残す。理由の文言は、どのホストの値かを名指す (2026-09-25)。理由は `server doctor`、`status`、`agent ls`、Web UI で VPS の上で読まれるので、「このホスト」と書くと VPS の値に読めるためである。`server doctor` はこの理由を `rule.target` の理由の符号 `agent_ip_forward_off` に分類する (10.2a 節)。テーブル全体の失敗(3 つ目の種類)には当たらない。`agent doctor` の `host.forwarding` はこの状態を FAILED とする(10.2c 節)。エージェントは値を 30 秒ごとに読み直し、1 になればルールの `error` を消す。自宅のホストがルータとして振る舞える状態になることの影響は 11 節に書く。

`rp_filter` の strict は、複数の LAN セグメントを持つ家で転送を壊しうる(7a.8 節)。エージェントはこの値と、他のテーブルの forward の `policy drop` を検査して提示し、書き換えない(6.1 節と同じ方針)。

他の値の扱いは次のとおりである。

- 同時フロー数の上限:`WGFT_MAX_UDP_FLOWS` と `WGFT_MAX_TCP_FLOWS` はカーネルモードでは使わない。値が設定されていれば、使わない旨を起動時に 1 行出して起動を続ける。拒否にしないのは、モードを切り替えても同じ `agent.env` を使えるようにするためである。ルールごとの隔離も持たない(7a.10 節)
- UDP の期限:全体状態の `udp_timeout` と `udp_timeout_stream` は使わない。エージェントのホストの conntrack の期限が効く
- conntrack の表の上限:エージェントは変えず、読めれば提示するだけにする(7a.10 節の kernel 側の保護)
- エンドポイントの引き直し:4 節と同じく、ハンドシェイクが keepalive の 5 倍の間成立しなければ、名前を引き直して wgctrl でピアに設定し直す。カーネルの WireGuard は名前を自分では引き直さないためである。名前の解決はエージェントのプロセスが行い、インタフェースの収束には解決の結果のアドレスを渡す。解決できていない間の収束は、カーネルが持つエンドポイントをそのまま残す。この間に初めてピアを置く場合は、エンドポイントの無いピアを置き、解決できた後の収束で加える。名前を引くのは、起動時、この keepalive の 5 倍の契機、宣言のエンドポイントが変わったとき、まだ一度も解決できていない間の適用のたびである。5 倍の契機で引くのは、宣言のエンドポイントの名前である。宣言が新しい名前に変わってまだ解決できていない間も、旧い名前ではなく新しい名前を引く。5 倍の契機で引き直せたら、アドレスが変わらなくても wgft0 を収束させる。外から書き換えられたピアのエンドポイントは、ここで戻る。この収束に失敗したら、次の 30 秒ごとの見直しで引き直しと収束を試し直す。失敗した見直しも、残りの表の修復と経路の確かめは行う。稼働中に現れた重なりのように収束の失敗が続く間も、30 秒ごとの見直しが表の修復に届くためである。keepalive が 0 の設定では、5 倍の契機で引き直さない。5 倍の期間が 0 になり、見直しのたびに名前を引くことになるためである。エンドポイントが IP アドレスそのものの場合も、引く名前が無いので引き直さない。一度解決できた名前を引けなくなった場合は、直前に解決したアドレスを使い続ける。名前の解決が一時的に止まっただけで、それまで通じていたエンドポイントをピアから外すと、トンネルまで止めることになるためである。30 秒ごとの収束には直前に解決した結果を渡し、その都度引き直した結果もゼロ値も渡さない。その都度引き直すと、30 秒ごとに DNS へ問い合わせ、4 節の契機と違う時点でエンドポイントを動かすことになる。ゼロ値を渡すと、外から書き換えられたエンドポイントが戻らない。エンドポイントだけの食い違いは、テーブルの公開し直しを要する外からの変更として扱わない。インタフェースの収束だけで直り、またカーネルは認証済みのパケットが届いた送信元へエンドポイントを自分で移すので、外から変えられたとは限らないためである。7 節のトンネルの作り直しはカーネルモードには無い。作り直しが備える受信の goroutine の停止は、wireguard-go に固有の故障だからである
- セッションの回復:エージェントは keepalive ごとに、wgft0 を通して `vpsd` のトンネルアドレスへ小さな UDP のデータグラムを 1 つ送る。ユーザー空間モードのトンネルが keepalive ごとにトンネル内へ ping を送るのと同じ目的である。keepalive のパケットだけでは、`vpsd` の側がセッションを失ったとき(VPS の再起動や wg0 のピアの置き直し)に、エージェントは今のセッションを使い続け、新しいハンドシェイクを鍵の寿命まで始めない。エージェントがハンドシェイクを始めた側のセッションでは REKEY_AFTER_TIME の 120 秒の後、応じた側のセッションでは鍵が使えなくなる REJECT_AFTER_TIME の 180 秒までである。WireGuard は、データを送ってから 15 秒の間何も届かなければハンドシェイクをやり直すが、この契機を起こすのはデータのパケットだけで、keepalive は起こさない。データグラムを送れば、回復までの時間はユーザー空間モードと同じ桁になる。データグラムへの応答は要らない。セッションが生きていれば、データを受けた `vpsd` の側の WireGuard が keepalive を返し、それが契機を解く。ICMP の echo ではなく UDP を使うのは、生のソケットも追加の権限も要らないためである。データグラムは 1 バイトで、宛先は `vpsd` のトンネルアドレスの UDP のポート 9(discard)である。応答を求めないポートを選んだ。カーネルモードの `vpsd` は wg0 から入る新しい接続を input で数えずに落とし、ユーザー空間モードの `vpsd` の netstack はこのポートで待ち受けないので、どちらのモードでも `server doctor` とサーバのカウンタに表れない。keepalive が 0 の設定では送らない。送れない間は、理由が変わったときだけ 1 行出す。理由は下層の誤りの種類(errno)で比べる。書き込みの誤りの文言は、送るたびに違う送信元のポートを含むためである。ピアにエンドポイントが無い間、たとえば名前がまだ一度も解決できていない間は、送れない理由としてそのことを出す
- トンネルのアドレスの記録:エージェントは、登録で割り当てられたトンネルのアドレスを帯の長さまで状態ファイル `agent.json` に記録する(9 節)。カーネルモードのエージェントは、全体状態の `wg.address` が記録と違えば、その全体状態を wgft0、アドレス、経路に触る前に拒み、ルールも適用しない(2026-09-25、所有者の決定)。VPS を奪った攻撃者が LAN の帯より細かい帯を配ると、wgft0 の接続経路が LAN の経路に勝つためである。LAN が `192.168.1.0/24` のときに `192.168.1.100/25` を配ると、ホストから LAN の半分へ届かなくなり、帯の先頭の次のアドレス `192.168.1.1` 宛ての通信は暗号化されて VPS へ届く。帯は server が自由に選べるので、引き込める宛先も自由に選べる。正規の運用では、登録の後にエージェントのアドレスは変わらない。server は `WGFT_WG_ADDRESS` の帯の変更を、`server teardown --purge` と登録のし直しなしには拒むためである(9 節)。この記録が、server が配る帯に対する守りの境界である
  - 記録の時点:登録の応答はアドレスだけを返すので、登録の時点ではアドレスだけを記録し、帯の長さは最初に適用できた全体状態から記録する。記録の無い `agent.json`、つまりこの記録より前の版が書いたファイルも、最初に適用できた全体状態のアドレスを帯の長さまで記録する。起動時は `last_state` があれば stream より先に適用するので、その適用が成功すれば、更新したエージェントは更新の前に受け取った値を記録する。`last_state` が無い場合、たとえば停止中の `rotate-key` が消した後と、その適用が失敗した場合は、stream から最初に適用できた全体状態の値を記録する。適用に失敗した全体状態の値は記録しない。記録を置き換えるのは登録のし直しだけで、撤去(10.3 節)は記録を消さない。帯を移すときは、server の運用者が `server teardown --purge` を実行し、エージェントを新しい接続文字列で登録し直す
  - 拒んだとき:拒んだ全体状態の処理済み世代は進めない。トンネルが立っていれば、wgft0 とテーブルは直前に適用した全体状態のまま残り、30 秒ごとの見直しもその全体状態に対して続く。wgft0 とテーブルを消して転送を止めることはしない。奪われた VPS は VPS の側だけで転送を止められるので、止めても守れるものは増えず、見直しを止めると、テーブルが消えたときに守りの行が戻らなくなる(11 節)。server の側が新しい帯で動けば、トンネルの中の宛先と wgft0 の AllowedIPs が合わないので、通しの転送は止まる。ハートビートのトンネルの状態は `error` になり、理由は拒んだ世代、届いた値、記録を示す。ログの文面は、帯を移す正規の手順が登録のし直しであることを示す。トンネルがまだ無い間に届いた全体状態は、他の wg 設定の誤りと同じく作成の失敗として報告する。同じ検証は wg 設定の形も確かめるので、トンネルが立っている間に届いた全体状態の mtu、keepalive、server の公開鍵が不正な場合も、アドレスの場合と同じく wgft0 とテーブルを残したまま拒み、ハートビートに拒んだことを示す。拒んだことの表示を消すのは、拒んだ世代と同じか新しい世代の全体状態を受け入れたときだけである。公開に失敗していた古い世代の試し直しが通っても、表示は消えない。`agent doctor` の `tunnel.local` は、この場合に解決済みのエンドポイントが転送を続けられるとは述べず、server が拒んだ設定で動く間は転送が止まることと、登録のし直しを示す。server が配る wg 設定のうち、ホストに書く前に確かめる値の検証は、エージェントの中の 1 か所に集める
  - ユーザー空間モード:ユーザー空間モードのエージェントも同じ記録を持つが、記録と違うアドレスも使い、同じ値の間は警告を 1 行だけ出す。ユーザー空間モードのトンネルは netstack の中に閉じ、ホストのアドレスと経路に触れないので、この攻撃が成り立たないためである。公開済みのユーザー空間モードの挙動は変わらない。記録は書き換えないので、後でカーネルモードへ切り替えても照合の元が残る
- アドレス帯の重なり:エージェントは、wgft0 の帯がホストの他のインタフェースのアドレスの帯か main の経路と重なれば、wgft0 に何も書かずに終了コード 1 で止まる。重なりは両方向で見る(2026-09-25、所有者の決定)。wgft0 の帯が相手を含む場合は、相手の細かい経路が wgft0 の帯の一部を奪う。相手が wgft0 の帯を含む場合は、wgft0 の接続経路が相手の帯の一部を奪い、エージェントのホストからその部分のホストへ向かう通信がトンネルへ入る。既定経路はどの帯も含むので対象にしない。`0.0.0.0/1` と `128.0.0.0/1` の 2 本の経路も対象にしない。OpenVPN の `redirect-gateway def1` のような VPN は、既定経路を消さずに上書きするためにこの 2 本を入れる。2 本は合わせて既定経路と同じ働きをし、どの帯も含むので、既定経路と同じ理由で除外する。対象にすると、この VPN を使うホストではどの帯でもカーネルモードが起動できない。長さ 0 か 1 のアドレスの帯も、`vpsd` のトンネルアドレスそのものでなければ同じ理由で除外する。この検査は多重の守りの 1 つで、守りの境界は上のアドレスの記録である。記録は server が帯を変えることを止め、この検査は利用者の設定の誤りで帯が LAN と重なった場合も止める。重なりのうち、`vpsd` のトンネルアドレスそのもののアドレスと、そのアドレスを含み wgft0 の帯と同じかより細かい帯と経路は、`vpsd` への通信も wgft0 から奪う。前者はローカルに届き、後者は wgft0 の経路に勝つか並ぶためである。エラーの文面は、この場合に `vpsd` への応答がトンネルを通らないことを示す。帯の上半分を使うコンテナのブリッジのように、`vpsd` のトンネルアドレスを含まない重なりも拒む。読むのは main の経路表だけである。main より先に引かれる規則の表、たとえば Tailscale がサブネットの経路を受け入れたときの表 52 が `vpsd` のトンネルアドレスを奪う場合は、この検査では見えない。このためエージェントは、wgft0 を収束させた後と、30 秒ごとの見直しと変更の通知の後の見直し(7b.4 節)で wgft0 が宣言どおりになった後に、規則を含む経路の引き当て(`RouteGet`)で `vpsd` のトンネルアドレスへの経路が wgft0 を通るかを確かめ、通らなければ警告を 1 行出す(2026-09-24、所有者の決定)。wgft0 が宣言と違う間は確かめない。wgft0 が消えたか down の間は、経路が既定経路へ出るのが当然で、原因の違う警告になるためである。警告は、引き当てが示す経路の出口と、`vpsd` への応答がトンネルを通らないおそれだけを述べ、原因を決めつけない。規則の表のほかに、稼働中に main の表に現れた重なりの経路も同じ警告になるためである。引き当ては、エージェントのホスト自身が送るパケットの経路を引く。送信元や入力のインタフェースで表を分ける規則、たとえば `from <LAN の帯> lookup X` は反映しない。DNAT した通信への LAN のホストからの応答は、エージェントのホストが転送するパケットなので、この種の規則が応答をトンネルの外へ送っても警告は出ない。起動は止めない。ポリシールーティングは稼働中にも変わり、起動の後に現れた規則を起動の拒否では扱えないためである。警告は食い違いが続く間 1 行だけ出し、経路が戻ったときにも 1 行出す。この所見を `agent doctor` に示すのは、カーネルモードの診断の段である。帯は server が決めるので、エラーの文面は重なった相手を示し、次の一手を 3 つ案内する。ホストの側でそのアドレスか経路を外すこと、server の運用者が `WGFT_WG_ADDRESS` で帯を移すこと、このエージェントをユーザー空間モード(`WGFT_MODE=userspace`)で動かすことである。帯を移すには、VPS での `server teardown --purge` と、すべてのエージェントの新しい接続文字列による登録のし直しが要る(9 節)。ユーザー空間モードのトンネルはホストに経路を加えないので、重なりの影響を受けない。カーネルモードからユーザー空間モードへ切り替えるには、先に `agent teardown` が要る(11a 節)。同じ network namespace で `vpsd` を動かすと、その wg0 のアドレスがこの重なりに当たる。稼働中に重なりが現れた場合も、次の収束は何も書かずに失敗し、wgft0 はそのまま残る。次の収束は、wgft0 が宣言と食い違ったときか全体状態を適用するときであり、30 秒ごとの見直しは重なりのために経路とアドレスを読まない(7b.4 節)。このため、稼働中に現れた重なりは、その時点までこの検査では報告されない。ただし、引き当てが wgft0 以外を選ぶ重なりは、上の 30 秒ごとの経路の確かめが警告として報告する。起動の拒否(終了コード 3)にしないのは、相手のアドレスか帯が変われば次の起動で通るためである(11b 節)

### 7b.2 宛先の扱い

DNAT は宛先の IP アドレスを要するので、宛先の扱いの形はユーザー空間モードと違う。守る範囲は同じにする(2026-09-24、所有者の決定)。

- ホスト名の宛先:DNAT を組む前に解決し(7a.3 節の `Prepare`)、30 秒ごとに解決し直し、ポートごとの DNAT の宛先が変わったときだけテーブルを公開し直す。解決の結果の集合が変わっても、許可一覧を当てはめて選ぶアドレス(複数の A レコードの項)が同じなら公開し直さない。DNAT が同じでルールの理由の文言だけが変わった場合、たとえば解決の失敗の文面が変わった場合は、公開の記録とルールの状態を書き換え、テーブルは差し替えない。公開し直した後は新しいフローだけが新しい IP へ向き、成立済みのフローは切らない。ユーザー空間モードも宣言の宛先の文字列を比べ、解決の結果の変化ではリスナーを閉じ直さない(7 節)ので、同じ意味になる。解決できないルールには DNAT を作らない。これは 7a.3 節のルール単位で閉じる失敗であり、他のルールの公開は進める。ユーザー空間モードは新しいセッションごとに解決するので、DNS の変更が効くまでの時間は、カーネルモードのほうが最長で 30 秒長い
- 解決に失敗した名前:一度解決できた名前の解決がその後に失敗した場合は、宣言の宛先の文字列が変わらない間、直前に解決できたアドレスを使い続け、次に解決できたときに置き換える(2026-09-24、所有者の決定)。DNS の一時的な失敗や、DNS がまだ使えない間の再起動で、動いていた DNAT を消さないためである。宛先の文字列は、ルール ID と組にして比べる。同じホスト名でもポートが変われば新しい宛先であり、一度も解決できていない宛先と同じく DNAT を作らない。直前のアドレスを使うときも、今の宛先の許可一覧、IPv4 だけの規則、ループバックと未指定のアドレスの拒否、ブロードキャストとマルチキャストの拒否を当てはめ直す。直前のアドレスは公開の記録(7b.4 節)にあるので、再起動の後も使える。解決に失敗したことと、直前の解決の結果で転送を続けていることは、ルールの `error` と理由(`name resolution of target host ... failed: ...; still forwarding to ... from the last successful resolution`)として、ハートビートと `agent doctor` に示す。理由に入る解決の誤りの文面からは、5.2 節のとおり送信元とサーバのソケットの組を除く。同じルールに TCP の宛先の試し接続の誤りや `ip_forward` の誤り(7b.1 節)があれば、その文言をこの理由の後ろに `; ` で続ける(2026-09-25)。直前のアドレスの宛先が応えないことを、server から見分けられるようにするためである。ホスト名は理由に 2 回入り、有効なホスト名は 253 バイトまで長くなる。hub の切り詰め(11 節)の外へ目印と試し接続の誤りが出ないように、解決の誤りの文面は、目印までと、目印の後ろに続く試し接続の誤りが切り詰めに収まる長さに短くする。`server doctor` は、この報告を転送の停止としては扱わない(10.2a 節)。DNAT は残すので、この `error` は 7b.3 節の 2 つ目の種類と同じく報告に使う。ユーザー空間モードは新しいセッションごとに解決するので、名前を引けない間は新しいセッションを宛先へ繋げない。この点はモードの違いである
- IPv4 の宛先だけ:カーネルモードは IPv4 の宛先だけを扱う(2026-09-24、所有者の決定)。実装の制限ではなく、モードの機能の違いである。IPv6 のリテラルの宛先は、7b.3 節の 1 つ目の種類の失敗としてそのルールだけを公開しない。ホスト名は A レコードだけで解決し、AAAA レコードだけを持つ名前も同じ種類の失敗とする。ユーザー空間モードの扱いは変わらない
- 複数の A レコード:ホスト名が複数の A レコードに解決されたときは、ポートごとの実効宛先で許可一覧が通すアドレスだけを残し、その中で最も小さいアドレスを使う(2026-09-24、所有者の決定)。どのアドレスも一覧が通さないポートだけを公開せず、すべてのポートがそうならルールを 7b.3 節の 1 つ目の種類の失敗とする。許可一覧が無ければ最も小さいアドレスを使う。一覧が通すアドレスが 1 つでもあればルールが働くという、ユーザー空間モードの意味を保つためである。最も小さいアドレスに決めるのは、DNS の応答の順が回るたびに DNAT の宛先が変わり、30 秒ごとにテーブルを公開し直すことを避けるためである。解決の結果に混ざるループバック、未指定、ブロードキャスト、マルチキャストのアドレスは使わない。モードの違いが 2 つ残る。ユーザー空間モードは、選んだアドレスに接続できなければ次のアドレスを試すが、カーネルモードは他のアドレスへ切り替えない。ユーザー空間モードは接続ごとに解決するので、接続が複数のアドレスに分かれうるが、カーネルモードは 1 つのアドレスへすべてのフローを向ける。切り替えと振り分けはカーネルの DNAT に新しい機能を足すことになるので、v1.2 では扱わない
- 宛先の許可一覧(`WGFT_AGENT_ALLOW_TARGETS`):DNAT を組むときに、ポートごとの実効宛先を判定する。ホスト名は解決の結果で判定する。一覧の外のポートには DNAT の行を作らず、範囲の他のポートは公開する。7 節の IP リテラルの宛先の判定と同じ単位である。解決の結果が変わるたびに判定し直すので、DNS の変更で一覧の外へ向かうことはない
- ループバックの宛先(`127.0.0.0/8`):カーネルモードでは拒み、DNAT を作らない。カーネルは DNAT でループバックへ向けたパケットを捨てる。wgft0 に `route_localnet` を立てれば届くが、DNAT を経ずにループバックを宛先とするパケットを捨てる守りの行が要り、書き換える sysctl も増えるので、この方法は採らない(13 節)。ルールの理由の文言は、カーネルモードがループバックの宛先を扱わないことを示す。同じホストのサービスには、ホスト自身の LAN のアドレスを宛先に書く。未指定のアドレス(`0.0.0.0`)も同じく拒む。ユーザー空間モードでは、`0.0.0.0` への接続はホスト自身に届くためである
- ブロードキャストとマルチキャストの宛先:7 節と同じ判定で拒み、DNAT を作らない(2026-10-03、所有者の決定)。理由の文言はユーザー空間モードと同じである
- エージェントのホスト自身の LAN のアドレス:DNAT の後のパケットは forward ではなく input を通り、そのホストで待ち受けるサービスに届く。MASQUERADE を通らないので、サービスから見た送信元は VPS のトンネルアドレス(`10.200.0.1`)になる。LAN の別のホストのサービスから見た送信元は、エージェントのホストの LAN のアドレスである。送信元で接続を許可するサービスでは、この違いが設定に関わる。ホスト自身の input のファイアウォールがそのポートを塞いでいれば届かない。forward の MSS のクランプはこの経路に掛からない。UDP では、全アドレス(`0.0.0.0`)に bind したソケットから送信元のアドレスを選ばずに応答するサービスでは、応答が client に戻らない。入ったパケットは、宛先を wgft0 のアドレスからホストの LAN のアドレスへ DNAT されている。このソケットの応答では、カーネルが応答の宛先 `10.200.0.1` への経路から送信元を選ぶので、送信元は wgft0 のアドレスになる。この応答は conntrack が待つ応答の向きの組(送信元がホストの LAN のアドレス)と一致しないので、DNAT が戻されず、新しいフローとして wgft0 から出る。カーネルモードの server は、wg0 から届くこの応答を既存のフローに属さない新しいフローとして落とす。ユーザー空間モードの server も別の仕組みで落とすと見込むが、未確認である。ルールの `listen_port` を宛先のポートと同じにしても直らない。応答の組が既存のフローの組と衝突するので、conntrack が送信元のポートを付け替えるためである。ホストの LAN のアドレスで待ち受けるサービス、LAN の別のホストの宛先、TCP、ユーザー空間モードのエージェントでは起きない。受けたパケットの宛先のアドレス(`IP_PKTINFO`)から応答の送信元を選ぶサービスは影響を受けない見込みだが、未確認である。確かめたのは通常のソケットだけである。UDP の宛先は `server doctor` で NOT TESTED なので(10.2a 節)、この制限は診断の判定に現れない。回避は、UDP のサービスをホストの LAN のアドレスで待ち受けさせるか、エージェントをユーザー空間モードで動かすことである。未確認とした点を除き、以上を試験用の実機で確かめた。直すことは後の版に残す(13 節)

### 7b.3 ルールの状態と失敗の種類

カーネルモードのルールの状態は、次の 3 つの種類の失敗で決まる(2026-09-24、所有者の決定)。

1. 公開できないルール:宛先が許可一覧の外にある場合、ホスト名を解決できない場合、ループバックの宛先である場合、ブロードキャストかマルチキャストの宛先である場合である。ルール単位の失敗であり、そのルールの DNAT を作らず、他のルールの公開は進める。範囲のルールで一部のポートだけが許可一覧の外にある場合は、そのポートの DNAT だけを作らない。ルールは `error` と理由を報告する
2. TCP の宛先の接続確認の失敗:エージェントのプロセスは、5.2 節と同じく適用のときと 30 秒ごとに TCP の宛先へ試し接続する。失敗したルールは `error` として報告するが、DNAT は残して転送を続ける。ユーザー空間モードでも接続確認の `error` は報告にだけ使い、中継を止めない(5.2 節)ので、同じ意味になる。試すのは、公開の記録の範囲、つまり宛先が連続するポートの並びごとに、その先頭のポートの 1 つだけである(2026-09-24、所有者の決定)。ユーザー空間モードはリスナーのポートごとに試すが、全幅の範囲のルールでは 30 秒ごとに約 60,000 回の接続になり、診断の副作用として大きすぎるためである。接続を受け付けず応答も返さない宛先では、期限の 2 秒と同時に試す数の 32 から、1 周期の 30 秒に試し終わらない。接続をすぐに拒む宛先でも、30 秒ごとに約 60,000 回の接続を LAN へ送る。期限の 2 秒と同時に試す数の 32 はユーザー空間モードと同じである
3. テーブル全体の公開の失敗:nftables のバッチが拒まれた場合などであり、backend 全体の失敗である(7a.3 節)。エージェントは処理済み世代を進めず、新しい全体状態を `last_state` として確定せず、旧いテーブルを残したまま 30 秒ごとに試し直す。backend 全体の失敗では世代を進めないという 7a.3 節の規則に合わせたものである。ルールごとの状態をこの失敗で `error` に書き換えない。ルール単位の失敗と混ぜると、運用者は宛先の問題とテーブルの問題を区別できないためである。server からは、`server doctor` の世代の遅れ(10.2a 節の `agent.rules_received`)として見える。エージェントのホストの `agent doctor` は、公開の誤りを `dataplane.table` の所見として示すが、FAILED にはしない。旧いテーブルが残って転送を続けているので、このホストのエージェントが今は転送を担えない、とは言えないためである(10.2c 節)。WireGuard インタフェースを変えられない場合も、この種類に入る。試し直しは、公開できなかった全体状態を実行時の状態に控えて行う。控えはメモリの上だけに持ち、新しい全体状態が届けばそちらに置き換わる。同じ誤りが続く間はログを出さず、誤りが変わったときと公開できたときに 1 行ずつ出す

UDP のルールの `ok` は、そのルールの DNAT を公開したことを意味する。UDP の宛先に届くかどうかは、ユーザー空間モードと同じく確かめない。TCP のルールの `ok` は、DNAT を公開し、宛先への接続確認が成功したことを意味する。範囲の TCP のルールでは、確かめたのは範囲ごとの先頭のポートだけであり、範囲の他のポートの宛先が待ち受けているかは確かめていない。ユーザー空間モードの範囲の TCP のルールの `ok` は、すべてのポートの宛先への接続確認の成功を意味するので、この点はモードの違いである。エージェントのホストの `agent doctor` では、1 つ目と 2 つ目の種類の失敗を持つルールを `dataplane.table` が FAILED として示す(10.2c 節)。

理由は人が読む文言であり(7a.6 節)、全体状態とハートビートの形は変わらない。`server doctor`(10.2a 節)は、1 つ目の種類の理由を `rule.target` の理由の符号に分類する。許可一覧の外は既存の `target_not_allowed`、解決の失敗は既存の `target_resolve_failed`、ループバックの宛先は新しい `target_loopback_unsupported` とする(2026-09-24、所有者の決定)。ブロードキャストとマルチキャストの宛先は `target_not_unicast` とする(2026-10-03、所有者の決定)。この符号は 2 つのモードに共通である(7 節)。1 つの符号にまとめないのは、運用者が次に取る手当てがそれぞれ違うためである。分類は、エージェントの診断の実装と同じ段で加える。7b.2 節の、直前の解決の結果で転送を続けているルールは、1 つ目の種類ではない。DNAT が残っているので、`server doctor` はこのルールを解決で止まったとは言わない。扱いは 10.2a 節の `rule.target_resolve` の場合分けにある(2026-09-25)。健全な UDP のルールの `rule.target` は、カーネルモードでも NOT TESTED の `udp_listener_only` になる。符号の名前はリスナーを指すが、宛先を試していないという、符号が表す事実は変わらない。

### 7b.4 収束と停止

- 宛先の変更と削除:テーブルを差し替えても conntrack のエントリは残る。ユーザー空間モードがリスナーを閉じ直して得ていた意味(7 節の収束の表)を、カーネルモードは conntrack の収束で実現する。公開の後に、wgft0 から入って DNAT されたフローのうち、宣言から消えたポートのフローと、実効宛先が変わったポートのフローを消す。実効宛先は 7 節と同じく宣言の文字列で比べるので、ホスト名の解決の結果が変わっただけのフローは消さない。所属ルール ID だけが変わったポートのフローも残す。ルールの無効化とエージェントの無効化(5.1 節)はルールを宣言から外すので、成立済みのフローも切れる。切れ方はモードで違う。ユーザー空間モードの中継は、切るセッションの netstack の側を RST で切る(7 節)。カーネルモードの conntrack の削除はパケットを送らずにエントリを消す。ポートが宣言から消えた場合は、利用者の側には何も届かず、以後のパケットが届かなくなる。実効宛先が変わった場合は、TCP の以後のパケットが新しい宛先へ DNAT されるので、新しい宛先が RST を返せば、それが利用者に届く。ラボでは、wgft0 に見立てた veth でも、カーネルモードの `vpsd` と本物の wgft0 を通したフローでも届いた。これは、途中のパケットから conntrack のエントリを作り直す `nf_conntrack_tcp_loose` が既定の 1 のときの挙動である。0 のホストでは途中のパケットが INVALID として落ち、利用者の側には何も届かない見込みである。この点はラボで確かめておらず、未確認である。どちらも、そのフローが続かないという意味で切れている。公開できずに閉じたルールの成立済みのフローは、7a.3 節のとおり直前の `Active` の値で判定する
- conntrack の収束の照合:収束は `internal/dataplane/linuxkernel/conntrack` の `ConvergeAgent` が行う。入力は、今の公開の記録、それより前の公開の記録の列、wgft0 のアドレス、`vpsd` のトンネルアドレス、宛先の許可一覧であり、エージェントの実行時の状態を持たない。前の公開の列は、最後に収束を済ませた公開と、その後に公開したが収束が済んでいない公開を古い順に並べたものである。収束に失敗した公開を列に残すので、失敗の間に公開した宛先へ向かったフローも、次の試し直しで見分けられる。呼び出し側は、収束が済むまで列を状態ファイルに残す。残さないと、収束が済まないまま再起動したときに、記録より前の公開のフローを見分けられず、そのフローは conntrack の期限まで残る(2026-09-24)。conntrack は IPv4 のエントリだけを読む。conntrack のライブラリの説明によれば、種別で絞る読み出しは Linux 4.20 以降のカーネルでだけ効く。それより前のカーネルでの動作は未確認なので、判定の側でも IPv4 だけを見る。conntrack のエントリのうち、次のすべてを満たすものだけを、wgft0 から入って wgft が DNAT したフローとみなし、他のエントリには触れない
  - 印と向き:DNAT の印を持ち、元の向きの送信元が `vpsd` のトンネルアドレス、宛先が wgft0 のアドレスで、プロトコルが TCP か UDP であること。conntrack はパケットが入ったインタフェースを記録しない。wgft0 のピアの AllowedIPs は `vpsd` のトンネルアドレスの /32 だけなので、この送信元と宛先の組が wgft0 から入ったことを表す
  - DNAT の宛先:応答の向きの送信元のアドレスとポート、つまり DNAT の宛先が、今の公開のそのポートの実効宛先と一致するか、前の公開のどれかがそのポートに宣言した実効宛先と合うこと。宣言の宛先がホスト名のときは、公開の記録が解決の結果の履歴を持たないので、ポートだけを比べる。wgft の表が無かった間に他のテーブルが DNAT したフロー(Docker が公開したポートなど)は、wgft0 から入っていても DNAT の宛先が合わないので、wgft が同じポートを宣言していても残る。ただし、宛先がホスト名のポートで、他のテーブルが実効宛先と同じポートへ DNAT したフローは区別できない。このフローは wgft のフローとみなされ、wgft がそのポートを宣言から外すか実効宛先を変えると消える。許可一覧による削除(次項)は、このようにポートだけで照合したフローには掛けない
- conntrack の収束の判定:wgft のフローとみなしたもののうち、DNAT の宛先が今の公開の実効宛先と一致するフローは残す。残りは、そのフローを作った前の公開を起点にする。起点は、DNAT の宛先をそのポートに実際に公開した前の公開のうち最も新しいものであり、そのような公開が無いときだけ、宣言からそのフローを作りえた前の公開のうち最も新しいものを使う。ホスト名の宣言はポートだけで照合するので、先に宣言で探すと、そのフローを作っていない後の公開を起点に選び、途中の宛先の変更を見落とすためである。起点より後の公開と今の公開がそのポートを同じ実効宛先の文字列で宣言し続けていれば残す。途中でポートが宣言から消えていれば消し、実効宛先の文字列が変わっていれば消す。ポートの宣言には、7b.3 節の 1 つ目の種類の失敗で公開しなかったポートも含める。このため、宣言を変えずに名前を解決できなくなったルールの成立済みのフローは残る。「宛先の変更と削除」の項の「直前の `Active` の値で判定する」を、エージェントではこの形で実現する。残すフローのうち、アドレスとポートの両方で照合したもので、DNAT の宛先が今の許可一覧の外にあるものは消す。許可一覧は起動のときに読むので、一覧を狭めてエージェントを再起動した場合に当たる。ユーザー空間モードでは再起動が中継をすべて閉じるので、一覧の外の宛先へのフローは残らない。カーネルモードも、許可一覧が守る範囲をモードで変えないために、そのフローを残さない。DNAT の宛先がブロードキャストかマルチキャストのアドレスであるフローも、同じくアドレスとポートの両方で照合したものを消す(7 節、2026-10-03)。この判定の無い版のエージェントが帯のブロードキャストへ DNAT していた UDP のフローが、更新の後の最初の公開で消えることを、ラボで確かめた。ポートだけで照合したフローは、他のテーブルのフローでありうるので、許可一覧では消さない。このため、宛先がホスト名のルールのフローのうち、DNAT の宛先が前の公開のどれにも記録されていないもの、たとえば記録より前の公開で作られたフローは、エージェントの停止中に狭めた許可一覧の外にあっても残る。前の公開が 1 つも無ければ、どのフローも wgft のものと見分けられないので、何も消さない。conntrack の読み出しの失敗と削除の失敗は誤りとして返し、既に消えていたエントリの削除は失敗に数えない。誤りの後は、7a.3 節の修復と同じく、テーブルを公開し直さずに同じ入力で試し直す(2026-09-24)
- conntrack の収束の呼び出し:エージェントはテーブルの公開に成功するたびに、直前の公開を前の公開として収束させる。前の公開が 1 つも無い初回の公開では収束させない。収束に失敗したら、前の公開の列を状態ファイルに残し、30 秒ごとの見直しでテーブルを差し替えずに同じ列で試し直す(7a.3 節の修復)。その間に公開が進めば、列にその公開を加える。列は新しい 32 個までに限る。状態ファイルが大きくならないためであり、それより古い公開で成立したフローは見分けられずに残る。直前の要素と DNAT も宣言も同じ公開は置き換えて並びを伸ばさない。宣言は、ルールごとのプロトコル、待ち受けのポートの範囲、宣言の宛先の文字列であり、世代と理由は比べない。DNAT が同じでも宣言の宛先の文字列が違う公開は畳まない。収束は宣言の宛先の変化で宛先の変更を見分けるので、たとえばホスト名の宛先を IP リテラルへ変えてから同じホスト名へ戻すと、戻した公開は中間の公開と DNAT が同じになり、中間の公開を落とせば最初の宛先へのフローを残してしまう。再起動の後は、状態ファイルの公開の記録と列から収束させるので、エージェントが止まっている間の無効化や宛先の変更も、再起動の後の最初の公開で既存のフローに届く。収束の範囲は、wgft0 のアドレス、`vpsd` のトンネルアドレス、今の宛先の許可一覧である。消したフローの数は、消した場合だけ 1 行出し、収束の誤りは変わったときだけ 1 行出す。閉じられなかったフローの数は誤りの文面に含まれるので、同じ削除の失敗が続く間は出し直さない
- 停止と起動:エージェントは停止しても wgft0 とテーブルを消さないので、停止中も転送が続く(9 節の `vpsd` と同じ)。起動時は、wgft0 の所有を判定してから、認証情報ファイルの `last_state` へ収束させ、その後に stream に接続する。このプロセスの最初の wgft0 の収束は、stream に接続した後に行う場合も、起動の一部として扱う(2026-09-24、所有者の決定)。`last_state` を持たない初回の起動と停止中の `rotate-key` の後は、wgft0 の宣言が stream から届くまで分からないためである。最初の収束が他の所有者のインタフェースかアドレス帯の重なりで失敗すれば終了コード 1 で、権限か WireGuard のモジュールの欠如で失敗すれば終了コード 3 でプロセスを終える(11b 節)。所有の衝突や前提の欠如を抱えたまま稼働の状態に入らないためである。最初の収束の後の同じ失敗は、7b.3 節の 3 つ目の種類として旧い設定を残して 30 秒ごとに試し直す。起動時には、wgft0 と別の名前で今の鍵か 1 つ前の鍵を持つ WireGuard インタフェースがあれば警告する(2026-09-24、所有者の決定)。`WGFT_WG_INTERFACE` を変えた後に旧い名前のインタフェースが残った場合に当たる。サーバの wg0 と同じく、鍵で自分のものと判定しても名前の違う資源には触れないので、起動時には自動で消さず、撤去か運用者の操作に任せる。撤去はこのインタフェースも消す(10.3 節)。コンテナを再起動すると network namespace ごと消えるが、起動時の収束で戻る。テーブルの公開に成功するたびに、公開したポートと宛先を状態ファイルに記録する(9 節)。記録は、公開の元にした全体状態の世代と、ルールごとの公開したポートの範囲とその先頭の実効宛先、または 7b.3 節の 1 つ目の種類の理由を持つ。ポートごとではなく範囲ごとに持つので、60,000 ポートのルールでも記録は大きくならない。エージェントが止まっている間の `agent doctor` は、この記録と実際のテーブルを比べ、公開すべきルールの DNAT が残っているかを確かめる(10.2c 節)。比べるのは、テーブルの `nat_pre` の DNAT の行から読んだルールとポートごとの宛先と、DNAT の行を含むすべてのチェーンの行の形と並びである。filter_pre、forward の通す行、MASQUERADE のどれかが欠けても LAN への転送は止まるので、DNAT の行だけでは足りない
- 所有の判定:同名の WireGuard インタフェースの鍵が認証情報ファイルの鍵と一致するときだけ、自分のものとみなす。一致しなければ他の所有者の資源として触らず、終了コード 1 で終わる(11b 節)。`rotate-key` の途中で落ちて鍵がずれる場合に備え、状態ファイルに 1 つ前の鍵を残し、その鍵を持つインタフェースも自分のものとみなす。1 つ前の鍵は、次に鍵を変えるまで残す。停止中の `rotate-key` は、ユーザー空間モードでは状態ファイルの鍵を消すだけだが、カーネルモードでは消す鍵を 1 つ前の鍵として残す。稼働中の `rotate-key` は、今の鍵を 1 つ前の鍵として、新しい鍵と同じ 1 回の保存で残す。wgft0 を新しい鍵へ書き換える前に落ちても、次の起動が 1 つ前の鍵で所有を判定できるためである。カーネルモードかどうかは状態ファイルのモードの記録で決まり、ユーザー空間モードの状態ファイルは 1 つ前の鍵を持たない。停止中の `rotate-key` を続けて 2 回実行すると、2 回目には消す鍵が無いので、1 つ前の鍵を空の値で上書きせずに残す。インタフェースには古い鍵が残っているので、次の起動は 1 つ前の鍵で所有を判定し、新しい鍵へ収束させる。撤去(10.3 節)も 1 つ前の鍵を持つインタフェースを自分のものとして消す。空の鍵は、今の鍵とも 1 つ前の鍵とも一致させない。状態ファイルに 1 つ前の鍵が無い場合も、空の値を鍵として比べない。鍵を設定する前のインタフェースも自分のものとみなさない。同名の WireGuard 以外のリンクにも触れず、終了コード 1 で終わる。1 つ前の鍵を持つインタフェースは、起動時の収束で今の鍵に書き換える。サーバの wg0 の `--adopt-existing` に当たる、鍵の一致しないインタフェースを引き継ぐ手段は持たない。回復の経路は次項の `ip link del` だけとする
- 鍵の変更と最終ハンドシェイク:wgft0 の鍵を変える収束は、鍵と同じ wgctrl の設定で wgft0 のピアをすべて外し、server のピアだけを足し直す(2026-10-03)。Linux の WireGuard は、インタフェースの秘密鍵を変えても、ピアの最終ハンドシェイクの時刻と送受信バイト数を残す。ピアを置き直さないと、新しい鍵で一度もハンドシェイクしていない間も前の鍵の時刻が読める。その時刻を、ハートビートのトンネルの状態(5.2 節)、`agent doctor` の `tunnel.local` と `dataplane.interface`(10.2c 節)、stream の再接続の待ちを打ち切る判定(5.2 節)が今の鍵のものとして扱う。server が鍵の変更を断っていて転送が止まっている間も、これらは前の鍵の時刻を今のトンネルの値として示す。ピアを置き直すと、カーネルが持つ値そのものが wgft0 の今の鍵で成立したハンドシェイクだけになる。読む側はモードを区別せず、ユーザー空間モードが鍵を変えるたびに device を作り直すのと同じ意味の値を読む。server 以外のピアは、どの収束でも外すので(外からの変更の項)、すべてを外しても収束の結果は変わらない。置き直したピアは、宣言の AllowedIPs と keepalive を持つ。エンドポイントは、名前を解決できていればその結果を使い、できていなければカーネルが持っていた値を引き継ぐ。待ち受けポートは変えない。この設定はピアを 1 つ、AllowedIPs を 1 つだけ持つ。wgctrl が設定を複数の netlink のメッセージに分けるのは、ピアが 32 を超えるか AllowedIPs が合わせて 256 を超える場合だけなので、wgft0 にいくつピアがあっても、鍵の書き換えとピアの置き直しは 1 つのメッセージで送られる。外すピアを 1 つずつ並べる形では、ピアの多い wgft0 で設定が分かれ、2 度目に現れる server のピアからエンドポイントと keepalive が落ちることを、独立レビューのラボで確かめたので採らない。1 つのメッセージで送るので、エージェントが途中で落ちて新しい鍵と前のピアの組が残ることは無い。同時に読む側については、カーネルのソースでは設定の適用と読み出しがどちらも rtnl_lock とインタフェースの更新の排他を持つことと、独立レビューのラボで鍵の切り替えを繰り返す間に並行して読み続け、新しい鍵と前のピアの組を一度も読まなかったことを確かめた。どちらも証明ではない。カーネルは途中まで適用したメッセージを元に戻さない。鍵を書いた後でピアを足す処理がメモリの不足などで失敗すると、新しい鍵と server のピアの無い wgft0 が次の収束でピアを足すまで残り、その時点で名前を解決できていなければ、カーネルが持っていたエンドポイントは失われる。この挙動はカーネルのソースを読んで判断したもので、ラボでは試していない。カーネルの値を直すので、エージェントの再起動の後も、停止中の `agent doctor` でも、同じ値が読める。鍵の書き換えが失敗して wgft0 が 1 つ前の鍵を持ったままの場合、読める時刻は wgft0 が持つその 1 つ前の鍵のものであり、`dataplane.interface` はそれを 1 つ前の鍵として示す。この版より前のエージェントが鍵を変えた wgft0 は、前の鍵の時刻を持ったまま残る。更新の後の起動は鍵を変えないので、その時刻は次のハンドシェイクまで読める。採らなかった案は 3 つある。1 つ目は、鍵を適用した時刻を記録し、それより古いハンドシェイクを無いものとして扱う案である。再起動をまたぐには状態ファイルに時刻を残す必要があり、停止中の `agent doctor` を含む読む側のすべてが同じ規則を持つことになり、比べる時刻は壁時計の飛びに左右される。2 つ目は、鍵の書き換えとピアの置き直しを別のメッセージで行う案である。鍵を先に書くと、間で落ちた場合に新しい鍵と前の鍵の時刻の組が残る。ピアを先に置き直しても良くならない。足し直したピアはすぐに keepalive を送るので、鍵を書く前に前の鍵でハンドシェイクが成立し、その時刻が残りうる。3 つ目は、最終ハンドシェイクの古さの閾値だけを変える案である。前の鍵の時刻と今の鍵の時刻を区別しないので、断られた直後のように前の鍵の時刻が新しい間は、同じ表示が残る
- インタフェースの作成:エージェントは、自分の作成の途中で落ちても鍵を持たないインタフェースを残さないように、インタフェースを作業用の名前で作り、鍵を書いてから名前を変える。WireGuard のリンクは鍵を持たずに作られるので、今の名前のまま作ると、作った直後、鍵を書く前に落ちた場合に鍵の無い wgft0 が残り、以後の起動はそれを他人のものとして拒み続け、運用者が消すまで戻らないためである。作業用の名前は `wgftnew` にインタフェース名の CRC32 の 16 進 8 桁を続けた 15 バイトの名前で、インタフェース名ごとに決まる。作ったばかりのリンクは down なので、そのまま名前を変えられる。名前を変える前に落ちた場合は作業用の名前のリンクだけが残り、次の作成がそれを消してから作り直す。消すのは、作業用の名前を持つ WireGuard のリンクのうち、鍵を持たないものと、今の鍵か 1 つ前の鍵を持つものだけである。他の鍵の WireGuard のインタフェースと WireGuard 以外のリンクは、自分の作成が残したものとは言えないので触らず、作成を止めて名前を示す。文面は、そのリンクを消す道と、`WGFT_WG_INTERFACE` で別の名前を使う道を示す。インタフェース名が変われば作業用の名前も変わるためである。この場合の終了コードは、他の所有者の資源との衝突と同じく 1 である(11b 節)。名前を変える前に同じ名前のリンクが現れた場合は、そのリンクに触れず、作業用の名前のリンクを消して誤りを返す。この作り方により、鍵を持たない wgft0 はエージェント自身の作成からは残らないので、所有の判定の文面は、鍵の無いインタフェースを他の道具が作ったものとして示す。
- 状態ファイルを失った場合:登録し直すと鍵が変わるので、残った wgft0 は所有の判定で他人のものに見え、エージェントは終了コード 1 で止まる。wgft は鍵の一致しないインタフェースを消さないので、終了のメッセージは、そのインタフェースが以前のエージェントのものであることを運用者が確かめたうえで `ip link del <名前>` で消す手順を示す。`table inet wgft_agent` は名前で決まる wgft の資源なので、次の公開がそのまま差し替える
- 外からの変更:自宅のホストでも、`systemctl reload nftables` でテーブルが消えうる。エージェントは、カーネルの変更の通知の後(次項)と 30 秒ごとに、実際のテーブルとインタフェースを読み、直前の公開と食い違えば公開し直す。比べるのは、テーブルの指紋(7a.3 節)と、wgft0 の鍵、up、MTU、アドレス、ピアの集合と AllowedIPs と keepalive である。鍵の比較は所有の判定で行うので、同じ名前の WireGuard 以外のリンクと、鍵の違う WireGuard のインタフェースも、ここで食い違いとして見つかる。エンドポイントは比べない(7b.1 節)。テーブルが消えたか指紋が変わっていれば、同じ公開をやり直す。テーブルの削除では、成立済みのフローが切れうる。エージェントの稼働中に外から `nft delete table inet wgft_agent` を実行すると、保持していた TCP のフローがその場で切れることを、実機(Debian 13 の非特権のコンテナ)とラボ(Debian 12 の VM)で観測した。ラボでは両方のモードの `vpsd` で切れ、カーネルモードの `vpsd` では利用者の側に RST が届いた。新しい接続は、次の見直しがテーブルを公開し直した後に戻った。ラボ(Debian 12、カーネル 6.1)では、network namespace に wgft の表だけがある場合は切れた。空の nat の prerouting と postrouting のチェーンと、`ct state established` を数える filter の prerouting のチェーンを同じ別の表に持たせた場合は、フローが続いた。どちらか一方だけを持つ別の表を加えた場合は切れた。原因はカーネルのソースで確かめておらず、未確認である。Docker や firewalld のように conntrack を使う別の表があるホストでは続く可能性があるが、これも未確認である。`systemctl reload nftables` でも同じことが起きる見込みだが、未確認である。wgft0 の削除では、同じ実機とラボでフローは切れずに続いた。wgft0 が宣言と違えば、先に wgft0 を収束させてからテーブルを公開し直す。7b.1 節のアドレス帯の重なりの検査はインタフェースの収束の中で行うので、その検査のための経路とアドレスは 30 秒ごとには読まれず、wgft0 が食い違ったときと全体状態を適用するときにだけ読まれる。このため、稼働中に現れた重なりは、次に wgft0 が食い違うか全体状態を適用するまで、この検査では報告されない。引き当てが wgft0 以外を選ぶ重なりは、7b.1 節の 30 秒ごとの経路の確かめが警告として先に報告する。経路とアドレスの一覧を 30 秒ごとに読むと、経路の多いホストで負荷になると見込んで、この遅れを許容する。負荷は測っておらず、設計の前提である。名前の解決し直しと同じく、見直しは名前の解決を実行時の状態の排他の外で行い、その間に処理済みの全体状態が変わるか、公開できなかった全体状態の試し直しを待っていれば、解決の結果を捨てる。見直しが公開し直したときと、テーブルを差し替えずに記録の理由の文言だけを書き換えたときは、次の 30 秒を待たずにハートビートを送る。見直しの公開が失敗したら旧いテーブルと記録を残し、次の見直しで試し直す。同じ食い違いと同じ誤りは、続く間 1 行だけ出す。他のプロセスが同じ変更を繰り返す場合も、エージェントはそのたびに直し続けるが、ログは 30 秒ごとの見直しが食い違いを見つけない回を挟むまで 1 行だけである。通知の後の見直しが食い違いを見つけない回は、この区切りに数えない。自分の公開の直後の通知の後の見直しは必ず一致を見つけるので、数えると、繰り返される変更のたびに 1 行出すことになるためである
- 変更の通知:エージェントのカーネルモードは、`vpsd` の kernel backend と同じカーネルの変更の通知(7a.3 節の実際の状態への収束。nftables、リンク、IPv4 アドレス)を購読し、30 秒ごとの見直しを待たずに外からの変更を直す。購読には `internal/dataplane/linuxkernel` の `vpsd` と同じ部品を使うので、受信バッファの大きさも `vpsd` と同じである。購読が切れたときと受信バッファが溢れたときは、何かが変わったものとして見直し、1 秒から 1 分まで間隔を倍にしながら購読を張り直す。購読の失敗は、失敗が続く間 1 行だけ出す。通知の内容は読まない。どのテーブルのどの変更の通知でも、最初の通知から 250 ミリ秒待って続く通知をまとめ、前項と同じくテーブルの指紋と wgft0 を直前の公開と宣言に比べ、食い違えば前項と同じ手順で直す。エージェント自身の公開と wgft0 の収束も通知を生む。公開の直後に指紋を読み直して比べる基準にしているので、その通知の後の見直しは一致を確かめて終わり、公開し直しは続かない。`vpsd` と同じ扱いである。通知の後の見直しは名前を引かず、宛先への試し接続もしない。公開し直すのは直前の公開そのものであり、宛先の名前の解決し直し(7b.2 節)とエンドポイントの引き直し(7b.1 節)は 30 秒ごとの見直しに残す。通知はホストの他のテーブルやインタフェースの変更でも届くので、通知のたびに DNS へ問い合わせないためである。経路の確かめ(7b.1 節)は通知の後の見直しでも行う。公開できなかった全体状態の試し直しを待つ間は、30 秒ごとの見直しと同じく通知の後の見直しも行わず、公開し直しは試し直しが担う。テーブルの公開か wgft0 の収束が失敗した後は、`vpsd` と同じく、通知による公開し直しの間隔を空ける(7a.3 節の再試行)。失敗した公開もテーブルを差し替えることがあり、その差し替えの通知で公開し直すと、失敗が 1 秒に数回の間隔で繰り返されるためである。間隔は失敗の後 1 秒から始まり、失敗が続くたびに倍になって 30 秒で頭打ちになり、公開に成功すると 1 秒に戻る。新しく見つかった食い違い、つまり前項のログの規則で新たに 1 行出す食い違いは、この間隔を待たずに直す。30 秒ごとの見直しは、この間隔に関係なく走る。間隔のために何も試さなかった通知の後の見直しは、直前の見直しの誤りを消さず、回復のログも出さない。試していないので直ったとは言えず、消すと、公開の失敗が続く間に無関係な通知が届くたびに、失敗と回復のログが交互に出るためである。エンドポイントの引き直しの後の wgft0 の収束の誤りと、宛先の名前の解決し直しで変わった DNAT の公開の誤りは、30 秒ごとの見直しだけが消す。通知の後の見直しは名前もエンドポイントも扱わないためである。変わった DNAT の公開がテーブルを差し替えずに失敗すると、テーブルは直前の公開のままなので、通知の後の見直しは食い違いを見つけないが、新しい宛先の DNAT はまだ公開されていない。この誤りは、30 秒ごとの見直しが変わった DNAT を公開できたときか、DNAT が直前の公開と同じに戻ったときに消える。30 秒ごとの見直しは、通知の取りこぼしと、通知の届かない変更への備えとして残す。通知の届かない変更は、WireGuard のピアの変更(7a.3 節の安全網)と、経路と経路の規則の変更である。ユーザー空間モードのエージェントは、カーネルに残す資源を持たないので購読しない
- 撤去:`wgft agent teardown` が、停止したエージェントの資源を消す(10.3 節)

### 7b.5 権限と配置

- 権限:`CAP_NET_ADMIN` だけで足りる。WireGuard インタフェースの作成と設定、nftables、conntrack の削除、`ip_forward` の書き込みのすべてが、非 root のプロセスで `CAP_NET_ADMIN` だけを持てば通ることを、ラボで確かめた。systemd の `ProtectKernelTunables=yes` は `/proc/sys` を読み取り専用にして `ip_forward` の書き込みを止め、`RestrictAddressFamilies` から `AF_NETLINK` を外すとどの操作も失敗する
- unit:同梱の `deploy/agent.service` は変えない。ユーザー空間モードのエージェントに要らない権限を渡さないためである。カーネルモードに要る `CAP_NET_ADMIN` は、unit に重ねる systemd の drop-in の例 `deploy/agent.kernel.conf` として別に配る(2026-09-24、所有者の決定)。置き場所は `/etc/systemd/system/wgft-agent.service.d/kernel.conf` である。中身は `AmbientCapabilities=CAP_NET_ADMIN` と `CapabilityBoundingSet=CAP_NET_ADMIN` の 2 行だけであり、エージェントは `User=wgft` のまま動き、unit の他のサンドボックスの設定も変わらない。2 行目が要るのは、unit の空の `CapabilityBoundingSet=` が境界の集合を空にしており、境界の集合に無い権限はプロセスが ambient の集合に置けないためである。drop-in の空でない値は unit の値に加わるので、境界の集合は `CAP_NET_ADMIN` だけになる。drop-in には `ProtectKernelTunables=` を加えず、`RestrictAddressFamilies=` から `AF_NETLINK` を外さない。前項のとおり、前者は `ip_forward` の書き込みを止め、後者はどの操作も失敗させるためである。この drop-in は、配布物の VM 試験(docs/testing.md の B9)の Debian 12 の VM と、試験用の実機の Proxmox VE の非特権の LXC のコンテナ(Debian 13、nesting を有効、AppArmor のプロファイルは unconfined)で確かめた
- 非特権の LXC:動作の対象にする。`ip_forward`、WireGuard、nftables、conntrack の操作はどれもコンテナの network namespace の中で完結し、ホストの値を変えないことを、ラボの非特権の LXC で確かめた。conntrack の表の上限はコンテナから変えられないので、読むだけにする
- Docker:v1.2 ではカーネルモードの手順を書かない(13 節)
- Linux 以外:Windows と macOS で `WGFT_MODE=kernel` を指定すると、種別 `prerequisite` の拒否として終了コード 3 で止まる(11b 節)
- カーネルの前提:WireGuard のリンク種別を持たないカーネルと、権限が足りない配置は、9 節の `vpsd` と同じく種別 `prerequisite` の拒否とし、ユーザー空間モードへの案内を添える
- 前提の検査の時点:エージェントは上の 2 つの前提を、モードを `agent.json` に記録するより前、つまり登録で接続文字列を使うより前に確かめる(2026-09-25、所有者の決定)。検査はカーネルに何も書かない。権限は、`CAP_NET_ADMIN` を要する読み出しである nftables のテーブルの一覧で確かめ、権限の誤りだけを拒否にする。プロセスの `CapEff` のビットで判定しないのは、後の書き込みと同じ判定をカーネルにさせるためである。WireGuard は、汎用 netlink の `wireguard` のファミリの問い合わせで確かめる。問い合わせに権限は要らない。カーネルは、知らないファミリを問われるとモジュールの読み込みを試すので、問い合わせの後もファミリが無ければ、リンクの作成も同じく失敗する。どちらの読み出しでも、それ以外の誤りでは起動を止めず、この検査が無い場合と同じく最初の収束(7b.4 節)に分類を任せる。前提で止まる起動は `agent.json` を書き換えず、接続文字列も使わないので、拒否の文面の案内どおり `WGFT_MODE=userspace` にすれば、そのまま登録して起動できる。記録の後に止まると、ユーザー空間モードへ戻す起動が 11a 節の関門に止められ、関門が案内する撤去には `CAP_NET_ADMIN` が要る。カーネルには何も作られていないのに、案内どおりに戻す道が閉じるので、検査を記録より前に置く。最初の収束での同じ分類は残す。検査を通っても、書き込みだけが拒まれる配置がありうるためである

### 7b.6 server との関係

server にはエージェントのモードを知らせない(2026-09-24、所有者の決定)。wire protocol、管理用 API、全体状態の形は変わらず、ハートビートの理由の文言だけがモードで変わる。`server doctor` と Web UI の経路の図の節点の名前(`listener / target` など)も変えない。モードを知らせるには、wire と管理用 API への加算と、7a.6 節の capability の検証が要るためである。見直しは 13 節に置く。

プロキシモードのルール(6.2 節)と疎通確認(10.1 節)では、`vpsd` がエージェントのトンネルアドレスの `listen_port` へ接続する。カーネルモードではこの接続も wgft0 から入るので、同じ DNAT で宛先に届く見込みである。この点は未確認である。

### 7b.7 未確認の点

- LAN の側に wgft0 の MTU より小さい区間がある場合の MSS。`rt mtu` はその区間の MTU を反映しない
- ホスト自身の LAN のアドレスへの DNAT での TCP の MSS。ホストの TCP が wgft0 の経路の MTU から MSS を決めると見込んでいる
- wgft0 から入る向きの SYN でも `rt mtu` が wgft0 の MTU から決まる理由。結果はラボで観測したが、カーネルのソースでは確かめていない
- `deploy/agent.kernel.conf` を Debian 以外のディストリビューション、たとえば Ubuntu と Fedora の systemd で使った配置
- SELinux または AppArmor が有効なディストリビューション、nesting が無効か AppArmor のプロファイルが制限をかける Proxmox VE の非特権のコンテナ、Incus の非特権のコンテナ、WireGuard のモジュールを自動で読み込めないホスト
- `rotate-key` の途中で鍵がずれた場合の通しの動作。部品の段の所有の判定、つまり 1 つ前の鍵を持つインタフェースを自分のものとし、今の鍵へ書き換えることは、ラボで確かめた
- Tailscale そのものが加える規則での経路の警告。ラボでは、`vpsd` のトンネルアドレスを別の表へ送る規則を手で加えて確かめた
- keepalive ごとのデータグラムによる回復の時間を、ユーザー空間モードのエージェントの回復の時間と並べて測ること
- プロキシモードのルールと疎通確認が DNAT を通って届くこと
- Docker でのカーネルモード
- エージェントのホストで Docker が公開しているポートを宛先にした DNAT
- Docker そのものを動かしたホストでの conntrack の収束。ラボでは、Docker に見立てた DNAT の行を部品の段で確かめただけである。本物の wgft0 を通したフローの収束は、エージェントへの組み込みの後にラボで確かめた
- エージェントの停止中に狭めた許可一覧が、宛先がホスト名のルールの古いフローに効かないこと(7b.4 節の conntrack の収束の判定)の、実際の運用での影響
- conntrack の表が大きいホストでの、エージェントの収束のメモリと時間。収束は IPv4 のエントリをすべて読んで持つ
- リンクや nftables の変更が頻繁なホスト(コンテナを次々に作る Docker のホストなど)での、変更の通知の後の見直しの負荷。見直しは通知をまとめるたびにテーブルと wgft0 を読む
