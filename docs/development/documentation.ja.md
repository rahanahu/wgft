# 文書の追加と更新

[English](documentation.md) · [開発資料](README.ja.md)

## 情報の正本と参照範囲

文書はチェックアウトした版を対象にし、main には未リリースの変更も含まれます。
リリース済みの版は、対応する Git タグの文書と release notes で確認します。
[マニュアル](../manual/README.ja.md)は確認済みの導入と運用を説明し、[設計仕様](../design/README.ja.md)は動作と互換性を、[テストの規範](testing.md)は必須の確認を定めます。
[追加テストの台帳](testing-catalog.md)は未実装の試験と確認の限界を示し、[ラボの手順](../../lab/README.md)は実行方法を説明します。
変更する前に、開発上の約束と対象の話題を確認します。

現行文書には制約、未実装の提案、判断を理解するために必要な理由を残します。
以前の仕様と完了した計画は Git の履歴で、変更の理由と詳細な検証結果は PR で、リリースごとの差は release notes で確認します。
作業中の草稿は作業ブランチに置き、提案と未実装の範囲を明示します。
文書をマージした事実だけでは、実装と検証の完了を確認できません。

## 文書の追加と変更の手順

1. 対象を扱う正本を更新し、関連ページからリンクして規範の重複を避けます。
2. 決定事項を変える場合は、現行の設計を先に直してから実装します。実装済みと記す前にコードと関係するテストを確認します。公開する手順のコマンドはラボか対象の実機で実行し、未確認の環境と未実装の部分を明記します。
3. 日英の対は構成と情報量を揃え、言語リンクを相互に置きます。日本語だけの設計本文は単一言語のまま保持でき、日英の索引で言語を示します。
4. 索引は現行の話題を案内します。完了した計画と詳細な実験記録は現行文書から外し、必要な理由を対象の仕様に残して、詳細な証拠は Git と PR で保持します。
5. 公開済みの URL と fragment は、短い案内ページか明示アンカーで維持します。維持する旧ページとアンカーは `scripts/check-docs-policy.json` に登録します。
6. 文書の検査を実行し、スクリプトと fixture を変える場合は[テストの規範](testing.md)も適用します。

## 更新の時点

- 決定時:現行の契約を更新し、判断に必要な理由と未確認の前提を残します。
- 実装時:コードとテストを確認し、実装した挙動だけ未実装の表示を解除します。関係する手順と制約を更新し、検証結果と測定値は PR に記載します。
- リリース時:タグの実装と文書を照合し、README の Status と release notes を更新して、更新手順と環境ごとの制約を確認します。

公開文書には、別の改訂ログを追記しません。
以前の本文は Git の履歴で参照できます。

## 生成するリファレンスと画像

`docs/cli.md` は手で編集しません。
`cmd/wgft/helptext.go` を変更し、同じコミットでリファレンスを生成し直します。

```sh
go test ./cmd/wgft -run TestCLIDocUpToDate -update
```

`TestCLIDocUpToDate` はヘルプとの一致と、実行可能なコマンドの使用例を検査します。
ヘルプの挙動はラボで確認したものだけを書きます。
README はコマンド一覧を重複させず、リファレンスと `wgft <command> --help` に案内します。
Web UI のテンプレート、文言、サンプルデータを変更した場合は `scripts/screenshot-ui.sh` を実行し、画像の差分を確認します。
前提と手順はスクリプトの冒頭に従います。
README の図は Mermaid にします。

## 自動検査の範囲

```sh
python3 scripts/check-docs.py
python3 scripts/check-docs-test.py
bash scripts/check-ascii-punct.sh
```

`lint-output` は、文書だけの変更も含めて push と PR で文書を検査します。
検査は追跡済み Markdown の相対ファイルへのリンク、Markdown の fragment、明示アンカー、重複見出しの slug、参照形式のリンクを対象にします。
fence、インラインのコード、コメントを除外し、外部 URL は取得しません。
Markdown 以外の fragment、表示された HTML のリンク、独自の Markdown 拡張は対象外です。
生成する CLI の使用例は Go テストが確認し、CLI の見出しへのリンクは文書の検査が確認します。

日英の対は `.ja.md` のファイル名か、相互の `<!-- docs-pair: other-file.md -->` コメントで宣言します。
検査は相手の存在と相互のリンクか宣言を確認し、翻訳の品質は判定しません。
旧案内ページには `<!-- docs-status: deprecated -->` を付け、旧ページの登録で URL とアンカーを維持します。
登録した現行索引から旧ページへ案内する場合は、旧リンクの節に置き、その行に `<!-- docs-history -->` を付けます。
意味の一致、実装状態、検証の証拠は保守者が確認します。

## 日本語と公開表記の規範

日本語を書く前に、[文章スタイル](https://raw.githubusercontent.com/megmogmog1965/claude-code-writing-style/main/plugins/writing-style/skills/style-review/references/rules.md)、[日本語技術文書の文章規範](https://gist.githubusercontent.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d/raw)、[緩みと駄文の見分け方](https://gist.githubusercontent.com/k16shikano/eb2929f13ed19c97188393d297be8432/raw)の「駄文の見分け方」だけを読み直します。
括弧とコロンを ASCII にするプロジェクトの約束を優先します。
です・ます体、一文一行、明示した主語、話題を特定する見出しで書きます。
体言止め、曖昧な指示語、擬人化、直訳、くだけた語を避け、未確認の主張は明記します。
箇条書きのラベルは名詞句と ASCII のコロンにします。
定着した訳語のない語は、意味を担う語を選ぶか、具体的な挙動で説明します。
README の括弧の補足は、できるだけ別の文にします。
README、SECURITY.md、ツールの出力は英語を主言語とし、対の文書も同じ情報を保持します。
