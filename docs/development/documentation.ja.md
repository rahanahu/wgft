# 文書の追加と更新

[English](documentation.md) · [開発資料](README.ja.md)

## 情報の正本と参照範囲

リポジトリの文書は、参照しているブランチの状態を対象にします。
`main` の文書には、最新のリリースに含まれない変更もあります。
リリース済みの挙動は、そのタグの文書と release notes で確認し、マージ済みの設計だけから実装済みと判断しません。

| 情報 | 正本 |
|---|---|
| 挙動、制約、互換性の保証 | [設計索引](../design/README.ja.md)から参照する現行仕様です |
| 導入と運用 | [利用者向け索引](../manual/README.ja.md)から参照する現行手順です |
| テストの関門と契機 | [テストの規範](testing.md)です |
| ラボの構築と実行 | [ラボの手順](../../lab/README.md)と各スクリプトの冒頭です |
| 未実装の試験と確認の限界 | [追加テストの台帳](testing-catalog.md)です |
| パッケージの責務と処理の経路 | [アーキテクチャ](architecture.md)です |
| コミットとリリースの手順 | [コミット](commits.md)と[リリース](releases.md)です |
| 過去の判断の理由と測定結果 | 設計と開発の履歴、および該当する PR です |
| CLI のヘルプと使用例 | `cmd/wgft/helptext.go` です。[CLI リファレンス](../cli.md)を生成します |

開発者と coding agent は、リポジトリの入口の約束を読み、対象分野の索引から変更に関係する節を選びます。
判断の理由、旧い挙動、測定の原条件が必要な場合に履歴を参照します。
導入手順の修正だけで、すべての設計記録を読む必要はありません。
複数の分野に影響する決定を変更する場合は、隣接する制約へのリンクも確認します。

## 文書の追加と変更の手順

1. 情報の種類から正本を選びます。既存のページが対象を扱う場合はそのページを直し、関連ページからリンクします。
2. 決定事項を変える場合は、設計を先に直してから実装します。草稿は作業ブランチに置き、提案と未実装の範囲を明示し、判断の理由は現行の契約と分けて記録します。
3. 実装済みの挙動を書く前に、コードと関係するテストを確認します。手順として公開するコマンドはラボか対象の実機で実行し、未確認の環境、未実装の部分、制約を明記します。
4. 日英の対は、構成と情報量を揃えて同じ変更で更新します。各言語で自然に書き、言語切り替えのリンクを相互に置きます。日本語だけの設計本文は単一言語のまま保持でき、日英の索引で言語を示します。
5. 対象の索引に、情報の役割が分かる名前とリンクを置きます。完了した計画は現行の作業一覧から履歴へ移し、現行の判断を理解するための理由を残します。
6. 旧 URL と見出しへのリンクは、廃止済みの案内ページか明示アンカーで維持します。新しい正本の節へ案内し、旧ページの廃止状態を明示します。維持するページとアンカーを `scripts/check-docs-policy.json` に登録し、削除する場合は公開済みのリンクの扱いを明示して決定します。
7. 文書の検査を実行し、表示された見出しとリンクを確認します。確認済みと未確認の範囲を報告し、スクリプト、テストの fixture、ワークフローを含む場合は[テストの規範](testing.md)に従います。

マージ済みの仕様は、契約か明示された計画です。
マージした事実だけでは実装の存在を確認できません。
設計草稿を持つブランチでは実装状態を記し、最新のリリースの挙動として案内しません。
「v1 の前に必須」のような過去の条件は、当時の範囲と出典を付けた記録に保存します。

## 更新の時点

- 決定時:現行仕様を更新し、理由、代案、未確認の前提を履歴に記録します。
- 実装時:コードとテストを確認し、実装した部分だけ未実装の表示を解除します。影響する手順、例、索引、確認の制約も更新します。
- リリース時:タグの実装と文書を照合し、最新リリースとの差、README の Status、release notes を更新します。更新手順と環境ごとの未確認の範囲も確認します。

実験の改訂記録には、結果、設計と仕様への影響、未確認の点を書きます。
測定値の一覧、試行回数、所要時間は PR の本文に書きます。
完了した計画には対象を限定した題名、履歴の状態、元の版を付け、現行の作業として扱いません。

## 生成するリファレンスと画像

`docs/cli.md` は手で編集しません。
ヘルプを変更した場合は、同じコミットで生成し直します。

```sh
go test ./cmd/wgft -run TestCLIDocUpToDate -update
```

`TestCLIDocUpToDate` はヘルプとの一致と実行可能なコマンドの使用例を検査します。
ヘルプの挙動はラボで確認したものだけを書きます。
README はコマンド一覧を重複させず、生成するリファレンスと `wgft <command> --help` に案内します。

Web UI のテンプレート、文言、サンプルデータを変更した場合は `scripts/screenshot-ui.sh` で撮り直します。
スクリプトの冒頭の前提と手順に従い、コミットの前に画像の差分の大きさを確認します。
README の図は Mermaid にします。

## 自動検査の範囲

```sh
python3 scripts/check-docs.py
python3 scripts/check-docs-test.py
bash scripts/check-ascii-punct.sh
```

`lint-output` は文書だけの変更も含め、push と PR で文書の検査を実行します。
週次の脆弱性の検査は別です。
リンクの検査は追跡済み Markdown の相対ファイル、Markdown の見出し、HTML の明示アンカー、GitHub 形式の重複見出し、参照形式のリンクを対象にします。
fence、インラインのコード、HTML コメントを除外し、外部 URL は取得しません。
Markdown 以外のファイルの fragment、HTML のリンク、独自の Markdown 拡張は対象外です。
生成する CLI の本文は生成元の Go テストで確認するため解析から除外しますが、CLI の見出しへのリンクは確認します。

日英の対は `.ja.md` のファイル名か、任意の相互コメント `<!-- docs-pair: other-file.md -->` で宣言します。
検査は相手の存在と相互の言語リンクか宣言を確認し、翻訳の品質と意味の一致は判定しません。
単一言語の設計本文と履歴に対の宣言は要りません。
履歴には `<!-- docs-status: historical -->`、旧案内ページには `<!-- docs-status: deprecated -->` を付けます。
検査の設定に登録した現行索引からこれらを参照する場合は、履歴か旧リンクの節に置き、その行に `<!-- docs-history -->` を付けます。
登録した旧ページとアンカーの削除も検出します。
実装と検証の完了は自動検査で決めず、保守者が証拠を確認します。

## 日本語と公開表記の規範

日本語の文書を書く前に、次の規範を読み直します。
括弧とコロンは ASCII にするプロジェクトの約束を優先します。

- [文章スタイル](https://raw.githubusercontent.com/megmogmog1965/claude-code-writing-style/main/plugins/writing-style/skills/style-review/references/rules.md)に従います。
- [日本語技術文書の文章規範](https://gist.githubusercontent.com/k16shikano/fd287c3133457c4fd8f5601d34aa817d/raw)に従います。
- [緩みと駄文の見分け方](https://gist.githubusercontent.com/k16shikano/eb2929f13ed19c97188393d297be8432/raw)の「駄文の見分け方」だけを使い、文書自身を語るだけの文を削ります。

です・ます体で、1 文を 1 行に書きます。
項目を主語にした定義文と、内容を特定する名詞句の見出しを使います。
体言止め、曖昧な指示語、擬人化、翻訳調、くだけた語を避け、未確認のことは未確認と書きます。
箇条書きのラベルは名詞句と ASCII のコロンにします。
定着した日本語の無い語は、意味を担う語か具体的な説明を選びます。
README の括弧による補足はできるだけ別の文にします。
README、SECURITY.md、ツールの出力は英語を基本とし、日英の対は同じ情報を保持します。
