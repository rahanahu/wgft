### B7 の not_active の確認

`proto/version.go` の `SupportedCapabilities` は空で、capability に紐づく機能をまだ持ちません。
最初の capability を追加するとき、旧い側が表せない機能を理由付きの `not_active` にする確認を `lab/version-skew.sh` に追加します。
登録、全体状態の配信、転送、再接続の試験は既に実装されています。

### C1 悪い条件のネットワーク

未実装の計画は、homerouter の WAN に損失、遅延、並べ替えを加える試験です。
経路 MTU を 1454 と 1460 に下げ、ICMP を遮断した状態で大きな TCP と UDP の転送を確認します。
WAN のアドレスを変更して NAT の状態を削除した後の再接続と、窃取の誤検知も対象にします。
既定の一式には、この回線条件を再現する仕組みがありません。

### C2 クラッシュと強制停止からの収束

未実装の計画は、ルールの変更中に server を SIGKILL で停止し、再起動後にデータベース、nftables、エージェントの状態が宣言した状態に収束する試験です。
VM の強制停止と、ディスクへの書き込みの途中での停止も対象にします。
L4 の変更の無い状態での再起動と、A4 の故障注入では、この条件を確認しません。

### C3 規模の試験

`lab/scale.sh` は、1 台の server と 5 台のエージェントで 10 本から 1000 本のルールを試します。
`rule import` のバッチと `rule add` の逐次追加で、適用時間、全体状態の大きさ、RSS、Web UI の応答を確認します。
1 台あたり 512 本を超えるルールは次のエージェントに置きます。
A9 には含めず、段階の完了ごとに両モードで実行します。
過去の結果を現在の HEAD の規模の保証に使いません。

### C4 ラボの一式を別のディストリビューションで

`WGFT_LAB_IMAGE` と `WGFT_LAB_VM` で別の Lab Host VM を選び、同じ一式を実行します。
過去に Debian 12、Ubuntu 24.04、Fedora 44 の既定のイメージで判定の一致を確認しました。
その Fedora のイメージには firewalld と SELinux のポリシーが入っていませんでした。
SELinux enforcing と firewalld 有効の条件、および現在の HEAD での再実行は未確認です。

### C5 長時間の TCP と UDP

未実装の計画は、1 本の TCP と 1 本の UDP を 1 時間以上保ち、WireGuard の通常の鍵の更新、ハートビート、conntrack の期限をまたぐ試験です。
`agent rotate-key` はトンネルを作り直して既存のセッションを切る仕様なので、継続の条件に含めません。
別の確認で、`agent rotate-key` 後に新しい TCP と UDP が戻ることを確かめます。

### C6 小さいメモリの環境

未実装の計画は、cgroup で server と agent のメモリを 256 MiB に制限し、`WGFT_MAX_UDP_FLOWS=2048` と `WGFT_MAX_TCP_FLOWS=1024` で上限を超えるフラッドを与える試験です。
判定は OOM の退行を対象にします。
設計上の上界はこの設定でも 256 MiB を超えるため、この試験は上界の内側に収まる保証を与えません。

### D4 旧版からの更新

`lab/upgrade.sh` は既定で v1.1.3 のデータに現在のビルドを重ねます。
既定は直前のリリースを意味しません。
`WGFT_UPGRADE_OLD_VERSION` で旧版を指定し、v0.4.0 の更新も確認できます。
両モードで、代表的な 7 種のルール、鍵、認証情報、再登録無しの復帰、片側だけを先に更新する両方の順序を確認します。
更新後には agent の無効化、有効化と server 再起動後の保持も確認します。
userspace の server の公開鍵は CLI と API で取得できないため、鍵の保持は agent 側の公開鍵だけで確認します。
旧版との比較で TCP の packet_rate、Relay の IPv4 待ち受け、Resource Guard の行の変化を判定し、旧版自身が既に持つ挙動は SKIP します。

`scripts/dist-vm.sh --upgrade` は、2 台の使い捨て VM で同梱の unit と VM の再起動を含む更新を確認します。
旧版は HEAD から辿れる安定版タグと、HEAD より前に作られた辿れない安定版タグから選びます。
HEAD 自身のタグとプレリリースは除き、辿れないタグは辿れる最大の版の major.minor 以下に限ります。
候補の最大の版を選び、`WGFT_DIST_VM_UPGRADE_OLD_VERSION` で上書きできます。
保守ブランチのリリースを選べない場合は、旧版を明示します。
旧版の unit で導入し、7 種のルールの転送とデータのバックアップ後に server、agent の順でバイナリを更新します。
各段階でルールの一致、再登録無しの再接続、転送、`server check` を確認し、最後に両 VM を順に再起動します。
unit の有効な行が変わらなければ、unit も入れ替える別経路は SKIP します。
転送の停止時間は測定するだけで、上限の保証には使いません。
データベースを読めない場合の失敗は、systemd が修復するディレクトリではなくファイルの権限で確認します。

この追加の段階は過去に Debian 12 で確認しました。
Ubuntu 24.04、Fedora 44、Docker/compose の更新経路、agent を先に更新する unit の経路は未確認です。
現在の HEAD での実行も未確認です。
旧版への戻しは[互換性の保証](testing.md#更新と戻しの約束)に含めません。
