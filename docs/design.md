# wgft 設計文書

VPS で受けた TCP/UDP を WireGuard 経由で自宅のサービスへ届けるツール。
名前は WireGuard Forwarding Tool の略。

## 背景と全体像

自宅のサービス(ゲームサーバ、Web サービス)を、固定 IP を持つ VPS 経由でインターネットに公開したい。
自宅側は NAT 配下でポート開放を避けたいので、自宅から VPS へ WireGuard トンネルを張り、VPS に届いたパケットをトンネル経由で自宅へ転送する。
この構成は Pangolin から着想を得た。Pangolin を使う中で VPS を入口にして自宅サービスを公開する構成の便利さを知った一方、ゲームサーバなどの raw TCP/UDP 転送だけが目的なら、より直接的で小さな構成が欲しくなった。
また、日本の IPv4 over IPv6 接続の一部では任意の受信 IPv4 ポートを使えない場合があり、VPS を入口にする構成はその制約を避ける用途にも合う。
そこで WireGuard と nftables を直接組み合わせ、その手作業をツールに置き換える。

置き換え後の全体像は次のとおりである。

- DNS:ワイルドカードレコードで VPS の IP を指す
- VPS:本ツールが、指定したポートを自宅へ素通しする。接続元 IP による制限もここで行う
- 自宅:本ツールのエージェントがトンネルを張り、届いたパケットを LAN 内のサービスへ中継する。HTTPS は自宅側のリバースプロキシ(Caddy)が TLS 終端とホスト名の振り分けを担う

本ツールは L4 の転送だけを担当し、TLS、証明書、認証は扱わない。

## 1. 目的と範囲

VPS から自宅へのポート転送に必要な nftables と WireGuard の手作業設定をなくすことが目的である。

やること:

- 任意の TCP/UDP ポートを VPS から自宅の任意ホストへ転送する
- 自宅側はエージェントを置くだけで繋がる(自宅側のポート開放は不要)
- 転送ルールごとに、接続元 IP による許可と拒否、レート制限を VPS 側で行う
- 転送ルールの追加削除を Web UI と CLI から行う
- 既存の nftables ルールを壊さない

やらないこと:

- TLS 終端、証明書取得、SNI やパスによる振り分け(自宅側の Caddy が担う)
- 認証ゲート、共有リンク
- L7 の解釈全般
- 接続元 IP を自宅側のサービスへ伝えること(TCP の PROXY protocol を除く)

## 2. 全体構成

| 部品 | 動作場所 | 役割 |
|---|---|---|
| `vpsd` | VPS | wg0 の管理、nftables の適用、conntrack の操作、API と Web UI、状態の保存 |
| `agent` | 自宅 | `vpsd` への登録、wg トンネルの維持、届いたパケットの LAN 内サービスへの中継 |
| `proto` | 両方 | 登録と全体状態配信の JSON スキーマを定める共有ライブラリ。実行されるプロセスではない |

実装言語は Go。
`vpsd` と `agent` は同一バイナリで、サブコマンド `server` と `agent` で切り替える(起動はそれぞれ `wgft server run`、`wgft agent run`)。`vpsd` は本書と内部での呼び名で、利用者に見えるコマンド名は `server` である。
`vpsd` は wgctrl-go で WireGuard を、google/nftables で nftables を、ti-mo/conntrack で conntrack を直接操作し、Web UI はバイナリに埋め込む。
`agent` は wireguard-go と gVisor の netstack でトンネルをユーザー空間に持ち、カーネルの設定を変更しない。

## 3. 用語

- **`vpsd`**:VPS 側で動くデーモン。`wgft server run` で起動するプロセスを本書と内部ではこう呼び、利用者に見える名前(コマンド、設定ファイル、unit)は `server` である
- **エージェント**:自宅側で動く `agent` の 1 インスタンス。1 拠点に 1 つ置く想定だが、複数登録できる
- **ルール**:「VPS の `<proto>/<port>` を、エージェント `<name>` 経由で `<host>:<port>` へ届ける」という 1 行の宣言
- **接続元制限**:ルールに付ける、接続元 IP の許可リスト、拒否リスト、レート制限
- **全体状態**:`vpsd` がエージェントに配る、そのエージェントに関わる wg 設定とルール集合の全体
- **世代**:全体状態の版を表す単調増加の整数。エージェントに配る内容が変わったときだけ `vpsd` が増やし、SQLite に保存する。管理用 API の 1 リクエストで上がる世代は最大 1 つ
- **リスナー**:エージェントが netstack 上に開く待ち受け。単一ポートごとに 1 つで、`(proto, port)` で同一性を取る。状態として実効宛先(`host:port`)と所属ルール ID を持つ
- **状態ファイル**:エージェントが恒久トークン、wg の秘密鍵、証明書のハッシュ、最後の全体状態を保存するファイル(`agent.json`。9 節)。本書と内部では状態ファイルと呼び、利用者に見える文言(UI、CLI、README)では**認証情報**(英語は credentials)と呼ぶ。`vpsd` 側の SQLite は別物で、利用者向けにはサーバのデータベースと呼ぶ
- **stream**:エージェントが `vpsd` に張る常時接続(WebSocket)。全体状態の配信、公開鍵の宣言、ハートビートに使う(5.2 節)
- **エージェント用 API** と **管理用 API**:`vpsd` が持つ 2 つの HTTP リスナー。前者は公開でエージェントの登録と stream だけを受け、後者は Unix ソケット(既定)か Tailscale のアドレスで Web UI と CLI が使う(5 節、11 節)
- **カーネルモード** と **プロキシモード**:VPS 側の転送方式。前者は nftables の DNAT でカーネルが転送し、後者は `vpsd` 自身が TCP を受けて中継する(6 節)。ルールごとに `vps_mode` で選ぶ
- **疎通確認**:管理者が UI から、`vpsd` 経由で自宅の `target` に届くかを試す操作(10.1 節)

## 4. ネットワーク

- `vpsd` の WireGuard インタフェースの既定名は `wgft0`(`--wg-interface` で変更可)。一般的な `wg0` を既定にすると、既に `wg0` を使っている VPS で既存の WireGuard を壊すため(9 節の所有判定と併せた対策)。本書では読みやすさのため以降も `wg0` と書くが、実際の既定名は `wgft0` を指す
- wg0 のアドレス帯は `10.200.0.0/24`。`vpsd` が `.1`、エージェントには登録時に `.2` 以降を割り当てる。stream に一度も来ないエージェントもアドレスを持ち、無効化で回収される
- VPS で外に開けるポートは次の 3 種類だけ。WireGuard の待ち受け(UDP 51820、変更可)、エージェント用 API(TCP 8443、変更可)、転送対象のポート
- 管理用 API と Web UI は Unix ソケット(既定)か Tailscale のアドレスで待ち受け、インターネットには開けない(11 節)
- wg0 の MTU は `vpsd` が決め(既定 1420)、全体状態でエージェントに渡す。エージェントは netstack の tun に同じ値を使う。TCP はエージェントの netstack で終端され、netstack が自分の MTU から MSS を広告するので、この 2 つが揃っていれば wg0 の MTU を超える TCP は生まれず、VPS 側に MSS クランプは要らない。ずれると、PMTUD の ICMP が途中で落ちる経路で大きな TCP が止まる
- wg0 の MTU 1420 は、外側の回線の MTU が 1500 である前提の値である。自宅回線の MTU が小さい場合(PPPoE の 1454 など)でも、WireGuard の外側の UDP は DF なしなので途中でフラグメントされて動くが、大きなパケットがすべて 2 つに割れる。回線の MTU が分かっているなら `vpsd` の MTU を下げる方が効率がよい(全体状態でエージェントにも渡る)。また、トンネル一般の挙動として、DF 付きで 1393 バイト以上のペイロードの UDP を送る client は初回だけ ICMP fragmentation needed で失敗し、経路 MTU を学習した後は通る(実験で確認)
- エージェントは `PersistentKeepalive = 25` で NAT 越しに接続を維持する。keepalive の 5 倍の間ハンドシェイクが成功しなければ、エージェントはエンドポイントの名前を引き直してピアに設定し直す
- VPS の conntrack の UDP タイムアウト 2 値(`nf_conntrack_udp_timeout` と `nf_conntrack_udp_timeout_stream`)は `vpsd` が起動時に読み、全体状態でエージェントに渡す
- `vpsd` は wg0 上で待ち受けをしない。エージェントへ張る接続(プロキシモードの中継、疎通確認)はすべて `vpsd` 側から外向きに開く
- IPv4 のみ対応する(IPv6 は未決事項)

## 5. 制御プレーン

制御プレーンは常にエージェントから `vpsd` への外向き HTTPS で行う。
`vpsd` からエージェントへ接続を張ることはない。

`vpsd` は 2 つのリスナーを持つ。

- **エージェント用 API**:公開。`/api/v1/agents/register` と `/api/v1/agents/stream` だけを露出する。TLS 証明書は `vpsd` が初回起動時に生成する有効期限 10 年の自己署名証明書で、秘密鍵ごと SQLite に保存する
- **管理用 API**:既定は Unix ソケット。Web UI と CLI が使う。独自の認証は持たず、接続経路(ソケットのパーミッション、SSH、Tailscale)に任せる(11 節)

エージェント用 API を wg 経由に切り替えない理由は、wg が落ちたときに制御まで落ちると復旧の手がかりが減るからである。

### 5.1 登録

人が扱うのは接続文字列 1 本だけである。
登録は初回だけ行い、目的は恒久トークンを得ることに限る。

1. 管理者が Web UI か CLI で接続文字列を発行する。中身はエンドポイント、1 回限りの登録トークン、エージェント用 API の証明書の SHA-256 で、`wgft://host:port/token#sha256:...` の形をとる。トークンにはエージェント名を紐付ける
2. エージェントは接続文字列を環境変数 `WGFT_JOIN` か引数で受け取る。名前は環境変数 `WGFT_NAME` か引数で任意に受け取る。接続先の証明書がハッシュと一致しなければ中断する
3. エージェントは登録トークンを登録 API へ送る。名前を受け取っていれば名前も送り、名前がトークンに紐付いたものと違えば `vpsd` は拒否する。名前を送らなければ、トークンに紐付いた名前で登録する。名前はトークンに紐付いているので、自宅側で同じ名前をもう一度入力させる必要はない
4. `vpsd` はエージェントを SQLite に作り、恒久トークン、割り当てアドレス、確定した名前を返す。この時点では wg ピアはまだない
5. エージェントは恒久トークンと名前を状態ファイル(9 節)に保存し、stream に接続する。wg ピアの作成と設定の受け取りは stream で行う(5.2 節)

トークンの扱いは次のとおり。

- 登録トークンと恒久トークンは 128 ビット以上の乱数。SQLite にはハッシュだけを保存し、比較は定数時間で行う
- 登録と stream 接続の試行は送信元 IP ごとにレート制限する
- 登録トークンは 1 回限り、既定の有効期限は 1 時間
- 同じ名前に対して新しい登録トークンを発行すると、その名前に対する以前の未使用トークンはすべて無効化する。有効なトークンは常に最新の 1 本だけであり、複数の接続文字列が同じ名前で有効なままにはならない
- エージェントを無効化すると、その名前に対して発行済みの未使用トークンも合わせて無効化する。無効化の前に発行され、まだ登録に使われていない古い接続文字列は、無効化のあとは使えない

無効化された恒久トークンを持つエージェントの復帰経路は次のとおり。
stream の認証が拒否(401)され、かつ `WGFT_JOIN` が与えられていれば、エージェントは初回登録をやり直す。
状態ファイルは初回登録が成功した時点で置き換え、失敗したら既存のファイルを残したまま止まる。
`WGFT_JOIN` は compose ファイルに残されたままになりやすく、管理者の誤操作や SQLite の復元で 401 が返ったとき、期限切れのトークンで登録に失敗して鍵まで失うことを防ぐためである。
状態ファイルには使用済みの登録トークンのハッシュを残し、`WGFT_JOIN` の値がそれと同じなら登録を試みずにエラーで止まる。
一時的な失敗(5xx、接続不能)は認証拒否と区別し、復帰経路に入らず再接続を続ける。
`WGFT_JOIN` がなければエラーを出して止まる。
無効化したエージェントの名前は新しい接続文字列で再利用でき、割り当てアドレスは回収される。

サーバ証明書が変わったエージェントの復帰経路は次のとおり。
証明書が変わるのは `teardown --purge` のあとに `vpsd` を立て直したときで、エージェントの状態ファイルにあるピンと一致しなくなる。
エージェントはピンの不一致をほかの接続失敗と区別する。
`WGFT_JOIN` が与えられ、使用済みではなく、そのピンが状態ファイルのピンと違うときだけ、その接続文字列で初回登録をやり直す。
新しいピンを信頼する根拠は管理者が与えた接続文字列であり、登録トークンはそのピンに一致するサーバにしか送られないので、初回登録と同じ安全性になる。
状態ファイルの扱いは 401 の復帰経路と同じで、登録が成功した時点で置き換え、失敗したら既存のファイルを残す。
条件を満たす `WGFT_JOIN` がなければ、停止せずに再接続を続け、新しい接続文字列が要ることをログで案内する。ピンの不一致は経路上の第三者が TLS を終端しているときにも起き、その場合は待てば元のサーバに戻るためである。

接続文字列が漏れた場合、先に登録した側だけがエージェントになれ、本物は登録失敗で気付ける。
本物の起動後に漏れても、トークンは使用済みか期限切れなので使えない。
漏れた登録で得られるのは、無効化されるまで有効な恒久トークン 1 つである。
それで得られる wg0 上の 1 ピアは、ピア同士の通信も、wg0 から VPS 自身への新規接続も、wg0 から VPS の他のインタフェースへの転送も 6.1 節で遮断するため、到達できる先がない。
第三者の接続は、5.2 節の IP の食い違いの警告と、10.1 節の両 IP の表示で管理者に見える。

### 5.2 全体状態の配信とハートビート

stream は双方向で、エージェントは自分の公開鍵を、`vpsd` は全体状態を、それぞれ宣言し、接続のたびに両方が収束する。

接続時:

- エージェントは `/api/v1/agents/stream` に WebSocket で接続し、恒久トークンで認証したのち、最初のメッセージで自分の wg 公開鍵を送る
- `vpsd` は宣言された公開鍵を検証する。32 バイトの正しい形式であること、他のエージェントの保存値ともサーバ公開鍵とも一致しないことを確認し、違えば接続を拒否する。同じ公開鍵のピアを 2 つ持てず、後から設定したピアが先のピアを上書きするため、他エージェントの鍵を受け入れるとそのトンネルが壊れる
- `vpsd` は保存している公開鍵と違えば、そのエージェントのピアを新しい公開鍵で置き換える。初回接続ならピアを作る
- `vpsd` は続けて全体状態を送る

処理の順序は、認証、鍵の検証、ピアの置き換え、旧接続の切断、全体状態の送信で固定する。
鍵の検証に失敗した接続は旧接続に影響を与えない。
同一エージェントの接続処理は `vpsd` 内で直列化する。

stream はエージェントごとに 1 本だけである。

- 新しい接続が認証されたら、`vpsd` は旧接続を理由コード `superseded` で閉じる。旧 TCP が死んでいる場合に備え、常に新しい方を優先する
- 閉じられた側は指数バックオフ(初期 1 秒、上限 5 分)で再接続する。これは善意の二重起動どうしの振動を抑える手段であり、バックオフを守らない第三者に対する保証ではない。窃取に対する保証は後述の警告と無効化だけである
- 置き換えそのものは検知の対象にしない。二重起動、`agent rotate-key`、再起動、回線の IP 更新のいずれでも起きる正常な事象で、窃取と区別する材料にならないためである。窃取は下の「IP の食い違い」で見る

配信:

- `vpsd` は接続直後と、そのエージェントに配る内容が変わるたびに、全体状態を送る。差分ではなく全体を送る
- 世代の比較は同一 WebSocket 接続内に限る。接続直後の最初の全体状態は世代に関わらず必ず適用し、以後は手元より古い世代を捨てる。`vpsd` の再構築やバックアップからの復元で世代が巻き戻っても、これで収束する
- エージェントは全体状態を「宣言された状態に収束させる」方式で適用する。wg 設定が変わればトンネルを張り直し、リスナーは変わったものだけを開閉する。収束の単位は 7 節に定める

ハートビート:

- エージェントは 30 秒ごとに送る。中身は処理済み世代(最後に受け取って処理した世代。部分失敗でも進める)、トンネルの状態(`ok` または `error` と理由、エンドポイントの解決結果)、ルールごとの状態(`ok` または `error` と理由)
- ルールの `error` は、リスナーの開放失敗(bind できない)か、TCP ルールで適用時の `target` への接続確認が失敗した場合を指す。UDP は到達確認ができないので開放失敗だけを見る。`error` のトンネル設定とルールは、エージェントが 30 秒ごとに再適用と確認を試み、状態が変わったら次のハートビートで報告する。所属ルール ID が移ったリスナーの状態は、移った直後の再確認で新しいルール ID に付け替える
- `vpsd` は最終ハートビート、処理済み世代、トンネルとルールの状態、wg の最終ハンドシェイク時刻を記録し、UI に表示する
- `vpsd` は 15 秒ごとに wg のピア状態(wgctrl の `Endpoint` と最終ハンドシェイク時刻)を読み、下の検知に使う

窃取の検知:

- `vpsd` はエージェントごとに 2 つの IP を観測している。**stream の接続元 IP**(最終ハートビートが 45 秒以内の、生きている接続のもの)と、**wg ピアのエンドポイント IP**(最終ハンドシェイクが 3 分以内のもの)である。本物のエージェント 1 つだけが動いていれば、この 2 つは常に同じ IP になる
- 両方が観測でき、かつ食い違っている状態が 2 分間(15 秒間隔の監視で連続 8 回)続いたら、`ip-mismatch` の警告を 1 件残す。中身は両 IP と日時
- 食い違いだけでは、第三者と本物の両方がフル稼働で置き換え合う場合を取りこぼす(ラボで実測)。WireGuard は認証済みパケットを受けるたびにエンドポイントを送信元へ更新するので、同じ鍵を 2 か所から使うとエンドポイントは keepalive のたびに両者の間を往復し、15 秒ごとの観測ではほぼ毎回ランダムになる。stream は supersede の後しばらく安定するため、食い違う確率は各観測で約 1/2 にとどまり、8 回連続は期待値で 1 時間ほどかかる。そこで第 2 の判定を置く
- **IP の往復**:`vpsd` はエージェントごと、チャネル(stream の接続元 IP、wg エンドポイント IP)ごとに、直近 10 分間に観測した IP の変化を記録する。stream は接続が認証されるたびに、wg は 15 秒ごとの観測で記録する。同じチャネルの IP が 10 分以内に A → B → A と、以前の値へ戻ったら `ip-flapping` の警告を 1 件残す。中身はチャネル、往復した 2 つの IP、回数と日時。正規の運用で IP が変わるのは回線の更新だけで、それは一方向にしか動かない。同じチャネルが往復するのは、同じ鍵か同じ恒久トークンを 2 か所が使っているときだけである
- 2 つの判定の分担:フル稼働の置き換え合いと、本物が再接続や keepalive を続けている非対称の窃取は「往復」が数十秒から 1 分で捕まえる。本物が片方のチャネルで黙っている場合(stream を奪われて再接続できていない、など)は「食い違い」が 2 分で捕まえる
- どちらでも検知できない場合:本物のエージェントが完全に止まっていて第三者だけが動いているとき。往復も食い違いも起きず、正規の引っ越しと区別できない。これは IP を根拠にする限り検知できないので、受け入れる
- 自宅回線の IP 更新では警告しない。旧 IP の stream は TCP ごと死んでハートビートが止まり、45 秒で観測対象から外れる。新しい stream は新しい IP から来て、wg のエンドポイントも同じ IP に動くので一致する。2 分の猶予はこの入れ替わりの間の一時的な食い違いを吸収するためのものである
- どちらの警告も自動で消さない。置き換え合いの最中に出たり消えたりしないためである。同じ内容が再検出されたら日時と回数を更新するだけで、件数は増やさない
- 警告への対処は恒久トークンの無効化しかないので、UI では警告の隣に無効化と「警告を消す」の操作を置く。「消す」は正当な事情(自分で 2 拠点から動かした、など)を管理者が確認したときに使う
- 以前の版にあった置き換え回数の警告、二重接続の警告、交互置き換えでの受け付け停止、既知エンドポイント IP 集合と「受け入れる」操作は持たない。「往復」は以前の交互検出と似ているが、stream の置き換えだけでなく wg エンドポイントも見ること、受け付けを止めず警告にとどめること、管理者に IP の登録を求めないことが違う。回線の IP 更新のたびに管理者の操作を要求する割に、守っている資産(wg0 上の 1 ピア。5.1 節のとおり到達できる先がない)に見合わないためである

全体状態の形:

```json
{
  "generation": 42,
  "wg": {
    "server_pubkey": "...",
    "endpoint": "vps.example.com:51820",
    "address": "10.200.0.2/24",
    "mtu": 1420,
    "keepalive": 25,
    "udp_timeout": 30,
    "udp_timeout_stream": 120
  },
  "rules": [ ... ]
}
```

### 5.3 ルールのスキーマ

```json
{
  "id": "r_01J...",
  "agent": "home",
  "group": "valheim",
  "note": "週末サーバ。フレンド用",
  "proto": "udp",
  "listen_port": "2456-2457",
  "target": "192.168.1.20:2456",
  "vps_mode": "kernel",
  "proxy_protocol": false,
  "source_allow": [],
  "source_deny": ["203.0.113.0/24"],
  "new_flow_rate": "100/second",
  "packet_rate": null,
  "per_source_rate": "10/second",
  "enabled": true
}
```

- `group`:任意。ルールを束ねる短いラベル 1 つ(例 `minecraft`)。1 ルールに 1 つ。英数と `-_.`、32 文字以内。転送には影響しない。空のルールは UI で「その他」に入る
- `note`:任意。このルールが何のためかを書く自由記述(120 文字以内)。転送には影響しない
- `proto`:`tcp` または `udp`
- `listen_port`:VPS で待ち受けるポート。`"2456-2457"` の範囲指定も許す。範囲のときは `target` のポートは先頭に対応し、以降は連番で写す。ルール間で重複できない
- `target`:自宅側の宛先。エージェントと同じホストなら `127.0.0.1:port` と書く
- `vps_mode`:`kernel`(nftables で転送)または `proxy`(`vpsd` 内の TCP 中継で転送)。`proxy` は TCP のみで単一ポート運用に限り、`listen_port` を範囲にはできない(カーネルモードとユーザー空間モードのどちらでも中継は 6.2 節の `proxyrelay` を使い、範囲を許すと先頭ポート以外が中継されないまま黙って失われるため)。ユーザー空間モード(6.3 節)では全ルールが `vpsd` 内の中継になるため区別に意味は無く、`proxy` は「PROXY protocol を付けられる TCP の中継」を選ぶ印としてだけ残る
- `proxy_protocol`:`vps_mode = proxy` のときだけ有効。PROXY protocol v2 ヘッダを付けて送る
- `source_deny`:列挙した CIDR を捨てる。最初に評価する
- `source_allow`:空でなければ、列挙した CIDR 以外を捨てる
- `new_flow_rate`:ルール全体の新規フロー数の上限
- `packet_rate`:ルール全体のパケット数の上限
- `per_source_rate`:接続元 IP ごとの新規フロー数の上限
- `enabled`:`false` でリスナーを閉じ、VPS 側のルールも外す。`true` に戻すと開き直す

エージェントに配るのは `id`、`proto`、`listen_port`、`target`、`enabled` だけである。
`vps_mode`、`group`、`note` はエージェントに配らない。`group` と `note` は管理用のメタデータで、転送にも全体状態にも影響しないため、変更しても世代は上がらずエージェントには配信されない。プロキシモードのルールでも、エージェントはカーネルモードと同じく `listen_port` のリスナーを開き、`vpsd` はそこへ接続して中継する(6.2 節)。
接続元制限の変更は全体状態の内容を変えないので、エージェントには配信されず、世代も上がらない。

`listen_port` に WireGuard、エージェント用 API、管理用 API(TCP で待ち受けている場合)のポートを指定した場合、`vpsd` は拒否する。
`target` のポートに範囲の幅を足した実効宛先が 65535 を超える場合も拒否する。
VPS 上のプロセスが `0.0.0.0` か公開 IP で bind 中のポート(`/proc/net/tcp` と `/proc/net/udp` で確認する)も拒否する。SSH のポートを指定して VPS から締め出される事故を防ぐためで、`--force` で上書きできる。

### 5.4 ルールのバッチ操作

管理用 API は、複数ルールの追加、変更、削除を 1 トランザクションで行うバッチ操作を持つ。
バッチの結果で上がる世代は 1 つで、`listen_port` の重複検査はバッチ全体の適用後の状態に対して行う。
ルールの分割と統合はこのバッチで行い、CLI の `rule split` と `rule merge` はバッチの薄い層である。
分割を「縮める、足す」の 2 リクエストで行うと、中間の世代でポートが宣言から消えてセッションが切れるため、バッチが必要になる。
`vps_mode = proxy` のルールは単一ポート運用(5.3 節)のため、分割は結果の両側が単一ポートになる場合だけ受け付ける(2 ポートの範囲を境界で割る場合に限る)。3 ポート以上の `proxy` の範囲は、単一ポート運用にする前から保存されていた既存データとしてしか存在しえず、単発の分割では単一ポートまで割り切れないので、削除して単一ポートずつ作り直す。
統合(`rule merge <id1> <id2>`)は、エージェント、プロトコル、方式、`listen_port` の隣接、実効宛先の連続に加え、PROXY protocol、拒否/許可リスト、3 つのレート、`enabled` がすべて同じ組み合わせだけを受け付ける。これらが違う 2 つを統合すると一方の値が黙って失われるため、条件に含める。`vps_mode = proxy` の組は、隣接していても統合すると必ず 2 ポート以上の範囲になるため、単一ポート運用の制約によりどちらの組み合わせでも統合できない。統合したルールは `id1` の ID・`group`・`note`・接続元制限・レート・`enabled` を保ち、`listen_port` と実効宛先だけを `id2` の分まで広げる。`id2` は削除する。組み立てと検査は CLI と Web UI(10.1 節)で共有する。

バッチ操作は、事前に読んだルール集合のハッシュ(`proto.RulesDigest`)を任意で受け取る(`ExpectedDigest`)。指定すると、バッチはこのバッチ自身が変更しようとしている今のルール集合のハッシュと比べ、一致しなければ何も変えずに専用の誤り(`ErrBatchConflict`。管理用 API では HTTP 409)を返す。この照合は、ルール集合を読み取ってから変更を確定するまでを 1 トランザクションの内側で行うため、読み取りと、それを基にした変更の呼び出しとの間に他経路(別の CLI 呼び出しや別タブの Web UI)が割り込む競合を防ぐ。ルール集合を読んでから確定までの間が開く操作(Web UI の読み込み確認・適用、CLI の `rule import`)がこれを使う。

バッチは変更後のルール集合全体を毎回検査するため、`Rule.Validate` に検査を後から追加すると、追加前から保存されていた、今回のバッチが触っていない既存ルールがその検査に落ち、以後の無関係なバッチまで失敗しうる。これを避けるため、`store.ApplyBatch` は `proto.ValidateUpsert` を使い、バッチの前後で ID・内容が変わらない行には `Rule.Validate` を掛け直さない。ID の重複、予約ポート、`listen_port` の重なりの検査は変更の有無を問わず全体に対して行う(これらは以前から全体を検査していたため、保存済みのデータは既に満たしている)。読み込みも同じ規則に従う。CLI の `rule import` はこのバッチにそのまま送り、Web UI の読み込みの確認ページは、今のルールから変わっていない行を同じ判定(`proto.UnchangedIDs`)で除いてから `Rule.Validate` を掛ける。確認ページだけが全体を検査すると、古い行を変えない読み込みが CLI では通るのに Web UI では適用ボタンが出ない、という経路の差が生まれるためである。行が変わったかどうかの判定では、空の接続元リストの `nil` と空の配列を同じとみなす。

### 5.5 複数サービスへの配り方

エージェントは `target` へ自分から接続するので、宛先はサービスと同じホストでなくてよい。
1 拠点に 1 つのエージェントを置き、ルールごとに `target` を各ホストへ向けるのが基本形である。

```
wgft rule add --agent home --udp 2456-2457 --to 192.168.1.20:2456
wgft rule add --agent home --udp 2458-2459 --to 192.168.1.21:2456
wgft rule add --agent home --tcp 25565     --to 192.168.1.22:25565
```

同じサービスを複数台動かす場合は、VPS 側の `listen_port` をずらし、`target` 側で本来のポートに写す(上の例の 2458 から 2456 への写し替え)。

ホストごとにエージェントを置く構成も同じ仕組みで動く。
ホスト間で到達性がない場合や、片方の停止をもう片方に波及させたくない場合に使う。

## 6. データプレーン(VPS 側)

### 6.1 カーネルモード

`vpsd` は `table inet wgft` を自分専用に持ち、ルール変更のたびにテーブル全体を 1 トランザクションで差し替える。
他のテーブルには一切触れない。
conntrack のエントリは差し替えの影響を受けないので、既存のセッションは切れない。

接続元制限とレート制限は nat ではなく filter の prerouting に置く。
nat のチェーンはフローの最初のパケットしか通らないので、そこに置いた `drop` は通信中のフローに効かないためである。

```
table inet wgft {
  set deny_1  { type ipv4_addr; flags interval; elements = { 203.0.113.0/24 } }
  set meter_1 { type ipv4_addr; flags dynamic; timeout 1m; size 65535; }
  # source_allow が空でないルールなら、次の set と行が加わる(空なら生成しない。空の set に != を書くと全送信元が落ちる)
  #   set allow_1 { type ipv4_addr; flags interval; elements = { ... } }
  #   iifname != "wg0" udp dport 2456-2457 ip saddr != @allow_1 counter drop

  chain filter_pre {
    type filter hook prerouting priority -150; policy accept;
    iifname != "wg0" udp dport 2456-2457 ip saddr @deny_1 counter drop
    iifname != "wg0" udp dport 2456-2457 ct state new add @meter_1 { ip saddr limit rate over 10/second } counter drop
    iifname != "wg0" udp dport 2456-2457 ct state new limit rate over 100/second counter drop
    # packet_rate を設定したルールの場合(5.3 節の例は null なので、実際には生成しない)
    iifname != "wg0" udp dport 2456-2457 limit rate over 5000/second counter drop
  }
  chain nat_pre {
    type nat hook prerouting priority dstnat - 1; policy accept;
    iifname != "wg0" udp dport 2456-2457 dnat ip to 10.200.0.2
    iifname != "wg0" tcp dport 25565 dnat ip to 10.200.0.2
  }
  chain input {
    type filter hook input priority filter - 10; policy accept;
    iifname "wg0" ct state new drop
  }
  chain forward {
    type filter hook forward priority filter - 10; policy accept;
    iifname "wg0" oifname "wg0" drop
    oifname "wg0" ct status dnat accept
    iifname "wg0" ct state established,related accept
    iifname "wg0" drop
    oifname "wg0" drop
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "wg0" ct status dnat masquerade
  }
}
```

- 評価順は deny、allow、接続元ごとの meter、新規フローの集約上限、パケットの集約上限、DNAT の順。`allow` が空のルール、`packet_rate` が未設定のルールでは対応する行を生成しない
- set 名はルール ID ではなく `vpsd` が振る連番を使う。古いカーネルの set 名の長さ制限(32 文字)を避けるためである
- meter は集約上限より前に置く。送信元を偽装したフラッドで meter の set が `size` まで埋まると、その間は `add` が失敗して接続元ごとの制限だけが外れ、集約上限で守る状態になる。順序を入れ替えれば set は埋まらないが、単一の乱用者が集約枠を食い尽くしてから接続元ごとの制限が評価される順になり、正規利用者を守る目的を失うので、この順序と劣化の仕方を採る
- DNAT では宛先アドレスだけを書き換え、ポートは書き換えない。エージェントは VPS と同じポートで待ち受け、`target` のポートへの写し替え(5.3 節の連番)はエージェント側で行う(7 節の実効宛先)
- 公開インタフェース名を特定せず `iifname != "wg0"` で書く
- nat prerouting の優先度を `dstnat - 1` にして、既存の nat チェーンより先に評価されるようにする。先に評価されるのは標準の優先度(`dstnat`。iptables の nat、firewalld、Docker が使う)のチェーンに対してだけで、それより小さい優先度(-199 まで付けられる)のチェーンには負ける。そのため後述の「他テーブルの同じポートの DNAT」の検査は優先度に関係なく行う
- input で wg0 からの新規接続を全部落とす。`vpsd` が wg0 上で待ち受けないので(4 節)、VPS 上の他サービスが wg0 から見える経路をここで塞ぐ
- forward では、先頭でピア同士の通信を遮断し、DNAT 済みのフローとその返りを通した後、wg0 が絡む残りの転送をすべて落とす。対象は wg0 から VPS の他のインタフェース(private NIC、別の VPN)へ出るフローと、他のインタフェースから wg0 へ入る DNAT 以外のフローである。これにより、既存のファイアウォールの forward が accept のままの VPS でも、認証情報を盗んだピアが VPS の内側のネットワークへ届かない。wg0 が絡まない転送には触れない
- masquerade は DNAT された接続に限定し、VPS 自身の通信には触れない
- 各 drop のカウンタは、テーブル差し替えの直前に `vpsd` が読んで SQLite に累積する。meter の状態は差し替えでリセットされるが、短時間のすり抜けにとどまるので許容する

`vpsd` は起動時に `net.ipv4.ip_forward` を確認し、1 でなければ 1 にする。
これは firewalld や nftables の設定ではなくカーネルの sysctl で、Docker や firewalld(masquerade を使うゾーン)も同じように 1 にする。転送する以上ここに正しい値は 1 の一つしかなく、他に異論を持つ主体がいない設定なので、ポート開放や `policy drop`(提示だけして触らない、後述)と違い `vpsd` 自身が設定する。手順は次のとおり。

- まず現在値を読む。すでに 1 なら何も書かない。
- 0 なら 1 にし、書けたことをログに残す(起動のたびに黙って上書きしない)。
- 書き込みに失敗しても `vpsd` は落ちない。読み取り専用の `/proc` や seccomp/LSM で `/proc/sys` への書き込みが塞がれていても、値がすでに 1 なら問題なく動く。0 のまま書けない場合は、`policy drop` の提示と同じ流儀で「`net.ipv4.ip_forward=1` にせよ」という警告を残して起動を続ける。
- この警告は他テーブルの `policy drop` の提示と同じ起動時 Findings として UI とログに出し、単なるログ 1 行にとどめない。カーネルモードのルールが 1 つも無いとき(プロキシ専用やルール 0 件)も同じ警告を出す。Findings は起動時に 1 回だけ作り、ルールは起動後に追加できるので、起動時の件数で警告を弱めると、追加した時点で転送が動かない理由が見えなくなるためである。
- いったん 1 にした値を 0 に戻すことはない。

conntrack の表の上限(`net.netfilter.nf_conntrack_max`)は `vpsd` が変えない。転送するフローは 1 本につき表の 1 件を使い、表が埋まるとカーネルはホスト全体の新規接続を落とす。上限はメモリの量から決まり、小さい VPS では 16384 のような値になる。`server check` は現在の件数と上限を表示し、上限が 65536 未満なら、上げる sysctl と `new_flow_rate` の設定を提示する。`new_flow_rate` と `per_source_rate` の drop は prerouting の優先度 -150 で行われ、その時点のフローはまだ表に登録されていないので、落としたフローは表を消費しない。
- `vpsd` が 0 から 1 に変えたときは、その事実と日時を状態ファイルの meta に記録する。撤去(10.3 節)のとき、運用者に「`vpsd` が変えたので戻す候補」か「元から 1 だった」かを具体的に示すためである。

運用者が sysctl を自分で管理していても、その管理も 1 にするのが普通なので衝突しない。値を触られたくない配置では 1 にしておけば `vpsd` は読むだけになる。この振る舞いで足りるため、設定するかを切り替えるフラグは持たない。
1 にすると VPS はルータとして振る舞える状態になる。wgft 以外の転送を止めるのは既存のファイアウォール(ufw、Docker、firewalld の既定の drop / reject)の役目で、`wgft` の forward チェーンは自分の DNAT 済みフローを accept するだけで他の転送を drop しない。ファイアウォールのない VPS では、VPS を経由するよう仕向けられたパケットが転送されうるが、公開 IP が 1 つの VPS では現実にはほぼ起きない。

conntrack の操作は「宣言状態に収束させる」1 手順だけを持つ。

1. `status` に DNAT フラグが立ち、orig 側の宛先が `10.200.0.0/24` の外で、かつ reply 側の送信元が `10.200.0.0/24` のエントリをすべて Dump する。外から入って DNAT されたフローだけが対象になり、`vpsd` 自身が wg0 へ張ったフロー(プロキシモードの中継、疎通確認)は最初から含まれない
2. 各エントリについて、現在有効なカーネルモードのルールのいずれかで、その proto と宛先ポートが DNAT され、エントリの reply 側の送信元(アドレスとポート)がそのルールの DNAT 先と一致し、かつ送信元が `source_deny` に含まれず `source_allow` を満たすかを判定する。DNAT 先を見るのは、ルールの `agent` を変えたとき旧エージェントへの既存フローを消すためである
3. 満たさないエントリを削除する

収束は nftables テーブルの差し替えの後に走らせる。先に走らせると、旧テーブルで許可されたフローが差し替えまでの間に入る。起動時の突き合わせも同じ順序である。
手作業で nftables を触られた場合も、この手順で不要なフローが拾える。
フロー数は多くないので、毎回全走査でよい。

契機は次の 3 つである。

- ルールテーブルまたは接続元制限への書き込みが 1 件でもあったとき(フィールドの種類を問わない)
- 恒久トークンの無効化
- `vpsd` の起動時(手作業で nftables を触られた後の復旧のため)

契機を変更の種類ごとに列挙しない。編集できるフィールドが増えるたびに漏れるためである。

起動時と `rule add` 時に次を検査し、問題があれば警告する。自動では書き換えない。

- `ip` `ip6` `inet` の全ファミリで forward フックの base chain を列挙し、`policy drop` があれば、そのチェーンに足す 2 行(`oifname "wg0" accept` と `iifname "wg0" ct state established,related accept`)を提示する。ufw の残骸が `ip filter FORWARD` にある場合もこれで拾う。この手作業は 1 回きりでポートに依存しない
- input フックの base chain で `ct state established` が accept されているかを確認し、されていなければ提示する。`vpsd` から wg0 経由で張る接続の返りが通るために必要である
- 他テーブルの nat prerouting チェーンに同じポートの DNAT があれば、そのルールの追加を拒否する。ポートが multiport や読めない無名 set、未知の式の形で判定できない規則は、拒否せずに Finding として警告する。黙って見逃すと、優先度で先に評価される wgft の DNAT(`dstnat - 1`)がそれと知らずに勝つため
- VPS 上で bind 中のポートとの衝突は 5.3 節のとおり拒否する

### 6.2 プロキシモード

`vps_mode = proxy` のルールは、`vpsd` が Go の TCP リスナーで受け、wg0 経由でエージェントの `10.200.0.x:listen_port`(エージェントが開いているリスナー)へ接続して中継する。
`proxy_protocol = true` なら接続先に PROXY protocol v2 ヘッダを先頭に送る。
接続元制限は `vpsd` が受け付け時に判定する。
中継はハーフクローズを保ち、片方向の EOF は `CloseWrite` で反対側に伝え、両方向が閉じたら接続を解放する。
同時に中継する接続の数は、7 節の「同時フロー数の上限」の TCP の値(ルールごと、プロセス全体、接続元 IP ごと)で抑え、超えた接続は accept の直後に閉じる。

進行中の中継を閉じる契機は次のとおり。conntrack の操作(6.1 節)は `vpsd` 自身のソケットには効かないので、別の部品として持つ。

- ルールの削除と `enabled = false`:リスナーと進行中の全中継を閉じる
- 接続元制限の変更:条件を満たさなくなった接続元の中継を閉じる
- 恒久トークンの無効化:そのエージェント宛の全中継を閉じる

このモードは `vpsd` 自身が待ち受けるので、既存ファイアウォールの input チェーンでそのポートが通る必要がある。
`rule add` 時に input フックの base chain に `policy drop` があれば、必要な行(`tcp dport <port> accept`)を提示する。

用途は接続元 IP を自宅側の Caddy に伝えたい HTTPS で、UDP には使わない。

### 6.3 ユーザー空間モード

`WGFT_MODE=userspace` は、VPS 側にも root、カーネル WireGuard、nftables を要求しない動作モードである。`vpsd` は自宅側と同じ wireguard-go と gVisor の netstack でトンネルを持ち、公開ポートを自分のソケットで受けて netstack 越しにエージェントへ中継する。root の取れない VPS、OpenVZ 系や LXC ベースの VPS、compose で全部を管理したい人のための入口で、カーネルモードを置き換えるものではない。モードは `vpsd` 全体で 1 つであり、ルール単位で混ぜない(11a 節の記録と照合)。

構成は次のとおり。

- サーバ側トンネル:wireguard-go の `device` と `netstack.CreateNetTUN` で、`listen_port` を開き `10.200.0.1` を持つ。サーバ鍵は SQLite の同じ鍵を使う。ピアの追加と削除は `IpcSet`(`public_key`、`allowed_ip`、`remove`)で行い、エンドポイントは指定せずローミングで学習する。ピアの状態(エンドポイント、最終ハンドシェイク、転送量)は `IpcGet` から読み、5.2 節の窃取検知と 10.1 節の表示に使う。wgctrl は使わない
- 中継:全ルールがプロキシモード相当になる。UDP と TCP は自宅側の中継部品(7 節の `relay.Manager`)の向きを反転して使い、ホストのソケットで listen し、netstack の dial でエージェントの `10.200.0.x:listen_port` へつなぐ。エージェントから見た送信元は `10.200.0.1` の一時ポートになり、カーネルモードの masquerade と同じ見え方である。PROXY protocol 付きの TCP は 6.2 節の中継をそのまま使う。`vps_mode` の kernel と proxy の区別はこのモードでは意味を持たず、PROXY protocol を付けるかどうかだけが残る
- 接続元制限とレート制限:nftables が無いので Go で判定する。deny、allow、接続元ごとの新規フロー上限(`per_source_rate`。表は 1 分で期限切れ、上限 65535 件で古いものから落とす)、ルール全体の新規フロー上限(`new_flow_rate`)、UDP のデータグラム上限(`packet_rate`)の順で、6.1 節と同じ評価順である。`packet_rate` は UDP にだけ効き、TCP には効かない。3 つとも nftables の `limit rate over` と同じく burst 5 のトークンバケットで、ラボで両モードの通過数と drop の累計が一致することを確かめた(2026-09-17、`lab/rates.sh`)
- 拒否のカウンタ:Go で数え、カーネルモードと同じ累積の経路(SQLite への加算)に流す。UI と CLI の表示は変わらない
- 進行中の中継を閉じる契機は 6.2 節と同じ(ルールの削除と無効化、接続元制限の変更、恒久トークンの無効化)。conntrack 収束の代わりに、これが全ルールに効く
- 起動時の検査:input チェーンが `policy drop` の場合の「`tcp/udp dport <port> accept` を足す」提示だけを行う。forward、`ip_forward`、他テーブルの DNAT、bind 中ポートの `/proc` の検査は行わない(bind の失敗で分かる)
- `server teardown` は `--purge` 以外にすることが無く、`server nft` は「ユーザー空間モードでは nftables を使わない」と出す

カーネルモードとの性質の違いは次のとおりで、文書では入れ方の分岐(systemd ならカーネル、Docker ならユーザー空間)の下にこの違いを先に書く。

- `vpsd` を止めると転送も止まる。カーネルモードは wg0 とテーブルが残るので、更新や再起動の間も通る
- TCP は `vpsd` が終端して 2 本になる。エージェントが落ちているとき、カーネルモードは SYN が返らないが、ユーザー空間モードは接続してから切れる
- フラッド耐性はユーザー空間のプロキシ一般(Traefik など)と同じ弱さを持つ。フローを開いて保持するだけの攻撃に対しては、7 節の「同時フロー数の上限」で `vpsd` のメモリの最大値を抑える。`vpsd` では接続元 IP ごとの上限も効く。PROXY protocol 付きの TCP(6.2 節の中継)も同じ上限で数える。スループットの目安は、ラボ(2 vCPU の VM、veth 越し)で TCP 1 本の 100 MB 転送がカーネルモード約 2.3 Gbit/s、ユーザー空間モード約 1.3 Gbit/s であり(2026-09-17)、想定用途の数 Mbps から数十 Mbps に対して余裕がある
- 公開ポートで `vpsd` の Go のコードがインターネットに直接さらされる(11 節)
- ピアを足す前に届いた握手は捨てられ、エージェントの再送は 5 秒後になる。5.2 節の順(stream の接続時に公開鍵を宣言してからピアを足す)で吸収する

エージェントとプロトコルは変えない。サーバ鍵と証明書は SQLite にあるので、同じ SQLite で別のモードに上げれば、エージェントは再登録なしに再接続する。1024 未満のポートは、Docker の bridge ネットワーク(`ports:` で公開)ではコンテナの名前空間で非特権の bind が許されるので使える(443 で確認済み)。`network_mode: host` ではホストの名前空間の制限が効き、非 root では bind できない。systemd で非 root なら `AmbientCapabilities=CAP_NET_BIND_SERVICE` で足す。コンテナに `NET_ADMIN` と host ネットワークを付けてカーネルモードを動かすことには対応しない。

## 7. データプレーン(自宅側)

エージェントは 1 つのモードだけを持つ。

- 動作条件:なし。Docker コンテナ 1 つで動き、特権も `NET_ADMIN` も不要。LXC でも Proxmox ホストでも同じ
- wireguard-go と gVisor の netstack でユーザー空間にトンネルを持つ。netstack の IPv4 再組み立ては既定で有効で、フラグメントのバッファ上限(4MB で古いものから捨て始め 3MB まで減らす)と再組み立ての期限(30 秒)は gVisor の定数で固定されている。wireguard-go の `CreateNetTUN` からは変更できないが、想定する用途には十分なので既定値を使う
- ルールの各ポートごとにリスナーを netstack 上に開き、LAN 内の `target` へ自分で接続して中継する
- エージェントから見た送信元は VPS の masquerade により常に `10.200.0.1` で、フローは送信元ポートで区別される。したがって全ルール共通の UDP 同時フロー上限は約 64k になる
- UDP は `(送信元 IP, 送信元ポート)` の組ごとにセッションを持ち、無通信が全体状態の `udp_timeout_stream` 続いたら閉じる。VPS の conntrack は assured になる前のフローを `udp_timeout`(既定 30 秒)で消すので、数パケットで終わるフローではエージェント側に死んだセッションが最長 90 秒残る。害は小さいので、この非対称は許容する。セッション数の上限は後述の「同時フロー数の上限」に従い、超えた新規パケットは捨てる。宛先からの応答を待つ間、セッションは読み取りバッファを持たない。データグラムの到着だけを先に待ち、届いてから共有プールの 65535 バイトのバッファを借りて全体を読み、書き終えたら返す。したがって応答の大きさによらずデータグラムは欠けない。到着を待つ手段は、カーネルのソケット(エージェントの宛先側)では、Unix は 1 バイトの `MSG_PEEK`、Windows はゼロバイトの `WSARecv`(`MSG_PEEK` 付き)をオーバーラップ I/O で発行し完了通知で待つ(Go ランタイムの `RawRead` が行う。スレッドは塞がない)。netstack の接続(`vpsd` のエージェント側)ではエンドポイントの待ち行列(`waiter.Queue`)である。`vpsd` は後者のために、wireguard-go の `tun/netstack` から netstack と TUN の接着部を写して自前で持つ(`netstack.Net` は stack を公開しないため)。この 3 つ以外の GOOS のエージェントでは到着だけを待つ手段を使わず、セッションごとに 65535 バイトを持ち続ける。2026-09-18 までは Windows を含む全セッションが 65535 バイトを保持し、上限いっぱいの 4096 セッションがルール 1 本で約 292 MiB になっていた(改訂の記録 2026-09-18 の実測)。macOS のエージェントは、宛先へのカーネルのソケットを開くたびに送信バッファ(`SO_SNDBUF`)を 65535 バイトに上げる。macOS の UDP の送信バッファの既定は `net.inet.udp.maxdgram` の 9216 バイトで、これを超えるデータグラムの書き込みは `EMSGSIZE` で失敗するためである。BSD 系のカーネルは UDP の送信バッファにデータを溜めず、この値は 1 個のデータグラムの最大長として効くだけなので、上げてもセッションごとのメモリは増えない。Linux の既定(約 208 KiB)は 65535 バイトより大きいので変えない。netstack の接続も変えない。宛先への書き込みが失敗したらセッションを閉じ、そのことをリスナーごとに 1 分に 1 回までログに出す
- TCP は接続ごとに `target` へ接続し、ハーフクローズを保って中継する(6.2 節と同じ)。接続数の上限は後述の「同時フロー数の上限」に従い、超えた接続は accept の直後に閉じる。無通信のタイムアウトは持たない。カーネルモードの conntrack が established の TCP を 5 日間保つのと同じく、長く黙る正規の接続(SSH など)を切らないためである
- `vpsd` からの PROXY protocol ヘッダは中身を見ずに素通しする

収束の判定はポート単位で行う。
エージェントは全体状態から、各リスナーの宣言値 `(proto, port) → (実効宛先, 所属ルール ID)` を計算し、現在の状態と突き合わせる。
実効宛先は、ルールの `target` のポートに、そのポートの範囲内での位置を足したものである。
実効宛先の比較は文字列で行い、`target` がホスト名のときの名前解決はセッション確立時に行う。DNS の変更でリスナーは閉じ直されず、新規セッションだけが新しい IP へ向く。

- ポートが宣言に現れて現在にない:開く
- ポートが現在にあって宣言にない:閉じる。そのポートの UDP セッション表を破棄し、中継中の TCP 接続もすべて閉じる
- 実効宛先が違う:閉じてから開く。セッションは切れる
- 所属ルール ID だけが違う:何もしない。セッションは残る

この規則から、ルールの操作ごとの挙動が次のように導かれる。

- `enabled = false`:そのルールの全ポートが宣言から消えるので閉じる。`true` に戻すと開くだけで、切れるセッションはない
- `target` の変更:全ポートの実効宛先が変わるので閉じ直す
- 範囲の伸縮:差分のポートだけ開閉する。範囲をずらして同じポートの実効宛先が変わった場合は、そのポートだけ閉じ直す
- ルールの分割と統合(5.4 節のバッチで 1 世代として行う):ポートの実効宛先が変わらなければセッションは残り、所属ルール ID だけが移る

セッション数の上限はルールごとに、そのルールに所属するリスナーのセッション合計で数える。
分割で移ったリスナーの既存セッションは、移動先のルールで数える。
統合で合計が上限を超えた場合、既存セッションは追い出さず、期限切れで上限を下回るまで新規を捨てる。

同時フロー数の上限は次の 3 段で、どれかに達したら新規のフローだけを拒む。既存のフローは追い出さない。プロセス全体の上限だけが設定項目で(11a 節)、ほかの値は固定である。

| 上限 | UDP のセッション | TCP の接続 | 数え方 |
|---|---|---|---|
| ルールごと | 4096 | 1024 | そのルールに所属するリスナーの合計 |
| プロセス全体 | `WGFT_MAX_UDP_FLOWS`(既定 8192) | `WGFT_MAX_TCP_FLOWS`(既定 2048) | 全ルールの合計。`vpsd` では 6.2 節の中継の接続も同じ数に含める。ルールごとの上限より小さくすれば、ルールごとの上限もこの値で頭打ちになる |
| 接続元 IP ごと | 256 | 128 | 全ルールの合計。`vpsd` だけ。エージェントから見た接続元は常に `10.200.0.1` なので、エージェントでは数えない |

プロセス全体の上限があるので、ルールの本数を増やしてもフローの保持によるメモリの最大値は増えない。ルールの本数そのものには上限を設けない。リスナー 1 つの固定費(UDP は受信用の 65535 バイトのバッファ 1 つ)は管理者が決めるポートの数に比例し、攻撃者からは増やせない。上限に達して拒んだことは、リスナーごとに 1 分に 1 回までログに出す。

プロセス全体の上限は、メモリの最大値を決める値である。ラボの実測(改訂の記録 2026-09-18)では、`vpsd` のユーザー空間モードで UDP のセッション 1 件が約 14 KiB、TCP の接続 1 本が約 30 から 55 KiB を使う。Go のランタイムは、生きているヒープの 2 倍になるまで回収を待つので、フラッドのように割り当てが続く間は RSS が保持分の約 2 倍まで膨らむ(既定の上限で保持分 176 MiB が 320 MiB になった)。これを抑えるために、`vpsd` とエージェントは起動時に、上限から計算したメモリのソフト上限をランタイムに設定する(`debug.SetMemoryLimit`)。値は `32 MiB + 12 KiB × UDP の全体上限 + 44 KiB × TCP の全体上限` で、既定の上限では 216 MiB になる。VPS のメモリの量は見ない。運用者が環境変数 `GOMEMLIMIT` を設定していれば、その値を優先し、wgft は設定しない。有効な値は起動ログに出す。メモリが 256 MiB の VPS では `WGFT_MAX_UDP_FLOWS=2048` と `WGFT_MAX_TCP_FLOWS=1024` を目安とする(ソフト上限は約 100 MiB になる)。

接続元 IP ごとの上限は、少数の IP からフローを保持してルールの上限を埋め、正規の利用者を締め出す攻撃を防ぐ。送信元を偽装できる UDP では、この攻撃は防げない。カーネルモードの VPS にはこれに当たる上限がまだ無く、1 つの IP がエージェントのルールごとの上限を埋められる(13 節)。

サービスから見た接続元は常にエージェントのアドレスになる。
カーネルモードを持たない理由は、自宅側にも nftables と `ip_forward` の設定を要求し、6.1 節と同じ他チェーンとの干渉問題を自宅側にも持ち込むためである。
性能面では、想定する用途(ゲームサーバの UDP、数 Mbps)に対して netstack の処理能力は十分に余裕がある。

## 8. 接続元 IP の扱い

サービスから見た接続元は、VPS 側の masquerade と自宅側の中継のため、常にエージェントのアドレスになる。
接続元 IP を使いたい処理は、実 IP が見える VPS 側で行う。

- 拒否と許可:5.3 節の `source_deny` と `source_allow`
- レート制限:5.3 節の `new_flow_rate`、`packet_rate`、`per_source_rate`
- TCP で自宅側のアプリケーションに元 IP を渡したい場合:`vps_mode = proxy` と `proxy_protocol = true`。受け側が PROXY protocol に対応している必要がある

UDP で自宅側のサービスに元 IP を渡す機能は持たない。
実現にはエージェントをサービスと同じホストに置いてカーネルの経路を変更する必要があり、7 節の方針と両立しないためである。

送信元を偽装した UDP は L4 では区別できない。
ルール全体の上限(`new_flow_rate`、エージェントのセッション上限)で VPS、トンネル、エージェントを守る以外にない。
上限いっぱいの偽装フラッドが続けばエージェントのセッション表が埋まり、正規の新規参加が止まる。
既存のセッションは、`new_flow_rate` と `per_source_rate` では影響を受けない。
`packet_rate` は全パケットに効くので、帯域を守る代わりに正規の既存セッションも巻き込む。
これは UDP サービス一般の限界で、このツールの守備範囲はここまでとする。

## 9. 状態の保存と再起動

`vpsd` 側:

- SQLite 1 ファイルにエージェント、ルール、登録トークンのハッシュ、世代、自己署名証明書と秘密鍵、wg0 のサーバ秘密鍵、累積カウンタを保存する
- SQLite の本体は、所有者だけが読み書きできる 0600 で作る。サーバ秘密鍵と証明書の秘密鍵を含むためである。既存の本体と WAL の補助ファイル(`-wal`、`-shm`)にグループかその他の権限があれば、起動時にその権限だけを外す。所有者の権限は変えないので、0644 は 0600 になり、管理者が 0400 にしたファイルは 0400 のまま残る。`wgft server check` は各ファイルの権限を表示するが、データベースを読み取り専用で開き、権限、内容、スキーマの版を変えない
- 設定のうち「変えるのに片付けが要る、または保存値と矛盾しうるもの」は初回起動で SQLite に記録し、以後は起動のたびに設定の値と照合する。対象は動作モード(`kernel`。`userspace` は 13 節)と wg のアドレス帯。アドレス帯が食い違えば、エージェントの割り当てアドレスと矛盾するので起動を拒否し、変えるには `teardown --purge` と再登録が要ると案内する。モードが食い違えば切り替えの関門(旧モードの残骸の有無)を通し、通れば記録を書き換えて起動する。記録の無い既存の SQLite は `kernel` とみなして記録する。設定の渡し方(`WGFT_*` の環境変数、その dotenv、フラグ、優先順位、出所の印字)の規則は 11a 節に定める
- 起動時に、既存の wg0 と `wgft` テーブルがあれば SQLite と突き合わせて差分だけを直す。突き合わせの対象はピア集合だけでなく、wg0 の秘密鍵、アドレス、MTU、待ち受けポートも含む。停止時にはどちらも削除しない。ユーザー空間モード(6.3 節)にはカーネルに残るものが無く、`vpsd` を止めると転送も止まる
- ただし wg0 は、**`vpsd` が作ったインタフェースだけを収束対象にする**。nft テーブルは名前 `wgft` で隔離できるが、wg インタフェースは同名なら誰のものでも同じ netlink 操作が通るので、隔離は「名前」ではなく「鍵」でしか作れない。起動時、既存の同名インタフェースの現在の秘密鍵を SQLite のサーバ秘密鍵と比べ、**一致する場合だけ収束させる**。この比較は `LinkByName` の直後、アドレス・MTU・鍵・ピアを書き換えるより前に行う(後で読むと、他人のインタフェースを一部書き換えてから気づくことになる)
- 鍵が一致しなければ、他人の WireGuard(例:先に上がった別の `wg-quick@wg0`)とみなし、**何も書き換えずに専用の終了コードで起動を中止する**。エラーには「`--wg-interface` で別名を使う」「相手の unit を無効化する」「意図的に引き継ぐなら `--adopt-existing`」を示し、収束するはずだった差分もドライランで出す。`--adopt-existing`(既定 false)のときだけ従来どおり収束させ、その際 `vpsd` が鍵を自分のものに書き換えるので、以後の起動は一致する。中止は設定起因なので、systemd の `Restart=on-failure` で無駄に再起動しないよう `RestartPreventExitStatus` にこの終了コードを入れる
- SQLite を失った場合(バックアップからの復元、`/var/lib/wgft` の削除)は、自分が作ったインタフェースでもサーバ鍵が変わって一致しなくなるため中止する。復元経路として `--adopt-existing` で引き継ぐ
- 起動時に、既存の他の WireGuard インタフェースと `--wg-port`・`--wg-address` の衝突を検査する。`wgctrl` の `Devices()` で全 WireGuard の待ち受けポートを列挙し、`--wg-port` が既に使われていれば(そのまま起動しても `ConfigureDevice` が `EADDRINUSE` で失敗する)中止する。WireGuard 以外のプロセスが同じ UDP ポートを bind している場合も、`/proc/net/udp` で検出してインタフェースを作る前に中止する(作ってから失敗すると、原因が消えるまで unit が再起動を繰り返す)。作った直後に後段の設定で失敗した場合は、作ったインタフェースを消してから中止する。`--wg-address` の `/24` が既存インタフェースのアドレスや経路と重なる場合も、経路の衝突に加え 6.1 節の conntrack 収束が他人の DNAT 済みフローを消しうるので中止する
- カーネルモードが要求するのは、カーネルの WireGuard モジュール(Linux 5.6 から本体に含まれる)と `nft` コマンドである。`wireguard-tools`(`wg`、`wg-quick`)は要らない。`vpsd` は netlink でカーネルを直接操作し、これらのコマンドを実行しない。カーネルが wireguard のリンク種別を知らない場合(独自の最小カーネル、コンテナ型の VPS など)、インタフェースの作成は `EOPNOTSUPP` で失敗する。再起動しても直らないので、衝突と同じく設定起因の中止として扱い、原因とユーザー空間モード(6.3 節)への案内を出して終了コード 3 で止まる
- ピアの公開鍵の正本はエージェント側にあり、SQLite の値はそのコピーである。stream 接続時にエージェントの宣言で更新する(5.2 節)
- VPS 再起動で wg0 が消えたときは、SQLite のサーバ秘密鍵で作り直す。公開鍵が変わらないので、エージェント側は再接続だけで復旧する
- 手作業で変更されたピアやルールは、起動時の突き合わせで SQLite の値に戻す。ピアの公開鍵については、その後の stream 再接続でエージェントの宣言値により再度上書きされる。ただしこの「戻す」は自分のインタフェース内の変更(ピア・アドレス・MTU・待ち受けポート)に限る。wg0 の秘密鍵そのものを手で変えられた場合だけは、上の所有判定で別人のインタフェースと区別できないため、戻さずに起動を中止する(許容する後退)

エージェント側:

- 状態ファイル 1 つに `{name, endpoint, cert_sha256, permanent_token, used_join_token_sha256, wg_private_key, last_state}` を保存する。`name` は登録の応答で確定した名前、`last_state` は最後に処理した全体状態、`used_join_token_sha256` は使用済み登録トークンのハッシュ(5.1 節の復帰経路で使う)
- 起動時は状態ファイルの鍵と `last_state` でトンネルとリスナーを先に立て、その後 stream に接続する。`vpsd` が停止中でも、VPS 側にピアが残っていれば転送は復旧する
- wg 鍵対は状態ファイルにないときだけ生成する。鍵を作り直したいときは `agent rotate-key` を使う。エージェントが稼働中なら、`rotate-key` は Unix ソケット経由で稼働中プロセスに指示し、プロセス自身が鍵を作り直して stream を張り直す。停止中なら状態ファイルの鍵と `last_state` を直接消す。稼働中のファイルは flock で保護されているので、外から書き換えない
- 状態ファイルは一時ファイルに書いて rename し、パーミッションは 0600。全体状態のたびに書き換わるので、途中でクラッシュしても壊れないようにする。Windows では 0600 相当の chmod がファイルの ACL には効かないため、別途の保護を 11a 節に定める
- 起動時に状態ファイルに flock をかけ、取れなければ二重起動として終了する
- 鍵を状態ファイルに置く理由は、恒久トークンと同じディスクにある以上、鍵を分けても守れる範囲が変わらず、一方で `vpsd` 不在時の可用性が上がるためである

## 10. 操作インタフェース

### 10.1 Web UI

- ダッシュボードは 1 カラムで、上からサーバー情報、警告、エージェント一覧、ルール一覧、適用中のファイアウォール設定の順に並べる。警告は 1 件以上あるときだけ帯状のバナーで出し、0 件のときは何も表示せず場所を取らない(ヘッダの全体ヘルスの見出しに件数が出るので十分)。ヘッダの全体ヘルスの隣には、警告が 1 件以上あるときだけ件数を出し、押すとバナーへ飛ぶ。エージェント一覧と警告バナーは 5 秒ごとに部分更新するので、警告バナーの受け皿の要素は 0 件でも DOM に残し、0 件から増えたときに次の更新で描き直す。ファイアウォール設定はルール一覧の下に全幅で置き、既定では折りたたむ
- ダッシュボード上部に vpsd と VPS 環境の情報を出す:バージョン、稼働時間、wg インタフェース/アドレス/待ち受けポート、エージェントの接続先エンドポイント、エージェント API ポート、MTU、カーネル版、nftables 版、`ip_forward` を wgft が設定したか、conntrack の UDP タイムアウト。これは構成・環境の確認用で、ヘッダの全体ヘルス(動的な健康)とは別

- エージェント一覧:名前、割り当てアドレス、最終ハートビート、処理済み世代、最終ハンドシェイク、wg ピアのエンドポイント IP、stream の接続元 IP、警告。名前の下に wg 公開鍵の先頭だけを小さく添え、`agent pubkey` の出力と見比べられるよう全体は title 属性(ホバー表示)に持たせる。両 IP の食い違いが続くと 5.2 節の警告になる。警告の隣に恒久トークンの無効化と「警告を消す」操作を置く
- 接続文字列の発行
- ルール一覧と追加、編集、削除、有効無効の切り替え。各ルールにエージェント側の適用状態と、接続元制限で拒否した累積数を表示する。適用状態は無効なルールなら常に disabled とし、有効なルールは持ち主のエージェントの直近のハートビート(5.2 節)から次の優先順位で判定する:エージェントが未登録・未接続なら agent offline、エージェントの処理済み世代が最新より古い(そのルールをまだ報告していない場合を含む)なら pending、それ以外はエージェントが報告したそのルールの状態に従い ok なら applied、error なら理由を副題に添えて error とする。一覧は `group` ごとの見出しで畳めるように区切り(見出しにグループ名と件数、折りたたみ可)、`group` の空いたルールは「その他」に入れる。畳んだグループでも見出しに error のルール数を出す。ヘッダの全体ヘルスの要約にも error のルール数を含める。各ルールには `note` を薄字の副題として常に添える。追加フォームで「説明」(`note`)と「グループ」(`group`。既存グループの候補を出しつつ自由入力)を設定できる。追加フォームの「無効のまま追加」は CLI の `rule add --disabled` にあたる
- ルールの詳細ページ(`/ui/rules/{id}`)。一覧の各ルールの「詳細」から開く。ルールの要約に一覧と同じ適用状態(理由を含む)を出し、有効無効の切り替えの下に、次の 6 つの区画を置く。区画ごとに別のフォームで保存し、保存は管理用 API のバッチ 1 回(`upsert`、分割は 2 件の `upsert`、統合は `upsert` と `delete`)で行う。group、note、接続元制限、レートの変更では ID も世代も変わらない(5.3 節)。保存の後は同じ詳細ページを表示する(分割の後は縮んだ元のルールの、統合の後はこのルールの、どちらも ID が変わらない詳細ページ)
  - グループと説明:group と note は転送に関わらないので、既存ルールに対して ID そのままで後付け・変更できる
  - 拒否リスト(`source_deny`):各 CIDR の行に「外す」を置く。追加は複数行の入力で受け、1 行に 1 つの CIDR かアドレスを書く。前後の空白と空行は無視し、単独のアドレスには `/32` を補い、既にある CIDR は重ねて加えない。解釈は CLI の `rule deny add` と同じである。IPv4 の CIDR として読めない行が 1 つでもあれば何も保存せず、その行の番号と内容を示し、入力を残したまま同じページを表示し直す
  - 許可リスト(`source_allow`):拒否リストと同じ形である。空のリストへの最初の追加は他の接続元を全部落とし、最後の 1 件を外すと全接続元に開くので、どちらも確認のダイアログを出す
  - レート制限:`per_source_rate`(1 つの接続元からの新しい接続)、`new_flow_rate`(ルール全体の新しい接続)、`packet_rate`(パケット。通信中のデータも含めて数える)の 3 つに、回数、単位(`second` から `week`)、「制限しない」を置く。`per_source_rate` と `new_flow_rate` が数えるのは新しい接続(TCP は 1 本のコネクション、UDP は初めて見た送信元アドレスとポートの組)であり、開いている接続は数えない。`packet_rate` は通信中のデータも含めて数えるため誤読されやすく、区画を折りたたんで値が入っているときだけ開く。値が入っている欄には読み上げの一文(例:「1 つの接続元から 1 分に 10 本まで」)を添える。「制限しない」は値を外す。ユーザー空間モードの TCP のルールでは `packet_rate` が効かないこと(6.3 節)を、その欄に添える。区画の見出しには、このルールの累積 drop 数を一覧と同じ値で添える
  - 分割:`listen_port` が範囲のルールにだけ出す。分割する位置は範囲の 2 番目から末尾までのポートから選ぶ。結果の 2 つのルール(受信範囲と実効宛先)は、送信前に JS がその場で計算して示す。組み立てと検査は CLI の `rule split` と共有する(5.4 節)
  - 統合:同じプロトコルの他のルールから、`listen_port` が直前・直後で隣接するものを探し、5.4 節の統合の条件をすべて満たすものだけを候補として、それぞれに「このルールと統合」ボタンを出す。候補が 1 つも無く、隣接するルールがあるときは、直前を優先してその 1 件の理由(例:拒否リストが違う)を示す。組み立てと検査は CLI の `rule merge` と共有し、この画面のルールが `id1` にあたる(削除されるのは相手)
- TCP ルールの疎通確認。`vpsd` から `10.200.0.x:listen_port`(エージェントのリスナー)に接続し、エージェントの中継を通して `target` に届くかを見る。`target` は LAN アドレスで `vpsd` からは経路がないため、直接は試さない。UDP は送信だけでは失敗が分からないので持たず、エージェントの適用状態で代える
- ルール一覧の見出しにある書き出しと読み込み(`GET /ui/rules/export`、`/ui/rules/import`)。書き出しは現在の全ルールを、CLI の `rule import` が読む配列と同じ形の JSON でダウンロードさせる。読み込みはアップロードした内容をまだ適用せず、現在のルールと ID で突き合わせた差分の確認ページを表示する。差分の計算(追加・変更・削除・変わらないの判定と、変更したルールのフィールドごとの説明)は `proto.DiffRules` が持ち、削除対象の抽出は `proto.DeletedIDs` が持つ。CLI の `rule import` もこの 2 つを使い、独自の突き合わせを持たない。拒否/許可リストの変更は件数でなく、増えた CIDR と減った CIDR(例:`+198.51.100.0/24 -203.0.113.0/24`)で示す。件数だけでは、同じ件数のまま内容が入れ替わる変更(1 件を別の CIDR に差し替えるなど)が変わらないと見えてしまうためである。確認ページは、削除の行に通信中のセッションが切れる旨の注記を添え、未登録のエージェントを指すルールと `Rule.Validate` に落ちるルール(今のルールから変わっていない行は除く。5.4 節)があれば一覧にして適用ボタンを出さない。適用は、アップロードした内容(ID を確定させた後の JSON)と、確認ページを描いた時点の世代、およびその時点のルール集合全体のハッシュ(`proto.RulesDigest`)を hidden で持たせて送る。`group`、`note`、接続元制限、レートだけの変更は世代を上げない(5.3 節)ため、世代の一致だけでは別経路(CLI など)からの変更を見逃すので、ハッシュも一致させる。適用の直前に今の世代とハッシュを取り直し、どちらかが確認ページを描いた時点と違えば何も変えず、アップロードし直すよう求める。この事前の取り直しと、実際にバッチを確定させる呼び出しとの間にも狭い競合の窓が残るため、確定の呼び出し自身にも同じハッシュを `ExpectedDigest`(5.4 節)として渡し、バッチ側のトランザクションの内側で読み取りと確定を割り込みなく結びつける。事前の取り直しをすり抜けた食い違いは、この照合の誤り(`ErrBatchConflict`)を同じ「アップロードし直す」画面に写して防ぐ。削除を含む適用には `data-confirm` を付ける

### 10.2 CLI

CLI は管理用 API を叩く薄い層で、Web UI と同じことができる。

```
wgft agent join-string --name home
wgft agent rotate-key
wgft rule add --agent home --udp 2456-2457 --to 192.168.1.20:2456 --group valheim --note "週末サーバ"
wgft rule add --agent home --tcp 443 --to 192.168.1.30:443 --proxy --proxy-protocol
wgft rule set r_01J --group minecraft --note "公開サバ"
wgft rule deny add r_01J 203.0.113.0/24
wgft rule ls
wgft server nft
```

`rule ls` は `group` ごとにまとめて表示し、各ルールの `note` も出す。`rule add` の `--group` と `--note` は省略できる。`rule set` は既存ルールの `group` と `note` だけを ID そのままで変える(転送に影響せず世代も上げない)。`--group ""` で外す。
`server nft` は適用中の `wgft` テーブルをそのまま表示し、手で確認したいときに使う。

### 10.3 運用の流れ

初回セットアップ(VPS):

1. `/etc/wgft/server.env` に `WGFT_MODE=kernel` と `WGFT_WG_ENDPOINT` を書き、`wgft server check` で検査してから、systemd で `wgft server run` を起動する。root もカーネル WireGuard も使えない VPS では、代わりに `WGFT_MODE=userspace` を焼き込んだコンテナイメージを `WGFT_WG_ENDPOINT` とデータのボリュームだけ与えて起動する(6.3 節)。入れ方でモードが決まり、systemd ならカーネル、Docker ならユーザー空間である。初回起動で SQLite、自己署名証明書、wg0 のサーバ鍵を作り、モードとアドレス帯を記録する(9 節)。対話は無く、初回に決めるのはモードだけである
2. VPS のファイアウォールで WireGuard とエージェント用 API のポートを開ける。これは手作業で、`vpsd` は行わない
3. 起動ログに 6.1 節の警告(forward の `policy drop` など)が出ていれば、提示された行を 1 回だけ足す

同梱の systemd の unit は `vpsd` を root では動かさない。`DynamicUser=yes` で systemd がサービスの寿命だけ非特権の利用者を割り当て、`AmbientCapabilities` で `CAP_NET_ADMIN` と `CAP_NET_BIND_SERVICE` の 2 つだけを渡す。前者はカーネルの WireGuard、nftables、conntrack の netlink と `net.ipv4.ip_forward` の書き込みに、後者はプロキシモードの 1024 未満の待ち受けに使う。ネットワーク系の sysctl は `CAP_NET_ADMIN` があれば root でなくても書けるので、6.1 節の「`vpsd` 自身が 1 にする」はそのまま成り立つ。`ProtectKernelTunables` は `/proc/sys` を読み取り専用にして書き込みを妨げるので付けない。root のままで `/proc/sys` を書き込み可にすると、侵害されたときに root 所有のほかの sysctl まで書き換えられるので、非 root にする意味はここにある。ファイルシステムは `ProtectSystem=strict` で読み取り専用にし、書けるのはデータの置き場と実行時ディレクトリだけにする。システムコールは `@system-service` から `@privileged` と `@resources` を除いたものに絞る。データの置き場の実体は `/var/lib/private/wgft` になり、`/var/lib/wgft` はそこへのシンボリックリンクになる。root で動く旧い unit が作ったディレクトリは、最初の起動で systemd が移して所有者を付け替えるので、unit を差し替えて再起動するだけで更新でき、サーバ鍵も登録済みのエージェントも引き継がれる。root からは従来どおり読めるので、CLI と `teardown` の使い方は変わらない。設定ファイルの権限は 11a 節による。`systemd-analyze security` の値は 8.6 から 2.0 になった(systemd 252)。

メモリが尽きたときの扱いは次のとおり。7 節の同時フロー数の上限とメモリのソフト上限が、`vpsd` をその手前に留める。それでも OOM キラーに殺された場合は、unit の `Restart=on-failure` が 2 秒後に起動し直す(compose は `restart: unless-stopped`)。ルール、サーバ鍵、エージェントの登録は SQLite にあるので失われない。カーネルモードでは、`vpsd` が落ちている間も、プロキシモード(6.2 節)以外のルールの転送は続く。ホスト全体のメモリが尽きた場合にカーネルが選ぶプロセスは `vpsd` とは限らないので、unit には `MemoryMax=` の例をコメントで添える。値はホストの大きさで変わるので既定では有効にせず、起動時に出るソフト上限より上に置くよう書く。

管理 UI と CLI への入り方(11 節)。どの経路でもパスワードの入力は無い:

- VPS 上の CLI:`sudo wgft rule add ...` のように root で叩く。ソケットを開けるのは root と `vpsd` 自身だけなので、sudo がそのまま認証になる
- Tailscale を使う場合(推奨):`--admin-tailscale` を付けて起動し、tailnet 内の端末から `http://<VPS の tailnet 名>:8686/` を開く
- Tailscale が無い、または tailnet が落ちたとき:SSH でソケットを手元に引く。`~/.ssh/config` の該当ホストに `LocalForward 8686 /run/wgft/admin.sock` を書いておけば、`ssh vps` を張るだけで `http://localhost:8686/` が開く

エージェントの追加(自宅):

1. `wgft agent join-string --name home` で接続文字列を 1 本発行する
2. 自宅の LXC か Docker で、接続文字列を `WGFT_JOIN` に入れてエージェントを起動する。名前は接続文字列に紐付いているので入力しない。接続文字列には `#` が入るのでクォートする。状態ファイルの置き場所をボリュームにしておく
3. エージェント一覧に名前が現れ、最終ハンドシェイクが埋まれば完了。接続文字列はこの時点で使い切りになる

ルールの追加と監視:

1. `wgft rule add` で追加する。VPS の nftables に即反映され、エージェントに全体状態が配信され、ルール一覧に `ok` が出る
2. `error` なら理由(`target` に繋がらない、など)が一覧に出る
3. 拒否カウンタや新規フロー数はルール一覧で見る。荒らしには `wgft rule deny add` で対処し、通信中のフローも含めて即座に切れる

普段の運用で人が触るのは、ルールの追加と拒否リストの追加だけである。
エージェントは再起動しても状態ファイルから復旧し、VPS が再起動しても `vpsd` が同じ鍵で wg0 を作り直すので、どちらも手作業は要らない。

撤去(アンインストール):

`vpsd` は停止しても wg0 と `table inet wgft` を残す(再起動で転送を途切れさせないため)。
やめるときは、`vpsd` が自分で作ったものだけを消す撤去操作を CLI の 1 コマンドとして持つ。
これは**停止した `vpsd` の後片付け**として行う。`vpsd` が稼働中なら何も消さずに拒否し、
先に停止するよう案内する(動いたまま消すと、次のルール変更や systemd の再起動で
作り直される)。稼働の判定は、`vpsd` が起動時に状態ファイルへ取る flock(エージェントの
状態ファイルと同じ形)で行う。

消す順序と対象(`vpsd` が作ったものだけ。既に無いものはエラーにせず飛ばす):

1. `table inet wgft` を削除する。他テーブルには触れない。
2. ルール 0 件で 6.1 節の conntrack 収束を走らせ、wgft 由来の DNAT 済みエントリを消す(テーブルを消してもエントリは残るため)。順序はテーブル削除・conntrack 収束・wg0 削除。
3. wg0 を削除する。消すのは秘密鍵が状態ファイルのサーバ鍵と一致するインタフェースだけで、状態ファイルに鍵が無い(空)場合は相手の鍵が空でも所有とみなさず、`--adopt-existing` を要求する。`--adopt-existing` でも、同名でも WireGuard 以外のリンク(veth や bridge)は消さない。
4. `--purge` のときだけ、状態ファイルを消す。SQLite は WAL なので `.sqlite` と `-wal`・`-shm` の 3 つ。

可逆性:`--purge` を付けない撤去は元に戻せる。`vpsd` を起動し直せば同じ鍵と証明書で
wg0 とテーブルが戻り、エージェントは再接続だけで復旧する(9 節)。鍵が消えて
再登録が要るのは `--purge` のときだけである。

自動では戻さないもの(「手で戻す一覧」を出すだけ。追加を自動でやらない原則の裏返し)。
一覧は一般論ではなく、状態ファイルと実状態から具体値を出す:

- VPS のファイアウォールで開けたポート。SQLite から出す(`wg-port` の UDP、エージェント用 API の TCP、全ルールの `listen_port`)。
- 他テーブルに足した wg0 参照行(6.1 節の提示で `DOCKER-USER` などに足した `oifname "wg0" accept` の類)。実状態から所在を列挙する(`check` の検査の逆向き)。
- `ip_forward`。6.1 節の meta の記録から「`vpsd` が 0→1 にした(日時)」か「元から 1 だった」かを出し、前者だけ戻し方を示す。他の転送が使っている可能性があるので自動では戻さない。
- systemd の unit・env、バイナリ、`/var/lib/wgft` ディレクトリは `vpsd` が置いたものではないので一覧に出す。

全体の順序:先に自宅エージェントを止めるか VPS 側で `agent revoke` し(稼働中の `vpsd`
にしか効かない)、その後 `vpsd` を停止して撤去する。撤去後にエージェントが残っても、
接続不能を 5.1 節の一時障害とみなしてバックオフ再接続を続けるだけで害はないが、止まらない。

自宅エージェントはユーザー空間の wireguard-go と netstack なのでカーネルに何も残さず、
プロセスを止めて `agent.json`(と隣の `.lock`・`.sock`)を消せば消える。恒久トークンは
VPS 側の無効化でピア・conntrack・割り当てアドレスを回収する。

## 11. セキュリティ

管理用 API と Web UI の待ち受け先は `--admin` で選ぶ。独自のパスワードは持たない。ユーザー空間モード(6.3 節)では、転送対象の公開ポートで `vpsd` の Go のコードがインターネットに直接さらされる。カーネルモードではその面はカーネルの DNAT だけで、`vpsd` 自身が受けるのはエージェント用 API とプロキシモードのポートに限られる。

- Unix ソケット(既定 `unix:///run/wgft/admin.sock`、0600。systemd の unit では `vpsd` の実行利用者が所有し、置き場のディレクトリは 0700 なので、開けるのは root と `vpsd` 自身だけ):VPS 上の CLI は root で直接叩く。手元のブラウザからは SSH のポート転送でソケットを引く(10.3 節)。到達できるのは「VPS の root」と「SSH でその root に入れる人」だけで、どちらも SQLite と wg の鍵を読める立場なので、パスワードを足しても守れる範囲は広がらない
- `--admin-tailscale`:加えて Tailscale のアドレスでも待ち受ける。起動時にまず `tailscale status --json` を実行し、`Self.TailscaleIPs` の最初の IPv4 アドレスと `Self.DNSName`(MagicDNS 名)を使う。`tailscale` コマンドが PATH にない、または失敗したときは、名前が `tailscale` で始まるインタフェース(Linux 版 Tailscale の既定は `tailscale0`)にある `100.64.0.0/10` のアドレスを使う。`100.64.0.0/10` は Tailscale 専用の帯ではなく VPS 事業者が内部網に使っていることがあるため、この帯を持つだけの他のインタフェースは使わない。検出した MagicDNS 名は `Host` の許可リストに自動で加わり、`--admin-host` は追加の名前のためだけに使う。認証、TLS、総当たり対策を Tailscale に任せられ、`vpsd` 側に追加の実装が要らないので、外から触りたい場合はこれを推奨する。tailnet が落ちても SSH で代替できる
- TCP(`--admin 127.0.0.1:8686` など):Unix ソケットの転送に対応しない SSH クライアントや、ラボ向けに残す。ループバック以外の TCP アドレスに開いた場合、`vpsd` は起動ログに警告を出すだけで止めない
- `public`:インターネットに公開する。ACME による正規の TLS 証明書、パスキーか TOTP、ログイン試行のレート制限、セッション期限と CSRF 対策を `vpsd` に実装したうえでなければ選べない。v1 では実装しない(13 節)

管理用 API が破られると VPS を任意の自宅ホストへの中継器にできるため、エージェント用 API より守る優先度が高い。
その守りは独自の認証ではなく、すでに信頼している境界(VPS の root、SSH、tailnet)に置く。
以前の管理者パスワード(Basic 認証)は、ハッシュが root の読める SQLite にある以上 root には効かず、ブラウザは Basic 認証の資格情報を他サイト発のリクエストにも自動で付けるため CSRF にも効かなかった。守れていたのは「VPS 上の root でないプロセスからループバックへの到達」だけで、それは Unix ソケットのパーミッションで代えられる。

ブラウザ経路の守りは、パスワードの代わりに次の 2 つで行う。CLI は影響を受けない。

- `Host` の検査:`localhost`、`127.0.0.1`、`[::1]`、`--admin-tailscale` で検出した自分の tailnet 名と IP、`--admin-host` で追加した名前、以外の `Host` を持つリクエストを拒否する。攻撃者のドメインを `127.0.0.1` に向ける DNS リバインディングは、ここで `Host` が合わずに落ちる
- 他オリジン発の変更の拒否:`GET` と `HEAD` 以外のリクエストで、`Sec-Fetch-Site` が `same-origin` でも `none` でもないもの、または `Origin` のホストが上の許可リストにないものを拒否する。CLI はどちらのヘッダも送らないので通る。Web UI のフォーム送信は同一オリジンなので通る

- エージェント用 API は公開するが、登録と stream のエンドポイントしか持たず、認証は登録トークンか恒久トークンだけである。トークンの生成、保存、比較、試行制限は 5.1 節のとおり
- エージェント用 API は TLS 1.2 以上、HTTP/1.1 だけで応じる。通信は登録の POST と WebSocket だけなので、HTTP/2 は ALPN で広告しない。鍵交換の曲線は固定せず Go の既定に従う。既定には耐量子のハイブリッド鍵交換が含まれ、固定するとそれが外れるためである
- 恒久トークンは無効化できる。無効化すると wg ピア、そのピア宛の conntrack エントリ、進行中の中継を削除し、割り当てアドレスを回収する。名前は新しい接続文字列で再利用できる
- wg0 上のピア同士は通信できず、wg0 から VPS 自身への新規接続もできない
- `vpsd` は転送対象のポート以外を開けない。VPS のファイアウォール設定そのものは扱わない

## 11a. 設定の渡し方

wgft のどのプロセス(`vpsd`、`agent`、CLI)も `WGFT_*` の環境変数で設定を受け取る。ファイルはその dotenv、フラグはその別名であり、優先順位はフラグ、プロセスの環境変数、ファイルの順である。

ファイルの既定の置き場所は `vpsd` と CLI が `/etc/wgft/server.env`、`agent` が `/etc/wgft/agent.env` で、`--config` で変更できる。同じファイルは systemd の読み込み、Docker の `--env-file`、compose の `env_file` の 3 つの経路で扱われ、この 3 者は構文の解釈が一致しないため、3 者で一致する範囲だけの構文を許す。1 行に `KEY=value` を 1 つ書き、行頭の `#` だけをコメントとして扱う。値の途中の `#` は値の一部として扱い、引用符は使わず、値に空白を含めることもできない。引用符で始まる値は警告ではなくエラーにする。3 つの経路それぞれで解釈が異なり、たとえば Docker では引用符ごと 1 つの値として扱われ、黙って認証エラーになるなどの事故につながるためである。この規則の下では、`WGFT_JOIN` の接続文字列(`wgft://host:port/token#sha256:...`)は引用符なしでそのまま書ける。

systemd の unit では `EnvironmentFile=` を使わない。バイナリが既定で同じファイルを自分で読むため不要であり、`EnvironmentFile=` を使うと値の出所がすべて「環境変数」になり、出所付き印字(下記)が意味を失う。

`server.env` には秘密の値を置かない。`vpsd` の設定項目に秘密は無く、サーバ鍵、証明書、トークンはすべて SQLite にある。同梱の unit は `DynamicUser=yes` の非特権の利用者で動く(10.3 節)ため、`server.env` はその利用者が読める 0644 にする。`agent.env` は `WGFT_JOIN` を含むので、root 所有、グループ `wgft` の 0640 にし、固定の `User=wgft` で動く unit から読ませる。ファイルが無い場合はエラーにせず、環境変数と既定値だけで動く。unit に `LoadCredential=` でファイルを渡す方法は採らない。0600 のままでも動くが、`--config` で別の場所を指す必要があり、root の CLI が読む既定の場所と二重になり、起動ログの出所の見え方も変わる。秘密の無いファイルに対しては重いためである。

設定起因の失敗は終了コード 3 で止め、直し方をエラーに添える。再起動しても直らないので、同梱の 2 つの unit(`server.service` と `agent.service`)の `RestartPreventExitStatus=3` で再起動の繰り返しを止める。対象は次のとおりで、どれも運用者が設定を直すか `teardown` するまで、何度起動しても同じ結果になる。

- 設定ファイルがあるのに読めない
- 設定ファイルの構文の誤り(上記の規則に反する行)
- 値の誤り:`WGFT_WG_PORT` と `WGFT_MTU` が整数でない、`WGFT_MAX_UDP_FLOWS` と `WGFT_MAX_TCP_FLOWS` が範囲外
- 必須の値の欠落:`vpsd` の `WGFT_WG_ENDPOINT`
- `vpsd` の照合による拒否:`WGFT_MODE` の未指定(初回)と不正な値、関門を通らないモードの変更、`WGFT_WG_ADDRESS` の食い違い
- `vpsd` の wg の所有判定と衝突による中止(9 節)

設定以外の失敗(SQLite の読み書き、データの置き場の作成、ネットワーク)は終了コード 1 のままにし、unit の再起動に任せる。エージェントが終了コード 3 で終わるのは設定ファイルの読み取り、構文、値の誤りだけで、再起動で直る失敗を止めることはない。Docker の `restart: unless-stopped` は終了コードを見ないので、コンテナでは設定の誤りでも再起動を繰り返す。

起動ログの先頭と `wgft server check` の出力は、有効な設定を値と出所(フラグ、環境変数、ファイル、既定値のいずれか)付きですべて印字する。トークンなど秘密の値は伏せ字にする。

他のプロセス向けの `WGFT_*` はエラーにせず無視する。知らない名前だけでなく、`vpsd` から見た `WGFT_MODE=userspace` のように「知っているが自分には関係ない」名前も対象である。この規則により、同じ Docker イメージや同じ設定ファイルで `agent` と `vpsd` を切り替えて使える。

同時フロー数のプロセス全体の上限(7 節)は `WGFT_MAX_UDP_FLOWS`(既定 8192)と `WGFT_MAX_TCP_FLOWS`(既定 2048)で、`vpsd` とエージェントの両方が受け取る。値は 16 から 65535 の整数で、範囲外は起動時のエラーにする。メモリの小さいホストで下げるための設定であり、ホストのメモリの量から自動では決めない。

データの置き場所は `WGFT_DATA_DIR`(既定 `/var/lib/wgft`)に統一する。この下に `vpsd` は SQLite ファイルを、`agent` は状態ファイルを置く(9 節)。

既定の置き場所は OS ごとに決める。Linux は上のとおりである。Windows は設定ファイルもデータも `%ProgramData%\wgft` に、macOS は `~/Library/Application Support/wgft` に置く。どの OS でも `--config` と `WGFT_DATA_DIR` で変更できる。Linux 以外のバイナリが持つのはエージェントと CLI だけで、`server` サブコマンドは「Linux でしか動かない」と答えて終わる。`vpsd` はカーネルの WireGuard と nftables に依存するためである。エージェントは wireguard-go と netstack だけで動くので OS を選ばない設計であり、Windows は 2026-09-19 に Windows 11(非管理者権限での実行)から実機の VPS に対して確認した。ホームルータの NAT を越えた join string による登録、トンネルの確立、LAN サービスへの UDP と TCP の中継、server の再起動と agent の強制終了からの復帰、2 つ目の `agent run` の拒否、認証情報ファイルの書き換え、稼働中の `rotate-key` が通ったため、Windows 版のエージェントと CLI は Releases に含め、README にも対応として書く。macOS は 2026-09-19 に macOS 27(Apple シリコン、arm64)から、ホームルータの NAT の内側で実機の VPS(v0.3.0、カーネルモード)に対して確認した。join string による登録、トンネルの確立、Mac 自身と LAN の他のホストへの UDP と TCP の中継、Mac の再起動と server の再起動からの復帰、2 つ目の `agent run` の拒否、稼働中の `rotate-key`、データディレクトリ(0700)と `agent.json`・`agent.json.lock`・`agent.json.sock`(0600)の権限が通ったため、macOS 版のエージェントと CLI も Releases に含め、README にも対応として書く。macOS で公開するのは darwin/arm64 だけである。Intel Mac は対象にせず、amd64 の自宅マシンには Linux 版で対応する。

Windows での常駐は、`agent run` をそのときの利用者の権限で起動するところまでを wgft が提供し、サービス、タスクスケジューラ、通知領域への常駐は提供しない。ログオン時の自動起動(スタートアップフォルダへの登録など)は利用者に任せる。Windows のゲームサーバの多くがユーザー権限で動いており、agent も管理者権限を必要としないことに合わせた判断であり、サービス化には Program Files への配置、SYSTEM と対話利用者の間の ACL の取り合い、SCM(サービス制御マネージャ)対応のコードが新たに要ることを理由に見送った。

Windows Defender Firewall は、初回起動時に `wgft.exe` の受信を許可するかどうかのダイアログを表示する。wireguard-go が UDP を `0.0.0.0` で待ち受けるためである。実機では、このダイアログで許可した場合はもちろん、キャンセルして受信拒否の規則が作られた場合でも、agent は外向きの接続しか使わないため、トンネルと中継は WireGuard の鍵の再交換をまたいで動作し続けることを確認した。ダイアログは許可してもキャンセルしてもよい。

未確認の点は、Windows サービスまたは SYSTEM としての実行である。

macOS での常駐には、`UserName` に利用者を指定した LaunchDaemon(`/Library/LaunchDaemons` に置き、システムの launchd が起動するジョブ)を推奨し、その例を `deploy/io.github.rahanahu.wgft.agent.plist` として配る。プロセスは root ではなくその利用者の権限で動き、`WGFT_DATA_DIR` で利用者の `~/Library/Application Support/wgft` を指すので、ターミナルから起動した `agent run` と同じ認証情報ファイルを使う。launchd は `UserName` を持つジョブの環境に `HOME` を設定する(実機で、その利用者のホームディレクトリが入ることを確認した)が、plist の文字列の中の `~` は展開しないため、plist はログのパスを書き下す。`WGFT_DATA_DIR` も明示し、既定の置き場所の解決に依らず、ターミナルから起動した `agent run` と同じディレクトリを LaunchDaemon が使うようにする。plist は root 所有の 0644 で置かれ全員が読めるため、`WGFT_JOIN` を書かない。初回登録は、ターミナルから `WGFT_JOIN` を付けて `agent run` を起動し、登録できたら止めてから LaunchDaemon を読み込む手順とした。launchd には systemd の `RestartPreventExitStatus` に当たる設定が無いため、`KeepAlive` の `SuccessfulExit` を偽にして異常終了と強制終了のときに再起動させ、間隔は `ThrottleInterval` で空ける。root での実行は必要が無いため試していない。

LaunchAgent(`~/Library/LaunchAgents` に置き、利用者のログインセッションで動くジョブ)は推奨しない。実機では、LaunchAgent として起動した agent はデフォルトゲートウェイには接続できたが、LAN の他のホストへの接続は `connect: no route to host`(`EHOSTUNREACH`)で失敗し、許可を求めるダイアログも出なかった。同じバイナリをターミナルから起動した場合(ターミナルのアプリの許可を引き継ぐ)と、`UserName` 付きの LaunchDaemon として起動した場合は、他のホストへ UDP と TCP で接続できた。この失敗を macOS 15 以降のローカルネットワークのプライバシー保護によるものとするのは症状からの推測であり、システムログには該当する記録が見つからなかった。LaunchAgent を使う `brew services` も同じ問題に当たる可能性があるが、未確認である。

FileVault を有効にした Mac では、再起動後に LaunchDaemon が起動したのはカーネルの起動時ではなく最初のログインの時点だった。最初のログインまでデータボリュームがロックされたままであるためと推測する。起動した agent は十数秒のあいだ `network is unreachable` で再試行し、その後は自力で接続した。この制約には対処せず、文書に書くにとどめる。想定する利用者はその Mac で遊び、ゲームサーバもその利用者のセッションで動くため、ログインまで agent が動かないことによる不都合は小さい。`fdesetup authrestart` は試していないため、手順として勧めない。

macOS のバイナリは Apple の公証を受けない。ブラウザで取得したファイルには隔離の属性が付き、Gatekeeper は隔離の属性を持つ公証の無いバイナリの起動を止めるため、README とセットアップガイドは `curl` での取得を案内する。`curl` で取得したファイルに隔離の属性が付かないことは確認したが、ブラウザで取得した場合の挙動は試していない。

macOS のエージェントのメモリ使用量は、同時フロー数の上限(既定の UDP 8192、TCP 2048)までフローを保持した状態で、Linux と同じく 7 節のソフト上限(216 MiB)の内に収まった(改訂の記録 2026-09-19)。上限を超える TCP の接続のフラッドでソフト上限を大きく超える問題は Linux のエージェントでも起き、macOS に固有ではないため、13 節の未決事項として扱う。macOS の `ps` の RSS は負荷が止んだ後も高いまま残るので、macOS でのメモリ使用量は物理フットプリント(`footprint`)で見る。

macOS の未確認の点は、TCP の接続のフラッドの間に、保持していた TCP の接続の一部が相手側から閉じられた原因(同じ試験で Linux のエージェントでは起きなかった)、FileVault を無効にした Mac でログインせずに起動時から動くかどうか、ログアウト後も動き続けるかどうか、終了コード 3 で終わったときの launchd の実際の挙動(`KeepAlive` の `SuccessfulExit` を偽にしているので `ThrottleInterval` の間隔で再起動を繰り返すと見込む)、darwin/amd64、Homebrew での配布である。

二重起動を止める排他ロック(9 節)は、Unix では `flock`、Windows では `LockFileEx` で取り、どちらもファイルを閉じるかプロセスが終わると消える。

Windows の `%ProgramData%\wgft` は、既定では親ディレクトリから `BUILTIN\Users` の読み取りと実行を継承する。状態ファイルの `Chmod(0o600)` は Windows では読み取り専用属性の切り替えにしかならず、この継承を止めないため、`agent.json` を PC の他の利用者が読める状態のまま残しうる。`agent.json.lock` と `agent.json.sock` は秘密を持たないが、同じ継承を受ける。agent はこれを、データディレクトリ全体ではなく、自分が書く 3 つのファイルだけを対象に締める。`WGFT_DATA_DIR` は利用者が任意の場所を指せる設定であり、ディレクトリそのものや直下の無関係なファイルまで毎起動で書き換えると、管理者が意図して加えた ACL(バックアップ用アカウントへの読み取りなど)を消しかねず、Unix の `MkdirAll` が既存のディレクトリを chmod しない設計とも食い違うためである。`agent.json` は `Save` が一時ファイルを作る瞬間に、SYSTEM・`BUILTIN\Administrators`・実行中プロセスの利用者の 3 者だけにフルアクセスを許す保護 DACL(継承を切ったもの)を付けて作る(Windows の `CreateFile` に `SECURITY_ATTRIBUTES` として渡す)。作ってから付け直すのでは、付け直すまでの間その一時ファイルが親ディレクトリから継承した緩い ACL のままになり、Windows はハンドルを開く瞬間にしかアクセス可否を見ないため、その間に別の利用者がハンドルを開けてしまえば後から DACL を締めてもその接続は取り消せない。同じディレクトリ内での rename はこの DACL をそのまま持ち越すので、緩い ACL の期間は生じない。緩い ACL の下で既に作られている `agent.json` は、起動時に読むたびに同じ DACL を単独で付け直して締める。Windows 11 の実機で見つかった環境がこれに当たる。`agent.json.lock` は `Acquire` が開く・作るたびに、`agent.json.sock` は制御ソケットを開くたびに、同じ DACL を単独で付け直す。データディレクトリ自体は、agent が新規に作った場合だけ同じ DACL(継承可能な形)を付けて作り、既に存在するディレクトリは変更しない。DACL を付け直せない場合(所有者でも Administrators でもない利用者で実行した場合など)は、その処理(読み込み・保存・ロック取得)を失敗として扱い起動を止める。制御ソケットだけは、開けない場合と同じく `rotate-key` の稼働中経路だけを諦め、agent 自体は動き続ける。9 節の SQLite の権限の扱い(グループとその他の権限だけを外し、それ以外は変えない)と同じ、変更を対象自身に限る考え方である。

制御ソケットには、agent.json の一時ファイルとは違い、既知の小さな窓が残る。`Listen` がソケットのファイルを作った瞬間から `SecureSocket` で締め直すまでの間、親ディレクトリから継承した緩い ACL のままであり、この間に接続した相手はその後の締め直しでは切断されない。この窓を完全に無くすには、専用のディレクトリを起動のたびに新規に作って先に締め、その中でだけソケットを開く必要があるが、制御ソケットが受け付けるコマンドは `rotate-key` の 1 つだけで、応答も新しい公開鍵かエラー文言のみであり秘密は一切やり取りしない。窓を突いた最悪の場合でも、利用者の意図しない鍵の作り直し(次のハンドシェイクから新しい鍵になるだけ)にとどまり、恒久トークンや wg 秘密鍵の漏えいには至らない。この非対称性から、ソケットの窓は塞がず既知の制約として残す。

この既存ファイルの締め直しは Windows だけで行う。Unix では `Chmod(0o600)` で足りるので、既存ファイルの締め直しは行わない。既存の `agent.json`・`agent.json.lock` を起動のたびに 0600 へ揃え直すと、管理者が意図して 0400 のように絞った権限を緩めてしまい、9 節の「余分な権限だけを外し、それ以外は変えない」という原則に反する。さらに、agent を非特権で動かす構成(`deploy/agent.compose.yaml` の `cap_drop: [ALL]` など)でボリューム上のファイルを所有していない場合、chmod は `EPERM` で失敗し、起動できなくなる。したがって、既存ファイルの締め直しと、制御ソケットを開けない場合に `rotate-key` の稼働中経路だけを諦める扱いは、Windows に限る。`Save` の一時ファイルへの `Chmod(0o600)` は失敗を呼び出し元に伝え、Unix の挙動は Windows の対応によって変えない。

SYSTEM と対話ユーザーの関係は次のとおりである。DACL は毎回そのときの実行者を含めて作り直すため、agent を Windows サービスとして SYSTEM で動かす場合は、SYSTEM 自身の項目が常に含まれるので読み書きできる。対話ユーザーによる実行では、UAC の昇格を伴わない管理者アカウントのトークンは `BUILTIN\Administrators` が拒否専用(deny-only)になり、このグループへの許可が効かないため、直前にそのファイルを書いた本人(同じ SID)でなければ読み書きできない。したがって、SYSTEM のサービス実行と対話ユーザーの実行を交互に行き来する運用では、最後に書き込んだ側と異なる非昇格の利用者は読み書きできず、昇格した管理者(「管理者として実行」)か SYSTEM だけが例外的に読める。wgft は Windows サービスや常駐の仕組みを持たず、`agent run` を対話利用者の権限で起動する運用だけを提供する方針とした(本節前段)ため、SYSTEM でのサービス実行と対話利用者の実行を行き来する運用そのものが生じない設計である。対話利用者どうしの間での UAC の昇格の有無によるこの挙動は上記のとおり成り立つが、SYSTEM としての実行との組み合わせは実機で確かめていない。

設定と状態の線引きは、「変えるのに片付けが要る、または保存済みの値と矛盾しうるもの」を状態として SQLite に置き、それ以外を設定としてファイルに置く、という基準による。エンドポイントやポート、MTU などは編集して再起動すれば変わる設定であり、サーバ鍵、証明書、ルール、エージェントの情報は状態である。動作モード(`WGFT_MODE`)と wg のアドレス帯(`WGFT_WG_ADDRESS`)は値そのものは設定だが、初回起動時に SQLite へ記録し、以後は起動のたびに env の値と照合するという扱いを受ける。どちらも変えると片付けが要る、または保存済みの値と矛盾しうるためである。設定を状態として持たない理由は、人がファイルとして読め、構成管理に置け、SQLite が壊れても復旧できる状態を保つためである。

`WGFT_MODE` は初回の起動で必須である。初回に省略すると、`kernel` か `userspace` かを指定するよう求めて起動を止め、環境を見て推測することはしない。初回に指定した値は SQLite に記録する。2 回目以降に省略した場合は、記録したモードで起動する。指定した場合は記録と照合し、一致すれば通常どおり起動する。食い違った場合は関門を通し、通れば記録を書き換えて起動し、通らなければ起動を拒否する。関門の中身は次のとおりである。`kernel` から `userspace` へ切り替えるときは、wg インタフェースと `table inet wgft` の残骸が無いことを確かめる。残骸があれば、先に `teardown` するよう案内して拒否する。残骸の有無を確かめるには `CAP_NET_ADMIN` が要るため、確かめられない環境では「確認できない」と警告したうえで、wireguard-go の UDP bind を試みる。この bind がカーネル側の `wgft0` に既に使われているポートと衝突して失敗した場合は、残骸の疑いとして host 上での `teardown` を案内する。`userspace` から `kernel` へ切り替えるときは残骸が生じないため、そのまま通す。モードの記録が無い既存の SQLite は、これまで `kernel` しか存在しなかったことから `kernel` とみなして記録する。`wgft server teardown` はモードの記録に触れない。切り替えの判断は起動時の照合と関門だけで完結する。

wg のアドレス帯(`WGFT_WG_ADDRESS`、既定 `10.200.0.1/24`)も初回起動時に記録し、以後は env の値と照合する。省略した場合は既定値を照合の対象にするので、省略しても起動は止まらない。記録済みの値と食い違えば、エージェントの割り当てアドレスと矛盾するため起動を拒否し、変えるには `wgft server teardown --purge` と全エージェントの再登録が要ると案内する。

インタフェース名(`WGFT_WG_INTERFACE`、既定 `wgft0`)は記録しないが、変更すると旧インタフェースが鍵ごと残ることがあるため、`wgft server check` と起動時に、自分のサーバ鍵を持つ別名の WireGuard デバイスが無いかを検査し、あれば警告する。

環境変数とファイルに置けるのは設定だけであり、その 1 回の起動や実行にだけ意味を持つ操作はフラグでしか渡さない。対象は `--adopt-existing`、`--force`、`--purge`、`--yes`、`--dry-run` である。たとえば `WGFT_ADOPT_EXISTING=true` のような値がファイルに残ると、再起動のたびに他人の WireGuard インタフェースを引き継いでしまうためである。例外は 2 つあり、どちらも居座っても害が無いことを仕様で保証している。1 つは `WGFT_MODE` と `WGFT_WG_ADDRESS` で、初回に記録された後は照合にしか使われない。もう 1 つは `WGFT_JOIN`(エージェントの初回登録)で、これは 1 回限りの操作でありながら、compose ファイルに残ることを前提に設計してある。エージェントは使用済みの登録トークンのハッシュを状態ファイルに残し、`WGFT_JOIN` の値がそれと同じであれば登録を試みずに止まる(5.1 節)。恒久トークンが無効化されて認証が拒否された場合だけ、この値を使って再登録する。

## 12. マイルストーン

1. `proto` のスキーマ(全体状態とルール)と `vpsd` の nftables 適用。ルールは JSON ファイルから読み、API なし
2. 登録 API、stream での公開鍵の宣言と全体状態の配信、エージェント。実際のゲームサーバで UDP と TCP が通ることを確認する。トークンの扱い(5.1 節)、サーバ秘密鍵の永続化、公開鍵の検証、stream の 1 本化とバックオフ、無効化後の復帰経路、バッチ操作、状態ファイルの原子的な書き込みと flock、input チェーン、ハーフクローズ、エンドポイントの再解決、bind 中ポートの衝突検査はここで入れる
3. 接続元制限とレート制限。conntrack の収束手順、プロキシモードの中継を閉じる部品、カウンタの累積、`error` の再試行、wg0 属性の突き合わせ、IP の食い違いによる窃取の警告もここで入れる
4. Web UI
5. `vps_mode = proxy` と PROXY protocol
6. 既存のリバースプロキシから 443 を移し、そちらを停止する

2 が終われば当初の問題は解決しているので、3 以降は使いながら進める。

- macOS のエージェントの UDP の送信バッファを拡大(2026-09-19、macOS の実機での確認を受けて):macOS 27(arm64)のエージェントを実機の Linux の VPS(v0.3.0、カーネルモード)に対して確かめたところ、8000 バイトの UDP は通ったが、12000 バイトの UDP は VPS とトンネルを通ってエージェントまで届き、エージェントから宛先への書き込みで落ちた。原因は、macOS の UDP の送信バッファの既定が `net.inet.udp.maxdgram` の 9216 バイトで、これを超える書き込みが `EMSGSIZE` で即座に失敗することである。この失敗はログを出さずに、その送信元のセッションを閉じていた。`SetWriteBuffer` で送信バッファを上げると制限が外れることを確かめた。7 節に、macOS に限り宛先へのカーネルのソケットの送信バッファを 65535 バイトに上げること、宛先への書き込みの失敗をリスナーごとに 1 分に 1 回までログに出すことを追記した。セッションごとの Go のバッファは増やさない(2026-09-18 の項目の方針のまま)。修正後のエージェントで、12000 バイトと 30000 バイトの UDP が実機の VPS を通って中継され、同じ送信元ポートのままセッションが閉じられないことを確認した。未確認:同時フロー数の上限までセッションを張ったときの macOS のエージェントのメモリ使用量
- macOS のエージェントと CLI を公開(2026-09-19、macOS の実機での確認を受けて):macOS 27(Apple シリコン)のエージェントを、ホームルータの NAT の内側から実機の VPS(v0.3.0、カーネルモード)に対して確認した。登録、トンネル、Mac 自身と LAN の他のホストへの UDP と TCP の中継、Mac と server の再起動からの復帰、強制終了後の launchd による再起動、二重起動の拒否、稼働中の `rotate-key`、データディレクトリと認証情報ファイルの権限が通った。これを受けて darwin/arm64 を GoReleaser の build、release の証明と SBOM、README に加えることを決めた。darwin/amd64 は Intel Mac を対象にしないため公開しない。常駐には `UserName` 付きの LaunchDaemon を推奨し、`deploy/io.github.rahanahu.wgft.agent.plist` を加えた。LaunchAgent として起動した agent は LAN の他のホストに接続できず、ターミナルからの起動と LaunchDaemon では接続できたためである。原因をローカルネットワークのプライバシー保護とするのは症状からの推測である。FileVault を有効にした Mac では再起動後に最初のログインまで LaunchDaemon が起動しないが、想定する利用者はその Mac のセッションでゲームサーバも動かすため、対処せず文書に書く判断をした。初回登録はターミナルから行い、全員が読める plist には join string を書かない。11a 節を改訂した。未確認:同時フロー数の上限でのメモリ使用量、FileVault を無効にした Mac でのログイン前の起動、ログアウト後の動作、終了コード 3 での launchd の挙動、darwin/amd64、Homebrew
- macOS のエージェントのメモリ使用量を測定(2026-09-19、同時フロー数の上限での確認):Apple シリコンの Mac のコンテナで server をユーザー空間モードで動かし、Mac 上の macOS のエージェントと、比較のためにコンテナ内の Linux のエージェントを、どちらも既定の上限(UDP 8192、TCP 2048)で確かめた。UDP のセッション 8192 件と無通信の TCP の接続 2048 本を保持した状態では、macOS のエージェントの RSS は約 130 から 140 MiB、同じ環境の Linux のエージェントは約 160 MiB で、どちらも 7 節のソフト上限(216 MiB)の内に収まった。保持の費用から、macOS のエージェントも UDP のセッションごとに 65535 バイトを持たず、到着だけを待つ経路を使っていることが分かった。保持した状態で上限を超える UDP のフラッドを加えても、macOS のエージェントは約 200 MiB に収まった。一方、上限を超える TCP の接続のフラッドを加えると、macOS と Linux のどちらのエージェントも約 650 から 700 MiB に達し、ソフト上限と 2026-09-18 のラボの実測の約 3 倍になった。この超過は macOS に固有ではない。macOS の `ps` の RSS は負荷が止んだ後も高いまま残ったが、物理フットプリント(`footprint`)は約 100 MB に下がった。macOS については設計を変えず、11a 節の未確認の点から上限でのメモリ使用量を外し、測定の結果を書いた。TCP の接続のフラッドでの超過は 13 節の未決事項に加えた(GitHub issue #25)。未確認:TCP の接続のフラッドでの超過の原因(拒んだ接続が netstack の TIME_WAIT に残ると推測している)、`vpsd` のユーザー空間モードへの影響、macOS に限り TCP の接続のフラッドの間に保持していた TCP の接続の一部が相手側から閉じられた原因
