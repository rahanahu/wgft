### 7a.10 Resource Guard の再設計

Phase 6 では、`internal/flowcap` を `internal/resource` に改め、Resource Guard(7a.5 節)を Admission Policy から型の上でも切り離す。userspace のルールごとの隔離は、共有プールと隔離予約の方式に置き換える。隔離予約は、その後にルールの登録ごとの最低分と予備の形に改めた(後述の「共有プール、最低分と予備」と移行の手順 6)。kernel 側は conntrack の表と set の大きさを観測して提示するだけで、新しい強制は加えない。Phase 6 は、Phase 5(7a.9 節)の移行の手順 3 で送信元ごとの同時フロー数を評価器へ移した後のコードから始める。

#### 判定の位置と範囲

Resource Guard は、Admission Policy がフローを通した後にだけ判定する(7a.9 節の Phase 6 との境界)。Go の側で判定する場所は、`relay.Manager` の UDP の新しいセッションと TCP の accept、`internal/vpsd/proxyrelay` の accept の 3 つである。Admission Policy がフローを通した時点で、そのフローはレートのトークンと送信元ごとの同時フロー数の枠を使っている。Resource Guard が拒んだときは、評価器が返した手形で送信元ごとの枠をその場で返し(7a.9 節の `AdmitFlow`)、レートのトークンは返さない。kernel でも、conntrack の表が溢れて落ちるフローは prerouting の meter のトークンを既に使っているので、両モードで同じ扱いになる。

Resource Guard の対象は次の 4 つである。

- プロセス全体のフロー予算:`WGFT_MAX_UDP_FLOWS`/`WGFT_MAX_TCP_FLOWS`(7 節)の値で、Go が保持するフローの合計を抑える
- ルールごとの隔離:1 つのルールへのフラッドが予算を使い切り、他のルールの新しいフローまで止めることを防ぐ。後述の共有プール、ルール 1 本の上限、登録ごとの最低分と予備で実現する
- メモリのソフト上限:予算から導く値をランタイムに設定する(後述)。GC の目標であり、メモリの使用量の上限ではない
- kernel の資源:conntrack の表と nftables の set の大きさを観測し、足りなければ提示する(後述)

#### 型の分割

`flowcap.Limits` は、次の 2 つの型に分ける。

| 型 | 置き場所 | 持つもの | 使う側 |
|---|---|---|---|
| `AdmissionLimits` | `internal/policy` | `UDPPerSource`、`TCPPerSource`、無効を表す `PerSourceOff`、既定値(256、128)、実効値を返す `UDPPerSourceCap`/`TCPPerSourceCap` | `policy.Build`、`planner.Input`、server の設定層 |
| `resource.Limits`(7a.5 節の `ResourceLimits`) | `internal/resource` | `UDPTotal`、`TCPTotal`、設定できる範囲(`TotalMin`、`TotalMax`)、既定値(8192、2048)、`MemoryLimit` | userspace backend、`proxyrelay`、agent、`cmd/wgft` のメモリの設定 |

`resource.Limits` は、7a.5 節が `ResourceLimits` と呼んだ型である。package の名前と型の名前が重ならないよう、型は `Limits` とする。ゼロ値の項目を既定値で埋める規則(`WithDefaults`)は、両方の型が今の `flowcap.Limits` からそのまま引き継ぐ。ゼロ値を「上限なし」にしないのは、設定層を通らずに組み立てた値で守りが黙って外れるためである。

`flowcap.Counter` は `resource.Pool` に置き換える。Phase 5 の後の `Counter` はプロセス全体の数だけを数えており、ルールごとの数は `relay.Manager` と `proxyrelay` がそれぞれ listener の数から別に数えている。`Pool` は両方を 1 つの排他の中で数える。上限で拒んだことのログを間引く `flowcap.LogGate` は、宛先への dial の失敗のログにも使うので `internal/resource` には置かず、小さな package `internal/lograte` へ移す。

`cmd/wgft` の設定層は、`WGFT_MAX_*_FLOWS` から `resource.Limits` を、`WGFT_MAX_*_FLOWS_PER_SOURCE` から `AdmissionLimits` を作る。server は両方を、agent は `resource.Limits` だけを受け取る。設定項目の名前、範囲の検査、エラーの文言は変えない。

#### 共有プール、最低分と予備

`resource.Pool` は、プロトコルごとに 1 つずつ作る、プロセス全体のフロー予算である。フローは listener(プロトコルとポート)で受け付け、2 通りに数える。最低分と請求の合計は、ルールの登録(後述)に数える。フローは受け付けたときの登録で数え、後述の「退役した登録のフローの帰属」の場合だけ別の登録へ移す。分割で listener の所属ルールが変わっても、分割元の登録が続くあいだ、その listener の既存のフローは分割元で数え、移動先のルールでは数えない(7 節、2026-09-29 の所有者の決定)。ルール 1 本の上限と予約の部分の入口は、登録の listener が今運んでいるフローの数も見る。この数は改訂の前のルールのフロー数と同じ数え方である(2026-09-30 の所有者の決定)。改訂の前は、ルールのフロー数をそのルールの listener のフロー数の合計とし、分割と統合で移った listener の既存のフローを移動先のルールで数え、予約 `q = floor(floor(T/2) / (N - 1))` で判定していた(改訂の記録 2026-09-20)。

プールの値は次の記号で定める。

- `T`:プロセス全体の予算(`resource.Limits` の `UDPTotal` または `TCPTotal`)
- `C`:ルールが 2 本以上あるときの、ルール 1 本の上限。どの `T` でも `ceil(T/2)` である
- `f`:登録ごとの下限。`T` によらない定数 4 であり、設定項目にしない
- `P`:次に加わる 1 つの登録のための予備。常に `f` である。帳簿の値として持たず、後述の条件 4 と条件 5 に常に含める
- 登録:1 つの `Pool` の中で、あるルール ID が新しいフローを受け付けている listener を 1 つ以上持ち続けている期間であり、ルールの登録と呼ぶ。エージェントの登録(5.1 節)とは別のものである。そのルールの受け付けている listener が 0 個から 1 個になった時点で始まり、0 個になった時点で退役する。退役した登録には、以後どの listener も加わらない。同じ ID のルールが再び受け付けを始めると、新しい登録になる。ルールの削除と無効化、ルール単位の fail-closed(7a.3 節)、統合と名前の変更で消えるルールは登録を退役させる
- `A`:今受け付けている登録の集合。listener が新しいフローを受け付けるのは、bind が成功してから、`Retiring` になるか閉じるまでのあいだである。bind の途中の listener と bind に失敗した listener は受け付けていない。listener が受け付けを始めるのは bind が成功した時点であり、中継を始めるより前である。この 2 つの順序を逆にすると、bind が終わるまでのあいだ `N` が増えて他のルールの最低分が変わり(前者)、受け付けを始める前に受けたフローが拒まれる(後者)
- `N`:`A` の登録の数
- `q`:隔離予約。`N` が 2 以上なら `floor(floor((T - f)/2) / (N - 1))` で、`N` が 1 なら 0 である。改訂の前の式の `T` を、予備を除いた `T - f` に置き換えたものである
- `m`:登録ごとの最低分 `max(f, q)`。受け付けているすべての登録で同じ値であり、`N` が変わるたびに求め直す。最低分のうち最初の `f` を下限の部分、残りを予約の部分と呼ぶ
- `a_g`:登録 `g` に数える、まだ終わっていないフローの数。listener が `Retiring` になっても閉じても、そのフローが終わるまで数える。後述の帰属の規則で移したフローは、移し先の登録で数える
- `c_g`:登録 `g` の listener が運ぶ数。`g` に今属する受け付けている listener が運ぶ、まだ終わっていないフローの数で、そのフローをどの登録に数えるかは問わない。フローを運ぶ listener は、そのフローを受け付けた listener である。退役した登録は受け付けている listener を持たないので 0 である。受け付けているルールと登録は 1 対 1 なので、値は改訂の前のルールのフロー数(そのルールの受け付けている listener のフロー数の合計)と同じである
- `x_g`:`max(a_g, c_g)`。予約の部分の入口の判定にだけ使う
- `u`:プロセス全体のフロー数。退役した登録のフローも含める
- `S`:満たされていない最低分の合計 `Σ max(0, m - a_g)`。和は `A` の登録 `g` を取る
- `S_f`:満たされていない下限の合計 `Σ max(0, f - a_g)`。和は `A` の登録 `g` を取る

受け付けている listener の新しいフローは、その listener が属する今の登録 `g` について、次の順に判定する。

1. `u < T` を満たさなければ `budget` で拒む
2. `N ≥ 2` のとき、`c_g < C` を満たさなければ `rule_cap` で拒む
3. `a_g < f`(下限の部分)なら通す
4. `x_g < m`(予約の部分)なら、`u + 1 + S_f + P ≤ T`(他の登録の満たされていない下限と予備を残しても、空きが 1 つ以上ある)のとき通し、満たさなければ `floor` で拒む
5. それ以外は、`u + 1 + S + P ≤ T`(満たされていない最低分と予備を残しても、空きが 1 つ以上ある)のとき通す。満たさなければ拒み、理由は `u + 1 + S > T` なら `reserve`、そうでなければ `spare` である。`a_g < m` でも `x_g ≥ m` のため条件 4 に入らなかった登録では、`S` に自分の不足 `m - a_g` も入る

空いた枠が回る順は、下限の部分、予備、予約の部分、共有分である。下限の部分は予備の枠も使えるので、後から加わった登録は予備として空いていた枠で下限を得る。

条件 2 は `c_g` で、条件 4 は `x_g` で判定し、下限の部分と `S`、`S_f`、請求の合計は `a_g` で数える。分割の直後、分割先は新しい登録として `a_g = 0` から数え始める。`C` と予約の部分の入口を `a_g` で判定すると、分割先の listener が分割元の既存のフローを運んでいても分割先は最低分を新しく取れるので、フラッドを受けたポートを分割で切り出すたびに無関係のルールの取り分が減り、分割を重ねると無関係のルールが下限を下回り 0 本まで下がる(使い捨ての模型で確かめた)。`c_g` で判定すると、分割先の listener が既に `C` 以上を運べば分割先を止め、`m` 以上を運べば予約の部分を使わせないので、分割先が新しく取る数は、改訂の前と同じく分割先の listener が既に運ぶフローで抑えられる。予約の部分の入口の `x_g` は、改訂の前の「ルールのフロー数が予約以上なら予約の内側ではない」を登録の上で書いたものである。下限の部分は `a_g` で判定するので、新しい登録の下限は listener が運ぶ数に左右されない。ただし条件 2 が条件 3 より先なので、listener が `C` 以上を運ぶ登録は下限の分も取れない。条件 2 を条件 3 と条件 4 より後に置くと、分割先が `a_g = 0` のまま最低分を取れて、分割先を止められない。

`rule_cap` は改訂の前と同じ定義である。`c_g` は改訂の前のルールのフロー数と同じ数え方だからである。`reserve` は、改訂の前と同じく、自分の取り分に届いていて、残りの空きが取り分の未使用分で埋まっていることを表す。改訂の前の定義の `q` を `m` に、ルールのフロー数を `x_g` に置き換えたものである。`floor` は、自分の最低分に届いていないルールの拒否で、空きを他の登録の満たされていない下限と予備に残すためのものである。改訂の前の定義では予約の内側として `u < T` なら通していた場合に当たる。`spare` は、`x_g` で見て自分の最低分に届いているルールの拒否で、他の登録の満たされていない最低分と予備を残すと空きが無いが、予備を除けば空きがある場合である。他の登録の最低分が満たされていない場合を含み、ルールが 1 本のときにも起きる。`floor` と `spare` はどちらも `reserve` と意味が違うので、`reserve` にまとめず、7a.11 節の開いた集合への値の加算とする。

受け付けていない listener(bind の前、`Retiring`、閉じた後)の新しいフローは、この判定の前に拒む。この拒否は予算による拒否ではないので、拒否の数に入れず、ログにも出さない。中継は、拒んだ TCP の接続を他の拒否と同じく RST で終え(7a.5 節)、UDP のデータグラムを捨てる。この拒否は予算を持たない `Pool`(`T` が 0 以下。試験だけで使う)でも行う。listener を止める操作の途中、中継が停止の印を下ろしてから `Pool` の listener を止めるまでのあいだに取得したフローは、`Pool` から見ると受け付けている listener のフローなので、予算が埋まっていれば予算による拒否として数える。改訂の前と同じ振る舞いである。

#### 退役した登録のフローの帰属

ルールの登録が退役したとき、その登録のまだ終わっていないフローのうち、新しいフローを受け付けている listener が運ぶものは、その listener の今の登録へ移して数える。フローを運ぶ listener は、そのフローを受け付けた listener であり、所属ルールが変わっても変わらない。listener が登録に加わったとき(`Retiring` の UDP の listener の再開と、受け付けている listener の所属ルールの付け替え)も、その listener が運ぶフローのうち退役した登録にあるものを、加わった登録へ移す。移すのはこの 2 つの時点だけである。

- 受け付けていない listener(`Retiring`、閉じた後)が運ぶフローは移さず、退役した登録に残す。そのフローはどのルールの数にも入らず、`u` にだけ入る。`Retiring` の listener が後で受け付けを再開すれば、そのときに移す
- 生きている登録どうしでは移さない。分割の後、分割元の登録が続くあいだは、分割先の listener が運ぶ既存のフローは分割元で数える
- 移したフローは、移し先の登録が続くあいだは動かない。移し先が後で退役すれば、同じ規則でもう一度移る

この規則により、統合と名前の変更で消えたルールの既存のフロー、受け付けを再開した `Retiring` の UDP の listener の旧いセッション、分割の後に削除、無効化、fail-closed、閉じ直しをした分割元のフローのうち分割先の listener が運ぶものは、それを運ぶ listener の今のルールで数える。移しは `u` を変えず、移し先の不足を減らすだけなので、請求の合計を増やさない。listener の所属は変わらないので `c_g` も変えない。統合の後は、統合先の listener が運ぶ数が `C` を超えることがあり、そのあいだ統合先は `rule_cap` で新しいフローを拒まれる。改訂の前の統合と同じ振る舞いである。

移しは、遷移の時点で `Pool` の操作の順に当てる。どの時点でも受け付けている listener が運ぶフローをその listener の今の登録で数える、という規則にすると、分割でも生きている分割元から移すことになり、所属ルールの付け替えだけで請求の合計が増える。そのため遷移の時点だけで移し、1 回の適用の中の操作の順に結果が依る場合を残す(後述の「保証しないこと」)。適用の終わりに退役をまとめて処理する操作は持たない(2026-09-30、所有者の決定)。

#### 最低分と予備の性質

判定と帰属の規則は、1 つの `Pool` の中で次の性質を持つ。

- `u ≤ T` は常に成り立つ
- `N ≥ 2` のあいだ、`c_g` が `C` 以上の登録は新しいフローを通せない。フローの受け付けで `c_g` が `C` を超えることはない。`a_g` は `C` を超えることがある
- `m ≤ floor((T - f)/2) < C` なので、`rule_cap` が最低分に届いていない登録を拒むのは、その登録の listener が運ぶフローのうち `C - a_g` 本以上が他の受け付けている登録に数えるフローのときだけである。他の登録のフローが listener に乗るのは、分割元が続く分割と、元の登録が続く付け替えで listener を受け取ったときだけである。新しいルールは最初は何も運ばないので `rule_cap` に拒まれない
- 予約の部分の入口が `a_g < m` の登録を閉じるのは、その登録の listener が、他の受け付けている登録に数えるフローを `m - a_g` 本以上運ぶときだけである
- 請求の合計 `u + S + P` が `T` を超える状態を許す。請求の合計を `T` より大きくするのは設定の変更だけで、フローの受け付けと終わりと帰属の移しはそれを増やさない。新しい登録のほかに、`N` が減って `m` が上がる退役と、`N` が 1 から 2 に増えて `m` が `f` から予算の約半分に上がる登録がこれに当たる
- 請求の合計が `T` 以下の時点では、`A` のどの登録も、その後に設定の変更が無く `c_g` が `C` 未満である限り、`a_g` が下限に届くまでと、その後 `x_g` が最低分 `m` に届くまで、新しいフローを通せる。`m` は改訂の前の `q` より高々 `f/2` 小さい。`q` が `f` 以上である限り `N × m + P ≤ T` が成り立つので、ルールの数が変わらないあいだに通したフローだけなら、請求の合計は `T` 以下に保たれる
- 請求の合計が `T` 以下なら `u ≤ T - P` なので、`budget`、`reserve`、`floor` は起きない。この 3 つは請求の合計が `T` を超えているあいだだけ起きる
- 空きが満たされていない下限と予備の合計以上(`T - u ≥ S_f + P`)という式は、フローの受け付けと終わり、退役、`N` の変化、帰属の移しでは崩れず、崩すのは新しい登録だけである。この式が成り立つあいだ、下限に届かないどの登録も、`c_g` が `C` 未満なら、他の登録の取得の順によらず下限まで新しいフローを通せる。加わる時点で `u + S_f + P ≤ T` なら、新しい登録も下限まで通せる。下限の保証はこの式が成り立つあいだに限る。予備は 1 つ分なので、続けて加わった 2 つ目以降の登録は予備が戻るまで保証されず、そのあいだは既存の登録で下限に届いていないものも含めて先着順になる
- 下限に届かない登録は、`c_g` が `C` 未満なら、`u = T` のときだけ拒まれる
- 請求の合計が `T` を超えているあいだは条件 5 を満たさないので、終わったフローの空きは、下限、予備の回復、予約の部分の順に回り、共有分には回らない。予約の部分どうしは先着順である。既存のフローは追い出さないので、この状態が続く時間に上限は無い
- ルールが 2 本以上あるとき、他のルールがフローを持たなければ、1 本のルールが保持できるのは `min(C, max(m, T - P - (N - 1) × m))` である。ルールが 2 本なら `ceil((T - f)/2)` で、`C` を下回る。このため、1 本のルールへのフラッドで `rule_cap` が拒否の理由になるのは、`T - P - (N - 1) × m ≥ C` となる構成である。`m` の切り捨てのため、この構成はルールの数に対して単調ではない(既定の TCP では 4 本から 7 本が最初の範囲である)。ほかに、ルールが加わって `m` が下がった直後と、統合や分割や付け替えで listener が `C` 以上を運ぶ登録でも `rule_cap` になる。ルールが 1 本なら、そのルールは `T - P` まで保持できる
- `q` が `f` を下回るほどルールが多い構成では `m = f` になる。`(N + 1) × f ≥ T` のときは条件 5 を満たせないので、どのルールも下限までしか保持できない。`f = 4` では、既定の TCP で受け付けているルールが 511 本以上のときに当たる。`(N + 1) × f > T` では予備の保証が成り立たない。`(N + 1) × f ≤ T` でも、下限の保証は前述の `T - u ≥ S_f + P` が成り立つあいだに限る
- 受け付けている listener が運ぶフローが、退役した登録に残ることは無い

使い捨ての模型では、フラッドを受けたポートを分割で切り出すことを重ねる場面(フラッドが 1 ポートに集中する場合と、範囲に一様な場合)、分割と統合を数回往復する場面、統合、名前の変更、UDP の再開、分割の後の分割元の削除の場面で、無関係のルールが新しく通せる数は、改訂の前の形より少ない場合でも、その差は数本以内だった。この値は模型の場面の値であり、証明ではない。分割元を削除した後に閉じた listener の旧い接続が残るあいだは除く。

この形は次のことを保証しない。

- 受け付けていない listener の旧い接続:閉じた listener と、再開しない `Retiring` の listener が運ぶ旧い接続は、切れるか終わるまで退役した登録に残り、どのルールの数にも入らずに `u` を占める。そのあいだに同じ ID のルールを登録し直したり、ルールの数が変わったりすると、無関係のルールが最低分を下回ることがあり、最悪で下限まで下がる。閉じた listener の接続はその場で切るので、影響は切り終えるまでのあいだと考えるが、未確認である。fail-closed の `Retiring` の listener の接続は、ルールが失敗しているあいだ残る
- 分割元が続くあいだの分割元と分割先:分割元の登録が続くあいだ、分割先の listener が運ぶ既存のフローは分割元の `a_g` に数える。このため、分割元の `a_g` が `m` 以上なら、分割元に残ったポートの新しいフローは下限の部分も予約の部分も使えず、共有分だけになり、請求の合計が `T` に近いと 1 本も通せない。改訂の前の形では、分割元のフロー数を分割元に残った listener のフローで数えるので、予約の内側として通せる。判定の式から計算し、使い捨ての模型でも同じ値を確かめた例では、`T = 2048` で、ルール B の 1 ポートへのフラッドで B が 1022 本を持ち、そのポートを分割して D とすると、B に残ったポートは 1 本も通せない(改訂の前の形では 512 本まで通せる)。この状態は、分割先の listener が運ぶ既存のフローが終わるか、分割元の登録が退役して帰属の規則でそのフローが分割先へ移るまで続く。分割元に残ったポートの新しいフローをすぐに通すには、分割の後に分割元のルールを別の ID に置き換える。ルールの名前を変える専用のコマンドは無いので、分割元のルールの削除と、同じポート、同じ宛先で新しい ID を持つルールの追加を、1 つのバッチで適用する。`rule import` なら、`rule ls --json` の `rules` を書き出し、分割元の行の `id` を消して読み込む。分割元の登録が退役し、分割先の listener が運ぶ既存のフローは帰属の規則で分割先へ移り、新しい ID の登録は最低分を得る。ポートと宛先が変わらないので listener は閉じずに所属ルールを付け替えるだけであり、分割元に残ったポートの既存の接続は切れない。この手順は、ユーザー空間モードの server とエージェントで、`rule import` の経路についてラボで確かめた(`lab/lifecycle.sh` の check 5g)。フラッドを受けたポートを分割で切り出し、分割元に別の利用者のポートが残る場合に当たる。無関係のルールの最低分はこの影響を受けない。分割先は新しい登録として最低分を全部請求し、分割先の listener が既存のフローを `m` 以上運べば予約の部分を使えず、その不足は請求に残って他のルールの最低分を超える取得を止める
- 1 回の適用の中の順:1 回の適用(`vpsd` の 1 回の `Commit` か、エージェントの 1 回の `Apply`)の中で、分割元の最後の listener の閉鎖と、分割先の listener の別のルールへの付け替えが重なると、既存のフローをどちらのルールで数えるかは操作の順に依る。悪い順では、無関係のルールが新しく通せる数が下がる。使い捨ての模型では、`T = 2048` で良い順の 511 に対して悪い順で 341 だった(改訂の前は 512)。`vpsd` の順は listener の表の順で決まらず、1 つのバッチにこの 2 つの変更を入れる経路は `rule import` で作れる。`proxyrelay` はいつも閉鎖を付け替えより先に行う。エージェントは操作をポートの順に行うので、同じルールの listener の開放が閉鎖より先になると、登録が退役せずフローを移さないことがある。この場合の影響は関わるルールの中にとどまる
- 移し先と分割元の上限:帰属の移しの後、移し先の `a_g` と `c_g` は `C` を超えることがあり、最大で `T` までである。`c_g` が `C` を下回るまで、移し先は新しいフローを `rule_cap` で拒まれる。分割元は、分割先の listener が運ぶ既存のフローを `a_g` に数え続け、自分の listener が運ぶ数が `C` 未満なら共有分を取れるので、`a_g` が `C` を超えることがある。この場合、後でルールが減って `m` が上がると、無関係のルールが通せる数が、`C` を登録の数で判定する形より数本から数十本少なくなりうると見積もるが、模型では再現していない。改訂の前の形も同じ振る舞いである
- listener が運ぶ数による行き詰まり:listener が `C` 以上を運ぶ登録は、自分に数えるフローが 1 本も無くても `rule_cap` で拒まれる。自分の他のポートの新しいフローも同じである。長く続く接続が残るあいだは拒まれ続ける。改訂の前と同じ振る舞いである
- フラッドを受けた分割先の新しいフロー:予約の部分の入口が閉じた分割先は、自分の不足を共有分の条件でしか取れない。共有分の条件は取る登録自身の不足を差し引かず、請求の合計が `T` 未満のときだけ通すので、分割の時点で請求の合計が `T` 以上なら、分割先は下限の分しか通せない。請求の合計に 1 つでも余りがあれば、分割先の取得は請求の合計を変えないので、分割先は不足を最低分まで取れる。このため、フラッドを受けた分割先が新しく通せる数は、分割の時点の請求の合計によって、改訂の前より少ないことも多いこともある。使い捨ての模型で、分割の時点の請求の合計だけを変えてこの違いを確かめた。無関係のルールの最低分には影響しない
- 分割と統合の往復:分割のたびに分割先は新しい登録になり、下限の部分は `u < T` だけで通るので、フラッドを受けた分割先は下限の分を取る。統合で分割先が退役すると、その分は帰属の規則で統合先へ移り、請求の合計が `T` を超える量が 1 往復ごとに `f` 増える。使い捨ての模型では、往復を百回を超えて重ねると統合の後の無関係のルールが最低分を下回り始め、その後は下がりが止まった。止まるのは、往復ごとに分割先の listener が運ぶ数が増えて `C` に届くと、条件 2 が下限の部分より先に分割先を拒むためであることを、同じ模型で確かめた
- 続けて加わる登録:フラッドを受ける新しいルールを 1 本ずつ加えていくと、無関係のルールは最低分を下回り、下限の分も失うことがある。改訂の前の形にも同じ型の後退がある
- 請求の超過が続く時間:請求の合計が `T` を超える状態は既存のフローが終わるまで続く。長く続く接続で予算が埋まっていると、新しいルールは誰かが切断するまで下限も得られないことがある
- ルールが 2 本の構成の共有分:`T - f` が偶数なら `2 × m + P = T` になるので、ルールが 2 本の構成では共有分が無く、どちらのルールも、他方が空いていても `m` を超えて保持できない
- 最低分は登録ごとで、listener ごとではない。範囲のルールでは、最初に受け付けたポートが最低分を使う
- フローの数のほかの資源(byte、バッファ、RSS、TIME_WAIT、netstack の endpoint)は、この式では抑えない

閉じ直し(7 節の「実効宛先が違う:閉じてから開く」)は、`Pool` の上では別の操作として扱わない。閉じ直しのあいだもそのルールが別の listener で受け付けていれば登録は続き、そうでなければ旧い登録が退役して新しい登録が始まる。エージェントの 1 ポートのルールの閉じ直しは後者、範囲のルールの閉じ直しと、listener を開き直さない server の中継と `proxyrelay` の宛先の変更は前者に当たる。閉じた listener が運ぶフローは移さない。

`A`、登録、`m`、`S`、`S_f` と帰属の移しは、トランザクションの `Commit`(7a.2 節の戻れない地点の後)で更新する。更新はメモリの上の値の置き換えだけで失敗しないので、frontend の `Commit` の「失敗してはならない」という約束に合う。既に数えているフローを切ることも追い出すこともしない。`Commit` を持たないエージェントの `Apply` の経路(7 節)では、listener ごとの bind の成功が同じ地点に当たる。

1 回の判定は、`a_g`、`u`、`S`、`S_f` を足し引きで保った値から、1 つの排他の中で一定の手間で行う。`m` は `N` が変わるときだけ変わるので、`A` の登録の数に比例する `S` の作り直しは、登録の始まりと退役のときだけ行う。帰属の移しの手間は、退役した登録の、listener と登録の組の数に比例する。どれも `Commit` から呼ばれる操作であり、フローの取得と返却の経路には入らない。`S_f` は `N` によらないので作り直さない。フローの取得は、そのフローを受け付けた listener と登録の組を指す手形を返し、中継はフローの終わりにその手形を 1 度だけ返す。2 度目の返却は何も変えない。`Pool` の排他は末端の錠であり、`Pool` はその排他を持ったまま中継の関数を呼ばない。

保証は 1 つの `Pool` の中に限る。エージェントはトンネルを立て直すたびに `Pool` を作り直すので(10.2c 節)、旧い `Pool` のフローが終わるまでのあいだ、プロセス全体の保持数は `T` を超えうる。旧い世代の数に構造の上限は無いが、立て直しを起こすのは `vpsd` の全体状態、管理者の操作、7 節の作り直しの判定だけであり、旧い世代は、それを使っていた処理がすべて戻ると消える。プロセス全体のメモリの上界での扱いは 7 節の「プロセス全体のメモリの上界」の段落に書く(2026-09-30、所有者の決定)。

#### 既定値と今の挙動との対応

ルールごとの隔離は、次の 3 点だけから成る。追加の設定項目は持たない。

- ルールが 2 本以上なら、ルール 1 本の listener が運ぶフローの数は `C = ceil(T/2)` を超えない
- 受け付けている登録はそれぞれ最低分 `m = max(f, q)` を持つ。`q` は予算から予備を除いた `T - f` から求める
- 次に加わる 1 つの登録のために予備 `P = f = 4` を空けておき、残りは先着順に共有する

置き換える前のルールごとの上限は `max(floor(T/2), min(F, T))` で、`F` は設定項目にする前の固定値(UDP 4096、TCP 1024)である。`F` は実際の資源の境界ではなく、以前の実装から引き継いだ定数なので、Phase 6 の式には使わない。既定の予算はちょうど `T = 2F`(UDP 8192、TCP 2048)であり、`C` は以前の上限と同じ値(4096、1024)になる。`T` が既定以上なら、`C` は以前の上限と同じか、`T` が奇数のときだけ 1 大きい。ルールが 2 本以上の構成でルール 1 本の上限が下がるのは、`T` が既定より小さい場合だけである。`T` が `F` 以下なら以前の上限 `T` が `ceil(T/2)` に、`F` と `2F` のあいだなら以前の上限 `F` が `ceil(T/2)` に下がり(UDP 6000 なら 4096 が 3000)、代わりにルール間の隔離を持つ。

| 予算 `T` | 置き換える前のルールごとの上限 | `C` | `N = 1` の上限 | `N = 2` の `m` と 1 本の上限 | `N = 3` の `m` と 1 本の上限 |
|---|---|---|---|---|---|
| UDP 2048 | 2048 | 1024 | 2044 | 1022、1022 | 511、1022 |
| UDP 4096 | 4096 | 2048 | 4092 | 2046、2046 | 1023、2046 |
| UDP 6000 | 4096 | 3000 | 5996 | 2998、2998 | 1499、2998 |
| UDP 8192(既定) | 4096 | 4096 | 8188 | 4094、4094 | 2047、4094 |
| UDP 16384 | 8192 | 8192 | 16380 | 8190、8190 | 4095、8190 |
| TCP 1024 | 1024 | 512 | 1020 | 510、510 | 255、510 |
| TCP 2048(既定) | 1024 | 1024 | 2044 | 1022、1022 | 511、1022 |

表の「1 本の上限」は、他のルールがフローを持たないときの値である。隔離予約 `q = floor(floor(T/2) / (N - 1))` の形(2026-09-20 から)との違いは次のとおりである。

- ルールが 1 本なら、保持できるのは `T - 4` である(`q` の形では `T`)
- ルールが 2 本以上なら、各ルールの最低分と 1 本の上限は `q` の形より高々 2 小さい。既定の TCP でルールが 2 本なら、1 本のルールが保持できるのは 1022 で、`C` の 1024 に届かない。このため、フラッドを受けたルールの拒否の理由は `rule_cap` ではなく `spare` になる
- 新しいルールは、予算が埋まっていても、加わる時点で予備の分の空きがあれば、すぐに下限の 4 本を通せる。`q` の形では、既存のフローが終わるまで 1 本も通せないことがある
- 請求の合計が `T` を超えているあいだ、予約の部分の取得が `floor` で拒まれることがある。`q` の形では、予約の内側のルールは `u < T` なら拒まれない。`budget` と `reserve` も、請求の合計が `T` を超えているあいだだけ起きる
- 統合、名前の変更、`Retiring` の UDP の listener の再開の後は、`q` の形と同じく、旧い接続をそれを運ぶ listener の今のルールで数える。分割の後は、分割元の登録が続くあいだ、分割先の listener の既存のフローを最低分の判定では分割元で数える点が `q` の形と違う。ルール 1 本の上限と予約の部分の入口は listener が運ぶ数で見るので、分割先は `q` の形と同じく既存のフローで抑えられるが、前述の「保証しないこと」のとおり、分割元に残ったポートは `q` の形より少なくしか通せない場合がある
- ルールの追加と統合で受け付けを拒まず、既存のフローを追い出さないことは変わらない

置き換える前の固定値 `F` の挙動との違いは、ルールが 1 本なら以前のルールごとの上限ではなく `T - 4` まで保持できること、ルールが 3 本以上なら 2 本のルールがフラッドを受けても残りのルールが最低分まで新しいフローを通せること(以前は 2 本で `T` を使い切れるので、3 本目は 1 つも通せない)、`T` が既定より小さくルールが 2 本以上の構成ではルール 1 本の上限が下がり、代わりにルール間の隔離を持つこと(`T` が `F` 以下なら、以前はルール間の隔離を持たない)である。

最低分と予備には費用がある。フローを持たないルールの最低分と予備も空きから除くので、他のルールが使っていなくても、1 本のルールが持てる数は前述の値で止まり、ルールが 1 本でも予算 `T` のすべては使えない。フローを持たないルールの最低分を使わせるには、そのルールがフローを持ち始めたときに他のルールのフローを追い出す必要があり、7a.5 節が禁じている。7a.8 節の完了条件のうち「1 本のルールなら空いている予算をほぼ使い切れ」は、ルールが 1 本(`N = 1`)の構成を指す。

#### 拒否の報告

Resource Guard の拒否は、Admission Policy の drop の種類(`deny`、`allow`、`per_source`、`src_flow`、`new_flow`、`packet`)に数えない。SQLite に累積する drop カウンタにも、admin API の `drops` にも、7a.9 節の fixture にも含めない。drop カウンタは利用者が設定した通信方針による拒否を表し、Resource Guard の拒否は wgft 自身の資源の都合による拒否なので、混ぜると利用者が方針の効き方を読み違えるためである。

UDP の受信の会計の拒否(7 節)は、後述の `resource.Pool` の拒否の数にも含めない。会計は Device ごとに拒否をメモリに数え、ログに 1 分に 1 回までの 1 行で出すだけである。

`resource.Pool` は、ルールごと、理由(`budget`、`rule_cap`、`reserve`、`floor`、`spare`)ごとの拒否の数をメモリに持つ。SQLite には保存しない。資源の逼迫は今の状態を示す情報であり、再起動をまたいで累積しても意味を持たないためである。累計の起点は、その `Pool` を作った時点である。`vpsd` は起動時に 1 つ作って使い続けるので、起点はプロセスの起動と一致する。エージェントは `Pool` をトンネルの中継の一部として作るので、トンネルを立て直すたびに起点が動く(10.2c 節)。

ログは、今と同じく listener ごとに 1 分に 1 回までとし、文言で理由を分ける。例は次のとおりである。

```
udp/2456: flow budget full: 8192 of 8192 in use in this process; dropping new flows
udp/2456: rule r1 holds 4096 flows and the rest of the budget is reserved for 1 other rule; dropping new flows
```

ルールが 2 本か 3 本の構成でフラッドを受けたルールは、他のルールの最低分と予備を残して `C` の手前で止まり、その拒否の理由は `spare` なので、2 行目ではなく `spare` の行になる。`spare`、`floor`、`reserve` の文言は、空きの数、他の登録の満たされていない最低分と下限の合計と登録の数、予備の数から組み立て、空きをどのルールのために残しているかを示す。他の登録の最低分が満たされていれば、その部分を文言に含めない。文言が示すそのルールのフローの数は、その判定に使った数である。`rule_cap` では listener が運ぶ数 `c_g`(改訂の前と同じ意味)を、`floor`、`spare`、`reserve` では `x_g` を示す。英語の出力の約束(括弧の中で説明を続けない)に従う。例は次のとおりである。

```
udp/2456: rule r1 holds 4094 flows, at or above its minimum of 2047, and the free part of the budget, 2051 of 8192, is held for the unfilled minimums of 1 other rule, 2047 flows, and 4 spare flows for a rule added later; dropping new flows
udp/2456: rule r1 holds 8188 flows and the free part of the budget, 4 of 8192, is kept spare for a rule added later; dropping new flows
udp/2456: rule r1 holds 300 flows, below its minimum of 4094, and the free part of the budget, 8 of 8192, is held for the first flows of 1 other rule and 4 spare flows for a rule added later; dropping new flows
```

admin API には、既存のフィールドを変えずに次の 2 つを加える。`GET /api/v1/rules` と `POST /api/v1/rules/batch` の応答に、プロトコルごとの `in_use` と `limit` を持つ `flow_budget` と、ルール ID から理由ごとの拒否の数への表 `resource_refusals` を加える。Web UI の表示は Phase 6 では変えない。`rule ls --json` は応答をそのまま出力するので、同じキーが増える。kernel モードの server が数えるのは `Relay` のルールの TCP だけであり、`Transparent` のフローは conntrack が持つので、これらのフィールドには現れない。

#### メモリのソフト上限との関係

メモリのソフト上限は、`resource.Limits` の `MemoryLimit` だけから導く。式(`32 MiB + 12 KiB × UDPTotal + 44 KiB × TCPTotal`)、`GOMEMLIMIT` を優先する規則、起動ログと `server check` の `memory soft limit:` の行は変えない。隔離予約と、それを改める最低分と予備は予算 `T` の内側での配分なので、保持するフローの数の合計の最大もメモリのソフト上限も変わらない。ルールが 1 本の構成では、1 本のルールへのフラッドで予算 `T` のすべてが埋まりうる。ラボでは、既定の上限を全部埋めてフラッドを重ねたときの RSS の最大は約 210 MiB だった(改訂の記録 2026-09-18)。この値はその負荷での測定であり、プロセスのメモリの上界ではない(7 節)。

kernel モードの server は Go で UDP のフローを持たないが、ソフト上限の式は UDP の項を含めたままにする。ソフト上限は GC の回収の目安であって、メモリを確保する値ではないため、実際より大きくても害が無い。式をモードで変えると、同じ設定で起動ログの値がモードによって変わる。

Resource Guard は、ヒープの量を見て新しいフローを拒む判定を持たない。フロー数の予算はフローの数を抑え、ソフト上限は GC の目標である。Phase 6 はこの役割を変えない。どちらもプロセスのメモリの量を抑える上限ではない(7 節)。IPv4 の断片の再組み立ては gVisor に渡さず、TUN の入口の固定の大きさの表で行い(7 節)、UDP の endpoint の受信のキューは TUN の入口の会計の予算で数え(7 節)、拒んだ TCP の TIME_WAIT は RST で閉じて残さない(7a.5 節)。宛先からの応答を読むバッファは、プロセス全体の枠で数える(7 節)。Phase 6 はこれらに新しい上限を加えない。応答のバッファの枠はソフト上限の式に入れない。枠の上限は式の値に比べて小さく、ソフト上限は GC の目標であって上限ではないためである。netstack の出力のキューと wireguard-go の送信のキューに滞留するパケットの上限は、1 回の `Read` の件数を 1 に保つことで決まり、wireguard-go の受信のキューに滞留するパケットの上限は、バインドの 1 回の受信の件数を 1 に保つことで決まる(7 節)。netstack の握手途中の TCP の数に上限が効いているかは未確認である。

#### kernel 側の保護

kernel 側の Resource Guard は、観測して提示するだけで、値を変えず、強制も加えない。wgft の方針は、環境を見て挙動を推測せず、明示された値に従うか、提示して止まることである。conntrack の表はホスト全体の資源であり、wgft 以外の通信も同じ表を使うので、wgft が上限を決める立場にない。

kernel 側で Resource Guard が行うことは次のとおりである。

- conntrack の表の上限と件数の読み取り:`internal/platform/linux` の `ReadConntrackUsage` が `nf_conntrack_max` と `nf_conntrack_count` を読む。`server check` は今のとおり件数と上限を表示し、上限が 65536 未満なら、上げる sysctl と `new_flow_rate` の設定を提示する。実際の VPS(メモリ 462 MB)では、上限は 4096 で、この提示が出た。6.1 節が例に挙げた 16384 より小さい上限の VPS もある
- 起動時の Finding:以前は `server check` を実行したときにしか出なかった。Phase 6 のこの段で、同じ判定を `ip_forward` と同じ起動時のログにも出すようにした。`server check` を実行しない運用者にも気付けるようにするためである。管理用 API と Web UI への表示は、他の nftables の Finding(`ip_forward` を含む)と同じくこの段の対象外であり、今もログだけである
- 提示する値:以前の提示は `nf_conntrack_max=262144` だった。所有者の決定により、`server check` と起動時の Finding のどちらも、メモリの数値(MiB、エントリ 1 件のバイト数、bucket 数のいずれも)を出さない。提示する値は 65536 に改めた。判定の閾値も同じ 65536 である

  観測:Debian 12 / Linux 6.1 のラボで約 6 万件を埋めて測ったところ、DNAT を伴う conntrack のエントリは 1 件あたり約 384 バイト(本体 256 バイトと NAT の拡張 128 バイト)、NAT を伴わないエントリは約 256 バイトだった。ほかにハッシュ表の費用がある。これは kernel の版、設定、エントリの種類で変わるので、wgft の診断の出力にも推奨値の計算にも使わない。65536 はメモリの量から出した値ではなく、wgft が運用上の最低の推奨値として定める
- set の大きさ:`meter_N` と `flows_udp`/`flows_tcp` の大きさ(65535)は、Phase 5 から IR の定数である(7a.9 節)。埋まったときの劣化(送信元ごとの制限が外れ、集約上限に委ねる)は 6.1 節のとおりで、Phase 6 は変えない。set の要素数は監視しない

kernel 側で Resource Guard が行わないことは次のとおりである。

- `nf_conntrack_max` と `nf_conntrack_buckets` を書き換えない(6.1 節)
- ホストのメモリの量から提示する値を計算しない。提示は判定の閾値(65536)という固定の値だけから作り、メモリの数値(MiB、エントリの費用、bucket 数)は出さない
- wgft のポート全体の同時フロー数を `ct count` で抑える行を加えない。この上限は利用者の設定項目にない新しい通信方針になり、`flows_udp`/`flows_tcp` と同じくテーブルの差し替えで数がリセットされる。`new_flow_rate` と conntrack の表の上限という既存の手段で足りる
- ルールごとの隔離を持たない(7a.5 節)

kernel モードの `Relay` のルールの接続は、`vpsd` のソケットが終端するので、Go の側の Resource Guard(`proxyrelay` の TCP のプール)で数える。同じ接続は、公開側と wg0 側で conntrack のエントリを 2 件使う(ラボで確認した)。`Transparent` なルールの接続は、DNAT だけを経由するので 1 件のエントリを使う(同じラボで確認した)。

#### agent への適用

agent の userspace dataplane は server と同じ `relay.Manager` を使うので、共有プール、ルール 1 本の上限、最低分と予備、拒否の数とログ、メモリのソフト上限をそのまま使う。agent の `A` は、全体状態のうちその agent のルールで、listener を開けているものである。最低分と予備の計算は agent が自分の `resource.Limits` と自分のルールの集合だけから行うので、全体状態にも join protocol にも何も加えない。agent には `AdmissionLimits` が無い。agent から見た送信元は常に `10.200.0.1` であり(7 節)、Admission Policy は server だけで評価するためである。

agent の拒否の数は、Phase 6 では agent のログにだけ出す。ハートビートには加えない。ハートビートに加えるには wire protocol に加算的なフィールドと capability を加える必要があり(7a.6 節)、版と capability の規則の検証を伴う変更は Phase 6 の範囲より大きいためである。

agent の kernel dataplane(Phase 7)では、kernel 側の保護を server と同じく `internal/platform/linux` の読み取りと提示で行い、ルールごとの隔離は持たない。

#### Phase 6 の移行の手順

各段は、7a.8 節の共通の完了条件を満たしてから次へ進む。最初の 2 段は、並行した取得の超過を除いて挙動を変えない。

1. 型を分ける。`internal/flowcap` を `internal/resource` に改め、`AdmissionLimits` を `internal/policy` へ、`LogGate` を `internal/lograte` へ移す。`cmd/wgft`、`planner.Input`、`policy.Build`、userspace backend、`proxyrelay`、agent の `Options` を新しい型に書き換える。完了条件は、`MemoryLimit` の値(既定で 216 MiB、2048 と 1024 で 100 MiB)と、設定層の検査とエラーの文言が変わらないことである
2. `resource.Pool` を置き、ルールごとの上限を今の値のまま `Pool` で判定する。`relay.Manager` の `ruleFlows` による判定と、`proxyrelay` の listener ごとの `ConnsMax` の判定を置き換える。今の `relay.Manager` は、ルールごとの数を読んでからプロセス全体の枠を取るまでを 1 つの排他の中で行わないので、範囲のルールの複数の listener が同時に受け付けると、ルールごとの上限をわずかに超えうる。`Pool` は両方を 1 つの排他の中で判定するので、この超過が無くなる。拒否の理由ごとの数とログの文言もこの段で加える。完了条件は、同じ入力の列に対して、今の実装と通す・拒むが一致する単体テストを通すことである
3. `proxyrelay` が accept の後に拒む接続(Admission Policy の拒否と Resource Guard の拒否)を、`SetLinger(0)` による RST で閉じる。今は通常の `Close` で閉じており、6.3 節の「実ソケットでも拒否は `SetLinger(0)` の RST で閉じ」という記述と食い違っている。`relay` の TCP の拒否(`abortRefused`)と同じ閉じ方にそろえる
4. 判定を隔離予約の式(`C = ceil(T/2)`)に切り替え、コードから従来の下限の定数(`UDPPerRuleFloor`、`TCPPerRuleFloor`)を削除する(完了)。7 節の同時フロー数の上限の表と説明、6.2 節と 6.3 節の関連する記述、`lab/lifecycle.sh` の check 5 と `lab/connlimit.sh` の説明を同じコミットで改める。7 節の「ルールごとの上限はプロセス全体の上限の半分になるので、この目安でも 1024 UDP・512 TCP を 1 ルールが保持できる」は、置き換える前の実装(2048 と 1024)と食い違っていたので、「ルールが 2 本以上あると、ルール 1 本の上限はプロセス全体の上限の半分(切り上げ)になるので、この目安では 1 ルールが 1024 UDP・512 TCP を保持できる。ルールが 1 本なら、プロセス全体の上限のすべてを保持できる」の旨に書き改めた。7 節の表と説明からも、下限(4096、1024)の記述を除いた
5. `nf_conntrack_max` が 65536 未満のときの判定を、`ip_forward` と同じ起動時のログにも出す。`server check` と起動時の Finding の提示は、メモリの数値を出さず、65536 を wgft の運用上の推奨値として示す形に改めた。admin API に `flow_budget`(プロトコルごとの `in_use` と `limit`)と `resource_refusals`(ルール ID から理由ごとの拒否の数への表)を加える。`GET /api/v1/rules` と `POST /api/v1/rules/batch` は、どちらも同じ応答の型を返すので、Backend が Resource Guard の状態を持つときだけ両方に加わる(`ApplyStatusBackend` と同じ、報告が無ければ何も足さない別の interface)。kernel モードの server は UDP を Go の `resource.Pool` で数えないので `flow_budget` に "udp" は現れず、Go が判定しないルール(kernel モードの `Transparent`)は `resource_refusals` にも現れない。`rule ls` は REFUSED 列(理由を問わない合計)と、`generation` の行に続く flow budget の要約行(`flow budget: tcp 3/2048` の形)を出す。`rule ls --json` は応答をそのまま出すので同じキーが増える。Web UI は 7a.10 節のとおり変えない(完了)
6. 隔離予約の形を、登録ごとの最低分と予備の形に改める(前述の「共有プール、最低分と予備」と「退役した登録のフローの帰属」、2026-09-29 と 2026-09-30 の所有者の決定)。`resource.Pool` はフローを受け付けたときのルールの登録で数え、退役した登録のフローを帰属の規則で移し、登録ごとに listener が運ぶ数を保ち、受け付けていない listener からの取得を拒み、listener と登録の組を指す取得の手形を返す。拒否の理由に `floor` と `spare` を加え、拒否のログの文言を改める。`relay` の TCP の worker は今の順序(取得の後、listener ごとの排他の下で停止の印を確かめ、止まっていれば手形を返して接続を拒む)を保つ。止まっていたときと、受け付けていない listener からの取得を拒んだときは、どちらも RST で終える。前者はまだデータをやり取りしていない接続なので、ホストのソケットでも RST にする(7a.5 節)。`relay` の UDP の listener は、受け付けを止めるときも再開するときも今の順序(止めるときは listener の印を先に下ろし、再開するときは印を先に立ててから `Pool` の受け付けを始める)を保つ。再開と同時に所属ルールが変わるときは、受け付けを再開する前に付け替え、旧いセッションを宣言のルールの登録へ移す。印と `Pool` の状態が食い違うあいだの取得は `Pool` が受け付けていないとして拒むので、帳簿は崩れない。セッションを表に入れる前に listener が閉じていないことを確かめることも、今の順序を保つ。`proxyrelay` は、listener の排他の下で停止の印を確かめてから取得する今の順序を保つ。7 節の表と説明、`docs/setup.md` と `docs/setup.ja.md` のルールごとの上限の説明、`lab/lifecycle.sh` の check 5 から 5e の説明と期待値と拒否の理由、`agent doctor` の budget の表示と `refusals` の説明を同じ変更で改め、拒否の理由と分割元に残ったポートを確かめる check 5f と 5g を加える。admin API には、拒否の理由のキーのほかに何も加えない(完了)

#### 利用者から見て変わらないものと変わるもの

CLI のコマンドとフラグ、`WGFT_MAX_UDP_FLOWS`、`WGFT_MAX_TCP_FLOWS`、`WGFT_MAX_UDP_FLOWS_PER_SOURCE`、`WGFT_MAX_TCP_FLOWS_PER_SOURCE` の意味と既定値と範囲、`GOMEMLIMIT` の扱い、メモリのソフト上限の値、機械向けの CLI 出力、ルールの書き出しと読み込みの形式、admin API v1 の既存のフィールド、join string と agent/server の通信、drop の種類とカウンタは変わらない。`T` が既定以上の構成でルールが 2 本なら、ルールごとに保持できる数も変わらない(`T` が奇数のときだけ 1 増える)。

次の挙動が変わる。

- ルールが 1 本の構成では、そのルールが予算 `T` のすべてを保持できる(既定で UDP 8192、TCP 2048。以前は 4096、1024)
- ルールが 3 本以上の構成では、2 本以上のルールがフラッドを受けても、残りのルールが予約の分だけ新しいフローを通せる
- `T` が既定より小さい構成でルールが 2 本以上なら、ルール 1 本の上限が `ceil(T/2)` に下がる。対象は、`T` が従来の固定値以下の構成(UDP 2048、TCP 1024 など。以前の上限は `T`)と、従来の固定値と既定のあいだの構成(UDP 4097 から 8191、TCP 1025 から 2047。以前の上限は従来の固定値)である。代わりに、1 本のルールへのフラッドの最中も、他のルールが新しいフローを通せる
- 上限で拒んだことのログの文言が、理由(`budget`、`rule_cap`、`reserve`)で分かれる
- `proxyrelay` が拒む接続は、クライアントから RST として見える
- admin API の応答に `flow_budget` と `resource_refusals` が加わり、`rule ls --json` の出力にも同じキーが増える
- `rule ls` の人が読む出力に、ルールごとの Resource Guard の拒否の総数を示す `REFUSED` の列と、`generation` の行の後の `flow budget: tcp 3/2048` の形の行が加わる。kernel モードの server は UDP を数えないので、`udp` は出ない
- `nf_conntrack_max` が 65536 未満なら、起動時のログにも警告が出る(管理用 API と Web UI は、他の nftables の Finding と同じく対象外)。`server check` が提示する値は 262144 から 65536 に変わり、メモリの数値 は出さない

手順 6 では、次の挙動が変わる。

- ルールが 1 本の構成では、保持できるのが予算 `T` から予備の 4 を除いた値になる
- ルールが 2 本以上の構成では、各ルールの最低分と 1 本の上限が隔離予約の形より高々 2 小さくなる。ルールが 2 本か 3 本の構成でフラッドを受けたルールの拒否の理由は、`rule_cap` ではなく `spare` になる
- 新しいルールは、加わる時点で予備の分の空きがあれば、予算が埋まっていても下限の 4 本をすぐ通せる
- 請求の合計が `T` を超えているあいだ、自分の最低分に届いていないルールが `floor` で拒まれることがある
- 分割で所属ルールが変わった listener の既存のフローは、分割元の登録が続くあいだ、最低分の判定では移動先のルールで数えない。分割元の登録が退役すると、移動先のルールで数える。ルール 1 本の上限は今までどおり listener が運ぶ数で判定する。統合、名前の変更、UDP の再開の後は、今までどおり旧い接続を今のルールで数える
- フラッドを受けたポートを分割で切り出すと、分割元が続くあいだ、分割元に残ったポートが新しいフローを通せないことがある(前述の「保証しないこと」)
- 1 回の適用の中の操作の順と、分割と統合の多数回の往復によって、無関係のルールが最低分を下回ることがある(前述の「保証しないこと」)
- 停止と重なって拒む `relay` の TCP の接続は、ホストのソケットでも RST で終わる
- 拒否の理由に `floor` と `spare` が加わる。`resource_refusals` の理由のキーは開いた集合なので(7a.11 節)、加算である。定常の状態(請求の合計が `T` 以下で、分割元が続いていない)で出る理由は `spare` と、前述の一部の構成の `rule_cap` だけになる
- 拒否のログの文言が、最低分、満たされていない最低分、予備を示す形になる。admin API のフィールドは増えない

#### ホストで確かめることとラボで確かめること

`resource.Pool` は OS に触れない純粋な Go の型なので、式の性質はホストの単体テスト(`go test ./internal/resource/...`)で確かめ、CI でも走らせる。対象は次のとおりである。

- `N = 1` で `T - f` まで通すこと。`TotalMin` から `TotalMax` までのすべての `T` と、2 から数百までの `N` で、1 本のルールに受け付けを続けたときの最大が `min(C, max(m, T - P - (N - 1) × m))` になること(他のルールがフローを持たないとき)
- `TotalMin` から `TotalMax` までのすべての `T` で `C = ceil(T/2)` になり、既定以上の `T` で `C` が今のルールごとの上限を下回らないこと
- `TotalMin` から `TotalMax` までのすべての `T` で `f ≤ C` と `3f ≤ T` が成り立ち、`q ≥ f` となるすべての `N` で `N × m + P ≤ T` が成り立つこと
- 請求の合計が `T` 以下の時点で、どの登録も、他のルールのフラッドの最中も最低分まで通せること。空きが満たされていない下限の合計以上の時点で、下限に届かない登録が下限まで通せること。`N` が 1 から 2 に変わるときも含めて、加わる時点で `u + S_f + P ≤ T` なら新しい登録が下限まで通せること
- `floor` の拒否が請求の合計が `T` を超えているときだけ起きること。請求の合計が `T` を超えているあいだ、共有分の取得が拒まれること。`A` の更新と統合で既存のフローを追い出さないこと
- 分割で listener の所属ルールが変わっても、分割元の登録が続くあいだ、既存のフローが分割元で数えられ続けること。登録ごとに保った listener が運ぶ数が、listener のフロー数の和と毎手で一致すること。分割先の listener が `C` 以上を運ぶあいだ分割先が `rule_cap` で拒まれ、`m` 以上を運ぶあいだ予約の部分を使わないこと。条件 2 を下限の部分より後に置くとテストが落ちること。同じ ID の削除と再登録が別の登録になること。受け付けていない listener からの取得を拒み、拒否の数に入れないこと。手形の 2 度目の返却が何も変えないこと
- 帰属の規則:統合、名前の変更、`Retiring` の listener の再開、分割の後の分割元の削除、fail-closed、閉じ直しの後に、受け付けている listener が運ぶフローが退役した登録に残らないこと。受け付けていない listener が運ぶフローを移さないこと。生きている登録どうしで移さないこと。移しが `u` を変えず請求の合計を増やさないこと。これらを無作為の操作の列の毎手で確かめ、移しの発火を 1 つずつ外すとテストが落ちること
- `T - u ≥ S_f + P` が、いったん成り立った後、新しい登録のほかの操作で崩れないこと。`budget`、`reserve`、`floor` が請求の合計が `T` を超えているときだけ起きること
- 拒否の理由と数、並行した取得と返却(`-race`)
- 手順 2 で、今の実装と通す・拒むが一致すること、手順 3 で `proxyrelay` の拒否が RST になること(ループバックのソケットで確かめられる)
