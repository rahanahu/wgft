# wgft 設計文書

VPS で受けた TCP/UDP を WireGuard 経由で自宅のサービスへ届けるツール。
名前は WireGuard Forwarding Tool の略。

## 背景と全体像

自宅のサービス(ゲームサーバ、Web サービス)を、固定 IP を持つ VPS 経由でインターネットに公開したい。
自宅側は NAT 配下でポート開放を避けたいので、自宅から VPS へ WireGuard トンネルを張り、VPS に届いたパケットをトンネル経由で自宅へ転送する。
この構成は Pangolin から着想を得た。Pangolin を使う中で VPS を入口にして自宅サービスを公開する構成の便利さを知った一方、ゲームサーバなどの raw TCP/UDP 転送だけが目的なら、より直接的で小さな構成が欲しくなった。
また、日本の IPv4 over IPv6 接続の一部では任意の受信 IPv4 ポートを使えない場合があり、VPS を入口にする構成はその制約を避ける用途にも合う。
そこで WireGuard と nftables を直接組み合わせ、その手作業をツールに置き換える。

置き換え後の全体像は次のとおりである。

- DNS:ワイルドカードレコードで VPS の IP を指す
- VPS:本ツールが、指定したポートを自宅へ素通しする。接続元 IP による制限もここで行う
- 自宅:本ツールのエージェントがトンネルを張り、届いたパケットを LAN 内のサービスへ中継する。HTTPS は自宅側のリバースプロキシ(Caddy)が TLS 終端とホスト名の振り分けを担う

本ツールは L4 の転送だけを担当し、TLS、証明書、認証は扱わない。

## 1. 目的と範囲

VPS から自宅へのポート転送に必要な nftables と WireGuard の手作業設定をなくすことが目的である。

やること:

- 任意の TCP/UDP ポートを VPS から自宅の任意ホストへ転送する
- 自宅側はエージェントを置くだけで繋がる(自宅側のポート開放は不要)
- 転送ルールごとに、接続元 IP による許可と拒否、レート制限を VPS 側で行う
- 転送ルールの追加削除を Web UI と CLI から行う
- 既存の nftables ルールを壊さない

やらないこと:

- TLS 終端、証明書取得、SNI やパスによる振り分け(自宅側の Caddy が担う)
- 認証ゲート、共有リンク
- L7 の解釈全般
- 接続元 IP を自宅側のサービスへ伝えること(TCP の PROXY protocol を除く)

## 2. 全体構成

| 部品 | 動作場所 | 役割 |
|---|---|---|
| `vpsd` | VPS | wg0 の管理、nftables の適用、conntrack の操作、API と Web UI、状態の保存 |
| `agent` | 自宅 | `vpsd` への登録、wg トンネルの維持、届いたパケットの LAN 内サービスへの転送(ユーザー空間モードは自分で中継し、カーネルモードはカーネルの DNAT を設定する) |
| `proto` | 両方 | 登録と全体状態配信の JSON スキーマを定める共有ライブラリ。実行されるプロセスではない |

実装言語は Go。
`vpsd` と `agent` は同一バイナリで、サブコマンド `server` と `agent` で切り替える(起動はそれぞれ `wgft server run`、`wgft agent run`)。`vpsd` は本書と内部での呼び名で、利用者に見えるコマンド名は `server` である。
`vpsd` は wgctrl-go で WireGuard を、google/nftables で nftables を、ti-mo/conntrack で conntrack を直接操作し、Web UI はバイナリに埋め込む。
`agent` は 2 つのモードを持つ。既定のユーザー空間モードは、wireguard-go と gVisor の netstack でトンネルをユーザー空間に持ち、カーネルの設定を変更しない(7 節)。Linux のエージェントだけが明示して選べるカーネルモードは、カーネルの WireGuard インタフェースと nftables の DNAT で転送し、`vpsd` と同じく wgctrl-go、google/nftables、ti-mo/conntrack でカーネルを直接操作する(7b 節)。

## 3. 用語

- **`vpsd`**:VPS 側で動くデーモン。`wgft server run` で起動するプロセスを本書と内部ではこう呼び、利用者に見える名前(コマンド、設定ファイル、unit)は `server` である
- **エージェント**:自宅側で動く `agent` の 1 インスタンス。1 拠点に 1 つ置く想定だが、複数登録できる
- **ルール**:「VPS の `<proto>/<port>` を、エージェント `<name>` 経由で `<host>:<port>` へ届ける」という 1 行の宣言
- **接続元制限**:ルールに付ける、接続元 IP の許可リスト、拒否リスト、レート制限
- **全体状態**:`vpsd` がエージェントに配る、そのエージェントに関わる wg 設定とルール集合の全体
- **世代**:全体状態の版を表す単調増加の整数。エージェントに配る内容が変わったときだけ `vpsd` が増やし、SQLite に保存する。管理用 API の 1 リクエストで上がる世代は最大 1 つ
- **リスナー**:エージェントが netstack 上に開く待ち受け。単一ポートごとに 1 つで、`(proto, port)` で同一性を取る。状態として実効宛先(`host:port`)と所属ルール ID を持つ
- **状態ファイル**:エージェントが恒久トークン、wg の秘密鍵、証明書のハッシュ、最後の全体状態を保存するファイル(`agent.json`。9 節)。本書と内部では状態ファイルと呼び、利用者に見える文言(UI、CLI、README)では**認証情報**(英語は credentials)と呼ぶ。`vpsd` 側の SQLite は別物で、利用者向けにはサーバのデータベースと呼ぶ
- **stream**:エージェントが `vpsd` に張る常時接続(WebSocket)。全体状態の配信、公開鍵の宣言、ハートビートに使う(5.2 節)
- **エージェント用 API** と **管理用 API**:`vpsd` が持つ 2 つの HTTP リスナー。前者は公開でエージェントの登録と stream だけを受け、後者は Unix ソケット(既定)か Tailscale のアドレスで Web UI と CLI が使う(5 節、11 節)
- **カーネルモード** と **プロキシモード**:VPS 側の転送方式。前者は nftables の DNAT でカーネルが転送し、後者は `vpsd` 自身が TCP を受けて中継する(6 節)。ルールごとに `vps_mode` で選ぶ。内部の実装ではこの選択を `Forwarding` という型(`Transparent`/`Relay`)で表し、`proxy_protocol` は別の型 `SourceMetadata`(`None`/`ProxyV2`)で表す。どちらも server・agent 全体の転送方式(`DataplaneMode`。11a 節の `WGFT_MODE`)とは区別する(7a 節)
- **疎通確認**:管理者が UI から、`vpsd` 経由で自宅の `target` に届くかを試す操作(10.1 節)
- **エージェントの無効化** と **有効化**:前者は、エージェントの登録を残したまま、そのエージェントのルールの転送を止める操作であり、後者はそれを戻す操作である。英語は disable と enable である。無効化したエージェントの状態を「無効」と呼ぶ。エージェントの無効は、ルールごとの `enabled`(5.3 節)とは別の値であり、互いを書き換えない(5.1 節)
- **エージェントの削除**:エージェントの登録を取り消す操作。英語は revoke である。恒久トークンは使えなくなり、元に戻せない。同じ名前で使い直すには、新しい接続文字列で登録し直す(5.1 節)

## 4. ネットワーク

- `vpsd` の WireGuard インタフェースの既定名は `wgft0`(`--wg-interface` で変更可)。一般的な `wg0` を既定にすると、既に `wg0` を使っている VPS で既存の WireGuard を壊すため(9 節の所有判定と併せた対策)。本書では読みやすさのため以降も `wg0` と書くが、実際の既定名は `wgft0` を指す
- wg0 のアドレス帯は `10.200.0.0/24`。`vpsd` が `.1`、エージェントには登録時に `.2` 以降を割り当てる。stream に一度も来ないエージェントもアドレスを持ち、エージェントの削除で回収される
- VPS で外に開けるポートは次の 3 種類だけ。WireGuard の待ち受け(UDP 51820、変更可)、エージェント用 API(TCP 8443、変更可)、転送対象のポート
- 管理用 API と Web UI は Unix ソケット(既定)か Tailscale のアドレスで待ち受け、インターネットには開けない(11 節)
- wg0 の MTU は `vpsd` が決め(既定 1420)、全体状態でエージェントに渡す。エージェントは netstack の tun に同じ値を使う。ユーザー空間モードのエージェントでは TCP はエージェントの netstack で終端され、netstack が自分の MTU から MSS を広告するので、この 2 つが揃っていれば wg0 の MTU を超える TCP は生まれず、VPS 側に MSS クランプは要らない。ずれると、PMTUD の ICMP が途中で落ちる経路で大きな TCP が止まる。カーネルモードのエージェントは TCP を終端しないので、エージェントが自分の WireGuard インタフェースを通る SYN の MSS をクランプする(7b 節)
- wg0 の MTU 1420 は、外側の回線の MTU が 1500 である前提の値である。自宅回線の MTU が小さい場合(PPPoE の 1454 など)でも、WireGuard の外側の UDP は DF なしなので途中でフラグメントされて動くが、大きなパケットがすべて 2 つに割れる。回線の MTU が分かっているなら `vpsd` の MTU を下げる方が効率がよい(全体状態でエージェントにも渡る)。また、トンネル一般の挙動として、DF 付きで 1393 バイト以上のペイロードの UDP を送る client は初回だけ ICMP fragmentation needed で失敗し、経路 MTU を学習した後は通る(実験で確認)
- エージェントは `PersistentKeepalive = 25` で NAT 越しに接続を維持する。keepalive の 5 倍の間ハンドシェイクが成功しなければ、エージェントはエンドポイントの名前を引き直してピアに設定し直す。この引き直しでも戻らない故障に備えた第 2 段の回復は 7 節に定める
- VPS の conntrack の UDP タイムアウト 2 値(`nf_conntrack_udp_timeout` と `nf_conntrack_udp_timeout_stream`)は `vpsd` が起動時に読み、全体状態でエージェントに渡す
- `vpsd` は wg0 上で待ち受けをしない。エージェントへ張る接続(プロキシモードの中継、疎通確認)はすべて `vpsd` 側から外向きに開く
- IPv4 のみ対応する(IPv6 は未決事項)

## 5. 制御プレーン

制御プレーンは常にエージェントから `vpsd` への外向き HTTPS で行う。
`vpsd` からエージェントへ接続を張ることはない。

`vpsd` は 2 つのリスナーを持つ。

- **エージェント用 API**:公開。`/api/v1/agents/register` と `/api/v1/agents/stream` だけを露出する。TLS 証明書は `vpsd` が初回起動時に生成する有効期限 10 年の自己署名証明書で、秘密鍵ごと SQLite に保存する
- **管理用 API**:既定は Unix ソケット。Web UI と CLI が使う。独自の認証は持たず、接続経路(ソケットのパーミッション、SSH、Tailscale)に任せる(11 節)

エージェント用 API を wg 経由に切り替えない理由は、wg が落ちたときに制御まで落ちると復旧の手がかりが減るからである。

### 5.1 登録

人が扱うのは接続文字列 1 本だけである。
登録は初回だけ行い、目的は恒久トークンを得ることに限る。

1. 管理者が Web UI か CLI で接続文字列を発行する。中身はエンドポイント、1 回限りの登録トークン、エージェント用 API の証明書の SHA-256 で、`wgft://host:port/token#sha256:...` の形をとる。トークンにはエージェント名を紐付ける
2. エージェントは接続文字列を環境変数 `WGFT_JOIN` か引数で受け取る。名前は環境変数 `WGFT_NAME` か引数で任意に受け取る。接続先の証明書がハッシュと一致しなければ中断する
3. エージェントは登録トークンを登録 API へ送る。名前を受け取っていれば名前も送り、名前がトークンに紐付いたものと違えば `vpsd` は拒否する。名前を送らなければ、トークンに紐付いた名前で登録する。名前はトークンに紐付いているので、自宅側で同じ名前をもう一度入力させる必要はない
4. `vpsd` はエージェントを SQLite に作り、恒久トークン、割り当てアドレス、確定した名前を返す。この時点では wg ピアはまだない
5. エージェントは恒久トークンと名前を状態ファイル(9 節)に保存し、stream に接続する。wg ピアの作成と設定の受け取りは stream で行う(5.2 節)

トークンの扱いは次のとおり。

- 登録トークンと恒久トークンは 128 ビット以上の乱数。SQLite にはハッシュだけを保存し、比較は定数時間で行う
- 登録と stream 接続の試行は送信元 IP ごとにレート制限する
- 登録トークンは 1 回限り、既定の有効期限は 1 時間
- 同じ名前に対して新しい登録トークンを発行すると、その名前に対する以前の未使用トークンはすべて無効化する。有効なトークンは常に最新の 1 本だけであり、複数の接続文字列が同じ名前で有効なままにはならない
- エージェントを削除すると、その名前に対して発行済みの未使用トークンも合わせて無効化する。削除の前に発行され、まだ登録に使われていない古い接続文字列は、削除のあとは使えない

エージェントが削除され、恒久トークンが使えなくなった場合の復帰経路は次のとおり。
stream の認証が拒否(401)され、かつ `WGFT_JOIN` が与えられていれば、エージェントは初回登録をやり直す。
状態ファイルは初回登録が成功した時点で置き換え、失敗したら既存のファイルを残したまま止まる。
`WGFT_JOIN` は compose ファイルに残されたままになりやすく、管理者の誤操作や SQLite の復元で 401 が返ったとき、期限切れのトークンで登録に失敗して鍵まで失うことを防ぐためである。
状態ファイルには使用済みの登録トークンのハッシュを残し、`WGFT_JOIN` の値がそれと同じなら登録を試みずにエラーで止まる。
一時的な失敗(5xx、接続不能)は認証拒否と区別し、復帰経路に入らず再接続を続ける。
`WGFT_JOIN` がなければエラーを出して止まる。
削除したエージェントの名前は新しい接続文字列で再利用でき、割り当てアドレスは回収される。

サーバ証明書が変わったエージェントの復帰経路は次のとおり。
証明書が変わるのは `teardown --purge` のあとに `vpsd` を立て直したときで、エージェントの状態ファイルにあるピンと一致しなくなる。
エージェントはピンの不一致をほかの接続失敗と区別する。
`WGFT_JOIN` が与えられ、使用済みではなく、そのピンが状態ファイルのピンと違うときだけ、その接続文字列で初回登録をやり直す。
新しいピンを信頼する根拠は管理者が与えた接続文字列であり、登録トークンはそのピンに一致するサーバにしか送られないので、初回登録と同じ安全性になる。
状態ファイルの扱いは 401 の復帰経路と同じで、登録が成功した時点で置き換え、失敗したら既存のファイルを残す。
条件を満たす `WGFT_JOIN` がなければ、停止せずに再接続を続け、新しい接続文字列が要ることをログで案内する。ピンの不一致は経路上の第三者が TLS を終端しているときにも起き、その場合は待てば元のサーバに戻るためである。

v1 は、稼働中の証明書の入れ替えを stream の中では行わない。証明書の秘密鍵が漏れた場合の対処は、`wgft server teardown --purge` と全エージェントの再登録だけである。再登録で配る新しい接続文字列が新しい証明書のピンを運ぶので、上記の復帰経路がそのまま使える。入れ替えの手段を持たない判断の理由は、全体状態に「次の証明書ハッシュ」を載せる方式(13 節)が、ピンを追記する経路と、古いピンを捨てる時期の判断を新たに必要とし、v1 の想定する台数(自宅の数台)ではその費用に見合わないためである。証明書の秘密鍵は、サーバ鍵とエージェントのトークンと同じくサーバのデータベースにあるので、守る範囲はデータベースの権限(9 節)と同じになる。

接続文字列が漏れた場合、先に登録した側だけがエージェントになれ、本物は登録失敗で気付ける。
本物の起動後に漏れても、トークンは使用済みか期限切れなので使えない。
漏れた登録で得られるのは、エージェントが削除されるまで有効な恒久トークン 1 つである。
それで得られる wg0 上の 1 ピアは、ピア同士の通信も、wg0 から VPS 自身への新規接続も、wg0 から VPS の他のインタフェースへの転送も 6.1 節で遮断するため、到達できる先がない。
第三者の接続は、5.2 節の IP の食い違いの警告と、10.1 節の両 IP の表示で管理者に見える。

#### エージェントの無効化と有効化

エージェントの無効化は、登録を残したまま、そのエージェントのルールの転送を一時的に止める操作である(2026-09-24、所有者の決定)。有効化は無効化を戻す。操作は `wgft agent disable <name>` と `wgft agent enable <name>`、管理用 API の `POST /api/v1/agents/{name}/disable` と `POST /api/v1/agents/{name}/enable` である(7a.11 節)。この 2 つのコマンドは `--json` を持たない。無効かどうかは `agent ls --json` の `disabled` で読む。

無効化が止めるものは次のとおり。

- VPS 側の転送:`vpsd` は、無効なエージェントのルールを dataplane に渡す宣言から外す。外れたルールは、ルール自身の無効化と同じ経路で止まる。DNAT と中継の待ち受けが消え、成立済みのフローも切れる(6.1・6.2・7a.3 節)。管理用 API の `rule_states` では、外れたルールの `apply_state` は `not_active` になり、`reason` はエージェントが無効であることを示す。ルール自身も無効なら、`reason` はルール自身の無効を示す。直す操作が `rule enable` と `agent enable` で違うためである
- エージェント側の転送:`vpsd` は、無効なエージェントに配る全体状態で、そのエージェントのルールをすべて `enabled:false` として載せる。エージェントは既存の `enabled` の扱いでリスナーとセッションを閉じる。無効化を知らない旧い版のエージェントも、同じ扱いで止まる。無効化の守りは、VPS 側の宣言からの除外と、この `enabled:false` の 2 つだけに頼る。全体状態には、エージェント自身の診断のために無効であることを示すフィールドを加算する。このフィールドは守りに使わない

無効化が変えないものは次のとおり。

- ルールの保存値:サーバのデータベースに保存したルールの `enabled` を書き換えない。`enabled:false` は配るときの写しだけにある。有効化すると、各ルールは自分の `enabled` のとおりに戻る。例えばルール A と C が有効で B が無効のエージェントを無効化すると、3 本とも転送しなくなる。有効化すると A と C は転送を再開し、B は無効のまま残る
- 登録と接続:登録、恒久トークン、WireGuard の鍵とピア、トンネルのアドレスは残る。エージェントは無効の間も stream に接続でき、ハートビートとトンネルの状態も見える。ピアが残っていても、6.1 節の forward は DNAT 済みでない wg0 行きのフローを落とすので、外からエージェントへ届く経路は無い
- 無効の間のルールの操作:ルールの追加、変更、削除と、ルールごとの有効と無効の切り替えは受け付けて保存する。保存したルールは有効化の時点から転送する

世代は、無効化と有効化のどちらでも 1 つ進める。配る内容、つまり `enabled` の写しと、上の無効を示すフィールドが変わるためである(3 節の世代の定義)。状態が変わらない操作、つまり既に無効なエージェントの無効化と既に有効なエージェントの有効化は、世代を進めない。世代はルール集合全体に 1 つなので(5.2 節)、進めた世代は接続中の全エージェントへ配る。世代を進めるかどうかは、保存値ではなく配る写しで比べる。無効なエージェントのルールの `enabled` だけを切り替える操作は、配る写しが `enabled:false` のまま変わらないので、世代を進めない。無効なエージェントへのルールの追加、削除、`target` などの変更は、配る写しを変えるので世代を進める。

データの持ち方:無効であることは、サーバのデータベースのエージェントの行の列 `disabled_at` の 1 つだけで持つ。NULL は有効を、値は無効にした時刻を表す。既に無効なエージェントの無効化は、最初に無効にした時刻を書き換えない。ルールの行には何も持たない。この列を加えるためにスキーマの版を 1 つ上げる。版を上げない置き方(既存の表に値を置くなど)では、旧い版の server に戻したとき、旧い版が無効の印を読み飛ばし、無効のエージェントの転送を再開してしまう(fail-open)。版を上げれば、旧い版の server はデータベースを新しすぎるとして起動を拒む(9・11b 節)。無効は、server の再起動、エージェントの再起動と再接続をまたいで保たれる。

操作の順序と失敗の扱い:

- 無効化の順序:サーバのデータベースへの保存を確定し、無効化だけを最後に公開に成功した全体状態へ重ねて配信を開始し、その後に dataplane へ公開する。実際の送信は非同期であり、dataplane の公開より先に完了する保証はない。配信は公開の成否を待たず、止める向きの内容は公開より先に届いても安全側である。ルールのバッチ(5.4 節)は公開に失敗すると配らないので、無効化だけが配信の点で例外になる。保存は済んだがまだ公開していない他のエージェントの有効化やルール変更は、この配信に含めない
- 有効化の書き込みの時の検査:有効化は、そのエージェントの有効なルールに、ルールのバッチの upsert と同じ書き込みの時の検査(他のテーブルの DNAT との重なりと、VPS 上で bind 中のポート。6.1 節)を行う。無効の間に他のテーブルやプロセスがそのポートを取った場合に備えるためである。検査が拒んだ場合は何も保存せず、応答はその旨を伝える。有効化は、バッチの `force` に当たる上書きを持たない(2026-09-24、所有者の決定)。VPS 上でポートが bind されていれば、運用者がそのポートを空けてから有効化し直す。リクエストの本文を持たないという約束(7a.11 節)とも揃う。上書きを後から加えることは、管理用 API と CLI の両方への加算になる
- 有効化の順序:保存を確定し、公開し、公開が成功したときだけ配る。公開に失敗した場合は配らず、30 秒ごとの再試行(7a.3 節)が公開した時点で配る。公開に失敗している間、VPS とエージェントの両方が止まったままなので安全側である
- 保存は済んだが公開に失敗した場合:管理用 API は 422 を返し、「保存済みで、まだ公開していない」ことを伝える。有効化の検査が拒んで何も保存しなかった場合も 422 だが、応答の本文で 2 つを機械が区別できることを保証する(7a.11 節)。CLI は 0 以外で終わる。無効化でこの場合に当たると、VPS には旧いテーブルが残り、転送を続けうる。接続中のエージェントが停止の全体状態を受け取れば、リスナーとセッションを閉じる。stream が切れている場合や配信が失敗した場合は、最後に受け取った全体状態のままリスナーを開いていることがある。30 秒ごとの再試行が公開するか、エージェントが接続し直して停止の全体状態を受け取るまで、転送が続きうる
- 保存を確定できなかった場合:500 を返し、何も変えない
- 有効化の検査に要る読み取りに失敗した場合:他のテーブルの読み取りか、bind 中のポートの読み取りに失敗した場合である。検査の拒否ではないので 500 を返し、何も保存しない
- 公開できなかった世代の配信:公開に失敗した有効化の内容は、後の成功した全体適用で配る。30 秒ごとの再試行に限らず、変更の無いルールのバッチやエージェントの削除のように、別の理由で公開した経路も含む。`vpsd` は、配る全体状態の内容が変わったときに接続中の全エージェントへ配ることを、適用の 1 か所で行う。同じ世代でも内容が変われば配り直す
- 不明なエージェント名:404 を返す

疎通確認(`POST /api/v1/rules/{id}/check`。10.1 節)は、無効なエージェントのルールを、無効なルールと同じく 422 で拒む。

無効化は削除の前提ではない。削除は無効化を経ずに行え、無効なエージェントも削除できる。削除でエージェントの行ごと `disabled_at` も消えるので、同じ名前で登録し直したエージェントは有効から始まる。

表示:Web UI は、エージェントの状態を「無効」と、そのエージェントのルールの状態を、頭に横棒を添えた「エージェント無効」と示し、どちらも故障の色にしない。無効は宣言どおりの状態であり、故障ではない。`server doctor`、`status`、`agent doctor` での扱いは 10.2a・10.2b・10.2c 節に書く。

#### エージェントの削除とルール

エージェントの削除(`wgft agent revoke <name>`、`DELETE /api/v1/agents/{name}`)は、サーバのデータベースからエージェントの行を消す。恒久トークンは使えなくなり、ピアと割り当てアドレスは回収される(11 節)。そのエージェントを持ち主とするルールは、削除の後も残る。削除とルールの扱いは次のとおり(2026-09-24、所有者の決定)。

- Web UI の削除の確認:「このエージェントのルール N 本も削除する」の選択を置く。既定では選ばない。選んだ場合は、エージェントを削除した後に、既存のルールのバッチ(5.4 節)でそのルールを削除する。2 つの操作は 1 つのトランザクションではないので、ルールの削除だけが失敗すると、ルールは次項の形で残る
- CLI の削除:`agent revoke` に同じ選択を加えない。`agent revoke` の挙動は変えない
- 持ち主が削除されたルールの Web UI での扱い:故障ではなく、エージェントの登録を待つ状態として示す。削除の既定ではルールを残すので、同じ名前で登録し直せばそのまま使える。Web UI は、頭に横棒を添えた灰色の「エージェント未登録」と示し、エラーの数に含めない
- 持ち主が削除されたルールの CLI と管理用 API での扱い:`status` と `server doctor` は、次のメジャー版まで、これらのルールを今までどおりに扱う(2026-09-24、所有者の決定)。`status` は degraded に数え、`server doctor` は `rule.public_port` を FAILED `not_published` に、`agent.connection` を FAILED `agent_not_registered` にし、終了コードを 1 にする。機械向けの結果を変えると、それに頼る既存の自動化を壊すためである(7a.11 節)。Web UI との違いは意図したものであり、互換性の保証から来る。人向けの表示である Web UI は 7a.11 節の保証の対象ではない
- 持ち主が削除されたルールの一括削除:ダッシュボードのルール一覧の上に、ルールが残っている未登録のエージェントごとに帯を出す。帯は、そのエージェントが削除済みであることと、そのエージェントを参照するルールの本数を示し、それらをまとめて削除するボタンを持つ(10.1 節)。問題の単位(削除したエージェント)と操作の単位を揃え、灰色の行の説明と解消を同じ画面で済ませるためである

### 5.2 全体状態の配信とハートビート

stream は双方向で、エージェントは自分の公開鍵を、`vpsd` は全体状態を、それぞれ宣言し、接続のたびに両方が収束する。

接続時:

- エージェントは `/api/v1/agents/stream` に WebSocket で接続し、恒久トークンで認証したのち、最初のメッセージ(`pubkey`)で自分の wg 公開鍵と、対応する版の範囲・機能を送る(版と機能の交渉。下記)
- `vpsd` は、WebSocket の接続から 10 秒以内に届いた 4 KiB 以下の最初のメッセージだけを受け取り、それ以外の接続は閉じる。接続を確立した後のメッセージの大きさの上限は 1 MiB である。エージェントは接続の直後に `pubkey` を送り、現在の `pubkey` は約 130 byte なので、どちらの上限にも収まる。capabilities の語彙が増えても、`pubkey` は 4 KiB に収める。確立の前の stream の数の上限は 11 節にある
- `vpsd` は宣言された公開鍵を検証する。32 バイトの正しい形式であること、他のエージェントの保存値ともサーバ公開鍵とも一致しないことを確認し、違えば接続を拒否する。同じ公開鍵のピアを 2 つ持てず、後から設定したピアが先のピアを上書きするため、他エージェントの鍵を受け入れるとそのトンネルが壊れる
- `vpsd` は agent の範囲と自分の範囲の共通部分を取り、この接続の版を決める。範囲が壊れている、または共通部分が無ければ、ピアの置き換えに進まず理由を示すエラーで接続を拒否する(下記)
- `vpsd` は保存している公開鍵と違えば、そのエージェントのピアを新しい公開鍵で置き換える。初回接続ならピアを作る
- 鍵の変更の頻度の上限:`vpsd` は、保存している公開鍵を別の鍵に変える宣言を、登録ごとに続けて 3 回までと、その後は 10 分に 1 回までに限る。数え方はトークンバケットで、10 分ごとに 1 回分が戻り、3 回分まで溜まる。数えるのは保存している鍵を変える宣言だけである。初回の宣言、保存している鍵と同じ鍵での再接続、新しい鍵の適用が失敗している間の最後に成功した鍵での再接続(後述の配信の項)は数えない。適用に失敗した変更は数える。失敗した適用もテーブルを差し替えうるためである(6.1 節)。上限を超えた宣言では、鍵を保存せず、ピアもテーブルも変えず、公開鍵の拒否と同じ WebSocket の符号 1008 で接続を閉じる。理由の文言は上限による拒否であることを示す。`vpsd` のログの行は、エージェントごとに 1 分に 1 行までに間引く。間引きを `vpsd` の全体で 1 つにすると、あるエージェントの拒否の行が、同じ 1 分の間の別のエージェントの拒否の行を隠すためである
- 上限による拒否の記録:`vpsd` は、上限で宣言を断った直近の時刻を、エージェントの stream の状態とともにメモリの上に持つ。記録は、そのエージェントの公開鍵の宣言を受け付けると消え、登録の取り消しで stream の状態を捨てるときにも消える。接続を受け付けるのは宣言を受け付けた後なので、接続を受け付けたときにも記録は無い。したがって記録が述べるのは、その時刻に断ったことと、それより後にそのエージェントの公開鍵の宣言を受け付けていないことである。今も断り続けていることは述べない。断られた後にエージェントが試みをやめても記録は残るためである。記録には、断った接続が認証した登録も持つ。登録の取り消しが上限の判定と記録の書き込みの間に済むと、取り消した登録の記録が残りうるので、管理用 API のエージェント一覧は、今の登録と一致する記録の時刻だけを `key_change_refused_at` として返す(7a.11 節)。切断しているエージェントについて、`agent ls` は `STREAM` にこの拒否と経過を示し、`server doctor` は `agent.connection` を理由の符号 `key_change_limited` で示す(10.2a 節)。接続しているエージェントでは記録を表示に使わない。確立した接続は、より後の拒否で置き換わらないためである。エージェントの側は、直近の試みが上限による拒否で終わったことを、close の符号 1008 と理由の文言から判定して制御ソケットの応答に載せ、`agent doctor` の `stream.connection` が同じ符号で示す(10.2c 節)。記録は `vpsd` の再起動で消える。上限の状態も再起動で戻るので、記録と上限は食い違わない
- 上限が要る理由:カーネルモードの `vpsd` は、鍵の変更のたびに `table inet wgft` の全体を差し替え、全エージェントのルールの meter と `ct count` の状態を作り直す(6.1 節)。鍵の宣言を送れるのはそのエージェントの恒久トークンの持ち主で、秘密鍵は要らない。2 つの鍵を交互に宣言すると、保存している鍵と同じ鍵の省略も、最後に成功した鍵での再接続の省略も効かない。上限が無ければ、接続の試みのたびに差し替えを起こせた。上限は差し替えの回数を抑えるだけで、上限の内側の変更による差し替えは残る。ピアだけを変えてテーブルを差し替えない形は 13 節に残す
- 上限の値の根拠:wgft は自分から鍵を変えない。正規の鍵の変更は、運用者の操作(稼働中と停止中の `agent rotate-key`、古い `agent.json` への戻し)によるものだけで、続けて行っても数回である。3 回はその連続を通す。10 分に 1 回は、恒久トークンの持ち主が起こせる差し替えを、続けての 3 回の後は 1 時間に 6 回までに抑える。上限を超えた正規の変更は、1 回分が戻るまで断られ、その間はそのエージェントのトンネルが張れない。稼働中の `rotate-key` は、エージェントの側の鍵を先に新しい鍵へ替えるためである。断られたエージェントは通常のバックオフで再接続を続け、1 回分が戻った後の再接続で新しい鍵が通る。上限は設定項目にしない。上限の状態はプロセスのメモリの上だけに持ち、`vpsd` の再起動で戻る。再起動のたびに、恒久トークンの持ち主は続けて 3 回の差し替えをもう一度起こせる。それでも許容するのは、再起動が管理者の操作であり、恒久トークンの持ち主からは起こせないためである。登録をし直したエージェントは、新しい登録として数え直す
- 置き換えでは、新しい公開鍵のピアに、同じアドレスを持っていた古いピアのエンドポイントを引き継ぐ。エンドポイントは、古い公開鍵で認証されたパケットの送信元として WireGuard が最後に記録したアドレスである。稼働中の `agent rotate-key` では、エージェントは新しい鍵を設定してすぐに新しい鍵でハンドシェイクを始めるが、その時点の `vpsd` はまだ新しいピアを持たないので、そのハンドシェイクは捨てられる。エージェントが送り直すのは WireGuard の REKEY_TIMEOUT(5 秒)の後なので、引き継ぎが無いと転送はその間止まる。エンドポイントを持つ新しいピアには、`vpsd` がエージェント宛てのパケットを送る時点で `vpsd` の側からハンドシェイクを始められる。新しい鍵で認証されたパケットが届けば、WireGuard はエンドポイントをその送信元に更新する。引き継いだエンドポイントがエージェントに届かない場合は、引き継ぎの無い場合と同じく、エージェントの送り直しでつながる。カーネルモードのエージェントは wgft0 の待ち受けポートを変えずに鍵を書き換えるので、server のピアを置き直しても(7b.4 節の鍵の変更と最終ハンドシェイク)送信元のポートは保たれ、引き継いだエンドポイントに届く。ユーザー空間モードのエージェントは `rotate-key` でトンネルを作り直し、`vpsd` が観測するエンドポイントのポートがそのたびに変わるので、引き継いだエンドポイントは新しいトンネルに届かず、断は縮まない。この規則は、トランザクションの失敗で古いピアの集合に戻す場合(7a.3 節の Rollback)にも同じく働き、戻した古い鍵のピアは新しい鍵のピアのエンドポイントを引き継ぐ。そのエンドポイントは新しい鍵で認証されたパケットの送信元なので、11 節の議論は鍵の新旧を入れ替えても成り立つ。引き継ぎの安全性は 11 節で扱う
- `vpsd` は続けて全体状態を送る。全体状態には、この接続で選んだ版と `vpsd` の機能を含める(下記)

処理の順序は、認証、鍵の検証、版と機能の交渉、ピアの置き換え、旧接続の切断、全体状態の送信で固定する。
鍵の検証と版の交渉に失敗した接続は旧接続に影響を与えない。
同一エージェントの接続処理は `vpsd` 内で直列化する。

版と機能の交渉(仕様の正本は 7a.6 節。ここでは stream の手順としての要点だけを書く):

- `pubkey` メッセージは、対応する版の範囲を整数 `protocol_min`/`protocol_max` で、機能を文字列の配列 `capabilities` で持つ。両方のフィールドが無ければ、そのエージェントは版のフィールドを持たない legacy v0 として扱い、共通部分の計算はしない
- `vpsd` は `protocol_min`/`protocol_max` の宣言を、両方とも無い(上記の legacy v0)、片方だけある、両方あるが範囲そのものが無効(`protocol_min` が 1 未満、または `protocol_min` が `protocol_max` を超える。番号の付いた版は 1 から始まるため)、両方あって有効な範囲、の 3 通りに分けて扱う。片方だけある場合と範囲が無効な場合(まとめて malformed な advertisement と呼ぶ)は相手の実装の不具合を示すため、範囲は正しいが共通部分が無い場合(版を上げれば直る、正常であり得る状態)とは別の WebSocket の理由コードで区別して閉じる。どちらも、理由文字列に何が悪かったか(malformed なら欠けているフィールドや無効な範囲の値、共通部分が無ければ双方の範囲)を含める。エージェントはどちらの場合も指数バックオフ(通常の再接続と同じ)で再接続を続けるだけで、版を上げるか advertisement を直さない限り解決しない
- 全体状態(`state`)は、agent が legacy v0 でない限り、選んだ版を整数 `server_protocol_version` で、`vpsd` の機能を文字列の配列 `server_capabilities` で持つ。legacy v0 の agent にはどちらのフィールドも載せない(今の形のまま送る)
- `capabilities`/`server_capabilities` は、空配列(版はあるが追加の機能は無い)とフィールドの不在(legacy v0)を区別する。両者を JSON の `omitempty` だけで区別すると空配列も省かれてしまうため、実装はポインタ型で持つ
- エージェントは、返ってきた `server_protocol_version`(フィールドがあれば)が 1 以上の番号の付いた版であり、かつ自分の範囲に入っていることを確かめる。1 未満はそもそも版として無効で、1 以上でも範囲外なら外れている。どちらも接続を切り、通常のバックオフで再接続する(server の実装が誤った版を返した場合の防御であり、通常は起きない)
- 選んだ版は、接続ごとに 1 回だけ両側のログに出す(メッセージごとには出さない)

stream はエージェントごとに 1 本だけである。

- 新しい接続が認証されたら、`vpsd` は旧接続を理由コード `superseded` で閉じる。旧 TCP が死んでいる場合に備え、常に新しい方を優先する
- 新しい接続は、旧接続の閉じる処理が終わるまで、確立の前の stream の枠(11 節)を返さない。新しい接続の確立と全体状態の送信は、この処理の終わりを待たない
- 閉じられた側は指数バックオフ(初期 1 秒、上限 5 分)で再接続する。これは善意の二重起動どうしの振動を抑える手段であり、バックオフを守らない第三者に対する保証ではない。窃取に対する保証は後述の警告とエージェントの削除だけである
- エージェントは、WireGuard の新しいハンドシェイクを観測したとき、残りのバックオフの待ちを打ち切って直ちに再接続し、バックオフを初期値に戻す。ハンドシェイクの成立は `vpsd` までの経路が戻ったことを示すためである。観測には、トンネルの点検(7 節)が 30 秒ごとに読む最終ハンドシェイクの値をそのまま使い、別の監視を持たない。点検の周期が 30 秒なので、ハンドシェイクの成立から待ちの打ち切りまでに最長 30 秒かかる
- 待ちを打ち切る根拠になるのは、その接続の試みが終わった後に観測したハンドシェイクだけである。接続していた間に観測したものは、その接続が切れる前の経路の話でしかないので、切れた後の待ちの根拠にしない。エージェントは、接続の試みが戻った時点で、溜まっていた観測を捨ててから待ちに入る
- 打ち切りによる再接続の試みは、2 分に 1 回を超えない。1 つのトンネルの最終ハンドシェイクは、WireGuard の時定数により 2 分に 1 回程度しか新しくならないためである。打ち切りとは別に、トンネルが新しい間の試みの間隔は、次の項の 10 秒の上限が決める
- トンネルが新しい間の待ちの上限:エージェントは、WireGuard の最終ハンドシェイクが新しい間、接続できなかった後の待ちの上限を 5 分ではなく 10 秒にする。データの経路が生きているという追加の証拠がある場合だけ、積極的に制御の経路を探すためである。待ちは 1 秒から倍々に伸び、トンネルが新しい間は 10 秒で止まる。つまり 1、2、4、8、10、10 秒と続く。トンネルが古くなると、待ちは 10 秒から倍々に伸びて 5 分の上限に戻る。トンネルが再び新しくなると、次の待ちから上限は 10 秒に戻る
- 上限が要る理由:カーネルモードの `vpsd` は、プロセスが止まっても wg0 と鍵を残す(9 節)。プロセスが止まっている間もトンネルは生きており、プロセスが戻ったことは新しいハンドシェイクに現れない。前の項の打ち切りが働くのは、鍵の更新で最終ハンドシェイクが新しくなったときだけで、その時刻はプロセスが戻った時刻と関係が無い。打ち切りの間に待ちは倍々に伸びるので、この上限が無いと、プロセスが戻ってからエージェントが繋がるまでに、伸びた待ちの残りだけ遅れる。その間、転送は続くがルールの変更は届かず、`agent ls` と Web UI はそのエージェントを未接続と示す
- 「新しい」の判定:最終ハンドシェイクが、その値を観測した時刻から数えても、値そのものが示す時刻から数えても 180 秒未満であることとする。観測には、トンネルの点検(7 節)が 30 秒ごとに読む値をそのまま使い、別の監視を持たない。エージェントのユーザー空間モードとカーネルモードは、どちらもこの点検で今のトンネルの最終ハンドシェイクを読むので、同じ判定になる。180 秒は WireGuard の `RejectAfterTime` で、`server doctor` の `tunnel.handshake` の 3 分の閾値(10.2a 節)と同じ値である。健全なトンネルの最終ハンドシェイクは 145 秒(`RekeyAfterTime` の 120 秒と keepalive の 25 秒)より古くならず(7 節)、点検の周期の 30 秒を足しても 175 秒なので、健全なトンネルを古いと数えない。180 秒を過ぎた鍵は送信にも使えないので、それより古いハンドシェイクはデータの経路が生きている証拠にならない。145 秒の上限には但し書きがある。wireguard-go は、時間による鍵の更新を、そのセッションのハンドシェイクを始めた側だけが始める。`vpsd` が始めた側で、`vpsd` からエージェントへ送るデータが無い場合、更新は `vpsd` がエージェントの keepalive を受けた時点になり、最終ハンドシェイクは約 190 秒まで古く見えうる。その間は上限が一時的に外れ、待ちが 20 秒程度に伸び、次のハンドシェイクで打ち切られて戻る。害は小さいので閾値は変えない。この但し書きはラボと実機では確かめておらず、未確認である。一度新しかったというだけで 10 秒の上限を保ち続けることはない。`vpsd` のホストごと消えた場合も、最後のハンドシェイクから 180 秒の内に待ちは通常の伸び方に戻る
- 2 つの起点から数える理由:観測した時刻からの時間は単調な時計で測るので、壁時計が戻っても古い値を新しいと数え続けない。トンネルの作り直しの判定(7 節)と同じ理由である。値そのものからの時間は、起動の直後に初めて読んだ古い値を新しいと数えないために見る。カーネルモードのエージェントは停止の間も wgft0 を残すので(7b.4 節)、起動の直後に読む値は何時間も前のものでありうる。壁時計が進んだ場合は健全なトンネルを古いと数えるが、そのときの待ちは通常の伸び方に戻るだけである
- 上限を当てない切断:`vpsd` が応答したうえで、再試行では直らない食い違いを示した切断には上限を当てず、通常のバックオフで再接続する。制御の経路は届いており、探す理由が無いためである。当たるのは、恒久トークンの拒否(401)と取り消し(`revoked`)、同じエージェントの新しい接続による置き換え(`superseded`)、版の不一致(`vpsd` が理由コードで閉じた場合と、`vpsd` が選んだ版をエージェントが拒む場合。上記)、証明書のピンの不一致、公開鍵の拒否である。公開鍵の拒否は、`vpsd` が WebSocket の標準の符号 1008(policy violation)で閉じる切断で、他のエージェントの公開鍵やサーバの公開鍵と同じ鍵、形の誤った鍵と、鍵の変更の頻度の上限(上記)を超えた宣言が当たる。`vpsd` はこの符号を公開鍵の検証の失敗と鍵の変更の拒否にだけ使うので、エージェントは理由の文言を見ずに符号で見分ける。上限による拒否は時間が経てば解けるが、待ちの上限を 10 秒にしても 1 回分が早く戻るわけではないので、上限を当てない側に置く。`superseded` では、上に書いた善意の二重起動どうしの振動を抑える役目も保つ
- 上限を当てる切断:接続の失敗、429 のような一時的な拒否、つながっていた接続が切れた場合(ping の期限による切断を含む)、ハートビートの期限切れ(`heartbeat_timeout`)、`vpsd` の内部の誤り(1011)、版の宣言の形の誤り(`protocol_malformed`)である。形の誤りは相手の実装の不具合を示し通常は起きないので、分けて扱わない
- 上限の負荷:`vpsd` のプロセスが止まっていて wg0 が残っている間、エージェント 1 台あたり毎分 6 回程度、閉じたポートへの TCP の接続を試みる。鍵の更新による打ち切りのたびに、待ちが初期値から伸びて 10 秒に達するまでの数回が加わる。閉じたポートはすぐに RST を返すので、試み 1 回は 1 往復で終わる。ホストのファイアウォールが API のポートへのパケットを黙って捨てる場合は、試みごとに接続の期限の 30 秒を待つので、試みはさらに少ない。プロセスが接続を受けたうえで stream を認めない場合は、試みごとに TLS のハンドシェイクと HTTP の要求が 1 回ずつ起きる。再接続の待ちに入るたびの 1 行は、前の行と同じ文面なら 1 分に 1 行までに間引き、文面が変われば出す(10.4 節)。間引いた数は次に出す行に添える
- 置き換えそのものは検知の対象にしない。二重起動、`agent rotate-key`、再起動、回線の IP 更新のいずれでも起きる正常な事象で、窃取と区別する材料にならないためである。窃取は下の「IP の食い違い」で見る

接続の生死の判定:

- stream が生きているとは、その TCP が `ESTABLISHED` であることではなく、相手の応答が限られた時間の内に届くことである。半開きの TCP は `ESTABLISHED` のまま何分も残り、書き込みも成功し続けるので、ソケットの状態は判定の材料にならない
- ハートビートと ping は役割が違い、どちらも要る。ハートビートはエージェントの状態を `vpsd` に報告するもので、送信が成功したことは経路が通っていることを意味しない。ping と pong は、stream が双方向に通ることだけを測る
- エージェントは接続中の stream に 30 秒ごとに WebSocket の ping を送り、20 秒以内に pong が返らなければその接続を閉じて再接続する。経路が死んでから判定までに要する時間は最長 50 秒である
- 50 秒は、`vpsd` が何も届かない stream を閉じるまでの 90 秒に対して 40 秒の余裕を残す。エージェントの側が必ず先に気付いて繋ぎ直すので、運用者の画面が未接続を示す区間は、長くても繋ぎ直しに要する数秒になる。経路が戻っていなければ `vpsd` の側が 90 秒で閉じ、表示は従来どおり未接続になる
- 期限を間隔の 2 / 3 とするのは、同種の仕組みが採る比率に合わせるためである。Python の `websockets` は 20 秒の間隔に 20 秒の期限(1.0 倍)、MQTT は仕様が 1.5 倍、SSH の `ServerAliveInterval` と `ServerAliveCountMax` は 3 倍、NATS は 2 倍から 3 倍である。間隔の半分のような短い期限は、15 分の故障に対して数秒しか得をしないのに、混んだ回線や移動体の回線での 1 回の遅い往復を切断と見なす。30 秒と 20 秒は、どの実装も採っている範囲の内側にある
- ping を判定に使う理由は、`vpsd` が待機中の stream へ定期的な送信を行わず、読みの期限を相手の送信に結び付けられないことである。ping は RFC 6455 が pong の返送を求める制御フレームなので、版と機能の交渉の対象にならず、旧い版の `vpsd` も応答する。JSON のメッセージの種類は増えない
- この判定が測るのは、経路が通っていることと、エージェント自身の読みの繰り返しが動いていることの両方である。`coder/websocket` は ping と pong の制御フレームを読みの繰り返しの中でしか処理せず、`Conn.Ping` 自身は接続から読まない(ライブラリの注釈が `Reader` と並行に呼ぶことを求めている)。エージェントが自分の都合で読みを止めれば pong は期限内に処理されない。転送の経路が生きているエージェントを未接続にしないためにこの性質が要るが、後から読む者が、エージェントの内部で止まった状態を回線の不調と取り違えないよう、ここに書いておく
- エージェントの ping は `vpsd` 側の 90 秒の期限を延ばさない。`vpsd` の期限が戻るのはデータのメッセージを読んだときだけなので、ハートビートが止まったエージェントが ping だけで接続を保ち続けることはない
- OS の TCP の再送の打ち切りは判定に使わない。半開きの TCP への書き込みは送信バッファに入って成功するため、ハートビートの送信が失敗するのは OS が再送を諦めた後になる。打ち切りまでの時間は OS ごとに違い、実機の macOS では 1 分 31 秒、Linux の既定(`tcp_retries2` が 15)ではラボの実測で 15 分 53 秒だった。Linux の `tcp(7)` はこの既定を「およそ 13 分から 30 分」と書いており、実測はその範囲の内側にある。OS ごとの差をそのまま wgft の回復時間にしないために、判定は wgft 自身が持つ
- `TCP_USER_TIMEOUT` は判定に使わない。Linux にしかない設定であり、エージェントは Windows と macOS でも動くためである。TCP の keepalive も判定に使わない。送信したデータの応答を待っている区間では probe を送らないので、半開きの stream で頼りになる上限を与えない。ラボの実測でも、Go の既定の 15 秒の keepalive は上の 15 分 53 秒を縮めなかった
- Linux では、網の口を落とす操作もこの判定の対象になる。アドレスが残るので既存の接続への書き込みは成功し続け、stream は誤りを返さずに半開きになるためである
- 全体状態の適用の間は ping を送らず、ping を送ってから pong を待つ区間に適用が挟まった場合も判定しない。適用は TCP の宛先への試し接続を含み、宛先 1 つにつき最長 10 秒かかるので、pong の期限より長くなりうる。適用が戻らない場合の上限は、`vpsd` が何も届かない stream を閉じる 90 秒が与える

配信:

- `vpsd` は接続直後と、そのエージェントに配る内容が変わるたびに、全体状態を送る。差分ではなく全体を送る
- 全体状態はエージェントごとに組み立てる。そのエージェントを持ち主とするルールだけが入る(5.3 節の `agent`)
- 全体状態は 1 通のメッセージで送る。エージェントが読む 1 通の大きさの上限は 4 MiB で、これを超える全体状態をエージェントは読めない。この上限と、確立した stream で `vpsd` が読む 1 通の上限(1 MiB、上記)が、エージェントあたりのルールの数の上限と、ルールの ID と `target` の長さの上限(5.3 節)の根拠である
- 世代はエージェントごとの値ではなく、ルール集合全体に対して 1 つの値である。どれか 1 つのエージェントに配る内容が変われば 1 つ上がり、`vpsd` は接続中の全エージェントへ配り直す。配る内容が変わらないエージェントは、同じ内容を新しい世代で受け取る
- 適用が成功した後に `vpsd` が配り直すのは、配信用の写し(次項)が直前の写しと違うエージェントだけである。世代が上がれば全エージェントの写しが変わるので、ルールの変更は全エージェントに届く。鍵の宣言は世代を上げず、宣言したエージェントの写しの鍵だけを変えるので、他のエージェントには配らない。宣言したエージェントの新しい接続は、接続時の全体状態を受け取る。無効化は保存の確定時に世代を上げ、全エージェントへ配る
- 1 つの全体状態の世代、ルール、エージェントの無効の印は、転送面の適用に使った宣言から組み立て、適用に成功したときに配信用の写しとして保持する。保存後の適用に失敗した宣言は、接続時や後から動く配信処理でもこの写しに混ぜない。無効化だけは保存の確定時に対象の無効の印とルールの停止、世代を先に反映する。登録を削除したら、その登録の写しは後の適用が失敗しても直ちに配信対象から外す。送信する接続ごとに写しを選び、接続固有の版の情報はその写しを変更せずに加える。接続はトークンを認証した時点の登録 identity を保持し、鍵の保存と State の選択で現在の登録 identity と照合する。認証後、最初の鍵の受信前に登録を削除して同じ名前で登録し直しても、旧接続は新しい登録を変更できない。接続の鍵は配信用の写しの鍵とも照合し、保存後の適用に失敗した新しい鍵の接続は旧接続を置き換えない。旧接続は成功済みの鍵で無効化の停止を受け取れる。送信済みの状態をエージェントが適用したことは、この選択と送信だけでは確認できない
- 新しい鍵を保存した後の適用が失敗している間、同じ登録の恒久トークンと最後に成功した鍵で再接続したエージェントは、その鍵に対応する配信用の写しを一時的に受け取れる。この再接続は保存済みの新しい鍵を書き戻さず、無効化の停止も受け取る。新しい鍵の全体適用が成功したら旧鍵の接続を退役させ、旧鍵に新しい写しを配らない。新しい鍵の接続は、その成功後に最新の写しを受け取る
- 配信要求は接続ごとに 1 件だけ保留し、連続した要求は 1 回の最新状態の送信にまとめる。接続ごとの送信処理は接続終了時に終わる。新しい State は、その接続の送信権を得た後に配信用の写しを選ぶ。無効化や登録削除の確定後に新しく選ぶ State は停止または削除を反映する。確定前に選択を始めた送信は既に進行中なので、送信途中の内容を遡って取り消すことはできない。接続の差し替え後、旧接続で既に進行中の送信は完了するか失敗し、新接続は自身の初回 State を選ぶ
- 世代の比較は同一 WebSocket 接続内に限る。接続直後の最初の全体状態は世代に関わらず必ず適用し、以後は手元より古い世代を捨てる。`vpsd` の再構築やバックアップからの復元で世代が巻き戻っても、これで収束する
- 接続直後の最初の全体状態より後に届いた全体状態が、手元で最後に適用に成功した全体状態と世代も中身も同じなら、エージェントは適用し直さない。トンネルが立っていて、試し直しを待つ全体状態も、拒んだ wg 設定も無いときに限る。旧い版の `vpsd` は他のエージェントの鍵の変更でも全体状態を配り直し、カーネルモードのエージェントはそのたびに wgft0 の収束、テーブルの差し替え、宛先への試し接続をやり直していたためである。同じ世代でも中身が違えば適用する。`vpsd` は UDP のタイムアウトの値を、世代を上げずに配信用の写しへ書き込むことがあるためである
- エージェントは全体状態を「宣言された状態に収束させる」方式で適用する。wg 設定が変わればトンネルを張り直し、リスナーは変わったものだけを開閉する。収束の単位は 7 節に定める。カーネルモードのエージェントの収束は 7b 節に定める

ハートビート:

- エージェントは 30 秒ごとに送る。加えて、全体状態を適用するたびに(接続直後の最初の適用を含む)すぐに送る。WireGuard のハンドシェイクがまだ済んでいなければ、済むまで 1 秒ごとに、最長 10 秒まで送り直す。適用が続いたときは、まだ送っていない通知を 1 通にまとめる。中身は処理済み世代(最後に受け取って処理した世代。backend 全体の失敗を除き、部分失敗でも進める。7・7b 節)、トンネルの状態(`ok` または `error` と理由、エンドポイントの解決結果)、ルールごとの状態(`ok` または `error` と理由)
- ルールの `error` は、リスナーの開放失敗(bind できない)か、TCP ルールで適用時の `target` への接続確認が失敗した場合を指す。UDP は到達確認ができないので開放失敗だけを見る。宛先の許可一覧(7 節)が `target` を拒んだ場合も `error` になる。IP リテラルの `target` は適用のときに拒まれ、ホスト名の `target` は名前解決の後の接続のときに拒まれる。どちらの理由にも設定の名前を含める。`error` のトンネル設定とルールは、エージェントが 30 秒ごとに再適用と確認を試み、状態が変わったら次のハートビートで報告する。ルールとトンネルの状態の理由に入る名前の解決の誤りの文面からは、問い合わせごとに変わる送信元とサーバのソケットの組(`read udp <送信元>-><サーバ>: `)を除く。DNS サーバは誤りの文面の `on <サーバ>` に残る。除かないと、同じ誤りが続く間も確認のたびに文面が変わり、状態の変化として扱われるためである(改訂の記録 2026-09-24)。所属ルール ID が移ったリスナーの状態は、移った直後の再確認で新しいルール ID に付け替える。カーネルモードのエージェントはリスナーを持たないので、`error` の出どころを 7b 節で置き換える。`ok` と `error` がそのルールの転送について意味することは、モードで変わらない
- ハートビートのトンネルの状態と理由・解決したエンドポイント・ルールごとの状態と理由・ルール ID は、エージェントが選ぶ文字列であり、エージェントは信頼の境界の外にある(11 節)。`vpsd` はこれらの文字列を受け取ったまま保存せず、まず表示できない文字(`unicode.IsGraphic` が偽の文字。C0・C1 の制御文字、不正な UTF-8 のバイトを含む。日本語の文中の全角スペースのような Unicode の空白(Zs)は対象外である)を、その文字を Go の `strconv.Quote` と同じ書式(`\x1b` のような形)へ置き換え、続いてその結果を長さの上限で切り詰めてから保存する。この順序(置き換えてから切り詰める)は、保存する値の長さを上限の範囲に収めるためである。逆の順(切り詰めてから置き換える)では、上限まで残した生の文字がすべて表示できない文字だった場合、1 文字が数バイトへ膨らむ置き換えによって保存される長さが上限の数倍に達しうる(2026-09-26、レビューの指摘)。上限はトンネルとルールの理由が 512 バイト、ルール ID とトンネルのエンドポイントが 128 バイト、トンネルとルールの状態が 64 バイトで、いずれも実際にエージェントが送る値の長さに対して数倍の余裕を持つ値である。超えた分は rune の境目で切り、末尾に切ったことを示す印を添える。ルール ID の上限は、ルールの ID に許す長さ(5.3 節)と同じ値である。ルールの検査が受ける ID は、この置き換えにも切り詰めにも掛からない。切り詰めと置き換えは、`agent ls`・`rule ls`・`status`・`server doctor` の人向けの出力だけでなく、保存する値そのもの、つまり管理用 API の `--json` が返す値にも及ぶ(7a.11 節)。人向けの出力は、この受け口の処理とは別に、表示の直前でも同じ書式の置き換えをもう 1 段掛ける。エージェント自身の `agent doctor`・`rotate-key` が読む制御ソケットの応答は、この受け口を経由しないため、表示の直前の置き換えだけがこれを守る
- エージェントの側の理由の上限:エージェントは、ハートビートのトンネルとルールの理由を、送る前に次の順で変換する。まず不正な UTF-8 のバイトを、Go の `json.Marshal` と同じく 1 バイトずつ U+FFFD に置き換える。続けて受け口と同じ変換にかける。表示できない文字を同じ書式に置き換え、その結果を 512 バイトで切り詰める。切る位置は rune の境目で、末尾に切ったことを示す印を添える。印は 512 バイトの外に付く。理由はエージェントが作る文言で、宛先のホスト名や OS の誤りの文面を含むので、長さが決まらない。受け口の切り詰めはメッセージを読んだ後に掛かるので、接続を確立した後のメッセージの上限(1 MiB)は、エージェントが送ったままのメッセージに掛かる。上限を超えたメッセージは読めず、stream が切れる。理由を持つのは `error` のルールなので、上限が無いと、ルールが一斉に失敗した場面、つまり診断が最も要る場面で 1 通が上限を超えうる。最初の置き換えは、この変更より前に JSON の符号化がしていた置き換えと同じである。これを省いて受け口の変換を先にかけると、不正なバイトが 4 バイトの見える形(`\xfe` の形)になり、512 バイトの内に残る文言が前より短くなる。受け口の変換は、自分の結果にもう一度かけても、切り詰めの印より前の文言を変えない。したがって受け口の変換を持つ v1.2.0 以降の `vpsd` が保存する理由は、エージェントが切り詰めずに送った場合と、印より前の文言が同じである。違いは、エージェントが多バイト文字の途中を避けて 512 バイトより手前で切った場合に、受け口が保存する値の印の前に、エージェントの印の頭の 1 から 3 バイト(`.`)が残ることだけである。`server doctor` が分類に使う語(10.2a 節)は印より前の文言から探すので、分類は変わらない。v1.2.0 より前の `vpsd` は理由を受け取ったまま保存するので、このエージェントと組むと、保存する理由は切り詰めて置き換えた後の値に変わる。その場合、分類に使う語が理由の 512 バイトより後ろにだけあれば、`server doctor` の理由の符号が変わりうる。この変化は理論上のもので、観測していない。エージェントのログの行には、切り詰める前の理由を書く
- メッセージの符号化:エージェントは stream のメッセージを、HTML に埋め込むための書き換えをせずに JSON にする。この書き換えは Go の `json.Marshal` の既定で、`<`・`>`・`&` を `\u003c` の形の 6 バイトにする。どちらの形も同じ JSON の文字列を表すので、`vpsd` はどの版でも同じ値に読む。書き換えを残すと、`&` を並べた理由が 1 文字あたり 6 バイトになり、1 つの理由が JSON で上限の 6 倍まで膨らむ。置き換えの後の理由には表示できない文字が無いので、JSON で 2 バイトになるのは `"` と `\` だけである。切り詰めの印は JSON で膨らまない ASCII なので、1 つの理由は、JSON で印と引用符を含めて 1039 バイトを超えない。ルール ID の長さは server が配る値で決まり、この上限の外にある。ID が 128 バイトまでの表示できる文字なら、512 本のルールのすべてが最も膨らむ理由で `error` のハートビートも 1 MiB に収まる
- TCP ルールの `target` への接続確認は、適用のときだけでなく定期的にも行う。周期はハートビートと同じで、現在は 30 秒である。この値は今後変えることがあり、固定はしない。`error` のルールだけでなく `ok` のルールも確認の対象にする。`target` が落ちれば次の周期でそのルールが `error` になり、戻れば `error` は自動で消える。結果は後続のハートビートのルールごとの状態に入る。確認は TCP の接続を開いてすぐに閉じる操作なので、`target` の側には、データを伴わない接続が周期ごとに 1 本届く。接続を記録するサーバでは、その記録が残る。宛先の許可一覧(7 節)が拒む `target` には、この確認でも接続しない。UDP はこの方法で到達性を判定できないので、定期の確認を行わない
- 接続確認は中継の錠を持たない。エージェントは確認の対象の待ち受けとその `target` を錠の中で写し取り、錠を放してから最大 32 件を同時に試み、結果を反映するときにもう一度錠を取る。反映するのは、その待ち受けが今もあり、かつ `target` が試したときの値と同じ場合だけである。錠を放している競合可能期間に待ち受けが閉じた場合と `target` が変わった場合は、その結果を捨てる。この作りは適用のときの確認にも使う。適用は確認の結果を待ってから戻るので、ルールの最初の状態は適用の直後のハートビートに今までどおり載る
- 接続確認 1 件の期限は 2 秒である。この値は、中継が実際の通信のために `target` へ接続するときの期限とは別の値である。LAN の `target` の TCP のハンドシェイクは 1 ミリ秒の桁で済むので、2 秒には三桁の余裕がある。ハンドシェイクに 2 秒を超える `target` は、接続を受け付けていても `error` として報告される。`error` は報告にだけ使い、中継そのものを止めないので、誤って `error` になったルールも転送を続ける。期限を長く取ると、黙って捨てる `target` 1 つがその長さだけ確認を延ばす
- 到達性が変わった待ち受けは、変わったときだけログを 1 行出す。周期ごとには出さない。運用者が「LAN の `target` に届かない」と「エージェントが止まっている」を区別できるようにするためである
- `vpsd` は最終ハートビート、処理済み世代、トンネルとルールの状態、wg の最終ハンドシェイク時刻を記録し、UI に表示する
- 管理用 API は、ルールごとのこの状態(`state`・`reason`)を、報告したエージェント名・最終ハートビートの日時・そのエージェントが今も接続しているかとともに、`rule_id` をキーにした加算的なフィールドで `GET /api/v1/rules` にも載せる(7a.11 節)。以前は `agent ls` の RULES 列と Web UI にしか出ておらず、`rule ls` だけを見る自動化はエージェント側の拒否理由(宛先の許可一覧による拒否、リスナーの開放失敗、接続確認の失敗)を追えなかった。この状態は、必ずそのルールの今の持ち主(`Rule.Agent`)のハートビートから引く。持ち主でない別のエージェントが、同じルール ID をたまたま古いハートビートに載せていても(ルールが持ち主を移った直後や、削除された後もそのエージェントが未接続のままだと起こりうる)、それを拾わない。今あるルールは、その持ち主がまだ一度もハートビートでこのルールを報告していなくても、必ずこのフィールドに 1 件の項目を持つ(2026-09-21、所有者の決定)。報告がまだ無いことと、この節点自体を実装していない Backend であることを JSON だけから見分けられるようにするためで、詳細は 7a.11 節に定める
- stream が切れると `vpsd` は `Connected` を false にするが、最後に記録したトンネルとルールの状態、接続元 IP は消さずに残す(診断に使うため)。UI と CLI は `Connected` が false のエージェントについて、これらの値を今の状態として描いてはならない。最後の報告であることが分かる形(古さを示す色、CLI の `last:` 接頭辞)で示し、いつの時点かは最終ハートビートの経過時間で表す。管理用 API の上記フィールドも、そのエージェントが接続中かを別途持たせることで同じ区別を伝える。stream の接続元 IP と wg エンドポイント IP の食い違いの比較(窃取の兆候。下記)も、両方が今のものでなければ意味を持たないので、`Connected` が false の間は出さない
- `vpsd` は 15 秒ごとに wg のピア状態(wgctrl の `Endpoint` と最終ハンドシェイク時刻)を読み、下の検知に使う。この読み取りかエージェント一覧の読み取りが失敗した回は判定を飛ばす(10.5 節のフェイルオープン)。原因はログに残す

窃取の検知:

- `vpsd` はエージェントごとに 2 つの IP を観測している。**stream の接続元 IP**(最終ハートビートが 45 秒以内の、生きている接続のもの)と、**wg ピアのエンドポイント IP**(最終ハンドシェイクが 3 分以内のもの)である。本物のエージェント 1 つだけが動いていれば、この 2 つは常に同じ IP になる
- 両方が観測でき、かつ食い違っている状態が 2 分間(15 秒間隔の監視で連続 8 回)続いたら、`ip-mismatch` の警告を 1 件残す。中身は両 IP と、最後に検出した日時
- 食い違いだけでは、第三者と本物の両方がフル稼働で置き換え合う場合を取りこぼす(ラボで実測)。WireGuard は認証済みパケットを受けるたびにエンドポイントを送信元へ更新するので、同じ鍵を 2 か所から使うとエンドポイントは keepalive のたびに両者の間を往復し、15 秒ごとの観測ではほぼ毎回ランダムになる。stream は supersede の後しばらく安定するため、食い違う確率は各観測で約 1/2 にとどまり、8 回連続は期待値で 1 時間ほどかかる。そこで第 2 の判定を置く
- **IP の往復**:`vpsd` はエージェントごと、チャネル(stream の接続元 IP、wg エンドポイント IP)ごとに、直近 10 分間に観測した IP の変化を記録する。stream は接続が認証されるたびに、wg は 15 秒ごとの観測で記録する。同じチャネルの IP が 10 分以内に A → B → A と、以前の値へ戻ったら `ip-flapping` の警告を 1 件残す。中身はチャネルと往復した 2 つの IP と、最後に検出した日時である。往復が示すのは、同じチャネルを 2 つのアドレスから交互に観測したという事実だけである。同じ鍵や同じ恒久トークンを 2 か所が使っている場合と、1 台のエージェントが 2 つの回線の間を移動して区間内に戻ってきた場合(ローミング)を、往復という現象自体からは見分けられない。回線の更新のような一方向の変化は往復にならない。運用者への対応は、そのエージェントがローミングすると分かっていれば警告を消し、分からなければエージェントを削除して登録し直すことである
- 2 つの判定の分担:フル稼働の置き換え合いと、本物が再接続や keepalive を続けている非対称の窃取は「往復」が数十秒から 1 分で捕まえる。本物が片方のチャネルで黙っている場合(stream を奪われて再接続できていない、など)は「食い違い」が 2 分で捕まえる
- どちらでも検知できない場合:本物のエージェントが完全に止まっていて第三者だけが動いているとき。往復も食い違いも起きず、正規の引っ越しと区別できない。これは IP を根拠にする限り検知できないので、受け入れる
- 自宅回線の IP 更新では警告しない。旧 IP の stream は TCP ごと死んでハートビートが止まり、45 秒で観測対象から外れる。新しい stream は新しい IP から来て、wg のエンドポイントも同じ IP に動くので一致する。2 分の猶予はこの入れ替わりの間の一時的な食い違いを吸収するためのものである
- どちらの警告も自動で消さない。置き換え合いの最中に出たり消えたりしないためである。同じ内容が再検出されたら、最後に検出した日時を更新するだけで、行は増やさない。回数は数えない。例外は次の 2 つの項の上限で、種類ごとに古い行だけを消す
- `ip-flapping` の警告の行の上限:サーバのデータベースは、エージェントごとに `ip-flapping` の行を 64 行まで持つ(2026-10-02、所有者の決定)。往復を記録するたびに、そのエージェントの `ip-flapping` の行のうち、いま記録した行と、ほかの行で最後に検出した日時が新しい 63 行を残し、それより古い行を消す。いま記録した行は必ず残るので、往復を検出したエージェントの警告が上限によって消えることはなく、前の項の「自動で消さない」は警告の単位では保たれる。上限に達しても検知は止まらず、管理者に見えるのは直近に検出した往復である。ただし時計が戻ると、未来の日時を持つ行は、時計がその日時に追いつくまで残る。その間に必ず見えるのは最新の往復 1 件だけである。64 行は 2 つのチャネルで共有し、8 つの回線の間を行き来するエージェントが作るすべての組(2 つのチャネルを合わせて 56 通り)を収める。1 つの回線を 1 つの IP と数え、デュアルスタックの回線や IPv6 の一時アドレスで増える IP は数えていない。上限を超えた行を持つ既存のデータベースは、そのエージェントの次の往復の記録で 64 行まで減る。`ip-mismatch` の行の上限は次の項にあり、この 64 行には数えない
- `ip-mismatch` の警告の行の上限:サーバのデータベースは、エージェントごとに `ip-mismatch` の行を 64 行まで持つ(2026-10-02、所有者の決定)。この 64 行は `ip-flapping` の 64 行とは別に数える。食い違いを記録するたびに、そのエージェントの `ip-mismatch` の行のうち、いま記録した行と、ほかの行で最後に検出した日時が新しい 63 行を残し、それより古い行を消す。観測した組が確認済みの組で、警告を記録しなかった回は、行を消さない。いま記録した行が必ず残ること、上限に達しても検知が止まらないこと、時計が戻ったときに見える行は、`ip-flapping` の上限と同じである。上限で消すのは警告の行だけであり、確認済みの組を作ることも、変えることも、捨てることもない。上限で行が消えた組は確認済みにならないので、その組の食い違いを再び観測すれば、上限が無い場合と同じ判定で警告になる。管理者の「警告を消す」で確認済みの組になるのは、消す時点で行が残っている組だけである。連続回数の数え方と、確認済みの組との照合と破棄は、上限によって変わらない。64 行は、8 つの回線を持つエージェントで stream の接続元と wg エンドポイントが別の回線に出るすべての組(56 通り)を収める。1 つの回線を 1 つの IP と数える数え方は `ip-flapping` の上限と同じである。上限を超えた行を持つ既存のデータベースは、そのエージェントの次の食い違いの記録で 64 行まで減る
- 警告への対処はエージェントの削除しかないので、Web UI の警告のバナーでは、警告の隣に削除と「警告を消す」の操作を置く。エージェント一覧の行には削除を置かない(10.1 節)。バナーの削除の確認は、削除が元に戻せないことと、一時的に止めるだけなら無効化を使うことを示す。「消す」は正当な事情(自分で 2 拠点から動かした、など)を管理者が確認したときに使う
- `ip-mismatch` の警告を消す操作は、警告の行を消すことに加えて、その警告が示す 2 つの IP の組を管理者が正当と確認した記録として、サーバのデータベースに残す(2026-09-24、所有者の決定)。以下、この記録を確認済みの組と呼ぶ。以前は行を消すだけだったので、同じ食い違いが続く限り、次の 15 秒の観測で同じ警告が戻っていた。確認済みの組は、エージェント、警告の種類、stream の接続元 IP、wg エンドポイント IP の 4 つで識別する。IP は正規化した値で比べ(IPv4 射影の IPv6 アドレスは IPv4 として扱う)、ポートと detail の文字列は識別に使わない
- 確認済みの組は、15 秒ごとの観測で次のように扱う
  - 同じ組の食い違いが続く間:警告を出し直さない
  - 2 つの IP が一致した観測:確認済みの組を捨てる
  - 別の組の食い違いの観測:確認済みの組を捨て、連続回数を数え直す。新しい組は、通常どおり 2 分(連続 8 回)続いてから警告になる。確認済みの組が無い間は、組が変わっても連続回数を数え直さない。IP を短い間隔で替える第三者が食い違いの警告を逃れないようにするためである
  - どちらかの IP を観測できない回:確認済みの組を捨てない。エージェントが切断している間と、server の再起動の直後で接続がまだ揃っていない間がこれに当たる
  - server の再起動:確認済みの組は残る
  - エージェントの削除:そのエージェントの確認済みの組を消す
  - 確認済みの組を読めない回:その回の判定を飛ばし、連続回数も進めない。読めないまま判定すると、管理者が確認した組の警告を出し直すためである
- 監視の回は、確認済みの組を読んでから警告を記録するまでの間に、管理者の「警告を消す」と入れ違うことがある。警告の記録は、確認済みの組との照合と同じ SQL の文で行い、消したばかりの警告を戻さない
- 登録が無いエージェントの `ip-mismatch` の警告を消す操作は、行を消すだけで、確認済みの組を残さない。エージェントの削除の後に残った警告がこれに当たる。削除は確認済みの組を消すので、組を残すと、どのエージェントのものでもない組が残り続ける
- `ip-flapping` の警告を消す操作は、これまでどおり行を消すだけで、確認済みの組を残さない。往復を再び観測すれば警告は戻る
- 確認済みの組は、管理用 API、CLI、Web UI のどれにも一覧として出さない。記録したときと捨てたときに、エージェントの名前と 2 つの IP をログに 1 行ずつ出す(10.4 節)。確認済みの組を手で消す操作は持たない。確認した組を窃取と疑い直したときの対処はエージェントの削除であり、削除は確認済みの組も消す
- 以前の版にあった置き換え回数の警告、二重接続の警告、交互置き換えでの受け付け停止、既知エンドポイント IP 集合と「受け入れる」操作は持たない。「往復」は以前の交互検出と似ているが、stream の置き換えだけでなく wg エンドポイントも見ること、受け付けを止めず警告にとどめること、管理者に IP の登録を求めないことが違う。回線の IP 更新のたびに管理者の操作を要求する割に、守っている資産(wg0 上の 1 ピア。5.1 節のとおり到達できる先がない)に見合わないためである

全体状態の形:

```json
{
  "generation": 42,
  "wg": {
    "server_pubkey": "...",
    "endpoint": "vps.example.com:51820",
    "address": "10.200.0.2/24",
    "mtu": 1420,
    "keepalive": 25,
    "udp_timeout": 30,
    "udp_timeout_stream": 120
  },
  "rules": [ ... ],
  "server_protocol_version": 1,
  "server_capabilities": []
}
```

`server_protocol_version`/`server_capabilities` は、agent が legacy v0 なら載らない(上記)。`pubkey` メッセージの側も同じ形で `protocol_min`/`protocol_max`/`capabilities` を持つ(7a.6 節)。

### 5.3 ルールのスキーマ

```json
{
  "id": "r_01J...",
  "agent": "home",
  "group": "game",
  "note": "週末サーバ。フレンド用",
  "proto": "udp",
  "listen_port": "2456-2457",
  "target": "192.168.1.20:2456",
  "vps_mode": "kernel",
  "proxy_protocol": false,
  "source_allow": [],
  "source_deny": ["203.0.113.0/24"],
  "new_flow_rate": "100/second",
  "packet_rate": null,
  "per_source_rate": "10/second",
  "enabled": true
}
```

- `id`:ルールの ID。CLI と Web UI は `r_` と ULID の 28 バイトを作る。`rule import`、Web UI の読み込み、管理用 API のバッチでは、ID を書いて渡せる。ID は UTF-8 で 128 バイト以内とし、すべての文字が Go の `unicode.IsGraphic` が真の文字でなければならない。長さは文字数ではなくバイトで数える。日本語、記号、ASCII の空白と、全角スペースのような Unicode の空白(Zs)は受ける。空白を削ることも、全角と半角をそろえることもしない。制御文字(改行とタブを含む)、行と段落の区切り(U+2028、U+2029)、双方向の上書きやゼロ幅の文字、私用領域の文字は受けない。不正な UTF-8 も受けないが、管理用 API と読み込みは ID を JSON で受け取り、Go の `encoding/json` は不正な UTF-8 のバイトと対になっていないサロゲートの escape(`\ud800` など)を U+FFFD に置き換えてから渡す。このため、JSON の経路ではそのような ID は U+FFFD を含む ID として受ける。不正な UTF-8 の検査は、JSON を経ずに Go から検査を呼ぶ側のための多重の守りである。`.` と `..` も受けない(10.2 節)。この長さと文字の範囲は、ハートビートの受け口(5.2 節)が置き換えも切り詰めもせずに保存する範囲と一致する。範囲の外の ID のルールは、エージェントの報告と ID が一致しないので、状態が永久に届かない。nftables のカウンタのコメント `wgft:<ID>:<種類>` も、この上限の下で 256 バイトの userdata に収まる。改行を含む ID がログの行を偽ることも防ぐ(2026-10-03、所有者の決定)。この検査の前に保存された行の扱いは 5.4 節に定める
- `agent`:このルールの持ち主となるエージェントの名前。登録済みのエージェントでなければ `vpsd` は拒否する。転送の経路と、このルールを載せる全体状態の配り先の両方を決める
- `group`:任意。ルールを束ねる短いラベル 1 つ(例 `game`)。1 ルールに 1 つ。英数と `-_.`、32 文字以内。転送には影響しない。空のルールは UI で「その他」に入る
- `note`:任意。このルールが何のためかを書く自由記述(120 文字以内)。転送には影響しない
- `proto`:`tcp` または `udp`
- `listen_port`:VPS で待ち受けるポート。`"2456-2457"` の範囲指定も許す。範囲のときは `target` のポートは先頭に対応し、以降は連番で写す。ルール間で重複できない
- `target`:自宅側の宛先。エージェントと同じホストなら `127.0.0.1:port` と書く。`host:port` の全体を UTF-8 で 259 バイト以内とし、すべての文字が `unicode.IsGraphic` が真の文字でなければならない。259 は DNS の名前の上限の 253 バイトに `:` と 5 桁のポートを足した値である。長さはバイトで数えるので、ポートの先頭に 0 を並べて長くした値も拒む。文字の範囲はルールの ID と同じで、制御文字と不正な UTF-8 を受けない(2026-10-03、所有者の決定)。この検査の前に保存された行の扱いは 5.4 節に定める
- `vps_mode`:`kernel`(nftables で転送)または `proxy`(`vpsd` 内の TCP 中継で転送)。`proxy` は TCP のみで単一ポート運用に限り、`listen_port` を範囲にはできない(カーネルモードとユーザー空間モードのどちらでも中継は 6.2 節の `proxyrelay` を使い、範囲を許すと先頭ポート以外が中継されないまま黙って失われるため)。ユーザー空間モード(6.3 節)では全ルールが `vpsd` 内の中継になるため区別に意味は無く、`proxy` は「PROXY protocol を付けられる TCP の中継」を選ぶ印としてだけ残る
- `proxy_protocol`:`vps_mode = proxy` のときだけ有効。PROXY protocol v2 ヘッダを付けて送る
- `source_deny`:列挙した CIDR を捨てる。最初に評価する
- `source_allow`:空でなければ、列挙した CIDR 以外を捨てる
- `new_flow_rate`:ルール全体の新規フロー数の上限
- `packet_rate`:ルール全体のパケット数の上限。UDP のデータグラムだけに効く。TCP のルールでも値は受け付けて保存するが、効かない(7a.9 節「TCP の packet_rate」)
- `per_source_rate`:接続元 IP ごとの新規フロー数の上限
- `enabled`:`false` でリスナーを閉じ、VPS 側のルールも外す。`true` に戻すと開き直す

エージェントに配るのは `id`、`proto`、`listen_port`、`target`、`enabled` だけである。
`agent` は全体状態に載せるフィールドではないが、どのエージェントの全体状態にその行を入れるかを決める。
持ち主を別のエージェントへ移す変更は、移す前のエージェントに配る内容からその行を取り除き、移した先のエージェントに配る内容にその行を加えるので、世代が上がる。
世代が上がるかどうかの判定は、行ごとの配る部分だけを並べて比べるのではなく、持ち主ごとにまとめた配る内容どうしを比べて行う。
`vps_mode`、`group`、`note` はエージェントに配らない。`group` と `note` は管理用のメタデータで、転送にも全体状態にも影響しないため、変更しても世代は上がらずエージェントには配信されない。プロキシモードのルールでも、エージェントは `vps_mode = kernel` のルールと同じく `listen_port` で受け、`vpsd` はそこへ接続して中継する(6.2 節)。受けるのは、ユーザー空間モードのエージェントではリスナー、カーネルモードのエージェントでは DNAT である(7・7b 節)。
接続元制限の変更は全体状態の内容を変えないので、エージェントには配信されず、世代も上がらない。

1 つのエージェントが持てるルールは 512 本までである(2026-10-03、所有者の決定)。数えるのは `agent` がそのエージェントの名前である行で、有効と無効を問わない。無効なルールも `enabled:false` として全体状態に載るためである。上限は設定項目にしない。根拠は全体状態とハートビートの 1 通の上限(5.2 節)で、どちらもコードの定数である。数の上限だけを設定で上げられると、エージェントが読めない全体状態を保存できるようになる。ルールの ID、`target`、ハートビートの理由(5.2 節)の長さの上限の範囲で、符号化の後が最も長くなる値を選んでも、512 本の全体状態はエージェントが読む 4 MiB に収まり、この版のエージェントが送る 512 本のハートビートは `vpsd` が読む 1 MiB に収まる。`target` の検査は全体の長さだけを見てホストの長さを別に制限しないので、最も長くなる `target` は、符号化で 6 バイトになる `&` をホストに詰め、1 桁のポートを付けた 259 バイトの値である。単体試験が、`vpsd` とエージェントの実際の符号化でこの 2 つを確かめる。この保証は、ルールの ID と `target` が上限の内側にあるルールについてのものである。判定の仕方と、上限を超えて保存されたデータの扱いは 5.4 節に定める。

`listen_port` に WireGuard、エージェント用 API、管理用 API(TCP で待ち受けている場合)のポートを指定した場合、`vpsd` は拒否する。
API のポートは待ち受けが実際に bind するポートで判定し、`host:port` のホストの部分は判定に使わない。ポートをサービス名で書いた設定は、待ち受けと同じ規則で番号に直す(11a 節)。
`target` のポートに範囲の幅を足した実効宛先が 65535 を超える場合も拒否する。
VPS 上のプロセスが `0.0.0.0` か公開 IP で bind 中のポート(`/proc/net/tcp` と `/proc/net/udp` で確認する)も拒否する。SSH のポートを指定して VPS から締め出される事故を防ぐためで、`--force` で上書きできる。

### 5.4 ルールのバッチ操作

管理用 API は、複数ルールの追加、変更、削除を 1 トランザクションで行うバッチ操作を持つ。
バッチの結果で上がる世代は 1 つで、`listen_port` の重複検査はバッチ全体の適用後の状態に対して行う。
ルールの分割と統合はこのバッチで行い、CLI の `rule split` と `rule merge` はバッチの薄い層である。
分割を「縮める、足す」の 2 リクエストで行うと、中間の世代でポートが宣言から消えてセッションが切れるため、バッチが必要になる。
`vps_mode = proxy` のルールは単一ポート運用(5.3 節)のため、分割は結果の両側が単一ポートになる場合だけ受け付ける(2 ポートの範囲を境界で割る場合に限る)。3 ポート以上の `proxy` の範囲は、単一ポート運用にする前から保存されていた既存データとしてしか存在しえず、単発の分割では単一ポートまで割り切れないので、削除して単一ポートずつ作り直す。
統合(`rule merge <id1> <id2>`)は、エージェント、プロトコル、方式、`listen_port` の隣接、実効宛先の連続に加え、PROXY protocol、拒否/許可リスト、3 つのレート、`enabled` がすべて同じ組み合わせだけを受け付ける。これらが違う 2 つを統合すると一方の値が黙って失われるため、条件に含める。`vps_mode = proxy` の組は、隣接していても統合すると必ず 2 ポート以上の範囲になるため、単一ポート運用の制約によりどちらの組み合わせでも統合できない。統合したルールは `id1` の ID・`group`・`note`・接続元制限・レート・`enabled` を保ち、`listen_port` と実効宛先だけを `id2` の分まで広げる。`id2` は削除する。組み立てと検査は CLI と Web UI(10.1 節)で共有する。

バッチ操作は、事前に読んだルール集合のハッシュ(`proto.RulesDigest`)を任意で受け取る(`ExpectedDigest`)。指定すると、バッチはこのバッチ自身が変更しようとしている今のルール集合のハッシュと比べ、一致しなければ何も変えずに専用の誤り(`ErrBatchConflict`。管理用 API では HTTP 409)を返す。この照合は、ルール集合を読み取ってから変更を確定するまでを 1 トランザクションの内側で行うため、読み取りと、それを基にした変更の呼び出しとの間に他経路(別の CLI 呼び出しや別タブの Web UI)が割り込む競合を防ぐ。ルール集合を読んでから確定までの間が開く操作(Web UI の読み込み確認・適用、CLI の `rule import`)がこれを使う。

バッチは変更後のルール集合全体を毎回検査するため、`Rule.Validate` に検査を後から追加すると、追加前から保存されていた、今回のバッチが触っていない既存ルールがその検査に落ち、以後の無関係なバッチまで失敗しうる。これを避けるため、`store.ApplyBatch` は `proto.ValidateUpsert` を使い、バッチの前後で ID・内容が変わらない行には `Rule.Validate` を掛け直さない。ID の重複、予約ポート、`listen_port` の重なりの検査は変更の有無を問わず全体に対して行う。これらは以前から全体を検査していたため、保存済みのデータは既に満たしている。例外は、2026-10-02 の改訂で予約に加わったポート(ホスト名やサービス名で書いた API のポート)に重なる保存済みのルールで、扱いは 11a 節に定める。読み込みも同じ規則に従う。CLI の `rule import` はこのバッチにそのまま送り、Web UI の読み込みの確認ページは、今のルールから変わっていない行を同じ判定(`proto.UnchangedIDs`)で除いてから `Rule.Validate` を掛ける。確認ページだけが全体を検査すると、古い行を変えない読み込みが CLI では通るのに Web UI では適用ボタンが出ない、という経路の差が生まれるためである。行が変わったかどうかの判定では、空の接続元リストの `nil` と空の配列を同じとみなす。

ルールの ID の長さと文字の検査(5.3 節、2026-10-03)の前に保存された、この検査に落ちる ID の行も、この規則で扱う。その行は読み込みと転送を続け、無関係なバッチを妨げない。書き出しをそのまま読み込み直す操作も通る。同じ ID のままその行を変えるバッチは拒む。有効と無効の切り替え、接続元制限、レート、`group` と `note`、分割、その行の ID を残す統合がこれに当たる。削除は通る。その行を使い続けるには、同じ設定の行を正しい ID で作り直す。`listen_port` の重なりはバッチの後の集合で判定するので、古い行を消して新しい ID の行を足す 1 回のバッチ(`rule import`)なら、ポートを空けずに置き換えられる。

`target` の長さと文字の検査(5.3 節、2026-10-03)の前に保存された、この検査に落ちる `target` の行も、この規則で扱う。その行は読み込み、転送、配信を続け、無関係なバッチを妨げない。書き出しをそのまま読み込み直す操作も通る。その `target` のまま行を変えるバッチは拒む。有効と無効の切り替え、接続元制限、レート、`group` と `note`、分割、統合がこれに当たる。削除と、`target` を正しい値に変える書き換え(`rule import`、管理用 API のバッチ)は通る。

エージェントあたりのルールの数の上限(5.3 節)は、バッチの前後の集合を比べて判定する。あるエージェントについて、バッチの後の本数が 512 を超え、かつバッチの前の本数より多いときに限り、バッチ全体を保存の前に拒む。上限まで足すバッチ(511 本から 512 本)は通り、超えるバッチ(512 本から 513 本)は拒む。持ち主を別のエージェントへ移す行は、移した先のエージェントの本数を同じ式で判定し、移す前のエージェントの本数を減らす。判定は `proto.ValidateUpsert` が行うので、`store.ApplyBatch` を通るすべての保存に効く。CLI の `rule add`・`split`・`merge`・`rm`・`set`・`enable`・`disable`・`deny`・`allow`・`rate`・`import`、Web UI の追加・編集・分割・統合・有効と無効の切り替え・削除・読み込み・未登録のエージェントの帯の一括削除、管理用 API のバッチである。CLI の `--dry-run` と Web UI の読み込みの確認は、`admin.PreflightBatch` から同じ関数を呼ぶ。拒否は管理用 API の既存の 422 で返し、文言はエージェントの名前、バッチの後の本数、上限を示す。stream の接続と再接続、全体状態の組み立てと送信、エージェントの登録、無効化と有効化は本数を見ない。

上限の導入の前に保存された、512 本を超えるエージェントのルールは、読み込み、転送、配信を続ける。`vpsd` は起動のたびに、上限を超えるエージェントごとに警告を 1 行ログに出す。管理用 API と Web UI は開き、一覧を返す。本数を増やさないバッチは通る。削除、別のエージェントへの移し替え、統合、本数を変えない書き換え(有効と無効の切り替え、接続元制限、レート、`group`、`note`)、同じ本数での置き換えの読み込みがこれに当たる。追加と分割、そのエージェントへの移し替えは、本数が上限まで減るまで拒む。512 本を超えるエージェントには、5.3 節の保証は及ばない。本数が増えると、多くのルールが長い理由で error を報告したときに、ハートビートが全体状態より先に読む側の上限を超えうる。ハートビートが `vpsd` の読む 1 MiB を超えると、`vpsd` はその 1 通を読めずに stream を閉じる(5.2 節)。ルールの ID と `target` の検査(5.3 節)の前に保存された、上限より長い ID や `target` の行も、1 本あたりの大きさを 5.3 節の前提より大きくする。そのような行を持つエージェントには、512 本以下でも 5.3 節の保証は及ばない。

### 5.5 複数サービスへの配り方

エージェントは `target` へ自分から接続するので、宛先はサービスと同じホストでなくてよい。
1 拠点に 1 つのエージェントを置き、ルールごとに `target` を各ホストへ向けるのが基本形である。

```
wgft rule add --agent home --udp 2456-2457 --to 192.168.1.20:2456
wgft rule add --agent home --udp 2458-2459 --to 192.168.1.21:2456
wgft rule add --agent home --tcp 25565     --to 192.168.1.22:25565
```

同じサービスを複数台動かす場合は、VPS 側の `listen_port` をずらし、`target` 側で本来のポートに写す(上の例の 2458 から 2456 への写し替え)。

ホストごとにエージェントを置く構成も同じ仕組みで動く。
ホスト間で到達性がない場合や、片方の停止をもう片方に波及させたくない場合に使う。
