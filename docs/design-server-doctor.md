### 10.2a 転送の診断 (`server doctor`)

`wgft server doctor` は、転送が通らないときに、どこまで通ってどこで止まったか、運用者が次に何を見るかを答えるコマンドである。内部の状態を並べる機能ではない。成功の条件は、利用者が次に見る場所を知らないまま残らないことである。次の行動を伴わない所見は、この機能の失敗として扱う。

対象とする場面は次の 5 つである。ポートを開いたのに接続できない。昨日まで通っていたのに今日は通らない。エージェントは接続しているのに転送されない。1 本のルールだけが通らない。server、トンネル、エージェント、宛先のどれが原因か分からない。

#### 名前と置き場所

コマンドは `server` の下の `doctor` である。理由は 3 つある。CLI は名詞で束ねており (`server`、`rule`、`agent`)、最上位の動詞は `version` だけなので、最上位の `doctor` は他と揃わない。`server check` の隣に置くと、`check` が「このホストの設定は正しいか」に、`doctor` が「なぜ転送が通らないか」に答える対になる。後述の自宅側の `agent doctor` と対称になる。

この配置には、明らかでない結果が 1 つある。`server` の一群は Linux 以外のビルドでは拒否する代替に置き換わる (`cmd/wgft/server_other.go`) ため、Windows と macOS のバイナリは、管理用 API しか必要としない `server doctor` を持たない。10.3 節のとおり CLI は VPS 上で root として使い、SSH で転送したソケットはブラウザのためのものなので、この制約は受け入れる。手元の端末から使いたくなった場合の出口は、診断の実装を Linux の build tag の付いたファイルの外へ移すことだけである。実装は既に build tag を持たない `cmd/wgft/doctor.go` にあり、登録だけが `server.go` にあるので、移すのは登録の位置を変える作業に収まる。現時点では `server` の一群の構造を変更しない。

#### 両側の診断と、この版の範囲

診断は両側に置く。server 側の `server doctor` は、server とエージェントが対応できている間、端から端までの答えを出す。自宅側の `agent doctor` は、server と対応できない場合でも、その節点だけを手元で診断する。`agent doctor` が server 無しで動く必要があるのは、まさに server と対応できない場合が診断を最も必要とする場面だからである。Web UI からも同じ診断を呼び出せるようにするが、順序は `agent doctor`、Web UI、`--report`、遠隔の診断の順とする。Web UI の診断の画面の設計は 10.2d 節にある。

この版で実装するのは `wgft server doctor [rule]` だけである。`agent doctor`、Web UI の操作、`--report` は含めない。

`agent doctor` がまだ無いので、出力は存在しないコマンドを案内しない。自宅側を見る必要がある所見は、今あるもの、つまりエージェントのホストでのログの読み取り (`systemctl status wgft-agent`、`journalctl -u wgft-agent`、コンテナなら `docker logs`)、名前の解決の確認、server 側の `wgft agent ls` による公開鍵の突き合わせを案内する。`agent doctor` ができた時点で案内し直す。実装には該当箇所に印を置いてある。

遠隔の診断は、server がエージェントに診断を要求し、その結果を併せて示す形である。server からエージェントへの新しいメッセージが要るので `proto` と v1.0 の保証 (7a.6 節の機能の交渉) に触れる。この版では実装しない。遠隔の診断が加えるのは、エージェント自身の環境である。エージェントの OS、権限、インタフェースの状態、名前解決の詳細がそれに当たる。将来これを加えるときは、機能の交渉の上に載せ、出力の形を変えずに検査を追加する形にする。必要かどうかの判断は `agent doctor` ができてからにする。手元で見えるものが分かって初めて、server 側から要求すべき情報が決まるためである。

この版は、既に届いている観測だけから組み立てる。ハートビートがエージェントのルールごとの状態と理由、トンネルの状態、最終ハンドシェイクの古さを運び、`conncheck` (10.1 節) が内側の経路を実際に試す。

#### 5 つの状態

検査 1 件の結果は次の 5 つのいずれかである。意味はこの表のとおりであり、他の読み方をしない。

| 状態 | 意味 |
|---|---|
| OK | その項目が成功することを実際に観測した |
| FAILED | その項目が失敗することを実際に観測した |
| UNKNOWN | 証拠はあるが、古い、食い違う、または判定に足りない |
| NOT TESTED | その到達性や条件をこのコマンドがそもそも試さない |
| SKIPPED | 試せたはずだが、手前の失敗によって今回は試せなかった |

OK は実際に検証したものだけに使う。公開ポートは、server がそのポートを扱えていても、外からの到達性を試していないので NOT TESTED である。

```
public port        NOT TESTED
                   serving tcp 2456; reachability from outside was not tested
```

UDP のルールの宛先 (`rule.target`) も、同じ規則により、エージェントの新しい報告が `ok` であっても NOT TESTED とする。理由の符号は `udp_listener_only` とする。UDP のルールの `ok` は、エージェントがリスナーを開けたことしか意味しない (5.2 節)。宛先がデータグラムを受け取ったことも、応答したことも示さないので、OK の定義に当たらない。報告が古い場合の UNKNOWN と、報告が `error` の場合の FAILED は、TCP のルールと同じである。NOT TESTED はルールの総合判定も終了コードも動かさないので、健全な UDP のルールの総合判定は OK のままであり、終了コードは 0 のままである。

```
target             NOT TESTED
                   not tested: the agent has its listener open, last report 12s ago, but a
                   UDP send cannot tell whether the target received it or answered
```

能動的な確認が通った宛先は OK である。

```
target             OK
                   connected to 192.168.1.50:2456 through the tunnel and the agent, observed just now
```

無効なルールは宣言どおりの状態であり、失敗ではない。検査はすべて SKIPPED になり、理由の符号は `rule_disabled` になる。終了コードは 0 のままとする。意図して無効にしたルールで監視が鳴り続けることを避けるためである。

#### 観測の古さ

OK は永続しない。OK の所見は必ず観測の古さを伴い、閾値を越えた項目は OK でなくなる。

```
connected          OK         heartbeat 12s ago
WireGuard          OK         handshake 32s ago
target             UNKNOWN
                   the agent last reported this rule ok, but that was 2m14s ago
```

越えたときにどの状態へ移るかは、その値がどこから来るかで 2 つに分かれる。`ObservedAt` が古いことと、観測した内容そのものが古いことは、別の事柄である。

**エージェントが過去に送った報告**は、古くなると UNKNOWN になり、理由の符号は `stale_report` になる。値は報告した時点のものであり、その後どうなったかを server は知らないためである。

- エージェントの接続 (`agent.connection`): 90 秒とする。エージェントは 30 秒ごとにハートビートを送る (5.2 節) ので、3 回分の沈黙を越えたら、接続しているという表示を今の値として扱わない
- エージェントが報告したルールの状態 (`rule.target`): 90 秒とする。TCP の `target` への接続確認は 30 秒ごとに行われる (5.2 節) ので、接続の判定と同じ長さを使う

**server が今読む値**は、古くなると FAILED になる。`tunnel.handshake` の 1 つだけが当たり、閾値は 3 分、理由の符号は `no_recent_handshake` である。最終ハンドシェイクはエージェントの報告ではなく、server が WireGuard から今読む値である。「最終ハンドシェイクは 181 秒前」という値は、今この瞬間に読んだ現在の観測であり、そのトンネルが健全の条件を満たしていないことを示す。判定に足りない古い証拠ではないので、UNKNOWN ではなく FAILED とする。

閾値の 3 分は 7 節の時定数から決まる。server が配る keepalive は 25 秒 (`internal/vpsd/admin_backend.go`) で、`RekeyAfterTime` は 120 秒なので、健全なトンネルの最終ハンドシェイクは 145 秒より古くならない。`RejectAfterTime` の 180 秒を過ぎた鍵は送信にも使えない。したがって 3 分を越えた値は、健全なトンネルでは生じない。窃取検知が生きている wg エンドポイントを 3 分以内のものに限る (5.2 節) のとも同じ値である。

この規則が防ぐのは、2026-09-21 に実測した 2 つの区間で、診断が誤って安心させることである。1 つは、転送を続けているエージェントを server が切断と表示する区間である。もう 1 つは、受信の経路が死んだトンネルの最終ハンドシェイクが 3 分間は新しいままである区間である (7 節)。後者の区間の長さは `tunnel.handshake` の閾値そのものであり、別の値ではない。エージェントが device と netstack を作り直す 300 秒 (7 節) はエージェント側の watchdog の閾値であって、診断が気付けない期間ではない。

#### ルール集合の世代の遅れ

`agent.rules_received` は互換性のため ID を保つが、検査するのはエージェントがハートビートで報告した世代番号と server の世代番号だけである。人向けの名前は「rule generation」とし、番号が等しい場合の OK は番号の比較に限る。番号が等しくても、エージェントが適用した State の内容が server の公開した State と同一かどうかは UNKNOWN である。現在の wire には内容の確認値や受領の確認が無く、この変更で wire と認証情報の保存形式を変えない。診断の所見は、この限界を世代番号の一致、不一致のどちらでも明示する。適用済み State の内容は継続して検証不能であり、番号がそろっても OK と報告しない。

ルール別の CLI と Web UI では、この検査の詳細に内容の UNKNOWN を記す。一覧では同じ制約をルールごとに繰り返さず、「この診断が試していない範囲」に一度示す。内容の検証不能は転送失敗の証拠ではないので、ルールの総合判定、終了コード、ダッシュボードの印を変えない。検査の ID、status、reason の機械向けの値と管理用 API のフィールドも変えない。

`agent.rules_received` は、接続中のエージェントの世代が server の世代と違うとき、その遅れが続いている長さで判定を 2 つに分ける (2026-09-24、所有者の決定)。60 秒未満は UNKNOWN とし、理由の符号を `generation_pending` とする。60 秒以上は FAILED とし、理由の符号を `generation_behind` とする。世代はルール集合全体に 1 つだけあり (5.2 節)、どのルールを変えても、そのエージェントを名指す有効なすべてのルールがこの検査を経由する。遅れを直ちに FAILED にすると、ルールを 1 本変えるたびに、そのエージェントのすべてのルールが一時的に FAILED になる。ラボではエージェントは新しい世代を 1 秒未満で取り、取った直後にハートビートを送る (5.2 節) ので、60 秒続く遅れは届く途中の遅れではない。このため 60 秒以上の FAILED は、原因の候補にも次の手順にも、届く途中であることや数秒後の再実行を挙げない。

遅れの長さは、server がエージェントごとにメモリに持つ遅れの始まりの時刻から測る。管理用 API のエージェント一覧は、この時刻を `generation_behind_since` として返し、遅れていないエージェントでは省く。一覧は、直近のハートビートの内容 (`last_heartbeat`、`generation`) とこの時刻を、ハートビートの記録が済んだ後の 1 つの時点の組として返す。別々に読むと、ハートビートの内容だけが新しく、始まりの時刻の記録がまだの途中を返すことがあり、その形は `generation_behind_since` を返さない旧い server の応答と区別できない。診断は管理用 API だけを読むので、この値を経由する。始まりの時刻は次の規則で決める。

- 記録の契機:server の世代が進んだときと、ハートビートが届いたときに、エージェントの世代が server の世代より古ければ、始まりの時刻が無い場合に限りその時刻を記録する
- 遅れの間に世代がさらに進んだ場合の扱い:始まりの時刻を動かさない。動かすと、ルールの変更が続く間は遅れがいつまでも閾値に届かない
- 始まりの時刻が消える条件:エージェントが server の今の世代を報告したときだけである
- server の再起動の後の扱い:始まりの時刻はメモリにしか無いので失われる。起動の後に初めて遅れを観測した時刻から数え直す。起動の前から続いていた遅れの長さを server は知らないので、その分だけ FAILED になる時刻が遅れる

接続してからまだハートビートが届いていないエージェントは、世代を比べず UNKNOWN とし、理由の符号を `not_reported` とする。hub は接続ごとにエージェントの状態を作り直すので、この間の管理用 API の応答は `last_heartbeat` を省き、`generation` を 0 とする。この 0 は報告された世代ではない。判定の条件は `agent.connection` と同じく `last_heartbeat` が無いことであり、2 つの検査は同じ判定を返す。再接続の前から遅れの始まりの時刻が記録されていても、この判定を先に行う。最初のハートビートが届いた後は、記録されている始まりの時刻から遅れの長さを測る。

応答に `generation_behind_since` が無いまま世代が違う場合は、v1.1 と同じく FAILED とし、理由の符号を `generation_behind` とする。この値を返さない旧い server を新しい CLI で診断する場合が当たる。遅れの長さが分からないまま UNKNOWN にすると、止まった遅れを見逃すためである。

`generation_behind` の意味は v1.1 から変えず、止まった遅れを表す。`generation_pending` は、理由の符号の開いた集合への加算である (7a.11 節)。`generation_pending` の UNKNOWN は、経路の上の他の UNKNOWN と同じく、ルールの総合判定を UNKNOWN にし、終了コードを動かさない。

#### UDP の応答の観測

UDP のルールの `rule.target` には、server 自身が見た宛先の応答を補足の 1 行として添える(2026-09-24、所有者の決定)。エージェントの報告はリスナーを開けたことしか示さないので、宛先が応答しているかどうかの手掛かりを、server が転送の途中で受動的に観測する。wire、ハートビート、capability は変えないので、観測はエージェントの版とモードに依らない。

観測する事実は、そのルールの UDP の応答がトンネルを通ってこの server に最後に届いた時刻である。応答を返せるのはそのルールの宛先だけなので、この時刻は宛先からの応答の時刻と読める。観測の方法はモードごとに次のとおりである。

- ユーザー空間モード:中継(6.3 節)は、宛先の側から応答を 1 つ読むたびに、待ち受けごとの最後の応答の時刻を記す。記すのは 1 秒に 1 回までで、時刻にはセッションの無通信の判定が既に読む値を使う。読み取りの誤りは応答として数えないので、宛先の側が ICMP で拒んだ場合も数えない。範囲のルールの値は、そのルールの待ち受けのうち最も新しいものである
- カーネルモード:`table inet wgft` に、UDP のルールごとの応答のカウンタの行を置く(6.1 節)。行は `meta l4proto udp` を持つので、ICMP の誤りを数えない。`vpsd` は 10 秒ごとにカウンタを読み、前回より増えたルールの最後の応答の時刻を、その読み取りの時刻にする。パケットごとに Go を起こさないので、時刻は最大で 10 秒ほどの誤差を持つ

カーネルモードでは、起動の後とテーブルの差し替えの後の最初の読み取りは基準にしかならない。0 でない値から過去の応答の時刻を推定しない(所有者の決定)。差し替えはカウンタを 0 に戻すので、drop のカウンタ(6.1 節)と同じく差し替えの直前に読み、直後にもう一度読んで基準にする。2 つの読み取りの間には、数えない短い区間が残る。その区間にだけ届いた応答は見落とされるが、無かった応答を作ることは無い。この区間があっても、差し替えでは `since` を保つ。連続性が途切れたときは、観測を捨てて次の読み取りを基準に始め直す。読み取りの失敗、wgft の外でのカウンタの減少、成否の分からない差し替えがこれに当たる。

観測はメモリだけに持つので、server を再起動すると観測を始め直す。ルールの ID が変わった場合(分割と統合)、ルールが別のエージェントへ移った場合、宛先が変わった場合も、応答の主が変わるので観測を捨てて始め直す(所有者の決定)。公開ポートとエージェントのアドレスが変わった場合も始め直す。この 2 つは、安全側に倒すために実装で加えた条件である。無効にしたルールと削除したルールの観測は消える。宛先を変えた直後は、エージェントが新しいルールを適用するまでの間、古い宛先が返した応答が新しい観測に数えられうる。この区間はカーネルモードとユーザー空間モードの両方にある。

観測は状態を変えない。最近の応答があっても NOT TESTED は OK にならない。応答が無いことや古いことも UNKNOWN や FAILED にならず、閾値も持たない。使われていないルールと応答しないサービスは、どちらも応答が無いように見えるためである。ルールの総合判定、報告全体の状態、終了コードも動かさない。カウンタを読めない場合は、応答が無いことと区別して、観測できないことをその理由とともに示す。この場合も状態は動かさない。

```
target             NOT TESTED
                   not tested: the agent has its listener open, last report 12s ago, but a
                   UDP send cannot tell whether the target received it or answered
                   last UDP reply seen by this server 18s ago
```

応答を見ていない場合の行は `no UDP reply seen since this server started watching the rule 3h12m0s ago; an idle rule looks the same`、観測できない場合の行は `UDP replies are not observed: <理由>` である。`--json` では `rule.target` の検査に任意の項目 `last_reply_at`・`reply_since`・`reply_not_observed` を加え、新しい検査の `id` は作らない。新しい `id` は 5 つの状態のどれかを返す必要があり、観測を状態に写さない決定と両立しないためである。管理用 API には `udp_replies` を加える(7a.11 節)。`rule ls` の表とダッシュボードのルール一覧には出さない。

この観測は、宛先の応答とトンネルの戻りの経路を切り分けられない。戻りの経路だけが壊れた場合も観測は止まるが、観測が無いことを失敗にしないので、誤った判定にはならない。宛先とトンネルの切り分けは `tunnel.handshake` と `agent.connection` が担う。TCP のルールには加えない。TCP の宛先は 30 秒ごとの接続確認を既に持つためである。

#### この VPS の ip_forward

カーネルモードの server は、起動時にだけ `net.ipv4.ip_forward` を 1 にする(6.1 節)。稼働中に外から 0 にされると、DNAT を公開したままカーネルは wg0 へ転送しなくなり、カーネルで転送するルールはすべて止まる。2026-09-25 まで、この状態の `server doctor` は `server.dataplane` を OK とし、失敗の無い報告を返していた。

管理用 API の `GET /api/v1/rules` は、カーネルモードの server が応答を組むときに読んだ今の値を `ip_forward` として返す(7a.11 節)。ユーザー空間モードの server は返さない。カーネルで転送しないので、値がルールについて何も述べないためである。読む節点は増えない。値が 1 でないとき、次のとおり判定する(2026-09-25、所有者の決定)。

- `rule.public_port`:カーネルで転送するルール、つまり `vps_mode` がプロキシでないルールで、`apply_state` が `active` なら FAILED とし、理由の符号を `ip_forward_off` とする。server が今読んだ値であり、転送が止まっていることの観測である。プロキシのルールは `vpsd` が受けて自分から wg0 へ接続し直すので、`ip_forward` に依らず、判定を変えない
- `server.dataplane`:カーネルで転送する公開中のルールが 1 本以上あれば FAILED とし、理由の符号を `ip_forward_off` とする。1 本も無ければ、止まる転送が無いので状態は変えず、所見に値と、後から加えるカーネルモードのルールは転送されないことを添える。世代の遅れが同時にあれば、世代の遅れの FAILED を先に示し、所見に `ip_forward` を併せて示す。世代の遅れが無く、保存済みの全体 State が未公開でも、観測した転送停止の FAILED を優先し、その所見に未公開の事実も添える

次の一手は、`sysctl -w net.ipv4.ip_forward=1` で 1 にすることと、0 にしたもの(`/etc/sysctl.d` の設定や堅牢化のスクリプト)を探すことである。書けない場合は、起動時の書き込みも同じ原因で失敗するので再起動だけでは直らない。読み取り専用の `/proc` やコンテナの制限などの原因を除いてから 1 にする(2026-10-03)。`--probe` の疎通確認は、この状態でも成功する。server 自身が wg0 へ接続し、カーネルの転送を経ないためである。止まった位置は `rule.public_port` が示す。稼働中の server は自分では戻さない(6.1 節)。値を読めなかった場合は状態を変えず、`--verbose` の内部の値に読めなかった理由を示す。

#### 検査の一覧と証拠の出どころ

検査はすべて既存の管理用 API の応答から組み立てる。新しい節点を追加しない (7a.11 節の保証を変えない)。

| 検査の ID | 見出し | 証拠 | 呼び出し |
|---|---|---|---|
| `rule.enabled` | enabled | `Rule.Enabled` | `GET /api/v1/rules` |
| `agent.enabled` | agent enabled | `AgentInfo.Disabled`、`AgentInfo.DisabledAt` | `GET /api/v1/agents` |
| `rule.public_port` | public port | `rule_states[id].apply_state` と `reason`、`drift`、`ip_forward` | `GET /api/v1/rules` |
| `rule.source_filter` | source filter | `source_deny`、`source_allow` と `--from` の値 | `GET /api/v1/rules` |
| `server.dataplane` | dataplane | `desired_generation`、`active_generation`、`agent_state_generation`、`agent_state_pending`、`apply_error`、`ip_forward` | `GET /api/v1/rules` |
| `tunnel.handshake` | WireGuard | `AgentInfo.LastHandshake`、`AgentInfo.Tunnel` | `GET /api/v1/agents` |
| `agent.connection` | connected | `AgentInfo.Connected`、`LastHeartbeat`、`StreamFrom`、`KeyChangeRefusedAt` | `GET /api/v1/agents` |
| `agent.rules_received` | rule generation | `AgentInfo.Generation`、`AgentInfo.GenerationBehindSince` と応答の `generation` | `GET /api/v1/agents`、`GET /api/v1/rules` |
| `agent.credentials` | credentials | `AgentInfo.Warnings` | `GET /api/v1/agents` |
| `rule.target_resolve` | target resolve | `agent_rule_states[id].reason` の文言 | `GET /api/v1/rules` |
| `rule.target` | target | `agent_rule_states[id]` の `state`・`reason`・`at`・`connected`。UDP のルールの補足の行は `udp_replies[id]` | `GET /api/v1/rules` |
| `rule.flow_budget` | flow budget | `resource_refusals[id]`、`flow_budget` | `GET /api/v1/rules` |
| `rule.probe` | end-to-end probe | 疎通確認の `reach` と `detail` | `POST /api/v1/rules/{id}/check` |

引数を付けない実行は `GET /api/v1/rules` と `GET /api/v1/agents` の 2 回だけを呼び出す。ルールの本数によらず費用は変わらない。

`rule.target_resolve` だけは、今の観測では単独の検査として成立しない。エージェントが `target` のホスト名を自分で解決し、server はその結果を直接観測しないためである。この版は次の 5 つに分けて扱う。

- `target` が IP リテラルである: 解決する名前が無いので OK とする
- ホスト名で、接続中のエージェントの新しい報告が、名前解決の失敗と、直前の解決の結果で転送を続けていること(7b.2 節)の両方を示す文言を持つ: UNKNOWN とし、理由の符号は `target_resolve_failed` のままとする(2026-09-25)。解決の失敗は観測しているが、DNAT は直前のアドレスへ向いたまま残っており、転送の停止は観測していない。FAILED は転送の停止そのものを観測した検査にだけ使う(本節「検査どうしの優先順位」)。直前のアドレスが今も正しい宛先かどうかは server にもエージェントにも分からないので、判定に足りない UNKNOWN とする。今この報告を送るのは、カーネルモードのエージェントだけである。人向けの出力では `DEGRADED` と表示する(本節「`DEGRADED` の意味」)。所見は直前の解決の結果で転送を続けていることを述べ、次に見るものとしてエージェントのホストの名前の解決を示す。ルールの結論の行も、止まった位置ではなく、転送を続けていることと名前の解決を直すことを述べる。経路の上に他の UNKNOWN もあれば、結論の行は他の証拠が古いか確かめられていないことも併せて述べる
- ホスト名で、接続中のエージェントの新しい報告が名前解決の失敗を示す文言を持ち、前項に当たらない: FAILED とする。文言による判定なので確実ではなく、当てはまらない失敗は `rule.target` の誤りとして扱い、決めつけない
- ホスト名で、TCP のルールで、接続中のエージェントの新しい報告が `ok` である: OK とする。TCP のルールの `ok` は、エージェントがその `target` への接続を開けたことを意味する (5.2 節)。名前への接続は解決を経るので、その報告の時点で解決が成功したことを観測している。仮定ではなく観測であり、OK を実際に検証したものだけに使う規則を満たす。観測の時刻はその報告の時刻とし、古さの閾値は `rule.target` と同じ 90 秒とする。UDP のルールには同じことが言えない。UDP の `ok` はリスナーを開けたことしか意味せず、解決を伴わないためである
- それ以外: NOT TESTED とする。UDP のルールでホスト名を使う場合と、TCP のルールで報告が古いか、まだ 1 度も報告が無い場合が当たる。証拠がどちらにも無いのだから、古い証拠を指す UNKNOWN ではなく、そもそも試さない条件として扱う。解決を server が観測しないこと自体は出力に示し、試していない範囲の「エージェントのホストの環境」とも対応する

解決を単独の検査にするには前述の遠隔の診断が要る。

`rule.target` が FAILED になる場合の理由の符号も、`rule.target_resolve` と同じくエージェントの人が読む文言による判定であり、確実ではない(2026-09-24)。許可一覧の外の宛先を示す文言には `target_not_allowed`、エージェント自身のリスナーの bind が失敗したと分かる文言には `listener_bind_failed`、名前解決の失敗を示す文言には `target_resolve_failed`(`rule.target_resolve` と同じ符号を、こちらの検査にも当てる)、接続を拒まれた・時間切れ・到達できないことを示す文言にはそれぞれ `connection_refused`・`target_timeout`・`target_unreachable` を当てる。カーネルモードのエージェントが、自分のホストの `net.ipv4.ip_forward` が 1 でないために転送できないと報告する文言には `agent_ip_forward_off` を当てる (2026-09-25)。ループバックの宛先の `target_loopback_unsupported` (7b.3 節) と同じく、直す場所がエージェントのホストだと分かる場合を専用の符号に分ける。所見は、どのエージェントのホストの値かを名指し、次の一手は、そのホストで `sysctl net.ipv4.ip_forward` で値を確かめ、1 でなければ `sysctl -w net.ipv4.ip_forward=1` にすることと、そのホストの `agent doctor` の `host.forwarding` を示す。この符号は、値が 0 の場合のほか、エージェントが値を読めず書けもしなかった場合と、0 を読んで書けなかった場合にも付くので、所見は値を 0 と断定せず、書けない場合は再起動だけでは直らないことと、読み取り専用の `/proc` やコンテナの制限などの原因を除くことを述べる(2026-10-03)。旧い版のエージェントの理由にも、この案内は当てはまる。宛先のサービスを疑わせる既定の案内も、VPS の設定を疑わせる読み方も避けるためである。この変更の前の版のエージェントは、同じ事実を「this host」と書く文言で報告するが、同じ符号に分類する。エージェントがブロードキャストかマルチキャストの宛先を拒んだ文言には `target_not_unicast` を当てる(2026-10-03、7 節)。直す場所はルールの宛先であり、許可一覧に加えても通らないので、`target_not_allowed` と分ける。UDP のルールの `ok` に当てる `udp_listener_only` は本節前段のとおりである。どの文言にも当てはまらない場合は `target_error` とする。`target_error` は原因を判定できなかったことを表す既定の符号であり、宛先のサービス自体に問題があるとは限らない。

直前の解決の結果で転送を続けているという報告では、`rule.target` はその部分を除いた残りの文言で判定する(2026-09-25)。残りが無ければ、報告が `ok` であった場合と同じに扱い、TCP のルールは OK、UDP のルールは NOT TESTED の `udp_listener_only` とする。カーネルモードのエージェントは試し接続の誤りを理由の後ろに続ける(7b.2 節)ので、残りが無い TCP のルールの報告は、直前のアドレスへの試し接続が失敗していないことを示す。残りがあれば、前段の規則で残りの文言を分類し、FAILED とする。たとえば直前のアドレスの宛先が接続を拒めば `connection_refused` になり、そのルールは `target` で止まる。

#### 2 つの粒度

引数を付けない実行は、server、エージェント、全ルールを 1 行ずつで概観する。ルールを指定した実行は、その 1 本を公開側から宛先まで順に調べ、`Server`、`Tunnel`、`Agent` のまとまりごとに示す。

```
$ wgft server doctor r_01M2R009
r_01M2R009AA…  tcp 2456 to 192.168.1.50:2456

Server
  public port        NOT TESTED
                     serving tcp 2456; reachability from outside was not tested
                     Check: test it from another host: nc -vz <this vps> 2456
  dataplane          OK         the server's forwarding matches the current rules
Tunnel
  WireGuard          OK         handshake 32s ago
Agent "home"
  connected          OK         heartbeat 12s ago
  rule generation    OK         the agent reported generation 12, matching this server's generation;
                                applied State content is UNKNOWN because generations do not verify its contents
  target             FAILED
                     the agent could not use this rule: connection refused, last check 8s ago
                     Check: the tunnel and the agent are healthy up to this point. Check that a
```

FAILED の所見には必ず次に見るものを添える。エージェントが接続していない場合であれば「最後に観測したのは 12 分前である。エージェントのホストで `wgft agent doctor` を動かす」に当たる文を出す。

既定の表示には、nftables のチェーン、ソケット、世代、Backend の内部状態を出さない。これらは `--verbose` が追加する。

#### 能動的に試す範囲

既定は読み取りだけである。`--probe` を付けたときに限り、server から wg0 経由でエージェントのリスナーへ実際に TCP 接続する (10.1 節の疎通確認)。宛先の側にはデータを伴わない接続が 1 本届くので、運用者が明示したときだけ行う。`--probe` は 1 本のルールにしか付けられない。全ルールに対して能動的な確認を行うと、server 側の dial の期限 (既定 5 秒) がルールの本数だけ積み上がり、自宅の全サービスに同時に接続することになるためである。引数を付けない実行で `--probe` を渡した場合は、ルールを指定するよう求めて止める。

`--from <アドレス>` を付けると、その接続元がそのルールの拒否リストと許可リストを通るかを判定する。判定の順序は 5.3 節のとおり拒否が先である。付けない実行では `rule.source_filter` を NOT TESTED とし、通るとは言わない。

#### 経路の上の検査と経路の外の検査

ルールの総合判定は、転送の経路の上にある検査だけから決める。経路の上の検査とは、失敗や証拠の古さがそのまま「今このルールは転送していないかもしれない」を意味する検査である。`rule.enabled`、`agent.enabled`、`rule.public_port`、`rule.source_filter`、`server.dataplane`、`tunnel.handshake`、`agent.connection`、`agent.rules_received`、`rule.target_resolve`、`rule.target`、`rule.probe` が当たる。

`agent.credentials` と `rule.flow_budget` の 2 つは経路の外にある。どちらも server の起動からの累積の事実を述べるだけで、そのルールが今転送しているかどうかを述べない。Resource Guard の拒否は、深夜に一度フラッドを受ければ、その後は転送が完全に健全でも server を再起動するまで数え続ける。窃取の警告も、運用者が削除するまで残り続ける。これらを総合判定に混ぜると、一度の異常のあと要約が永久に下がったままになり、要約が健全なルールと壊れたルールを区別しなくなる。沈黙する診断と同じく、鳴りやまない診断も運用者から読まれなくなる。

したがって、この 2 つは所見としては必ず出し、次に何をするかも添えるが、ルールの総合判定と終了コードを動かさない。経路の外の検査は FAILED を返さない。転送が止まったという主張をしないためである。検査そのものの状態の意味は本節の表のままで変わらない。UNKNOWN は依然として「証拠はあるが判定に足りない」であり、変えたのは判定を積み上げる範囲だけである。

機械向けの出力では、この区別を今のところ項目として持たない。`rules[].status` は上の規則で計算した値をそのまま返すので、読み手が自分で積み上げ直す場合にだけ、経路の外の 2 つの `id` を上の一覧から除く必要がある。後から `id` ごとの項目として加えることはできる (加算は互換である)。

#### `agent.connection` が測るもの

`agent.connection` は、制御の経路の健全さと、新しい設定を配れるかどうかを測る。転送が止まった位置を測るのではない。両者は普段は一致するが、1 つの状態だけで食い違う。stream が切れていて、なお最終ハンドシェイクが新しい状態である。エージェントは受け取り済みのルールを保持したまま転送を続けられる一方、新しいルールだけが届かない (5.2、7 節)。

この状態を FAILED にすると、`agent.connection` は `rule.probe` より経路の順で前にあるので、疎通確認が実際にトンネルとエージェントを通って `target` まで届いた場合でも、「転送はここで止まった」と報告してしまう。同じ所見の文が「転送は続いている」と述べながら止まった位置を主張する、自己矛盾した報告になる。

したがって `ai.Connected` が偽のときを 2 つに分ける。

- 最終ハンドシェイクが新しい (`tunnel.handshake` の閾値の内側): UNKNOWN とする。理由の符号は `agent_disconnected` のままとする。stream が切れていること自体は確かであり、確かでないのはそれがこのルールの転送に与える結果だからである。所見は両方を述べる。制御の経路が切れていること、トンネルは生きていること、受け取り済みのルールは転送を続けているかもしれないこと、新しいルールは届いていないことである
- 最終ハンドシェイクが新しくない: FAILED のままとする。この場合は `tunnel.handshake` も FAILED であり、経路の順でそちらが先に来るので、ルールはトンネルで止まる。位置としてそれが正しい
- そのエージェントが登録されていない: FAILED のままとする。`tunnel.handshake` は SKIPPED になるので、`agent.connection` が最初の失敗として正しい
- 直近に鍵の変更の上限で宣言を断り、その後にそのエージェントの公開鍵の宣言を受け付けておらず、その記録が試みを続けるエージェントのものと読める (管理用 API の `key_change_refused_at` が、1 回分の戻る間隔とエージェントの再接続の待ちの上限の和より新しい。5.2 節): 理由の符号を `key_change_limited` とする (2026-10-02、所有者の決定)。状態は最初の 2 項と同じく、最終ハンドシェイクが新しければ UNKNOWN、新しくなければ FAILED とする。所見は、断った時刻と、その後に公開鍵の宣言を受け付けていないことを述べる。今も断り続けているとは述べない。受け取り済みのルールが転送を続けているかもしれないとも述べない。断った鍵はこの VPS の WireGuard のピアに入っていないので、稼働中の `rotate-key` のようにその鍵へ替えたエージェントは、鍵が通るまで転送できないためである。最終ハンドシェイクが新しくても、それはエージェントの前の鍵によるものでありうる。最終ハンドシェイクが新しい間を FAILED にしないのは、断った宣言が正規のエージェントのものかどうかを server が見分けられないためである。恒久トークンを持つ別の者が宣言した場合は、前の鍵のままのエージェントが転送を続けうる。次に見るものは、エージェントが同じ鍵で再接続を続け、1 回分が戻った後の試みで鍵が通ること、`rotate-key` を繰り返さないこと、`agent rotate-key --help` の戻し方である
- 前項の記録が、1 回分の戻る間隔とエージェントの再接続の待ちの上限の和より古い: 前項に当たらず、最初の 2 項の判定、理由の符号 `agent_disconnected`、原因と次に見るものをそのまま使う。所見には、断った時刻を過去の事実として 1 文だけ添える。記録は直近の拒否の時刻である。断られた試みは 1 回分を使わず、試みを続けるエージェントの記録は、試みのたびに新しい拒否で更新されるか、鍵が通って消える。エージェントは 5 分より長くは待たないので、試みを続けるエージェントの記録は、再接続の待ちの上限に 1 回の試みに要する時間を足した長さより古くならない。閾値に加えた 1 回分の戻る間隔の 10 分は、この判断に必要な長さではなく余裕である。閾値より古い記録は、エージェントの試みが鍵の判定まで届いていないことを示す。古い記録から今の拒否を述べないためである。余裕を持たせた分、断られた後に止まったエージェントについても、拒否から 15 分ほどの間は `server doctor` が `key_change_limited` を示し続ける (2026-10-02、所有者の決定)

`agent.connection` を経路の外の検査にはしない。本当に落ちているエージェントは、ルールの要約を動かさなければならないためである。UNKNOWN はそれを保つ。ルールは OK ではなく UNKNOWN になり、要約から消えない。同時に、転送が止まった位置だという主張だけを取り下げる。

この訂正は `agent.credentials` と `rule.flow_budget` と同じ種類だが、たどり着き方が違う。あの 2 つは今の経路をそもそも述べないので、経路の外に置いた。`agent.connection` は経路を述べており、ただ 1 つの食い違う状態でだけ述べ方を誤っていたので、その状態の判定だけを変えた。

人向けの出力では、この状態を `DEGRADED` と表示する(本節「`DEGRADED` の意味」)。機械向けの出力は変えず、`status` は `unknown`、`reason` は `agent_disconnected` のままとする。この検査の見出しは `connected` から `control connection` に改めた。`connected DEGRADED` は 1 行の中で矛盾して読めるためであり、状態の語ではなく対象の名前を見出しにした。

この結果として、stream が切れていてトンネルが生きているルールは、総合判定が UNKNOWN になり、終了コードは 0 になる。転送が止まったことを観測していない以上、監視を鳴らす根拠が無いためである。この区間は長く続かない。エージェントが本当に落ちていれば最終ハンドシェイクもやがて閾値を越え、`tunnel.handshake` が FAILED になって終了コードは 1 になる。区間の長さは `tunnel.handshake` の閾値で上から抑えられている。

#### `DEGRADED` の意味

`DEGRADED` は人向けの出力だけで使う語であり、転送の停止とは判定しないが、今の正常な状態から劣化していることは確かめている検査を表す(2026-09-25、所有者の決定)。劣化そのものは観測しているので、「判定に足りない」と読める `UNKNOWN` より、人には正確に伝わる。終了コードが 0 であっても、出力はこの劣化を黙らない。転送の停止は観測していないので FAILED にはせず、機械向けの `status` は `unknown` のままとし、状態は 5 つから増やさない。ルールの総合判定は UNKNOWN、終了コードは 0 である。

今この意味に当たる検査の例は次のとおりである。

- `agent.connection` の `agent_disconnected`:制御の経路は切れているが、トンネルは生きており、受け取り済みのルールで転送は続きうる(本節「`agent.connection` が測るもの」)
- `agent.connection` の `key_change_limited` のうち、最終ハンドシェイクが新しい場合:制御の経路は切れており、鍵の変更を断った記録が残っている。転送が止まったかどうかは、server の証拠からは決まらない(本節「`agent.connection` が測るもの」)
- `rule.target_resolve` の `target_resolve_failed` のうち、直前の解決の結果で転送を続けている場合:名前の解決は失敗しているが、DNAT は直前のアドレスへ向いたまま残っている(本節「検査の一覧と証拠の出どころ」)。同じ符号でも、直前の解決の結果を持たない場合は転送の停止を観測しているので FAILED であり、`DEGRADED` ではない

他の `unknown` は、証拠が古いか判定に足りないだけで劣化を確かめていないので、`UNKNOWN` のまま表示する。画面の語と JSON の値は、この意味の検査でだけ意図して食い違う。両方を並べて読む人が片方を誤りと判断しないよう、決定としてここに書き残す。機械は `status` と `reason` を読み、画面の語は人のためのものである(7a.11 節のとおり、人向けの表示は保証の対象ではない)。

#### 検査どうしの優先順位

所見が互いに矛盾しないよう、順序と扱いを次のとおり定める。

- ルールが無効なら、`rule.enabled` を SKIPPED にし、下流の検査もすべて SKIPPED にする
- ルールが有効で、持ち主のエージェントが無効(5.1 節)なら、`agent.enabled` を SKIPPED にし、理由の符号を `agent_disabled` とし、下流の検査もすべて SKIPPED にする。次に見るものは `wgft agent enable` である。無効なルールと同じく宣言どおりの状態なので、終了コードは 0 のままとする。ルール自身も無効なら、前項の `rule_disabled` を先に示す。`rule enable` と `agent enable` のどちらで直すかが違うので、`rule_disabled` を流用しない
- エージェントが登録されていないなら、`agent.connection` を FAILED にし、トンネルとエージェントに属する他の検査を SKIPPED にする。`agent.enabled` は、無効の印を持つ登録済みの行が無いので OK とし、既存の検査の結果、ルールの総合判定、終了コードを動かさない。この OK は観測に基づく。`agent.enabled` が答えるのは、そのルールを止める無効の印があるかどうかであり、server は無効の印の正本である自分のデータベースを読むので、エージェントが登録済みかどうかに関わらず、そのルールに無効の印が無いことを直接観測している。登録の有無は、この検査ではなく `agent.connection` が判定する。`rule.public_port` は FAILED `not_published` のまま、`agent.connection` は FAILED `agent_not_registered` のままである。Web UI はこれらのルールを灰色の「エージェント未登録」と示し故障に数えないが、`server doctor` は次のメジャー版まで今の結果を保つ。この違いは 7a.11 節の互換性の保証による意図したものである(5.1 節)
- エージェントの stream が切れている間は、そのエージェントが報告した値を今の値として扱わない (5.2 節)。`agent.rules_received` と `rule.target` は UNKNOWN とし、理由の符号を `stale_report` とし、人向けの出力では `agent ls` と同じ `last:` の接頭辞を付ける。古い宛先の誤りを今の原因として示さない
- 最終ハンドシェイクは server が WireGuard から直接読む今の値なので、stream が切れていてもトンネルの判定に使う。エージェント自身のトンネルの報告は履歴として添えるにとどめる
- stream が切れていてトンネルが生きている間は、`agent.connection` も UNKNOWN とする。理由は前項のとおりである
- 「転送は止まった」と読む位置は、経路の順で最初に FAILED になった検査である。したがって FAILED は、その検査が転送の停止そのものを観測した場合にだけ使う

#### 切り分けられない所見

VPS の側からは原因を 1 つに決められない所見がある。決めつけずに、切り分けられない原因を並べ、何をすれば決まるかを示す。最終ハンドシェイクが無いことには、少なくとも次の 4 つの原因がある。この VPS の WireGuard の UDP ポートがエージェントの回線から届かないこと。自宅のファイアウォールまたは ISP がトンネルの UDP を落としていること。エージェントが動いていないか、別の鍵を持っていること。その間の何かが落としていること。決めるにはエージェントのホストで確かめる必要があり、出力はそのとおりに示す。

#### 試していない範囲

何も壊れていない実行でも、試していない範囲を必ず出力する。黙っていると運用者が沈黙を健全と読むためであり、沈黙する診断は無いほうがましである。次のうち最初の 8 項目は常に出し、最後の「内側の経路」だけは条件に応じて出す。

- 外から公開ポートへの到達: DNAT は外部からの入力にしか効かないので、`vpsd` は自分の公開ポートに自分から到達できない (10.1 節)。見えない原因は、事業者のセキュリティグループ、このホストの input のファイアウォール、ISP、そしてユーザー空間モードでエフェメラルポートの範囲に入った待ち受けポート (docs/setup.md) である。別のホストから試すよう示す。試し方はプロトコルで分ける (2026-09-25)。TCP のポートには `nc -vz` を、UDP のポートには実際のクライアントを示す。`nc -u` のような UDP の送信は届いたかどうかを知らせないので、正常な UDP のルールも届かないように見えるためである。`rule.public_port` の次の一手も同じ分け方をし、UDP のルールでは、宛先が応答すれば `rule.target` の補足の行に server が見た応答の時刻が出ることを添える
- UDP の端から端まで: 疎通確認は TCP だけである。UDP の送信では成否が分からないため、UDP のルールは静的な信号だけで判定する。エージェントがリスナーを開けたと報告している間も、`rule.target` は OK にならず NOT TESTED にとどまる。server が見た宛先の応答を補足の行に示しても、状態は変わらない(本節「UDP の応答の観測」)
- MTU とフラグメント: ハンドシェイクが成立し小さなパケットが通るトンネルでも、大きなデータグラムだけが失われることがある。「ときどき動く」と言われる故障がこれに当たる
- 負荷に依存する故障: レート制限、フロー予算、conntrack の表は、ある瞬間の値しか読まない。負荷のときだけ達する上限は現れない
- 宛先の先にあるサービス: どの確認も接続して閉じるだけで、プロトコルで対話しない。ポートは受け付けるがアプリケーションが拒む場合、満員の場合、別のサービスである場合は、健全に見える
- 片方向だけのトンネルの故障の最初の 3 分: 受信が止まったトンネルも、最終ハンドシェイクは `tunnel.handshake` の閾値のあいだは新しいままである
- 適用済み State の内容: 世代番号が一致しても、エージェントが server の公開した State と同じ内容を適用したかどうかは UNKNOWN である。現在の通信には内容の確認が無い
- エージェントのホストの環境: OS、権限、インタフェース、名前解決は、ハートビートが運ぶ範囲しか見えない。自宅側の診断を動かすよう示す
- 内側の経路: `--probe` を付けない実行は何も dial しない。この項目が外れるのは、`--probe` を付けた実行と、診断の対象がすべて UDP のルールである実行の 2 つである。後者は、UDP のルールが `--probe` を付けても管理用 API に確認そのものを拒まれ、この項目の案内が意味を持たないためであり、同じ一覧の「UDP の端から端まで」が同じ事実を既に述べている。1 本でも TCP のルールが混じっていれば、そのルールには `--probe` が意味を持つので出す

さらに、server 自身の観測の古さを常に示す。エージェントについて読む値はすべてハートビート経由で届くので、最大で 1 周期ぶん古く、転送しているエージェントが切断と表示される区間も実在する。

#### 履歴

この版は履歴を持たない。診断のために保存の仕組みを追加することはしない。出力はその事実を明示する。

```
History
  when it broke      NOT AVAILABLE
                     this command only evaluates the current state. To find when a rule stopped
                     working, read the server log and the agent's log.
```

他の目的で実際に履歴を保存するようになった場合に限り、「最後に健全だった時刻」と「最初に異常を観測した時刻」へ育てる。

#### 機械向けの出力

`--json` はこの版から持つ。出力は人向けの表の写しではなく、診断そのものの模型である。形は次のとおりである。

```json
{"status":"failed","checked_at":"...","probed":false,
 "checks":[{"id":"agent.connection","status":"ok","observed_at":"..."},
           {"id":"rule.target","rule_id":"r_01J...","status":"failed","reason":"connection_refused"}],
 "rules":[...],"history":{...},"not_tested":[...]}
```

検査の `id` と `reason` の値は、公開した時点で機械向けの保証になる。7a.11 節の規則に従い、開いた集合として扱う。項目を増やすことだけができ、既存の `id` の名前の変更も意味の変更も互換ではない。読み手は知らない `id` を読み飛ばし、知らない `reason` を「不明」として扱わなければならない。v1 が定める `id` は前掲の表のとおりである。`status` の 5 つの値は本節の表のとおりで、これも増えうる開いた集合とする。`group`・`label`・`detail`・`next` は人向けの文であり、保証の対象ではない。

#### 終了コード

このコマンドの終了コードは次のとおりである。

| コード | 意味 |
|---|---|
| 0 | FAILED の検査が 1 つも無い |
| 1 | FAILED の検査が 1 つ以上ある |
| 2 | 報告を作れなかったか、診断に必要な証拠に権限で到達できず完全な判断ができなかった。管理用 API が応答しない、指定したルールが無い、`--from` の値が読めない、引数の数が誤っている、知らないフラグを渡した場合が当たる (2026-09-23、所有者の決定) |
| 3 | 設定の誤り (11a 節) |

終了コード 2 の意味は `agent doctor` (10.2c 節) と揃えて広げたが、`server doctor` が読む証拠のほとんどは管理用 API への呼び出しが成功するか失敗するかの二値であり、権限によって証拠に部分的にしか届かない場合を今は持たない。唯一の例外は `--probe` である。`c.CheckConnectivity` の誤りは `unavailable` に包まず `probeResult` へ畳み込み、報告そのものは出す (`cmd/wgft/doctor.go`)。この経路でも権限の事例は作らないので、この改訂で挙動は変わらない。

UNKNOWN と NOT TESTED だけでは 0 のままとする。外からの到達性を決して試さない以上、これらを非零にすると監視が鳴り続けるためである。この規則は終了コード 2 にも及ぶ。UNKNOWN と NOT TESTED がいくつ並んでも終了コードは 0 のままであり、終了コード 2 は証拠そのものに権限で到達できなかった実行に限る。

終了コードが答える問いを 1 つに保つため、次を規則として定める。

> 制御の経路の故障だけでは `server doctor` を失敗にしない。今の転送の経路が健全だと確かめられている限り、制御の経路の故障は運用上の劣化であり、転送の故障ではない。劣化は状態とエージェントのサーフェスが報告する。

この規則を置く理由は、終了コードに 2 つの意味を混ぜないことにある。終了コードが「転送が止まった」と「管理の経路が壊れた」の両方を指すようになると、それを見ている側はどちらが起きたのかを区別できない。責任は次のように分ける。

- `server doctor`: このルールの転送の経路が壊れているかどうかに答える
- `wgft status`: 配置全体の運用の状態が健全かどうかに答える。制御の経路が切れている状態は、そこでは配置全体の劣化として終了コードを動かす。この関係を 10.2b 節が実装として定める
- `wgft agent ls`: エージェント 1 台ごとの詳細を担う

引数の数の誤りとフラグの誤りも 2 で終わる。どちらも診断そのものを始められなかった失敗であり、「壊れた検査があった」の 1 と混ぜると監視から見分けが付かなくなるためである。包む場所は 2 か所ある。引数の数は引数を検査する関数が、フラグはフラグの誤りを扱う関数が包む。フラグの解析は引数の検査より前に行われるので、片方だけでは入口の違いで終了コードが分かれる。

11b 節との関係を明示する。11b 節が定めるのは、監督するプロセスに起動の失敗を伝える意味論であり、終了コード 3 だけが起動の拒否に対応する。`server doctor` は常駐しないので、0 と 1 と 2 は起動の失敗とは別の層の値である。実装では、起動の拒否を表す `*startup.Refusal` に加えて、報告を作れなかったことを表す型を 1 つだけ持ち、`cmd/wgft` の `exitCode` はこの 2 つの型の有無だけを見る。新しい失敗を足すときの写し忘れを防ぐ 11b 節の考え方は変えない。

#### `--report` の設計上の約束

`--report` は、GitHub の Issue にそのまま貼れる形を出す将来の選択肢である。この版では実装しないが、後から加えるときに出力の形を変えずに済むよう、原則を先に定める。`--report` は許可一覧であり、伏せ字ではない。内部の構造をそのまま直列化してから秘密を取り除く形にはしない。報告専用の型 (版、OS、モード、エージェントの状態、ルールの状態など) を明示的に埋める形にし、後から加えたフィールドが既定で漏れるのではなく既定で現れないようにする。今の診断が読む値には、秘密鍵も恒久トークンも接続文字列も含まれない。管理用 API のうち診断が呼び出す 3 つの節点がそれらを返さないためである。
