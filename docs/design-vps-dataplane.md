## 6. データプレーン(VPS 側)

### 6.1 カーネルモード

`vpsd` は `table inet wgft` を自分専用に持ち、ルール変更のたびにテーブル全体を 1 トランザクションで差し替える。
他のテーブルには一切触れない。
conntrack のエントリは差し替えの影響を受けないので、既存のセッションは切れない。

接続元制限とレート制限は nat ではなく filter の prerouting に置く。
nat のチェーンはフローの最初のパケットしか通らないので、そこに置いた `drop` は通信中のフローに効かないためである。

```
table inet wgft {
  set deny_1  { type ipv4_addr; flags interval; elements = { 203.0.113.0/24 } }
  set meter_1 { type ipv4_addr; flags dynamic; timeout 1m; size 65535; }
  # 接続元 IP ごとの同時フロー数の上限(7 節の設定値。既定は次の例のとおり UDP 256、TCP 128)。
  # プロトコルごとに 1 つで、そのプロトコルの全ルールが共有する。値を 0 にしたプロトコルには
  # 作らない。timeout は持たせない(ct count と組み合わせると nftables が拒む)
  set flows_udp { type ipv4_addr; flags dynamic; size 65535; }
  set flows_tcp { type ipv4_addr; flags dynamic; size 65535; }
  # source_allow が空でないルールなら、次の set と行が加わる(空なら生成しない。空の set に != を書くと全送信元が落ちる)
  #   set allow_1 { type ipv4_addr; flags interval; elements = { ... } }
  #   iifname != "wg0" udp dport 2456-2457 ip saddr != @allow_1 counter drop

  chain filter_pre {
    type filter hook prerouting priority -150; policy accept;
    iifname != "wg0" udp dport 2456-2457 ip saddr @deny_1 counter drop
    iifname != "wg0" udp dport 2456-2457 ct state new add @meter_1 { ip saddr limit rate over 10/second } counter drop
    iifname != "wg0" udp dport 2456-2457 ct state new add @flows_udp { ip saddr ct count over 256 } counter drop
    # 送信元を読まない集約のレートの行も IPv4 のパケットにだけ一致させる(7a.9 節)。無いと IPv6 のパケットがトークンを使う
    iifname != "wg0" udp dport 2456-2457 ct state new meta nfproto ipv4 limit rate over 100/second counter drop
    # packet_rate を設定したルールの場合(5.3 節の例は null なので、実際には生成しない)
    iifname != "wg0" udp dport 2456-2457 meta nfproto ipv4 limit rate over 5000/second counter drop
    iifname != "wg0" tcp dport 25565 ct state new add @flows_tcp { ip saddr ct count over 128 } counter drop
  }
  chain nat_pre {
    type nat hook prerouting priority dstnat - 1; policy accept;
    iifname != "wg0" udp dport 2456-2457 dnat ip to 10.200.0.2
    iifname != "wg0" tcp dport 25565 dnat ip to 10.200.0.2
  }
  chain input {
    type filter hook input priority filter - 10; policy accept;
    iifname "wg0" ct state new drop
  }
  chain forward {
    type filter hook forward priority filter - 10; policy accept;
    iifname "wg0" oifname "wg0" drop
    oifname "wg0" ct status dnat accept
    # UDP のルールがあるときだけ置く(本節の UDP の応答のカウンタの項目)
    iifname "wg0" meta l4proto udp ct direction reply ct status dnat jump udp_reply
    iifname "wg0" ct state established,related accept
    iifname "wg0" drop
    oifname "wg0" drop
  }
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "wg0" ct status dnat masquerade
  }
  chain udp_reply {
    udp sport 2456-2457 counter return comment "wgft:<ルール ID>:reply"
  }
}
```

- 評価順は deny、allow、接続元ごとの meter、接続元ごとの同時フロー数の上限、新規フローの集約上限、パケットの集約上限、DNAT の順。`allow` が空のルール、`packet_rate` が未設定のルールでは対応する行を生成しない。`packet_rate` は UDP のデータグラムだけに効くので、TCP のルールでは値が設定されていてもパケットの集約上限の行を作らない(7a.9 節「TCP の packet_rate」)
- 判定の行を付けるポートは、カーネルモードのルールのポートと、`vpsd` が待ち受けを開けているプロキシモードのルールのポート(6.2 節)である。どちらのポートにも同じ段の行を同じ順で付ける。プロキシモードのルールの拒否も、そのため nftables で行われる
- set 名はルール ID ではなく `vpsd` が振る連番を使う。古いカーネルの set 名の長さ制限(32 文字)を避けるためである。連番は判定の行を付けるポートの順に振るので、プロキシモードのルールも連番を進める
- meter は集約上限より前に置く。送信元を偽装したフラッドで meter の set が `size` まで埋まると、その間は `add` が失敗して接続元ごとの制限だけが外れ、集約上限で守る状態になる。順序を入れ替えれば set は埋まらないが、単一の乱用者が集約枠を食い尽くしてから接続元ごとの制限が評価される順になり、正規利用者を守る目的を失うので、この順序と劣化の仕方を採る
- 接続元 IP ごとの同時フロー数の上限は、7 節の設定値(`WGFT_MAX_UDP_FLOWS_PER_SOURCE`、`WGFT_MAX_TCP_FLOWS_PER_SOURCE`。既定 UDP 256、TCP 128)をカーネルモードにも適用する。値が 0 のプロトコルには `flows_udp` / `flows_tcp` の set も対応する行も生成しない。`flows_udp` と `flows_tcp` はプロトコルごとに 1 つだけ作り、そのプロトコルの有効なルールすべてが同じ set を使う。プロキシモードのルール(6.2 節)は DNAT を持たないが、`vpsd` が待ち受けを開けている場合に限り、この上限の行も Admission Policy の他の段の行も持ち、この上限はカーネルモードのルールと同じ `flows_tcp` で数える。bind に失敗したポートに行を置くと、同じポートで待ち受ける別のプロセスへの通信に wgft の上限を掛けてしまうためである。適用は 2 段で行う。まず新しい待ち受けだけを開き、旧い待ち受けは閉じずに残す(新しい待ち受けはまだ中継しない)。次に、残る待ち受けと新しく開けた待ち受けのポートだけを行の対象にして nftables を差し替える。差し替えが失敗したら新しい待ち受けを閉じ、旧い待ち受けと旧いテーブルを揃えたまま残す。成功したら新しい待ち受けで中継を始め、宣言から消えた待ち受けを閉じる。こうすると、差し替えの失敗で、閉じた待ち受けの行だけがテーブルに残ることも、開いた待ち受けに行が無いこともない。SQLite には新しいルールが入ったまま差し替えだけが失敗した場合、宣言と実際の転送が食い違うが、次の適用(次のルールの変更、`vpsd` の再起動、30 秒ごとの再試行。7a.3 節)で収束する。起動時も同じ手順で、bind に失敗したポートは次の適用で開き直し、開けたときに行が付く。`vpsd` の中継の側では接続元ごとに数えない(数えると二重になる)。set の要素は送信元 IP だけをキーにするため、複数のルールが同じ送信元から `add` しても `ct count` は 1 つの値に合算され、これが「全ルールの合計」を成立させる。ルールごとに別の set を作ると合計にならないので、共有が要件である
- この上限も `ct state new` の一致条件を持つ行にする。既存のフローの継続パケットは `ct state new` に一致しないため素通りし、既存のフローを追い出すことはない。meter と同じ理由(前項)で集約上限より前、meter と同じ並びに置く
- `ct count` を使う set には timeout を持たせない。timeout を持つ set に `ct count` を組み合わせると、カーネルが `Operation not supported` で規則を拒む(ラボで確かめた)。要素は conntrack のエントリに従って消える。TCP は接続を閉じた後、UDP は conntrack のエントリが消えた後に、送信元の要素が set から消えることをラボで確かめた
- set が `size`(65535)まで埋まると、meter と同じく新しい送信元の `add` が失敗し、その間は接続元ごとの上限だけが外れて集約上限に委ねる劣化になる。UDP の meter は短命なトークンバケットの状態を都度作るのに対し、この set の要素は生きた conntrack のフローに紐付くため、埋めるには実際にそれだけのフローを維持する必要があり、埋めにくい
- UDP の `ct count` は conntrack のエントリ数を数えるため、7 節で述べた `udp_timeout` / `udp_timeout_stream` とエージェント側のセッションタイムアウトの非対称の影響を受ける。エージェントがセッションを閉じた後も、そのぶんの conntrack エントリが `udp_timeout` の間は数に残ることがある。既存の非対称と同じ許容範囲とする
- テーブルの差し替えは `flows_udp` と `flows_tcp` を作り直す。差し替え前から続くフローは新しい set の数に入らないので、その送信元は差し替えの後にさらに上限まで新しいフローを開ける。ラボで、TCP の 128 本を保持したままルールを 1 本足すと、同じ送信元から新しい接続がさらに通った。この超過は差し替え前のフローが閉じるまで続く。差し替えは、管理者のルールの変更、`vpsd` の起動、wgft の外で変えられたテーブルやインタフェースの公開し直し(7a.3 節)のほかに、エージェントの登録と公開鍵の変更(5.2 節)でも起きる。ピアの変更もトランザクションの一部で、トランザクションはテーブルの全体を差し替えるためである(7a.3 節)。公開鍵の変更は、そのエージェントの恒久トークンの持ち主が起こせるので、攻撃者から起こせない差し替えとは言えない。差し替えはテーブルの全体に及ぶので、鍵を変えたエージェントのルールだけでなく、全エージェントのルールの meter と `flows_udp`/`flows_tcp` が作り直される。超過は 1 回の差し替えにつき上限 1 つ分で、差し替えを重ねると重なる。ラボで、別のエージェントが鍵を変えるたびに、同じ送信元が上限 1 つ分ずつ多くの TCP のフローを保持できた。恒久トークンの持ち主が起こせる差し替えの回数は、5.2 節の鍵の変更の頻度の上限で抑える。この上限と、エージェントのルールごとの上限(7 節)がその外側で効くので、許容する。set を差し替えの対象から外すには上限の行を別のテーブルに分ける必要があり、差し替えの原子性を失う。ピアだけを変えるトランザクションでテーブルを差し替えない形は 13 節に残す
- 落としたパケットのカウンタは、ほかの行と同じ `wgft:<ルール ID>:src_flow` という形式のコメントを付け、既存の drop カウンタと同じ経路(本節の最後の項目)でルールごとに累積する。上限は全ルールで共有するため、この累積値は「そのルールの行が拒んだ回数」であり、送信元がどのルールで最初に上限へ達したかを示す近似値になる
- `ct count` は nftables 0.9.0 と Linux カーネル 4.19.10 以降が必要である(nftables wiki の記述による)。対応する最小構成の Debian 12(kernel 6.1、nftables 1.0.6)のラボで動作を確かめた
- DNAT では宛先アドレスだけを書き換え、ポートは書き換えない。エージェントは VPS と同じポートで待ち受け、`target` のポートへの写し替え(5.3 節の連番)はエージェント側で行う(7 節の実効宛先)
- 公開インタフェース名を特定せず `iifname != "wg0"` で書く
- nat prerouting の優先度を `dstnat - 1` にして、既存の nat チェーンより先に評価されるようにする。先に評価されるのは標準の優先度(`dstnat`。iptables の nat、firewalld、Docker が使う)のチェーンに対してだけで、それより小さい優先度(-199 まで付けられる)のチェーンには負ける。そのため後述の「他テーブルの同じポートの DNAT」の検査は優先度に関係なく行う
- input で wg0 からの新規接続を全部落とす。`vpsd` が wg0 上で待ち受けないので(4 節)、VPS 上の他サービスが wg0 から見える経路をここで塞ぐ
- forward では、先頭でピア同士の通信を遮断し、DNAT 済みのフローとその返りを通した後、wg0 が絡む残りの転送をすべて落とす。対象は wg0 から VPS の他のインタフェース(private NIC、別の VPN)へ出るフローと、他のインタフェースから wg0 へ入る DNAT 以外のフローである。これにより、既存のファイアウォールの forward が accept のままの VPS でも、認証情報を盗んだピアが VPS の内側のネットワークへ届かない。wg0 が絡まない転送には触れない
- masquerade は DNAT された接続に限定し、VPS 自身の通信には触れない
- UDP のルールごとに、応答のカウンタの行を通常のチェーン `udp_reply` に 1 つ置く(10.2a 節「UDP の応答の観測」)。forward の入口の行が、wg0 から戻る DNAT 済みの UDP の応答だけを `udp_reply` へ送るので、他のパケットは 1 行の評価で抜ける。`udp_reply` の行は応答の送信元ポートでルールを見分ける。DNAT はポートを書き換えず、forward の時点では応答の送信元の逆変換(postrouting で行う)がまだ済んでいないので、送信元ポートは公開ポートのままである。行が持つ判定は、入口のチェーンへ戻る `return` だけであり、転送の結果を変える判定を持たない。wg0 から戻る UDP の応答は、パケットごとに `udp_reply` の行を順に評価する。行は UDP のルールごとに 1 つなので、この費用は UDP のルールの数に比例し、公開側から入るパケットがルールごとの判定の行を評価する既存の費用と同じ桁である。この費用が問題になれば、送信元ポートから名前付きのカウンタを引く map にすれば、ルールの数に依らない 1 回の検索にできる。宛先が返す ICMP の誤りは同じ conntrack のエントリの応答の向きに一致するが、`meta l4proto udp` で外す。コメントは `wgft:<ルール ID>:reply` とし、drop の行とは別のチェーンに置くので、次の項目の drop の累積に混ざらない。カウンタは差し替えで 0 に戻るので、drop のカウンタと同じく差し替えの直前に読む。UDP のルールが無ければ、チェーンも入口の行も作らない
- 各 drop のカウンタは、テーブル差し替えの直前に `vpsd` が読み、差し替えが成功したときだけ SQLite に累積する。差し替えが失敗すると旧いテーブルがカウンタを持ち続けるので、次の成功した差し替えの直前にもう一度読まれ、1 回だけ累積される(7a.2 節)。commit の後の応答の受信に失敗した場合(6.1 節の受信側の壁)と、差し替えの後の送信元の一覧の set の検査(本節)に失敗した場合だけは、テーブルが差し替わった後で失敗と判断するので、その回に読んだ分は累積されずに失われる。meter の状態は差し替えでリセットされるが、短時間のすり抜けにとどまるので許容する

テーブルの差し替えは、nftables のバッチ 1 つ、つまり netlink のデータグラム 1 つとして送る。カーネルの `nfnetlink_rcv_batch` は 1 つの skb の中だけでバッチを読むので、`NFNL_MSG_BATCH_BEGIN` から `NFNL_MSG_BATCH_END` までを複数のデータグラムに分ける余地は無い。差し替えの不可分性はこの 1 つのデータグラムが担う。大きなルール集合をデータグラムごとに分ける案は、分けた時点で別のトランザクションになるので採らない。

そのため、バッチ自身の長さと、カーネルが返す応答の量の両方が、1 つの netlink ソケットのバッファに収まらなければならない。応答は 2 種類ある。バッチの 1 通ごとに返る ACK と、ルールの追加に立つ `NLM_F_ECHO` に対するルールの写しである。`vpsd` はバッチを送り終えてから応答を読み出すので、応答は受信キューに積み上がる。既定のバッファのままだと、ルール数を増やしたときに 2 つの壁に当たる。

- 受信側の壁:応答が `sk_rcvbuf` を超えると、カーネルは ENOBUFS を立てて応答を捨てる。応答はバッチの commit の後に送られるため、テーブルは差し替わっているのに `vpsd` は失敗と判断する
- 送信側の壁:バッチの長さが `sk_sndbuf` を超えると、sendmsg が EMSGSIZE で拒む。カーネルには何も届かないので、旧いテーブルがそのまま残る

`vpsd` はテーブルを組み立てながらバッチのメッセージ数と長さを数え、送る直前に、その大きさに合わせた送信側と受信側のバッファを要求する。受信側には 1 通ごとの ACK の分を上乗せする。要求する値の下限は 1 MiB、上限は 64 MiB である。`nft` コマンドも同じ手順を取り、バッチの長さと命令の数からバッファを決めてから 1 回の sendmsg で送る。

要求は `SO_SNDBUFFORCE` と `SO_RCVBUFFORCE` で行い、権限が足りなければ `SO_SNDBUF` と `SO_RCVBUF` に落ちる。前者は init の user namespace での CAP_NET_ADMIN を必要とする。`deploy/server.service` はこの権限を与えるので、systemd から動かす VPS では要求が通る。user namespace を分けた非特権のコンテナは、自分の netns の nftables を操作できても FORCE の側は拒まれ、`SO_SNDBUF` と `SO_RCVBUF` に落ちる。落ちた配置では `net.core.rmem_max` と `net.core.wmem_max` の 2 倍が上限になり、壁は既定の 2 倍ほど遠のくだけで残る。ラボでは `unshare --user --map-root-user --net` の中でカーネルモードの `vpsd` を動かして確かめた。WireGuard のインタフェースの作成、`net.ipv4.ip_forward` の書き込み、テーブルの適用は通る。両方の sysctl が既定の 212992 のとき、1 回の `rule import` は 120 本まで適用でき、125 本で ENOBUFS になり、500 本からは EMSGSIZE になった。両方を 8388608 にすると 2000 本まで適用できた。この 2 つの sysctl は network namespace ごとの値ではなく、ホスト全体で 1 つである。分けた namespace の中での見え方はカーネルによって違う。Debian 12 のカーネル 6.1 と Ubuntu 24.04 のカーネル 6.8 では、分けた namespace の中の `/proc/sys/net/core` に現れない。Ubuntu のカーネル 6.17 と Fedora 44 のカーネル 7.2 では、初期の network namespace の値が読み取り専用で現れ、root が書き込んでも拒まれる。6.8 と 6.17 は非特権の Incus のコンテナで確かめ、6.17 のコンテナに現れる値はホストの値の変更をそのまま追った。6.17 のコンテナの root が実行した `sysctl -w` は `Invalid argument` を表示したが、終了コードは 0 だった。どのカーネルでも、値を変えられるのは初期の network namespace の側だけである。文書にある配置で当てはまるものは無い。コンテナの配置はユーザー空間モードだけを対象にしている(`deploy/server.compose.yaml`)。

確かめた範囲は Debian 12 のラボである。1 回の `rule import` による 1000 本と、1 本ずつの `rule add` による 1000 本のどちらも適用でき、10 本から 1000 本までのすべての段で転送が通った。適用だけなら 2000 本まで通った。2000 本を超える規模は確かめていない。

この壁で適用が失敗したときの意味論は、他の差し替えの失敗と同じである。失敗した世代は active にならない。ENOBUFS の場合は実際のテーブルだけが新しい世代に進むので、`vpsd` が持つ active な世代と食い違う。この食い違いは 7a.3 節の「実際の状態への収束」が拾い、`Observe` がテーブルの指紋の違いを drift として報告し、次のトランザクションを起こす。ただし、そのトランザクションが公開し直すのは Desired であり、直前に成功していた世代ではない。Desired が壁を越える大きさのままなら、公開し直しは同じ壁で同じ失敗を繰り返す。繰り返しに終端は無く、運用者が Desired を小さくするか、バッファの上限を引き上げるまで続く。食い違っている間も、DNAT の宛先のエージェントが新しいルールを受け取っていないため、新しい世代のポートへの転送は通らない。新しい宣言にも同じ内容で残っているルールの転送は続く。新しい宣言から外れたルールの転送は、テーブルが既に差し替わっているので続かない(改訂の記録 2026-09-23)。

繰り返しの間、運用者から見える手掛かりは薄い。`vpsd` は同じ文言の誤りを繰り返し出さないので(7a.3 節)、ログは最初の 1 行で止まる。`wgft rule ls` の表は適用の状態を持たないため、何も異常を示さない。食い違いが出たことを示すのは、`rule ls --json` の `active_generation` と `desired_generation` の差、`rule_states` の `apply_state`、および Web UI の「反映待ち」の表示である。drift を見つけた後は、宣言の変わっていないルールも含めて `apply_state` が `pending` になる。カーネルへの通知を受け取るソケットも同じ受信側の壁に当たりうるので、繰り返しを進めるのは主に 30 秒ごとの再試行である。

起動時の最初の適用(9 節)が同じ壁に当たった場合の扱いは、稼働中の再試行とは違う。起動時の最初の適用が失敗しても、プロセスは終了しない。管理用 API だけを開いて起動の残りを止め、30 秒ごとに適用を試し直す(11b 節の起動の保留)。運用者は `wgft rule rm` か `wgft rule disable` で Desired を小さくでき、適用が成功した時点で起動の残りに進む。2026-09-22 まではこの失敗が終了コード 1 で終わり、管理用 API がこの適用より後に開くために回復の経路そのものが失われていた。

送信元の一覧(`source_deny`、`source_allow`)の set の要素は、1 通の `NFT_MSG_NEWSETELEM` にまとめずに、複数の通に分けて同じバッチで送る。1 通の要素は `NFTA_SET_ELEM_LIST_ELEMENTS` という 1 つの入れ子の属性に入る。netlink の属性の長さは 16 ビットなので、この属性は 65535 バイトを超えられない。依存する google/nftables と mdlayher/netlink は超えたことを検査せず、長さの下位 16 ビットだけを書く。カーネルはその短い長さの分だけを要素として読むので、要素の欠けた set が誤りなく公開される(改訂の記録 2026-09-24)。`vpsd` は 1 通の要素の一覧を 32 KiB 以下にし、区間の開始と終端の印を同じ通に入れる。分けた通も同じバッチの中にあるので、差し替えの不可分性は変わらない。set には大きさ(`NFTA_SET_DESC_SIZE`)を付けないので、カーネルは要素の数を制限しない。

差し替えの後、`vpsd` は送信元の一覧の set をカーネルから読み直し、送った要素と比べる。要素の数か中身が違えば、その差し替えを backend 全体の失敗とする(7a.3 節)。テーブルは既に差し替わっているので、扱いは受信側の壁の ENOBUFS と同じである。失敗した世代は active にならず、読み直したテーブルを `Observe` の基準にもしない。差し替わったテーブルは drift として報告され、公開し直しが同じ検査で失敗を繰り返す。繰り返しの間隔は、30 秒を上限に失敗のたびに倍になる(7a.3 節の再試行)。この間は要素の欠けた set が転送に効いている。`source_deny` が欠ければ拒むはずの送信元が通り、`source_allow` が欠ければ許すはずの送信元が落ちる。要素を分けて送る組み立てでは、この食い違いは起きない想定である。読み直しは、同じ種類の取りこぼしが別の経路で起きた場合に、それを成功として扱わないための検査である。運用者には、他の backend 全体の失敗と同じく、`apply_error` とルールの `pending` の理由で示す。どちらも食い違った set の名前と、読み直した set の要素の数と送った数を含む。この数は一覧の CIDR の数ではなく、区間ごとの開始と終端の印を数えた set の要素の数である。

`vpsd` は起動時に `net.ipv4.ip_forward` を確認し、1 でなければ 1 にする。
これは firewalld や nftables の設定ではなくカーネルの sysctl で、Docker や firewalld(masquerade を使うゾーン)も同じように 1 にする。転送する以上ここに正しい値は 1 の一つしかなく、他に異論を持つ主体がいない設定なので、ポート開放や `policy drop`(提示だけして触らない、後述)と違い `vpsd` 自身が設定する。手順は次のとおり。

- まず現在値を読む。すでに 1 なら何も書かない。
- 0 なら 1 にし、書けたことをログに残す(起動のたびに黙って上書きしない)。
- 書き込みに失敗しても `vpsd` は落ちない。読み取り専用の `/proc` や seccomp/LSM で `/proc/sys` への書き込みが塞がれていても、値がすでに 1 なら問題なく動く。0 のまま書けない場合は、`policy drop` の提示と同じ流儀で「`net.ipv4.ip_forward=1` にせよ」という警告を残して起動を続ける。
- 値を読めず、書けもしない場合は、0 とは言わず、読めなかった誤りと書けなかった誤りの両方を示す警告にする(2026-10-03)。値が分からないので、転送が動かないかもしれないことと、`sysctl net.ipv4.ip_forward` で値を見て 0 なら `sysctl -w net.ipv4.ip_forward=1` にする手順を案内する。起動は続ける。
- この警告は他テーブルの `policy drop` の提示と同じ起動時 Findings として UI とログに出し、単なるログ 1 行にとどめない。カーネルモードのルールが 1 つも無いとき(プロキシ専用やルール 0 件)も同じ警告を出す。Findings は起動時に 1 回だけ作り、ルールは起動後に追加できるので、起動時の件数で警告を弱めると、追加した時点で転送が動かない理由が見えなくなるためである。
- いったん 1 にした値を 0 に戻すことはない。
- 稼働中に外から 0 にされた値を、`vpsd` は 1 に戻さない (2026-09-25、所有者の決定)。1 にするのは起動時だけである。理由は 3 つある。第 1 に、稼働中に 0 にするのは運用者か、運用者が置いた sysctl の設定や堅牢化のスクリプトの明示の操作であり、`vpsd` が黙って書き戻すとその操作と争う。第 2 に、sysctl の変更には通知が無いので、戻すには定期的な読み取りと書き込みを常駐させることになる。第 3 に、エージェントのカーネルモードも 30 秒ごとに値を読み直すが、戻さずに報告だけする (7b.1 節) ので、両側で扱いが揃う。そのかわり、0 にされたことを黙らせない。管理用 API はカーネルモードの server の今の値を返し (7a.11 節)、`server doctor` はカーネルで転送する公開中のルールがあれば FAILED とし (10.2a 節)、`wgft status` は Server 行を degraded とし (10.2b 節)、Web UI は今の値を示し (10.1 節)、`server check` は書ける場合も所見にする。戻す手順は、`sysctl -w net.ipv4.ip_forward=1` か server の起動し直しである。ただし書き込みが塞がれている場合は、起動時の書き込みも同じ原因で失敗するので、起動し直しでは直らない。`server doctor` の案内は再起動を勧めず、塞ぐ原因を除いてから `sysctl -w` で 1 にすることを述べる(2026-10-03)

conntrack の表の上限(`net.netfilter.nf_conntrack_max`)は `vpsd` が変えない。転送するフローは 1 本につき表の 1 件を使い、表が埋まるとカーネルはホスト全体の新規接続を落とす。上限はメモリの量から決まり、小さい VPS では 16384 のような値になる。`server check` は現在の件数と上限を表示し、上限が 65536 未満なら、上げる sysctl と `new_flow_rate` の設定を提示する。`new_flow_rate` と `per_source_rate` の drop は prerouting の優先度 -150 で行われ、その時点のフローはまだ表に登録されていないので、落としたフローは表を消費しない。
- `vpsd` が 0 を読んで 1 にするときは、状態ファイルの meta に 2 段の記録を残す(2026-10-03、所有者の決定)。撤去(10.3 節)のとき、運用者に「`vpsd` が変えたので戻す候補」か「元から 1 だった」かを具体的に示すためである。予定の記録は「この日時に `vpsd` が値 0 を読み、1 を書き始めた」という記録であり、書けたかどうかは述べない。確定の記録は「この日時に `vpsd` が 0 を 1 に書き換えた」という記録であり、管理用 API の `ip_forward_set_at` はこの記録だけを返す(7a.11 節)。手順は次のとおりである。
  1. 値を読む。1 なら何も書かず、記録も変えない。前の起動の予定の記録が残っていても消さない。前の起動が書いたかもしれない証拠だからである
  2. 値を読めなければ 1 を書き、どちらの記録も残さない。0 だったとは言えないためである。書けなければ、0 とは言わず、読めなかった誤りと書けなかった誤りを示す Finding を出す
  3. 0 なら、書く前に予定の記録を保存する。保存できなければ警告をログに出し、値は書く。記録は撤去の案内にだけ使い、転送には効かない。記録できないことで値を書かずにおくと、サーバのデータベースに書けない間は転送が戻らない。転送が落ちたままになることのほうが悪い(11b 節)
  4. 1 を書く。書けなければ、「0 のまま書けない」ことを示す起動時の Finding を出し、予定の記録を消す。消せなければ警告だけを出す。残った予定の記録について、撤去は今の値を添えて示す
  5. 書けたら、確定の記録の保存と予定の記録の削除を 1 つのトランザクションで行う。失敗すれば警告を出し、予定の記録が残る

  記録を 2 段にする理由は、1 段の記録ではどちらの順序でも、止まる時点によって誤った記録が残ることにある。書いた後に記録する形では、書いた直後に止まるか記録に失敗すると記録が欠け、撤去は `vpsd` が 1 にした値を「変えていない」と示す。2026-10-03 までの実装はこの形だった。書く前に記録する形では、書く前に止まるか、書けずに記録の取り消しにも失敗すると、撤去は変えていない値を「変えた」と示し、運用者に 0 へ戻すよう勧める。その間に別の仕組みが 1 にしていれば、その転送を止める。2 段の記録では、これらの場合に予定の記録だけが残り、撤去は「変えたかもしれない」と今の値を示して、判断を運用者に任せる。

  0 を読んで 1 を書き、手順が 5 まで進んだ場合に、どちらの記録も残らないのは、3 と 5 の両方が失敗したときだけである。この場合は起動時の Finding で、`vpsd` が値を 1 にしたことと、撤去がそれを知らないかもしれないことを示す。3 だけが失敗して 5 が成功した場合は、確定の記録が残るので Finding は出さず、3 の警告がログに残る。3 が失敗して値を書いた後、5 の前に止まった場合も記録は残らない。このときは 3 の警告がログに残るだけで、Finding は出ない。

運用者が sysctl を自分で管理していても、その管理も 1 にするのが普通なので衝突しない。値を触られたくない配置では 1 にしておけば `vpsd` は読むだけになる。この振る舞いで足りるため、設定するかを切り替えるフラグは持たない。
1 にすると VPS はルータとして振る舞える状態になる。wgft 以外の転送を止めるのは既存のファイアウォール(ufw、Docker、firewalld の既定の drop / reject)の役目で、`wgft` の forward チェーンは自分の DNAT 済みフローを accept するだけで他の転送を drop しない。ファイアウォールのない VPS では、VPS を経由するよう仕向けられたパケットが転送されうるが、公開 IP が 1 つの VPS では現実にはほぼ起きない。

conntrack の操作は「宣言状態に収束させる」1 手順だけを持つ。

1. `status` に DNAT フラグが立ち、orig 側の宛先が `10.200.0.0/24` の外で、かつ reply 側の送信元が `10.200.0.0/24` のエントリをすべて Dump する。外から入って DNAT されたフローだけが対象になり、`vpsd` 自身が wg0 へ張ったフロー(プロキシモードの中継、疎通確認)は最初から含まれない
2. 各エントリについて、現在有効なカーネルモードのルールのいずれかで、その proto と宛先ポートが DNAT され、エントリの reply 側の送信元(アドレスとポート)がそのルールの DNAT 先と一致し、かつ送信元が `source_deny` に含まれず `source_allow` を満たすかを判定する。DNAT 先を見るのは、ルールの `agent` を変えたとき旧エージェントへの既存フローを消すためである
3. 満たさないエントリを削除する

収束は nftables テーブルの差し替えの後に走らせる。先に走らせると、旧テーブルで許可されたフローが差し替えまでの間に入る。起動時の突き合わせも同じ順序である。
手作業で nftables を触られた場合も、この手順で不要なフローが拾える。
フロー数は多くないので、毎回全走査でよい。

契機は次の 3 つである。

- ルールテーブルまたは接続元制限への書き込みが 1 件でもあったとき(フィールドの種類を問わない)
- エージェントの削除
- `vpsd` の起動時(手作業で nftables を触られた後の復旧のため)

契機を変更の種類ごとに列挙しない。編集できるフィールドが増えるたびに漏れるためである。

起動時と `rule add` 時に次を検査し、問題があれば警告する。自動では書き換えない。

- `ip` `ip6` `inet` の全ファミリで forward フックの base chain を列挙し、`policy drop` があれば、そのチェーンに足す 2 行(`oifname "wg0" accept` と `iifname "wg0" ct state established,related accept`)を提示する。ufw の残骸が `ip filter FORWARD` にある場合もこれで拾う。この手作業は 1 回きりでポートに依存しない
- input フックの base chain で `ct state established` が accept されているかを確認し、されていなければ提示する。`vpsd` から wg0 経由で張る接続の返りが通るために必要である
- 他テーブルの nat prerouting チェーンに同じポートの DNAT があれば、そのルールの追加を拒否する。ポートが multiport や読めない無名 set、未知の式の形で判定できない規則は、拒否せずに Finding として警告する。黙って見逃すと、優先度で先に評価される wgft の DNAT(`dstnat - 1`)がそれと知らずに勝つため
- VPS 上で bind 中のポートとの衝突は 5.3 節のとおり拒否する

`vpsd` 自身が待ち受ける 2 つのポート(4 節の WireGuard の UDP とエージェント用 API の TCP)も、
起動時と `server check` で input フックの `policy drop` を検査し、塞がれていれば
`udp dport <port> accept` / `tcp dport <port> accept` を提示する(実機の Debian 13、input が
policy drop で SSH の TCP 22 しか accept していない構成で見つかった。改訂の記録参照)。
host の input firewall はデータプレーンのモードに関係しない層なので、ユーザー空間モード
(6.3 節)でも同じ検査を行う。管理用 API(既定 Unix ソケット。5 節)は対象から外す。
外部に公開しない設計であり、host の input を開ける提示を出す理由が無いためである。

### 6.2 プロキシモード

`vps_mode = proxy` のルールは、`vpsd` が Go の TCP リスナー(IPv4 だけで開く。7a.9 節)で受け、wg0 経由でエージェントの `10.200.0.x:listen_port`(エージェントが開いているリスナー)へ接続して中継する。
`proxy_protocol = true` なら接続先に PROXY protocol v2 ヘッダを先頭に送る。

公開ポートごとの accept ループが、受け付けた接続の Admission Policy と Resource Guard をこの順に同期して判定する。
予算の取得前に接続ごとの goroutine は作らず、判定中の公開側ソケットはポートごとに高々 1 個を保持する。
停止中のポートも数に含め、同じポートの古い accept ループが終了するまで新しいループを開始しない。
停止は判定中のソケットを閉じ、停止と、予算取得直前の確認・取得・引き渡しを同じ排他で順序付ける。
停止した接続がその後の予算取得で資源不足の拒否に数えられることも防ぐ。
引き渡し済みの接続は、その処理が終わるまで既存の予算を保持する。
複数ポートを止めるときは全ポートへ停止を要求してからループの終了を待つ。
同期したポリシー判定そのものは中断できないため、停止と設定適用の完了時間の上界は保証しない。
判定を待つ間の追加接続はカーネルの listen backlog で待ち、溢れると接続の遅延や失敗になりうる。
処理できた拒否は従来どおり RST で閉じる。
これは予算取得前の保持の制限であり、カーネルのソケットのメモリを含むプロセス全体のメモリ上界ではない。
既に引き渡されて接続中の処理について、Retire と接続元制限だけの変更では接続完了時のポリシー再判定を行わない既存の制約が残る。

プロキシモードのルールも、カーネルモードのルールと同じ Admission Policy のすべての段を受ける(7a.9 節)。段を評価する場所はモードで決まる。カーネルモードでは、`vpsd` が待ち受けを開けているポートの行を nftables が評価する(6.1 節)ので、レートと接続元ごとの同時フロー数で拒んだパケットはリスナーに届かない。この場合、中継に残るのは deny と allow による状態を持たない確認だけで、その拒否は drop カウンタに数えない。ユーザー空間モードでは、中継が Go の評価器(7a.9 節)を受け付け時に呼び、IR の `Order` の順(deny、allow、`per_source_rate`、接続元ごとの同時フロー数の上限、`new_flow_rate`、`packet_rate`)に判定し、拒んだ段の drop カウンタを数える。プロキシモードのルールは TCP なので、`packet_rate` の段はどちらのモードでも効かない(7a.9 節の「TCP の packet_rate」)。
中継はハーフクローズを保ち、片方向の EOF は `CloseWrite` で反対側に伝え、両方向が閉じたら両側を通常の `Close` で閉じて中継を終える。片方向が EOF 以外で終わったとき、つまり読み取りが RST などの誤りで失敗したときと書き込みが失敗したときは、ハーフクローズとして扱わず、すぐに両側を通常の `Close` で閉じて中継を終える。ハーフクローズとして扱うと、反対向きは黙ったままの相手を読み続けるので、相手が閉じるまで接続と同時フロー数の枠が残る。公開側のクライアントの RST で終わったとき、つまり公開側の接続の読み取りか書き込みが RST(`ECONNRESET`)で失敗したときだけは、エージェントへの接続を通常の `Close` ではなく RST で切る。切り方は後述の中継を閉じるときと同じで、公開側の接続は通常の `Close` で閉じる。エージェントへの接続を FIN で閉じると、エージェントの中継はハーフクローズとして扱うので、FIN を受けても閉じない宛先では、エージェント側の宛先への接続と同時フロー数の枠が宛先が閉じるまで残る。カーネルの TCP 同士の中継(カーネルモードのプロキシのルール)は、RST による誤りが公開側とエージェント側のどちらの接続のものかを区別できないので、どちらの場合もエージェントへの接続を RST で切る。誤りがエージェント側の接続のものなら、その接続は RST を受けて既に閉じた状態にあり、RST で切っても何も送らない。これは Linux のコードから導き、network namespace の Tcp OutRsts の計数器が増えないことでも確かめた。パケットのキャプチャでは確かめていない。EOF とハーフクローズ、後述の中継の側からの切断、エージェント側から届いた RST の扱いは変えない。この規則は同じ部品(`internal/netpipe`)を使う 6.3 節と 7 節の中継にも効く。ただし 7 節のエージェントの中継では、宛先への接続が実ソケットなので、トンネル側の RST で終わったときも宛先への接続を通常の `Close` で閉じる。通常の `Close` は、netstack の接続を閉じた時点で解放するとは限らない。送り残しのデータを持つ netstack の接続は、閉じた後もそのデータを持って残りうる(7 節の「送り残しを持って閉じた netstack の接続」)。
同時に中継する接続の数は、7 節の「同時フロー数の上限」の TCP の値(ルールごと、プロセス全体、接続元 IP ごと)で抑え、拒んだ接続は accept の直後に閉じる。ルールごとの上限と最低分は、プロセス全体の予算を共有するプールが判定する(7a.10 節)。カーネルモードでは、接続元 IP ごとの数だけは中継ではなく 6.1 節の `flows_tcp` で、カーネルモードのルールと合わせて数える。ユーザー空間モードでは、接続元 IP ごとの数を Go の評価器が、6.3 節の中継の TCP の接続と合わせて数え、上限で拒んだ接続を `src_flow` の drop に数える。どちらのモードでも、接続元 IP ごとの上限はルールごととプロセス全体の上限より先に判定する。
接続元制限、レート、同時フロー数の上限のどの拒否も、accept の直後、まだデータをやり取りしていない接続を `SetLinger(0)` の RST で即座に閉じ、通常の Close によるグレースフルクローズ(FIN、TIME_WAIT)にはしない(6.3 節、7 節と同じ考え方)。フラッドの間に不要な TIME_WAIT の TCP 状態を大量に残さず、その分のカーネル資源を保持し続けないためで、成立した中継の通常のクローズ(前段のハーフクローズ)は変えない。カーネルモードでは、レートと接続元ごとの同時フロー数で拒む接続は nftables がパケットを捨てるので、クライアントには RST ではなく時間切れとして見える(7a.9 節の許容差)。

進行中の中継を閉じる契機は次のとおり。conntrack の操作(6.1 節)は `vpsd` 自身のソケットには効かないので、別の部品として持つ。

- ルールの削除と `enabled = false`:リスナーと進行中の全中継を閉じる
- 実効宛先の変更:リスナーは残したまま、そのリスナーの進行中の全中継を閉じる
- 接続元制限の変更:条件を満たさなくなった接続元の中継を閉じる
- エージェントの削除:そのエージェント宛の全中継を閉じる

中継を閉じるときは、エージェントへの接続を RST で切る。カーネルモードの接続は実ソケットなので `SetLinger(0)` の後に閉じ、ユーザー空間モードの接続は netstack の接続なので `Abort` で切る。公開側の接続は通常の `Close` で閉じる。FIN で閉じると、エージェントの中継はそれをハーフクローズとして扱い、宛先へ FIN を送った後も宛先からの読み取りを続けるので、FIN を受けても閉じない宛先では、エージェント側の宛先への接続と同時フロー数の枠が宛先が閉じるまで残る。RST を受けたエージェントの中継は、前述の規則で両側を閉じて枠を返す。エージェントへの接続を先に切るのは、公開側を先に閉じると、中継がその読み取りの失敗を受けてエージェントへの接続を通常の `Close` で閉じ、RST の前に FIN が出ることがあるためである。

実効宛先は、ルールを割り当てたエージェントのトンネルのアドレスと、エージェント側の待ち受けポートの組である。ルールを別のエージェントへ移した場合と、エージェントのトンネルのアドレスが変わった場合に変わる。成立済みの接続は accept の時点の実効宛先へ張った上流の接続を持つので、宣言の値を書き換えても新しいエージェントへは向かない。7 節の収束の表の「実効宛先が違う:閉じてから開く。セッションは切れる」と同じ扱いであり、`vpsd` 側のリスナーを開き直さない点だけが異なる。開き直しの bind が失敗する余地を残さないためで、この点は 6.3 節の中継と同じである。所属ルール ID だけが変わった場合と、`proxy_protocol` だけが変わった場合は中継を閉じない。7 節の表が所属ルール ID の変更でセッションを残すと定めており、`proxy_protocol` のヘッダは接続の先頭で 1 回だけ送るものなので、成立済みの接続に後から付ける手段が無いためである。

公開ポートの accept が、リスナーを閉じた場合以外の理由で失敗したときは、リスナーを開いたまま後退して試し直し、失敗をリスナーごとに 1 分に 1 回までログに出す。失敗が続く間も、ルールの状態は変えず、ログだけで知らせる。ファイル記述子の枯渇のような失敗で accept をやめると、ソケットは bind されたまま新しい接続を受け付けない状態で残る。適用はそのポートを開いているものとして扱い、リスナーを開き直さないので、`vpsd` を再起動するまでそのポートの中継が戻らない。

このモードは `vpsd` 自身が待ち受けるので、既存ファイアウォールの input チェーンでそのポートが通る必要がある。
`rule add` 時に input フックの base chain に `policy drop` があれば、必要な行(`tcp dport <port> accept`)を提示する。
`server check` も、保存済みの全ルールのうち有効なプロキシモードのルールについて同じ検査を行う。
Transparent なルールは他テーブルの DNAT と forward を経由し input を通らないため対象にしない。

用途は接続元 IP を自宅側の Caddy に伝えたい HTTPS で、UDP には使わない。

### 6.3 ユーザー空間モード

`WGFT_MODE=userspace` は、VPS 側にも root、カーネル WireGuard、nftables を要求しない動作モードである。`vpsd` は自宅側と同じ wireguard-go と gVisor の netstack でトンネルを持ち、公開ポートを自分のソケットで受けて netstack 越しにエージェントへ中継する。root の取れない VPS、OpenVZ 系や LXC ベースの VPS、compose で全部を管理したい人のための入口で、カーネルモードを置き換えるものではない。モードは `vpsd` 全体で 1 つであり、ルール単位で混ぜない(11a 節の記録と照合)。

構成は次のとおり。

- サーバ側トンネル:wireguard-go の `device` と、エージェントと共通の netstack の TUN(`internal/nettun`、7 節)で、`listen_port` を開き `10.200.0.1` を持つ。サーバ鍵は SQLite の同じ鍵を使う。ピアの追加と削除は `IpcSet`(`public_key`、`allowed_ip`、`remove`)で行う。エンドポイントは原則として指定せず、エージェントのハンドシェイクで学習する。例外は鍵の置き換えで、新しいピアには 5.2 節の引き継ぎのエンドポイントを `endpoint` で与える。ピアの状態(エンドポイント、最終ハンドシェイク、転送量)は `IpcGet` から読み、5.2 節の窃取検知と 10.1 節の表示に使う。wgctrl は使わない。UDP バインドの選び方は 7 節と同じ理由で Windows だけ変える。`vpsd` 自体は Linux でしか動かないが、この実装(`internal/dataplane/userspace/utun`)は CI の `windows-test` の単体テストと、cross-build の `go vet`(windows/amd64、windows/arm64)の対象であるため、7 節の選択にそろえる
- 中継:全ルールがプロキシモード相当になる。UDP と TCP は自宅側の中継部品(7 節の `relay.Manager`)の向きを反転して使い、ホストのソケットを IPv4 だけで開いて(`udp4`、`tcp4`。7a.9 節)listen し、netstack の dial でエージェントの `10.200.0.x:listen_port` へつなぐ。エージェントから見た送信元は `10.200.0.1` の一時ポートになり、カーネルモードの masquerade と同じ見え方である。PROXY protocol 付きの TCP は 6.2 節の中継をそのまま使う。`vps_mode` の kernel と proxy の区別はこのモードでは意味を持たず、PROXY protocol を付けるかどうかだけが残る
- 宛先への試し接続:`vpsd` は、TCP の待ち受けを開くときに宛先へ試し接続しない。7 節の試し接続(`checkTarget`)はエージェントが LAN の宛先を確かめるためのもので、`vpsd` の中継の宛先はエージェントのトンネルのアドレスである。エージェントがそのポートを開くのは、`vpsd` が待ち受けを開いた後に配る全体状態を受け取ってからなので、待ち受けを開いた時点の試し接続は届かないのが普通である。起動の直後は、すでにそのポートを開いているエージェントにも届かない。起動した `vpsd` はピアにエンドポイントを与えず、エージェントのハンドシェイクが新しいプロセスに届くまでトンネルが通らないためである(後述の性質の違いの項)。カーネルモードのエージェントは、公開していないポートへの新しい接続を入口の守り(7b.1 節)で黙って捨てるので、試し接続は 1 件ごとに期限まで待ち、適用と起動を遅らせる。宛先に届くかどうかは、エージェントが自分の試し接続の結果をルールの状態として報告する(5.2 節)
- 接続元制限とレート制限:nftables が無いので、Admission Policy の IR から作る Go の評価器(`internal/policy/goengine`、7a.9 節)で判定する。deny、allow、接続元ごとの新規フロー上限(`per_source_rate`。表は最後に触れてから 1 分で期限切れ、上限 65535 件で最も長く触れていないものから落とす)、接続元ごとの同時フロー数の上限(7 節)、ルール全体の新規フロー上限(`new_flow_rate`)、UDP のデータグラム上限(`packet_rate`)の順で、6.1 節と同じ評価順である。ある段で拒んだフローは、後の段のトークンと同時フロー数の枠を使わない。新しいフロー(TCP の接続、UDP の新しいセッションの最初のデータグラム)はすべての段で判定し、成立済みの UDP セッションのデータグラムは `packet_rate` だけで判定する。したがって deny と allow で拒む送信元のデータグラムは `packet_rate` のトークンを使わない。`proxy_protocol` を付ける TCP の中継(6.2 節)の新しい接続も、同じ評価器の同じ段で判定する。`packet_rate` は UDP にだけ効き、TCP には効かない。3 つのレートとも nftables の `limit rate over` と同じく burst 5 のトークンバケットで、ラボで両モードの通過数と drop の累計が一致することを確かめた(2026-09-17、`lab/rates.sh`)
- 拒否のカウンタ:Go で数え、カーネルモードと同じ累積の経路(SQLite への加算)に流す。UI と CLI の表示は変わらない
- 進行中の中継を閉じる契機は 6.2 節と同じ(ルールの削除と無効化、接続元制限の変更、エージェントの削除)。conntrack 収束の代わりに、これが全ルールに効く。閉じるときにエージェントへの接続を RST で切ることも 6.2 節と同じで、netstack 越しに張った接続なので `Abort` を使う。公開側のクライアントの RST で終わった中継のエージェントへの接続を RST で切ることも、6.2 節と同じである。UDP の新しいセッションは、エージェントへの dial の後にセッションの表へ入る。読み取りのループが新しい送信元のデータグラムを読んでセッションの表を引いてから、表へ登録するまでの間に、実効宛先の変更か接続元制限の変更でその listener の中継を閉じ、その判定がこの送信元を閉じるものであれば、セッションを登録せずに最初のデータグラムを捨て、取った枠を返す。この間は所属ルールと実効宛先を読む前から始まる。実効宛先の変更は送信元によらずすべてのセッションを閉じるので、表を引いた後、実効宛先を読む前に実効宛先が変われば、ループが新しい実効宛先を読んで dial した場合でも最初のデータグラムを捨てる。次のデータグラムは新しいセッションとして今の宣言で扱う
- 公開ポートの TCP の accept と UDP の読み取りが、リスナーを閉じた場合以外の理由で失敗したときの扱いは 6.2 節の accept と同じで、リスナーを開いたまま後退して試し直し、失敗をリスナーごとに 1 分に 1 回までログに出す。失敗が続く間も、ルールの状態は変えない。この中継の公開側はホストの実ソケットなので、TCP ではファイル記述子の枯渇のような失敗が起こりうる。UDP では、管理者がソケットを破棄したとき(`ss -K`)に読み取りが 1 回 `ECONNABORTED` で失敗し、ソケットは bind したポートを持ったまま残る。試し直さずにやめると、リスナーは bind されたまま新しい接続もデータグラムも受け付けない状態で残り、適用はそのポートを開いているものとして扱って開き直さない
- 起動時と `server check` の検査:input チェーンが `policy drop` の場合の「`tcp/udp dport <port> accept`(範囲は `<lo>-<hi>`)を足す」提示を、`vpsd` 自身の 2 つのポート(6.1 節)と、有効な全ルールの listen port(範囲を含む)について行う。`vps_mode` の区別に意味を持たないため、`kernel`/`proxy` のどちらの値でも対象にする。forward、`ip_forward`、他テーブルの DNAT、bind 中ポートの `/proc` の検査は行わない(bind の失敗で分かる)
- ソケットのバッファ:`vpsd` はトンネルを立てた直後に自分の WireGuard の UDP ソケットを測り、7 節の「ソケットのバッファの条件」に届かなければ警告の 1 行をログに出す。公開側の UDP ソケットには開くたびに固定の送信バッファを要求し、切り詰められたら同じ形の警告を出す(7 節の「公開側のソケットの送信バッファ」)。`server check` は、判断の材料として 3 つの値を示す。今の `net.core.rmem_max` と `net.core.wmem_max`、`CAP_NET_ADMIN` を持たないプロセスが得る値、条件の値である。`server check` は条件の判定をせず、終了コードも変えない。理由は 7 節の「`server check` が示す材料」の項に書く
- `server teardown` は `--purge` 以外にすることが無く、`server nft` は「ユーザー空間モードでは nftables を使わない」と出す

カーネルモードとの性質の違いは次のとおりで、文書では入れ方の分岐(systemd ならカーネル、Docker ならユーザー空間)の下にこの違いを先に書く。

- `vpsd` を止めると転送も止まる。カーネルモードは wg0 とテーブルが残るので、更新や再起動の間も通る
- `vpsd` を再起動すると、転送はエージェントの次の WireGuard のハンドシェイクの後に戻り、それまで数十秒かかる。起動した `vpsd` はピアにエンドポイントを与えないので(上の構成のサーバ側トンネルの項)、自分からはハンドシェイクを始めない。v1.1.3 でも同じであることを、ラボで確かめた。ハンドシェイクの前に公開ポートへ届いた TCP の接続は、`vpsd` がすぐ accept してエージェントへ dial する。dial の期限の 5 秒の内にハンドシェイクが成立しなければ、dial が失敗して接続は切れ、クライアントは繋ぎ直す必要がある。期限の内に成立した場合に中継されるかどうかは未確認である
- TCP は `vpsd` が終端して 2 本になる。エージェントが落ちているとき、カーネルモードは SYN が返らないが、ユーザー空間モードは接続してから切れる
- フラッド耐性はユーザー空間のプロキシ一般(Traefik など)と同じ弱さを持つ。フローを開いて保持するだけの攻撃に対しては、7 節の「同時フロー数の上限」で `vpsd` が保持するフローの数を抑える。1 つのルールへのフラッドが他のルールの新しいフローまで止めることは、ルール 1 本の上限とルールごとの最低分(7a.10 節)が防ぐ。宛先からの応答を読むバッファは、プロセス全体で 64 個までの枠で借り、公開側のソケットの送信バッファが満杯の応答は待たずに捨てる(7 節の「応答のバッファの枠」と「公開側への応答の送信」)。`vpsd` では接続元 IP ごとの上限も効く。PROXY protocol 付きの TCP(6.2 節の中継)も同じ上限で数える。公開側の accept はホストの実ソケット(`net.Listen`)で行うため、上限を超えた接続を拒否しても netstack の TIME_WAIT(7 節)は残らない。実ソケットでも拒否は `SetLinger(0)` の RST で閉じ、フラッドの間にエフェメラルポートを浪費しない。スループットの目安は、ラボ(2 vCPU の VM、veth 越し)で TCP 1 本の 100 MB 転送がカーネルモード約 2.3 Gbit/s、ユーザー空間モード約 1.3 Gbit/s であり(2026-09-17)、想定用途の数 Mbps から数十 Mbps に対して余裕がある
- 公開ポートで `vpsd` の Go のコードがインターネットに直接さらされる(11 節)
- ユーザー空間モードは、パケットの水準の隔離を持たない。netstack の出力は、ルールとプロトコルで分けない FIFO のキュー 1 つを通る(7 節の「netstack の出力」の項)。過負荷のときは、他のルールの通信にも少量のパケットの欠落が起こることがあり、欠落は負荷が終われば止まる。ユーザー空間モードは、カーネルモードと同等の QoS と DoS の隔離を保証しない。wireguard-go の送信と受信のキューに滞留するパケットはピアごとに構造の上限を持ち、`vpsd` ではその値にピアの数を掛けたものになる。1 つのピアの受信のキューが満杯になると、同じ address family の他のピアの読み取りも待つ(7 節の滞留のメモリの上限の段落)
- ユーザー空間モードの netstack の TCP は、経路の短い障害の後の回復がカーネルの TCP より遅い。障害が終わっても、送り手は障害の間に失った segment を再送のタイマーが切れるたびに少しずつしか送り直さないので、転送の完了は障害の長さを大きく超えて遅れる。障害の時点で送信中のデータの多い接続ほど長く止まる。データは失われない。回復を待つ間、接続は送り直すデータを送信のバッファに持ち続ける。boost の枠を持っていれば、その枠も、送信のキューが floor の確かめを通るまでは回収されない(7 節の「TCP のバッファで保証しないこと」)。原因は固定版の gVisor の TCP の送り手にある。障害の後の再送が確認されると、RACK(送った時刻に基づく損失の検出、RFC 8985)は障害の前に送った残りの segment を損失と判定する。一方で、送り手が送信中と見なす量の計算はこの判定を差し引かない。このため送り手は輻輳の窓が送信中の segment で埋まっていると見て、次の再送のタイマーが切れるまで送らない。対象は、netstack が TCP の接続の端になる区間で、netstack が送る向きである。`vpsd` とエージェントがどちらもユーザー空間モードの組では 2 つの netstack の間が対象になる。`vpsd` がカーネルモードでエージェントがユーザー空間モードの組では、`vpsd` が DNAT でエージェントの netstack へ転送するので、エージェントの netstack と公開側のクライアントのカーネルの TCP の間が対象になる。`vpsd` がユーザー空間モードでエージェントがカーネルモードの組では、`vpsd` の netstack と LAN の宛先のカーネルの TCP の間が対象になる。ユーザー空間モードだけで動く Windows と macOS のエージェントも対象である。公開側のクライアントと `vpsd` の公開側のソケットの間や、エージェントの LAN 側のソケットと宛先の間のように、両端がカーネルの TCP である区間は対象にならない。ユーザー空間モードは、カーネルモードと同等の損失の回復を保証しない(改訂の記録 2026-10-03)
- ユーザー空間モードは、7 節の上界の式に数えた保持点が最悪になった場合のメモリの量を、ホストの要件として持つ。既定の上限で、エージェントが 1 つ、TCP の宛先が 1 つなら、`vpsd` のホストに約 5.9 GiB のメモリが要る。上限を下げても、要るメモリは約 2.9 GiB より小さくならない(7 節の「プロセス全体のメモリの上界」の段落)
- ユーザー空間モードは、動作条件として 7 節の「ソケットのバッファの条件」を要する。カーネルモードの WireGuard はカーネルの中で動くので、カーネルモードにこの条件は無い。付属の systemd の unit は `CAP_NET_ADMIN` を与えるので、VM や専用のホストでは、その `vpsd` のソケットは sysctl の値によらず条件を満たしうる。LXC ベースの VPS とコンテナでは、unit が与える `CAP_NET_ADMIN` はコンテナの user namespace の中に限られ、FORCE は通らない(6.1 節)。条件はコンテナのホストの sysctl で決まる。付属の compose ファイルの `vpsd` は、ホストの値を上げて条件を満たした(7 節の「コンテナでのバッファの条件」)。LXC のコンテナの中と LXC ベースの VPS の `vpsd` が条件を満たせるかどうかは未確認であり、利用者がホストの sysctl を変えられないこともある。root の取れない VPS で unit を使わずに動かす `vpsd` は、`CAP_NET_ADMIN` を持たない。どの配置でも、決め手は `vpsd` が自分のソケットを測った値とその警告の行である
- ピアを足す前に届いた握手は捨てられ、エージェントの再送は 5 秒後になる。接続時の握手は、5.2 節の順(stream の接続時に公開鍵を宣言してからピアを足す)で吸収する

稼働中の `agent rotate-key` では、新しい鍵の握手がピアを足す前に届いて捨てられうる。`vpsd` は 5.2 節の引き継ぎで新しいピアに古いピアのエンドポイントを与え、自分の側から握手を始める。この扱いはカーネルモードと共通である。ユーザー空間モードのエージェントは `rotate-key` でトンネルを作り直して送信元のポートが変わるので、引き継ぎは効かず、エージェントの再送を待つ(5.2 節)

エージェントとプロトコルは変えない。サーバ鍵と証明書は SQLite にあるので、同じ SQLite で別のモードに上げれば、エージェントは再登録なしに再接続する。1024 未満のポートは、Docker の bridge ネットワーク(`ports:` で公開)ではコンテナの名前空間で非特権の bind が許されるので使える(443 で確認済み)。`network_mode: host` ではホストの名前空間の制限が効き、非 root では bind できない。systemd で非 root なら `AmbientCapabilities=CAP_NET_BIND_SERVICE` で足す。コンテナに `NET_ADMIN` と host ネットワークを付けてカーネルモードを動かすことには対応しない。
